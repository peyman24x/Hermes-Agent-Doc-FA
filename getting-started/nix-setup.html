راه‌اندازی Nix و NixOS

⚠️ پلتفرم Tier 2

‏Nix و NixOS پلتفرم‌های Tier 2 هستند. فلیک و ماژول NixOS ی مستندشده اینجا فقط روی مبنای best-effort نگهداری می‌شوند. کامیت‌های main ممکن است هر لحظه این پکیج‌ها را بشکنند.

برای یک setup پشتیبانی‌شده از یکی از مسیرهای عادی نصب استفاده کنید — یا Docker یا یک محیط FHS.

‏Hermes Agent یک Nix flake، یک ماژول NixOS و یک ماژول Home Manager ارسال می‌کند.

سطحبرای چه کسیچه می‌گیرید
‏nix run / ‏nix profile installهر کاربر Nix ‏(macOS، ‏Linux)باینری از-پیش-ساخته با همهٔ وابستگی‌ها — بعد گردش‌کار عادی CLI
ماژول Home Managerیک ایجنت برای یک نفر، روی هر توزیعی یا macOSپیکربندی تعریفی و یک سرویس کاربری، بدون root
ماژول NixOS ‏(native)استقرارهای سرور NixOSپیکربندی تعریفی، سرویس systemd ی سخت‌گیرانه، secrets های مدیریت‌شده
ماژول NixOS ‏(کانتینر)ایجنت‌هایی که خوداصلاحی لازم دارندهمهٔ موارد بالا به‌علاوهٔ یک کانتینر Ubuntu ی پایدار که ایجنت می‌تواند در آن apt/pip/npm install کند
📌 فرقش با نصب استاندارد

نصب‌کنندهٔ curl | bash خودش Python، ‏Node و وابستگی‌ها را مدیریت می‌کند. Nix flake همهٔ آن را جایگزین می‌کند — هر وابستگی پایتونی یک derivation ی Nix است که توسط uv2nix ساخته می‌شود و ابزارهای runtime ‏(Node.js، ‏git، ‏ripgrep، ‏ffmpeg) داخل PATH باینری پیچیده شده‌اند. هیچ pip ی در runtime، هیچ فعال‌سازی venv، هیچ npm install وجود ندارد.

برای کاربران غیر-NixOS این فقط مرحلهٔ نصب را عوض می‌کند. هر چیز بعد از آن ‏(hermes setup، hermes gateway install، ویرایش config) دقیقاً مثل نصب استاندارد کار می‌کند.

برای کاربران ماژول NixOS کل چرخهٔ حیات متفاوت است: پیکربندی در configuration.nix زندگی می‌کند، secrets از sops-nix/agenix می‌روند، سرویس یک unit ی systemd است و فرمان‌های config ی CLI بلاک می‌شوند. hermes را همان‌طور مدیریت می‌کنید که هر سرویس NixOS دیگری را مدیریت می‌کنید.

۱ پیش‌نیازها و شروع سریع

پیش‌نیازها

  • Nix با flakes فعال — ‏Determinate Nix توصیه می‌شود ‏(flakes را پیش‌فرض فعال می‌کند)
  • کلیدهای API برای سرویس‌هایی که می‌خواهید استفاده کنید ‏(حداقل: یک کلید OpenRouter یا Anthropic)

شروع سریع ‏(هر کاربر Nix)

بدون نیاز به clone. ‏Nix همه‌چیز را fetch، build و اجرا می‌کند:

# Run the desktop app
nix run github:NousResearch/hermes-agent#desktop

# Or install persistently
nix profile install github:NousResearch/hermes-agent#desktop

# run the tui
nix run github:NousResearch/hermes-agent -- setup
nix run github:NousResearch/hermes-agent -- --tui

# or install it in your profile
nix profile install github:NousResearch/hermes-agent
hermes setup
hermes --tui

بعد از nix profile install مقدار hermes و hermes-agent و hermes-acp روی PATH شما هستند. از اینجا گردش‌کار با نصب استاندارد یکی است — ‏hermes setup انتخاب ارائه‌دهنده را قدم‌به‌قدم انجام می‌دهد، ‏hermes gateway install یک سرویس کاربری launchd ‏(macOS) یا systemd راه می‌اندازد و config در ‏~/.hermes/ زندگی می‌کند.

⚠️ پلتفرم‌های پیام‌رسانی ‏(دیسکورد، تلگرام، اسلک)

پکیج default همهٔ کتابخانه‌هایی را دارد که hermes-agent ممکن است لازم داشته باشد. اگر نوع کوچک‌تری می‌خواهید سایر خروجی‌های فلیک را ببینید. پکیج default حدود ‎۷۰۰MB‎ به closure اضافه می‌کند. اگر فقط پلتفرم‌های پیام‌رسانی می‌خواهید مقدار #messaging فقط ~۳۳MB اضافه می‌کند.

اجرای از یک clone محلی 
git clone https://github.com/NousResearch/hermes-agent.git
cd hermes-agent
nix develop
hermes setup

۲ ماژول NixOS

فلیک مقدار ‏nixosModules.default را export می‌کند — یک ماژول سرویس کامل NixOS که ساخت کاربر، دایرکتوری‌ها، تولید config، ‏secrets، ‏اسناد و چرخهٔ حیات سرویس را تعریفی مدیریت می‌کند.

📌

این ماژول NixOS می‌خواهد. هرمس ایجنتی برای یک نفر است. اگر ایجنت برای یک نفر می‌خواهید و نه یک سرویس سیستمی، از ماژول Home Manager استفاده کنید. آن ماژول روی NixOS و هر سیستم دیگری که Home Manager پشتیبانی می‌کند اجرا می‌شود.

افزودن Flake Input

# /etc/nixos/flake.nix (or your system flake)
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    hermes-agent.url = "github:NousResearch/hermes-agent";
  };

  outputs = { nixpkgs, hermes-agent, ... }: {
    nixosConfigurations.your-host = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        hermes-agent.nixosModules.default
        ./configuration.nix
      ];
    };
  };
}

پیکربندی مینیمال

# configuration.nix
{ config, ... }: {
  services.hermes-agent = {
    enable = true;
    settings.model.default = "anthropic/claude-sonnet-4";
    environmentFiles = [ config.sops.secrets."hermes-env".path ];
    addToSystemPackages = true;
  };
}

همین. ‏nixos-rebuild switch کاربر hermes را می‌سازد، config.yaml تولید، secrets را سیم‌کشی و گیت‌وی را شروع می‌کند — سرویسی بلندمدت که ایجنت را به پلتفرم‌های پیام‌رسانی ‏(تلگرام، ‏دیسکورد و…) وصل و پیام‌های ورودی را گوش می‌دهد.

⚠️ Secrets الزامی‌اند

خط environmentFiles بالا فرض می‌کند sops-nix یا agenix را پیکربندی کرده‌اید. فایل باید دست‌کم یک کلید ارائه‌دهندهٔ LLM داشته باشد ‏(مثل OPENROUTER_API_KEY=sk-or-...). setup کامل را در بخش مدیریت Secrets ببینید. هنوز مدیر secrets ندارید؟ می‌توانید موقتاً از یک فایل ساده استفاده کنید — فقط مطمئن شوید world-readable نباشد:

echo "OPENROUTER_API_KEY=sk-or-your-key" | sudo install -m 0600 -o hermes /dev/stdin /var/lib/hermes/env
services.hermes-agent.environmentFiles = [ "/var/lib/hermes/env" ];
💡 addToSystemPackages

ست کردن addToSystemPackages = true دو کار می‌کند: CLI ی hermes را روی PATH سیستمی می‌گذارد و HERMES_HOME را system-wide ست می‌کند تا CLI ی تعاملی وضعیت ‏(نشست‌ها، مهارت‌ها، cron) را با سرویس گیت‌وی شریک کند. بدون آن اجرای hermes در شل شما یک دایرکتوری ~/.hermes/ جدا می‌سازد.

CLI آگاه-از-کانتینر

ℹ️

وقتی container.enable = true و addToSystemPackages = true باشد، هر فرمان hermes روی host خودکار وارد کانتینرِ مدیریت‌شده مسیریابی می‌شود. یعنی نشست تعاملی CLI تان داخل همان محیطی اجرا می‌شود که سرویس گیت‌وی — با دسترسی به همهٔ پکیج‌ها و ابزارهای نصب‌شده در کانتینر.

  • مسیریابی شفاف است: hermes chat، ‏hermes sessions list، ‏hermes --version و… همگی زیر کاپوت exec به داخل کانتینر می‌شوند
  • همهٔ فلگ‌های CLI همان‌طور forward می‌شوند
  • اگر کانتینر اجرا نباشد CLI چند لحظه دوباره تلاش می‌کند ‏(۵ ثانیه با spinner برای مصرف تعاملی، ‏۱۰ ثانیه بی‌صدا برای اسکریپت‌ها) سپس با خطای واضح شکست می‌خورد — بدون fallback ی بی‌صدا
  • برای توسعه‌دهندگان روی codebase ی hermes مقدار HERMES_DEV=1 را ست کنید تا مسیریابی کانتینر دور زده و checkout ی محلی مستقیماً اجرا شود

container.hostUsers را ست کنید تا symlink ای از ~/.hermes به دایرکتوری وضعیت سرویس ساخته شود تا CLI ی host و کانتینر نشست‌ها، config و حافظه‌ها را شریک کنند:

services.hermes-agent = {
  container.enable = true;
  container.hostUsers = [ "your-username" ];
  addToSystemPackages = true;
};

کاربران فهرست‌شده در hostUsers خودکار به گروه hermes برای دسترسی مجوز فایل اضافه می‌شوند.

کاربران Podman: سرویس NixOS کانتینر را به‌عنوان root اجرا می‌کند. کاربران Docker از طریق socket ی گروه docker دسترسی دارند ولی کانتینرهای rootful ی Podman به sudo نیاز دارند. sudo بی‌رمز برای runtime کانتینرتان اعطا کنید:

security.sudo.extraRules = [{
  users = [ "your-username" ];
  commands = [{
    command = "/run/current-system/sw/bin/podman";
    options = [ "NOPASSWD" ];
  }];
}];

CLI وقتی sudo لازم است خودآشکار و شفاف استفاده می‌کند. بدون این باید دستی ‏sudo hermes chat اجرا کنید.

تأیید اینکه کار می‌کند

بعد از nixos-rebuild switch بررسی کنید سرویس در حال اجراست:

۳ پیکربندی

تنظیمات تعریفی

گزینهٔ settings یک attrset ی دلخواه می‌پذیرد که به‌صورت config.yaml رندر می‌شود. ادغام عمیق بین تعاریف متعدد ماژول را پشتیبانی می‌کند ‏(از طریق lib.recursiveUpdate)، پس می‌توانید config را بین فایل‌ها تقسیم کنید:

# base.nix
services.hermes-agent.settings = {
  model.default = "anthropic/claude-sonnet-4";
  toolsets = [ "all" ];
  terminal = { backend = "local"; timeout = 180; };
};

# personality.nix
services.hermes-agent.settings = {
  display = { compact = false; personality = "kawaii"; };
  memory = { memory_enabled = true; user_profile_enabled = true; };
};

هر دو موقع ارزیابی deep-merge می‌شوند. کلیدهای اعلام‌شده-Nix همیشه بر کلیدهای موجود در config.yaml ی روی دیسک برنده‌اند اما کلیدهای اضافه‌شده-توسط-کاربر که Nix لمس نمی‌کند حفظ می‌شوند. یعنی اگر ایجنت یا یک ویرایش دستی کلیدهایی مثل skills.disabled یا streaming.enabled اضافه کند آنها از nixos-rebuild switch جان سالم به در می‌برند.

📌 نام‌گذاری مدل

‏settings.model.default از شناسهٔ مدلی استفاده می‌کند که ارائه‌دهنده‌تان انتظار دارد. با OpenRouter ‏(پیش‌فرض) شبیه anthropic/claude-sonnet-4 یا google/gemini-3-flash است. ارائه‌دهنده را مستقیم استفاده می‌کنید؟ ‏settings.model.base_url را روی API شان ست و ID های native ی خودشان را به کار ببرید ‏(مثل claude-sonnet-4-20250514). بدون base_url هرمس به OpenRouter برمی‌گردد.

💡 کشف کلیدهای config ی موجود

‏nix build .#configKeys && cat result را اجرا کنید تا هر کلید برگِ config استخراج‌شده از DEFAULT_CONFIG ی پایتون را ببینید. می‌توانید config.yaml ی فعلی‌تان را داخل attrset ی settings paste کنید — ساختار یک‌به-یک نگاشت می‌شود.

مثال کامل: همهٔ تنظیمات رایج سفارشی‌سازی‌شده 
{ config, ... }: {
  services.hermes-agent = {
    enable = true;
    container.enable = true;

    # ── Model ──────────────────────────────────────────────────────────
    settings = {
      model = {
        base_url = "https://openrouter.ai/api/v1";
        default = "anthropic/claude-opus-4.6";
      };
      toolsets = [ "all" ];
      max_turns = 100;
      terminal = { backend = "local"; cwd = "."; timeout = 180; };
      compression = {
        enabled = true;
        threshold = 0.85;
        summary_model = "google/gemini-3-flash-preview";
      };
      memory = { memory_enabled = true; user_profile_enabled = true; };
      display = { compact = false; personality = "kawaii"; };
      agent = { max_turns = 60; verbose = false; };
    };

    # ── Secrets ────────────────────────────────────────────────────────
    environmentFiles = [ config.sops.secrets."hermes-env".path ];

    # ── Documents ──────────────────────────────────────────────────────
    # USER.md is memory, so it goes to HERMES_HOME. Workspace files use
    # `documents`, and that option needs an explicit `workingDirectory`.
    hermesHomeFiles = {
      "memories/USER.md" = ./documents/USER.md;
    };

    # ── MCP Servers ────────────────────────────────────────────────────
    mcpServers.filesystem = {
      command = "npx";
      args = [ "-y" "@modelcontextprotocol/server-filesystem" "/data/workspace" ];
    };

    # ── Container options ──────────────────────────────────────────────
    container = {
      image = "ubuntu:24.04";
      backend = "docker";
      hostUsers = [ "your-username" ];
      extraVolumes = [ "/home/user/projects:/projects:rw" ];
      extraOptions = [ "--gpus" "all" ];
    };

    # ── Service tuning ─────────────────────────────────────────────────
    addToSystemPackages = true;
    extraArgs = [ "--verbose" ];
    restart = "always";
    restartSec = 5;
  };
}

۴ مدیریت Secrets

🚫 هرگز کلیدهای API داخل settings یا environment نگذارید

مقادیر داخل عبارات Nix به /nix/store می‌روند که world-readable است. همیشه از environmentFiles همراه یک مدیر secrets استفاده کنید.

هر ‏environment ‏(متغیرهای غیر-secret) و environmentFiles ‏(فایل‌های secret) موقع فعال‌سازی ‏(nixos-rebuild switch) داخل ‏$HERMES_HOME/.env ادغام می‌شوند. هرمس این فایل را در هر startup می‌خواند، پس تغییرات با systemctl restart hermes-agent مؤثر می‌شوند — بدون بازسازی کانتینر.

sops-nix

{
  sops = {
    defaultSopsFile = ./secrets/hermes.yaml;
    age.keyFile = "/home/user/.config/sops/age/keys.txt";
    secrets."hermes-env" = { format = "yaml"; };
  };

  services.hermes-agent.environmentFiles = [
    config.sops.secrets."hermes-env".path
  ];
}

فایل secrets جفت‌های کلید-مقدار دارد:

# secrets/hermes.yaml (encrypted with sops)
hermes-env: |
    OPENROUTER_API_KEY=sk-or-...
    TELEGRAM_BOT_TOKEN=123456:ABC...
    ANTHROPIC_API_KEY=sk-ant-...

agenix

{
  age.secrets.hermes-env.file = ./secrets/hermes-env.age;

  services.hermes-agent.environmentFiles = [
    config.age.secrets.hermes-env.path
  ];
}

Seed کردن OAuth / Auth

برای پلتفرم‌های نیازمند OAuth ‏(مثل دیسکورد) از authFile برای seed کردن credential ها در اولین استقرار استفاده کنید:

{
  services.hermes-agent = {
    authFile = config.sops.secrets."hermes/auth.json".path;
    # authFileForceOverwrite = true;  # overwrite on every activation
  };
}

فایل فقط وقتی کپی می‌شود که auth.json از قبل نباشد ‏(مگر authFileForceOverwrite = true). refresh های runtime ی توکن OAuth در دایرکتوری وضعیت نوشته و بین rebuild ها حفظ می‌شوند.

۵ اسناد

هرمس فایل‌ها را از دو دایرکتوری می‌خواند؛ پس دو گزینه وجود دارد. برای هر فایل از گزینهٔ دایرکتوری مربوطه استفاده کنید.

‏documents داخل دایرکتوری کاری ایجنت نصب می‌کند که همان workingDirectory است. ایجنت زمینهٔ پروژه‌اش را از آن workspace می‌خواند:

{
  services.hermes-agent = {
    # documents needs this option. Read the note below.
    workingDirectory = "/var/lib/hermes/workspace";
    documents = {
      "AGENTS.md" = ./documents/AGENTS.md;   # path reference, copied from Nix store
      "notes/oncall.md" = "Page #infra before restarting anything.";
    };
  };
}
⚠️ documents به workingDirectory ی صریح نیاز دارد

ماژول تا وقتی workingDirectory را ست نکنید مقدار documents را نمی‌پذیرد. پیش‌فرض این گزینه در هر ماژول متفاوت است: روی Home Manager دایرکتوری خانهٔ شماست و روی NixOS مقدار ${stateDir}/workspace. پس پیش‌فرضِ unset فایل‌ها را در دایرکتوری‌ای می‌گذارد که انتخابش نکرده‌اید. انتخاب مسیری معادل پیش‌فرض هم صحیح است و قانون را ارضا می‌کند.

‏hermesHomeFiles داخل HERMES_HOME نصب می‌کند. هرمس فایل هویت و فایل‌های حافظهٔ ایجنت را از آن دایرکتوری می‌خواند. ‏SOUL.md و memories/ فقط از آنجا کار می‌کنند. یک SOUL.md داخل documents یک فایل workspace می‌سازد؛ هرمس آن را به‌عنوان هویت load نمی‌کند:

{
  services.hermes-agent.hermesHomeFiles = {
    "SOUL.md" = "You are a helpful AI assistant.";
    "memories/USER.md" = ./documents/USER.md;
  };
}

هر مقدار رشته یا مسیر است. کلید در هر دو گزینه می‌تواند زیردایرکتوری داشته باشد و ماژول دایرکتوری‌های والد را می‌سازد. هر فعال‌سازی فایل‌ها را دوباره نصب می‌کند.

‏hermesHomeFiles به workingDirectory نیاز ندارد چون ماژول مالک دایرکتوری HERMES_HOME است. بیشتر کاربران hermesHomeFiles را می‌خواهند.

۶ سرورهای MCP

گزینهٔ mcpServers سرورهای MCP ‏(Model Context Protocol) را تعریفی پیکربندی می‌کند. هر سرور یا transport ی stdio ‏(فرمان محلی) یا HTTP ‏(URL ی راه‌دور) دارد.

Transport ی Stdio ‏(سرورهای محلی)

{
  services.hermes-agent.mcpServers = {
    filesystem = {
      command = "npx";
      args = [ "-y" "@modelcontextprotocol/server-filesystem" "/data/workspace" ];
    };
    github = {
      command = "npx";
      args = [ "-y" "@modelcontextprotocol/server-github" ];
      env.GITHUB_PERSONAL_ACCESS_TOKEN = "\${GITHUB_TOKEN}"; # resolved from .env
    };
  };
}
💡

متغیرهای محیطی در مقادیر env هنگام runtime از ‏$HERMES_HOME/.env حل می‌شوند. secrets را با environmentFiles تزریق کنید — هرگز توکن مستقیم داخل config ی Nix نگذارید.

Transport ی HTTP ‏(سرورهای راه‌دور)

{
  services.hermes-agent.mcpServers.remote-api = {
    url = "https://mcp.example.com/v1/mcp";
    headers.Authorization = "Bearer \${MCP_REMOTE_API_KEY}";
    timeout = 180;
  };
}

HTTP با OAuth

برای سرورهای OAuth 2.1 دار مقدار auth = "oauth" را ست کنید. هرمس جریان کامل PKCE را پیاده می‌کند — کشف metadata، ثبت داینامیک کلاینت، مبادلهٔ توکن و refresh خودکار.

{
  services.hermes-agent.mcpServers.my-oauth-server = {
    url = "https://mcp.example.com/mcp";
    auth = "oauth";
  };
}

توکن‌ها در ‏$HERMES_HOME/mcp-tokens/<server-name>.json ذخیره و بین ری‌استارت‌ها و rebuild ها می‌مانند.

مجوزدهی اولیه OAuth روی سرورهای headless

اولین مجوزدهی OAuth جریان رضایت مرورگری می‌خواهد. در استقرار headless هرمس به‌جای باز کردن مرورگر URL مجوز را به stdout/لاگ چاپ می‌کند.

گزینهٔ A: bootstrap تعاملی — جریان را یک بار با docker exec ‏(کانتینر) یا sudo -u hermes ‏(native) اجرا کنید:

# Container mode
docker exec -it hermes-agent \
  hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth

# Native mode
sudo -u hermes HERMES_HOME=/var/lib/hermes/.hermes \
  hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth

کانتینر از --network=host استفاده می‌کند پس شنوندهٔ callback ی OAuth روی 127.0.0.1 از مرورگر host قابل‌رسید است.

گزینهٔ B: پیش-seed کردن توکن‌ها — جریان را روی یک workstation تمام و توکن‌ها را کپی کنید:

hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth
scp ~/.hermes/mcp-tokens/my-oauth-server{,.client}.json \
    server:/var/lib/hermes/.hermes/mcp-tokens/
# Ensure: chown hermes:hermes, chmod 0600

Sampling ‏(درخواست‌های LLM آغاز-شده-توسط-سرور)

بعضی سرورهای MCP می‌توانند completion های LLM را از ایجنت بخواهند:

{
  services.hermes-agent.mcpServers.analysis = {
    command = "npx";
    args = [ "-y" "analysis-server" ];
    sampling = {
      enabled = true;
      model = "google/gemini-3-flash";
      max_tokens_cap = 4096;
      timeout = 30;
      max_rpm = 10;
    };
  };
}

اجرای بک‌اند Desktop / Dashboard

‏gateway.enable گیت‌وی پیام‌رسانی را برای تلگرام، دیسکورد، اسلک و سایر پلتفرم‌ها اجرا می‌کند. ‏Hermes Desktop و داشبورد وب به یک پروسهٔ متفاوت وصل می‌شوند که hermes serve یا hermes dashboard است. backend.mode آن پروسه را همراه گیت‌وی اجرا می‌کند:

{
  services.hermes-agent = {
    enable = true;
    gateway.enable = true;      # messaging platforms
    backend.mode = "dashboard"; # + the browser dashboard on 127.0.0.1:9119
    backend.port = 9119;
  };
}

‏serve بدون رابط کاربری اجرا می‌شود و socket های /api/ws و /api/pty ی که Hermes Desktop به آنها وصل می‌شود را می‌دهد و اپ وب را build نمی‌کند. dashboard همهٔ آن به‌علاوهٔ پنل مدیریتی مرورگری را می‌دهد. هر دو پروسه یک HERMES_HOME با گیت‌وی استفاده می‌کنند، پس نشست‌ها، مهارت‌ها، حافظه و cron job ها برای همه یکی است. backend.mode روی ماژول NixOS همین‌طور کار می‌کند ولی نه در حالت کانتینر.

آدرس پیش‌فرض 127.0.0.1 است. هر آدرس دیگر گیت احراز هویت داشبورد را روشن می‌کند. سرور همچنین هر درخواستی با هدر Host ی متفاوت از آدرسی که bind شده رد می‌کند — دفاعی در برابر DNS rebinding. به نام یا آدرسی bind کنید که کلاینت‌تان استفاده می‌کند.

ℹ️

با فعال بودن حالت کانتینر، هرمس داخل یک کانتینر Ubuntu ی پایدار اجرا می‌شود که باینری ساخته-Nix به‌صورت read-only از host در آن bind-mount شده:

/var/lib/hermes/                    ──►  /data/          (rw)
  ├── current-package -> /nix/store/...    (symlink, updated each rebuild)
  ├── .gc-root -> /nix/store/...           (prevents nix-collect-garbage)
  ├── .container-identity                  (sha256 hash, triggers recreation)
  ├── .hermes/                             (HERMES_HOME)

باینری ساخته-Nix داخل کانتینر Ubuntu کار می‌کند چون /nix/store ی bind-mount شده مفسر خودش و همهٔ وابستگی‌هایش را می‌آورد، پس اتکایی به کتابخانه‌های سیستمی کانتینر نیست. entrypoint ی کانتینر از طریق symlink ی current-package حل می‌شود: ‏/data/current-package/bin/hermes gateway run --replace. روی nixos-rebuild switch فقط symlink به‌روز می‌شود — کانتینر همچنان در حال اجراست.

⚠️ از دست رفتن لایهٔ قابل‌نوشتن

وقتی hash ی هویت عوض شود ‏(ارتقای image، ‏volume های جدید، گزینه‌های جدید کانتینر) کانتینر نابود و از pull تازهٔ container.image بازسازی می‌شود. هر apt install یا pip install یا npm install داخل لایهٔ قابل‌نوشتن از دست می‌رود. وضعیت در /data و /home/hermes حفظ می‌شود ‏(اینها bind mount اند).

اگر ایجنت به پکیج‌های مشخصی تکیه دارد آنها را داخل یک image سفارشی بپزید ‏(container.image = "my-registry/hermes-base:latest") یا نصبشان را در SOUL.md ایجنت اسکریپت کنید.

محافظت GC Root

اسکریپت preStart یک GC root در ${stateDir}/.gc-root می‌سازد که به پکیج فعلی hermes اشاره می‌کند. این مانع حذف باینری درحال-اجرا توسط nix-collect-garbage می‌شود. اگر GC root به هر دلیلی بشکند ری‌استارت سرویس دوباره می‌سازدش.

۱۰ پلاگین‌ها

ماژول NixOS نصب تعریفی پلاگین‌ها را پشتیبانی می‌کند — بدون نیاز به hermes plugins install ی امری.

پلاگین‌های دایرکتوری ‏(extraPlugins)

برای پلاگین‌هایی که صرفاً یک درخت سورس با plugin.yaml + __init__.py هستند ‏(مثل ‏hermes-lcm):

services.hermes-agent.extraPlugins = [
  (pkgs.fetchFromGitHub {
    owner = "stephenschoettler";
    repo = "hermes-lcm";
    rev = "v0.7.0";
    hash = "sha256-...";
  })
];

پلاگین‌ها موقع فعال‌سازی به‌صورت symlink داخل $HERMES_HOME/plugins/ می‌روند. هرمس با اسکن عادی دایرکتوری کشفشان می‌کند. حذف پلاگین از فهرست و اجرای nixos-rebuild switch symlink را حذف می‌کند.

پلاگین‌های Entry-Point ‏(extraPythonPackages)

برای پلاگین‌های pip-packaged که از طریق [project.entry-points."hermes_agent.plugins"] ثبت می‌شوند ‏(مثل ‏rtk-hermes):

services.hermes-agent.extraPythonPackages = [
  (pkgs.python312Packages.buildPythonPackage {
    pname = "rtk-hermes";
    version = "1.0.0";
    src = pkgs.fetchFromGitHub {
      owner = "ogallotti";
      repo = "rtk-hermes";
      rev = "v1.0.0";
      hash = "sha256-...";
    };
    format = "pyproject";
    build-system = [ pkgs.python312Packages.setuptools ];
  })
];

site-packages ی پکیج به PYTHONPATH در wrapper ی hermes اضافه می‌شود. importlib.metadata نقطهٔ ورود را در شروع نشست آشکار می‌کند.

گروه‌های وابستگی اختیاری ‏(extraDependencyGroups)

برای extras های اختیاری اعلام‌شده در pyproject.toml ی hermes-agent از extraDependencyGroups استفاده کنید تا در زمان build داخل venv مهرشده بگنجند. برای هر extra خارج از مجموعهٔ پیش‌فرض [all] الزامی است — روی Nix نصب runtime داخل store ی فقط-خواندنی ممکن نیست.

# Enable Discord, Telegram, Slack
services.hermes-agent.extraDependencyGroups = [ "messaging" ];
# Enable a memory provider
services.hermes-agent = {
  extraDependencyGroups = [ "hindsight" ];
  settings.memory.provider = "hindsight";
};

‏programs.hermes-agent ‏(فقط Home Manager)

‏Home Manager «این اپ را برای من نصب کن» را از «این دیمون را اجرا کن» جدا می‌کند. services.hermes-agent وضعیت، پیکربندی و دیمون‌ها را نگه می‌دارد. programs.hermes-agent آنچه استفاده می‌کنید را نصب و hermesHome و آدرس backend را از services می‌خواند.

گزینهنوعپیش‌فرضتوضیح
enableboolfalseCLI ی hermes به home.packages اضافه و HERMES_HOME برای شل‌هایتان export می‌شود
packagepackageservices.hermes-agent.packageپکیج نصبی. پیش‌فرض extraPythonPackages و extraDependencyGroups را از services اعمال می‌کند تا هر دو یک build باشند.

desktop.packagepackagepackage.hermesDesktopپکیج دسکتاپ. پیش‌فرض از package پیروی می‌کند تا اپ و سرویس‌ها یک runtime ی هرمس اجرا کنند.
 
programs.hermes-agent = {
  enable = true;
  desktop.enable = true;
};

services.hermes-agent = {
  enable = true;
  backend.mode = "serve";
  backend.sessionTokenFile = config.sops.secrets."hermes/desktop-token".path;
};

launcher خودش HERMES_HOME را حمل می‌کند. منوی دسکتاپ هیچ shell profile نمی‌خواند، پس مقداری که programs.hermes-agent.enable با home.sessionVariables export می‌کند فقط به شل تعاملی می‌رسد. بدون آن مقدار در launcher، اپ ~/.hermes را باز می‌کند در حالی که سرویس‌ها از hermesHome استفاده می‌کنند و نه نشستی می‌بینید و نه کلیدی.

با backend.sessionTokenFile اپ به backend ی سرویس وصل می‌شود به‌جای راه انداختن یکی برای خودش. هر دو سمت فایل را موقع شروع می‌خوانند، پس توکن وارد هیچ مسیر Nix store نمی‌شود. بدون این گزینه هر سمت backend خودش را اجرا می‌کند.

‏services.hermes-agent.installPackage توسط این تفکیک حذف شد. پیکربندی‌ای که هنوز ستش کند خطایی نام‌برندهٔ جایگزین می‌گیرد.
