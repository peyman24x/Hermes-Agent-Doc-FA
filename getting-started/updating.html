به‌روزرسانی و حذف

۱ به‌روزرسانی

با یک فرمان به آخرین نسخه به‌روزرسانی کنید:

bash
hermes update

این فرمان آخرین کد را از main می‌گیرد، وابستگی‌ها را به‌روز می‌کند و از شما می‌پرسد گزینه‌های جدیدی که از آخرین به‌روزرسانی‌تان اضافه شده‌اند را پیکربندی کنید.

💡 نکته

hermes update گزینه‌های پیکربندی جدید را خودکار تشخیص می‌دهد و پیشنهاد افزودنشان را می‌دهد. اگر آن پیام را رد کردید، می‌توانید بعداً دستی hermes config check را برای دیدن گزینه‌های مفقود و سپس hermes config migrate را برای افزودن تعاملی آن‌ها اجرا کنید.

هنگام به‌روزرسانی چه اتفاقی می‌افتد؟

وقتی hermes update را اجرا می‌کنید، این مراحل رخ می‌دهد:

  1. اسنپ‌شاتِ پیش از به‌روزرسانی — به‌طور پیش‌فرض یک اسنپ‌شات سبکِ وضعیت ذخیره می‌شود (شامل داده‌های جفت‌سازی، کارهای کرون، config.yaml، .env، auth.json و سایر فایل‌های وضعیتی که در زمان اجرا تغییر می‌کنند؛ فایل‌های تکیِ بالای ۱ گیگابایت رد می‌شوند تا یک دیتابیس نشست‌های بزرگ، به‌روزرسانی را کُند نکند). چون تعویض کد و ری‌استارت گیت‌وی به همهٔ پروفایل‌ها دست می‌زند، همین اسنپ‌شات برای هر پروفایلِ روی نصب گرفته می‌شود — هر کدام در پوشهٔ state-snapshots/ خودش — و تور ایمنیِ کرونِ پس از به‌روزرسانی هر پروفایل را با اسنپ‌شات خودش بررسی می‌کند. با updates.pre_update_backup کنترل می‌شود (quick پیش‌فرض، full برای زیپ کاملِ HERMES_HOME، off برای غیرفعال‌کردن). از مسیر بازیابیِ اسنپ‌شاتِ توضیح‌داده‌شده در «اسنپ‌شات‌ها و بازگشت» قابل بازیابی است. اسنپ‌شات‌های سریع برای بازیابیِ از دست‌رفت فایل‌اند، نه بیمهٔ بازگشتِ کد — برای بازگشتِ منسجم به یک نقطهٔ زمانی از --backup (حالت full) استفاده کنید.
  2. Git pull — آخرین کد را از شاخهٔ main می‌گیرد و ساب‌ماژول‌ها را به‌روز می‌کند
  3. اعتبارسنجی نحوی پس از pull + بازگشت خودکار — بعد از pull، هرمس نُه فایلِ حیاتی‌ای را که هر فراخوانی hermes هنگام راه‌اندازی ایمپورت می‌کند کامپایل می‌کند. اگر هر کدام تجزیه نشود (مثلاً یک نشانگر تعارض merge یتیم، یا فایلی که تصادفی بریده شده)، هرمس git reset --hard <pre-pull-sha> را اجرا می‌کند تا نصب برگردد و شل شما قابل بوت بماند. بعد از رسیدن اصلاح بالادستی، hermes update را یک بار دیگر اجرا کنید.
  4. نصب وابستگی‌ها — uv pip install -e ".[all]" را برای گرفتن وابستگی‌های جدید یا تغییریافته اجرا می‌کند
  5. مهاجرت پیکربندی — گزینه‌های پیکربندی جدیدِ افزوده‌شده از نسخهٔ شما را تشخیص می‌دهد و از شما می‌خواهد تنظیمشان کنید
  6. ری‌استارت خودکار گیت‌وی — گیت‌وی‌های در حال اجرا پس از اتمام به‌روزرسانی نوسازی می‌شوند تا کد جدید فوراً اثر بگیرد. گیت‌وی‌های مدیریت‌شده با سرویس (systemd در لینوکس، launchd در مک) از طریق مدیر سرویس ری‌استارت می‌شوند. گیت‌وی‌های دستی وقتی خودکار دوباره اجرا می‌شوند که هرمس بتواند PID در حال اجرا را به یک پروفایل نگاشت کند.

۲ به‌روزرسانی نسبت به شاخهٔ غیرپیش‌فرض: --branch

به‌طور پیش‌فرض hermes update از origin/main پیروی می‌کند. با --branch <name> نسبت به شاخهٔ دیگری به‌روزرسانی کنید — مفید برای کانال‌های QA، شاخه‌های ویژگی یا تست نسخهٔ کاندید:

bash
hermes update --branch release-candidate
hermes update --check --branch experimental   # فقط پیش‌نمایش میزان عقب‌ماندگی

اگر چک‌اوت محلی‌تان روی شاخهٔ دیگری است، هرمس هر کارِ کامیت‌نشده را خودکار stash می‌کند، HEAD را به شاخهٔ هدف می‌برد و سپس pull می‌کند. شاخه‌هایی که به‌صورت محلی وجود ندارند به‌طور خودکار از origin/<name> ردیابی می‌شوند (git checkout -B <name> origin/<name>). شاخه‌هایی که هیچ‌جا وجود ندارند با تمیزی شکست می‌خورند — تغییرات stash‌شدهٔ شما پیش از خروج بازیابی می‌شود تا هرگز در وضعیت عجیبی رها نشوید. منطقِ همگام‌سازی fork-upstream که مخصوص main است روی شاخه‌های غیر-main به‌طور خودکار رد می‌شود.

چک‌اوتِ پارک‌شده روی شاخهٔ ویژگی

اگر چک‌اوت سورس روی یک شاخهٔ ویژگی رها شده باشد (به‌واسطهٔ ابزارها، یک آزمایش worktree یا checkout دستی)، hermes update هر وقت درخت کاری تمیز باشد به‌طور خودکار آن را به هدفِ به‌روزرسانی برمی‌گرداند:

  • شاخه کاملاً merge شده (هر کامیت از قبل در origin/main موجود است — git cherry چیزی merge‌نشده گزارش نمی‌کند): به‌روزرسانی این را می‌گوید — Checkout was parked on '<branch>' (fully merged) — switched back to main — و پس از آن روی main می‌ماند.
  • شاخه کامیت‌های merge‌نشده دارد ولی درخت تمیز است: به‌روزرسانی باز هم به main سوئیچ می‌کند تا به‌روزرسانی بتواند پیش برود — همین است که فراخوان‌های غیرتعاملی (دکمهٔ به‌روزرسانی دسکتاپ، /update گیت‌وی، کرون) بدان تکیه می‌کنند، چون راهی برای حل یک skip ندارند. کامیت‌های شما دست‌نخورده می‌مانند: git checkout هرگز کارِ کامیت‌شده را دور نمی‌ریزد، و به‌روزرسانی یک اعلان بلند با نام شاخه و تعداد کامیت‌ها، به‌همراه فرمان git checkout <branch> برای برداشتنِ دوبارهٔ کار چاپ می‌کند.

اگر عمداً شاخهٔ سفارشی اجرا می‌کنید (وصله‌های محلیِ نگه‌داشته‌شده روی main)، updates.parked_branch_strategy: update_in_place را در config.yaml تنظیم کنید. آن‌گاه به‌روزرسانی origin/main را داخل شاخهٔ شما merge می‌کند به‌جای اینکه از آن خارج شود — چک‌اوت هرگز جابه‌جا نمی‌شود، کامیت‌های شما زنده می‌مانند و کدِ در حال اجرا جلو می‌رود. در صورت امکان fast-forward؛ در واگرایی یک merge واقعی پشت یک تگ ایمنیِ pre-update-<stamp>، و در تعارض با توقف تمیز (هیچ‌چیز تغییر نمی‌کند). hermes update --switch-branch برای یک اجرا دوباره به مسیر سوئیچ برمی‌گرداند — مفید روی شاخهٔ ویژگیِ عمیقی که نباید کامیت‌های mergeِ ناشی از به‌روزرسانی انباشته کند.

وقتی شاخهٔ پارک‌شده تغییرات کامیت‌نشده دارد (درخت کثیف)، هرمس به آن دست نمی‌زند. به‌روزرسانی کد با هشدار بلندی که نام شاخه، میزان عقب‌ماندگی از origin/main و فرمان‌های دقیقِ حل را می‌گوید SKIPPED علامت می‌خورد — به‌جای اینکه وانمود کند به‌روزرسانی موفق بوده. خط اتمام همیشه شاخه و HEAD واقعی را نشان می‌دهد (✓ Update complete! [main @ 30fcf9580]) تا انحراف در یک نگاه دیده شود. updates.auto_switch_parked_branch: false را در config.yaml تنظیم کنید تا سوئیچ خودکار کاملاً غیرفعال شود (هشدار skip همچنان صادر می‌شود).

۳ تغییرات محلی در به‌روزرسانی‌های غیرتعاملی

وقتی hermes update را در ترمینال اجرا می‌کنید، هرمس تغییرات کامیت‌نشدهٔ درخت سورس را stash می‌کند، pull می‌زند و بعد می‌پرسد که آیا بازیابی شوند — دقیقاً مثل همیشه. برای به‌روزرسانی‌های تعاملی هیچ‌چیز عوض نمی‌شود.

وقتی به‌روزرسانی بدون ترمینال اجرا می‌شود — از دکمهٔ «Update» اپ دسکتاپ/چت یا یک به‌روزرسانیِ trigger‌شده توسط گیت‌وی — پیامی برای پاسخ‌دادن وجود ندارد. تنظیم updates.non_interactive_local_changes تصمیم می‌گیرد با تغییرات stash‌شدهٔ شما چه شود:

yaml — ~/.hermes/config.yaml
updates:
  non_interactive_local_changes: stash   # پیش‌فرض: نگه‌داشتن + بازیابی خودکار
  # non_interactive_local_changes: discard  # دورریختن ویرایش‌های محلی سورس
  • stash (پیش‌فرض) — stash خودکار، pull و سپس بازیابی خودکار تغییرات شما روی کدِ به‌روزرسانی‌شده. هیچ‌چیز از دست نمی‌رود؛ اگر بازیابی به تعارض بخورد، در یک git stash برای بازیابی دستی نگه داشته می‌شوند.
  • discard — stash خودکار و سپس انداختن stash پس از pull، تا به‌روزرسانی همیشه روی درختی تمیز فرود بیاید. فقط روی ماشین‌هایی استفاده کنید که هرگز نمی‌خواهید ویرایش محلیِ سورس هرمس نگه دارید. با stash-drop انجام می‌شود (نه git reset --hard + git clean -fd)، پس مسیرهای ignore‌شده مثل node_modules، venv و خروجی‌های بیلد هرگز دست نمی‌خورند.

در اپ دسکتاپ این تنظیم در Settings ← Advanced ← In-App Update Local Changes است.

به‌روزرسانی‌های دسکتاپ هرگز خودکار بازیابی نمی‌کنند. به‌روزرسانِ دسکتاپ hermes update --keep-stash را اجرا می‌کند: ویرایش‌های محلی سورس همچنان stash می‌شوند تا به‌روزرسانی پیش برود، اما پس از آن دوباره اعمال نمی‌شوند — در git stash پارک می‌مانند و لاگ به‌روزرسانی، فرمان دقیق git stash apply <ref> برای برگرداندن‌شان را چاپ می‌کند. این مانع می‌شود ویرایش‌های محلی به‌طور خاموش سوار به‌روزرسانی‌های دسکتاپ شوند و نصبِ تازه‌به‌روز‌شده را بشکنند. (اگر non_interactive_local_changes: discard را انتخاب کرده‌اید، همان برنده است.) برای بازیابی دستیِ تغییرات پارک‌شده:

bash
cd ~/.hermes/hermes-agent   # یا ریشهٔ نصب خودتان
git stash list --format='%gd %H %s'   # یافتن مدخل hermes-update-autostash
git stash apply stash@{0}

می‌توانید --keep-stash را به hermes update ترمینالی هم بدهید اگر همین رفتارِ هرگز-بازیابی‌نکن را به‌صورت تعاملی می‌خواهید.

۴ فقط پیش‌نمایش: hermes update --check

می‌خواهید قبل از pull بدانید به‌روزرسانی‌ای هست؟ hermes update --check را اجرا کنید — کامیت‌ها را fetch و با origin/main مقایسه می‌کند. هیچ فایلی تغییر نمی‌کند و هیچ گیت‌وی‌ای ری‌استارت نمی‌شود. در اسکریپت‌ها و کارهای کرونی که به «آیا به‌روزرسانی هست» گره خورده‌اند مفید است.

۵ پیش‌نمایش ناوگان: hermes update --plan

قبل از به‌روزرسانی ماشینی که چند پروفایل یا سرویس اجرا می‌کند، hermes update --plan نقشهٔ کامل به‌روزرسانی را بدون تغییرِ هیچ‌چیز چاپ می‌کند: نوع نصب (چک‌اوت git، ایمیج داکر، مدیریت‌شده با Nix/apt)، هر سرویس هرمسِ در حال اجرا در همهٔ پروفایل‌ها به‌همراه ناظرش (systemd، launchd، دستی) و نسخهٔ کدی که واقعاً سرویس می‌دهد، و سازوکار ری‌استارتی که هر کدام دریافت خواهند کرد. روی نصب‌های مبتنی بر ایمیج یا مدیر-پکیج، نقشه گزارش می‌دهد که نصب در جا به‌روزرسانی‌شدنی نیست و فرمان به‌روزرسانی درست را نام می‌برد. فقط-خواندنی و روی ناوگانِ زنده امن است.

همین فهرست در رسیدِ هر به‌روزرسانی واقعی هم جاسازی شده (~/.hermes/logs/update_receipts/)، تا بعد از یک به‌روزرسانی بتوانید آن‌چه به‌روزرسان دیده را با آن‌چه انجام داد مقایسه کنید.

۶ رسیدهای به‌روزرسانی و بررسی نسخهٔ ناوگان

هر اجرای hermes update رسیدی ماشین‌خوان در ~/.hermes/logs/update_receipts/ می‌نویسد (۲۰ تای آخر نگه داشته می‌شوند و latest.json همیشه به جدیدترین اشاره می‌کند): نقشهٔ ناوگانِ پیش از به‌روزرسانی، هر گامِ برداشته‌شده، هر چیزِ ردشده و چرایی‌اش، نتیجهٔ ری‌استارت گیت‌وی، و ماتریس نسخهٔ نهایی ناوگان. پس از مرحلهٔ ری‌استارت، به‌روزرسان کدِ در حال اجرای هر گیت‌ویِ زنده را با چک‌اوتِ تازه‌به‌روز‌شده مقایسه می‌کند و یک ماتریس به‌ازای-پروفایل چاپ می‌کند — گیت‌ویی که هنوز کدِ پیش از به‌روزرسانی سرویس می‌کند با فرمان دقیقِ ری‌استارت به‌طور بلند گزارش می‌شود، و به‌روزرسانی با کد غیرصفر خارج می‌شود تا اتوماسیون هرگز ناوگانِ چندنسخه‌ای را سالم تلقی نکند. هر دو --plan و بررسی ناوگان وقتی در دسترس باشد مستقیماً از طریق سوکت کنترل محلیِ هر گیت‌وی (gateway.sock در پوشهٔ دادهٔ پروفایل، یک named pipe در ویندوز) می‌پرسند، پس اطلاعات نسخه و ناظر از خود گیت‌وی می‌آید؛ گیت‌وی‌های نسخه‌های قدیمی‌تر همچنان از راه فایل‌های وضعیتشان کشف می‌شوند.

۷ پشتیبان کامل پیش از به‌روزرسانی: --backup

برای پروفایل‌های ارزشمند (گیت‌وی‌های عملیاتی، نصب‌های تیمیِ مشترک) می‌توانید پشتیبان کاملِ پیش از pull از HERMES_HOME را فعال کنید (پیکربندی، احراز هویت، نشست‌ها، مهارت‌ها، جفت‌سازی):

bash
hermes update --backup

یا آن را برای همهٔ اجراها پیش‌فرض کنید:

yaml — ~/.hermes/config.yaml
updates:
  pre_update_backup: full

updates.pre_update_backup یک تنظیم واحد با سه حالت است: quick (پیش‌فرض — همان اسنپ‌شات سبک وضعیت که بالاتر توضیح داده شد)، full (اسنپ‌شات سریع به‌علاوهٔ زیپ کامل HERMES_HOME؛ روی homeهای بزرگ می‌تواند چند دقیقه اضافه کند) و off (بدون هیچ پشتیبانِ پیش از به‌روزرسانی — --no-backup همین کار را برای یک اجرای واحد می‌کند). مقادیر بولی قدیمی هنوز کار می‌کنند: true یعنی full و false یعنی off.

💡 به ماشین جدید می‌روید؟

پشتیبان‌های به‌روزرسانی از یک به‌روزرسانیِ درجا محافظت می‌کنند. اگر کل راه‌اندازی‌تان را به سخت‌افزار دیگری منتقل می‌کنید، به‌جایش از hermes backup + hermes import استفاده کنید — به «صادرات هرمس به ماشین دیگر» و «hermes backup در برابر hermes profile export» مراجعه کنید.

۸ ویندوز: یک hermes.exe دیگر در حال اجراست

در ویندوز، hermes update اگر ببیند پروسهٔ دیگری از hermes.exe فایل اجراییِ نقطهٔ ورود venv را باز نگه داشته — معمولاً بک‌اندِ spawn‌شدهٔ Hermes Desktop، یک REPL بازِ hermes در ترمینال دیگر، یا یک گیت‌وی در حال اجرا — از اجرا سر باز می‌زند:

خروجی ترمینال
$ hermes update
✗ Another hermes.exe is running:
    PID 12345  hermes.exe

  Updating now would fail to overwrite ...\venv\Scripts\hermes.exe because
  Windows blocks REPLACE on a running executable.

  Close Hermes Desktop, exit any open `hermes` REPLs, and
  stop the gateway (`hermes gateway stop`) before retrying.
  Override with `hermes update --force` if you've already
  confirmed those processes will not write to the venv.

پروسه‌های فهرست‌شده را ببندید و دوباره اجرا کنید. اگر مطمئنید پروسهٔ هم‌زمان مزاحمتی نمی‌کند (کم‌پیش — معمولاً فقط وقتی مفید است که یک shim آنتی‌ویروس اشتباه شناسایی کرده باشد)، --force را برای ردکردن این بررسی بدهید. در آن صورت به‌روزرسان همچنان تغییرنام .exe را با تأخیر نمایی retry می‌کند و روی قفلهای لجباز، جایگزینی را برای ری‌بوت بعدی از طریق MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT) زمان‌بندی می‌کند تا به‌روزرسانی بتواند کامل شود.

یک محافظ دوم و جداگانه از دست‌زدن به venv وقتی هر پروسه‌ای از مفسر پایتونِ آن در حال اجراست خودداری می‌کند (بک‌اند اپ دسکتاپ، یک گیت‌وی، یک REPL پایتون). آن پروسه‌ها فایل‌های پسوند نیتیو (.pyd) را قفل نگه می‌دارند و یک همگام‌سازی وابستگی که وسط راه با خطای access-denied بمیرد، نصب را بین دو نسخه رها می‌کند. این محافظ با --force دورزدنی نیست؛ اگر مطمئنید دارنده‌های تشخیص‌داده‌شده مثبت کاذب‌اند، از hermes update --force-venv صریح استفاده کنید.

بازسازی venv ویندوز تراکنشی است

وقتی نصب‌کنندهٔ ویندوز باید یک venv موجود را بازسازی کند، اول پوشهٔ قدیمی را به نام یکتای venv.stale.* منتقل می‌کند، سپس جایگزین را می‌سازد و تأیید می‌کند. درخت قدیمی فقط بعد از اتمام نصب وابستگی‌ها و موفقیتِ ایمپورت‌های پایه در درخت جدید حذف می‌شود — تا آن لحظه منبعِ بازگشت است (ثبت‌شده در venv.pending-backup).

اگر انتقال کامل نشود، نصب‌کننده می‌ایستد و venv زنده را دست‌نخورده می‌گذارد. اگر uv شکست بخورد یا بدون ساختن مفسر موفقیت را گزارش کند، هر جایگزینِ ناقص به venv.failed.* منتقل و venv قبلی بازیابی می‌شود. این باعث می‌شود بررسی‌های سلامت و مسدودکننده پس از یک نصبِ ناموفق قابل استفاده بمانند.

ممکن است یک پوشهٔ venv.stale.* یا venv.failed.* وقتی باقی بماند که پروسهٔ دیگری هنوز دستگیرهٔ فایلی را در اختیار داشته باشد. هرمس دسکتاپ، گیت‌وی‌ها و پروسه‌های پایتونیِ استفاده‌کننده از نصب را ببندید، سپس نصب/به‌روزرسانی را دوباره امتحان کنید؛ پوشه‌های پارک‌شده بعد از یک بازسازی موفق به‌صورت در حد توان پاک‌سازی می‌شوند.

۹ اعتبارسنجی توصیه‌شده پس از به‌روزرسانی

hermes update مسیر اصلی به‌روزرسانی را مدیریت می‌کند، اما یک اعتبارسنجی سریع تأیید می‌کند که همه‌چیز تمیز فرود آمده:

  1. git status --short — اگر درخت به‌طور غیرمنتظره کثیف است، قبل از ادامه بررسی کنید
  2. hermes doctor — پیکربندی، وابستگی‌ها و سلامت سرویس را بررسی می‌کند
  3. hermes --version — تأیید کنید نسخه طبق انتظار بالا رفته
  4. اگر از گیت‌وی استفاده می‌کنید: hermes gateway status
  5. اگر doctor مشکلات npm audit گزارش کرد: npm audit fix را در پوشهٔ علامت‌خورده اجرا کنید
⚠️ درخت کاریِ کثیف بعد از به‌روزرسانی

اگر git status --short بعد از hermes update تغییرات غیرمنتظره‌ای نشان داد، متوقف شوید و قبل از ادامه بررسی‌شان کنید. این معمولاً یعنی تغییرات محلی روی کدِ به‌روزرسانی‌شده دوباره اعمال شده‌اند، یا یک مرحلهٔ وابستگی، فایل‌های قفل (lockfile) را نوسازی کرده است.

۱۰ اگر ترمینال وسط به‌روزرسانی قطع شد

hermes update از خودش در برابر از دست رفتن تصادفی ترمینال محافظت می‌کند:

  • به‌روزرسانی SIGHUP را نادیده می‌گیرد، پس بستن نشست SSH یا پنجرهٔ ترمینال دیگر آن را وسط نصب نمی‌کشد. پروسه‌های فرزندِ pip و git هم این محافظت را به ارث می‌برند، پس محیط پایتون نمی‌تواند به‌واسطهٔ یک اتصالِ رهاشده نیمه‌نصب باقی بماند.
  • همهٔ خروجی حین اجرای به‌روزرسانی به ~/.hermes/logs/update.log هم آینه می‌شود. اگر ترمینالتان غیب شد، دوباره وصل شوید و لاگ را بررسی کنید تا ببینید به‌روزرسانی تمام شده یا نه و ری‌استارت گیت‌وی موفق بوده یا نه:
    bash
    tail -f ~/.hermes/logs/update.log
  • Ctrl-C (SIGINT) و خاموشی سیستم (SIGTERM) همچنان پاسخ داده می‌شوند — آن‌ها لغوهای عمدی‌اند، نه تصادفی.

دیگر لازم نیست hermes update را در screen یا tmux بپیچید تا از افت ترمینال جان سالم به در ببرد.

۱۱ بررسی نسخهٔ فعلی

bash
hermes --version

آن را با آخرین انتشار در صفحهٔ releases گیت‌هاب مقایسه کنید.

۱۲ به‌روزرسانی از پلتفرم‌های پیام‌رسانی

می‌توانید مستقیم از تلگرام، دیسکورد، اسلک، واتساپ یا تیمز هم به‌روزرسانی کنید با فرستادن:

فرمان در چت
/update

این آخرین کد را می‌گیرد، وابستگی‌ها را به‌روز می‌کند و گیت‌وی‌های در حال اجرا را ری‌استارت می‌کند. بات در طول ری‌استارت کوتاهی آفلاین می‌شود (معمولاً ۵ تا ۱۵ ثانیه) و بعد ادامه می‌دهد.

۱۳ به‌روزرسانی دستی

اگر دستی نصب کرده‌اید (نه با نصب‌کنندهٔ سریع):

bash
cd /path/to/hermes-agent
# فعال‌سازی venvی که هنگام نصب ساختید (بیرون از درخت سورس)
export VIRTUAL_ENV="$HOME/.hermes/venvs/hermes-dev"
export PATH="$VIRTUAL_ENV/bin:$PATH"

# گرفتن آخرین کد
git pull origin main

# نصب مجدد (وابستگی‌های جدید را می‌گیرد)
uv pip install -e ".[all]"

# بررسی گزینه‌های پیکربندی جدید
hermes config check
hermes config migrate   # افزودن تعاملی گزینه‌های مفقود

۱۴ دستورالعمل بازگشت (Rollback)

اگر یک به‌روزرسانی مشکل ایجاد کرد، می‌توانید به نسخهٔ قبلی برگردید:

bash
cd /path/to/hermes-agent

# فهرست نسخه‌های اخیر
git log --oneline -10

# بازگشت به یک کامیت مشخص
git checkout <commit-hash>
uv pip install -e ".[all]"

# ری‌استارت گیت‌وی در صورت اجرا بودن
hermes gateway restart

برای بازگشت به یک تگ انتشار مشخص (تگ قبلی خودتان را جایگزین کنید — مثلاً یک انتشار اخیر مثل v2026.5.16، یا هر تگ قدیمی‌تری از git tag --sort=-version:refname):

bash
git checkout vX.Y.Z
uv pip install -e ".[all]"
⚠️ هشدار

بازگشت ممکن است اگر گزینه‌های جدیدی اضافه شده باشند، ناسازگاری پیکربندی ایجاد کند. پس از بازگشت hermes config check را اجرا کنید و در صورت برخورد با خطا، گزینه‌های ناشناخته را از config.yaml حذف کنید.

۱۵ نکته‌ای برای کاربران Nix

Nix دیگر مسیر نصبِ پشتیبانی‌شدهٔ رسمی نیست (فقط در حد توان) — به «راه‌اندازی Nix» مراجعه کنید. اگر با Nix flake نصب کرده‌اید، به‌روزرسانی‌ها از طریق مدیر پکیج Nix مدیریت می‌شوند:

bash
# به‌روزرسانی ورودی flake
nix flake update hermes-agent

# یا بازسازی با آخرین نسخه
nix profile upgrade hermes-agent

نصب‌های Nix تغییرناپذیرند — بازگشت توسط سیستم نسل‌های (generation) Nix انجام می‌شود:

bash
nix profile rollback

برای جزئیات بیشتر به «راه‌اندازی Nix» مراجعه کنید.

۱۶ حذف نصب

bash
hermes uninstall

حذف‌کننده به شما گزینه می‌دهد فایل‌های پیکربندی‌تان (~/.hermes/) را برای یک نصب مجدد آینده نگه دارید.

💡 به ماشین جدید می‌روید، نه اینکه کلاً حذف کنید؟

قبل از حذف هر چیزی، راه‌اندازی‌تان را با خودتان ببرید: hermes backup کل پوشهٔ ~/.hermes شامل اعتبارنامه‌ها را ضبط می‌کند، در حالی که hermes profile export یک پروفایل واحد را — به‌طرز طراحی‌شده بدون اعتبارنامه‌ها — بسته‌بندی می‌کند (پس خروجیِ تنها، پشتیبان کامل نیست). به «hermes backup در برابر hermes profile export» مراجعه کنید.

حذف دستی

bash
rm -f ~/.local/bin/hermes
rm -rf /path/to/hermes-agent
rm -rf ~/.hermes            # اختیاری — اگر می‌خواهید دوباره نصب کنید نگه دارید
ℹ️ توجه

اگر گیت‌وی را به‌عنوان سرویس سیستمی نصب کرده‌اید، اول آن را متوقف و غیرفعال کنید:

bash
hermes gateway stop
# لینوکس: systemctl --user disable hermes-gateway
# مک: launchctl remove ai.hermes.gateway
