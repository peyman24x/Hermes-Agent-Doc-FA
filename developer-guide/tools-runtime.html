زمان اجرای ابزارها

ابزارهای هرمس توابعی خودثبت‌کننده هستند که در تول‌ست‌ها گروه‌بندی شده و از طریق یک سامانهٔ مرکزی ثبت/ارسال اجرا می‌شوند.

پرونده‌های اصلی:

  • tools/registry.py
  • model_tools.py
  • toolsets.py
  • tools/terminal_tool.py
  • tools/environments/*

۱ مدل ثبت ابزار

هر ماژول ابزار هنگام ایمپورت، registry.register(...) را فرامی‌خواند.

model_tools.py مسئول ایمپورت/کشف ماژول‌های ابزار و ساخت فهرست اسکیمایی است که به مدل داده می‌شود.

روش کار registry.register()

هر پروندهٔ ابزار در tools/ در سطح ماژول registry.register() را فرامی‌خواند تا خود را اعلام کند. امضای تابع چنین است:

registry.register(
    name="terminal",               # Unique tool name (used in API schemas)
    toolset="terminal",            # Toolset this tool belongs to
    schema={...},                  # Model-facing schema (description, parameters)
    handler=handle_terminal,       # The function that executes when the tool is called
    check_fn=check_terminal,       # Optional: returns True/False for availability
    requires_env=["SOME_VAR"],     # Optional: env vars needed (for UI display)
    is_async=False,                # Whether the handler is an async coroutine
    description="Run commands",    # Optional ToolEntry registry metadata
    emoji="💻",                    # Emoji for spinner/progress display
)

هر فراخوانی یک ToolEntry می‌سازد که در دیکشنری تکنمونهٔ ToolRegistry._tools با کلید نام ابزار ذخیره می‌شود. ثبتی که ابزار موجودی از یک تول‌ست متفاوت را سایه‌اندازی کند رد می‌شود (با ثبت خطا در لاگ)، مگر آنکه فراخوان override=True بدهد؛ بازنویسی ابزارهای داخلی توسط پلاگین‌ها افزون بر این به موافقت اپراتور یعنی plugins.entries.<plugin_id>.allow_tool_override: true در config.yaml نیاز دارد.

schema["description"] توصیفِ معتبرِ رودررو با مدل است. آرگومان جداگانهٔ description= مقدار ToolEntry.description را پر می‌کند؛ وقتی حذف شود، فرادادهٔ رجیستری به توصیف اسکیما بازمی‌گردد. get_definitions() تعریف تابع OpenAI را از entry.schema می‌سازد و entry.description را در اسکیمایی که description ندارد کپی نمی‌کند. بنابراین description= به‌تنهایی ابزار را برای مدل توصیف نمی‌کند و وقتی دو مقدار متفاوت باشند، مدل مقدار اسکیما را می‌بیند. مگر آنکه مصرف‌کننده‌ای از رجیستری آگاهانه به فرادادهٔ متفاوتی نیاز داشته باشد، توصیف را یک‌بار در خود اسکیما تعریف کنید.

کشف: discover_builtin_tools()

وقتی model_tools.py ایمپورت می‌شود، discover_builtin_tools() را از tools/registry.py فرامی‌خواند. این تابع همهٔ پرونده‌های tools/*.py را با تحلیل AST اسکن می‌کند تا ماژول‌های دارای فراخوان registry.register() در سطح بالا را بیابد و سپس آن‌ها را ایمپورت می‌کند:

# tools/registry.py (simplified)
def discover_builtin_tools(tools_dir=None):
    tools_path = Path(tools_dir) if tools_dir else Path(__file__).parent
    for path in sorted(tools_path.glob("*.py")):
        if path.name in {"__init__.py", "registry.py", "mcp_tool.py"}:
            continue
        if _module_registers_tools(path):  # AST check for top-level registry.register()
            importlib.import_module(f"tools.{path.stem}")

این کشف خودکار یعنی پرونده‌های ابزار جدید خودبه‌خود شناسایی می‌شوند — فهرستی برای نگه‌داری دستی وجود ندارد. بررسی AST فقط فراخوان‌های registry.register() در سطح بالا را می‌یابد (نه فراخوان‌های درون توابع)، بنابراین ماژول‌های کمکیِ موجود در tools/ ایمپورت نمی‌شوند.

هر ایمپورت فراخوانی‌های registry.register() آن ماژول را فعال می‌کند. خطاهای ابزارهای اختیاری (مثلاً نبودن fal_client برای تولید تصویر) گرفته و ثبت می‌شوند — جلوی بارگذاری بقیهٔ ابزارها را نمی‌گیرند.

پس از کشف ابزارهای هسته، ابزارهای MCP و ابزارهای پلاگین هم کشف می‌شوند:

  1. ابزارهای MCP — tools.mcp_tool_discovery.discover_mcp_tools() (که توسط نمای tools.mcp_tool دوباره صادر شده) پیکربندی سرور MCP را می‌خواند و ابزارهای سرورهای بیرونی را ثبت می‌کند.
  2. ابزارهای پلاگین — hermes_cli.plugins.discover_plugins() پلاگین‌های کاربر/پروژه/pip را بارگذاری می‌کند که ممکن است ابزارهای بیشتری ثبت کرده باشند.

۲ بررسی در دسترس بودن ابزار (check_fn)

هر ابزار می‌تواند به‌اختیار یک check_fn ارائه کند — فراخوان‌دادی که وقتی ابزار در دسترس است True و در غیر این صورت False برمی‌گرداند. بررسی‌های معمول عبارت‌اند از:

  • موجود بودن کلید API — مثلاً lambda: bool(os.environ.get("SERP_API_KEY")) برای جستجوی وب
  • در حال اجرا بودن سرویس — مثلاً بررسی پیکربندی‌شده بودن سرور Honcho
  • نصب بودن باینری — مثلاً وارسی موجود بودن playwright برای ابزارهای مرورگر

وقتی registry.get_definitions() فهرست اسکیما را برای مدل می‌سازد، check_fn() هر ابزار را اجرا می‌کند:

# Simplified from registry.py
if entry.check_fn:
    try:
        available = bool(entry.check_fn())
    except Exception:
        available = False   # Exceptions = unavailable
    if not available:
        continue            # Skip this tool entirely

رفتارهای کلیدی:

  • نتیجهٔ بررسی‌ها به‌ازای هر فراخوان کش می‌شود — اگر چند ابزار check_fn یکسانی داشته باشند، فقط یک‌بار اجرا می‌شود.
  • استثناهای check_fn() به معنای «در دسترس نیست» تلقی می‌شوند (رفتار ایمن در برابر خطا).
  • متد is_toolset_available() بررسی می‌کند آیا check_fn یک تول‌ست موفق می‌شود؛ برای نمایش در رابط کاربری و حل تول‌ست به کار می‌رود.

۳ حل تول‌ست‌ها

تول‌ست‌ها بسته‌های نام‌دار ابزارها هستند. هرمس آن‌ها را از این راه‌ها حل می‌کند:

  • فهرست‌های صریح تول‌ست‌های فعال/غیرفعال
  • پیش‌تنظیم‌های پلتفرمی (hermes-cli، hermes-telegram و غیره)
  • تول‌ست‌های پویای MCP
  • مجموعه‌های ویژهٔ منتخب مانند hermes-acp

روش فیلتر ابزارها در get_tool_definitions()

نقطهٔ ورود اصلی model_tools.get_tool_definitions(enabled_toolsets, disabled_toolsets, quiet_mode) است:

  1. اگر enabled_toolsets داده شده باشد — فقط ابزارهای آن تول‌ست‌ها گنجانده می‌شوند. هر نام تول‌ست از طریق resolve_toolset() حل می‌شود که تول‌ست‌های ترکیبی را به نام‌های ابزار منفرد باز می‌کند.
  2. اگر disabled_toolsets داده شده باشد — از همهٔ تول‌ست‌ها آغاز و تول‌ست‌های غیرفعال از آن کسر می‌شود.
  3. اگر هیچ‌کدام — همهٔ تول‌ست‌های شناخته‌شده گنجانده می‌شوند.
  4. فیلتر رجیستری — مجموعهٔ نام‌های ابزارِ حل‌شده به registry.get_definitions() داده می‌شود که فیلتر check_fn را اعمال و اسکیماهای قالب OpenAI را برمی‌گرداند.
  5. وصله‌گذاری پویای اسکیما — پس از فیلتر، اسکیماهای execute_code و browser_navigate به‌صورت پویا تنظیم می‌شوند تا فقط به ابزارهایی ارجاع دهند که واقعاً از فیلتر گذشته‌اند (از توهم مدل دربارهٔ ابزارهای در دسترس نیست جلوگیری می‌کند).

نام‌های قدیمی تول‌ست‌ها

نام‌های قدیمی با پسوند _tools (مثل web_tools، terminal_tools) برای سازگاری با گذشته از طریق _LEGACY_TOOLSET_MAP به نام‌های امروزی ابزار نگاشت می‌شوند.

۴ ارسال (Dispatch)

در زمان اجرا، ابزارها از طریق رجیستری مرکزی ارسال می‌شوند، با استثناهای حلقهٔ ایجنت برای برخی ابزارهای سطح ایجنت مانند حافظه/تودو/جستجوی نشست.

جریان ارسال: tool_call مدل ← اجرای هندلر

وقتی مدل یک tool_call برمی‌گرداند، جریان چنین است:

Model response with tool_call
    ↓
agent loop (`agent/conversation_loop.py`, via `run_agent.py`'s `AIAgent` facade)
    ↓
model_tools.handle_function_call(name, args, task_id, user_task)
    ↓
[Agent-loop tools?] → handled directly by agent loop (todo, memory, session_search, delegate_task)
    ↓
[Plugin pre-hook] → invoke_hook("pre_tool_call", ...)
    ↓
registry.dispatch(name, args, **kwargs)
    ↓
Look up ToolEntry by name
    ↓
[Async handler?] → bridge via _run_async()
[Sync handler?]  → call directly
    ↓
Return result string (or JSON error)
    ↓
[Plugin post-hook] → invoke_hook("post_tool_call", ...)

پیچش خطا

تمام اجرای ابزار در دو سطح در مدیریت خطا پیچیده می‌شود:

  1. registry.dispatch() — هر استثنای هندلر را می‌گیرد و {"error": "Tool execution failed: ExceptionType: message"} را به‌صورت JSON برمی‌گرداند.
  2. handle_function_call() — کل ارسال را در یک try/except ثانویه می‌پیچد که {"error": "Error executing tool_name: message"} برمی‌گرداند.

این تضمین می‌کند مدل همیشه یک رشتهٔ JSON خوش‌ساخت دریافت کند، نه یک استثنای مدیریت‌نشده.

ابزارهای حلقهٔ ایجنت

چهار ابزار پیش از ارسال رجیستری رهگیری می‌شوند، چون به وضعیت سطح ایجنت (TodoStore، MemoryStore و غیره) نیاز دارند:

  • todo — برنامه‌ریزی/پیگیری وظایف
  • memory — نوشتن حافظهٔ پایدار
  • session_search — یادآوری بین‌نشستی
  • delegate_task — ایجاد نشست‌های ساب‌ایجنت

اسکیمای این ابزارها همچنان در رجیستری ثبت می‌شود (برای get_tool_definitions)، اما اگر ارسال به‌طرزی به‌طور مستقیم به هندلرهایشان برسد، یک خطای موقتی برمی‌گردانند.

پل‌زنی ناهمگام

وقتی هندلر ابزار ناهمگام (async) باشد، _run_async() آن را به مسیر همگام ارسال پل می‌زند:

  • مسیر CLI (بدون حلقهٔ در حال اجرا) — از یک حلقهٔ رویداد پایدار استفاده می‌کند تا کلاینت‌های ناهمگامِ کش‌شده زنده بمانند
  • مسیر گیت‌وی (حلقهٔ در حال اجرا) — یک نخ یک‌بارمصرف با asyncio.run() برپا می‌کند
  • نخ‌های کاری (ابزارهای موازی) — از حلقه‌های پایدار به‌ازای هر نخ ذخیره‌شده در thread-local storage استفاده می‌کند

۵ جریان تأیید DANGEROUS_PATTERNS

ابزار ترمینال سامانهٔ تأیید فرمان خطرناکِ تعریف‌شده در tools/approval.py را یکپارچه کرده است:

  1. شناسایی الگو — DANGEROUS_PATTERNS فهرستی از تاپل‌های (regex, description) است که عملیات مخرب را پوشش می‌دهد:
    • حذف بازگشتی (rm -rf)
    • قالب‌بندی فایل‌سیستم (mkfs، dd)
    • عملیات مخرب SQL (DROP TABLE، DELETE FROM بدون WHERE)
    • بازنویسی پیکربندی سیستم (> /etc/)
    • دستکاری سرویس‌ها (systemctl stop)
    • اجرای کد از راه دور (curl | sh)
    • بمب فورک، کشتن فرایندها و غیره
  2. تشخیص — پیش از اجرای هر فرمان ترمینال، detect_dangerous_command(command) فرمان را با همهٔ الگوها می‌سنجد.
  3. درخواست تأیید — اگر تطبیقی یافت شود:
    • حالت CLI — یک پرامپت تعاملی از کاربر تأیید، رد یا اجازهٔ دائمی می‌خواهد
    • حالت گیت‌وی — یک کالبک تأیید ناهمگام درخواست را به پلتفرم پیام‌رسانی می‌فرستد
    • تأیید هوشمند — به‌صورت اختیاری، یک LLM کمکی می‌تواند فرمان‌های کم‌خطری را که با الگوها تطبیق دارند خودکار تأیید کند (مثلاً rm -rf node_modules/ بی‌خطر است ولی با «حذف بازگشتی» تطبیق می‌کند)
  4. وضعیت نشست — تأییدها به‌ازای هر نشست پیگیری می‌شوند. پس از تأیید «حذف بازگشتی» برای یک نشست، فرمان‌های بعدی rm -rf دوباره پرسش نمی‌کنند.
  5. فهرست مجاز دائمی — گزینهٔ «اجازهٔ دائمی» الگو را در command_allowlist پروندهٔ config.yaml می‌نویسد و در سراسر نشست‌ها پایدار می‌ماند.

۶ محیط‌های ترمینال/اجرا

سامانهٔ ترمینال از بک‌اندهای چندگانه پشتیبانی می‌کند:

  • local
  • docker
  • ssh
  • singularity
  • modal
  • daytona
  • vercel_sandbox

همچنین از این‌ها پشتیبانی می‌کند:

  • بازنویسی cwd به‌ازای هر وظیفه
  • مدیریت فرایندهای پس‌زمینه
  • حالت PTY
  • کالبک‌های تأیید برای فرمان‌های خطرناک

tools/process_registry_checkpoint.py مالک چک‌پوینت‌های فرایندهای در حال اجرا و پذیرش امنِ PID است. خروجی تکمیل‌شده جداگانه است: tools/process_registry_results.py به‌ازای هر فرایند یک رسید اتمیک و پاک‌سازیشده زیر logs/process-results/ پروفایل می‌نویسد. تولیدکننده‌ها نمی‌توانند با بازنویسی چک‌پوینت مشترک PID، نتایج والد دیگری را بازنویسی کنند. رجیستری رسید را پیش از آزادکردن رویداد تکمیلش پایدار می‌کند؛ مکث یک‌بارهٔ (one-shot linger) روی آن رویداد منتظر می‌ماند. متدهای موجود پرس‌وجوی فرایند، اسنپ‌شات‌های نگه‌داشته‌شده را بدون پذیرش PID یا صف‌کردن اعلان‌ها بارگذاری می‌کنند. خواندن‌ها نیازمند نشست پایدارِ درخواست‌کننده یا ادامهٔ فشرده‌سازی آن هستند؛ دانستن صرف یک هندل، خواندن نتیجهٔ نگه‌داشته‌شده را مجاز نمی‌کند. رجیستری این مالک را پیش از راه‌اندازی هر خوانندهٔ خروجی ثبت می‌کند — از جمله روی CLI و فرایندهای بدون اعلان — و زمینهٔ پروفایل تولیدکننده را در نخ‌های خواننده حفظ می‌کند. پاک‌سازی رسید مستقل از انصراف از خروجی زنده اجباری است؛ نگه‌داری با سن و شمار محدود می‌شود.
