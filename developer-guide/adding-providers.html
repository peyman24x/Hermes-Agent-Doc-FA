افزودن ارائه‌دهندهٔ جدید

هرمس از هم‌اکنون می‌تواند با هر نقطهٔ پایانی سازگار با OpenAI از مسیر ارائه‌دهندهٔ سفارشی (custom provider) گفتگو کند. مگر اینکه بخواهید برای آن سرویس تجربهٔ کاربری درجه‌یک داشته باشید، ارائه‌دهندهٔ (provider) داخلی جدید اضافه نکنید:

  • احراز هویت یا تازه‌سازی توکن مخصوص همان ارائه‌دهنده
  • کاتالوگ منتخب مدل‌ها
  • موارد منوی setup / hermes model
  • نام‌های مستعار ارائه‌دهنده برای سینتکس provider:model
  • شکل API غیر-OpenAI که به آداپتور (adapter) نیاز دارد

اگر ارائه‌دهنده فقط «یک base URL سازگار با OpenAI به‌علاوهٔ یک کلید API» دیگر باشد، شاید یک ارائه‌دهندهٔ سفارشیِ نام‌دار کافی باشد.

۱ مدل ذهنی

یک ارائه‌دهندهٔ داخلی باید در چند لایه هم‌راستا شود:

  1. hermes_cli/auth.py تعیین می‌کند اعتبارنامه‌ها چطور پیدا می‌شوند.
  2. hermes_cli/runtime_provider.py آن را به دادهٔ زمان اجرا تبدیل می‌کند:
    • provider
    • api_mode
    • base_url
    • api_key
    • source
  3. run_agent.py از api_mode برای تصمیم‌گیری دربارهٔ نحوهٔ ساخته‌شدن و ارسال درخواست‌ها استفاده می‌کند.
  4. hermes_cli/models.py و hermes_cli/main.py باعث می‌شوند ارائه‌دهنده در CLI دیده شود. (hermes_cli/setup.py به‌طور خودکار به main.py واگذار می‌کند — آنجا نیازی به تغییر نیست.)
  5. agent/auxiliary_client.py و agent/model_metadata.py کارکرد کارهای جانبی و بودجه‌بندی توکن را حفظ می‌کنند.

مهم‌ترین انتزاع، api_mode است.

  • بیشتر ارائه‌دهنده‌ها از chat_completions استفاده می‌کنند.
  • Codex و Meta Model API‏ (api.meta.ai — Muse Spark) از codex_responses استفاده می‌کنند (برای کش پرامپت (prompt caching) به‌طور خودکار prompt_cache_retention: 24h را می‌فرستد؛ api.meta.ai فقط روی /v1/responses به ۹۳ تا ۹۹٪ hit کش می‌رسد).
  • Anthropic از anthropic_messages استفاده می‌کند.
  • پروتکل جدید غیر-OpenAI معمولاً یعنی افزودن یک آداپتور جدید و یک شاخهٔ جدید api_mode.

قالب سیمی فراخوانی ابزار (tool-call wire format)

هرمس تاریخچهٔ گفتگو را به‌صورت داخلی در شکل chat-completions خودِ OpenAI ذخیره می‌کند؛ بنابراین convert_messages / convert_tools در ترنسپورت chat_completions‏ (agent/transports/chat_completions.py) تقریباً هویتی‌اند و هر ترنسپورت دیگری آن شکل را به پروتکل بومی خودش تبدیل می‌کند. مرجع اصلی برای این شکل — تعریف‌های tools با parameters از نوع JSON-schema، رکوردهای tool_calls دستیار با function.arguments رشته‌ای‌شده، و پیام‌های نتیجهٔ role: "tool" کلیدخورده با tool_call_id — مرجع API چت کامپلیشنز OpenAI است. وقتی یک آداپتور بومی می‌نویسید، آن صفحه سمت ورودیِ تبدیل شما را تعریف می‌کند و مستندات ارائه‌دهندهٔ شما سمت خروجی را.

۲ اول مسیر پیاده‌سازی را انتخاب کنید

مسیر A — ارائه‌دهندهٔ سازگار با OpenAI

وقتی از این مسیر استفاده کنید که ارائه‌دهنده درخواست‌های استاندارد به سبک chat-completions را می‌پذیرد.

کارهای معمول:

  • افزودن متادیتای احراز هویت
  • افزودن کاتالوگ مدل‌ها / نام‌های مستعار
  • افزودن resolve زمان اجرا
  • افزودن سیم‌کشی منوی CLI
  • افزودن پیش‌فرض‌های مدل کمکی (aux)
  • افزودن تست‌ها و مستندات کاربری

معمولاً به آداپتور یا api_mode جدید نیازی ندارید.

مسیر B — ارائه‌دهندهٔ بومی

وقتی از این مسیر استفاده کنید که ارائه‌دهنده مثل OpenAI chat completions رفتار نمی‌کند.

نمونه‌های موجود در مخزن امروز:

  • codex_responses‏ (OpenAI Codex، xAI Grok و Meta Muse Spark از طریق api.meta.ai — مورد آخر به‌طور خودکار prompt_cache_retention: 24h را می‌فرستد)
  • anthropic_messages

این مسیر همه‌چیزِ مسیر A را به‌علاوهٔ این‌ها شامل می‌شود:

  • یک آداپتور ارائه‌دهنده در agent/
  • شاخه‌های run_agent.py برای ساخت درخواست، dispatch، استخراج usage، مدیریت اینتراپت و نرمال‌سازی پاسخ
  • تست‌های آداپتور

۳ چک‌لیست فایل‌ها

لازم برای هر ارائه‌دهندهٔ داخلی

  1. hermes_cli/auth.py
  2. hermes_cli/models.py
  3. hermes_cli/runtime_provider.py
  4. hermes_cli/main.py
  5. agent/auxiliary_client.py
  6. agent/model_metadata.py
  7. تست‌ها
  8. مستندات رو به کاربر زیر website/docs/
💡

hermes_cli/setup.py نیازی به تغییر ندارد. جادوگر setup، انتخاب ارائه‌دهنده/مدل را به select_provider_and_model() در main.py واگذار می‌کند — هر ارائه‌دهنده‌ای که آنجا اضافه شود به‌طور خودکار در hermes setup در دسترس است.

موارد اضافی برای ارائه‌دهنده‌های بومی / غیر-OpenAI

  1. agent/<provider>_adapter.py
  2. run_agent.py
  3. pyproject.toml اگر SDK ارائه‌دهنده لازم باشد

۴ مسیر سریع: ارائه‌دهنده‌های ساده با کلید API

اگر ارائه‌دهندهٔ شما فقط یک نقطهٔ پایانی سازگار با OpenAI است که با یک کلید API واحد احراز هویت می‌شود، لازم نیست سراغ auth.py، ‏runtime_provider.py، ‏main.py یا هیچ‌کدام از فایل‌های چک‌لیست کاملِ پایین بروید.

تنها چیزی که لازم دارید:

  1. یک پوشهٔ پلاگین زیر plugins/model-providers/<your-provider>/ شامل:
    • __init__.py — در سطح ماژول ‏register_provider(profile) را صدا می‌زند
    • plugin.yaml — مانیفست (name، kind: model-provider، version، description)
  2. همین. پلاگین‌های ارائه‌دهنده دفعهٔ اول که چیزی ‏get_provider_profile() یا ‏list_providers() را صدا بزند به‌طور خودکار بارگذاری می‌شوند — هم پلاگین‌های همراه مخزن (این ریپو) و هم پلاگین‌های کاربر در $HERMES_HOME/plugins/model-providers/ برداشته می‌شوند.

وقتی پلاگینی اضافه می‌کنید و آن ‏register_provider() را صدا می‌زند، این‌ها به‌طور خودکار وصل می‌شوند:

  1. رکورد PROVIDER_REGISTRY در auth.py‏ (resolve اعتبارنامه، جستجوی متغیر محیطی)
  2. api_mode روی chat_completions تنظیم می‌شود
  3. base_url از کانفیگ یا متغیر محیطی اعلام‌شده گرفته می‌شود
  4. env_vars‌ها به ترتیب اولویت برای کلید API بررسی می‌شوند
  5. فهرست fallback_models برای ارائه‌دهنده ثبت می‌شود
  6. پرچم --provider در CLI شناسهٔ ارائه‌دهنده را می‌پذیرد
  7. منوی hermes model ارائه‌دهنده را شامل می‌شود
  8. جادوگر hermes setup به‌طور خودکار به main.py واگذار می‌کند
  9. سینتکس مستعار provider:model کار می‌کند
  10. resolver زمان اجرا ‏base_url و ‏api_key درست را برمی‌گرداند
  11. پرچم --provider <name> در CLI شناسهٔ ارائه‌دهنده را می‌پذیرد
  12. فعال‌سازی مدل پشتیبان می‌تواند به‌شکل تمیز به ارائه‌دهنده سوئیچ کند

پلاگین‌های کاربر در $HERMES_HOME/plugins/model-providers/<name>/ پلاگین‌های هم‌نامِ همراه را بازنویسی می‌کنند (در register_provider() آخرین نویسنده برنده است) — پس اشخاص ثالث می‌توانند بدون دست‌کاری مخزن، هر پروفایل داخلی را monkey-patch یا جایگزین کنند.

‏plugins/model-providers/nvidia/ یا ‏plugins/model-providers/gmi/ را به‌عنوان الگو ببینید، و برای مرجع فیلدها، اصطلاحات هوک (hook) و مثال‌های سرتاسری، راهنمای کامل پلاگین ارائه‌دهندهٔ مدل را بخوانید.

۵ مسیر کامل: ارائه‌دهنده‌های OAuth و پیچیده

وقتی ارائه‌دهندهٔ شما به هرکدام از این‌ها نیاز دارد، از چک‌لیست کامل پایین استفاده کنید:

  • OAuth یا تازه‌سازی توکن (Nous Portal، Codex، Qwen Portal، Copilot)
  • شکل API غیر-OpenAI که آداپتور جدید می‌خواهد (Anthropic Messages، Codex Responses)
  • تشخیص نقطهٔ پایانی سفارشی یا کاوش چندمنطقه‌ای (z.ai، Kimi)
  • کاتالوگ ایستای منتخب مدل‌ها یا واکشی زندهٔ /models
  • موارد منوی hermes model مخصوص ارائه‌دهنده با جریان‌های احراز هویت اختصاصی

۶ گام ۱: انتخاب یک شناسهٔ مرجع واحد برای ارائه‌دهنده

یک شناسهٔ (id) واحد برای ارائه‌دهنده انتخاب کنید و همه‌جا از همان استفاده کنید.

نمونه‌هایی از مخزن:

  • openai-codex
  • kimi-coding
  • minimax-cn

همان شناسه باید در این‌ها ظاهر شود:

  • PROVIDER_REGISTRY در hermes_cli/auth.py
  • _PROVIDER_LABELS در hermes_cli/models.py
  • _PROVIDER_ALIASES در هر دوی hermes_cli/auth.py و hermes_cli/models.py
  • گزینه‌های --provider در CLI در hermes_cli/main.py
  • شاخه‌های setup / انتخاب مدل
  • پیش‌فرض‌های مدل کمکی
  • تست‌ها

اگر شناسه بین آن فایل‌ها فرق کند، ارائه‌دهنده نیمه‌وصل حس می‌شود: احراز هویت شاید کار کند ولی /model، ‏setup یا resolve زمان اجرا بی‌سروصدا آن را از دست می‌دهد.

۷ گام ۲: افزودن متادیتای احراز هویت در hermes_cli/auth.py

برای ارائه‌دهنده‌های کلید-API، یک رکورد ProviderConfig به PROVIDER_REGISTRY اضافه کنید با:

  • id
  • name
  • auth_type="api_key"
  • inference_base_url
  • api_key_env_vars
  • اختیاری: base_url_env_var

همچنین نام‌های مستعار را به _PROVIDER_ALIASES اضافه کنید.

ارائه‌دهنده‌های موجود را الگو قرار دهید:

  • مسیر سادهٔ کلید API: Z.AI، MiniMax
  • مسیر کلید API با تشخیص نقطهٔ پایانی: Kimi، Z.AI
  • resolve بومی توکن: Anthropic
  • مسیر OAuth / auth-store: Nous، OpenAI Codex

سؤال‌هایی که اینجا باید پاسخ دهید:

  • هرمس باید چه متغیرهای محیطی را بررسی کند و با چه ترتیب اولویتی؟
  • آیا ارائه‌دهنده به بازنویسی base URL نیاز دارد؟
  • آیا به کاوش نقطهٔ پایانی یا تازه‌سازی توکن نیاز دارد؟
  • وقتی اعتبارنامه‌ها موجود نیستند، خطای احراز هویت چه بگوید؟

اگر ارائه‌دهنده چیزی بیش از «پیدا کردن یک کلید API» لازم دارد، به‌جای هل‌دادن منطق به شاخه‌های بی‌ربط، یک credential resolver مخصوص اضافه کنید.

۸ گام ۳: افزودن کاتالوگ مدل و نام‌های مستعار در hermes_cli/models.py

کاتالوگ ارائه‌دهنده را به‌روز کنید تا ارائه‌دهنده در منوها و در سینتکس provider:model کار کند.

ویرایش‌های معمول:

  • _PROVIDER_MODELS
  • _PROVIDER_LABELS
  • _PROVIDER_ALIASES
  • ترتیب نمایش ارائه‌دهنده‌ها داخل list_available_providers()
  • provider_model_ids() اگر ارائه‌دهنده واکشی زندهٔ /models را پشتیبانی کند

اگر ارائه‌دهنده فهرست مدل زنده می‌دهد، اول همان را در اولویت بگذارید و _PROVIDER_MODELS را به‌عنوان پشتیبان ایستا نگه دارید.

همین فایل است که ورودی‌هایی مثل این‌ها را کارا می‌کند:

anthropic:claude-sonnet-4-6
kimi:model-name

اگر نام‌های مستعار اینجا نباشند، ممکن است ارائه‌دهنده درست احراز هویت شود ولی در پارس /model همچنان شکست بخورد.

۹ گام ۴: resolve دادهٔ زمان اجرا در hermes_cli/runtime_provider.py

‏resolve_runtime_provider() مسیر مشترکی است که CLI، گیت‌وی (gateway)، کرون، ACP و کلاینت‌های کمکی از آن استفاده می‌کنند.

شاخه‌ای اضافه کنید که دست‌کم دیکشنری زیر را برگرداند:

{
    "provider": "your-provider",
    "api_mode": "chat_completions",  # یا حالت بومی خودتان
    "base_url": "https://...",
    "api_key": "...",
    "source": "env|portal|auth-store|explicit",
    "requested_provider": requested_provider,
}

اگر ارائه‌دهنده سازگار با OpenAI است، api_mode معمولاً باید chat_completions بماند.

مراقب اولویت کلید API باشید. هرمس از قبل منطقی دارد که جلوی لو رفتن کلید OpenRouter به نقاط پایانیِ بی‌ربط را می‌گیرد. ارائه‌دهندهٔ جدید هم باید به همان‌اندازه صریح باشد که کدام کلید به کدام base URL می‌رود.

۱۰ گام ۵: سیم‌کشی CLI در hermes_cli/main.py

ارائه‌دهنده تا وقتی در جریان تعاملی hermes model ظاهر نشود، کشف‌شدنی نیست.

این‌ها را در hermes_cli/main.py به‌روز کنید:

  • دیکشنری provider_labels
  • فهرست providers در select_provider_and_model()
  • dispatch ارائه‌دهنده‏ (if selected_provider == ...)
  • گزینه‌های آرگومان --provider
  • گزینه‌های login/logout اگر ارائه‌دهنده آن جریان‌ها را پشتیبانی می‌کند
  • تابع _model_flow_<provider>()، یا استفادهٔ دوباره از _model_flow_api_key_provider() اگر جا بگیرد
💡

hermes_cli/setup.py نیازی به تغییر ندارد — این فایل select_provider_and_model() را از main.py صدا می‌زند، پس ارائه‌دهندهٔ جدید شما هم در hermes model و هم در hermes setup به‌طور خودکار ظاهر می‌شود.

۱۱ گام ۶: سرپا نگه‌داشتن فراخوانی‌های کمکی

اینجا دو فایل مهم‌اند:

agent/auxiliary_client.py

اگر این یک ارائه‌دهندهٔ مستقیم کلید-API است، یک مدل کمکیِ پیش‌فرضِ ارزان/سریع به _API_KEY_PROVIDER_AUX_MODELS اضافه کنید.

کارهای کمکی شامل چیزهایی مثل این‌اند:

  • خلاصه‌سازی تصویر (vision)
  • خلاصه‌سازی استخراج از وب
  • خلاصه‌سازی فشرده‌سازی زمینه (context)
  • خلاصه‌سازی جستجوی نشست (session)
  • تخلیهٔ حافظه

اگر ارائه‌دهنده پیش‌فرض کمکیِ معقول نداشته باشد، کارهای جانبی ممکن است بد fallback کنند یا بی‌خبر از یک مدل اصلیِ گران استفاده کنند.

agent/model_metadata.py

طول زمینهٔ مدل‌های ارائه‌دهنده را اضافه کنید تا بودجه‌بندی توکن، آستانه‌های فشرده‌سازی و محدودیت‌ها عقلانی بمانند.

۱۲ گام ۷: اگر ارائه‌دهنده بومی است، آداپتور و پشتیبانی run_agent.py را اضافه کنید

اگر ارائه‌دهنده chat completions ساده نیست، منطق مخصوص ارائه‌دهنده را در agent/<provider>_adapter.py ایزوله کنید.

‏run_agent.py را متمرکز روی orchestration نگه دارید. این فایل باید helperهای آداپتور را صدا بزند، نه اینکه payloadهای ارائه‌دهنده را این‌ور و آن‌ورِ فایل به‌صورت دستی بسازد.

یک ارائه‌دهندهٔ بومی معمولاً در این جاها کار می‌خواهد:

فایل آداپتور جدید

مسئولیت‌های معمول:

  • ساخت SDK / کلاینت HTTP
  • resolve کردن توکن‌ها
  • تبدیل پیام‌های گفتگوی به سبک OpenAI به فرمت درخواست ارائه‌دهنده
  • تبدیل طرح‌واره‌های ابزار در صورت نیاز
  • نرمال‌سازی پاسخ‌های ارائه‌دهنده به آنچه run_agent.py انتظار دارد
  • استخراج داده‌های usage و finish-reason

run_agent.py

دنبال api_mode بگردید و هر نقطهٔ سوئیچ را ممیزی کنید. دست‌کم این‌ها را بررسی کنید:

  • __init__ ‏api_mode جدید را انتخاب می‌کند
  • ساخت کلاینت برای ارائه‌دهنده کار می‌کند
  • _build_api_kwargs() می‌داند درخواست‌ها را چطور فرمت کند
  • _interruptible_api_call() به فراخوانی کلاینتِ درست dispatch می‌کند
  • مسیرهای اینتراپت / بازسازی کلاینت کار می‌کنند
  • اعتبارسنجی پاسخ، شکل ارائه‌دهنده را می‌پذیرد
  • استخراج finish-reason درست است
  • استخراج مصرف توکن درست است
  • فعال‌سازی مدل پشتیبان می‌تواند تمیز به ارائه‌دهندهٔ جدید سوئیچ کند
  • مسیرهای تولید خلاصه و تخلیهٔ حافظه همچنان کار می‌کنند

همچنین در run_agent.py دنبال self.client. بگردید. هر مسیر کدی که فرض کند کلاینت استاندارد OpenAI وجود دارد، وقتی ارائه‌دهندهٔ بومی از آبجکت کلاینت متفاوتی استفاده کند یا self.client = None باشد، ممکن است بشکند.

کش پرامپت و فیلدهای درخواست مخصوص ارائه‌دهنده

کش پرامپت و تنظیمات مخصوص ارائه‌دهنده به‌راحتی پسرفت می‌کنند.

نمونه‌های موجود در مخزن:

  • Anthropic مسیر بومی کش پرامپت دارد
  • OpenRouter فیلدهای provider-routing می‌گیرد
  • هر ارائه‌دهنده‌ای نباید همهٔ گزینه‌های سمت درخواست را بگیرد

وقتی ارائه‌دهندهٔ بومی اضافه می‌کنید، دوباره چک کنید که هرمس فقط فیلدهایی را می‌فرستد که آن ارائه‌دهنده واقعاً می‌فهمد.

۱۳ گام ۸: تست‌ها

دست‌کم تست‌هایی که سیم‌کشی ارائه‌دهنده را محافظت می‌کنند را به‌روز کنید.

جاهای رایج:

  • tests/hermes_cli/test_runtime_provider_resolution.py
  • tests/cli/test_cli_provider_resolution.py
  • tests/hermes_cli/test_model_switch_custom_providers.py‏ (و فایل‌های مجاور tests/hermes_cli/test_model_switch_*.py)
  • tests/hermes_cli/test_setup_model_provider.py
  • tests/run_agent/test_provider_parity.py
  • tests/run_agent/test_run_agent.py
  • tests/test_<provider>_adapter.py برای ارائه‌دهندهٔ بومی

برای مثال‌های فقط-مستنداتی، مجموعهٔ دقیق فایل‌ها ممکن است فرق کند. نکته پوشش این‌هاست:

  • resolve احراز هویت
  • منوی CLI / انتخاب ارائه‌دهنده
  • resolve ارائه‌دهنده در زمان اجرا
  • مسیر اجرای ایجنت
  • پارس provider:model
  • هر تبدیل پیام مخصوص آداپتور

تست‌های هدفمند را اجرا کنید (یا از scripts/run_tests.sh استفاده کنید که هر فایل را در ساب‌پروسس خودش اجرا می‌کند):

source venv/bin/activate
python -m pytest tests/hermes_cli/test_runtime_provider_resolution.py tests/cli/test_cli_provider_resolution.py tests/hermes_cli/test_setup_model_provider.py tests/run_agent/test_provider_parity.py -q

برای تغییرهای عمیق‌تر، قبل از push کل مجموعه را اجرا کنید:

source venv/bin/activate
python -m pytest tests/ -n0 -q

۱۴ گام ۹: راستی‌آزمایی زنده

بعد از تست‌ها، یک تست دود واقعی اجرا کنید.

source venv/bin/activate
python -m hermes_cli.main chat -q "Say hello" --provider your-provider --model your-model

اگر منوها را تغییر داده‌اید، جریان‌های تعاملی را هم تست کنید:

source venv/bin/activate
python -m hermes_cli.main model
python -m hermes_cli.main setup

برای ارائه‌دهنده‌های بومی، دست‌کم یک فراخوانی ابزار (tool call) را هم راستی‌آزمایی کنید، نه فقط یک پاسخ متنی ساده.

۱۵ گام ۱۰: به‌روزرسانی مستندات رو به کاربر

اگر قرار است ارائه‌دهنده به‌عنوان گزینهٔ درجه‌یک عرضه شود، مستندات کاربری را هم به‌روز کنید:

  • website/docs/getting-started/quickstart.md
  • website/docs/user-guide/configuration.md
  • website/docs/reference/environment-variables.md

یک توسعه‌دهنده می‌تواند ارائه‌دهنده را بی‌نقص سیم‌کشی کند و همچنان کاربران را جایی بگذارد که متغیرهای محیطی لازم یا جریان setup را پیدا نمی‌کنند.

۱۶ چک‌لیست ارائه‌دهندهٔ سازگار با OpenAI

اگر ارائه‌دهنده chat completions استاندارد است، از این استفاده کنید.

  • ☐ ProviderConfig در hermes_cli/auth.py اضافه شده است
  • ☐ نام‌های مستعار در hermes_cli/auth.py و hermes_cli/models.py اضافه شده‌اند
  • ☐ کاتالوگ مدل در hermes_cli/models.py اضافه شده است
  • ☐ شاخهٔ زمان اجرا در hermes_cli/runtime_provider.py اضافه شده است
  • ☐ سیم‌کشی CLI در hermes_cli/main.py اضافه شده است (setup.py به‌طور خودکار به ارث می‌برد)
  • ☐ مدل کمکی در agent/auxiliary_client.py اضافه شده است
  • ☐ طول زمینه‌ها در agent/model_metadata.py اضافه شده است
  • ☐ تست‌های زمان اجرا / CLI به‌روز شده‌اند
  • ☐ مستندات کاربری به‌روز شده است

۱۷ چک‌لیست ارائه‌دهندهٔ بومی

وقتی ارائه‌دهنده به مسیر پروتکل جدید نیاز دارد، از این استفاده کنید.

  • ☐ همه‌چیز در چک‌لیست سازگار با OpenAI
  • ☐ آداپتور در agent/<provider>_adapter.py اضافه شده است
  • ☐ api_mode جدید در run_agent.py پشتیبانی شده است
  • ☐ مسیر اینتراپت / بازسازی کار می‌کند
  • ☐ استخراج usage و finish-reason کار می‌کند
  • ☐ مسیر پشتیبان کار می‌کند
  • ☐ تست‌های آداپتور اضافه شده‌اند
  • ☐ تست دود زنده پاس می‌شود

۱۸ دام‌های رایج

۱. اضافه‌کردن ارائه‌دهنده به احراز هویت، ولی نه به پارس مدل

نتیجه این می‌شود که اعتبارنامه‌ها درست resolve می‌شوند ولی ورودی‌های /model و provider:model شکست می‌خورند.

۲. فراموش‌کردن اینکه config["model"] می‌تواند رشته یا دیکشنری باشد

بسیاری از کدهای انتخاب ارائه‌دهنده باید هر دو شکل را نرمال کنند.

۳. فرض‌کردن اینکه ارائه‌دهندهٔ داخلی الزامی است

اگر سرویس فقط سازگار با OpenAI است، شاید یک ارائه‌دهندهٔ سفارشی از قبل مسئلهٔ کاربر را با نگه‌داری کمتر حل کند.

۴. فراموش‌کردن مسیرهای کمکی

مسیر اصلی چت می‌تواند کار کند درحالی‌که خلاصه‌سازی، تخلیهٔ حافظه یا helperهای vision شکست می‌خورند، چون مسیریابی aux هرگز به‌روز نشده است.

۵. شاخه‌های ارائه‌دهندهٔ بومی که در run_agent.py پنهان‌اند

دنبال api_mode و self.client. بگردید. فرض نکنید مسیر درخواستِ بدیهی تنها مسیر است.

۶. فرستادن تنظیمات مخصوص OpenRouter به ارائه‌دهنده‌های دیگر

فیلدهایی مثل provider routing فقط به ارائه‌دهنده‌هایی تعلق دارند که از آن‌ها پشتیبانی می‌کنند.

۷. به‌روزرسانی hermes model ولی نه hermes setup

هر دو جریان باید ارائه‌دهنده را بشناسند.

۱۹ هدف‌های جستجوی خوب هنگام پیاده‌سازی

اگر دنبال همهٔ جاهایی هستید که ارائه‌دهنده به آن‌ها دست می‌زند، این نمادها را جستجو کنید:

  • _PROVIDER_ALIASES
  • _PROVIDER_MODELS
  • resolve_runtime_provider
  • _model_flow_
  • select_provider_and_model
  • api_mode
  • _API_KEY_PROVIDER_AUX_MODELS
  • self.client.
