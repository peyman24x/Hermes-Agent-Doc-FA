یکپارچه‌سازی برنامه‌پذیر

هرمس سه پروتکل برای کنترل ایجنت از برنامه‌های خارجی ارائه می‌کند — پلاگین‌های IDE، رابط‌های کاربری سفارشی، خطوط لولهٔ CI و ساب‌ایجنت‌های تعبیه‌شده. گزینه‌ای را انتخاب کنید که با روش انتقال و مصرف‌کنندهٔ شما هماهنگ باشد.

پروتکلانتقالمناسب برایتعریف‌شده در
ACPJSON-RPC روی stdioکلاینت‌های IDE مانند VS Code، Zed و JetBrains که از قبل از پروتکل کلاینت ایجنت پشتیبانی می‌کنندacp_adapter/
گیت‌وی TUIJSON-RPC روی stdio (یا WebSocket)میزبان‌های سفارشی که کنترل دقیق نشست‌ها، فرمان‌های اسلش، تأییدها و رویدادهای استریم را می‌خواهندtui_gateway/server.py
سرور APIHTTP + رویدادهای ارسالی سرور (Server-Sent Events)فرانت‌اندهای سازگار با OpenAI مانند Open WebUI، LobeChat، LibreChat و کلاینت‌های وب مستقل از زبان برنامه‌نویسیgateway/platforms/api_server.py

هر سه همان هستهٔ AIAgent را کنترل می‌کنند. تنها تفاوتشان قالب دادهٔ تبادل‌شده و مجموعهٔ قابلیت‌های در دسترس است.

۱ ACP (پروتکل کلاینت ایجنت)

hermes acp سرور JSON-RPC روی stdio را با پروتکل ACP راه‌اندازی می‌کند. VS Code (افزونهٔ ACP از Zed Industries)، Zed و هر IDE از JetBrains با پلاگین ACP در محیط عملیاتی از آن استفاده می‌کنند.

قابلیت‌های ارائه‌شده: ایجاد نشست، ارسال پرامپت، قطعه‌های استریم پیام ایجنت، رویدادهای فراخوانی ابزار، درخواست مجوز، انشعاب نشست، لغو و احراز هویت. خروجی ابزار به بلوک‌های محتوای Diff/ToolCall در ACP تبدیل می‌شود که IDE آن‌ها را می‌فهمد.

چرخهٔ حیات کامل، پل رویداد و جریان تأیید را در درون‌مایهٔ ACP ببینید.

hermes acp                  # serve ACP on stdio
hermes acp --check          # verify ACP dependencies and adapter imports
hermes acp --setup          # interactive provider/model setup for ACP terminal auth

عقب‌بردن تاریخچه در prompt.submit

عقب‌بردن / ویرایش / تولید دوباره، یک prompt.submit است که پیش از اجرای نوبت جدید بخشی از رونوشت ذخیره‌شده را حذف می‌کند. چون این نوشتن، بازنویسی مخربِ ردیف‌های پایدار نشست است، گیت‌وی تنها وقتی آن را می‌پذیرد که کلاینت قصد خود را اعلام کند:

پارامترمعنا
truncate_before_user_ordinalاندیس از صفرِ نوبت کاربر که برش از آن آغاز می‌شود. همه‌چیز از آن نوبت به بعد حذف می‌شود. ردیف‌های صرفاً نمایشی خط زمانی (display_kind) شمرده نمی‌شوند. باید واقعاً عدد صحیح باشد — مقدار بولی JSON با کد 4004 رد می‌شود.
truncate_before_row_idشناسهٔ عدد صحیحِ ردیف SQLite (messages.id / row_id) برای نوبت کاربر هدفِ برش. آدرس پایدار ترجیحی است. وقتی هم شمارهٔ ترتیبی و هم شناسهٔ ردیف داده شوند، گیت‌وی تطابقشان را بررسی می‌کند (در صورت عدم تطابق 4030 برمی‌گرداند). شناسهٔ ردیف ناشناخته/قدیمی با 4018 رد می‌شود — به شمارهٔ ترتیبی رجوع نمی‌کند.
confirm_truncateهر زمان شمارهٔ ترتیبی، شناسهٔ پیام یا شناسهٔ ردیف ارسال شود لازم است. اعلام می‌کند این ارسال واقعاً عقب‌بردن است، نه ارسال عادی با پارامترهای باقی‌ماندهٔ تصادفی. ارسال آن بدون هدف با کد 4004 رد می‌شود.
confirm_empty_truncateوقتی برش رونوشت را خالی می‌کند (شمارهٔ ترتیبی 0) علاوه بر مورد قبلی لازم است.

پارامتر برش بدون confirm_truncate با کد 4004 یا 4029 رد می‌شود و چیزی نوشته نمی‌شود. میزبان‌هایی که عقب‌بردن را پیاده‌سازی می‌کنند باید همان لحظهٔ درخواست کاربر این پرچم را تنظیم کنند و هرگز پارامترهای برش را بین ارسال‌های عادی در وضعیت نگه ندارند. truncate_before_row_id (از row_id / _row_id هنگام ازسرگیری) را بر شماره‌های ترتیبی ترجیح دهید؛ شمارهٔ ترتیبی را فقط وقتی هنوز شناسهٔ پایدار ندارید، برای سازگاری عقب‌رو / مسیر ردیف خوش‌بینانه نگه دارید.

در ارسال همراه با برشِ موفق روی نشست پایدار، نتیجهٔ prompt.submit علاوه بر موارد دیگر شامل survivor_user_row_ids است — شناسه‌های تازهٔ ردیف‌های نوبت‌های کاربر باقی‌مانده پس از بازنویسی، به ترتیب شمارهٔ ترتیبیِ کاربران قابل‌مشاهده. بازنویسی، پیشوند نگه‌داشته‌شده را به‌صورت ردیف‌های جدید درج می‌کند؛ بنابراین هر شناسه‌ای که میزبان پیش از عقب‌بردن کش کرده، پس از آن قدیمی است. شناسه‌های کش‌شده را از این فهرست دوباره متصل کنید (ورودی null یعنی آن نوبت شناسهٔ پایدار ندارد — شناسهٔ کش‌شده را حذف کنید)، وگرنه عقب‌بردن بعدی که نوبت قدیمی‌ترِ باقی‌مانده را هدف می‌گیرد با 4018 رد می‌شود.

رویدادهای استریم برگشتی

message.delta، message.complete، tool.start، tool.progress، tool.complete، approval.request، clarify.request، sudo.request، sudo.expire، secret.request، secret.expire، gateway.ready، به‌علاوهٔ رویدادهای چرخهٔ حیات نشست و خطا. رویدادهای انقضا همان { request_id } اصلی را حمل می‌کنند؛ میزبان خارجی باید فقط پرامپت در انتظارِ متناظر را پاک کند.

۳ سرور API سازگار با OpenAI

gateway/platforms/api_server.py هرمس را از طریق HTTP در اختیار هر کلاینتی می‌گذارد که از قبل قالب OpenAI را پشتیبانی می‌کند. برای فرانت‌اند وب، اجراگر CI مبتنی بر curl یا مصرف‌کنندهٔ غیرپایتونی مفید است.

نقطه‌های پایانی:

POST /v1/chat/completions        OpenAI Chat Completions (streaming via SSE)
POST /v1/responses               OpenAI Responses API (stateful)
POST /v1/runs                    Start a run, returns run_id (202)
GET  /v1/runs/{id}               Run status
GET  /v1/runs/{id}/events        SSE stream of lifecycle events
POST /v1/runs/{id}/approval      Resolve a pending approval
POST /v1/runs/{id}/steer         Inject mid-run guidance at the next tool boundary
POST /v1/runs/{id}/stop          Interrupt the run
GET  /v1/capabilities            Machine-readable feature flags
POST /v1/browser-control/register Register a browser controller
GET  /v1/browser-control/ws       Browser-controller WebSocket
GET  /v1/models                  Lists hermes-agent
GET  /api/model/options          Provider-aware picker inventory
GET  /health, /health/detailed

راه‌اندازی، هدرها (X-Hermes-Session-Id، X-Hermes-Session-Key) و اتصال فرانت‌اند را در سرور API ببینید.

افزونه‌های مرورگر می‌توانند پروتکل کنترل‌کننده را که پیش‌فرض غیرفعال است صریحاً فعال کنند تا دقیقاً همان نشست مرورگری را کنترل کنند که گفتگوی هرمس را باز کرده است. انتقال‌های API و داشبورد از یک واسط مقید به هویت امنیتی و یک فهرست مجاز صریحِ قابلیت‌ها استفاده می‌کنند؛ کنترل افزونهٔ مرورگر را ببینید.

رابط‌های فهرست مدل

API سازگار با OpenAI عمداً GET /v1/models را حداقلی نگه می‌دارد: این نقطهٔ پایانی سازگاری است که فرانت‌اندها انتظار دارند، نه فهرست کامل انتخابگر ارائه‌دهنده/مدل هرمس.

اگر لایهٔ کنترل خارجی به ردیف‌های گزینش‌شدهٔ ارائه‌دهندگان هرمس، قیمت‌گذاری هر مدل یا راهنمای قابلیت‌ها نیاز دارد، یکی از رابط‌های انتخابگرِ نیازمند احراز هویت را استفاده کنید:

  • REST سرور API: GET /api/model/options با کلید bearer سرور API
  • REST بک‌اند داشبورد: GET /api/model/options با X-Hermes-Session-Token
  • RPC گیت‌وی TUI: model.options

این رابط‌ها سازندهٔ بدنهٔ داده و سیاست بررسی ارائه‌دهندهٔ سفارشی یکسانی دارند:

  • بازشدن عادی: فقط ارائه‌دهندهٔ سفارشی فعلی بررسی می‌شود تا نقطه‌های پایانی ذخیره‌شدهٔ آفلاین انتخابگر را معطل نکنند.
  • نوسازی صریح (refresh=1 یا refresh: true): کش مدل‌های ارائه‌دهنده باطل و همهٔ ارائه‌دهندگان سفارشی ذخیره‌شده بررسی می‌شوند تا فهرست‌های زنده کاملاً دوباره پر شوند.

برای سازگاری با کلاینت OpenAI از /v1/models استفاده کنید. هنگام ساخت انتخابگر مدلِ آگاه از هرمس، از /api/model/options یا model.options استفاده کنید.

POST /v1/runs/{id}/steer معادل HTTP فرمان /steer هرمس است: نوبت کاربر جدیدی ایجاد نمی‌کند و خروجی دستیارِ در حال تولید را فوراً بازنویسی نمی‌کند. در عوض متن به اجرای زنده افزوده می‌شود و پس از مرز ابزار بعدی برای ایجنت قابل‌مشاهده می‌شود تا بدون دورریختن حلقهٔ جاریِ فراخوانی ابزار مسیرش را اصلاح کند.

/v1/runs/{id}/steer فقط وقتی وضعیت اجرا running باشد پذیرفته می‌شود. اجراهای در صف، متوقف در انتظار تأیید، در حال توقف، لغوشده، شکست‌خورده و تکمیل‌شده 409 run_not_accepting_steer برمی‌گردانند؛ حتی اگر سرور هنگام خاموشی مشارکتی هنوز ارجاع‌های داخلی ایجنت را نگه داشته باشد.

کد 200 (و رویداد run.steered) یعنی متن در صف قرار گرفت، نه اینکه ایجنت آن را مصرف کرده است. اگر هدایت پس از پاسخ نهایی ایجنت برسد — بدون مرز ابزار بعدی برای تحویل — متن تحویل‌نشده به‌صورت pending_steer در رویداد پایانی run.completed و وضعیت اجرا برمی‌گردد تا کلاینت به‌جای ازدست‌دادنش آن را به‌عنوان نوبت کاربر بعدی بازپخش کند.

۴ از کدام استفاده کنم؟

  • پلاگین IDE می‌نویسید و IDE از قبل ACP را پشتیبانی می‌کند ← ACP. سمت IDE هیچ کار پروتکلی لازم نیست.
  • میزبان سفارشی دسکتاپ / وب / TUI می‌نویسید و تمام قابلیت‌های هرمس را می‌خواهید (فرمان‌های اسلش، تأییدها، درخواست توضیح، چندایجنتی، انشعاب نشست) ← JSON-RPC گیت‌وی TUI.
  • فرانت‌اند سازگار با OpenAI، کلاینت HTTP مستقل از زبان یا اتوماسیون مبتنی بر curl می‌خواهید ← سرور API.
  • تعبیهٔ درون‌فرایندی پایتون بدون زیرفرایند می‌خواهید ← مستقیماً run_agent.AIAgent را ایمپورت کنید. حلقهٔ ایجنت را ببینید.

۵ تعویض مدل حین اجرا

تعویض مدل در میانهٔ نشست روی تمام رابط‌ها کار می‌کند — پشت صحنه همان فرمان اسلش /model است.

  • CLI / TUI: /model claude-sonnet-4 یا /model openrouter:anthropic/claude-sonnet-4.6
  • RPC گیت‌وی TUI: command.dispatch با {"command": "/model claude-sonnet-4"}
  • ACP: IDE فرمان اسلش را به‌عنوان پرامپت می‌فرستد؛ ایجنت آن را اجرا می‌کند
  • سرور API: فیلد model را در بدنهٔ درخواست بگنجانید

تعیین مدل با درنظرگرفتن ارائه‌دهنده به‌صورت داخلی انجام می‌شود (نام مدل یکسان، قالب درست را برای هر ارائه‌دهنده‌ای که استفاده می‌کنید انتخاب می‌کند). hermes_cli/model_switch.py را ببینید.

۶ نکته‌ای دربارهٔ --mode rpc

هرمس پرچم --mode rpc ندارد. سه پروتکل بالا از قبل موارد استفاده را پوشش می‌دهند — ACP برای کلاینت‌های پروتکل IDE، گیت‌وی TUI برای میزبان‌های JSON-RPC روی stdio و سرور API برای HTTP. اگر شکاف واقعی‌ای یافتید که هیچ‌کدام پر نمی‌کنند، با توضیح مصرف‌کنندهٔ مشخصی که می‌سازید یک ایشو باز کنید.
