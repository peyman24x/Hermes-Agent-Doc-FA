فشرده‌سازی و کش زمینه

Hermes Agent از یک سامانهٔ فشرده‌سازی دوگانه و کش پرامپت Anthropic برای مدیریت بهینهٔ مصرف پنجرهٔ زمینه در گفتگوهای طولانی استفاده می‌کند.

فایل‌های منبع: agent/context_engine.py (ABC)، agent/context_compressor.py (موتور پیش‌فرض)، agent/prompt_caching.py، gateway/run.py (بهداشت نشست)، run_agent.py (جستجو برای _compress_context)

۱ موتور زمینهٔ قابل‌تعویض

مدیریت زمینه بر پایهٔ ABC به نام ContextEngine (agent/context_engine.py) ساخته شده است. ContextCompressor داخلی پیاده‌سازی پیش‌فرض است، اما پلاگین‌ها می‌توانند آن را با موتورهای جایگزین (مثلاً Lossless Context Management) عوض کنند.

context:
  engine: "compressor"    # پیش‌فرض — خلاصه‌سازیِ با اتلافِ داخلی
  engine: "lcm"           # مثال — پلاگینی که زمینهٔ بدون اتلاف فراهم می‌کند

موتور مسئول این کارها است:

  • تصمیم‌گیری دربارهٔ زمان فعال‌شدن فشرده‌سازی (should_compress())
  • انجام فشرده‌سازی (compress())
  • در صورت نیاز در اختیار گذاشتن ابزارهایی که ایجنت می‌تواند فراخوانی کند (مثلاً lcm_grep)
  • پیگیری مصرف توکن از پاسخ‌های API

انتخاب موتور از طریق context.engine در config.yaml و بر اساس پیکربندی انجام می‌شود. ترتیب حل‌شدن:

  1. بررسی پوشهٔ plugins/context_engine/<name>/
  2. بررسی سامانهٔ عمومی پلاگین (register_context_engine())
  3. بازگشت به ContextCompressor داخلی

موتورهای پلاگینی هرگز به‌طور خودکار فعال نمی‌شوند — کاربر باید صریحاً context.engine را روی نام پلاگین تنظیم کند. مقدار پیش‌فرض "compressor" همیشه از موتور داخلی استفاده می‌کند.

پیکربندی از طریق hermes plugins و سپس Provider Plugins و Context Engine، یا با ویرایش مستقیم config.yaml.

برای ساخت پلاگین موتور زمینه، به پلاگین موتور زمینه نگاه کنید.

۲ سامانهٔ فشرده‌سازی دوگانه

هرمس دو لایهٔ فشرده‌سازی جداگانه دارد که مستقل از هم کار می‌کنند:

                     ┌──────────────────────────┐
  Incoming message   │   Gateway Session Hygiene │  Fires at 85% of context
  ─────────────────► │   (pre-agent, rough est.) │  Safety net for large sessions
                     └─────────────┬────────────┘
                                   │
                                   ▼
                     ┌──────────────────────────┐
                     │   Agent ContextCompressor │  Fires at 50% of context (default)
                     │   (in-loop, real tokens)  │  Normal context management
                     └──────────────────────────┘

۱. بهداشت نشست گیت‌وی (آستانهٔ ۸۵٪)

در gateway/run.py قرار دارد (جستجو برای Session hygiene: auto-compress). این یک تور ایمنی است که قبل از پردازش پیام توسط ایجنت اجرا می‌شود. وقتی نشست‌ها بین نوبت‌ها بیش از حد بزرگ شوند (مثلاً انباشت یک‌شبه در Telegram/Discord) از خطاهای API جلوگیری می‌کند.

  • آستانه: ثابت روی ۸۵٪ طول زمینهٔ مدل
  • منبع توکن: ترجیحاً توکن‌های واقعیِ گزارش‌شده از API در نوبت آخر؛ در غیر این صورت بازگشت به تخمین تقریبی مبتنی بر کاراکتر (estimate_messages_tokens_rough)
  • فعال‌شدن: فقط وقتی len(history) >= 4 باشد و فشرده‌سازی فعال باشد
  • هدف: گرفتن نشست‌هایی که از فشرده‌ساز خودِ ایجنت فرار کرده‌اند

آستانهٔ بهداشت گیت‌وی عمداً بالاتر از فشرده‌ساز ایجنت گذاشته شده است. تنظیم آن روی ۵۰٪ (مثل خود ایجنت) باعث فشرده‌سازی زودهنگام در هر نوبت از نشست‌های طولانی گیت‌وی می‌شد.

۲. ContextCompressor ایجنت (آستانهٔ ۵۰٪، قابل‌پیکربندی)

در agent/context_compressor.py قرار دارد. این سامانهٔ اصلی فشرده‌سازی است که داخل حلقهٔ ابزار ایجنت اجرا می‌شود و به شمارش‌های دقیق توکنِ گزارش‌شده از API دسترسی دارد.

۳ پیکربندی

همهٔ تنظیمات فشرده‌سازی از config.yaml و زیر کلید compression خوانده می‌شوند:

compression:
  enabled: true              # فعال/غیرفعال کردن فشرده‌سازی (پیش‌فرض: true)
  threshold: 0.50            # کسری از پنجرهٔ زمینه (پیش‌فرض: 0.50 = 50%)
  # model_thresholds:        # بازنویسی آستانه به‌ازای هر مدل (تطبیق زیررشته،
  #   "glm-5.2": 0.40        # کلید بلندتر برنده است). بخش «بازنویسی آستانهٔ
  #   "claude-sonnet": 0.35  # به‌ازای هر مدل» را در پایین ببینید.
  target_ratio: 0.20         # چه کسری از آستانه به‌عنوان دُم نگه داشته شود (پیش‌فرض: 0.20)
  tail_mode: legacy          # سیاست نگه‌داری دُم: legacy | lean (پیش‌فرض: legacy)
  protect_last_n: 20         # حداقل پیام‌های محافظت‌شدهٔ دُم (پیش‌فرض: 20)
  min_tail_user_messages: 1  # پیام‌های واقعی کاربر که در دُم تضمین می‌شوند (پیش‌فرض: 1)
  codex_gpt55_autoraise: true  # gpt-5.5 روی Codex OAuth: بالا بردن ماشه تا 85% (پیش‌فرض: true)
  codex_gpt55_autoraise_notice: true  # نمایش اعلان یک‌بارهٔ افزایش خودکار (پیش‌فرض: true)
  codex_app_server_auto: native  # native|hermes|off برای فشرده‌سازی رشتهٔ Codex app-server
  codex_responses_native: false  # gpt-5.6 روی OpenAI/Codex مستقیم: فشرده‌سازی سمت سرور (داوطلبانه)
  codex_responses_compact_threshold: 200000  # ماشهٔ فشرده‌سازی سمت سرور (توکن‌های ورودی)
  in_place: true             # فشرده‌سازی روی همان شناسهٔ نشست، بدون چرخش (پیش‌فرض: true)

# مدل/ارائه‌دهندهٔ خلاصه‌سازی زیر auxiliary پیکربندی می‌شود:
auxiliary:
  compression:
    model: null              # بازنویسی مدل برای خلاصه‌ها (پیش‌فرض: تشخیص خودکار)
    provider: auto           # ارائه‌دهنده: "auto"، "openrouter"، "nous"، "main" و غیره
    base_url: null           # نقطهٔ پایانی سفارشی سازگار با OpenAI

فشرده‌سازی درجا (شناسهٔ نشست یکتا و پایدار)

با compression.in_place: true (پیش‌فرض)، هر فشرده‌سازی فهرست زندهٔ پیام‌ها را روی همان شناسهٔ نشست بازنویسی می‌کند: پرامپت سیستمی از نو ساخته می‌شود، بخش میانیِ خلاصه‌شده جایگزین می‌شود و نوبت‌های پیش از فشرده‌سازی زیر همان شناسه به‌صورت نرم آرشیو می‌شوند (active=0, compacted=1 در ذخیره‌ساز نشست) — همچنان از طریق session_search قابل‌جستجو و قابل‌بازیابی است و هرگز حذف نمی‌شود. هیچ زنجیرهٔ parent_session_id و هیچ شماره‌گذاری مجددِ name #N وجود ندارد؛ یک گفتگو در تمام عمر خود یک شناسهٔ بادوام نگه می‌دارد. این کار خوشهٔ باگ‌های چرخش نشست را از بین برد (از دست رفتن وضعیت /goal، نشست‌های بی‌سرپرست، شکاف‌های جستجو در مرزها).

مصرف‌کنندگان به‌جای دیف‌کردن شناسه‌های نشست، خود حالت را مشاهده می‌کنند:

  • رویداد session:compress شامل in_place: true/false و old_session_id است (در حالت درجا رشتهٔ خالی، چون شناسهٔ قدیمی وجود ندارد).
  • گیت‌وی مبنای مدیریت رونوشت گفتگو را از فلگِ مستقل از چرخشِ ایجنت یعنی _last_compaction_in_place می‌گیرد، نه از دیفِ تغییر شناسه.

برای بازگرداندن مسیر قدیمیِ چرخشی in_place: false بگذارید؛ در آن حالت هر فشرده‌سازی یک شناسهٔ نشست جدید ثبت می‌کند که از طریق parent_session_id به شناسهٔ قبلی پیوند دارد.

بازنویسی آستانه به‌ازای هر مدل

compression.model_thresholds اجازه می‌دهد فشرده‌سازی را بسته به مدل فعال در نقاط متفاوتی فعال کنید — وقتی بین مدل‌هایی با پنجره‌های زمینهٔ بسیار متفاوت جابه‌جا می‌شوید مفید است (مثلاً مدل با زمینهٔ ۱ میلیون توکنی می‌تواند دیرتر فشرده کند، در حالی که مدل ۱۲۸ هزار توکنی باید زودتر فشرده کند):

compression:
  threshold: 0.50
  model_thresholds:
    "glm-5.2": 0.40
    "glm-5.2-1M": 0.25
    "claude-sonnet": 0.35

قواعد حل‌شدن:

  • کلیدها بر اساس تطبیق زیررشته با نام مدل مقایسه می‌شوند؛ کلیدِ تطبیق‌یافتهٔ بلندتر برنده است (برای مدل glm-5.2-1M، کلید glm-5.2-1M بر glm-5.2 غلبه می‌کند).
  • وقتی هیچ کلیدی تطبیق نکند (یا نقشه خالی باشد)، threshold سراسری اعمال می‌شود.
  • بازنویسی با هر تغییر مدل از طریق /model دوباره حل می‌شود؛ رفتن به مدلی بدون کلیدِ تطبیقی به threshold سراسری برمی‌گردد.
  • کف زمینهٔ کوچک همچنان روی بازنویسی‌ها اعمال می‌شود (فقط به بالا): مدل‌هایی با پنجرهٔ زمینهٔ کمتر از ۵۱۲K در 0.75 کف‌گذاری می‌شوند؛ پس بازنویسیِ زیر کف به 0.75 بالا برده می‌شود، در حالی که بازنویسیِ بالای آن (مثلاً 0.80) برنده است.

موتورهای زمینهٔ پلاگینی می‌توانند همان منطق حل‌شدن را از طریق from agent.context_compressor import resolve_model_threshold بازاستفاده کنند؛ موتورهایی که update_model() را بازنویسی می‌کنند، سیاست فشرده‌سازی خودشان را دارند و ممکن است این نقشه را نادیده بگیرند.

افزایش خودکار آستانه برای gpt-5.5 در Codex

بک‌اند ChatGPT Codex OAuth پنجرهٔ زمینهٔ gpt-5.5 را سخت به ۲۷۲K محدود می‌کند (همین اسلاگ روی API مستقیم OpenAI و OpenRouter مقدار ۱.۰۵M و روی GitHub Copilot مقدار ۴۰۰K را نشان می‌دهد). با ماشهٔ پیش‌فرض ۵۰٪، فشرده‌سازی در حدود ۱۳۶K فعال می‌شد — نصف پنجره‌ای که مدل واقعاً می‌تواند استفاده کند. وقتی مسیر فعال Codex OAuth باشد (provider: openai-codex) و مدل gpt-5.5 باشد، هرمس ماشه را به ۸۵٪ (حدود ۲۳۱K) بالا می‌برد و اعلانی همراه با فرمان انصراف نشان می‌دهد. این اعلان برای هر پروفایل یک‌بار نشان داده می‌شود — یک نشانگر زیر $HERMES_HOME (به نام .codex_gpt55_autoraise_notice) ثبت می‌کند که اجرا شده است، تا راه‌اندازی‌های مکرر ایجنت/نشست (مثلاً هر پیام ورودی گیت‌وی) دوباره صادرش نکنند؛ اگر بعدها آستانهٔ افزایش‌یافته تغییر کند، یک‌بار دیگر اعلان می‌دهد. فقط همین مسیر مشخص تحت تأثیر است؛ gpt-5.5 روی هر ارائه‌دهندهٔ دیگر، threshold سراسری شما را نگه می‌دارد. برای برگشتن به مقدار سراسری:

hermes config set compression.codex_gpt55_autoraise false

برای حفظ افزایش خودکار ۸۵٪ ولی پنهان‌کردن فقط اعلان یک‌باره:

hermes config set compression.codex_gpt55_autoraise_notice false

واریانت‌های -900k با زمینهٔ بزرگ در Codex (داوطلبانه)

بک‌اند ChatGPT Codex برای خانواده‌های gpt-5.4 و gpt-5.6 (Sol/Terra/Luna) پنجرهٔ ۲۷۲K را اعلام می‌کند، اما در واقع حدود ۹۱۱K توکن ورودی را برای حساب‌های اشتراکی ChatGPT می‌پذیرد (راستی‌آزمایی‌شدهٔ زنده در اوت ۲۰۲۶). هرمس برای اسلاگ‌های پایه همان ۲۷۲K اعلام‌شده را پیش‌فرض نگه می‌دارد — پنجرهٔ بزرگ‌تر یعنی توکن بیشتر در هر درخواست و سوختن بسیار سریع‌ترِ سهمیهٔ اشتراک؛ پس پنجرهٔ بزرگ کاملاً داوطلبانه است.

برای استفاده از پنجرهٔ بزرگ، واریانت صریح -900k را در /model انتخاب کنید (مثلاً gpt-5.6-sol-900k، gpt-5.6-terra-900k، gpt-5.6-luna-900k، gpt-5.4-900k). این‌ها نام‌های مستعار سمت هرمس هستند: پسوند قبل از ارسال شناسهٔ مدل به بک‌اند حذف می‌شود و حسابداری قیمت/مصرف آن‌ها را مثل مدل پایه می‌بیند. اسلاگ‌هایی که واقعاً ۲۷۲K را اعمال می‌کنند (gpt-5.5، gpt-5.4-mini) واریانت -900k ندارند.

آستانه‌های فشرده‌سازی تابع پنجره‌اند: اسلاگ‌های پایه (۲۷۲K) همان افزایش خودکار ۸۵٪ توضیح‌داده‌شدهٔ بالا را می‌گیرند، در حالی که واریانت‌های -900k مقدار سراسری compression.threshold شما را نگه می‌دارند (پیش‌فرض ۵۰٪، حدود ۴۵۰K) — افزایش خودکار برای جلوگیری از هدررفت یک پنجرهٔ کوچک است، چیزی که پنجرهٔ ۹۰۰K به آن نیاز ندارد.

فشرده‌سازی رشتهٔ Codex app-server

نشست‌های Codex app-server (api_mode: codex_app_server — زمان اجرای CLI/ایجنتِ codex) با همهٔ مسیرهای دیگر فرق دارند: ایجنت codex مالک زمینهٔ رشتهٔ پشتیبان است، پس خلاصه‌ساز کمکیِ هرمس نمی‌تواند آن را کوچک کند — بازنویسی آینهٔ محلیِ رونوشت، رشتهٔ واقعی را تا یک ریست کامل زمینه بدون‌مرز رشد می‌گذارد. برای این زمان اجرا، فشرده‌سازی به‌جای آن از سازوکار خود app-server عبور می‌کند:

  • فشرده‌سازی دستی (/compress) از app-server می‌خواهد رشته را فشرده کند (thread/compact/start) و منتظر کامل‌شدن نوبت فشرده‌سازی می‌ماند.
  • فشرده‌سازی خودکار با compression.codex_app_server_auto کنترل می‌شود: مقدار پیش‌فرض native اجازه می‌دهد خود app-server تصمیم بگیرد چه زمانی فشرده کند و هرمس رویدادهای فشرده‌سازیِ حاصل را ثبت می‌کند (شمارنده‌های فشرده‌سازی، رویدادهای نشست). مقدار hermes را بگذارید تا آستانهٔ فشرده‌سازی هرمس، فشرده‌سازی app-server را آغاز کند، یا off تا فشرده‌سازی خودکارِ آغازشده توسط هرمس کاملاً غیرفعال شود (codex همچنان می‌تواند به‌صورت بومی فشرده کند).

رونوشت محلی هرمس روی این زمان اجرا هرگز بازنویسی نمی‌شود — state.db مرز فشرده‌سازی را ثبت می‌کند در حالی که رونوشتِ قابل‌مشاهده دست‌نخورده می‌ماند. همهٔ مسیرهای دیگر (از جمله نشست‌های چت Codex OAuth) از فشرده‌ساز خلاصهٔ هرمس استفاده می‌کنند.

فشرده‌سازی بومی Responses (gpt-5.6 روی OpenAI مستقیم / اشتراک Codex)

Responses API در OpenAI از فشرده‌سازی سمت سرور پشتیبانی می‌کند: وقتی درخواست شامل context_management: [{type: "compaction", compact_threshold: N}] باشد و ورودی رندرشده از N توکن عبور کند، سرور زمینهٔ قدیمی‌تر را به یک آیتم خروجی رمزنگاری‌شده و غیرقابل‌خواندن به نام compaction هرس می‌کند. هرمس آن آیتم را به sidecar پخشِ موجودِ پیام دستیار اضافه می‌کند و در نوبت‌های بعدی برمی‌گرداند تا جایگزین تاریخچهٔ هرس‌شده باشد — بازیابی بلندمدت بدون گذر خلاصه‌سازی سمت کلاینت، و سازگار با ZDR (store: false، بدون previous_response_id).

با compression.codex_responses_native: true فعالش کنید. این گیت عمداً باریک است و در هر درخواست دوباره بررسی می‌شود:

  • مدل‌ها: فقط خانوادهٔ gpt-5.6. مدل‌های دیگر وقتی این فیلد حاضر باشد سمت سرور خطا می‌دهند (gpt-5.1/5.2 یا HTTP 500 برمی‌گردانند یا استریم را قفل می‌کنند — هیچ ردِ ساختاریافته‌ای برای سوییچ به مسیر جایگزین وجود ندارد، راستی‌آزمایی‌شدهٔ زنده در اوت ۲۰۲۶).
  • مسیرها: فقط api.openai.com (کلید OpenAI API) یا بک‌اند ChatGPT Codex (OAuth اشتراک Codex). xAI، GitHub/Copilot، OpenRouter، رله‌ها و سرورهای محلی هرگز این فیلد را نمی‌بینند.

همهٔ چیزهای دیگر دربارهٔ فشرده‌سازی بدون تغییر می‌ماند: فشرده‌ساز محلی به‌عنوان مالک پشتیبان مسلح می‌ماند (آستانهٔ بومی حدود ۸K توکن زیر ماشهٔ محلی محدود می‌شود تا سرور اول فشرده‌سازی کند)، و یک ردِ ساختاریافتهٔ ارائه‌دهنده نسبت به این فیلد، فشرده‌سازی بومی را برای آن نشست غیرفعال می‌کند و درخواست را بدون آن دوباره امتحان می‌کند. تغییر نشست به مدل یا مسیری که واجد شرایط نیست، به‌سادگی ارسال فیلد را متوقف می‌کند — چک‌پوینت‌های ثبت‌شده با گارد موجودِ بین-صادرکننده هنگام تغییر نقطهٔ پایانی از پخش حذف می‌شوند.

مقادیر محاسبه‌شده (برای مدلی با زمینهٔ ۲۰۰K در تنظیمات پیش‌فرض)

context_length       = 200,000
threshold_tokens     = 200,000 × 0.50 = 100,000
tail_token_budget    = 100,000 × 0.20 = 20,000
max_summary_tokens   = min(200,000 × 0.05, 12,000) = 10,000
ℹ️ آستانه از پنجرهٔ زمینهٔ مدل اصلی (MAIN) مشتق می‌شود

threshold_tokens همیشه threshold × context_length است، که در آن context_length پنجرهٔ زمینهٔ مدل اصلی ایجنت است — هرگز مدل کمکی/خلاصه‌ساز. روی مدلی با ۲۶۲٬۱۴۴ توکن در پیش‌فرض 0.50، آستانه برابر 262,144 × 0.50 = 131,072 است. نزدیک‌بودن این عدد به «زمینهٔ ۱۲۸K» رایج، تصادفِ درصدها است، نه نشانهٔ این‌که پنجرهٔ مدل کمکی ماشه باشد. پنجرهٔ زمینهٔ مدل کمکی موضوع جداگانه‌ای است — هشدار «طول زمینهٔ مدل خلاصه‌ساز» را در پایین ببینید تا بدانید این پنجره بر این تأثیر می‌گذارد که آیا اصلاً خلاصه‌ای تولید می‌شود، نه این‌که فشرده‌سازی کِی فعال شود.

۴ الگوریتم فشرده‌سازی

متد ContextCompressor.compress() از یک الگوریتم ۴فازی پیروی می‌کند:

فاز ۱: هرس نتایج قدیمی ابزار (ارزان، بدون فراخوانی LLM)

نتایج قدیمی ابزار (بیش از ۲۰۰ کاراکتر) بیرون از دُمِ محافظت‌شده با این جایگزین می‌شوند:

[Old tool output cleared to save context space]

این یک گذر اولیهٔ ارزان است که از خروجی‌های پرحجم ابزار (محتوای فایل‌ها، خروجی ترمینال، نتایج جستجو) توکن‌های قابل‌توجهی ذخیره می‌کند.

فاز ۲: تعیین مرزها

┌─────────────────────────────────────────────────────────────┐
│  Message list                                               │
│                                                             │
│  [0..2]  ← protect_first_n (system + first exchange)        │
│  [3..N]  ← middle turns → SUMMARIZED                        │
│  [N..end] ← tail (by token budget OR protect_last_n)        │
│                                                             │
└─────────────────────────────────────────────────────────────┘

محافظت از دُم مبتنی بر بودجهٔ توکن است: از انتهای فهرست به عقب می‌رود و توکن‌ها را آن‌قدر جمع می‌کند تا بودجه تمام شود. اگر بودجه پیام‌های کمتری را پوشش دهد، به شمار ثابت protect_last_n برمی‌گردد.

مرزها طوری هم‌تراز می‌شوند که گروه‌های tool_call/tool_result از هم نپاشند. متد _align_boundary_backward() از نتایج متوالی ابزار عبور می‌کند تا به پیام دستیارِ والد برسد و گروه‌ها سالم بمانند.

فاز ۳: تولید خلاصهٔ ساختاریافته

⚠️ طول زمینهٔ مدل خلاصه‌ساز

مدل خلاصه‌ساز باید پنجرهٔ زمینه‌ای دست‌کم هم‌اندازهٔ مدل اصلی ایجنت داشته باشد. کل بخش میانی در یک فراخوانی call_llm(task="compression") به مدل خلاصه‌ساز فرستاده می‌شود. اگر زمینهٔ مدل خلاصه‌ساز کوچک‌تر باشد، API خطای طول زمینه برمی‌گرداند — _generate_summary() آن را می‌گیرد، هشدار لاگ می‌کند و None برمی‌گرداند. فشرده‌ساز سپس نوبت‌های میانی را بدون خلاصه حذف می‌کند و زمینهٔ گفتگو بی‌سروصدا از دست می‌رود. این رایج‌ترین علت افت کیفیت فشرده‌سازی است.

نوبت‌های میانی با LLM کمکی و یک قالب ساختاریافته خلاصه می‌شوند:

## Goal
[What the user is trying to accomplish]

## Constraints & Preferences
[User preferences, coding style, constraints, important decisions]

## Progress
### Done
[Completed work — specific file paths, commands run, results]
### In Progress
[Work currently underway]
### Blocked
[Any blockers or issues encountered]

## Key Decisions
[Important technical decisions and why]

## Relevant Files
[Files read, modified, or created — with brief note on each]

## Next Steps
[What needs to happen next]

## Critical Context
[Specific values, error messages, configuration details]

بودجهٔ خلاصه با حجم محتوایی که فشرده می‌شود مقیاس می‌گیرد:

  • فرمول: content_tokens × 0.20 (ثابت _SUMMARY_RATIO)
  • حداقل: ۲٬۰۰۰ توکن
  • حداکثر: min(context_length × 0.05, 12,000) توکن

فاز ۴: سرهم‌بندی پیام‌های فشرده‌شده

فهرست پیام‌های فشرده‌شده چنین است:

  1. پیام‌های سر (با یادداشتی که در اولین فشرده‌سازی به پرامپت سیستمی اضافه می‌شود)
  2. پیام خلاصه (نقش طوری انتخاب می‌شود که نقضِ نقش‌های یکسانِ متوالی پیش نیاید)
  3. پیام‌های دُم (بدون تغییر)

جفت‌های بی‌قرینهٔ tool_call/tool_result با _sanitize_tool_pairs() پاک‌سازی می‌شوند:

  • نتایج ابزاری که به فراخوانی‌های حذف‌شده ارجاع می‌دهند ← حذف می‌شوند
  • فراخوانی‌هایی که نتایجشان حذف شده ← یک استابِ نتیجه تزریق می‌شود

فشرده‌سازی مجدد تکراری

در فشرده‌سازی‌های بعدی، خلاصهٔ قبلی همراه با دستورالعملِ به‌روزرسانی آن به LLM داده می‌شود، نه خلاصه‌کردن از صفر. این کار اطلاعات را در چندین فشرده‌سازی حفظ می‌کند — موارد از «در حال انجام» به «انجام‌شده» منتقل می‌شوند، پیشرفت جدید اضافه می‌شود و اطلاعات منسوخ حذف می‌شود.

فیلد _previous_summary روی نمونهٔ فشرده‌ساز، متن آخرین خلاصه را برای همین منظور نگه می‌دارد.

۶ کش پرامپت (Anthropic)

منبع: agent/prompt_caching.py

با کش‌کردن پیشوند گفتگو، هزینهٔ توکن‌های ورودی را در گفتگوهای چندنوبتی حدود ۷۵٪ کاهش می‌دهد. از نقاط شکست (breakpoint)‌های cache_control در Anthropic استفاده می‌کند.

راهبرد: system_and_3

Anthropic حداکثر ۴ نقطهٔ شکست cache_control در هر درخواست اجازه می‌دهد. هرمس از راهبرد «system_and_3» استفاده می‌کند:

Breakpoint 1: System prompt           (stable across all turns)
Breakpoint 2: 3rd-to-last non-system message  ─┐
Breakpoint 3: 2nd-to-last non-system message   ├─ Rolling window
Breakpoint 4: Last non-system message          ─┘

چطور کار می‌کند

apply_anthropic_cache_control() از پیام‌ها کپی عمیق می‌گیرد و نشانگرهای cache_control تزریق می‌کند:

# قالب نشانگر کش
marker = {"type": "ephemeral"}
# یا برای TTL یک‌ساعته:
marker = {"type": "ephemeral", "ttl": "1h"}

نشانگر بسته به نوع محتوا به شکل متفاوتی اعمال می‌شود:

نوع محتوامحل قرارگیری نشانگر
محتوای رشته‌ایبه [{"type": "text", "text": ..., "cache_control": ...}] تبدیل می‌شود
محتوای لیستیبه دیکشنریِ آخرین عنصر اضافه می‌شود
None/خالیبه‌صورت msg["cache_control"] اضافه می‌شود
پیام‌های ابزاربه‌صورت msg["cache_control"] اضافه می‌شود (فقط Anthropic بومی)

الگوهای طراحی هماهنگ با کش

  1. پرامپت سیستمی پایدار: پرامپت سیستمی نقطهٔ شکست ۱ است و در همهٔ نوبت‌ها کش می‌شود. از تغییر دادن آن در میانهٔ گفتگو بپرهیزید (فشرده‌سازی فقط در اولین فشرده‌سازی یادداشتی اضافه می‌کند).
  2. ترتیب پیام‌ها مهم است: برخورد با کش نیازمند تطبیق پیشوند است. اضافه‌ یا حذف‌کردن پیام در میانه، کشِ همهٔ چیزهای بعد از آن را باطل می‌کند.
  3. تعامل فشرده‌سازی و کش: بعد از فشرده‌سازی، کشِ ناحیهٔ فشرده‌شده باطل می‌شود ولی کشِ پرامپت سیستمی باقی می‌ماند. پنجرهٔ لغزان ۳پیامی ظرف ۱ تا ۲ نوبت کش‌کردن را دوباره برقرار می‌کند.
  4. انتخاب TTL: پیش‌فرض 5m (۵ دقیقه) است. برای نشست‌های طولانی که کاربر بین نوبت‌ها وقفه می‌اندازد از 1h استفاده کنید.
  5. هویت مدل بخشی از کلید کش است: کش‌های سمت ارائه‌دهنده به مدل (و حساب/کلید API)ِ سرویس‌کنندهٔ درخواست محدود هستند. هر تغییر مدل در میانهٔ گفتگو — تغییر صریح با /model، پشتیبان‌رفتن مدل اصلی، یا چرخش استخر اعتبارنامه‌ها به حسابی دیگر — یعنی درخواست بعدی هیچ برخورد کشی ندارد و کل گفتگو را با قیمت بی‌تخفیفِ ورودی دوباره می‌خواند. این ذاتیِ نحوهٔ کار کش‌های ارائه‌دهنده است و هرمس نمی‌تواند از آن بگریزد؛ به همین دلیل مستندات رو به کاربر برای /model، ارائه‌دهندگان پشتیبان و استخرهای اعتبارنامه هشدار هزینه دارند. قابلیتی اضافه نکنید که مدل یا اعتبارنامه‌ها را بی‌سروصدا در میانهٔ نشست عوض کند.

فعال‌کردن کش پرامپت

کش پرامپت به‌طور خودکار وقتی فعال می‌شود که:

  • مدل، یک مدل Claude از Anthropic باشد (از روی نام مدل تشخیص داده می‌شود)
  • ارائه‌دهنده از cache_control پشتیبانی کند (API بومی Anthropic یا OpenRouter)
# config.yaml — TTL قابل پیکربندی است (باید "5m" یا "1h" باشد)
prompt_caching:
  cache_ttl: "5m"

CLI وضعیت کش را هنگام راه‌اندازی نشان می‌دهد:

💾 Prompt caching: ENABLED (Claude via OpenRouter, 5m TTL)

۷ هشدارهای فشار زمینه

هشدارهای میانیِ فشار زمینه حذف شده‌اند (به بلوک بودجهٔ تکرار در run_agent.py نگاه کنید که این یادداشت دارد: "No intermediate pressure warnings — they caused models to 'give up' prematurely on complex tasks"). فشرده‌سازی وقتی فعال می‌شود که توکن‌های پرامپت به compression.threshold پیکربندی‌شده (پیش‌فرض ۵۰٪) برسند، بدون هیچ گام هشدار قبلی؛ بهداشت نشست گیت‌وی هم به‌عنوان تور ایمنی ثانویه در ۸۵٪ پنجرهٔ زمینهٔ مدل فعال می‌شود.
