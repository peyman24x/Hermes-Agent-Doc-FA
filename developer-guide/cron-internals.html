درون‌مایهٔ Cron

زیرسیستم کرون، اجرای وظایف زمان‌بندی‌شده را فراهم می‌کند — از تأخیرهای سادهٔ یک‌بارمصرف تا کارهای تکرارشوندهٔ مبتنی بر عبارت cron، همراه با تزریق مهارت و تحویلِ بین‌پلتفرمی.

۱ فایل‌های کلیدی

۲ مدل زمان‌بندی

چهار قالب زمان‌بندی پشتیبانی می‌شود:

قالبمثالرفتار

سطحِ رو به مدل، یک ابزار واحد cronjob با عملیات‌های اکشن‌محور است: create، list، update، pause، resume، run، remove.

۳ ذخیره‌سازی کارها

کارها در ~/.hermes/cron/jobs.json با معناشناسی نوشتنِ اتمیک ذخیره می‌شوند (نوشتن در فایل موقت، سپس تغییر نام). هر رکورد کار شامل موارد زیر است:

{
  "id": "a1b2c3d4e5f6",
  "name": "Daily briefing",
  "prompt": "Summarize today's AI news and funding rounds",
  "schedule": {
    "kind": "cron",
    "expr": "0 9 * * *",
    "display": "0 9 * * *"
  },
  "skills": ["ai-funding-daily-report"],
  "deliver": "telegram:-1001234567890",
  "repeat": {
    "times": null,
    "completed": 42
  },
  "state": "scheduled",
  "enabled": true,
  "next_run_at": "2025-01-16T09:00:00Z",
  "last_run_at": "2025-01-15T09:00:00Z",
  "last_status": "ok",
  "created_at": "2025-01-01T00:00:00Z",
  "model": null,
  "provider": null,
  "script": null
}

وضعیت‌های چرخهٔ حیات کار

وضعیتمعنا
scheduledفعال؛ در زمان‌بندی بعدی اجرا می‌شود
pausedمعلق — تا زمان از سرگیری، اجرا نمی‌شود
completedشمار تکرار تمام شده یا یک‌بارمصرفی که اجرا شده است
runningدر حال اجرا (وضعیت گذرا)

سازگاری با نسخه‌های قدیمی

کارهای قدیمی‌تر ممکن است به‌جای آرایهٔ skills، یک فیلد تکی skill داشته باشند. زمان‌بند این را هنگام بارگذاری نرمال‌سازی می‌کند — skill تکی به skills: [skill] ارتقا می‌یابد.

۴ زمان اجرای زمان‌بند

چرخهٔ تیک

زمان‌بند روی تیکِ دوره‌ای اجرا می‌شود (پیش‌فرض: هر ۶۰ ثانیه):

tick()
  1. Acquire scheduler lock (prevents overlapping ticks)
  2. Load all jobs from jobs.json
  3. Filter to due jobs (next_run <= now AND state == "scheduled")
  4. For each due job:
     a. Set state to "running"
     b. Create fresh AIAgent session (no conversation history)
     c. Load attached skills in order (injected as user messages)
     d. Run the job prompt through the agent
     e. Deliver the response to the configured target
     f. Update run_count, compute next_run
     g. If repeat count exhausted → state = "completed"
     h. Otherwise → state = "scheduled"
  5. Write updated jobs back to jobs.json
  6. Release scheduler lock

یکپارچگی گیت‌وی

در حالت گیت‌وی، تریگرِ کرون (بخشی که تصمیم می‌گیرد یک کار سررسیده چه زمانی به‌وقت برسد — «محور B») از طریق یک ارائه‌دهندهٔ CronScheduler قابل‌تعویض انتخاب می‌شود. گیت‌وی resolve_cron_scheduler() را صدا می‌زند (cron/scheduler_provider.py) و start() ارائه‌دهندهٔ حل‌شده را در یک نخ پس‌زمینهٔ اختصاصی، در کنار نخِ جداگانهٔ خانه‌داریِ گیت‌وی اجرا می‌کند.

ارائه‌دهندهٔ فعال با کلید پیکربندی cron.provider انتخاب می‌شود:

  • خالی (پیش‌فرض) ← InProcessCronScheduler داخلی، که حلقهٔ تاریخی درون‌پروسسی را اجرا می‌کند و هر ۶۰ ثانیه scheduler.tick() را صدا می‌زند. این رفتار بایت‌به‌بایت با رفتار پیش از ارائه‌دهنده یکسان است.
  • یک ارائه‌دهندهٔ نام‌دار (مثلاً chronos، ارائه‌دهندهٔ کرونِ مدیریت‌شده برای استقرارهایی که به صفر مقیاس می‌شوند) ← از plugins/cron_providers/<name>/ یا $HERMES_HOME/plugins/<name>/ کشف می‌شود.

اگر ارائه‌دهندهٔ نام‌دار غایب باشد، بارگذاری‌اش شکست بخورد، یا is_available() == False گزارش کند، حل‌کننده با یک هشدار به نمونهٔ داخلی برمی‌گردد — کرون هرگز بدون تریگر رها نمی‌شود. ارائه‌دهندهٔ داخلی در هسته (cron/scheduler_provider.py) زندگی می‌کند، نه در plugins/، پس پشتیبان نمی‌تواند به‌طور تصادفی حذف شود.

آنچه «به‌وقت‌رسیدن» معنا می‌دهد (اجرای کار + تحویل) تغییری نکرده و بین همهٔ ارائه‌دهندگان مشترک است — همان‌جا باقی می‌ماند: scheduler.run_job() / scheduler._deliver_result(). ارائه‌دهنده فقط تریگر را کنترل می‌کند، هرگز اجرا را.

در حالت CLI، کارهای کرون فقط وقتی به‌وقت می‌رسند که فرمان‌های hermes cron اجرا شده باشند یا نشست‌های فعال CLI در جریان باشد.

کرون مدیریت‌شده (Chronos) برای مقیاس تا صفر

گیت‌وی‌های میزبانی‌شده می‌توانند به‌جای تیکر داخلی، ارائه‌دهندهٔ Chronos را اجرا کنند (cron.provider: chronos). Chronos به گیت‌ویِ بیکار اجازه می‌دهد به صفر مقیاس شود و همچنان کارهای کرون را به‌وقت اجرا کند: به‌جای حلقهٔ درون‌پروسسیِ ۶۰ ثانیه‌ای (که پروسس را بیدار نگه می‌داشت)، از زیرساخت Nous می‌خواهد دقیقاً یک one-shot مدیریت‌شده به‌ازای هر کار، در زمانِ واقعیِ اجرای بعدیِ همان کار مسلح کند. در زمان اجرا، Nous از طریق یک وب‌هوکِ احرازهویت‌شده (POST /api/cron/fire) دوباره گیت‌وی را صدا می‌زند؛ گیت‌وی کار را از همان مسیر run_one_job نمونهٔ داخلی اجرا می‌کند و سپس one-shot بعدی را دوباره مسلح می‌کند. بین اجراها پروسس می‌تواند کاملاً متوقف باشد — فقط با یک اجرای واقعی بیدار می‌شود، هرگز با تایمر دوره‌ای.

جریان کار (زمان‌بندِ مدیریت‌شده توسط Nous ارائه می‌شود؛ ایجنت هیچ اعتبارنامهٔ زمان‌بندی ندارد):

create/update a cron job
  → Chronos asks Nous to arm a one-shot at the job's next_run_at
      (authenticated with the agent's existing Nous token)
  → at fire time Nous calls the gateway: POST {callback_url}/api/cron/fire
      (authenticated with a short-lived, purpose-scoped Nous-minted JWT)
  → the gateway verifies the token, claims the job (store compare-and-set so
    multi-replica deployments fire at-most-once), runs it, and re-arms the next
    one-shot

پیکربندی (همه غیرمحرمانه؛ روی ایجنت‌های میزبانی‌شده، Nous این‌ها را در زمان فراهم‌سازی تنظیم می‌کند):

کلیدمعنا
cron.providerchronos برای فعال‌سازی (خالی = تیکر داخلی)
cron.chronos.portal_urlURL پایهٔ Nous (مسلح‌سازی + صادرکنندهٔ توکن اجرا)
cron.chronos.callback_urlURL پایهٔ عمومیِ خودِ گیت‌وی برای اجراهای ورودی
cron.chronos.expected_audienceمخاطب (audience) توکن اجرای این ایجنت
cron.chronos.nas_jwks_urlمجموعهٔ کلید برای اعتبارسنجی توکن اجرای ورودی

اگر Chronos بد پیکربندی شده باشد یا ایجنت وارد Nous نشده باشد، resolve_cron_scheduler() به تیکر داخلی برمی‌گردد (با ثبت هشدار در لاگ) — کرون هرگز تریگرش را از دست نمی‌دهد. کارهای تکرارشونده پس از هر اجرا دوباره مسلح می‌شوند؛ کارهای repeat-N وقتی شمارش تمام شود تمیز متوقف می‌شوند (بدون one-shot یتیم). قرارداد کامل سیمیِ ایجنت↔Nous در docs/chronos-managed-cron-contract.md است.

ایزوله‌سازی نشست تازه

هر کار کرون در یک نشست ایجنتِ کاملاً تازه اجرا می‌شود:

  • بدون تاریخچهٔ گفتگو از اجراهای قبلی
  • بدون حافظه از اجراهای قبلی کرون (حافظهٔ مانا — MEMORY.md / USER.md — مثل هر اجرای دیگر ایجنت بارگذاری می‌شود، پس ترجیحات و واقعیت‌های ماندگار باقی می‌مانند؛ زمینهٔ گفتگوی هر اجرا نه)
  • پرامپت باید خودبسنده باشد — کارهای کرون نمی‌توانند سؤال شفاف‌سازی بپرسند
  • تول‌ست cronjob غیرفعال است (گارد بازگشتی)

۵ کارهای مبتنی بر مهارت

یک کار کرون می‌تواند از طریق فیلد skills یک یا چند مهارت پیوست کند. در زمان اجرا:

  1. مهارت‌ها به ترتیب مشخص‌شده بارگذاری می‌شوند
  2. محتوای SKILL.md هر مهارت به‌عنوان زمینه تزریق می‌شود
  3. پرامپت کار به‌عنوان دستورِ کار ضمیمه می‌شود
  4. ایجنت مجموعِ زمینهٔ مهارت + پرامپت را پردازش می‌کند

این قابلیت، گردش‌کارهای قابل‌استفادهٔ مجدد و تست‌شده را بدون چسباندن دستورالعمل کامل در پرامپت‌های کرون ممکن می‌کند. برای مثال:

Create a daily funding report → attach "ai-funding-daily-report" skill

کارهای مبتنی بر اسکریپت

کارها همچنین می‌توانند از طریق فیلد script یک اسکریپت پایتون پیوست کنند. اسکریپت قبل از هر نوبت ایجنت اجرا می‌شود و خروجی stdout آن به‌عنوان زمینه در پرامپت تزریق می‌شود. این، الگوهای جمع‌آوری داده و تشخیص تغییر را ممکن می‌کند:

# ~/.hermes/scripts/check_competitors.py
import requests, json
# یادداشت‌های انتشار رقبا را بگیر، با اجرای قبلی diff بزن
# خلاصه را در stdout چاپ کن — ایجنت تحلیل و گزارش می‌کند

تایم‌اوت اسکریپت به‌طور پیش‌فرض ۳۶۰۰ ثانیه (۱ ساعت) است. _get_script_timeout() این محدودیت را از طریق یک زنجیرهٔ سه‌لایه حل می‌کند:

  1. بازنویسی در سطح ماژول — _SCRIPT_TIMEOUT (برای تست‌ها/monkeypatching). فقط وقتی استفاده می‌شود که با پیش‌فرض فرق داشته باشد.
  2. متغیر محیطی — HERMES_CRON_SCRIPT_TIMEOUT
  3. پیکربندی — cron.script_timeout_seconds در config.yaml (خوانده‌شده از طریق load_config())
  4. پیش‌فرض — ۳۶۰۰ ثانیه (۱ ساعت)

این تایم‌اوت فقط اسکریپتِ پیش از اجرا را محدود می‌کند، نه ایجنت را. کارهای مبتنی بر مهارت / رانده‌شده با LLM روی بودجهٔ جداگانه‌ای بر مبنای بی‌فعالیتی اجرا می‌شوند (HERMES_CRON_TIMEOUT، پیش‌فرض ۶۰۰ ثانیه بیکاری، 0 = نامحدود) — این کارها می‌توانند ساعت‌ها اجرا شوند تا وقتی مدام ابزار فراخوانی می‌کنند یا توکن استریم می‌کنند، و فقط پس از دورهٔ بیکاریِ پیکربندی‌شده و بدون هیچ فعالیتی کشته می‌شوند. اسکریپت‌ها به یک استخر نخِ ماندگار سپرده می‌شوند (تحت قفل تیک نگه داشته نمی‌شوند)، پس یک اسکریپت طولانی‌اجرا مانع به‌وقت‌رسیدنِ کارهای سررسیدهٔ دیگر نمی‌شود.

بازیابی ارائه‌دهنده

run_job() ارائه‌دهندگان پشتیبان و استخر اعتبارنامهٔ پیکربندی‌شدهٔ کاربر را به نمونهٔ AIAgent می‌دهد:

  • ارائه‌دهندگان پشتیبان — fallback_providers (لیست) یا fallback_model (دیکشنری قدیمی) را از config.yaml می‌خواند، مطابق الگوی _load_fallback_model() گیت‌وی. به‌صورت fallback_model= به AIAgent.__init__ داده می‌شود که هر دو قالب را به یک زنجیرهٔ پشتیبان نرمال‌سازی می‌کند.
  • استخر اعتبارنامه — از طریق load_pool(provider) از agent.credential_pool با نام ارائه‌دهندهٔ زمان‌اجرای حل‌شده بارگذاری می‌شود. فقط وقتی داده می‌شود که استخر اعتبارنامه داشته باشد (pool.has_credentials()). چرخش کلیدِ همان ارائه‌دهنده را روی خطاهای 429/محدودیت نرخ ممکن می‌کند.

این کار آینهٔ رفتار گیت‌وی است — بدون آن، ایجنت‌های کرون روی محدودیت‌های نرخ شکست می‌خوردند بدون آنکه تلاشی برای بازیابی کنند.

۶ مدل تحویل

نتایج کارهای کرون را می‌توان به هر پلتفرم پشتیبانی‌شده‌ای تحویل داد.

یک نام پلتفرمِ لخت (slack، telegram و...) به کانال خانه پیکربندی‌شدهٔ آن پلتفرم تحویل می‌دهد. برای نشانه‌گیری یک مقصد خاص، بعد از دونقطه یک هدف اضافه کنید: platform:<target>. هدف در زمان اجرا حل می‌شود (نه هنگام ساخته‌شدن کار)، پس یک کار می‌تواند مقصدی روی پلتفرمی که هنوز متصل نشده نام ببرد و به‌محض آنلاین‌شدن آن، تحویل را شروع کند.

بیشتر پلتفرم‌ها همچنین یک ترید/تاپیک اختیاری را به‌عنوان سگمنت سوم می‌پذیرند: platform:<chat_id>:<thread_id>.

پلتفرم‌های گروه اول نحوِ هدفِ صریح و اعتبارسنجی‌شده دارند — کانال‌های نام‌دار (#channel)، تاپیک‌ها/تریدها، شناسه‌های اتاق/کاربر، شناسه‌های گروه یا شماره تلفن. بقیهٔ پلتفرم‌ها قالب عمومی platform:<chat_id> را می‌پذیرند (مقدار بعد از دونقطه عیناً به‌عنوان شناسهٔ مقصد استفاده می‌شود)؛ نام لختِ پلتفرم همیشه به کانال خانه تحویل می‌دهد.

کانال‌های نام‌دار (slack:#engineering، discord:#engineering یا یک نام دوستانه مثل slack:engineering) بر اساس فهرست کانال‌هایی حل می‌شوند که گیت‌وی از آداپتورهای متصل می‌سازد، پس برای موفقیتِ حلِ نام، گیت‌وی باید کانال را کشف کرده باشد؛ شناسه‌های خام (slack:C0123ABCD45) همیشه کار می‌کنند.

برای تاپیک‌های Telegram از telegram:<chat_id>:<thread_id> استفاده کنید (مثلاً telegram:-1001234567890:17585). برای تریدهای Slack، سگمنت سوم thread_ts پیام والد است (مثلاً slack:C0123ABCD45:1700000000.000100)، پس فقط وقتی اعمال می‌شود که زیر یک پیام موجود پاسخ بدهید.

Bot Chat (bot-chat، bot-chat:<profile>) یک شبه‌پلتفرمِ محلیِ ماشین است، نه یک آداپتور گیت‌وی: زمان‌بند با اجرای hermes [-p <profile>] chat --in ~ -c "Bot Chat" --create-if-missing -Q --query-file <tmp> تحویل می‌دهد — همان لِینی که پیام‌های ایجنت‌به‌ایجنتِ حالت بات استفاده می‌کنند — بنابراین خروجی به‌صورت یک نوبت ورودی واقعی در Bot Chat مرجعِ پروفایل می‌رسد و بات روی آن یک نوبت کامل ایجنت اجرا می‌کند (از نظر تناوبِ پیام، به‌طرزی ساختاری ایمن؛ این لِین فرمان چت است، نه آینهٔ ترنسکریپت). توکن لخت، پروفایل خودِ کار را نشانه می‌گیرد؛ قالب نام‌دار هنگام ساختن کار و دوباره هنگام اجرا نسبت به ~/.hermes/profiles/ اعتبارسنجی می‌شود و هرگز بین ماشین‌ها حل نمی‌شود. هدف‌های bot-chat از توکن مسیریابی all و از پیش‌بررسیِ تحویل مستثنی هستند (هیچ اعتبارنامهٔ گیت‌وی در کار نیست). تایم‌اوت ساب‌پروسسِ هر تحویل، cron.bot_chat_delivery_timeout_seconds است (پیش‌فرض ۶۰۰).

پوشش پاسخ

به‌طور پیش‌فرض (cron.wrap_response: true)، تحویل‌های کرون با این‌ها پوشانده می‌شوند:

  • سرصفحه‌ای که نام کار کرون و وظیفه را مشخص می‌کند
  • پاصفحه‌ای که یادآوری می‌کند ایجنت پیامِ تحویل‌شده را در گفتگو نمی‌بیند

پیشوند [SILENT] در پاسخ کرون، تحویل را کاملاً متوقف می‌کند — برای کارهایی که فقط باید در فایل‌ها بنویسند یا عوارض جانبی انجام دهند مفید است.

ایزوله‌سازی نشست

تحویل‌های کرون در تاریخچهٔ گفتگوی نشستِ گیت‌وی آینه‌سازی نمی‌شوند. آن‌ها فقط در نشستِ خودِ کار کرون وجود دارند. این کار از نقض تناوب پیام در گفتگوی چتِ هدف جلوگیری می‌کند.

۷ گارد بازگشتی

نشست‌های اجراشده توسط کرون، تول‌ست cronjob را غیرفعال دارند. این کار جلوگیری می‌کند از:

  • ساختن کارهای کرون جدید توسط یک کارِ زمان‌بندی‌شده
  • زمان‌بندی بازگشتی‌ای که می‌تواند مصرف توکن را منفجر کند
  • تغییر تصادفی زمان‌بندی کار از درون خودِ کار

۸ قفل‌گذاری

زمان‌بند از قفل‌گذاریِ فایل‌محورِ بین‌پروسسی (fcntl.flock روی یونیکس، msvcrt.locking روی ویندوز) استفاده می‌کند تا تیک‌های هم‌پوشان، همان دستهٔ کارِ سررسیده را دو بار اجرا نکنند — حتی بین تیکر درون‌پروسسیِ گیت‌وی و فراخوانی مستقل hermes cron یا tick() دستی. اگر نتوان قفل را به دست آورد، tick() بلافاصله ۰ برمی‌گرداند.

۹ رابط CLI

رابط خط فرمان hermes cron مدیریت مستقیم کارها را فراهم می‌کند:

hermes cron list                    # نمایش همهٔ کارها
hermes cron create                  # ساخت تعاملی کار (نام مستعار: add)
hermes cron edit <job_id>           # ویرایش پیکربندی کار
hermes cron pause <job_id>          # توقف موقت یک کار در حال اجرا
hermes cron resume <job_id>         # از سرگیری کار متوقف‌شده
hermes cron run <job_id>            # اجرای فوری
hermes cron remove <job_id>         # حذف کار
