میان‌افزار Hermes

میان‌افزار Hermes مکملِ تغییردهندهٔ رفتار برای هوک‌های ناظر است. هوک‌های ناظر گزارش می‌دهند چه اتفاقی افتاده است. میان‌افزار می‌تواند با بازنویسی درخواست پیش از اجرا یا با قرار دادن تابع بازفراخوانِ اجرا در یک لایهٔ پوشاننده، آنچه را اتفاق می‌افتد تغییر دهد.

این قرارداد عمداً مستقل از بک‌اند طراحی شده است. یک پلاگین می‌تواند از آن برای سیاست‌های محلی، شکل‌دهی درخواست، ردیابی، مسیریابی تطبیقی، کنترل کش، انتخاب سندباکس یا واگذاری به محیط‌های اجرایی مانند NeMo Relay استفاده کند، بدون آنکه برنامه‌ریز Hermes، آداپتورهای ارائه‌دهندگان مدل، رجیستری ابزارها، حافظه یا تجربهٔ کاربری CLI را تغییر دهد.

با فعال‌بودن میان‌افزار، پلاگین‌ها می‌توانند:

  • آرگومان‌های کلیدواژه‌ای (kwargs) درخواست ارائه‌دهندهٔ LLM را پیش از آنکه Hermes ارائه‌دهنده را فراخوانی کند، بازنویسی کنند.
  • آرگومان‌های ابزار را پیش از آنکه سازوکارهای محافظتی، بررسی‌های تأیید، هوک‌ها و اجرای ابزار آن‌ها را ببینند، بازنویسی کنند.
  • تابع بازفراخوانِ اجرای واقعی LLM را در یک لایهٔ پوشاننده قرار دهند و در عین حال رفتار Hermes در تلاش مجدد، پردازش جریانی، وقفه و هوک‌ها را حفظ کنند.
  • تابع بازفراخوانِ اجرای واقعی ابزار را در یک لایهٔ پوشاننده قرار دهند و در عین حال سازوکارهای محافظتی Hermes، تأیید، هوک‌های پس از ابزار و تبدیل نتیجهٔ ابزار را حفظ کنند.

۱ قرارداد

پلاگین‌ها میان‌افزار را از داخل register(ctx) ثبت می‌کنند:

def register(ctx):
    ctx.register_middleware("llm_request", on_llm_request)
    ctx.register_middleware("llm_execution", on_llm_execution)
    ctx.register_middleware("tool_request", on_tool_request)
    ctx.register_middleware("tool_execution", on_tool_execution)

هر تابع بازفراخوانِ میان‌افزار موارد زیر را دریافت می‌کند:

  • telemetry_schema_version: در حال حاضر hermes.observer.v1
  • middleware_schema_version: در حال حاضر hermes.middleware.v1
  • اطلاعات زمینهٔ زمان اجرا، مانند session_id، task_id، turn_id، api_request_id، provider، model، api_mode، tool_name و tool_call_id، در مواردی که کاربرد دارند.

انواع پشتیبانی‌شدهٔ میان‌افزار:

نوعدادهٔ ورودیقالب مقدار بازگشتیهدف
llm_requestrequest، original_request{"request": {...}}جایگزینی آرگومان‌های کلیدواژه‌ای مؤثرِ ارائه‌دهنده پیش از اجرای آن.
tool_requesttool_name، args، original_args{"args": {...}}جایگزینی آرگومان‌های مؤثرِ ابزار پیش از هوک‌ها، سازوکارهای محافظتی، تأییدها و اجرا.
llm_executionrequest، original_request، next_callهر نوع پاسخ ارائه‌دهندهقرار دادن در یک لایهٔ پوشاننده یا جایگزینی فراخوانی واقعی ارائه‌دهنده.
tool_executiontool_name، args، original_args، next_callهر نوع نتیجهٔ ابزارقرار دادن در یک لایهٔ پوشاننده یا جایگزینی فراخوانی واقعی ابزار.

میان‌افزار درخواست می‌تواند فیلدهای اختیاریِ ردیابی را برگرداند:

return {
    "request": updated_request,
    "source": "my-plugin",
    "reason": "selected fallback model",
}

Hermes این مدخل‌های ردیابی را با نام middleware_trace در داده‌های ارسالی به هوک‌های ناظرِ بعدی ذخیره می‌کند.

میان‌افزار اجرا یک تابع بازفراخوان به نام next_call دریافت می‌کند. برای ادامهٔ زنجیره، آن را فراخوانی کنید:

def on_tool_execution(**kwargs):
    result = kwargs["next_call"](kwargs["args"])
    return result

اگر چند پلاگین نوع یکسانی از میان‌افزار اجرا را ثبت کنند، Hermes آن‌ها را به‌شکل زنجیره‌ای تودرتو و به‌ترتیب ثبت اجرا می‌کند. شکست میان‌افزار از نوع fail-open است: Hermes هشداری ثبت می‌کند و کار را با میان‌افزار بعدی یا مسیر پایهٔ زمان اجرا ادامه می‌دهد.

۲ ترتیب اجرا

فراخوانی‌های LLM

Hermes برای هر درخواست ارائه‌دهنده، میان‌افزار را به این ترتیب اعمال می‌کند:

  1. آرگومان‌های کلیدواژه‌ای ارائه‌دهنده را از گفتگوی جاری می‌سازد.
  2. میان‌افزار llm_request را اعمال می‌کند.
  3. هوک‌های ناظرِ pre_api_request را با درخواست مؤثر فراخوانی می‌کند.
  4. اجرای ارائه‌دهنده را از مسیر میان‌افزار llm_execution انجام می‌دهد.
  5. هوک‌های ناظرِ post_api_request یا api_request_error را فراخوانی می‌کند.

میان‌افزار درخواست، همهٔ آرگومان‌های کلیدواژه‌ای ارائه‌دهنده را می‌بیند؛ از جمله messages یا input در Responses API، تنظیمات مدل، تعریف ابزارها، گزینه‌های پردازش جریانی و گزینه‌های مختص ارائه‌دهنده. میان‌افزار اجرا همان درخواست مؤثر را به‌همراه next_call دریافت می‌کند.

فراخوانی‌های ابزار

Hermes برای هر فراخوانی ابزار، میان‌افزار را به این ترتیب اعمال می‌کند:

  1. آرگومان‌های ابزارِ ارائه‌شده از سوی مدل را تجزیه می‌کند و نوع آن‌ها را به نوع مورد انتظار تبدیل می‌کند.
  2. میان‌افزار tool_request را اعمال می‌کند.
  3. مسیر معمول پیش از اجرای Hermes را روی آرگومان‌های مؤثر اجرا می‌کند: بررسی‌های در دسترس بودن ابزار، دستورهای مسدودسازی ناظر، سازوکارهای محافظتی و بررسی‌های تأیید.
  4. اجرای ابزار را از مسیر میان‌افزار tool_execution انجام می‌دهد.
  5. هوک‌های ناظرِ post_tool_call را فراخوانی می‌کند.
  6. پیش از آنکه نتیجه دوباره به زمینهٔ گفتگو افزوده شود، هوک‌های transform_tool_result را اعمال می‌کند.

میان‌افزار درخواست ابزار پیش از بررسی‌های تأیید اجرا می‌شود. با احتیاط از آن استفاده کنید: مسیر، فرمان یا URL بازنویسی‌شده همان مقداری است که سیاستِ مراحل بعدی ارزیابی خواهد کرد.

۳ فعال‌سازی

میان‌افزار فقط برای پلاگین‌های فعال اجرا می‌شود. برای یک پلاگین که همراه Hermes عرضه می‌شود:

hermes plugins enable <plugin-name>

برای آزمایش محلیِ ایزوله، هم برای فعال‌سازی پلاگین و هم برای اجرای ایجنت از یک HERMES_HOME یکسان استفاده کنید:

export HERMES_HOME=/tmp/hermes-middleware-test
mkdir -p "$HERMES_HOME"
hermes plugins enable <plugin-name>
hermes chat --query 'Reply exactly ok'

اگر از نسخهٔ کاریِ کد منبع استفاده می‌کنید، ترجیحاً فرمان را از محیط کد منبع اجرا کنید تا زمان اجرا، پلاگین‌ها و میان‌افزارهای موجود در درخت کاری را ببیند:

uv sync
uv run hermes plugins enable <plugin-name>
uv run hermes chat --query 'Reply exactly ok'

۴ نمونه‌های عمومی پلاگین

نمونه‌های زیر عمداً کوچک هستند. آن‌ها ساختار قرارداد میان‌افزار را بدون وابستگی به NeMo Relay نشان می‌دهند.

میان‌افزار درخواست LLM

این پلاگین درخواست‌های ارائه‌دهنده را برچسب‌گذاری می‌کند و یک مدخل ردیابی میان‌افزار ثبت می‌کند:

def register(ctx):
    ctx.register_middleware("llm_request", tag_llm_request)


def tag_llm_request(**kwargs):
    request = dict(kwargs["request"])
    extra_body = dict(request.get("extra_body") or {})
    extra_body.setdefault("metadata", {})["hermes_middleware_demo"] = True
    request["extra_body"] = extra_body
    return {
        "request": request,
        "source": "middleware-demo",
        "reason": "tagged provider request",
    }

درخواست مؤثر به pre_api_request، اجرای ارائه‌دهنده و post_api_request فرستاده می‌شود.

میان‌افزار درخواست ابزار

این پلاگین فراخوانی‌های terminal را به یک پوشهٔ کاریِ مشخص محدود می‌کند:

def register(ctx):
    ctx.register_middleware("tool_request", normalize_terminal_workdir)


def normalize_terminal_workdir(**kwargs):
    if kwargs.get("tool_name") != "terminal":
        return None
    args = dict(kwargs["args"])
    args.setdefault("workdir", "/tmp/hermes-middleware-demo")
    return {
        "args": args,
        "source": "middleware-demo",
        "reason": "defaulted terminal workdir",
    }

از آنجا که این کد پیش از هوک‌ها و تأییدها اجرا می‌شود، تله‌متری و سیاستِ مراحل بعدی، workdir بازنویسی‌شده را مشاهده می‌کنند.

یادداشت مترجم: در مثال بالا، setdefault فقط وقتی workdir وجود نداشته باشد مقدار پیش‌فرض را اضافه می‌کند؛ مقدار ازپیش‌تعیین‌شده را تغییر نمی‌دهد. بنابراین این مثال به‌تنهایی محدودیت اجباری برای پوشهٔ کاری ایجاد نمی‌کند.

میان‌افزار اجرای LLM

این پلاگین فراخوانی ارائه‌دهنده را در یک لایهٔ پوشاننده قرار می‌دهد و پاسخ خام ارائه‌دهنده را حفظ می‌کند:

import time


def register(ctx):
    ctx.register_middleware("llm_execution", time_llm_execution)


def time_llm_execution(**kwargs):
    started = time.monotonic()
    response = kwargs["next_call"](kwargs["request"])
    elapsed_ms = int((time.monotonic() - started) * 1000)
    print(f"llm_execution elapsed_ms={elapsed_ms}")
    return response

پاسخ را با همان قالبی برگردانید که Hermes از آداپتور ارائه‌دهنده انتظار دارد. پاسخ را در یک ساختار پوشانندهٔ مختص پلاگین قرار ندهید، مگر آنکه سایر بخش‌های زمان اجرا همان ساختار را انتظار داشته باشند.

میان‌افزار اجرای ابزار

این پلاگین اجرای ابزار را در یک لایهٔ پوشاننده قرار می‌دهد و در عین حال نتیجهٔ ابزار را حفظ می‌کند:

def register(ctx):
    ctx.register_middleware("tool_execution", annotate_tool_execution)


def annotate_tool_execution(**kwargs):
    result = kwargs["next_call"](kwargs["args"])
    # Metrics, logging, or external routing can happen here.
    return result

میان‌افزار اجرا می‌تواند next_call(modified_args) را فراخوانی کند تا دادهٔ تغییریافته را به میان‌افزارهای بعدی و توزیع‌کنندهٔ پایهٔ ابزار بفرستد.

نمونه‌های مختص هر پلاگین باید همراه همان پلاگینی نگهداری شوند که مسئول آن رفتار است. میان‌افزار اجرای NeMo Relay از طریق یک فایل plugins.toml متعلق به Relay که صریحاً انتخاب شده باشد، نصب می‌شود؛ معیارهای مشترک Relay را ببینید.

۵ نکات ایمنی

  • میان‌افزار باید برای ورودی یکسان، رفتاری قطعی داشته باشد؛ مگر آنکه صریحاً مسیریابی به یک سامانهٔ خارجیِ پویا را انجام دهد.
  • میان‌افزار درخواست باید داده‌های جایگزینِ کامل برگرداند، نه اصلاحات جزئی.
  • میان‌افزار اجرا باید next_call(...) را دقیقاً یک بار فراخوانی کند، مگر آنکه عمداً ادامهٔ مسیر اجرا را میان‌بُر بزند.
  • اگر میان‌افزار اجرا پیش از فراخوانی next_call(...) استثنا ایجاد کند، Hermes آن را شکست میان‌افزار تلقی می‌کند و کار را با بقیهٔ زنجیرهٔ میان‌افزار و اجرای پایه ادامه می‌دهد.
  • اگر میان‌افزار اجرا، next_call(...) را با موفقیت فراخوانی کند و سپس در پس‌پردازش استثنا ایجاد کند، Hermes نتیجهٔ مراحل بعدی را حفظ می‌کند و ارائه‌دهنده یا ابزار را بار دوم اجرا نمی‌کند.
  • اگر اجرای ارائه‌دهنده یا ابزار در مراحل بعدی شکست بخورد، میان‌افزار می‌تواند اجازه دهد آن خطا منتشر شود یا آگاهانه آن را به خطای دیگری تبدیل کند. Hermes شکست مراحل بعدی را به یک نتیجهٔ موفق با مقدار None تبدیل نمی‌کند.
  • میان‌افزار درخواست ابزار پیش از تأییدها اجرا می‌شود. اگر مسیرهای فایل، فرمان‌ها، URLها یا آرگومان‌ها را تغییر دهد، همان مقادیر تغییریافته هستند که سازوکارهای محافظتی و تأییدها ارزیابی می‌کنند.
  • هوک‌های ناظر همچنان محل مناسب برای تله‌متریِ فقط‌خواندنی هستند. فقط زمانی از میان‌افزار استفاده کنید که پلاگین نیاز دارد رفتار را تغییر دهد یا در یک لایهٔ پوشاننده قرار دهد.
