زمان اجرای ارائه‌دهنده

هرمس یک حل‌وفصل‌کنندهٔ (resolver) مشترک زمان اجرای ارائه‌دهنده دارد که در این‌ها استفاده می‌شود:

  • CLI
  • گیت‌وی
  • کارهای کرون
  • ACP
  • فراخوانی‌های مدل کمکی

پیاده‌سازی اصلی:

  • hermes_cli/runtime_provider.py — حل‌وفصل اعتبارنامه، حل‌وفصل زمان اجرای نقطهٔ پایانی سفارشی
  • hermes_cli/auth.py — رجیستری ارائه‌دهنده، resolve_provider()
  • hermes_cli/model_switch.py — خط لولهٔ مشترک تغییر /model (CLI + گیت‌وی)
  • agent/auxiliary_client.py — مسیریابی مدل کمکی
  • providers/ — ABC + نقاط ورودی رجیستری (ProviderProfile، register_provider، get_provider_profile، list_providers)
  • plugins/model-providers/<name>/ — پلاگین‌های مخصوص هر ارائه‌دهنده (هم‌بسته) که api_mode، base_url، env_vars و fallback_models را اعلام می‌کنند و در نخستین دسترسی، خودشان را در رجیستری ثبت می‌کنند. پلاگین‌های کاربر در $HERMES_HOME/plugins/model-providers/<name>/ هم‌نام‌های هم‌بسته را بازنویسی می‌کنند.

get_provider_profile() در providers/ برای یک شناسهٔ ارائه‌دهندهٔ مشخص، یک ProviderProfile برمی‌گرداند. runtime_provider.py این تابع را در زمان حل‌وفصل صدا می‌زند تا base_url مرجع، فهرست تقدم env_vars، api_mode و fallback_models را بگیرد، بدون آن‌که لازم باشد آن داده‌ها را در چند فایل تکرار کند. افزودن یک پلاگین جدید زیر plugins/model-providers/<your-provider>/ (یا $HERMES_HOME/plugins/model-providers/<your-provider>/) که register_provider() را صدا بزند، برای آن‌که runtime_provider.py آن را بردارد کافی است — هیچ شاخه‌ای در خودِ حل‌وفصل‌کننده لازم نیست.

اگر می‌خواهید یک ارائه‌دهندهٔ استنتاج درجه‌یک جدید اضافه کنید، این صفحه را همراه با افزودن ارائه‌دهندهٔ جدید و راهنمای پلاگین ارائه‌دهندهٔ مدل بخوانید.

۱ ترتیب تقدم حل‌وفصل

در سطح بالا، حل‌وفصل ارائه‌دهنده از این‌ها استفاده می‌کند:

  1. درخواست صریح CLI/زمان اجرا
  2. پیکربندی مدل/ارائه‌دهنده در config.yaml
  3. متغیرهای محیطی
  4. پیش‌فرض‌های مخصوص هر ارائه‌دهنده یا حل‌وفصل خودکار

این ترتیب مهم است، چون هرمس انتخاب ذخیره‌شدهٔ مدل/ارائه‌دهنده را منبع حقیقت برای اجراهای عادی می‌داند. این کار جلوی آن را می‌گیرد که یک export قدیمی در شل، بی‌سروصدا نقطهٔ پایانی‌ای را که کاربر آخرین‌بار در hermes model انتخاب کرده بازنویسی کند.

۳ خروجی حل‌وفصل زمان اجرا

حل‌وفصل‌کنندهٔ زمان اجرا داده‌هایی مثل این‌ها را برمی‌گرداند:

  • provider
  • api_mode
  • base_url
  • api_key
  • source
  • فرادادهٔ مخصوص ارائه‌دهنده مثل اطلاعات انقضا/تازه‌سازی

۴ چرا این مهم است

این حل‌وفصل‌کننده دلیل اصلی آن است که هرمس می‌تواند منطق احراز هویت/زمان اجرا را بین این‌ها به اشتراک بگذارد:

  • hermes chat
  • مدیریت پیام گیت‌وی
  • کارهای کرون که در نشست‌های تازه اجرا می‌شوند
  • نشست‌های ویرایشگر ACP
  • کارهای مدل کمکی

۵ AI Gateway

AI_GATEWAY_API_KEY را در ~/.hermes/.env تنظیم کنید و با --provider ai-gateway اجرا کنید. هرمس مدل‌های موجود را از نقطهٔ پایانی /models گیت‌وی می‌گیرد و آن‌ها را به مدل‌های زبانیِ دارای پشتیبانی استفاده از ابزار محدود می‌کند.

۶ OpenRouter، AI Gateway و base URLهای سفارشیِ سازگار با OpenAI

هرمس منطقی دارد برای جلوگیری از درزکردن کلید API اشتباه به یک نقطهٔ پایانی سفارشی وقتی چند کلید ارائه‌دهنده وجود دارد (مثلاً OPENROUTER_API_KEY، AI_GATEWAY_API_KEY و OPENAI_API_KEY).

کلید API هر ارائه‌دهنده به base URL خودش محدود است:

  • OPENROUTER_API_KEY فقط به نقطه‌های پایانی openrouter.ai فرستاده می‌شود
  • AI_GATEWAY_API_KEY فقط به نقطه‌های پایانی ai-gateway.vercel.sh فرستاده می‌شود
  • OPENAI_API_KEY برای نقطه‌های پایانی سفارشی و به‌عنوان پشتیبان استفاده می‌شود

هرمس همچنین بین این دو تمایز می‌گذارد:

  • یک نقطهٔ پایانی سفارشی واقعی که کاربر انتخاب کرده
  • مسیر پشتیبان OpenRouter که وقتی هیچ نقطهٔ پایانی سفارشی پیکربندی نشده استفاده می‌شود

این تمایز به‌ویژه برای این‌ها مهم است:

  • سرورهای مدل محلی
  • APIهای سازگار با OpenAI که OpenRouter یا AI Gateway نیستند
  • تغییر ارائه‌دهنده بدون اجرای مجدد راه‌اندازی
  • نقطه‌های پایانی سفارشیِ ذخیره‌شده در پیکربندی که باید حتی وقتی OPENAI_BASE_URL در شل فعلی export نشده، به کار کردن ادامه دهند

۷ مسیر بومی Anthropic

Anthropic دیگر فقط «از طریق OpenRouter» نیست.

وقتی حل‌وفصل ارائه‌دهنده anthropic را انتخاب کند، هرمس از این‌ها استفاده می‌کند:

  • api_mode = anthropic_messages
  • API بومی Anthropic Messages
  • agent/anthropic_adapter.py برای ترجمه

حل‌وفصل اعتبارنامه برای Anthropic بومی حالا وقتی هر دو موجود باشند، اعتبارنامه‌های تازه‌شوندهٔ Claude Code را به توکن‌های کپی‌شده در متغیر محیطی ترجیح می‌دهد. در عمل یعنی:

  • فایل‌های اعتبارنامهٔ Claude Code وقتی احراز هویت تازه‌شونده داشته باشند، منبع ترجیحی در نظر گرفته می‌شوند
  • مقادیر دستی ANTHROPIC_TOKEN / CLAUDE_CODE_OAUTH_TOKEN همچنان به‌عنوان بازنویسی صریح کار می‌کنند
  • هرمس قبل از فراخوانی‌های بومی Messages API، تازه‌سازی اعتبارنامهٔ Anthropic را پیش‌بررسی می‌کند
  • هرمس همچنان روی 401 و بعد از بازسازی کلاینت Anthropic یک‌بار تلاش مجدد می‌کند، به‌عنوان مسیر پشتیبان

۸ مسیر OpenAI Codex

Codex از یک مسیر جداگانهٔ Responses API استفاده می‌کند:

  • api_mode = codex_responses
  • حل‌وفصل اعتبارنامه و پشتیبانی مخزن احراز هویتِ اختصاصی

۹ مسیریابی مدل کمکی

کارهای کمکی مثل:

  • بینایی
  • خلاصه‌سازی استخراج وب
  • خلاصه‌های فشرده‌سازی زمینه
  • عملیات هاب مهارت‌ها
  • عملیات کمکی MCP
  • تخلیه (flush) حافظه‌ها

می‌توانند به‌جای مدل اصلی گفتگو، مسیریابی ارائه‌دهنده/مدل مخصوص خودشان را داشته باشند.

وقتی یک کار کمکی با ارائه‌دهندهٔ main پیکربندی شود، هرمس آن را از همان مسیر مشترک زمان اجرای گفتگوی عادی حل‌وفصل می‌کند. در عمل یعنی:

  • نقطه‌های پایانی سفارشیِ مبتنی بر متغیر محیطی همچنان کار می‌کنند
  • نقطه‌های پایانی سفارشیِ ذخیره‌شده از طریق hermes model / config.yaml هم کار می‌کنند
  • مسیریابی کمکی می‌تواند تفاوت نقطهٔ پایانی سفارشیِ واقعیِ ذخیره‌شده و مسیر پشتیبان OpenRouter را تشخیص دهد

۱۰ مدل‌های پشتیبان

هرمس از زنجیرهٔ پشتیبانِ ارائه‌دهندهٔ پیکربندی‌شده پشتیبانی می‌کند — فهرستی از ورودی‌های (provider, model) که به ترتیب امتحان می‌شوند وقتی مدل اصلی با خطا روبه‌رو می‌شود. دیکشنری قدیمیِ تک‌جفتیِ fallback_model همچنان برای سازگاری با نسخه‌های پیشین پذیرفته می‌شود (و در اولین نوشتن مهاجرت داده می‌شود).

کارکرد داخلی چگونه است

  1. ذخیره‌سازی: AIAgent.__init__ دیکشنری fallback_model را نگه می‌دارد و _fallback_activated = False را تنظیم می‌کند.
  2. نقاط محرک: _try_activate_fallback() از سه جای حلقهٔ تلاش مجدد اصلی در run_agent.py صدا زده می‌شود:
    • بعد از حداکثر تلاش‌ها روی پاسخ‌های نامعتبر API (انتخاب‌های None، محتوای غایب)
    • روی خطاهای کلاینتِ غیرقابل‌تلاش‌مجدد (HTTP 401، 403، 404)
    • بعد از حداکثر تلاش‌ها روی خطاهای گذرا (HTTP 429، 500، 502، 503)
  3. جریان فعال‌سازی (_try_activate_fallback):
    • اگر قبلاً فعال شده یا پیکربندی نشده باشد، بلافاصله False برمی‌گرداند
    • resolve_provider_client() را از auxiliary_client.py صدا می‌زند تا کلاینت جدیدی با احراز هویت درست بسازد
    • api_mode را تعیین می‌کند: codex_responses برای openai-codex، anthropic_messages برای anthropic و chat_completions برای بقیه
    • درجا جابه‌جا می‌کند: self.model، self.provider، self.base_url، self.api_mode، self.client، self._client_kwargs
    • برای پشتیبان anthropic: به‌جای کلاینت سازگار با OpenAI، کلاینت بومی Anthropic می‌سازد
    • کش پرامپت را دوباره ارزیابی می‌کند (برای مدل‌های Claude روی OpenRouter فعال است)
    • _fallback_activated = True را تنظیم می‌کند — از فعال‌شدن دوباره جلوگیری می‌شود
    • شمارندهٔ تلاش مجدد را صفر می‌کند و حلقه را ادامه می‌دهد
  4. جریان پیکربندی:
    • CLI: زنجیرهٔ پشتیبان را با hermes_cli/fallback_config.get_fallback_chain() می‌خواند ← به AIAgent(fallback_model=...) می‌دهد
    • گیت‌وی: gateway/run.py._load_fallback_model() مقدار config.yaml را می‌خواند ← به AIAgent می‌دهد
    • اعتبارسنجی: هر دو کلید provider و model باید غیرخالی باشند، وگرنه پشتیبان غیرفعال می‌شود

چه چیزهایی از پشتیبان پشتیبانی نمی‌کنند

  • واگذاری به ساب‌ایجنت (tools/delegate_tool.py): ساب‌ایجنت‌ها ارائه‌دهندهٔ والد را به ارث می‌برند، اما نه پیکربندی پشتیبان را
  • کارهای کمکی: زنجیرهٔ تشخیص خودکار ارائه‌دهندهٔ مستقل خودشان را دارند (بخش مسیریابی مدل کمکی در بالا را ببینید)

کارهای کرون از پشتیبان پشتیبانی می‌کنند: run_job() مقدار fallback_providers (یا fallback_model قدیمی) را از config.yaml می‌خواند و به AIAgent(fallback_model=...) می‌دهد؛ مطابق الگوی _load_fallback_model() گیت‌وی. بخش درون‌مایهٔ Cron را ببینید.
