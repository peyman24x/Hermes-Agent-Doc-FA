پلاگین ارائه‌دهندهٔ مدل

پلاگین‌های ارائه‌دهندهٔ مدل یک بک‌اند استنتاج تعریف می‌کنند — یک نقطهٔ پایانی سازگار با ‎OpenAI، سرور ‎Anthropic Messages، رابط ‎Responses API به سبک ‎Codex یا رابط بومی ‎Bedrock — که ‎Hermes می‌تواند فراخوانی‌های ‎AIAgent را از طریق آن مسیریابی کند. هر ارائه‌دهندهٔ داخلی (‎OpenRouter، Anthropic، GMI، DeepSeek، Nvidia و …) به‌شکل یکی از این پلاگین‌ها عرضه می‌شود. توسعه‌دهندگان شخص ثالث می‌توانند با قرار دادن یک پوشه زیر ‎$HERMES_HOME/plugins/model-providers/، بدون هیچ تغییری در مخزن، ارائه‌دهندهٔ خود را اضافه کنند.

نکته

پلاگین‌های ارائه‌دهندهٔ مدل سومین نوع پلاگین ارائه‌دهنده هستند. انواع دیگر عبارت‌اند از پلاگین ارائه‌دهندهٔ حافظه (دانش میان‌نشستی) و پلاگین موتور زمینه (راهبردهای فشرده‌سازی زمینه). هر سه از الگوی یکسان «قرار دادن یک پوشه، تعریف یک پروفایل، بدون ویرایش مخزن» پیروی می‌کنند.

۱ نحوهٔ کشف

تابع ‎providers/__init__.py._discover_providers() به‌صورت تنبل، نخستین باری اجرا می‌شود که بخشی از کد ‎get_provider_profile() یا ‎list_providers() را فراخوانی کند. ترتیب کشف:

  1. پلاگین‌های همراه بسته — ‎<repo>/plugins/model-providers/<name>/ — همراه ‎Hermes عرضه می‌شوند
  2. پلاگین‌های کاربر — ‎$HERMES_HOME/plugins/model-providers/<name>/ — هر پوشه‌ای را می‌توانید قرار دهید؛ برای نشست‌های بعدی به راه‌اندازی مجدد نیازی نیست
  3. تک‌فایلی قدیمی — ‎<repo>/providers/<name>.py — سازگاری عقب‌رو برای نصب‌های قابل‌ویرایش خارج از درخت مخزن

پلاگین‌های کاربر جایگزین پلاگین‌های همراهِ هم‌نام می‌شوند، زیرا در ‎register_provider() آخرین ثبت برنده است. با قرار دادن پوشهٔ ‎$HERMES_HOME/plugins/model-providers/gmi/ می‌توانید پروفایل داخلی ‎GMI را بدون دست‌زدن به مخزن جایگزین کنید.

۲ ساختار پوشه

plugins/model-providers/my-provider/
├── __init__.py       # Calls register_provider(profile) at module-level
├── plugin.yaml       # kind: model-provider + metadata (optional but recommended)
└── README.md         # Setup instructions (optional)

تنها فایل الزامی ‎__init__.py است. ‎hermes plugins برای بررسی مشخصات و ‎PluginManager عمومی برای هدایت پلاگین به بارگذار درست از ‎plugin.yaml استفاده می‌کنند؛ در نبود آن، بارگذار عمومی به یک روش ابتکاری مبتنی بر متن کد منبع متوسل می‌شود.

۳ مثال حداقلی — ارائه‌دهندهٔ ساده با کلید ‎API

# plugins/model-providers/acme-inference/__init__.py
from providers import register_provider
from providers.base import ProviderProfile

acme = ProviderProfile(
    name="acme-inference",
    aliases=("acme",),
    display_name="Acme Inference",
    description="Acme — OpenAI-compatible direct API",
    signup_url="https://acme.example.com/keys",
    env_vars=("ACME_API_KEY", "ACME_BASE_URL"),
    base_url="https://api.acme.example.com/v1",
    auth_type="api_key",
    default_aux_model="acme-small-fast",
    fallback_models=(
        "acme-large-v3",
        "acme-medium-v3",
        "acme-small-fast",
    ),
)

register_provider(acme)
# plugins/model-providers/acme-inference/plugin.yaml
name: acme-inference
kind: model-provider
version: 1.0.0
description: Acme Inference — OpenAI-compatible direct API
author: Your Name

۵ هوک‌های قابل‌بازنویسی

برای رفتارهای خاص و غیرساده، زیرکلاسی از ‎ProviderProfile بسازید:

from typing import Any
from providers.base import ProviderProfile

class AcmeProfile(ProviderProfile):
    def prepare_messages(self, messages: list[dict[str, Any]]) -> list[dict[str, Any]]:
        """Provider-specific message preprocessing. Runs after codex
        sanitization, before developer-role swap. Default: pass-through."""
        # Example: Qwen normalizes plain-text content to a list-of-parts
        # array and injects cache_control; Kimi rewrites tool-call JSON
        return messages

    def build_extra_body(self, *, session_id=None, **context) -> dict:
        """Provider-specific extra_body fields merged into the API call.
        Context includes: session_id, provider_preferences, model, base_url,
        reasoning_config. Default: empty dict."""
        # Example: OpenRouter's provider-preferences block,
        # Gemini's thinking_config translation.
        return {}

    def build_api_kwargs_extras(self, *, reasoning_config=None, **context):
        """Returns (extra_body_additions, top_level_kwargs). Needed when some
        fields go top-level (Kimi's reasoning_effort, OpenRouter's verbosity for
        adaptive Anthropic models) and some go in extra_body (OpenRouter's
        reasoning dict). Default: ({}, {})."""
        return {}, {}

    def fetch_models(self, *, api_key=None, base_url=None, timeout=8.0) -> list[str] | None:
        """Live catalog fetch. Default hits {models_url or base_url}/models with
        Bearer auth. Override for: custom auth (Anthropic), no REST endpoint
        (Bedrock → None), or public/unauthenticated catalogs (OpenRouter)."""
        return super().fetch_models(api_key=api_key, base_url=base_url, timeout=timeout)

۷ بازنویسی‌های کاربر — جایگزینی ارائه‌دهندهٔ داخلی بدون ویرایش مخزن

فرض کنید می‌خواهید برای آزمایش، ‎gmi را به نقطهٔ پایانی خصوصی محیط پیش‌تولید خود متصل کنید. فایل ‎~/.hermes/plugins/model-providers/gmi/__init__.py را بسازید:

from providers import register_provider
from providers.base import ProviderProfile

register_provider(ProviderProfile(
    name="gmi",
    aliases=("gmi-cloud", "gmicloud"),
    env_vars=("GMI_API_KEY",),
    base_url="https://gmi-staging.internal.example.com/v1",
    auth_type="api_key",
    default_aux_model="google/gemini-3.1-flash-lite-preview",
))

در نشست بعدی، ‎get_provider_profile("gmi").base_url نشانی محیط پیش‌تولید را برمی‌گرداند. نه وصله‌ای در مخزن لازم است و نه ساخت مجدد. چون پلاگین‌های کاربر پس از پلاگین‌های همراه کشف می‌شوند، فراخوانی ‎register_provider() کاربر برنده می‌شود.

۸ انتخاب ‎api_mode

چهار مقدار شناخته می‌شوند. ‎Hermes یکی را بر اساس ترتیب زیر انتخاب می‌کند:

  1. بازنویسی صریح کاربر (‎model.api_mode در ‎config.yaml، در صورت تنظیم)
  2. توزیع فراخوانی بر اساس مدل در ‎OpenCode (‎opencode_model_api_mode برای ‎Zen و ‎Go)
  3. تشخیص خودکار از نشانی — پسوند ‎/anthropic ← ‎anthropic_messages، ‎api.openai.com ← ‎codex_responses، ‎api.x.ai ← ‎codex_responses، ‎/coding در دامنه‌های ‎Kimi ← ‎chat_completions
  4. ‎api_mode پروفایل به‌عنوان پشتیبان، وقتی تشخیص نشانی چیزی پیدا نکند
  5. پیش‌فرض ‎chat_completions

‎profile.api_mode را مطابق پیش‌فرض ارائه‌دهندهٔ خود تنظیم کنید — نقش راهنما دارد. بازنویسی‌های نشانی توسط کاربر همچنان اولویت دارند.

۹ انواع احراز هویت

‎auth_type تعیین می‌کند کدام مسیرهای کد با ارائه‌دهندهٔ شما مانند یک «ارائه‌دهندهٔ ساده با کلید ‎API» رفتار کنند — اگر مقدارش ‎api_key نباشد، ‎PluginManager همچنان مانیفست را ثبت می‌کند، اما خودکارسازی سطح رابط خط فرمان ‎Hermes (بررسی‌های ‎doctor، پرچم ‎--provider، واگذاری به جادوگر راه‌اندازی) ممکن است آن را نادیده بگیرد.

۱۰ زمان‌بندی کشف

کشف ارائه‌دهنده تنبل است — نخستین فراخوانی ‎get_provider_profile() یا ‎list_providers() در فرایند آن را آغاز می‌کند. در عمل، این اتفاق در ابتدای راه‌اندازی رخ می‌دهد (بارگذاری ماژول ‎auth.py بلافاصله ‎PROVIDER_REGISTRY را گسترش می‌دهد). برای اطمینان از بارگذاری پلاگین اجرا کنید:

hermes doctor

پروفایل موفق با ‎auth_type="api_key" در بخش «اتصال ارائه‌دهندگان» (‎Provider Connectivity) همراه با آزمون ‎/models ظاهر می‌شود.

برای بررسی برنامه‌نویسی‌شده:

from providers import list_providers
for p in list_providers():
    print(p.name, p.base_url, p.api_mode)

۱۲ یکپارچه‌سازی با ‎PluginManager عمومی

‎PluginManager عمومی (بخشی که ‎hermes plugins با آن کار می‌کند) پلاگین‌های ارائه‌دهندهٔ مدل را می‌بیند، اما آن‌ها را وارد نمی‌کند — مالک چرخهٔ حیاتشان ‎providers/__init__.py است. مدیر، مانیفست را برای بررسی مشخصات ثبت و بر اساس ‎kind: model-provider دسته‌بندی می‌کند. وقتی یک پلاگین کاربر بدون برچسب در ‎$HERMES_HOME/plugins/ قرار دهید که ‎register_provider را با یک ‎ProviderProfile فراخوانی می‌کند، مدیر با روشی ابتکاری مبتنی بر متن منبع، نوع آن را خودکار به ‎kind: model-provider تبدیل می‌کند — بنابراین حتی بدون ‎plugin.yaml نیز پلاگین به‌درستی هدایت می‌شود.

۱۳ توزیع از طریق ‎pip

ارائه‌دهندگان مدل می‌توانند به‌شکل پکیج ‎pip عرضه شوند. در ‎pyproject.toml خود یک نقطهٔ ورود در گروه ‎hermes_agent.plugins تعریف کنید:

[project.entry-points."hermes_agent.plugins"]
acme-inference = "acme_hermes_plugin:register"

مقصد می‌تواند یکی از این دو باشد:

  • یک شیء قابل‌فراخوانی (‎module:func) — بدون آرگومان فراخوانی می‌شود؛ باید ‎register_provider(profile) را صدا بزند، یا
  • یک ماژول بدون نام تابع (‎module) — برای اجرای اثر جانبی ‎register_provider(...) در سطح ماژول وارد می‌شود؛ مشابه قرارداد ‎__init__.py در پلاگین‌های پوشه‌ای.

‎providers/__init__.py خودش این نقاط ورود را کشف می‌کند — ‎PluginManager عمومی هرگز ثبت ارائه‌دهنده را برای پکیج‌های ‎pip فراخوانی نمی‌کند (مسیر نقاط ورود آن مخصوص پلاگین‌های عمومی با الگوی ‎register(ctx) است و با ‎plugins.enabled کنترل می‌شود)؛ بنابراین رجیستری ارائه‌دهندگان اسکن مستقل خود را انجام می‌دهد. دو قاعده اعمال می‌شود:

  • فعال‌سازی صریح الزامی است. همان فهرست مجاز ‎plugins.enabled (و فهرست مسدود ‎plugins.disabled) در ‎config.yaml بر این اسکن حاکم است. پکیج ‎pip هرگز صرفاً به‌دلیل نصب بودن وارد نمی‌شود — کاربران باید نام نقطهٔ ورود را به ‎plugins.enabled اضافه کنند:

    plugins:
  enabled:
    - acme-inference

  • پایین‌ترین اولویت. پلاگین‌های نقاط ورود پیش از پلاگین‌های سیستم فایل کشف می‌شوند؛ چون در ‎register_provider() آخرین ثبت برنده است، پروفایل هم‌نام همراه بسته یا موجود در ‎$HERMES_HOME همیشه جایگزین نمونهٔ نصب‌شده با ‎pip می‌شود. یک پکیج ‎pip می‌تواند ارائه‌دهنده‌ای واقعاً جدید اضافه کند، اما نمی‌تواند نام ارائه‌دهندهٔ رسمی را بی‌سروصدا تصاحب کند.

مقصدهایی که آرگومان می‌خواهند (‎register(ctx) در یک پلاگین عمومی) در اسکن ارائه‌دهنده رد می‌شوند — آن‌ها متعلق به ‎PluginManager هستند. خرابی یک نقطهٔ ورود محدود به همان مورد می‌ماند — در سطح هشدار ثبت و نادیده گرفته می‌شود و هرگز کشف ارائه‌دهندگان دیگر را متوقف نمی‌کند.
