ساخت پرامپت سیستمی

هرمس عمداً این دو را جدا می‌کند:

  • وضعیت پرامپت سیستمیِ کش‌شده
  • افزودنی‌های زودگذرِ زمان فراخوانی API

این یکی از مهم‌ترین انتخاب‌های طراحی در پروژه است، چون روی این‌ها اثر می‌گذارد:

  • مصرف توکن
  • اثربخشی کش پرامپت
  • پیوستگی نشست
  • درستی حافظه

فایل‌های اصلی:

  • run_agent.py
  • agent/prompt_builder.py
  • tools/memory_tool.py

۱ لایه‌های پرامپت سیستمیِ کش‌شده

پرامپت سیستمیِ کش‌شده به‌شکل سه طبقهٔ مرتب مونتاژ می‌شود (نگاه کنید به agent/system_prompt.py):

  1. stable — هویت (SOUL.md یا پشتیبان)، راهنمای ابزار/مدل، پرامپت مهارت‌ها، راهنماهای محیط، راهنماهای پلتفرم
  2. context — system_message ارائه‌شده از سمت فراخوان، به‌علاوهٔ فایل‌های زمینهٔ پروژه (.hermes.md / AGENTS.md / CLAUDE.md / .cursorrules)
  3. volatile — اسنپ‌شات حافظهٔ داخلی (MEMORY.md)، اسنپ‌شات پروفایل کاربر (USER.md)، بلوک ارائه‌دهندهٔ حافظهٔ خارجی، خط زمان/نشست/مدل/ارائه‌دهنده

پرامپت سیستمی نهایی سپس به این صورت به هم می‌پیوندد: stable → context → volatile.

این ترتیب برای بحث‌های تقدم اهمیت دارد:

  • مهارت‌ها بخشی از طبقهٔ stable هستند
  • اسنپ‌شات‌های حافظه/پروفایل بخشی از طبقهٔ volatile هستند
  • هر دو همچنان در پرامپت سیستمیِ کش‌شده‌اند (به‌شکل overlayهای موردیِ وسط نوبت تزریق نمی‌شوند)

وقتی skip_context_files تنظیم شده باشد (مثلاً در واگذاری به ساب‌ایجنت)، SOUL.md بارگذاری نمی‌شود و به‌جای آن DEFAULT_AGENT_IDENTITY هاردکدشده استفاده می‌شود.

۲ سفارشی‌سازی راهنماهای پلتفرم

راهنمای پلتفرم (لایهٔ ۱۰ در بالا) راهنمای هر-سطحی است که هرمس برای Telegram، WhatsApp، Slack، CLI و سایر پلتفرم‌ها تزریق می‌کند — مثلاً «روی ترمینال هستی، از Markdown استفاده نکن». پیش‌فرض‌های داخلی در PLATFORM_HINTS (agent/system_prompt.py) زندگی می‌کنند؛ پلتفرم‌های ارائه‌شده توسط پلاگین، راهنمای خودشان را از طریق رجیستری پلتفرم عرضه می‌کنند.

یک مدیر می‌تواند راهنمای یک پلتفرمِ واحد را از config.yaml و از طریق کلید سطح‌بالای platform_hints الحاق یا جایگزین کند، بدون دست زدن به پلتفرم دیگر:

platform_hints:
  whatsapp:
    append: >
      When tabular output would be useful, invoke the table_formatting
      skill instead of emitting a Markdown table.
  slack:
    replace: "You are on Slack. Keep responses tight and avoid wide tables."
  telegram: "Prefer short messages; split long answers."   # خلاصه‌نویسی = append
  • append — راهنمای داخلی را نگه می‌دارد و متن اضافی را بعد از آن می‌نشیند.
  • replace — راهنمای داخلی را کاملاً جایگزین می‌کند.
  • یک رشتهٔ خام — خلاصه‌نویسیِ append است.
  • وقتی هر دو حاضر باشند، replace بر append می‌چربد.
  • ورودی بدشکل به‌شکل دفاعی نادیده گرفته می‌شود و به پیش‌فرض دست‌نخورده برمی‌گردد؛ پس یک مقدار بدِ پیکربندی هرگز نمی‌تواند ساخت پرامپت را بشکند یا بین پلتفرم‌ها نشت کند.

override هنگام ساخته‌شدن پرامپت سیستمی resolve می‌شود (شروع نشست، و دوباره هنگام compaction چون پرامپت را بازسازی می‌کند). برای یک پیکربندی ثابت، راهنمای بایت-پایداری تولید می‌کند؛ پس در طبقهٔ stable کنار راهنمای داخلی می‌نشیند و کش پرامپت را نمی‌شکند — این یک جهشِ زندهٔ وسط-نشستِ پرامپت منجمد نیست.

۳ SOUL.md چطور در پرامپت ظاهر می‌شود

SOUL.md در ~/.hermes/SOUL.md زندگی می‌کند و نقش هویت ایجنت را دارد — همان بخش نخستِ پرامپت سیستمی. منطق بارگذاری در prompt_builder.py این‌طور کار می‌کند:

# از agent/prompt_builder.py (ساده‌شده)
def load_soul_md() -> Optional[str]:
    soul_path = get_hermes_home() / "SOUL.md"
    if not soul_path.exists():
        return None
    content = soul_path.read_text(encoding="utf-8").strip()
    content = _scan_context_content(content, "SOUL.md")  # اسکن امنیتی
    content = _truncate_content(content, "SOUL.md")       # سقف با پنجرهٔ زمینهٔ مدل مقیاس می‌یابد (کف 20k)؛ override پیکربندی برنده است
    return content

وقتی load_soul_md() محتوا برگرداند، جای DEFAULT_AGENT_IDENTITY هاردکدشده را می‌گیرد. سپس تابع build_context_files_prompt() با skip_soul=True فراخوانی می‌شود تا SOUL.md دوبار ظاهر نشود (یک‌بار به‌عنوان هویت، یک‌بار به‌عنوان فایل زمینه).

اگر SOUL.md وجود نداشته باشد، سیستم به این پشتیبان می‌رود:

You are Hermes Agent, an intelligent AI assistant created by Nous Research.
You are helpful, knowledgeable, and direct. You assist users with a wide
range of tasks including answering questions, writing and editing code,
analyzing information, creative work, and executing actions via your tools.
You communicate clearly, admit uncertainty when appropriate, and prioritize
being genuinely useful over being verbose unless otherwise directed below.
Be targeted and efficient in your exploration and investigations.

۴ فایل‌های زمینه چطور تزریق می‌شوند

build_context_files_prompt() از یک سیستم اولویت استفاده می‌کند — فقط یک نوع زمینهٔ پروژه بارگذاری می‌شود (اولین تطابق برنده است):

# از agent/prompt_builder.py (ساده‌شده)
def build_context_files_prompt(cwd=None, skip_soul=False):
    cwd_path = Path(cwd).resolve()

    # اولویت: اولین تطابق برنده است — فقط «یک» زمینهٔ پروژه بارگذاری می‌شود
    project_context = (
        _load_hermes_md(cwd_path)       # 1. .hermes.md / HERMES.md (تا ریشهٔ گیت بالا می‌رود)
        or _load_agents_md(cwd_path)    # 2. AGENTS.md (فقط cwd)
        or _load_claude_md(cwd_path)    # 3. CLAUDE.md (فقط cwd)
        or _load_cursorrules(cwd_path)  # 4. .cursorrules / .cursor/rules/*.mdc
    )

    sections = []
    if project_context:
        sections.append(project_context)

    # SOUL.md از HERMES_HOME (مستقل از زمینهٔ پروژه)
    if not skip_soul:
        soul_content = load_soul_md()
        if soul_content:
            sections.append(soul_content)

    if not sections:
        return ""

    return (
        "# Project Context\n\n"
        "The following project context files have been loaded "
        "and should be followed:\n\n"
        + "\n".join(sections)
    )

جزئیات کشف فایل زمینه

اولویتفایل‌هادامنهٔ جستجونکات
1.hermes.md، HERMES.mdاز CWD تا ریشهٔ گیتپیکربندی بومیِ پروژهٔ هرمس
2AGENTS.mdفقط CWDفایل رایج دستورالعمل ایجنت

4.cursorrules، .cursor/rules/*.mdcفقط CWDسازگاری با Cursor

همهٔ فایل‌های زمینه:

  • اسکن امنیتی می‌شوند — برای الگوهای تزریق پرامپت بررسی می‌شوند (یونیکد نامرئی، «ignore previous instructions»، تلاش برای بیرون‌کشی اعتبارنامه)
  • بریده می‌شوند — به سقف context_file_max_chars کاراکتر با تقسیم 70/20 سر/دُم و یک نشانگر برش. سقف با پنجرهٔ زمینهٔ مدل مقیاس می‌یابد (کف ۲۰٬۰۰۰ کاراکتر، سقف ۵۰۰ هزار)؛ مقدار صریح context_file_max_chars در config.yaml همیشه برنده است.
  • frontmatter یامل حذف می‌شود — frontmatter فایل .hermes.md برداشته می‌شود (برای overrideهای پیکربندی آینده رزرو شده)

۵ لایه‌های فقط-زمان-فراخوانی-API

این‌ها عمداً به‌عنوان بخشی از پرامپت سیستمیِ کش‌شده ماندگار نمی‌شوند:

  • ephemeral_system_prompt
  • پیام‌های prefill
  • overlayهای زمینهٔ نشستِ مشتق از گیت‌وی
  • یادآوری Honcho/خارجیِ نوبت‌های بعدی که در پیام user نوبت جاری تزریق می‌شود

زمینهٔ پلاگین pre_llm_call هم در همین مسیرِ زمان-فراخوانی-API می‌نشیند: به پیام user نوبت جاری اضافه می‌شود، نه اینکه در پرامپت سیستمیِ کش‌شده نوشته شود. وقتی چند پلاگین زمینه برمی‌گردانند، هرمس آن بلوک‌های زمینه را به هم می‌چسباند (نگاه کنید به هوک‌ها ← pre_llm_call).

این جداسازی پیشوند پایدار را برای کش، پایدار نگه می‌دارد.

۶ اسنپ‌شات‌های حافظه

حافظهٔ محلی و داده‌های پروفایل کاربر در طبقهٔ volatile پرامپت سیستمی ثبت می‌شوند. نوشتن‌های وسط نشست، وضعیت دیسک را به‌روز می‌کنند ولی پرامپت سیستمیِ کش‌شدهٔ از قبل ساخته‌شده را دست‌کاری نمی‌کنند تا زمانی که یک مسیر بازسازی اجرا شود (نشست جدید، یا جریان صریح ابطال/بازسازی مثل بازسازیِ برخاسته از فشرده‌سازی).

۷ فایل‌های زمینه

agent/prompt_builder.py فایل‌های زمینهٔ پروژه را با یک سیستم اولویت اسکن و پاک‌سازی می‌کند — فقط یک نوع بارگذاری می‌شود (اولین تطابق برنده است):

  1. .hermes.md / HERMES.md (تا ریشهٔ گیت بالا می‌رود)
  2. AGENTS.md (CWD هنگام شروع؛ زیرپوشه‌ها به‌تدریج در طول نشست از طریق agent/subdirectory_hints.py کشف می‌شوند)
  3. CLAUDE.md (فقط CWD)
  4. .cursorrules / .cursor/rules/*.mdc (فقط CWD)

SOUL.md برای جایگاه هویت، جداگانه از طریق load_soul_md() بارگذاری می‌شود. وقتی با موفقیت بارگذاری شود، build_context_files_prompt(skip_soul=True) جلوی دوبار ظاهرشدنش را می‌گیرد.

فایل‌های بلند قبل از تزریق بریده می‌شوند.

۸ شاخص مهارت‌ها

سیستم مهارت‌ها وقتی ابزارهای مهارتی در دسترس باشد، یک شاخص فشردهٔ مهارت‌ها به پرامپت اضافه می‌کند.

۹ سطوح مجاز سفارشی‌سازی پرامپت

بیشتر کاربران باید agent/prompt_builder.py را کدِ پیاده‌سازی بدانند، نه یک سطح پیکربندی. مسیر پشتیبانی‌شدهٔ سفارشی‌سازی، تغییر ورودی‌های پرامپتی است که هرمس از قبل بارگذاری می‌کند، نه ویرایش درجای قالب‌های پایتون.

اول از این سطوح استفاده کنید

  • ~/.hermes/SOUL.md — بلوک هویت پیش‌فرض داخلی را با پرسونای ایجنت و رفتار دائمی خودتان جایگزین کنید.
  • ~/.hermes/MEMORY.md و ~/.hermes/USER.md — واقعیت‌های پایدار بین‌نشستی و داده‌های پروفایل کاربر را فراهم کنید که باید در نشست‌های جدید اسنپ‌شات شوند.
  • فایل‌های زمینهٔ پروژه مثل .hermes.md، HERMES.md، AGENTS.md، CLAUDE.md یا .cursorrules — قواعد کاری مخصوص مخزن را تزریق کنید.
  • مهارت‌ها — گردش‌کارها و مراجعِ استفاده‌پذیر مجدد را بدون ویرایش کد اصلی پرامپت بسته‌بندی کنید.
  • پیکربندی اختیاری پرامپت سیستمی / overrideهای API — متن دستورالعمل مخصوص استقرار را بدون فورک‌کردن هرمس اضافه کنید.
  • Overlayهای زودگذر مثل HERMES_EPHEMERAL_SYSTEM_PROMPT یا پیام‌های prefill — راهنماییِ محدود به نوبت اضافه کنید که نباید بخشی از پیشوند پرامپتِ کش‌شده شود.

کی به‌جای آن کد را ویرایش کنید

agent/prompt_builder.py را فقط وقتی ویرایش کنید که عمداً یک فورک را نگه می‌دارید یا در حال مشارکتِ تغییر رفتار به بالادست هستید. آن فایل لوله‌کشی پرامپت، مرزهای کش و ترتیب تزریق را برای هر نشست مونتاژ می‌کند. ویرایش مستقیم آن، تغییر محصولِ سراسری است نه سفارشی‌سازی پرامپتِ هر کاربر.

به بیان دیگر:

  • اگر هویت متفاوتی برای دستیار می‌خواهید، SOUL.md را ویرایش کنید
  • اگر قواعد متفاوتی برای مخزن می‌خواهید، فایل‌های زمینهٔ پروژه را ویرایش کنید
  • اگر رویه‌های عملیاتیِ استفاده‌پذیر مجدد می‌خواهید، مهارت اضافه کنید یا تغییر دهید
  • اگر می‌خواهید نحوهٔ ساخت پرامپت هرمس برای همه تغییر کند، پایتون را تغییر دهید و با آن مثل یک مشارکت کدی رفتار کنید

۱۰ چرا ساخت پرامپت این‌طور تقسیم شده

معماری عمداً برای این‌ها بهینه شده است:

  • حفظ کش پرامپت سمت ارائه‌دهنده
  • پرهیز از دست‌کاری غیرضروری تاریخچه
  • نگه‌داشتن معناشناسی حافظه در حد فهم‌پذیری
  • اجازه به گیت‌وی/ACP/CLI برای افزودن زمینه، بدون آلوده‌کردن وضعیت پایدار پرامپت
