هوک‌های ناظر Hermes

هوک‌های ناظر Hermes قرارداد تله‌متریِ فقط‌خواندنی برای افزونه‌هایی هستند که باید روند اجرای ایجنت را بدون تغییر رفتار زمان اجرا بازسازی کنند. این قرارداد از یکپارچه‌سازی‌های ردیابی، سنجه‌ها، ممیزی، بازپخش و صدور داده پشتیبانی می‌کند؛ از جمله Langfuse، گردآورنده‌های به‌سبک OpenTelemetry و NeMo Relay.

هوک‌های ناظر عمداً به هیچ بک‌اندی وابسته نیستند. آن‌ها رویدادهای پایدار چرخهٔ حیات، شناسه‌های هم‌بستگی، محموله‌های پاک‌سازی‌شده، زمان‌بندی، وضعیت و فیلدهای خطا را در دسترس قرار می‌دهند. این هوک‌ها جایگزین برنامه‌ریز Hermes، ارائه‌دهندگان مدل، حافظه، رجیستری ابزارها، تجربهٔ کاربری تأیید، CLI، رفتار گیت‌وی یا معنای عملیاتی اجرا نمی‌شوند.

پوشاننده‌های درخواست یا اجرا که رفتار را تغییر می‌دهند، خارج از این قرارداد ناظر هستند. هوک‌های ناظر باید آنچه رخ داده است را گزارش کنند؛ نباید درخواست‌های ارائه‌دهنده، آرگومان‌های ابزار یا توابع بازفراخوانِ اجرا را جایگزین کنند.

Hermes همچنین یک مسیر رسمی و داخلی برای سنجه‌های مشترک NeMo Relay دارد. این مسیر مستقیماً از همین مرزهای چرخهٔ حیات استفاده می‌کند و نیازی به فعال‌کردن افزونهٔ مشاهده‌پذیری ندارد. به سنجه‌های مشترک Relay مراجعه کنید.

۱ قرارداد

افزونه‌ها توابع بازفراخوانِ ناظر را از داخل register(ctx) ثبت می‌کنند:

def register(ctx):
    ctx.register_hook("pre_api_request", on_pre_api_request)
    ctx.register_hook("post_api_request", on_post_api_request)
    ctx.register_hook("pre_tool_call", on_pre_tool_call)
    ctx.register_hook("post_tool_call", on_post_tool_call)

هر تابع بازفراخوانِ هوک، آرگومان‌ها را به‌صورت نام‌دار دریافت می‌کند. افزونه‌ها باید **kwargs را بپذیرند تا افزودن فیلدهای جدید، سازگاری با نسخه‌های قبلی را حفظ کند:

def on_post_tool_call(**kwargs):
    tool_name = kwargs.get("tool_name")
    status = kwargs.get("status")
    result = kwargs.get("result")

مدیر افزونه این فیلد را به محمولهٔ هر هوک تزریق می‌کند:

telemetry_schema_version = "hermes.observer.v1"

توابع بازفراخوانِ هوک از الگوی ادامهٔ کار در صورت خطا (fail-open) پیروی می‌کنند. Hermes استثناهای این توابع را می‌گیرد، هشداری در گزارش ثبت می‌کند و حلقهٔ ایجنت را در حال اجرا نگه می‌دارد.

بیشتر مقادیر بازگشتی هوک‌های ناظر نادیده گرفته می‌شوند. استثناها، هوک‌های قدیمی‌تری هستند که بر رفتار اثر می‌گذارند:

هوکرفتار مقدار بازگشتی
pre_llm_callمی‌تواند یک رشته یا {"context": "..."} برگرداند تا زمینه‌ای موقتی را به پیام فعلی کاربر تزریق کند.
pre_tool_callمی‌تواند {"action": "block", "message": "..."} برگرداند تا ابزار را پیش از اجرا مسدود کند، یا {"action": "modify", "args": {...}} برگرداند تا آرگومان‌های ورودی ابزار را تبدیل کند.
transform_tool_resultمی‌تواند پس از post_tool_call یک رشتهٔ جایگزین برای نتیجهٔ ابزار برگرداند.
transform_llm_outputمی‌تواند یک رشتهٔ جایگزین برای متن نهایی دستیار برگرداند.

افزونه‌های تله‌متری باید این مقادیر بازگشتیِ مؤثر بر رفتار را قابلیت‌های اختیاریِ سازگاری در نظر بگیرند، نه الزامات مشاهده‌پذیری.

۲ شناسه‌های هم‌بستگی

محموله‌های ناظر از شناسه‌های پایدار استفاده می‌کنند تا افزونه‌ها بتوانند رویدادها را بدون اتکای صرف به ترتیب توابع بازفراخوان به هم مرتبط کنند.

فیلدمعنا
session_idهویت گفتگو/نشست.
task_idهویت وظیفه؛ به‌ویژه برای زیرایجنت‌ها و اجرای ایزوله مفید است.
turn_idهویت نوبت کاربر که میان تلاش‌های API و فراخوانی‌های ابزار در یک نوبت مشترک است.
api_request_idشناسهٔ غیرقابل‌تفسیرِ تلاش نزد ارائه‌دهنده. قالب رشته‌ای آن را تجزیه نکنید.
api_call_countشمار عددی تلاش‌های API در حلقهٔ ایجنت.
tool_call_idشناسهٔ فراخوانی ابزار که ارائه‌دهنده تأمین می‌کند، در صورت موجود بودن.
parent_session_id / child_session_idپیوند نشست برای زیرایجنت‌هایی که کار به آن‌ها واگذار شده است.
parent_subagent_id / child_subagent_idپیوند زیرایجنت، در صورت موجود بودن.
parent_turn_idنوبت والد که کار واگذارشده را ایجاد کرده است.

مصرف‌کنندگان باید فیلدهای صریح را بر تجزیهٔ شناسه‌های مرکب ترجیح دهند. به‌طور خاص، api_request_id یک مقدار هم‌بستگیِ غیرقابل‌تفسیر است.

۳ خانواده‌های رویداد

چرخهٔ حیات نشست

هوک‌های نشست، مرزهای گفتگو و بازنشانی‌ها را توصیف می‌کنند:

هوکزمان فعال‌شدن
on_session_startنشستی کاملاً جدید پس از ساخته‌شدن پرامپت سیستم آغاز می‌شود.
on_session_endیک فراخوانی run_conversation پایان می‌یابد؛ نوبت‌های قطع‌شده یا ناتمام را نیز شامل می‌شود.
on_session_finalizeCLI یا گیت‌وی به استفاده از یک هویت نشست فعال پایان می‌دهد و آن را برمی‌چیند.
on_session_resetCLI یا گیت‌وی از هویت نشست قدیمی به هویتی جدید منتقل می‌شود.

فیلدهای رایج، در صورت موجود بودن، عبارت‌اند از session_id، completed، interrupted، reason، old_session_id و new_session_id.

دامنهٔ on_session_end یک نوبت/اجرا است. این رویداد لزوماً مرز نهایی طول عمر یک هویت گفتگو نیست. برای پاک‌سازی چرخهٔ حیات که باید یک بار به‌ازای هر هویت نشست انجام شود، از on_session_finalize و on_session_reset استفاده کنید.

هوک‌های LLM در سطح نوبت

این هوک‌ها آغاز و پایان نوبت کاربر را مشخص می‌کنند، نه تک‌تک تلاش‌های API ارائه‌دهنده را:

هوکزمان فعال‌شدن
pre_llm_callپیش از آغاز حلقهٔ ابزار برای یک نوبت کاربر.
post_llm_callپس از تکمیل نوبت با خروجی نهایی دستیار.

فیلدهای رایج pre_llm_call عبارت‌اند از session_id، turn_id، user_message، conversation_history، is_first_turn، model، platform و sender_id.

فیلدهای رایج post_llm_call عبارت‌اند از session_id، turn_id، user_message، assistant_response، conversation_history، model و platform.

برای تله‌متری بازه‌های ردیابی (span) مدل زبانی، از هوک‌های API در سطح درخواست استفاده کنید. از pre_llm_call و post_llm_call برای زمینهٔ سطح نوبت، سازگاری و خلاصهٔ نهایی نوبت استفاده کنید.

هوک‌های API در سطح درخواست

هوک‌های API تلاش‌های ارسال درخواست به ارائه‌دهنده درون حلقهٔ ایجنت را توصیف می‌کنند:

هوکزمان فعال‌شدن
pre_api_requestبلافاصله پیش از یک درخواست API به ارائه‌دهنده.
post_api_requestپس از پاسخ موفق ارائه‌دهنده.
api_request_errorپس از شکست درخواست به ارائه‌دهنده یا طی‌شدن مسیر خطایی که قابل تلاش مجدد است.

pre_api_request شامل موارد زیر است:

  • هویت: session_id، task_id، turn_id، api_request_id
  • زمان اجرا: platform، model، provider، base_url، api_mode
  • فرادادهٔ تلاش: api_call_count، message_count، tool_count، approx_input_tokens، request_char_count، max_tokens
  • زمان‌بندی: started_at
  • محمولهٔ پاک‌سازی‌شدهٔ درخواست: request

post_api_request همان فیلدهای هویت/زمان اجرا را به‌همراه موارد زیر دارد:

  • api_duration، started_at، ended_at
  • finish_reason، message_count، response_model
  • usage
  • assistant_content_chars، assistant_tool_call_count
  • محمولهٔ پاک‌سازی‌شدهٔ پاسخ: response
  • شیء سازگاری: assistant_message

api_request_error همان فیلدهای هویت/زمان اجرا را به‌همراه موارد زیر دارد:

  • api_duration، started_at، ended_at
  • status_code، retry_count، max_retries، retryable، reason
  • خطای ساخت‌یافتهٔ error = {"type": ..., "message": ...}
  • محمولهٔ پاک‌سازی‌شدهٔ درخواست ناموفق: request

فیلدهای پاک‌سازی‌شدهٔ request، response و error ورودی‌های مرجعِ ناظر برای مصرف‌کنندگان جدید هستند.

چرخهٔ حیات ابزار

هوک‌های ابزار، تک‌تک فراخوانی‌های ابزار را توصیف می‌کنند:

هوکزمان فعال‌شدن
pre_tool_callپیش از ارسال ابزار برای اجرا، پس از تأیید کنترل‌های محافظتی.
post_tool_callپس از ارسال ابزار برای اجرا، لغو، مسدودشدن یا پایان‌یافتن با خطا.
transform_tool_resultپس از post_tool_call و پیش از افزوده‌شدن نتیجه به زمینهٔ مدل.

pre_tool_call شامل tool_name، args، task_id، session_id، tool_call_id، turn_id و api_request_id است.

post_tool_call همان فیلدهای هویت را به‌همراه result، duration_ms، status، error_type و error_message دارد.

status بیانگر نتیجهٔ چرخهٔ حیات به‌شکلی مناسب برای ناظر است. مقادیر رایج عبارت‌اند از:

وضعیتمعنا
okابزار به‌طور عادی به پایان رسید.
errorابزار اجرا شد و نتیجه‌ای خطادار برگرداند یا خطایی ایجاد کرد.
blockedیک هوک pre_tool_call اجرا را مسدود کرد.
cancelledاجرا پیش از پایان عادی لغو شد.

post_tool_call برای مسیرهای مسدودشده و لغوشده نیز منتشر می‌شود تا افزونه‌های تله‌متری بتوانند بازه‌های ردیابی را به‌درستی ببندند.

چرخهٔ حیات تأیید

هوک‌های تأیید، اعلان‌های درخواست تأیید فرمان‌های خطرناک را توصیف می‌کنند:

هوکزمان فعال‌شدن
pre_approval_requestپیش از نمایش یا ارسال درخواست تأیید.
post_approval_responseپس از پاسخ کاربر یا پایان مهلت درخواست.

فیلدهای رایج عبارت‌اند از command، description، pattern_key، pattern_keys، session_key و surface.

post_approval_response همچنین شامل choice است، با مقادیری مانند once، session، always، deny، timeout و cancelled (هیچ‌کس پاسخ نداده است: اعلان پس گرفته شده — چون نوبت قطع شده یا پایان یافته — یا در CLI هرگز به کاربر نرسیده است).

هوک‌های تأیید صرفاً برای مشاهده هستند. افزونه‌ها نمی‌توانند از طریق این هوک‌ها از پیش به درخواست‌های تأیید پاسخ دهند یا آن‌ها را وتو کنند. برای جلوگیری از رسیدن یک ابزار به مرحلهٔ تأیید، از مسدودسازی با pre_tool_call استفاده کنید.

چرخهٔ حیات زیرایجنت

هوک‌های زیرایجنت، کاری را توصیف می‌کنند که به ایجنت فرزند واگذار شده است:

هوکزمان فعال‌شدن
subagent_startیک ایجنت فرزند برای انجام کار واگذارشده ایجاد می‌شود.
subagent_stopیک ایجنت فرزندِ مأمور به کار واگذارشده، نتیجه را برمی‌گرداند یا شکست می‌خورد.

فیلدهای subagent_start عبارت‌اند از parent_session_id، parent_turn_id، parent_subagent_id، child_session_id، child_subagent_id، child_role و child_goal.

فیلدهای subagent_stop شامل شناسه‌های نشست والد/فرزند، فیلدهای نقش/وضعیت، child_summary، duration_ms و یک tool_call_history صرفاً حاوی فراداده هستند. هر مدخل تاریخچه شامل نام ابزار، نام آرگومان‌ها، هدف‌های اثرات جانبی با اطلاعات محدودشده، تعداد بایت‌های ورودی/خروجی و نتیجه است. رشتهٔ پرس‌وجو و بخش قطعه (fragment) نشانی‌های URL حذف می‌شوند؛ آرگومان‌های خام، پرامپت‌ها، فرمان‌ها، محتواها، سرآیندها و نتایج عمداً کنار گذاشته می‌شوند.

ناظرها می‌توانند از این هوک‌ها برای مدل‌سازی مسیرهای اجرای تودرتو استفاده کنند و در عین حال، اجرای ایجنت فرزند را به نوبت والدی که آن را ایجاد کرده است پیوند دهند.

۴ ایمنی محموله

محموله‌های ناظر برای مصرف‌کنندگان تله‌متری طراحی شده‌اند، نه برای دسترسی به اشیای خام. مصرف‌کنندگان جدید باید از محموله‌های پاک‌سازی‌شدهٔ API استفاده کنند:

  • pre_api_request.request
  • post_api_request.response
  • api_request_error.request
  • api_request_error.error

پاک‌سازی، اشیای ارائه‌دهنده را به ساختارهای سازگار با JSON تبدیل می‌کند، اندازهٔ محموله‌های بزرگ را محدود می‌کند، مقادیر کلیدهای حساس را می‌پوشاند و از افشای اشیای خام پاسخ در فیلدهای پاک‌سازی‌شده جلوگیری می‌کند.

فیلدهای سازگاری قدیمی مانند request_messages، conversation_history و assistant_message ممکن است همچنان برای افزونه‌های موجود حضور داشته باشند. مصرف‌کنندگان جدید مشاهده‌پذیری باید محموله‌های پاک‌سازی‌شده را ترجیح دهند.

۵ کارایی

مسیر پیش‌فرضِ بدون ابزارگذاری باید کم‌هزینه بماند. ساخت پرهزینهٔ محموله‌های درخواست/پاسخ به بررسی has_hook(...) مشروط شده است؛ بنابراین Hermes فقط زمانی محموله‌های پاک‌سازی‌شدهٔ تله‌متری API را می‌سازد که دست‌کم یک افزونه، هوک مربوطه را ثبت کرده باشد.

نویسندگان افزونه باید این ویژگی را حفظ کنند:

  • فقط هوک‌هایی را ثبت کنید که افزونه واقعاً مصرف می‌کند.
  • از کپی عمیق یا پاک‌سازی مجدد محموله‌هایی که قبلاً پاک‌سازی شده‌اند خودداری کنید.
  • توابع بازفراخوانِ هوک را سریع و با رفتار ادامهٔ کار در صورت خطا نگه دارید.
  • هرجا عملی است، صدور داده از طریق شبکه یا نوشتن دسته‌ای را از مسیر اجرای هوک خارج کنید.

۶ نوشتن افزونهٔ ناظر

یک افزونهٔ ناظر حداقلی:

def register(ctx):
    ctx.register_hook("pre_api_request", on_pre_api_request)
    ctx.register_hook("post_api_request", on_post_api_request)
    ctx.register_hook("pre_tool_call", on_pre_tool_call)
    ctx.register_hook("post_tool_call", on_post_tool_call)


def on_pre_api_request(**kwargs):
    start_llm_span(
        request_id=kwargs.get("api_request_id"),
        turn_id=kwargs.get("turn_id"),
        request=kwargs.get("request"),
        model=kwargs.get("model"),
    )


def on_post_api_request(**kwargs):
    finish_llm_span(
        request_id=kwargs.get("api_request_id"),
        response=kwargs.get("response"),
        usage=kwargs.get("usage"),
        duration=kwargs.get("api_duration"),
    )


def on_pre_tool_call(**kwargs):
    start_tool_span(
        call_id=kwargs.get("tool_call_id"),
        name=kwargs.get("tool_name"),
        args=kwargs.get("args"),
    )


def on_post_tool_call(**kwargs):
    finish_tool_span(
        call_id=kwargs.get("tool_call_id"),
        result=kwargs.get("result"),
        status=kwargs.get("status"),
        duration_ms=kwargs.get("duration_ms"),
    )

برای هم‌بسته‌سازی بازه‌های ردیابی، از session_id، turn_id، api_request_id و tool_call_id استفاده کنید. هنگامی که قالب صدور داده از کار تودرتوی ایجنت‌ها یا رویدادهای چرخهٔ حیات امنیتی پشتیبانی می‌کند، از هوک‌های زیرایجنت و تأیید استفاده کنید.

۷ مصرف‌کنندگان موجود

افزونهٔ Langfuse که همراه Hermes عرضه می‌شود، نمونه‌ای از مشاهده‌پذیری مستقیم مبتنی بر هوک برای نوبت‌ها، درخواست‌های ارائه‌دهنده و فراخوانی‌های ابزار است.

یکپارچه‌سازی بومی SDKِ NeMo Relay، چرخه‌های حیات نشست، نوبت، LLM و ابزار در Hermes را به Relay نگاشت می‌کند. پیکربندی صریح افزونه‌های Relay می‌تواند صادرکننده‌های ATOF، ATIF یا OTEL و میان‌افزار اجرا را اضافه کند؛ به سنجه‌های مشترک Relay مراجعه کنید.
