دسترسی LLM در پلاگین

ctx.llm روش پشتیبانی‌شده برای فراخوانی LLM از یک پلاگین است. تکمیل گفتگو، استخراج ساخت‌یافته، همگام، ناهمگام، با تصویر یا بدون آن — همگی از یک رابط، یک دروازهٔ اعتماد و اعتبارنامه‌های تحت مالکیت میزبان استفاده می‌کنند.

پلاگین‌ها زمانی سراغ این قابلیت می‌روند که به کاری مرتبط با مدل نیاز دارند که بخشی از گفتگوی ایجنت نیست. هوکی که خطای ابزار را به متنی قابل‌فهم برای فرد غیرفنی بازنویسی می‌کند. آداپتور گیت‌وی که پیام ورودی را پیش از صف‌کردن ترجمه می‌کند. فرمان اسلشی که متن طولانیِ چسبانده‌شده را خلاصه می‌کند. کار زمان‌بندی‌شده‌ای که فعالیت دیروز را امتیازدهی می‌کند و یک خط روی تابلوی وضعیت می‌نویسد. پیش‌فیلتری که تصمیم می‌گیرد آیا اصلاً پیام ارزش بیدارکردن ایجنت را دارد یا نه.

این‌ها کارهایی هستند که ایجنت نباید در حلقهٔ آن‌ها باشد. به یک فراخوانی LLM و پاسخی دارای نوع نیاز دارند تا کار تمام شود.

۱ کوچک‌ترین فراخوانی ممکن

result = ctx.llm.complete(messages=[{"role": "user", "content": "ping"}])
return result.text

تمام API در همین یک خط است. نه کلیدی، نه پیکربندی ارائه‌دهنده‌ای، نه مقداردهی اولیهٔ SDK. پلاگین با همان ارائه‌دهنده و مدلی اجرا می‌شود که کاربر در حال استفاده از آن است — با تغییر ارائه‌دهنده توسط کاربر، پلاگین هم خودکار همراه او تغییر می‌کند.

۲ مثالی کامل‌تر از گفتگو

result = ctx.llm.complete(
    messages=[
        {"role": "system", "content": "Rewrite errors as one short sentence a non-engineer can act on."},
        {"role": "user",   "content": traceback_text},
    ],
    max_tokens=64,
    purpose="hooks.error-rewrite",
)
return result.text

purpose رشتهٔ آزادِ ممیزی است — در agent.log و result.audit ظاهر می‌شود تا راهبران ببینند کدام پلاگین کدام فراخوانی را انجام داده است. اختیاری است، اما برای هر کاری که مکرراً اجرا می‌شود توصیه می‌شود.

۳ خروجی ساخت‌یافته

وقتی پلاگین به پاسخی دارای نوع نیاز دارد، به مسیر ساخت‌یافته بروید:

result = ctx.llm.complete_structured(
    instructions="Score this support reply for urgency (0–1) and pick a category.",
    input=[{"type": "text", "text": message_body}],
    json_schema=TRIAGE_SCHEMA,
    purpose="support.triage",
    temperature=0.0,
    max_tokens=128,
)

if result.parsed["urgency"] > 0.8:
    await dispatch_to_oncall(result.parsed["category"], message_body)

میزبان از ارائه‌دهنده خروجی JSON درخواست می‌کند، به‌عنوان پشتیبان آن را محلی تجزیه می‌کند، در صورت نصب‌بودن jsonschema آن را با اسکیمای شما اعتبارسنجی می‌کند و یک شیء پایتون در result.parsed تحویل می‌دهد. اگر مدل نتواند JSON معتبر تولید کند، result.parsed برابر None است و result.text پاسخ خام را نگه می‌دارد.

۴ این مسیر چه امکاناتی می‌دهد

  • یک فراخوانی، چهار شکل. complete() برای گفتگو، complete_structured() برای JSON دارای نوع، و acomplete() و acomplete_structured() برای asyncio. آرگومان‌ها و اشیای نتیجه یکسان‌اند.
  • اعتبارنامه‌های تحت مالکیت میزبان. توکن‌های OAuth، جریان‌های نوسازی، مخزن اعتبارنامه و بازنویسی‌های کمکیِ هر وظیفه — تمام مفاهیم اعتبارنامه‌ای که هرمس از قبل دارد اعمال می‌شوند. پلاگین هرگز توکن را نمی‌بیند؛ میزبان انتساب فراخوانی را از طریق result.audit برمی‌گرداند.
  • محدود. یک فراخوانی همگام یا ناهمگام. بدون استریم، حلقه‌های ابزار یا وضعیت گفتگو برای مدیریت‌کردن. ورودی را مشخص کنید، نتیجه را بگیرید و برگردید.
  • اعتماد با رد پیش‌فرض (fail-closed). پلاگینی که هرگز پیکربندی نکرده‌اید نمی‌تواند ارائه‌دهنده، مدل، ایجنت یا اعتبارنامهٔ ذخیره‌شدهٔ خودش را انتخاب کند. رویکرد پیش‌فرض «از همان چیزی استفاده کن که کاربر استفاده می‌کند» است. راهبران بازنویسی‌های مشخص را برای هر پلاگین در config.yaml صریحاً مجاز می‌کنند.

۵ شروع سریع

در ادامه دو پلاگین کامل آمده است — یکی برای گفتگو و دیگری ساخت‌یافته. هر دو در یک تابع register(ctx) عرضه می‌شوند و برای اجرا با مدل فعال کاربر به هیچ پیکربندی بیرونی نیاز ندارند.

تکمیل گفتگو — /tldr

def register(ctx):
    ctx.register_command(
        name="tldr",
        handler=lambda raw: _tldr(ctx, raw),
        description="Summarise the supplied text in one paragraph.",
        args_hint="<text>",
    )


def _tldr(ctx, raw_args: str) -> str:
    text = raw_args.strip()
    if not text:
        return "Usage: /tldr <text to summarise>"
    result = ctx.llm.complete(
        messages=[
            {"role": "system",
             "content": "Summarise the user's text in one tight paragraph. No preamble."},
            {"role": "user", "content": text},
        ],
        max_tokens=256,
        temperature=0.3,
        purpose="tldr",
    )
    return result.text

result.text پاسخ مدل است؛ result.usage شمار توکن‌ها را نگه می‌دارد؛ result.provider و result.model اطلاعات انتساب را نگه می‌دارند.

استخراج ساخت‌یافته — /paste-to-tasks

def register(ctx):
    ctx.register_command(
        name="paste-to-tasks",
        handler=lambda raw: _paste_to_tasks(ctx, raw),
        description="Turn freeform meeting notes into structured tasks.",
        args_hint="<text>",
    )


_TASKS_SCHEMA = {
    "type": "object",
    "properties": {
        "tasks": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "owner":  {"type": "string"},
                    "action": {"type": "string"},
                    "due":    {"type": "string", "description": "ISO date or empty"},
                },
                "required": ["action"],
            },
        },
    },
    "required": ["tasks"],
}


def _paste_to_tasks(ctx, raw_args: str) -> str:
    if not raw_args.strip():
        return "Usage: /paste-to-tasks <meeting notes>"
    result = ctx.llm.complete_structured(
        instructions=(
            "Extract concrete action items from these meeting notes. "
            "One task per actionable line. If no owner is named, leave 'owner' blank."
        ),
        input=[{"type": "text", "text": raw_args}],
        json_schema=_TASKS_SCHEMA,
        schema_name="meeting.tasks",
        purpose="paste-to-tasks",
        temperature=0.0,
        max_tokens=512,
    )
    if result.parsed is None:
        return f"Couldn't parse a response. Raw output:\n{result.text}"
    lines = [f"- [{t.get('owner') or '?'}] {t['action']}" for t in result.parsed["tasks"]]
    return "\n".join(lines) or "(no tasks found)"

مثال عملی سوم، این بار با ورودی تصویر، در مخزن hermes-example-plugins قرار دارد (مخزن همراه برای پلاگین‌های مرجع — همراه خود hermes-agent بسته‌بندی نشده است). برای رابط ناهمگام (acomplete() / acomplete_structured() با asyncio.gather())، plugin-llm-async-example را در همان مخزن ببینید.

۶ چه زمانی از کدام استفاده کنیم

می‌خواهید…استفاده کنید از
پاسخ متنی آزاد (ترجمه، خلاصه، بازنویسی، تولید)complete()
پرامپت چندنوبتی (سیستم + مثال‌های چندنمونه‌ای + کاربر)complete()
دیکشنری دارای نوع که با اسکیما اعتبارسنجی شده باشدcomplete_structured()
ورودی تصویر یا متن با خروجی دیکشنری دارای نوعcomplete_structured()
همان فراخوانی از کد ناهمگام (آداپتورهای گیت‌وی، هوک‌های ناهمگام)acomplete() / acomplete_structured()

بقیهٔ موارد — انتخاب ارائه‌دهنده، تعیین مدل، احراز هویت، پشتیبان، مهلت زمانی و مسیریابی بینایی — در هر چهار مورد یکسان‌اند.

۷ رابط API

ctx.llm نمونه‌ای از agent.plugin_llm.PluginLlm است.

complete()

result = ctx.llm.complete(
    messages=[{"role": "user", "content": "Hi"}],
    provider=None,         # optional, gated — Hermes provider id (e.g. "openrouter")
    model=None,            # optional, gated — whatever string that provider expects
    temperature=None,
    max_tokens=None,
    timeout=None,          # seconds
    agent_id=None,         # optional, gated
    profile=None,          # optional, gated — explicit auth-profile name
    purpose="optional-audit-string",
    task=None,             # optional — a plugin-registered auxiliary slot
)
# → PluginLlmCompleteResult(text, provider, model, agent_id, usage, audit)

تکمیل گفتگوی ساده. messages شکل استاندارد OpenAI را دارد — فهرستی از دیکشنری‌های {"role": "...", "content": "..."}. پرامپت‌های چندنوبتی (سیستم + چند جفت نمونهٔ کاربر/دستیار + کاربر نهایی) دقیقاً مانند SDK مربوط به OpenAI کار می‌کنند.

provider= و model= مستقل‌اند و از همان ساختار پیکربندی اصلی میزبان (model.provider + model.model) پیروی می‌کنند. فقط model= را تنظیم کنید تا از ارائه‌دهندهٔ فعال کاربر با مدل متفاوتی در آن استفاده شود. برای تعویض کامل ارائه‌دهنده هر دو را تنظیم کنید. هر یک از این آرگومان‌ها بدون اجازهٔ صریح راهبر، PluginLlmTrustError ایجاد می‌کند.

complete_structured()

result = ctx.llm.complete_structured(
    instructions="What you want extracted.",
    input=[
        {"type": "text",  "text": "..."},
        {"type": "image", "data": b"...", "mime_type": "image/png"},
        {"type": "image", "url":  "https://..."},
    ],
    json_schema={...},     # optional — triggers parsed result + validation
    json_mode=False,       # set True without a schema to ask for JSON anyway
    schema_name=None,      # optional human-readable schema name
    system_prompt=None,
    provider=None,         # optional, gated
    model=None,            # optional, gated
    temperature=None,
    max_tokens=None,
    timeout=None,
    agent_id=None,
    profile=None,
    purpose=None,
    task=None,             # optional — a plugin-registered auxiliary slot
)
# → PluginLlmStructuredResult(text, provider, model, agent_id,
#                             usage, parsed, content_type, audit)

ورودی‌ها بلوک‌های دارای نوعِ متن یا تصویرند (بایت‌های خام خودکار با base64 به URL با پیشوند data: تبدیل می‌شوند). وقتی json_schema یا json_mode=True ارائه شود، میزبان از طریق response_format خروجی JSON درخواست می‌کند، به‌عنوان پشتیبان آن را محلی تجزیه می‌کند و در صورت نصب jsonschema آن را با اسکیمای شما اعتبارسنجی می‌کند.

  • result.content_type == "json" — result.parsed شیء پایتونی منطبق با اسکیمای شما است.
  • result.content_type == "text" — تجزیه یا اعتبارسنجی شکست خورده است؛ برای پاسخ خام مدل result.text را بررسی کنید.

ناهمگام

result = await ctx.llm.acomplete(messages=..., task="classifier")
result = await ctx.llm.acomplete_structured(
    instructions=..., input=..., task="classifier"
)

آرگومان‌ها و انواع نتیجه با همتایان همگام یکسان‌اند. از این‌ها در آداپتورهای گیت‌وی، هوک‌های ناهمگام یا هر کد پلاگینی که از قبل روی حلقهٔ asyncio اجرا می‌شود استفاده کنید.

فراخوانی‌های کمکیِ مسیریابی‌شده بر اساس وظیفه

وقتی پلاگین به مسیر کمکیِ پیکربندی‌شدهٔ خودش نیاز دارد، task= را به هر یک از چهار شکل فراخوانی بدهید. آن وظیفه را هنگام راه‌اندازی پلاگین ثبت کنید؛ پیش‌فرض‌های پلاگین اعمال می‌شوند تا زمانی که راهبر ارائه‌دهنده و مدل آن را در auxiliary.<task> بازنویسی کند:

def register(ctx):
    ctx.register_auxiliary_task(
        "classifier", display_name="Classifier", description="Classify input."
    )


result = ctx.llm.complete(messages=[...], task="classifier")
result = ctx.llm.complete_structured(instructions=..., input=..., task="classifier")

auxiliary:
  classifier:
    provider: openrouter
    model: vendor/model-id

پلاگین‌ها می‌توانند برای وظایف خود پیش‌فرض‌های ثبت ارائه‌دهنده/مدل عرضه کنند. پیکربندی راهبر در auxiliary.<task> بر آن پیش‌فرض‌ها مقدم است و انتخاب استقرار را کنترل می‌کند. پلاگین فقط می‌تواند از وظیفه‌ای استفاده کند که خودش ثبت کرده است؛ نام وظیفهٔ ناشناخته یا متعلق به دیگری، پیش از فراخوانی ارائه‌دهنده شکست می‌خورد. allow_task_override: true مجوز صریح راهبر برای استفاده از وظایف کمکیِ داخلی هرمس است؛ وظایف پلاگین دیگر را مجاز نمی‌کند. task= را حذف کنید (یا "auto" بدهید) تا ارائه‌دهنده/مدل اصلیِ فعال حفظ شود.

ویژگی‌های نتیجه

@dataclass
class PluginLlmCompleteResult:
    text: str                    # the assistant's response
    provider: str                # e.g. "openrouter", "anthropic"
    model: str                   # whatever the provider returned for this call
    agent_id: str                # whose model/auth was used
    usage: PluginLlmUsage        # tokens + cache + cost estimate
    audit: Dict[str, Any]        # plugin_id, purpose, profile

@dataclass
class PluginLlmStructuredResult:
    # same fields as PluginLlmCompleteResult, plus:
    parsed: Optional[Any]        # JSON object when content_type == "json"
    content_type: str            # "json" or "text"
    # audit also carries schema_name when supplied

وقتی ارائه‌دهنده این فیلدها را برگرداند، usage شامل input_tokens، output_tokens، total_tokens، cache_read_tokens، cache_write_tokens و cost_usd است.

۸ دروازهٔ اعتماد

رفتار پیش‌فرض، رد پیش‌فرض است. بدون بلوک پیکربندی plugins.entries، پلاگین می‌تواند:

  • هر یک از چهار روش را با ارائه‌دهنده و مدل فعال کاربر اجرا کند،
  • آرگومان‌های شکل‌دهی درخواست (temperature، max_tokens، timeout، system_prompt، purpose، messages، instructions، input، json_schema) را تنظیم کند،

…و همین. آرگومان‌های provider=، model=، agent_id= و profile= تا زمانی که راهبر صریحاً اجازه ندهد، PluginLlmTrustError ایجاد می‌کنند. به همین ترتیب، task= فقط می‌تواند از وظیفهٔ کمکیِ ثبت‌شدهٔ خود پلاگین استفاده کند، مگر اینکه راهبر برای وظیفه‌ای داخلی allow_task_override را مجاز کند.

بیشتر پلاگین‌ها هرگز به این بخش نیاز ندارند. پلاگینی که صرفاً ctx.llm.complete(messages=...) را بدون بازنویسی فراخوانی کند، با گزینهٔ فعال کاربر و بدون پیکربندی کار می‌کند. بلوک زیر فقط وقتی مرتبط است که پلاگین مشخصاً بخواهد به مدل یا ارائه‌دهنده‌ای متفاوت از کاربر مقید شود.

plugins:
  entries:
    my-plugin:
      llm:
        # Allow this plugin to choose a different Hermes provider
        # (must be one Hermes already knows about — same names as
        # `hermes model` and config.yaml model.provider).
        allow_provider_override: true

        # Optionally restrict which providers. Use ["*"] for any.
        allowed_providers:
          - openrouter
          - anthropic

        # Allow this plugin to ask for a specific model.
        allow_model_override: true

        # Optionally restrict which models. Use ["*"] for any.
        # Models are matched literally against whatever string the
        # plugin sends — Hermes does not look anything up.
        allowed_models:
          - openai/gpt-4o-mini
          - anthropic/claude-3-5-haiku

        # Allow cross-agent calls (rare).
        allow_agent_id_override: false

        # Allow the plugin to request a specific stored auth profile
        # (e.g. a different OAuth account on the same provider).
        allow_profile_override: false

شناسهٔ پلاگین برای پلاگین‌های تخت همان فیلد name: در مانیفست است؛ برای پلاگین‌های تودرتو کلید مشتق‌شده از مسیر است (image_gen/openai، memory/honcho و غیره).

دروازه چه چیزی را اعمال می‌کند

بازنویسیپیش‌فرضکلید پیکربندی
provider=ردallow_provider_override: true
↳ فهرست مجاز—allowed_providers: [...]
model=ردallow_model_override: true
↳ فهرست مجاز—allowed_models: [...]
agent_id=ردallow_agent_id_override: true
profile=ردallow_profile_override: true
task= داخلیردallow_task_override: true

هر بازنویسی مستقلاً کنترل می‌شود. اعطای allow_model_override به‌معنای اعطای allow_provider_override نیست — پلاگینی که برای انتخاب مدل مورد اعتماد است، همچنان به ارائه‌دهندهٔ فعال کاربر مقید می‌ماند مگر اینکه مجوز ارائه‌دهنده را هم بگیرد.

دروازه لازم نیست چه چیزی را اعمال کند

  • آرگومان‌های شکل‌دهی درخواست — temperature، max_tokens، timeout، system_prompt، purpose، messages، instructions، input، json_schema، schema_name، json_mode — همیشه مجازند؛ اعتبارنامه یا مسیر را انتخاب نمی‌کنند.
  • رویکرد رد پیش‌فرض به این معنا است که پلاگین پیکربندی‌نشده همچنان می‌تواند کار مفیدی انجام دهد — فقط با ارائه‌دهنده و مدل فعال اجرا می‌شود. راهبران تنها برای پلاگین‌هایی که مسیریابی دقیق‌تری می‌خواهند باید به plugins.entries فکر کنند.

۹ مسئولیت‌های میزبان

فهرست کامل کارهایی که ctx.llm برای پلاگین انجام می‌دهد تا شما مجبور نباشید انجام دهید:

  • تعیین ارائه‌دهنده. model.provider + model.model را از پیکربندی کاربر می‌خواند (یا در صورت اعتماد، بازنویسی‌های صریح را).
  • احراز هویت. کلیدهای API، توکن‌های OAuth یا توکن‌های نوسازی را از ~/.hermes/auth.json / محیط می‌گیرد؛ اگر مخزن اعتبارنامه پیکربندی شده باشد، آن را هم شامل می‌شود. پلاگین هرگز آن‌ها را نمی‌بیند.
  • مسیریابی بینایی. وقتی ورودی تصویر ارائه شود و مدل متنی فعال کاربر فقط متنی باشد، میزبان خودکار به مدل بیناییِ پیکربندی‌شده رجوع می‌کند.
  • زنجیرهٔ پشتیبان. اگر ارائه‌دهندهٔ اصلی کاربر خطای 5xx یا 429 بدهد، درخواست پیش از برگرداندن خطا به پلاگین از مسیر پشتیبان معمول هرمس که از تجمیع‌کننده آگاه است عبور می‌کند.
  • مهلت زمانی. آرگومان timeout= شما را رعایت می‌کند و در نبود آن به پیکربندی auxiliary.<task>.timeout یا پیش‌فرض سراسری فراخوانی کمکی رجوع می‌کند.
  • شکل‌دهی JSON. وقتی JSON می‌خواهید، response_format را به ارائه‌دهنده می‌فرستد و سپس اگر ارائه‌دهنده پاسخی در حصار کد برگرداند، آن را دوباره محلی تجزیه می‌کند.
  • اعتبارسنجی اسکیما. در صورت نصب jsonschema، با json_schema شما اعتبارسنجی می‌کند؛ در غیر این صورت یک خط دیباگ ثبت می‌کند و از اعتبارسنجی سخت‌گیرانه می‌گذرد.
  • لاگ ممیزی. هر فراخوانی یک خط INFO با شناسهٔ پلاگین، ارائه‌دهنده/مدل، هدف و مجموع توکن‌ها در agent.log می‌نویسد.

۱۰ مسئولیت‌های پلاگین

  • شکل درخواست. messages برای گفتگو، instructions + input برای حالت ساخت‌یافته. پلاگین پرامپت را می‌سازد؛ میزبان آن را اجرا می‌کند.
  • اسکیما. هر ساختاری که برای پاسخ می‌خواهید. میزبان آن را برایتان استنباط نمی‌کند.
  • مدیریت خطا. complete_structured() برای ورودی خالی و شکست اعتبارسنجی اسکیما ValueError ایجاد می‌کند. وقتی دروازهٔ اعتماد بازنویسی را رد کند، PluginLlmTrustError رخ می‌دهد. هر مورد دیگر (خطای 5xx ارائه‌دهنده، نبود اعتبارنامهٔ پیکربندی‌شده، پایان مهلت) همان استثنایی را ایجاد می‌کند که auxiliary_client.call_llm() ایجاد می‌کند.
  • هزینه. هر فراخوانی با ارائه‌دهندهٔ پولی کاربر اجرا می‌شود. بدون توجه به مصرف توکن، برای تک‌تک پیام‌های گیت‌وی روی complete() حلقه نزنید.

۱۱ جایگاه این قابلیت در رابط پلاگین

روش‌های موجود ctx.* یک زیرسیستم موجود هرمس را گسترش می‌دهند:

ctx.register_toolابزاری اضافه می‌کند که ایجنت می‌تواند فراخوانی کند
ctx.register_platformآداپتور گیت‌وی جدیدی وصل می‌کند
ctx.register_image_gen_providerبک‌اند تولید تصویر را جایگزین می‌کند
ctx.register_memory_providerبک‌اند حافظه را جایگزین می‌کند
ctx.register_context_engineفشرده‌ساز زمینه را جایگزین می‌کند
ctx.register_hookرویداد چرخهٔ حیات را مشاهده می‌کند

ctx.llm نخستین رابطی است که به پلاگین اجازه می‌دهد همان مدلی را که کاربر با آن گفتگو می‌کند، خارج از مسیر اصلی و بدون هیچ‌یک از موارد بالا اجرا کند. تنها وظیفه‌اش همین است. اگر پلاگین شما باید ابزاری ثبت کند که ایجنت فراخوانی‌اش می‌کند، از register_tool استفاده کنید. اگر باید به رویداد چرخهٔ حیات واکنش نشان دهد، از register_hook استفاده کنید. اگر باید فراخوانی مدلِ خودش را انجام دهد — به هر دلیل، ساخت‌یافته یا غیر آن — از ctx.llm استفاده کنید.
