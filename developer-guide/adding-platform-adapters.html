افزودن آداپتور پلتفرم

این راهنما افزودن یک پلتفرم (platform) پیام‌رسانی جدید به گیت‌وی (gateway) هرمس را پوشش می‌دهد. آداپتور پلتفرم (platform adapter) هرمس را به یک سرویس پیام‌رسانی خارجی (Telegram، Discord، WeCom و…) متصل می‌کند تا کاربران بتوانند از طریق آن سرویس با ایجنت تعامل کنند.

💡

دو راه برای افزودن پلتفرم وجود دارد:

  • پلاگین (برای جامعه/اشخاص ثالث توصیه‌شده): یک پوشهٔ پلاگین در ~/.hermes/plugins/ بیندازید — بدون هیچ تغییری در کد هسته. پایین به مسیر پلاگین نگاه کنید.
  • داخلی: ویرایش بیش از ۲۰ فایل در کد، پیکربندی و مستندات. از چک‌لیست مسیر داخلی پایین استفاده کنید.

۱ نمای کلی معماری

User ↔ Messaging Platform ↔ Platform Adapter ↔ Gateway Runner ↔ AIAgent

هر آداپتور از BasePlatformAdapter در gateway/platforms/base.py ارث می‌برد و این‌ها را پیاده می‌کند:

  • connect() — برقراری اتصال (WebSocket، long-poll، سرور HTTP و…) ‏(انتزاعی)
  • disconnect() — خاموشی تمیز ‏(انتزاعی)
  • send() — ارسال یک پیام متنی به یک چت ‏(انتزاعی)
  • send_typing() — نمایش نشانگر در-حال-نوشتن (بازنویسی اختیاری)
  • get_chat_info() — برگرداندن متادیتای چت (بازنویسی اختیاری)

پیام‌های ورودی توسط آداپتور دریافت و از طریق self.handle_message(event) هدایت می‌شوند؛ کلاس پایه آن‌ها را به gateway runner مسیریابی می‌کند.

۲ مسیر پلاگین (توصیه‌شده)

سامانهٔ پلاگین اجازه می‌دهد بدون دست‌زدن به هیچ کد هستهٔ هرمس، آداپتور پلتفرم اضافه کنید. پلاگین شما یک پوشه با دو فایل است:

~/.hermes/plugins/my-platform/
  plugin.yaml      # متادیتای پلاگین
  adapter.py       # کلاس آداپتور + نقطهٔ ورود register()

plugin.yaml

متادیتای پلاگین. بلوک‌های requires_env و optional_env موارد رابط کاربریِ hermes config را به‌طور خودکار پر می‌کنند (پایین به نمایش متغیرهای محیطی نگاه کنید).

name: my-platform
label: My Platform
kind: platform
version: 1.0.0
description: My custom messaging platform adapter
author: Your Name
requires_env:
  - MY_PLATFORM_TOKEN          # رشتهٔ ساده هم کار می‌کند
  - name: MY_PLATFORM_CHANNEL  # یا دیکشنری کامل برای UX بهتر
    description: "Channel to join"
    prompt: "Channel"
    password: false
optional_env:
  - name: MY_PLATFORM_HOME_CHANNEL
    description: "Default channel for cron delivery"
    password: false

ابزارهای کلاینت خروجی: provides_tools

پلاگین‌های kind: platform ‌به‌تأخیر بارگذاری می‌شوند (deferred): ماژول آداپتور (و ایمپورت‌های SDK آن) فقط وقتی بارگذاری می‌شود که مسیر گیت‌وی، کرون یا send_message برای اولین‌بار از رجیستری پلتفرم‌ها آن پلتفرم را بخواهد. اگر پلاگین شما هم‌چنین ابزارهای کلاینت خروجی‌ای دارد که ایجنت باید بتواند از هر نشستی (session) صدا بزند (مثل a2a_call / a2a_discover پلاگین همراه a2a)، آن‌ها را در یک tools.py جداگانه با تابع register_tools(ctx) بگذارید و در مانیفست اعلام کنید:

provides_tools:
  - my_platform_call
  - my_platform_list

با اعلام provides_tools، هرمس در زمان کشف پلاگین فقط tools.py را ایمپورت می‌کند و ابزارهای کلاینت را در همهٔ پروسس‌ها — از جمله CLI و TUI — ثبت می‌کند، درحالی‌که آداپتور deferred می‌ماند. __init__.py پکیج را از نظر ایمپورت سبک نگه دارید و آداپتور را از داخل register() بیاورید تا ایمپورتِ پیش از موعد ارزان بماند. بدون این فیلد چیزی عوض نمی‌شود: کل پلاگین deferred می‌ماند.

کاربران تول‌ست (toolset) را مثل هر تول‌ست دیگری برای هر پلتفرم فعال می‌کنند، مثلاً با hermes tools enable my_platform --platform cli، یا با فهرست‌کردن کلید تول‌ست زیر platform_toolsets در config.yaml. نام پلتفرم‌های پلاگینی هم مقصد --platform معتبری‌اند، پس می‌توان به یک نشست ورودی روی پلتفرم شما، ابزارهای خروجی مخصوص خودش را داد.

adapter.py

import os
from gateway.platforms.base import (
    BasePlatformAdapter, SendResult, MessageEvent, MessageType,
)
from gateway.config import Platform, PlatformConfig


class MyPlatformAdapter(BasePlatformAdapter):
    def __init__(self, config: PlatformConfig):
        super().__init__(config, Platform("my_platform"))
        extra = config.extra or {}
        self.token = os.getenv("MY_PLATFORM_TOKEN") or extra.get("token", "")

    async def connect(self, *, is_reconnect: bool = False) -> bool:
        # اتصال به API پلتفرم، راه‌اندازی شنونده‌ها
        self._mark_connected()
        return True

    async def disconnect(self) -> None:
        self._mark_disconnected()

    async def send(self, chat_id, content, reply_to=None, metadata=None):
        # ارسال پیام از طریق API پلتفرم
        return SendResult(success=True, message_id="...")

    async def get_chat_info(self, chat_id):
        return {"name": chat_id, "type": "dm"}


def check_requirements() -> bool:
    return bool(os.getenv("MY_PLATFORM_TOKEN"))


def validate_config(config) -> bool:
    extra = getattr(config, "extra", {}) or {}
    return bool(os.getenv("MY_PLATFORM_TOKEN") or extra.get("token"))


def _env_enablement() -> dict | None:
    token = os.getenv("MY_PLATFORM_TOKEN", "").strip()
    channel = os.getenv("MY_PLATFORM_CHANNEL", "").strip()
    if not (token and channel):
        return None
    seed = {"token": token, "channel": channel}
    home = os.getenv("MY_PLATFORM_HOME_CHANNEL")
    if home:
        seed["home_channel"] = {"chat_id": home, "name": "Home"}
    return seed


def register(ctx):
    """نقطهٔ ورود پلاگین — توسط سامانهٔ پلاگین هرمس صدا زده می‌شود."""
    ctx.register_platform(
        name="my_platform",
        label="My Platform",
        adapter_factory=lambda cfg: MyPlatformAdapter(cfg),
        # پروب منفعل (PASSIVE) — «آیا الان وابستگی‌ها/کانفیگ حاضرند؟». از
        # نمایش‌های وضعیت و بارگذاری کانفیگ صدا زده می‌شود، پس هرگز نباید
        # pip-install انجام دهد.
        check_fn=check_requirements,
        # نصب‌کنندهٔ فعال (اختیاری) — فقط برای پلتفرم‌هایی با SDK نصب‌شدنیِ
        # تنبل. create_adapter() وقتی check_fn مقدار False برگرداند، درست
        # قبل از اتصال گیت‌وی به پلتفرم آن را صدا می‌زند. معمولاً
        # tools.lazy_deps.ensure_and_bind(...) را wrap می‌کند. اگر حذفش
        # کنید، False بودن check_fn یک بلاک سخت است.
        # ensure_deps_fn=ensure_requirements,
        validate_config=validate_config,
        required_env=["MY_PLATFORM_TOKEN"],
        install_hint="pip install my-platform-sdk",
        # پیکربندی خودکار با متغیرهای محیطی — قبل از ساخته‌شدن آداپتور،
        # PlatformConfig.extra را از متغیرهای محیطی پر می‌کند. بخش
        # «پیکربندی خودکار با متغیرهای محیطی» را پایین ببینید.
        env_enablement_fn=_env_enablement,
        # پشتیبانی از تحویل کرون به کانال خانه. باعث می‌شود کارهای کرونِ
        # deliver=my_platform بدون ویرایش cron/scheduler.py مسیریابی شوند.
        # بخش «تحویل کرون» را پایین ببینید.
        cron_deliver_env_var="MY_PLATFORM_HOME_CHANNEL",
        # متغیرهای محیطی مجوز کاربر به‌تفکیک پلتفرم
        allowed_users_env="MY_PLATFORM_ALLOWED_USERS",
        allow_all_env="MY_PLATFORM_ALLOW_ALL_USERS",
        # محدودیت طول پیام برای تقسیم‌بندی هوشمند (0 = بدون محدودیت)
        max_message_length=4000,
        # راهنمای LLM که به پرامپت سیستم تزریق می‌شود
        platform_hint=(
            "You are chatting via My Platform. "
            "It supports markdown formatting."
        ),
        # نمایش
        emoji="💬",
    )

    # اختیاری: ثبت ابزارهای مخصوص پلتفرم
    ctx.register_tool(
        name="my_platform_search",
        toolset="my_platform",
        schema={...},
        handler=my_search_handler,
    )

۳ افزونه‌های مسیر ارسال مستقل

یک پلتفرم مستقل می‌تواند با اعلام رفتار ارسال روی همان PlatformEntry که ctx.register_platform() می‌سازد، در تحویل خروجیِ به‌راه‌انداختهٔ میزبان از طریق hermes send --to ... مستقیم و کرونِ deliver=platform:... شرکت کند. send_message عمداً یک ابزار مدلِ قابل‌فراخوانیِ ایجنت نیست؛ پلاگین‌ها نباید معادل سطح‌مدلی ثبت کنند که ایجنت بتواند خودش پیام خروجی آغاز کند.

async def _send_request(args, chat_id, platform_name, pconfig):
    # `args` فیلدهای درخواست ارسالِ به‌راه‌انداختهٔ میزبان را در خود دارد.
    message_id = await client.send(
        address=chat_id,
        body=args["message"],
        subject=args.get("subject"),
    )
    return {"success": True, "platform": platform_name,
            "chat_id": chat_id, "message_id": message_id}


def _parse_address(raw):
    normalized = raw.strip().lower()
    if normalized.startswith("@") and "@" in normalized[1:]:
        return normalized, None  # (chat_id، thread_id اختیاری)
    return None                 # ادامه به resolve فهرست کانال‌ها


def _validate_address(address):
    # True یعنی پذیرش؛ False یعنی رد؛ رشته یعنی رد با همان پیام تشخیصی.
    return True if address.endswith("@example.com") else "unsupported domain"


def register(ctx):
    ctx.register_platform(
        name="fmsg",
        label="Fixture Message",
        adapter_factory=lambda cfg: FmsgAdapter(cfg),
        check_fn=check_requirements,
        parse_target_ref_fn=_parse_address,
        validate_target_ref_fn=_validate_address,
        # می‌تواند تابع معمولی یا async def باشد. هرمس هر نتیجهٔ awaitable
        # را — از جمله آبجکت‌های callable و wrapperهای functools.partial —
        # await می‌کند.
        send_message_handler=_send_request,
        # وقتی کرون باید از پروسسی بدون گیت‌وی زنده ارسال کند، این هوکِ
        # سطح‌پایین‌تر را ترجیح دهید.
        standalone_sender_fn=_standalone_send,
    )

resolve مقصد بین هر سه سطح خروجی مشترک است. خروجی پارسر اول نرمال می‌شود و شناسه‌های فهرست کانال مورد اعتمادند. پارسر پلاگین باید سینتکس بومی مقصد را صریحاً بپذیرد؛ رشته‌های resolve‌نشده هرگز به‌صورت اپک از میان عبور داده نمی‌شوند. پلتفرم‌های ناشناخته و شکست‌های اعتبارسنج به‌جای تلاش بی‌سروصدا برای تحویل، یک پیام تشخیصی برمی‌گردانند. reload اجباری پلاگین و گذار پروفایل، رکوردهای متعلق به پلاگین را لغو ثبت می‌کنند، پس پارسرها و هندلرها نمی‌توانند به پروفایل بعدی نشت کنند.

۴ پیکربندی خودکار با متغیرهای محیطی

بیشتر کاربران پلتفرم را با ریختن متغیرهای محیطی در ~/.hermes/.env راه می‌اندازند، نه با ویرایش config.yaml. هوک (hook) ‏env_enablement_fn به پلاگین شما اجازه می‌دهد آن متغیرهای محیطی را قبل از ساخته‌شدن آداپتور بردارد، تا hermes gateway status، ‏get_connected_platforms() و تحویل کرون بدون نمونه‌سازی SDK پلتفرم، وضعیت درست را ببینند.

def _env_enablement() -> dict | None:
    """پر کردن PlatformConfig.extra از متغیرهای محیطی.

    رجیستری پلتفرم در زمان load_gateway_config() آن را صدا می‌زند.
    وقتی پلتفرم حداقلی پیکربندی نشده None برگردانید — در این صورت
    فراخوان از فعال‌سازی خودکار می‌گذرد. برای پر کردن extras یک dict
    برگردانید.

    کلید خاص 'home_channel' جدا می‌شود و به یک HomeChannel dataclass
    واقعی روی PlatformConfig تبدیل می‌شود؛ هر کلید دیگری در
    PlatformConfig.extra ادغام می‌شود.
    """
    token = os.getenv("MY_PLATFORM_TOKEN", "").strip()
    channel = os.getenv("MY_PLATFORM_CHANNEL", "").strip()
    if not (token and channel):
        return None
    seed = {"token": token, "channel": channel}
    home = os.getenv("MY_PLATFORM_HOME_CHANNEL")
    if home:
        seed["home_channel"] = {
            "chat_id": home,
            "name": os.getenv("MY_PLATFORM_HOME_CHANNEL_NAME", "Home"),
        }
    return seed


def register(ctx):
    ctx.register_platform(
        name="my_platform",
        label="My Platform",
        adapter_factory=lambda cfg: MyPlatformAdapter(cfg),
        check_fn=check_requirements,
        validate_config=validate_config,
        env_enablement_fn=_env_enablement,

    )

۵ پل کانفیگ YAML→env

بعضی کاربران ترجیح می‌دهند به‌جای متغیرهای محیطی، کلیدهای config.yaml‏ (مثل my_platform.require_mention، ‏my_platform.allowed_channels و…) را تنظیم کنند. هوک apply_yaml_config_fn اجازه می‌دهد این ترجمه کارِ پلاگین خودتان باشد، به‌جای آنکه هستهٔ gateway/config.py مجبور شود اسکیمای YAML پلتفرم شما را بداند.

import os

def _apply_yaml_config(yaml_cfg: dict, platform_cfg: dict) -> dict | None:
    """ترجمهٔ کلیدهای `my_platform:` در config.yaml به متغیرهای محیطی / extras.

    yaml_cfg     — دیکشنری کاملِ config.yaml پارس‌شده در سطح بالا
    platform_cfg — زیردیکشنری خود پلتفرم (yaml_cfg.get("my_platform", {}))

    می‌تواند مستقیماً os.environ را تغییر دهد (با گاردهای
    `not os.getenv(...)` اولویت env > YAML حفظ می‌شود) و/یا یک dict
    برای ادغام در PlatformConfig.extra برگرداند. برای «بدون extras»
    مقدار None یا {} برگردانید.
    """
    if "require_mention" in platform_cfg and not os.getenv("MY_PLATFORM_REQUIRE_MENTION"):
        os.environ["MY_PLATFORM_REQUIRE_MENTION"] = str(platform_cfg["require_mention"]).lower()
    allowed = platform_cfg.get("allowed_channels")
    if allowed is not None and not os.getenv("MY_PLATFORM_ALLOWED_CHANNELS"):
        if isinstance(allowed, list):
            allowed = ",".join(str(v) for v in allowed)
        os.environ["MY_PLATFORM_ALLOWED_CHANNELS"] = str(allowed)
    return None  # چیزی برای ادغام در PlatformConfig.extra نیست

def register(ctx):
    ctx.register_platform(
        name="my_platform",
        ...,
        apply_yaml_config_fn=_apply_yaml_config,
    )

این هوک در زمان load_gateway_config() بعد از حلقهٔ عمومی کلیدهای مشترک (که کلیدهای رایج مثل unauthorized_dm_behavior، ‏notice_delivery، ‏reply_prefix، ‏require_mention و… را مدیریت می‌کند) و قبل از _apply_env_overrides() صدا زده می‌شود، پس پلاگین شما فقط لازم است کلیدهای مخصوص پلتفرم را پل بزند.

اکششن‌های raisedشده توسط هوک بلعیده و در سطح debug لاگ می‌شوند — پلاگینِ بدرفتار هرگز بارگذاری کانفیگ گیت‌وی را متوقف نمی‌کند.

۶ تحویل کرون

برای اینکه کارهای کرونِ deliver=my_platform به کانال خانهٔ پیکربندی‌شده مسیریابی شوند، cron_deliver_env_var را برابر نام متغیر محیطی‌ای بگذارید که شناسهٔ پیش‌فرض چت/اتاق/کانال را نگه می‌دارد:

ctx.register_platform(
    name="my_platform",
    ...
    cron_deliver_env_var="MY_PLATFORM_HOME_CHANNEL",
)

زمان‌بند هنگام resolve مقصد خانه برای کارهای deliver=my_platform این متغیر محیطی را می‌خواند و در بررسی‌های به سبک _KNOWN_DELIVERY_PLATFORMS هم پلتفرم را هدف کرونِ معتبر حساب می‌کند. اگر env_enablement_fn شما یک دیکشنری home_channel پر کند (بالا را ببینید)، همان اولویت دارد — ‏cron_deliver_env_var پشتیبانِ کارهای کرونی است که قبل از seeding متغیرهای محیطی اجرا می‌شوند.

تحویل کرون بیرون از پروسس

‏cron_deliver_env_var پلتفرم شما را به یک مقصد شناخته‌شدهٔ deliver= تبدیل می‌کند. برای اینکه ارسال واقعی وقتی کار کرون در پروسسی جدا از گیت‌وی اجرا می‌شود (یعنی hermes cron run جدا از hermes gateway) موفق شود، یک standalone_sender_fn ثبت کنید:

async def _standalone_send(
    pconfig,
    chat_id,
    message,
    *,
    thread_id=None,
    media_files=None,
    force_document=False,
):
    """یک اتصال زودگذر باز کن / توکن تازه بگیر، ارسال کن، و ببند."""
    # ... اتصال را باز کن، پیام را بفرست، نتیجه را برگردان ...
    return {"success": True, "message_id": "..."}
    # یا {"error": "..."}

ctx.register_platform(
    name="my_platform",
    ...
    cron_deliver_env_var="MY_PLATFORM_HOME_CHANNEL",
    standalone_sender_fn=_standalone_send,
)

چرا این هوک لازم است: پلتفرم‌های داخلی (Telegram، Discord، Slack و…) helperهای REST مستقیم را در tools/send_message_tool.py دارند تا کرون بتواند بدون نگه‌داشتن گیت‌وی در همان پروسس تحویل دهد. پلتفرم‌های پلاگینی سابقاً به _gateway_runner_ref() وابسته بودند که بیرون از پروسس گیت‌وی ‏None برمی‌گرداند؛ پس بدون standalone_sender_fn ارسالِ سمت کرون با خطای No live adapter for platform '<name>' شکست می‌خورد.

این تابع همان pconfig و chat_id‌ای را می‌گیرد که آداپتور زنده می‌گرفت، به‌علاوهٔ آرگومان‌های کلیدواژه‌ای اختیاری thread_id، ‏media_files و force_document. برگرداندن {"success": True, "message_id": ...} تحویل موفق حساب می‌شود؛ برگرداندن {"error": "..."} پیام را در delivery_errors کرون ظاهر می‌کند. اکششن‌های داخل تابع توسط dispatcher گرفته می‌شوند و با پیام Plugin standalone send failed: <reason> گزارش می‌شوند. پیاده‌سازی‌های مرجع در plugins/platforms/{irc,teams,google_chat}/adapter.py هستند.

۷ نمایش متغیرهای محیطی در hermes config

‏hermes_cli/config.py در زمان ایمپورت، ‏plugins/platforms/*/plugin.yaml را اسکن می‌کند و OPTIONAL_ENV_VARS را از بلوک‌های requires_env و (اختیاری) optional_env به‌طور خودکار پر می‌کند. از فرم دیکشنریِ کامل استفاده کنید تا description، prompt، پرچم password و URLهای درست به UI بدهید — رابط setup در CLI آن‌ها را مجانی برمی‌دارد.

۸ تجربهٔ کاربری مخصوص پلتفرم برای LLMِ کند

بعضی پلتفرم‌ها محدودیت‌هایی دارند که نحوهٔ ارائهٔ پاسخِ کندِ LLM را عوض می‌کند:

  • LINE یک reply token یک‌بارمصرف صادر می‌کند که تقریباً ۶۰ ثانیه بعد از رویداد ورودی منقضی می‌شود. پاسخ‌دادن با آن توکن مجانی است؛ افتادن به API پولی Push این‌طور نیست. اگر LLM تا ددلاین کارش تمام نشده باشد، انتخاب بین «سوزاندن سهمیهٔ پولی Push» یا «کار هوشمندانه‌تر با reply token قبل از انقضای آن» است.
  • WhatsApp بعد از ۲۴ ساعت نشست را غیرفعال علامت می‌زند و بعد از آن فقط پیام‌های template پذیرفته می‌شوند.
  • SMS مفهوم نشانگر در-حال-نوشتن یا به‌روزرسانی تدریجی ندارد — پاسخ‌های طولانی فقط این حس را می‌دهند که بات آفلاین است.

این‌ها محدودیت‌های واقعی‌ای هستند که BasePlatformAdapter پایه نمی‌تواند پیش‌بینی‌شان کند. سطح پلاگین عمداً جا می‌گذارد تا آداپتور بتواند UX مخصوص پلتفرم را روی حلقهٔ typing پایه لایه کند، بدون آنکه فهرست kwargها بزرگ شود.

الگو: زیرکلاس‌کردن _keep_typing برای لایه‌کردن UX حین کار

‏BasePlatformAdapter._keep_typing تپشِ نشانگر typing است — درحالی‌که LLM در حال تولید است به‌عنوان تسک پس‌زمینه اجرا می‌شود و وقتی پاسخ تحویل داده شد لغو می‌شود. برای لایه‌کردن یک رفتار مخصوص پلتفرم روی یک آستانه (مثلاً فرستادن حباب «هنوز دارم فکر می‌کنم» در ثانیهٔ ۴۵)، در آداپتور خودتان _keep_typing را بازنویسی کنید، تسک خودتان را کنار super()._keep_typing() زمان‌بندی کنید، و در finally جمعش کنید:

class LineAdapter(BasePlatformAdapter):
    async def _keep_typing(self, chat_id: str, *args, **kwargs) -> None:
        if self.slow_response_threshold <= 0:
            await super()._keep_typing(chat_id, *args, **kwargs)
            return

        async def _fire_at_threshold() -> None:
            try:
                await asyncio.sleep(self.slow_response_threshold)
            except asyncio.CancelledError:
                raise
            # کار مخصوص پلتفرم اینجا — برای LINE، حباب Template Buttons
            # «Get answer» را با reply token کش‌شده بفرستید تا کاربر
            # بعداً بتواند پاسخ کش‌شده را با یک reply token تازه
            # (مجانی) از کال‌بک postback بگیرد.
            await self._send_slow_response_button(chat_id)

        side_task = asyncio.create_task(_fire_at_threshold())
        try:
            await super()._keep_typing(chat_id, *args, **kwargs)
        finally:
            if not side_task.done():
                side_task.cancel()
                try:
                    await side_task
                except (asyncio.CancelledError, Exception):
                    pass

نکات کلیدی:

  • همیشه ‏await super()._keep_typing(...) را صدا بزنید. تپش typing به‌خودش مفید است — جایگزینش نکنید، روی آن لایه بگذارید.
  • تسک جانبی را در finally جمع کنید. وقتی LLM تمام می‌شود (یا /stop ران را لغو می‌کند)، گیت‌وی تسک typing را لغو می‌کند. تسک جانبی شما هم باید آن لغو را حس کند، وگرنه باقی می‌ماند و ممکن است بعد از تحویل‌شدن پاسخ آتش بگیرد.
  • با interrupt_session_activity جفت کنید تا هر وضعیت UX یتیم وقتی کاربر /stop می‌زند حل شود. برای LINE یعنی انتقال رکورد کش postback از PENDING به ERROR تا دکمهٔ پایدار «Get answer» به‌جای حلقه‌زدن، پیام «Run was interrupted» تحویل دهد.

الگو: زیرکلاس‌کردن send برای مسیردادن از طریق کش به‌جای ارسال فوری

اگر UX پاسخ‌کندِ شما پاسخ را برای بازیابی بعدی کش می‌کند (جریان postback خط LINE)، بازنویسی send شما باید سه حالت را تشخیص دهد:

  1. postback در انتظار برای این چت فعال است → پاسخ را زیر request_id کش کن، هیچ چیز قابل‌دیدنی نفرست.
  2. تأیید مشغولیت سیستم‏ (⚡ Interrupting، ‏⏳ Queued، ‏⏩ Steered) → از کش عبور کن و قابل‌دیدن بفرست تا کاربر پاسخ گیت‌وی به ورودی‌اش را ببیند.
  3. پاسخ عادی → مثل همیشه با reply-token-یا-push بفرست.
async def send(self, chat_id: str, content: str, **kw) -> SendResult:
    if _is_system_bypass(content):
        return await self._send_text_chunks(chat_id, content, force_push=False)
    pending_rid = self._pending_buttons.get(chat_id)
    if pending_rid:
        self._cache.set_ready(pending_rid, content)
        return SendResult(success=True, message_id=pending_rid)
    return await self._send_text_chunks(chat_id, content, force_push=False)

‏_SYSTEM_BYPASS_PREFIXES پیشوندهای تأیید مشغولیتِ خودِ گیت‌وی‌اند‏ (⚡، ‏⏳، ‏⏩، ‏💾). فارغ از وضعیت UX کش‌شده، همیشه اجازه دهید این‌ها قابل‌دیدن رد شوند.

چه وقت این الگو مناسب است

رویکرد بازنویسی حلقهٔ typing را وقتی استفاده کنید که:

  • API خروجی پلتفرم محدودیت پنجرهٔ زمانی سخت دارد (reply token یک‌بارمصرف، نشست sticky منقضی‌شونده و…) و
  • یک حباب قابل‌مشاهدهٔ حین کار در آن پلتفرم UX قابل‌قبولی باشد.

مسیر ساده‌ترِ همیشه-Push با slow_response_threshold = 0 را وقتی استفاده کنید که:

  • پلتفرم تفکیک معنادار مجانی/پولی ندارد، یا
  • جامعهٔ کاربران «سکوتِ بعد-پاسخ» به سبک «loading… loading… DONE» را به یک حباب تعاملی میانی ترجیح می‌دهد.

LINE هر دو را پشتیبانی می‌کند: آستانه به‌طور پیش‌فرض برای واکشی مجانی postback ‏۴۵ ثانیه است و LINE_SLOW_RESPONSE_THRESHOLD=0 به «همیشه fallback به Push» برمی‌گردد.

پیاده‌سازی مرجع

پیاده‌سازی کامل postback خط LINE را در plugins/platforms/line/adapter.py ببینید — یک ماشین حالت RequestCache‏ (PENDING → READY → DELIVERED، به‌علاوهٔ ERROR برای /stop)، یک بازنویسی _keep_typing که در آستانه حباب Template Buttons را می‌فرستد، یک بازنویسی send که از کش مسیر می‌دهد، و یک بازنویسی interrupt_session_activity که رکوردهای PENDING یتیم را حل می‌کند.

پیاده‌سازی‌های مرجع (مسیر پلاگین)

یک مثال کامل و کارا را در plugins/platforms/irc/ مخزن ببینید — یک آداپتور IRC ناهمگامِ کامل بدون هیچ وابستگی خارجی. ‏plugins/platforms/teams/ پوشش Bot Framework / Adaptive Cards است، ‏plugins/platforms/google_chat/ پوشش APIهای REST مبتنی بر OAuth و ‏plugins/platforms/line/ پوشش APIهای پیام‌رسانیِ وب‌هوک‌محور با UX مخصوص پلتفرم برای LLM کند.

۱۰ ممیزی برابری (parity)

قبل از علامت‌زدن PR پلتفرم جدید به‌عنوان کامل، یک ممیزی برابری در برابر یک پلتفرم جاافتاده اجرا کنید:

# پیدا کردن هر فایل .py که به پلتفرم مرجع اشاره می‌کند
search_files "bluebubbles" output_mode="files_only" file_glob="*.py"

# پیدا کردن هر فایل .py که به پلتفرم جدید اشاره می‌کند
search_files "newplat" output_mode="files_only" file_glob="*.py"

# هر فایلی که در مجموعهٔ اول باشد ولی در دوم نه، یک شکاف احتمالی است

برای فایل‌های .md و .ts هم تکرار کنید. هر شکاف را بررسی کنید — یک شمارش پلتفرم است (باید به‌روز شود) یا یک ارجاع مخصوص پلتفرم (رد شود)؟

۱۱ الگوهای رایج

آداپتورهای Long-Poll

اگر آداپتور شما long-polling استفاده می‌کند (مثل Telegram یا Weixin)، از یک تسک حلقهٔ polling استفاده کنید:

async def connect(self):
    self._poll_task = asyncio.create_task(self._poll_loop())
    self._mark_connected()

async def _poll_loop(self):
    while self._running:
        messages = await self._fetch_updates()
        for msg in messages:
            await self.handle_message(self._build_event(msg))

آداپتورهای Callback/Webhook

اگر پلتفرم پیام‌ها را به نقطهٔ پایانی شما push می‌کند (مثل WeCom Callback)، یک سرور HTTP اجرا کنید:

async def connect(self):
    self._app = web.Application()
    self._app.router.add_post("/callback", self._handle_callback)
    # ... سرور aiohttp را راه بیندازید
    self._mark_connected()

async def _handle_callback(self, request):
    event = self._build_event(await request.text())
    await self._message_queue.put(event)
    return web.Response(text="success")  # بلافاصله تأیید (ack) کن

برای پلتفرم‌هایی با ددلاین پاسخِ تنگ (مثل محدودیت ۵ ثانیه‌ای WeCom)، همیشه بلافاصله تأیید کنید و پاسخ ایجنت را بعداً به‌طور فعال از طریق API تحویل دهید. نشست‌های ایجنت ۳ تا ۳۰ دقیقه طول می‌کشند — پاسخ درون‌خطی داخل پنجرهٔ پاسخ کال‌بک عملی نیست.

قفل‌های توکن

اگر آداپتور یک اتصال پایدار با یک اعتبارنامهٔ یکتا نگه می‌دارد، یک قفل scoped اضافه کنید تا دو پروفایل از یک اعتبارنامه استفاده نکنند:

from gateway.status import acquire_scoped_lock, release_scoped_lock

async def connect(self, *, is_reconnect: bool = False):
    acquired, _existing = acquire_scoped_lock("newplat", self._token)
    if not acquired:
        logger.error("Token already in use by another profile")
        return False
    # ... اتصال

async def disconnect(self):
    release_scoped_lock("newplat", self._token)
