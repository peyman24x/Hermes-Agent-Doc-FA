مشارکت در پروژه

از مشارکت شما در Hermes Agent متشکریم! این راهنما راه‌اندازی محیط توسعه، شناخت کدبیس و ادغام‌شدن PR شما را پوشش می‌دهد.

۱ اولویت‌های مشارکت

مشارکت‌ها را به این ترتیب ارزش‌گذاری می‌کنیم:

  1. رفع باگ — کرش‌ها، رفتار نادرست، از دست رفتن داده
  2. سازگاری چندپلتفرمی — macOS، توزیع‌های مختلف لینوکس، WSL2
  3. سخت‌سازی امنیتی — تزریق شل، تزریق پرامپت، پیمایش مسیر (path traversal)
  4. کارایی و استواری — منطق تلاش مجدد، مدیریت خطا، افت تدریجیِ کنترل‌شده (graceful degradation)
  5. مهارت‌های جدید — آن‌هایی که به‌طور گسترده مفیدند (نگاه کنید به ساخت مهارت)
  6. ابزارهای جدید — به‌ندرت لازم می‌شوند؛ بیشتر قابلیت‌ها باید مهارت باشند
  7. مستندات — اصلاحات، شفاف‌سازی‌ها، مثال‌های جدید

۲ مسیرهای رایج مشارکت

  • می‌خواهید یک ابزار سفارشی/محلی بدون دست‌کاری هستهٔ هرمس بسازید؟ با ساخت پلاگین هرمس شروع کنید
  • می‌خواهید یک ابزار هستهٔ داخلی جدید برای خود هرمس بسازید؟ با افزودن ابزار جدید شروع کنید
  • می‌خواهید یک مهارت جدید بسازید؟ با ساخت مهارت شروع کنید
  • می‌خواهید یک ارائه‌دهندهٔ استنتاج جدید بسازید؟ با افزودن ارائه‌دهندهٔ جدید شروع کنید

۳ راه‌اندازی توسعه

نصب با نصب‌کنندهٔ استاندارد

برای بیشتر مشارکت‌کنندگان، بهترین نقطهٔ شروع توسعه همان مسیری است که کاربران طی می‌کنند: نصب‌کنندهٔ استاندارد را اجرا کنید و سپس داخل مخزنی که کلون می‌کند کار کنید. نصب‌کننده venv هرمس را می‌سازد، فرمان hermes را وصل می‌کند، روش نصب را برای hermes update ثبت می‌کند و پروژهٔ کامل گیت را در $HERMES_HOME/hermes-agent (معمولاً ~/.hermes/hermes-agent) کلون می‌کند. این کار محیط توسعهٔ شما را روی همان چیدمانی نگه می‌دارد که CLI، به‌روزرسان، نصب‌کنندهٔ تنبلِ وابستگی‌ها، گیت‌وی و مستندات فرض می‌کنند.

curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
cd "${HERMES_HOME:-$HOME/.hermes}/hermes-agent"

# افزودن اکستراهای dev/test روی نصب استاندارد.
uv pip install -e ".[all,dev]"

# اختیاری: وابستگی‌های ابزارهای مرورگر / سایت مستندات.
npm install

بعد از آن، از همان checkout شاخه بسازید و تست‌ها را اجرا کنید:

git checkout -b fix/description
scripts/run_tests.sh

همچنین می‌توانید یک نمونهٔ کاملاً ایزولهٔ هرمس اجرا کنید (HERMES_HOME یک‌بارمصرف، userData جداگانهٔ Electron و نام اپلیکیشن Electron متمایز برای جلوگیری از قفل تک‌نمونه‌ای):

scripts/dev-sandbox.sh python -m hermes_cli.main
scripts/dev-sandbox.sh --persistent python -m hermes_cli.main desktop  # وضعیت پس از ری‌استارت باقی می‌ماند، ولی در ورک‌تری زندگی می‌کند :)

کلون دستی (گزینهٔ جایگزین)

از این روش فقط وقتی استفاده کنید که عمداً چیدمان نصبِ مدیریت‌شدهٔ هرمس را نمی‌خواهید (مثلاً یک کلون یک‌بارمصرف داخل کانتینر یا job کاری CI). اگر این‌طور نصب کردید، مطمئن شوید نقطهٔ ورود hermes را از همین venv اجرا می‌کنید؛ اجرای python3 -m hermes_cli.main سیستمی می‌تواند بسته‌های پایتونِ نامرتبط سیستم را بار بگیرد.

venv را بیرون از درخت سورسِ کلون‌شده بسازید. venvی که داخل پوشه‌ای که ایجنت در آن کار می‌کند زندگی کند، می‌تواند با یک فرمانِ مسیر-نسبی که ایجنت روی checkout خودش اجرا می‌کند (rm -rf venv، uv venv venv و...) پاک شود و این بی‌سروصدا رانتایمِ در حال اجرا را وسط نشست نابود می‌کند. نگه‌داشتن آن بیرون از درخت یعنی هیچ مسیر نسبی از فضای کاری به آن نمی‌رسد.

git clone https://github.com/NousResearch/hermes-agent.git
cd hermes-agent

# ساخت venv با Python 3.11، بیرون از درخت سورس
uv venv ~/.hermes/venvs/hermes-dev --python 3.11
export VIRTUAL_ENV="$HOME/.hermes/venvs/hermes-dev"
export PATH="$VIRTUAL_ENV/bin:$PATH"

# نصب با همهٔ اکستراها (پیام‌رسانی، کرون، منوهای CLI، ابزارهای توسعه)
uv pip install -e ".[all,dev]"

# اختیاری: ابزارهای مرورگر
npm install

پیکربندی برای توسعه

mkdir -p ~/.hermes/{cron,sessions,logs,memories,skills}
cp cli-config.yaml.example ~/.hermes/config.yaml
touch ~/.hermes/.env

# حداقل یک کلید ارائه‌دهندهٔ LLM اضافه کنید:
echo 'OPENROUTER_API_KEY=sk-or-v1-your-key' >> ~/.hermes/.env

اجرا

# نصب‌کنندهٔ استاندارد از قبل `hermes` را روی PATH گذاشته است.
hermes doctor
hermes chat -q "Hello"

اگر از کلون دستی استفاده کرده‌اید، ./hermes را از checkout اجرا کنید یا venv این کلون را صریحاً symlink کنید:

mkdir -p ~/.local/bin
ln -sf "$(pwd)/venv/bin/hermes" ~/.local/bin/hermes

scripts/run_tests.sh

۴ سبک کد

  • PEP 8 با استثناهای عملی (بدون اعمال سخت‌گیرانهٔ طول خط)
  • کامنت‌ها: فقط وقتی که نیتِ غیربدیهی، موازنه‌ها یا خَلق‌وخوهای عجیب API را توضیح می‌دهند
  • مدیریت خطا: اکششن‌های مشخص بگیرید. برای خطاهای غیرمنتظره از logger.warning()/logger.error() با exc_info=True استفاده کنید
  • چندپلتفرمی: هرگز یونیکس را مفروض نگیرید (پایین را ببینید)
  • مسیرهای امن از نظر پروفایل: هرگز ~/.hermes را هاردکد نکنید — برای مسیرهای کد از get_hermes_home() در hermes_constants و برای پیام‌های رو به کاربر از display_hermes_home() استفاده کنید. قواعد کامل را در AGENTS.md ببینید.

۵ سازگاری چندپلتفرمی

نگاه کنید به پشتیبانی پلتفرم‌ها. ویندوز بومی برای فرمان‌های شل از Git Bash (از Git for Windows) استفاده می‌کند. چند قابلیت به پریمیتیوهای هستهٔ POSIX نیاز دارند و گیت‌شده‌اند: پنل ترمینال PTY تعبیه‌شده در داشبورد (تب /chat) به یک PTY سیستمی POSIX نیاز دارد (لینوکس، macOS یا WSL2). اگر توسعهٔ سنگین ویندوزی انجام می‌دهید، قبل از push لینت Windows-footgun (scripts/check-windows-footguns.py) را اجرا کنید.

وقتی کد مشارکت می‌دهید، این قواعد را در نظر داشته باشید:

  • ارجاعِ بدون گارد به signal.SIGKILL اضافه نکنید. این ثابت روی ویندوز تعریف نشده است. یا از gateway.status.terminate_pid(pid, force=True) عبور دهید (پریمیتیو متمرکزی که روی ویندوز taskkill /T /F و روی POSIX سیگنال SIGKILL را اجرا می‌کند)، یا با getattr(signal, "SIGKILL", signal.SIGTERM) پشتیبان بسازید.
  • در پروب‌های os.kill(pid, 0) علاوه بر ProcessLookupError، OSError را هم بگیرید. ویندوز برای PIDِ از-قبل-رفته به‌جای ProcessLookupError خطای OSError می‌دهد (WinError 87 با پیام «parameter is incorrect»).
  • ترمینال را به معناشناسی POSIX مجبور نکنید. os.setsid، os.killpg، os.getpgid و os.fork همگی روی ویندوز خطا می‌دهند — آن‌ها را با if sys.platform != "win32": یا if os.name != "nt": گیت کنید.
  • فایل‌ها را با encoding="utf-8" صریح باز کنید. پیش‌فرض پایتون روی ویندوز همان locale سیستم است (اغلب cp1252) که روی متن غیرلاتین به‌هم می‌ریزد یا کرش می‌کند.
  • از pathlib.Path / os.path.join استفاده کنید — هرگز دستی با / رشته‌ها را به هم نچسبانید. این موضوع برای رشته‌هایی که سیستم‌عامل به ما برمی‌گرداند کمتر، و برای رشته‌هایی که خودمان می‌سازیم و به ساب‌پروسس می‌دهیم بیشتر اهمیت دارد.

الگوهای کلیدی:

۱. انکودینگ فایل

بعضی محیط‌ها ممکن است فایل‌های .env را با انکودینگ‌های غیر-UTF-8 ذخیره کنند:

try:
    load_dotenv(env_path)
except UnicodeDecodeError:
    load_dotenv(env_path, encoding="latin-1")

۲. مدیریت پروسس

os.setsid()، os.killpg() و مدیریت سیگنال بین پلتفرم‌ها فرق دارند:

import platform
if platform.system() != "Windows":
    kwargs["preexec_fn"] = os.setsid

۳. جداکننده‌های مسیر

به‌جای چسباندن رشته‌ها با / از pathlib.Path استفاده کنید.

مشارکت در کدهای حساس امنیتی

  • هنگام درون‌ریزی ورودی کاربر در فرمان‌های شل، همیشه از shlex.quote() استفاده کنید
  • قبل از بررسی‌های کنترل دسترسی، symlinkها را با os.path.realpath() resolve کنید
  • رمزها را لاگ نکنید
  • دور اجرای ابزار، اکششن‌های کلی بگیرید
  • اگر تغییر شما به مسیر فایل یا پروسس‌ها دست می‌زند، روی همهٔ پلتفرم‌ها تست کنید

۷ فرایند Pull Request

نام‌گذاری شاخه

fix/description        # رفع باگ
feat/description       # قابلیت‌های جدید
docs/description       # مستندات
test/description       # تست‌ها
refactor/description   # بازآرایی کد

قبل از ارسال

  1. تست‌ها را اجرا کنید: scripts/run_tests.sh برای هم‌سانی با CI. از python -m pytest ... مستقیم فقط وقتی استفاده کنید که wrapper در دسترس نباشد یا عمداً بیرون از wrapper دیباگ می‌کنید.
  2. دستی تست کنید: hermes را اجرا کنید و مسیر کدی را که تغییر داده‌اید امتحان کنید
  3. اثر چندپلتفرمی را بررسی کنید: macOS، لینوکس، WSL2 و ویندوز بومی را در نظر بگیرید. اگر به I/O فایل، مدیریت پروسس، مدیریت ترمینال، ساب‌پروسس‌ها یا سیگنال‌ها دست می‌زنید، scripts/check-windows-footguns.py را اجرا کنید.
  4. PRها را متمرکز نگه دارید: در هر PR فقط یک تغییر منطقی

  • چطور تستش کنید

چک‌لیست‌های بازبینیِ محلیِ مخزن: .agents/checks/*.md

پروژه‌هایی که روی هرمس ساخته شده‌اند (یا توسط هرمس بازبینی می‌شوند) می‌توانند چک‌لیست‌های بازبین را داخل مخزن و زیر .agents/checks/ نگه دارند. هر فایل یک چک‌لیست متمرکز و مارک‌داونِ ساده است که ایجنت قبل از بازبینیِ تغییری که به همان حوزه می‌خورد، بارگذاری می‌کند:

.agents/
  checks/
    security.md        # مثلاً: «diff را برای درون‌ریزی شل grep کن؛ چک کن فراخوانی‌های subprocess آرگومان‌ها را quote کنند»
    migrations.md      # مثلاً: «هر تغییر اسکیما با یک backfill و یک یادداشت بازگشت (Rollback) همراه است»
    public-api.md      # مثلاً: «امضاهای صادرشده تغییر کرده‌اند؟ برای بازبینی semver علامت بزن»

قراردادهایی که این‌ها را خوب کار می‌کنند:

  • یک نگرانی در هر فایل، با نامِ همان نگرانی. فایل‌های کوچک کامل خوانده می‌شوند؛ یک checklist.md یکپارچه فقط تندخوانی می‌شود.
  • چک‌ها را به‌شکل اقدامِ قابل راستی‌آزمایی بنویسید («X را اجرا کن و Y را تأیید کن»)، نه آرزو («کد باید امن باشد»).
  • محرک را در بالای فایل بگویید — چک‌لیست به کدام مسیرها یا نوع تغییرها مربوط است — تا ایجنت (یا انسان) بتواند به‌شکل ارزان از کنار موارد بی‌ربط عبور کند.
  • آن‌ها را کنار کدی که از آن محافظت می‌کنند در کنترل نسخه نگه دارید: با کدبیس تکامل می‌یابند و PRای که قواعد را تغییر دهد، چک‌لیست را هم در همان دیف تغییر می‌دهد.

وقتی از هرمس می‌خواهید PRای را در مخزنی که .agents/checks/ دارد بازبینی کند، به او بگویید (یا با یک مهارت به او یاد بدهید) اول چک‌لیست‌های مربوط را بخواند و بر اساس آن‌ها گزارش بدهد. این کار به ایجنت‌های بازبین همان معیارِ مخصوص پروژه را می‌دهد که پرامپت‌های بازبینی عمومی از دستشان می‌رود.
