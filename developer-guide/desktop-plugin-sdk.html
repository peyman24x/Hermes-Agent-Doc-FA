SDK پلاگین دسکتاپ

اپلیکیشن بومی Hermes Desktop مبتنی بر مشارکت است: هر سطح در پنجره — پن‌ها، مسیرها، ناوبری سایدبار، آیتم‌های نوار وضعیت، ورودی‌های پالت، کلیدهای میان‌بر و تم‌ها — در یک رجیستری مرکزی واحد ثبت می‌شود. هسته سطوح خودش را دقیقاً به همان شکلی ثبت می‌کند که یک پلاگین ثبت می‌کند؛ بنابراین داستان پلاگین همان داستان اصلی و واقعی است، نه یک الحاقِ بعدیِ چسبانده‌شده.

یک پلاگین دسکتاپ یک فایل ESM تکی است که به‌طور پیش‌فرض یک HermesPlugin اکسپورت می‌کند. فقط یک ماژول ایمپورت می‌کند — @hermes/plugin-sdk — و همه‌چیز را می‌گیرد: وضعیت زندهٔ اپلیکیشن، درِ JSON-RPC گیت‌وی، یک فضای‌نام بک‌اند REST/socket با محدودهٔ مشخص، React Query و کیت UI خودِ اپلیکیشن، به‌طوری که UI پلاگین به‌طور پیش‌فرض بومی به نظر می‌رسد. نه کلونِ مخزن لازم است، نه npm run build، نه دست‌کاری سورس اپلیکیشن. فایل را در $HERMES_HOME/desktop-plugins/<id>/plugin.js بگذارید؛ اپلیکیشن ظرف چند ثانیه آن را بارگذاری می‌کند و با هر ذخیره hot-reload می‌کند.

⚠️ این، SDK پلاگینِ داشبورد وب نیست

واژهٔ «پلاگین» در سراسر Hermes چند معنای نامرتبط دارد. این صفحه SDKِ اپلیکیشن دسکتاپ بومی (hermes desktop) است — یعنی ماژول @hermes/plugin-sdk و مسیر $HERMES_HOME/desktop-plugins/. داشبورد وب (hermes dashboard) سیستم پلاگین جداگانه و نامرتبط خودش را دارد که روی window.__HERMES_PLUGIN_SDK__ کار می‌کند و manifest.json دارد — مستندات آن در گسترش داشبورد وب است. پلاگین‌های پایتونیِ CLI/گیت‌وی در ساخت پلاگین هرمس مستند شده‌اند. این سه هیچ کد، API یا روش توزیع مشترکی ندارند. تنها بخش مشترک میان SDK دسکتاپ و داشبورد، فضای‌نام بک‌اندِ plugin_api.py (یعنی /api/plugins/<id>) است.

۱ مدل ذهنی

این SDK از مدل ماژولِ VS Code پیروی می‌کند. نویسندهٔ پلاگین دقیقاً یک ماژول ایمپورت می‌کند و هرگز با بخش‌های داخلی اپلیکیشن کار نمی‌کند (در پلاگین هم‌بسته با لینت مسدودند و در پلاگین دیسکی resolve نمی‌شوند). قابلیت‌ها در لایه‌هایی عرضه می‌شوند:

  • host.state.* — نمای‌های فقط-خواندنی روی وضعیت زندهٔ اپلیکیشن (اتم‌های nanostore): نشست فعال، مشغول‌بودنِ نوبت به تفکیک نشست، cwd، وضعیت سوکت گیت‌وی، مدل، پروفایل و viewport. gateway وضعیت WebSocket است، نه مشغول‌بودنِ نوبت.
  • اکشن‌های host.* — فعل‌های امنِ گزینش‌شده: نمایش toast، ناوبری، دنبال‌کردن لاگ‌ها، ری‌استارت گیت‌وی و اشتراک در جریان رویداد گیت‌وی.
  • host.request — درِ JSON-RPC گیت‌وی: نشست‌ها، پیکربندی، مهارت‌ها، کرون — هرچه خودِ اپلیکیشن فراخوانی می‌کند.
  • ctx.rest / ctx.socket — فضای‌نام بک‌اندِ اختصاصی پلاگین شما (/api/plugins/<id>)، اگر یک plugin_api.py همراه پلاگین بفرستید.
  • ui.* — زبان طراحی: کامپوننت‌های واقعی اپلیکیشن، متغیرهای تم، آیکون‌ها و قالب‌بندها، تا UI شما با اپلیکیشن پیکسل‌به‌پیکسل هم‌خوان شود.

۳ شروع سریع — اولین پلاگین شما

فایل $HERMES_HOME/desktop-plugins/hello/plugin.js را بسازید (به‌طور پیش‌فرض یعنی ~/.hermes/...، یا زیر یک پروفایل نام‌دار در ~/.hermes/profiles/<name>/...). نام پوشه باید با id پلاگین برابر باشد.

// ~/.hermes/desktop-plugins/hello/plugin.js
import { host, haptic, useValue } from '@hermes/plugin-sdk'
import { jsx, jsxs } from 'react/jsx-runtime'

function HelloPane() {
  const gateway = useValue(host.state.gateway)

  return jsxs('div', {
    className: 'flex h-full flex-col gap-2 p-3 text-sm',
    children: [
      jsx('div', { className: 'font-medium', children: 'Hello, Hermes' }),
      jsx('div', {
        className: 'text-(--ui-text-tertiary)',
        children: `gateway: ${gateway}`
      })
    ]
  })
}

export default {
  id: 'hello', // باید با نام پوشه یکی باشد
  name: 'Hello',
  register(ctx) {
    ctx.register({
      id: 'pane',
      area: 'panes',
      title: 'hello',
      data: { placement: 'right', width: '260px' },
      render: () => jsx(HelloPane, {})
    })
    ctx.register({
      id: 'chip',
      area: 'statusBar.right',
      order: 130,
      render: () =>
        jsx('button', {
          type: 'button',
          className: 'px-1.5 text-[0.6875rem] text-(--ui-text-tertiary)',
          onClick: () => {
            haptic('tap')
            host.notify({ kind: 'info', message: 'Hello from my plugin!' })
          },
          children: 'hello'
        })
    })
  }
}

ذخیره‌اش کنید. اپلیکیشن پوشهٔ desktop-plugins/ را زیر نظر دارد، فایل را ظرف چند ثانیه بارگذاری می‌کند و ذخیره‌های بعدی را در جا hot-reload می‌کند. اگر ظاهر نشد، ⌘K را بزنید و Reload desktop plugins را اجرا کنید. اگر بارگذاری شکست بخورد، یک toast نام خطا را اعلام می‌کند — اصلاح کنید و دوباره ذخیره کنید.

ℹ️ بدون JSX، بدون بیلد

فایل دیسکی بدون کامپایل بارگذاری می‌شود، پس سینتکس JSX پارس نخواهد شد. UI را با فراخوانی‌های jsx() / jsxs() از react/jsx-runtime (یا React.createElement) بنویسید. تنها specifierهای قابل ایمپورت، @hermes/plugin-sdk و react و react/jsx-runtime هستند — هر چیز دیگری عمداً resolve نمی‌شود.

۴ قرارداد پلاگین

هر پلاگین یک HermesPlugin را به‌طور پیش‌فرض اکسپورت می‌کند:

interface HermesPlugin {
  /** اسلاگِ پایدار — به منبع `plugin:<id>` و فضای‌نام id تبدیل می‌شود. */
  id: string
  /** نام انسانی برای Settings / رابط about. پیش‌فرض همان `id` است. */
  name?: string
  /** هنگام بارگذاری ثبت می‌شود وقتی کاربر انتخابی نکرده باشد (پیش‌فرض true). برای پلاگین‌های opt-in
   *  مقدار false بگذارید: در Settings ▸ Plugins فهرست می‌شوند، اما تا وقتی کاربر کلید را نزند خاموش‌اند. */
  defaultEnabled?: boolean
  /** یک‌بار هنگام بارگذاری صدا زده می‌شود؛ مشارکت‌ها را از طریق `ctx` وصل کنید. */
  register: (ctx: PluginContext) => void
}

register یک PluginContext با محدودهٔ مشخص دریافت می‌کند. این کانتکست هرگز مستقیماً با رجیستری کار نمی‌کند — کانتکست به‌طور خودکار منشأ را تگ می‌زند (source: 'plugin:<id>') و id هر مشارکت را در فضای‌نام قرار می‌دهد (<id>:<localId>)، بنابراین دو پلاگین هرگز با هم تداخل نمی‌کنند.

interface PluginContext {
  /** تگ منبعِ حل‌شده، مثلاً 'plugin:hello'. */
  readonly source: string
  /** ثبت یک مشارکت (id در فضای‌نام، منبع مهر شده). یک disposer برمی‌گرداند. */
  register: (c: PluginContribution) => () => void
  /** ثبت چند مشارکت با هم؛ disposer برگشتی همهٔ آن‌ها را حذف می‌کند. */
  registerMany: (cs: PluginContribution[]) => () => void
  /** REST به فضای‌نام بک‌اندِ خودِ همین پلاگین (`/api/plugins/<id>`). */
  rest: <T>(path: string, opts?: PluginRestOptions) => Promise<T>
  /** WebSocket زنده به فضای‌نام خودِ همین پلاگین. یک disposer برمی‌گرداند. */
  socket: (path: string, onMessage: (data: unknown) => void) => () => void
  /** درِ OS گزینش‌شده: نوتیفیکیشن بومی، open-external، reveal-in-file-manager، کلیپ‌بورد. */
  os: PluginOs
  /** ذخیره‌سازی JSON با محدودهٔ پلاگین (کلیدها زیر `hermes.plugin.<id>.` زندگی می‌کنند). */
  storage: PluginStorage
}

یک مشارکت (contribution) تنها پریمیتیوی است که همهٔ سطوح با هم مشترک‌اند:

interface Contribution {
  id: string          // شما id محلی را می‌نویسید؛ میزبان آن را در فضای‌نام قرار می‌دهد
  area: string        // کجا می‌رود (یک ثابت contribution-area)
  title?: string
  order?: number      // مرتب‌سازی داخل حوزه (کمتر = جلوتر)
  when?: () => boolean // visibility پویا؛ توسط حوزه دوباره ارزیابی می‌شود
  enabled?: boolean
  render?: () => ReactNode  // کامپوننتی که mount می‌شود
  data?: unknown      // payload مخصوص حوزه (کتاب آشپزی را ببینید)
}

بسته به حوزه، render را می‌دهید، یا data را، یا هر دو را.

پن‌ها

پن، یک کاشی در درخت چیدمان است. placement نقشِ معنایی است — پن با پن‌های موجودِ همان نقش (به‌شکل تب) پشته می‌شود؛ کاربر بعداً می‌تواند آن را هر جا خواست بکشد.

ctx.register({
  id: 'pane',
  area: 'panes',
  title: 'my pane',
  data: { placement: 'right', width: '260px' },
  render: () => jsx(MyPane, {})
})

placement یکی از 'main' | 'left' | 'right' | 'top' | 'bottom' است. برای فرودادن روی یک لبهٔ مشخص به‌جای پشته‌شدن، یک ژست dock اضافه کنید — همان کاری که با کشیدن روی drop chipِ یک پن انجام می‌شود:

// زیر مکالمه، به ارتفاع 200px
data: {
  placement: 'bottom',
  dock: { pane: 'workspace', pos: 'bottom' },
  height: '200px'
}

dock.pane هر pane id می‌تواند باشد (workspace همان thread اصلی است؛ همچنین sessions و terminal و files و review و logs)؛ dock.pos یکی از 'top' | 'bottom' | 'left' | 'right' | 'center' است. یک width/height هم اعلام کنید تا پن نیمی از ناحیه را تصاحب نکند.

بستنِ تنها پنی که یک پلاگین contributed کرده، آن پلاگین را غیرفعال می‌کند و می‌توان از تنظیمات ← افزونه‌ها دوباره فعالش کرد. وقتی پلاگین چند پن contributes می‌کند، بستن یکی فقط همان پن را می‌بندد و بقیهٔ پن‌ها، فرمان‌ها و middlewareهای پلاگین فعال می‌مانند. بازنشانی چیدمان پن‌های contributedِ بسته‌شده را برمی‌گرداند.

صفحه‌ها و ناوبری سایدبار

یک route یک صفحهٔ کامل را در پن ورک‌اسپیس سوار می‌کند، مثل هر نمای داخلی دیگری. برای قابل‌دسترس‌شدن، آن را با یک ردیف ناوبری سایدبار (و/یا یک فرمان پالت) جفت کنید.

import { ROUTES_AREA, SIDEBAR_NAV_AREA } from '@hermes/plugin-sdk'

ctx.registerMany([
  {
    id: 'page',
    area: ROUTES_AREA,
    data: { path: '/my-page' },
    render: () => jsx(MyPage, {})
  },
  {
    id: 'nav',
    area: SIDEBAR_NAV_AREA,
    data: { path: '/my-page', label: 'My Page', codicon: 'project' }
  }
])

codicon یک id از codiconهای VS Code است. با host.navigate('/my-page') از هر جا به یک route ناوبری کنید.

نوار وضعیت و نوار عنوان

آیتم‌های نوار وضعیت در خوشهٔ چپ یا راست نوار پایین رندر می‌شوند. ساده‌ترین حالت یک تابع render است؛ برای یک دکمهٔ ساده، data را به‌صورت StatusbarItem بدهید ({ id, label?, icon?, detail?, variant?, menuItems?, … }).

import { STATUSBAR_AREAS, TITLEBAR_AREAS } from '@hermes/plugin-sdk'

ctx.register({
  id: 'count',
  area: STATUSBAR_AREAS.right,
  order: 120,
  render: () => jsx(MyStatus, {})
})

ابزارهای نوار عنوان در TITLEBAR_AREAS.left | .center | .right به‌عنوان دادهٔ TitlebarTool زندگی می‌کنند ({ id, label, icon, active?, onSelect? }).

فرمان‌های پالت و کلیدهای میان‌بر

import { PALETTE_AREA, KEYBINDS_AREA } from '@hermes/plugin-sdk'

ctx.registerMany([
  {

    }
  },

کلیدهای میان‌بر را کاربر می‌تواند در تنظیمات دوباره bind کند؛ defaults فقط اتصال اولیه است.

تم‌ها

یک مشارکتِ تم، یک DesktopTheme کامل را به‌عنوان data خودش ارسال می‌کند (name، label، رنگ‌ها و...). در انتخاب‌گر تم مثل یک مورد داخلی دیده می‌شود.

import { THEMES_AREA } from '@hermes/plugin-sdk'

ctx.register({ id: 'noir', area: THEMES_AREA, data: myDesktopTheme })

ثبت تم فقط آن را فهرست می‌کند؛ انتخابش نمی‌کند. useTheme() ظاهرِ نقش‌شده را می‌خواند (theme، themeName، availableThemes، resolvedMode) و از داخل یک کامپوننت تغییرش می‌دهد (setTheme، setMode، previewTheme):

import { Button, useTheme } from '@hermes/plugin-sdk'

function ThemePicker() {
  const { availableThemes, setTheme, themeName } = useTheme()

  return availableThemes.map(t => (
    <Button key={t.name} disabled={t.name === themeName} onClick={() => setTheme(t.name)}>
      {t.label}
    </Button>
  ))
}

تغییری که چیزی غیر از رندر محرکش است — اتصال گیت‌وی، یک رویداد سوکت، هر callback از host.onEvent — کامپوننتی ندارد که هوک را به آن آویزان کند. در آن‌جا از requestTheme(name) استفاده کنید. نامی که resolve نشود رد می‌شود و به اسکین پیش‌فرض اجبار نمی‌شود؛ بنابراین مقدار بازگشتی هم‌زمان نقش بررسیِ در-دسترس‌بودن را هم بازی می‌کند و یک نام اشتباه هرگز به‌طور بی‌صدا ظاهر کسی را reset نمی‌کند:

import { host, requestTheme } from '@hermes/plugin-sdk'

host.onEvent('gateway.ready', () => {
  if (!requestTheme('noir')) {
    host.notifyError('Connected, but the noir theme is not installed.')
  }
})

هر دو درگاه به‌تفکیک پروفایل ذخیره می‌شوند، پس تغییری که پلاگین اعمال می‌کند دقیقاً مثل انتخاب دستی ماندگار است. برای رنگ‌آمیزی تمِ فعال به‌جای جایگزینی‌اش، از setAccentOverride(hex) استفاده کنید و در ctx.onDispose پاکش کنید — پلاگین هم‌بستهٔ accent نمونهٔ کارشدهٔ آن است.

گسترش‌های کامپوزر

COMPOSER_AREAS (top، bottom، leading، actions، attachments، middleware) به پلاگین اجازه می‌دهند کنترل‌هایی دور کامپوزر پیام اضافه کند، منبع پیوست فراهم کند یا پیش‌نویس را قبل از ارسال تبدیل کند (ComposerMiddleware با یک handler(draft) => draft | null).

دایرکتیوهای ترنسکریپت — کامپوننت‌های درون‌خطی که مدل آن‌ها را خطاب می‌کند

TRANSCRIPT_DIRECTIVE_AREA خودِ ترنسکریپت را به یک حوزهٔ مشارکت تبدیل می‌کند. یک دایرکتیو نام‌دار ثبت کنید تا ایجنت بتواند کامپوننت شما را با emitکردن پاراگرافی به شکل ::name{key="value"} به‌صورت درون‌خطی در پیام دستیار رندر کند:

import { TRANSCRIPT_DIRECTIVE_AREA } from '@hermes/plugin-sdk'

ctx.register({
  id: 'task-card',
  area: TRANSCRIPT_DIRECTIVE_AREA,
  data: {
    name: 'task', // مدل می‌نویسد ::task{id="BB-12"}
    render: ({ attrs, streaming }) => jsx(TaskCard, { taskId: attrs.id, streaming })
  }
})

قواعدی که میزبان اعمال می‌کند تا سطح امن بماند:

  • دایرکتیو باید کل پاراگراف باشد — ::name وسط متن، همان متن می‌ماند، بنابراین کامپوننت‌های پلاگین هرگز نمی‌توانند میانهٔ متنِ جاری را بربایند.
  • اتریبیوت‌ها خروجی مدل و غیرقابل‌اعتماد اند (جفت‌های key="value"، فقط رشته). فیلدهای خودتان را اعتبارسنجی کنید؛ با ورودی نامعتبر به‌جای حدس‌زدن، هیچ‌چیز رندر نکنید.
  • دایرکتیوی که ادعانشده باشد (هیچ پلاگینی برای آن نام ثبت نکرده باشد) مثل همان پاراگراف سادهٔ همیشگی رندر می‌شود — وقتی پلاگین خاموش است چیزی نمی‌شکند.
  • رندرها در error boundary مشارکت پیچیده می‌شوند: یک throw به یک چیپ خطای درون‌خطی تنزل می‌یابد، هرگز یک پیام مرده نمی‌شود.
  • در تداخل نام، اولین ثبت برنده است؛ نام‌های پرمدعا را با اسلاگ خودتان در فضای‌نام بگذارید (myplugin-board، نه board).

هسته یک دایرکتیو را به‌عنوان مصرف‌کنندهٔ مرجع ارسال می‌کند: ::preview{file="…"} فایل HTML ورک‌اسپیس را زنده داخل پیام رندر می‌کند — یک iframe سندباکس‌شدهٔ srcdoc با origin مات (اسکریپت‌ها اجرا می‌شوند و ویجت کاملاً تعاملی است؛ هیچ دست‌رسی به اپلیکیشن، حافظهٔ آن یا bridge نیست). قاب خودش را با محتوا هم‌اندازه می‌کند (ارتفاع زنده، عرض از گسترهٔ ذاتیِ محتوا گرفته می‌شود، چسبیده به چپ در جریان پیام)، و یک prelude تم، توکن‌های resolve‌شدهٔ اپلیکیشن (--foreground، --muted-foreground، --accent، --border، --card)، فونت اپلیکیشن و پس‌زمینهٔ شفاف را به سند می‌دهد — بنابراین HTML ویجت‌مانند بومی به نظر می‌رسد، در حالی که یک صفحهٔ کامل طراحی خودش را نگه می‌دارد. مقصدهای غیر-HTML و گیت‌وی‌های راه دور به کارت پیش‌نمایش کلاسیک برمی‌گردند. دایرکتیو خودتان را در یک مهارت به ایجنت معرفی کنید (همین‌طور یاد می‌گیرد emitش کند).

ویجت‌های پیش‌نمایش‌شده می‌توانند جواب هم بدهند. داخل قاب، window.hermes.send('get-price eth') (یا یک <button data-hermes-send="get-price eth"> اعلانی — بدون نیاز به اسکریپت) آن پرامپت را به‌عنوان یک نوبت کاربری به ایجنت می‌دهد، خارج از صفحه: هیچ حبابی فضای ترنسکریپت را اشغال نمی‌کند و به‌روز شدن ویجت همان پاسخِ قابل‌مشاهده است. نوبت همچنان واقعی است — ایجنت را بیدار می‌کند، از قواعد steer/queue کامپوزر پیروی می‌کند و ذخیره می‌شود (با نوع hidden) تا resume و دیتابیس نشست‌ها رکورد کامل را نگه دارند. پرامپت‌ها trim می‌شوند، به ۵۰۰ کاراکتر محدودند و به یک عدد در ثانیه به‌ازای هر قاب throttle می‌شوند.

کروم با محدودهٔ mount (Contribute)

ctx.register برای مشارکت‌های دائمی است. وقتی کروم باید با کامپوننتی که همین حالا روی صفحه است زنده بماند و بمیرد (کنترل نوارعنوانِ خودِ صفحه، وقتی صفحه unmount شود می‌رود)، به‌جایش <Contribute> را داخل آن رندر کنید:

import { Contribute, TITLEBAR_AREAS } from '@hermes/plugin-sdk'

jsx(Contribute, {
  area: TITLEBAR_AREAS.center,
  id: 'my-page:switcher', // با اسلاگ خودتان فضای‌نام کنید
  children: jsx(MySwitcher, {})
})

با mount ثبت می‌شود و با unmount خودکار dispose می‌شود.

۶ API میزبان

همه‌چیز روی host از هر نقطهٔ پلاگین در دسترس است. اتم‌های وضعیت فقط-خواندنی‌اند — در هندلرها با .get() بخوانید و در کامپوننت‌ها با useValue(atom) مشترک شوید.

host.state.activeSessionId  // ReadableAtom<string | null>
host.state.awaitingResponse // ReadableAtom<boolean>  تا اولین payload دستیار true است
host.state.busy             // ReadableAtom<boolean>  چت متمرکز پس از ارسال در حال کار است
host.state.busyBySession    // ReadableAtom<Record<string, boolean>>  runtime id → وسط نوبت
host.state.focusedSessionId // ReadableAtom<string | null>  (runtime id نشست متمرکز — آگاه از tile؛ برای RPCهای session.* ترجیح داده شود)
host.state.focusedSessionProfile // ReadableAtom<string>  (پروفایل مالکِ چت متمرکز — برای نمایش‌های per-bot/profile ترجیح داده شود)
host.state.focusedStoredSessionId // ReadableAtom<string | null>  (id پایدار — ناوبری / تطبیق فهرست نشست‌ها)
host.state.focusedUsage     // ReadableAtom<UsageStats | null>  (usage زندهٔ در-حال-stream نشست متمرکز، بدون نیاز به RPC)
host.state.cwd              // ReadableAtom<string>
host.state.gateway          // ReadableAtom<string>  وضعیت سوکت ('idle' | 'connecting' | 'open' | …)
host.state.model            // ReadableAtom<string>
host.state.profile          // ReadableAtom<string>
host.state.viewport         // ReadableAtom<{ width, height, narrow }>

host.state.gateway اتصال WebSocket است، نه اینکه آیا یک نوبت چت در حال اجراست. یک نشست می‌تواند وسط نوبت باشد در حالی که سوکت open است؛ هم‌زمان نشست دیگری می‌تواند بیکار باشد. اکشن‌های کامپوزر یا پلاگین را بر اساس مشغول‌بودنِ نوبتِ نشست متمرکز غیرفعال کنید (host.state.busyBySession[sessionId]، یا view.$busy همان نشست) — هرگز بر اساس gateway، و هرگز بر اساس یک فلگ busy سراسریِ پروسس.

host.notify({ kind, message, title?, detail?, action? })  // toast؛ یک id برمی‌گرداند
host.notifyError(error, fallbackMessage)                   // toast دادن یک خطا
ctx.os.notify({ title, body?, silent?, icon?, activate?, onActivate?, actions? })
                                           // نوتیفیکیشن بومی OS (منتسب به پلاگین شما)
ctx.os.openExternal(url)                   // هندلر پیش‌فرض OS (مرورگر، ایمیل، spotify:) → Promise<boolean>
ctx.os.revealPath(path)                    // نمایش در Finder / Explorer → Promise<boolean>
ctx.os.writeClipboard(text)                // کلیپ‌بورد سیستم → Promise<boolean>
host.navigate('/route')                    // ناوبری hash-route
host.openSession(id, { profile?, intent? }) // باز کردن یک نشست ذخیره‌شده به سبک هسته؛
                                           //   profile: اول سوییچ نرم به بک‌اند همان پروفایل
                                           //   intent: 'in-place' (پیش‌فرض) | 'stack' | 'tab' | 'window'
host.newChat(profile?)                     // پیش‌نویس چت تازه، اختیاراً در پروفایلی دیگر
host.openWorkspace(id, { render, title?, minWidth?, onClose? })
                                           // سوار کردن تبِ رندر‌شدهٔ پلاگین در ناحیهٔ MAIN
                                           //   ورک‌اسپیس و آشکارسازی آن؛ یک disposer برمی‌گرداند
host.paneVisibility(paneId)                // ReadableAtom<boolean> — آیا پنِ contributed
                                           //   واقعاً روی صفحه است (تبِ فعالِ ناحیه‌اش)؟
host.onEvent(type, fn)                     // جریان رویداد گیت‌وی ('*' = همه)؛ disposer برمی‌گرداند
host.logs(...)                             // دنبال کردن یک فایل لاگ اپلیکیشن
host.status()                              // اسنپ‌شاتِ یک‌بارهٔ وضعیت سیستم
host.restartGateway()                      // ری‌استارت گیت‌وی بک‌اند
host.profileRoutes()                       // [{ profile, targetProfile, connectionId, mode }]
host.requestProfile<T>(route, method, params?)   // RPC مسیریابی‌شده با رجیستری؛ بدون جابه‌جایی foreground
host.requestProfile<T>(profile, method, params?) // اورلود قدیمی v1/local
host.request<T>(method, params?)           // JSON-RPC گیت‌وی فعال — قدرت واقعی

host.request همان JSON-RPCای است که خودِ اپلیکیشن استفاده می‌کند (نشست‌ها، پیکربندی، مهارت‌ها، کرون، کانبان و...). host.requestProfile یک descriptor از host.profileRoutes() می‌پذیرد و آن RPC را دقیقاً از طریق همان منبع رجیستری و همان پروفایل مسیریابی می‌کند، بدون تغییر چت فعال یا گیت‌وی. اورلودِ فقط-پروفایل فقط برای توپولوژی تک-محلی/قدیمی نگه داشته شده است؛ پلاگین‌های آگاه-از-رجیستری باید descriptor را بدهند تا دو منبعی که یک نام پروفایل یکسان را expose می‌کنند نتوانند تداخل کنند.

host.openWorkspace(id, { render, title?, minWidth?, onClose? }) نمایِ رندر‌شدهٔ پلاگین را به‌شکل یک تب در ناحیهٔ اصلی ورک‌اسپیس — همان ناحیهٔ مرکزی که کاشی‌های نشست و پیش‌نمایش‌ها استفاده می‌کنند — سوار می‌کند و آشکارش می‌سازد. فراخوانی دوباره با همان id محتوا را در جا تازه می‌کند و تب را دوباره جلو می‌آورد، به‌جای باز کردن یک نسخهٔ تکراری. بستن تب (کنترل Close خودِ تب یا ⌘W) ثبت را برمی‌چیند و onClose شما را اجرا می‌کند؛ disposer برگشتی آن را به‌صورت برنامه‌نویسی‌شده می‌بندد. آن را با feature-detect بررسی کنید (typeof host.openWorkspace === 'function') و روی بیلدهای قدیمی‌تر دسکتاپ به یک پنِ contributed معمولی برگردید — اتاق‌های چت گروهی در Bot Mode مصرف‌کنندهٔ مرجع هستند (تصاحب پنجرهٔ اصلی وقتی موجود است، وگرنه نمای درون‌پنل).

host.paneVisibility(paneId) یک اتم واکنش‌گرای فقط-خواندنی برمی‌گرداند که وقتی یک پنِ contributed واقعاً روی صفحه است true است: در درخت چیدمان حاضر باشد، بسته یا پنهان نشده باشد، ناحیه‌اش minimize نشده باشد و اسلاتِ تبِ فعالِ ناحیه‌اش را نگه داشته باشد (پنِ تنها در ناحیهٔ خودش هم حساب است). id، همان pane id با محدودهٔ مشارکت است، یعنی <pluginId>:<paneId>. اتم‌ها به‌ازای هر id memoize می‌شوند، پس فراخوانی‌اش در render امن است. از آن برای ثبت UI همراه فقط وقتی پن شما دیده می‌شود استفاده کنید — پنِ Cronjobs در Bot Mode مصرف‌کنندهٔ مرجع است: وقتی پنِ Bots تبِ سایدبار را نگه داشته ثبت می‌شود و وقتی کاربر به Sessions برمی‌گردد ثبتش برمی‌دارد. روی دسکتاپ‌های قدیمی‌تر feature-detect کنید (typeof host.paneVisibility === 'function') و به رفتار همیشه-ثبت‌شده برگردید.

host.profileRoutes() همهٔ منابع ثبت‌شده در رجیستری اتصال جاری را فهرست می‌کند. منابع SSH از نوع connect-on-demand یک مسیر seed به نام default بدون اعتبارنامه ارائه می‌کنند، بدون اینکه تونلی باز شود، بنابراین یک پلاگین می‌تواند اولین تماس‌گیری باشد که شماره‌گیری‌شان می‌کند؛ remoteProfile یک اتصال SSH همان targetProfile بک‌اندِ مسیر باقی می‌ماند. connectionId هویت مسیریابی رجیستری است؛ برای کلیدها و ماندگاری، آن را با profile جفت کنید. نقطهٔ پایانی، توکن، هاست/کلید SSH و بقیهٔ فیلدهای خام اتصال هرگز از مرز IPC پلاگین عبور نمی‌کنند. profile مسیرِ محلیِ منبع است که برای درخواست‌ها استفاده می‌شود؛ targetProfile پروفایل هرمسِ بک‌اندی است که آن مسیر سرو می‌کند. وقتی مسیری صریحاً به یک پروفایل بک‌اند دیگر نگاشت شود (مثلاً یک override از نوع remoteProfile در SSH یا یک نام مستعار URL قدیمیِ per-profile) این دو با هم فرق می‌کنند. این تمایز، هویت بک‌اند را بدون افشای رمزهای اتصال حفظ می‌کند.

پلاگین‌های پروفایل‌محور متدهای درجه‌یک هم می‌گیرند: profiles.list (هر پروفایل + آخرین مکالمه‌اش به‌صورت last_session؛ برای رد کردن پروب دیتابیس per-profile مقدار include_sessions: false را بدهید؛ برای یک جست‌وجوی دقیق و existence-checkedِ یک نشست سنجاق‌شده به‌ازای هر پروفایل، preferred_session_ids: { profileName: sessionId } را بدهید — هر ردیف نام‌برده یک خلاصهٔ preferred_session می‌گیرد که ردیف‌های پنهان و نسب‌های فشرده‌سازی را به نوک زندهٔ آن‌ها resolve می‌کند، یا null وقتی id قطعاً از بین رفته است؛ گیت‌وی‌های قدیمی‌تر این پارامتر را نادیده می‌گیرند و آن فیلد را نمی‌فرستند) و profiles.create (name، description، clone_from، clone_all، no_skills، soul، پین اختیاری model + provider) — دوقلوهای ws مسیرهای REST /api/profiles داشبورد. host.state.busy نوبت زندهٔ چت متمرکز است (thinking و streaming). host.state.awaitingResponse از لحظهٔ ارسال تا اولین payload دستیار true می‌ماند. هر دو از چتی پیروی می‌کنند که کاربر واقعاً نگاهش می‌کند — کاشی نشست متمرکز وقتی یکی فوکوس دارد، وگرنه چت اصلی ورک‌اسپیس (همان سیگنالی که پالس busy نوار وضعیت می‌خواند). در یک کامپوننت مشترک شوید:

const busy = useValue(host.state.busy)

برای جزئیات در سطح توکن، با host.onEvent گوش دهید (message.start، message.delta، message.complete).

host.onEvent رویدادهای زندهٔ گیت‌وی را استریم می‌کند (دلتاهای پیام، چرخهٔ حیات نشست، فعالیت ابزار). شنونده‌ها ایزوله‌اند — یک throw در شنوندهٔ شما نمی‌تواند dispatch اپلیکیشن را تحت تأثیر بگذارد. هر درگاه host از نظر async امن است: یک throw همگام از یک helper داخلی (مثلاً نبودِ desktop bridge در یک مرورگر ساده) به یک rejection تبدیل می‌شود که .catch() شما می‌بیند، هرگز یک کرشِ error-boundary نیست.

ctx.os درِ OS گزینش‌شده است — هر راهی که پلاگین از پنجرهٔ اپلیکیشن بیرون می‌زند، در یک فضای‌نام که به پلاگین شما منتسب است. ctx.os.notify یک نوتیفیکیشن بومی OS می‌فرستد — همان خط لولهٔ Electron که هشدارهای approval/turn خودِ اپلیکیشن استفاده می‌کنند. فقط وقتی اجرا می‌شود که کاربر از Hermes دور باشد (background / بدون فوکوس)؛ برای toast درون‌برنامه‌ای وقتی کاربر نگاه می‌کند از host.notify استفاده کنید. کاربران می‌توانند آن را به‌تفکیک دستگاه زیر Settings ▸ Notifications ▸ «Plugin notifications» بی‌صدا کنند و تکرارها از یک پلاگین throttle می‌شوند، پس با آن مثل سیگنالی برای رویدادهای واقعاً قابل‌توجه رفتار کنید — نه یک لاگ.

ارائهٔ غنی + فعال‌سازی (گسترش درگاه اصلی ctx.os):

ctx.os.notify({
  title: 'New match found',
  body: 'Someone matched your signal',
  icon: '/abs/path/to/icon.png', // آیکون Electron Notification
  // کلیک روی بدنه → فوکوس Hermes + ناوبری. همان واژگان deep linkهای OS:
  activate: 'hermes://index-network/intent/1',
  // یا: activate: '/index-network/intent/1'
  // یا: activate: { path: '/index-network/intent/1' }
  onActivate: () => focusLocalState('1'), // callback اختیاری renderer
  actions: [
    { id: 'open', label: 'Open', activate: 'hermes://index-network/intent/1' },
    { id: 'dismiss', label: 'Dismiss', onAction: () => dismiss('1') },
  ],
})

activate با deeplink سازگار است: hermes://index-network/intent/1 و مسیر hash به شکل /index-network/intent/1 به همان route درون‌برنامه‌ای resolve می‌شوند (و همان URL hermes://… به‌عنوان OS deep link هم کار می‌کند). دکمه‌های اکشن فقط روی بیلدهای امضاشدهٔ macOS رندر می‌شوند؛ در جاهای دیگر کلیک روی بدنه همچنان فعال‌سازی می‌کند. ناوبری فقط با کلیک کاربر رخ می‌دهد — هرگز فقط از یک رویداد پس‌زمینه.

درگاه‌های دیگر (openExternal، revealPath، writeClipboard) وقتی قابلیت در دسترس نیست (شل دسکتاپ قدیمی، مرورگر ساده) به‌جای throw کردن، false برمی‌گردانند — روی نتیجه شاخه‌بندی کنید، نه بو کشیدنِ bridge.

پلاگین‌ها همان QueryClient واحد اپلیکیشن را به اشتراک می‌گذارند، بنابراین کوئری‌های پلاگین دقیقاً مثل صفحات هسته کش می‌شوند، dedupe می‌شوند، poll می‌کنند و invalidate می‌شوند — هرگز یک حلقهٔ fetch دست‌ساز ننویسید.

import { useQuery, useMutation, useQueryClient, atom, computed, useValue } from '@hermes/plugin-sdk'

function MyPanel() {
  const { data, isLoading } = useQuery({
    queryKey: ['my-plugin', 'items'],
    queryFn: () => host.request('my.list', {})
  })
  // …
}

برای وضعیت مشترک بین یک محرک و پنلش (یا یک حلقهٔ poll)، از atom / computed استفاده کنید — همان پریمیتیوی که host.state استفاده می‌کند. در برگِی که مقدار را رندر می‌کند با useValue مشترک شوید. برای invalidateکردن یک کوئری از بیرون React (مثلاً رسیدن یک فریم ctx.socket)، queryClient مشترک را ایمپورت کنید:

import { queryClient } from '@hermes/plugin-sdk'

ctx.socket('/events', () => {
  queryClient.invalidateQueries({ queryKey: ['my-plugin', 'items'] })
})

۸ کیت UI و تم‌بندی

کامپوننت‌های واقعی اپلیکیشن را مستقیم ایمپورت کنید تا UI شما به‌طور پیش‌فرض بومی باشد:

Button, Input, Textarea, Select*, Switch, Checkbox, SegmentedControl, Tabs*, Dialog*, ConfirmDialog, DropdownMenu*, ContextMenu*, Popover*, Tip/Tooltip*, Badge, Kbd/KbdGroup, SearchField, ScrollArea, Separator, Skeleton, GlyphSpinner, Loader, EmptyState, ErrorState, CopyButton, StatusDot, LogView, Codicon, DecodeText.

به‌علاوه helperها: cn (ادغام کلاس)، icons.* (مجموعهٔ lucide اپلیکیشن)، haptic، profileColor / profileColorSoft (رنگ‌های هویتی قطعی)، قالب‌بندهای زمان relativeTime / fmtDateTime / fmtDayTime / coarseElapsed، useI18n (متن‌های بومی‌سازی‌شده — پلاگین شما قابل ترجمه می‌ماند) و evaluateRuntimeReadiness.

با متغیرهای تم استایل بدهید، هرگز رنگ هاردکد نکنید. پن‌ها همین حالا روی پس‌زمینهٔ ادیتور اپلیکیشن نشسته‌اند — پس‌زمینه را به حال خود بگذارید و برای بقیهٔ چیزها از varها استفاده کنید: var(--ui-text-secondary)، var(--ui-text-tertiary)، var(--ui-text-quaternary)، var(--ui-stroke-secondary)، var(--ui-accent). برای رسم روی canvas، یک‌بار آن‌ها را با getComputedStyle(canvas).getPropertyValue('--ui-accent') resolve کنید. همین چیزی است که باعث می‌شود یک پلاگین با هر تم به‌طور خودکار reskin شود.

۹ یک بک‌اند برای پلاگین شما

اگر پلاگین شما کار سمت سرور لازم دارد، یک plugin_api.py پایتونی بفرستید و از طریق ctx.rest / ctx.socket به آن برسید — فضای‌نامی که ذاتاً به پلاگین شما محدود است.

یک بسته، هر دو SDK

قابلیتی که هم UI دسکتاپ و هم کد سمت ایجنت لازم دارد (یک پلاگین پایتونی، مسیرهای بک‌اندش، مهارت‌هایش) لازم نیست به‌شکل دو نصبِ وابسته به هم ارسال شود. اپلیکیشن دسکتاپ $HERMES_HOME/plugins/<id>/ — ریشهٔ معمول پلاگین‌های ایجنتی — را هم برای یک desktop/plugin.js اسکن می‌کند و آن را از دقیقاً همان خط لولهٔ درِ دیسکی مستقل بارگذاری می‌کند (شامل hot reload):

~/.hermes/plugins/<id>/           # یک پوشهٔ قابل‌نصبِ واحد
├── plugin.yaml                   # نیمهٔ ایجنتی: ابزارها، هوک‌ها، فرمان‌ها
├── skills/…
├── dashboard/
│   ├── manifest.json             # { "name": "<id>", "api": "plugin_api.py" }
│   └── plugin_api.py             # مسیرهای بک‌اند → /api/plugins/<id>/
└── desktop/
    └── plugin.js                 # نیمهٔ دسکتاپ: پن‌ها، فرمان‌ها، ctx.rest

نیمهٔ desktop/plugin.js یک پلاگین دیسکی معمولی است — همان قرارداد، همان ایمپورت‌ها، همان ctx.rest('/…') که به plugin_api.py کنارش می‌رسد. نصب، اشتراک‌گذاری یا حذف این قابلیت، یک پوشه است.

دو کلید فعال‌سازی همچنان اعمال می‌شوند، عمداً، و هر دو به‌طور پیش‌فرض خاموش‌اند: نیمهٔ دسکتاپ به‌صورت opt-in ارسال می‌شود — در تنظیمات ← افزونه‌ها فهرست می‌شود اما تا کاربر آن را نزند غیرفعال می‌ماند — مطابق با گیتِ plugins.enabled نیمهٔ پایتونی در config.yaml (همان مرز امنیتی پایین). گذاشتن یک بسته در ~/.hermes/plugins روی همهٔ سطوح بی‌اثر است تا وقتی کاربر چیز دیگری بگوید. نیمهٔ دسکتاپ وقتی نیمهٔ بک‌اند خاموش است به‌شکل لطیف تنزل می‌یابد — ctx.rest خطا برمی‌گرداند، نه کرش.

ℹ️

اسکن، محلی روی ماشینی است که اپلیکیشن دسکتاپ رویش اجراست. در برابر یک بک‌اند راه دور، ~/.hermes/pluginsِ آن ماشینِ دور به‌عنوان فایل‌سیستم قابل‌دسترس نیست — فقط بسته‌های نصب‌شدهٔ محلی نیمهٔ دسکتاپ دارند (همان قاعدهٔ درِ مستقل).

توزیع با لینک نصب

مخزن پلاگین خودتان را ارسال کنید (نیمهٔ ایجنتی، نیمهٔ دسکتاپ، یا هر دو) و با اسکیم hermes:// به آن لینک بدهید — یک anchor ساده در وب‌سایت یا README شما:

<a href="hermes://plugin/install?repo=owner/repo&enable=1">Install in Hermes</a>

کاربر یک دیالوگ تأیید می‌گیرد (id مخزن، لینک‌های منبع، پروبِ اینکه مخزن چه چیزی ارسال می‌کند) و قبل از اینکه چیزی نصب شود اجزا را انتخاب می‌کند — deep linkها هرگز خودکار نصب نمی‌کنند. force=1 نصب موجود را جایگزین می‌کند؛ بیلدهای dev از hermes-dev:// استفاده می‌کنند. مرجع کامل لینک‌ها: لینک‌های نصب یک‌کلیکی.

سمت پایتون

پلاگین‌های دسکتاپ mount بک‌اندِ پلاگینِ داشبورد را دوباره استفاده می‌کنند. بک‌اند را در زیرپوشهٔ dashboard/ یک پلاگین معمولی هرمس بگذارید و در یک manifest.json اعلامش کنید:

~/.hermes/plugins/<id>/
└── dashboard/
    ├── manifest.json      # { "name": "<id>", "api": "plugin_api.py" }
    └── plugin_api.py      # صادر می‌کند `router = APIRouter()`
# plugin_api.py
from fastapi import APIRouter

router = APIRouter()

@router.get("/board")
async def board():
    return {"items": ["one", "two", "three"]}

@router.post("/action")
async def action(body: dict):
    return {"ok": True, "received": body}

مسیرها زیر /api/plugins/<id>/ سوار می‌شوند (GET /api/plugins/<id>/board و...). کد بک‌اند داخل پروسس گیت‌وی اجرا می‌شود، بنابراین می‌تواند مستقیماً از کدبیس hermes-agent ایمپورت کند (hermes_state، hermes_cli.config و...). برای مرجع کامل بک‌اند به گسترش داشبورد وب ← مسیرهای API بک‌اند نگاه کنید — mount دقیقاً یکسان است.

⛔ بک‌اند پایتون جداگانه گیت شده است

فعال‌کردن یک پلاگین در پنل تنظیمات ← افزونه‌ها دسکتاپ یک انتخاب سمت renderer است؛ پایتون را import نمی‌کند. plugin_api.py یک پلاگین کاربری فقط وقتی import می‌شود که پلاگین در فهرست مجازِ plugins.enabled در config.yaml باشد (و در plugins.disabled نباشد). پلاگین‌های پروژه (./.hermes/) هرگز پایتون را خودکار import نمی‌کنند. این یک مرز امنیتی است، نه یک سهو (GHSA-mcfc-hp25-cjv7).

فراخوانی از داخل پلاگین

register(ctx) {
  // REST — مسیر نسبت به فضای‌نام.
  const load = () => ctx.rest('/board')                 // GET /api/plugins/<id>/board
  const act  = () => ctx.rest('/action', { method: 'POST', body: { go: true } })

  // دوقلوی زنده — یک WebSocket به فضای‌نام خودتان.
  const stop = ctx.socket('/events', frame => {
    queryClient.invalidateQueries({ queryKey: [ctx.source, 'board'] })
  })
}

ctx.rest پروفایل-آگاه است و پیمایش مسیر (..) را رد می‌کند، بنابراین هرگز نمی‌توانید از طریق آن API پلاگین دیگری یا یک مسیر هسته را صدا بزنید. PluginRestOptions این است: { method?, body?, upload?: { filename, contentType?, bytes }, timeoutMs? }.

ctx.socket تا وقتی dispose شود، با backoff خودکار دوباره وصل می‌شود. روی ریموت‌های OAuth به یک no-op resolve می‌شود (تیکت‌های WS یک‌بارمصرف توسط هسته مدیریت می‌شوند) — با سوکت مثل یک شتاب‌دهنده روی polling رفتار کنید، هرگز جایگزین. هر مصرف‌کننده به هر حال به یک fallback وابسته به polling نیاز دارد، چون هر سوکتی می‌تواند بیفتد.

برای داده‌های سراسر گیت‌وی (نه فضای‌نام خودتان)، به‌جایش از host.request (JSON-RPC) و host.onEvent (جریان رویداد گیت‌وی) استفاده کنید.

۱۰ تنظیمات، وضعیت فعال‌سازی و ذخیره‌سازی

هر پلاگین — فعال یا غیرفعال — در تنظیمات ← افزونه‌ها فهرست می‌شود، جایی که کاربر به‌صورت زنده آن را toggle می‌کند (بدون ری‌استارت اپلیکیشن)، پوشه‌اش را آشکار می‌کند یا rescan می‌کند. انتخاب کاربر به یاد سپرده می‌شود:

  • هنوز انتخابی نشده ← defaultEnabled خودِ پلاگین (پیش‌فرض true). با defaultEnabled: false یک پلاگین opt-in ارسال کنید که تا کاربر روشنش نکند تاریک می‌ماند.
  • انتخاب صریح ← ذخیره می‌شود و در ری‌استارت‌ها محترم شمرده می‌شود. پلاگینِ غیرفعال غیرفعال می‌ماند — با آن نجنگید؛ کاربر شما را خاموش کرده است.

وضعیت خودتان را با ctx.storage ماندگار کنید که به پلاگین شما فضای‌نام شده (hermes.plugin.<id>.*) تا پلاگین‌ها نتوانند همدیگر را بخوانند یا از بین ببرند:

ctx.storage.set('lastTab', 'board')
const tab = ctx.storage.get('lastTab', 'summary')
ctx.storage.remove('lastTab')

۱۱ پلاگین‌های هم‌بسته

یک پلاگین می‌تواند درون‌درخت در apps/desktop/src/plugins/<id>/plugin.tsx ارسال شود (default export یک HermesPlugin). توسط discoverBundledPlugins() هنگام boot کشف می‌شود — بدون ایمپورت، بدون ویرایش رجیستری — و دقیقاً همان قرارداد فهرست‌سازی + فعال/غیرفعال‌سازی زندهٔ یک پلاگین دیسکی را دارد. دو تفاوت:

  1. از بیلد Vite خودِ اپلیکیشن عبور می‌کند، پس می‌توانید JSX واقعی بنویسید و SDK را با نام مستعار @hermes/plugin-sdk ایمپورت کنید.
  2. همچنان از نظر لینت فقط به @hermes/plugin-sdk + react محدود است — بدون بخش‌های داخلی @/… اپلیکیشن.

امروز هیچ پلاگین دسکتاپی در درخت هسته ارسال نمی‌شود؛ اپلیکیشنِ ارسالی خلوت می‌ماند و دموها در مخزن همراهِ hermes-example-plugins زندگی می‌کنند.

۱۲ مدل امنیتی

پلاگینِ بارگذاری‌شده به‌عنوان ESM در قلمرو renderer با اختیار کامل اپلیکیشن ارزیابی می‌شود — سینگلتون React، کل SDK (RPC گیت‌وی از طریق host.request، ctx.rest، حافظهٔ ذخیره‌سازی، navigate). ایزوله‌ای که لودر فراهم می‌کند فقط ایزولهٔ خطا است: پلاگین نمی‌تواند اپلیکیشن را کرش کند (مشارکت‌ها error-boundedاند، شنونده‌ها ایزوله‌اند)، اما هر کاری که اپلیکیشن می‌تواند انجام دهد را می‌تواند انجام دهد.

این برای منابع محلی قابل‌قبول است — یک فایل دیسکی همین حالا هم می‌تواند روی ماشین شما کد اجرا کند — و دقیقاً به همین دلیل درِ دیسکی فقط فایل‌های محلی را بارگذاری می‌کند که شما (یا ایجنت شما) نوشته‌اید. بررسی اختیاری integrity (sha256-…) فقط اثبات می‌کند بایت‌ها با یک هش مطابق‌اند؛ سندباکس نمی‌کند. یک درگاه منبع-راه-دورِ آینده قبل از فرود به یک مرز واقعی نیاز خواهد داشت (iframe/worker + CSP + گیت‌بندی قابلیت)؛ این خط لوله را مرز اعتماد فرض نکنید.

۱۳ دام‌های رایج

  • JSX در پلاگین دیسکی پارس نمی‌شود. فایل بدون کامپایل بارگذاری می‌شود — از jsx() / jsxs() (یا React.createElement) استفاده کنید، نه سینتکس JSX. (پلاگین‌های هم‌بسته بیلد می‌شوند، پس JSX آن‌جا اشکالی ندارد.)
  • فقط سه specifier resolve می‌شود: @hermes/plugin-sdk، react و react/jsx-runtime. هر ایمپورت دیگری یک خطای بارگذاریِ از-ابتدا نشان می‌دهد.
  • هرگز رنگ هاردکد نکنید (#000، black، rgb(...)). پس‌زمینه را به حال خود بگذارید؛ برای همه‌چیز از متغیرهای تم (var(--ui-*)) استفاده کنید.
  • فقط به چیزهایی ارجاع بدهید که ایمپورت کرده‌اید. کامپوننتی که فراموش کرده‌اید ایمپورت کنید (مثلاً StatusDot) در زمان رندر یک ReferenceError است — دوباره چک کنید که هر شناسه در فراخوانی‌های jsx() شما در خط ایمپورت آمده باشد.
  • در هندلرها به‌صورت دستوری وضعیت بخوانید ($atom.get())، هرگز از یک closure رندر — وگرنه رویدادهای سریع مقادیر کهنه خواهند دید. فقط در برگِی که مقدار را رندر می‌کند مشترک شوید (useValue).
  • پن‌های canvas باید ظرف خودشان را دنبال کنند با یک ResizeObserver و اندازهٔ canvas را تغییر دهند (اتریبیوت‌های width/height، نه فقط CSS) — پن‌ها مدام resize می‌شوند.
  • با host.request سریع‌تر از چند ثانیه poll نکنید؛ host.onEvent / ctx.socket را ترجیح بدهید و بگذارید React Query دوباره‌کاری را حذف کند.
  • ctx.socket روی ریموت‌های OAuth یک no-op است. همیشه یک fallback وابسته به polling داشته باشید.

۱۵ عیب‌یابی

پلاگین من ظاهر نمی‌شود. مطمئن شوید فایل در $HERMES_HOME/desktop-plugins/<id>/plugin.js است و نام پوشه با id اکسپورت‌شده یکی است. ⌘K را بزنید و Reload desktop plugins را اجرا کنید. اپلیکیشن را برای یک toast خطا که نام شکست را اعلام می‌کند چک کنید و hermes logs gui -f را دنبال کنید.

پیام «unsupported import» هنگام بارگذاری. پلاگین دیسکی فقط می‌تواند @hermes/plugin-sdk و react و react/jsx-runtime را ایمپورت کند. هر ایمپورت دیگری را حذف کنید.

یک المنت jsx هیچ‌چیز رندر نمی‌کند / ReferenceError می‌دهد. شناسه‌ای که در فراخوانی jsx() استفاده شده ایمپورت نشده است. آن را به خط ایمپورت اضافه کنید.

ctx.rest مقدار 404 برمی‌گرداند. بک‌اند سوار نشده است: مطمئن شوید ~/.hermes/plugins/<id>/dashboard/manifest.json مقدار "api": "plugin_api.py" را دارد، پلاگین در plugins.enabled در config.yaml هست، و گیت‌وی را ری‌استارت کنید (مسیرهای بک‌اند هنگام راه‌اندازی سوار می‌شوند). ~/.hermes/logs/errors.log را برای پیام Failed to load plugin <id> API routes دنبال کنید.

ctx.socket هرگز اجرا نمی‌شود. روی ریموت OAuth عمداً no-op است — از fallback وابسته به polling خودتان استفاده کنید. در غیر این صورت بررسی کنید بک‌اند مسیر @router.websocket(...) متناظر را زیر فضای‌نامش expose می‌کند.

رنگ‌ها بعد از تعویض تم اشتباه به نظر می‌رسند. شما یک رنگ را هاردکد کرده‌اید. آن را با یک متغیر تم var(--ui-*) جایگزین کنید.
