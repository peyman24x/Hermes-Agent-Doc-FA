حلقهٔ ایجنت

موتور اصلی هماهنگ‌سازی، کلاس AIAgent در run_agent.py است — فایلی بزرگ که همه‌چیز را از ساخت پرامپت تا دیسپچ ابزار و failover ارائه‌دهنده مدیریت می‌کند.

۱ مسئولیت‌های اصلی

AIAgent مسئول این‌هاست:

  • ساخت پرامپت سیستمیِ مؤثر و اسکیماهای ابزار از طریق prompt_builder.py
  • انتخاب ارائه‌دهنده/حالت API درست (chat_completions، codex_responses، anthropic_messages)
  • برقراری فراخوانی‌های مدلِ قابل‌وقفه با پشتیبانی از لغو
  • اجرای فراخوانی‌های ابزار (به‌صورت ترتیبی یا هم‌زمان از طریق thread pool)
  • نگهداری تاریخچهٔ گفتگو در قالب پیام OpenAI
  • مدیریت فشرده‌سازی، تلاش مجدد و سوئیچ به مدل پشتیبان
  • ردیابی بودجهٔ تکرار میان ایجنت والد و فرزند
  • تخلیهٔ حافظهٔ پایدار قبل از از دست رفتن زمینه

۲ دو نقطهٔ ورود

# رابط ساده — رشتهٔ پاسخ نهایی را برمی‌گرداند
response = agent.chat("Fix the bug in main.py")

# رابط کامل — دیکشنری شامل پیام‌ها، متادیتا و آمار مصرف برمی‌گرداند
result = agent.run_conversation(
    user_message="Fix the bug in main.py",
    system_message=None,           # در صورت عدم تعیین، خودکار ساخته می‌شود
    conversation_history=None,      # در صورت عدم تعیین، خودکار از نشست بارگذاری می‌شود
    task_id="task_abc123"
)

chat() یک wrapper نازک دور run_conversation() است که فیلد final_response را از دیکشنری نتیجه بیرون می‌کشد.

۳ حالت‌های API

هرمس از سه حالت اجرای API پشتیبانی می‌کند که از انتخاب ارائه‌دهنده، آرگومان‌های صریح و هیوریستیک‌های base URL تشخیص داده می‌شوند:

حالت APIکاربردنوع کلاینت
chat_completionsنقطه‌های پایانی سازگار با OpenAI (OpenRouter، سفارشی، بیشتر ارائه‌دهنده‌ها)openai.OpenAI
codex_responsesOpenAI Codex / Responses APIopenai.OpenAI با قالب Responses
anthropic_messagesAnthropic Messages API بومیanthropic.Anthropic از طریق آداپتور

این حالت تعیین می‌کند پیام‌ها چطور قالب‌بندی شوند، فراخوانی‌های ابزار چطور ساختار بگیرند، پاسخ‌ها چطور پارس شوند و کش/استریم چطور کار کند. هر سه قبل و بعد از فراخوانی‌های API به همان قالب داخلی پیام می‌رسند (دیکشنری‌های role/content/tool_calls به سبک OpenAI).

ترتیب تشخیص حالت:

  1. آرگومان سازندهٔ صریح api_mode (بالاترین اولویت)
  2. تشخیص مخصوص ارائه‌دهنده (مثلاً ارائه‌دهندهٔ anthropic → anthropic_messages)
  3. هیوریستیک base URL (مثلاً api.anthropic.com → anthropic_messages)
  4. پیش‌فرض: chat_completions

۴ چرخهٔ حیات نوبت

هر تکرار از حلقهٔ ایجنت این توالی را دنبال می‌کند:

run_conversation()
  1. Generate task_id if not provided
  2. Append user message to conversation history
  3. Build or reuse cached system prompt (prompt_builder.py)
  4. Check if preflight compression is needed (>50% context)
  5. Build API messages from conversation history
     - chat_completions: OpenAI format as-is
     - codex_responses: convert to Responses API input items
     - anthropic_messages: convert via anthropic_adapter.py
  6. Inject ephemeral prompt layers (budget warnings, context pressure)
  7. Apply prompt caching markers if on Anthropic
  8. Make interruptible API call (_interruptible_api_call)
  9. Parse response:
     - If tool_calls: execute them, append results, loop back to step 5
     - If text response: persist session, flush memory if needed, return

قالب پیام

همهٔ پیام‌ها در درون از قالب سازگار با OpenAI استفاده می‌کنند:

{"role": "system", "content": "..."}
{"role": "user", "content": "..."}
{"role": "assistant", "content": "...", "tool_calls": [...]}
{"role": "tool", "tool_call_id": "...", "content": "..."}

محتوای reasoning (از مدل‌هایی که تفکر گسترده را پشتیبانی می‌کنند) در assistant_msg["reasoning"] ذخیره می‌شود و به‌اختیار از طریق reasoning_callback نمایش داده می‌شود.

قواعد تناوب پیام‌ها

حلقهٔ ایجنت تناوب سخت‌گیرانهٔ نقش پیام‌ها را اعمال می‌کند:

  • بعد از پیام سیستمی: User → Assistant → User → Assistant → ...
  • در حین فراخوانی ابزار: Assistant (with tool_calls) → Tool → Tool → ... → Assistant
  • هرگز دو پیام assistant پشت‌سرهم
  • هرگز دو پیام user پشت‌سرهم
  • فقط نقش tool می‌تواند رکوردهای متوالی داشته باشد (نتایج ابزارهای موازی)

ارائه‌دهنده‌ها این توالی‌ها را اعتبارسنجی می‌کنند و تاریخچه‌های بدشکل را رد خواهند کرد.

۵ فراخوانی‌های API قابل‌وقفه

درخواست‌های API در _interruptible_api_call() پیچیده می‌شوند که فراخوانی واقعی HTTP را در یک thread پس‌زمینه اجرا می‌کند و هم‌زمان یک رخداد وقفه را زیر نظر دارد:

┌────────────────────────────────────────────────────┐
│  Main thread                  API thread           │
│                                                    │
│   wait on:                     HTTP POST           │
│    - response ready     ───▶   to provider         │
│    - interrupt event                               │
│    - timeout                                       │
└────────────────────────────────────────────────────┘

وقتی وقفه رخ می‌دهد (کاربر پیام جدید می‌فرستد، فرمان /stop یا سیگنال):

  • thread API رها می‌شود (پاسخ دور انداخته می‌شود)
  • ایجنت می‌تواند ورودی جدید را پردازش کند یا به‌شکل تمیز خاموش شود
  • هیچ پاسخ ناقصی در تاریخچهٔ گفتگو تزریق نمی‌شود

۶ اجرای ابزار

ترتیبی در برابر هم‌زمان

وقتی مدل فراخوانی‌های ابزار برمی‌گرداند:

  • فراخوانی ابزار تکی → مستقیم در thread اصلی اجرا می‌شود
  • فراخوانی‌های ابزار متعدد → به‌صورت هم‌زمان از طریق ThreadPoolExecutor اجرا می‌شوند
    • استثنا: ابزارهای تعاملی (مثل clarify) اجرای ترتیبی را تحمیل می‌کنند
    • نتایج مستقل از ترتیب تکمیل، در ترتیب اصلیِ فراخوانی ابزار دوباره درج می‌شوند

جریان اجرا

for each tool_call in response.tool_calls:
    1. Resolve handler from tools/registry.py
    2. Fire pre_tool_call plugin hook
    3. Check if dangerous command (tools/approval.py)
       - If dangerous: invoke approval_callback, wait for user
    4. Execute handler with args + task_id
    5. Fire post_tool_call plugin hook
    6. Append {"role": "tool", "content": result} to history

ابزارهای سطح ایجنت

بعضی ابزارها قبل از رسیدن به handle_function_call() توسط run_agent.py رهگیری می‌شوند:

ابزاردلیل رهگیری
todoخواندن/نوشتن وضعیت وظیفهٔ محلی ایجنت
memoryنوشتن در فایل‌های حافظهٔ پایدار با محدودیت کاراکتر
session_searchپرس‌وجوی تاریخچهٔ نشست از طریق پایگاه دادهٔ نشست ایجنت
delegate_taskساخت ساب‌ایجنت(ها) با زمینهٔ ایزوله

این ابزارها وضعیت ایجنت را مستقیماً تغییر می‌دهند و بدون عبور از رجیستری، نتایج ابزارِ سینتتیک برمی‌گردانند.

۷ سطوح کال‌بک

AIAgent از کال‌بک‌های مخصوص پلتفرم پشتیبانی می‌کند که پیشرفت بی‌درنگ را در CLI، گیت‌وی و یکپارچگی‌های ACP ممکن می‌سازند:

کال‌بکزمان اجرااستفاده‌کننده
tool_progress_callbackقبل/بعد از هر اجرای ابزاراسپینر CLI، پیام‌های پیشرفت گیت‌وی
thinking_callbackوقتی مدل شروع/پایان تفکر را علامت می‌زندنشانگر «thinking...» در CLI
reasoning_callbackوقتی مدل محتوای reasoning برمی‌گرداندنمایش reasoning در CLI، بلوک‌های reasoning در گیت‌وی
clarify_callbackوقتی ابزار clarify فراخوانی می‌شودپرامپت ورودی CLI، پیام تعاملی گیت‌وی
step_callbackبعد از هر نوبت کامل ایجنتردیابی گام در گیت‌وی، پیشرفت ACP
stream_delta_callbackهر توکن استریم (وقتی فعال باشد)نمایش استریم در CLI
tool_gen_callbackوقتی فراخوانی ابزار از استریم پارس می‌شودپیش‌نمایش ابزار در اسپینر CLI
status_callbackتغییر وضعیت‌ها (thinking، executing و...)به‌روزرسانی‌های وضعیت ACP

۸ رفتار بودجه و پشتیبان

بودجهٔ تکرار

ایجنت تکرارها را از طریق IterationBudget ردیابی می‌کند:

  • پیش‌فرض: ۵۰۰ تکرار (قابل تنظیم از طریق agent.max_turns)
  • هر ایجنت بودجهٔ خودش را دارد. ساب‌ایجنت‌ها بودجه‌های مستقلی با سقف delegation.max_iterations (پیش‌فرض ۵۰) می‌گیرند — مجموع تکرارهای والد + ساب‌ایجنت‌ها می‌تواند از سقف والد فراتر رود
  • در ۱۰۰٪، ایجنت متوقف می‌شود و خلاصه‌ای از کارِ انجام‌شده برمی‌گرداند

مدل پشتیبان

وقتی مدل اصلی شکست می‌خورد (محدودیت نرخ 429، خطای سرور 5xx، خطای احراز هویت 401/403):

  1. فهرست fallback_providers در پیکربندی بررسی می‌شود
  2. هر پشتیبان به ترتیب امتحان می‌شود
  3. در صورت موفقیت، گفتگو با ارائه‌دهندهٔ جدید ادامه می‌یابد
  4. روی 401/403، قبل از failover تلاش برای تازه‌سازی اعتبارنامه انجام می‌شود

سیستم پشتیبان کارهای کمکی را هم مستقل پوشش می‌دهد — بینایی، فشرده‌سازی و استخراج وب هرکدام زنجیرهٔ پشتیبان خودشان را دارند که از بخش پیکربندی auxiliary.* قابل تنظیم است.

۹ فشرده‌سازی و ماندگاری

چه زمانی فشرده‌سازی فعال می‌شود

  • پیش از فراخوانی API (preflight): اگر گفتگو از ۵۰٪ پنجرهٔ زمینهٔ مدل بگذرد
  • فشرده‌سازی خودکار گیت‌وی: اگر گفتگو از ۸۵٪ بگذرد (تهاجمی‌تر، بین نوبت‌ها اجرا می‌شود)

در زمان فشرده‌سازی چه اتفاقی می‌افتد

  1. اول حافظه روی دیسک تخلیه می‌شود (جلوگیری از از دست رفتن داده)
  2. نوبت‌های میانی گفتگو در یک خلاصهٔ فشرده جمع می‌شوند
  3. N پیام آخر دست‌نخورده حفظ می‌شوند (compression.protect_last_n، پیش‌فرض: ۲۰)
  4. جفت‌پیام‌های فراخوانی ابزار/نتیجه کنار هم نگه داشته می‌شوند (هرگز جدا نمی‌شوند)
  5. یک شناسهٔ تبار نشست جدید تولید می‌شود (فشرده‌سازی، نشستِ «فرزند» می‌سازد)

ماندگاری نشست

بعد از هر نوبت:

  • پیام‌ها در فروشگاه نشست ذخیره می‌شوند (SQLite از طریق hermes_state.py)
  • تغییرات حافظه در MEMORY.md / USER.md تخلیه می‌شوند
  • نشست بعداً از طریق /resume یا hermes chat --resume قابل ازسرگیری است
