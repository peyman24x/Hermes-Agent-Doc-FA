پلاگین موتور زمینه

پلاگین‌های موتور زمینه به‌جای ContextCompressor داخلی، راهبرد جایگزینی برای مدیریت زمینهٔ گفتگو فراهم می‌کنند. برای مثال، موتوری از نوع Lossless Context Management (LCM) که به‌جای خلاصه‌سازیِ همراه با افت اطلاعات، یک DAG دانشی می‌سازد.

۱ چگونه کار می‌کند

مدیریت زمینهٔ ایجنت بر پایهٔ کلاس انتزاعی ContextEngine (agent/context_engine.py) ساخته شده است. ContextCompressor داخلی پیاده‌سازی پیش‌فرض است. موتورهای پلاگینی باید همین رابط را پیاده‌سازی کنند.

در هر لحظه فقط یک موتور زمینه می‌تواند فعال باشد. انتخابِ موتور از طریق پیکربندی انجام می‌شود:

# config.yaml
context:
  engine: "compressor"    # پیش‌فرض داخلی
  engine: "lcm"           # موتور پلاگینی با نام "lcm" را فعال می‌کند

موتورهای پلاگینی هرگز به‌طور خودکار فعال نمی‌شوند — کاربر باید صریحاً مقدار context.engine را روی نام پلاگین تنظیم کند.

۲ ساختار پوشه‌ها

هر موتور زمینه در plugins/context_engine/<name>/ قرار دارد:

plugins/context_engine/lcm/
├── __init__.py      # کلاس فرزند ContextEngine را صادر می‌کند
├── plugin.yaml      # فراداده (نام، توضیحات، نسخه)
└── ...              # هر ماژول دیگری که موتور شما به آن نیاز دارد

۳ کلاس انتزاعی ContextEngine

موتور شما باید این متدهای الزامی را پیاده‌سازی کند:

from agent.context_engine import ContextEngine

class LCMEngine(ContextEngine):

    @property
    def name(self) -> str:
        """Short identifier, e.g. 'lcm'. Must match config.yaml value."""
        return "lcm"

    def update_from_response(self, usage: dict) -> None:
        """Called after every LLM call with the usage dict.

        Update self.last_prompt_tokens, self.last_completion_tokens,
        self.last_total_tokens from the response.
        """

    def should_compress(self, prompt_tokens: int = None) -> bool:
        """Return True if compaction should fire this turn."""

    def compress(self, messages: list, current_tokens: int = None,
                 focus_topic: str = None) -> list:
        """Compact the message list and return a new (possibly shorter) list.

        The returned list must be a valid OpenAI-format message sequence.

        ``focus_topic`` is an optional topic string from manual
        ``/compress <focus>``; engines that support guided compression should
        prioritise preserving information related to it, others may ignore it.
        """

خصیصه‌های کلاسی که موتور شما باید نگه دارد

ایجنت این‌ها را مستقیماً برای نمایش و لاگ‌برداری می‌خواند:

last_prompt_tokens: int = 0
last_completion_tokens: int = 0
last_total_tokens: int = 0
threshold_tokens: int = 0        # زمانی که فشرده‌سازی فعال می‌شود
context_length: int = 0          # پنجرهٔ کامل زمینهٔ مدل
compression_count: int = 0       # چند بار compress() اجرا شده است

متدهای اختیاری

این‌ها در ABC پیش‌فرض‌های منطقی دارند. در صورت نیاز بازنویسی‌شان کنید:

متدپیش‌فرضچه زمانی بازنویسی کنید

on_session_end(session_id, messages)بدون عملیاتباید وضعیت را ذخیره (flush) و اتصال‌ها را ببندید

۴ انتخاب و مشاهدهٔ زمینه در هر نوبت

compress() به این مسئله پاسخ می‌دهد: «زمینه خیلی طولانی است ← کوتاهش کن». دو هوکِ اختیاری با پیش‌فرضِ بدون‌عملیات، محورِ جداگانهٔ انتخاب / مشاهده را پوشش می‌دهند تا دیگر موتور مجبور نباشد should_compress() را True کند و compress() را به‌عنوان کال‌بکِ هر نوبت به کار بگیرد:

def select_context(self, request_messages, *, conversation_messages=None,
                   incoming_message=None, budget_tokens=0):
    """Choose/replace the context for THIS request, before dispatch.

    Return a new message list to use for this one provider call (retrieval,
    topic routing, role/branch switching), or None to leave it unchanged.
    Request-only: the persisted conversation history is never mutated.
    """

def on_turn_complete(self, messages, usage=None, **kwargs):
    """Observe a finished turn after the assistant/tool loop completes.

    Receives a shallow copy of the finalized transcript plus the turn's
    canonical usage dict (or None if no provider response was reached), so the
    engine can ingest/index/summarize for the next select_context(). The return
    value is ignored.
    """

قرارداد:

  • به‌طور پیش‌فرض بدون عملیات و fail-open. هر دو به‌طور پیش‌فرض return None انجام می‌دهند. هوکِ غایب، یک استثنا یا مقدار بازگشتی نامعتبر، درخواست را دست‌نخورده باقی می‌گذارد — پس موتوری که خراب می‌شود هرگز بدتر از نصب‌نکردن آن نیست. میزبان همچنین برای پیش‌فرضِ به‌ارث‌رسیدهٔ ABC بررسی هویتی انجام می‌دهد و آن را کاملاً رد می‌کند، بنابراین موتورهایی که آن را پیاده‌سازی نکرده‌اند (از جمله فشرده‌سازِ داخلی) هیچ کارِ به‌ازای-هر-درخواستی انجام نمی‌دهند.
  • select_context() فقط مختص درخواست است. فهرست بازگشتی، پیام‌ها را فقط برای یک فراخوانی ارائه‌دهنده جایگزین می‌کند؛ تاریخچهٔ ذخیره‌شده هرگز نوشته نمی‌شود. بازگرداندن None، []، چیزی غیر از فهرست، یا فهرستی شامل آیتم‌های غیر دیکشنری، همگی به‌شکل fail-open به درخواستِ دست‌نخورده برمی‌گردند.
  • ترتیب / پایداری کش. این هوک قبل از کنترل کش پرامپت و همهٔ پاک‌سازهای درخواست اجرا می‌شود، بنابراین (الف) جایگزین‌شده همچنان همان اعتبارسنجیِ هر درخواست دیگر را پشت سر می‌گذارد، و (ب) پیش‌فرضِ بدون‌عملیات درخواست را بایت‌به‌بایت یکسان نگه می‌دارد — رفتار کش پرامپت برای موتورهای غیرپیاده‌ساز تغییر نمی‌کند. موتوری که فهرست را جایگزین می‌کند فقط پیشوند کشِ خودش را تغییر می‌دهد. به‌ازای هر درخواستِ ارائه‌دهنده ارزیابی می‌شود (در تلاش‌های مجدد دوباره اجرا می‌شود).
  • on_turn_complete() فقط مشاهدهٔ پس از نوبت است؛ messages را فقط‌خواندنی در نظر بگیرید. پوشش آن best-effort است: از نقطهٔ استانداردِ نهایی‌سازی نوبت صدا زده می‌شود. برخی مسیرهای بازگشتِ زودهنگامِ غیرعادی در حلقه (مثلاً مسدودشدن به‌واسطهٔ سیاست محتوایی یا شکست نهایی ارائه‌دهنده) ذخیره‌سازی کرده و برمی‌گردند بدون آنکه از مسیر نهایی‌سازی عبور کنند، بنابراین در حال حاضر این هوک را صادر نمی‌کنند — آن را مشاهده‌ای best-effort برای نوبت‌های کامل‌شده بدانید، نه کال‌بکی تضمین‌شده برای هر خروج زودهنگام. یکپارچه‌سازی همهٔ مسیرهای پایانی پشت یک نقطهٔ نهایی‌سازی واحد، کار جداگانه‌ای برای آینده است.

چه زمانی از این هوک‌ها استفاده کنیم — و چه زمانی نه

  • فقط وقتی select_context() را پیاده‌سازی کنید که موتور شما باید زمینهٔ هر درخواست را جایگزین کند — انتخابِ تقویت‌شده با بازیابی، مسیریابی موضوعی/شاخه‌ای، تعویض نقش. این تنها فعلِ دارای توانِ جابه‌جاییِ پیام‌های ورودی به یک درخواست است: هوک پلاگینیِ pre_llm_call طبق طراحی مستند، فقط تزریقی است (به پیام کاربر می‌افزاید و هرگز فهرست را بازنویسی نمی‌کند تا پیشوند کش پرامپت حفظ شود). اگر جایگزینی لازم ندارید، آن را پیاده‌سازی نکنید.
  • اگر پلاگین شما فقط مشاهده/درون‌ریزی پس از نوبت می‌خواهد (ایندکس‌گذاری، هم‌گام‌سازی حافظه، تحلیل)، به‌جای موتور زمینه یک ارائه‌دهندهٔ حافظه پیاده‌سازی کنید (sync_turn() — نگاه کنید به پلاگین ارائه‌دهندهٔ حافظه). یک موتور زمینه، مالکیت سیاست فشرده‌سازی نشست را در دست می‌گیرد؛ یک ارائه‌دهندهٔ حافظه نوبت‌ها را بدون مالکیت چیزی مشاهده می‌کند. on_turn_complete() به‌عنوان قرینهٔ مشاهده برای موتورهایی وجود دارد که از قبل به select_context() نیاز دارند — تا همان مؤلفه بتواند از نوبتی که تازه مسیریابی کرده بیاموزد — نه به‌عنوان یک کال‌بکِ همه‌منظورهٔ نوبت.
  • تأثیر یک select_context() واقعی بر کش پرامپت. انتخابی که بدون عملیات نباشد، به‌طور طبیعی پیشوند کش پرامپت را در نوبت‌هایی که انتخاب را تغییر می‌دهد عوض می‌کند — پیشوند آن درخواست دیگر با پیشوند کش‌شدهٔ ارائه‌دهنده مطابقت ندارد، پس آن نوبت‌ها به‌جای خواندن کش، آن را بازنویسی می‌کنند. موتورها باید وقتی چیزی تغییر نکرده، انتخابی پایدار برگردانند (همان شیء یا فهرستی برابر)، و فقط وقتی تصمیم مسیریابی واقعاً متفاوت است زمینه را بازشکل دهند؛ انتخابی که در هر نوبت به‌هم می‌ریزد، بی‌سروصدا در هر نوبت از استفادهٔ مجدد کش چشم‌پوشی می‌کند.

۵ ابزارهای موتور

موتورهای زمینه می‌توانند ابزارهایی را در معرض دید بگذارند که ایجنت مستقیماً فراخوانی‌شان کند. طرح‌واره‌ها (schema) را از get_tool_schemas() برگردانید و فراخوانی‌های ابزار را در handle_tool_call() مدیریت کنید:

def get_tool_schemas(self):
    return [{
        "name": "lcm_grep",
        "description": "Search the context knowledge graph",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "Search query"}
            },
            "required": ["query"],
        },
    }]

def handle_tool_call(self, name, args, **kwargs):
    if name == "lcm_grep":
        results = self._search_dag(args["query"])
        return json.dumps({"results": results})
    return json.dumps({"error": f"Unknown tool: {name}"})

ابزارهای موتور در زمان راه‌اندازی به فهرست ابزارهای ایجنت تزریق می‌شوند و به‌طور خودکار مسیریابی می‌شوند — نیازی به ثبت در رجیستری نیست.

۶ ثبت موتور

از طریق پوشه (توصیه‌شده)

موتور خود را در plugins/context_engine/<name>/ قرار دهید. __init__.py باید یک کلاس فرزند ContextEngine را صادر کند. سیستم کشف، به‌طور خودکار آن را پیدا و نمونه‌سازی می‌کند.

از طریق سیستم عمومی پلاگین

یک پلاگین عمومی هم می‌تواند یک موتور زمینه ثبت کند:

def register(ctx):
    engine = LCMEngine(context_length=200000)
    ctx.register_context_engine(engine)

فقط یک موتور قابل ثبت است. پلاگین دومی که بخواهد ثبت کند با یک هشدار رد می‌شود.

۷ چرخهٔ حیات

1. Engine instantiated (plugin load or directory discovery)
2. on_session_start() — conversation begins
3. update_from_response() — after each API call
4. should_compress() — checked each turn
5. compress() — called when should_compress() returns True
6. on_session_end() — session boundary (CLI exit, /reset, gateway expiry)

on_session_reset() هنگام /new یا /reset صدا زده می‌شود تا وضعیتِ مخصوص هر نشست، بدون خاموشی کامل پاک شود.

۸ پیکربندی

کاربران موتور شما را از طریق hermes plugins ← Provider Plugins ← Context Engine انتخاب می‌کنند، یا با ویرایش config.yaml:

context:
  engine: "lcm"   # باید با خصوصیت name موتور شما مطابقت داشته باشد

بلوک پیکربندی compression (compression.threshold، compression.protect_last_n و...) مخصوص ContextCompressor داخلی است، با یک استثنای صریح: compression.model_thresholds (بازنویسی‌های آستانه به‌ازای هر مدل) بخشی از قرارداد موتور زمینه است. میزبان نگاشتِ حل‌شده را قبل از فراخوانی اولیهٔ update_model() به engine.model_thresholds می‌دهد و update_model() کلاس پایه آن را اعمال می‌کند (تطبیق طولانی‌ترین زیررشته، با بازگشت به آستانهٔ پیکربندی‌شدهٔ موتور). موتورهایی که update_model() را بازنویسی می‌کنند مالک سیاست فشرده‌سازی خودشان هستند و می‌توانند این نگاشت را رعایت کنند یا نادیده بگیرند — برای استفادهٔ مجدد از همان منطق حل‌سازی: from agent.context_compressor import resolve_model_threshold. برای بقیهٔ موارد، موتور شما در صورت نیاز باید قالب پیکربندی خودش را تعریف کند و هنگام مقداردهی اولیه از config.yaml بخواند.

۹ تست

from agent.context_engine import ContextEngine

def test_engine_satisfies_abc():
    engine = YourEngine(context_length=200000)
    assert isinstance(engine, ContextEngine)
    assert engine.name == "your-name"

def test_compress_returns_valid_messages():
    engine = YourEngine(context_length=200000)
    msgs = [{"role": "user", "content": "hello"}]
    result = engine.compress(msgs)
    assert isinstance(result, list)
    assert all("role" in m for m in result)

مجموعهٔ کامل تست‌های قرارداد ABC را در tests/agent/test_context_engine.py ببینید.

۱۰ ایمنی نخ

وقتی compression.context_timeout_seconds > 0 باشد (پیش‌فرض)، هرمس کل گذرِ فشرده‌سازی — شامل compress() موتور شما و کال‌بک‌های مرزی، و on_pre_compress / on_session_switch هر ارائه‌دهندهٔ حافظه — را روی یک نخ دیمونِ استخری با محدودیت زمانی از سمت میزبان اجرا می‌کند. بنابراین موتور شما باید این را مفروض بگیرد:

  • فراخوانی‌ها ممکن است روی نخِ استخریِ دلخواهی برسند. به قرابت نخ (thread affinity) یا وضعیت threading.local مشترک با نخ گفتگو تکیه نکنید.
  • فهرست پیامی که دریافت می‌کنید یک اسنپ‌شاتِ عمیقِ خصوصی است؛ تغییر درجای آن مجاز است (قرارداد قدیمی)، اما این تغییر فقط در صورت کامیت‌شدنِ گذر دیده می‌شود. پس از انقضای زمانِ میزبان، کاری که هنوز در حال اجراست دور ریخته می‌شود — هرگز بیرون از کامیت، در وضعیت خارجی/مانا منتشر نکنید.
  • گذرهای نشست‌های مختلف می‌توانند هم‌زمان روی نخ‌های خواهرِ استخر اجرا شوند؛ یک نمونهٔ واحد موتور/ارائه‌دهنده که بین نشست‌ها مشترک است باید thread-safe باشد.

۱۱ همچنین ببینید

  • فشرده‌سازی و کش زمینه — فشرده‌ساز داخلی چگونه کار می‌کند
  • پلاگین ارائه‌دهندهٔ حافظه — سیستم پلاگینیِ تک‌انتخابیِ مشابه برای حافظه
  • پلاگین‌ها — نمای کلی سیستم پلاگین
