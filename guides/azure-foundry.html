Microsoft Foundry

ارائه‌دهندهٔ azure-foundry در Hermes Agent از Microsoft Foundry (با نام قبلی Azure AI Foundry) و Azure OpenAI پشتیبانی می‌کند. یک منبع Foundry می‌تواند مدل‌هایی با دو قالب متفاوت تبادل داده میزبانی کند:

  • به‌سبک OpenAI — POST /v1/chat/completions روی نقاط پایانی مانند https://<resource>.openai.azure.com/openai/v1. برای GPT-4.x، ‏GPT-5.x، ‏Llama، ‏Mistral و بیشتر مدل‌های با وزن باز استفاده می‌شود.
  • به‌سبک Anthropic — POST /v1/messages روی نقاط پایانی مانند https://<resource>.services.ai.azure.com/anthropic. زمانی استفاده می‌شود که Microsoft Foundry مدل‌های Claude را با قالب Anthropic Messages API ارائه می‌کند.

راهنمای راه‌اندازی، نقطهٔ پایانی شما را می‌آزماید و به‌طور خودکار روش انتقال مورد استفاده، استقرارهای در دسترس و طول زمینهٔ هر مدل را تشخیص می‌دهد.

۱ پیش‌نیازها

  • یک منبع Microsoft Foundry یا Azure OpenAI با دست‌کم یک استقرار
  • URL نقطهٔ پایانی استقرار
  • یا یک کلید API (از بخش «کلیدها و نقطهٔ پایانی» در Azure Portal) یا نقش RBAC با نام Azure AI User روی منبع Foundry، اگر قصد دارید از Microsoft Entra ID استفاده کنید (روش بدون کلید که Microsoft پیشنهاد می‌کند). طی تغییر نام محصولات Microsoft، برخی مستأجرها ممکن است این نقش را با نام Foundry User نمایش دهند.

۲ شروع سریع

hermes model
# → Select "Azure Foundry"
# → Enter your endpoint URL
# → Choose Authentication:
#     1. API key
#     2. Microsoft Entra ID  (managed identity / workload identity / az login)
# → (Entra) Hermes probes DefaultAzureCredential; on success it never asks for a key
# → (API key) Enter your API key
# Hermes probes the endpoint and auto-detects transport + models
# → Pick a model from the list (or type a deployment name manually)

راهنمای راه‌اندازی این کارها را انجام می‌دهد:

  1. بررسی مسیر URL — URLهایی که به /anthropic ختم می‌شوند، به‌عنوان مسیرهای Claude در Microsoft Foundry شناخته می‌شوند.
  2. آزمودن GET <base>/models — اگر نقطهٔ پایانی فهرست مدل‌ها را با ساختار OpenAI برگرداند، هرمس به chat_completions تغییر می‌کند و انتخاب‌گر را با شناسه‌های استقرار بازگشتی پر می‌کند.
  3. آزمودن قالب Anthropic Messages — مسیر پشتیبان برای نقاط پایانی‌ای که /models را ارائه نمی‌کنند، اما قالب Anthropic Messages را می‌پذیرند.
  4. بازگشت به ورود دستی — نقاط پایانی خصوصی یا دارای محدودیت دسترسی که همهٔ آزمون‌ها را رد می‌کنند همچنان کار می‌کنند؛ حالت API را انتخاب می‌کنید و نام استقرار را دستی می‌نویسید.

طول زمینهٔ مدل انتخاب‌شده از طریق زنجیرهٔ استاندارد فرادادهٔ هرمس (models.dev، فرادادهٔ ارائه‌دهنده و مقادیر پشتیبانِ ثابت برای خانوادهٔ مدل) تعیین و در config.yaml ذخیره می‌شود تا مدل بتواند اندازهٔ پنجرهٔ زمینهٔ خودش را درست تنظیم کند.

۳ Microsoft Entra ID (بدون کلید، RBAC) — پیشنهادشده

Microsoft برای بارهای کاری عملیاتی Foundry، احراز هویت بدون کلید با Microsoft Entra ID را پیشنهاد می‌کند. هرمس برای هر دو رابط API از Entra ID پشتیبانی می‌کند:

  • به‌سبک OpenAI (api_mode: chat_completions / codex_responses) — GPT-4/5، ‏Llama، ‏Mistral، ‏DeepSeek و غیره.
  • به‌سبک Anthropic (api_mode: anthropic_messages) — مدل‌های Claude روی Microsoft Foundry.

RBAC در Foundry به‌ازای هر منبع اعمال می‌شود (Azure AI User دسترسی به هر دو رابط را می‌دهد؛ برخی مستأجرها ممکن است Foundry User را نمایش دهند) و Microsoft برای هر دو، دامنهٔ استنتاج یکسانی (https://ai.azure.com/.default) مستند کرده است. در لایهٔ پیاده‌سازی:

  • روش OpenAI از قرارداد بومی api_key= با مقدار فراخواندنی در OpenAI Python SDK استفاده می‌کند — SDK برای هر درخواست به‌طور خودکار یک JWT تازه می‌سازد.
  • روش Anthropic از یک httpx.Client با هوک رویداد درخواست استفاده می‌کند که agent.azure_identity_adapter.build_bearer_http_client نصب کرده است، چون Anthropic SDK به‌صورت بومی auth_token فراخواندنی را نمی‌پذیرد. این هوک برای هر درخواست خروجی، Authorization: Bearer <fresh-jwt> را بازنویسی می‌کند. همان RBAC مایکروسافت و همان دامنهٔ Foundry — تنها تفاوت، قرارداد SDK است.

چرا از Entra ID استفاده کنیم؟

  • کلید API بلندمدتی وجود ندارد که به تعویض دوره‌ای یا لغو نیاز داشته باشد.
  • دسترسی مبتنی بر RBAC — نقش Azure AI User را روی منبع Foundry بدهید یا بردارید؛ بازنویسی پیکربندی لازم نیست.
  • لاگ‌های دسترسی و ممیزی بر اساس دریافت‌کنندهٔ نقش تفکیک می‌شوند، به‌جای آن‌که همهٔ فراخوانندگان یک کلید ثابت مشترک داشته باشند.
  • یک رابط احراز هویت واحد برای ماشین‌های مجازی Azure، پادهای AKS، ‏App Service، ‏Functions، ‏Container Apps و Foundry Agent Service از طریق هویت مدیریت‌شده.
  • جریان‌های هویت بار کاری و هویت سرویس برای خطوط لولهٔ CI/CD.

راه‌اندازی یک‌باره (سمت Azure)

  1. در Azure Portal، منبع Foundry را باز کنید ← کنترل دسترسی (IAM) ← افزودن ← افزودن تخصیص نقش.
  2. نقش Azure AI User را انتخاب کنید (یا Foundry User، اگر نقش در مستأجر شما تغییر نام داده است).
  3. آن را به یکی از موارد زیر اختصاص دهید:
    • حساب کاربری خودتان برای توسعهٔ محلی با az login.
    • یک هویت مدیریت‌شده یا هویت بار کاری برای منابع محاسباتی میزبانی‌شده در Azure (پیشنهادی برای محیط عملیاتی).
    • هویت ایجنتِ یک ایجنت میزبانی‌شده در Foundry Agent Service، وقتی هرمس داخل ایجنت میزبانی‌شده اجرا می‌شود.
    • یک هویت سرویس برای خطوط لولهٔ CI/CD، وقتی هویت بار کاری در دسترس نیست.
  4. حدود ۵ دقیقه منتظر بمانید تا نقش در سیستم منتشر شود.

معادل آن در Azure CLI:

az role assignment create \
  --assignee <principal-or-agent-identity-client-id> \
  --role "Azure AI User" \
  --scope <foundry-resource-id>

راه‌اندازی یک‌باره (سمت هرمس)

hermes model
# → Select "Azure Foundry"
# → Enter your endpoint URL
# → Authentication: 2 (Microsoft Entra ID)
# → (optional) user-assigned managed identity client ID
# → (optional) Azure tenant ID
# → Hermes probes DefaultAzureCredential() and reports which inner
#    credential succeeded (e.g. AzureCliCredential, ManagedIdentityCredential)

راهنمای راه‌اندازی یک آزمون مقدماتی محدود اجرا می‌کند (مهلت ۱۰ ثانیه). در صورت شکست، گزینهٔ «با این حال ذخیره کن، بعداً اعتبارسنجی کن» را پیشنهاد می‌دهد — زمانی مفید است که روی ماشینی پیکربندی می‌کنید که هنوز اعتبارنامه ندارد، اما هنگام اجرا خواهد داشت (مثلاً آماده‌سازی پیکربندی برای استقراری با هویت مدیریت‌شده).

azure-identity در اولین استفاده از طریق مسیر نصب هنگام نیازِ هرمس خودکار نصب می‌شود. برای نصب از پیش:

pip install azure-identity

پیکربندی نوشته‌شده در config.yaml

model:
  provider: azure-foundry
  base_url: https://my-resource.openai.azure.com/openai/v1
  api_mode: chat_completions
  auth_mode: entra_id
  default: gpt-4o
  context_length: 128000
  entra:
    scope: https://ai.azure.com/.default        # only when overriding the default

هرمس فقط یک گزینهٔ مختص Entra را در config.yaml مدیریت می‌کند:

  • scope — دامنهٔ منبع OAuth. پیش‌فرض آن دامنهٔ استنتاج مستندشدهٔ Microsoft است (https://ai.azure.com/.default). فقط زمانی آن را تغییر دهید که منبع شما برای مخاطب توکنِ غیراستاندارد ایجاد شده باشد.

همهٔ موارد دیگر (مستأجر، رمز هویت سرویس، فایل توکن فدره‌شده، مرجع ابر حاکمیتی و ترجیحات واسط احراز هویت) مستقیماً توسط azure-identity از متغیرهای محیطی استاندارد AZURE_* خوانده می‌شوند — ترتیب تعیین اعتبارنامه را در ادامه ببینید. آن‌ها را در ~/.hermes/.env یا محیط استقرار، دقیقاً مطابق مرجع SDK مایکروسافت تنظیم کنید.

در حالت Entra هیچ رمزی در ~/.hermes/.env ذخیره نمی‌شود — azure-identity توکن‌ها را داخل فرایند کش می‌کند (و در صورت امکان، در زنجیرهٔ کلید سیستم‌عامل یا ~/.IdentityService).

ترتیب تعیین اعتبارنامه

DefaultAzureCredential در azure-identity هنگام هر درخواست توکن این زنجیره را طی می‌کند و با اولین اعتبارنامه‌ای که توکن برگرداند، متوقف می‌شود:

  1. اعتبارنامهٔ محیطی — AZURE_TENANT_ID + AZURE_CLIENT_ID + AZURE_CLIENT_SECRET (یا AZURE_CLIENT_CERTIFICATE_PATH / AZURE_FEDERATED_TOKEN_FILE).
  2. هویت بار کاری — AZURE_FEDERATED_TOKEN_FILE (توکن‌های فدره‌شدهٔ AKS / ‏OIDC).
  3. هویت مدیریت‌شده — نقطهٔ پایانی IMDS ‏(169.254.169.254) برای ماشین‌های مجازی؛ IDENTITY_ENDPOINT برای App Service / Functions / Container Apps. ایجنت‌های میزبانی‌شدهٔ Foundry Agent Service از هویت ایجنتِ همان ایجنت میزبانی‌شده استفاده می‌کنند.
  4. Visual Studio Code — افزونهٔ حساب Azure.
  5. Azure CLI — نشست az login.
  6. Azure Developer CLI — azd auth login.
  7. Azure PowerShell — Connect-AzAccount.
  8. واسط احراز هویت (فقط Windows / WSL) — Web Account Manager.

اعتبارنامهٔ تعاملی مرورگر به‌طور پیش‌فرض برای اجراهای بدون نظارت هرمس کنار گذاشته می‌شود؛ به‌جای آن از Azure CLI، ‏Azure Developer CLI، هویت مدیریت‌شده، هویت بار کاری یا اعتبارنامهٔ هویت سرویس استفاده کنید.

الگوهای استقرار

توسعهٔ محلی:

az login
hermes model   # pick Azure Foundry → Entra ID
hermes         # uses your az login token

Azure VM / Functions / App Service / Container Apps (هویت مدیریت‌شدهٔ تخصیص‌یافته توسط سیستم):

  1. هویت تخصیص‌یافته توسط سیستم را روی منبع محاسباتی فعال کنید.
  2. نقش Azure AI User (یا Foundry User) را روی منبع Foundry به آن هویت بدهید.
  3. model.auth_mode: entra_id را در config.yaml تنظیم کنید — متغیر محیطی لازم نیست.

Azure VM / Functions / App Service / Container Apps (هویت مدیریت‌شدهٔ تخصیص‌یافته توسط کاربر):

  • AZURE_CLIENT_ID را روی شناسهٔ کلاینت هویت تخصیص‌یافته توسط کاربر تنظیم کنید تا DefaultAzureCredential هویت درست را انتخاب کند.

ایجنت میزبانی‌شده در Foundry Agent Service:

  • ایجنت میزبانی‌شده را بسازید و نقش Azure AI User (یا Foundry User) را روی منبع Foundry به هویت همان ایجنت بدهید. هرمس از داخل ایجنت میزبانی‌شده از ManagedIdentityCredential استفاده می‌کند؛ نقش باید به هویت ایجنت تخصیص داده شود، نه فقط به پروژهٔ والد یا کاربر شما.

هویت بار کاری AKS (جایگزین AAD Pod Identity):

  • شناسهٔ کلاینت هویت بار کاری را به‌صورت حاشیه‌نویسی به حساب سرویس پاد اضافه کنید.
  • فایل توکن فدره‌شدهٔ پاد از طریق AZURE_FEDERATED_TOKEN_FILE خودکار تشخیص داده می‌شود.
  • model.auth_mode: entra_id بدون تغییر دیگری در پیکربندی کار می‌کند.

هویت سرویس در CI:

  • AZURE_TENANT_ID، AZURE_CLIENT_ID و AZURE_CLIENT_SECRET را در محیط اجراکننده تنظیم کنید.

ابرهای حاکمیتی (دولتی، چین)

AZURE_AUTHORITY_HOST را در محیط صادر کنید (مثلاً https://login.microsoftonline.us برای Azure Government و https://login.partner.microsoftonline.cn برای Azure China). azure-identity آن را مستقیماً می‌خواند.

بررسی سلامت

وقتی model.auth_mode: entra_id باشد، hermes doctor یک آزمون ۱۰ ثانیه‌ای روی DefaultAzureCredential اجرا می‌کند و گزارش می‌دهد کدام اعتبارنامهٔ داخلی موفق بوده است (وجود متغیرهای محیطی، دسترس‌پذیری نقطهٔ پایانی هویت مدیریت‌شده و غیره).

hermes auth یک بلوک وضعیت ساختاریافته نشان می‌دهد:

azure-foundry (Microsoft Entra ID):
  Endpoint: https://my-resource.openai.azure.com/openai/v1
  Scope: https://ai.azure.com/.default
  Status: configured; live token probe is skipped here

محدودیت‌ها

  • نقاط پایانی به‌سبک Anthropic از هوک رویداد httpx استفاده می‌کنند. Anthropic Python SDK به‌صورت بومی auth_token فراخواندنی را نمی‌پذیرد (نسخهٔ ۰٫۸۶٫۰ و پایین‌تر). هرمس روی یک httpx.Client سفارشی هوک رویداد درخواست نصب می‌کند که برای هر درخواست خروجی یک JWT تازه می‌سازد و Authorization: Bearer <jwt> را بازنویسی می‌کند. از نظر عملکرد، این روش معادل قرارداد بومی Callable[[], str] در OpenAI SDK است، اما یک لایهٔ واسط اضافه دارد. اگر Anthropic SDK در نسخه‌ای آینده پشتیبانی مستقیم از احراز هویت فراخواندنی اضافه کند، هرمس بدون نیاز به دخالت کاربر به آن مهاجرت می‌کند.
  • کارهای دسته‌ای و multiprocessing.Pool. ارائه‌دهندهٔ توکن Entra یک کلوژر است که نمی‌توان آن را برای عبور از مرز فرایندها با pickle سریال‌سازی کرد. batch_runner.py خودکار مقدار فراخواندنی را از پیکربندی ورکر حذف می‌کند و اجازه می‌دهد هر فرایند ورکر، ارائه‌دهندهٔ خودش را از config.yaml بازسازی کند — اقدامی از طرف کاربر لازم نیست، اما هر ورکر هنگام شروع یک‌بار هزینهٔ پیمایش زنجیره را می‌پردازد.
  • JWT حامل در auth.json ذخیره نمی‌شود. هرمس کش داخلی توکن azure-identity را تکرار نمی‌کند؛ در شروع سرد، اولین استنتاج زنجیرهٔ اعتبارنامه را طی می‌کند.

۴ پیکربندی (نوشته‌شده در config.yaml)

پس از اجرای راهنمای راه‌اندازی، چیزی شبیه این خواهید دید:

model:
  provider: azure-foundry
  base_url: https://my-resource.openai.azure.com/openai/v1
  api_mode: chat_completions         # or "anthropic_messages"
  default: gpt-5.4-mini              # your deployment / model name
  context_length: 400000             # auto-detected

و در ~/.hermes/.env:

AZURE_FOUNDRY_API_KEY=<your-azure-key>

۵ نقاط پایانی به‌سبک OpenAI (GPT، ‏Llama و غیره)

نقطهٔ پایانی نسخهٔ عمومی v1 در Azure OpenAI، کلاینت استاندارد پایتون openai را با کمترین تغییر می‌پذیرد:

model:
  provider: azure-foundry
  base_url: https://my-resource.openai.azure.com/openai/v1
  api_mode: chat_completions
  default: gpt-5.4

رفتارهای مهم:

  • GPT-5.x، ‏codex و سری o خودکار به Responses API مسیریابی می‌شوند. Microsoft Foundry مدل‌های GPT-5 / codex / o1 / o3 / o4 را فقط با Responses API مستقر می‌کند — فراخوانی /chat/completions برای آن‌ها خطای ۴۰۰ با پیام «عملیات درخواستی پشتیبانی نمی‌شود» برمی‌گرداند. هرمس این خانواده‌های مدل را از روی نام تشخیص می‌دهد و api_mode را خودکار به codex_responses ارتقا می‌دهد، حتی اگر در config.yaml همچنان api_mode: chat_completions نوشته شده باشد. GPT-4، ‏GPT-4o، ‏Llama، ‏Mistral و سایر استقرارها روی /chat/completions می‌مانند.
  • max_completion_tokens خودکار استفاده می‌شود. Azure OpenAI (مانند OpenAI مستقیم) برای مدل‌های gpt-4o، سری o و gpt-5.x به max_completion_tokens نیاز دارد. هرمس بر اساس نقطهٔ پایانی، پارامتر درست را می‌فرستد.
  • نقاط پایانی پیش از v1 که به api-version نیاز دارند. اگر URL پایهٔ قدیمی مانند https://<resource>.openai.azure.com/openai?api-version=2025-04-01-preview دارید، هرمس رشتهٔ پرس‌وجو را استخراج می‌کند و در هر درخواست از طریق default_query می‌فرستد (در غیر این صورت OpenAI SDK هنگام اتصال مسیرها آن را حذف می‌کند).

۶ نقاط پایانی به‌سبک Anthropic (Claude از طریق Microsoft Foundry)

برای استقرارهای Claude از مسیر به‌سبک Anthropic استفاده کنید:

model:
  provider: azure-foundry
  base_url: https://my-resource.services.ai.azure.com/anthropic
  api_mode: anthropic_messages
  default: claude-sonnet-4-6

رفتارهای مهم:

  • /v1 از URL پایه حذف می‌شود. Anthropic SDK به URL هر درخواست /v1/messages اضافه می‌کند — هرمس پیش از تحویل URL به SDK، هر /v1 انتهایی را حذف می‌کند تا مسیرهای دارای /v1 تکراری ساخته نشوند.
  • api-version از طریق default_query فرستاده می‌شود، نه با افزودن به URL. مسیر Anthropic در Azure به رشتهٔ پرس‌وجوی api-version نیاز دارد. قراردادن آن در URL پایه مسیرهای معیوبی مانند /anthropic?api-version=.../v1/messages می‌سازد و خطای ۴۰۴ برمی‌گرداند. هرمس در عوض api-version=2025-04-15 را از طریق default_query در Anthropic SDK می‌فرستد.
  • به‌جای x-api-key از احراز هویت توکن حامل استفاده می‌شود. مسیر سازگار با Anthropic در Azure به Authorization: Bearer <key> نیاز دارد، نه هدر بومی x-api-key در Anthropic. هرمس azure.com را در URL پایه تشخیص می‌دهد و کلید API را از فیلد auth_token در SDK عبور می‌دهد تا هدر درست به سرویس بالادستی برسد.
  • هدر بتای پنجرهٔ زمینهٔ یک‌میلیونی حفظ می‌شود. Azure هنوز دسترسی به زمینهٔ یک‌میلیون‌توکنی Claude (Opus 4.6/4.7، ‏Sonnet 4.6) را به هدر anthropic-beta: context-1m-2025-08-07 وابسته می‌کند. هرمس این هدر بتا را روی مسیرهای Azure حفظ می‌کند (از درخواست‌های بومی OAuth در Anthropic حذف می‌شود، چون بعضی اشتراک‌ها آن را رد می‌کنند، اما Azure به آن نیاز دارد).
  • تازه‌سازی توکن OAuth غیرفعال است. استقرارهای Azure از کلید API ثابت استفاده می‌کنند. حلقهٔ تازه‌سازی توکن OAuth در ~/.claude/.credentials.json که برای Anthropic Console اعمال می‌شود، صریحاً برای نقاط پایانی Azure کنار گذاشته می‌شود تا توکن OAuth در Claude Code، کلید Azure شما را در میانهٔ نشست بازنویسی نکند.

۷ روش جایگزین: provider: anthropic + URL پایهٔ Azure

اگر از قبل provider: anthropic را پیکربندی کرده‌اید و فقط می‌خواهید برای Claude به Microsoft Foundry اشاره کند، می‌توانید ارائه‌دهندهٔ azure-foundry را کاملاً کنار بگذارید:

model:
  provider: anthropic
  base_url: https://my-resource.services.ai.azure.com/anthropic
  key_env: AZURE_ANTHROPIC_KEY
  default: claude-sonnet-4-6

همراه با تنظیم AZURE_ANTHROPIC_KEY در ~/.hermes/.env. هرمس azure.com را در URL پایه تشخیص می‌دهد و زنجیرهٔ توکن OAuth در Claude Code را دور می‌زند تا کلید Azure مستقیماً با احراز هویت x-api-key استفاده شود.

key_env نام اصلی فیلد با قالب snake_case است؛ api_key_env (و شکل‌های camelCase یعنی keyEnv / apiKeyEnv) به‌عنوان نام مستعار پذیرفته می‌شوند. اگر هم key_env و هم AZURE_ANTHROPIC_KEY/ANTHROPIC_API_KEY تنظیم شده باشند، متغیر محیطی نام‌برده در key_env اولویت دارد.

۸ کشف مدل

Azure نقطهٔ پایانی‌ای که صرفاً با کلید API، استقرارهای مدلِ مستقرشدهٔ شما را فهرست کند ارائه نمی‌دهد. شمارش استقرارها به احراز هویت Azure Resource Manager ‏(az cognitiveservices account deployment list) با یک هویت Azure AD نیاز دارد، نه کلید API استنتاج.

کارهایی که هرمس می‌تواند انجام دهد:

  • نقاط پایانی Azure OpenAI v1 ‏(<resource>.openai.azure.com/openai/v1)، GET /models را با کاتالوگ مدل‌های در دسترس منبع ارائه می‌کنند. هرمس از این فهرست برای پرکردن انتخاب‌گر مدل استفاده می‌کند.
  • مسیرهای /anthropic در Microsoft Foundry: از روی مسیر URL تشخیص داده می‌شوند و نام مدل دستی وارد می‌شود.
  • نقاط پایانی خصوصی یا پشت فایروال: ورود دستی همراه با پیام روشنی مبنی بر «آزمودن نقطهٔ پایانی ممکن نشد».

همیشه می‌توانید نام استقرار را مستقیماً بنویسید — هرمس آن را با فهرست بازگشتی اعتبارسنجی نمی‌کند.

۹ متغیرهای محیطی

Azure SDK متغیرهای محیطی AZURE_* را مستقیماً می‌خواند. هرمس جز برای گزارش منابع موجود در خروجی hermes doctor، هرگز آن‌ها را بررسی نمی‌کند.

۱۰ عیب‌یابی

خطای ۴۰۱ عدم مجوز در استقرارهای gpt-5.x.
Azure مدل‌های gpt-5.x را روی /chat/completions ارائه می‌کند، نه /responses. هرمس وقتی URL شامل openai.azure.com باشد این موضوع را خودکار مدیریت می‌کند، اما اگر خطای ۴۰۱ با بدنهٔ «کلید API نامعتبر است» دیدید، بررسی کنید که api_mode در config.yaml برابر chat_completions باشد.

خطای ۴۰۴ روی /v1/messages?api-version=.../v1/messages.
این همان باگ URL معیوب در راه‌اندازی‌های Azure Anthropic پیش از اصلاح است. هرمس را ارتقا دهید — پارامتر api-version اکنون به‌جای قراردادن در URL پایه، از طریق default_query منتقل می‌شود؛ بنابراین SDK نمی‌تواند هنگام اتصال URL آن را خراب کند.

راهنمای راه‌اندازی می‌گوید «تشخیص خودکار کامل نشد».
نقطهٔ پایانی هم آزمون /models و هم آزمون Anthropic Messages را رد کرده است. این برای نقاط پایانی خصوصی پشت فایروال یا دارای فهرست مجاز IP طبیعی است. به انتخاب دستی حالت API برگردید و نام استقرار را بنویسید — همه‌چیز همچنان کار می‌کند؛ هرمس فقط نمی‌تواند انتخاب‌گر را از پیش پر کند.

روش انتقال اشتباه انتخاب شده است.
hermes model را دوباره اجرا کنید تا راهنمای راه‌اندازی دوباره بیازماید. اگر باز هم حالت اشتباه انتخاب شد، می‌توانید config.yaml را مستقیم ویرایش کنید:

model:
  provider: azure-foundry
  api_mode: anthropic_messages   # or chat_completions

Entra ID: پیام «زنجیرهٔ اعتبارنامه به پایان رسید» یا خطای ۴۰۱ عدم مجوز پس از تغییر به auth_mode: entra_id.

  • برای تازه‌سازی نشست توسعه‌دهندهٔ خود az login را اجرا کنید (ممکن است توکن کش‌شده منقضی شده باشد).
  • بررسی کنید تخصیص نقش Azure AI User (یا Foundry User) اعمال شده است: az role assignment list --assignee <user-or-identity-id> باید آن را روی منبع Foundry شما فهرست کند. انتشار نقش می‌تواند تا ۵ دقیقه طول بکشد.
  • برای هویت‌های مدیریت‌شدهٔ تخصیص‌یافته توسط کاربر، دوباره بررسی کنید که AZURE_CLIENT_ID با هویت متصل به منبع محاسباتی مطابقت داشته باشد.
  • hermes doctor را اجرا کنید — آزمون Azure Entra گزارش می‌دهد دریافت توکن موفق بوده یا نه، و راهنمای رفع مشکل هم ارائه می‌کند.

Entra ID: آزمون مقدماتی راهنمای راه‌اندازی گیر می‌کند یا مهلتش تمام می‌شود.
آزمون مقدماتی ۱۰ ثانیه‌ای، بررسی الزام‌آور نیست. «با این حال ذخیره کن و بعداً اعتبارسنجی کن» را انتخاب کنید و پس از استقرار در محیط مقصد، hermes doctor را اجرا کنید. علت‌های رایج شامل دسترس‌ناپذیری سرویس توکن یا وضعیت کهنهٔ ورود محلی است — در CI هویت بار کاری را ترجیح دهید، هنگام استفاده از هویت سرویس AZURE_TENANT_ID + AZURE_CLIENT_ID + AZURE_CLIENT_SECRET را تنظیم کنید، یا برای توسعهٔ محلی az login را اجرا کنید.

خطای ۴۰۱ روی نقطهٔ پایانی به‌سبک Anthropic با Entra ID.
بررسی کنید همان نقش Azure AI User (یا Foundry User) روی منبع Foundry تخصیص داده شده باشد (هر دو مسیر /openai/v1 و /anthropic را پوشش می‌دهد). اگر آزمون به‌سبک OpenAI در راهنمای راه‌اندازی کار می‌کند، اما درخواست‌های claude-* در زمان اجرا شکست می‌خورند، رایج‌ترین علت، مقدار کهنهٔ model.entra.scope باقی‌مانده از اجرای قبلی راهنماست — خط entra.scope را از config.yaml حذف کنید تا زمان اجرا به دامنهٔ پیش‌فرض https://ai.azure.com/.default برگردد.
