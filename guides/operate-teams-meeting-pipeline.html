راهبری خط لولهٔ جلسات تیمز

این راهنما را بعد از آن به کار ببرید که قابلیت را از جلسات تیمز (خلاصه‌جلسه) فعال کرده باشید.

این صفحه شامل این‌هاست:

  • گردش‌کارهای CLI اپراتور
  • نگهداری روتین اشتراک‌ها
  • تریاژ خرابی‌ها
  • بررسی‌های راه‌اندازی نهایی (go-live)
  • کاربرگ استقرار

۱ فرمان‌های اصلی اپراتور

اعتبارسنجی اسنپ‌شات پیکربندی

hermes teams-pipeline validate

بعد از هر تغییر پیکربندی، اول این را اجرا کنید.

بررسی سلامت توکن

hermes teams-pipeline token-health
hermes teams-pipeline token-health --force-refresh

وقتی به کهنه‌بودن وضعیت احراز هویت شک دارید از --force-refresh استفاده کنید.

بررسی اشتراک‌ها

hermes teams-pipeline subscriptions

تمدید اشتراک‌های نزدیک به انقضا

hermes teams-pipeline maintain-subscriptions
hermes teams-pipeline maintain-subscriptions --dry-run

خودکارسازی تمدید اشتراک‌ها (برای پروداکشن الزامی است)

اشتراک‌های Microsoft Graph حداکثر ظرف ۷۲ ساعت منقضی می‌شوند. اگر چیزی آن‌ها را تمدید نکند، اعلان‌های جلسات بعد از ۳ روز بی‌سروصدا متوقف می‌شوند و خط لوله «خراب» به نظر می‌رسد. این شایع‌ترین حالت خرابی عملیاتی برای هر یکپارچه‌سازی مبتنی بر Graph است.

باید maintain-subscriptions را زمان‌بندی‌شده اجرا کنید. یکی از این سه گزینه را انتخاب کنید:

گزینهٔ ۱: کرون هرمس (پیشنهادی اگر از قبل گیت‌وی هرمس را اجرا می‌کنید)

هرمس یک زمان‌بند کرون داخلی دارد. حالت --no-agent یک اسکریپت را به‌عنوان کار اجرا می‌کند (به‌جای استفاده از LLM) و --script باید به فایلی زیر ~/.hermes/scripts/ اشاره کند. اول اسکریپت را بسازید:

mkdir -p ~/.hermes/scripts
cat > ~/.hermes/scripts/maintain-teams-subscriptions.sh <<'EOF'
#!/usr/bin/env bash
exec hermes teams-pipeline maintain-subscriptions
EOF
chmod +x ~/.hermes/scripts/maintain-teams-subscriptions.sh

بعد یک کار کرونِ فقط-اسکریپتی ثبت کنید که هر ۱۲ ساعت اجرا می‌شود (۶ برابر حاشیهٔ اطمینان نسبت به پنجرهٔ انقضای ۷۲ ساعته):

hermes cron create "0 */12 * * *" \
  --name "teams-pipeline-maintain-subscriptions" \
  --no-agent \
  --script maintain-teams-subscriptions.sh \
  --deliver local

مطمئن شوید ثبت شده و زمان اجرای بعدی را بررسی کنید:

hermes cron list
hermes cron status        # وضعیت زمان‌بند

گزینهٔ ۲: تایمر systemd (پیشنهادی برای استقرارهای پروداکشن لینوکس)

فایل /etc/systemd/system/hermes-teams-pipeline-maintain.service را بسازید:

[Unit]
Description=Hermes Teams pipeline subscription maintenance
After=network-online.target

[Service]
Type=oneshot
User=hermes
EnvironmentFile=/etc/hermes/env
ExecStart=/usr/local/bin/hermes teams-pipeline maintain-subscriptions

و /etc/systemd/system/hermes-teams-pipeline-maintain.timer:

[Unit]
Description=Run Hermes Teams pipeline subscription maintenance every 12 hours

[Timer]
OnBootSec=5min
OnUnitActiveSec=12h
Persistent=true

[Install]
WantedBy=timers.target

فعال‌سازی:

sudo systemctl daemon-reload
sudo systemctl enable --now hermes-teams-pipeline-maintain.timer
systemctl list-timers hermes-teams-pipeline-maintain.timer

گزینهٔ ۳: crontab ساده

0 */12 * * * /usr/local/bin/hermes teams-pipeline maintain-subscriptions >> /var/log/hermes/teams-pipeline-maintain.log 2>&1

مطمئن شوید محیط کرون اعتبارنامه‌های MSGRAPH_* را دارد. ساده‌ترین راه‌حل: سورس‌کردن ~/.hermes/.env در ابتدای یک اسکریپت رپر که crontab صدا می‌زند.

تأیید اینکه تمدید کار می‌کند

بعد از اینکه زمان‌بندی را راه انداختید، پس از اولین اجرای زمان‌بندی‌شده فعالیت تمدید را چک کنید:

hermes teams-pipeline subscriptions   # باید جلو رفتن expirationDateTime را نشان دهد
hermes teams-pipeline maintain-subscriptions --dry-run   # بیشتر مواقع باید "0 expiring soon" نشان بدهد

اگر دیدید وب‌هوک Graph‌تان بعد از دقیقاً ~۷۲ ساعت به‌طور مرموز «از کار افتاد»، اولین چیزی که باید چک کنید همین است: آیا کارِ تمدید واقعاً اجرا شده؟

بررسی کارهای اخیر

hermes teams-pipeline list
hermes teams-pipeline list --status failed
hermes teams-pipeline show <job-id>

اجرای مجدد یک کار ذخیره‌شده

hermes teams-pipeline run <job-id>

واکشی آزمایشی آرتیفکت‌های جلسه

hermes teams-pipeline fetch --meeting-id <meeting-id>
hermes teams-pipeline fetch --join-web-url "<join-url>"
hermes teams-pipeline fetch --join-web-url "<join-url>" --organizer-user-id <entra-user-id>

--organizer-user-id (شناسهٔ کاربر Microsoft Entra برگزارکننده) را پاس بدهید تا رفع ارجاع از مسیر Graphِ محدود به برگزارکننده یعنی /users/{id}/onlineMeetings انجام شود. این کار برای URLهای کوتاه /meet/ تیمز ضروری است، چون Graph آن‌ها را روی نقطهٔ پایانی /communications/onlineMeetings رد می‌کند. کارهای وب‌هوک‌محور، برگزارکننده را به‌طور خودکار از @odata.id اعلان استخراج می‌کنند.

۲ راهنمای عملیاتی روتین

بعد از اولین راه‌اندازی

این‌ها را به ترتیب اجرا کنید:

hermes teams-pipeline validate
hermes teams-pipeline token-health --force-refresh
hermes teams-pipeline subscriptions

سپس یک رویداد جلسهٔ واقعی را راه بیندازید یا منتظرش بمانید و تأیید کنید:

hermes teams-pipeline list
hermes teams-pipeline show <job-id>

بررسی‌های روزانه یا دوره‌ای

  • hermes teams-pipeline maintain-subscriptions --dry-run را اجرا کنید
  • hermes teams-pipeline list --status failed را بررسی کنید
  • مطمئن شوید مقصد تحویل تیمز همچنان همان چت یا کانال درست است

قبل از تغییر URLهای وب‌هوک یا مقاصد تحویل

  • URL عمومی اعلان‌ها یا پیکربندی مقصد تیمز را به‌روزرسانی کنید
  • hermes teams-pipeline validate را اجرا کنید
  • اشتراک‌های تحت تأثیر را تمدید یا بازسازی کنید
  • مطمئن شوید رویدادهای جدید در مقصد نهایی (sink) مورد انتظار فرود می‌آیند

۳ تریاژ خرابی‌ها

هیچ کاری ساخته نمی‌شود

چک کنید:

  • msgraph_webhook فعال باشد
  • URL عمومی اعلان‌ها به /msgraph/webhook اشاره کند
  • client state داخل اشتراک با MSGRAPH_WEBHOOK_CLIENT_STATE مطابقت داشته باشد
  • اشتراک‌ها هنوز در سمت سرویس وجود داشته باشند و منقضی نشده باشند

کارها در حالت retry می‌مانند یا قبل از خلاصه‌سازی شکست می‌خورند

چک کنید:

  • مجوزها و در دسترس‌بودن رونوشت (transcript)
  • مجوزهای ضبط و در دسترس‌بودن آرتیفکت‌ها
  • در دسترس‌بودن ffmpeg اگر حالت پشتیبان ضبط فعال باشد
  • سلامت توکن Graph

خلاصه‌ها تولید می‌شوند ولی به تیمز تحویل داده نمی‌شوند

چک کنید:

  • platforms.teams.enabled: true
  • delivery_mode
  • incoming_webhook_url برای حالت وب‌هوک
  • chat_id یا team_id به‌همراه channel_id برای حالت Graph
  • پیکربندی احراز هویت تیمز اگر ارسال از طریق Graph استفاده می‌شود

اجرای مجدد تکراری یا غیرمنتظره

چک کنید:

  • آیا کاری را با hermes teams-pipeline run دستی دوباره اجرا کرده‌اید
  • آیا رکورد مقصد نهایی برای آن جلسه از قبل وجود دارد
  • آیا عمداً مسیر ارسال مجدد را در پیکربندی محلی‌تان فعال کرده‌اید

۴ چک‌لیست راه‌اندازی نهایی

  • ☐ اعتبارنامه‌های Graph موجود و درست‌اند
  • ☐ msgraph_webhook فعال است و از اینترنت عمومی قابل دسترسی است
  • ☐ MSGRAPH_WEBHOOK_CLIENT_STATE تنظیم شده و با اشتراک‌ها مطابقت دارد
  • ☐ اشتراک رونوشت ساخته شده است
  • ☐ اگر حالت پشتیبان STT لازم است، اشتراک ضبط ساخته شده است
  • ☐ اگر حالت پشتیبان ضبط فعال است، ffmpeg نصب شده است
  • ☐ مقصد تحویل خروجی تیمز پیکربندی و تأیید شده است
  • ☐ مقاصد نهایی Notion و Linear فقط اگر واقعاً لازم‌اند پیکربندی شده‌اند
  • ☐ hermes teams-pipeline validate یک اسنپ‌شات OK برمی‌گرداند
  • ☐ hermes teams-pipeline token-health --force-refresh با موفقیت انجام می‌شود
  • ☐ maintain-subscriptions زمان‌بندی شده است (کرون هرمس، تایمر systemd یا crontab — به خودکارسازی تمدید اشتراک‌ها نگاهی بیندازید). بدون این، اشتراک‌های Graph ظرف ۷۲ ساعت بی‌سروصدا منقضی می‌شوند.
  • ☐ یک رویداد واقعی جلسهٔ سرتاسری، یک کار ذخیره‌شده تولید کرده است
  • ☐ حداقل یک خلاصه به مقصد تحویل مورد نظر رسیده است

۵ راهنمای انتخاب حالت تحویل
