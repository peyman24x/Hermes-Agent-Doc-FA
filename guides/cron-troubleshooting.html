عیب‌یابی Cron

وقتی یک کار کرون آن‌طور که انتظار می‌رود رفتار نمی‌کند، این بررسی‌ها را به ترتیب انجام دهید. بیشتر مشکل‌ها در یکی از چهار دسته قرار می‌گیرند: زمان‌بندی، تحویل، مجوزها یا بارگذاری مهارت‌ها.

۱ کارها اجرا نمی‌شوند

بررسی ۱: مطمئن شوید کار وجود دارد و فعال است

hermes cron list

کار را پیدا کنید و مطمئن شوید حالت آن [active] است (نه [paused] و نه [completed]). اگر [completed] نشان می‌دهد، شمارندهٔ تکرار احتمالاً تمام شده است — برای بازنشانی آن، کار را ویرایش کنید.

بررسی ۲: مطمئن شوید زمان‌بندی درست است

زمان‌بندی با قالب اشتباه، بی‌سروصدا به اجرای یک‌باره برمی‌گردد یا به‌طور کامل رد می‌شود. عبارت‌تان را تست کنید:

عبارت شماارزیابی مورد انتظار
0 9 * * *هر روز ساعت ۹:۰۰ صبح
0 9 * * 1هر دوشنبه ساعت ۹:۰۰ صبح
every 2hهر ۲ ساعت از الان به بعد
30m۳۰ دقیقه از الان به بعد
2025-06-01T09:00:00۱ ژوئن ۲۰۲۵، ساعت ۹:۰۰ صبح به وقت UTC

اگر کار یک‌بار اجرا می‌شود و بعد از فهرست محو می‌شود، یعنی زمان‌بندیِ یک‌بارِ مصرف است (30m، 1d یا یک مهر زمانی ISO) — این رفتار مورد انتظار است.

بررسی ۳: آیا گیت‌وی در حال اجراست؟

کارهای کرون توسط رشتهٔ تیکِ پس‌زمینهٔ گیت‌وی اجرا می‌شوند که هر ۶۰ ثانیه یک‌بار تیک می‌خورد. یک نشست چت عادی در CLI کارهای کرون را به‌طور خودکار اجرا نمی‌کند.

اگر انتظار دارید کارها به‌طور خودکار اجرا شوند، به یک گیت‌وی در حال اجرا نیاز دارید (hermes gateway برای حالت پیش‌زمینه، یا hermes gateway start برای سرویس نصب‌شده). برای دیباگ‌های موردی، می‌توانید یک تیک را به‌صورت دستی با hermes cron tick راه بیندازید.

بررسی ۴: ساعت سیستم و منطقهٔ زمانی را چک کنید

کارها از منطقهٔ زمانی محلی استفاده می‌کنند. اگر ساعت ماشین‌تان اشتباه یا در منطقهٔ زمانی متفاوتی از آنچه انتظار دارید باشد، کارها در زمان‌های اشتباه اجرا می‌شوند. بررسی کنید:

date
hermes cron list   # مقایسهٔ زمان‌های next_run با زمان محلی

۲ شکست‌های تحویل

بررسی ۱: مطمئن شوید مقصد تحویل درست است

مقاصد تحویل به بزرگی/کوچکی حروف حساس‌اند و نیازمند پیکربندی درست پلتفرم مربوطه هستند. یک مقصد بدپیکربندی‌شده، پاسخ را بی‌سروصدا دور می‌ریزد.

مقصدنیازمندی
telegramTELEGRAM_BOT_TOKEN در ~/.hermes/.env
discordDISCORD_BOT_TOKEN در ~/.hermes/.env
slackSLACK_BOT_TOKEN در ~/.hermes/.env
whatsappگیت‌وی WhatsApp پیکربندی شده باشد
signalگیت‌وی Signal پیکربندی شده باشد
matrixهوم‌سرور Matrix پیکربندی شده باشد
emailSMTP در config.yaml پیکربندی شده باشد
smsارائه‌دهندهٔ SMS پیکربندی شده باشد
localدسترسی نوشتن به ~/.hermes/cron/output/
originبه چتی که کار در آن ساخته شده تحویل می‌دهد

سایر پلتفرم‌های پشتیبانی‌شده عبارت‌اند از mattermost، homeassistant، dingtalk، feishu، wecom، weixin، bluebubbles، qqbot و webhook. همچنین می‌توانید با دستور platform:chat_id یک چت مشخص را هدف بگیرید (مثلاً telegram:-1001234567890).

اگر تحویل شکست بخورد، کار همچنان اجرا می‌شود — فقط به هیچ‌جا ارسال نمی‌شود. فیلد last_error را در hermes cron list چک کنید (اگر موجود باشد).

بررسی ۲: بررسی استفاده از [SILENT]

اگر کار کرون‌تان هیچ خروجی‌ای تولید نکند، تحویل سرکوب می‌شود. اگر پاسخ ایجنت شامل نشانگر سکوت کرون یعنی [SILENT] باشد، تحویل سرکوب می‌شود. این رفتار برای کارهای پایش عمدی است — اما مطمئن شوید پرامپت‌تان اشتباهی همه‌چیز را سرکوب نمی‌کند.

از پرامپت‌هایی مثل «فقط اگر چیزی تغییر نکرده بود با [SILENT] پاسخ بده» استفاده کنید. از ایجنت نخواهید که [SILENT] را داخل یک توضیح بلندتر بیاورد، چون کرون آن نشانگر را سیگنال سرکوب می‌داند.

بررسی ۳: مجوزهای توکن پلتفرم

باتِ هر پلتفرم پیام‌رسانی برای دریافت پیام‌ها به مجوزهای خاصی نیاز دارد. اگر تحویل بی‌سروصدا شکست می‌خورد:

  • تلگرام: بات باید در گروه/کانال مقصد ادمین باشد
  • دیسکورد: بات باید مجوز ارسال در کانال مقصد را داشته باشد
  • اسلک: بات باید به ورک‌اسپیس اضافه شده باشد و اسکوپ chat:write را داشته باشد

بررسی ۴: قاب‌بندی پاسخ

به‌صورت پیش‌فرض، پاسخ‌های کرون با یک سرصفحه و پاصفحه قاب‌بندی می‌شوند (cron.wrap_response: true در config.yaml). بعضی پلتفرم‌ها یا یکپارچه‌سازی‌ها ممکن است با این رفتار خوب کنار نیایند. برای غیرفعال‌کردن:

cron:
  wrap_response: false

۳ شکست‌های بارگذاری مهارت

بررسی ۱: مطمئن شوید مهارت‌ها نصب‌اند

hermes skills list

مهارت‌ها باید قبل از اینکه بتوان آن‌ها را به کارهای کرون وصل کرد نصب شده باشند. اگر مهارتی جا افتاده، اول آن را با hermes skills install <skill-name> یا از طریق /skills در CLI نصب کنید.

بررسی ۲: مقایسهٔ نام مهارت با نام پوشهٔ مهارت

نام مهارت‌ها به بزرگی/کوچکی حروف حساس است و باید با نام پوشهٔ مهارتِ نصب‌شده مطابقت داشته باشد. اگر کار شما ai-funding-report را مشخص کرده ولی پوشهٔ مهارت ai-funding-daily-report است، نام دقیق را از hermes skills list تأیید کنید.

بررسی ۳: مهارت‌هایی که به ابزارهای تعاملی نیاز دارند

کارهای کرون با تول‌ست‌های cronjob، messaging و clarifyِ غیرفعال اجرا می‌شوند. این کار جلوی ساخت بازگشتیِ کرون، ارسال مستقیم پیام (تحویل را زمان‌بند انجام می‌دهد) و پرامپت‌های تعاملی را می‌گیرد. اگر مهارتی به این تول‌ست‌ها تکیه کند، در بستر کرون کار نخواهد کرد.

مستندات مهارت را چک کنید تا مطمئن شوید در حالت غیرتعاملی (headless) کار می‌کند.

بررسی ۴: ترتیب چند مهارت

وقتی از چند مهارت استفاده می‌کنید، آن‌ها به ترتیب بارگذاری می‌شوند. اگر مهارت A به زمینهٔ مهارت B وابسته است، مطمئن شوید B اول بارگذاری شود:

/cron add "0 9 * * *" "..." --skill context-skill --skill target-skill

در این مثال، context-skill قبل از target-skill بارگذاری می‌شود.

۴ خطاها و شکست‌های کار

بررسی ۱: خروجی اخیر کار را مرور کنید

اگر کاری اجرا شده و شکست خورده، ممکن است بافت خطا را در این‌ها ببینید:

  1. چتی که کار به آن تحویل می‌دهد (اگر تحویل موفق بوده باشد)
  2. ~/.hermes/logs/agent.log برای پیام‌های زمان‌بند (یا errors.log برای هشدارها)
  3. فرادادهٔ last_run کار از طریق hermes cron list

بررسی ۲: الگوهای رایج خطا

«No such file or directory» برای اسکریپت‌ها
مسیر script باید یک مسیر مطلق باشد (یا نسبی نسبت به پوشهٔ پیکربندی هرمس). بررسی کنید:

ls ~/.hermes/scripts/your-script.py   # باید وجود داشته باشد
hermes cron edit <job_id> --script ~/.hermes/scripts/your-script.py

«Skill not found» هنگام اجرای کار
مهارت باید روی ماشینی که زمان‌بند روی آن اجراست نصب شده باشد. اگر بین ماشین‌ها جابه‌جا می‌شوید، مهارت‌ها خودکار همگام نمی‌شوند — آن‌ها را با hermes skills install <skill-name> دوباره نصب کنید.

کار اجرا می‌شود ولی چیزی تحویل نمی‌دهد
احتمالاً مشکل از مقصد تحویل است (به شکست‌های تحویل در بالا نگاهی بیندازید)، خروجی وجود ندارد، یا پاسخ شامل نشانگر سکوت کرون یعنی [SILENT] است.

کار هنگ می‌کند یا تایم‌اوت می‌شود
زمان‌بند از تایم‌اوت مبتنی بر بی‌تحرکی استفاده می‌کند (پیش‌فرض ۶۰۰ ثانیه، قابل تنظیم با متغیر محیطی HERMES_CRON_TIMEOUT، مقدار 0 برای بی‌نهایت). ایجنت تا وقتی فعالانه ابزار فراخوانی می‌کند می‌تواند اجرا شود — تایمر فقط بعد از بی‌تحرکی ممتد فعال می‌شود. کارهای طولانی‌مدت باید برای جمع‌آوری داده از اسکریپت استفاده کنند و فقط نتیجه را تحویل بدهند.

بررسی ۳: تداخل قفل

زمان‌بند برای جلوگیری از هم‌پوشانی تیک‌ها از قفلِ مبتنی بر فایل استفاده می‌کند. اگر دو نمونه گیت‌وی در حال اجرا باشند (یا یک نشست CLI با گیت‌وی تداخل داشته باشد)، ممکن است کارها به تأخیر بیفتند یا از قلم بیفتند.

پروسه‌های تکراری گیت‌وی را ببندید:

ps aux | grep hermes
# پروسه‌های تکراری را ببندید، فقط یکی را نگه دارید

بررسی ۴: مجوزهای jobs.json

کارها در ~/.hermes/cron/jobs.json ذخیره می‌شوند. اگر این فایل برای کاربر شما خواندنی/نوشتنی نباشد، زمان‌بند بی‌سروصدا شکست می‌خورد:

ls -la ~/.hermes/cron/jobs.json
chmod 600 ~/.hermes/cron/jobs.json   # باید متعلق به کاربر شما باشد

۵ مشکلات کارایی

شروعِ کند کار

هر کار کرون یک نشست AIAgent تازه می‌سازد که ممکن است شامل احراز هویت ارائه‌دهنده و بارگذاری مدل باشد. برای زمان‌بندی‌های حساس به زمان، زمان بافر اضافه کنید (مثلاً 0 8 * * * به‌جای 0 9 * * *).

کارهای هم‌پوشانِ بیش از حد

زمان‌بند کارها را در هر تیک به‌صورت ترتیبی اجرا می‌کند. اگر چند کار هم‌زمان سررسید شوند، پشت سر هم اجرا می‌شوند. برای جلوگیری از تأخیر، زمان‌بندی‌ها را پلکانی کنید (مثلاً 0 9 * * * و 5 9 * * * به‌جای اینکه هر دو در 0 9 * * * باشند).

خروجی حجیم اسکریپت

اسکریپت‌هایی که مگابایت‌ها خروجی می‌ریزند ایجنت را کند می‌کنند و ممکن است به سقف توکن بخورند. در سطح اسکریپت فیلتر/خلاصه کنید — فقط چیزی را خروجی بدهید که ایجنت برای استدلال به آن نیاز دارد.

۶ فرمان‌های تشخیصی

hermes cron list                    # نمایش همهٔ کارها، حالت‌ها و زمان‌های next_run
hermes cron run <job_id>            # زمان‌بندی برای تیک بعدی (برای تست)
hermes cron edit <job_id>           # رفع مشکلات پیکربندی
hermes logs                         # مشاهدهٔ لاگ‌های اخیر هرمس
hermes skills list                  # تأیید مهارت‌های نصب‌شده

۷ کمک بیشتر

اگر این راهنما را کامل انجام داده‌اید و مشکل همچنان باقی است:

  1. کار را با hermes cron run <job_id> اجرا کنید (در تیک بعدی گیت‌وی اجرا می‌شود) و خروجی چت را برای خطاها زیر نظر بگیرید
  2. ~/.hermes/logs/agent.log را برای پیام‌های زمان‌بند و ~/.hermes/logs/errors.log را برای هشدارها چک کنید
  3. در github.com/NousResearch/hermes-agent یک ایشو باز کنید، همراه با:
    • شناسهٔ کار و زمان‌بندی
    • مقصد تحویل
    • آنچه انتظار داشتید در مقایسه با آنچه اتفاق افتاد
    • پیام‌های خطای مرتبط از لاگ‌ها

برای مرجع کامل کرون، به اتوماسیون با Cron و کارهای زمان‌بندی (Cron) نگاهی بیندازید.
