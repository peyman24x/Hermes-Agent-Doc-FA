اجرای LLM های محلی روی مک

این راهنما اجرای یک سرور LLM محلی روی macOS با API ی سازگار-OpenAI را قدم‌به‌قدم نشان می‌دهد. حریم خصوصی کامل، هزینهٔ API صفر و کارایی به‌طرز شگفت‌آوری خوب روی Apple Silicon می‌گیرید.

دو backend را پوشش می‌دهیم:

بک‌اندنصببهترین درقالب
llama.cppbrew install llama.cppسریع‌ترین زمان-تا-اولین-توکن، کش KV ی کوانتیزه برای حافظهٔ کمGGUF
omlxomlx.aiسریع‌ترین تولید توکن، بهینه‌سازی native ی MetalMLX ‏(safetensors)

هر دو نقطهٔ پایانی سازگار-OpenAI ی ‎/v1/chat/completions‎ را expose می‌کنند. هرمس با هر کدام کار می‌کند — فقط به http://localhost:8080 یا http://localhost:8000 اشاره‌اش دهید.

📌

فقط Apple Silicon
این راهنما برای مک‌های Apple Silicon ‏(M1 به بعد) است. مک‌های Intel با llama.cpp کار می‌کنند ولی بدون شتاب‌دهی GPU — کارایی به‌طور قابل توجهی کندتر خواهد بود.

۱ انتخاب مدل

برای شروع، ‏Qwen3.5-9B را توصیه می‌کنیم — مدلی قدرتمند در reasoning که با کوانتیزه‌سازی راحت در ۸ گیگ حافظهٔ یکپارچه یا بیشتر جا می‌شود.

گونهحجم روی دیسکرم لازم ‏(زمینهٔ 128K)بک‌اند
Qwen3.5-9B-Q4_K_M ‏(GGUF)۵٫۳ گیگابایتحدود ۱۰ گیگ با کش KV ی کوانتیزهllama.cpp
Qwen3.5-9B-mlx-lm-mxfp4 ‏(MLX)حدود ۵ گیگابایتحدود ۱۲ گیگomlx

قاعده سرانگشتی حافظه:اندازهٔ مدل + کش KV. مدل 9B با Q4 حدود ۵ گیگ است. کش KV در زمینهٔ 128K با کوانتیزه‌سازی Q4 حدود ۴ تا ۵ گیگ اضافه می‌کند. با کش KV پیش‌فرض ‏(f16) این عدد به حدود ۱۶ گیگ می‌رسد. فلگ‌های کش KV ی کوانتیزه در llama.cpp ترفند کلیدی سیستم‌های کم‌حافظه‌اند.

برای مدل‌های بزرگ‌تر ‏(27B، ‏35B) به ۳۲ گیگ حافظهٔ یکپارچه یا بیشتر نیاز دارید. مدل 9B نقطهٔ طلایی ماشین‌های ۸ تا ۱۶ گیگی است.

۲ گزینهٔ A: llama.cpp

‏llama.cpp پرتابل‌ترین زمان اجرای LLM محلی است. روی macOS از ابتدا از Metal برای شتاب‌دهی GPU استفاده می‌کند.

نصب

brew install llama.cpp

این فرمان llama-server را global می‌دهد.

دانلود مدل

مدلی با قالب GGUF لازم دارید. راحت‌ترین منبع Hugging Face از طریق huggingface-cli است:

brew install huggingface-cli

بعد دانلود کنید:

huggingface-cli download unsloth/Qwen3.5-9B-GGUF Qwen3.5-9B-Q4_K_M.gguf --local-dir ~/models
💡

مدل‌های گیت‌دار:بعضی مدل‌های Hugging Face احراز هویت می‌خواهند. اگر خطای 401 یا 404 گرفتید اول huggingface-cli login را اجرا کنید.

اجرای سرور

llama-server -m ~/models/Qwen3.5-9B-Q4_K_M.gguf \
  -ngl 99 \
  -c 131072 \
  -np 1 \
  -fa on \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  --host 0.0.0.0

کار هر فلگ:

فلگهدف
-ngl 99انتقال همهٔ لایه‌ها به GPU ‏(Metal). عدد بالا بدهید تا چیزی روی CPU نماند.
-c 131072اندازهٔ پنجرهٔ زمینه ‏(۱۲۸ هزار توکن). اگر حافظه کم است کمش کنید.
-np 1تعداد اسلات‌های موازی. برای تک‌کاربر روی ۱ نگه دارید — اسلات بیشتر بودجهٔ حافظه را تقسیم می‌کند.
-fa onFlash attention. مصرف حافظه را کم و استنتاج زمینهٔ بلند را سریع می‌کند.
--cache-type-k q4_0کوانتیزه کردن کلید-کش به ۴ بیتی. این بزرگ‌ترین صرفه‌جوی حافظه است.
--cache-type-v q4_0کوانتیزه کردن مقدار-کش به ۴ بیتی. همراه مورد بالا، حافظهٔ KV cache را نسبت به f16 حدود ۷۵٪ کم می‌کند.
--host 0.0.0.0گوش دادن روی همهٔ اینترفیس‌ها. اگر دسترسی شبکه نمی‌خواهید 127.0.0.1 بگذارید.

سرور وقتی آماده است که این را ببینید:

main: server is listening on http://0.0.0.0:8080
srv  update_slots: all slots are idle

بهینه‌سازی حافظه برای سیستم‌های محدود

فلگ‌های ‎--cache-type-k q4_0 --cache-type-v q4_0‎ مهم‌ترین بهینه‌سازی برای سیستم‌های کم‌حافظه‌اند. اثرشان در زمینهٔ 128K:

نوع کش KVحافظهٔ کش KV ‏(زمینهٔ 128K، مدل 9B)
f16 ‏(پیش‌فرض)حدود ۱۶ گیگابایت
q8_0حدود ۸ گیگابایت
q4_0حدود ۴ گیگابایت

روی مک ۸ گیگی از کش KV ی q4_0 استفاده کنید و مدلی کوچک‌تر بردارید که حداقل زمینهٔ 64K ی هرمس را هنوز جا دهد. روی ۱۶ گیگ راحت می‌توانید زمینهٔ 128K داشته باشید. روی ۳۲ گیگ به بالا می‌توانید مدل بزرگ‌تر یا چند اسلات موازی اجرا کنید.

اگر باز هم حافظه کم آمد، زمینه را فقط تا حداقلِ ۶۴ هزارِ هرمس کم کنید؛ وگرنه به مدل کوچک‌تر یا کوانتیزه‌سازی کوچک‌تر سوئیچ کنید ‏(Q3_K_M به‌جای Q4_K_M).

تستش کنید

curl -s http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3.5-9B-Q4_K_M.gguf",
    "messages": [{"role": "user", "content": "Hello!"}],
    "max_tokens": 50
  }' | jq .choices[0].message.content

گرفتن نام مدل

اگر نام مدل یادتان رفت، نقطهٔ پایانی models را کوئری بزنید:

curl -s http://localhost:8080/v1/models | jq '.data[].id'

۳ گزینهٔ B: MLX از طریق omlx

omlx برنامه‌ای بومی-macOS است که مدل‌های MLX را مدیریت و سرویس می‌کند. ‏MLX فریم‌ورک یادگیری ماشین خودِ اپل است که مخصوصاً برای معماری حافظهٔ یکپارچهٔ Apple Silicon بهینه شده.

نصب

از omlx.ai دانلود و نصب کنید. GUI ی مدیریت مدل و یک سرور داخلی دارد.

دانلود مدل

با برنامهٔ omlx مدل‌ها را مرور و دانلود کنید. عبارت Qwen3.5-9B-mlx-lm-mxfp4 را جستجو و دانلودش کنید. مدل‌ها محلی ذخیره می‌شوند ‏(معمولاً در ~/.omlx/models/).

اجرای سرور

‏omlx به‌طور پیش‌فرض روی http://127.0.0.1:8000 سرویس می‌دهد. از UI برنامه شروعش کنید یا در صورت موجود بودن از CLI.

تستش کنید

curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3.5-9B-mlx-lm-mxfp4",
    "messages": [{"role": "user", "content": "Hello!"}],
    "max_tokens": 50
  }' | jq .choices[0].message.content

فهرست مدل‌های موجود

‏omlx می‌تواند هم‌زمان چند مدل سرویس کند:

curl -s http://127.0.0.1:8000/v1/models | jq '.data[].id'

۴ بنچمارک: llama.cpp در برابر MLX

هر دو بک‌اند روی یک ماشین ‏(Apple M5 Max با ۱۲۸ گیگ حافظهٔ یکپارچه) با همان مدل ‏(Qwen3.5-9B) در سطح کوانتیزه‌سازی مشابه ‏(Q4_K_M برای GGUF و mxfp4 برای MLX) تست شدند. پنج پرامپت متنوع، سه بار اجرای هرکدام، بک‌اندها پشت سر هم تست شدند تا رقابت منابع پیش نیاید.

یعنی چه؟

  • llama.cpp در پردازش پرامپت می‌درخشد — خط لوله flash attention + کش KV ی کوانتیزه اولین توکن را در حدود ۶۶ میلی‌ثانیه می‌دهد. اگر برنامه تعاملی می‌سازید که پاسخ‌دهی حس‌شده مهم است ‏(چت‌بات، autocomplete) این مزیت معناداری است.
  • MLX بعد از راه افتادن حدود ۳۷٪ سریع‌تر توکن تولید می‌کند. برای بارهای دسته‌ای، تولید متن بلند یا هر کاری که زمان کل تکمیل مهم‌تر از تأخیر اولیه است، MLX زودتر تمام می‌کند.
  • هر دو بک‌اند فوق‌العاده یکدست‌اند — پراکندگی بین اجراها ناچیز بود. به این اعداد می‌توانید اعتماد کنید.

۵ اتصال به Hermes

وقتی سرور محلی‌تان بالا بود:

hermes model

گزینهٔ Custom endpoint را انتخاب و مراحل را دنبال کنید. URL پایه و نام مدل را می‌پرسد — مقادیر همان بک‌اندی که بالا راه انداختید را بدهید.

۶ تایم‌اوت‌ها

هرمس نقاط پایانی محلی ‏(localhost، ‏IP های LAN) را خودکار تشخیص می‌دهد و تایم‌اوت‌های استریمش را آزادتر می‌کند. برای بیشتر راه‌اندازی‌ها پیکربندی لازم نیست.

اگر باز هم خطای تایم‌اوت گرفتید ‏(مثلاً زمینه‌های خیلی بزرگ روی سخت‌افزار کند)، تایم‌اوت خواندن استریم را بازنویسی کنید:

# In your .env — raise from the 120s default to 30 minutes
HERMES_STREAM_READ_TIMEOUT=1800
تایم‌اوتپیش‌فرضتنظیم خودکار محلیبازنویسی با متغیر محیطی
خواندن استریم ‏(سطح سوکت)۱۲۰ ثانیهبه ۱۸۰۰ ثانیه بالا می‌رودHERMES_STREAM_READ_TIMEOUT
تشخیص استریم راکد۱۸۰ ثانیهکاملاً غیرفعال می‌شودHERMES_STREAM_STALE_TIMEOUT
فراخوانی API ‏(غیراستریمی)۱۸۰۰ ثانیهتغییری لازم نیستHERMES_API_TIMEOUT

تایم‌اوت خواندن استریم محتمل‌ترین منبع مشکل است — مهلت سطح سوکت برای دریافت chunk بعدی داده است. هنگام prefill روی زمینه‌های بزرگ، مدل‌های محلی ممکن است چند دقیقه هیچ خروجی‌ای نداشته باشند در حالی که پرامپت را پردازش می‌کنند. تشخیص خودکار این را شفاف مدیریت می‌کند.

💡

نوبت اولِ خاموش معمولاً prefill است نه hang:هرمس system prompt و اسکیماهای ابزار را با هر فراخوانی می‌فرستد، پس روی سخت‌افزار کندتر نوبت اول می‌تواند دقیقه‌ها سکوت داشته باشد در حالی که مدل پرامپت را پردازش می‌کند قبل از تولید هر چیز. این کارِ prefill است نه نشست گیرکرده. راه‌حل‌هایی مثل نگه داشتن مدل بار‌شده و کوتاه کردن پرامپت ثابت با hermes prompt-size را در بخش «پاسخ اول کند» راهنمای Ollama محلی ببینید.
