ورود بومی دسکتاپ ‏(RFC 8252)

وقتی برنامهٔ دسکتاپ هرمس به یک گیت‌وی گیت‌دار وصل می‌شود ‏(داشبورد میزبانی‌شده یا خودمیزبانی که پشت یک ارائه‌دهندهٔ OAuth است)، دو راه برای ورود دارد:

  1. ورود بومی ‏(RFC 8252) — برنامه مرورگر واقعی سیستم‌عامل شما را باز می‌کند، شما در مرورگری که از قبل بهش اعتماد دارید تأیید می‌کنید و برنامه توکن‌هایی می‌گیرد که در keychain سیستم‌عامل ذخیره می‌کند. بدون webview جاسازی‌شده، بدون کوکی نشست مرورگر.هر وقت گیت‌وی پشتیبانی کند این حالت پیش‌فرض است.
  2. ورود جاسازی‌شده ‏(جایگزین قدیمی) — برنامه یک پنجرهٔ مرورگر کوچک داخل خودش باز می‌کند و کوکی نشست گیت‌وی را شکار می‌کند. وقتی گیت‌وی نسخهٔ قدیمی‌ای باشد که ورود بومی را تبلیغ نکند خودکار استفاده می‌شود.

شما بین این دو انتخاب نمی‌کنید — برنامه تشخیص می‌دهد گیت‌وی چه چیزی پشتیبانی می‌کند و بهترین را برمی‌دارد. این صفحه توضیح می‌دهد چه اتفاقی می‌افتد و چرا.

۱ چرا ورود بومی

جاسازی مرورگر داخل یک برنامهٔ بومی برای OAuth کاستی‌های شناخته‌شده‌ای دارد: صفحهٔ ورود نشست موجود مرورگر شما را نمی‌بیند ‏(پس credential ها را دوباره تایپ می‌کنید و MFA را دوباره انجام می‌دهید)، مدیرهای رمز و passkey ها اغلب کار نمی‌کنند و برنامه مجبور است کوکی نشست را از یک webview خصوصی بخواند. ‏RFC 8252 ‏(«OAuth 2.0 for Native Apps») بهترین شیوهٔ صنعتی است که از همهٔ این‌ها اجتناب می‌کند: احراز هویت در مرورگر سیستم انجام شود و برنامه توکن‌های مخصوص خودش را بگیرد.

برای خودِ هرمس، ورود بومی یعنی:

  • بدون webview جاسازی‌شده.احراز هویت در Safari / Chrome / Firefox / Edge اتفاق می‌افتد — هرچه استفاده می‌کنید — با ورودها، افزونه‌ها و passkey های دست‌نخوردهٔ شما.
  • بدون کوکی نشست.برنامه یک access token ی OAuth ‏(کوتاه‌عمر) و یک refresh token نگه می‌دارد که در حالت سکون با keychain سیستم‌عامل رمز شده‌اند ‏(safeStorage ی Electron). فراخوانی‌های REST و بلیت‌های WebSocket با هدر Authorization: Bearer احراز هویت می‌شوند نه با شیشهٔ کوکی.

۲ چطور کار می‌کند

Desktop app                Gateway (/auth/native/*)          Nous Portal (IDP)
   │ 1. open loopback 127.0.0.1:<random port>
   │ 2. system browser ─►  /auth/native/authorize
   │    (PKCE challenge)    (starts the normal PKCE login) ─► /oauth/authorize
   │                        ◄──── code ──── /auth/callback ◄──┘
   │                        3. mint one-time gateway code
   │ ◄─ 302 127.0.0.1/cb?code=… ─┘
   │ 4. POST /auth/native/token (code + PKCE verifier)
   │ ◄─ 5. { access_token, refresh_token, expires_at } ───────┘
   │ 6. store in OS keychain; use Bearer for REST + WS tickets

گیت‌وی واسطه‌گری جریان را انجام می‌دهد: نسبت به برنامهٔ دسکتاپ، سرور احراز هویت است و نسبت به تأمین‌کنندهٔ هویت بالادستی ‏(Nous Portal)، یک سرویس‌گیرندهٔ OAuth. این لازم است چون client_id ی بالادستی و redirect URI های مجاز به origin خودِ گیت‌وی مقیدند — برنامهٔ دسکتاپ نمی‌تواند مستقیماً سرویس‌گیرندهٔ Portal باشد. دسکتاپ همچنان تجربهٔ کامل RFC 8252 را می‌گیرد: جفت PKCE مخصوص خودش، ریدایرکت loopback مخصوص خودش و توکن‌هایی که متعلق به خودش است.

‏PKCE ‏(RFC 7636) پرش loopback را محافظت می‌کند: کد یک‌بارمصرف گیت‌وی بدون code verifier بی‌ارزش است و verifier هرگز از برنامه خارج نمی‌شود. کد تک‌مصرف و کوتاه‌عمر است.

۳ تشخیص قابلیت و fallback

دسکتاپ نقطهٔ پایانی عمومی ‎/api/status‎ ی گیت‌وی را می‌خواند که آرایه‌ای به نام auth_flows تبلیغ می‌کند:

مقدار auth_flowsمعنا
["cookie", "native_pkce"]گیت‌وی از ورود بومی پشتیبانی می‌کند ← برنامه از آن استفاده می‌کند
["cookie"]گیت‌وی فقط جریان قدیمی را پشتیبانی می‌کند ← برنامه از webview جاسازی‌شده استفاده می‌کند
(فیلد غایب)گیت‌وی قدیمی ← برنامه از webview جاسازی‌شده استفاده می‌کند

اگر ورود بومی تبلیغ شده ولی به دلیل محلی شکست بخورد — مثلاً یک ابزار امنیتی شنوندهٔ loopback را مسدود کند یا تب مرورگر را ببندید — برنامه خودکار به جریان جاسازی‌شده برمی‌گردد تا همچنان بتوانید وارد شوید.

۴ چرخهٔ حیات توکن

  • Access token: کوتاه‌عمر ‏(چند دقیقه). روی هر فراخوانی REST و هنگام ضرب بلیت WebSocket به‌صورت Authorization: Bearer فرستاده می‌شود.
  • Refresh token: طولانی‌عمرتر، چرخان. وقتی access token نزدیک انقضاست برنامه ‎/auth/native/refresh‎ را صدا می‌زند تا هر دو توکن بچرخند و بعد keychain را به‌روز می‌کند.
  • انقضای پایانی: اگر refresh token مرده باشد ‏(منقضی / لغوشده / استفادهٔ مجدد-تشخیص‌داده‌شده)، برنامه توکن‌های ذخیره‌شده را پاک و یک ورود تازه می‌خواهد.
  • خروج: هم توکن‌های بومی ‏(keychain) و هم هر کوکی نشست قدیمی آن گیت‌وی را پاک می‌کند.

۵ برای اپراتورهای گیت‌وی

ورود بومی روی هر گیت‌وی گیت‌داری که یک ارائه‌دهندهٔ نشست تعاملی ثبت کرده باشد خودکار موجوده. هیچ پیکربندی لازم نیست — مسیرهای ‎/auth/native/*‎ و تبلیغ auth_flows بخشی از زیرسیستم dashboard-auth هستند. ارائه‌دهنده‌های OAuth ‏(مثل ارائه‌دهندهٔ همراه Nous) ریدایرکت IDP ی بالادستی را واسطه‌گری می‌کنند؛ ارائه‌دهنده‌های رمزی ‏(مثل افزونهٔ همراه basic-auth) مرورگر سیستم را به فرم credential ی ‎/login‎ ی گیت‌وی می‌فرستند — همین چیزی است که به مدیرهای رمز سیستم‌عامل ‏(Passwords مک و…) اجازه می‌دهد فرم را autofill کنند؛ چیزی که هیچ webview دسکتاپی نمی‌تواند ارائه دهد. credential های فقط-توکنی ‏(مثل drain) ورود تعاملی نیستند و native_pkce تبلیغ نمی‌کنند.

نقاط پایانی مربوطه ‏(همگی عمومی، bootstrap قبل-از-احراز، مثل مسیرهای OAuth ی موجود ‎/auth/*‎):

  • GET /auth/native/authorize — شروع ورود PKCE ی واسطه‌گری‌شده
  • POST /auth/native/token — تبدیل کد loopback + verifier به توکن‌ها
  • POST /auth/native/refresh — چرخاندن توکن‌ها از refresh token ی برنامه

۶ ببینید نیز

  • OAuth روی SSH / Host های راه‌دور — الگوی callback ی loopback برای OAuth ی ارائه‌دهنده/MCP روی ماشین‌های راه‌دور.
