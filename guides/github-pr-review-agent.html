ایجنت بازبینی PR گیت‌هاب

مشکل: تیم‌تان PR را سریع‌تر از توان بازبینیتان باز می‌کند. PRها روزها منتظر می‌مانند تا چشمی پیدا شود. توسعه‌دهنده‌های جونیور باگ مرج می‌کنند چون هیچ‌کس وقت بررسی نداشته. صبح‌هایتان را صرف به‌روزشدن با دیف‌ها می‌کنید به‌جای ساختن.

راه‌حل: یک ایجنت هوش مصنوعی که شبانه‌روز مخزن‌هایتان را زیر نظر دارد، هر PR تازه را از نظر باگ، مشکلات امنیتی و کیفیت کد بازبینی می‌کند و یک خلاصه برایتان می‌فرستد — تا فقط وقتتان را روی PRهایی بگذارید که واقعاً به قضاوت انسانی نیاز دارند.

چه چیزی می‌سازید:

┌───────────────────────────────────────────────────────────────────┐
│                                                                   │
│   Cron Timer  ──▶  Hermes Agent  ──▶  GitHub API  ──▶  Review     │
│   (every 2h)       + gh CLI           (PR diffs)       delivery   │
│                    + skill                             (Telegram, │
│                    + memory                            Discord,   │
│                                                        local)     │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

این راهنما از کارهای کرون برای پرس‌وجوی دوره‌ای PRها طبق زمان‌بندی استفاده می‌کند — نه سرور لازم دارد نه نقطهٔ پایانی عمومی. پشت NAT و فایروال کار می‌کند.

💡

به‌جایش بازبینی بلادرنگ می‌خواهید؟
اگر یک نقطهٔ پایانی عمومی در دسترس دارید، کامنت‌گذاری خودکار PR گیت‌هاب با وب‌هوک را ببینید — گیت‌هاب وقتی PRها باز یا به‌روز می‌شوند رویدادها را بلافاصله به هرمس push می‌کند.

۱ پیش‌نیازها

  • Hermes Agent نصب شده — راهنمای نصب را ببینید
  • گیت‌وی در حال اجرا برای کارهای کرون: 
    hermes gateway install   # نصب به‌عنوان سرویس
# یا
hermes gateway           # اجرا در پیش‌زمینه
  • GitHub CLI (gh) نصب و احراز هویت شده: 
    # نصب
brew install gh        # macOS
sudo apt install gh    # Ubuntu/Debian

# احراز هویت
gh auth login
  • پیام‌رسانی پیکربندی‌شده (اختیاری) — تلگرام یا دیسکورد
💡

پیام‌رسانی ندارید؟ مشکلی نیست.
از deliver: "local" استفاده کنید تا بازبینی‌ها در ~/.hermes/cron/output/ ذخیره شوند. عالی برای تست قبل از وصل‌کردن اعلان‌ها.

۲ گام ۱: تأیید راه‌اندازی

مطمئن شوید هرمس می‌تواند به گیت‌هاب دسترسی داشته باشد. یک گفتگو شروع کنید:

hermes

با یک فرمان ساده تست کنید:

Run: gh pr list --repo NousResearch/hermes-agent --state open --limit 3

باید فهرستی از PRهای باز ببینید. اگر این کار کرد، آماده‌اید.

۳ گام ۲: امتحان یک بازبینی دستی

همچنان در همان گفتگو، از هرمس بخواهید یک PR واقعی را بازبینی کند:

Review this pull request. Read the diff, check for bugs, security issues,
and code quality. Be specific about line numbers and quote problematic code.

Run: gh pr diff 3888 --repo NousResearch/hermes-agent

هرمس این کارها را می‌کند:

  1. gh pr diff را اجرا می‌کند تا تغییرات کد را بگیرد
  2. کل دیف را می‌خواند
  3. یک بازبینی ساخت‌یافته با یافته‌های مشخص تولید می‌کند

اگر از کیفیت راضی هستید، وقت اتوماتیک‌کردنش است.

۴ گام ۳: ساخت مهارت بازبینی

یک مهارت به هرمس رهنمودهای بازبینیِ یکدستی می‌دهد که در طول نشست‌ها و اجراهای کرون باقی می‌مانند. بدون آن، کیفیت بازبینی نوسان دارد.

mkdir -p ~/.hermes/skills/code-review

فایل ~/.hermes/skills/code-review/SKILL.md را بسازید:

name: code-review
description: Review pull requests for bugs, security issues, and code quality

# Code Review Guidelines

When reviewing a pull request:

## What to Check
1. **Bugs** — Logic errors, off-by-one, null/undefined handling
2. **Security** — Injection, auth bypass, secrets in code, SSRF
3. **Performance** — N+1 queries, unbounded loops, memory leaks
4. **Style** — Naming conventions, dead code, missing error handling
5. **Tests** — Are changes tested? Do tests cover edge cases?

## Output Format
For each finding:
- **File:Line** — exact location
- **Severity** — Critical / Warning / Suggestion
- **What's wrong** — one sentence
- **Fix** — how to fix it

## Rules
- Be specific. Quote the problematic code.
- Don't flag style nitpicks unless they affect readability.
- If the PR looks good, say so. Don't invent problems.
- End with: APPROVE / REQUEST_CHANGES / COMMENT

تأیید کنید بارگذاری شده — hermes را اجرا کنید و باید code-review را در فهرست مهارت‌ها هنگام شروع ببینید.

۵ گام ۴: قراردادهایتان را به آن یاد بدهید

این چیزی است که بازبین را واقعاً مفید می‌کند. یک نشست شروع کنید و استانداردهای تیم‌تان را به هرمس یاد بدهید:

Remember: In our backend repo, we use Python with FastAPI.
All endpoints must have type annotations and Pydantic models.
We don't allow raw SQL — only SQLAlchemy ORM.
Test files go in tests/ and must use pytest fixtures.
Remember: In our frontend repo, we use TypeScript with React.
No `any` types allowed. All components must have props interfaces.
We use React Query for data fetching, never useEffect for API calls.

این حافظه‌ها برای همیشه می‌مانند — بازبین قراردادهایتان را بدون اینکه هر بار یادآوری کنید اجرا می‌کند.

۶ گام ۵: ساخت کار کرون خودکار

حالا همه را به هم وصل کنید. یک کار کرون بسازید که هر ۲ ساعت اجرا شود:

hermes cron create "0 */2 * * *" \
  "Check for new open PRs and review them.

Repos to monitor:
- myorg/backend-api
- myorg/frontend-app

Steps:
1. Run: gh pr list --repo REPO --state open --limit 5 --json number,title,author,createdAt
2. For each PR created or updated in the last 4 hours:
   - Run: gh pr diff NUMBER --repo REPO
   - Review the diff using the code-review guidelines
3. Format output as:

## PR Reviews — today

### [repo] #[number]: [title]
**Author:** [name] | **Verdict:** APPROVE/REQUEST_CHANGES/COMMENT
[findings]

If no new PRs found, say: No new PRs to review." \
  --name "pr-review" \
  --deliver telegram \
  --skill code-review

تأیید کنید زمان‌بندی شده:

hermes cron list

زمان‌بندی‌های مفید دیگر

زمان‌بندیکِی
0 */2 * * *هر ۲ ساعت
0 9,13,17 * * 1-5سه بار در روز، فقط روزهای هفته
0 9 * * 1جمع‌بندی هفتگی، صبح دوشنبه
30mهر ۳۰ دقیقه (مخازن پرترافیک)

۷ گام ۶: اجرای درخواستی

نمی‌خواهید منتظر زمان‌بندی بمانید؟ دستی اجرایش کنید:

hermes cron run pr-review

یا از داخل یک نشست گفتگو:

/cron run pr-review

۸ فراتر بروید

پست‌کردن بازبینی‌ها مستقیم در گیت‌هاب

به‌جای تحویل به تلگرام، بگذارید ایجنت روی خود PR کامنت بگذارد:

این را به پرامپت کرونتان اضافه کنید:

After reviewing, post your review:
- For issues: gh pr review NUMBER --repo REPO --comment --body "YOUR_REVIEW"
- For critical issues: gh pr review NUMBER --repo REPO --request-changes --body "YOUR_REVIEW"
- For clean PRs: gh pr review NUMBER --repo REPO --approve --body "Looks good"
⛔

مطمئن شوید gh توکنی با اسکوپ repo دارد. بازبینی‌ها به نام هر کسی که gh با آن احراز هویت شده پست می‌شوند.

داشبورد هفتگی PR

یک نمای کلیِ صبح دوشنبه از همهٔ مخزن‌هایتان بسازید:

hermes cron create "0 9 * * 1" \
  "Generate a weekly PR dashboard:
- myorg/backend-api
- myorg/frontend-app
- myorg/infra

For each repo show:
1. Open PR count and oldest PR age
2. PRs merged this week
3. Stale PRs (older than 5 days)
4. PRs with no reviewer assigned

Format as a clean summary." \
  --name "weekly-dashboard" \
  --deliver telegram

پایش چندمخزنی

با افزودن مخزن‌های بیشتر به پرامپت مقیاس بدهید. ایجنت آن‌ها را ترتیبی پردازش می‌کند — راه‌اندازی اضافه‌ای لازم نیست.

۹ عیب‌یابی

«gh: command not found»

گیت‌وی در یک محیط مینیمال اجرا می‌شود. مطمئن شوید gh در PATH سیستم است و گیت‌وی را ری‌استارت کنید.

بازبینی‌ها بیش از حد کلی‌اند

  1. مهارت code-review را اضافه کنید (گام ۳)
  2. قراردادهایتان را با حافظه به هرمس یاد بدهید (گام ۴)
  3. هرچه زمینهٔ بیشتری دربارهٔ استکتان داشته باشد، بازبینی‌ها بهتر می‌شوند

کار کرون اجرا نمی‌شود

hermes gateway status    # آیا گیت‌وی در حال اجراست؟
hermes cron list         # آیا کار فعال است؟

محدودیت‌های نرخ

گیت‌هاب به کاربران احراز-هویت‌شده ۵٬۰۰۰ درخواست API در ساعت می‌دهد. هر بازبینی PR حدود ۳ تا ۵ درخواست مصرف می‌کند (لیست + دیف + کامنت‌های اختیاری). حتی بازبینی ۱۰۰ PR در روز خیلی راحت داخل محدودیت‌ها می‌ماند.

۱۰ قدم‌های بعدی

  • بازبینی‌های PR مبتنی بر وب‌هوک — وقتی PRها باز می‌شوند بازبینی فوری بگیرید (به نقطهٔ پایانی عمومی نیاز دارد)
  • بات خلاصهٔ روزانه — بازبینی‌های PR را با خلاصهٔ اخبار صبحتان ترکیب کنید
  • ساخت پلاگین — منطق بازبینی را در یک پلاگین قابل‌اشتراک بسته‌بندی کنید
  • پروفایل‌ها — یک پروفایل بازبینِ اختصاصی با حافظه و پیکربندی مخصوص خودش اجرا کنید
  • ارائه‌دهندگان پشتیبان — مطمئن شوید بازبینی‌ها حتی وقتی یک ارائه‌دهنده از دسترس خارج شد اجرا می‌شوند
