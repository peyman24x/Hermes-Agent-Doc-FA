کامنت خودکار PR با وب‌هوک

این راهنما اتصال Hermes Agent به GitHub را قدم‌به‌قدم نشان می‌دهد تا ایجنت به‌طور خودکار diff یک pull request را بگیرد، تغییرات کد را تحلیل کند و یک کامنت بگذارد — با یک رویداد وب‌هوک فعال می‌شود و هیچ پرامپت دستی لازم نیست.

وقتی PR ای باز یا به‌روز می‌شود، GitHub یک درخواست POST وب‌هوک به نمونهٔ هرمس شما می‌فرستد. هرمس ایجنت را با پرامپتی اجرا می‌کند که به آن می‌گوید diff را از طریق CLI ‏gh بگیرد، و پاسخ در رشتهٔ همان PR پست می‌شود.

💡 دنبال راه‌اندازی ساده‌تر بدون نقطهٔ پایانی عمومی هستید؟

اگر URL عمومی ندارید یا فقط می‌خواهید سریع شروع کنید، راهنمای ایجنت بازبینی PR گیت‌هاب را ببینید — از کارهای کرون برای بررسی دوره‌ای PRها طبق زمان‌بندی استفاده می‌کند و پشت NAT و فایروال هم کار می‌کند.

ℹ️ مستندات مرجع

برای مرجع کامل پلتفرم وب‌هوک (همهٔ گزینه‌های پیکربندی، انواع تحویل، اشتراک‌های پویا، مدل امنیتی) وب‌هوک‌ها را ببینید.

⚠️ ریسک تزریق پرامپت

بارهای وب‌هوک داده‌ای دارند که مهاجم کنترلشان می‌کند — عنوان PR، پیام‌های commit و توضیحات می‌توانند دستورالعمل مخرب داشته باشند. وقتی نقطهٔ پایانی وب‌هوک شما در معرض اینترنت است، گیت‌وی را در محیط سندباکس‌شده اجرا کنید (Docker، بک‌اند SSH). بخش نکات امنیتی در پایین را ببینید.

۱ پیش‌نیازها

  • Hermes Agent نصب و در حال اجرا باشد (‏hermes gateway)
  • CLI ‏gh روی میزبان گیت‌وی نصب و احراز هویت شده باشد (‏gh auth login)
  • یک URL با دسترسی عمومی برای نمونهٔ هرمس شما (اگر محلی اجرا می‌کنید آزمایش محلی با ngrok را ببینید)
  • دسترسی مدیر به مخزن GitHub (برای مدیریت وب‌هوک‌ها لازم است)

۲ گام ۱ — فعال کردن پلتفرم وب‌هوک

موارد زیر را به ‏~/.hermes/config.yaml اضافه کنید:

platforms:
  webhook:
    enabled: true
    extra:
      port: 8644          # default; change if another service occupies this port
      rate_limit: 30      # max requests per minute per route (not a global cap)

      routes:
        github-pr-review:
          secret: "your-webhook-secret-here"   # must match the GitHub webhook secret exactly
          events:
            - pull_request

          # The agent is instructed to fetch the actual diff before reviewing.
          # {number} and {repository.full_name} are resolved from the GitHub payload.
          prompt: |
            A pull request event was received (action: {action}).

            PR #{number}: {pull_request.title}
            Author: {pull_request.user.login}
            Branch: {pull_request.head.ref} → {pull_request.base.ref}
            Description: {pull_request.body}
            URL: {pull_request.html_url}

            If the action is "closed" or "labeled", stop here and do not post a comment.

            Otherwise:
            1. Run: gh pr diff {number} --repo {repository.full_name}
            2. Review the code changes for correctness, security issues, and clarity.
            3. Write a concise, actionable review comment and post it.

          deliver: github_comment
          deliver_extra:
            repo: "{repository.full_name}"
            pr_number: "{number}"

فیلدهای کلیدی:

فیلدتوضیح
‏secret (سطح مسیر)رمز HMAC برای این مسیر. اگر حذف شود به ‏extra.secret سراسری برمی‌گردد.
‏eventsفهرست مقادیر هدر ‏X-GitHub-Event که پذیرفته می‌شوند. فهرست خالی = پذیرش همه.
‏promptقالب؛ ‏{field} و ‏{nested.field} از بار GitHub جایگذاری می‌شوند.
‏deliver‏github_comment از طریق ‏gh pr comment پست می‌کند. ‏log فقط در لاگ گیت‌وی می‌نویسد.
‏deliver_extra.repoاز بار به مثلاً ‏org/repo حل می‌شود.
‏deliver_extra.pr_numberبه شمارهٔ PR از بار حل می‌شود.
ℹ️ بار شامل کد نیست

بار وب‌هوک GitHub فرادادهٔ PR را شامل می‌شود (عنوان، توضیحات، نام شاخه‌ها، URLها) اما diff را نه. پرامپت بالا به ایجنت می‌گوید ‏gh pr diff را اجرا کند تا تغییرات واقعی را بگیرد. تول‌ست پیش‌فرض ‏hermes-webhook عمداً محدود نگه داشته شده (جستجو/استخراج وب، بینایی، روشن‌سازی — بدون ترمینال) چون بارهای وب‌هوک می‌توانند محتوای غیرقابل‌اعتماد حمل کنند. برای این‌که این مسیر بتواند ‏gh را اجرا کند، یک مجوز تول‌ست در سطح مسیر اضافه کنید: ‏toolsets: ["terminal", "web"] در پیکربندی مسیر — تول‌ست‌های مخصوص هر مسیر را ببینید.

۳ گام ۲ — راه‌اندازی گیت‌وی

hermes gateway

باید این را ببینید:

[webhook] Listening on 0.0.0.0:8644 — routes: github-pr-review

بررسی کنید که در حال اجراست:

curl http://localhost:8644/health
# {"status": "ok", "platform": "webhook"}

۴ گام ۳ — ثبت وب‌هوک در GitHub

  1. به مخزن خود بروید ← ‏Settings ← ‏Webhooks ← ‏Add webhook
  2. این‌ها را پر کنید:
    • ‏Payload URL: ‏https://your-public-url.example.com/webhooks/github-pr-review
    • ‏Content type: ‏application/json
    • ‏Secret: همان مقداری که برای ‏secret در پیکربندی مسیر ست کرده‌اید
    • ‏Which events? ← انتخاب «رویدادهای مجزا» ← تیک ‏Pull requests
  3. روی ‏Add webhook کلیک کنید

‏GitHub بلافاصله برای تأیید اتصال یک رویداد ‏ping می‌فرستد. این رویداد بی‌خطر نادیده گرفته می‌شود — ‏ping در فهرست ‏events شما نیست — و ‏{"status": "ignored", "event": "ping"} برمی‌گرداند. فقط در سطح DEBUG لاگ می‌شود، پس در کنسول با سطح لاگ پیش‌فرض دیده نمی‌شود.

۵ گام ۴ — باز کردن یک PR آزمایشی

یک شاخه بسازید، یک تغییر push کنید و یک PR باز کنید. ظرف ۳۰ تا ۹۰ ثانیه (بسته به حجم PR و مدل)، هرمس باید یک کامنت بازبینی بگذارد.

برای دنبال کردن پیشرفت ایجنت به‌صورت زنده:

tail -f "${HERMES_HOME:-$HOME/.hermes}/logs/gateway.log"

۶ آزمایش محلی با ngrok

اگر هرمس روی لپ‌تاپ شما اجرا می‌شود، با ngrok آن را در دسترس بیرون بگذارید:

ngrok http 8644

URL ‏https://...ngrok-free.app را کپی کنید و به‌عنوان Payload URL در GitHub استفاده کنید. در پلن رایگان ngrok هر بار که ngrok ری‌استارت شود URL عوض می‌شود — هر نشست، وب‌هوک GitHub خود را به‌روز کنید. حساب‌های پولی ngrok دامنهٔ ثابت می‌گیرند.

می‌توانید یک مسیر استاتیک را مستقیم با ‏curl آزمون اولیه بگیرید — نه حساب GitHub لازم است نه PR واقعی.

💡 هنگام آزمایش محلی از ‏deliver: log استفاده کنید

حین آزمایش در پیکربندی‌تان ‏deliver: github_comment را به ‏deliver: log تغییر دهید. وگرنه ایجنت تلاش می‌کند برای مخزن جعلی ‏org/repo#99 در بار آزمایشی کامنت بگذارد و شکست می‌خورد. وقتی از خروجی پرامپت راضی شدید، به ‏deliver: github_comment برگردید.

SECRET="your-webhook-secret-here"
BODY='{"action":"opened","number":99,"pull_request":{"title":"Test PR","body":"Adds a feature.","user":{"login":"testuser"},"head":{"ref":"feat/x"},"base":{"ref":"main"},"html_url":"https://github.com/org/repo/pull/99"},"repository":{"full_name":"org/repo"}}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | awk '{print "sha256="$2}')

curl -s -X POST http://localhost:8644/webhooks/github-pr-review \
  -H "Content-Type: application/json" \
  -H "X-GitHub-Event: pull_request" \
  -H "X-Hub-Signature-256: $SIG" \
  -d "$BODY"
# Expected: {"status":"accepted","route":"github-pr-review","event":"pull_request","delivery_id":"..."}

بعد تماشا کنید که ایجنت اجرا می‌شود:

tail -f "${HERMES_HOME:-$HOME/.hermes}/logs/gateway.log"
ℹ️

‏hermes webhook test <name> فقط برای اشتراک‌های پویا کار می‌کند که با ‏hermes webhook subscribe ساخته شده‌اند. مسیرها را از ‏config.yaml نمی‌خواند.

۷ فیلتر کردن روی اکشن‌های خاص

‏GitHub برای اکشن‌های زیادی رویداد ‏pull_request می‌فرستد: ‏opened، ‏synchronize، ‏reopened، ‏closed، ‏labeled و غیره. فهرست ‏events بر اساس مقدار هدر ‏X-GitHub-Event فیلتر می‌کند و ‏filters در سطح مسیر می‌تواند بر اساس فیلدهای بار مثل ‏action محدودترش کند.

پرامپت در گام ۱ همین را از قبل مدیریت می‌کند و به ایجنت می‌گوید برای رویدادهای ‏closed و ‏labeled زودتر متوقف شود.

⚠️ ایجنت همچنان اجرا می‌شود و توکن مصرف می‌کند

دستورالعمل «اینجا متوقف شو» جلوی یک بازبینی معنادار را می‌گیرد، اما ایجنت برای هر رویداد ‏pull_request فارغ از اکشن همچنان تا اتمام اجرا می‌شود. بهتر است پیش از بیدار شدن ایجنت فیلتر کنید:

filters:
  - field: "action"
    in: ["opened", "synchronize", "reopened"]

برای مخازن پربازدید، همچنان می‌توانید بالادست با یک گردش‌کار GitHub Actions که به‌شرط URL وب‌هوک شما را صدا می‌زند فیلتر کنید.

هیچ سینتکس قالب‌بندی شرطی یا Jinja2 وجود ندارد. ‏{field} و ‏{nested.field} تنها جایگزینی‌های پشتیبانی‌شده‌اند. هر چیز دیگری عیناً به ایجنت پاس داده می‌شود.

۸ استفاده از مهارت برای سبک بازبینی یکدست

یک مهارت هرمس بارگذاری کنید تا به ایجنت شخصیت بازبینی یکدستی بدهید. ‏skills را به مسیر خود داخل ‏platforms.webhook.extra.routes در ‏config.yaml اضافه کنید:

platforms:
  webhook:
    enabled: true
    extra:
      routes:
        github-pr-review:
          secret: "your-webhook-secret-here"
          events: [pull_request]
          prompt: |
            A pull request event was received (action: {action}).
            PR #{number}: {pull_request.title} by {pull_request.user.login}
            URL: {pull_request.html_url}

            If the action is "closed" or "labeled", stop here and do not post a comment.

            Otherwise:
            1. Run: gh pr diff {number} --repo {repository.full_name}
            2. Review the diff using your review guidelines.
            3. Write a concise, actionable review comment and post it.
          skills:
            - review
          deliver: github_comment
          deliver_extra:
            repo: "{repository.full_name}"
            pr_number: "{number}"

توجه: فقط اولین مهارتِ یافت‌شده در فهرست بارگذاری می‌شود. هرمس چند مهارت را روی هم سوار نمی‌کند — مدخل‌های بعدی نادیده گرفته می‌شوند.

۹ ارسال پاسخ‌ها به Slack یا Discord به‌جای آن

فیلدهای ‏deliver و ‏deliver_extra داخل مسیر خود را با پلتفرم مقصدتان عوض کنید:

# Inside platforms.webhook.extra.routes.<route-name>:

# Slack
deliver: slack
deliver_extra:
  chat_id: "C0123456789"   # Slack channel ID (omit to use the configured home channel)

# Discord
deliver: discord
deliver_extra:
  chat_id: "987654321012345678"  # Discord channel ID (omit to use home channel)

پلتفرم مقصد هم باید در گیت‌وی فعال و متصل باشد. اگر ‏chat_id حذف شود، پاسخ به کانال خانگی پیکربندی‌شدهٔ آن پلتفرم فرستاده می‌شود.

مقادیر معتبر ‏deliver: ‏log · ‏github_comment · ‏telegram · ‏discord · ‏slack · ‏signal · ‏sms

۱۰ پشتیبانی GitLab

همان آداپتور با GitLab هم کار می‌کند. GitLab برای احراز هویت از ‏X-Gitlab-Token استفاده می‌کند (مقایسهٔ رشتهٔ ساده، نه HMAC) — هرمس هر دو را خودکار مدیریت می‌کند.

برای فیلتر رویدادها، GitLab مقدار ‏X-GitLab-Event را مقادیری مثل ‏Merge Request Hook، ‏Push Hook، ‏Pipeline Hook ست می‌کند. مقدار دقیق هدر را در ‏events استفاده کنید:

events:
  - Merge Request Hook

فیلدهای بار GitLab با GitHub فرق دارد — مثلاً ‏{object_attributes.title} برای عنوان MR و ‏{object_attributes.iid} برای شمارهٔ MR. ساده‌ترین راه کشف ساختار کامل بار، دکمهٔ ‏Test در تنظیمات وب‌هوک GitLab است همراه با لاگ ‏Recent Deliveries. راه دیگر این‌که ‏prompt را از پیکربندی مسیر حذف کنید — هرمس در این حالت کل بار را به‌صورت JSON قالب‌بندی‌شده مستقیم به ایجنت می‌دهد و پاسخ ایجنت (که در لاگ گیت‌وی با ‏deliver: log دیده می‌شود) ساختار آن را توضیح می‌دهد.

۱۱ نکات امنیتی

  • هرگز در production از ‏INSECURE_NO_AUTH استفاده نکنید — اعتبارسنجی امضا را کاملاً غیرفعال می‌کند. فقط برای توسعهٔ محلی است.
  • رمز وب‌هوک‌تان را دوره‌ای عوض کنید و هم در GitHub (تنظیمات وب‌هوک) و هم در ‏config.yaml به‌روزرسانی‌اش کنید.
  • محدودیت نرخ به‌صورت پیش‌فرض ۳۰ درخواست در دقیقه برای هر مسیر است (از طریق ‏extra.rate_limit قابل تنظیم). عبور از آن ‏429 برمی‌گرداند.
  • تحویل‌های تکراری (ریترای وب‌هوک) از طریق یک کش idempotency یک‌ساعته حذف‌تکرار می‌شوند. کلید کش در صورت وجود ‏X-GitHub-Delivery است، بعد ‏X-Request-ID، و بعد یک timestamp میلی‌ثانیه‌ای. وقتی هیچ‌کدام از هدرهای شناسهٔ تحویل ست نشده باشند، ریترای‌ها حذف‌تکرار نمی‌شوند.
  • تزریق پرامپت: عنوان‌های PR، توضیحات و پیام‌های commit کنترلِ مهاجم‌اند. PRهای مخرب می‌توانند تلاش کنند اقدامات ایجنت را دستکاری کنند. وقتی در معرض اینترنت عمومی است، گیت‌وی را در محیط سندباکس‌شده (Docker، VM) اجرا کنید.

۱۲ عیب‌یابی

نشانهبررسی
‏401 Invalid signatureرمز در config.yaml با رمز وب‌هوک GitHub مطابقت ندارد
‏404 Unknown routeنام مسیر در URL با کلید داخل ‏routes: مطابقت ندارد
‏429 Rate limit exceededعبور از ۳۰ درخواست در دقیقه برای هر مسیر — رایج هنگام تحویل دوبارهٔ رویدادهای آزمایشی از UI گیت‌هاب؛ یک دقیقه صبر کنید یا ‏extra.rate_limit را بالا ببرید
کامنتی پست نشد‏gh نصب نیست، روی PATH نیست یا احراز هویت نشده است (‏gh auth login)
ایجنت اجرا می‌شود ولی کامنتی نیستلاگ گیت‌وی را چک کنید — اگر خروجی ایجنت خالی یا فقط «SKIP» بوده باشد، تحویل همچنان تلاش می‌شود
پورت در حال استفاده است‏extra.port را در config.yaml عوض کنید
ایجنت اجرا می‌شود ولی فقط توضیحات PR را بازبینی می‌کندپرامپت دستورالعمل ‏gh pr diff را شامل نمی‌شود — diff داخل بار وب‌هوک نیست

تب Recent Deliveries در GitHub (repo ← Settings ← Webhooks ← وب‌هوک شما) هدرهای دقیق درخواست، بار، وضعیت HTTP و بدنهٔ پاسخ هر تحویل را نشان می‌دهد. سریع‌ترین راه عیب‌یابی شکست‌ها بدون سرک کشیدن به لاگ‌های سرورتان است.

۱۳ مرجع کامل پیکربندی

platforms:
  webhook:
    enabled: true
    extra:
      port: 8644               # listen port (default: 8644)
      secret: ""               # optional global fallback secret
      rate_limit: 30           # requests per minute per route
      max_body_bytes: 1048576  # payload size limit in bytes (default: 1 MB)

      routes:
        <route-name>:
          secret: "required-per-route"
          events: []            # [] = accept all; otherwise list X-GitHub-Event values
          prompt: ""            # {field} / {nested.field} resolved from payload
          skills: []            # first matching skill is loaded (only one)
          deliver: "log"        # log | github_comment | telegram | discord | slack | signal | sms
          deliver_extra: {}     # repo + pr_number for github_comment; chat_id for others

۱۴ قدم بعدی؟

  • بازبینی PR مبتنی بر کرون — بررسی دوره‌ای PRها طبق زمان‌بندی، بدون نیاز به نقطهٔ پایانی عمومی
  • مرجع وب‌هوک — مرجع کامل پیکربندی پلتفرم وب‌هوک
  • ساخت پلاگین — بسته‌بندی منطق بازبینی در یک پلاگین قابل‌هم‌رسانی
  • پروفایل‌ها — اجرای یک پروفایل بازبین اختصاصی با حافظه و پیکربندی خودش
