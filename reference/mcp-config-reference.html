مرجع پیکربندی MCP

این صفحه، مرجع فشردهٔ همراه مستندات اصلی MCP است.

برای راهنمایی مفهومی، این صفحات را ببینید:

  • MCP (پروتکل زمینهٔ مدل)
  • استفاده از MCP با هرمس

۱ ساختار پیکربندی ریشه

mcp_servers:
  <server_name>:
    command: "..."      # stdio servers
    args: []
    env: {}

    # OR
    url: "..."          # HTTP servers
    headers: {}

    # Optional HTTP/SSE TLS settings:
    ssl_verify: true                # bool or path to a CA bundle (PEM)
    client_cert: "/path/to/cert.pem"  # mTLS client certificate (see below)
    # client_key: "/path/to/key.pem"  # optional, when key lives in a separate file

    enabled: true
    timeout: 120
    connect_timeout: 60
    supports_parallel_tool_calls: false
    tools:
      include: []
      exclude: []
      resources: true
      prompts: true

۲ کلیدهای سرور

کلیدنوعکاربرد درمعنا
commandرشتهstdioفایل اجرایی برای راه‌اندازی
argsفهرستstdioآرگومان‌های زیرفرایند
envنگاشتstdioمحیطی که به زیرفرایند داده می‌شود
urlرشتهHTTPنقطهٔ پایانی MCP از راه دور
headersنگاشتHTTPسرآیندهای درخواست‌های سرور از راه دور
ssl_verifyبولی یا رشتهHTTPاعتبارسنجی TLS. مقدار true (پیش‌فرض) از مراجع صدور گواهی سیستم استفاده می‌کند؛ false اعتبارسنجی را غیرفعال می‌کند (ناامن است)؛ یا می‌توان مسیر رشته‌ای به بستهٔ سفارشی گواهی‌های CA با قالب PEM داد.
client_certرشته یا فهرستHTTPگواهی کلاینت mTLS. رشته = مسیر فایل PEM شامل گواهی و کلید. فهرست [cert, key] = فایل‌های جداگانه. فهرست [cert, key, password] = کلید رمزگذاری‌شده.
client_keyرشتهHTTPمسیر کلید خصوصی کلاینت، وقتی client_cert رشته است و کلید در فایلی جداگانه قرار دارد
enabledبولیهر دووقتی مقدار آن false باشد، سرور به‌کلی نادیده گرفته می‌شود
timeoutعددهر دومهلت فراخوانی ابزار بر حسب ثانیه (پیش‌فرض: 300)
connect_timeoutعددهر دومهلت اتصال اولیه بر حسب ثانیه (پیش‌فرض: 60)
protocolرشتههر دومذاکره برای تعیین نسل پروتکل: auto (پیش‌فرض — ابتدا دست‌دهی قدیمی initialize؛ اگر سرور به‌دلیل پشتیبانی انحصاری از پروتکل مدرن آن را رد کند، به کاوش بدون حالت server/discover مربوط به نسخهٔ 2026-07-28 برمی‌گردد)، stateless (ابتدا کاوش server/discover؛ یک تلاش مجدد با روش قدیمی)، یا legacy (فقط دست‌دهی، بدون روش پشتیبان)
supports_parallel_tool_callsبولیهر دواجازهٔ اجرای هم‌زمان ابزارهای این سرور
skip_preflightبولیHTTPردکردن کاوش نوع محتوا با رویکرد تشخیص سریع خطا، برای نقاط پایانی معتبر Streamable HTTP که پاسخ HEAD/GET آن‌ها نوع محتوای غیر MCP دارد (پیش‌فرض: false)
transportرشتهHTTPبرای استفاده از انتقال SSE به‌جای Streamable HTTP، آن را روی sse بگذارید
keepalive_intervalعددهر دوفاصلهٔ زمانی پینگ بررسی زنده‌بودن، بر حسب ثانیه (پیش‌فرض: 180، با حداقل ۵ ثانیه). برای سرورهایی که نشست‌های بیکار را زود پاک‌سازی می‌کنند، این مقدار را کمتر از زمان اعتبار (TTL) نشست سرور قرار دهید.
lazyبولیهر دوهنگام شروع، ابزارهای سرور را از کش اسکیمای روی دیسک ثبت می‌کند و فقط هنگام نخستین فراخوانی ابزار، سرور را راه‌اندازی می‌کند یا به آن متصل می‌شود (پیش‌فرض: false). برای پرشدن کش به یک اتصال زندهٔ قبلی نیاز دارد؛ اگر ورودی کش موجود نباشد یا کهنه باشد، به اتصال معمولِ فوری برمی‌گردد. تا نخستین استفاده، نماهای وضعیت، سرور را با وضعیت lazy و تعداد ابزارهای کش‌شدهٔ آن نشان می‌دهند.
idle_timeout_secondsعددstdioراه‌اندازی مجدد اختیاری سرور stdio پس از مدت بیکاری (0 آن را غیرفعال می‌کند). می‌تواند زیر نگاشت lifecycle: هم قرار بگیرد.
max_lifetime_secondsعددstdioراه‌اندازی مجدد اختیاری سرور stdio پس از گذشت طول عمر تعیین‌شده (0 آن را غیرفعال می‌کند). می‌تواند زیر نگاشت lifecycle: هم قرار بگیرد.
toolsنگاشتهر دوفیلترکردن و سیاست ابزارهای کمکی
authرشتهHTTPروش احراز هویت. برای فعال‌کردن OAuth 2.1 همراه با PKCE، مقدار oauth را تنظیم کنید.
samplingنگاشتهر دوسیاست درخواست‌های LLM که سرور آغاز می‌کند (راهنمای MCP را ببینید)
elicitationنگاشتهر دودرخواست‌های دریافت ورودی از کاربر که سرور آغاز می‌کند. شامل enabled (پیش‌فرض true) و timeout بر حسب ثانیه (پیش‌فرض 300). درخواست‌های حالت فرم از رابط تأیید عبور می‌کنند؛ حالت URL رد می‌شود (راهنمای MCP را ببینید).
trustرشتههر دوسطح اعتماد: full (پیش‌فرض) یا untrusted. در سرور untrusted، هر فراخوانی ابزاری که قابلیت نوشتن دارد (هر ابزاری بدون حاشیه‌نویسی readOnlyHint: true) پیش از اجرا به تأیید کاربر از طریق رابط استاندارد تأیید نیاز دارد. readOnlyHint یک راهنما است که سرور ارائه می‌کند — سرور دروغ‌گو در بدترین حالت می‌تواند تأیید ابزارهایی را که فقط‌خواندنی معرفی می‌کند دور بزند، اما هرگز دسترسی بیشتری به دست نمی‌آورد — بنابراین هر سروری را که کاملاً تحت کنترل شما نیست، untrusted علامت بزنید. همین راهنما تعیین می‌کند که آیا پس از انقضای نشست انتقال در میانهٔ فراخوانی، آن فراخوانی به‌طور شفاف دوباره تلاش شود یا نه: فقط ابزارهای دارای readOnlyHint: true دوباره اجرا می‌شوند؛ ابزارهای بدون حاشیه‌نویسی (با قابلیت نوشتن) خطای outcome_uncertain برمی‌گردانند — در سرور Streamable HTTP که نشست‌های بیکار را منقضی می‌کند، این یعنی نخستین فراخوانی بدون حاشیه‌نویسی پس از یک دورهٔ بیکاری ممکن است شکست بخورد و پیش از فراخوانی دوباره باید نتیجه‌اش بررسی شود. مقادیر ناشناخته مانند untrusted در نظر گرفته می‌شوند (در صورت خطا، دسترسی بسته می‌ماند).

۳ ارجاع به متغیرهای محیطی

مقادیر رشته‌ای در هر جای ورودی سرور (env، headers، args، url و…) می‌توانند با ${VAR} یا شکل SecretRef به سبک Cursor یعنی ${env:VAR} به متغیرهای محیطی ارجاع بدهند — هر دو به همان متغیر تبدیل می‌شوند؛ بنابراین قطعه‌پیکربندی‌های MCP که از پیکربندی‌های Cursor / Claude کپی شده‌اند، بدون تغییر کار می‌کنند:

mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "${env:GITHUB_TOKEN}"   # same as "${GITHUB_TOKEN}"

مقادیر از محدودهٔ رمزهای پروفایل فعال به دست می‌آیند (در صورت نبود، به محیط فرایند بازمی‌گردند)، پس رمز را در ~/.hermes/.env قرار دهید. متغیری که تنظیم نشده باشد، همان عبارت جای‌نگهدار خود را بدون تغییر حفظ می‌کند.

متغیرهای زمینه

علاوه بر متغیرهای محیطی، متغیرهای زمینه به سبک Cursor هم جای‌گذاری می‌شوند (نام‌ها به بزرگی و کوچکی حروف حساس‌اند):

متغیرمقدار جایگزین
${userHome}پوشهٔ خانهٔ کاربر فعلی
${workspaceFolder}ریشهٔ فضای کاری نشست (دایرکتوری کاری فعلی ترمینال نشست، اگر مشخص باشد؛ وگرنه دایرکتوری کاری فعلی فرایند)
${workspaceFolderBasename}نام پایهٔ ${workspaceFolder}
${pathSeparator} / ${/}جداکنندهٔ مسیر سیستم‌عامل (os.sep)
mcp_servers:
  filesystem:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "${workspaceFolder}"]
    env:
      CACHE_DIR: "${userHome}${/}.cache${/}mcp"

هر ارجاع دیگر به شکل ${...} به جستجوی متغیر محیطیِ توضیح‌داده‌شده در بالا سپرده می‌شود.

۴ کلیدهای سیاست tools

کلیدنوعمعنا
includeرشته یا فهرستفهرست مجاز ابزارهای بومی MCP سرور. ورودی‌ها می‌توانند نام‌های دقیق یا الگوهای گلوب به سبک fnmatch باشند (*_radar_*، get_zones_*).
excludeرشته یا فهرستفهرست مسدود ابزارهای بومی MCP سرور. قواعد نام دقیق / گلوب آن مانند include است.
resourcesبولی‌مانندفعال/غیرفعال‌کردن list_resources + read_resource
promptsبولی‌مانندفعال/غیرفعال‌کردن list_prompts + get_prompt

۵ قواعد فیلترکردن

include

اگر include تنظیم شود، فقط همان ابزارهای بومی MCP سرور ثبت می‌شوند.

tools:
  include: [create_issue, list_issues]

exclude

اگر exclude تنظیم شود و include تنظیم نشده باشد، همهٔ ابزارهای بومی MCP سرور به‌جز نام‌های مشخص‌شده ثبت می‌شوند.

tools:
  exclude: [delete_customer]

اولویت

اگر هر دو تنظیم شوند، include اولویت دارد.

tools:
  include: [create_issue]
  exclude: [create_issue, delete_issue]

نتیجه:

  • create_issue همچنان مجاز است.
  • delete_issue نادیده گرفته می‌شود، چون include اولویت دارد.

۶ سیاست ابزارهای کمکی

هرمس ممکن است این پوشش‌های کمکی را برای هر سرور MCP ثبت کند:

منابع:

  • list_resources
  • read_resource

پرامپت‌ها:

  • list_prompts
  • get_prompt

غیرفعال‌کردن منابع

tools:
  resources: false

غیرفعال‌کردن پرامپت‌ها

tools:
  prompts: false

ثبت متناسب با قابلیت‌ها

حتی با وجود resources: true یا prompts: true، هرمس فقط زمانی آن ابزارهای کمکی را ثبت می‌کند که نشست MCP واقعاً قابلیت مربوط را در اختیار بگذارد.

بنابراین این وضعیت طبیعی است:

  • پرامپت‌ها را فعال می‌کنید؛
  • اما هیچ ابزار کمکی پرامپتی ظاهر نمی‌شود؛
  • چون سرور از پرامپت‌ها پشتیبانی نمی‌کند.

۷ enabled: false

mcp_servers:
  legacy:
    url: "https://mcp.legacy.internal"
    enabled: false

رفتار:

  • هیچ تلاشی برای اتصال انجام نمی‌شود.
  • هیچ کشفی انجام نمی‌شود.
  • هیچ ابزاری ثبت نمی‌شود.
  • پیکربندی برای استفادهٔ دوباره در آینده در جای خود باقی می‌ماند.

۸ رفتار در صورت خالی‌بودن نتیجه

اگر فیلترکردن همهٔ ابزارهای بومی سرور را حذف کند و هیچ ابزار کمکی هم ثبت نشود، هرمس برای آن سرور یک تول‌ست خالی MCP در زمان اجرا ایجاد نمی‌کند.

۹ نمونه‌های پیکربندی

فهرست مجاز ایمن برای GitHub

mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"
    tools:
      include: [list_issues, create_issue, update_issue, search_code]
      resources: false
      prompts: false

فهرست مسدود Stripe

mcp_servers:
  stripe:
    url: "https://mcp.stripe.com"
    headers:
      Authorization: "Bearer ***"
    tools:
      exclude: [delete_customer, refund_payment]

سرور مستندات فقط‌منبعی

mcp_servers:
  docs:
    url: "https://mcp.docs.example.com"
    tools:
      include: []
      resources: true
      prompts: false

گواهی کلاینت TLS (mTLS)

برای سرورهای HTTP/SSE که به گواهی کلاینت نیاز دارند، client_cert (و در صورت نیاز client_key) را تنظیم کنید:

mcp_servers:
  # Combined cert + key in a single PEM file
  internal_api:
    url: "https://mcp.internal.example.com/mcp"
    client_cert: "~/secrets/mcp-client.pem"

  # Separate cert and key files
  partner_api:
    url: "https://mcp.partner.example.com/mcp"
    client_cert: "~/secrets/client.crt"
    client_key: "~/secrets/client.key"

  # Encrypted key with a passphrase (3-element list form)
  bank_api:
    url: "https://mcp.bank.example.com/mcp"
    client_cert: ["~/secrets/client.crt", "~/secrets/client.key", "my-passphrase"]

  # Custom CA bundle (private CA / self-signed server)
  lab_api:
    url: "https://mcp.lab.local/mcp"
    ssl_verify: "~/secrets/lab-ca.pem"
    client_cert: "~/secrets/lab-client.pem"

نکات:

  • مسیرها از بسط ~ پشتیبانی می‌کنند. اگر فایل‌ها موجود نباشند، اتصال بلافاصله با پیام خطایی مربوط به همان سرور شکست می‌خورد.
  • ssl_verify: false اعتبارسنجی گواهی سرور را به‌کلی غیرفعال می‌کند. از این گزینه برای سرویس‌های واقعی استفاده نکنید.
  • روی هر دو روش انتقال Streamable HTTP و SSE کار می‌کند.

۱۰ بارگذاری مجدد پیکربندی

پس از تغییر پیکربندی MCP، سرورها را با این فرمان دوباره بارگذاری کنید:

/reload-mcp

۱۱ نام‌گذاری ابزارها

نام ابزارهای بومی MCP سرور به این شکل درمی‌آید:

mcp__<server>__<tool>

نمونه‌ها:

  • mcp__github__create_issue
  • mcp__filesystem__read_file
  • mcp__my_api__query_data

ابزارهای کمکی هم از همین الگوی پیشوندگذاری پیروی می‌کنند:

  • mcp__<server>__list_resources
  • mcp__<server>__read_resource
  • mcp__<server>__list_prompts
  • mcp__<server>__get_prompt

جداکنندهٔ دو زیرخطی (mcp__…__…) با قرارداد مورد استفادهٔ Claude Code، Codex و OpenCode مطابقت دارد و حتی وقتی هر یک از دو جزء شامل زیرخط باشد، مرز سرور/ابزار را بدون ابهام مشخص می‌کند.

پاک‌سازی نام‌ها

در نام سرور و نام ابزار، هر نویسه‌ای که حرف، رقم یا زیرخط نباشد (خط تیره، نقطه، فاصله و غیره)، پیش از ثبت با زیرخط جایگزین می‌شود. این کار تضمین می‌کند نام ابزارها شناسه‌های معتبری برای APIهای فراخوانی تابع در LLM باشند.

برای نمونه، سروری با نام my-api که ابزاری به نام list-items.v2 ارائه می‌کند، به این نام تبدیل می‌شود:

mcp__my_api__list_items_v2

هنگام نوشتن فیلترهای include / exclude این نکته را در نظر بگیرید — از نام اصلی ابزار MCP (با خط تیره/نقطه) استفاده کنید، نه نسخهٔ پاک‌سازی‌شده.

۱۲ احراز هویت OAuth 2.1

برای سرورهای HTTP که به OAuth نیاز دارند، در ورودی سرور auth: oauth را تنظیم کنید:

mcp_servers:
  protected_api:
    url: "https://mcp.example.com/mcp"
    auth: oauth

رفتار:

  • هرمس از جریان OAuth 2.1 PKCE در SDK مربوط به MCP استفاده می‌کند (کشف فراداده، معرفی کلاینت، مبادلهٔ توکن و نوسازی).
  • در نخستین اتصال، پنجرهٔ مرورگر برای اعطای مجوز باز می‌شود.
  • توکن‌ها در ~/.hermes/mcp-tokens/<server>.json ذخیرهٔ پایدار می‌شوند (پروفایل نام‌دار از ~/.hermes/profiles/<name>/mcp-tokens/ استفاده می‌کند) و در نشست‌های بعدی دوباره به کار می‌روند.
  • نوسازی توکن خودکار است؛ اعطای مجوز دوباره فقط وقتی انجام می‌شود که نوسازی شکست بخورد.
  • فقط برای انتقال HTTP/StreamableHTTP کاربرد دارد (سرورهای مبتنی بر url).
  • در یک گیت‌وی چندپروفایلیِ مالتی‌پلکس‌شده، اتصال OAuth هرگز میان پروفایل‌ها مشترک نیست: هر پروفایل با توکن خودش احراز هویت می‌کند و اتصال خودش را باز می‌کند، حتی اگر ورودی‌های mcp_servers یکسان باشند.

ورود با کد دستگاه (RFC 8628)

برای سرور اعطای مجوزی که device_authorization_endpoint را اعلام می‌کند، از ترمینالی روی دستگاهی که هرمس را اجرا می‌کند، صریحاً روش اعطای مجوز دستگاه را انتخاب کنید:

hermes mcp login protected_api --flow device

URL تأییدِ چاپ‌شده را روی هر دستگاهی باز کنید و کد کاربرِ نمایش‌داده‌شده را وارد کنید. هرمس برای دریافت تأیید به‌صورت دوره‌ای وضعیت را بررسی می‌کند، authorization_pending و slow_down را رعایت می‌کند و در صورت رد یا انقضا متوقف می‌شود. هیچ مرورگری اجرا نمی‌شود و نیازی به شنوندهٔ بازگشت نیست. oauth.timeout انتظار برای تأیید را محدود می‌کند (پیش‌فرض ۳۰۰ ثانیه)؛ طول عمر کد هم محدودیت دیگری برای آن است. اگر فرادادهٔ منبع محافظت‌شدهٔ سرور چند سرور اعطای مجوز را فهرست کند، ورود دستگاه آن‌ها را به‌ترتیب بررسی می‌کند و نخستین سروری را به کار می‌گیرد که صادرکنندهٔ فراداده‌اش با URL اعلام‌شدهٔ آن مطابقت داشته باشد و گرنت device_code را ارائه کند (اگر نخستین سرور فقط از مرورگر پشتیبانی کند، از آن عبور می‌شود)؛ اعتبارسنجی صادرکننده هرگز آسان‌گیرانه‌تر نمی‌شود.

برای اینکه hermes mcp login و hermes mcp reauth (از جمله reauth --all) از اعطای مجوز دستگاه استفاده کنند، روی سرور oauth.flow: device را تنظیم کنید. login --flow browser این تنظیم را برای یک ورود کنار می‌زند؛ PKCE مرورگری همچنان پیش‌فرض است. فرادادهٔ پشتیبانی‌نشده به‌جای بازگشت بی‌سروصدا به جریانی دیگر، خطایی همراه با راهنمای اقدام ایجاد می‌کند.

ورود دستگاه هنگام ثبت پویا، گرنت‌های دستگاه و نوسازی را درخواست می‌کند؛ یا از مقادیر پیکربندی‌شدهٔ oauth.client_id، oauth.client_secret و oauth.token_endpoint_auth_method شما استفاده می‌کند. کلاینت ثبت‌شده باید اعطای مجوز دستگاه را مجاز بداند. سند CIMD مرورگر استفاده نمی‌شود. oauth.scope همراه درخواست اعطای مجوز دستگاه ارسال می‌شود؛ oauth.user_agent روی بررسی دوره‌ای توکن هم اعمال می‌شود. توکن‌ها، اطلاعات ثبت و فرادادهٔ صادرکننده در مخزن توکن MCP پروفایل فعال می‌مانند و مسیر فعلی نوسازی در زمان اجرا، پس از راه‌اندازی مجدد دوباره از آن‌ها استفاده می‌کند. گرنت‌های ناموفق دستگاه جای اعتبارنامه‌های قبلاً ذخیره‌شده را نمی‌گیرند.

ورود اولیهٔ دستگاه فقط از ترمینال ممکن است: بازگشت‌های داشبورد/مرورگر و اتصال‌های مجدد پس‌زمینه، اعطای مجوز دستگاه را شروع نمی‌کنند. فرمان ورود را برای همان پروفایل و میزبان گیت‌وی اجرا کنید. گرنت دستگاهِ منقضی‌شده یا ردشده که توکن نوسازی قابل استفاده‌ای ندارد، به ورود صریح دیگری نیاز دارد.

معرفی کلاینت: CIMD و DCR

هرمس خود را با سند فرادادهٔ شناسهٔ کلاینت (Client ID Metadata Document یا CIMD) به سرورهای اعطای مجوز معرفی می‌کند؛ سازوکاری که مشخصات MCP نسخهٔ 2026-07-28 به‌جای ثبت پویای کلاینت پذیرفته است. این سند در https://nousresearch.github.io/hermes-agent/docs/oauth/client-metadata.json منتشر می‌شود و همین URL خودِ client_id است — سرور اعطای مجوز آن را واکشی می‌کند تا نام، نشان و URIهای بازگشت مجاز هرمس را بشناسد. برای هر نصب چیزی ثبت نمی‌شود و هیچ چیز مختص کاربر نیست.

انتخاب نهایی با سرور اعطای مجوز است: SDK فقط زمانی URL سند را به‌عنوان client_id می‌فرستد که سرور در فراداده‌اش client_id_metadata_document_supported: true را اعلام کند؛ در غیر این صورت، دقیقاً مثل قبل از طریق DCR ثبت می‌کند. DCR در مشخصات MCP منسوخ اعلام شده، اما هنوز تقریباً همهٔ سرورهای مستقر امروزی از آن استفاده می‌کنند.

پورت‌های بازگشت

سند مجموعه‌ای ثابت از URIهای تغییرمسیر لوپ‌بک را اعلام می‌کند و مشخصات ایجاب می‌کند URI تغییرمسیر در درخواست اعطای مجوز، از نظر رشته‌ای دقیقاً با یکی از آن‌ها یکسان باشد — بنابراین جریان CIMD نمی‌تواند از پورت بالای تصادفی که هرمس معمولاً انتخاب می‌کند استفاده کند. به همین دلیل هرمس بازگشت را به یکی از پورت‌های 27890 تا 27894 مقید می‌کند.

این پورت مقید باید پیش از مشخص‌شدن قابلیت‌های سرور انتخاب شود، چون URI تغییرمسیر در آغاز جریان ثابت می‌شود، ولی فرادادهٔ سرور در میانهٔ راه می‌رسد. بنابراین هرمس برای هر جریانی که ممکن است در نهایت از CIMD استفاده کند، پورت را مقید می‌کند و برای بقیه به پورت تصادفی برمی‌گردد:

  • سروری که هرمس قبلاً به آن متصل شده و فرادادهٔ کش‌شده‌اش CIMD را اعلام نمی‌کند، همان رفتار همیشگیِ پورت تصادفی را حفظ می‌کند.
  • سروری که هرمس هرگز به آن دسترسی نداشته، در نخستین ورود یک پورت مقید می‌گیرد؛ چون این حدس‌زدن تنها راه ممکن برای استفاده از CIMD است.
  • هر چیزی که بازگشت را به جای دیگری ببرد نیز باعث بازگشت به پورت تصادفی می‌شود: oauth.client_id ازپیش‌ثبت‌شده، oauth.client_secret، مقدار سفارشی oauth.client_name یا oauth.token_endpoint_auth_method، بازنویسی oauth.redirect_uri یا oauth.redirect_port، ورود آغازشده از داشبورد یا دسکتاپ، وجود ثبت کلاینت روی دیسک، یا اشغال‌بودن هر پنج پورت توسط فرایندهای دیگر.

هر پورت مقید به‌محض انتخاب رزرو می‌شود و تا رسیدن تغییرمسیر مرورگر نگه داشته می‌شود؛ بنابراین دو ورود هم‌زمان — یک پروفایل دوم یا سروری دیگر در همان فرایند — نمی‌توانند روی یک شنونده بنشینند.

وقتی سرور سند را رد می‌کند

اگر سرور سند را واکشی کند و در نقطهٔ پایانی توکن آن را نپذیرد (invalid_client)، هرمس این ردشدن را در لاگ می‌نویسد، آن را در ~/.hermes/mcp-tokens/<server>.cimd-off ثبت می‌کند و از آن پس برای آن سرور از DCR استفاده می‌کند.

سروری که اصلاً نتواند سند را واکشی یا اعتبارسنجی کند، در عوض در نقطهٔ پایانی اعطای مجوز و پیش از هر تغییرمسیر، فرایند را متوقف می‌کند. در آن مرحله هیچ نشانه‌ای وجود ندارد که هرمس بتواند مشاهده کند؛ بنابراین مرورگر خطای کلاینت نامعتبر نشان می‌دهد و مهلت ورود پس از پنج دقیقه تمام می‌شود. پیام پایان مهلت، نام سند را ذکر می‌کند و به cimd: false اشاره می‌کند. اجرای hermes mcp login <server> ردشدن ثبت‌شده را پاک می‌کند تا سند اصلاح‌شده فرصت دیگری پیدا کند.

کلیدهای اختیاری به‌ازای هر سرور

mcp_servers:
  protected_api:
    url: "https://mcp.example.com/mcp"
    auth: oauth
    oauth:
      client_metadata_url: "https://example.com/my-cimd.json"  # self-hosted document
      cimd: false                                              # force DCR
      user_agent: "My-MCP-Client/1.0"                          # token-request User-Agent

client_metadata_url باید یک URL از نوع HTTPS دارای مسیر باشد (نه فقط مبدأ؛ بدون قطعهٔ لنگر، اطلاعات کاربر یا بخش‌های ./..) که پاسخ 200 و Content-Type: application/json را بدون تغییرمسیر برگرداند — سرورهای اعطای مجوز هنگام واکشی آن اجازهٔ دنبال‌کردن تغییرمسیرها را ندارند. هرمس همچنان بازگشت خود را به همان بازهٔ 27890 تا 27894 مقید می‌کند؛ پس سند خودمیزبان باید هر ده URI لوپ‌بک را اعلام کند (http://127.0.0.1:<port>/callback و http://localhost:<port>/callback برای هر پورت)، و client_id آن باید URL خودش باشد.

user_agent، مقدار پیش‌فرض User-Agent کتابخانهٔ HTTP را فقط در درخواست‌های نقطهٔ پایانی توکن (مبادلهٔ کد اعطای مجوز و نوسازی) جایگزین می‌کند — برخی سرورهای اعطای مجوز و دیواره‌های آتش برنامهٔ وب (WAF) مقدار پیش‌فرض python-httpx/... را در آنجا رد می‌کنند. این گزینه هرگز روی ترافیک MCP یا کشف OAuth اعمال نمی‌شود و هیچ سرآیند دیگری برای درخواست توکن قابل پیکربندی نیست. مقادیر خالی یا null نادیده گرفته می‌شوند.

۱۳ پیوند افزودن به هرمس

ارائه‌دهندگان MCP و مستندات آن‌ها می‌توانند دکمهٔ تک‌کلیکی «افزودن به هرمس» ارائه کنند که برنامهٔ دسکتاپ هرمس را با پیکربندی ازپیش‌پرشدهٔ سرور باز می‌کند؛ مشابه طرح cursor://anysphere.cursor-deeplink/mcp/install در Cursor:

hermes://mcp/install?name=NAME&config=BASE64
  • name — نام سرور. باید با ^[A-Za-z0-9._-]{1,64}$ مطابقت داشته باشد.
  • config — شیء پیکربندی سرور به شکل JSON کدگذاری‌شده با base64url (base64 استاندارد هم پذیرفته می‌شود). JSON رمزگشایی‌شده باید شیئی باشد که یا فیلد رشته‌ای url دارد (فقط http:///https://) یا فیلد رشته‌ای command؛ و می‌تواند هر یک از کلیدهای سرورِ مستندشده در بالا را همراه داشته باشد. محموله‌های بیش از ۳۲ کیلوبایت رد می‌شوند.

نمونه (JavaScript):

const config = { url: 'https://mcp.example.com/mcp' }
const link = `hermes://mcp/install?name=example&config=${btoa(JSON.stringify(config))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '')}`

بازکردن پیوند به‌خودی‌خود هرگز چیزی نصب نمی‌کند: برنامهٔ دسکتاپ کادر تأییدی با نام سرور و کل پیکربندیِ قالب‌بندی‌شده و خوانا نشان می‌دهد (با احتیاط اضافه برای سرورهای مبتنی بر command که یک فرایند محلی اجرا می‌کنند) و کاربر باید صریحاً تأیید کند. نام سرورهای موجود هرگز بازنویسی نمی‌شود — از کاربر خواسته می‌شود نام را تغییر دهد یا لغو کند.
