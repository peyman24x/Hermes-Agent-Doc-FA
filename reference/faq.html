۱ پرسش‌های متداول

کدام ارائه‌دهندگان مدل زبانی بزرگ با Hermes کار می‌کنند؟

Hermes Agent با هر API سازگار با OpenAI کار می‌کند. ارائه‌دهندگان پشتیبانی‌شده عبارت‌اند از:

  • OpenRouter — دسترسی به صدها مدل با یک کلید API؛ پیشنهادشده برای انعطاف‌پذیری.
  • Nous Portal — گیت‌وی اشتراکی Nous Research؛ بیش از ۳۰۰ مدل به‌علاوهٔ وب، تصویر، تبدیل متن به گفتار و مرورگر با یک ورود OAuth؛ پیشنهادشده برای تازه‌واردان.
  • OpenAI — مدل‌های GPT-5.4، GPT-5-codex، GPT-4.1، GPT-4o و غیره.
  • Anthropic — مدل‌های Claude از طریق API مستقیم، OAuth با hermes auth add anthropic، OpenRouter یا هر پراکسی سازگار.
  • Google — مدل‌های Gemini از طریق API مستقیم با ارائه‌دهندهٔ gemini، OpenRouter یا پراکسی سازگار.
  • z.ai / ZhipuAI — مدل‌های GLM.
  • Kimi / Moonshot AI — مدل‌های Kimi.
  • MiniMax — نقاط پایانی جهانی و چین.
  • مدل‌های محلی — از طریق Ollama، vLLM، llama.cpp، SGLang یا هر سرور سازگار با OpenAI.

ارائه‌دهنده را با hermes model یا ویرایش ~/.hermes/.env تنظیم کنید. برای همهٔ کلیدهای ارائه‌دهندگان، مرجع متغیرهای محیطی را ببینید.

آیا روی Windows، Android، Termux یا پلتفرم من کار می‌کند؟

برای جدول کامل دسترس‌پذیری در پلتفرم‌های مختلف، پشتیبانی پلتفرم‌ها را ببینید.

Hermes را در WSL2 اجرا می‌کنم. بهترین راه کنترل Chrome معمولی من در Windows چیست؟

پل MCP را به /browser connect ترجیح دهید.

الگوی پیشنهادی:

  • Hermes را داخل WSL2 اجرا کنید.
  • همچنان از Chrome معمولی خود در Windows که به حساب‌هایتان وارد شده است استفاده کنید.
  • chrome-devtools-mcp را از طریق cmd.exe یا powershell.exe به‌عنوان سرور MCP اضافه کنید.
  • بگذارید Hermes از ابزارهای مرورگر MCP حاصل استفاده کند.

این روش از تلاش برای وادارکردن لایهٔ انتقال مرورگر هستهٔ Hermes به اتصال مستقیم از مرز WSL2/Windows قابل‌اعتمادتر است.

ببینید:

  • استفاده از MCP با Hermes
  • اتوماسیون مرورگر

آیا داده‌های من به جایی ارسال می‌شود؟

فراخوانی‌های API فقط به ارائه‌دهندهٔ LLM پیکربندی‌شدهٔ شما می‌روند؛ مثلاً OpenRouter یا نمونهٔ محلی Ollama شما. Hermes Agent هیچ تله‌متری، دادهٔ استفاده یا دادهٔ تحلیلی جمع‌آوری نمی‌کند. گفتگوها، حافظه و مهارت‌های شما به‌صورت محلی در ~/.hermes/ ذخیره می‌شوند.

آیا می‌توانم آفلاین یا با مدل‌های محلی از آن استفاده کنم؟

بله. hermes model را اجرا کنید، گزینهٔ نقطهٔ پایانی سفارشی (Custom endpoint) را انتخاب کنید و URL سرورتان را وارد کنید:

hermes model
# Select: Custom endpoint (enter URL manually)
# API base URL: http://localhost:11434/v1
# API key: ollama
# Model name: qwen3.5:27b
# Context length: 64000   ← Hermes minimum; set this to match your server's actual context window

یا آن را مستقیم در config.yaml پیکربندی کنید:

model:
  default: qwen3.5:27b
  provider: custom
  base_url: http://localhost:11434/v1

Hermes نقطهٔ پایانی، ارائه‌دهنده و URL پایه را در config.yaml ذخیره می‌کند تا پس از راه‌اندازی مجدد باقی بمانند. اگر دقیقاً یک مدل روی سرور محلی شما بارگذاری شده باشد، /model custom آن را خودکار تشخیص می‌دهد. همچنین می‌توانید provider: custom را در config.yaml تنظیم کنید؛ این یک ارائه‌دهندهٔ مستقل و کاملاً پشتیبانی‌شده است، نه نام مستعار چیز دیگری.

این روش با Ollama، vLLM، سرور llama.cpp، SGLang، LocalAI و موارد دیگر کار می‌کند. برای جزئیات، راهنمای پیکربندی را ببینید.

نکته — کاربران Ollama

اگر در Ollama مقدار سفارشی num_ctx تنظیم می‌کنید، مثلاً ollama run --num_ctx 64000، حتماً طول زمینهٔ متناظر را در Hermes هم تنظیم کنید؛ /api/show در Ollama حداکثر زمینهٔ مدل را گزارش می‌دهد، نه مقدار مؤثر num_ctx که شما پیکربندی کرده‌اید.

نکته — پایان مهلت با مدل‌های محلی

Hermes نقاط پایانی محلی را خودکار تشخیص می‌دهد و مهلت‌های استریم را افزایش می‌دهد؛ مهلت خواندن از ۱۲۰ به ۱۸۰۰ ثانیه می‌رسد و تشخیص استریم متوقف‌شده غیرفعال می‌شود. اگر همچنان با زمینه‌های بسیار بزرگ به پایان مهلت می‌رسید، HERMES_STREAM_READ_TIMEOUT=1800 را در .env تنظیم کنید. برای جزئیات، راهنمای LLM محلی را ببینید.

هزینهٔ آن چقدر است؟

خود Hermes Agent رایگان و متن‌باز است و مجوز MIT دارد. فقط هزینهٔ مصرف API مدل زبانی را به ارائه‌دهندهٔ انتخابی خود می‌پردازید. اجرای مدل‌های محلی کاملاً رایگان است.

آیا چند نفر می‌توانند از یک نمونه استفاده کنند؟

بله. گیت‌وی پیام‌رسانی به چند کاربر اجازه می‌دهد از طریق Telegram، Discord، Slack، WhatsApp یا Home Assistant با یک نمونهٔ Hermes Agent تعامل کنند. دسترسی با فهرست‌های مجازِ شناسه‌های مشخص کاربران و جفت‌سازی پیام خصوصی کنترل می‌شود؛ در جفت‌سازی، اولین کاربری که پیام می‌دهد دسترسی را در اختیار می‌گیرد.

تفاوت حافظه و مهارت‌ها چیست؟

  • حافظه، واقعیت‌ها را ذخیره می‌کند؛ چیزهایی که ایجنت دربارهٔ شما، پروژه‌ها و ترجیحاتتان می‌داند. حافظه‌ها بر اساس ارتباط با موضوع، خودکار بازیابی می‌شوند.
  • مهارت‌ها، رویه‌ها را ذخیره می‌کنند؛ دستورالعمل‌های گام‌به‌گام انجام کارها. وقتی ایجنت با وظیفه‌ای مشابه روبه‌رو شود، مهارت‌ها فراخوانده می‌شوند.

هر دو میان نشست‌ها باقی می‌مانند. برای جزئیات، حافظه و مهارت‌ها را ببینید.

آیا می‌توانم در پروژهٔ Python خودم از آن استفاده کنم؟

بله. کلاس AIAgent را وارد کنید و از Hermes به‌صورت برنامه‌نویسی استفاده کنید:

from run_agent import AIAgent

agent = AIAgent(model="anthropic/claude-opus-4.7")
response = agent.chat("Explain quantum computing briefly")

برای روش کامل استفاده از API، راهنمای کتابخانهٔ Python را ببینید.

۲ عیب‌یابی

مشکلات نصب

خطای hermes: command not found پس از نصب

علت: شل شما هنوز PATH به‌روزشده را دوباره بارگذاری نکرده است.

راه‌حل:

# Reload your shell profile
source ~/.bashrc    # bash
source ~/.zshrc     # zsh

# Or start a new terminal session

اگر هنوز کار نمی‌کند، محل نصب را بررسی کنید:

which hermes
ls ~/.local/bin/hermes
نکته

نصب‌کننده ~/.local/bin را به PATH اضافه می‌کند. اگر پیکربندی شل شما غیراستاندارد است، export PATH="$HOME/.local/bin:$PATH" را دستی اضافه کنید.

نسخهٔ Python بیش از حد قدیمی است

علت: Hermes به Python نسخهٔ ۳.۱۱ یا جدیدتر نیاز دارد.

راه‌حل:

python3 --version   # Check current version

# Install a newer Python
sudo apt install python3.12   # Ubuntu/Debian
brew install python@3.12      # macOS

نصب‌کننده این موضوع را خودکار مدیریت می‌کند؛ اگر هنگام نصب دستی این خطا را می‌بینید، ابتدا Python را ارتقا دهید.

فرمان‌های ترمینال خطای node: command not found می‌دهند؛ یا برای nvm، pyenv، asdf و غیره

علت: Hermes با یک‌بار اجرای bash -l هنگام شروع، اسنپ‌شاتی از محیط برای هر نشست می‌سازد. شل ورود bash فایل‌های /etc/profile، ~/.bash_profile و ~/.profile را می‌خواند، اما ~/.bashrc را بارگذاری نمی‌کند؛ بنابراین ابزارهایی که خود را در آن نصب می‌کنند، مانند nvm، asdf، pyenv، cargo و تعریف‌های سفارشی PATH، در اسنپ‌شات دیده نمی‌شوند. این مشکل بیشتر زمانی رخ می‌دهد که Hermes زیر systemd یا در شلی حداقلی اجرا شود که پروفایل شل تعاملی از قبل در آن بارگذاری نشده است.

راه‌حل: Hermes به‌طور پیش‌فرض ~/.bashrc را خودکار بارگذاری می‌کند. اگر کافی نیست، مثلاً کاربر zsh هستید و PATH شما در ~/.zshrc قرار دارد یا nvm را از فایلی مستقل مقداردهی می‌کنید، فایل‌های اضافی برای بارگذاری را در ~/.hermes/config.yaml فهرست کنید:

terminal:
  shell_init_files:
    - ~/.zshrc                     # zsh users: pulls zsh-managed PATH into the bash snapshot
    - ~/.nvm/nvm.sh                # direct nvm init (works regardless of shell)
    - /etc/profile.d/cargo.sh      # system-wide rc files
  # When this list is set, the default ~/.bashrc auto-source is NOT added —
  # include it explicitly if you want both:
  #   - ~/.bashrc
  #   - ~/.zshrc

فایل‌های ناموجود بی‌سروصدا رد می‌شوند. بارگذاری در bash انجام می‌شود، بنابراین فایل‌های متکی به نحو اختصاصی zsh ممکن است خطا دهند؛ اگر این موضوع نگران‌کننده است، فقط بخش تنظیم PATH را بارگذاری کنید، مثلاً مستقیماً nvm.sh مربوط به nvm را، نه کل فایل rc را.

مستقل از فایل‌های مقداردهی اولیه، PATH هر فرمان ترمینال با پوشه‌های استاندارد سیستم، مانند /usr/local/bin و /opt/homebrew/bin، پوشه‌های زمان اجرای تحت مدیریت Hermes و در صورت وجود ~/.local/bin، یعنی مقصد نصب pip --user، pipx و uv tool، تکمیل می‌شود. این‌ها پس از ورودی‌های خودتان اضافه می‌شوند، پس اولویت‌ها تغییر نمی‌کنند. این رفتار بدون نیاز به پیکربندی، بک‌اندهایی را پوشش می‌دهد که با PATH غیرتعاملی حداقلی شروع شده‌اند؛ از جمله systemd، اجراکننده‌های گرافیکی و بک‌اند SSH راه دور دسکتاپ.

برای غیرفعال‌کردن بارگذاری خودکار و رعایت صرفِ رفتار شل ورود:

terminal:
  auto_source_bashrc: false

خطای uv: command not found

علت: مدیر بستهٔ uv نصب نیست یا در PATH قرار ندارد.

راه‌حل:

curl -LsSf https://astral.sh/uv/install.sh | sh
source ~/.bashrc

خطاهای رد دسترسی هنگام نصب

علت: مجوز کافی برای نوشتن در پوشهٔ نصب ندارید.

راه‌حل:

# Don't use sudo with the installer — it installs to ~/.local/bin

sudo rm /usr/local/bin/hermes

curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

مشکلات ارائه‌دهنده و مدل

ایجنت می‌گوید «سیاست Hermes» یا «محدودیت‌های حفاظتی Hermes» درخواست من را رد کرده است

مدل نمی‌تواند با اطمینان علت رد درخواست را تشخیص دهد. اگر امتناع فقط در متن پاسخ دستیار دیده می‌شود، ادعای آن دربارهٔ وجود سیاست پنهان زمان اجرای Hermes ممکن است توضیحی ساختگی یا محدودیتی باشد که مدل یا ارائه‌دهندهٔ انتخاب‌شده اعمال کرده است.

اعمال محدودیت در Hermes صریح است: اقدام ابزاری مسدودشده خطایی برمی‌گرداند که فرمان یا مسیر ممنوع را نام می‌برد، و اقدامی که تأیید لازم دارد پرسش تأیید نشان می‌دهد. Hermes این کنترل‌های اجرایی را بی‌سروصدا به لایه‌ای عمومی برای امتناع محتوایی تبدیل نمی‌کند. کنترل‌های سطح ارائه‌دهنده، مانند Amazon Bedrock Guardrails، همچنان در صورت پیکربندی می‌توانند اعمال شوند.

برای مشخص‌کردن منبع:

  1. /status را اجرا کنید تا مدل و ارائه‌دهندهٔ فعال را تأیید کنید.
  2. بررسی کنید آیا امتناع شامل خطای واقعی ابزار Hermes یا پرسش تأیید است. اگر فقط متن است، نسبت‌دادن علت توسط مدل را شاهدی از زمان اجرا تلقی نکنید.
  3. در نشستی تازه با مدل یا ارائه‌دهندهٔ پیکربندی‌شدهٔ دیگری دوباره امتحان کنید. امتناعی که با تغییر مدل عوض می‌شود، رفتار مدل یا ارائه‌دهنده است، نه کنترل اجرایی Hermes.
  4. اگر خطای صریح ابزار ظاهر شد، هنگام گزارش مشکل متن دقیق آن را بیاورید.

برای کنترل‌های اجرایی مستندشدهٔ Hermes، امنیت و برای پیکربندی ارائه‌دهندگان، ارائه‌دهندگان را ببینید.

/model فقط یک ارائه‌دهنده نشان می‌دهد یا نمی‌توان ارائه‌دهنده را عوض کرد

علت: /model در نشست گفتگو فقط می‌تواند میان ارائه‌دهندگانی جابه‌جا شود که قبلاً پیکربندی کرده‌اید. اگر فقط OpenRouter را راه‌اندازی کرده‌اید، همین تنها گزینهٔ قابل نمایش است.

راه‌حل: از نشست خارج شوید و برای افزودن ارائه‌دهندگان جدید، hermes model را از ترمینال اجرا کنید:

# Exit the Hermes chat session first (Ctrl+C or /quit)

# Run the full provider setup wizard
hermes model

# This lets you: add providers, run OAuth, enter API keys, configure endpoints

پس از افزودن ارائه‌دهندهٔ جدید با hermes model، نشست گفتگوی تازه‌ای شروع کنید؛ اکنون /model همهٔ ارائه‌دهندگان پیکربندی‌شده را نشان می‌دهد.

کلید API کار نمی‌کند

علت: کلید وجود ندارد، منقضی شده، نادرست تنظیم شده یا متعلق به ارائه‌دهندهٔ دیگری است.

راه‌حل:

# Check your configuration
hermes config show

# Re-configure your provider
hermes model

# Or set directly
hermes config set OPENROUTER_API_KEY sk-or-v1-xxxxxxxxxxxx
هشدار

مطمئن شوید کلید با ارائه‌دهنده مطابقت دارد. کلید OpenAI با OpenRouter کار نمی‌کند و برعکس. ~/.hermes/.env را برای ورودی‌های متعارض بررسی کنید.

مدل در دسترس نیست یا پیدا نمی‌شود

علت: شناسهٔ مدل نادرست است یا مدل نزد ارائه‌دهندهٔ شما در دسترس نیست.

راه‌حل:

# List available models for your provider
hermes model

# Set a valid model
hermes config set model.default anthropic/claude-opus-4.7

# Or specify per-session
hermes chat --model openrouter/meta-llama/llama-3.1-70b-instruct

محدودیت نرخ؛ خطاهای ۴۲۹

علت: از محدودیت نرخ ارائه‌دهندهٔ خود عبور کرده‌اید.

راه‌حل: کمی صبر کنید و دوباره تلاش کنید. برای استفادهٔ مداوم، این گزینه‌ها را در نظر بگیرید:

  • ارتقای طرح اشتراک ارائه‌دهنده.
  • تغییر به مدل یا ارائه‌دهنده‌ای دیگر.
  • استفاده از hermes chat --provider <alternative> برای مسیریابی به بک‌اندی دیگر.

عبور از طول زمینه

علت: گفتگو برای پنجرهٔ زمینهٔ مدل بیش از حد طولانی شده یا Hermes طول زمینهٔ مدل را نادرست تشخیص داده است.

راه‌حل:

# Compress the current session
/compress

# Or start a fresh session
hermes chat

# Use a model with a larger context window
hermes chat --model openrouter/google/gemini-3-flash-preview

اگر این اتفاق در اولین گفتگوی طولانی رخ می‌دهد، ممکن است طول زمینهٔ مدل در Hermes نادرست باشد. مقدار تشخیص‌داده‌شده را بررسی کنید:

به خط آغازین CLI نگاه کنید؛ طول زمینهٔ تشخیص‌داده‌شده را نشان می‌دهد، مثلاً Context limit: 128000 tokens. همچنین می‌توانید در طول نشست با /usage آن را بررسی کنید.

سرورهای محلی مانند llama.cpp و Ollama که به‌جای خطا ساکت می‌شوند: وقتی ارائه‌دهنده درخواستی را به‌دلیل بزرگی بیش از حد رد می‌کند، Hermes گفتگو را فشرده و درخواست را بازسازی می‌کند. پیش از تلاش مجدد، Hermes اندازهٔ درخواست بازسازی‌شدهٔ کامل، شامل پرامپت سیستمی، اسکیماهای ابزار و پیام‌ها را دوباره می‌سنجد و اگر هنوز از آستانه بیشتر باشد، دورهای محدود دیگری از فشرده‌سازی اجرا می‌کند. اگر درخواست همچنان جا نشود، نوبت با پیام Context length exceeded: compression could not reduce the rebuilt request below the safe threshold پایان می‌یابد، به‌جای آنکه درخواست بزرگی ارسال شود که llama.cpp آن را بی‌سروصدا کوتاه کند؛ این حالت در لاگ سرور با stop processing: n_tokens = 65535, truncated = 1 دیده می‌شود. اگر با آن پیام روبه‌رو شدید، راه‌حل تقریباً همیشه همان context_length پیکربندی‌شدهٔ بالاست: آن را با مقدار واقعی -c یا --ctx-size سرور یکسان کنید.

برای اصلاح تشخیص زمینه، مقدار آن را صریح تنظیم کنید:

# In ~/.hermes/config.yaml
model:
  default: your-model-name
  context_length: 131072  # your model's actual context window

یا برای نقاط پایانی سفارشی، آن را به‌ازای هر مدل در ورودی ارائه‌دهنده اضافه کنید:

providers:
  my-server:
    api: "http://localhost:11434/v1"
    models:
      qwen3.5:27b:
        context_length: 64000

پیکربندی‌های قدیمی از فهرست قدیمی custom_providers: استفاده می‌کنند؛ این قالب همچنان پشتیبانی می‌شود و خودکار به providers: مهاجرت می‌کند.

برای نحوهٔ تشخیص خودکار و همهٔ گزینه‌های بازنویسی، تشخیص طول زمینه را ببینید.

WSL: گیت‌وی مدام قطع می‌شود یا hermes gateway start شکست می‌خورد

علت: پشتیبانی systemd در WSL قابل‌اعتماد نیست. بسیاری از نصب‌های WSL2، systemd فعال ندارند و حتی در صورت فعال‌بودن، ممکن است سرویس‌ها پس از راه‌اندازی مجدد WSL یا خاموش‌شدن هنگام بی‌کاری Windows باقی نمانند.

راه‌حل: به‌جای سرویس systemd، از حالت پیش‌زمینه استفاده کنید:

# Reattach later: tmux attach -t hermes

# Option 3: Background via nohup
nohup hermes gateway run > ~/.hermes/logs/gateway.log 2>&1 &

اگر بااین‌حال می‌خواهید systemd را امتحان کنید، مطمئن شوید فعال است:

  1. /etc/wsl.conf را باز کنید؛ اگر وجود ندارد آن را بسازید.
  2. این را اضافه کنید:
       [boot]
   systemd=true
  3. از PowerShell اجرا کنید: wsl --shutdown.
  4. ترمینال WSL خود را دوباره باز کنید.
  5. بررسی کنید: systemctl is-system-running باید running یا degraded نشان دهد.
نکته — شروع خودکار هنگام بوت Windows

برای شروع خودکار قابل‌اعتماد، از زمان‌بند وظایف Windows استفاده کنید تا هنگام ورود، WSL و گیت‌وی را اجرا کند:

  1. وظیفه‌ای بسازید که wsl -d Ubuntu -- bash -lc 'hermes gateway run' را اجرا کند.
  2. محرک آن را روی ورود کاربر تنظیم کنید.

۳ پروفایل‌ها

پروفایل‌ها چه تفاوتی با صرفاً تنظیم HERMES_HOME دارند؟

پروفایل‌ها لایه‌ای مدیریت‌شده روی HERMES_HOME هستند. می‌توانید پیش از هر فرمان، HERMES_HOME=/some/path را دستی تنظیم کنید، اما پروفایل‌ها همهٔ کارهای زیرساختی را برایتان انجام می‌دهند: ساخت ساختار پوشه‌ها، تولید نام‌های مستعار شل مانند hermes-work، ثبت پروفایل فعال در ~/.hermes/active_profile و همگام‌سازی خودکار به‌روزرسانی مهارت‌ها در همهٔ پروفایل‌ها. همچنین با تکمیل خودکار Tab یکپارچه‌اند، پس لازم نیست مسیرها را حفظ کنید.

آیا دو پروفایل می‌توانند توکن بات یکسان داشته باشند؟

خیر. هر پلتفرم پیام‌رسانی، مانند Telegram و Discord، به دسترسی انحصاری به توکن بات نیاز دارد. اگر دو پروفایل هم‌زمان از یک توکن استفاده کنند، گیت‌وی دوم نمی‌تواند وصل شود. برای هر پروفایل یک بات جدا بسازید؛ در Telegram برای ساخت بات‌های بیشتر با @BotFather گفتگو کنید.

آیا پروفایل‌ها حافظه یا نشست‌ها را به اشتراک می‌گذارند؟

خیر. هر پروفایل مخزن حافظه، پایگاه دادهٔ نشست و پوشهٔ مهارت‌های خودش را دارد و کاملاً ایزوله است. اگر می‌خواهید پروفایل جدیدی را با حافظه‌ها و نشست‌های موجود شروع کنید، با hermes profile create newname --clone-all همه‌چیز را از پروفایل فعلی کپی کنید یا --clone-from <profile> را اضافه کنید تا از پروفایل مبدأ مشخصی کپی شود.

همین جداسازی دلیل دیگری است که هرگز نباید دو ایجنت را روی یک پروفایل یا پوشهٔ خانگی Hermes اجرا کنید: هر دو خودکار در حافظه می‌نویسند و هرکدام در شروع نشست، نوشته‌های دیگری را بارگذاری می‌کند؛ بنابراین وضعیت ذخیره‌شدهٔ آن‌ها با هر نشست افت می‌کند. برای هر پروفایل یک ایجنت داشته باشید؛ برای حافظهٔ واقعاً مشترک میان ایجنت‌ها از ارائه‌دهندهٔ حافظهٔ خارجی استفاده کنید.

وقتی hermes update را اجرا می‌کنم چه می‌شود؟

hermes update آخرین کد را دریافت و وابستگی‌ها را یک‌بار، نه به‌ازای هر پروفایل، دوباره نصب می‌کند. سپس مهارت‌های به‌روزشده را خودکار در همهٔ پروفایل‌ها همگام می‌کند. کافی است hermes update را یک‌بار اجرا کنید؛ همهٔ پروفایل‌های ماشین را پوشش می‌دهد.

چند پروفایل می‌توانم اجرا کنم؟

محدودیت ثابتی وجود ندارد. هر پروفایل فقط یک پوشه در ~/.hermes/profiles/ است. محدودیت عملی به فضای دیسک و تعداد گیت‌وی‌های هم‌زمانی بستگی دارد که سیستم شما تحمل می‌کند؛ هر گیت‌وی یک فرایند سبک Python است. اجرای ده‌ها پروفایل مشکلی ندارد؛ هر پروفایل بی‌کار هیچ منبعی مصرف نمی‌کند.

۴ گردش‌کارها و الگوها

استفاده از مدل‌های مختلف برای وظایف مختلف؛ گردش‌کارهای چندمدلی

  model: "google/gemini-3-flash-preview"   # subagents use this model
  provider: "openrouter"                    # provider for subagents

اکنون وقتی به Hermes می‌گویید «یک رشته‌توییت دربارهٔ X برایم بنویس» و یک ساب‌ایجنت delegate_task ایجاد می‌کند، آن ساب‌ایجنت به‌جای مدل اصلی شما روی Gemini اجرا می‌شود. گفتگوی اصلی شما روی GPT-5.4 باقی می‌ماند.

می‌توانید در پرامپت هم صریح بگویید: «وظیفهٔ نوشتن پست‌های شبکه‌های اجتماعی دربارهٔ عرضهٔ محصولمان را واگذار کن. برای نوشتن متن اصلی از ساب‌ایجنتت استفاده کن.» ایجنت از delegate_task استفاده می‌کند که پیکربندی واگذاری را خودکار دریافت می‌کند.

برای تغییر موردی مدل بدون واگذاری، در CLI از /model استفاده کنید:

/model google/gemini-3-flash-preview    # switch for this session
# ... write your content ...
/model openai/gpt-5.4                   # switch back
هشدار

هر تغییر با /model کش پرامپت را بازنشانی می‌کند؛ کلید کش شامل مدل است، بنابراین اولین پیام پس از هر تغییر، کل گفتگو را با هزینهٔ کامل ورودی دوباره می‌خواند. در نشست‌های طولانی، واگذاری را ترجیح دهید، چون ساب‌ایجنت‌ها زمینهٔ تازهٔ خودشان را دارند، یا به‌جای جابه‌جایی مکرر رفت‌وبرگشتی نشست جدیدی شروع کنید.

برای اطلاعات بیشتر دربارهٔ روش واگذاری، واگذاری به ساب‌ایجنت را ببینید.

اجرای چند ایجنت روی یک شمارهٔ WhatsApp؛ اتصال به‌ازای هر گفتگو

سناریو: در OpenClaw چند ایجنت مستقل داشتید که به گفتگوهای مشخص WhatsApp متصل بودند؛ یکی برای گروه فهرست خرید خانواده و دیگری برای گفتگوی خصوصی. آیا Hermes این کار را انجام می‌دهد؟

محدودیت فعلی: هر پروفایل Hermes به شماره یا نشست WhatsApp خودش نیاز دارد. نمی‌توانید چند پروفایل را به گفتگوهای مختلف یک شمارهٔ WhatsApp متصل کنید؛ پل WhatsApp یعنی Baileys از یک نشست احرازهویت‌شده به‌ازای هر شماره استفاده می‌کند.

راه‌های جایگزین:

  1. از یک پروفایل با تغییر شخصیت استفاده کنید. فایل‌های زمینهٔ متفاوت AGENTS.md بسازید یا برای تغییر رفتار به‌ازای هر گفتگو از فرمان /personality استفاده کنید. ایجنت می‌بیند در کدام گفتگو قرار دارد و می‌تواند خود را تطبیق دهد.
  2. برای وظایف تخصصی از کارهای کرون استفاده کنید. برای پیگیری فهرست خرید، کار کرونی تنظیم کنید که گفتگوی مشخصی را پایش و فهرست را مدیریت کند؛ نیازی به ایجنت جداگانه نیست.
  3. از شماره‌های جدا استفاده کنید. اگر ایجنت‌های واقعاً مستقل نیاز دارید، هر پروفایل را با شمارهٔ WhatsApp خودش جفت کنید. شماره‌های مجازی سرویس‌هایی مانند Google Voice برای این کار مناسب‌اند.
  4. به‌جای آن از Telegram یا Discord استفاده کنید. این پلتفرم‌ها اتصال به‌ازای هر گفتگو را طبیعی‌تر پشتیبانی می‌کنند؛ هر گروه Telegram یا کانال Discord نشست خودش را دارد و می‌توانید روی یک حساب، چند توکن بات، یکی برای هر پروفایل، اجرا کنید.

برای جزئیات بیشتر، پروفایل‌ها و راه‌اندازی WhatsApp را ببینید.

کنترل آنچه در Telegram نمایش داده می‌شود؛ پنهان‌کردن لاگ‌ها و استدلال

سناریو: در Telegram به‌جای فقط خروجی نهایی، لاگ‌های اجرای گیت‌وی، استدلال Hermes و جزئیات فراخوانی ابزارها را می‌بینید.

راه‌حل: تنظیم display.tool_progress در config.yaml میزان نمایش فعالیت ابزار را کنترل می‌کند:

display:
  tool_progress: "off"   # options: off, new, all, verbose
  • off — فقط پاسخ نهایی؛ بدون فراخوانی ابزار، استدلال یا لاگ.
  • new — فراخوانی‌های جدید ابزار را هنگام وقوع، به‌صورت خلاصه‌های یک‌خطی نشان می‌دهد.
  • all — همهٔ فعالیت ابزار، از جمله نتایج، را نشان می‌دهد.
  • verbose — جزئیات کامل، از جمله آرگومان‌ها و خروجی ابزارها.

برای پلتفرم‌های پیام‌رسانی معمولاً off یا new مناسب است. پس از ویرایش config.yaml، گیت‌وی را دوباره راه‌اندازی کنید تا تغییرات اعمال شوند.

همچنین در صورت فعال‌بودن فرمان /verbose می‌توانید این وضعیت را به‌ازای هر نشست تغییر دهید:

display:
  tool_progress_command: true   # enables /verbose in the gateway

مدیریت مهارت‌ها در Telegram؛ محدودیت فرمان‌های اسلش

سناریو: Telegram محدودیت ۱۰۰ فرمان اسلش دارد و مهارت‌های شما از آن عبور می‌کنند. می‌خواهید مهارت‌های غیرضروری در Telegram را غیرفعال کنید، اما به نظر می‌رسد تنظیمات hermes skills config اثر نمی‌کنند.

راه‌حل: برای غیرفعال‌کردن مهارت‌ها به‌ازای هر پلتفرم از hermes skills config استفاده کنید. این فرمان در config.yaml می‌نویسد:

skills:
  disabled: []                    # globally disabled skills
  platform_disabled:
    telegram: [skill-a, skill-b]  # disabled only on telegram

پس از این تغییر، گیت‌وی را دوباره راه‌اندازی کنید؛ با hermes gateway restart یا توقف فرایند و اجرای دوباره. منوی فرمان‌های بات Telegram هنگام شروع بازسازی می‌شود.

نکته

توضیحات بسیار بلند مهارت‌ها در منوی Telegram به ۴۰ نویسه کوتاه می‌شوند تا محدودیت اندازهٔ دادهٔ ارسالی رعایت شود. اگر مهارت‌ها ظاهر نمی‌شوند، ممکن است مشکل از اندازهٔ کل دادهٔ ارسالی باشد، نه محدودیت تعداد ۱۰۰ فرمان؛ غیرفعال‌کردن مهارت‌های استفاده‌نشده به هر دو کمک می‌کند.

نشست‌های مشترک رشته‌گفتگو؛ چند کاربر، یک گفتگو

سناریو: رشته‌گفتگویی در Telegram یا Discord دارید که چند نفر بات را در آن منشن می‌کنند. می‌خواهید همهٔ منشن‌های آن رشته بخشی از یک گفتگوی مشترک باشند، نه نشست‌های جداگانه برای هر کاربر.

رفتار فعلی: Hermes در بیشتر پلتفرم‌ها نشست‌ها را با کلید شناسهٔ کاربر می‌سازد، بنابراین هر فرد زمینهٔ گفتگوی خودش را دارد. این طراحی برای حفظ حریم خصوصی و جداسازی زمینه است.

راه‌های جایگزین:

  1. از Slack استفاده کنید. نشست‌های Slack بر اساس رشته‌گفتگو کلیدگذاری می‌شوند، نه کاربر. چند کاربر در یک رشته، گفتگوی واحدی دارند؛ دقیقاً همان رفتاری که توصیف می‌کنید. این مناسب‌ترین گزینه است.
  2. از گفتگوی گروهی با یک کاربر فعال استفاده کنید. اگر یک نفر «اپراتور» مشخصی باشد که پرسش‌ها را منتقل می‌کند، نشست یکپارچه می‌ماند. دیگران می‌توانند گفتگو را بخوانند.
  3. از کانال Discord استفاده کنید. نشست‌های Discord بر اساس کانال کلیدگذاری می‌شوند، پس همهٔ کاربران یک کانال زمینهٔ مشترک دارند. برای گفتگوی مشترک، کانال اختصاصی در نظر بگیرید.

انتقال Hermes به ماشین دیگر

سناریو: روی یک ماشین مهارت‌ها، کارهای کرون و حافظه‌هایی ساخته‌اید و می‌خواهید همه‌چیز را به یک سیستم Linux اختصاصی جدید منتقل کنید.

راه‌حل:

  1. Hermes Agent را روی ماشین جدید نصب کنید:
       curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
  2. روی ماشین مبدأ پشتیبان کامل بسازید:
       hermes backup

    این کار از کل پوشهٔ ~/.hermes/ شامل پیکربندی، کلیدهای API، حافظه‌ها، مهارت‌ها، نشست‌ها و پروفایل‌ها، فایل zip می‌سازد و آن را در پوشهٔ خانگی شما با نام ~/hermes-backup-<timestamp>.zip ذخیره می‌کند.

  3. فایل zip را به ماشین جدید کپی و وارد کنید:
       # On the source machine
   scp ~/hermes-backup-<timestamp>.zip newmachine:~/

   # On the new machine
   hermes import ~/hermes-backup-<timestamp>.zip
  4. روی ماشین جدید، hermes setup را اجرا کنید تا کارکرد کلیدهای API و پیکربندی ارائه‌دهنده را بررسی کنید.

انتقال یک پروفایل به ماشین دیگر

سناریو: می‌خواهید یک پروفایل مشخص را منتقل یا به اشتراک بگذارید، نه کل نصب را.

# On the source machine
hermes profile export work ./work-backup.tar.gz

# Copy the file to the target machine, then:
hermes profile import ./work-backup.tar.gz work

پروفایل واردشده همهٔ پیکربندی، حافظه‌ها، نشست‌ها و مهارت‌های موجود در خروجی را خواهد داشت. اگر تنظیمات ماشین جدید متفاوت باشد، ممکن است لازم شود مسیرها را به‌روز کنید یا نزد ارائه‌دهندگان دوباره احراز هویت کنید.

rsync -av --exclude='hermes-agent' ~/.hermes/ newmachine:~/.hermes/
نکته

hermes backup حتی هنگام اجرای فعال Hermes، اسنپ‌شاتی سازگار تولید می‌کند. آرشیو بازیابی‌شده فایل‌های زمان اجرای مختص ماشین، مانند gateway.pid و cron.pid، را شامل نمی‌شود.

خطای رد دسترسی هنگام بارگذاری دوبارهٔ شل پس از نصب

سناریو: پس از اجرای نصب‌کنندهٔ Hermes، فرمان source ~/.zshrc خطای رد دسترسی می‌دهد.

علت: این معمولاً زمانی رخ می‌دهد که مجوزهای فایل ~/.zshrc یا ~/.bashrc نادرست باشند یا نصب‌کننده نتوانسته باشد به‌درستی در آن بنویسد. این مشکل اختصاصی Hermes نیست؛ مسئلهٔ مجوز فایل پیکربندی شل است.

راه‌حل:

# Check permissions
ls -la ~/.zshrc

# Fix if needed (should be -rw-r--r-- or 644)
chmod 644 ~/.zshrc

# Then reload
source ~/.zshrc

# Or just open a new terminal window — it picks up PATH changes automatically

اگر نصب‌کننده خط PATH را اضافه کرده اما مجوزها نادرست‌اند، می‌توانید آن را دستی اضافه کنید:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc

خطای ۴۰۰ در اولین اجرای ایجنت

سناریو: راه‌اندازی بدون مشکل تمام می‌شود، اما اولین تلاش برای گفتگو با HTTP 400 شکست می‌خورد.

علت: معمولاً نام مدل مطابقت ندارد؛ مدل پیکربندی‌شده نزد ارائه‌دهندهٔ شما وجود ندارد یا کلید API به آن دسترسی ندارد.

راه‌حل:

# Check what model and provider are configured
hermes config show | head -20

# Re-run model selection
hermes model

# Or test with a known-good model
hermes chat -q "hello" --model anthropic/claude-opus-4.7

اگر از OpenRouter استفاده می‌کنید، مطمئن شوید کلید API شما اعتبار مالی دارد. خطای ۴۰۰ از OpenRouter اغلب یعنی مدل به طرح پولی نیاز دارد یا شناسهٔ مدل اشتباه تایپی دارد.
