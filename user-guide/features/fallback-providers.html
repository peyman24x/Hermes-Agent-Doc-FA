ارائه‌دهندگان پشتیبان ‏(Fallback Providers)

‏Hermes Agent سه لایهٔ تاب‌آوری دارد که نشست‌هایتان را وقتی ارائه‌دهنده‌ها مشکل پیدا می‌کنند سرپا نگه می‌دارد:

  1. استخرهای credential — چرخش بین چند کلید API برای همان ارائه‌دهنده ‏(اول امتحان می‌شود)
  2. Fallback ی مدل اصلی — سوئیچ خودکار به جفت provider:model متفاوت وقتی مدل اصلی شکست می‌خورد
  3. Fallback تسک‌های کمکی — حل مستقل ارائه‌دهنده برای کارهای جانبی مثل بینایی، فشرده‌سازی و استخراج وب

استخرهای credential همان-ارائه‌دهنده rotation را هندل می‌کنند ‏(مثلاً چند کلید OpenRouter). این صفحه fallback ی بین-ارائه‌دهنده‌ای را پوشش می‌دهد. هر دو اختیاری و مستقل‌اند.

۱ Fallback مدل اصلی

وقتی ارائه‌دهندهٔ LLM اصلی‌تان به خطا بخورد — rate limit، ‏overload سرور، شکست auth، قطع اتصال — هرمس می‌تواند وسط نشست خودکار به یک زوج provider:model پشتیبان سوئیچ کند بدون از دست دادن گفتگو.

پیکربندی

ساده‌ترین مسیر مدیر تعاملی است:

hermes fallback

‏hermes fallback همان انتخاب‌گر ارائه‌دهندهٔ hermes model را دوباره مصرف می‌کند — همان فهرست، همان پرامپت‌های credential، همان اعتبارسنجی. زیرفرمان‌های add، ‏list (مستعار ls)، ‏remove (مستعار rm) و clear را برای مدیریت زنجیره دارید. تغییرات زیر فهرست top-level ی fallback_providers در config.yaml ماندگار می‌شوند.

اگر ترجیح می‌دهید YAML را دستی ویرایش کنید، فهرست top-level ی fallback_providers را به ~/.hermes/config.yaml اضافه کنید:

fallback_providers:
  - provider: openrouter
    model: anthropic/claude-sonnet-4

هر ورودی هم provider هم model می‌خواهد؛ ورودی‌های فاقد هر کدام نادیده گرفته می‌شوند.

📌 fallback_model در برابر fallback_providers

‏fallback_providers ‏(جمع، لیستی) شکل فعلی config است و چند fallback را به‌ترتیب امتحان می‌کند. ‏fallback_model (مفرد) کلید legacy تک-fallback است — هرمس هنوز برای سازگاری محترمش می‌شمارد ولی hermes fallback کلید فعلی fallback_providers را می‌نویسد و config ی legacy را موقع نوشتن migrate می‌کند. ست بودن هر دو: fallback_providers اولویت دارد.

کی fallback فعال می‌شود

fallback خودکار وقتی فعال می‌شود که مدل اصلی با این‌ها شکست بخورد:

  • Rate limit ها ‏(HTTP ۴۲۹) — بعد از اتمام تلاش‌های retry
  • خطاهای سرور ‏(HTTP ۵۰۰، ۵۰۲، ۵۰۳) — بعد از اتمام retry ها
  • شکست‌های auth ‏(HTTP ۴۰۱، ۴۰۳) — فوری ‏(retry کردن بی‌فایده است)
  • Not found ‏(HTTP ۴۰۴) — فوری
  • پاسخ‌های نامعتبر — وقتی API مرتباً پاسخ بدفرم یا خالی برگرداند

وقتی فعال شود هرمس: credential های ارائه‌دهندهٔ fallback را حل، کلاینت API جدید می‌سازد، مدل/ارائه‌دهنده/کلاینت را in-place عوض، شمارندهٔ retry را reset و گفتگو را ادامه می‌دهد. سوئیچ یکپارچه است — تاریخچهٔ گفتگو، فراخوانی ابزار و زمینه حفظ می‌شود؛ ایجنت دقیقاً از همان‌جا ادامه می‌دهد فقط با مدلی متفاوت.

⚠️ fallback کش پرامپت را ریست می‌کند

کش‌های پرامپت به مدل ‏(و روی اکثر ارائه‌دهنده‌ها حساب) سرویس‌کنندهٔ درخواست کلید می‌خورند. وقتی fallback شلیک کند provider:model جدید هیچ پیشوند کش‌شده‌ای برای گفتگوی شما ندارد، پس درخواست بعدی کل تاریخچه را با قیمت کامل توکن ورودی بازمی‌خواند نه نرخ تخفیفی ‎۷۵–۹۰٪‎ کش. همین‌طور وقتی نوبت تمام و primary بازیابی شود — اولین درخواست روی primary هم re-read کامل است ‏(مگر TTL کش primary منقضی نشده باشد). اجتناب‌ناپذیر است — هزینهٔ زنده ماندن حین outage — ولی دلیل اینکه نشست بلندی که بین ارائه‌دهنده‌ها بالا-پایین می‌رود محسوساً گران‌تر از نشست ثابت است.

ℹ️ Per-Turn نه Per-Session

fallback ‏scope شده-به-نوبت است: هر پیام جدید کاربر با primary بازیابی‌شده شروع می‌شود. اگر primary وسط نوبت شکست بخورد fallback فقط برای آن نوبت فعال می‌شود. در پیام بعدی هرمس دوباره primary را امتحان می‌کند. داخل یک نوبت حداکثر یک بار فعال می‌شود — شکست fallback هم یعنی هندل خطای عادی ‏(retry ها سپس پیام خطا). این از حلقه‌های failover آبشاری داخل نوبت جلوگیری و به primary هر نوبت شانس تازه می‌دهد.

retry ی per-turn ‏reset-aware است: وقتی credential های primary زمان ریست rate-limit گزارش کنند که هنوز نرسیده ‏(پنجره‌های اشتراکی مثل بلوک‌های ۵ ساعته Claude Pro/Max یا سقف‌های هفتگی Codex اینها را ساعت/روز گزارش می‌کنند)، هرمس retry ی محکوم‌به-شکست را skip و تا عبور ریست روی fallback می‌ماند — جلوگیری از دو سوئیچ بی‌فایده ‏(و دو invalidation کش) per-turn. لحظهٔ عبور ریست، نوبت بعد خودکار به primary برمی‌گردد. ‏429 های گذری بدون زمان ریست رفتار قبلی را دارند: cooldown کوتاه سپس retry هر نوبت.

مثال‌ها

# OpenRouter as fallback for Anthropic native:
model:
  provider: anthropic
  default: claude-sonnet-4-6

fallback_providers:
  - provider: openrouter
    model: anthropic/claude-sonnet-4

# Nous Portal as fallback for OpenRouter:
model:
  provider: openrouter
  default: anthropic/claude-opus-4

fallback_providers:
  - provider: nous

# Local model as fallback for cloud:

    key_env: LOCAL_API_KEY

# Codex OAuth as fallback:
fallback_providers:
  - provider: openai-codex
    model: gpt-5.3-codex

برای زنجیرهٔ fallback اصلی هیچ متغیر محیطی وجود ندارد — انحصاراً از طریق config.yaml یا hermes fallback پیکربندی کنید. عمدی است: پیکربندی fallback انتخابی آگاهانه است نه چیزی که export ی کهنه شل override کند.

۲ Fallback تسک‌های کمکی

هرمس برای کارهای جانبی مدل‌های سبک جدا مصرف می‌کند. هر تسک زنجیرهٔ حل ارائه‌دهندهٔ خودش را دارد که به‌عنوان سیستم fallback داخلی عمل می‌کند.

زنجیرهٔ خودآشکاری

وقتی provider ی تسک auto ‏(پیش‌فرض) باشد، هرمس اول main provider + main model را برای آن تسک کمکی امتحان می‌کند. غیرقابل‌رسید یا بعداً با خطای ظرفیت‌گونه شکست بخورد، قبل از زنجیرهٔ کشف داخلی به سیاست fallback ی پیکربندی‌شده-توسط-کاربر احترام می‌گذارد:

Main provider + main model → auxiliary.<task>.fallback_chain →
fallback_providers / fallback_model → built-in auxiliary discovery chain

زنجیرهٔ کشف متن داخلی: ‏OpenRouter ← Nous Portal ← Custom endpoint ← Codex OAuth ← API-key providers ‏(z.ai، Kimi، MiniMax، Xiaomi MiMo، Hugging Face، Anthropic) ← تسلیم.
زنجیرهٔ بینایی داخلی: ‏Main provider (اگر vision-capable) ← OpenRouter ← Nous Portal ← Codex OAuth ← Anthropic ← Custom endpoint ← تسلیم.

پیکربندی ارائه‌دهنده‌های کمکی

هر تسک مستقلاً در config.yaml پیکربندی می‌شود — الگوی یکسان provider/model/base_url برای همه؛ هر تسک می‌تواند fallback_chain اختصاصی اعلام کند و در نبودش provider: auto از زنجیرهٔ top-level استفاده می‌کند. فشرده‌سازی زیر auxiliary.compression است.

Override ی مستقیم نقطهٔ پایانی

برای هر تسک کمکی، ست کردن base_url حل ارائه‌دهنده را کلاً bypass و درخواست‌ها را مستقیم به آن endpoint می‌فرستد؛ api_key پیکربندی‌شده برای auth مصرف و در نبودش به OPENAI_API_KEY برمی‌گردد. برای endpoint های سفارشی OPENROUTER_API_KEY دوباره‌مصرف نمی‌شود.

۳ Fallback ظرفیت، فشرده‌سازی، delegation و cron

Fallback ظرفیت-خطای تسک‌های کمکی

با ست کردن ارائه‌دهندهٔ صریح کمکی ‏(مثل auxiliary.vision.provider: glm)، هرمس آن را انتخاب ترجیحی شما می‌داند — ولی اگر ارائه‌دهنده واقعاً نتواند درخواست را سرو کند به‌خاطر خطای ظرفیت ‏(۴02 payment required، ‏اتلاف سهمیه روزانه ۴۲۹، شکست اتصال)، هرمس از یک زنجیره لایه‌ای عبور می‌کند نه شکست بی‌صدا:

  1. ارائه‌دهندهٔ aux ی اصلی — پیکربندی‌شدهٔ شما ‏(اول، همیشه)
  2. ‏auxiliary.<task>.fallback_chain — فهرست override ی per-task شما اگر نوشته باشید
  3. Main agent provider + model — تور ایمنی آخر ‏(همیشه امتحان می‌شود حتی بدون chain)
  4. هشدار + re-raise — شکست همهٔ لایه‌ها یعنی لاگ WARNING ی «all fallbacks exhausted» و پرتاب مجدد خطای اصلی

‏429 های گذری با Retry-After قیدِ-درخواست تلقی می‌شوند نه مشکل ظرفیت — به انتخاب صریح شما احترام می‌گذارند و نردبان fallback را trigger نمی‌کنند. فقط اتلاف سهمیه روزانه/ماهانه، خطاهای پرداخت و شکست اتصال از گیت ارائه‌دهنده-صریح عبور می‌کنند. برای کاربران provider: auto زنجیرهٔ خودآشکاری جای گام‌های ۲–۳ اجرا می‌شود و گام اولش همین main agent model است.

اگر fallback_chain متفاوتی از «اول مدل ایجنت اصلی» می‌خواهید صریحاً پیکربندی‌اش کنید — هر ورودی حداقل provider لازم دارد و model/base_url/api_key اختیاری‌اند. هر ورودی می‌تواند timeout ی خودش را هم declare کند تا fallback ی کندتر-ولی-قابل‌اعتماد بودجه واقعی بگیرد.

خطاهای سهمیه‌ای که هرماس capacity-equivalent ی ۴۰۲ می‌شناسد: Bedrock/LiteLLM «Too many tokens per day»، Vertex AI/GCP «quota exceeded / resource exhausted / RESOURCE_EXHAUSTED» و عمومی «daily quota / quota_exceeded». عبارت متفاوت ارائه‌دهنده‌تان trigger نشد؟ bug است — با رشتهٔ دقیق خطا issue بزنید.

Fallback ی فشرده‌سازی زمینه

فشرده‌سازی زمینه از بلوک auxiliary.compression برای کنترل مدل/ارائه‌دهندهٔ خلاصه‌سازی استفاده می‌کند. ‏config های قدیمی با compression.summary_model/summary_provider/summary_base_url خودکار به auxiliary.compression.* migrate می‌شوند ‏(نسخهٔ config ۱۷). اگر هیچ ارائه‌دهنده‌ای برای فشرده‌سازی موجود نباشد هرمس نوبت‌های میانی گفتگو را بدون تولید خلاصه drop می‌کند نه اینکه نشست را بیندازد.

Override ی ارائه‌دهندهٔ delegation

زیرایجنت‌های spawn‌شده توسط delegate_task زنجیرهٔ fallback اصلی والد را به ارث می‌برند. برای مسیریابی زیرایجنت‌ها به زوج primary متفاوت جهت بهینه‌سازی هزینه delegation.provider و delegation.model را ست کنید.

ارائه‌دهندگان cron job ها

cron job ها موقع ساخت ایجنت زنجیرهٔ fallback_providers پیکربندی‌شده‌تان را به ارث می‌برند. برای primary ی متفاوت per-job، provider و model را روی خود job تنظیم کنید.
