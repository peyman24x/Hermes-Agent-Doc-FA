لاین‌های worker کانبان

لاین worker کلاسی از پروسه است که dispatcher کانبان می‌تواند task ها را به آن مسیریابی کند. هر لاین یک هویت دارد ‏(رشتهٔ assignee)، یک مکانیزم spawn و قراردادی برای اینکه با task بعد از spawn چه باید بکند.

این صفحه همان قرارداد است و برای دو مخاطب وجود دارد:

  • اپراتورهایی که انتخاب می‌کنند کدام لاین‌ها را به یک board سیم کنند ‏(کدام پروفایل‌ها ساخته شوند، کدام assignee ها استفاده شوند).
  • نویسندگان افزونه/یکپارچه‌سازی که می‌خواهند شکل لاین جدیدی بیفزایند ‏(worker CLI که Codex/Claude Code/OpenCode را wrap می‌کند، worker بازبینی کانتینری، سرویس غیر-هرمسی که از طریق API کار می‌کشد).

اگر خودِ کد worker را می‌نویسید — ایجنتی که داخل یک لاین اجرا می‌شود — چرخهٔ حیات کانبان و جزئیات مرجع خودکار در پرامپت سیستمی worker تزریق می‌شوند ‏(بلوک ‏KANBAN_GUIDANCE در ‏agent/prompt_builder.py مخزن).

۱ سلسله‌مراتب

text
Hermes Kanban  =  canonical task lifecycle + audit trail
Worker lane    =  implementation executor for one assigned card
Reviewer       =  human or human-proxy that gates "done"
GitHub PR      =  upstreamable artifact (optional, for code lanes)

‏Hermes Kanban مالک حقیقت چرخهٔ حیات است — ‏ready ← ‏running ← ‏review/blocked/done/archived. لاین‌های worker کار را اجرا می‌کنند ولی هرگز مالک آن حقیقت نیستند؛ هر کاری می‌کنند از طریق ابزارهای ‏kanban_* ‏(یا برای worker های خارجی غیر-هرمس، از طریق API) به کرنل کانبان برمی‌گردد. بازبین‌ها گذر از «تغییر کد نوشته شد» به «task تمام شد» را گیت می‌زنند.

۲ یک لاین چه چیزی فراهم می‌کند

برای تبدیل‌شدن به یک لاین worker کانبان، یکپارچه‌سازی باید سه چیز فراهم کند:

۱. رشتهٔ assignee

‏dispatcher مقدار ‏task.assignee را یا با نام پروفایل هرمس ‏(شکل پیش‌فرض لاین) یا شناسهٔ ثبت‌شدهٔ غیر-spawn‌پذیر تطبیق می‌دهد ‏(شکل لاین افزونه — «افزودن لاین worker خارجی CLI» پایین). ‏task هایی که assignee‌شان حل نمی‌شود روی ‏ready با رویداد ‏skipped_nonspawnable رها می‌شوند تا اپراتور board اصلاحشان کند؛ بی‌صدا دور ریخته یا توسط fallback دلخواه اجرا نمی‌شوند.

۲. مکانیزم spawn

برای لاین‌های پروفایل هرمس، ‏_default_spawn مربوط به dispatcher مقدار ‏hermes -p <assignee> chat -q <prompt> ‏(یا فرم ماژول معادل وقتی shim ‏hermes روی ‏$PATH نیست) را داخل workspace قفل‌شدهٔ task اجرا می‌کند با این env ها:

متغیرحمل‌کننده
HERMES_KANBAN_TASKشناسهٔ task‌ای که worker رویش کار می‌کند
HERMES_KANBAN_DBمسیر مطلق فایل SQLite به‌ازای-board
HERMES_KANBAN_BOARDslug مربوط به board
HERMES_KANBAN_WORKSPACES_ROOTریشهٔ درخت workspace مربوط به board
HERMES_KANBAN_WORKSPACEمسیر مطلق workspace همین task
HERMES_KANBAN_RUN_IDشناسهٔ run فعلی ‏(برای گیتی چرخهٔ حیات)
HERMES_KANBAN_CLAIM_LOCKرشتهٔ قفل claim ‏(<host>:<pid>:<uuid>)
HERMES_PROFILEنام پروفایل خود worker ‏(برای انتساب نویسندهٔ kanban_comment)
HERMES_TENANTnamespace مربوط به tenant اگر task داشته باشد

برای لاین‌های غیر-هرمس ‏(ثبت‌شده از طریق افزونه) افزونه ‏spawn_fn callable خودش را می‌دهد که ‏task، ‏workspace و ‏board می‌گیرد و pid اختیاری برای تشخیص کرش برمی‌گرداند.

۳. پایان‌دهندهٔ چرخهٔ حیات

هر claim باید دقیقاً به یکی از این‌ها بینجامد:

  • ‏kanban_complete(summary=..., metadata=...) — task موفق می‌شود، وضعیت به ‏done flip می‌شود.
  • ‏kanban_request_review(summary=..., metadata=..., reviewer=...) — پیاده‌سازی همان-کارت کامل و وارد بازبینی درجه‌یک می‌شود؛ وضعیت به ‏review flip می‌شود. dispatcher مهارت همراه‌بستهٔ ‏sdlc-review را لود می‌کند مگر ‏kanban.review_dispatch خاموش شده باشد. بازبین با ‏kanban_complete تأیید، با ‏kanban_request_changes بازکاری actionable برمی‌گرداند یا مانع خارجی واقعی را با ‏kanban_block تشدید می‌کند.
  • ‏kanban_block(reason=...) — task منتظر ورودی انسانی است، وضعیت به ‏blocked flip می‌شود. dispatcher وقتی ‏kanban_unblock اجرا شود دوباره spawn می‌کند.
  • پروسهٔ worker بدون فراخوانی ابزار خارج می‌شود. کرنل آن را reap و ‏crashed ‏(PID مرد)، ‏gave_up ‏(مدارشکن شکست متوالی تریگر شد) یا ‏timed_out ‏(max_runtime گذشت) صادر می‌کند. این مسیر شکست است؛ worker های سالم اینجا تمام نمی‌شوند.

کرنل کانبان الزام می‌کند دقیقاً یکی از این‌ها هر run را پایان دهد. worker‌ای که هیچ‌کدام را صدا نزند و عادی خارج شود crashed تلقی می‌شود.

۳ خروجی‌ها و handoff بازبینی

برای task های تغییر-دهندهٔ کد، مدل بازبینی رمزگذاری‌شده توسط گراف task را انتخاب کنید:

  • بازبینی همان-کارت: ‏kanban_request_review(summary=..., metadata=..., reviewer=...) را صدا بزنید. Task بدون دست‌زدن به حساب‌داری تکرار-بلاک وارد ‏review می‌شود. ‏dispatcher به‌طور پیش‌فرض آن را با مهارت همراه‌بستهٔ ‏sdlc-review claim می‌کند. بازبین با ‏kanban_complete تأیید، ‏kanban_request_changes(reason=...) را برای بستن run بازبینی و برگرداندن task به پیاده‌ساز اصلی صدا می‌زند یا فقط برای تشدید خارجی واقعی بلاک می‌کند.
  • کارت پایین‌دستیِ از-قبل‌ساختهٔ بازبینی/QA/release: ‏kanban_show شناسه‌های فرزند را فهرست می‌کند؛ قبل از انتخاب اکشن پایانی آن کارت‌ها را با ‏kanban_show(task_id=...) بازرسی کنید. وقتی فرزندی فاز پایین‌دستیِ بازبینی/QA/release است، روی فاز پیاده‌سازی ‏kanban_complete را صدا بزنید. آن فرزند تا این والد done/archived نشود نمی‌تواند ارتقا یابد. بازبینی همان-کارت را هم‌زمان درخواست نکنید و هرگز والد را با ‏review-required: چسبناک-بلاک نکنید — هر انتخاب، لاین پایین‌دستی را معلق یا تکراری می‌کند.
  • board های فقط-انسانی: ‏kanban.review_dispatch: false را ست کنید. Task می‌تواند در review بماند تا انسانی تأیید کند یا با ‏reopen-review/داشبورد به ready/todo برگردد.

هر دو مدل بازبینی handoff ساختاریافته‌شان را روی خود جابه‌جایی چرخهٔ حیات حمل می‌کنند. رمزها، توکن‌ها یا PII خام داخل summary یا metadata نگذارید؛ ردیف‌های run ماندگارند.

‏KANBAN_GUIDANCE تزریق‌شده هر دو شکل گراف، ‏kanban_complete، حلقهٔ بازبینی همان-کارت و ‏kanban_block برای موانع واقعی را پوشش می‌دهد.

۴ لاگ‌ها و رد حسابرسی

‏dispatcher خروجی stdout/stderr مربوط به worker هر task را در ‏<board-root>/logs/<task_id>.log می‌نویسد. لاگ‌ها از متادیتای کانبان قابل حسابرسی‌اند:

  • ردیف‌های ‏task_runs مقدار ‏log_path، exit code ‏(هرجا موجود)، summary و metadata را حمل می‌کنند.
  • ردیف‌های ‏task_events هر جابه‌جایی وضعیت را حمل می‌کنند ‏(promoted، ‏claimed، ‏heartbeat، ‏completed، ‏blocked، ‏review_requested، ‏changes_requested، ‏review_reopened، ‏gave_up، ‏crashed، ‏timed_out، ‏reclaimed، ‏claim_extended).
  • ‏kanban_show هر دو را برمی‌گرداند، پس بازبین ‏(یا worker پیگیری) که task را می‌خواند کل تاریخچه را بدون نیاز به دسترسی داشبورد می‌گیرد.

داشبورد تاریخچهٔ اجرا را با خلاصه‌ها، بلوک‌های metadata و badge های وضعیت خروج رندر می‌کند. کاربران CLI برای دنبال‌کردن زنده ‏hermes kanban tail <task_id> و برای فهرست تاریخی تلاش‌ها ‏hermes kanban runs <task_id> را اجرا می‌کنند.

۵ اشکال لاین موجود

لاین پروفایل هرمس ‏(پیش‌فرض)

شکلی که امروز هر worker کانبانی می‌گیرد: assignee نام پروفایلی است، dispatcher ‏hermes -p <profile> را spawn، worker بلوک پرامپت سیستمی KANBAN_GUIDANCE را خودکار تزریق‌شده می‌گیرد و برای پایان دادن به run از ابزارهای ‏kanban_* استفاده می‌کند. بدون setup فراتر از تعریف پروفایل.

وقتی برای ناوگانتان پروفایل می‌سازید نام‌هایی متناسب با نقشی که می‌خواهید ارکستراتور به آن مسیریابی کند انتخاب کنید. ارکستراتور ‏(وقتی وجود دارد) نام‌های پروفایل شما را از طریق ‏hermes profile list کشف می‌کند — سیستم هیچ فهرست ثابتی فرض نمی‌کند ‏(سمت ارکستراتور قرارداد جزء KANBAN_GUIDANCE تزریق‌شده است).

لاین پروفایل ارکستراتور

تخصصی‌سازی لاین پروفایل: ارکستراتور پروفایل هرمسی است whose تول‌ست شامل ‏kanban ولی فاقد ‏terminal/file/code/web برای پیاده‌سازی است. کارش تجزیه هدف سطح-بالا به task های فرزند از طریق ‏kanban_create + ‏kanban_link و عقب‌نشینی است. مهارت ارکستراتور قواعد ضدوسوسه را رمزگذاری می‌کند.

۶ افزودن لاین worker خارجی CLI

سیم‌کشی یک ابزار CLI غیر-هرمس ‏(Codex CLI، ‏Claude Code CLI، ‏OpenCode CLI، اجراکنندهٔ مدل-کدنویس محلی و...) به‌عنوان لاین worker کانبانی هنوز مسیر هموارشده‌ای نیست. تابع spawn dispatcher قابل‌افزودن است ‏(spawn_fn پارامتری روی ‏dispatch_once است) و افزونه می‌تواند ‏spawn_fn خودش را برای یک assignee غیر-هرمس ثبت کند ولی کار یکپارچه‌سازی اطراف — wrap کردن exit code مربوط به CLI داخل فراخوانی‌های ‏kanban_complete/kanban_block، نگاشت قواعد workspace/sandbox مربوط به CLI روی env ‏HERMES_KANBAN_WORKSPACE مربوط به dispatcher، هندل احراز و سیاست به‌ازای-CLI — هنوز طراحی per-integration است.

اگر افزودن لاین CLI را مد نظر دارید issue ای با توصیف CLI مشخص و گردش‌کار موردنظرتان باز کنید. قرارداد بالا محدودیت‌هایی است که هر چنین لاینی باید ارضا کند؛ شکل پیاده‌سازی ‏(یک افزونه به‌ازای هر CLI در برابر افزونهٔ عمومی runner-CLI پارامتری‌شده با config) باز است.

issue تاریخی این موضوع ‏#19931 و PR مخصوص-Codexِ بسته‌نشده-ولی-ادغام‌نشدهٔ ‏#19924 است — این‌ها پیشنهاد معماری اصلی را شرح می‌دهند ولی runner‌ای فرود نیاوردند.

۷ حالت‌های شکستی که dispatcher هندل می‌کند

تا نویسندگان لاین مجبور به بازپیاده‌سازی این‌ها نباشند:

  • TTL claim کهنه — worker‌ای که claim می‌کند و سپس هرگز heartbeat/completes/blocks نمی‌شود بعد از ‏DEFAULT_CLAIM_TTL_SECONDS ‏(پیش‌فرض ۱۵ دقیقه) پس گرفته می‌شود — ولی فقط اگر پروسهٔ worker واقعاً مرده باشد. worker زنده ‏(مدل کند که ۲۰+ دقیقه در یک فراخوانی LLM بدون-ابزار می‌گذراند) به‌جای کشته شدن claim‌اش تمدید می‌شود؛ فقط PID مرده پس گرفته می‌شود.
  • worker کرش‌کرده — worker‌ای whose PID میزبان-محلی غیبش زده توسط ‏detect_crashed_workers تشخیص و reap می‌شود؛ task مقدار ‏consecutive_failures افزایش و ممکن است وقتی مدارشکن تریگر شود خودکار بلاک شود.
  • retry در سطح-run — وقتی taskی retry می‌شود ‏(پس از بلاک، پس از کرش، پس از reclaim) worker می‌تواند پارامتر ‏expected_run_id روی ابزارهای پایانی را استفاده کند تا اگر run خودش قبلاً جایگزین شده سریع شکست بخورد.
  • حداکثر runtime به‌ازای-task — ‏task.max_runtime_seconds زمان دیواری هر run را مستقل از زنده‌بودن PID سخت سقف می‌زند. worker های واقعاً بن‌بست‌شده را می‌گیرد که extension ‏live-PID وگرنه اجازه ادامه‌شان می‌داد.
  • تشخیص task معلق — task ‏ready‌ای که assignee‌اش ظرف ‏kanban.stranded_threshold_seconds ‏(پیش‌فرض ۳۰ دقیقه) هیچ claim‌ای تولید نکند در ‏hermes kanban diagnostics به‌صورت هشدار ‏stranded_in_ready ظاهر می‌شود. شدت در ۲× آستانه به خطا و در ۶× به critical تشدید می‌شود. assignee های غلط‌تایپی، پروفایل‌های حذف‌شده و pool های worker خارجیِ پایین را در یک سیگنال می‌گیرد — مستقل-از-هویت، بدون لیست مجاز به‌ازای-board برای نگهداشت.
  • بن‌بست وابستگی بازبینی قدیمی — والدِ چسبناک-بلاک‌شده با ‏review-required: در حالی که یک یا چند فرزند مستقیم همچنان گیتی-والد در todo هستند بلافاصله خطای ‏review_dependency_deadlock تولید می‌کند. تشخیص فقط-خواندنی است: تکمیل فاز تمام‌شده یا unlink کردن یال غلط را پیشنهاد می‌دهد ولی هرگز بلاک کاربر را خودکار برنمی‌دارد.

۸ مرتبط
