اجراگر App-Server ی Codex ‏(اختیاری)

هرمس می‌تواند به‌صورت اختیاری نوبت‌های openai/* و ‏openai-codex/* را به app-server ی Codex CLI بسپارد به‌جای اجرای حلقهٔ ابزار خودش. با فعال شدن، فرمان‌های ترمینال، ویرایش فایل‌ها، sandboxing و فراخوانی‌های ابزار MCP همگی داخل runtime ی Codex اجرا می‌شوند — هرمس پوستهٔ دور آن می‌شود ‏(پایگاه‌دادهٔ نشست‌ها، دستورات اسلش، گیت‌وی، حافظه و بازبینی مهارت‌ها).

این فقط-با-انتخاب شماست. رفتار پیش‌فرض هرمس تا فلگ را نزنید تغییری نمی‌کند. هرمس هرگز خودکار شما را روی این runtime نمی‌برد.

💡 از OpenAI Codex استفاده نمی‌کنید؟

‏hermes setup --portal یک بک‌اند غیر-Codex با Claude/Gemini/و… در یک قدم پیکربندی می‌کند. بخش Nous Portal را ببینید.

۱ چرا

  • اجرای نوبت‌های ایجنتی OpenAI روی اشتراک ChatGPT تان ‏(بدون نیاز به کلید API) با همان جریان auth ی که Codex CLI استفاده می‌کند.
  • استفاده از تول‌ست و sandbox خودِ Codex — ‏shell برای ترمینال/خواندن/نوشتن/جستجو، ‏apply_patch برای ویرایش‌های ساختاریافته، ‏update_plan برای برنامه‌ریزی؛ همه داخل sandboxing ی seatbelt/landlock.
  • پلاگین‌های native ی Codex — Linear، ‏GitHub، ‏Gmail، ‏Calendar، ‏Canva و… — نصب‌شده با codex plugin خودکار مهاجرت و در نشست هرمس شما فعال می‌شوند.
  • ابزارهای غنی‌تر هرمس هم همراه می‌آیند — ‏web_search، ‏web_extract، اتوماسیون مرورگر، بینایی، تولید تصویر، مهارت‌ها و TTS از طریق یک callback ی MCP کار می‌کنند. Codex برای ابزارهایی که داخلی ندارد به هرمس callback می‌زند.
  • نوخه‌های حافظه و مهارت همچنان کار می‌کنند — رویدادهای Codex به شکل پیام هرمس تصویر می‌شوند تا حلقهٔ خودبهبودی transcript ای عادی ببیند.

۲ مدل واقعاً چه ابزارهایی دارد

این همان بخشی است که بیشتر کاربران اول می‌خواهند بدانند. وقتی این runtime روشن است، مدلی که نوبت شما را اجرا می‌کند سه منبع مستقل ابزار دارد:

۱. تول‌ست داخلی Codex ‏(همیشه روشن)

اینها همراه خودِ codex app-server ارسال می‌شوند — بدون دخالت هرمس، بدون MCP، بدون پلاگین. هر پنج‌تا از لحظهٔ شروع runtime در دسترس‌اند:

  • ‏shell — اجرای هر فرمان شل داخل sandbox. مدل با همین فایل می‌خواند ‏(cat، ‏head، ‏tail)، می‌نویسد ‏(echo > foo، heredoc ها)، جستجو می‌کند ‏(find، ‏rg، ‏grep)، بین دایرکتوری‌ها حرکت می‌کند ‏(ls، ‏cd)، build می‌گیرد، پروسه‌ها را مدیریت می‌کند و هر کار دیگری که در bash می‌کردید.
  • ‏apply_patch — اعمال یک diff ساختاریافتهٔ چندفایلی در فرمت patch ی Codex. مدل برای ویرایش‌های کدی غیرساده ‏(افزودن تابع، refactor بین چند فایل) از این استفاده می‌کند؛ heredoc های شل برای نوشتن‌های یک‌باره همچنان در دسترس‌اند.
  • ‏update_plan — ردیاب todo/برنامه داخلی codex. معادل ابزار todo هرمس، اما کاملاً داخل runtime ی codex مدیریت می‌شود.
  • ‏view_image — بارگذاری یک فایل تصویر محلی در گفتگو تا مدل آن را ببیند.
  • ‏web_search — codex وقتی پیکربندی شده باشد جستجوی وب داخلی خودش را دارد. هرمس هم ‏web_search ‏(پشت‌بنده Firecrawl) را از طریق callback پایین expose می‌کند؛ مدل هر کدام را ترجیح دهد برمی‌دارد.

پس هر کاری که با ترمینال می‌کردید — خواندن/نوشتن/جستجو/یافتن/اجرا — codex به‌صورت native انجام می‌دهد. پروفایل sandbox ‏(پیش‌فرض :workspace هنگام فعال کردن runtime) کنترل می‌کند چه چیزی قابل‌نوشتن است.

۲. پلاگین‌های native ی Codex ‏(مهاجرت‌یافته از نصب codex plugin شما)

وقتی runtime را فعال کنید هرمس RPC ی plugin/list ی codex را پرس‌وجو و برای هر پلاگین نصب‌شده‌تان یک ورودی [plugins."<name>@openai-curated"] می‌نویسد. خود پلاگین‌ها توسط codex مدیریت و یک بار از طریق UI خود codex مجوزدهی می‌شوند.

نمونه‌ها ‏(همان‌هایی که thread ی OpenClaw «قابل-فیلم‌شدن-در-یوتیوب» خواند):

  • Linear — یافتن/به‌روزرسانی issue ها
  • GitHub — جستجوی کد، دیدن PR ها، کامنت
  • Gmail — خواندن/ارسال ایمیل
  • Google Calendar — ساخت/یافتن رویدادها
  • تقویم/ایمیل Outlook — همان شکل از طریق connector ی Microsoft
  • Canva — تولید طرح گرافیکی
  • …و هر چیز دیگری که با codex plugin marketplace add openai-curated + ‏codex plugin install ... نصب کرده باشید

چه چیزی مهاجرت نمی‌کند:

  • پلاگین‌هایی که هنوز نصب نکرده‌اید — اول در Codex نصبشان کنید.
  • ورودی‌های marketplace اپ ChatGPT ‏(app/list) — اینها به لطف auth ی حسابتان از قبل داخل codex فعاله.

۳. Callback ی ابزار هرمس ‏(سرور MCP ثبت‌شده در ~/.codex/config.toml)

هرمس خودش را به‌عنوان یک سرور MCP ثبت می‌کند تا codex برای ابزارهایی که همراه ندارد به او callback بزند. از طریق callback در دسترس است:

  • ‏web_search / ‏web_extract — پشت‌بنده Firecrawl؛ برای محتوای ساختاریافته معمولاً تمیزتر از scraping است.
  • ‏browser_navigate / ‏browser_click / ‏browser_type / ‏browser_press / ‏browser_snapshot / ‏browser_scroll / ‏browser_back / ‏browser_get_images / ‏browser_console / ‏browser_vision — اتوماسیون کامل مرورگر از طریق Camofox یا Browserbase.
  • ‏vision_analyze — صدا زدن یک مدل بینایی جدا برای بررسی یک تصویر ‏(متفاوت از view_image ی codex که آن را وارد گفتگو می‌کند).
  • ‏image_generate — تولید تصویر از طریق زنجیرهٔ پلاگین image_gen هرمس.
  • ‏skill_view / ‏skills_list — خواندن از کتابخانهٔ مهارت‌های هرمس.
  • ‏text_to_speech — TTS از طریق ارائه‌دهندهٔ پیکربندی‌شدهٔ هرمس.

وقتی مدل یکی از اینها را بخواهد، codex زیرپروسهٔ hermes_tools_mcp_server را از طریق stdio MCP spawn می‌کند، فراخوانی از مسیر model_tools.handle_function_call() دیسپچ می‌شود ‏(همان مسیر کدِ runtime پیش‌فرض هرمس) و نتیجه مثل هر پاسخ MCP دیگری به codex برگردانده می‌شود.

چه چیزی روی این runtime در دسترس نیست

این چهار ابزار هرمس برای dispatch به زمینهٔ AIAgent ی درحال‌اجرا ‏(وضعیت وسط-حلقه) نیاز دارند و یک callback ی MCP ی stateless نمی‌تواند آنها را براند. وقتی به هرکدام لازم دارید به runtime پیش‌فرض برگردید ‏(/codex-runtime auto):

  • ‏delegate_task — spawn کردن زیرایجنت‌ها
  • ‏memory — انبار حافظهٔ پایدار هرمس
  • ‏session_search — جستجوی بین-نشستی
  • ‏todo — انبار todo ی هرمس ‏(update_plan ی codex معادل در-runtime است)

۳ قابلیت‌های گردش‌کار ‏(/goal، کانبان، کرون)

‏/goal ‏(حلقهٔ Ralph)

روی این runtime کار می‌کند. اهداف در state_meta کلیدخورده-با-شناسه-نشست ماندگارند، پرامپت ادامه از طریق run_conversation() مثل یک پیام عادی کاربر پس داده می‌شود و codex نوبت بعدی را native اجرا می‌کند. قاضی هدف از طریق کلاینت کمکی اجرا می‌شود ‏(پیکربندی با auxiliary.goal_judge در config.yaml)، مستقل از اینکه کدام runtime فعال است. رأیِ «blocked, needs user input» ی قاضی راه فرار تمیزی است اگر codex روی تأییدها بماند.

یک نکته: هر پرامپت ادامه یک نوبت codex تازه است، یعنی codex سیاست تأیید فرمان را از صفر دوباره ارزیابی می‌کند. اگر هدف بلندمدتی با نوشتن‌های زیاد دارید انتظار پرامپت‌های تأیید بیشتری نسبت به یک تسک تک-نشسته داشته باشید. ‏default_permissions = ":workspace" را ست کنید ‏(هرمس هنگام فعال کردن runtime خودکار همین کار را می‌کند) تا نوشتن‌های سادهٔ workspace نیازمند پرامپت نباشند.

کانبان ‏(dispatch چندایجنتی worktree)

روی این runtime کار می‌کند، با یک وابستگی ظریف. dispatcher کانبان هر کارگر را به‌صورت زیرپروسهٔ جداگانهٔ hermes chat -q ای spawn می‌کند که config کاربر را می‌خواند — یعنی اگر model.openai_runtime: codex_app_server سراسری ست شده باشد، کارگرها هم روی runtime ی codex بالا می‌آیند.

چه چیزهایی داخل یک کارگرِ codex-runtime کار می‌کند:

  • تول‌ست کامل codex ‏(shell، ‏apply_patch، ‏update_plan، ‏view_image، ‏web_search) — کارگر کار واقعی تسکش را native انجام می‌دهد
  • پلاگین‌های مهاجرت‌یافتهٔ codex — Linear، ‏GitHub و…
  • Callback ی ابزار هرمس برای browser_*، ‏vision، ‏image_gen، ‏skills، ‏TTS

چه چیزهایی هم به لطف expose شدن در callback کار می‌کند:

  • ‏kanban_complete / ‏kanban_block / ‏kanban_comment / ‏kanban_heartbeat — ابزارهای تحویل کارگر. اینها HERMES_KANBAN_TASK را از env می‌خوانند ‏(dispatcher ست می‌کند)، دسترسی را درست gate و در SQLite ی هر بردِ پین‌شده توسط HERMES_KANBAN_DB می‌نویسند. بدون اینها در callback، کارگرِ روی این runtime می‌توانست تسکش را انجام دهد ولی نمی‌توانست گزارش کند و تا timeout ی dispatcher معلق می‌ماند.
  • ‏kanban_show / ‏kanban_list — پرس‌وجوهای فقط-خواندنی برد برای اینکه کارگر زمینهٔ خودش را چک کند.
  • ‏kanban_create / ‏kanban_unblock / ‏kanban_link — عملیات مخصوص orchestrator. برای ایجنت‌های ارکستراتورِ روی runtime ی codex که باید تسک جدید dispatch کنند در دسترس‌اند.

ابزارهای kanban با متغیر محیطی HERMES_KANBAN_TASK که dispatcher ست می‌کند gate می‌شوند — آن متغیر به زیرپروسهٔ codex منتقل ‏(codex env را به ارث می‌برد) و از آنجا به زیرپروسهٔ سرور MCP ی hermes-tools ی spawn‌شده می‌رسد. پس ابزارها شناسهٔ تسک درست را می‌بینند و درست gate می‌کنند. برای کارگرهای Codex app-server هرمس وقتی HERMES_KANBAN_TASK حاضر است override های باریک sandbox ی app-server هم پاس می‌دهد: حفظ sandboxing ی workspace-write، افزودن دایرکتوری DB برد به‌علاوهٔ هر مسیر Kanban ی که dispatcher پین کرده به‌عنوان ریشه‌های اضافی قابل‌نوشتن ‏(HERMES_KANBAN_WORKSPACES_ROOT، ‏HERMES_KANBAN_WORKSPACE، قدیمیِ ‏HERMES_KANBAN_ROOT — بدون تکرار، اول DB-dir)، و نگه داشتن شبکه به‌طور پیش‌فرض خاموش. این از راه‌حل شکنندهٔ ‏:danger-no-sandbox جلوگیری و همزمان اجازه می‌دهد ‏kanban_complete/kanban_block دیتابیس برد را به‌روز کنند و کارگرها گزارش/محصولات را زیر مانت‌های workspace بیرون از دایرکتوری DB بنویسند ‏(مثلاً /media/.../kanban-workspaces/... روی یک درایو جدا — ‏issue ‎#۲۷۹۴۱).

Cron jobs

مخصوصاً تست نشده. cron job ها از مسیر ‏cronjob ← ‏AIAgent.run_conversation اجرا می‌شوند، همان مسیر کدِ CLI. اگر config ی cron job مقدار openai_runtime: codex_app_server داشته باشد روی codex اجرا می‌شود. همان قواعد دسترسی ابزار برقرارند — داخلی‌های codex + پلاگین‌ها + callback ی MCP کار می‌کنند، ابزارهای حلقهٔ ایجنت ‏(delegate_task، ‏memory، ‏session_search، ‏todo) نه. اگر cron job تان به اینها تکیه دارد، cron را به پروفایلی محدود کنید که runtime پیش‌فرض دارد.

نمایش زنده

اگرچه حلقهٔ ایجنت داخل زیرپروسهٔ Codex اجرا می‌شود، runtime جریان رویداد Codex را به همان مسیر نمایشی که runtime پیش‌فرض استفاده می‌کند پل می‌زند:

  • دلتاهای زندهٔ دستیار، استدلال ‏(شامل دلتاهای summary) و رویدادهای شروع/اتمام ابزار با-ID-پایدار در TUI، دسکتاپ و گیت‌وی‌های پیام‌رسانی همزمان با اجرای نوبت ظاهر می‌شوند. تصویرگر تاریخچهٔ فقط-تکمیل جدا می‌ماند تا نشستِ از-سر-گرفته‌شده همان کارت‌های ابزار نمایش‌داده‌شده در طول نوبت را hydrate کند.
  • کامنتاری گیت‌وی وقتی استریم توکن خاموش است هم مرئی می‌ماند و رویدادهای زندهٔ ابزار حتی برای نوتیفیکیشن‌های تخلیه‌شده قبل از یک درخواست تأیید forward می‌شوند. کامنتاری به display.show_commentary احترام می‌گذارد.

۵ پیش‌نیازها

  1. نصب بودن Codex CLI: 
    npm i -g @openai/codex
codex --version   # 0.130.0 or newer
  2. ورود OAuth ی Codex. زیرپروسهٔ codex ‏~/.codex/auth.json را می‌خواند. دو راه پر کردن آن: 
    codex login                  # writes tokens to ~/.codex/auth.json
    ‏

    ‏hermes auth add openai-codex ی خود هرمس در ~/.hermes/auth.json می‌نویسد — نشست جداست. اگر نکرده‌اید ‏codex login را جداگانه اجرا کنید.

  3. ‏(اختیاری) نصب پلاگین‌های Codex موردنظر. هنگام فعال کردن runtime، هرمس هر پلاگین curated ی که از قبل با Codex CLI نصب کرده‌اید خودکار مهاجرت می‌دهد: 
    codex plugin marketplace add openai-curated
# then via codex's TUI, install Linear / GitHub / Gmail / etc.
    هرمس آنها را کشف و ورودی‌های [plugins."<name>@openai-curated"] را به‌طور خودکار در ~/.codex/config.toml می‌نویسد.

۶ فعال‌سازی

داخل یک نشست هرمس:

/codex-runtime codex_app_server

این فرمان:

  • نصب بودن CLI ی codex را بررسی می‌کند ‏(اگر نباشد با راهنمای نصب بلاک می‌کند).
  • ‏model.openai_runtime: codex_app_server را در config.yaml شما ماندگار می‌کند.
  • سرورهای MCP کاربر را از ~/.hermes/config.yaml به ‏~/.codex/config.toml مهاجرت می‌دهد.
  • پلاگین‌های native ی Codex نصب‌شده را کشف و مهاجرت می‌دهد ‏(Linear، ‏GitHub، ‏Gmail، ‏Calendar، ‏Canva و…) با پرس‌وجوی RPC ی plugin/list ی Codex.
  • ابزارهای خود هرمس را به‌عنوان یک سرور MCP ثبت می‌کند تا زیرپروسهٔ codex برای ابزارهایی که همراه ندارد callback بزند.
  • ‏default_permissions = ":workspace" را می‌نویسد تا sandbox نوشتن داخل workspace را بدون پرامپت برای هر عملیات اجازه دهد.
  • می‌گوید چه چیزهایی مهاجرت داده شد. روی نشستِ بعدی اثر می‌گذارد — ایجنت کش‌شدهٔ فعلی runtime قبلی را نگه می‌دارد تا کش‌های پرامپت سالم بمانند.

مترادف‌ها: ‏/codex-runtime on، ‏/codex-runtime off، ‏/codex-runtime auto.

برای دیدن وضعیت فعلی بدون تغییر چیزی:

/codex-runtime

می‌توانید دستی هم در ~/.hermes/config.yaml ست کنید:

yaml
model:
  openai_runtime: codex_app_server   # default is "auto" (= Hermes runtime)

۷ حلقهٔ خودبهبودی ‏(نوخه‌های حافظه + مهارت)

خودبهبودی پس‌زمینه‌ای هرمس روی آستانه‌های شمارنده شلیک می‌شود:

  • هر ۱۰ پرامپت کاربر ← یک ایجنت بازبینی fork شده به گفتگو نگاه می‌کند و تصمیم می‌گیرد چیزی باید در حافظه ذخیره شود یا نه.
  • هر ۱۰ تکرار ابزار داخل یک نوبت ← همان ایده ولی برای مهارت‌ها ‏(نوشتن‌های skill_manage).

هر دو روی runtime ی codex همچنان کار می‌کنند. مسیر codex هر item تکمیل‌شدهٔ ‏commandExecution / ‏fileChange / ‏mcpToolCall / ‏dynamicToolCall را به یک پیام مصنوعی «assistant tool_call» + «tool» تصویر می‌کند، پس موقع اجرای بازبینی همان شکلی را می‌بیند که روی runtime پیش‌فرض هرمس می‌بیند.

چطور wiring معادل می‌ماند:

runtime پیش‌فرضruntime ی Codex
افزایش _turns_since_memoryبه‌ازای هر پرامپت کاربر، در pre-loop ی run_conversationهمان مسیر کد، قبل از early-return
افزایش _iters_since_skillبه‌ازای هر تکرار ابزار در حلقهٔ chat-completionsبا turn.tool_iterations بعد از برگشتن نوبت codex
تریگر حافظه ‏(_turns_since_memory >= _memory_nudge_interval)در pre-loop محاسبه، بعد از پاسخ شلیکدر pre-loop محاسبه، عبور به helper ی codex
تریگر مهارت ‏(_iters_since_skill >= _skill_nudge_interval)بعد از حلقه محاسبهبعد از نوبت codex محاسبه
فراخوانی _spawn_background_review(messages_snapshot=..., review_memory=..., review_skills=...)وقتی یکی از تریگرها شلیک کندوقتی یکی از تریگرها شلیک کند دقیقاً مشابه

یک جزئیات: خودِ fork بازبینی باید ابزارهای حلقهٔ ایجنت هرمس ‏(memory، ‏skill_manage) را صدا بزند که dispatch اختصاصی هرمس می‌خواهند. پس وقتی ایجنت والد روی codex_app_server است، fork بازبینی به codex_responses تنزل می‌یابد — همان اعتبارنامه‌های OAuth، همان ارائه‌دهندهٔ openai-codex، ولی مستقیم با Responses API ی OpenAI حرف می‌زند تا هرمس مالک حلقه باشد و ابزارهای حلقهٔ ایجنت کار کنند. برای کاربر نامرئی است.

اثر خالص: runtime ی codex را فعال کنید و نوخه‌های حافظه + مهارت دقیقاً مثل قبل شلیک می‌کنند.

۸ نحوهٔ کار تأییدها

‏Codex قبل از اجرای فرمان‌ها یا اعمال patch ها تأیید می‌خواهد. اینها به پرامپت استاندارد «Dangerous Command» هرمس ترجمه می‌شوند:

╭───────────────────────────────────────╮
│ Dangerous Command                     │
│                                       │
│ /bin/bash -lc 'echo hello > foo.txt'  │
│                                       │
│ ❯ 1. Allow once                       │
│   2. Allow for this session           │
│   3. Deny                             │
│                                       │
│ Codex requests exec in /your/cwd      │
╰───────────────────────────────────────╯
  • Allow once ← تأیید فقط همین فرمان.
  • Allow for this session ← Codex برای فرمان‌های مشابه دوباره پرامپت نمی‌دهد.
  • Deny ← فرمان رد می‌شود؛ Codex در حالت فقط-خواندنی ادامه می‌دهد.

برای تأییدهای apply_patch ‏(ویرایش فایل)، وقتی codex داده را از طریق item ی مربوطهٔ fileChange بدهد، هرمس خلاصه‌ای از تغییرات نشان می‌دهد ‏(1 add, 1 update: /tmp/new.py, /tmp/old.py).

۹ پروفایل‌های مجوز

‏Codex سه پروفایل مجوز داخلی دارد:

  • ‏:read-only — بدون نوشتن؛ هر فرمان شل تأیید می‌خواهد
  • ‏:workspace — نوشتن داخل فضای‌کاری فعلی بدون پرامپت مجاز است ‏(پیش‌فرض هرمس هنگام فعال کردن runtime)
  • ‏:danger-no-sandbox — اصلاً بدون sandbox ‏(استفاده نکنید مگر اینکه بدانید چه می‌کنید)

می‌توانید پیش‌فرض را در ~/.codex/config.toml بیرون از بلوک مدیریت‌شدهٔ هرمس بازنویسی کنید:

toml
default_permissions = ":read-only"

‏(هرمس بازنویسی شما را تا وقتی بیرون نشانگرهای # managed by hermes-agent زندگی کند در مهاجرت‌های بعدی حفظ می‌کند.)

۱۰ تسک‌های کمکی و هزینهٔ توکن اشتراک ChatGPT

وقتی این runtime با ارائه‌دهندهٔ openai-codex روشن باشد، تسک‌های کمکی ‏(تولید عنوان، فشرده‌سازی زمینه، آشکارسازی خودکار بینایی، fork بازبینی خودبهبودی پس‌زمینه) هم به‌طور پیش‌فرض از اشتراک ChatGPT شما عبور می‌کنند، چون کلاینت کمکی هرمس وقتی override ی per-task ست نباشد از ارائه‌دهنده/مدل اصلی استفاده می‌کند.

این مخصوص ‏codex_app_server نیست — برای مسیر موجودِ codex_responses هم صادق است — ولی اینجا محسوس‌تر است چون صریحاً برای صورتحساب اشتراک شرکت کرده‌اید.

برای مسیریابی تسک‌های کمکی مشخص به مدلی ارزان‌تر/متفاوت، override های صریح در ~/.hermes/config.yaml ست کنید:

yaml
auxiliary:
  title_generation:
    provider: openrouter
    model: google/gemini-3-flash-preview
  compression:
    provider: openrouter
    model: google/gemini-3-flash-preview
  vision:
    provider: openrouter
    model: google/gemini-3-flash-preview
  goal_judge:
    provider: openrouter
    model: google/gemini-3-flash-preview

fork بازبینی خودبهبودی از طریق _current_main_runtime() runtime اصلی را به ارث می‌برد و هرمس خودکار آن را از codex_app_server به codex_responses تنزل می‌دهد ‏(تا fork واقعاً بتواند memory و skill_manage — ابزارهای حلقهٔ ایجنت خود هرمس — را صدا بزند). آن fork مگر اینکه تسک‌های کمکی را جایی دیگر مسیریابی کرده باشید، همچنان از auth اشتراک شما استفاده می‌کند.

۱۱ ویرایش امن ~/.codex/config.toml

هرمس هرچه مدیریت می‌کند بین دو کامنت نشانگر می‌پیچد:

# managed by hermes-agent — `hermes codex-runtime migrate` regenerates this section
default_permissions = ":workspace"
[mcp_servers.filesystem]
...
[plugins."github@openai-curated"]
...
# end hermes-agent managed section

هر چیز بیرون آن بلوک متعلق به شماست. اجرای دوبارهٔ مهاجرت ‏(از طریق /codex-runtime codex_app_server یا هر بار toggle کردن runtime) بلوک مدیریت‌شده را در جا جایگزین ولی محتوای کاربری بالا و پایینش را verbatim حفظ می‌کند. یعنی می‌توانید:

  • سرورهای MCP خودتان را که هرمس نمی‌شناسد اضافه کنید
  • ‏default_permissions را اگر پرامپت‌گرفتن را ترجیح می‌دهید روی :read-only بگذارید
  • گزینه‌های مخصوص codex را پیکربندی کنید ‏(model، ‏providers، ‏otel و…)
  • پروفایل‌های مجوز تعریف‌شده-توسط-کاربر در جدول‌های [permissions.<name>] اضافه کنید

هر چه داخل بلوک مدیریت‌شده اضافه کنید در مهاجرت بعدی له می‌شود. اگر تغییری لازم دارید که ویرایش بلوک مدیریت‌شده را طلب می‌کند، یک issue ثبت کنید تا پیچش را اضافه کنیم.

۱۲ راه‌اندازی چند-پروفایل / چند-مستأجر

به‌طور پیش‌فرض هرمس زیرپروسهٔ codex را فارغ از پروفایل فعال هرمس به ~/.codex/ اشاره می‌دهد. یعنی ‏hermes -p work و ‏hermes -p personal همان auth، پلاگین‌ها و config ی Codex را شریک‌اند. برای بیشتر کاربران رفتار درست همین است — مطابق اجرای مستقیم CLI ی codex.

اگر ایزوله‌سازی Codex per-profil می‌خواهید ‏(auth جدا، پلاگین‌های نصب‌شده جدا، config جدا)، ‏CODEX_HOME را صریحاً per-profil ست کنید. تمیزترین راه اشاره به دایرکتوری زیر HERMES_HOME تان است:

# Inside the work profile, you might wrap hermes:
CODEX_HOME=~/.hermes/profiles/work/codex hermes chat

یک بار باید codex login را با همان CODEX_HOME دوباره اجرا کنید تا توکن‌های OAuth در محل مخصوص-پروفایل فرود بیایند. بعد از آن ‏hermes -p work روی وضعیت Codex ی ایزوله کار می‌کند.

این را خودکار scope نمی‌کنیم چون جابه‌جا کردن ~/.codex/ ی موجود، auth ی CLI ی Codex کاربر را بی‌سروصدا باطل می‌کند — هر کسی که قبلاً codex login کرده بود باید دوباره احراز هویت می‌شد. opt-in امن‌تر از غافلگیر کردن کاربران است.

۱۳ عبور متغیر محیطی HOME

هرمس هنگام spawn کردن زیرپروسهٔ app-server ی codex مقدار HOME را بازنویسی نمی‌کند ‏(از os.environ.copy() استفاده و فقط CODEX_HOME و ‏RUST_LOG را overlay می‌کند). یعنی:

  • فرمان‌هایی که codex با ابزار shell اجرا می‌کند HOME واقعی کاربر را می‌بینند و ‏~/.gitconfig، ‏~/.gh/، ‏~/.aws/، ‏~/.npmrc و… را درست پیدا می‌کنند.
  • وضعیت داخلی codex از طریق CODEX_HOME ‏(که به‌طور پیش‌فرض به ~/.codex/ اشاره دارد) ایزوله می‌ماند.

این همان مرزی است که OpenClaw بعد از کمی آزمایش اولیه به آن رسید: وضعیت Codex را ایزوله کن، خانهٔ کاربر را ول کن. ‏(Cf. openclaw/openclaw#81562.)

۱۴ مهاجرت سرور MCP و پلاگین‌های native ی Codex

config ی mcp_servers هرمس خودکار به قالب TOML ی مورد انتظار Codex ترجمه می‌شود. مهاجرت هر بار که runtime را فعال کنید اجرا و idempotent است — اجراهای دوباره بخش مدیریت‌شده را جایگزین می‌کنند ولی config ی Codex ی ویرایش‌شده توسط کاربر را حفظ می‌کنند.

چه چیزی ترجمه می‌شود:

هرمس ‏(config.yaml)Codex ‏(config.toml)
command + ‏args + ‏envtransport ی stdio
url + ‏headerstransport ی streamable_http
timeouttool_timeout_sec
connect_timeoutstartup_timeout_sec
enabled: falseenabled = false

چه چیزی مهاجرت نمی‌شود:

  • کلیدهای مخصوص-هرمس مثل sampling ‏(کلاینت MCP ی Codex معادلی ندارد — با یک هشدار per-server رها می‌شوند).

مهاجرت پلاگین‌های native ی Codex

پلاگین‌های نصب‌شده با codex plugin ‏(Linear، ‏GitHub، ‏Gmail، ‏Calendar، ‏Canva و…) از طریق RPC ی plugin/list ی Codex کشف می‌شوند. برای هر پلاگینی که installed: true باشد، هرمس یک بلوک [plugins."<name>@openai-curated"] می‌نویسد که آن را در نشست هرمس شما فعال می‌کند.

یعنی: وقتی دوستتان می‌گوید «Calendar و GitHub را در Codex CLI ام راه انداخته‌ام» و runtime ی codex هرمس را فعال کند، هرمس آنها را خودکار فعال می‌کند. هیچ پیکربندی دوباره لازم نیست.

چه چیزی مهاجرت نمی‌شود:

  • پلاگین‌هایی که هنوز نصب نکرده‌اید — اول در Codex نصبشان کنید.
  • پلاگین‌هایی که codex گزارششان ‏availability != AVAILABLE است ‏(نصب خراب، ‏OAuth منقضی، حذف از marketplace و…). برای جلوگیری از نوشتن config ای که موقع فعال شدن شکست می‌خورد رد می‌شوند.
  • ورودی‌های marketplace اپ ChatGPT ‏(نتایج per-account ی app/list — به لطف auth حسابتان از قبل داخل codex فعاله).
  • OAuth ی پلاگین — هر پلاگین را یک بار داخل خود Codex مجوز می‌دهید؛ هرمس کاری با اعتبارنامه‌ها ندارد.

۱۵ Callback ی ابزار هرمس ‏(سرور جدید MCP)

تول‌ست داخلی Codex عملیات شل/فایل/patch را پوشش می‌دهد ولی جستجوی وب، اتوماسیون مرورگر، بینایی، تولید تصویر و… ندارد. تا اینها در یک نوبت codex قابل‌استفاده بمانند، هرمس خودش را به‌عنوان یک سرور MCP در ~/.codex/config.toml ثبت می‌کند:

[mcp_servers.hermes-tools]
command = "/path/to/python"
args = ["-m", "agent.transports.hermes_tools_mcp_server"]
env = { HERMES_HOME = "/your/.hermes", PYTHONPATH = "...", HERMES_QUIET = "1" }
startup_timeout_sec = 30.0
tool_timeout_sec = 600.0

وقتی مدل web_search ‏(یا دیگر ابزار expose‌شدهٔ هرمس) را صدا بزند، codex زیرپروسهٔ hermes_tools_mcp_server را از طریق stdio spawn، درخواست از مسیر model_tools.handle_function_call() دیسپچ و نتیجه مثل هر پاسخ MCP دیگری به codex تصویر می‌شود.

ابزارهای موجود از طریق callback: ‏web_search، ‏web_extract، ‏browser_navigate، ‏browser_click، ‏browser_type، ‏browser_press، ‏browser_snapshot، ‏browser_scroll، ‏browser_back، ‏browser_get_images، ‏browser_console، ‏browser_vision، ‏vision_analyze، ‏image_generate، ‏skill_view، ‏skills_list، ‏text_to_speech.

ابزارهای غیرموجود: ‏delegate_task، ‏memory، ‏session_search، ‏todo. اینها برای dispatch به زمینهٔ AIAgent ی درحال‌اجرا نیاز دارند و callback ی stateless نمی‌تواند براندشان. وقتی لازم شدند از runtime پیش‌فرض هرمس ‏(/codex-runtime auto) استفاده کنید.

۱۶ غیرفعال‌سازی

هر زمان برگردید:

/codex-runtime auto

روی نشست بعدی مؤثر است. بلوک مدیریت‌شدهٔ Codex در ~/.codex/config.toml می‌ماند تا بعداً بدون از دست دادن config دوباره فعال کنید — یا اگر ترجیح می‌دهید دستی حذفش کنید.

۱۷ محدودیت‌ها

این runtime بتای انتخابی است. تا Hermes Agent ۲۰۲۶٫۵ + Codex CLI ۰٫۱۳۰٫۰ کارا:

  • گفتگوهای چند-نوبتی
  • تأییدهای ‏commandExecution و ‏fileChange ‏(apply_patch) از طریق UI هرمس
  • فراخوانی ابزار MCP ‏(تأییدشده روی @modelcontextprotocol/server-filesystem و callback جدید hermes-tools)
  • مهاجرت پلاگین‌های native ی Codex ‏(تأییدشده روی موجودی Linear / GitHub / Calendar)
  • مسیرهای Deny/cancel
  • چرخهٔ toggle روشن/خاموش
  • شمارنده‌های نوخهٔ حافظه و مهارت ‏(تأیید زنده با تست‌های یکپارچگی)
  • web_search هرمس از طریق codex ‏(تأیید زنده: «OpenAI Codex CLI – Getting Started» سر-تا-سر برگشت)

محدودیت‌های شناخته‌شده:

  • auth هرمس و auth codex دو نشست جداهستند. تمیزترین UX هر دو را می‌خواهد: هم codex login هم ‏hermes auth add openai-codex ‏(runtime از نشست codex برای فراخوانی LLM استفاده می‌کند). انتخاب طراحی عمدی در _import_codex_cli_tokens ی هرمس است — هرمس وضعیت OAuth را با codex CLI شریک نمی‌کند تا در refresh توکن له هم نکنند.
  • ‏delegate_task، ‏memory، ‏session_search، ‏todo روی این runtime در دسترس نیستند. به زمینهٔ AIAgent درحال‌اجرا نیاز دارند که callback ی stateless نمی‌دهد. وقتی لازم شدند ‏/codex-runtime auto.
  • بدون پیش‌نمایش inline ی patch در پرامپت‌های تأیید وقتی codex changeset را ردیابی نمی‌کند. پارامترهای تأیید fileChange ی codex همیشه changeset را حمل نمی‌کنند. هرمس داده را از نوتیفیکیشن item/started مربوطه تا حد امکان کش می‌کند ولی اگر تأیید قبل از استریم شدن item برسد، پرامپت به whatever ی reason ی codex fallback می‌کند.
  • لغو زیر-ثانیه تضمین نمی‌شود. interrupt های وسط-استریم ‏(Ctrl+C وقتی codex در حال پاسخ دادن است) از طریق turn/interrupt فرستاده می‌شوند ولی اگر codex پیام نهایی را flush کرده باشد، پاسخ را به هر حال می‌گیرید.

باگ پیدا کردید؟ یک issue باز کنید همراه خروجی hermes logs --since 5m. در عنوان codex-runtime را بنویسید تا triage راحت شود.
