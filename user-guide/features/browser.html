اتوماسیون مرورگر ‏(Browser Automation)

هرمس ایجنت یک تول‌ست کامل اتوماسیون مرورگر با گزینه‌های بک‌اند متعدد دارد:

  • حالت ابری Browserbase از طریق ‏Browserbase برای مرورگرهای ابریِ مدیریت‌شده و ابزارهای ضد-بات
  • حالت ابری Browser Use از طریق ‏Browser Use به‌عنوان ارائه‌دهندهٔ جایگزین مرورگر ابری
  • حالت Browser Use از طریق ‏CLI ی ۳٫۰ ی Browser Use — هارنس جدیدی که در تسک‌های وب SOTA است؛ Chrome محلی شما یا مرورگرهای ابری Browser Use را اتومات می‌کند
  • حالت ابری Firecrawl از طریق ‏Firecrawl برای مرورگرهای ابری با scraping داخلی
  • حالت محلی Camofox از طریق ‏Camofox برای مرور ضددیدگی محلی ‏(فریب اثر انگشت مبتنی بر Firefox)
  • موتور محلی Lightpanda از طریق ‏Lightpanda — مرورگر headless ساخته‌شده از صفر در Zig برای ماشین‌ها؛ راه‌اندازی آنی، حافظهٔ ‎۱۶×‎ کمتر و سرعت ‎۹×‎ بیشتر از Chrome با fallback خودکار Chrome برای اقداماتی که هنوز پشتیبانی نمی‌کند
  • CDP خانوادهٔ Chromium محلی — وصل کردن ابزارهای مرورگر به نمونهٔ خودتان از Chrome، ‏Brave، ‏Chromium یا Edge با ‏/browser connect
  • حالت مرورگر محلی از طریق CLI ی ‏agent-browser و یک نصب محلی Chromium

در همهٔ حالت‌ها ایجنت می‌تواند به سایت‌ها برود، با عناصر صفحه تعامل کند، فرم پر کند و اطلاعات استخراج کند.

۱ نمای کلی

صفحات به‌صورت درخت‌های دسترس‌پذیری ‏(snapshot های متنی) نمایش داده می‌شوند که آنها را برای ایجنت‌های LLM ایده‌آل می‌کند. عناصر تعاملی ref ID می‌گیرند ‏(مثل ‏@e1، ‏@e2) که ایجنت برای کلیک و تایپ استفاده می‌کند.

قابلیت‌های کلیدی:

  • اجرای ابری چند-ارائه‌دهنده‌ای — Browserbase، ‏Browser Use یا Firecrawl — بدون نیاز به مرورگر محلی
  • یکپارچگی محلی خانوادهٔ Chromium — اتصال به مرورگر درحال‌اجرا ی Chrome، ‏Brave، ‏Chromium یا Edge از طریق CDP برای مرور دستی
  • استلث داخلی — اثر انگشت تصادفی، حل CAPTCHA، پروکسی‌های رزیدنشیال ‏(Browserbase)
  • ایزوله‌سازی نشست — هر تسک نشست مرورگری خودش را می‌گیرد
  • پاکسازی خودکار — نشست‌های بی‌کار بعد از timeout بسته می‌شوند
  • تحلیل بینایی — اسکرین‌شات + تحلیل AI برای درک بصری

۲ راه‌اندازی

💡 مشترکان Nous

اگر اشتراک پولی Nous Portal دارید می‌توانید اتوماسیون مرورگر را از طریق Tool Gateway بدون هیچ کلید API جداگانه‌ای استفاده کنید. نصب‌های تازه می‌توانند ‏hermes setup --portal را اجرا کنند تا وارد شوند و همهٔ ابزارهای گیت‌وی را یکجا روشن کنند؛ نصب‌های موجود می‌توانند از طریق ‏hermes model یا ‏hermes tools مقدار Nous Subscription را به‌عنوان ارائه‌دهندهٔ مرورگر بردارند.

حالت ابری Browserbase

برای استفاده از مرورگرهای ابری مدیریت‌شدهٔ Browserbase اضافه کنید:

# Add to ~/.hermes/.env
BROWSERBASE_API_KEY=***
BROWSERBASE_PROJECT_ID=your-project-id-here

اعتبارنامه‌هایتان را از ‏browserbase.com بگیرید.

حالت ابری Browser Use

برای استفاده از Browser Use به‌عنوان ارائه‌دهندهٔ مرورگر ابری اضافه کنید:

# Add to ~/.hermes/.env
BROWSER_USE_API_KEY=***

کلید API تان را از ‏browser-use.com بگیرید.

📌 انتخاب ارائه‌دهنده

کلیدهای .env بالا فقط اعتبارنامه تأمین می‌کنند. مرورگر ابری فعال با انتخاب ‏browser.cloud_provider نوشته‌شده توسط ‏hermes tools ← Browser Automation برگزیده می‌شود ‏(browserbase، ‏browser-use، ‏camofox یا nous برای اشتراک Nous). به‌محض وجود یک انتخاب، افزودن یا حذف کلید ارائه‌دهنده را عوض نمی‌کند — و ارائه‌دهندهٔ انتخاب‌شده با کلید غایب خطایی همراه راهنمای اجرای hermes tools می‌دهد نه اینکه بی‌سروصدا تغییر مسیر دهد. راه‌اندازی‌های هرگز-پیکربندی‌نشده همچنان از اعتبارنامه‌های موجود خودآشکار می‌شوند.

حالت Browser Use ‏(پیش‌فرض)

حالت Browser Use از ‏CLI ی ۳٫۰ ی Browser Use — هارنس جدیدی که در تسک‌های وب پیشرفته‌ترین حال را دارد — به‌جای ابزارهای مرورگر داخلی استفاده می‌کند. ایجنت داخل مرورگر پایتون می‌نویسد و اجرا می‌کند تا کلیک کند، تایپ کند، بکشد، scrape کند و با صفحات وب تعامل داشته باشد.

این حالت پیش‌فرض مرورگر است: وقتی ‏browser.backend ست نباشد و CLI ی browser-use قابل‌اجرا باشد ‏(نصب‌شده، یا در دسترس از طریق uvx)، ایجنت تک‌ابزار ‏browser_exec را می‌گیرد. اگر CLI نتواند اجرا شود هرمس خودکار به ابزارهای مرورگر داخلی برمی‌گردد.

این حالت یک درایور است که با بک‌اند مرورگری پیکربندی‌شده‌تان ترکیب می‌شود: Chrome محلی‌تان، یک مرورگر ابری اشتراک-Nous، ‏Browserbase، ‏Firecrawl یا مرورگرهای ابری Browser Use را می‌رانَد — هر منبع مرورگری که در hermes tools ← Browser Automation انتخاب شده. تنها استثنا Camofox است که نقطهٔ پایانی CDP ای برای اتصال هارنس ندارد؛ setup های Camofox خودکار ابزارهای مرورگر داخلی را نگه می‌دارند.

نشست‌های همزمان: ‏browser_exec آرگومان ‏session=<name> می‌پذیرد که کارِ مرورگری را per-name روی همهٔ بک‌اندها ایزوله می‌کند. هر نام دیمون هارنس خودش را دارد ‏(socket IPC و log و وضعیت خودش) و روی بک‌اندهای ابری مرورگر خودش را — پس زیرایجنت‌های موازی یا گفتگوهای همزمان دیگر اتصال مشترک واحد را له نمی‌کنند. حذف session از دیمون پیش‌فرض مشترک استفاده می‌کند که برای مرور یکی-در-آن-واحد کافی است.

برای انصراف و اجبار به ابزارهای مرورگر داخلی از ‏/browser use off استفاده کنید یا:

yaml
# Add to ~/.hermes/config.yaml
browser:
  backend: "off"

‏(backend: "browser-use" برای اجبار صریح به این حالت معتبر می‌ماند.)

مرورگرهای ابری خودِ Browser Use به ‏browser-use auth login یا ‏BROWSER_USE_API_KEY نیاز دارند؛ سایر منابع مرورگر از اعتبارنامه‌های فعلی‌شان بدون تغییر استفاده می‌کنند.

📌

چون حالت Browser Use پایتون نوشته-شده-توسط-مدل را روی ماشین شما اجرا می‌کند، ابزار browser_exec فقط به نشست‌هایی عرضه می‌شود که ترمینال هم دارند. پلتفرم‌هایی بدون تول‌ست ترمینال پیکربندی شده‌اند ‏(مثلاً یک سطح پیام‌رسانی قفل‌شده) به‌جایش ابزارهای مرورگر پیش‌فرض را نگه می‌دارند.

حالت ابری Firecrawl

برای استفاده از Firecrawl به‌عنوان ارائه‌دهندهٔ مرورگر ابری اضافه کنید:

# Add to ~/.hermes/.env
FIRECRAWL_API_KEY=fc-***

کلید API تان را از ‏firecrawl.dev بگیرید. سپس Firecrawl را به‌عنوان ارائه‌دهندهٔ مرورگر انتخاب کنید:

hermes setup tools
# → Browser Automation → Firecrawl

تنظیمات اختیاری:

# Self-hosted Firecrawl instance (default: https://api.firecrawl.dev)
FIRECRAWL_API_URL=http://localhost:3002

# Session TTL in seconds (default: 300)
FIRECRAWL_BROWSER_TTL=600

۳ مسیریابی هیبریدی: ابر برای URL های عمومی، محلی برای LAN/localhost

وقتی یک ارائه‌دهندهٔ ابری پیکربندی شده باشد، هرمس برای URL هایی که به آدرس خصوصی/loopback/LAN حل می‌شوند ‏(localhost، ‏127.0.0.1، ‏192.168.x.x، ‏10.x.x.x، ‏172.16-31.x.x، ‏*.local، ‏*.lan، ‏*.internal، loopback ی IPv6 ی ‏::1، link-local ی ‏169.254.x.x) خودکار یک sidecar ی Chromium محلی spawn می‌کند. URL های عمومی در همان گفتگو همچنان از ارائه‌دهندهٔ ابری استفاده می‌کنند.

این گردش‌کار رایج «محلی توسعه می‌دهم ولی از Browserbase استفاده می‌کنم» را حل می‌کند — ایجنت می‌تواند از داشبوردتان در ‏http://localhost:3000 اسکرین‌شات بگیرد و github.com را scrape کند بدون اینکه ارائه‌دهنده عوض کنید یا گارد SSRF را خاموش کنید. ارائه‌دهندهٔ ابری هرگز URL خصوصی را نمی‌بیند.

این قابلیت به‌طور پیش‌فرض روشن است. برای غیرفعال کردن ‏(همهٔ URL ها مثل قبل به ارائه‌دهندهٔ ابری پیکربندی‌شده بروند):

yaml
# ~/.hermes/config.yaml
browser:
  cloud_provider: browserbase
  auto_local_for_private_urls: false

با خاموش بودن مسیریابی خودکار، URL های خصوصی با پیام «Blocked: URL targets a private or internal address» رد می‌شوند مگر اینکه ‏browser.allow_private_urls: true را هم ست کنید ‏(که اجازه می‌دهد ارائه‌دهندهٔ ابری امتحانشان کند — معمولاً کار نمی‌کند چون Browserbase و… به LAN شما نمی‌رسند).

نیازمندی‌ها: sidecar محلی همان CLI ی agent-browser حالت کاملاً محلی را استفاده می‌کند، پس باید نصب باشد ‏(‏hermes setup tools ← Browser Automation خودش نصبش می‌کند). redirect های بعد-از-ناوبری از URL عمومی به آدرس خصوصی همچنان بلاک‌اند ‏(میان‌برِ redirect-به-داخلی برای رسیدن به LAN از مسیر عمومی جواب نمی‌دهد).

۴ حالت محلی Camofox

‏Camofox سرور Node.js ی خودمیزبانی است که دور Camoufox ‏(یک fork ی Firefox با فریب اثر انگشت C++) پیچیده شده. مرور ضددیدگی محلی بدون وابستگی ابری فراهم می‌کند.

# Clone the Camofox browser server first
git clone https://github.com/jo-inc/camofox-browser
cd camofox-browser

# Build and start with Docker using the default container settings
# (auto-detects arch: aarch64 on M1/M2, x86_64 on Intel)
make up

# Stop and remove the default container
make down

# Force a clean rebuild (for example, after upgrading VERSION/RELEASE)
make reset

# Just download binaries without building
make fetch

# Override arch or version explicitly
make up ARCH=x86_64
make up VERSION=135.0.1 RELEASE=beta.24

‏make up کانتینر پیش‌فرض را فوراً شروع می‌کند. اگر تنظیمات runtime سفارشی مثل heap بزرگ‌تر Node، ‏VNC یا دایرکتوری پروفایل پایدار می‌خواهید اول image را build و خودتان اجرا کنید:

# Build the image without starting the default container
make build

# Start with persistence, VNC live view, and a larger Node heap
mkdir -p ~/.camofox-docker
docker run -d \
  --name camofox-browser \
  --restart unless-stopped \
  -p 9377:9377 \
  -p 6080:6080 \
  -p 5901:5900 \
  -e CAMOFOX_PORT=9377 \
  -e ENABLE_VNC=1 \
  -e VNC_BIND=0.0.0.0 \
  -e VNC_RESOLUTION=1920x1080 \
  -e MAX_OLD_SPACE_SIZE=2048 \
  -v ~/.camofox-docker:/root/.camofox \
  camofox-browser:135.0.1-aarch64

با فعال بودن VNC مرورگر در حالت headed اجرا و می‌توانید زنده در مرورگرتان از ‏http://localhost:6080 ‏(noVNC) تماشایش کنید. کلاینت VNC ی native هم به ‏localhost:5901 می‌توانید وصل کنید.

اگر قبلاً make up زده‌اید قبل از شروع کانتینر سفارشی، آن پیش‌فرض را متوقف و حذف کنید:

make down
# then run the custom docker run command above

سپس در ‏~/.hermes/.env ست کنید:

CAMOFOX_URL=http://localhost:9377

اگر Camofox در Docker اجراست و می‌خواهید اپ‌های وب سرویس‌شده از ماشین میزبان را باز کند، بازنویسی loopback را روشن کنید. CAMOFOX_URL باید همچنان به API ی کنترل منتشر-شده-به-میزبان اشاره کند ولی URL های صفحه مثل ‏http://127.0.0.1:3000 باید از داخل کانتینر به‌صورت ‏http://host.docker.internal:3000 باز شوند:

yaml
# ~/.hermes/config.yaml
browser:
  camofox:
    rewrite_loopback_urls: true
    loopback_host_alias: host.docker.internal  # default; use a LAN IP if needed

معادل env ی:

CAMOFOX_REWRITE_LOOPBACK_URLS=true
CAMOFOX_LOOPBACK_HOST_ALIAS=host.docker.internal

بازنویسی فقط روی URL های ناوبری صفحه با host های loopback ‏(localhost، ‏127.0.0.1، ‏::1) اعمال می‌شود و CAMOFOX_URL را عوض نمی‌کند. برای نصب‌های غیر-Docker ی Camofox که مرورگر از قبل روی host اجراست و loopback درست است، خاموش بگذاریدش.

یا از طریق ‏hermes tools ← Browser Automation ← Camofox پیکربندی کنید.

‏Camofox مثل هر بک‌اند مرورگری دیگری انتخاب می‌شود: در ‏hermes tools ← Browser Automation مقدار Camofox را بردارید که ‏browser.cloud_provider: camofox را در config.yaml می‌نویسد. ‏CAMOFOX_URL فقط آدرس سرور است — وقتی انتخاب مرورگری وجود دارد ست کردنش دیگر به‌تنهایی بک‌اند را انتخاب نمی‌کند ‏(setup های هرگز-پیکربندی‌نشده همچنان خودآشکارش می‌کنند).

نشست‌های مرورگری پایدار

به‌طور پیش‌فرض هر نشست Camofox هویت تصادفی می‌گیرد — کوکی‌ها و ورودها بین ری‌استارت‌های ایجنت دوام ندارند. برای فعال کردن نشست‌های مرورگری پایدار این را به config.yaml اضافه کنید:

yaml
browser:
  camofox:
    managed_persistence: true

سپس هرمس را کامل ری‌استارت کنید تا config جدید خوانده شود.

⚠️ مسیر تو-در-تو مهم است

هرمس ‏browser.camofox.managed_persistence را می‌خواند، نه یک managed_persistence ی سطح-بالا. اشتباه رایج نوشتن این است:

# ❌ Wrong — Hermes ignores this
managed_persistence: true

اگر فلگ در مسیر غلط باشد هرمس بی‌سروصدا به userId ی زودگذر تصادفی برمی‌گردد و وضعیت ورودتان هر نشست از دست می‌رود.

چه کاری هرمس می‌کند

  • یک userId ی قطعی مخصوص-پروفایل به Camofox می‌فرستد تا سرور بتواند همان پروفایل Firefox را بین نشست‌ها دوباره استفاده کند.
  • نابودی context سمت-سرور را موقع cleanup رد می‌کند تا کوکی‌ها و ورودها بین تسک‌های ایجنت دوام بیاورند.
  • userId را به پروفایل فعال هرمس scope می‌کند تا پروفایل‌های مختلف هرمس پروفایل‌های مرورگری متفاوت بگیرند ‏(ایزوله‌سازی پروفایل).

چه کاری هرمس نمی‌کند

  • پایداری را روی سرور Camofox تحمیل نمی‌کند. هرمس فقط userId پایداری می‌فرستد؛ سرور باید با نگاشت آن userId به یک دایرکتوری پروفایل Firefox پایدار محترمش بشمارد.
  • اگر build ی سرور Camofox تان هر درخواستی را زودگذر تلقی کند ‏(مثلاً همیشه browser.newContext() صدا بزند بدون بارگذاری پروفایل ذخیره‌شده)، هرمس نمی‌تواند آن نشست‌ها را پایدار کند. مطمئن شوید build ی Camofox اجرا می‌کنید که پایداری per-user ی مبتنی-بر-userId را پیاده کرده است.

تأیید اینکه کار می‌کند

  1. هرمس و سرور Camofox تان را شروع کنید.
  2. در یک تسک مرورگر Google ‏(یا هر سایت ورودی) را باز و دستی وارد شوید.
  3. تسک مرورگر را عادی تمام کنید.
  4. تسک مرورگر جدیدی شروع کنید.
  5. همان سایت را دوباره باز کنید — هنوز باید وارد بوده باشید.

اگر گام ۵ شما را خارج کرد یعنی سرور Camofox به userId پایدار احترام نمی‌گذارد. مسیر config را دوباره چک کنید، تأیید کنید بعد از ویرایش config.yaml هرمس را کامل ری‌استارت کرده‌اید و نسخهٔ سرور Camofox تان پروفایل‌های پایدار per-user را پشتیبانی می‌کند.

وضعیت کجا زندگی می‌کند

هرمس userId پایدار را از دایرکتوری مخصوص-پروفایل ‏~/.hermes/browser_auth/camofox/ ‏(یا معادلش زیر HERMES_HOME برای پروفایل‌های غیرپیش‌فرض) مشتق می‌کند. دادهٔ واقعی پروفایل مرورگر سمت سرور Camofox زندگی می‌کند کلیدخورده با همان userId. برای ریست کامل یک پروفایل پایدار، آن را روی سرور Camofox پاک و دایرکتوری وضعیت پروفایل متناظر هرمس را حذف کنید.

نشست‌های Camofox ی مدیریت‌شده-از-بیرون

وقتی اپ دیگری مرورگر مرئی Camofox را می‌راند ‏(یک دستیار دسکتاپ، یک یکپارچه‌سازی سفارشی، ایجنت دیگری)، هرمس را طوری پیکربندی کنید که داخل همان هویت کار کند به‌جای spawn کردن پروفایل ایزولهٔ خودش.

سه پیچ رفتار را کنترل می‌کنند:

تنظیممتغیر محیطیاثر
browser.camofox.user_idCAMOFOX_USER_IDuserId ی Camofox که هرمس موقع ساخت تب استفاده می‌کند. ست کردنش نشست را وارد حالت «مدیریت‌شده-از-بیرون» می‌کند.
browser.camofox.session_keyCAMOFOX_SESSION_KEYsessionKey ‏(همان listItemId) که موقع ساخت تب فرستاده می‌شود. برای تطبیق یک tab موجود حین adoption. پیش‌فرض مقداری per-task اگر unset باشد.
browser.camofox.adopt_existing_tabCAMOFOX_ADOPT_EXISTING_TABوقتی true، هرمس در اولین استفاده ‏GET /tabs?userId=<user_id> را صدا و قبل از ساخت تب جدید از تب موجود دوباره استفاده می‌کند.

متغیرهای env بر config.yaml مقدم‌اند. هر فرم کار می‌کند:

yaml
browser:
  camofox:
    user_id: shared-camofox
    session_key: visible-tab
    adopt_existing_tab: true
CAMOFOX_USER_ID=shared-camofox
CAMOFOX_SESSION_KEY=visible-tab
CAMOFOX_ADOPT_EXISTING_TAB=true

وقتی user_id ست شود چه عوض می‌شود:

  • هرمس cleanup ی مخرب را در پایان تسک skip می‌کند ‏(مثل managed_persistence: true). تب/کوکی/پروفایل اپ دیگر سالم می‌ماند.
  • هرمس ‏DELETE /sessions/<user_id> را صدا نمی‌زند — آن نقطهٔ پایانی همهٔ داده‌های کاربر را پاک می‌کند و اگر شلیک شود نشست اپ بیرونی را نابود می‌کرد.

adoption ی تب چطور کار می‌کند ‏(وقتی adopt_existing_tab: true):

  1. در اولین فراخوانی ابزار مرورگر بعد از شروع پروسه، هرمس ‏GET /tabs?userId=<user_id> را صادر می‌کند ‏(timeout ی ۵ ثانیه).
  2. اگر هر تبی در پاسخ listItemId == session_key داشته باشد، هرمس جدیدترین‌شان در آن گروه را adopt می‌کند.
  3. در غیر این صورت هرمس جدیدترین تب کاربر را ‏(هر listItemId) adopt می‌کند.
  4. اگر تبی وجود نداشته یا درخواست شکست بخورد، هرمس در عملیات بعدی به ساخت تب جدید fallback می‌کند.

Adoption فقط تا وقتی tab_id برای نشست پر شود شلیک می‌کند. اگر اپ بیرونی تب adopt‌شده را وسط run ببندد، فراخوانی بعدی ابزار مرورگر خطای Camofox surface می‌کند — هرمس هر بار برای تب تازه دوباره poll نمی‌کند.

انتخاب session_key: اگر می‌خواهید هرمس قابل‌اعتماد به یک تب مشخص موجود بچسبد، session_key را روی listItemId ای که اپ بیرونی موقع ساختش استفاده کرده بگذارید. اگر session_key را unset بگذارید و فقط user_id ست کنید، هرماس session_key ی per-task تولید می‌کند ‏(task_<id>) — هرمس کوکی‌ها و پروفایل را با اپ بیرونی شریک می‌کند ولی تب خودش را کنارشان باز می‌کند به‌جای دوباره‌استفاده از یکی.

یادداشت همزمانی: اپ بیرونی و هرمس می‌توانند همزمان همان userId ی Camofox را برانند ولی Camofox فوکوس per-tab را بین کلاینت‌ها هماهنگ نمی‌کند. مالکیت را در لایهٔ اپ هماهنگ کنید ‏(مثلاً اپ بیرونی حین اجرای هرمس pause کند).

نمای زنده VNC

وقتی Camofox در حالت headed اجرا شود ‏(با پنجرهٔ مرورگر مرئی)، یک پورت VNC را در پاسخ health check اش expose می‌کند. هرمس خودکار آن را کشف و URL ی VNC را در پاسخ‌های ناوبری می‌گنجاند تا ایجنت بتواند لینکی برای تماشای زندهٔ مرورگر با شما به اشتراک بگذارد.

۵ موتور Lightpanda و اتصال CDP محلی

موتور محلی Lightpanda

‏Lightpanda مرورگری headless متن‌باز و ساخته‌شده از صفر است. فوری شروع می‌شود ‎۹×‎ سریع‌تر اجرا و ‎۱۶×‎ حافظهٔ کمتر از Chrome مصرف می‌کند که برای ایجنت‌هایی که طولانی روی VM های کوچک زندگی می‌کنند مهم است.

‏Lightpanda یک موتور محلی است که زیر مسیر محلی agent-browser انتخاب می‌شود ‏(نه یک ارائه‌دهندهٔ ابری). باینری را نصب و روی PATH تان بگذارید ‏(راهنمای نصب Lightpanda)، سپس:

yaml
# Add to ~/.hermes/config.yaml
browser:
  engine: lightpanda

یا از طریق متغیر محیطی:

AGENT_BROWSER_ENGINE=lightpanda

هرمس Lightpanda را از طریق agent-browser و با CDP می‌راند، همان‌طور که Chrome ی محلی را می‌راند.

Fallback ی خودکار Chrome. ‏Lightpanda هنوز همهٔ کارهای Chrome را پوشش نمی‌دهد، پس یکپارچه‌سازی غیرمزاحم است: Lightpanda اقداماتی را که پشتیبانی می‌کند هندل و هرمس برای هر چه نمی‌کند شفاف روی Chrome دوباره تلاش می‌کند. مجموعهٔ پشتیبانی‌شده هستهٔ گردش‌کار ایجنت را پوشش می‌دهد — navigate، snapshot، click، type، scroll، back، press و eval. اسکرین‌شات‌ها هم به Chrome برمی‌گردند چون Lightpanda رندرکنندهٔ گرافیکی ندارد؛ browser_vision هم به همین دلیل از قبل مستقیم به Chrome مسیریابی می‌شود.

مرورگر محلی خانوادهٔ Chromium از طریق CDP ‏(‏/browser connect)

به‌جای ارائه‌دهندهٔ ابری می‌توانید ابزارهای مرورگر هرمس را از طریق Chrome DevTools Protocol ‏(CDP) به نمونهٔ درحال‌اجرا ی خودتان از Chrome، ‏Brave، ‏Chromium یا Edge بچسبانید. وقتی مفید است که بخواهید بلادرنگ ببینید ایجنت چه می‌کند، با صفحاتی تعامل کنید که کوکی/نشست خودتان را می‌خواهند یا از هزینه‌های مرورگر ابری اجتناب کنید.

📌

‏/browser connect یک دستور اسلش مخصوص-CLI ی تعاملی است — توسط گیت‌وی dispatch نمی‌شود. اگر داخل WebUI، ‏تلگرام، ‏دیسکورد یا چت گیت‌وی دیگری اجرایش کنید پیام به‌عنوان متن عادی به ایجنت فرستاده و فرمان اجرا نمی‌شود. هرمس را از ترمینال ‏(‏hermes یا hermes chat) شروع و آنجا /browser connect را صادر کنید.

در CLI استفاده کنید:

/browser connect                 # Auto-launch/connect to a local Chromium-family browser at http://127.0.0.1:9222
/browser connect ws://host:port  # Connect to a specific CDP endpoint
/browser status                  # Check current connection
/browser disconnect              # Detach and return to cloud/local mode

اگر مرورگری از قبل با remote debugging در حال اجرا نباشد، هرمس تلاش می‌کند یک مرورگر خانوادهٔ Chromium ی پشتیبانی‌شده را با ‏--remote-debugging-port=9222 خودکار launch کند. آشکارسازی شامل Brave، ‏Google Chrome، ‏Chromium و Microsoft Edge با مسیرهای نصب رایج لینوکسی مثل ‏/opt/brave-bin/brave و ‏/snap/bin/brave است.

💡

برای شروع دستی مرورگر خانوادهٔ Chromium با CDP فعال از یک user-data-dir ی اختصاصی استفاده کنید تا پورت دیباگ واقعاً بالا بیاید حتی وقتی مرورگر از قبل با پروفایل عادی‌تان در حال اجراست:

# Linux — Brave
brave-browser \
  --remote-debugging-port=9222 \
  --user-data-dir=$HOME/.hermes/chrome-debug \
  --no-first-run \
  --no-default-browser-check &

# Linux — Google Chrome
google-chrome \
  --remote-debugging-port=9222 \
  --user-data-dir=$HOME/.hermes/chrome-debug \
  --no-first-run \
  --no-default-browser-check &

# macOS — Brave
"/Applications/Brave Browser.app/Contents/MacOS/Brave Browser" \
  --remote-debugging-port=9222 \
  --user-data-dir="$HOME/.hermes/chrome-debug" \
  --no-first-run \
  --no-default-browser-check &

# macOS — Google Chrome
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 \
  --user-data-dir="$HOME/.hermes/chrome-debug" \
  --no-first-run \
  --no-default-browser-check &

سپس CLI ی هرمس را launch و /browser connect را اجرا کنید.

چرا user-data-dir؟ بدون آن، launch کردن مرورگر خانوادهٔ Chromium وقتی نمونهٔ عادی در حال اجراست معمولاً پنجره جدیدی روی پروسهٔ موجود باز می‌کند — و آن پروسهٔ موجود بدون remote-debugging-port شروع شده پس پورت ۹۲۲۲ هیچ‌وقت بالا نمی‌آید. user-data-dir ی اختصاصی پروسهٔ مرورگر تازه‌ای اجبار می‌کند که پورت دیباگ واقعاً گوش دهد. ‏no-first-run و no-default-browser-check هم ویزارد اولین-اجرا را برای پروفایل تازه skip می‌کنند.

Chrome ی ۱۳۶ به بالا پروفایل اختصاصی را الزامی می‌کند. به‌عنوان سخت‌سازی امنیتی، ‏Chrome ۱۳۶ به بعد وقتی remote-debugging-port با user-data-dir ی پیش‌فرض ترکیب شود پورت دیبگ راه‌دور را بی‌سروصدا باز کردن رد می‌کند — حتی از cold start بدون هیچ Chrome ی دیگر. مرورگر عادی launch می‌شود ولی هیچ‌وقت چیزی روی ۹۲۲۲ گوش نمی‌دهد، پس browser connect ‏(و هر curl دستی به ‏http://127.0.0.1:9222/json/version) با connection refused شکست می‌خورد. هیچ پیام خطایی نیست. اصلاح دقیقاً همان فرمان‌های بالاست: همیشه user-data-dir ای غیر از دایرکتوری پروفایل پیش‌فرض پاس دهید ‏(مثلاً ‏$HOME/.hermes/chrome-debug). این روی buildهای Chrome، ‏Chromium، ‏Edge و Brave ای که تغییر را گرفته‌اند صدق می‌کند.

وقتی از طریق CDP وصل باشید همهٔ ابزارهای مرورگر ‏(browser_navigate، ‏browser_click و…) روی نمونهٔ زندهٔ مرورگر شما عمل می‌کنند به‌جای بالا آوردن نشست ابری.

WSL2 + Chrome ی ویندوز: MCP را به /browser connect ترجیح دهید

اگر هرمس داخل WSL2 اجرا شود ولی پنجرهٔ Chrome ای که می‌خواهید کنترل کنید روی host ی ویندوز باشد، ‏/browser connect اغلب بهترین مسیر نیست.

چرا:

  • ‏/browser connect انتظار دارد خودِ هرمس به یک نقطهٔ پایانی CDP قابل‌استفاده برسد
  • نشست‌های live-debugging مدرن Chrome اغلب نقطهٔ پایانی host-محلی expose می‌کنند که از WSL مثل پورت کلاسیک ۹۲۲۲ مستقیماً قابل‌رسید نیست
  • حتی وقتی Chrome ی ویندوز قابل‌دیباگ است تمیزترین یکپارچگی این است که سرور MCP مرورگر سمت-ویندوز به Chrome بچسبد و هرمس با آن سرور MCP حرف بزند

برای آن setup مقدار chrome-devtools-mcp را از طریق پشتیبانی MCP ی هرمس ترجیح دهید.

حالت مرورگر محلی

اگر هیچ اعتبارنامهٔ ابری ست نکنید و از ‏/browser connect استفاده نکنید، هرمس همچنان می‌تواند ابزارهای مرورگر را از طریق نصب محلی Chromium ی رانده توسط agent-browser به کار ببرد.

متغیرهای محیطی اختیاری

# Residential proxies for better CAPTCHA solving (default: "true")
BROWSERBASE_PROXIES=true

# Advanced stealth with custom Chromium — requires Scale Plan (default: "false")
BROWSERBASE_ADVANCED_STEALTH=false

# Session reconnection after disconnects — requires paid plan (default: "true")
BROWSERBASE_KEEP_ALIVE=true

# Custom session timeout in seconds (max 21600 = 6 hours) (default: project default)
# Examples: 600 (10min), 1800 (30min), 21600 (6h max)
BROWSERBASE_SESSION_TIMEOUT=1800

# Inactivity timeout before auto-cleanup in seconds (default: 120)
BROWSER_INACTIVITY_TIMEOUT=120

# Local browser engine. Applies to the built-in browser tools
# (agent-browser path). Equivalent to browser.engine in config.yaml.
#   auto       — agent-browser's default (currently Chrome)
#   lightpanda — Lightpanda
#   chrome     — force Chrome explicitly
AGENT_BROWSER_ENGINE=auto

# Extra Chromium launch flags (comma- or newline-separated). Hermes auto-injects
# `--no-sandbox,--disable-dev-shm-usage` when it detects root or AppArmor-restricted
# unprivileged user namespaces (Ubuntu 23.10+, DGX Spark, many container images),
# so most users don't need to set this. Set it manually only if you need a flag
# Hermes doesn't add automatically; setting it disables the auto-injection.
AGENT_BROWSER_ARGS=--no-sandbox

نصب CLI ی agent-browser

لازم نیست چیزی نصب کنید — ‏agent-browser در اولین استفاده از ابزار مرورگر خودکار از طریق ‏npx agent-browser حل می‌شود. برای جلوگیری از واکشی یک‌بارهٔ npx می‌توانید از قبل سراسری نصبش کنید ‏(اختیاری):

npm install -g agent-browser
📌

تول‌ست browser باید در فهرست toolsets ی config تان باشد یا با ‏hermes config set toolsets '["hermes-cli", "browser"]' فعال شود.

۶ ابزارهای موجود

‏browser_navigate

ناوبری به یک URL. قبل از هر ابزار مرورگر دیگری باید صدا زده شود. نشست Browserbase را مقداردهی می‌کند.

Navigate to https://github.com/NousResearch
💡

برای بازیابی سادهٔ اطلاعات web_search یا web_extract را ترجیح دهید — سریع‌تر و ارزان‌ترند. ابزارهای مرورگر را وقتی به کار ببرید که لازم است با صفحه تعامل کنید ‏(کلیک دکمه، پر کردن فرم، محتوای داینامیک).

‏browser_snapshot

snapshot متنی از درخت دسترس‌پذیری صفحهٔ فعلی می‌گیرد. عناصر تعاملی را با ref ID هایی مثل ‏@e1 و @e2 برمی‌گرداند برای مصرف browser_click و browser_type.

  • ‏full=false ‏(پیش‌فرض): نمای فشرده فقط عناصر تعاملی
  • ‏full=true: محتوای کامل صفحه

snapshot های بالای ‎۱۵٬۰۰۰ نویسه خودکار بریده یا توسط LLM خلاصه می‌شوند ‏(همان بودجه per-page ی web_extract). وقتی این رخ دهد snapshot کامل در ‏~/.hermes/cache/web/ ذخیره و خروجی ابزار مسیر فایل + یک فراخوانی آمادهٔ read_file را شامل می‌شود تا ایجنت بتواند کل درخت دسترس‌پذیری — شامل ref های عنصر فراتر از برش — را بدون snapshot مجدد ورق بزند.

‏browser_click

روی عنصری شناسایی‌شده با ref ID اش از snapshot کلیک می‌کند.

Click @e5 to press the "Sign In" button

‏browser_type

متن را داخل یک فیلد ورودی تایپ می‌کند. اول فیلد را خالی بعد متن جدید را تایپ می‌کند.

Type "hermes agent" into the search field @e3

‏browser_scroll

صفحه را بالا/پایین می‌کند تا محتوای بیشتری پیدا شود.

Scroll down to see more results

‏browser_press

یک کلید کیبورد فشار می‌دهد. برای submit کردن فرم‌ها یا ناوبری مفید.

Press Enter to submit the form

کلیدهای پشتیبانی‌شده: ‏Enter، ‏Tab، ‏Escape، ‏ArrowDown، ‏ArrowUp و بیشتر.

‏browser_back

به صفحهٔ قبلی در تاریخچهٔ مرورگر برمی‌گردد.

‏browser_get_images

همهٔ تصاویر صفحهٔ فعلی را با URL و alt text شان فهرست می‌کند. برای یافتن تصاویر جهت تحلیل مفید.

‏browser_vision

اسکرین‌شات می‌گیرد و با vision AI تحلیلش می‌کند. وقتی استفاده کنید که snapshot های متنی اطلاعات بصری مهم را نمی‌گیرند — مخصوصاً برای CAPTCHA ها، چیدمان‌های پیچیده یا چالش‌های تأیید بصری.

اسکرین‌شات به‌طور پایدار ذخیره و مسیر فایل کنار تحلیل AI برگردانده می‌شود. روی پلتفرم‌های پیام‌رسانی ‏(تلگرام، ‏دیسکورد، ‏اسلک، ‏واتساپ) می‌توانید از ایجنت بخواهید اسکرین‌شات را به اشتراک بگذارد — به‌صورت پیوست عکس native از طریق سازوکار MEDIA: فرستاده می‌شود.

What does the chart on this page show?

اسکرین‌شات‌ها در ‏~/.hermes/cache/screenshots/ ذخیره و بعد از ۲۴ ساعت خودکار پاک می‌شوند.

‏browser_console

خروجی console ی مرورگر ‏(پیام‌های log/warn/error) و exception های JS ی شکار-نشده را از صفحهٔ فعلی می‌گیرد. برای کشف خطاهای JS ی بی‌صدایی که در درخت دسترس‌پذیری ظاهر نمی‌شوند ضروری است.

Check the browser console for any JavaScript errors

با ‏clear=True بعد از خواندن console پاک می‌شود تا فراخوانی‌های بعدی فقط پیام‌های جدید را نشان دهند.

‏browser_console با آرگومان expression همچنین جاوااسکریپت eval می‌کند — هم‌شکل console ی DevTools؛ نتیجه parse شده برمی‌گردد ‏(آبجکت‌های JSON-سریالایز شده dict می‌شوند؛ مقادیر primitive همان‌طور می‌مانند).

browser_console(expression="document.querySelector('h1').textContent")
browser_console(expression="JSON.stringify(performance.timing)")

وقتی supervisor ی CDP برای نشست فعلی فعال باشد ‏(معمول برای هر نشستی که browser_navigate روی بک‌اند CDP-capable زده) ارزیابی روی WebSocket ی پایدار supervisor اجرا می‌شود — بدون هزینهٔ راه‌اندازی زیرپروسه. در غیر این صورت به مسیر عادی CLI ی agent-browser می‌رسد. رفتار هر دو یکسان است؛ فقط تأخیر فرق می‌کند.

ارزیابی به‌طور پیش‌فرض نامحدود است — ایجنت می‌تواند fetch بزند، storage بخواند، مقادیر فرم را query و هر استخراج DOM ای انجام دهد. درخواست‌های رو-به-آدرس‌های خصوصی/داخلی روی بک‌اندهای غیرمحلی همچنان بلاک‌اند ‏(گارد SSRF مستقل از این تنظیم است). اگر با پروفایل وارد‌شده صفحات متخاصم مرور می‌کنید و denylist ی سخت‌گیری روی primitive های حساس JS ‏(cookies، ‏storage، ‏clipboard، ‏network calls، ‏form values) می‌خواهید با ‏browser.restrict_evaluate: true در config.yaml شرکت کنید. توجه کنید denylist نام primitive ها را تطبیق می‌دهد پس عبارات مشروعی که صرفاً واژه‌هایی مثل fetch یا cookie دارند را هم بلاک می‌کند.

‏browser_cdp

passthrough خام Chrome DevTools Protocol — دریچهٔ فرار برای عملیات مرورگری که سایر ابزارها پوشش نمی‌دهند. برای هندل دیالوگ‌های native، ارزیابی scoped در iframe، کنترل کوکی/شبکه یا هر فعل CDP ای که ایجنت لازم دارد.

فقط وقتی در شروع نشست نقطهٔ پایانی CDP قابل‌رسید باشد موجود است — یعنی /browser connect به یک Chrome/Brave/Chromium/Edge ی در حال اجرا چسبیده باشد یا browser.cdp_url در config.yaml ست شده باشد. حالت پیش‌فرض local agent-browser و Camofox و ارائه‌دهنده‌های ابری ‏(Browserbase، ‏Browser Use، ‏Firecrawl) فعلاً CDP را به این ابزار نمی‌دهند — ارائه‌دهنده‌های ابری URL های CDP ی per-session دارند ولی مسیریابی live-session یک follow-up است.

مرجع متد CDP: ‏chromedevtools.github.io/devtools-protocol — ایجنت می‌تواند صفحهٔ یک متد مشخص را web_extract کند تا پارامترها و شکل بازگشت را پیدا کند.

الگوهای رایج:

# List tabs (browser-level, no target_id)
browser_cdp(method="Target.getTargets")

# Handle a native JS dialog on a tab
browser_cdp(method="Page.handleJavaScriptDialog",
            params={"accept": true, "promptText": ""},
            target_id="<tabId>")

# Evaluate JS in a specific tab
browser_cdp(method="Runtime.evaluate",
            params={"expression": "document.title", "returnByValue": true},
            target_id="<tabId>")

# Get all cookies
browser_cdp(method="Network.getAllCookies")

متدهای سطح-مرورگر ‏(Target.*، ‏Browser.*، ‏Storage.*) بدون target_id هستند. متدهای سطح-صفحه ‏(Page.*، ‏Runtime.*، ‏DOM.*، ‏Emulation.*) به target_id ای از Target.getTargets نیاز دارند. هر فراخوانی stateless مستقل است — نشست‌ها بین فراخوانی‌ها پایدار نمی‌مانند.

iframe های cross-origin: مقدار frame_id ‏(از ‏browser_snapshot.frame_tree.children[] جایی که is_oopif=true) را پاس دهید تا فراخوانی CDP از طریق نشست زندهٔ supervisor برای آن iframe مسیریابی شود. این همان روشی است که Runtime.evaluate داخل iframe ی cross-origin روی Browserbase کار می‌کند، جایی که اتصالات stateless ی CDP به انقضای signed-URL می‌خورند. مثال:

browser_cdp(
  method="Runtime.evaluate",
  params={"expression": "document.title", "returnByValue": True},
  frame_id="<frame_id from browser_snapshot>",
)

iframe های same-origin به frame_id نیاز ندارند — به‌جایش document.querySelector('iframe').contentDocument را از یک Runtime.evaluate ی سطح-بالا استفاده کنید.

‏browser_dialog

به دیالوگ native ی JS ‏(alert / confirm / prompt / beforeunload) پاسخ می‌دهد. قبل از وجود این ابزار دیالوگ‌ها thread ی JS ی صفحه را بی‌سروصدا بلاک و فراخوانی‌های بعدی browser_* معلق یا exception می‌دادند؛ حالا ایجنت دیالوگ‌های معلق را در خروجی browser_snapshot می‌بیند و صریح پاسخ می‌دهد.

گردش‌کار:

  1. browser_snapshot را صدا بزنید. اگر دیالوگی صفحه را بلاک کرده به‌صورت ‏pending_dialogs: [{"id": "d-1", "type": "alert", "message": "..."}] ظاهر می‌شود.
  2. ‏browser_dialog(action="accept") یا ‏browser_dialog(action="dismiss") را صدا بزنید. برای دیالوگ‌های prompt() مقدار prompt_text="..." را پاس دهید.
  3. دوباره snapshot بگیرید — pending_dialogs خالی است؛ thread ی JS ی صفحه ادامه یافته.

آشکارسازی خودکار از طریق یک supervisor ی پایدار CDP رخ می‌دهد — یک WebSocket per-task که به رویدادهای Page/Runtime/Target مشترک می‌شود. supervisor همچنین فیلد frame_tree ی snapshot را پر می‌کند تا ایجنت ساختار iframe ی صفحهٔ فعلی را ببیند شامل iframe های cross-origin ‏(OOPIF).

ماتریس در دسترس بودن:

بک‌اندآشکارسازی با pending_dialogsپاسخ ‏(ابزار browser_dialog)
Chrome ی محلی با /browser connect یا browser.cdp_url✓✓ گردش‌کار کامل
Browserbase✓✓ گردش‌کار کامل ‏(via پُل XHR ی تزریق‌شده)
Camofox / local agent-browser پیش‌فرض✗✗ ‏(نقطهٔ پایانی CDP ندارد)

روی Browserbase چطور کار می‌کند. proxy ی CDP ی Browserbase دیالوگ‌های native واقعی را سمت سرور ظرف ~۱۰ میلی‌ثانیه auto-dismiss می‌کند، پس نمی‌توانیم از Page.handleJavaScriptDialog استفاده کنیم. supervisor اسکریپت کوچکی از طریق Page.addScriptToEvaluateOnNewDocument تزریق می‌کند که window.alert/confirm/prompt را با یک XHR ی همگام override می‌کند. ما آن XHR ها را با Fetch.enable intercept می‌کنیم — thread ی JS ی صفحه تا وقتی Fetch.fulfillRequest را با پاسخ ایجنت صدا بزنیم روی XHR بلاک می‌ماند. مقادیر بازگشتی prompt() بدون تغییر به JS ی صفحه round-trip می‌شوند.

سیاست دیالوگ در config.yaml زیر ‏browser.dialog_policy پیکربندی می‌شود:

سیاسترفتار
must_respond ‏(پیش‌فرض)capture، نمایش در snapshot، انتظار برای فراخوانی صریح browser_dialog(). ‏auto-dismiss ایمنی بعد از ‏browser.dialog_timeout_s ‏(پیش‌فرض ۳۰۰ ثانیه) تا ایجنت خراب تا ابد گیر نیندازد.
auto_dismisscapture، dismiss فوری. ایجنت همچنان دیالوگ را در تاریخچهٔ browser_state می‌بیند ولی مجبور به اقدام نیست.
auto_acceptcapture، accept فوری. برای ناوبری صفحات دارای پرامپت‌های beforeunload ی تهاجمی مفید.

درخت frame داخل ‏browser_snapshot.frame_tree روی ۳۰ فریم و عمق OOPIF ی ۲ سقف می‌خورد تا payload ها روی صفحات پر-تبلیغ محدود بمانند. فلگ truncated: true وقتی به سقف‌ها خورده شد surface می‌شود؛ ایجنت‌هایی که درخت کامل می‌خواهند می‌توانند از browser_cdp با Page.getFrameTree استفاده کنند.

۸ ضبط نشست، حالت headed و استلث

ضبط نشست

ضبط خودکار نشست‌های مرورگر به‌صورت فایل‌های ویدیویی WebM:

yaml
browser:
  record_sessions: true  # default: false

وقتی فعال باشد ضبط روی اولین browser_navigate خودکار شروع و هنگام بسته شدن نشست در ‏~/.hermes/browser_recordings/ ذخیره می‌شود. هم در حالت محلی هم ابری ‏(Browserbase) کار می‌کند. ضبط‌های قدیمی‌تر از ۷۲ ساعت خودکار پاک می‌شوند.

حالت headed ‏(پنجرهٔ مرورگر مرئی)

به‌طور پیش‌فرض مرورگر محلی headless اجرا می‌شود. حالت headed را روشن کنید تا پنجرهٔ Chromium ی مرئی بگیرید که می‌توانید تماشا و دستکاری‌اش کنید:

yaml
browser:
  headed: true  # default: false

یا از طریق متغیر محیطی: ‏AGENT_BROWSER_HEADED=1.

حالت headed دو کار می‌کند:

  1. Chromium را با پنجرهٔ مرئی launch می‌کند ‏(در حالت محلی --headed را به agent-browser پاس می‌دهد).
  2. پنجره بین نوبت‌ها باز می‌مانَد. عادی این است که نشست مرورگر بعد از هر پاس ایجنت پاکسازی شود؛ در حالت headed پاکسازی per-turn رد می‌شود تا کار ایجنت را تماشا، مداخله دستی ‏(چالش‌های ورود، ‏CAPTCHA) و وضعیت ورود را در طول گفتگو گرم نگه دارید.

نشست‌های بی‌کار همچنان بعد از browser.inactivity_timeout جمع می‌شوند ‏(پیش‌فرض ۱۲۰ ثانیه بدون فعالیت مرورگر) و همهٔ نشست‌ها هنگام shutdown بسته می‌شوند. حالت headed فقط مرورگر محلی را تحت تأثیر می‌گذارد — نشست‌های ابری ‏(Browserbase) مصون‌اند.

قابلیت‌های استلث

‏Browserbase قابلیت‌های استلث خودکار فراهم می‌کند:

اگر قابلیت‌های پولی روی پلن شما موجود نباشند هرمس خودکار fallback می‌کند — اول غیرفعال کردن keepAlive بعد proxies — تا مرور روی پلن‌های رایگان هم کار کند.

مدیریت نشست

  • هر تسک نشست مرورگری ایزوله از طریق Browserbase می‌گیرد
  • نشست‌ها بعد از بی‌کاری خودکار پاک می‌شوند ‏(پیش‌فرض ۲ دقیقه)
  • یک thread ی پس‌زمینه هر ۳۰ ثانیه نشست‌های کهنه را بررسی می‌کند
  • پاکسازی اضطراری موقع خروج پروسه اجرا می‌شود تا نشست‌های یتیم پیش نیایند
  • نشست‌ها از طریق API ی Browserbase آزاد می‌شوند ‏(وضعیت REQUEST_RELEASE)

۹ محدودیت‌ها

  • تعامل متنی — به درخت دسترس‌پذیری تکیه دارد نه مختصات پیکسلی
  • اندازهٔ snapshot — صفحات بزرگ ممکن است در ‎۱۵٬۰۰۰ نویسه بریده یا LLM-خلاصه شوند ‏(مطابق web_extract)؛ snapshot کامل در ‏~/.hermes/cache/web/ ذخیره و خروجی به آن اشاره می‌کند برای paging با read_file
  • timeout ی نشست — نشست‌های ابری طبق تنظیمات پلن ارائه‌دهنده‌تان منقضی می‌شوند
  • هزینه — نشست‌های ابری credit ی ارائه‌دهنده مصرف می‌کنند؛ نشست‌ها هنگام پایان گفتگو یا بعد از بی‌کاری خودکار پاک می‌شوند. برای مرور محلی رایگان از ‏/browser connect استفاده کنید.
  • بدون دانلود فایل — نمی‌تواند از مرورگر فایل دانلود کند
