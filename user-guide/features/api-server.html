سرور API ‏(سازگار با OpenAI)

سرور API مقدار hermes-agent را به‌عنوان یک نقطهٔ پایانی HTTP سازگار-با-OpenAI expose می‌کند. هر frontend ای که قالب OpenAI را حرف می‌زند — ‏Open WebUI، ‏LobeChat، ‏LibreChat، ‏NextChat، ‏ChatBox و صدهای دیگر — می‌تواند به hermes-agent وصل و آن را به‌عنوان backend مصرف کند.

ایجنت شما درخواست‌ها را با تول‌ست کاملش هندل می‌کند ‏(ترمینال، عملیات فایل، جستجوی وب، حافظه، مهارت‌ها) و پاسخ نهایی را برمی‌گرداند. حین streaming نشانگرهای پیشرفت ابزار inline ظاهر می‌شوند تا frontend ها ببینند ایجنت چه می‌کند.

💡 یک backend هم مدل هم ابزار

هرمس خودش ارائه‌دهندهٔ پیکربندی‌شده و بک‌اندهای ابزار می‌خواهد تا سرور API مفید باشد. اشتراک Nous Portal هر دو را هندل می‌کند — +۳۰۰ مدل به‌علاوهٔ وب/تصویر/TTS/مرورگر از طریق Tool Gateway. قبل از شروع سرور API یک بار ‏hermes setup --portal اجرا کنید تا frontend هایی مثل Open WebUI یا LobeChat بک‌اندی کاملاً مسلح-به-ابزار بگیرند.

۱ شروع سریع

۱. فعال کردن سرور API

به ~/.hermes/.env اضافه کنید:

API_SERVER_ENABLED=true
API_SERVER_KEY=change-me-local-dev
# Optional: only if a browser must call Hermes directly
# API_SERVER_CORS_ORIGINS=http://localhost:3000

۲. شروع گیت‌وی

hermes gateway

این را می‌بینید:

[API Server] API server listening on http://127.0.0.1:8642

۳. اتصال frontend

هر کلاینت سازگار-با-OpenAI را به ‏http://localhost:8642/v1 اشاره دهید:

# Test with curl
curl http://localhost:8642/v1/chat/completions \
  -H "Authorization: Bearer change-me-local-dev" \
  -H "Content-Type: application/json" \
  -d '{"model": "hermes-agent", "messages": [{"role": "user", "content": "Hello!"}]}'

یا Open WebUI، ‏LobeChat یا هر frontend دیگری وصل کنید — راهنمای گام‌به‌گام در راهنمای یکپارچه‌سازی Open WebUI.

۲ نقاط پایانی

‏POST /v1/chat/completions

قالب استاندارد Chat Completions ی OpenAI. stateless — کل گفتگو در هر درخواست از طریق آرایهٔ messages فرستاده می‌شود. درخواست و پاسخ JSON استاندارد؛ usage ی توکن هم برگردانده می‌شود.

ورودی تصویر inline: پیام‌های کاربر می‌توانند content را آرایه‌ای از بخش‌های text و image_url بفرستند. هم URL های راه‌دور http(s) و هم URL های data:image/... پشتیبانی می‌شوند. فایل‌های آپلودی ‏(file/input_file/file_id) و URL های data: ی غیر-تصویری 400 unsupported_content_type برمی‌گردانند.

Streaming ‏("stream": true): رویدادهای SSE با chunk های توکن-به-توکن برمی‌گرداند. برای Chat Completions استریم از رویدادهای استاندارد chat.completion.chunk به‌علاوهٔ رویداد سفارشی hermes.tool.progress هرمس برای UX ی شروع-ابزار استفاده می‌کند. برای Responses از انواع رویداد OpenAI Responses مثل response.created، ‏response.output_text.delta، ‏response.output_item.added/done و response.completed.

  • Chat Completions: هرمس event: hermes.tool.progress را برای دید شروع ابزار emit می‌کند بدون آلوده کردن متن دستیارِ ماندگار.
  • Responses: آیتم‌های خروجی spec-native ی function_call و function_call_output حین استریم SSE صادر می‌شود تا کلاینت‌ها UI ی ساختاریافتهٔ ابزار را بلادرنگ رندر کنند.

‏POST /v1/responses

قالب OpenAI Responses API. وضعیت گفتگوی سمت-سرور را با previous_response_id پشتیبانی می‌کند — سرور تاریخچهٔ کامل گفتگو ‏(شامل فراخوانی‌ها و نتایج ابزار) را ذخیره می‌کند تا زمینهٔ چندنوبتی بدون مدیریت سمت-کلاینت حفظ شود. فراخوانی‌های ابزار در آرایهٔ output قبلاً سمت-سرور توسط ایجنت هرمس اجرا شده‌اند — با status: completed برای UI ی ساختاریافته replay می‌شوند، هرگز به‌عنوان call های در-انتظار برای اجرا توسط کلاینت.

چندنوبت با previous_response_id: پاسخ‌ها را زنجیر کنید تا کل زمینه ‏(شامل tool calls) بین نوبت‌ها حفظ شود. سرور کل گفتگو را از زنجیرهٔ پاسخ ذخیره‌شده بازسازی می‌کند. درخواست‌های زنجیره‌شده همان نشست را هم share می‌کنند پس گفتگوهای چندنوبتی به‌صورت یک ورود واحد در داشبورد و تاریخچهٔ نشست دیده می‌شوند.

گفتگوهای نام‌دار: به‌جای ردیابی response ID ها از پارامتر conversation استفاده کنید — سرور خودکار به آخرین پاسخ همان گفتگو زنجیر می‌کند؛ مثل فرمان ‎/title‎ برای نشست‌های گیت‌وی.

‏GET /v1/responses/{id} و ‏DELETE /v1/responses/{id}

واکشی یا حذف یک پاسخ ذخیره‌شده با ID.

‏GET /v1/models

ایجنت را به‌عنوان مدل موجود advertise می‌کند. نام مدل advertised پیش‌فرض نام پروفایل است ‏(یا hermes-agent برای پروفایل پیش‌فرض). توسط بیشتر frontend ها برای کشف مدل لازم است. عمداً سطح ارزان سازگار-با-OpenAI است و همهٔ ترکیب‌های provider/model احراز‌شده یا قیمت‌گذاری را enumerate نمی‌کند.

‏GET /api/model/options

کلاینت‌های هرمس-آگاه می‌توانند همان موجودی منتخب provider/model که داشبورد و TUI مصرف می‌کنند را بخواهند. این route احراز bearer معمول سرور API را دارد و ردیف‌های ارائه‌دهنده، ‏سرنخ‌های قابلیت مدل و متادیتای قیمت‌گذاری خارج از محدودهٔ /v1/models را برمی‌گرداند. باز شدن‌های عادی برای ارائه‌دهنده‌های سفارشی محافظه‌کارند — فقط نقطهٔ پایانی سفارشیِ فعلاً-انتخاب‌شده probe می‌شود؛ refresh ی صریح به probing کامل فلپ و کش مدل ارائه‌دهنده را bust می‌کند ‏(?refresh=1).

‏GET /v1/capabilities

توصیف machine-readable از سطح پایدار سرور API برای UI های بیرونی، orchestrator ها و پل‌های پلاگین برمی‌گرداند — chat_completions، ‏responses_api، ‏run_submission/status/events_sse/stop و… . موقع یکپارچه‌سازی داشبوردها یا control plane ها این endpoint را مصرف کنید تا بدون اتکا به internals ی خصوصی پایتون تشخیص دهند نسخهٔ در حال اجرا چه پشتیبانی می‌کند.

۳ کنترل مرورگر از طریق افزونه

هرمس می‌تواند ابزارهای مرورگر را از طریق افزونه‌ای احراز‌شده که نشست مرورگر مقید به نشست فعلی هرمس را کنترل می‌کند مسیریابی دهد. پیش‌فرض خاموش است؛ browser.extension_control.enabled را true کنید. مسیر API ی محلی هم کلید bearer ی سرور API را می‌خواهد. controller فقط برای یک نشست سرور موجود ثبت می‌شود و principal از وضعیت احراز‌شدهٔ سرور مشتق می‌شود؛ principal_id ی ارسالی-کلاینت نادیده گرفته می‌شود.

قرارداد زنده را از GET /v1/capabilities کشف کنید — آبجکت browser_extension_control فعال بودن، نسخهٔ پروتکل، نام transport ها و allowlist ی دقیق قابلیت‌ها را گزارش می‌کند ‏(browser_click/navigate/type/scroll/snapshot/back/press/tabs/tab_activate/screenshot/controller.noop). قابلیت‌های خارج این فهرست فیلتر می‌شوند؛ ‏CDP خام، ‏eval ی اسکریپت دلخواه، ‏دسترسی console، ‏آپلود، ‏استخراج تصویر و vision بخش پروتکل controller نیستند.

وقتی درخواستی هویت controller مقید ندارد یا قابلیت خاموش است هرمس backend ی موجود مرورگر را حفظ می‌کند. بعد از bind شدن controller به درخواست، آن لاین authoritative است: ‏controller های غایب/مبهم/قطع‌شده/ناکارا fail closed می‌کنند نه اینکه بی‌سروصدا به مرورگر محلی/ابری دیگری سوئیچ کنند. بعد از انتخاب دقیق controller نتیجه یا خطایش authoritative است و هرمس هرگز همان اقدام را از backend دیگری retry نمی‌کند.

ثبت از طریق API ی محلی

  1. ‏POST /v1/browser-control/register ی احراز‌شده با protocol_version، ‏session_id، ‏controller_id، ‏browser_profile_id و capabilities ی خواسته بفرستید.
  2. هرمس ticket ی تک‌مصرفی با TTL ی ۳۰ ثانیه و scope ی فیلترشده برمی‌گرداند.
  3. GET /v1/browser-control/ws را با هر دو زیرپروتکل WebSocket باز کنید: hermes-browser-control-v1 و hermes-browser-control-ticket.<ticket>.

ticket هرگز در query string پذیرفته نمی‌شود. ticket های ناشناخته، منقضی، ‏مصرف‌شده یا بدفرم قبل از upgrade ی WebSocket رد می‌شوند.

فریم‌های controller

هرمس فریم‌های browser.controller.command با command_id، ‏action، ‏arguments ی تغییرناپذیر، شناسه‌های مرورگر/controller و tool_call_id ی مبدأ می‌فرستد. controller با browser.controller.result، همان command_id، ‏ok ی دقیقاً boolean و result یا error جواب می‌دهد. لغو و timeout مقدار browser.controller.cancel emit می‌کنند؛ نتایج دیرهنگام نادیده گرفته می‌شوند.

قطع غیرمنتظرهٔ socket کنترلر را offline علامت و کار در-جریان را تا deadline اصلی هر فرمان حفظ می‌کند. reconnect با همان هویت transport را refresh می‌کند بدون پذیرش کار جدید قبل از flush شدن cancel های معوق. تغییر controller id یا browser profile در همان lane ی احراز‌شده جایگزینی سخت است: کار معوق قدیمی قبل از قابل-مسیر شدن جانشین لغو می‌شود. ‏browser.controller.detach روی transport ی احراز‌شده برای detach سخت عمدی بفرستید — فوراً کار pending را لغو می‌کند؛ صرف بستن socket قطع قابل-ریکاوری تلقی می‌شود.

transport ی داشبورد احراز‌شده همین معناشناسی ثبت/نتیجه/heartbeat/قابلیت/مالکیت را روی کانال RPC/event ی Gateway خودش ارائه می‌دهد. در هر دو transport، انتخاب نیازمند یک تطبیق دقیق بی‌ابهام روی principal، ‏profile، ‏session، ‏controller، ‏browser profile، ‏خانواده transport و قابلیت است. بعد از انتخاب شکست controller authoritative است و هرگز از backend مرورگری دیگر retry نمی‌شود.

۴ انتخاب مدل per-request

کلاینت‌های احراز‌شده می‌توانند انتخاب پیش‌فرض مدل هرمس را per-request بازنویسی کنند با ارسال model ‏(شناسه مدل هدف این نوبت)، ‏provider ‏(slug ی هرمس برای حل credential/runtime) و model_options ‏(کنترل‌های reasoning/service-tier ی scope‌شده-به-درخواست).

همین فیلدها روی POST /v1/chat/completions، ‏POST /v1/responses، ‏POST /v1/runs، ‏POST /api/sessions/{id}/chat و chat/stream پذیرفته می‌شوند. اولویت قطعی است:

  1. override ی ‎/model‎ ی نشست اگر آن نشست داشته باشد
  2. نگاشت ایستای gateway.platforms.api_server.model_routes وقتی model ی درخواست alias ی مسیر پیکربندی‌شده باشد
  3. model/provider مستقیم درخواست وقتی هیچ alias ای نخورد
  4. پیش‌فرض‌های سراسری config ی گیت‌وی / محیط

model_options فارغ از برنده بودن مدل/ارائه‌دهنده scope ی درخواست می‌ماند. اگر درخواست provider ای بفرستد که با alias ی model_routes تضاد داشته باشد هرمس با ۴۰۰ رد می‌کند نه اینکه بی‌سروصدا credential های مسیر را با ارائه‌دهندهٔ دیگری مخلوط کند.

مقادیر لخت model روی نقاط پایانی سازگار-با-OpenAI opt-in اند. کلاینت‌های عمومی OpenAI مرتباً نام مدل هاردکد می‌کنند ‏(gpt-4o و…) و استقرارهای فعلی به fallback آنها به پیش‌فرض گیت‌وی تکیه دارند. روی chat/completions و responses مقدار model بدون provider نادیده گرفته می‌شود مگر این را روشن کنید:

yaml
gateway:
  platforms:
    api_server:
      direct_model_requests: true

درخواست‌های دارای provider صریح — و نقاط پایانی native ی ‎/v1/runs‎ و session-chat — فارغ از این فلگ مدل خواسته را محترم می‌شمارند. مثال درخواست با model_options شامل reasoning_effort: high و service_tier: priority.

‏GET /health و ‏GET /health/detailed

بررسی سلامت. ‏{"status": "ok"} برمی‌گرداند؛ روی GET /v1/health هم برای کلاینت‌های سازگار-با-OpenAI موجود است. ‏/health/detailed بررسی آمادگی احراز‌شده برای مانیتورینگ و control plane هاست و وضعیت محدود config پروفایل فعال، ‏DB ی وضعیت، ‏مدل پیکربندی‌شده، فضای دیسک، وضعیت گیت‌وی/پلتفرم، run های فعال API، تکمیل‌های pending ی پروسه و delegation های فعال را گزارش می‌کند — فقط وضعیت و شمارنده‌ها، نه مقادیر config، ‏credential ها، ‏مسیرها، فرمان‌ها، payload صف یا خطاهای خام. ‏/health عمومی همچنان probe ی ارزان liveness است و readiness چک نمی‌کند؛ نتیجهٔ degraded هنوز HTTP 200 است و فیلدهای status و readiness.checks را inspect کنید.

۵ Runs API و Jobs API

Runs API

علاوه بر chat/completions و responses، سرور API ی runs را برای نشست‌های بلند expose می‌کند که کلاینت می‌خواهد به رویدادهای پیشرفت مشترک شود به‌جای مدیریت خودِ streaming:

  • ‏POST /v1/runs — ایجاد run جدید؛ ‏run_id برای subscribe کردن به رویدادهای پیشرفت برمی‌گردد. ورودی رشتهٔ input ساده + session_id/instructions/conversation_history/previous_response_id اختیاری.
  • ‏GET /v1/runs/{run_id} — poll ی وضعیت فعلی؛ برای داشبوردهایی که SSE باز نگه نمی‌دارند. وضعیت‌ها مدتی بعد از حالات پایانه ‏(completed/failed/cancelled) برای reconciliation حفظ می‌شوند.
  • ‏GET /v1/runs/{run_id}/events — استریم SSE ی پیشرفت tool-call، دلتاهای توکن و رویدادهای چرخهٔ حیات. هنگام delegation به زیرایجنت‌ها رویدادهای subagent.start/complete هم carry می‌شوند ‏(وضعیت، خلاصه، مدت، توکن/هزینه، child_session_id)؛ رویدادهای per-tool فرزندان عمداً forward نمی‌شوند — transcript زندهٔ per-child را ببینید. بافرهای رویداد مصرف‌نشده بعد از ۵ دقیقه منقضی می‌شوند؛ فقط state ی transport است — run ی در حال اجرا برای polling، تأیید، stop و حساب concurrency تا خروج واقعی executor مرئی می‌ماند.
  • ‏POST /v1/runs/{run_id}/stop — قطع نوبت ایجنتی در حال اجرا؛ فوراً stopping برمی‌گرداند و بعد از خروج کار settled به cancelled می‌نشیند.
  • ‏POST /v1/runs/{run_id}/approval — حل تأیید pending برای run ی منتظر تصمیم انسانی؛ run بعد از ثبت تصمیم ادامه می‌یابد. در capabilities به‌عنوان run_approval advertise می‌شود.

Jobs API

سطح CRUD سبکی برای مدیریت اجراهای زمان‌بندی/پس‌زمینه از کلاینت راه‌دور؛ همه پشت همان auth ی bearer:

  • ‏GET /api/jobs — فهرست همهٔ job های زمان‌بندی‌شده
  • ‏POST /api/jobs — ساخت job جدید؛ body همان شکل hermes cron را می‌پذیرد ‏(prompt، schedule، مهارت‌ها، override ی ارائه‌دهنده، هدف تحویل)
  • ‏GET/PATCH/DELETE /api/jobs/{job_id} — خواندن تعریف و آخرین اجرا / merge ی partial update / حذف همراه لغو اجرای در-جریان
  • ‏POST …/pause و …/resume — توقف موقت (تعلیق timestamp های اجرای بعدی) و ازسرگیری
  • ‏POST …/run — trigger ی فوری خارج از برنامه

۶ Sessions API، کشف مهارت‌ها و کلید نشست بلندمدت

Sessions API

UI های بیرونی می‌توانند نشست‌های هرمس را از طریق REST مدیریت کنند بدون بالا آوردن داشبورد. همه gated با API_SERVER_KEY و زیر /api/sessions/*: فهرست صفحه‌بندی‌شده، ‏ساخت نشست خالی، ‏خواندن متادیتا، ‏ویرایش title/end_reason، ‏حذف، ‏تاریخچهٔ پیام‌ها، ‏fork از طریق lineage ی SessionDB ‏(مطابق ‎/branch‎ ی CLI)، ‏اجرای یک نوبت همگام و wrapper ی SSE یک نوبت ‏(رویدادهای assistant.delta، ‏tool.started، ‏tool.completed، ‏run.completed). تصاویر inline در chat و chat/stream پشتیبانی می‌شوند. مثال curl برای fork و stream در متن اصلی.

کشف مهارت‌ها و تول‌ست‌ها

GET /v1/skills و GET /v1/toolsets به کلاینت‌های بیرونی اجازه می‌دهد قابلیت‌های ایجنت را قطعی از طریق REST enumerate کنند نه اینکه از مدل بپرسند. هر دو فقط-خواندنی و gated با کلید هستند؛ skills همان متادیتای hub ی مهارت‌ها و toolsets مجموعه‌های حل‌شده برای پلتفرم api_server با فهرست concrete ی tools هرکدام را برمی‌گرداند. هر دو در capabilities زیر endpoints.* advertise می‌شوند.

scope ی حافظهٔ بلندمدت ‏(X-Hermes-Session-Key)

frontend های چند-کاربره مثل Open WebUI برای حافظهٔ بلندمدت ‏(Honcho و…) به شناسهٔ پایدار per-channel نیاز دارند که مستقل از X-Hermes-Session-Id ی scope‌شده-به-transcript ‏(که روی ‎/new‎ می‌چرخد) باشد. مقدار X-Hermes-Session-Key را روی chat/completions، ‏responses یا runs بفرستید و هرمس آن را تا AIAgent(gateway_session_key=...) عبور می‌دهد تا ارائه‌دهندهٔ Honcho از آن scope ی پایدار مشتق کند. قواعد: حداکثر ۲۵۶ نویسه، نویسه‌های کنترلی رد می‌شوند و مقدار روی پاسخ‌ها echo می‌شود. بدون این کلید، استراتژی per-session ی Honcho per session_id یک scope متفاوت تولید می‌کند — دقیقاً رفتار قبلی هرمس.

هندل System Prompt

وقتی frontend پیام system ‏(Chat Completions) یا instructions ‏(Responses) بفرستد، hermes-agent آن را روی پرامپت سیستمی هسته‌اش لایه می‌کند. ایجنت همهٔ ابزارها، حافظه و مهارت‌هایش را نگه می‌دارد — پرامپت سیستم frontend فقط دستورالعمل اضافه می‌کند. یعنی رفتار را per-frontend سفارشی می‌کنید بدون از دست دادن قابلیت‌ها.

۷ احراز هویت، مسیریابی چند-پروفایلی و پیکربندی

احراز هویت

Bearer token از طریق هدر Authorization. کلید با API_SERVER_KEY ست می‌شود. اگر مرورگر باید مستقیم صدا بزند API_SERVER_CORS_ORIGINS را هم به allowlist ی صریح ست کنید.

مسیریابی چند-پروفایلی ‏(‎/p/<profile>/…‎)

با فعال بودن مسیریابی چند-پروفایلی گیت‌وی، شنوندهٔ مشترک هر پروفایل را از طریق پیشوند /p/<profile>/ سرو می‌کند و احراز هویت به پروفایل مسیریابی‌شده مقید است: درخواست‌های /p/<profile>/v1/... باید API_SERVER_KEY ی خودِ آن پروفایل را ارائه کنند و کلید شنوندهٔ پیش‌فرض روی پیشوندهای نام‌دار رد می‌شود؛ مسیرهای بدون پیشوند و /p/default/... از کلید پیش‌فرض استفاده می‌کنند؛ پروفایل نام‌دار بدون کلید اختصاصی fail closed می‌شود.

⚠️ تغییر breaking ‏(ژوئیه ۲۰۲۶)

قبل از این fix، کلید معتبر پروفایل پیش‌فرض روی هر پیشوند /p/<profile>/ پذیرفته می‌شد. اگر روی share کردن یک کلید بین پیشوندها تکیه داشتید، برای هر پروفایل API_SERVER_KEY ی متمایز ست کنید — کلیدهای پیش‌فرض بازیافتی روی پیشوندهای نام‌دار الان 401 می‌دهند.

⚠️ امنیت

سرور API دسترسی کامل به تول‌ست hermes-agent می‌دهد، شامل فرمان‌های ترمینال. ‏API_SERVER_KEY برای هر استقراری الزامی است حتی bind ی پیش‌فرض loopback روی 127.0.0.1. ‏API_SERVER_CORS_ORIGINS را محدود نگه دارید تا دسترسی مرورگر را وقتی صریحاً مجازش می‌کنید کنترل کنید.

سقف اجرای هم‌زمان

سرور API محدود می‌کند چند اجرای ایجنت همزمان از نقاط پایانی سازگار-با-OpenAI و Runs اجرا شوند؛ از gateway.api_server.max_concurrent_runs خوانده می‌شود ‏(پیش‌فرض ۱۰؛ صفر = بی‌حد؛ منفی به صفر clamp). رسیدن به سقف یعنی درخواست‌های start جدید با HTTP 429 «Too many concurrent runs (max N)» رد می‌شوند — کلاینت backoff و retry کند.

هدرهای امنیتی و CORS

  • همهٔ پاسخ‌ها X-Content-Type-Options: nosniff و Referrer-Policy: no-referrer دارند.
  • CORS پیش‌فرض روشن نیست؛ برای دسترسی مستقیم مرورگر allowlist ی صریح ست کنید. با فعال بودن CORS: ‏preflight ها Access-Control-Max-Age: 600 دارند، پاسخ‌های SSE هدرهای CORS دارند و Idempotency-Key هدر درخواست مجاز است ‏(پاسخ‌ها ۵ دقیقه per-key کش می‌شوند).
  • بیشتر frontend های مستند مثل Open WebUI server-to-server وصل می‌شوند و اصلاً CORS نمی‌خواهند.

setup چندکاربره با پروفایل‌ها

برای دادن نمونهٔ هرمس ایزوله به هر کاربر ‏(config، حافظه، مهارت‌های جدا) از پروفایل‌ها استفاده کنید: per کاربر profile بسازید، API_SERVER_* را در .env ی هر پروفایل با پورت و کلید متمایز بنویسید و گیت‌وی هر پروفایل را اجرا کنید. سرور API هر پروفایل خودکار نام پروفایل را به‌عنوان model ID advertise می‌کند — در Open WebUI هرکدام را اتصال جدا اضافه کنید تا alice و bob به‌عنوان مدل‌های متمایز با نمونه‌های هرمس کاملاً ایزوله دیده شوند.

محدودیت‌ها و Proxy Mode

  • ذخیرهٔ پاسخ‌ها — پاسخ‌های ذخیره‌شده ‏(برای previous_response_id) در SQLite ماندگارند و از ری‌استارت گیت‌وی جان می‌برند؛ حداکثر ۱۰۰ پاسخ ‏(eviction ی LRU).
  • بدون آپلود فایل — تصاویر inline روی هر دو endpoint پشتیبانی می‌شوند ولی فایل‌های آپلودی و ورودی‌های سند غیر-تصویری از طریق API پشتیبانی نمی‌شوند.
  • کلاینت‌های ساده OpenAI همچنان alias می‌بینند — ‎/v1/models‎ مقدار پایدار alias ی هرمس را advertise می‌کند؛ کلاینت‌های غنی می‌توانند provider/model_options صریح بفرستند.
  • Proxy Mode — سرور API بک‌اند حالت proxy ی گیت‌وی هم هست: گیت‌وی هرمس دیگری با GATEWAY_PROXY_URL به این سرور همهٔ پیام‌ها را forward می‌کند به‌جای اجرای ایجنت خودش؛ استقرارهای split مثل کانتینر Docker ی هندل‌کنندهٔ Matrix E2EE که به ایجنت سمت-host relay می‌کند ممکن می‌شود. راهنمای کامل در بخش Proxy Mode ی Matrix.
