هوک‌های رویداد ‏(Event Hooks)

هرمس چهار سیستم هوک دارد که کد سفارشی را در نقاط کلیدی چرخهٔ حیات اجرا می‌کنند:

سیستمثبت از طریقاجرا درمورد استفاده
هوک‌های گیت‌وی‏HOOK.yaml + ‏handler.py در ‏~/.hermes/hooks/فقط گیت‌ویلاگ‌گیری، هشدارها، وب‌هوک‌ها
هوک‌های پلاگین‏ctx.register_hook() در یک پلاگینCLI + گیت‌ویinterception ی ابزار، متریک‌ها، گاردها
هوک‌های شلبلوک ‏hooks: در ‏~/.hermes/config.yaml اشاره‌کننده به اسکریپت‌های شلCLI + گیت‌ویاسکریپت‌های drop-in برای بلاک کردن، فرمت خودکار، تزریق زمینه
وب‌هوک‌های خروجیفهرست ‏hooks.outbound: در ‏~/.hermes/config.yamlCLI + گیت‌ویpush ی رویدادهای چرخهٔ حیاتِ امضاشده به نقطه‌پایان‌های HTTP بیرونی — CI، داشبوردها، ایجنت‌های دیگر

خطاهای callback ی هوک ایزوله و لاگ می‌شوند نه اینکه ایجنت را کرش کنند. هوک‌ها همه منفعل نیستند: هوک‌های directive/control می‌توانند جریان را عوض کنند، transform ها می‌توانند محتوا را جایگزین کنند و یک هوک شل ی ‏pre_tool_call می‌تواند بلاک یا fail closed کند.

۱ هوک‌های رویداد گیت‌وی

هوک‌های گیت‌وی حین عملکرد گیت‌وی ‏(تلگرام، ‏دیسکورد، ‏اسلک، ‏واتساپ، ‏Teams) خودکار شلیک می‌شوند بدون بلاک کردن خط‌لولهٔ اصلی ایجنت.

ساخت یک هوک

هر هوک دایرکتوری‌ای زیر ‏~/.hermes/hooks/ است شامل دو فایل:

~/.hermes/hooks/
└── my-hook/
    ├── HOOK.yaml      # Declares which events to listen for
    └── handler.py     # Python handler function

‏HOOK.yaml

yaml
name: my-hook
description: Log all agent activity to a file
events:
  - agent:start
  - agent:end
  - agent:step

فهرست events تعیین می‌کند کدام رویدادها هندلرتان را شلیک کنند. می‌توانید به هر ترکیبی از رویدادها مشترک شوید شامل wildcard هایی مثل ‏command:*.

‏handler.py

import json
from datetime import datetime
from pathlib import Path

LOG_FILE = Path.home() / ".hermes" / "hooks" / "my-hook" / "activity.log"

async def handle(event_type: str, context: dict):
    """Called for each subscribed event. Must be named 'handle'."""
    entry = {
        "timestamp": datetime.now().isoformat(),
        "event": event_type,
        **context,
    }
    with open(LOG_FILE, "a") as f:
        f.write(json.dumps(entry) + "\n")

قواعد هندلر:

  • باید نامش handle باشد
  • ‏event_type ‏(رشته) و context ‏(dict) دریافت می‌کند
  • می‌تواند ‏async def یا def ی معمولی باشد — هر دو کار می‌کنند
  • خطاها گرفته و لاگ می‌شوند؛ هرگز ایجنت را کرش نمی‌کنند

رویدادهای موجود

رویدادکی شلیک می‌شودکلیدهای context
gateway:startupپروسهٔ گیت‌وی شروع شود‏platforms ‏(فهرست نام پلتفرم‌های فعال)
session:startنشست پیام‌رسانی جدید ساخته شود‏platform، ‏user_id، ‏session_id، ‏session_key
session:endنشست تمام شود ‏(قبل از reset)‏platform، ‏user_id، ‏session_key
session:resetکاربر ‏/new یا ‏/reset بزند‏platform، ‏user_id، ‏session_key
session:compressفشرده‌سازی زمینه برای نشستی کامل شود‏platform، ‏session_id، ‏old_session_id ‏(خالی وقتی درجا compact شده)، ‏in_place ‏(بولی — true یعنی transcript روی همان id فشرده شده، false یعنی از old_session_id چرخیده)، ‏compression_count
agent:startایجنت پردازش یک پیام را شروع کند‏platform، ‏user_id، ‏chat_id، ‏thread_id ‏(شناسهٔ ریشهٔ forum-topic/thread؛ خالی وقتی داخل thread نیست)، ‏chat_type ‏(dm | group | forum؛ خالی اگر نامعلوم)، ‏session_id، ‏message ‏(بریده تا ۵۰۰ نویسه)
agent:stepهر تکرار حلقهٔ فراخوانی ابزار‏platform، ‏user_id، ‏session_id، ‏iteration، ‏tool_names
agent:endایجنت پردازش را تمام کندهمان کلیدهای agent:start به‌علاوهٔ ‏response ‏(بریده تا ۵۰۰ نویسه)
reaction:addedیک ری‌اکشن ایموجی به پیامی که ربات می‌بیند اضافه شود ‏(فعلاً adapter ی اسلک). نیازمند scope ی reactions:read + اشتراک رویداد باتی reaction_added؛ ربات باید عضو کانال باشد.‏platform، ‏reaction، ‏user_id، ‏item_user_id، ‏item_type، ‏channel_id، ‏message_ts، ‏team_id، ‏event_ts، ‏raw_event
reaction:removedیک ری‌اکشن ایموجی از پیامی که ربات می‌بیند حذف شود. نیازمند اشتراک رویداد باتی reaction_removed.همان شکل reaction:added
command:*هر دستور اسلشی اجرا شود‏platform، ‏user_id، ‏command، ‏args

تطبیق wildcard

هندلرهای ثبت‌شده برای ‏command:* برای هر رویداد command: شلیک می‌شوند ‏(command:model، ‏command:reset و…). همهٔ دستورات اسلش را با یک اشتراک مانیتور کنید.

💡 پاسخ‌های threaded

هندلری که پیام پیگیری داخل همان forum topic ی تلگرام پست می‌کند باید وقتی chat_type == «forum» و thread_id غیرخالی است ‏message_thread_id=int(thread_id) را هم بگنجاند.

هشدار تلگرام روی تسک‌های طولانی

وقتی ایجنت بیش از ۱۰ قدم برد به خودتان پیام بدهید:

# ~/.hermes/hooks/long-task-alert/HOOK.yaml
name: long-task-alert
description: Alert when agent is taking many steps
events:
  - agent:step
# ~/.hermes/hooks/long-task-alert/handler.py
import os
import httpx

THRESHOLD = 10
BOT_TOKEN = os.getenv("TELEGRAM_BOT_TOKEN")
CHAT_ID = os.getenv("TELEGRAM_HOME_CHANNEL")

async def handle(event_type: str, context: dict):
    iteration = context.get("iteration", 0)
    if iteration == THRESHOLD and BOT_TOKEN and CHAT_ID:
        tools = ", ".join(context.get("tool_names", []))
        text = f"⚠️ Agent has been running for {iteration} steps. Last tools: {tools}"
        async with httpx.AsyncClient() as client:
            await client.post(
                f"https://api.telegram.org/bot{BOT_TOKEN}/sendMessage",
                json={"chat_id": CHAT_ID, "text": text},
            )

لاگر مصرف فرمان‌ها

ردیابی اینکه کدام دستورات اسلش استفاده می‌شوند:

# ~/.hermes/hooks/command-logger/HOOK.yaml
name: command-logger
description: Log slash command usage
events:
  - command:*
# ~/.hermes/hooks/command-logger/handler.py
import json
from datetime import datetime
from pathlib import Path

LOG = Path.home() / ".hermes" / "logs" / "command_usage.jsonl"

def handle(event_type: str, context: dict):
    LOG.parent.mkdir(parents=True, exist_ok=True)
    entry = {
        "ts": datetime.now().isoformat(),
        "command": context.get("command"),
        "args": context.get("args"),
        "platform": context.get("platform"),
        "user": context.get("user_id"),
    }
    with open(LOG, "a") as f:
        f.write(json.dumps(entry) + "\n")

وب‌هوک شروع نشست

روی نشست‌های جدید به یک سرویس بیرونی POST بزنید:

# ~/.hermes/hooks/session-webhook/HOOK.yaml
name: session-webhook
description: Notify external service on new sessions
events:
  - session:start
  - session:reset
# ~/.hermes/hooks/session-webhook/handler.py
import httpx

WEBHOOK_URL = "https://your-service.example.com/hermes-events"

async def handle(event_type: str, context: dict):
    async with httpx.AsyncClient() as client:
        await client.post(WEBHOOK_URL, json={
            "event": event_type,
            **context,
        }, timeout=5)

آموزش: BOOT.md — اجرای چک‌لیست راه‌اندازی در هر boot ی گیت‌وی

الگویی محبوب از جامعهٔ کاربری: یک چک‌لیست Markdown در ‏~/.hermes/BOOT.md بگذارید و بگذارید ایجنت هر بار که گیت‌وی شروع می‌شود یک بار اجرایش کند. مفید برای جملاتی مثل «در هر boot، شکست‌های cron ی شبانه را بررسی کن و اگر چیزی شکست خورد در دیسکورد خبرم کن» یا «۲۴ ساعت آخر deploy.log را خلاصه کن و در اسلک ‎#ops‎ بگذار.»

این آموزش نشان می‌دهد چطور خودتان آن را به‌عنوان یک هوک تعریف‌شده-توسط-کاربر بسازید. هرمس هوک BOOT.md داخلی ندارد — دقیقاً رفتاری که می‌خواهید را سیم‌کشی می‌کنید.

چه چیزی می‌سازیم

  1. یک فایل در ‏~/.hermes/BOOT.md با دستورالعمل‌های راه‌اندازی زبان-طبیعی.
  2. یک هوک گیت‌وی که روی gateway:startup شلیک می‌کند، یک ایجنت تک‌مصرفی با مدل/اعتبارنامه‌های حل‌شدهٔ گیت‌وی spawn و دستورالعمل‌های BOOT.md را اجرا می‌کند.
  3. یک قرارداد [SILENT] تا ایجنت وقتی چیزی برای گزارش نیست از فرستادن پیام انصراف دهد.

گام ۱: چک‌لیست را بنویسید

‏~/.hermes/BOOT.md را بسازید. طوری بنویسیدش که انگار به یک دستیار انسانی دستور می‌دهید:

# Startup Checklist

1. Run `hermes cron list` and check if any scheduled jobs failed overnight.
2. If any failed, summarize them for Discord #ops (the hook delivers your final response to its configured target).
3. Check if `/opt/app/deploy.log` has any ERROR lines from the last 24 hours. If yes, summarize them and include in the same report.
4. If nothing went wrong, reply with only `[SILENT]` so no message is sent.

ایجنت این را بخشی از پرامپتش می‌بیند، پس هر چه در زبان ساده توصیف کنید کار می‌کند — فراخوانی ابزار، فرمان شل، فرستادن پیام، خلاصه‌سازی فایل.

گام ۲: هوک را بسازید

~/.hermes/hooks/boot-md/
├── HOOK.yaml
└── handler.py

‏~/.hermes/hooks/boot-md/HOOK.yaml

yaml
name: boot-md
description: Run ~/.hermes/BOOT.md on gateway startup
events:
  - gateway:startup

‏~/.hermes/hooks/boot-md/handler.py

"""Run ~/.hermes/BOOT.md on every gateway startup."""

import logging
import threading
from pathlib import Path

logger = logging.getLogger("hooks.boot-md")

BOOT_FILE = Path.home() / ".hermes" / "BOOT.md"


def _build_prompt(content: str) -> str:
    return (
        "You are running a startup boot checklist. Follow the instructions "
        "below exactly.\n\n"
        "---\n"
        f"{content}\n"
        "---\n\n"
        "Execute each instruction. Put any user-facing summary in your "
        "final response — the hook delivers it to the configured channel "
        "(e.g. Discord or Slack); you do not send messages yourself.\n"
        "If nothing needs attention and there is nothing to report, reply "
        "with ONLY: [SILENT]"
    )


def _run_boot_agent(content: str) -> None:
    """Spawn a one-shot agent and execute the checklist.

    Uses the gateway's resolved model and runtime credentials so this works
    against custom endpoints, aggregators, and OAuth-based providers alike.
    """
    try:
        from gateway.run import _resolve_gateway_model, _resolve_runtime_agent_kwargs
        from run_agent import AIAgent

        agent = AIAgent(
            model=_resolve_gateway_model(),
            **_resolve_runtime_agent_kwargs(),
            platform="gateway",
            quiet_mode=True,
            skip_context_files=True,
            skip_memory=True,
            max_iterations=20,
        )
        result = agent.run_conversation(_build_prompt(content))
        response = (result.get("final_response", "") or "").strip()
        if response.upper() not in {"[SILENT]", "SILENT", "NO_REPLY", "NO REPLY"}:
            logger.info("boot-md completed: %s", response[:200])
        else:
            logger.info("boot-md completed (nothing to report)")
    except Exception as e:
        logger.error("boot-md agent failed: %s", e)


async def handle(event_type: str, context: dict) -> None:
    if not BOOT_FILE.exists():
        return
    content = BOOT_FILE.read_text(encoding="utf-8").strip()
    if not content:
        return

    logger.info("Running BOOT.md (%d chars)", len(content))

    # Background thread so gateway startup isn't blocked on a full agent turn.
    thread = threading.Thread(
        target=_run_boot_agent,
        args=(content,),
        name="boot-md",
        daemon=True,
    )
    thread.start()

دو خط کلیدی:

  • ‏_resolve_gateway_model() مدل فعلاً-پیکربندی‌شدهٔ گیت‌وی را می‌خواند.
  • ‏_resolve_runtime_agent_kwargs() اعتبارنامه‌های ارائه‌دهنده را مثل یک نوبت عادی گیت‌وی حل می‌کند — شامل کلیدهای API، ‏base URL ها، ‏توکن‌های OAuth و استخرهای اعتبارنامه.

بدون اینها یک AIAgent() ی لخت به پیش‌فرض‌های داخلی برمی‌گردد و با هر نقطهٔ پایانی غیر-پیش‌فرض ۴۰۱ می‌گیرد.

گام ۳: تستش کنید

گیت‌وی را ری‌استارت کنید:

hermes gateway restart

لاگ‌ها را زیر نظر بگیرید:

hermes logs --follow --level INFO | grep boot-md

باید «Running BOOT.md (N chars)» را ببینید و بعدش یا «boot-md completed: ...» ‏(خلاصهٔ کار ایجنت) یا وقتی ایجنت دقیقاً با یک توکن سکوت مثل [SILENT] جواب داده باشد «boot-md completed (nothing to report)».

برای غیرفعال کردن چک‌لیست ‏~/.hermes/BOOT.md را حذف کنید — هوک لود شده می‌ماند ولی وقتی فایل نباشد بی‌صدا skip می‌کند.

گسترش الگو

  • چک‌لیست‌های آگاه-از-زمان‌بندی: داخل دستورالعمل‌های BOOT.md به ‏datetime.now().weekday() اشاره کنید («اگر دوشنبه است، لاگ deploy هفتگی را هم چک کن»). دستورالعمل‌ها متن آزادند پس هر چیزی که ایجنت بتواند درباره‌اش استدلال کند مجاز است.
  • چک‌لیست‌های متعدد: هوک را به فایل دیگری ‏(STARTUP.md، ‏MORNING.md و…) اشاره دهید و دایرکتوری هوک جداگانه برای هرکدام ثبت کنید.
  • نسخهٔ غیر-ایجنتی: اگر حلقهٔ کامل ایجنت نمی‌خواهید کلاً از AIAgent عبور کنید و هندلر مستقیماً با httpx نوتیفیکیشن ثابت پست کند. ارزان‌تر، سریع‌تر و بدون وابستگی به ارائه‌دهنده.

چرا داخلی نشده

نسخهٔ قبلی هرمس این را به‌عنوان هوک داخلی ارسال می‌کرد و در هر boot ی گیت‌وی بی‌سروصدا ایجنتی با پیش‌فرض‌های لخت spawn می‌کرد. کاربرانِ دارای نقطه‌پایانی سفارشی را غافلگیر می‌کرد و قابلیت برای کاربرانی که نمی‌دانستند در حال اجراست نامرئی بود. نگه داشتنش به‌عنوان یک الگوی مستند — ساخته‌شده توسط شما، در دایرکتوری هوک‌هایتان — یعنی دقیقاً می‌بینید چه می‌کند و با نوشتن فایل‌ها انتخابش می‌کنید.

نحوهٔ کار

  1. هنگام startup ی گیت‌وی، ‏HookRegistry.discover_and_load() مقدار ‏~/.hermes/hooks/ را اسکن می‌کند
  2. هر زیردایرکتوری با HOOK.yaml + handler.py به‌صورت داینامیک بارگذاری می‌شود
  3. هندلرها برای رویدادهای اعلام‌شده‌شان ثبت می‌شوند
  4. در هر نقطهٔ چرخهٔ حیات، ‏hooks.emit() همهٔ هندلرهای منطبق را شلیک می‌کند
  5. خطاهای هر هندلر گرفته و لاگ می‌شوند — هوک خراب هرگز ایجنت را کرش نمی‌کند
📌

هوک‌های گیت‌وی فقط در گیت‌وی شلیک می‌شوند ‏(تلگرام، ‏دیسکورد، ‏اسلک، ‏واتساپ، ‏Teams). CLI هوک‌های گیت‌وی را load نمی‌کند. برای هوک‌هایی که همه‌جا کار کنند از هوک‌های پلاگین استفاده کنید.

۲ هوک‌های پلاگین

پلاگین‌ها می‌توانند هوک‌هایی ثبت کنند که در نشست‌های هم CLI و هم گیت‌وی شلیک می‌شوند. اینها به‌صورت برنامه‌نویسی‌شده از طریق ‏ctx.register_hook() در تابع register() ی پلاگین‌تان ثبت می‌شوند.

برای جزئیات بسته‌بندی و ثبت پلاگین، راهنمای پلاگین‌ها را ببینید.

def register(ctx):
    ctx.register_hook("pre_tool_call", my_tool_observer)
    ctx.register_hook("post_tool_call", my_tool_logger)
    ctx.register_hook("pre_llm_call", my_memory_callback)
    ctx.register_hook("post_llm_call", my_sync_callback)
    ctx.register_hook("on_session_start", my_init_callback)
    ctx.register_hook("on_session_end", my_cleanup_callback)
    # Kanban board lifecycle (dependency-wait blocking may fire inside its transaction):
    ctx.register_hook("kanban_task_claimed", my_claim_callback)     # dispatcher process
    ctx.register_hook("kanban_task_completed", my_done_callback)    # worker process
    ctx.register_hook("kanban_task_blocked", my_blocked_callback)   # worker process

قواعد عمومی همهٔ هوک‌ها:

  • callback ها آرگومان‌های کلیدواژه‌ای می‌گیرند. برای سازگاری رو-به-جلو همیشه ‏**kwargs را بپذیرید.
  • exception های callback لاگ و skip می‌شوند؛ callback های بعدی ادامه می‌یابند.
  • کاتالوگ پایین توصیفی است: observer ها مقدار بازگشتی را نادیده می‌گیرند، transform ها اولین جایگزینی رشته‌ای معتبر را می‌پذیرند و هوک‌های directive/control شکل‌های بازگشتی مستند را مصرف می‌کنند. middleware ی پلاگین یک registry و سطح جداست نه دستهٔ دیگری از هوک‌ها.
  • فیلدهای correlation مثل turn_id، ‏api_request_id، ‏task_id، ‏session_id و api_call_count مخصوص-هوک‌اند و ممکن است غایب باشند. با IDها به‌مثابهٔ opaque رفتار کنید.
  • اعتبار نام رویداد در runtime از ‏hermes_cli.plugins.VALID_HOOKS می‌آید. ‏hermes hooks list هوک‌های شل/خروجی پیکربندی‌شده را فهرست می‌کند نه هر رویداد موجود را؛ ‏hermes hooks test <event> فقط وقتی رویداد نامعتبری داده شود مجموعهٔ معتبر را گزارش می‌دهد.

قرارداد عمداً باریک است:

  • IDها سراسری، پایدار، شناسه‌های ۱ تا ۱۲۸ نویسه‌ایِ حروف-کوچک با تنها حروف، اعداد، .، _ و - هستند. ID های تکراری رد می‌شوند.
  • after_memory تنها لنگر جایگذاری است. بخش‌ها بر اساس ID مرتب، بعد از زمینهٔ memory/profile و قبل از متادیتای نشست رندر می‌شوند؛ پلاگین‌ها نمی‌توانند محتوای هستهٔ پرامپت را جابه‌جا یا جایگزین کنند.
  • یک callable نگاشت فقط-خواندنی با session_id، ‏model، ‏provider، ‏platform، ‏profile_name و cwd دریافت می‌کند. برای نشست جدید فقط یک بار اجرا می‌شود. بایت‌های رندرشده‌اش هنگام فشرده‌سازی منجمد و بعد از ری‌استارت/resume ی پروسه از پرامپت سیستمی کاملِ از-قبل-ماندگار‌شده بازیابی می‌شود؛ وضعیت پلاگین برای نشست موجود دوباره خوانده نمی‌شود.
  • ‏max_chars روی ‎۴٬۰۰۰‎ نویسه سقف می‌خورد. همهٔ بخش‌های پلاگین با هم — شامل سرصفحه‌های ممیزی‌شان — روی ‎۸٬۰۰۰‎ نویسه و ۳۲ بخش سقف دارند. بخش‌های خالی، غیر-رشته‌ای، بیش‌ازحد بزرگ، فراتر-از-بودجه-تجمعی یا خطادهنده با هشدار skip و ساخت پرامپت ادامه می‌یابد.

هوک‌های خروجی استریم

این هوک‌های فقط-observer به پلاگین‌ها اجازه می‌دهد خروجی استریمی LLM را برای تلمتری، داشبوردهای زنده یا خط‌لوله‌های TTS مصرف کنند بدون تغییر دادن پاسخ. از طریق صف‌های محدود متعلق-به-میزبان با یک worker پس‌زمینه per-callback تحویل می‌یابند، پس callback های پلاگین هرگز inline روی مسیر توکن اجرا نمی‌شوند. اگر یک callback معلق شود فقط صف همان callback می‌تواند پر شده و قدیمی‌ترین رویداد observer ی در انتظارش را drop کند؛ سایر observer ها مستقل رویدادها را دریافت می‌کنند.

مثل هر هوک پلاگین دیگری ثبت‌شان کنید:

def on_delta(delta, kind, model, provider, **kwargs):
    if kind == "text":
        print(delta, end="", flush=True)

def register(ctx):
    ctx.register_hook("on_stream_delta", on_delta)

‏on_interim_message می‌تواند بعد از پاسخ غیر-استریمی هم شلیک کند، پس ثبت کردن فقط همین هوک Provider را مجبور به transport ی استریم نمی‌کند.

delta های reasoning به‌طور پیش‌فرض به پلاگین‌ها داده نمی‌شوند. صریحاً شرکت کنید:

  stream_reasoning_deltas: true

مقادیر بازگشتی نادیده گرفته می‌شوند. برای سریع ماندن stream، callback ها کارشان را در صف خودشان بگذارند و سریع برگردند. exception ها لاg و stream را متوقف نمی‌کنند.

۳ ‏pre_tool_call

بلافاصله قبل از هر اجرای ابزار شلیک می‌شود — هم ابزارهای داخلی هم پلاگینی.

امضای callback:

def my_callback(tool_name: str, args: dict, task_id: str, **kwargs):
پارامترنوعتوضیح
tool_namestrنام ابزاری که در آستانهٔ اجراست ‏(مثل terminal، web_search، read_file)
argsdictآرگومان‌هایی که مدل به ابزار پاس داده
task_idstrشناسهٔ نشست/تسک. رشتهٔ خالی اگر ست نباشد.

شلیک: در model_tools.py داخل handle_function_call() قبل از اجرای هندلر ابزار. یک بار per-call ی ابزار — اگر مدل ۳ ابزار را موازی صدا بزند این ۳ بار شلیک می‌شود.

مقدار بازگشتی — بلاک یا الزام تأیید:

return {"action": "block", "message": "Reason the tool call was blocked"}
# or
return {"action": "approve", "message": "Why approval is required", "rule_key": "optional:scope"}

اولین directive ی معتبر برنده است ‏(پلاگین‌های پایتونی اول ثبت‌شده، بعد هوک‌های شل). block یک message ی غیرخالی لازم دارد و ابزار را short-circuit می‌کند با همان متن به‌عنوان خطای برگردانده-به-مدل. approve فراخوانی را به گیت تأیید انسانی موجود ارتقا می‌دهد؛ message و rule_key اختیاری‌اند و رد شدن، timeout یا خطای گیت fail closed می‌شود. سایر مقادیر بازگشتی نادیده گرفته می‌شوند، پس callback های فعلیِ فقط-observer بدون تغییر کار می‌کنند.

مقدار بازگشتی — بازنویسی آرگومان‌های ابزار:

return {"action": "modify", "args": {"new_string": "fixed content"}}

dict ی args برگشتی قبل از اجرای ابزار روی آرگومان‌های اصلی shallow-merge می‌شود. چند هوک modify تجمعی عمل می‌کنند — کلیدهای هر هوک در یک dict ی تجمعی ساخته‌شده از args ی اصلی ادغام می‌شوند، پس هوک A که path را عوض کند و هوک B که content را عوض کند هر دو دوام می‌آورند. اگر دو هوک همان کلید را عوض کنند هوکِ بعدی برنده است.

هوک‌های شل فرمت سازگار-با-Claude-Code را هم می‌پذیرند:

{"decision": "modify", "tool_input": {"new_string": "fixed content"}}

هر دو فرمت داخلیاً به ‏{"action": "modify", "args": {...}} نرمال می‌شوند.

موارد استفاده: لاگ‌گیری، ردپای ممیزی، شمارنده‌های فراخوانی ابزار، بلاک کردن عملیات خطرناک، rate limiting، اعمال سیاست per-user، پاک‌سازی آرگومان، بازنویسی مسیر، تزریق پارامترهای پیش‌فرض.

یک بار در هر نوبت قبل از شروع حلقهٔ فراخوانی ابزار شلیک می‌شود. همهٔ بازگشت‌های معتبر callback ها به ترتیب پلاگین جمع و داخل پیام کاربر نوبت فعلی تزریق می‌شوند.

‏pre_verify

یک بار در هر نوبت وقتی ایجنت کد ویرایش کرده درست قبل از پایان ‏(بعد از گارد verify-on-stop داخلی) شلیک می‌شود. این یک گیت سیاست کاربر/پلاگین است: callback می‌تواند ایجنت را ادامه دهد — چک اجرا کند، به تعویق بیندازد، diff را مرتب کند — به‌جای گذاشتنش برای توقف.

راهنمای verification ی ارسالی هرمس یک هوک pre_verify ی پیش‌فرض نیست. وقتی کد ویرایش‌شده شواهد تازهٔ verification ندارد به nudge ی verify-on-stop مبتنی-بر-شواهد الحاق می‌شود تا مسیر ادامهٔ دوم پیش‌فرض نسازد. برای کوتاه ماندن آن nudge ی شواهد داخلی ‏agent.verify_guidance: false را ست کنید.

محدود: directive های continue ی متوالی در یک نوبت با ‏agent.max_verify_nudges سقف می‌خورند ‏(پیش‌فرض ۳)، پس هوکی که همیشه می‌گوید ادامه بده هرگز نمی‌تواند حلقه را به دام بیندازد. پاسخِ تلاش‌شده در تاریخچه نگه داشته می‌شود ولی وقتی ایجنت nudge می‌شود به کاربر surface نمی‌گردد.

idempotent کنید: هوک بعد از هر nudge دوباره شلیک می‌شود، پس روی attempt گیت بزنید ‏(if attempt: return None) — وگرنه فقط تا رسیدن به سقف nudge می‌کند.

‏transform_api_error_classification

یک بار per-call ی API ناموفق، بالای agent/error_classifier.classify_api_error() قبل از خط‌لوله داخلی شلیک می‌شود. پلاگین‌های ارائه‌دهنده از آن استفاده می‌کنند تا عجیب‌وغریبی‌های خطای ارائه‌دهنده‌شان را بدون وصله به هسته مالک شوند. تغییردهندهٔ رفتار است ‏(خانوادهٔ transform): classification ی برگشتی retry، فشرده‌سازی، چرخش credential و مسیریابی fallback را می‌رانَد.

callback ها زمینهٔ خطای parse‌شده را به‌عنوان kwargs می‌گیرند — provider ‏(self-scope روی همین)، model، status_code، error_type، error_code، error_message، error_body، error، approx_tokens، context_length، num_messages. برای انصراف None یا برای تصاحب خطا dict برگردانید:

return {"reason": "model_not_found",   # required: a FailoverReason name
        "retryable": False, "should_fallback": True}  # optional recovery-hint overrides

dispatch به سبک اجرا-ی-همه-سپس-انتخاب-اولین است: هر callback اجرا، شکست‌ها ایزوله و اولین نتیجهٔ معتبر به ترتیب ثبت برنده است ‏(نتایج معتبرِ بازنده هشدار runtime لاg می‌کنند). dict های نامعتبر و reason های ناشناخته skip می‌شوند، پس پلاگین خراب هرگز classification را نمی‌شکند.

حریم خصوصی: error_message و error_body ممکن است دادهٔ redact‌نشدهٔ ارائه‌دهنده حمل کنند. فقط پلاگین‌های پایتونی — ثبت‌های شل هنگام parse ی config با هشدار رد می‌شوند.

این هوک فقط-observer است: دسترسی raw-event یا دسترسی adapter اضافه نمی‌کند. دسترسی payload خام SDK عمداً ارسال نمی‌شود — آبجکت‌های SDK ی adapter بدون اطلاع شکل عوض می‌کنند و سطح API ی غیرقابل-تکامل می‌شدند؛ جایی که واقعاً لازم باشد قابلیت صریح خودش را می‌طلبد ‏(gateway.raw_events) با برچسب «بدون تضمین پایداری». برای اقدام روی یک پلتفرم ‏(افزودن ری‌اکشن، rename ی thread) از facade ی gate‌شده با قابلیت ‏ctx.platform_actions مستند در راهنمای پلاگین‌ها استفاده کنید — پیش‌فرض پشت قابلیت gateway.platform_actions خاموش است. PluginContext.dispatch_tool() فقط ابزارهای registered در tool registry را صدا می‌زند؛ send_message عمداً آنجا ثبت نیست ‏(transport اش برای مسیرهای تحویل صریح CLI، cron، kanban و MCP رزرو شده). قرارداد آیندهٔ تحویل-خروجی باید اول تحویل پایدار محتوا/handle ها را بین همهٔ adapter ها تضمین کند؛ این برش هوک inert ی gateway_message_delivered را پیش‌ثبت نمی‌کند.

‏transform_tool_result

بعد از برگشتن ابزار و قبل از الحاق نتیجه به گفتگو شلیک می‌شود. به پلاگین اجازه می‌دهد رشتهٔ نتیجهٔ هر ابزاری را — نه فقط خروجی ترمینال — قبل از دیدن توسط مدل بازنویسی کند.

هوک‌های observer ی درخواست API

‏pre_api_request — به‌ازای هر تلاش ارائه‌دهنده بلافاصله قبل از ارسالش شلیک می‌شود. فقط-observer است. فیلدهای قدیمی user_message، ‏conversation_history و request_messages خام و برای سازگاری عمداً پاک‌سازی‌نشده‌اند؛ مصرف‌کننده‌های جدید envelope ی پاک‌سازی‌شدهٔ request را ترجیح دهند.

‏post_api_request — بعد از نرمال‌سازی موفق پاسخ ارائه‌دهنده شلیک می‌شود. فقط-observer است. response ی پاک‌سازی‌شده را ترجیح دهید؛ assistant_message پیام خام نرمال‌شده است و usage دادهٔ حسابداری دارد.

‏api_request_error — برای تلاش ناموفق ارائه‌دهنده با زمان‌بندی status/retry، یک آبجکت error و request ی پاک‌سازی‌شده شلیک می‌شود. فقط-observer است. پیام‌های خطا همچنان ممکن است دادهٔ ارائه‌دهنده یا کاربر داشته باشند.

observer های چرخهٔ حیات کانبان

‏kanban_task_claimed — بعد از commit ی claim در پروسهٔ dispatcher، بلافاصله قبل از spawn ی worker.

‏kanban_task_completed — بعد از تکمیل و cleanup معمولاً در پروسهٔ worker. summary اش ممکن است محتوای پروژه یا کاربر داشته باشد.

‏kanban_task_blocked — بعد از گذار عادی بلاک‌شده. مسیر انتظار-وابستگی قبل از خروج تراکنش نوشتن آن را invoke می‌کند. reason اش ممکن است محتوای پروژه یا کاربر داشته باشد.

هر سه هوک کانبان فقط-observer اند و task_id، ‏profile_name، ‏board، ‏assignee و run_id حمل می‌کنند؛ completed مقدار summary و blocked مقدار reason اضافه می‌کند.

observer های worker-lifecycle، task-mutation و dispatch ی کانبان

پنج observer اضافی ‏(RFC ‎#۵۸۵۴۸‎) خانوادهٔ کانبان را گسترش می‌دهند. همه فقط-observer اند، بعد از commit شدن تراکنش مرتبط شلیک و روی has_hook short-circuit می‌کنند — بدون مشترک، رفتار dispatch تغییری نمی‌کند. هوک‌های مقید-به-تسک همان فیلدهای مشترک هوک‌های بالا را دارند.

  • ‏on_kanban_worker_spawned — بعد از برگشتن spawn_fn و ماندگار شدن PID ی worker. worker_pid ‏(ممکن است None باشد) و workspace_path اضافه می‌کند. داخل lock ی dispatch اجرا می‌شود؛ callback ها سریع باشند.
  • ‏on_kanban_worker_exited — مشتق-از-tick وقتی detect_crashed_workers تسک dead-PID را پس می‌گیرد. worker_pid، ‏exit_kind، ‏exit_code، ‏outcome و retry_status اضافه می‌کند.
  • ‏on_kanban_worker_stale_claim — وقتی claim ی منقضی-TTL پس گرفته شود؛ extension های live-PID شلیک نمی‌کنند. worker_pid، ‏heartbeat_stale و retry_status اضافه می‌کند.
  • ‏on_kanban_task_updated — بعد از نوشتن کامیت‌شدهٔ فیلد-تسک بیرون از چرخهٔ claim/complete/block ‏(assign_task، override های مدل/استدلال، editorهای داشبورد). changed_fields اضافه می‌کند — فقط نام فیلدها هرگز مقادیرشان نه.
  • ‏on_kanban_dispatch_tick — یک بار per-tick ی dispatcher، اکیداً بعد از آزاد شدن lock ی dispatch، شامل tick های idle و رقابت-دار-بر-lock. payload: ‏board، ‏profile_name، ‏dry_run، ‏outcome، ‏result.

۴ هوک‌های شل ‏(Shell Hooks)

هوک‌های اسکریپت-شل را در ‏~/.hermes/config.yaml اعلام کنید و هرمس هر بار رویداد متناظرِ هوک-پلاگینی شلیک شود آنها را به‌صورت زیرپروسه اجرا می‌کند — هم در نشست‌های CLI هم گیت‌وی. بدون نیاز به نگارش پلاگین پایتونی.

هوک شل وقتی استفاده کنید که یک اسکریپت تک‌فایلی drop-in می‌خواهید ‏(Bash، ‏Python، هر چیزی با shebang) تا:

  • فراخوانی ابزار را بلاک یا modify کند — رد کردن فرمان‌های terminal خطرناک، اعمال سیاست per-directory، الزام تأیید برای عملیات write_file / patch ی مخرب یا بازنویسی آرگومان‌ها ‏(پاک‌سازی مسیر، تزریق پیش‌فرض‌ها) قبل از اجرای ابزار.
  • بعد از فراخوانی ابزار اجرا شود — auto-format کردن فایل‌های Python/TypeScript ای که ایجنت همین الان نوشته، لاگ فراخوانی‌های API، شلیک workflow ی CI.
  • زمینه به نوبت LLM بعدی تزریق کند — prepend کردن خروجی git status، روز هفتهٔ فعلی یا سندهای بازیابی‌شده به پیام کاربر ‏(بخش pre_llm_call را ببینید).
  • رویدادهای چرخهٔ حیات را مشاهده کند — نوشتن یک خط لاگ وقتی زیرایجنتی تمام می‌شود ‏(subagent_stop) یا نشستی شروع می‌شود ‏(on_session_start).

هوک‌های شل با صدا زدن ‏agent.shell_hooks.register_from_config(cfg) هم در startup ی CLI ‏(hermes_cli/main.py) هم در startup ی گیت‌وی ‏(gateway/run.py) ثبت می‌شوند. طبیعتاً با هوک‌های پلاگین پایتونی ترکیب می‌شوند — هر دو از همان dispatcher عبور می‌کنند.

پروتکل سیمی JSON

هر بار رویداد شلیک شود هرمس برای هر هوک منطبق ‏(matcher اجازه دهد) یک زیرپروسه spawn، payload ی JSON را به stdin pipe و stdout را به‌عنوان JSON برمی‌خواند.

stdin — payload ای که اسکریپت دریافت می‌کند:

{
  "hook_event_name": "pre_tool_call",
  "tool_name":       "terminal",
  "tool_input":      {"command": "rm -rf /"},
  "session_id":      "sess_abc123",
  "cwd":             "/home/user/project",
  "extra":           {"task_id": "...", "tool_call_id": "..."}
}

‏tool_name و tool_input برای رویدادهای غیر-ابزاری ‏(pre_llm_call، ‏subagent_stop، چرخهٔ نشست) مقدار null دارند. dict ی extra همهٔ kwargs های مخصوص-رویداد را حمل می‌کند ‏(user_message، ‏conversation_history، ‏child_role، ‏duration_ms و…). مقادیر غیرقابل‌سریالایزی به‌جای حذف، رشته‌ای می‌شوند.

stdout — پاسخ اختیاری:

// Block a pre_tool_call (both shapes accepted; normalised internally):
{"decision": "block", "reason":  "Forbidden: rm -rf"}   // Claude-Code style
{"action":   "block", "message": "Forbidden: rm -rf"}   // Hermes-canonical

// Modify a pre_tool_call — rewrite tool args before dispatch:
{"action": "modify", "args": {"new_string": "fixed content"}}         // Hermes-canonical
{"decision": "modify", "tool_input": {"new_string": "fixed content"}} // Claude-Code style

// Inject context for pre_llm_call:
{"context": "Today is Friday, 2026-04-17"}

// Keep the agent going at the verify gate (pre_verify); both shapes accepted:
{"action": "continue", "message": "Run the formatter, then finish."}
{"decision": "block",  "reason":  "Run the formatter, then finish."}

// Silent no-op — any empty / non-matching output is fine:

JSON ی بدفرم، کدهای خروج غیرصفر و timeout ها هشدار لاگ می‌کنند ولی هرگز حلقهٔ ایجنت را abort نمی‌کنند.

کد خروج ۲ = بلاک ‏(سازگار با Claude Code / Cursor)

هوک pre_tool_call ای که با کد خروج ۲ خارج شود حتی وقتی stdout اش هیچ block JSON ی ندارد فراخوانی ابزار را بلاک می‌کند. پیام بلاک به ترتیب اولویت حل می‌شود:

  1. block JSON ی stdout ‏(reason / message) وقتی حاضر است؛
  2. ۴۰۰ نویسهٔ اول stderr؛
  3. پیش‌فرض عمومی «Blocked by shell hook.».

پس ساده‌ترین هوک بلاک‌کنندهٔ ممکن:

#!/usr/bin/env bash
echo "policy violation: rm -rf is not permitted" >&2
exit 2

برای رویدادهایی که directive ی بلاکشان محترم شمرده نمی‌شود ‏(همه جز pre_tool_call)، کد خروج ۲ مثل هر خروج غیرصفر دیگری رفتار می‌شود: هشداری لاg و stdout همچنان parse می‌شود.

fail-open در برابر fail-closed

به‌طور پیش‌فرض هوک‌های شل fail-open هستند: خطای spawn، ‏timeout یا stdout ی غیرقابل-parse هشداری لاگ و اقدام ادامه می‌یابد. این برای هوک‌های observability پیش‌فرض درست است — ولی برای گیت‌های امنیتی غلط. اسکنر-secrets کرش‌کرده نباید بی‌سروصدا فراخوانی ابزاری را که قرار بود بازرسی کند مجاز کند.

مقدار ‏fail_closed: true ‏(یا failClosed: true، املای Cursor/Claude Code) را روی ورودی pre_tool_call ست کنید تا معکوس شود:

yaml
hooks:
  pre_tool_call:
    - matcher: "terminal|write_file|patch"
      command: "~/.hermes/agent-hooks/secret-scan.sh"
      timeout: 10
      fail_closed: true

با fail_closed: true هر کدام از اینها حالا فراخوانی ابزار را با پیام «hook <command> failed closed: <reason>» بلاک می‌کند:

شکستFail-open ‏(پیش‌فرض)‏fail_closed: true
فرمان پیدا نشد / قابل‌اجرا نبودهشدار، ادامهبلاک
Timeoutهشدار، ادامهبلاک
stdout ی غیر-JSON ‏(مثلاً stack trace)هشدار، ادامهبلاک
خروج تمیز، JSON ی no-op ی معتبر ‏({})ادامهادامه

‏fail_closed فقط روی رویدادهای دارای-قابلیت-بلاک اعمال می‌شود ‏(امروز pre_tool_call)؛ ست کردنش روی هر رویداد دیگری هنگام parse ی config هشدار لاگ و نادیده گرفته می‌شود. hermes hooks test این معناشناسی را منعکس می‌کند — خط parsed دقیقاً شکل بلوکی را نشان می‌دهد که dispatcher دریافت می‌کرد.

۱. Auto-format فایل‌های پایتون بعد از هر نوشتن

yaml

      command: "~/.hermes/agent-hooks/auto-format.sh"
#!/usr/bin/env bash
# ~/.hermes/agent-hooks/auto-format.sh

۲. بلاک کردن فرمان‌های terminal ی مخرب

۳. تزریق git status در هر نوبت ‏(معادل UserPromptSubmit ی Claude-Code)

yaml
hooks:

#!/usr/bin/env bash
# ~/.hermes/agent-hooks/inject-cwd-context.sh

مدل رضایت

هر جفت یکتای ‏(event, command) اولین باری که هرمس می‌بیند برای تأیید از کاربر پرامپت می‌گیرد و بعد تصمیم را در ‏~/.hermes/shell-hooks-allowlist.json ماندگار می‌کند. اجراهای بعدی ‏(CLI یا گیت‌وی) پرامپت را skip می‌کنند.

سه دریچهٔ فرار پرامپت تعاملی را دور می‌زنند — هر یکی کافی است:

  1. فلگ ‏--accept-hooks روی CLI ‏(مثلاً ‏hermes --accept-hooks chat)
  2. متغیر محیطی ‏HERMES_ACCEPT_HOOKS=1
  3. ‏hooks_auto_accept: true در ‏~/.hermes/config.yaml

اجراهای non-TTY ‏(گیت‌وی، ‏cron، ‏CI) یکی از این سه را لازم دارند — وگرنه هر هوک تازه‌اضافه‌شده بی‌صدا ثبت‌نشده می‌ماند و هشدار لاg می‌کند.

ویرایش اسکریپت‌ها بی‌سروصدا مورد اعتماد است. allowlist روی رشتهٔ دقیق فرمان کلید می‌خورد نه hash ی اسکریپت، پس ویرایش اسکریپت روی دیسک رضایت را باطل نمی‌کند. ‏hermes hooks doctor انحراف mtime را پرچم می‌زند تا ویرایش‌ها را ببینید و تصمیم بگیرید دوباره approve کنید یا نه.

allowlist دستی

allowlist دستی برای استقرارهای non-TTY یا حساب-سرویس مفید است که اپراتور نمی‌تواند پرامپت اولین-مصرف را تعاملی جواب دهد. فایل allowlist ‏~/.hermes/shell-hooks-allowlist.json است و قالب مورد انتظار آرایه‌ای approvals است. هر approval مقدار event ی هوک و رشتهٔ دقیق command را ثبت می‌کند:

{
  "approvals": [
    {
      "event": "post_llm_call",
      "command": "/home/hermes/.hermes/hooks/my-hook.py"
    }
  ]
}

رشتهٔ فرمان باید دقیقاً با فرمان هوک پیکربندی‌شده بخورد. آبجکت کلیدخورده-با-مسیر با فیلد sha256 قالب مورد انتظار نیست و هوک را approve نمی‌کند. ورودی‌های دستی را با ‏hermes hooks list تأیید کنید.

امنیت

هوک‌های شل با کل اعتبارنامهٔ کاربری شما اجرا می‌شوند — همان مرز اعتماد یک ورودی cron یا alias ی شل. بلوک hooks: در config.yaml را پیکربندی ممتاز تلقی کنید:

  • فقط به اسکریپت‌هایی ارجاع دهید که خودتان نوشته‌اید یا کامل بازبینی کرده‌اید.
  • اسکریپت‌ها را داخل ‏~/.hermes/agent-hooks/ نگه دارید تا مسیرشان آسان auditable باشد.
  • بعد از pull کردن config ی مشترک، hermes hooks doctor را دوباره اجرا کنید تا هوک‌های تازه‌اضافه را قبل از ثبت شدن ببینید.
  • اگر config.yaml تان بین تیم version-control می‌شود PR هایی که بخش hooks: را عوض می‌کنند را مثل config ی CI بازبینی کنید.

ترتیب و اولویت

هم هوک‌های پلاگین پایتونی هم هوک‌های شل از dispatcher ی واحد invoke_hook() عبور می‌کنند. پلاگین‌های پایتونی اول ثبت ‏(discover_and_load()) و هوک‌های شل دوم ‏(register_from_config()) می‌شوند، پس تصمیم‌های بلاکِ pre_tool_call ی پایتون در حالت تساوی مقدم‌اند. اولین بلاکِ معتبر برنده است — aggregator به‌محض تولید {"action": "block", "message": str} توسط هر callback ای با message غیرخالی برمی‌گردد.

۵ وب‌هوک‌های خروجی

وب‌هوک‌های خروجی آینهٔ push-side ی پلتفرم وب‌هوک ورودی هستند: وب‌هوک‌های ورودی هرمس را وقتی دنیا تغییر کند بیدار می‌کنند؛ وب‌هوک‌های خروجی به دنیا می‌گویند هرمس چه کرد. فهرستی از نقاط پایانی HTTP و رویدادهای چرخهٔ حیاتی موردعلاقه‌شان را پیکربندی می‌کنید و هرمس هر بار رویداد منطبق شلیک شود payload ی JSON ی امضاشده به هر نقطهٔ پایانی POST می‌کند — بدون polling در سمت گیرنده.

کاربردهای معمول:

  • نوتیفیکیشن به سیستم CI یا داشبورد وقتی نوبت ایجنت تمام شود ‏(on_session_end)
  • ردیابی تکمیل‌های زیرایجنت در سراسر یک fleet ‏(subagent_stop)
  • تغذیهٔ فعالیت ابزار در مانیتورینگ بیرونی ‏(post_tool_call با matcher)
  • بیدار کردن نمونهٔ دیگر هرمس: URL را روی وب‌هوک ورودی آن نمونه اشاره دهید

پیکربندی

فهرست ‏hooks.outbound: را به ‏~/.hermes/config.yaml اضافه کنید:

yaml
hooks:
  outbound:
    - name: ci-notify                       # optional label for logs
      url: https://ci.example.com/hermes-events
      events: [on_session_end, subagent_stop]
      secret_env: HERMES_OUTBOUND_WEBHOOK_SECRET   # env var holding the HMAC secret
      timeout: 10                           # per-attempt seconds (1–60)

    - name: tool-monitor
      url: https://metrics.example.com/hooks/hermes
      events: [post_tool_call]
      matcher: "terminal|delegate_task"     # regex, tool-scoped events only

هر رویدادی از مجموعهٔ هوک-پلاگینی معتبر است ‏(pre_tool_call، ‏post_tool_call، ‏pre_llm_call، ‏post_llm_call، ‏on_session_start، ‏on_session_end، ‏subagent_start، ‏subagent_stop و…). ورودی‌های بدفرم هشدار می‌دهند و skip می‌شوند — وب‌هوک خراب هرگز ایجنت را کرش نمی‌کند. تغییرات روی نشست CLI بعدی / ری‌استارت گیت‌وی مؤثر می‌شوند.

Secrets: مقدار ‏secret_env ‏(نام متغیر محیطی، معمولاً ست‌شده در ‏~/.hermes/.env) را به literal ی inline ی secret ترجیح دهید تا فایل config عاری از اعتبارنامه بماند. ورودی‌های بدون secret unsigned تحویل می‌یابند ‏(توسط hermes hooks list با برچسب UNSIGNED فلگ می‌شوند).

X-Hermes-Signature-256sha256=<hex> — ‏HMAC-SHA256 ی body خام به سبک GitHub؛ فقط وقتی secret پیکربندی شده حاضر است

امضا را دقیقاً مثل وب‌هوک GitHub تأیید کنید:

import hashlib, hmac

def verify(body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)

چون delivery_id و timestamp داخل body ی امضاشده زندگی می‌کنند، گیرندهٔ verify‌شده حفاظت replay را هم مجاناً می‌گیرد:

  • Dedupe روی delivery_id ‏(یا هدر X-Hermes-Delivery ی متناظر) — id های اخیراً دیده‌شده را به یاد داشته و تکراری‌ها را skip کنید. هرمس تحویل‌های ناموفق را یک بار retry می‌کند پس رسیدن دو بارهٔ همان id مشروع است.
  • رد کردن رویدادهای کهنه با بررسی timestamp علیه ساعتتان با پنجرهٔ تحمل ‏(۵ دقیقه رایج است). مهاجمی که درخواست captured را replay می‌کند بدون secret نمی‌تواند timestamp تازه‌ای جعل کند.

معناشناسی تحویل

  • Fire-and-forget، بیرون مسیر داغ. رویدادها فوری سریالایز و صف می‌شوند؛ یک thread ی پس‌زمینه POST های HTTP را انجام می‌دهد. نقطهٔ پایانی کند یا مرده هرگز فراخوانی ابزار یا نوبت ایجنتی را معلق نمی‌کند.
  • فقط-نوتیفیکیشن. برخلاف هوک‌های شل، وب‌هوک‌های خروجی نمی‌توانند ابزار بلاک یا زمینه تزریق کنند — body ی پاسخ نادیده گرفته می‌شود. آنها مشاهده می‌کنند هرگز هدایت نمی‌کنند.
  • retry های محدود. خطاهای اتصال و پاسخ‌های ۵xx یک بار با backoff دوباره تلاش می‌شوند؛ پاسخ‌های ۴xx retry نمی‌شوند ‏(گیرنده گفت خود درخواست غلط است). شکست‌ها لاگ و drop می‌شوند — تحویل best-effort است نه تضمینی.
  • redirect ها هرگز دنبال نمی‌شوند. پاسخ 3xx پیکربندی‌غلط تلقی و لاگ می‌شود — دنبال کردن POST ی redirect‌شده payload ی امضاشده را بی‌سروصدا drop می‌کرد. url را روی نقطهٔ پایانی نهایی اشاره دهید.
  • صف محدود. اگر صف عقب بیفتد ‏(نقطهٔ پایانی مرده، طوفان رویداد)، رویدادهای جدید با هشدار drop می‌شوند نه مصرف حافظهٔ نامحدود.
  • بدون پرامپت رضایت. اهداف خروجی هیچ کدی روی ماشین شما اجرا نمی‌کنند — داده را در URL ای که شما پیکربندی کرده‌اید دریافت می‌کنند. ‏HERMES_SAFE_MODE=1 همچنان مثل پلاگین‌ها و هوک‌های شل ثبت را skip می‌کند. توجه کنید payload ها ورودی‌های ابزار و متادیتای رویداد را شامل می‌شوند، پس اهداف را فقط به نقاط پایانی مورد اعتماد اشاره دهید و https را ترجیح دهید.

‏hermes hooks list اهداف خروجی پیکربندی‌شده را کنار هوک‌های شل نشان می‌دهد شامل اینکه هر هدف امضاشده است یا نه.
