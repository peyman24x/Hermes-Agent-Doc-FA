ابزارها و تول‌ست‌ها

ابزارها توابعی هستند که توانایی‌های ایجنت را گسترش می‌دهند. آن‌ها در تول‌ست‌های منطقی سازمان یافته‌اند که می‌توان به‌ازای هر پلتفرم فعال یا غیرفعالشان کرد.

۱ ابزارهای موجود

هرمس با یک رجیستری گستردهٔ ابزار داخلی عرضه می‌شود که جستجوی وب، اتوماسیون مرورگر، اجرای ترمینال، ویرایش فایل، حافظه، واگذاری، کارهای زمان‌بندی، هوم‌اسیسنت و بیشتر را پوشش می‌دهد.

ℹ️ توجه

حافظهٔ بین-نشستی Honcho به‌صورت پلاگین ارائه‌دهندهٔ حافظه (plugins/memory/honcho/) موجود است، نه به‌عنوان تول‌ست داخلی. برای نصب به «پلاگین‌ها» مراجعه کنید.

دسته‌های کلی:

برای رجیستری معتبرِ برگرفته از کد، به «مرجع ابزارهای داخلی» و «مرجع تول‌ست‌ها» مراجعه کنید.

💡 گیت‌وی ابزار Nous

مشترکین پولی Nous Portal می‌توانند جستجوی وب، تولید تصویر، TTS و اتوماسیون مرورگر را از طریق «گیت‌وی ابزار» استفاده کنند — بدون نیاز به کلیدهای API جداگانه. برای فعال‌سازی hermes model را اجرا کنید، یا ابزارهای تکی را با hermes tools پیکربندی کنید.

۲ استفاده از تول‌ست‌ها

bash
# استفاده از تول‌ست‌های مشخص
hermes chat --toolsets "web,terminal"

# دیدن همهٔ ابزارهای موجود
hermes tools

# پیکربندی ابزارها به‌ازای پلتفرم (تعاملی)
hermes tools

تول‌ست‌های رایج شامل web، search، terminal، file، browser، vision، image_gen، skills، tts، todo، memory، session_search، cronjob، code_execution، delegation، clarify، homeassistant، messaging، spotify، discord، discord_admin، debugging و safe هستند.

برای مجموعهٔ کامل، از جمله پیش‌تنظیم‌های پلتفرمی مانند hermes-cli و hermes-telegram و تول‌ست‌های داینامیک MCP مانند mcp-<server>، به «مرجع تول‌ست‌ها» مراجعه کنید.

۳ حاشیه‌نویسی نتایج ابزار

چند رفتار ابزار که هنگام خواندن رونوشت‌های ایجنت ارزش دانستن دارند:

  • مرگ با سیگنال توضیح داده می‌شود. وقتی یک دستور ترمینالی توسط سیگنال کشته می‌شود، نتیجه به‌جای کد عددیِ خالی یک یادداشت انسانی‌خوان حمل می‌کند — مثلاً خروج -9/137 می‌شود «terminated by signal 9: SIGKILL — often the kernel OOM killer on memory exhaustion, or an explicit kill -9» و segfault، abort، SIGTERM، pipe شکسته و محدودیت‌های CPU/حجم-فایل هم به همین شکل برچسب می‌خورند. کدهای منفی (معناشناسی زیرپروسه) قطعی بیان می‌شوند؛ قرارداد 128+signum شل با «usually» احتیاط‌آمیز ذکر می‌شود چون یک اپلیکیشن می‌تواند به‌طور مشروع با آن کدها خارج شود.
  • فایل‌های متنی UTF-16 تبدیل می‌شوند، نه رد. read_file فایل UTF-16 را تشخیص می‌دهد (BOM یا حدس الگوی بایتی، در هر دو endian — رایج برای فایل‌های نت‌پد ویندوز و خروجی‌های > پاورشل) و برای نمایش به UTF-8 تبدیل‌اش می‌کند به‌جای اینکه فایل را باینری علامت بزند. نتیجه نکته‌ای افشای تبدیل را هم دارد؛ ویرایش‌ها با patch/write_file به‌صورت UTF-8 بازکدگذاری می‌شوند. فایل‌های بالای ۱۰ مگابایت و فایل‌های واقعاً باینری همچنان ردِ فایل-باینری می‌گیرند.

پیکربندی

yaml — در ~/.hermes/config.yaml
terminal:
  backend: local    # یا: docker, ssh, singularity, modal, daytona, vercel_sandbox
  cwd: "."          # پوشهٔ کاری
  timeout: 180      # مهلت دستور بر حسب ثانیه

فایل‌های راه‌اندازی شل و دستورات غیرتعاملی

فراخوانی‌های ترمینال ایجنت، شل شما را غیرتعاملی اجرا می‌کنند — نه TTY هست و نه انسانی سر پرامپت. مقداردهی اولیهٔ شلِ سنگین یا تعاملی که در ترمینال عادی هرگز متوجهش نمی‌شوید می‌تواند هر دستوری که ایجنت اجرا می‌کند را بشکند یا به‌شدت کُند کند:

  • مقداردهی کُند (nvm، مدیرهای نسخه، پرامپت‌های دست‌کار-شبکه): سورس‌کردن کلاسیک nvm.sh به هر شروعِ شل تأخیر محسوسی اضافه می‌کند و ایجنت شل‌های زیادی شروع می‌کند. rc‌فایل‌های چندثانیه‌ای یک git status سریع را به ریسک تایم‌اوت تبدیل می‌کنند.
  • بلوک‌های منتظر-TTY: هر چیزی در .bashrc/.zshrc که پرامپت بدهد، tmux/screen attach کند، read بزند یا منو چاپ کند یک شل غیرتعاملی را معلق می‌کند — دستور ظاهراً تا ابد اجرا می‌شود و بعد تایم‌اوت.
  • خروجی بدون قید و شرط: rc‌فایل‌هایی که بنر echo می‌کنند، خروجی هر دستور را که ایجنت باید تجزیه کند آلوده می‌کنند.

راه‌حل، همان گارد استانداردی است که اغلب توزیع‌ها از قبل بالای .bashrc می‌فرستند — وقتی شل غیرتعاملی است زود return کنید و هر چیز سنگین یا تعاملی را زیر آن نگه دارید:

bash — ~/.bashrc
# این گارد را نزدیک بالای فایل نگه دارید
case $- in
  *i*) ;;      # تعاملی: ادامه بده
  *) return;;  # غیرتعاملی: همین‌جا توقف کن
esac

# مقداردهی سنگین/تعاملی زیرِ گارد می‌رود
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"

کاربران Zsh: راه‌اندازیِ مخصوص-لاگین را در .zprofile و مخصوص-تعامل را در .zshrc بگذارید؛ .zshenv را مینیمال نگه دارید چون برای همهٔ شل‌ها از جمله غیرتعاملی‌ها اجرا می‌شود. اگر ایجنت واقعاً به ابزاری نیاز دارد که فقط rc‌فایل شما روی PATH می‌گذارد، تغییر PATH را بالای گارد export کنید (خروجیِ PATH ارزان است) یا باینری را در ~/.local/bin سیم‌لینک کنید.

اگر دستورات ترمینال ایجنت بلافاصله بعد از کارکردنِ درست در ترمینال خودتان هنگ یا تایم‌اوت می‌کنند، اولین مظنون مقداردهی اولیهٔ شل شماست.

بک‌اند داکر

yaml
terminal:
  backend: docker
  docker_image: python:3.11-slim

یک کانتینر ماندگار، مشترک در کل پروسه. هرمس در اولین استفاده یک کانتینر طولانی‌عمرِ واحد شروع می‌کند (docker run -d ... sleep infinity) و هر فراخوانی ترمینال، فایل و execute_code را از طریق docker exec به همان کانتینر هدایت می‌کند. تغییرهای پوشهٔ کاری، پکیج‌های نصب‌شده، تنظیمات محیط و فایل‌های نوشته‌شده در /workspace همه از یک فراخوانی ابزار تا بعدی، در سراسر /new، /reset و ساب‌ایجنت‌های delegate_task و برای تمام طول عمر پروسهٔ هرمس باقی می‌مانند. کانتینر هنگام خاموشی متوقف و حذف می‌شود.

یعنی بک‌اند داکر مثل یک VM سندباکسِ ماندگار رفتار می‌کند، نه یک کانتینر تازه به‌ازای هر دستور. اگر یک بار pip install foo بزنید، برای باقی نشست همان‌جا هست. اگر cd /workspace/project کنید، فراخوانی‌های ls بعدی همان پوشه را می‌بینند. برای جزئیات کامل چرخهٔ حیات و پرچم container_persistent که کنترل می‌کند /workspace و /root از ری‌استارت‌های هرمس جان سالم به در ببرند، به «پیکربندی ← بک‌اند داکر» مراجعه کنید.

بک‌اند SSH

برای امنیت توصیه می‌شود — ایجنت نمی‌تواند کد خودش را ویرایش کند:

yaml
terminal:
  backend: ssh

TERMINAL_SSH_HOST=my-server.example.com
TERMINAL_SSH_USER=myuser
TERMINAL_SSH_KEY=~/.ssh/id_rsa

Singularity/Apptainer

bash
# پیش‌ساخت SIF برای کارگرهای موازی
apptainer build ~/python.sif docker://python:3.11-slim

# پیکربندی
hermes config set terminal.backend singularity
hermes config set terminal.singularity_image ~/python.sif

Modal (ابر سرورلس)

bash
uv pip install modal
modal setup
hermes config set terminal.backend modal

Vercel Sandbox

bash
pip install 'hermes-agent[vercel]'
hermes config set terminal.backend vercel_sandbox
hermes config set terminal.vercel_runtime node24

با هر سهٔ VERCEL_TOKEN، VERCEL_PROJECT_ID و VERCEL_TEAM_ID احراز هویت کنید. این راه‌اندازیِ مبتنی بر access-token مسیر پشتیبانی‌شده برای استقرارها و پروسه‌های بلندمدتِ معمول هرمس روی Render، Railway، داکر و میزبان‌های مشابه است. Runtimeهای پشتیبانی‌شده node24، node22 و python3.13 هستند؛ هرمس به‌طور پیش‌فرض /vercel/sandbox را به‌عنوان ریشهٔ ورک‌اسپیس راهن انتخاب می‌کند.

برای توسعهٔ محلیِ موردی، هرمس توکن‌های کوتاه‌عمر OIDC ورسل را هم می‌پذیرد:

bash
VERCEL_OIDC_TOKEN="$(vc project token <project-name>)" hermes chat

از داخل پوشهٔ پروژهٔ ورسلِ لینک‌شده:

bash
VERCEL_OIDC_TOKEN="$(vc project token)" hermes chat

با container_persistent: true، هرمس از اسنپ‌شات‌های ورسل برای حفظ وضعیت فایل‌سیستم در بازسازی‌های سندباکس برای همان کار استفاده می‌کند. این می‌تواند شامل اعتبارنامه‌ها، مهارت‌ها و فایل‌های کشِ همگام‌شدهٔ هرمس داخل سندباکس باشد. اسنپ‌شات‌ها پروسه‌های زنده، فضای PID یا همان هویتِ زندهٔ سندباکس را حفظ نمی‌کنند.

دستورات ترمینال پس‌زمینه از جریان عمومیِ پروسهٔ غیر-محلیِ هرمس استفاده می‌کنند: تولید، poll، انتظار، لاگ و kill هنگام زنده‌بودن سندباکس از طریق ابزار process معمول کار می‌کنند، اما هرمس بازیابی بومیِ پروسهٔ جداشدهٔ ورسل پس از پاکسازی یا ری‌استارت ارائه نمی‌دهد.

container_disk را تنظیم‌نشده بگذارید یا روی پیش‌فرض مشترک 51200؛ اندازه‌دهی دیسک سفارشی برای Vercel Sandbox پشتیبانی نمی‌شود و تشخیص‌ها/ساخت بک‌اند را شکست می‌دهد.

منابع کانتینر

CPU، حافظه، دیسک و ماندگاری را برای همهٔ بک‌اندهای کانتینری پیکربندی کنید:

yaml
terminal:
  backend: docker  # یا singularity, modal, daytona, vercel_sandbox
  container_cpu: 1              # هسته‌های CPU (پیش‌فرض: 1)
  container_memory: 5120        # حافظه به MB (پیش‌فرض: ۵GB)
  container_disk: 51200         # دیسک به MB (پیش‌فرض: ۵۰GB)
  container_persistent: true    # ماندگاری فایل‌سیستم بین نشست‌ها (پیش‌فرض: true)

وقتی container_persistent: true باشد، پکیج‌ها، فایل‌ها و پیکربندیِ نصب‌شده در سراسر نشست‌ها باقی می‌مانند.

امنیت کانتینر

همهٔ بک‌اندهای کانتینری با سخت‌سازی امنیتی اجرا می‌شوند:

  • فایل‌سیستم ریشهٔ فقط‌خواندنی (داکر)
  • حذف همهٔ قابلیت‌های (capabilities) لینوکس
  • بدون ارتقای امتیاز
  • محدودیت PID (۲۵۶ پروسه)
  • ایزوله‌سازی کامل فضای نام (namespace)
  • ورک‌اسپیس ماندگار از طریق والوم‌ها، نه لایهٔ ریشهٔ قابل‌نوشتن

داکر می‌تواند به‌صورت اختیاری یک فهرست مجاز محیطیِ صریح از طریق terminal.docker_forward_env بگیرد، اما متغیرهای فورواردشده برای دستورات داخل کانتینر قابل‌مشاهده‌اند و باید برای آن نشست در معرض بدانند.

۵ مدیریت پروسه‌های پس‌زمینه

پروسه‌های پس‌زمینه را شروع کنید و مدیریتشان کنید:

python
terminal(command="pytest -v tests/", background=true)
# خروجی: {"session_id": "proc_abc123", "pid": 12345}

# سپس با ابزار process مدیریت کنید:
process(action="list")       # نمایش همهٔ پروسه‌های در حال اجرا
process(action="poll", session_id="proc_abc123")   # بررسی وضعیت
process(action="wait", session_id="proc_abc123")   # بلاک تا اتمام
process(action="log", session_id="proc_abc123")    # خروجی کامل
process(action="kill", session_id="proc_abc123")   # خاتمه
process(action="write", session_id="proc_abc123", data="y")  # ارسال ورودی

حالت PTY‏ (pty=true) ابزارهای CLI تعاملی مثل Codex و Claude Code را ممکن می‌کند.

۶ پشتیبانی sudo

اگر دستوری به sudo نیاز داشته باشد، از شما رمز پرسیده می‌شود (برای نشست کش می‌شود). یا SUDO_PASSWORD را در ~/.hermes/.env تنظیم کنید.

⚠️ هشدار

در پلتفرم‌های پیام‌رسانی، اگر sudo شکست بخورد، خروجی نکته‌ای برای افزودن SUDO_PASSWORD به ~/.hermes/.env دارد.
