فایل‌های زمینه

‏هرمس ایجنت خودکار فایل‌های زمینه‌ای را که رفتارش را شکل می‌دهند کشف و لود می‌کند. بعضی محلی-پروژه‌اند و از پوشهٔ کاری شما کشف می‌شوند. ‏SOUL.md الان سراسری برای نمونهٔ هرمس است و فقط از ‏HERMES_HOME لود می‌شود.

📌 سیستم اولویت

در هر نشست فقط یک نوع زمینهٔ پروژه لود می‌شود ‏(اولین تطبیق برنده است): ‏.hermes.md ← ‏AGENTS.override.md ← ‏AGENTS.md ← ‏CLAUDE.md ← ‏.cursorrules. ‏SOUL.md همیشه مستقل به‌عنوان هویت ایجنت لود می‌شود ‏(اسلات #۱).

اگر ‏AGENTS.override.md کنار ‏AGENTS.md وجود داشته باشد override به‌جای فایل کامیت‌شده لود می‌شود — وقتی دستورالعمل متفاوتی از چیزی که داخل repo است می‌خواهید بدون ویرایش ‏AGENTS.md ردیابی‌شده، یک ‏AGENTS.override.md شخصی ‏(معمولاً gitignored) نگه دارید.

۲ AGENTS.md

‏AGENTS.md فایل اصلی زمینهٔ پروژه است. به ایجنت می‌گوید پروژه‌تان چگونه ساختار دارد، چه قواعدی را دنبال کند و هر دستورالعمل ویژه‌ای.

زنجیرهٔ پوشه‌ها ‏(ریشهٔ گیت ← پوشهٔ کاری)

وقتی پوشهٔ کاری‌تان داخل یک مخزن گیت است هرمس هنگام شروع نشست یک زنجیرهٔ ادغام‌شده از فایل‌های ‏AGENTS.md لود می‌کند: اول ‏AGENTS.md ریشهٔ گیت، بعد ‏AGENTS.md هر پوشهٔ واسطه تا پوشهٔ کاری شما. فایل‌های عمیق‌تر بعدتر در پرامپت می‌آیند تا راهنمای خاص‌تر مقدم شود. هر فایل سربرگ provenance خودش را می‌گیرد ‏(مثل ‏## ../../AGENTS.md) و کپی‌های یکسان در طول زنجیره dedupe می‌شوند.

monorepo/                   (git root, cwd = packages/webapp/)
├── AGENTS.md              ← Loaded first (repo-wide conventions)
└── packages/
    ├── AGENTS.md          ← Loaded second
    └── webapp/
        └── AGENTS.md      ← Loaded last (most specific, takes precedence)

بیرون مخزن گیت فقط خودِ پوشهٔ کاری چک می‌شود — هرگز به والدین سرک نمی‌شود، پس ‏AGENTS.md کاشته‌شده در ‎/tmp یا ‏$HOME نمی‌تواند به نشست‌های نامرتبط نشت کند.

کشف تدریجی زیرپوشه‌ای

هنگام شروع نشست هرمس ‏AGENTS.md پوشهٔ کاری شما را داخل پرامپت سیستمی لود می‌کند. وقتی ایجنت حین نشست به زیرپوشه‌ها حرکت می‌کند ‏(از طریق ‏read_file، ‏terminal، ‏search_files و...)، آن فایل‌های زمینه را به‌صورت تدریجی کشف و در لحظهٔ مرتبط شدنشان داخل گفتگو تزریق می‌کند.

my-project/
├── AGENTS.md              ← Loaded at startup (system prompt)
├── frontend/
│   └── AGENTS.md          ← Discovered when agent reads frontend/ files
├── backend/
│   └── AGENTS.md          ← Discovered when agent reads backend/ files
└── shared/
    └── AGENTS.md          ← Discovered when agent reads shared/ files

این رویکرد دو مزیت نسبت به لود کردن همه‌چیز هنگام شروع دارد:

  • بدون بادکردن پرامپت سیستمی — سرنخ‌های زیرپوشه فقط وقتی لازم‌اند ظاهر می‌شوند
  • حفظ کش پرامپت — پرامپت سیستمی بین نوبت‌ها پایدار می‌ماند

هر زیرپوشه حداکثر یک‌بار به‌ازای هر نشست چک می‌شود. کشف به پوشه‌های والد هم صعود می‌کند، پس خواندن ‏backend/src/main.py حتی اگر ‏backend/src/ فایل زمینه خودش را نداشته باشد ‏backend/AGENTS.md را کشف می‌کند.

📌 نکته

فایل‌های زمینهٔ زیرپوشه‌ای از همان اسکن امنیتی فایل‌های شروع عبور می‌کنند. فایل‌های مخرب بلاک می‌شوند.

مثال AGENTS.md

markdown
# Project Context

This is a Next.js 14 web application with a Python FastAPI backend.

## Architecture
- Frontend: Next.js 14 with App Router in `/frontend`
- Backend: FastAPI in `/backend`, uses SQLAlchemy ORM
- Database: PostgreSQL 16
- Deployment: Docker Compose on a Hetzner VPS

## Conventions
- Use TypeScript strict mode for all frontend code
- Python code follows PEP 8, use type hints everywhere
- All API endpoints return JSON with `{data, error, meta}` shape
- Tests go in `__tests__/` directories (frontend) or `tests/` (backend)

## Important Notes
- Never modify migration files directly — use Alembic commands
- The `.env.local` file has real API keys, don't commit it
- Frontend port is 3000, backend is 8000, DB is 5432

۳ SOUL.md

‏SOUL.md شخصیت، لحن و سبک ارتباط ایجنت را کنترل می‌کند. جزئیات کامل در صفحهٔ شخصیت.

محل:

  • ‏~/.hermes/SOUL.md
  • یا ‏$HERMES_HOME/SOUL.md اگر هرمس را با دایرکتوری خانه سفارشی اجرا کنید

جزئیات مهم:

  • هرمس اگر هنوز ‏SOUL.md وجود نداشته باشد خودکار یک پیش‌فرض seed می‌کند
  • هرمس ‏SOUL.md را فقط از ‏HERMES_HOME لود می‌کند
  • هرمس برای ‏SOUL.md در پوشهٔ کاری جست‌وجو نمی‌کند
  • اگر فایل خالی باشد هیچ چیزی از SOUL.md به پرامپت اضافه نمی‌شود
  • اگر فایل محتوا داشته باشد، محتوا بعد از اسکن و برش تحت‌اللفظی تزریق می‌شود

۴ .cursorrules

هرمس با فایل ‏.cursorrules و ماژول‌های قاعدهٔ ‏.cursor/rules/*.mdc مربوط به Cursor IDE سازگار است. اگر این فایل‌ها در ریشهٔ پروژه‌تان باشند و هیچ فایل زمینهٔ بالاتر-اولویتی ‏(.hermes.md، ‏AGENTS.md یا ‏CLAUDE.md) پیدا نشود، به‌عنوان زمینهٔ پروژه لود می‌شوند.

یعنی قواعد Cursor موجودتان هنگام استفاده از هرمس خودکار اعمال می‌شود.

۵ نحوهٔ لود فایل‌های زمینه

هنگام شروع ‏(پرامپت سیستمی)

فایل‌های زمینه توسط ‏build_context_files_prompt() در ‏agent/prompt_builder.py لود می‌شوند:

  1. اسکن پوشهٔ کاری — چک ‏.hermes.md ← ‏AGENTS.md ← ‏CLAUDE.md ← ‏.cursorrules ‏(اولین تطبیق برنده)
  2. خواندن محتوا — هر فایل به‌عنوان متن UTF-8 خوانده می‌شود
  3. اسکن امنیتی — محتوا برای الگوهای prompt injection چک می‌شود
  4. برش — فایل‌های فراتر از سقف کاراکتری head/tail بریده می‌شوند ‏(۷۰٪ سر، ‏۲۰٪ دُم، با نشانگری وسط). سقف مقدار صریح ‏context_file_max_chars از config.yaml است وقتی ست باشد؛ وگرنه دینامیک با پنجرهٔ زمینه مدل مقیاس می‌یابد ‏(کف ۲۰٬۰۰۰ کاراکتر، سقف ۵۰۰٬۰۰۰)
  5. اسمبل — همهٔ بخش‌ها زیر سربرگ ‏# Project Context ترکیب می‌شوند
  6. تزریق — محتوای اسمبل‌شده به پرامپت سیستمی افزوده می‌شود

حین نشست ‏(کشف تدریجی)

‏SubdirectoryHintTracker در ‏agent/subdirectory_hints.py آرگومان‌های فراخوانی ابزار را برای مسیرهای فایل زیر نظر دارد:

  1. استخراج مسیر — بعد از هر فراخوانی ابزار مسیرهای فایل از آرگومان‌ها ‏(path، ‏workdir، فرمان‌های شل) استخراج می‌شود
  2. صعود اجداد — پوشه و تا ۵ والد بررسی می‌شوند ‏(توقف روی پوشه‌های قبلاً بازدید‌شده)
  3. لود سرنخ — اگر ‏AGENTS.md، ‏CLAUDE.md یا ‏.cursorrules پیدا شود لود می‌شود ‏(اولین تطبیق به‌ازای هر پوشه)
  4. اسکن امنیتی — همان اسکن prompt injection فایل‌های شروع
  5. برش — سقف ۸٬۰۰۰ کاراکتر به‌ازای هر فایل
  6. تزریق — به نتیجهٔ ابزار الصاق می‌شود تا مدل طبیعی در زمینه ببیندش

بخش نهایی پرامپت تقریباً این شکل را دارد:

# Project Context

The following project context files have been loaded and should be followed:

## AGENTS.md

[Your AGENTS.md content here]

## .cursorrules

[Your .cursorrules content here]

[Your SOUL.md content here]

توجه کنید محتوای SOUL مستقیم تزریق می‌شود بدون متن wrapper اضافه.

۶ امنیت: محافظت prompt injection

همهٔ فایل‌های زمینه قبل از گنجانده شدن برای prompt injection احتمالی اسکن می‌شوند. اسکنر این‌ها را چک می‌کند:

  • تلاش‌های override دستورالعمل: «ignore previous instructions»، «disregard your rules»
  • الگوهای فریب: «do not tell the user»
  • override پرامپت سیستمی: «system prompt override»
  • کامنت‌های HTML مخفی: ‏<!-- ignore instructions -->
  • عناصر div مخفی: ‏<div style="display:none">
  • خروج برداشتگاه اعتبارنامه: ‏curl ... $API_KEY
  • دسترسی فایل رمز: ‏cat .env، ‏cat credentials
  • کاراکترهای نامرئی: فاصله‌های zero-width، overrides دوجهته، word joiner ها

اگر هر الگوی تهدیدی تشخیص داده شود فایل بلاک می‌شود:

[BLOCKED: AGENTS.md contained potential prompt injection (prompt_injection). Content not loaded.]
⚠️ هشدار

این اسکنر در برابر الگوهای رایج تزریق محافظت می‌کند ولی جایگزین بازبینی فایل‌های زمینه در مخازن مشترک نیست. همیشه محتوای AGENTS.md را در پروژه‌هایی که خودتان ننوشته‌اید اعتبارسنجی کنید.

۸ نکاتی برای فایل‌های زمینهٔ مؤثر

💡 بهترین شیوه‌ها برای AGENTS.md
  1. مختصر نگه دارید — زیر ‏context_file_max_chars پیکربندی‌شده بمانید؛ ایجنت هر نوبت می‌خواندش
  2. با تیتر ساختار دهید — از بخش‌های ‏## برای معماری، قواعد و یادداشت‌های مهم
  3. مثال‌های عینی بیاورید — الگوهای کد ترجیحی، شکل API، قواعد نام‌گذاری را نشان دهید
  4. بگویید چه نباید کرد — «هرگز فایل‌های migration را مستقیم تغییر نده»
  5. مسیرها و پورت‌های کلیدی را فهرست کنید — ایجنت برای فرمان‌های ترمینال استفاده‌شان می‌کند
  6. همراه تحول پروژه به‌روز کنید — زمینه کهنه بدتر از نبود زمینه است

زمینه به‌ازای-زیرپوشه

برای monorepo ها دستورالعمل خاص-زیرپوشه را در فایل‌های AGENTS.md تو در تو بگذارید:

markdown — frontend/AGENTS.md
<!-- frontend/AGENTS.md -->
# Frontend Context

- Use `pnpm` not `npm` for package management
- Components go in `src/components/`, pages in `src/app/`
- Use Tailwind CSS, never inline styles
- Run tests with `pnpm test`
markdown — backend/AGENTS.md
<!-- backend/AGENTS.md -->
# Backend Context

- Use `poetry` for dependency management
- Run the dev server with `poetry run uvicorn main:app --reload`
- All endpoints need OpenAPI docstrings
- Database models are in `models/`, schemas in `schemas/`
