گسترش داشبورد وب ‏(Extending the Dashboard)

داشبورد وب هرمس ‏(hermes dashboard) برای ریسکین و گسترش بدون fork کردن کدبیس ساخته شده. سه لایه expose شده است:

  1. تم‌ها — فایل‌های YAML که پالت، تایپوگرافی، چیدمان و chrome ی هر-کامپوننت داشبورد را رنگ می‌کنند. یک فایل در ‏~/.hermes/dashboard-themes/ بگذارید؛ در انتخاب‌گر تم ظاهر می‌شود.
  2. پلاگین‌های UI — یک دایرکتوری شامل ‏manifest.json + بستهٔ JavaScript که یک تب ثبت می‌کند، صفحهٔ داخلی را جایگزین، از طریق slot های مخصوص-صفحه غنی می‌کند یا کامپوننت‌هایی به shell slot های نام‌دار تزریق می‌کند.
  3. پلاگین‌های بک‌اند — یک فایل پایتون داخل همان دایرکتوری پلاگین که یک ‏router ی FastAPI expose می‌کند؛ مسیرها زیر ‏/api/plugins/<name>/ سوار و از UI پلاگین صدا زده می‌شوند.

هر سه drop-in در runtime هستند: بدون clone مخزن، بدون ‏npm run build، بدون وصله زدن به سورس داشبورد. این صفحه مرجع رسمی هر سه است.

اگر فقط می‌خواهید از داشبورد استفاده کنید بخش داشبورد وب را ببینید. اگر می‌خواهید CLI ترمینال را ریسکین کنید ‏(نه داشبورد وب)، بخش پوسته‌ها و تم‌ها را ببینید — سیستم پوستهٔ CLI ربطی به تم‌های داشبورد ندارد.

📌 این صفحه اپ دسکتاپ نیست

این صفحه سیستم پلاگینِ داشبورد وب ‏(hermes dashboard) را پوشش می‌دهد — ‏window.__HERMES_PLUGIN_SDK__، یک ‏manifest.json و یک باندل JS از پیش ساخته‌شده. اپ دسکتاپ native ‏(hermes desktop) SDK ی جدا و بی‌ربط خودش را دارد — ‏@hermes/plugin-sdk، یک فایل ESM واحد بدون مرحله build — که در بخش Desktop Plugin SDK مستند شده. فقط namespace ی بک‌اندِ ‏plugin_api.py ‏(/api/plugins/<name>) بین آنها مشترک است.

📌 قطعه‌ها چطور کنار هم می‌نشینند

تم‌ها و پلاگین‌ها مستقل اما هم‌افزا هستند. یک تم می‌تواند تنها باشد ‏(فقط یک فایل YAML). یک پلاگین می‌تواند تنها باشد ‏(فقط یک تب). با هم اجازه می‌دهند یک ریسکین کامل بصری با HUD های سفارشی بسازید — دموی نمونهٔ ‏strike-freedom-cockpit ‏(در مخزن همراه hermes-example-plugins — برای مراحل نصب بخش دموی ترکیبی تم + پلاگین) دقیقاً همین کار را می‌کند.

۱ تم‌ها

تم‌ها فایل‌های YAML ذخیره‌شده در ‏~/.hermes/dashboard-themes/ هستند. نام فایل مهم نیست ‏(فیلد ‏name: ی تم همان چیزی است که سیستم استفاده می‌کند) ولی قرارداد ‏<name>.yaml است. هر فیلدی اختیاری است — کلیدهای غایب به تم داخلی default برمی‌گردند، پس یک تم می‌تواند به کوچکی یک رنگ باشد.

شروع سریع — اولین تم شما

mkdir -p ~/.hermes/dashboard-themes
yaml
# ~/.hermes/dashboard-themes/neon.yaml
name: neon
label: Neon
description: Pure magenta on black

palette:
  background: "#000000"
  midground: "#ff00ff"

داشبورد را refresh کنید. روی آیکن پالت در header کلیک و Neon را بردارید. پس‌زمینه سیاه، متن و اکسنت‌ها مجنتا می‌شوند و هر رنگ مشتق‌شده ‏(card، ‏border، ‏muted، ‏ring و…) از آن دو-تایی رنگ از طریق ‏color-mix() در CSS محاسبه دوباره می‌شود.

کل onboarding همین بود: یک فایل، دو رنگ. هرچه پایین‌تر می‌آید اصلاح اختیاری است.

پالت، تایپوگرافی، چیدمان

این سه بلوک قلب یک تم‌اند. هرکدام مستقل‌اند — یکی را override کنید، بقیه را ول کنید.

پالت ‏(۳ لایه)

پالت سه‌تاییِ لایه‌های رنگ به‌علاوهٔ یک رنگ vignette ی warm-glow و ضریب نویز دانه است. آبشار سیستم طراحی داشبورد هر توکن سازگار-با-shadcn ‏(card، ‏popover، ‏muted، ‏border، ‏primary، ‏destructive، ‏ring و…) را از این سه‌تایی از طریق ‏color-mix() ی CSS مشتق می‌کند. override کردن سه رنگ به کل UI آبشار می‌شود.

کلیدتوضیح
palette.backgroundعمیق‌ترین رنگ بوم — معمولاً نزدیک سیاه. پس‌زمینهٔ صفحه و fill ی card ها را می‌راند.
palette.midgroundمتن اصلی و اکسنت. بیشتر chrome های UI این را می‌خوانند ‏(متن foreground، outline دکمه‌ها، حلقه‌های فوکوس).
palette.foregroundهایلایت لایهٔ بالا. تم پیش‌فرض این را سفید با alpha صفر ‏(نامرئی) ست می‌کند؛ تم‌هایی که اکسنت روشنی روی همه‌چیز می‌خواهند alpha اش را بالا ببرند.
palette.warmGlowرشتهٔ ‏rgba(...) که به‌عنوان رنگ vignette توسط ‏<Backdrop /> استفاده می‌شود.
palette.noiseOpacityضریب ۰–۱٫۲ روی overlay ی دانه. کمتر = نرم‌تر، بیشتر = زمخت‌تر.

هر لایه یا ‏{hex: "#RRGGBB", alpha: 0.0–1.0} می‌پذیرد یا یک رشتهٔ hex ی لخت ‏(alpha پیش‌فرض ۱٫۰).

yaml
palette:
  background:
    hex: "#05091a"
    alpha: 1.0
  midground: "#d8f0ff"          # bare hex, alpha = 1.0
  foreground:
    hex: "#ffffff"
    alpha: 0                    # invisible top layer
  warmGlow: "rgba(255, 199, 55, 0.24)"
  noiseOpacity: 0.7

تایپوگرافی

کلیدنوعتوضیح
fontSansstringپشتهٔ font-family ی CSS برای متن بدنه ‏(اعمال روی html و body).
fontMonostringپشتهٔ CSS برای بلوک‌های کد، ‏<code> و utility های ‏.font-mono.
fontDisplaystringپشتهٔ اختیاری عنوان/display. به ‏fontSans برمی‌گردد.
fontUrlstringURL ی stylesheet خارجی اختیاری. موقع تعویض تم به‌صورت ‏<link rel="stylesheet"> در head تزریق می‌شود. همان URL هرگز دوبار تزریق نمی‌شود. با Google Fonts، ‏Bunny Fonts و برگه‌های self-hosted ‏@font-face کار می‌کند — هر چیزی linkable.
baseSizestringاندازهٔ فونت ریشه — مقیاس rem را کنترل می‌کند. مثلاً ‏"14px"، ‏"16px".
lineHeightstringline-height پیش‌فرض. مثلاً ‏"1.5"، ‏"1.65".
letterSpacingstringletter-spacing پیش‌فرض. مثلاً ‏"0"، ‏"0.01em"، ‏"-0.01em".
yaml
typography:
  fontSans: '"Orbitron", "Eurostile", "Impact", sans-serif'
  fontMono: '"Share Tech Mono", ui-monospace, monospace'
  fontDisplay: '"Orbitron", "Eurostile", sans-serif'
  fontUrl: "https://fonts.googleapis.com/css2?family=Orbitron:wght@400;500;600;700&family=Share+Tech+Mono&display=swap"
  baseSize: "14px"
  lineHeight: "1.5"
  letterSpacing: "0.04em"
تعویض فونت از UI ‏(بدون YAML)

انتخاب‌گر تم در header ی داشبورد زیر فهرست تم‌ها یک بخش Font دارد. هر فونتی آنجا بردارید فونت بدنه‌ی هر تم فعالی را override می‌کند — انتخاب مستقل از تم است و بین تعویض‌های تم می‌ماند ‏(در config.yaml زیر ‏dashboard.font ذخیره می‌شود). برای پاک کردن override و برگشت به ‏fontSans ی خود تم فعال، Theme default را انتخاب کنید.

انتخاب‌گر یک کاتالوگ منتخب ارائه می‌دهد ‏(پشته‌های سیستمی به‌علاوهٔ مجموعه‌ای از خانواده‌های Google-Fonts در سه سبک sans / serif / mono). عمداً URL فونت آزاد نمی‌پذیرد — stylesheet فونت به‌صورت ‏ تزریق می‌شود، پس کاتالوگ origin های تزریق را ثابت نگه می‌دارد. برای فونت کاملاً سفارشی مثل بالا در تم YAML مقدار ‏fontSans + ‏fontUrl را ست کنید. فونت ‏fontMono ی تم ‏(بلوک‌های کد، ترمینال) همیشه دست‌نخورده از override ی UI می‌ماند.

چیدمان

کلیدمقادیرتوضیح
radiusهر طول CSS ‏("0"، ‏"0.25rem"، ‏"0.5rem"، ‏"1rem" و…)توکن گردی گوشه‌ها. به ‏--radius نگاشت و به ‏--radius-sm/md/lg/xl آبشار می‌شود — هر عنصر گرد با هم جابه‌جا می‌شود.
density‏compact | ‏comfortable | ‏spaciousضریب فاصله که به‌صورت متغیر CSS ی ‏--spacing-mul اعمال می‌شود. ‏compact = ‎۰٫۸۵×‎، ‏comfortable = ‎۱٫۰×‎ ‏(پیش‌فرض)، ‏spacious = ‎۱٫۲×‎. فاصله‌گذاری پایه Tailwind را مقیاس می‌دهد، پس padding، ‏gap و utility های space-between همه تناسبی شیفت می‌خورند.
yaml
layout:
  radius: "0"
  density: compact

انواع چیدمان ‏(Layout variants)

‏layoutVariant چیدمان کلی پوسته را برمی‌گزیند. در غیاب آن پیش‌فرض "standard" است.

نوعرفتار
standardتک‌ستونی، عرض بیشینه ‎۱۶۰۰px‎ ‏(پیش‌فرض).
cockpitریل sidebar چپ ‏(‎۲۶۰px‎) + محتوای اصلی. توسط پلاگین‌ها از طریق slot ی sidebar پر می‌شود — بخش Shell slots را ببینید. بدون پلاگین، ریل placeholder نشان می‌دهد.
tiledسقف max-width را حذف می‌کند تا صفحات کل عرض viewport را بگیرند.
 
layoutVariant: cockpit

نوع فعلی به‌عنوان ‏document.documentElement.dataset.layoutVariant expose می‌شود، پس CSS خام داخل ‏customCSS می‌تواند با ‏:root[data-layout-variant="cockpit"] ... نشانه‌گیری‌اش کند.

asset های تم ‏(تصاویر به‌عنوان CSS var)

URL های artwork را همراه تم بفرستید. هر slot نام‌دار یک CSS var می‌شود ‏(--theme-asset-<name>) که پوستهٔ داخلی و هر پلاگینی می‌تواند بخواند. slot ی bg خودکار به backdrop سیم‌کشی می‌شود؛ سایر slot ها رو-به-پلاگین‌اند.

yaml
assets:
  bg: "https://example.com/hero-bg.jpg"           # auto-wired into <Backdrop />
  hero: "/my-images/strike-freedom.png"           # for plugin sidebars
  crest: "/my-images/crest.svg"                   # for header-left plugins
  logo: "/my-images/logo.png"
  sidebar: "/my-images/rail.png"
  header: "/my-images/header-art.png"
  custom:
    scanLines: "/my-images/scanlines.png"         # → --theme-asset-custom-scanLines

مقادیر اینها را می‌پذیرند:

  • URL های لخت — خودکار در ‏url(...) پیچیده می‌شوند.
  • عبارات از-قبل-پیچیده‌شدهٔ ‏url(...)، ‏linear-gradient(...)، ‏radial-gradient(...) — همان‌طور استفاده می‌شوند.
  • ‏"none" — انصراف صریح.

هر asset همچنین به‌صورت ‏--theme-asset-<name>-raw ‏(URL باز‌شده) هم emit می‌شود، برای اینکه پلاگین لازم داشت به ‏<img src> پاسش دهد نه background-image.

پلاگین‌ها با CSS یا JS ساده می‌خوانند:

// In a plugin slot
const hero = getComputedStyle(document.documentElement)
  .getPropertyValue("--theme-asset-hero").trim();

بازنویسی chrome ی کامپوننت‌ها

‏componentStyles کامپوننت‌های منفرد پوسته را بدون نوشتن selector ی CSS ری‌استایل می‌کند. ورودی‌های هر bucket به CSS var تبدیل می‌شوند ‏(--component-<bucket>-<kebab-property>) که کامپوننت‌های مشترک پوسته می‌خوانند. پس override های ‏card: روی هر ‏<Card> اعمال می‌شود و ‏header: روی نوار اپ و… .

yaml
componentStyles:
  card:
    clipPath: "polygon(12px 0, 100% 0, 100% calc(100% - 12px), calc(100% - 12px) 100%, 0 100%, 0 12px)"
    background: "linear-gradient(180deg, rgba(10, 22, 52, 0.85), rgba(5, 9, 26, 0.92))"
    boxShadow: "inset 0 0 0 1px rgba(64, 200, 255, 0.28)"
  header:
    background: "linear-gradient(180deg, rgba(16, 32, 72, 0.95), rgba(5, 9, 26, 0.9))"
  tab:
    clipPath: "polygon(6px 0, 100% 0, calc(100% - 6px) 100%, 0 100%)"
  sidebar: {}
  backdrop: {}
  footer: {}
  progress: {}
  badge: {}
  page: {}

bucket های پشتیبانی‌شده: ‏card، ‏header، ‏footer، ‏sidebar، ‏tab، ‏progress، ‏badge، ‏backdrop، ‏page.

نام property ها camelCase است ‏(clipPath) و به kebab emit می‌شود ‏(clip-path). مقادیر رشته‌های CSS ساده‌اند — هر چیزی که CSS قبول کند ‏(clip-path، ‏border-image، ‏background، ‏box-shadow، ‏animation و…).

بازنویسی رنگ‌ها

بیشتر تم‌ها به این نیاز ندارند — پالت ۳لایه هر توکن shadcn را مشتق می‌کند. از ‏colorOverrides وقتی استفاده کنید که اکسنت خاصی می‌خواهید که مشتق‌سازی تولیدش نمی‌کند ‏(قرمز destructive ملایم‌تر برای تم پاستلی، سبز success مشخص برای یک برند).

yaml
colorOverrides:
  primary: "#ffce3a"
  primaryForeground: "#05091a"
  accent: "#3fd3ff"
  ring: "#3fd3ff"
  destructive: "#ff3a5e"
  border: "rgba(64, 200, 255, 0.28)"

کلیدهای پشتیبانی‌شده: ‏card، ‏cardForeground، ‏popover، ‏popoverForeground، ‏primary، ‏primaryForeground، ‏secondary، ‏secondaryForeground، ‏muted، ‏mutedForeground، ‏accent، ‏accentForeground، ‏destructive، ‏destructiveForeground، ‏success، ‏warning، ‏border، ‏input، ‏ring.

هر کلید یک‌به-یک به CSS var ی ‏--color-<kebab> نگاشت می‌شود ‏(مثلاً ‏primaryForeground ← ‏--color-primary-foreground). هر کلیدی اینجا ست شود فقط برای تم فعال بر آبشار پالت مقدم است — سوئیچ به تم دیگر override ها را پاک می‌کند.

‏customCSS خام

برای chrome سطح-selector که componentStyles نمی‌رسد — pseudo-element ها، انیمیشن‌ها، media query ها، override های مخصوص-تم — CSS خام را داخل ‏customCSS بریزید:

css
customCSS: |
  /* Scanline overlay — only visible when cockpit variant is active. */
  :root[data-layout-variant="cockpit"] body::before {
    content: "";
    position: fixed;
    inset: 0;
    pointer-events: none;
    z-index: 100;
    background: repeating-linear-gradient(to bottom,
      transparent 0px, transparent 2px,
      rgba(64, 200, 255, 0.035) 3px, rgba(64, 200, 255, 0.035) 4px);
    mix-blend-mode: screen;
  }

CSS هنگام apply شدن تم به‌صورت یک تگ scoped واحد ‏<style data-hermes-theme-css> تزریق و موقع تعویض تم پاک می‌شود. سقف ۳۲ KiB به‌ازای هر تم.

مرجع کامل YAML ی تم

همهٔ پیچ‌ومهره‌ها در یک فایل — کپی کنید و آنچه لازم ندارید را حذف کنید:

yaml
# ~/.hermes/dashboard-themes/ocean.yaml
name: ocean
label: Ocean Deep
description: Deep sea blues with coral accents

# 3-layer palette (accepts {hex, alpha} or bare hex)
palette:
  background:
    hex: "#0a1628"
    alpha: 1.0
  midground:
    hex: "#a8d0ff"
    alpha: 1.0
  foreground:
    hex: "#ffffff"
    alpha: 0.0
  warmGlow: "rgba(255, 107, 107, 0.35)"
  noiseOpacity: 0.7

typography:
  fontSans: "Poppins, system-ui, sans-serif"
  fontMono: "Fira Code, ui-monospace, monospace"
  fontDisplay: "Poppins, system-ui, sans-serif"   # optional
  fontUrl: "https://fonts.googleapis.com/css2?family=Poppins:wght@400;500;600&family=Fira+Code:wght@400;500&display=swap"
  baseSize: "15px"
  lineHeight: "1.6"
  letterSpacing: "-0.003em"

layout:
  radius: "0.75rem"
  density: comfortable

layoutVariant: standard        # standard | cockpit | tiled

assets:
  bg: "https://example.com/ocean-bg.jpg"
  hero: "/my-images/kraken.png"
  crest: "/my-images/anchor.svg"
  logo: "/my-images/logo.png"
  custom:
    pattern: "/my-images/waves.svg"

componentStyles:
  card:
    boxShadow: "inset 0 0 0 1px rgba(168, 208, 255, 0.18)"
  header:
    background: "linear-gradient(180deg, rgba(10, 22, 40, 0.95), rgba(5, 9, 26, 0.9))"

colorOverrides:
  destructive: "#ff6b6b"
  ring: "#ff6b6b"

customCSS: |
  /* Any additional selector-level tweaks */

بعد از ساخت فایل داشبورد را refresh کنید. تم‌ها را زنده از نوار header عوض کنید — روی آیکن پالت کلیک کنید. انتخاب در config.yaml زیر ‏dashboard.theme ماندگار و بعد از reload بازیابی می‌شود.

۲ پلاگین‌ها

پلاگین داشبورد یک دایرکتوری با ‏manifest.json، یک باندل JS از پیش ساخته‌شده و به‌صورت اختیاری یک فایل CSS و یک فایل پایتون با مسیرهای FastAPI است. پلاگین‌ها کنار دیگر پلاگین‌های هرمس در ‏~/.hermes/plugins/<name>/ زندگی می‌کنند — گسترش داشبورد یک زیرپوشهٔ ‏dashboard/ داخل همان دایرکتوری پلاگین است، پس یک پلاگین از یک نصب واحد هم CLI/گیت‌وی را گسترش می‌دهد هم داشبورد را.

پلاگین‌ها React یا کامپوننت‌های UI را bundle نمی‌کنند. از Plugin SDK ای که روی ‏window.__HERMES_PLUGIN_SDK__ expose شده استفاده می‌کنند. این باندل‌های پلاگین را ریز نگه می‌دارد ‏(معمولاً چند KB) و از تداخل نسخه‌ها جلوگیری می‌کند.

شروع سریع — اولین پلاگین شما

ساختار دایرکتوری را بسازید:

mkdir -p ~/.hermes/plugins/my-plugin/dashboard/dist

manifest را بنویسید:

// ~/.hermes/plugins/my-plugin/dashboard/manifest.json
{
  "name": "my-plugin",
  "label": "My Plugin",
  "icon": "Sparkles",
  "version": "1.0.0",
  "tab": {
    "path": "/my-plugin",
    "position": "after:skills"
  },
  "entry": "dist/index.js"
}

باندل JS را بنویسید ‏(یک IIFE ساده — بدون نیاز به build):

// ~/.hermes/plugins/my-plugin/dashboard/dist/index.js
(function () {
  "use strict";

  const SDK = window.__HERMES_PLUGIN_SDK__;
  const { React } = SDK;
  const { Card, CardHeader, CardTitle, CardContent } = SDK.components;

  function MyPage() {
    return React.createElement(Card, null,
      React.createElement(CardHeader, null,
        React.createElement(CardTitle, null, "My Plugin"),
      ),
      React.createElement(CardContent, null,
        React.createElement("p", { className: "text-sm text-muted-foreground" },
          "Hello from my custom dashboard tab.",
        ),
      ),
    );
  }

  window.__HERMES_PLUGINS__.register("my-plugin", MyPage);
})();

داشبورد را refresh کنید — تب شما در نوار nav، بعد از Skills ظاهر می‌شود.

💡 رد شدن از React.createElement

اگر JSX ترجیح می‌دهید، هر bundler ای ‏(esbuild، ‏Vite، ‏rollup) را با React به‌عنوان external و خروجی IIFE به کار ببرید. تنها الزام سخت این است که فایل نهایی یک فایل JS ی واحد قابل‌بارگذاری از طریق ‏<script> باشد. React هرگز bundle نمی‌شود؛ از ‏SDK.React می‌آید.

چیدمان دایرکتوری

~/.hermes/plugins/my-plugin/
├── plugin.yaml              # optional — existing CLI/gateway plugin manifest
├── __init__.py              # optional — existing CLI/gateway hooks
└── dashboard/               # dashboard extension
    ├── manifest.json        # required — tab config, icon, entry point
    ├── dist/
    │   ├── index.js         # required — pre-built JS bundle (IIFE)
    │   └── style.css        # optional — custom CSS
    └── plugin_api.py        # optional — backend API routes (FastAPI)

یک دایرکتوری پلاگین واحد می‌تواند سه گسترش عمود بر هم حمل کند:

  • ‏plugin.yaml + ‏__init__.py — پلاگین CLI/گیت‌وی ‏(بخش پلاگین‌ها).
  • ‏dashboard/manifest.json + ‏dashboard/dist/index.js — پلاگین UI ی داشبورد.
  • ‏dashboard/plugin_api.py — مسیرهای بک‌اند داشبورد.

هیچ‌کدام الزامی نیست؛ فقط لایه‌هایی را که لازم دارید بگنجانید.

فیلدالزامیتوضیح
nameبلهشناسهٔ یکتای پلاگین. حروف کوچک، خط تیره مجاز. در URLها و ثبت استفاده می‌شود.
labelبلهنام نمایشی که در تب nav نشان داده می‌شود.
descriptionنهتوضیح کوتاه ‏(در سطح‌های admin ی داشبورد نمایش داده می‌شود).
iconنهنام آیکن Lucide. پیش‌فرض ‏Puzzle. نام‌های ناشناخته بی‌سروصدا به ‏Puzzle برمی‌گردند.
versionنهرشتهٔ Semver. پیش‌فرض ‏0.0.0.
tab.pathبلهمسیر URL برای تب ‏(مثلاً ‏/my-plugin).
tab.positionنهکجا تب درج شود. ‏"end" ‏(پیش‌فرض)، ‏"after:<path>" یا ‏"before:<path>" — مقدار بعد از دونقطه segment ی مسیر تب هدف است ‏(بدون اسلش ابتدایی). مثال‌ها: ‏"after:skills"، ‏"before:config".
tab.overrideنهروی یک مسیر route داخلی ‏("/"، ‏"/sessions"، ‏"/config" و…) ست کنید تا به‌جای افزودن تب جدید آن صفحه را جایگزین کند. بخش جایگزینی صفحات داخلی را ببینید.
tab.hiddenنهوقتی true باشد کامپوننت و هر slot را ثبت می‌کند بدون افزودن تب به nav. استفاده توسط پلاگین‌های فقط-slot.
slotsنهshell slot های نام‌داری که این پلاگین پر می‌کند. فقط کمک مستندات — ثبت واقعی از باندل JS از طریق ‏registerSlot() انجام می‌شود. فهرست کردن slotها سطوح کشف را اطلاعات‌مندتر می‌کند.
entryبلهمسیر باندل JS نسبت به ‏dashboard/. پیش‌فرض ‏dist/index.js.
cssنهمسیر فایل CSS برای تزریق به‌عنوان تگ ‏<link>.
apiنهمسیر فایل پایتون حامل مسیرهای FastAPI. زیر ‏/api/plugins/<name>/ سوار می‌شود.

آیکن‌های موجود

پلاگین‌ها از نام‌های آیکن Lucide استفاده می‌کنند. داشبورد با نام نگاشت‌شان می‌کند — نام‌های ناشناخته بی‌سروصدا به Puzzle برمی‌گردند.

فعلاً نگاشت‌شده: ‏Activity، ‏BarChart3، ‏Clock، ‏Code، ‏Database، ‏Eye، ‏FileText، ‏Globe، ‏Heart، ‏KeyRound، ‏MessageSquare، ‏Package، ‏Puzzle، ‏Settings، ‏Shield، ‏Sparkles، ‏Star، ‏Terminal، ‏Wrench، ‏Zap.

آیکن دیگری می‌خواهید؟ به ‏ICON_MAP ی ‏web/src/App.tsx یک PR بزنید — تغییر کاملاً افزایشی است.

۴ Shell slots

slot ها به پلاگین اجازه می‌دهد کامپوننت‌هایی به مکان‌های نام‌دار پوسته اپ تزریق کند — ریل cockpit، ‏header، ‏footer، لایهٔ overlay — بدون تصاحب یک تب کامل. چند پلاگین می‌توانند همان slot را پر کنند؛ روی هم در ترتیب ثبت رندر می‌شوند.

از داخل باندل پلاگین ثبت کنید:

window.__HERMES_PLUGINS__.registerSlot("my-plugin", "sidebar", MySidebar);
window.__HERMES_PLUGINS__.registerSlot("my-plugin", "header-left", MyCrest);

کاتالوگ slot ها

slot های سراسری-پوسته ‏(در هر جای chrome ی اپ رندر می‌شوند):

Slotموقعیت
backdropداخل پشتهٔ لایه‌های ‏<Backdrop />، بالای لایهٔ نویز.
header-leftقبل از برند هرمس در نوار بالا.
header-rightقبل از سوئیچ‌گرهای تم/زبان در نوار بالا.
header-bannerنوار تمام-عرض زیر nav.
sidebarریل sidebar ی cockpit — فقط وقتی ‏layoutVariant === "cockpit" رندر می‌شود.
pre-mainبالای خروجی route ‏(داخل main).
post-mainزیر خروجی route ‏(داخل main).
footer-leftمحتوای خانهٔ footer ‏(جایگزین پیش‌فرض).
footer-rightمحتوای خانهٔ footer ‏(جایگزین پیش‌فرض).
overlayلایهٔ fixed بالای همه‌چیز. برای chrome هایی ‏(scanline، vignette) که customCSS به‌تنهایی نمی‌رسد مفید است.

slot های مخصوص-صفحه ‏(فقط روی صفحهٔ داخلی نام‌برده رندر می‌شوند — برای تزریق widget، کارت یا toolbar به صفحهٔ موجود بدون override کردن کل route):

Slotکجا رندر می‌شود
‏sessions:top / ‏sessions:bottomبالا / پایین صفحهٔ ‏/sessions.
‏analytics:top / ‏analytics:bottomبالا / پایین صفحهٔ ‏/analytics.
‏logs:top / ‏logs:bottomبالا ‏(بالای toolbar فیلتر) / پایین ‏(زیر نمایشگر لاگ) در ‏/logs.
‏cron:top / ‏cron:bottomبالا / پایین صفحهٔ ‏/cron.
‏skills:top / ‏skills:bottomبالا / پایین صفحهٔ ‏/skills.
‏config:top / ‏config:bottomبالا / پایین صفحهٔ ‏/config.
‏env:top / ‏env:bottomبالا / پایین صفحهٔ ‏/env ‏(Keys).
‏docs:top / ‏docs:bottomبالا ‏(بالای iframe) / پایین ‏/docs.
‏chat:top / ‏chat:bottomبالا / پایین ‏/chat ‏(فقط وقتی چت تعبیه‌شده فعال باشد).

مثال — افزودن یک کارت بنر به بالای صفحهٔ Sessions:

function PinnedSessionsBanner() {
  return React.createElement(Card, null,
    React.createElement(CardContent, { className: "py-2 text-xs" },
      "Pinned note injected by my-plugin"),
  );
}

window.__HERMES_PLUGINS__.registerSlot("my-plugin", "sessions:top", PinnedSessionsBanner);

slot های مخصوص-صفحه را با ‏tab.hidden: true ترکیب کنید اگر پلاگین فقط صفحات موجود را غنی می‌کند و تب مستقل در sidebar نمی‌خواهد.

پوسته فقط برای slotهای بالا ‏<PluginSlot name="..." /> را رندر می‌کند. نام‌های اضافی توسط registry برای UI های تو-در-تو پذیرفته می‌شوند — پلاگین می‌تواند slot های خودش را از طریق ‏SDK.components.PluginSlot expose کند.

ثبت دوباره و HMR

اگر همان جفت ‏(plugin، slot) دو بار ثبت شود، فراخوانی بعدی قبلی را جایگزین می‌کند — مطابق رفتاری که React HMR از remount شدن پلاگین‌ها انتظار دارد.

۵ جایگزینی صفحات داخلی، غنی‌سازی و پلاگین‌های فقط-slot

جایگزینی صفحات داخلی ‏(‏tab.override)

ست کردن ‏tab.override روی یک مسیر route داخلی باعث می‌شود کامپوننت پلاگین آن صفحه را جایگزین کند نه اینکه تب جدیدی اضافه کند. وقتی مفید است که تمی بخواهد صفحهٔ خانه سفارشی ‏(/) داشته باشد ولی بقیهٔ داشبورد سالم بماند.

{
  "name": "my-home",
  "label": "Home",
  "tab": {
    "path": "/my-home",
    "override": "/",
    "position": "end"
  },
  "entry": "dist/index.js"
}

با ست بودن override:

  • کامپوننت اصلی صفحه در ‏/ از router حذف می‌شود.
  • پلاگین شما به‌جایش در ‏/ رندر می‌شود.
  • برای ‏tab.path هیچ تب nav اضافه نمی‌شود ‏(نقطهٔ override همین است).

فقط یک پلاگین می‌تواند یک مسیر مشخص را override کند. اگر دو پلاگین ادعای override یکسان کنند اولی برنده است و دومی با هشدار dev-mode نادیده گرفته می‌شود.

اگر فقط نیاز به افزودن کارت یا toolbar به صفحهٔ موجود دارید بدون تصاحبش، به‌جایش از slot های مخصوص-صفحه استفاده کنید.

غنی‌سازی صفحات داخلی ‏(slot های مخصوص-صفحه)

جایگزینی کامل با tab.override سنگین است — پلاگین حالا مالک کل صفحه است شامل هر به‌روزرسانی آینده‌ای که ما برایش ارسال کنیم. بیشتر وقت‌ها فقط می‌خواهید بنر، کارت یا toolbar ای به صفحهٔ موجود اضافه کنید. کارِ slot های مخصوص-صفحه دقیقاً همین است.

هر صفحهٔ داخلی slot های ‏<page>:top و ‏<page>:bottom را در بالا و پایین ناحیه محتوایش expose می‌کند. پلاگین با فراخوانی registerSlot() یکی را پر می‌کند — صفحهٔ داخلی عادی کار می‌کند و کامپوننت شما کنارش رندر می‌شود.

slot های موجود: ‏sessions:*، ‏analytics:*، ‏logs:*، ‏cron:*، ‏skills:*، ‏config:*، ‏env:*، ‏docs:*، ‏chat:* ‏(هر کدام با ‏:top و ‏:bottom). کاتالوگ کامل را در بخش Shell slots ببینید.

مثال مینیمال — پین کردن بنری به بالای صفحهٔ Sessions:

// ~/.hermes/plugins/session-notes/dashboard/manifest.json
{
  "name": "session-notes",
  "label": "Session Notes",
  "tab": { "path": "/session-notes", "hidden": true },
  "slots": ["sessions:top"],
  "entry": "dist/index.js"
}
// ~/.hermes/plugins/session-notes/dashboard/dist/index.js
(function () {
  const SDK = window.__HERMES_PLUGIN_SDK__;
  const { React } = SDK;
  const { Card, CardContent } = SDK.components;

  function Banner() {
    return React.createElement(Card, null,
      React.createElement(CardContent, { className: "py-2 text-xs" },
        "Remember to label important sessions before archiving."),
    );
  }

  // Placeholder for the hidden tab.
  window.__HERMES_PLUGINS__.register("session-notes", function () { return null; });

  // The real work.
  window.__HERMES_PLUGINS__.registerSlot("session-notes", "sessions:top", Banner);
})();

نکات کلیدی:

  • ‏tab.hidden: true پلاگین را از sidebar دور نگه می‌دارد — صفحهٔ مستقلی ندارد.
  • فیلد manifest ی ‏slots فقط مستندات است. binding واقعی در باندل JS با registerSlot() انجام می‌شود.
  • چند پلاگین می‌توانند مدعی همان slot ی مخصوص-صفحه شوند. روی هم در ترتیب ثبت رندر می‌شوند.
  • بدون هیچ پلاگین ثبت‌شده صفر footprint: صفحهٔ داخلی دقیقاً مثل قبل رندر می‌شود.

یک پلاگین مرجع ‏(example-dashboard در مخزن ‏hermes-example-plugins) دموی زنده‌ای دارد که بنری به ‏sessions:top تزریق می‌کند — نصبش کنید تا الگو را سر-تا-سر ببینید.

پلاگین‌های فقط-slot ‏(‏tab.hidden)

وقتی ‏tab.hidden: true، پلاگین کامپوننتش ‏(برای بازدید مستقیم URL) و هر slot اش را ثبت می‌کند ولی هرگز تب به ناوبری اضافه نمی‌کند. استفاده توسط پلاگین‌هایی که فقط برای تزریق به slot ها وجود دارند — crest ی header، ‏HUD ی sidebar، یک overlay.

{
  "name": "header-crest",
  "label": "Header Crest",
  "tab": {
    "path": "/header-crest",
    "position": "end",
    "hidden": true
  },
  "slots": ["header-left"],
  "entry": "dist/index.js"
}

باندل همچنان register() را با یک کامپوننت placeholder صدا می‌زند ‏(رویهٔ خوب برای اینکه کسی مستقیم URL را باز کرد) و بعد registerSlot() برای کار واقعی.

۶ مسیرهای API ی بک‌اند

پلاگین‌ها با ست کردن ‏api در manifest مسیرهای FastAPI ثبت می‌کنند. فایل را بسازید و یک ‏router export کنید:

# ~/.hermes/plugins/my-plugin/dashboard/plugin_api.py
from fastapi import APIRouter

router = APIRouter()

@router.get("/data")
async def get_data():
    return {"items": ["one", "two", "three"]}

@router.post("/action")
async def do_action(body: dict):
    return {"ok": True, "received": body}

مسیرها زیر ‏/api/plugins/<name>/ سوار می‌شوند، پس بالا می‌شود:

  • ‏GET /api/plugins/my-plugin/data
  • ‏POST /api/plugins/my-plugin/action

مسیرهای API ی پلاگین پشت گate احراز هویت عادی داشبورد نشسته‌اند — درخواست احراز-نشده قبل از اجرای مسیر پلاگین ‏401 می‌گیرد و درخواست‌ها به مسیرهای پلاگین غیرفعال در لحظهٔ درخواست reject می‌شوند. با این حال اگر پلاگین‌های نامعتبر اجرا می‌کنید داشبورد را با ‎--host 0.0.0.0‎ روی یک interface عمومی expose نکنید — یک نشست احراز-هویت‌شده هم به مسیرهایشان می‌رسد.

دسترسی به internals ی هرمس

مسیرهای بک‌اند داخل پروسهٔ داشبورد اجرا می‌شوند، پس می‌توانند مستقیماً از codebase ی hermes-agent ایمپورت کنند:

from fastapi import APIRouter
from hermes_state import SessionDB
from hermes_cli.config import load_config

router = APIRouter()

@router.get("/session-count")
async def session_count():
    db = SessionDB()
    try:
        count = len(db.list_sessions(limit=9999))
        return {"count": count}
    finally:
        db.close()

@router.get("/config-snapshot")
async def config_snapshot():
    cfg = load_config()
    return {"model": cfg.get("model", {})}

۷ CSS ی اختصاصی per-plugin و کشف/reload پلاگین‌ها

CSS اختصاصی هر پلاگین

اگر پلاگینتان به استایل‌هایی فراتر از کلاس‌های Tailwind و ‏inline style= نیاز دارد، یک فایل CSS اضافه و در manifest ارجاع دهید:

{
  "css": "dist/style.css"
}

فایل موقع بارگذاری پلاگین به‌عنوان تگ ‏ تزریق می‌شود. از نام کلاس‌های خاص استفاده کنید تا با استایل‌های داشبورد تداخل نکند و برای theme-aware ماندن به CSS var های داشبورد ارجاع دهید:

/* dist/style.css */
.my-plugin-chart {
  border: 1px solid var(--color-border);
  background: var(--color-card);
  color: var(--color-card-foreground);
  padding: 1rem;
}
.my-plugin-chart:hover {
  border-color: var(--color-ring);
}

داشبورد هر توکن shadcn را به‌صورت ‏--color-* به‌علاوهٔ extras ی تم ‏(--theme-asset-*، ‏--component-<bucket>-*، ‏--radius، ‏--spacing-mul) expose می‌کند. به آنها ارجاع دهید تا پلاگین‌تان خودکار با تم فعال ریسکین شود.

کشف و reload ی پلاگین‌ها

داشبورد سه دایرکتوری را برای ‏dashboard/manifest.json اسکن می‌کند:

اولویتدایرکتوریبرچسب منبع
۱ ‏(برنده در تداخل)‏~/.hermes/plugins/<name>/dashboard/user
۲‏<repo>/plugins/memory/<name>/dashboard/bundled
۲‏<repo>/plugins/<name>/dashboard/bundled
۳‏./.hermes/plugins/<name>/dashboard/project — فقط وقتی HERMES_ENABLE_PROJECT_PLUGINS ست باشد

نتایج کشف per-processe ی داشبورد کش می‌شوند. بعد از افزودن پلاگین جدید یا:

# Force a rescan without restart
curl http://127.0.0.1:9119/api/dashboard/plugins/rescan

…یا ری‌استارت ‏hermes dashboard.

چرخه‌حیات بارگذاری پلاگین

  1. داشبورد بارگذاری می‌شود. ‏main.tsx مقدار SDK را روی ‏window.__HERMES_PLUGIN_SDK__ و registry را روی ‏window.__HERMES_PLUGINS__ expose می‌کند.
  2. App.tsx مقدار ‏usePlugins() را صدا می‌زند ← واکشی ‏GET /api/dashboard/plugins.
  3. برای هر manifest: اول ‏ ی CSS تزریق می‌شود ‏(اگر اعلام شده باشد)، بعد تگ ‏script باندل JS را بارگذاری می‌کند.
  4. IIFE ی پلاگین اجرا و ‏window.__HERMES_PLUGINS__.register(name, Component) را صدا می‌زند — و به‌طور اختیاری ‏registerSlot(name, slot, Component) برای هر slot.
  5. داشبورد کامپوننت ثبت‌شده را علیه manifest حل، تب را به ناوبری اضافه ‏(مگر hidden) و کامپوننت را به‌عنوان route mount می‌کند.

پلاگین‌ها تا ۲ ثانیه بعد از بارگذاری اسکریپتشان وقت دارند register() را صدا بزنند. بعدش داشبورد منتظر ماندن را قطع و رندر اولیه را تمام می‌کند. اگر پلاگینی بعداً ثبت شود همچنان ظاهر می‌شود — nav واکنشی است.

اگر اسکریپت پلاگینی بارگذاری نشود ‏(۴۰۴، خطای نحو، exception داخل IIFE)، داشبورد هشداری به console مرورگر لاگ و بدون آن ادامه می‌دهد.

۸ دموی ترکیبی تم + پلاگین

پلاگین ‏strike-freedom-cockpit ‏(مخزن همراه hermes-example-plugins) یک دموی ریسکین کامل است. یک YAML تم را با یک پلاگین فقط-slot جفت می‌کند تا بدون fork کردن داشبورد یک HUD به سبک کابین تولید کند.

چه چیزی نشان می‌دهد:

  • یک تم کامل با palette، ‏typography، ‏fontUrl، ‏layoutVariant: cockpit، ‏assets، ‏componentStyles ‏(گوشه‌های notch دار card، پس‌زمینه‌های گرادیانی)، ‏colorOverrides و ‏customCSS ‏(overlay ی scanline).
  • یک پلاگین فقط-slot ‏(tab.hidden: true) که در سه slot ثبت می‌شود:
    • ‏sidebar — پنل MS-STATUS با نوارهای تلمتری زنده رانده توسط ‏SDK.api.getStatus().
    • ‏header-left — crest ی جناحی که ‏--theme-asset-crest را از تم فعال می‌خواند.
    • ‏footer-right — tagline سفارشی جایگزین خط پیش‌فرض سازمان.
  • پلاگین artwork ی تأمین-تم را از طریق CSS var ها می‌خواند، پس تعویض تم hero/crest را بدون تغییر کد پلاگین عوض می‌کند.

نصب:

git clone https://github.com/NousResearch/hermes-example-plugins.git

# Theme
cp hermes-example-plugins/strike-freedom-cockpit/theme/strike-freedom.yaml \
   ~/.hermes/dashboard-themes/

# Plugin
cp -r hermes-example-plugins/strike-freedom-cockpit ~/.hermes/plugins/

داشبورد را باز و از انتخاب‌گر تم Strike Freedom را بردارید. sidebar ی کابین ظاهر می‌شود، crest در header نمایش داده می‌شود و tagline جایگزین footer می‌شود. برگردید روی Hermes Teal؛ پلاگین نصب مانده اما نامرئی است ‏(slot ی sidebar فقط زیر نوع چیدمان cockpit رندر می‌شود).

سورس پلاگین ‏(strike-freedom-cockpit/dashboard/dist/index.js در مخزن همراه) را بخوانید تا ببینید چطور CSS var می‌خواند، در برابر داشبوردهای قدیمی‌ترِ بدون پشتیبانی slot گارد می‌گذارد و از یک باندل سه slot ثبت می‌کند.

۱۰ عیب‌یابی

تمم در انتخاب‌گر ظاهر نمی‌شود.
بررسی کنید فایل در ‏~/.hermes/dashboard-themes/ باشد و با ‏.yaml یا ‏.yml تمام شود. صفحه را refresh کنید. ‏curl http://127.0.0.1:9119/api/dashboard/themes را اجرا کنید — تم شما باید در پاسخ باشد. اگر YAML خطای parse دارد داشبورد در errors.log زیر ‏~/.hermes/logs/ لاگ می‌کند.

تب پلاگینم نشان داده نمی‌شود.

  1. بررسی کنید manifest در ‏~/.hermes/plugins/<name>/dashboard/manifest.json باشد ‏(به زیرپوشهٔ dashboard توجه کنید).
  2. ‏curl http://127.0.0.1:9119/api/dashboard/plugins/rescan برای کشف دوبارهٔ اجباری.
  3. dev tools مرورگر ← Network — تأیید کنید ‏manifest.json و index.js و هر CSS بدون ۴۰۴ لود شده‌اند.
  4. dev tools مرورگر ← Console — دنبال خطاهای حین IIFE یا ‏window.__HERMES_PLUGINS__ is undefined باشید ‏(یعنی SDK مقداردهی نشده، معمولاً کرش رندر React ی زودهنگام).
  5. تأیید کنید باندل شما register(...) را با همان نامی که در ‏manifest.json:name هست صدا می‌زند.

کامپوننت‌های ثبت‌شده در slot رندر نمی‌شوند.
slot ی sidebar فقط وقتی تم فعال ‏layoutVariant: cockpit داشته باشد رندر می‌شود. سایر slot ها همیشه رندر می‌شوند. اگر در slot ای ثبت می‌کنید که hit ندارد، داخل registerSlot یک console.log اضافه کنید تا تأیید شود اصلاً باندل پلاگین اجرا شده.

مسیرهای بک‌اند پلاگین ۴۰۴ می‌دهند.

  1. تأیید کنید manifest مقدار ‏"api": "plugin_api.py" دارد که به فایل موجود داخل dashboard/ اشاره کند.
  2. ‏hermes dashboard را ری‌استارت کنید — مسیرهای API ی پلاگین یک بار هنگام startup سوار می‌شوند، نه هنگام rescan.
  3. بررسی کنید plugin_api.py یک ‏router = APIRouter() سطح-ماژول export کند. سایر نام‌های export برداشته نمی‌شوند.
  4. ‏~/.hermes/logs/errors.log را tail کنید برای «Failed to load plugin <name> API routes» — خطاهای import آنجا لاگ می‌شوند.

تعویض تم، colorOverrides هایم را می‌اندازد.
‏colorOverrides ها به تم فعال scope شده و موقع تعویض تم پاک می‌شوند — عمدی است. اگر override های ماندگار می‌خواهید در YAML خود تم بگذاریدشان نه در switcher زنده.

customCSS ی تمم بریده می‌شود.
بلوک customCSS سقف ۳۲ KiB به‌ازای هر تم دارد. stylesheet های بزرگ را بین چند تم بشکنید یا به پلاگینی سوئیچ کنید که از طریق فیلد css اش یک stylesheet کامل تزریق می‌کند ‏(بدون سقف حجمی).

می‌خواهم پلاگینی روی PyPI منتشر کنم.
پلاگین‌های داشبورد با چیدمان دایرکتوری نصب می‌شوند نه pip entry point. تمیزترین مسیر توزیع امروز مخزن git ای است که کاربر در ‏~/.hermes/plugins/ کلون می‌کند. نصاب pip-محور برای پلاگین‌های داشبورد فعلاً سیم‌کشی نشده است.
