استخرهای اعتبارنامه ‏(Credential Pools)

استخرهای credential اجازه می‌دهند چند کلید API یا توکن OAuth برای همان ارائه‌دهنده ثبت کنید. وقتی یک کلید به rate limit یا سهمیه صورتحساب بخورد، هرمس خودکار به کلید سالم بعدی می‌چرخد — نشست شما زنده می‌ماند بدون تعویض ارائه‌دهنده.

این با ارائه‌دهندگان پشتیبان فرق دارد که کلاً به ارائه‌دهندهٔ متفاوت سوئیچ می‌کنند. استخرهای credential چرخش همان-ارائه‌دهنده‌اند؛ ارائه‌دهندگان پشتیبان failover ی بین-ارائه‌دهنده‌ای. استخرها اول امتحان می‌شوند — تمام کلیدهای استخر تمام شد، بعد ارائه‌دهندهٔ پشتیبان فعال می‌شود.

⚠️ چرخش کلید کش پرامپت را ریست می‌کند

کش‌های پرامپت سمت-ارائه‌دهنده ‏(Anthropic، OpenAI، OpenRouter) به حساب/کلید API ی درخواست‌کننده scope شده‌اند. وقتی استخر وسط نشست به کلید دیگری بچرخد، کلید جدید هیچ پیشوند کش‌شده‌ای برای گفتگوی شما ندارد — درخواست بعدی کل تاریخچه را با قیمت ورودی بدون تخفیف بازمی‌خواند و چرخش دوباره به عقب هم یک re-read کامل دیگر است مگر TTL کش کلید قبلی هنوز زنده باشد. چرخش نشست را سرپا نگه می‌دارد که همان هدف است، ولی روی گفتگوهای بلند هر چرخش هزینهٔ یک پاس کامل قیمت روی زمینه دارد.

💡

استخرهای credential بیشتر برای ارائه‌دهندگان کلید-API اند ‏(OpenRouter، Anthropic). یک OAuth ی Nous Portal بیش از ۳۰۰ مدل را پوشش می‌دهد پس اکثر کاربران روی Portal به استخر نیازی ندارند.

۱ نحوهٔ کار و شروع سریع

سازوکار

Your request
  → Pick key from pool (round_robin / least_used / fill_first / random)
  → Send to provider
  → 429 rate limit?
      → Plan/usage limit reached (e.g. ChatGPT/Codex "usage limit reached")?
          → Rotate to next pool key immediately (no retry — the cap won't clear on retry)
      → Generic / transient 429?
          → Retry same key once (transient blip)
          → Second 429 → rotate to next pool key
      → All keys exhausted → fallback_model (different provider)
  → 402 billing error?
      → Immediately rotate to next pool key (1h cooldown)
  → 401 auth expired?
      → Try refreshing the token (OAuth)
      → Refresh failed → rotate to next pool key
  → Success → continue normally

شروع سریع

اگر از قبل کلیدی در .env دارید هرمس خودآشکارش می‌کند به‌عنوان استخر ۱-کلیدی. برای بهره بردن از pooling کلیدهای بیشتری اضافه کنید:

# Add a second OpenRouter key
hermes auth add openrouter --api-key sk-or-v1-your-second-key

# Add a second Anthropic key
hermes auth add anthropic --type api-key --api-key sk-ant-api03-your-second-key

# Add an Anthropic OAuth credential (requires Claude Max plan + extra usage credits)
hermes auth add anthropic --type oauth
# Opens browser for OAuth login

بررسی استخرها:

hermes auth list

خروجی فهرست credential های هر ارائه‌دهنده با شماره و نشانگر ← روی credential فعلی است.

مدیریت تعاملی

‏hermes auth بدون زیرفرمان ویزارد تعاملی را اجرا می‌کند: وضعیت کامل استخرها و منویی شامل افزودن credential، حذف، ریست cooldown ها و ست کردن استراتژی چرخش per-provider. برای ارائه‌دهنده‌هایی که هم API key و هم OAuth دارند ‏(Anthropic، Nous، Codex) جریان افزودن نوع را می‌پرسد: ‏۱. کلید API از داشبورد ۲. ورود OAuth از طریق مرورگر.

۲ استراتژی‌های چرخش و بازیابی خطا

استراتژی‌های چرخش

از طریق hermes auth ← «Set rotation strategy» یا در config.yaml:

credential_pool_strategies:
  openrouter: round_robin
  anthropic: least_used
استراتژیرفتار
fill_first ‏(پیش‌فرض)اولین کلید سالم را تا اتمام مصرف و بعد سراغ بعدی
round_robinچرخش یکنواخت بین کلیدها بعد از هر انتخاب
least_usedهمیشه کلید با کمترین تعداد درخواست
randomانتخاب تصادفی بین کلیدهای سالم

بازیابی خطا

خطارفتارCooldown
۴۲۹ Rate Limitیک بار retry روی همان کلید ‏(گذری). دومین ۴۲۹ متوالی یعنی چرخش به کلید بعدی۱ ساعت
۴۰۲ Billing/Quotaفوراً چرخش به کلید بعدی۱ ساعت
۴۰۱ Auth Expiredاول refresh توکن OAuth امتحان می‌شود؛ فقط در شکست refresh چرخش۵ دقیقه
اتمام همهٔ کلیدهاFall through به fallback_model اگر پیکربندی شده—

timestamp های reset_at ی تأمین‌شده-توسط-ارائه‌دهنده بر این cooldown پیش‌فرض‌ها مقدم‌اند. فلگ has_retried_429 روی هر فراخوانی موفق API ریست می‌شود تا یک ۴۲۹ گذری چرخش trigger نکند.

استخرهای نقطهٔ پایانی سفارشی

نقاط پایانی سفارشی سازگار-با-OpenAI ‏(Together.ai، ‏RunPod، سرورهای محلی) استخر خودشان را می‌گیرند، کلیدخورده با نام endpoint از dict ی providers در config.yaml ‏(یا فهرست legacy ی custom_providers که خودکار migrate می‌شود). راه‌اندازی endpoint سفارشی با hermes model نامی مثل «Together.ai» یا «Local (localhost:8080)» تولید می‌کند که همان کلید استخر می‌شود؛ کلید دوم همان endpoint با hermes auth add اضافه می‌شود. استخرهای سفارشی در auth.json زیر credential_pool با پیشوند custom: ذخیره می‌شوند.

ورودی‌های خود-seed در هر بار load ی استخر به‌روز می‌شوند — حذف متغیر env یعنی هرس خودکار ورودی استخر. ورودی‌های دستی هرگز خودهرس نمی‌شوند. secrets قرضی runtime ‏(env vars، ارجاع‌های Bitwarden/Vault/keyring/systemd و مقادیر config سفارشی) در مرز auth.json فقط-ارجاع‌اند: هرمس مقدار حل‌شده را در حافظه برای run فعلی مصرف می‌کند ولی فقط متادیتا مثل source ref، ‏label، ‏status، ‏شمارنده‌ها و fingerprint ی غیر-برگشت‌پذیر ماندگار می‌کند. ورودی‌های دستی و وضعیت OAuth/device-code ی متعلق-به-هرمس توکن‌های ماندگاری که برای refresh لازم دارند را حفظ می‌کنند.

۳ اشتراک با زیرایجنت‌ها، ایمنی thread و معماری

Delegation و اشتراک زیرایجنت

وقتی ایجنت با delegate_task زیرایجنت spawn کند، استخر credential والد خودکار با فرزندان share می‌شود:

  • همان ارائه‌دهنده — فرزند استخر کامل والد را می‌گیرد و چرخش کلید روی rate limit ممکن می‌شود
  • ارائه‌دهندهٔ متفاوت — فرزند استخر همان ارائه‌دهنده را لود می‌کند ‏(اگر پیکربندی باشد)
  • بدون استخر — فرزند به تک کلید API ی به-ارث‌رسیده برمی‌گردد

یعنی زیرایجنت‌ها همان تاب‌آوری rate-limit والدی را بدون config اضافه دارند. اجارهٔ credential ی per-task تضمین می‌کند فرزندان موقع چرخش همزمان کلیدها با هم تصادم نکنند.

ایمنی thread

استخر credential برای همهٔ جهش‌های وضعیت ‏(select، mark_exhausted_and_rotate، try_refresh_current، mark_used) قفل threading مصرف می‌کند تا دسترسی همزمان وقتی گیت‌وی چند نشست چت را همزمان هندل می‌کند امن بماند.

معماری

نمودار کامل جریان داده را در فایل credential-pool-flow.excalidraw مخزن ببینید. استخر در لایهٔ حل ارائه‌دهنده یکپارچه می‌شود:

  1. ‏agent/credential_pool.py — مدیر استخر: storage، انتخاب، چرخش، ‏cooldown ها
  2. ‏hermes_cli/auth_commands.py — فرمان‌های CLI و ویزارد تعاملی
  3. ‏hermes_cli/runtime_provider.py — حل credential آگاه-از-استخر
  4. ‏run_agent.py — بازیابی خطا: ۴۲۹/۴۰۲/۴۰۱ ← چرخش استخر ← fallback

Storage

وضعیت استخر در ~/.hermes/auth.json زیر کلید credential_pool ذخیره می‌شود. ورودی قرض‌شده از منبع بیرونی کلیر خام را در auth.json نگه نمی‌دارد ‏(به‌جایش secret_source و secret_fingerprint)، ولی ورودی دستی عمداً افزوده‌شده به انبار credential ی هرمس توکن قابل‌ماندگاری دارد. استراتژی‌ها در config.yaml ذخیره می‌شوند نه auth.json.
