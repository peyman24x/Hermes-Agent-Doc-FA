خانه/قابلیت‌ها/پروتکل ACP

یکپارچگی میزبان ACP ‏(ACP Host Integration)

‏Hermes Agent می‌تواند به‌عنوان سرور ACP اجرا شود تا میزبان‌های سازگار-با-ACP از طریق stdio با هرمس حرف بزنند. ویرایشگرها می‌توانند رندر کنند:

  • پیام‌های گفتگو
  • فعالیت ابزار
  • diff های فایل
  • فرمان‌های ترمینال
  • پرامپت‌های تأیید
  • chunk های استریم‌شدهٔ تفکر / پاسخ

سایر میزبان‌ها می‌توانند با همین پروتکل رویدادهای همکاری را به هرمس مسیریابی کنند. ‏ACP وقتی انتخاب خوبی است که بخواهید هرمس هویت، ‏setup ی ارائه‌دهنده، حافظه، مهارت‌ها و ابزارهای فعلی‌اش را نگه دارد در حالی که اپ دیگری مالک transport ی گفتگوست.

۱ هرمس در حالت ACP چه چیزی expose می‌کند

هرمس با تول‌ست منتخب ‏hermes-acp طراحی‌شده برای گردش‌کارهای ویرایشگر اجرا می‌شود. شامل:

  • ابزارهای فایل: ‏read_file، ‏write_file، ‏patch، ‏search_files
  • ابزارهای ترمینال: ‏terminal، ‏process
  • ابزارهای وب/مرورگر
  • حافظه، ‏todo، جستجوی نشست
  • مهارت‌ها
  • execute_code و delegate_task
  • بینایی

عمداً چیزهایی که در UX ی معمول ویرایشگر جا نمی‌شوند — مثل تحویل پیام‌رسانی و مدیریت cronjob — مستثنی‌اند.

نصب

هرمس را عادی نصب کنید سپس extra ی ACP را از checkout نصب اضافه کنید:

cd ~/.hermes/hermes-agent && uv pip install -e '.[acp]'

این وابستگی agent-client-protocol را نصب و اینها را فعال می‌کند: ‏hermes acp، ‏hermes-acp و python -m acp_adapter.

راه‌اندازی سرور ACP

هرکدام از این‌ها هرمس را در حالت ACP شروع می‌کنند: ‏hermes acp · ‏hermes-acp · ‏python -m acp_adapter

هرمس به stderr لاg می‌زند تا stdout فقط برای ترافیک ACP ی JSON-RPC محفوظ بماند. برای بررسی‌های غیرتعاملی: ‏hermes acp --version و hermes acp --check.

ابزارهای مرورگر ‏(اختیاری)

ابزارهای مرورگر ‏(browser_navigate، ‏browser_click و…) به پکیج npm ی agent-browser و Chromium تکیه دارند که بخشی از wheel ی پایتون نیستند. با این نصبشان کنید:

hermes acp --setup-browser           # interactive (prompts before ~400 MB download)
hermes acp --setup-browser --yes     # accept the download non-interactively

این فرمان مستقل است؛ جریان terminal-auth ‏(hermes acp --setup) بعد از انتخاب مدل سؤال bootstrap ی مرورگر را هم می‌پرسد، پس بیشتر کاربران هرگز لازم نیست مستقیم --setup-browser بزنند. کارهایی که می‌کند:

  • Node.js ۲۶ را اگر غایب باشد در ~/.hermes/node/ نصب می‌کند
  • ‏agent-browser و @askjo/camofox-browser را با npm global داخل همان prefix نصب می‌کند ‏(--prefix ی npm به Node ی مدیریت‌شده-توسط-هرمسِ قابل-نوشتن-توسط-کاربر اشاره دارد؛ بدون sudo)
  • ‏Chromium ی Playwright را نصب یا Chrome/Chromium سیستمی آشکارشده را مصرف می‌کند

bootstrap ی idempotent است — اجرای دوباره سریع است و کار انجام‌شده را skip می‌کند.

۲ راه‌اندازی میزبان‌ها

کانال‌های Buzz ‏(relay bridge)

Buzz پلتفرم همکاری مبتنی-بر-Nostr برای انسان‌ها و ایجنت‌هاست. harness ی buzz-acp آن کانال‌های Buzz را روی stdio به هر ایجنت ACP ی وصل می‌کند:

Buzz relay <-- WebSocket --> buzz-acp <-- ACP over stdio --> Hermes Agent

این یک یکپارچگی transport است نه نصب دوم هرمس. زیرپروسهٔ launch‌شده توسط buzz-acp همان config، credential ها، حافظه، مهارت‌ها و وضعیت hermes ی همان host را مصرف می‌کند.

(این با runtime ی مدیریت‌شدهٔ Buzz Desktop فرق دارد که هرمس را محلیاً به‌عنوان harness ی preset spawn می‌کند. relay bridge برای پیوستن به کانال‌های Buzz به‌عنوان هویت ایجنتی است، معمولاً روی سرور.)

پیش‌نیازها:

  • نصب ACP و hermes acp --check بالا را کامل کرده باشید.
  • buzz-acp و CLI ی buzz را از مخزن Buzz بسازید ‏(cargo build --release -p buzz-acp).
  • یک keypair ی Nostr اختصاصی برای هرمس ضرب ‏(buzz-admin generate-key) و به‌عنوان عضو relay ثبت کنید ‏(buzz-admin add-member). هر ایجنت هویت خودش را needs — keypair انسانی را دوباره‌مصرف نکنید.
  • آن هویت را به کانال‌های مقصود Buzz اضافه کنید.

اجرای یک پل:

export BUZZ_RELAY_URL="wss://community.example.com"
export BUZZ_PRIVATE_KEY="..."
export BUZZ_API_TOKEN="..."
export BUZZ_ACP_AGENT_COMMAND="hermes"
export BUZZ_ACP_AGENT_ARGS="acp"

buzz-acp

‏BUZZ_API_TOKEN فقط وقتی لازم است که relay احراز هویت توکنی اجبار کند. کلید خصوصی یا توکن API را commit یا paste نکنید.

برای استقرار سروری پایدار buzz-acp را زیر service manager با همان کاربر سیستمی که مالک خانهٔ هرمس مقصود است اجرا کنید. ‏setup، تولید کلید، کشف کانال و گزینه‌های per-agent در README ی buzz-acp مستند است.

پل هر کانال Buzz ی که هویت هرمس عضوش باشد را آشکار و موقع افزوده شدن به کانال جدید خودکار مشترک می‌شود. پس عضویت کانال Buzz همان مرز دسترسی می‌ماند؛ هرمس نیازی به فهرست کانال جداگانه در config خودش ندارد.

برای expose کردن فعالیت ACP ی هرمس در Buzz Desktop ی owner مقدار زیر را اضافه کنید:

export BUZZ_ACP_RELAY_OBSERVER="true"

این فریم‌های observer رمزشدهٔ kind ۲۴۲۰۰ خطاب به owner ی ایجمنت منتشر می‌کند ‏(NIP-AO ی Buzz). ‏Desktop جریان زندهٔ چرخهٔ حیات، ابزار، پاسخ و مصرف را در Activity log ایجنت رندر می‌کند. relay این فریم‌ها را زودگذر تلقی می‌کند پس Desktop باید قبل از شروع نوبت آنلاین باشد؛ آرشیو observer ی محلی‌اش تاریخچهٔ پایدار سمت-owner است.

پل‌های headless درخواست‌های مجوز ACP را خودشان جواب می‌دهند چون ویرایشگری حاضر نیست دیالوگ تأیید نشان دهد — بخش نگه داشتن ایجنت‌های Buzz فقط-owner را ببینید. پل را اتوماسیون ممتاز تلقی کنید: حساب OS ی اختصاصی، محدود کردن کاربران Buzz ای که می‌توانند ایجنت را prompt کنند ‏(buzz-acp گیت respond ی فقط-owner با BUZZ_ACP_AGENT_OWNER دارد) و اعطای عضویت فقط در کانال‌هایی که انتظار کار هرمس را دارید.

VS Code

افزونهٔ ACP Client را نصب کنید. اتصال: پنل ACP Client را از Activity Bar باز ← از فهرست ایجنت‌های داخلی Hermes Agent را بردارید ← Connect و شروع به چت.

تعریف دستی از طریق settings ی VS Code زیر acp.agents:

{
  "acp.agents": {
    "Hermes Agent": {
      "command": "hermes",
      "args": ["acp"]
    }
  }
}

Zed

هرمس را به‌عنوان سرور ایجنت سفارشی در settings ی Zed پیکربندی کنید: Agent Panel را باز، سرور ایجنت سفارشی را با config زیر اضافه کنید و thread جدید external-agent ی Hermes را شروع کنید.

{
  "agent_servers": {
    "hermes-agent": {
      "type": "custom",
      "command": "hermes",
      "args": ["acp"]
    }
  }
}

پیش‌نیاز: اول credential های ارائه‌دهنده را با hermes model پیکربندی کنید یا در ~/.hermes/.env / ~/.hermes/config.yaml ست کنید.

JetBrains

افزونه‌ای سازگار-با-ACP مصرف و به hermes acp یا hermes-acp اشاره دهید.

Buzz Desktop

‏Buzz مقدار Hermes Agent را به‌عنوان runtime ی preset ارسال می‌کند. با نصب عادی هرمس، Buzz خودآشکارش می‌کند — Settings ← Runtimes را باز کنید و هرمس زیر runtimes تان ظاهر می‌شود.

اگر کشف شکست خورد ‏(نصب‌های قدیمی) مطمئن شوید launcher ی ACP روی PATH ی login-shell حل می‌شود:

command -v hermes-acp || command -v hermes

نصب‌های اخیر هر دو launcher ی hermes و hermes-acp را در ~/.local/bin می‌نویسند؛ ‏hermes update مقدار hermes-acp را به نصب‌های قدیمی اضافه می‌کند. fallback دستی: فرمان ایجنت Buzz را hermes با args ی [acp] پیکربندی کنید.

انتخاب‌گر مدل

‏Buzz Desktop ‏(v0.5.1+) منوی کامل مدل‌های هرمس را در settings ی runtime ایجنت رندر می‌کند. فهرست از خود هرمس روی ACP می‌آید: هر مدلی از ارائه‌دهنده‌هایی که در هرمس احراز کرده‌اید را نشان می‌دهد ‏(همان موجودی پشت hermes model و فرمان ‎/model‎)، پس نبود مدلی از منو یعنی provider اش در سمت هرمس credential ندارد.

ID های ورودی به شکل provider:model ‏(مثل openrouter:z-ai/glm-5.1) یا custom:<name>:<model> برای نقاط پایانی سفارشی سازگار-با-OpenAI تعریف‌شده در config.yaml اند. انتخاب مدل به نشست همان ایجنت اعمال می‌شود؛ پیش‌فرض سراسری هرمس‌تان را عوض نمی‌کند — آن کار با hermes model.

نگه داشتن ایجنت‌های Buzz فقط-owner

‏Buzz هر ایجنتی را با «Who can talk to this agent» روی Owner only می‌سازد. وقتی runtime هرمس است همین‌جا رهایش کنید.

دو رفتار روی این مسیر ترکیب می‌شوند. تول‌ست hermes-acp شامل terminal و execute_code است و پل ACP ی Buzz درخواست‌های مجوز هرمس را خودش با allow_once جواب می‌دهد نه اینکه surface کند. پس ایجنت هرمس در Buzz بدون پرامپت روی host فرمان شل اجرا می‌کند — یکی را برای rm -rf روی دایرکتوری scratch فرستادم و حذفش کرد، بدون هیچ پرامپتی.

انتخاب Anyone همان دسترسی شل را به هر نویسنده‌ای که به کانال برسد می‌دهد. Buzz موقع انتخابش هشدار نمی‌دهد.

هیچ‌کدام از mitigation های بدیهی امروز جواب نمی‌دهند:

  • ‏approvals.mode: manual باعث می‌شود هرمس درخواست مجوز بدهد ولی Buzz خودکار approve و فرمان همچنان اجرا می‌شود.
  • platform_toolsets.acp تول‌ست ACP را تنگ نمی‌کند، پس نمی‌توان با آن terminal را انداخت.

‏!shutdown از طرف owner ایجنت را در هر حالتی متوقف می‌کند و Buzz آن فرمان را از بقیه نادیده می‌گیرد.

۳ پیکربندی، credential ها و متغیرهای میزبان

پیکربندی و credential ها

حالت ACP همان پیکربندی هرمسِ CLI را مصرف می‌کند: ‏~/.hermes/.env، ‏~/.hermes/config.yaml، ‏~/.hermes/skills/ و ~/.hermes/state.db.

حل ارائه‌دهنده از resolver ی runtime عادی هرمس استفاده می‌کند، پس ACP ارائه‌دهنده و credential های فعلی‌تان را به ارث می‌برد. هرمس همچنین روش auth ی ترمینال ‏(--setup) را برای کلاینت‌های ACP ی اولین-اجرا advertise می‌کند که setup ی تعاملی مدل/ارائه‌دهنده را باز می‌کند.

یکپارچگی میزبان

این متغیرها توسط پروسهٔ میزبان ACP ‏(یک ویرایشگر یا harness ی ایجنت دیگر) روی زیرپروسهٔ هرمسِ spawn شده ست می‌شوند. پیکربندی کاربر نیستند — دستی در .env یا config.yaml ست نکنید.

متغیرمقداراثر
‏HERMES_ACP_SKIP_CONFIGURED_MCP1رد شدن از شروع سرورهای MCP ی پیکربندی-سراسری config.yaml قبل از شروع حلقهٔ JSON-RPC ی ACP.

هرمس معمولاً قبل از ورود به حلقهٔ JSON-RPC ی ACP همهٔ سرورهای MCP ی config.yaml را شروع می‌کند. میزبانی که خودش MCP را مالک است — و سرورهای نشست را صریحاً از طریق session/new پاس می‌دهد — به آن startup سراسری نیاز ندارد وگرنه سرور MCP ی کند یا تعاملی نامرتبط initialize را به تأخیر می‌انداخت. ست کردن نشانگر دقیقاً به ۱ اجازه می‌دهد چنین میزبانی آن را skip کند.

فقط کشف سراسری config.yaml رد می‌شود. سرورهای MCP ی تأمین‌شده توسط نشست ACP از طریق session/new همچنان ثبت می‌شوند، پس میزبان هیچ قابلیتی که خواسته را از دست نمی‌دهد. هر مقدار دیگر ‏(unset، ‏خالی، ۰، false) رفتار پیش‌فرض را نگه می‌دارد تا رشته‌ای truthy-نما نتواند بی‌سروصدا MCP را خاموش کند.

رفتار نشست

نشست‌های ACP تا سرور در حال اجراست توسط مدیر نشست درون-حافظه‌ای adapter ردیابی می‌شوند. هر نشست ذخیره می‌کند: شناسهٔ نشست، ‏دایرکتوری کاری، ‏مدل انتخابی، تاریخچهٔ فعلی گفتگو و cancel event. ‏AIAgent ی زیرین همچنان مسیرهای ماندگاری/لاg عادی هرمس را مصرف می‌کند ولی list/load/resume/fork ی ACP به پروسهٔ سرور ACP ی فعلاً-در-حال-اجرا scope شده‌اند.

رفتار دایرکتوری کاری

نشست‌های ACP مقدار cwd ی ویرایشگر را به task ID هرمس bind می‌کنند تا ابزارهای فایل و ترمینال نسبت به workspace ی ویرایشگر اجرا شوند نه cwd ی پروسهٔ سرور.

۴ تأییدها

فرمان‌های ترمینال خطرناک را می‌توان به‌عنوان پرامپت تأیید به ویرایشگر برگرداند. گزینه‌های تأیید ACP ساده‌تر از جریان CLI اند:

  • allow once
  • allow always
  • deny

اینکه واقعاً پرامپت ببینید به میزبان بستگی دارد. میزبان آزاد است درخواست را برنامه‌نویسی‌شده جواب دهد به‌جای نمایش به شما، در این صورت این گزینه‌ها روی سیم وجود دارند ولی هرگز به انسان نمی‌رسند. ‏Buzz Desktop همین کار را می‌کند، پس آن مسیر را فارغ از تنظیم approvals تان execution ی بی‌نظارت تلقی کنید.

روی timeout یا خطا، پل تأیید درخواست را deny می‌کند.

auto-approval ی ویرایش-محور scope شده-به-نشست

‏ACP طبقهٔ سومی بین allow once و allow always expose می‌کند: Allow for session. برداشتنش از پرامپت مجوز ویرایشگر، تأیید را فقط داخل نشست ACP ی فعلی ثبت می‌کند — هر فرمان منطبق بعدی در همان نشست بدون پرامپت عبور می‌کند ولی نشست ACP ی جدید ‏(یا ری‌استارت ویرایشگر) تخته را پاک و اولین بار دوباره prompt می‌کند.

گزینهبرچسب ویرایشگرScopeماندگار بین ری‌استارت‌ها؟
allow_onceAllow onceهمین یک فراخوانی ابزارنه
allow_sessionAllow for sessionهمهٔ فراخوانی‌های منطبق در این نشست ACPنه — پایان نشست پاک می‌شود
allow_alwaysAllow alwaysهمهٔ نشست‌های آیندهبله ‏(در allowlist ی دائمی هرمس نوشته می‌شود)
denyDenyهمین یک فراخوانی ابزارنه

‏allow_session پیش‌فرض درست برای گردش‌کار ویرایشگری است که ایجنت را در طول یک تسک اعتماد می‌کنید ولی نمی‌خواهید ورودی allowlist بلندعمر بدهید. مصالحه امنیتی ساده است: هرچه scope پهن‌تر، ویرایشگر کمتر مزاحمتان می‌شود و ایجنت بدرفتار ‏(یا prompt injection) بیشتر می‌تواند پیش از متوجه شدن‌تان خرابکاری کند. برای فرمان‌های ناآشنا از allow_once شروع؛ بعد از دیدن چند اجرای صحیح الگوی واحد به allow_session ارتقا دهید؛ ‏allow_always را برای فرمان‌های واقعاً idempotent ی همیشه-مورد-اعتماد ‏(مثل git status) نگه دارید.

پل ACP این گزینه‌ها را روی معناشناسی تأیید داخلی هرمس نگاشت می‌کند — allow_always مثل CLI ورودی allowlist دائمی می‌نویسد و allow_session فقط cache ی تأیید درون-پروسه‌ای نشست ACP ی فعلی را تحت تأثیر می‌گذارد.

۵ عیب‌یابی

ایجنت ACP در ویرایشگر ظاهر نمی‌شود

بررسی کنید:

  • برای توسعهٔ دستی/محلی، فرمان میزبان به hermes acp اشاره کند.
  • هرمس نصب و روی PATH باشد.
  • extra ی ACP نصب باشد ‏(cd ~/.hermes/hermes-agent && uv pip install -e '.[acp]').

ACP شروع می‌شود ولی فوراً خطا می‌دهد

این بررسی‌ها را امتحان کنید:

hermes acp --version
hermes acp --check
hermes doctor
hermes status

credential های جامانده

حالت ACP از setup ی موجود هرمس مصرف می‌کند. با این credential ها را پیکربندی کنید:

hermes model

یا با ویرایش ~/.hermes/.env. جریان terminal-auth ‏(hermes acp --setup) هم می‌تواند setup ی تعاملی ارائه‌دهنده/مدل را trigger کند.
