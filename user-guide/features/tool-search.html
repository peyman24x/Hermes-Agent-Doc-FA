جستجوی ابزار ‏(Tool Search)

وقتی سرورهای MCP یا ابزارهای پلاگینِ غیر-هستهٔ زیادی به یک نشست وصل باشند، اسکیمای JSON شان می‌تواند در هر نوبت کسر قابل‌توجهی از پنجرهٔ زمینه را بخورد — حتی وقتی فقط چند موردشان به درخواست واقعی کاربر مربوط است.

جستجوی ابزار لایهٔ افشای-تدریجیِ انتخابی هرمس برای همین مسئله است. با فعال شدن، ابزارهای MCP و پلاگین در آرایهٔ ابزارهای قابل-مشاهده-برای-مدل با سه ابزار پُل جایگزین می‌شوند و مدل، اسکیمای هر ابزار مشخص را بر تقاضا بارگذاری می‌کند.

📌 ابزارهای داخلی هرمس هرگز به تعویق نمی‌افتند

ابزارهایی که مجموعهٔ قابلیت هستهٔ هرمس را می‌سازند ‏(terminal، ‏read_file، ‏write_file، ‏patch، ‏search_files، ‏todo، ‏memory، ‏browser_*، ‏web_search، ‏web_extract، ‏clarify، ‏execute_code، ‏delegate_task، ‏session_search و بقیهٔ _HERMES_CORE_TOOLS) همیشه مستقیم بارگذاری می‌شوند. فقط ابزارهای MCP و ابزارهای غیر-هستهٔ پلاگین واجد شرایط تعویق‌اند.

۱ نحوهٔ کار

وقتی جستجوی ابزار برای یک نوبت فعال شود، مدل به‌جای ابزارهای به-تعویق-افتاده سه ابزار تازه می‌بیند:

tool_search(query, limit?)     — search the deferred-tool catalog
tool_describe(name)            — load the full schema for one tool
tool_call(name, arguments)     — invoke a deferred tool

یک تعامل معمول چنین است:

Model: tool_search("create a github issue")
  → { matches: [{ name: "mcp_github_create_issue", ... }, ...] }
Model: tool_describe("mcp_github_create_issue")
  → { parameters: { type: "object", properties: { ... } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }

وقتی مدل tool_call را صدا می‌زند، هرمس پیچ پُل را باز می‌کند و ابزار زیرین را دقیقاً مثل وقتی که مدل خودش مستقیم صداش زده بود دیسپچ می‌کند. هوک‌های pre-tool-call، گاردها، پرامپت‌های تأیید و هوک‌های post-tool-call همه روی نام ابزار واقعی اجرا می‌شوند — نه روی tool_call. فید فعالیت در CLI و گیت‌وی هم بازمی‌شود تا ابزار زیرین را ببینید نه پُل را.

۲ چه وقت فعال می‌شود؟

جستجوی ابزار از افشای طبقه‌بندی‌شده استفاده می‌کند: حضور هر ابزار قابل-تعویق ‏(MCP/پلاگین) پُل را فعال می‌کند؛ چیزی که با اندازهٔ کاتالوگ مقیاس می‌گیرد این است که چه مقدار از کاتالوگ مرئی بماند، نه اینکه اسکیماها به تعویق بیفتند یا نه.

طبقهشرطمدل چه می‌بیند
۰بدون ابزار MCP/پلاگینهمهٔ ابزارها eager، بدون پُل. عبور مستقیم.
۱فهرستِ کاتالوگ قابل-تعویق در بودجه جا می‌شودپُل + مانیفست مهارت‌گونه از هر ابزار قابل-تعویق ‏(نام + توضیح کوتاه؛ بالاتر از بودجه فقط-نام). تنزل per server است: وقتی یک سرور بزرگ ‏(Cloudflare) کنار سرورهای کوچک ‏(Linear) وصل باشد، سرورهای کوچک فهرست هر-ابزار خودشان را نگه می‌دارند و فقط سرور بزرگ به یک خط خلاصه جمع می‌شود.
۲فهرست هر-ابزار حتی فقط-نام هم برای همهٔ سرورها از بودجه بزند بیرون ‏(مثلاً سطح API ی تخت Cloudflare تنها: حدود ۳٬۳۰۰ ابزار که نام‌هایشان ~۳۲ هزار توکن است)پُل خالی + خلاصهٔ یک-خط-برای-هر-سرور ‏(نام سرور + تعداد ابزار)، تا مدل بداند کدام حوزه‌ها در دسترس‌اند؛ ابزارهای منفرد فقط از طریق tool_search کشف می‌شوند.

بودجهٔ فهرست برابر min(threshold_pct٪ از context، listing_max_tokens) است. تصمیم هر بار که آرایهٔ ابزارها ساخته می‌شود دوباره ارزیابی می‌شود، پس اضافه/حذف کردن سرورهای MCP وسط نشست، نشست را در مونتاژ بعدی بین طبقه‌ها جابه‌جا می‌کند.

۳ پیکربندی

yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 20
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
کلیدپیش‌فرضمعنا
enabledauto‏auto/on هرگاه دست‌کم یک ابزار قابل-تعویق موجود باشد فعال می‌شوند؛ ‏off کاملاً غیرفعال می‌کند ‏(همه‌چیز eager می‌ماند).
threshold_pct5بودجهٔ فهرست به درصد طول زمینهٔ مدل فعال. بازهٔ ۰–۱۰۰.
search_default_limit5تعداد نتایج وقتی مدل بدون limit صدا بزند.
max_search_limit20سقف سخت مقداری که مدل می‌تواند با limit بخواهد. بازهٔ ۱–۵۰.
listingautoمانیفست مهارت‌گونهٔ هر ابزار قابل-تعویق ‏(نام + جملهٔ اول توضیح، ≤۶۰ نویسه، گروه‌بندی بر اساس سرور MCP) داخل توضیح پُلِ tool_search تعبیه می‌شود. ‏auto اگر در بودجه بگنجاند آن را می‌گذارد ‏(fallback به فقط-نام و بعد به خلاصهٔ سرورِ طبقهٔ ۲)؛ ‏on/off اجبار می‌کنند.
listing_max_tokens4000سقف مطلق فهرست تعبیه‌شده فارغ از اندازهٔ زمینه. بازهٔ ۲۰۰–۶۰۰۰۰. کاتالوگ‌های بزرگ به فقط-نام یا خلاصهٔ هر-سرور تنزل می‌یابند و اسکیماهای کامل از طریق جستجو در دسترس می‌مانند.

چرا این فهرست وجود دارد

بدون آن قابلیت‌های به-تعویق-افتاده نامرئی‌اند — بنچمارک زنده نشان داد مدل‌ها به‌جای صدا زدن tool_search ابزارهای هستهٔ مرئی را جانشین می‌کنند ‏(اجرای gh در ترمینال به‌جای جستجوی ابزار GitHub ی به-تعویق-افتاده) یا وجود نداشتن قابلیت را اعلام می‌کنند. فهرست الگوی skills را روی ابزارها اعمال می‌کند: هر قابلیتی همیشه با نام کشف‌پذیر می‌ماند، در حالی که اسکیماهای کامل پارامتر همچنان به تعویق افتاده‌اند. اگر مدل نام دقیق ابزار را در فهرست ببیند می‌تواند از tool_search عبور و مستقیم به tool_describe برود و یک رفت‌وبرگشت صرفه کند.

می‌توانید شکل بولی قدیمی را هم به کار ببرید:

yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}

۴ چه وقت نباید استفاده کرد

جستجوی ابزار یک هزینهٔ ثابت هر-نوبتِ توکن ‏(اسکیمای سه ابزار پُل + فهرست کاتالوگ) و دست‌کم یک رفت‌وبرگشت اضافه روی ابزارهای سرد ‏(describe ← call) را در برابر صرفهٔ اسکیماهای به-تعویق-افتاده معامله می‌کند. در طبقهٔ ۱ فهرست هر قابلیت را مرئی نگه می‌دارد پس رفت‌وبرگشت کشف معمولاً حذف می‌شود — مدل مستقیم به tool_describe می‌رود. بنچمارک زنده نشان داد حالت فهرست موفقیت تسکِ بارگذاری eager را جواب می‌دهد ولی کمتر از پُل خالی هزینه دارد.

اگر رفتار قدیمیِ همیشه-eager را برای تول‌ست کوچک می‌خواهید enabled: off کنید.

۵ مصالحه‌هایی که از بین نمی‌روند

اینها از ناورداِ تمامیت کش-پرامپت می‌آیند — ذاتیِ هر طراحی افشای-تدریجی‌اند، نه مخصوص این پیاده‌سازی:

  • یک رفت‌وبرگشت اضافه روی ابزارهای سرد. اولین باری که مدل به ابزاری قابل-تعویق نیاز پیدا کند، یکی دو فراخوانی مدل اضافه برای پیدا و بارگذاری schema خرج می‌کند. صرفهٔ توکن در سمت ایستا واقعی است ولی بخشی از آن در زمان اجرا پس داده می‌شود.
  • بدون منفعت کش روی اسکیماهای به-تعویق-افتاده. نتیجهٔ بارگذاری‌شدهٔ tool_describe وارد تاریخچهٔ گفتگو می‌شود ‏(پس در نوبت‌های بعدی کش می‌گیرد) اما هرگز از پیشوند کشِ پرامپت سیستمی بهره نمی‌برد.
  • وابستگی به کیفیت مدل. جستجوی ابزار فرض می‌کند مدل بتواند برای ابزاری که می‌خواهد یک کوئری جستجوی معقول بنویسد. مدل‌های کوچک‌تر این را کمتر خوب انجام می‌دهند؛ اعداد منتشرشدهٔ Anthropic ‏(۴۹٪ ← ۷۴٪ روی Opus 4 با و بدون جستجوی ابزار) هم upside را نشان می‌دهد هم اینکه ~۲۶ واحد دقت همچنان شکست بازیابی است.
  • ویرایش تول‌ست کش را باطل می‌کند. اضافه/حذف ابزار وسط نشست توضیحات ابزارهای پُل ‏(که تعداد ابزارهای قابل-تعویق را حمل می‌کنند) و کاتالوگ را عوض می‌کند پس کش پرامپت باطل می‌شود. همان مصالحهٔ هر ویرایش تول‌ست.

۶ جزئیات پیاده‌سازی

  • بازیابی: BM25 روی نام توکنیزه‌شدهٔ ابزار + توضیح + نام پارامترها. وقتی BM25 هیچ hit مثبت‌امتیازی برگرداند به تطبیق substring تحت‌اللفظی روی نام ابزار fallback می‌شود که از حالت‌های انحطاطیِ صفر-IDF محافظت می‌کند ‏(مثلاً جستجوی "github" در کاتالوگی که نام هر ابزارش «github» دارد).
  • کاتالوگ بین نوبت‌ها stateless است. در هر مونتاژ از فهرست فعلی tool-defs از نو ساخته می‌شود — بدون Map کلیدخورده-با-نشست. این از ردهٔ باگ‌هایی جلوگیری می‌کند که کاتالوگ ذخیره‌شده با registry زندهٔ ابزار ناهمگام شود.
  • کاتالوگ به تول‌ست‌های نشست محدود است. ‏tool_search، ‏tool_describe و tool_call فقط ابزارهایی را می‌بینند و صدا می‌زنند که نشست واقعاً گرفته است. یک زیرایجنت، کارگر کانبان یا نشست گیت‌ویِ محدود به زیرمجموعه‌ای از تول‌ست‌ها نمی‌تواند با پُل ابزاری بیرون آن زیرمجموعه را کشف یا صدا بزند — کاتالوگ قابل-تعویق، برشِ قابل-تعویقِ همان تول‌ست‌های فعال/غیرفعالِ خود نشست است نه registry کل پروسه.
  • بدون sandbox ی JS. هرمس حالت ساده‌تر «structured tools» را به کار می‌برد ‏(search / describe / call به‌صورت توابع ساده). «code mode» با sandbox ی JS که بعضی پیاده‌سازی‌های دیگر ارائه می‌دهند سطح حملهٔ بزرگی دارد؛ ما از آن عبور می‌کنیم.
