داشبورد وب

داشبورد وب یک رابط مرورگری برای مدیریت نصب Hermes Agent شماست. به‌جای ویرایش فایل‌های YAML یا اجرای فرمان‌های CLI، می‌توانید تنظیمات را پیکربندی، کلیدهای API را مدیریت و نشست‌ها را از یک رابط وب تمیز مانیتور کنید.

💡 نکته

احراز حالت-میزبانی از OAuth مربوط به Nous Portal استفاده می‌کند؛ اگر همچنین می‌خواهید داشبورد با یک بک‌اند واقعی حرف بزند ‏hermes setup --portal دروازهٔ مدل و ابزار را هم سیم‌کشی می‌کند. بخش Nous Portal را ببینید.

۱ شروع سریع

bash
hermes dashboard

این یک سرور وب محلی شروع و ‏http://127.0.0.1:9119 را در مرورگرتان باز می‌کند. داشبورد کلاً روی ماشین شما اجرا می‌شود — هیچ داده‌ای از localhost خارج نمی‌شود.

گزینه‌ها

فلگپیش‌فرضتوضیح
--port9119پورت اجرای سرور وب
--host127.0.0.1آدرس bind
--no-open—مرورگر خودکار باز نشود
--insecureخاموشDeprecated / no-op. قبلاً احراز را روی bind غیر-loopback دور می‌زد؛ دیگر احراز را غیرفعال نمی‌کند — bind عمومی همیشه ارائه‌دهندهٔ احراز ‏(رمز یا OAuth) می‌خواهد
--isolatedخاموشوقتی از یک alias پروفایل لانچ شود ‏(worker dashboard)، به‌جای مسیریابی به داشبورد ماشین یک سرور اختصاصی به‌ازای-پروفایل اجرا کند
bash
# پورت سفارشی
hermes dashboard --port 8080

# بایند به همهٔ interface ها (روی شبکه‌های مشترک با احتیاط)
hermes dashboard --host 0.0.0.0

# شروع بدون بازکردن مرورگر
hermes dashboard --no-open

۲ مدیریت چند پروفایل

داشبورد یک سطح مدیریت سطح-ماشین است: یک سرور همهٔ پروفایل‌های روی ماشین را مدیریت می‌کند. یک سوییچر پروفایل در نوار کناری ‏(هر وقت بیش از یک پروفایل موجود باشد دیده می‌شود) تعیین می‌کند صفحات مدیریتی چه پروفایلی را بخوانند و بنویسند — Config، API Keys، Skills، ‏MCP، ‏Models و تب Chat همه از آن پیروی می‌کنند. وقتی پروفایلی غیر از مالِ خودِ داشبورد انتخاب شده باشد، بنر کهربایی‌رنگ نام پروفایلِ تحت-مدیریت را نشان می‌دهد تا هدف نوشتن هرگز مبهم نباشد.

انتخاب در URL زندگی می‌کند ‏(?profile=<name>)، پس deep link هایی مثل ‏http://127.0.0.1:9119/skills?profile=worker با انتخاب پیش‌فرضِ سوییچر فرود می‌آیند و از refresh جان سالم می‌برند.

لانچ داشبورد از alias یک پروفایل به‌جای شروع سرور دوم به داشبورد ماشین مسیریابی می‌شود:

bash
worker dashboard
# → در حال اجرا: مرورگر روی ?profile=worker باز می‌شود
# → در حال اجرا نیست: داشبورد ماشین با "worker" پیش‌انتخاب‌شده شروع می‌شود

‏--isolated را بدهید تا انصراف دهید و سروری اختصاصی محدود-به-آن-پروفایل اجرا کنید ‏(رفتار قبل از یکسان‌سازی — وقتی مفید است که عمداً داشبورد پروفایل‌های مختلف را با احراز متفاوت expose کنید).

تب Chat هم از سوییچر پیروی می‌کند: چت scoped فرزند PTY خودش را با ‏HERMES_HOME پروفایل انتخاب‌شده spawn می‌کند، پس گفتگو با مدل، مهارت‌ها، حافظه و تاریخچهٔ نشست همان پروفایل اجرا می‌شود. تغییر پروفایل یک نشست ترمینال تازه شروع می‌کند.

چه چیزی به‌ازای-پروفایل می‌ماند و سوییچر جذبش نمی‌کند: پروسه‌های گیت‌وی ‏(با ‏hermes -p <name> gateway … مدیریتشان کنید)، دیتابیس نشست هر پروفایل و زمان‌بندهای کرون ‏(صفحهٔ Cron خودش با فیلتر مخصوص بین پروفایل‌ها تجمیع می‌کند).

۳ پیش‌نیازها

نصب پیش‌فرض ‏hermes-agent پشتهٔ HTTP یا helper ‏PTY را حمل نمی‌کند — آن‌ها extras اختیاری‌اند. داشبورد وب به FastAPI و Uvicorn نیاز دارد ‏(extra ‏web). تب Chat هم برای spawn کردن TUI جاسازی‌شده پشت شبه‌ترمینال به ‏ptyprocess نیاز دارد ‏(extra ‏pty روی POSIX). هر دو را نصب کنید:

bash
cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"

‏extra ‏web مقدار FastAPI/Uvicorn را می‌کشد؛ ‏pty مقدار ‏ptyprocess ‏(POSIX) یا ‏pywinpty ‏(ویندوز native — توجه: خود TUI جاسازی‌شده همچنان WSL می‌خواهد) را. ‏cd ~/.hermes/hermes-agent && uv pip install -e ".[all]" هر دو extra را شامل است و ساده‌ترین مسیر است اگر پیام‌رسانی/صوت/و... هم می‌خواهید.

وقتی ‏hermes dashboard را بدون وابستگی‌ها اجرا کنید می‌گوید چه نصب کنید. اگر فرانت هنوز build نشده و ‏npm موجود باشد، اولین launch خودکار build می‌شود.

تب Chat جزء هر launch ‏hermes dashboard است — پنل چت جاسازی‌شدهٔ مرورگر ‏(اجرای TUI روی PTY/WebSocket) همیشه بدون فلگ اضافه در دسترس است.

۴ صفحات

Status ‏(وضعیت)

صفحهٔ فرود نمای زندهٔ نصب شما را نشان می‌دهد:

  • نسخهٔ ایجنت و تاریخ ریلیز
  • وضعیت گیت‌وی — running/stopped، ‏PID، پلتفرم‌های متصل و وضعیت‌شان
  • نشست‌های فعال — تعداد نشست‌های فعال در ۵ دقیقهٔ اخیر
  • نشست‌های اخیر — فهرست ۲۰ نشست آخر با مدل، تعداد پیام، مصرف توکن و پیش‌نمایش گفتگو

صفحهٔ وضعیت هر ۵ ثانیه خودکار refresh می‌شود.

بنر فشار منابع

وقتی میزبان کمبود حافظه یا دیسک دارد بنری بالای داشبورد ظاهر می‌شود ‏(با همان poll وضعیت تغذیه می‌شود — بدون درخواست اضافه):

  • «Your agent is almost out of memory and may restart» — حافظهٔ موجود سیستم به سطح elevated ‏(< ‏۱۲۸ MiB یا < ‏۱۵٪) یا critical ‏(< ‏۶۴ MiB یا < ‏۵٪) رسیده، طبق نمونه‌گیری ضربان ۳۰ثانیه‌ای گیت‌وی.
  • «Your agent restarted unexpectedly, most likely because it ran out of memory» — دفتر چرخهٔ حیات خروج ناسالم زیر فشار حافظه در بوت قبل را ثبت کرده ‏(یک OOM kill مشکوک).
  • هشدارهای دیسک — والوم نگهدارندهٔ ‏~/.hermes تقریباً پر است ‏(elevated زیر ۵۱۲ MB آزاد، ‏critical زیر ۲۵۶ MB آزاد).

در هر لحظه فقط شدیدترین هشدار فعال نمایش داده می‌شود ‏(دیسک critical > حافظه critical > ری‌استارت OOM > دیسک elevated > حافظه elevated). رد کردن‌ها به بوت فعلی گیت‌وی scope دارند: ردکردن یک هشدار بعدیِ فعال را سطح می‌آورد، ری‌استارت گیت‌وی یا تشدید ‏(elevated ← critical) آن را دوباره باز می‌کند و ضربان کهنه به‌جای alert کاذب هیچ رندر نمی‌کند.

Chat ‏(چت)

تب Chat کل TUI هرمس ‏(همان رابطی که از ‏hermes --tui می‌گیرید) را مستقیم داخل مرورگر جاسازی می‌کند. هر کاری که در TUI ترمینال می‌کنید — فرمان‌های اسلش، انتخاب‌گر مدل، کارت‌های فراخوانی-ابزار، استریم مارک‌داون، پرامپت‌های clarify/sudo/تأیید، تم‌سازی — اینجا عیناً کار می‌کند، چون داشبورد باینری واقعی TUI را اجرا و خروجی ANSI‌اش را با xterm.js با رندرر WebGL برای چیدمان سلولی پیکسل‌به‌پیکسل رندر می‌کند.

نحوهٔ کار:

  • ‏/api/pty یک WebSocket با توکن نشست داشبورد احراز می‌کند
  • سرور ‏hermes --tui را پشت یک شبه‌ترمینال POSIX spawn می‌کند
  • کلیدهای فشرده‌شده به PTY می‌روند؛ خروجی ANSI به مرورگر استریم می‌شود
  • رندرر WebGL ‏xterm.js هر سلول را روی شبکهٔ integer-pixel نقاشی می‌کند؛ ردیابی موس ‏(SGR 1006)، کاراکترهای عریض ‏(Unicode 11) و گلیف‌های خط‌کشی همه native رندر می‌شوند
  • تغییر اندازهٔ پنجره مرورگر TUI را با addon ‏@xterm/addon-fit resize می‌کند

ازسرگیری نشست موجود: از تب Sessions آیکون play ‏(▶) کنار هر نشستی را کلیک کنید. به ‏/chat?resume=<id> می‌پرد و TUI را با ‏--resume لانچ و کل تاریخچه را لود می‌کند.

سوییچر نشست ‏(ریل راست): تب Chat فهرست گفتگوی سبک ChatGPT خودش را در ریل نازکی کنار ترمینال دارد تا بدون ترک صفحه بین گفتگوها جابه‌جا شوید. ریل، انتخاب‌گر مدل را بالای فهرست نشست می‌گذارد؛ ترمینال بیشتر صفحه را می‌گیرد. فهرست جدیدترین نشست‌های پروفایل فعال را نشان می‌دهد — عنوان ‏(fallback به پیش‌نمایش پیام)، زمان نسبی آخرین فعالیت، تعداد پیام و کانال مبدأ برای نشست‌های غیر-CLI. کلیک روی هر ردیف همان‌جا resume‌اش می‌کند ‏(ترمینال با تاریخچهٔ آن گفتگو respawn می‌شود)؛ نشست فعال هایلایت است. New chat نشست تازه می‌سازد و کنترل refresh فهرست را دوباره می‌کشد. ریل برای سوئیچ فقط-خواندنی است — delete، rename، export و cleanup انبوه همچنان در تب Sessions زندگی می‌کنند. روی صفحه‌های باریک به پنل slide-over جمع می‌شود.

پیش‌نیازها:

  • ‏Node.js ‏(همان الزام ‏hermes --tui؛ بستهٔ TUI در اولین launch ساخته می‌شود)
  • ‏ptyprocess — توسط extra ‏pty نصب می‌شود ‏(cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"، یا ‏[all] هر دو را می‌پوشاند)
  • کرنل POSIX ‏(لینوکس، ‏macOS یا WSL2). پنل ترمینال ‏/chat مشخصاً PTY ‏POSIX می‌خواهد — ‏Python ویندوز native معادلی ندارد، پس روی نصب ویندوز native بقیهٔ داشبورد ‏(نشست‌ها، job ها، متریک‌ها، ویرایشگر config) کار می‌کند ولی تب ‏/chat بنری نشان می‌دهد که برای آن قابلیت از WSL2 استفاده کنید.

تب مرورگر را ببندید و PTY روی سرور تمیز برداشت می‌شود. بازکردن مجدد نشست تازه spawn می‌کند.

برای اشاره‌دادن ‏Hermes Desktop به داشبوردی روی ماشین دیگر به‌جای بک‌اند همراه‌بسته‌اش، بخش «اتصال Hermes Desktop به بک‌اند راه‌دور» پایین را ببینید.

Config ‏(پیکربندی)

ویرایشگر فرم‌محور برای config.yaml. هر ۱۵۰+ فیلد پیکربندی از ‏DEFAULT_CONFIG خودکار کشف و در دسته‌های تب‌بندی‌شده سازمان می‌یابند:

  • model — مدل پیش‌فرض، ارائه‌دهنده، base URL، تنظیمات استدلال
  • terminal — بک‌اند ‏(local/docker/ssh/modal)، timeout، ترجیحات شل
  • display — skin، پیشرفت ابزار، نمایش resume، تنظیمات spinner
  • agent — حداکثر iteration ها، timeout گیت‌وی، service tier
  • delegation — سقف زیرایجنت، سطح استدلال
  • memory — انتخاب ارائه‌دهنده، تنظیمات تزریق زمینه
  • approvals — حالت تأیید فرمان خطرناک ‏(smart/manual/off)
  • و بیشتر — هر بخش config.yaml فیلدهای فرم متناظر دارد

فیلدهای دارای مقادیر معتبر شناخته ‏(بک‌اند terminal، skin، حالت approval و...) به‌صورت dropdown رندر می‌شوند. بولین‌ها toggle هستند. بقیه ورودی متنی.

اقدامات:

  • Save — تغییرات را فوراً در config.yaml می‌نویسد
  • Reset to defaults — همهٔ فیلدها را به مقادیر پیش‌فرض برمی‌گرداند ‏(تا Save بزنید ذخیره نمی‌شود)
  • Export — پیکربندی فعلی را JSON دانلود می‌کند
  • Import — فایل پیکربندی JSON آپلود می‌کند تا مقادیر فعلی جایگزین شود
💡 نکته

تغییرات Config در نشست بعدی ایجنت یا ری‌استارت گیت‌وی اعمال می‌شوند. داشبورد وب همان فایل config.yaml‌ای را ویرایش می‌کند که ‏hermes config set و گیت‌وی از آن می‌خوانند.

API Keys ‏(کلیدهای API)

مدیریت فایل .env که کلیدهای API و اعتبارنامه‌ها در آن ذخیره می‌شوند. کلیدها بر اساس دسته گروه‌بندی می‌شوند:

  • LLM Providers — OpenRouter، ‏Anthropic، ‏OpenAI، ‏DeepSeek و...
  • Tool API Keys — Browserbase، ‏Firecrawl، ‏Tavily، ‏ElevenLabs و...
  • Messaging Platforms — توکن‌های بات تلگرام، دیسکورد، اسلک و...
  • Agent Settings — متغیرهای env غیر-محرمانه مثل ‏API_SERVER_ENABLED

هر کلید نشان می‌دهد:

  • الان ست شده یا نه ‏(با پیش‌نمایش سانسورشدهٔ مقدار)
  • توضیح اینکه برای چیست
  • لینک صفحهٔ ثبت‌نام/کلید ارائه‌دهنده
  • فیلد ورودی برای ست یا به‌روزرسانی مقدار
  • دکمهٔ حذف

کلیدهای پیشرفته/کم‌استفاده پیش‌فرض پشت یک toggle مخفی‌اند.

Sessions ‏(نشست‌ها)

مرور و بازرسی همهٔ نشست‌های ایجنت. هر ردیف عنوان نشست، آیکون پلتفرم مبدأ ‏(CLI، تلگرام، دیسکورد، اسلک، کرون)، نام مدل، تعداد پیام، تعداد فراخوانی ابزار و اینکه چقدر قبل فعال بوده را نشان می‌دهد. نشست‌های زنده با badge تپنده علامت می‌خورند.

  • Filter — تب‌های ‏Chats / Automation / All فهرست را scope می‌کنند: *Chats* ‏(پیش‌فرض) گفتگوهای انسانی را نشان و نویز اتوماسیون را پنهان می‌کند ‏(نشست‌های cron/tool/API/ACP)؛ *Automation* فقط همان‌ها؛ *All* همه‌چیز. کشویی exact-source باز هم به یک کانال واحد محدود می‌کند ‏(مثلاً فقط تلگرام). جست‌وجو فیلتر فعال را رعایت می‌کند.
  • Search — جست‌وجوی تمام‌متن در کل محتوای پیام‌ها با FTS5. نتایج snippet هایلایت‌شده نشان می‌دهند و هنگام باز شدن به اولین پیام منطبق auto-scroll می‌کنند.
  • Stats — نوار خلاصه کل نشست‌ها، چندتا در مخزن فعال‌اند، تعداد آرشیوشده، کل پیام‌ها و تفکیک به‌ازای-منبع را نشان می‌دهد.
  • Expand — کلیک روی نشست تاریخچهٔ کامل پیام‌هایش را لود می‌کند. پیام‌ها بر اساس نقش رنگ‌بندی ‏(user، ‏assistant، ‏system، ‏tool) و به‌صورت Markdown با syntax highlighting رندر می‌شوند.
  • Tool calls — پیام‌های assistant دارای فراخوانی ابزار بلوک‌های تاشو با نام تابع و آرگومان‌های JSON نشان می‌دهند.
  • Rename — ست یا پاک کردن عنوان نشست درجا ‏(آیکون مداد).
  • Export — دانلود نشست ‏(متادیتا + تاریخچهٔ کامل پیام‌ها) به‌صورت JSON ‏(آیکون دانلود).
  • Prune — دکمهٔ «Prune old sessions» در سربرگ نشست‌های پایان‌یافتهٔ قدیمی‌تر از N روز را حذف می‌کند.
  • Delete — حذف نشست و تاریخچهٔ پیام‌هایش با آیکون سطل.

Logs ‏(لاگ‌ها)

مشاهدهٔ فایل‌های لاگ ایجنت، گیت‌وی و خطاها با فیلتر و tail زنده.

  • File — جابه‌جایی بین لاگ‌های ‏agent، ‏errors و ‏gateway
  • Level — فیلتر بر اساس سطح: ALL، ‏DEBUG، ‏INFO، ‏WARNING یا ERROR
  • Component — فیلتر بر اساس مؤلفهٔ مبدأ: all، ‏gateway، ‏agent، ‏tools، ‏cli یا cron
  • Lines — انتخاب تعداد خطوط نمایش ‏(۵۰، ‏۱۰۰، ‏۲۰۰ یا ۵۰۰)
  • Auto-refresh — toggle ‏tail زنده که هر ۵ ثانیه خطوط جدید را poll می‌کند
  • Color-coded — خطوط لاگ بر اساس شدت رنگ می‌گیرند ‏(قرمز خطا، زرد هشدار، dim دیباگ)

Analytics ‏(تحلیل‌ها)

تحلیل مصرف و هزینه محاسبه‌شده از تاریخچهٔ نشست‌ها. بازهٔ زمانی ‏(۷، ‏۳۰ یا ۹۰ روز) انتخاب کنید تا ببینید:

  • کارت‌های خلاصه — کل توکن‌ها ‏(ورودی/خروجی)، درصد cache hit، کل هزینهٔ تخمینی یا واقعی و کل تعداد نشست با میانگین روزانه
  • نمودار توکن روزانه — نمودار میله‌ای انباشتهٔ مصرف توکن ورودی/خروجی به‌ازای هر روز، با tooltip های hover نشان‌دهندهٔ تفکیک و هزینه
  • جدول تفکیک روزانه — تاریخ، تعداد نشست، توکن ورودی، توکن خروجی، نرخ cache hit و هزینهٔ هر روز
  • تفکیک به‌ازای-مدل — جدول هر مدل استفاده‌شده، تعداد نشستش، مصرف توکن و هزینهٔ تخمینی

Cron ‏(کرون)

ساخت و مدیریت کارهای cron زمان‌بندی‌شده که پرامپت‌های ایجنت را طبق برنامه تکراری اجرا می‌کنند.

  • Create — پر کردن نام ‏(اختیاری)، پرامپت، عبارت cron ‏(مثل ‏0 9 * * *) و هدف تحویل ‏(local، ‏Telegram، ‏Discord، ‏Slack یا email)
  • Job list — هر job نام، پیش‌نمایش پرامپت، عبارت زمان‌بندی، badge وضعیت ‏(enabled/paused/error)، هدف تحویل، آخرین اجرا و اجرای بعدی را نشان می‌دهد
  • Pause / Resume — جابه‌جایی job بین حالت فعال و مکث
  • Edit — باز کردن modal پیش‌پر‌شده برای تغییر پرامپت، زمان‌بندی، نام یا هدف تحویل
  • Trigger now — اجرای فوری job خارج از برنامهٔ عادی‌اش
  • Delete — حذف دائمی کار cron

Profiles ‏(پروفایل‌ها)

ساخت و مدیریت پروفایل‌ها — نمونه‌های ایزولهٔ هرمس با config، مهارت‌ها و نشست‌های خودشان.

  • Profile cards — هرکدام مدل/ارائه‌دهنده، تعداد مهارت، وضعیت گیت‌وی، توضیح و badge ها ‏(active، default، alias) را نشان می‌دهد
  • Create — نام + اختیارات clone-from-default / clone-everything / no-bundled-skills، توضیح و مدل؛ صفحهٔ اختصاصی Profile Builder ‏(/profiles/new) جریان کامل را دارد ‏(مدل، ‏MCPها، مهارت‌ها)
  • Manage skills & tools — به صفحهٔ Skills محدود-به-همان-پروفایل می‌پرد ‏(سوییچر پروفایل نوار کناری را ست می‌کند)
  • Set as active — پیش‌فرض چسبانِ اجراهای آیندهٔ CLI/گیت‌وی را برمی‌گرداند ‏(مثل ‏hermes profile use). این چیزی که داشبورد مدیریت می‌کند را عوض نمی‌کند — آن کار سوییچر پروفایل است
  • Edit model / description / SOUL — ویرایشگرهای درجا که داخل همان پروفایل می‌نویسند
  • Rename / Delete — فقط پروفایل‌های نام‌دار

Skills ‏(مهارت‌ها)

مرور، جست‌وجو و toggle مهارت‌ها و تول‌ست‌های نصب‌شده، و نصب موارد جدید از hub. مهارت‌ها از ‏~/.hermes/skills/ لود و بر اساس دسته گروه‌بندی می‌شوند.

  • Search — فیلتر مهارت‌ها و تول‌ست‌های نصب‌شده بر اساس نام، توضیح یا دسته
  • Category filter — کلیک قرص‌های دسته فهرست را محدود می‌کند ‏(مثل MLOps، ‏MCP، ‏Red Teaming، ‏AI)
  • Toggle — فعال/غیرفعال کردن تک‌تک مهارت‌ها با یک سوییچ. تغییرات در نشست بعدی اعمال می‌شود.
  • Toolsets — نمای جداگانه‌ای که تول‌ست‌های داخلی ‏(عملیات فایل، مرور وب و...) را با وضعیت active/inactive، الزامات setup و فهرست ابزارهای شامل نشان می‌دهد
  • Browse hub — نمای سومی که skill hub را بین همهٔ منابع جست‌وجو می‌کند ‏(همان ‏hermes skills search)، هر نتیجه را با شناسه نصب می‌کند با لاگ نصب زنده و دکمهٔ «Update all» برای refresh مهارت‌های نصب‌شده می‌دهد.

MCP

مدیریت سرورهای MCP بدون CLI. همان بلوک ‏mcp_servers در config.yaml که ‏hermes mcp می‌خواند.

سرورهای MCP شما:

  • Add — ثبت یک سرور HTTP/SSE ‏(URL) یا stdio ‏(فرمان + آرگومان‌ها)، با متغیرهای محیطی اختیاری ‏KEY=VALUE برای سرورهای stdio
  • Enable / disable — روشن/خاموش کردن سرور بدون حذف. سرور خاموش در config می‌ماند تا بعداً دوباره فعالش کنید. در ری‌استارت بعدی گیت‌وی اعمال می‌شود.
  • Test — اتصال به سرور، فهرست ابزارش و قطع — اتصال را قبل از اینکه ایجنت به آن وابسته شود تأیید می‌کند
  • Remove — حذف سرور از پیکربندی
  • مقادیر env شبیه-رمز در نمای فهرست سانسور می‌شوند

Catalog: مرور سرورهای MCP تأیید-شدهٔ Nous ‏(کاتالوگ همراه‌بستهٔ ‏optional-mcps/) و نصب هرکدام با یک کلیک. ورودی‌هایی که کلید API می‌خواهند درجا می‌پرسند؛ مقادیر به .env می‌روند. همین کاتالوگی است که ‏hermes mcp catalog/install استفاده می‌کنند.

Webhooks ‏(وب‌هوک‌ها)

مدیریت اشتراک‌های وب‌هوک داینامیک. پلتفرم webhook باید اول در تنظیمات پیام‌رسانی فعال شود؛ صفحه وقتی نیست سرنخی نشان می‌دهد.

  • Create — نام، توضیح، فیلتر رویداد، هدف تحویل، حالت اختیاری تحویل-مستقیم و پرامپت ایجنت. هنگام ساخت صفحه URL مسیر و رمز HMAC یک‌بارمصرف قابل‌کپی را نشان می‌دهد.
  • Enable / disable — روشن/خاموش کردن اشتراک. مسیرهای خاموش در فایل اشتراک‌ها می‌مانند ولی گیت‌وی رویدادهای ورودی‌شان را رد می‌کند ‏(403). گیت‌وی فایل را hot-reload می‌کند، پس تغییر روی رویداد بعدی اعمال می‌شود — بدون ری‌استارت.
  • List — هر اشتراک URL، رویدادها و هدف تحویلش را نشان می‌دهد
  • Delete — حذف اشتراک

Pairing ‏(جفت‌سازی)

تأیید و لغو کاربران پیام‌رسانی بدون CLI — نحوهٔ onboard کردن کاربران تلگرام/دیسکورد/و... توسط ادمین راه‌دور به یک گیت‌وی جفت‌شده. هم‌ترازی کامل با ‏hermes pairing.

  • Pending requests — هرکدام پلتفرم، کد، کاربر و عمر را با دکمهٔ Approve نشان می‌دهد
  • Approved users — هرکدام پلتفرم و کاربر را با دکمهٔ Revoke نشان می‌دهد
  • Clear pending — انداختن همهٔ کدهای جفت‌سازی در انتظار

Channels ‏(کانال‌ها)

اتصال هرمس به هر پلتفرم پیام‌رسانی از مرورگر — هم‌ترازی کامل با ‏hermes setup gateway. صفحه هر کانال پشتیبانی‌شده ‏(تلگرام، دیسکورد، اسلک، ماتریکس، Mattermost، واتساپ، سیگنال، BlueBubbles/iMessage، ایمیل، SMS/Twilio، دینگ‌تاک، فیشو/لارک، ویکام، وی‌چت، QQ Bot، یوان‌بائو به‌اضافهٔ سرور API و endpoint های وب‌هوک) را با وضعیت اتصال زنده‌اش فهرست می‌کند.

  • Configure — باز کردن فرم به‌ازای-پلتفرم با دقیقاً فیلدهایی که آن کانال لازم دارد ‏(توکن بات، توکن اپ، URL سرور، لیست مجاز و...). رمزها به‌صورت ورودی password رندر و سانسورشده ذخیره می‌شوند؛ خالی گذاشتن فیلد مقدار موجود را نگه می‌دارد. فیلدهای الزامی علامت‌گذاری و اعتبارسنجی می‌شوند. لینک «Setup guide» به مستندات اعتبارنامهٔ پلتفرم اشاره می‌کند.
  • Enable / disable — روشن/خاموش کردن کانال. اعتبارنامه روی دیسک می‌ماند؛ فقط وضعیت فعال عوض می‌شود.
  • Test — بررسی اینکه کانال پیکربندی، فعال و گزارشگر اتصال زنده از گیت‌وی است.
  • Restart gateway — اعتبارنامه‌ها در ‏~/.hermes/.env و فلگ فعال در config.yaml نوشته می‌شوند؛ گیت‌وی هر کانال فعال را در ری‌استارت بعدی وصل می‌کند که می‌توانید مستقیماً از صفحه تریگرش کنید.

System ‏(سیستم)

پنل اداری تلفیقی برای عملیات سراسر-نصب:

  • Host — آمار زندهٔ سیستم: OS/کرنل، معماری، hostname، نسخه‌های Python و هرمس، تعداد هسته + بار CPU، حافظه، مصرف دیسک خانهٔ هرمس، uptime و load average. ‏(CPU/حافظه/دیسک وقتی ‏psutil نصب است از psutil می‌آیند؛ فیلدهای هویت همیشه نشان داده می‌شوند.) نسخهٔ هرمس badge وضعیت به‌روزرسانی ‏(به‌روز / N commit عقب) و دکمهٔ Check for updates دارد. وقتی روی نصب گیت به‌روزرسانی موجود باشد دکمهٔ Update now دیالوگ تأییدی باز می‌کند — چند commit خواهید کشید — قبل از اجرای ‏hermes update در پس‌زمینه. روی نصب‌های Docker/Nix داشبورد نمی‌تواند به‌روزرسانی را درجا اعمال کند پس فرمان صحیح out-of-band را نشان می‌دهد.
  • Nous Portal — وضعیت ورود، ارائه‌دهندهٔ inference فعال و جدول مسیریابی Tool Gateway ‏(کدام ابزارها از طریق Portal اجرا شوند vs محلی)، با لینک مدیریت اشتراک. آینهٔ فقط-خواندنی ‏hermes portal.
  • Skill curator — وضعیت نگهداشت-پس‌زمینهٔ مهارت‌ها ‏(فعال/مکث، interval، آخرین اجرا) با pause/resume و دکمهٔ run-now. آینهٔ ‏hermes curator.
  • Gateway — شروع، توقف و ری‌استارت گیت‌وی پیام‌رسانی با وضعیت زنده ‏(running/stopped، PID، state)
  • Memory — انتخاب ارائه‌دهندهٔ حافظهٔ خارجی ‏(یا فقط داخلی) و ریست مخازن داخلی ‏MEMORY.md/USER.md
  • Credential pool — افزودن و حذف کلیدهای API چرخشی که ایجنت round-robin می‌کند ‏(به‌ازای ارائه‌دهنده). کلیدها در فهرست سانسورند؛ مقدار خام فقط به ایجنت می‌رسد.
  • Operations — اجرای ‏doctor، audit امنیتی، ساخت بکاپ، بازیابی از آرشیو بکاپ، به‌روزرسانی مهارت‌ها، نمایش تفکیک حجم پرامپت-سیستمی، تولید dump پشتیبانی یا مهاجرت پیکربندی تنظیمات بازنشسته. هرکدام یک اقدام پس‌زمینه spawn می‌کند که لاگ زنده‌اش داخل صفحه استریم می‌شود.
  • Checkpoints — دیدن حجم مخزن سایهٔ ‏/rollback و هرس آن
  • Shell hooks — فهرست هوک‌های پیکربندی‌شده با وضعیت رضایت+اجرایی‌بودن، ساخت هوک ‏(رویداد، فرمان، matcher، timeout، با grant رضایت انتخابی) و حذف. هوک‌ها فرمان دلخواه اجرا می‌کنند، پس فرم ساخت هشدار امنیتی حمل می‌کند و هوک فقط بعد از اعطای رضایت شلیک می‌شود.
⚠️ امنیت

داشبورد وب فایل .env شما را می‌خواند و می‌نویسد که کلیدهای API و رمزها در آن است. پیش‌فرض روی ‏127.0.0.1 بایند می‌شود — فقط از ماشین محلی‌تان قابل‌دسترس، بدون نیاز به ورود. بایند به هر آدرس غیر-loopback ‏(شامل ‏0.0.0.0) گیت احراز را فعال می‌کند: سرور تا وقتی ارائه‌دهندهٔ احراز ‏(رمزعبور یا OAuth) پیکربندی نشود از شروع امتناع می‌کند.

۵ فرمان اسلش ‏/reload

PR داشبورد فرمان اسلش ‏/reload را هم به CLI تعاملی اضافه کرده. بعد از تغییر کلیدهای API از طریق داشبورد وب ‏(یا ویرایش مستقیم .env)، در یک نشست فعال CLI از ‏/reload استفاده کنید تا بدون ری‌استارت تغییرات گرفته شوند:

You → /reload
  Reloaded .env (3 var(s) updated)

این ‏~/.hermes/.env را دوباره داخل محیط پروسهٔ در-حال-اجرا می‌خواند. وقتی کلید ارائه‌دهندهٔ جدیدی از داشبورد اضافه کرده‌اید و می‌خواهید فوراً استفاده شود مفید است.

۶ REST API

داشبورد وب یک REST API expose می‌کند که فرانت مصرفش می‌کند. برای اتوماسیون مستقیم هم می‌توانید این endpoint ها را صدا بزنید:

💡 endpoint های scoped-به-پروفایل

خانواده‌های endpoint مدیریتی — ‏/api/config، ‏/api/env، ‏/api/skills، ‏/api/tools/toolsets، ‏/api/mcp و ‏/api/model/{info,options,auxiliary,set} — پارامتر query اختیاری ‏?profile=<name> ‏(یا ‏"profile" در بدنهٔ JSON برای نوشتن‌ها) را می‌پذیرند که خواندن/نوشتن را به ‏HERMES_HOME آن پروفایل scope کند. حذف = پروفایل خودِ داشبورد. نام پروفایل ناشناخته ‏404 می‌دهد. ‏WebSocket ‏/api/pty همین پارامتر را می‌پذیرد تا چت زیر پروفایل انتخابی spawn شود.

‏GET /api/status

نسخهٔ ایجنت، وضعیت گیت‌وی، وضعیت پلتفرم‌ها و تعداد نشست فعال را برمی‌گرداند.

پاسخ دو بلوک منبع مشورتی هم حمل می‌کند ‏(هرگز بر حکم سلامت ‏components/overall اثری ندارند):

  • ‏memory — تقطیرشده از ضربان ۳۰ثانیه‌ای گیت‌وی و دفتر چرخهٔ حیات. فیلدها: ‏pressure ‏(ok/elevated/critical/unknown)، ‏gateway_rss_mb، ‏system_total_mb، ‏system_available_mb، ‏swap_used_mb، ‏sampled_at، ‏boot_id، ‏last_boot_unclean، ‏last_boot_suspected_oom. فشار زیر ۱۲۸ MiB ‏(یا ۱۵٪) حافظهٔ موجود سیستم ‏elevated و زیر ۶۴ MiB ‏(یا ۵٪) ‏critical است — همان سطوحی که خروج ناسالم بعدی به‌عنوان OOM kill مشکوک فلگ می‌شود. ضربان‌های قدیمی‌تر از ۱۵۰ ثانیه ‏(یا مؤرخ-در-آینده) اعدادشان را نگه می‌دارند ولی فشار را به ‏unknown تنزل می‌دهند، تا آخرین نمونهٔ گیت‌وی مرده نتواند خودش را قرائت زنده جا بزند.
  • ‏disk — یک نمونهٔ زندهٔ ‏shutil.disk_usage() از والوم نگهدارندهٔ ‏~/.hermes. فیلدها: ‏pressure، ‏free_mb، ‏total_mb، ‏used_percent، ‏sampled_at. فشار زیر ۵۱۲ MB آزاد ‏(یا ≥۸۵٪ مصرف با کمتر از ۴ GB ذخیره) ‏elevated و زیر ۲۵۶ MB آزاد ‏(یا ≥۹۵٪ مصرف با کمتر از ۱ GB ذخیره) ‏critical است.

هر دو collector fail-safe هستند: هر خطای نمونه‌گیری بلوک را به ‏{"pressure": "unknown"} تنزل می‌دهد نه شکست endpoint وضعیت. اعداد درشت‌اند ‏(MB کامل، درصد کامل) چون ‏/api/status عمومی است.

سایر endpoint ها

  • ‏GET /api/sessions — ۲۰ نشست اخیر با متادیتا ‏(مدل، شمارش توکن، timestamp ها، پیش‌نمایش)
  • ‏GET /api/config — محتوای فعلی config.yaml به‌صورت JSON
  • ‏GET /api/config/defaults — مقادیر پیش‌فرض پیکربندی
  • ‏GET /api/config/schema — schema هر فیلد پیکربندی — نوع، توضیح، دسته و گزینه‌های select در صورت وجود. فرانت با این برای هر فیلد ویجت ورودی درست را رندر می‌کند.
  • ‏PUT /api/config — ذخیرهٔ پیکربندی جدید. بدنه: ‏{"config": {...}}
  • ‏GET /api/env — همهٔ متغیرهای محیطی شناخته‌شده با وضعیت ست/unset، مقادیر سانسورشده، توضیحات و دسته‌ها
  • ‏PUT /api/env — ست متغیر محیطی. بدنه: ‏{"key": "VAR_NAME", "value": "secret"}
  • ‏DELETE /api/env — حذف متغیر محیطی. بدنه: ‏{"key": "VAR_NAME"}
  • ‏GET /api/sessions/{session_id} — متادیتای یک نشست واحد
  • ‏GET /api/sessions/{session_id}/messages — یک صفحه محدود از تاریخچهٔ پیام‌ها شامل فراخوانی‌های ابزار و timestamp ها. پیش‌فرض ۵۰۰ پیام اخیر به ترتیب زمانی. برای صفحه‌بندی صریح ‏limit ‏(حداکثر ۵۰۰)، ‏offset و ‏order=oldest|latest را استفاده کنید.
  • ‏GET /api/sessions/search — جست‌وجوی تمام‌متن در محتوای پیام. پارامتر: ‏q. شناسه‌های نشست منطبق با snippet هایلایت‌شده برمی‌گرداند.
  • ‏DELETE /api/sessions/{session_id} — حذف نشست و تاریخچهٔ پیام‌هایش
  • ‏GET /api/logs — خطوط لاگ. پارامترها: ‏file ‏(agent/errors/gateway)، ‏lines، ‏level، ‏component
  • ‏GET /api/analytics/usage — تحلیل مصرف توکن، هزینه و نشست. پارامتر: ‏days ‏(پیش‌فرض ۳۰). پاسخ شامل تفکیک روزانه و تجمیع به‌ازای-مدل.
  • ‏GET /api/cron/jobs — همهٔ کارهای cron پیکربندی‌شده با وضعیت، زمان‌بندی و تاریخچهٔ اجرا
  • ‏POST /api/cron/jobs — ساخت کار cron جدید. بدنه: ‏{"prompt": "...", "schedule": "0 9 * * *", "name": "...", "deliver": "local"}
  • ‏POST /api/cron/jobs/{job_id}/pause — مکث کار کرون · ‏/resume — ازسرگیری · ‏/trigger — اجرای فوری خارج از برنامه

۷ احراز ‏(حالت گیت‌خورده)

وقتی داشبورد به آدرس عمومی یا غیر-loopback بایند شود — هر چیز غیر از ‏127.0.0.1/localhost — هرمس ایجنت گیت احراز را فعال می‌کند. هر درخواست باید کوکی نشست تأییدشده حمل کند وگرنه به صفحهٔ ورود برگردانده می‌شود. سه ارائه‌دهنده همراه‌بسته است:

  • رمزعبور — ساده‌ترین راه گذاشتن احراز روی داشبورد خودمیزبان/on-prem/homelab. بدون ارائه‌دهندهٔ هویت خارجی. فقط روی شبکهٔ مطمئن یا پشت VPN — برای قرار گرفتن مستقیم در اینترنت عمومی نه.
  • OAuth ‏(Nous Portal) — برای استقرارهای میزبانی‌شده و هر داشبورد قابل‌رسید از اینترنت عمومی، و مسیر توصیه‌شده برای اتصال راه‌دور Hermes Desktop. هر ورود علیه حسابتان در Nous تأیید می‌شود، پس ارائه‌دهندهٔ مناسب استفادهٔ رو-به-اینترنت همین است.
  • OIDC خودمیزبان — برای آوردن ارائه‌دهندهٔ هویت خودتان از طریق OpenID Connect استاندارد ‏(Keycloak، ‏Auth0، ‏Okta، ‏Google، ‏GitHub از طریق پل OIDC و...). بدون دخالت Nous Portal؛ برای اینترنت عمومی وقتی جلویش سرور OIDC منطبق باشد مناسب است.

داشبوردهای متعلق-به-اپراتور که روی loopback بایند شده‌اند بی‌تأثیرند — بدون احراز، بدون صفحهٔ ورود.

کِی گیت فعال می‌شود

فلگ‌هاگیت احرازکاربرد
hermes dashboard ‏(پیش‌فرض — بایند به ‏127.0.0.1)خاموشتوسعه محلی
hermes dashboard --host 0.0.0.0روشنراه‌دور / تولید — با ارائه‌دهندهٔ رمزعبور یا OAuth محافظت کنید

گیت اگر و فقط اگر میزبان bind نه ‏127.0.0.1 باشد نه ‏::1 نه ‏localhost روشن است. بایند به ‏0.0.0.0 ‏(یا هر آدرس RFC1918/LAN) گیت را فعال می‌کند. فلگ قدیمی ‏--insecure دیگر آن را خاموش نمی‌کند — برای سازگاری پذیرفته ولی با هشدار نادیده گرفته می‌شود.

🚨 ‏--insecure بی‌اثر است — احراز را خاموش نمی‌کند

از سخت‌سازی ژوئن ۲۰۲۶، ‏--insecure دیگر احراز داشبورد را دور نمی‌زند: بایند غیر-loopback همیشه ارائه‌دهندهٔ احراز می‌خواهد ‏(رمزعبور یا OAuth). اگر داشبورد بدون احراز می‌خواهید، روی ‏127.0.0.1 بایند و از طریق تونل SSH یا Tailscale برسید.

معناشناسی fail-closed

اگر گیت فعال می‌شد ولی هیچ ‏DashboardAuthProvider ثبت نبود ‏(بدون افزونهٔ Nous، بدون افزونهٔ سفارشی)، ‏hermes dashboard با پیام خطای صریح از بایند امتناع می‌کند. هیچ fallback «deny-پیش‌فرض-ولی-قبول-همه‌چیز» وجود ندارد — داشبورد گیت‌خوردهٔ بدپیکربندی هرگز شروع نمی‌شود.

وقتی ‏hermes dashboard --host 0.0.0.0 را تعاملی ‏(ترمینال واقعی) اجرا کنید و هنوز ارائه‌دهنده‌ای پیکربندی نشده باشد، هرمس فقط شکست نمی‌خورد — همان‌جا پیشنهاد setup می‌دهد: انتخاب username & password ‏(‏dashboard.basic_auth را در config.yaml می‌نویسد و ظرف چند ثانیه بالا هستید) یا OAuth ‏(شما را به ‏hermes dashboard register اشاره می‌دهد). فراخواننده‌های غیرتعاملی — Docker/s6، ‏CI، اجراهای pipe‌شده — پرامپت را رد و به خطای fail-closed بالا می‌خورند، پس استقرار بی‌نگهبان هم بدون احراز هرگز شروع نمی‌شود.

۸ ارائه‌دهندهٔ پیش‌فرض: Nous Research

افزونهٔ همراه‌بستهٔ ‏plugins/dashboard_auth/nous همیشه نصب و خودکار لود می‌شود. وقتی client ID پیکربندی شده باشد خودکار یک ‏DashboardAuthProvider به نام ‏nous ثبت می‌کند.

چون هر ورود علیه Nous Portal تأیید و با حسابتان در Nous محافظت می‌شود، ارائه‌دهندهٔ Nous همان است که برای expose کردن داشبورد به اینترنت عمومی مناسب است.

ثبت داشبورد

برای استفاده از ارائه‌دهندهٔ Nous به یک client ID مربوط به OAuth ‏(قالب ‏agent:{id}) نیاز دارید. دو راه:

  • ‏CLI — ‏hermes dashboard register. روی میزبانی که داشبورد در آن است اجرا کنید. ورود موجود Nous شما را حل می‌کند ‏(اگر وارد نشده‌اید اول ‏hermes setup)، یک کلاینت OAuth خودمیزبان با Portal ثبت و ‏HERMES_DASHBOARD_OAUTH_CLIENT_ID را در ‏~/.hermes/.env می‌نویسد. فلگ‌های اختیاری: ‏--name ‏(برچسب خوانا، وگرنه خودکار تولید می‌شود) و ‏--redirect-uri ‏(URL callback عمومی HTTPS برای میزبان رو-به-اینترنت).
bash
hermes dashboard register
# ✓ Registered dashboard "swift_falcon"
# …writes HERMES_DASHBOARD_OAUTH_CLIENT_ID to ~/.hermes/.env
  • GUI — صفحهٔ Local Dashboards. ‏‎/local-dashboards را در Nous Portal باز کنید تا داشبوردهای خودمیزبان را از مرورگر ثبت، نام‌گذاری، مدیریت و لغو کنید. ‏client ID حاصل ‏agent:{id} را داخل ‏HERMES_DASHBOARD_OAUTH_CLIENT_ID ‏(env) یا ‏dashboard.oauth.client_id ‏(config.yaml) کپی کنید. همین‌جاست که داشبورد ثبت‌شده با CLI را هم لغو می‌کنید.

    client_id: agent:01HXYZ…             # برای فعال شدن گیت لازم است

طبق قاعدهٔ هرمس ایجنت ‏(~/.hermes/.env فقط برای کلیدهای API/رمزهاست) config.yaml مکان توصیه‌شده برای ست این مقادیر برای توسعه محلی، on-prem و هر استقراری که مستقیم کنترلش می‌کنید است. مسیر متغیر محیطی وجود دارد تا تزریق رمزِ پلتفرم میزبانی بتواند client_id های به‌ازای-deploy را بدون ویرایش config.yaml داخل ایمیج push کند — هدف اصلیش همین است.

مقادیر env خالی unset تلقی می‌شوند تا رمزِ provision-شده-ولی-پر‌نشده نتواند تصادفاً سایه‌ای روی ورودی معتبر config.yaml بیندازد.

اگر هیچ‌یک از دو منبع client_id ندهد، افزونه دلیل مشخص را گزارش و خطای fail-closed بایند داشبورد دقیقاً می‌گوید چه اصلاح کنید:

مثال کاربردی: Nous Research

از نصب وارد‌شدهٔ هرمس تا داشبورد گیت‌خورده-با-Nous در سه گام.

۱. ورود و ثبت داشبورد. ‏hermes dashboard register با ورود موجود Nous شما کلاینت OAuth تأمین و ‏HERMES_DASHBOARD_OAUTH_CLIENT_ID را در ‏~/.hermes/.env می‌نویسد:

۲. اجرای داشبورد روی آدرس قابل‌دسترس. بایند غیر-loopback گیت OAuth را فعال و ‏client_id همین الان نوشته‌شده ارائه‌دهندهٔ ‏nous را فعال می‌کند:

bash

bash

‏GET /api/auth/me سپس نشست تأییدشده را برمی‌گرداند ‏(provider: nous). برای میزبان رو-به-اینترنت با ‏--redirect-uri https://hermes.example.com/auth/callback ثبت و ‏HERMES_DASHBOARD_PUBLIC_URL را بگذارید تا callback مربوط به OAuth به URL عمومی‌تان حل شود ‏(«override URL عمومی» را ببینید).

۹ ارائه‌دهندهٔ رمزعبور ‏(بدون IDP مربوط به OAuth)

اگر نمی‌خواهید ارائه‌دهندهٔ هویت OAuth سیم‌کشی کنید — استقرار خودمیزبانی «فقط یک رمز روی داشبوردم بگذار» — افزونهٔ همراه‌بستهٔ ‏plugins/dashboard_auth/basic یک ‏DashboardAuthProvider به نام ‏basic ثبت می‌کند که به‌جای redirect مربوط به OAuth با نام کاربری و رمزعبور احراز می‌کند.

به همان گیتی که ارائه‌دهندهٔ OAuth وصله وصله می‌شود: گیت روی بایند غیر-loopback فعال می‌شود، صفحهٔ ورود برای این ارائه‌دهنده فرم اعتبارنامه رندر می‌کند ‏(نه دکمهٔ «Log in with X») و هر چیز بعد از ورود — کوکی‌های نشست، refresh شفاف، تیکت‌های WS، خروج، لاگ حسابرسی — عین مسیر OAuth است. نشست‌ها توکن‌های امضاشدهٔ HMAC بدون-وضعیت‌اند که ارائه‌دهنده خودش ضرب می‌کند، پس نه دیتابیسی هست نه IDP خارجی. hash رمز از ‏scrypt کتابخانهٔ استاندارد استفاده می‌کند ‏(بدون وابستگی شخص ثالث).

⚠️ فقط روی شبکه‌های مطمئن — نه اینترنت عمومی

ارائه‌دهندهٔ رمزعبور برای داشبوردهای خودمیزبان/on-prem/homelab روی شبکهٔ مطمئن یا فقط-قابل‌رسید-از-طریق VPN طراحی شده. یک اعتبارنامهٔ مشترک واحد را بدون ارائه‌دهندهٔ هویت خارجی، ‏MFA یا حساب‌های به‌ازای-کاربر محافظت می‌کند، پس برای expose مستقیم داشبورد به اینترنت عمومی مناسب نیست. برای داشبورد رو-به-اینترنت از ارائه‌دهندهٔ Nous Research ‏(یا ‏OIDC خودمیزبان خودتان) استفاده کنید.

پیکربندی

مثل ارائه‌دهندهٔ Nous از config.yaml ‏(مرجع) می‌خواند و env غیرخالی برنده است. فقط وقتی ‏username به‌اضافهٔ ‏password_hash ‏(ترجیحی) یا ‏password پیکربندی شده باشند فعال می‌شود — وگرنه no-op است، پس کاربران OAuth و اپراتورهای loopback بی‌تأثیرند.

config.yaml:

yaml
dashboard:
  basic_auth:
    username: admin
    # Preferred — no plaintext at rest. Compute with:
    #   python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"
    password_hash: "scrypt$16384$8$1$…$…"
    # ...or a plaintext password (hashed in-memory at load; less safe at rest):
    # password: "s3cret"
    secret: "<32+ random bytes, base64 or hex>"  # token-signing key
    session_ttl_seconds: 43200                    # optional; access-token lifetime (default 12h)

متغیر envoverride می‌کندیادداشت‌ها
HERMES_DASHBOARD_BASIC_AUTH_USERNAMEdashboard.basic_auth.usernameبرای فعال شدن لازم
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASHdashboard.basic_auth.password_hashترجیحی ‏(بدون plaintext در حالت سکون)
HERMES_DASHBOARD_BASIC_AUTH_PASSWORDdashboard.basic_auth.passwordplaintext؛ بر password_hash پیکربندی برنده می‌شود تا چرخش با env ممکن باشد

⚠️ secret صریح بگذارید برای نشست‌های پایدار

وقتی ‏secret خالی باشد کلید امضای تصادفی به‌ازای-پروسه تولید می‌شود. برای یک پروسه اوکی است ولی یعنی هر نشست با ری‌استارت باطل می‌شود و نشست‌ها بین چند worker گسترده نمی‌شوند. برای استقرارهای چند-worker/پایدار-در-برابر-ری‌استارت secret صریح بگذارید.

نقطهٔ پایانی ‏/auth/password-login به‌ازای IP کلاینت rate-limit دارد ‏(پیش‌فرض ۱۰ تلاش/دقیقه ← HTTP 429) و برای هم کاربر ناشناخته هم رمز غلط یک ‏401 Invalid credentials عمومی واحد برمی‌گرداند تا oracle شمارش-یوزرنیم نشود.

نوشتن ارائه‌دهندهٔ رمزعبور خودتان

‏basic فقط یک پیاده‌سازی از یک نقطهٔ توسعه است. هر افزونه‌ای می‌تواند ارائه‌دهندهٔ رمزعبور ثبت کند: روی زیرکلاس ‏DashboardAuthProvider خودتان ‏supports_password = True بگذارید و ‏complete_password_login(*, username, password) -> Session را پیاده کنید ‏(در رد شدن ‏InvalidCredentialsError، اگر مخزن پشتیبانتان پایین است ProviderError). متدهای ‏start_login/complete_login مربوط به OAuth می‌توانند stub ‏NotImplementedError بمانند برای ارائه‌دهندهٔ صرفاً-رمزی. این مسیر LDAP-bind، دیتابیس اعتبارنامه یا هر طرح احراز غیر-redirect است — فریم‌ورک فرم، مسیر، کوکی‌ها و refresh را برایتان هندل می‌کند.

۱۰ ارائه‌دهندهٔ OIDC خودمیزبان

اگر ارائه‌دهندهٔ هویت خودتان را اجرا می‌کنید، افزونهٔ همراه‌بستهٔ ‏plugins/dashboard_auth/self_hosted داشبورد را با OpenID Connect استاندارد علیه آن احراز می‌کند — بدون کد per-IDP، بدون دخالت Nous Portal. با هر سرور OIDC منطبق تأیید و کار می‌کند:

Authentik · Keycloak · Zitadel · Authelia · Auth0 · Okta · Google · …

مثل ارائه‌دهندهٔ Nous خودکار لود و فقط وقتی پیکربندی شده باشد خودش را ثبت می‌کند، پس برای داشبوردهای loopback بی‌اثر است.

پیکربندی

یک issuer و یک ‏client_id پیکربندی کنید ‏(کلاینت عمومی PKCE — بدون client secret). افزونه مقدارهای ‏authorization_endpoint، ‏token_endpoint و ‏jwks_uri مربوط به IDP را از ‏{issuer}/.well-known/openid-configuration می‌گیرد، پس هرگز URL های endpoint را هاردکد نمی‌کنید.

config.yaml — سطح مرجع:

yaml
dashboard:
  oauth:
    provider: self-hosted
    self_hosted:
      issuer: https://auth.example.com/application/o/hermes/   # required
      client_id: hermes-dashboard                              # required
      scopes: "openid profile email"                           # optional (this is the default)

متغیرهای محیطی — override های اپراتور ‏(env وقتی غیرخالی باشد بر config.yaml مقدم است؛ مقدار خالی unset تلقی می‌شود):

در IDP خود یک اپلیکیشن/کلاینت عمومی با grant ‏authorization-code + ‏PKCE ‏(S256) ثبت و callback داشبورد را به‌عنوان redirect URI مجاز اضافه کنید. callback مقدار ‏<public URL داشبورد>/auth/callback است ‏(نحوهٔ مشتق URL عمومی پشت پروکسی را در «override URL عمومی» ببینید).

چه چیزی را تأیید می‌کند

ارائه‌دهنده ID token مربوط به OpenID Connect ‏(RS256/ES256) را نسبت به ‏jwks_uri کشف‌شده تأیید می‌کند، با claim های ‏iss و aud قفل‌شده به issuer و client_id پیکربندی‌شده‌تان. claim های استاندارد OIDC به نشست داشبورد نگاشت می‌شوند:

فیلد نشستclaim(ها)
user_idsub ‏(الزامی)
emailemail
display_name‏name ← ‏preferred_username ← ‏nickname ← ‏email
org_id‏org_id/organization، وگرنه ‏groups الحاق‌شده

ID token همان چیزی است که هویت را برقرار می‌کند — access token مات تلقی می‌شود ‏(spec مربوط به OIDC نیازمند JWT بودنش نیست). URL های endpoint باید HTTPS باشند ‏(‏http مربوط به loopback برای IDP های توسعه-محلی اجازه دارد) و issuer اعلام‌شدهٔ سند کشف باید با پیکربندی‌شده‌تان بخواند ‏(اختلاف اسلش انتهایی تحمل می‌شود). refresh token ها وقتی IDP ضربشان کند برای re-auth بی‌صدا از طریق grant استاندارد ‏refresh_token استفاده می‌شوند؛ خروج وقتی اعلام شده ‏revocation_endpoint مربوط به RFC 7009 را صدا می‌زند.

کلاینت‌های محرمانه ‏(دارای client_secret) هنوز پشتیبانی نمی‌شوند — کلاینت عمومی + ‏PKCE را پیکربندی کنید که انتخاب معمول برای داشبورد رو-به-مرورگر است.

مثال کاربردی: Keycloak

Keycloak یکی از راحت‌ترین سرورهای OIDC خودمیزبان برای تست محلی است — در حالت dev به‌صورت یک کانتینر اجرا می‌شود ‏(DB درون-حافظه) و کشف OIDC درسی expose می‌کند. این راهنما در چند دقیقه از هیچ به ورود کارا داشبورد می‌رسد.

۱۱ override URL عمومی

به‌طور پیش‌فرض داشبورد URL callback مربوط به OAuth را از درخواست بازسازی می‌کند — ‏X-Forwarded-Host + ‏X-Forwarded-Proto + ‏X-Forwarded-Prefix ‏(وقتی uvicorn با ‏proxy_headers=True پیکربندی شده که ‏start_server زیر گیت فعالش می‌کند). این پشت پروکسی معکوسی که هر سه هدر را درست ست کند از جعبه کار می‌کند.

برای deploy های پشت پروکسی‌هایی که این هدرها را مطمئن فوروارد نمی‌کنند ‏(setup های دستی nginx، ingress های on-prem، deploy های custom-domain با زنجیرهٔ پروکسی ناقص) مقدار ‏dashboard.public_url ‏(یا ‏HERMES_DASHBOARD_PUBLIC_URL) را روی URL عمومی کاملِ رسیدن به داشبورد بگذارید:

yaml
dashboard:
  public_url: "https://dashboard.example.com/hermes"

با تنظیم شدن، URL callback مربوط به OAuth عیناً ‏<public_url>/auth/callback می‌شود — ‏X-Forwarded-Prefix روی آن مسیر کد نادیده گرفته می‌شود چون اپراتور صریحاً URL عمومی را اعلام کرده. عمدی است: انباشتن prefix رویش، در حالت رایجی که prefix از قبل داخل public_url baked شده، دوبار-prefix می‌کرد.

سطحمسیر overrideکِی
dashboard.public_url در config.yamlHERMES_DASHBOARD_PUBLIC_URLتوسعه محلی / on-prem ‏(مرجع)
متغیر env ‏HERMES_DASHBOARD_PUBLIC_URL—رمزهای پلتفرم میزبانی / CI
‹تنظیم‌نشده›—پیش‌فرض — بازسازی از هدرهای ‏X-Forwarded-*

اعتبارسنجی مقادیر بدون scheme ‏http:///https://، بدون host یا حاوی quote/angle/whitespace/کاراکتر کنترلی را رد می‌کند. مقدار بدفرم بی‌صدا به بازسازی-هدر برمی‌گردد تا جریان ورود به کار ادامه دهد به‌جای dispatch کردن کاربر به URL خصمانه.

یادداشت: ‏public_url فقط URL callback مربوط به OAuth را override می‌کند. فلگ ‏Secure کوکی همچنان توسط ‏request.url.scheme کنترل می‌شود ‏(X-Forwarded-Proto زیر proxy_headers)، پس public_url با ‏http روی deploy عمومیِ TLS-خاتمه‌یافته کوکی‌های non-Secure تولید می‌کند. این دام اپراتوری است — public_url را با TLS termination صحیح بالادستی جفت کنید.

۱۲ جریان OAuth، کوکی‌ها، خروج و حسابرسی

ارائه‌دهنده قرارداد OAuth مربوط به Nous Portal v1 را پیاده می‌کند — grant authorization-code با ‏PKCE ‏(S256):

  1. کاربر بدون کوکی نشست به ‏/ ضربه می‌زند ← گیت به ‏/login redirect می‌کند.
  2. صفحهٔ ورود دکمهٔ «Continue with Nous Research» نشان می‌دهد ← ‏/auth/login?provider=nous.
  3. سرور وضعیت PKCE را در کوکی کوتاه‌عمر stash و کاربر را به ‏https://portal.nousresearch.com/oauth/authorize?… redirect می‌کند.
  4. کاربر در Portal احراز و در ‏/auth/callback?code=…&state=… فرود می‌آید.
  5. سرور کد را در ‏POST /api/oauth/token به access token تبدیل، امضای JWT را نسبت به JWKS مربوط به Portal ‏(/.well-known/jwks.json) تأیید و کوکی ‏hermes_session_at را ست می‌کند.
  6. کاربر به ‏/ ‏(یا مسیر deep-link اصلی از طریق پارامتر query ‏next=`) برگردانده می‌شود.

‏Access token ها TTL ‏۱۵ دقیقه دارند. در قرارداد v1 هیچ refresh token‌ای نیست — وقتی توکن منقضی شود wrapper ‏fetch مربوط به SPA پاکت 401 را تشخیص و تمام-صفحه به ‏/login navigate می‌کند تا جریان دوباره اجرا شود.

hermes_session_pkce۱۰ دقیقهHttpOnly؛ verifier مربوط به PKCE + سرنخ ارائه‌دهنده را در طول رفت‌وبرگشت نگه می‌دارد

هر سه ‏Path=/ و ‏SameSite=Lax هستند. فلگ ‏Secure وقتی داشبورد از HTTPS رسیده باشد ست می‌شود ‏(تشخیص با scheme مربوط به URL درخواست — X-Forwarded-Proto از TLS terminator بالادستی زیر ‏proxy_headers=True را رعایت می‌کند).

خروج

ویجت نوار کناری ‏Logged in as <user_id…> via nous را با آیکون خروج نشان می‌دهد. کلیکش ‏/auth/logout را POST می‌کند که همهٔ کوکی‌های احراز-داشبورد را پاک و به ‏/login برمی‌گرداند.

لاگ حسابرسی

هر شروع ورود، موفقیت، شکست و شکست تأیید نشست به‌صورت خط JSON در ‏$HERMES_HOME/logs/dashboard-auth.log نوشته می‌شود. فیلدهای حساس ‏(access_token، ‏refresh_token، ‏code، ‏code_verifier، ‏state، هدر Authorization) قبل از لاگ سانسور می‌شوند.

ارائه‌دهنده‌های سفارشی

برای وصله‌کردن ارائه‌دهندهٔ OAuth غیر-Nous ‏(مثل Google، ‏GitHub، ‏OIDC سفارشی) افزونه‌ای بسازید که یک ‏DashboardAuthProvider ثبت کند:

python — ~/.hermes/plugins/dashboard-auth-myidp/__init__.py
from hermes_cli.dashboard_auth import DashboardAuthProvider, Session, LoginStart

class MyIdPProvider(DashboardAuthProvider):
    name = "myidp"
    display_name = "My Identity Provider"

    def start_login(self, *, redirect_uri): ...
    def complete_login(self, *, code, state, code_verifier, redirect_uri): ...
    def verify_session(self, *, access_token): ...
    def refresh_session(self, *, refresh_token): ...
    def revoke_session(self, *, refresh_token): ...

def register(ctx):
    ctx.register_dashboard_auth_provider(MyIdPProvider())

صفحهٔ ورود همهٔ ارائه‌دهنده‌های ثبت‌شده را فهرست می‌کند؛ چند ارائه‌دهنده قابل انباشتن است و کاربر در ‏/login یکی را انتخاب می‌کند.

احراز غیرتعاملی ‏(bearer-token)

در کنار ورود تعاملی انسانی ‏(کوکی‌های نشست + refresh)، ABC مربوط به DashboardAuthProvider یک قابلیت غیرتعاملی، سرویس-به-سرویس را با ‏supports_token = True + ‏verify_token(token=...) پشتیبانی می‌کند. وقتی ارائه‌دهنده انتخابش کند، ‏Authorization: Bearer <token> ورودی تأیید و در موفقیت یک ‏TokenPrincipal به درخواست الصاق می‌شود ‏(request.state.token_principal) برای endpoint هایی که آن ارائه‌دهنده token-authable علامتشان زده — بدون کوکی، بدون redirect، بدون refresh.

اولین مصرف‌کنندهٔ همراه‌بسته ارائه‌دهندهٔ drain است ‏(plugins/dashboard_auth/drain): ‏nous-account-service رمز به‌ازای-ایجنت را از طریق ‏HERMES_DASHBOARD_DRAIN_SECRET تأمین و ارائه‌دهنده bearer token های ورودی را با مقایسهٔ constant-time علیه آن تأیید و ‏/api/gateway/drain را به‌عنوان token-authable ثبت می‌کند. ‌fail-closed است — رمز ضعیف/کوتاه ‏(< ‏۲۵۶ بیت) هنگام ثبت رد و endpoint خاموش می‌ماند؛ وقتی env تنظیم نباشد no-op است. کلیدهای رفتاری ‏(scope، ‏min_secret_chars) زیر ‏dashboard.drain_auth در config.yaml زندگی می‌کنند.

ارائه‌دهنده‌های سفارشی می‌توانند ‏supports_token/verify_token را به همان شکل پیاده کنند تا endpoint های machine-authable خودشان را expose کنند.

۱۳ اتصال Hermes Desktop به بک‌اند راه‌دور

‏Hermes Desktop می‌تواند بک‌اند هرمس در حال اجرا روی ماشین دیگری ‏(VPS، سرور خانگی، Mini پشت Tailscale) را رانندگی کند. داخل اپ زیر ‏Settings ← Gateways ← Remote gateway است که یک Remote URL و راهی برای Sign in می‌خواهد. ‏(برای خود اپ دسکتاپ — نصب، تنظیمات، چت — صفحهٔ Hermes Desktop را ببینید.)

داشبورد راه‌دور را با یکی از ارائه‌دهنده‌های احراز همراه‌بسته محافظت می‌کنید و اپ دسکتاپ علیه هرکدام که بک‌اند advertise کند وارد می‌شود. برای بک‌اندی که فراتر از ماشین خودتان قابل‌رسید است — VPS، میزبان عمومی، هر چیز رو-به-اینترنت — ارائه‌دهندهٔ توصیه‌شده OAuth ‏(Nous Portal) است ‏(با hermes dashboard register ثبت و با *Sign in with Nous Research* وارد شوید). ارائه‌دهندهٔ همراه‌بستهٔ رمزعبور سریع‌ترین گزینه وقتی بک‌اند روی LAN مطمئن است یا فقط از VPN قابل‌رسید است، ولی برای expose مستقیم اینترنت عمومی مناسب نیست. بایند داشبورد به آدرس غیر-loopback گیت احرازش را فعال می‌کند؛ بعد از ورود Desktop نشست را برای WebSocket چت خودکار بازمصرف می‌کند — توکنی برای کپی یا paste نیست.

دستورالعمل پایین از مسیر رمزعبور استفاده می‌کند چون سریع‌ترین راه‌اندازی روی شبکهٔ مطمئن است؛ برای مسیر OAuth بخش «ارائه‌دهندهٔ پیش‌فرض: Nous Research» را ببینید.

روی بک‌اند ‏(ماشین راه‌دور)

bash
# 1. Set the dashboard login credentials in ~/.hermes/.env (secrets file, 0600).
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the dashboard bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes dashboard --no-open --host 0.0.0.0 --port 9119

plaintext در حالت سکون نمی‌خواهید؟ به‌جایش ‏HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH با hash ‏scrypt استفاده کنید — سطح کامل در بخش «ارائه‌دهندهٔ رمزعبور».

اگر داشبورد را سرویس systemd اجرا می‌کنید ‏~/.hermes/.env وقتی unit دارای ‏EnvironmentFile=%h/.hermes/.env باشد خودکار گرفته می‌شود، پس اعتبارنامه‌ها هنگام بوت در محیط هستند.

⚠️ هشدار

داشبورد .env شما را می‌خواند و می‌نویسد ‏(کلیدهای API، رمزها) و می‌تواند فرمان‌های ایجنتی اجرا کند. setup رمزعبور نشان‌داده‌شده برای شبکهٔ مطمئن است — هرگز داشبورد محافظت‌شده-با-رمز را مستقیم به اینترنت باز expose نکنید. پشت VPN بگذارید. ‏Tailscale گزینهٔ تمیز است: به IP tailscale ماشین بایند کنید ‏(--host <tailscale-ip>) و ‏http://<tailscale-ip>:9119 را به‌عنوان Remote URL استفاده کنید. فقط دستگاه‌های روی tailnet‌تان به آن می‌رسند. برای رسیدن به بک‌اند از اینترنت عمومی به‌جایش ارائه‌دهندهٔ OAuth ‏(Nous Portal) را استفاده کنید.

داخل Hermes Desktop

Settings ← Gateways ← Remote gateway:

  • Remote URL — ‏http://<backend-host>:9119 ‏(prefix های مسیر مثل ‏/hermes اگر با پروکسی معکوس جلویش بگذارید پشتیبانی می‌شوند)
  • Sign in — اپ گیت‌وی رمزعبور را تشخیص و دکمهٔ Sign in نشان می‌دهد؛ کلیک و وارد کردن اعتبارنامه‌های گام ۱
  • Save and reconnect — shell دسکتاپ را روی بک‌اند راه‌دور سوار می‌کند

نشست خودکار refresh و وقتی ‏HERMES_DASHBOARD_BASIC_AUTH_SECRET روی بک‌اند ست باشد از ری‌استارت‌ها جان می‌برد.

override متغیر محیطی

به‌جای تنظیم درون-اپ، می‌توانید قبل از لانچ با متغیر env دسکتاپ را به بک‌اند اشاره دهید. وقتی ‏HERMES_DESKTOP_REMOTE_URL ست باشد URL ذخیره‌شدهٔ درون-اپ را override می‌کند ‏(پنل Gateway settings badge «env override» نشان و ویرایش را غیرفعال می‌کند)؛ همچنان با username/password از همان پنل Sign in می‌کنید.

متغیر envمقدار
HERMES_DESKTOP_REMOTE_URLhttp://<backend-host>:9119

عیب‌یابی

  • «Remote gateway incomplete» — URL راه‌دور وارد نکرده‌اید.
  • ورود با 401 / «Invalid credentials» شکست می‌خورد — username یا password با ‏HERMES_DASHBOARD_BASIC_AUTH_USERNAME/PASSWORD بک‌اند نمی‌خواند. بک‌اند برای کاربر ناشناخته و رمز غلط همان خطای عمومی را برمی‌گرداند، پس هر دو را چک کنید. گیت را با ‏curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers' تأیید کنید — باید ‏true و شامل ‏"basic" گزارش کند.
  • دکمهٔ «Sign in» ندارد — به‌جایش توکن نشست می‌خواهد — ارائه‌دهندهٔ رمزعبور فعال نیست ‏(/api/status مقدار ‏"basic" را فهرست نخواهد کرد). مطمئن شوید username و رمز ‏(یا hash) ست و پروسهٔ داشبورد آنها را لود کرده.
  • هر ری‌استارت sign-out می‌شوید — ‏HERMES_DASHBOARD_BASIC_AUTH_SECRET را روی مقدار پایدار بگذارید؛ وگرنه کلید امضا به‌ازای هر بوت بازتولید می‌شود.
  • Connection refused / timeout — بک‌اند به ‏127.0.0.1 ‏(پیش‌فرض) بایند شده به‌جای آدرس قابل‌دسترس، یا فایروال/VPN پورت را بسته. به ‏0.0.0.0 یا IP tailscale بایند و پورت را به شبکهٔ مطمئن‌تان باز کنید.

(همچنین بخش «اتصال Hermes Desktop به بک‌اند راه‌دور» ابتدای صفحه، زیر تب Chat، نکات گیت را پوشش می‌دهد — probe ‏«remote backend ready» دسکتاپ فقط ‏GET /api/status عمومی را می‌زند، ولی WebSocket چت واقعی به ‏/api/ws و ‏/api/pty احراز ‏+ تطبیق Host/peer می‌خواهد.)

۱۴ CORS

سرور وب CORS را فقط به origin های localhost محدود می‌کند:

  • ‏http://localhost:9119 / ‏http://127.0.0.1:9119 ‏(تولید)
  • ‏http://localhost:3000 / ‏http://127.0.0.1:3000
  • ‏http://localhost:5173 / ‏http://127.0.0.1:5173 ‏(سرور dev ‏Vite)

اگر سرور را روی پورت سفارشی اجرا کنید آن origin خودکار اضافه می‌شود.

۱۵ توسعه

اگر به فرانت داشبورد وب مشارکت می‌دهید:

bash
# Terminal 1: start the backend API
hermes dashboard --no-open

# Terminal 2: start the Vite dev server with HMR
cd web/
npm install
npm run dev

سرور dev ‏Vite روی ‏http://localhost:5173 درخواست‌های ‏/api را به بک‌اند FastAPI روی ‏http://127.0.0.1:9119 پروکسی می‌کند.

فرانت با React 19، ‏TypeScript، ‏Tailwind CSS v4 و کامپوننت‌های سبک-shadcn/ui ساخته شده. build های تولیدی به ‏hermes_cli/web_dist/ خروجی می‌روند که سرور FastAPI به‌عنوان SPA ایستا سروشان می‌کند.

۱۶ Build خودکار هنگام Update

وقتی ‏hermes update را اجرا کنید اگر ‏npm موجود باشد فرانت وب خودکار rebuild می‌شود. این داشبورد را با به‌روزرسانی‌های کد همگام نگه می‌دارد. اگر ‏npm نصب نباشد update ساخت فرانت را رد و ‏hermes dashboard آن را در اولین launch می‌سازد.

۱۷ تم‌ها و افزونه‌ها

داشبورد با هشت تم داخلی عرضه می‌شود و با تم‌های تعریف-شده-توسط-کاربر، تب‌های افزونه و مسیرهای REST بک‌اند قابل توسعه است — همه drop-in، بدون clone مخزن.

تعویض تم به‌صورت زنده از نوار سربرگ — آیکون palette کنار سوییچر زبان را کلیک کنید. انتخاب در config.yaml زیر ‏dashboard.theme ماندگار و هنگام لود صفحه بازیابی می‌شود.

تغییر فونت مستقل از همان picker — بخش Font زیر فهرست تم، فونت UI هر تم فعلی را override می‌کند. انتخاب بین تعویض تم‌ها ماندگار است ‏(config.yaml ← ‏dashboard.font)؛ ‏Theme default را انتخاب کنید تا پاک و به فونت خود تم فعال برگردد.
