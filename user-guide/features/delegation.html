خانه/قابلیت‌ها/واگذاری به ایجنت فرزند

واگذاری به زیرایجنت ‏(Subagent Delegation)

ابزار delegate_task نمونه‌های فرزند AIAgent را با زمینهٔ مجزا، دسترسی ابزارِ به‌ارث‌رسیده و نشست‌های ترمینال خودشان spawn می‌کند. هر فرزند گفتگوی کاملاً تازه‌ای دارد و مستقل کار می‌کند — فقط خلاصهٔ نهایی‌اش وارد زمینهٔ والد می‌شود.

فراخوانی‌های مدلِ سطح-بالا به‌طور خودکار در پس‌زمینه اجرا می‌شوند. هرمس فوراً یک handle برمی‌گرداند تا گفتگو ادامه یابد و بعد نتیجه را به‌عنوان پیام جدید پس می‌فرستد. یک زیرایجنت orchestrator منتظر کارگران خودش می‌ماند تا بتواند نتایجشان را قبل از برگشتن ترکیب کند.

۱ تسک تکی

python
delegate_task(
    goal="Debug why tests fail",
    context="Error: assertion in test_foo.py line 42"
)

۲ دستهٔ موازی

به‌طور پیش‌فرض تا ۳ زیرایجنت همزمان ‏(قابل‌پیکربندی، بدون سقف قطعی):

python
delegate_task(tasks=[
    {"goal": "Research topic A", "context": "Focus on recent primary sources"},
    {"goal": "Research topic B", "context": "Compare the leading explanations"},
    {"goal": "Fix the build", "context": "Project root: /home/user/project"}
])

۳ نحوهٔ کار زمینهٔ زیرایجنت

⚠️ حیاتی: زیرایجنت‌ها هیچ نمی‌دانند

زیرایجنت‌ها با یک گفتگوی کاملاً تازه شروع می‌کنند. هیچ دانشی از تاریخچهٔ گفتگوی والد، فراخوانی‌های قبلی ابزار یا هر چیز دیگری که قبل از واگذاری بحث شده ندارند. تنها زمینهٔ زیرایجنت همان فیلدهای goal و context است که ایجنتِ والد هنگام فراخوانی delegate_task پر می‌کند.

یعنی ایجنت والد باید همه‌چیزِ موردنیاز زیرایجنت را داخل فراخوانی پاس دهد:

python
# BAD - subagent has no idea what "the error" is
delegate_task(goal="Fix the error")

# GOOD - subagent has all context it needs
delegate_task(
    goal="Fix the TypeError in api/handlers.py",
    context="""The file api/handlers.py has a TypeError on line 47:
    'NoneType' object has no attribute 'get'.
    The function process_request() receives a dict from parse_body(),
    but parse_body() returns None when Content-Type is missing.
    The project is at /home/user/myproject and uses Python 3.11."""
)

زیرایجنت یک پرامپت سیستمی متمرکز ساخته‌شده از goal و context شما می‌گیرد که به آن دستور می‌دهد تسک را کامل کند و خلاصه‌ای ساختاریافته از کارِ انجام‌شده، یافته‌ها، فایل‌های تغییریافته و مسائل پیش‌آمده ارائه دهد.

۴ مثال‌های عملی

پژوهش موازی

چند موضوع را همزمان پژوهش و خلاصه‌ها را جمع کنید:

python
delegate_task(tasks=[
    {
        "goal": "Research the current state of WebAssembly in 2025",
        "context": "Focus on: browser support, non-browser runtimes, language support"
    },
    {
        "goal": "Research the current state of RISC-V adoption in 2025",
        "context": "Focus on: server chips, embedded systems, software ecosystem"
    },
    {
        "goal": "Research quantum computing progress in 2025",
        "context": "Focus on: error correction breakthroughs, practical applications, key players"
    }
])

بازبینی + اصلاح کد

یک گردش‌کار بازبینی-و-اصلاح را به زمینه‌ای تازه واگذار کنید:

python
delegate_task(
    goal="Review the authentication module for security issues and fix any found",
    context="""Project at /home/user/webapp.
    Auth module files: src/auth/login.py, src/auth/jwt.py, src/auth/middleware.py.
    The project uses Flask, PyJWT, and bcrypt.
    Focus on: SQL injection, JWT validation, password handling, session management.
    Fix any issues found and run the test suite (pytest tests/auth/)."""
)

بازآرایی چندفایلی

تسک بازآرایی بزرگی که زمینهٔ والد را غرق می‌کرد:

python
delegate_task(
    goal="Refactor all Python files in src/ to replace print() with proper logging",
    context="""Project at /home/user/myproject.
    Use the 'logging' module with logger = logging.getLogger(__name__).
    Replace print() calls with appropriate log levels:
    - print(f"Error: ...") -> logger.error(...)
    - print(f"Warning: ...") -> logger.warning(...)
    - print(f"Debug: ...") -> logger.debug(...)
    - Other prints -> logger.info(...)
    Don't change print() in test files or CLI output.
    Run pytest after to verify nothing broke."""
)

۵ جزئیات حالت دسته‌ای

وقتی یک ایجنت سطح-بالا آرایهٔ tasks بدهد، هرمس یک handle پس‌زمینه برمی‌گرداند، زیرایجنت‌ها را موازی اجرا می‌کند و بعد از پایان همهٔ فرزندها یک نتیجهٔ تلفیقی پست می‌کند. زیرایجنت orchestrator در همان نوبت فعلی منتظر دسته‌اش می‌ماند تا بتواند نتایج را ترکیب کند.

  • حداکثر همزمانی: ‏۳ تسک به‌طور پیش‌فرض ‏(قابل‌پیکربندی از طریق delegation.max_concurrent_children یا متغیر محیطی DELEGATION_MAX_CONCURRENT_CHILDREN؛ کف ۱، بدون سقف قطعی). دسته‌های بزرگ‌تر از حد، خطای ابزار برمی‌گردانند نه اینکه بی‌سروصدا کوتاه شوند.
  • استخر thread: از ThreadPoolExecutor با سقف همزمانیِ پیکربندی‌شده به‌عنوان max workers استفاده می‌شود
  • نمایش پیشرفت: در حالت CLI، نمای درختی فراخوانی‌های ابزار هر زیرایجنت را بلادرنگ همراه خطوط تکمیل هر-تسک نشان می‌دهد. در حالت گیت‌وی، پیشرفت دسته‌ای و به callback پیشرفت والد رله می‌شود
  • ترتیب نتایج: نتایج بر اساس اندیس تسک مرتب می‌شوند تا با ترتیب ورودی بخوانند فارغ از ترتیب تکمیل
  • لغو: پیام‌های پیگیری، یک دستهٔ پس‌زمینهٔ سطح-بالا را لغو نمی‌کنند. ‏/stop یا بستن/ریست کردن نشستِ مالک، فرزندان فعالش را لغو می‌کند. فرزندان همگامِ orchestrator همچنان از وضعیت interrupt والد پیروی می‌کنند

واگذاری همگامِ تک‌تسکِ از طرف یک orchestrator مستقیم و بدون سربار استخر thread اجرا می‌شود.

تکمیل‌های پایدار پس‌زمینه

وقتی یک واگذاری پس‌زمینه تمام می‌شود، هرمس رویداد تکمیل آن را در state.db پروفایل فعال ذخیره می‌کند و بعد به صف عادی fresh-turn منتشر می‌سازد. اگر هرمس بعد از تکمیل ولی قبل از تحویل ری‌استارت شود، رویداد معلق بازیابی و از همان بررسی‌های مالکیت عبور داده می‌شود. مصرف‌کننده‌های رقیب از claim پایدار استفاده می‌کنند، پس فقط مصرف‌کننده‌ای که نوبت مصنوعی را موفقیت بپذیرد تحویل را تأیید می‌کند؛ تلاش‌های ناموفق claim را برای تلاش مجدد آزاد می‌کنند.

این، اجرای فرزند را بعد از کرش از سر نمی‌گیرد. واگذاری‌ای که پروسهٔ مالکش وسط اجرا غیب شود unknown ثبت می‌شود، چون هرمس نمی‌تواند اثبات کند عوارض جانبی بیرونی‌اش رخ داده یا نه. رکوردهای معلق و تحویل‌شده محدود و مخصوص-پروفایل‌اند.

۶ بازنویسی مدل

می‌توانید مدلی متفاوت برای زیرایجنت‌ها در config.yaml تنظیم کنید — برای واگذاری تسک‌های ساده به مدل‌های ارزان‌تر/سریع‌تر مفید است:

yaml
# In ~/.hermes/config.yaml
delegation:
  model: "google/gemini-flash-2.0"    # Cheaper model for subagents
  provider: "openrouter"              # Optional: route subagents to a different provider

اگر حذف شود، زیرایجنت‌ها از همان مدل والد استفاده می‌کنند.

استراتژی هزینه: برنامه‌ریز frontier، کارگران کم‌هزینه

تجزیهٔ یک مسئله به زیرتسک‌های خوب-مشخص، قضاوت در سطح frontier می‌خواهد؛ اجرای یک زیرتسک که از قبل هدف روشن، زمینهٔ کامل و قرارداد خروجی دارد معمولاً نه. از سوی دیگر فرزندها هستند که توکن مصرف می‌کنند — یک دستهٔ موازی از زیرایجنت‌ها معمولاً اکثریت عظیم کل توکن‌های یک run را می‌سوزاند، پس مدلِ کارگر جایی است که هزینه واقعاً زندگی می‌کند. پین کردن delegation.model روی مدلی ارزان در حالی که نشست اصلی‌تان روی مدل frontier مانده، کیفیت برنامه‌ریزی را سر جای مهمش نگه می‌دارد و هزینه را جایی که حجم است کم می‌کند:

yaml
# ~/.hermes/config.yaml
model:
  default: "your-frontier-model"     # parent (planner) stays on the frontier model
delegation:
  model: "your-inexpensive-model"    # all delegate_task children run on this
  provider: "openrouter"             # optional: route children to a different provider

ترتیب حل: ‏delegation.base_url ‏(نقطهٔ پایانی مستقیم) اولویت دارد، بعد delegation.provider ‏(بستهٔ کامل اعتبارنامه از طریق سیستم ارائه‌دهندهٔ runtime)، و وقتی هیچ‌کدام ست نباشند فرزندان ارائه‌دهنده و اعتبارنامهٔ والد را به ارث می‌برند؛ ‏delegation.model در همهٔ حالات اعمال می‌شود و وقتی خالی باشد فرزندان مدل والد را به ارث می‌برند.

توجه کنید این پین سراسری است: ‏delegate_task پارامتر مدل per-task ندارد، پس همهٔ فرزندان یک دسته روی مدل واگذاریِ پیکربندی‌شده اجرا می‌شوند. برای زیرتسک‌های حساس-به-کیفیت که مدل قوی‌تری لازم دارند یا delegation.model را برای آن نشست unset بگذارید یا تسک را به برد کانبان بدهید که بازنویسی مدل per-task دارد.

۷ دسترسی ابزارِ به‌ارث‌رسیده

‏delegate_task پارامتر رو-به-مدلِ toolsets ندارد. هر زیرایجنت تول‌ست‌های فعال والد را به ارث می‌برد تا مدل نتواند به فرزند قابلیتی بدهد که والد ندارد. اگر کارِ واگذارشده قابلیت اضافه لازم دارد قبل از شروع گفتگو ابزارهای والد را پیکربندی کنید.

بعضی ابزارها برای زیرایجنت‌ها حتی وقتی والد آنها را دارد بلاک‌اند:

  • ‏delegate_task — برای زیرایجنت‌های برگ ‏(پیش‌فرض) بلاک. برای فرزندان role="orchestrator" حفظ می‌شود، محدود به max_spawn_depth — بخش سقف عمق و ارکستراسیون تو-در-تو.
  • ‏clarify — زیرایجنت‌ها نمی‌توانند با کاربر تعامل کنند
  • ‏memory — بدون نوشتن در حافظهٔ پایدار مشترک
  • ‏send_message — بدون عوارض جانبی بین-پلتفرمی
  • ‏cronjob — بدون زمان‌بندی کار بیشتر به نام والد

هر دو نقش execute_code ‏(فراخوانی برنامه‌نویسی‌شدهٔ ابزار) را حفظ می‌کنند تا فرزندان بتوانند کارهای مکانیکی را دسته‌ای انجام دهند.

۸ حداکثر تکرارها

هر زیرایجنت یک سقف تکرار دارد ‏(پیش‌فرض: ۵۰) که کنترل می‌کند چند نوبت فراخوانی-ابزار می‌تواند داشته باشد:

python
delegate_task(
    goal="Quick file check",
    context="Check if /etc/nginx/nginx.conf exists and print its first 10 lines",
    max_iterations=10  # Simple task, don't need many turns
)

۹ مهلت زمانی فرزند

به‌طور پیش‌فرض روی زیرایجنت‌ها هیچ timeout ساعت-دیواری وجود ندارد. فرزندان فقط از کاری که واقعاً انجام می‌دهند شکست می‌خورند — خطاهای API، خطاهای ابزار یا تمام شدن بودجهٔ تکرار — هرگز از کرنومترِ سطح-واگذاری. نسخه‌های قبلی سقف سخت داشتند ‏(۳۰۰ ثانیه، بعداً ۶۰۰) که مدام فرزندانِ مشغولِ مشروع را وسط کار می‌کشت: بازبینی‌های عمیق کد، fan-out های بزرگ پژوهشی و مدل‌های استدلالی کند به‌طور روتین بیش از ۱۰ دقیقه لازم دارند در حالی که تمام مدت پیشرفت پیوسته دارند.

فرزندان واقعاً گیرکرده همچنان شناسایی می‌شوند: مانیتور کهنگی heartbeat وقتی فرزندی هیچ پیشرفتی نکند ‏(نه فراخوانی API، نه شروع ابزار، نه tick های timestamp فعالیت) refresh فعالیت والد را متوقف می‌گذارد تا timeout بی‌کاری گیت‌وی روی worker واقعاً گیرکرده شلیک کند. انتظار برای یک فراخوانی مدلِ در جریان همچنان پیشرفت حساب می‌شود — زیرایجنت‌ها هنگام انتظار روی ارائه‌دهنده ساعت فعالیت را refresh می‌کنند، پس یک completion کندِ محلی / long-prefill معطل‌مانده تلقی نمی‌شود.

اگر با این حال سقف سخت می‌خواهید ‏(مثلاً کنترل هزینه روی واگذاری cron-محورِ بی‌نظارت)، per-install شرکت کنید:

yaml
delegation:
  child_timeout_seconds: 0     # default: 0 = no timeout
  # child_timeout_seconds: 1800  # opt-in hard cap (floor 30s)

مقدار مثبت سقف سخت ساعت-دیواری روی هر فرزند اعمال می‌کند؛ ‏0 یا مقدار منفی آن را غیرفعال می‌کند.

وقتی سقف پیکربندی‌شده شلیک شود، نتیجهٔ فرزند متادیتای ساختاریافتهٔ timeout را کنار پیام خطا حمل می‌کند تا والد‌ها و هوک‌ها بتوانند کشتنِ کرنومتری را از شکست‌های دیگر بدون تجزیهٔ متن تشخیص دهند: ‏timeout_seconds ‏(سقف پیکربندی‌شده)، ‏timed_out_after_seconds ‏(ساعت‌دیواری واقعی) و timeout_phase ‏(before_first_llm_call وقتی فرزند هرگز به اولین درخواستش نرسید، وگرنه after_llm_calls). هر سه روی خطاهای غیر-timeout مقدار null دارند.

💡 تخلیهٔ تشخیصی روی timeout صفر-فراخوانی

با سقف سختِ پیکربندی‌شده، اگر زیرایجنتی timeout شود که صفر فراخوانی API کرده ‏(معمولاً: ارائه‌دهندهٔ غیرقابل‌رسید، شکست احراز هویت، یا reject شدن schema ابزار)، ‏delegate_task یک تشخیص ساختاریافته در ~/.hermes/logs/subagent-timeout-<session>-<timestamp>.log می‌نویسد شامل snapshot پیکربندی زیرایجنت، ردّ حل اعتبارنامه، هر پیام خطای زودهنگام و stack trace برای همهٔ threadهای زنده ‏(نه فقط فرزند) — چون فرزندی که منتظر یک helper thread تو-در-تو پارک شده بدون دید کامل از فراهم‌کنندهٔ کند قابل‌تفکیک نیست.

۱۰ آشکارسازی وقفه برای زیرایجنت‌های پس‌زمینه

واگذاری‌های پس‌زمینه ‏(delegate_task(background=true)) توسط یک مانیتور وقفهٔ مبتنی-بر-پیشرفت دیده می‌شوند — به‌طور پیش‌فرض روشن، بدون پیکربندی. برخلاف timeout ساعت-دیواری، هرگز فرزندی را که در حال پیشرفت است لمس نمی‌کند، هرقدر هم طول بکشد.

مانیتور سیگنال‌های پیشرفتِ هر فرزند جدا‌شده را نمونه‌برداری می‌کند — تعداد فراخوانی API، ابزار فعلی و آخرین-timestamp فعالیت (که روی هر توکن استریم‌شده، گذار ابزار و مرز فراخوانی API تیک می‌خورد، پس فرزندی وسط استریم یک پاسخ طولانی همیشه زنده حساب می‌شود):

  1. فرزندانِ درحال‌پیشرفت هرگز لمس نمی‌شوند. هر سیگنال رو-به-جلوی ساعت را reset می‌کند.
  2. فرزندی که پیشرفتش کاملاً منجمد شده و از آستانهٔ stale گذشته ‏(۴۵۰ ثانیه idle، ‏۱۲۰۰ ثانیه داخل یک ابزار — فرمان‌های ترمینال و واکشی‌های وبِ مشروعاً کند سقف بالاتر می‌گیرند) interrupt و پنجرهٔ لطف ۱۲۰ ثانیه‌ای می‌گیرد. فرزندی که به‌موقع جمع شود نتایج جزئی‌اش را از مسیر عادی تکمیل تحویل می‌دهد.
  3. فرزندی که هرگز برنمی‌گردد force-finalize می‌شود با یک رویداد تکمیل پایانهٔ stalled، تا نشست مالک به‌جای سکوت یک سرنوشت بشنود و اسلات async برای کار جدید آزاد شود.

رویداد stalled متادیتای ساختاریافته‌ای آینهٔ فیلدهای timeout مسیر همگام حمل می‌کند: ‏stalled_after_quiet_seconds، ‏stall_threshold_seconds، ‏stall_phase ‏(idle / in_tool) و stall_grace_seconds.

این یک الگوی شکست قدیمی را بست که فرزند پس‌زمینهٔ گیرکرده نشستش را تا ری‌استارت پروسه مرده جلوه می‌داد. گیرِ underlying هم ‏(فرزندان معلق در اولین فراخوانی API بعد از چند-روز آپ‌تایم گیت‌وی) از ریشه اصلاح شد: فرزندان واگذاری الان درخواست‌های API سیمی-OpenAI را inline روی thread گفتگوی خودشان اجرا می‌کنند به‌جای یک worker thread تودرتو — همان لایه‌ای که گیر در آن زندگی می‌کرد. مانیتور وقفه به‌عنوان تور ایمنی برای بقیه موارد باقی است.

۱۱ پایش زیرایجنت‌های درحال‌اجرا ‏(/agents)

‏TUI یک overlay ی /agents ‏(نام مستعار /tasks) دارد که fan-out بازگشتیِ delegate_task را به یک سطح ممیزی درجه‌یک تبدیل می‌کند:

  • نمای درختی زنده از زیرایجنت‌های درحال‌اجرا و به‌تازگی-تمام‌شده، گروه‌بندی بر اساس والد
  • جمع‌بندی هزینه، توکن و فایل-لمس‌شده به تفکیک شاخه
  • کنترل‌های kill و pause — لغو یک زیرایجنت مشخص وسط کار بدون قطع خواهربرادرهایش
  • بازبینی پس‌رویدادی: مرور تاریخچهٔ نوبت-به-نوبت هر زیرایجنت حتی بعد از برگشتن به والد

CLI کلاسیک /agents را فقط به‌صورت خلاصهٔ متنی چاپ می‌کند؛ TUI جایی است که overlay می‌درخشد. بخش TUI — دستورات اسلش را ببینید.

روی CLI کلاسیک و همهٔ پلتفرم‌های گیت‌وی ‏(تلگرام، دیسکورد، اسلک و…)، ‏/agents همچنین واگذاری‌های پس‌زمینه با فعالیت زندهٔ هر-فرزند را فهرست می‌کند که مستقیم از هر فرزند درحال‌اجرا نمونه‌برداری شده:

Background delegations: 1 running
- deleg_ab12cd34 · running · research the delegation stall monitor
  - child 1: 4 api calls · in web_search · active 12s ago
  - child 2: 7 api calls · between turns · active 3s ago

واگذاری‌ای که مانیتور وقفه پرچمش زده به‌صورت stalling · no progress 450s — interrupting نمایش می‌یابد و فرزندانِ ساکت-اما-سالم زمان سکوتشان را نشان می‌دهند تا «کند» را از «گیرکرده» یک‌نگاهی تشخیص دهید.

۱۲ فرمان‌دادن به زیرایجنت درحال‌اجرا

قطع کردن یک فرزند، کارِ در-جریانش را دور می‌ریزد؛ اغلب فقط می‌خواهید مسیرش را عوض کنید.

از ایجنت والد ‏(رو-به-مدل)

ایجنت والد فرزندان درحال‌اجرایش را با همان ابزار delegate_task که آنها را spawn کرده هدایت می‌کند — بدون ابزار کنترلی جدا:

json
{"action": "list"}
{"action": "steer", "subagent_id": "sa-0-1a2b3c4d", "message": "focus on pricing instead"}
{"action": "stop",  "subagent_id": "sa-0-1a2b3c4d"}
  • ‏list فرزندان زندهٔ گفتگو را برمی‌گرداند: ‏subagent_id، هدف، وضعیت، ‏running_seconds، ‏accepting_steer و مسیر transcript زنده. شناسه‌ها در پاسخ dispatch ی spawn هم به‌عنوان subagent_ids برمی‌گردند.
  • ‏steer یک اصلاح مسیر در صفِ فرزندِ درحال‌اجرا قرار می‌دهد بدون توقف آن ‏(معناشناسی تحویل پایین‌تر).
  • ‏stop فرزند را در مرز تکرار بعدی زودتر تمام می‌کند؛ نتیجهٔ جزئی همچنان به‌عنوان پیام عادی تکمیل به گفتگو برمی‌گردد.

اکشن‌های کنترلی همگام در-نوبت اجرا می‌شوند ‏(هرگز به پس‌زمینه نمی‌روند)، به درخت spawn خود فراخواننده محدودند — یک گفتگو هرگز نمی‌تواند فرزندان نشست دیگر را ببیند یا کنترل کند — و هرگز سقف spawn هر-نوبت را مصرف نمی‌کنند، پس stop حتی بعد از پر شدن سقف هم کار می‌کند.

از TUI / گیت‌وی ‏(رو-به-نشست)

‏steer_subagent(subagent_id, text) در tools/delegate_tool.py آینهٔ سمت-هدایتِ interrupt_subagent() است: متن را از طریق همان سازوکار ‎/steer‎ در فرزند زنده صف می‌کند — متن به آخرین نتیجهٔ ابزارِ فرزند در مرز تکرار بعدی الصاق می‌شود، فراخوانی ابزار در-جریان هرگز بریده نمی‌شود و فرزند آن را مثل یک پیام کاربر خارج-از-باندا می‌بیند. میزبان‌های برنامه‌نویسی‌شده از طریق RPC ی گیت‌ویِ subagent.steer محدود-به-نشست به آن می‌رسند که کنار subagent.interrupt نشسته:

json
{"method": "subagent.steer", "params": {"session_id": "owning-ui-session", "subagent_id": "sa-0-1a2b3c4d", "text": "focus on pricing instead"}}

شناسه‌های زیرایجنت از delegation.status ‏(یا list_active_subagents()) می‌آیند — همان جایی که subagent.interrupt برمی‌دارد. گیت‌وی steer را فقط از همان نشست UI/گیت‌ویِ زنده‌ای که فرزند را spawn کرده می‌پذیرد. هویت نشستِ غایب، بیگانه، مبهم یا کهنه/بازیافتی رد می‌شود؛ دانستن یک شناسهٔ سراسری زیرایجنت اختیار نیست. فراخواننده‌های مستقیم درون-پروسه‌ای عمداً قرارداد helper بدون-محدودیت را نگه داشته‌اند.

صف‌شده یعنی تحویل‌شده نیست، اما هرگز موفقیت مصنوعی نیست. پاسخ "queued" یعنی متن قبل از مرز تکمیلِ فرزند پذیرفته شده، نه اینکه حتماً فرزند دیده باشد. پذیرش و تکمیل همگام‌اند: یا فرزند هنوز می‌تواند متن را مصرف کند، یا دقیقاً همان متن به‌عنوان pending_steer از نتیجه تخلیه می‌شود. فراخوانی‌های بعد از بسته‌شدن "rejected" برمی‌گردانند. اگر فرزندی steer را پذیرفته ولی جواب نهایی را قبلاً تولید کرده بود، ورودی تکمیلی که والد می‌گیرد آن را به‌عنوان missed_steer نگه می‌دارد با یادداشتی الحاقی به خلاصه:

[steer did not land — the subagent finished before it could be delivered: focus on pricing instead]

پس والد ‏(یا اپراتوری که آن را می‌راند) فرزند steered را از فرزندی که طبق دستورات قدیمی تمام شده تشخیص می‌دهد و به‌جای اطمینان به رسیده‌بودن، راهنما را به‌عنوان پیگیری دوباره صادر می‌کند.

۱۳ رونوشت‌های زنده

هر dispatch ی delegate_task یک لاگ فقط-الحاقیِ خوانا-برای-انسان به‌ازای هر تسک هم می‌سازد تا شما ‏(یا ایجنت والد) بتوانید کار یک زیرایجنت را بلادرنگ تماشا کنید به‌جای انتظار برای خلاصهٔ تلفیقی:

<hermes_home>/cache/delegation/live/<delegation_id>/task-<n>.log

پاسخ dispatch مسیرها را به‌عنوان live_transcripts شامل می‌شود و فایل‌ها در زمان dispatch از قبل ساخته می‌شوند، پس همین حالا کار می‌کند:

tail -f ~/.hermes/cache/delegation/live/deleg_ab12cd34/task-0.log

هر خط timestamp دارد و متن دستیارِ فرزند، قطعات thinking، فراخوانی ابزار ‏(-> tool_name({args}))، نتایج ابزار و نشانگر وضعیت نهایی را نشان می‌دهد. یک manifest.json در همان دایرکتوری دسته را توصیف می‌کند ‏(اهداف، تعداد تسک، وضعیت هر-تسک). لاگ‌ها بعد از تکمیل باقی می‌مانند — هم نقش رکورد عملیاتی تمام-وفاداری را در کنار خلاصه دارند — و دایرکتوری‌های قدیمی‌تر از ۷ روز در dispatch های جدید خودکار هرس می‌شوند. چون زیر cache/delegation زندگی می‌کنند از بک‌اندهای ترمینال راه‌دور ‏(Docker/Modal/SSH) هم خواندنی‌اند.

۱۴ سقف عمق و ارکستراسیون تو-در-تو

به‌طور پیش‌فرض واگذاری تخت است: والدی ‏(عمق ۰) فرزندانی ‏(عمق ۱) spawn می‌کند و آن فرزندان دیگر نمی‌توانند واگذار کنند. این از واگذاری بازگشتیِ مهارناپذیر جلوگیری می‌کند.

برای گردش‌کارهای چندمرحله‌ای ‏(پژوهش ← ترکیب، یا ارکستراسیون موازی روی زیرمسئله‌ها)، والد می‌تواند فرزندان orchestrator بسازد که می‌توانند کارگران خودشان را spawn کنند:

python
delegate_task(
    goal="Survey three code review approaches and recommend one",
    role="orchestrator",  # Allows this child to spawn its own workers
    context="...",
)
  • ‏role="leaf" ‏(پیش‌فرض): فرزند نمی‌تواند واگذار کند — دقیقاً رفتار واگذاری تخت.
  • ‏role="orchestrator": فرزند تول‌ست delegation را حفظ می‌کند. محدود به delegation.max_spawn_depth ‏(پیش‌فرض ۱ = تخت، پس role="orchestrator" روی پیش‌فرض‌ها no-op است). ‏max_spawn_depth را به ۲ بالا ببرید تا فرزندان orchestrator بتوانند نوه‌های برگ بسازند؛ برای درخت‌های عمیق‌تر ۳+. سقف بالایی نیست — هزینه حد عملی است.
  • ‏delegation.orchestrator_enabled: false: کلید قطع سراسری که هر فرزندی را صرف‌نظر از پارامتر role به leaf اجبار می‌کند.

هشدار هزینه: با max_spawn_depth: 3 و ‏max_concurrent_children: 3 درخت می‌تواند به ‎۳×۳×۳ = ۲۷‎ ایجنت برگِ همزمان برسد. هر سطح اضافی هزینه را ضرب می‌کند — ‏max_spawn_depth را آگاهانه بالا ببرید.

۱۵ طول عمر و دوام

⚠️ دوام تکمیل پس‌زمینه یعنی اجرای پایدار نیست

فراخوانی‌های رو-به-مدلِ سطح-بالای delegate_task هرجا نشست از تحویل بعدی پشتیبانی کند به‌طور خودکار در پس‌زمینه اجرا می‌شوند. هرمس فوراً handle می‌دهد و نتیجه بعد از پایان فرزند یا دسته به گفتگو برمی‌گردد. زیرایجنت‌های orchestrator در نوبت فعلی منتظر کارگران‌اند چون باید نتایج را قبل از برگشتن ترکیب کنند. نقاط پایانی stateless درخواست/پاسخ وقتی نمی‌توانند نتیجهٔ جداشده را بعداً تحویل دهند به اجرای همگام fallback می‌کنند.

  • پیام‌های پیگیریِ عادی فرزندان پس‌زمینه را لغو نمی‌کنند. ‏/stop واگذاری‌های پس‌زمینهٔ درحال‌اجرا را لغو می‌کند و بستن/ریست نشست مالک فرزندان فعالش را دور می‌ریزد.
  • بستن/ریست صریح نشست، فرزندان پس‌زمینهٔ همان نشست را قطع می‌کند. بستن نمایشگر TUI ی یک نشستِ متعلق-به-گیت‌وی کارِ گیت‌وی را نمی‌کشد.
  • ری‌استارت پروسهٔ هرمس فرزندِ درحال‌اجرا را از سر نمی‌گیرد. تلاشش unknown ثبت می‌شود چون هرمس نمی‌تواند اثبات کند کدام عوارض جانبی رخ داده.
  • فرزندی که قبل از ری‌استارت تمام شده ولی نتیجه‌اش تحویل نشده بازیابی و از بررسی‌های عادی نشست مالک عبور داده می‌شود.
  • فرزندان لغوشده نتیجهٔ ساختاریافته برمی‌گردانند ‏(status="interrupted"، ‏exit_reason="interrupted")، اما چون والد هم interrupt شده آن نتیجه اغلب هرگز وارد پاسخی قابل‌دید-برای-کاربر نمی‌شود.

برای اجرای پایدار که باید از بستن نشست یا ری‌استارت پروسه جان سالم به در ببرد:

  • ‏cronjob ‏(action=create) — یک اجرای ایجنت جداگانه زمان‌بندی می‌کند؛ نسبت به interrupt های نوبت والد ایمن است.
  • ‏terminal(background=True, notify_on_complete=True) — فرمان‌های شل بلندمدت که در حین کار ایجنت به اجرا ادامه می‌دهند.

۱۶ ویژگی‌های کلیدی

  • هر زیرایجنت نشست ترمینال خودش را دارد ‏(جدای از والد)
  • زیرایجنت‌ها تول‌ست‌های فعال والد را به ارث می‌برند؛ مدل نمی‌تواند per-call آنها را انتخاب یا گسترده کند
  • واگذاری تو-در-تو انتخابی است — فقط فرزندان role="orchestrator" می‌توانند واگذار کنند و فقط وقتی max_spawn_depth از پیش‌فرض ۱ ‏(تخت) بالا رفته باشد. غیرفعال‌سازی سراسری با orchestrator_enabled: false.
  • زیرایجنت‌های برگ نمی‌توانند صدا بزنند: ‏delegate_task، ‏clarify، ‏memory، ‏send_message، ‏cronjob. زیرایجنت‌های orchestrator ‏delegate_task را حفظ می‌کنند ولی بقیهٔ بلاک‌ها سرجایشان است. هر دو نقش execute_code ‏(فراخوانی برنامه‌نویسی‌شدهٔ ابزار) را نگه می‌دارند تا فرزندان کار مکانیکی را دسته‌ای کنند به‌جای سوزاندن تکرارهای استدلال.
  • لغو از مالکیت پیروی می‌کند — ‏/stop یا بستن/ریست نشست مالک فرزندان پس‌زمینه‌اش را لغو می‌کند؛ نوادگان همگام زیر orchestratorها از وضعیت interrupt والد پیروی می‌کنند
  • فقط خلاصهٔ نهایی وارد زمینهٔ والد می‌شود و مصرف توکن کارا می‌ماند
  • زیرایجنت‌ها کلید API، پیکربندی ارائه‌دهنده و استخر اعتبارنامهٔ والد را به ارث می‌برند ‏(چرخش کلید روی rate limit ها را ممکن می‌کند)

۱۷ ایزوله‌سازی worktree

به‌طور پیش‌فرض زیرایجنت‌ها دایرکتوری کاری والد را شریک‌اند — برای پژوهش و کارهای پر-خواندن اشکالی ندارد، ولی فرزندان موازی که همان مخزن را ویرایش می‌کنند می‌توانند تصادم کنند. ‏delegation.worktree_isolation: true را ست کنید تا هر فرزند git worktree اختصاصی خودش را داشته باشد که از HEAD فعلی مخزن انشعاب یافته ‏(الهام از --subagent-worktree-isolation ی Muse Code):

yaml
delegation:
  worktree_isolation: true   # default: false

با روشنبودن ایزوله‌سازی:

  • هر فرزند ترمینالش را در <repo>/.worktrees/subagent-<id> روی شاخهٔ اختصاصی hermes-subagent/subagent-<id> شروع می‌کند و پیام هدفش به آن می‌گوید همانجا کار کند و commit بزند.
  • checkout والد دست‌نخورده می‌ماند؛ فرزندان نمی‌توانند ویرایش‌های هم را له کنند.
  • وقتی فرزند تمام می‌شود، ورودی نتیجه‌اش فیلد worktree می‌گیرد گزارش‌دهندهٔ path، ‏branch، ‏commits ‏(جلوتر از پایه) و dirty. والد هر شاخه را بازبینی یا merge می‌کند ‏(git log <branch>، ‏git merge <branch>).
  • worktree ی رهاشده با هیچ commit و درخت تمیز خودکار prune می‌شود ‏(pruned: true)؛ هرچه کار نگه داشته نگه داشته می‌شود.
  • prune نیاز به اثبات دارد. اگر پروب بازرسی git شکست بخورد — یا خود finalization خطا بدهد — worktree و شاخه نگه داشته می‌شوند و ورودی inspection_failed: true به‌همراه یک note حمل می‌کند — ‏commits/dirty در این حالت پیش‌فرض‌اند نه اندازه‌گیری، پس worktree را بازرسی کنید به‌جای فرض اینکه فرزند هیچ تولید نکرده.

دامنه: انتخابی، فقط-git و فقط-بک‌اند-ترمینال-محلی. در دایرکتوری غیر-git، روی بک‌اندهای docker/ssh/modal، یا اگر ساخت worktree شکست بخورد، این تنظیم بی‌سروصدا به رفتار امروزِ فضای‌کاری-مشترک تنزل می‌یابد — هرگز خطا نمی‌دهد.

  # api_mode: "anthropic_messages"  # Optional. Wire protocol override for base_url ("chat_completions", "codex_responses", or "anthropic_messages"). Empty = auto-detect from URL (e.g. /anthropic suffix). Set explicitly for endpoints the heuristic can't classify (Azure AI Foundry, MiniMax, Zhipu GLM, LiteLLM proxies, …).

وقتی base_url به نقطهٔ پایانی سازگار-با-Anthropic اشاره کند — مثلاً مسیری که به /anthropic ختم شود، مسیر Claude ی Azure Foundry، یا پروکسی /anthropic ی MiniMax — ‏api_mode به‌صورت خودکار anthropic_messages آشکار می‌شود تا زیرایجنت بدون هیچ تنظیمی قالب سیم درست را به کار ببرد. وقتی حدس auto-detect غلط است ‏(نادر) صریحاً api_mode را ست کنید.
