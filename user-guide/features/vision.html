بینایی و چسباندن تصویر

‏هرمس ایجنت از بینایی چندوجهی پشتیبانی می‌کند — می‌توانید تصاویر را مستقیم از کلیپ‌بورد داخل CLI بچسبانید و از ایجنت بخواهید تحلیل، توصیف یا کار با آن‌ها را انجام دهد. تصاویر به‌عنوان بلوک‌های محتوای base64-رمزگذاری‌شده به مدل فرستاده می‌شوند، پس هر مدل توانمند-بینایی می‌تواند پردازششان کند.

💡 نکته

مشترکان Portal مدل‌های توانمند-بینایی ‏(Claude، ‏GPT-5، ‏Gemini) را در همان کاتالوگ می‌گیرند — بدون اعتبارنامهٔ اضافه. بخش Nous Portal را ببینید.

۱ نحوهٔ کار

  1. یک تصویر در کلیپ‌بورد کپی کنید ‏(اسکرین‌شات، تصویر مرورگر و...)
  2. با یکی از روش‌های پایین الصاقش کنید
  3. سؤالتان را تایپ و Enter بزنید
  4. تصویر به‌صورت badge ‏[📎 Image #1] بالای ورودی ظاهر می‌شود
  5. هنگام ارسال، تصویر به‌عنوان بلوک محتوای بینایی به مدل می‌رود

می‌توانید قبل از ارسال چندین تصویر الصاق کنید — هرکدام badge خودش را می‌گیرد. برای پاک‌کردن همهٔ تصاویر الصاقی ‏Ctrl+C بزنید.

تصاویر با نام‌فایل‌های مؤرخ به‌صورت PNG در ‏~/.hermes/images/ ذخیره می‌شوند.

۲ روش‌های paste

نحوهٔ الصاق تصویر به محیط ترمینال شما بستگی دارد. همهٔ روش‌ها همه‌جا کار نمی‌کنند — تفکیک کامل:

فرمان ‏/paste

مطمئن‌ترین fallback صریح الصاق تصویر.

/paste

‏/paste را تایپ و Enter بزنید. هرمس کلیپ‌بوردتان را برای تصویر چک و الصاق می‌کند. امن‌ترین گزینه وقتی ترمینال‌تان ‏Cmd+V/Ctrl+V را بازنویسی می‌کند، یا وقتی فقط تصویری کپی کرده‌اید و payload متنیِ bracketed-paste‌ای برای بازرسی نیست.

‏Ctrl+V / Cmd+V

هرمس الان paste را یک جریان لایه‌بندی‌شده تلقی می‌کند:

  • اول paste متن عادی
  • fallback متنِ کلیپ‌بورد-native / ‏OSC52 اگر ترمینال متن را تمیز تحویل نداد
  • الصاق تصویر وقتی کلیپ‌بورد یا payload چسبانده‌شده به تصویر یا مسیر تصویر حل شود

یعنی مسیرهای temp اسکرین‌شات مک و URI های تصویری ‏file://... می‌توانند فوراً الصاق شوند به‌جای اینکه به‌صورت متن خام در کامپوزر بنشینند.

⚠️ هشدار

اگر کلیپ‌بوردتان فقط تصویر دارد ‏(بدون متن)، ترمینال‌ها همچنان نمی‌توانند بایت‌های باینری تصویر را مستقیم بفرستند. از ‏/paste به‌عنوان fallback صریح الصاق تصویر استفاده کنید.

‏/terminal-setup برای VS Code / Cursor / Windsurf

اگر TUI را داخل ترمینال یکپارچه خانواده-VS Code روی macOS اجرا می‌کنید، هرمس می‌تواند binding های پیشنهادی ‏workbench.action.terminal.sendSequence را برای هم‌ترازی بهتر multiline و undo/redo نصب کند:

/terminal-setup

مخصوصاً وقتی مفید است که ‏Cmd+Enter، ‏Cmd+Z یا ‏Shift+Cmd+Z توسط IDE رهگیری می‌شوند. فقط روی ماشین محلی اجرایش کنید — داخل نشست SSH نه.

۴ setup مخصوص پلتفرم

macOS

بدون setup. هرمس از ‏osascript ‏(داخلی macOS) برای خواندن کلیپ‌بورد استفاده می‌کند. برای سرعت بیشتر اختیاراً ‏pngpaste نصب کنید:

brew install pngpaste

لینوکس ‏(X11)

‏xclip نصب کنید:

bash
# Ubuntu/Debian
sudo apt install xclip

# Fedora
sudo dnf install xclip

# Arch
sudo pacman -S xclip

لینوکس ‏(Wayland)

دسکتاپ‌های مدرن لینوکس ‏(Ubuntu ‏۲۲.۰۴+، ‏Fedora ‏۳۴+) اغلب پیش‌فرض Wayland دارند. ‏wl-clipboard را نصب کنید:

bash
# Ubuntu/Debian
sudo apt install wl-clipboard

# Fedora
sudo dnf install wl-clipboard

# Arch
sudo pacman -S wl-clipboard
💡 چک کنید روی Wayland هستید
echo $XDG_SESSION_TYPE
# "wayland" = Wayland, "x11" = X11, "tty" = no display server

WSL2

بدون setup اضافه. هرمس WSL2 را خودکار تشخیص می‌دهد ‏(از طریق ‏/proc/version) و از ‏powershell.exe برای دسترسی به کلیپ‌بورد ویندوز از طریق ‏System.Windows.Forms.Clipboard دات‌نت استفاده می‌کند. این جزء interop ویندوزِ WSL2 است — ‏powershell.exe پیش‌فرض موجود است.

دادهٔ کلیپ‌بورد به‌صورت PNG رمزگذاری‌شده-base64 روی stdout منتقل می‌شود، پس نیازی به تبدیل مسیر فایل یا فایل‌های temp نیست.

📌 یادداشت WSLg

اگر WSLg دارید ‏(WSL2 با پشتیبانی GUI)، هرمس اول مسیر PowerShell را امتحان سپس به ‏wl-paste برمی‌گردد. پل کلیپ‌بورد WSLg برای تصاویر فقط قالب BMP را پشتیبانی می‌کند — هرمس BMP را با Pillow ‏(اگر نصب باشد) یا فرمان ‏convert مربوط به ImageMagick خودکار به PNG تبدیل می‌کند.

تأیید دسترسی کلیپ‌بورد WSL2

bash
# 1. Check WSL detection
grep -i microsoft /proc/version

# 2. Check PowerShell is accessible
which powershell.exe

# 3. Copy an image, then check
powershell.exe -NoProfile -Command "Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.Clipboard]::ContainsImage()"
# Should print "True"

۵ SSH و نشست‌های راه‌دور

Paste تصویر کلیپ‌بورد از طریق SSH کامل کار نمی‌کند. وقتی با SSH وارد ماشین راه‌دوری می‌شوید، CLI هرمس روی میزبان راه‌دور اجرا می‌شود. ابزارهای کلیپ‌بورد ‏(xclip، ‏wl-paste، ‏powershell.exe، ‏osascript) کلیپ‌بورد ماشینی که رویش اجرا می‌شوند را می‌خوانند — یعنی سرور راه‌دور نه ماشین محلی شما. پس تصویر کلیپ‌بورد محلی‌تان از سمت راه‌دور غیرقابل‌دسترس است.

متن گاهی همچنان از طریق paste ترمینال یا OSC52 پل می‌شود، ولی دسترسی کلیپ‌بورد-تصویری و مسیرهای temp اسکرین‌شات محلی به ماشینی که هرمس را اجرا می‌کند مقیدند.

راه‌حل‌های جایگزین برای SSH

  1. آپلود فایل تصویر — تصویر را محلی ذخیره، از طریق ‏scp، فایل‌اکسپلورر VSCode ‏(drag-and-drop) یا هر روش انتقال فایلی به سرور راه‌دور ببرید. بعد با مسیر به آن ارجاع دهید. ‏(یک فرمان ‏‎/attach <filepath> برای ریلیز آینده برنامه‌ریزی شده.)
  2. استفاده از URL — اگر تصویر آنلاین در دسترس است فقط URL را در پیامتان paste کنید. ایجنت می‌تواند با ‏vision_analyze مستقیماً به هر URL تصویری نگاه کند.
  3. X11 forwarding — با ‏ssh -X وصل شوید تا X11 فوروارد شود. این اجازه می‌دهد ‏xclip روی ماشین راه‌دور به کلیپ‌بورد X11 محلی شما برسد. سرور X در حال اجرای محلی می‌خواهد ‏(XQuartz روی macOS، داخلی در دسکتاپ‌های X11 لینوکس). برای تصاویر بزرگ کند است.
  4. استفاده از پلتفرم پیام‌رسانی — تصاویر را از طریق تلگرام، دیسکورد، اسلک یا واتساپ به هرمس بدهید. این پلتفرم‌ها آپلود تصویر را native هندل و تحت تأثیر محدودیت‌های کلیپ‌بورد/ترمینال نیستند.

۶ چرا ترمینال‌ها نمی‌توانند تصویر paste کنند

منبع رایج سردرگمی است، پس توضیح فنی:

ترمینال‌ها interface های متنی هستند. وقتی ‏Ctrl+V ‏(یا Cmd+V) می‌زنید شبیه‌ساز ترمینال:

  1. کلیپ‌بورد را برای محتوای متنی می‌خواند
  2. آن را در توالی‌های escape ‏bracketed paste wrap می‌کند
  3. از طریق جریان متنی ترمینال به اپلیکیشن می‌فرستد

اگر کلیپ‌بورد فقط تصویر داشته باشد ‏(بدون متن)، ترمینال چیزی برای فرستادن ندارد. هیچ توالی escape ترمینالیِ استانداردی برای دادهٔ باینری تصویر وجود ندارد. ترمینال به‌سادگی هیچ نمی‌کند.

به همین دلیل هرمس از چک جداگانهٔ کلیپ‌بورد استفاده می‌کند — به‌جای دریافت دادهٔ تصویر از طریق رویداد paste ترمینال، ابزارهای سطح-OS ‏(osascript، ‏powershell.exe، ‏xclip، ‏wl-paste) را مستقیم با subprocess صدا می‌زند تا کلیپ‌بورد را مستقل بخواند.

۷ مدل‌های پشتیبانی‌شده

‏Paste تصویر با هر مدلی که بینایی دارد کار می‌کند. تصویر به‌صورت data URL رمزگذاری‌شده-base64 در قالب محتوای vision مربوط به OpenAI فرستاده می‌شود:

json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/png;base64,..."
  }
}

بیشتر مدل‌های مدرن این قالب را پشتیبانی می‌کنند شامل ‏GPT-4 Vision، ‏Claude ‏(با بینایی)، ‏Gemini و مدل‌های چندوجهی متن‌بازِ سرو‌شده از طریق OpenRouter.

مسیریابی تصویر ‏(مدل‌های توانمند-بینایی در برابر فقط-متنی)

وقتی کاربری تصویری الصاق کند — از کلیپ‌بورد CLI، گیت‌وی ‏(عکس تلگرام/دیسکورد) یا هر نقطهٔ ورود دیگری — هرمس بر اساس اینکه مدل فعلی واقعاً از بینایی پشتیبانی می‌کند مسیریابی می‌کند:

مدل شمابا تصویر چه می‌شود
توانمند-بینایی ‏(GPT-4V، ‏Claude با بینایی، ‏Gemini، ‏Qwen-VL، ‏MiMo-VL و...)به‌صورت پیکسل واقعی با قالب محتوای تصویری native ارائه‌دهنده بالا فرستاده می‌شود. بدون لایهٔ خلاصهٔ متنی.
فقط-متنی ‏(DeepSeek V3، مدل‌های متن‌باز کوچکتر، endpoint های قدیمی فقط-چت)از طریق ابزار کمکی ‏vision_analyze مسیریابی می‌شود — یک مدل بینایی کمکی تصویر را توصیف و توضیح متنی داخل گفتگو تزریق می‌شود.

این را شما پیکربندی نمی‌کنید — هرمس قابلیت مدل فعلی‌تان را در متادیتای ارائه‌دهنده جست‌وجو و خودکار مسیر درست را انتخاب می‌کند. اثر عملی: می‌توانید وسط نشست بین مدل‌های بینایی‌دار و غیر-بینایی سوئیچ کنید و هندل تصویر «از خودش درست» بدون تغییر گردش‌کار. مدل‌های فقط-متنی زمینهٔ منسجم دربارهٔ تصویر می‌گیرند به‌جای payload چندوجهی شکسته‌ای که مجبور به رد کردنش باشند.

اینکه کدام مدل کمکی مسیر توضیح-متنی را هندل کند زیر ‏auxiliary.vision قابل پیکربندی است — «مدل‌های کمکی» را در پیکربندی ببینید.

‏vision_analyze همان رفتار دوگانه را دارد

خود ابزار ‏vision_analyze همان مسیریابی را دنبال می‌کند. وقتی مدل اصلی فعال توانمند-بینایی و ارائه‌دهنده‌اش پشتیبان تصویر داخل نتایج ابزار باشد ‏(الان پشته‌های Anthropic، ‏OpenAI، ‏Azure-OpenAI و ‏Gemini ‏3.x)، ‏vision_analyze توصیف‌گر کمکی را short-circuit کرده و پیکسل خام تصویر را به‌صورت پاکت نتیجه-ابزار چندوجهی برمی‌گرداند. مدل اصلی نوبت بعدش تصویر را native می‌بیند — بدون فراخوانی کمکی، بدون افت اطلاعات خلاصهٔ متنی، بدون تأخیر اضافه.

برای مدل‌های اصلی فقط-متنی ‏(یا ارائه‌دهنده‌هایی whose کانال نتیجه-ابزار تصویر حمل نمی‌کند)، ‏vision_analyze به مسیر قدیمی برمی‌گردد: از مدل بینایی کمکی پیکربندی‌شده می‌خواهد تصویر را توصیف کند و توضیح را به‌عنوان متن ساده برمی‌گرداند. در هر حالت امضای ابزار فراخواننده یکی است — ابزار هنگام runtime بر اساس مدل فعال تصمیم می‌گیرد کدام مسیر را برود.
