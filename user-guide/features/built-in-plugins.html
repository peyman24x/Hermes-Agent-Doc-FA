پلاگین‌های داخلی

هرمس مجموعهٔ کوچکی از پلاگین‌ها را همراه مخزن ارائه می‌کند. آنها زیر مسیر <repo>/plugins/<name>/ زندگی می‌کنند و به‌طور خودکار در کنار پلاگین‌های نصب‌شدهٔ کاربر در ~/.hermes/plugins/ بارگذاری می‌شوند. آنها از همان سطح API پلاگینِ پلاگین‌های ثالث استفاده می‌کنند — هوک‌ها، ابزارها، دستورات اسلش — فقط اینکه داخل خود مخزن نگهداری می‌شوند.

برای سیستم کلی پلاگین‌ها صفحهٔ پلاگین‌ها و برای نوشتن پلاگین اختصاصی خودتان ساخت یک پلاگین هرمس را ببینید.

۱ نحوهٔ کشف پلاگین‌ها

‏PluginManager چهار منبع را به این ترتیب اسکن می‌کند:

  1. داخلی ‏(Bundled) — <repo>/plugins/<name>/ ‏(همان چیزی که این صفحه مستند می‌کند)
  2. کاربر — ~/.hermes/plugins/<name>/
  3. پروژه — ./.hermes/plugins/<name>/ ‏(نیازمند HERMES_ENABLE_PROJECT_PLUGINS=1)
  4. نقاط ورود Pip — hermes_agent.plugins

در برخورد نام، منابع بعدی برنده می‌شوند — یک پلاگین کاربری با نام disk-cleanup نسخهٔ داخلی را جایگزین می‌کند.

دایرکتوری‌های plugins/memory/ و plugins/context_engine/ عمداً از اسکن پلاگین‌های داخلی مستثنی شده‌اند. آن دایرکتوری‌ها مسیر کشف مخصوص خودشان را دارند چون ارائه‌دهندگان حافظه و موتورهای زمینه، ارائه‌دهنده‌های تک‌انتخابی هستند که از طریق hermes memory setup و context.engine در config پیکربندی می‌شوند.

۲ پلاگین‌های داخلی به‌صورت انتخابی فعال می‌شوند

پلاگین‌های داخلی غیرفعال ارسال می‌شوند. کشف، آنها را پیدا می‌کند (در hermes plugins list و رابط تعاملی hermes plugins ظاهر می‌شوند)، ولی هیچ‌کدام بارگذاری نمی‌شوند تا اینکه صریحاً فعالشان کنید:

hermes plugins enable disk-cleanup

یا از طریق ~/.hermes/config.yaml:

yaml
plugins:
  enabled:
    - disk-cleanup

این همان سازوکار پلاگین‌های نصب‌شدهٔ کاربر است. پلاگین‌های داخلی هیچ‌وقت خودکار فعال نمی‌شوند — نه روی نصب تازه، نه برای کاربران فعلی که به هرمس جدیدتر ارتقا می‌دهند. شما همیشه صریحاً انتخاب می‌کنید.

برای خاموش کردن دوبارهٔ یک پلاگین داخلی:

hermes plugins disable disk-cleanup
# یا: آن را از plugins.enabled در config.yaml حذف کنید

۳ پلاگین‌هایی که هم‌اکنون ارسال می‌شوند

مخزن این پلاگین‌های داخلی را زیر plugins/ ارائه می‌کند. همه انتخابی هستند — با hermes plugins enable <name> فعالشان کنید.

ارائه‌دهندگان حافظه (plugins/memory/*) و موتورهای زمینه (plugins/context_engine/*) جداگانه در صفحهٔ ارائه‌دهندگان حافظه فهرست شده‌اند — آنها از طریق hermes memory و hermes plugins مدیریت می‌شوند. جزئیات کامل هر پلاگین برای دو پلاگین بلندمدتِ هوک-محور در ادامه آمده است.

disk-cleanup

فایل‌های زودگذری که در طول نشست‌ها ساخته می‌شوند — اسکریپت‌های تست، خروجی‌های موقت، لاگ‌های cron، پروفایل‌های کهنه chrome — را به‌طور خودکار پیگیری و حذف می‌کند، بدون اینکه ایجنت لازم باشد یادش بماند ابزاری را صدا بزند.

نحوهٔ کار:

هوکرفتار
post_tool_callوقتی write_file / terminal / patch فایلی مطابق test_*، ‏tmp_* یا *.test.* داخل HERMES_HOME یا /tmp/hermes-* می‌سازد، آن را بی‌صدا به‌عنوان test / temp / cron-output پیگیری می‌کند.
on_session_endاگر در طول نوبت فایل تستی پیگیری شده باشد، پاکسازی امنِ quick را اجرا و خلاصه‌ای یک‌خطی لاگ می‌کند. در غیر این صورت ساکت می‌ماند.

قواعد حذف:

دستهآستانهتأیید
testپایان هر نشستهرگز
tempبیش از ۷ روز از پیگیریهرگز
cron-outputبیش از ۱۴ روز از پیگیریهرگز
دایرکتوری‌های خالی زیر HERMES_HOMEهمیشههرگز
researchبیش از ۳۰ روز، خارج از ۱۰ مورد جدیدترهمیشه (فقط deep)
chrome-profileبیش از ۱۴ روز از پیگیریهمیشه (فقط deep)
فایل‌های بالای ‎۵۰۰ MBهرگز خودکارهمیشه (فقط deep)

دستور اسلش — /disk-cleanup هم در نشست‌های CLI و هم گیت‌وی در دسترس است:

/disk-cleanup status                     # breakdown + top-10 largest
/disk-cleanup dry-run                    # preview without deleting
/disk-cleanup quick                      # run safe cleanup now
/disk-cleanup deep                       # quick + list items needing confirmation
/disk-cleanup track <path> <category>    # manual tracking
/disk-cleanup forget <path>              # stop tracking (does not delete)

وضعیت — همه‌چیز در $HERMES_HOME/disk-cleanup/ قرار دارد:

فایلمحتوا
tracked.jsonمسیرهای پیگیری‌شده همراه دسته، حجم و زمان
tracked.json.bakنسخهٔ پشتیبانِ نوشتن-اتمی موارد بالا
cleanup.logردپای ممیزیِ فقط-الحاقی از هر عملیات پیگیری / رد شدن / reject / حذف

ایمنی — پاکسازی فقط مسیرهای زیر HERMES_HOME یا /tmp/hermes-* را لمس می‌کند. مانت‌های ویندوز (/mnt/c/...) رد می‌شوند. دایرکتوری‌های وضعیت شناخته‌شدهٔ سطح-بالا (logs/، ‏memories/، ‏sessions/، ‏cron/، ‏cache/، ‏skills/، ‏plugins/ و خودِ disk-cleanup/) حتی وقتی خالی‌اند هرگز حذف نمی‌شوند — یک نصب تازه در اولین پایان نشست تخلیه نمی‌شود.

فعال‌سازی: ‏hermes plugins enable disk-cleanup ‏(یا تیک زدن در hermes plugins).

غیرفعال‌سازی دوباره: ‏hermes plugins disable disk-cleanup.

security-guidance

هشدارهای امنیتی سریع و مبتنی بر تطبیق الگو روی نوشتن فایل‌ها. وقتی فراخوانی‌های write_file / patch / skill_manage ایجنت محتوایی حمل کند که با یکی از الگوهای کدِ شناخته‌شدهٔ خطرناک تطبیق بخورد — ‏pickle.load، ‏yaml.load بدون SafeLoader، ‏eval(، ‏os.system، ‏subprocess(..., shell=True)، ‏child_process.exec جاوااسکریپت، ‏dangerouslySetInnerHTML ری‌اکت، ‏.innerHTML = / ‏.outerHTML = / ‏document.write خام، ‏crypto.createCipher در Node، حالت AES ECB، غیرفعال بودن تأیید TLS، پارسرهای مستعد XXE مثل xml.etree / minidom، ‏<script src="//..."> بدون SRI، ‏torch.load بدون weights_only=True، تزریق ${{ github.event.* }} در GitHub Actions — پلاگین یک بلوک «⚠️ Security guidance» به نتیجهٔ ابزار اضافه می‌کند.

فایل همچنان نوشته می‌شود. مدل هشدار را در پیام ابزارِ نوبت بعدی می‌خواند و می‌تواند یا کد را اصلاح کند یا مستند سازد که چرا این سازه در این زمینه امن است. تطبیق الگو نرخ مثبت-کاذب قابل توجهی دارد؛ به همین دلیل warn (و نه block) پیش‌فرض است.

پوشش: در مجموع ۲۵ قانون، شامل deserialization ناامن، تزریق فرمان، sinkهای XSS، خطاهای رایج رمزنگاری، XXE، زنجیرهٔ تأمین (SRI) و تزریق workflow در CI/CD. دادهٔ الگوها انشعاب عیناً Apache-2.0 از claude-plugins-official شرکت Anthropic است — برای مشخصات، فایل‌های LICENSE و NOTICE پلاگین را ببینید.

حالت‌ها:

متغیر محیطیاثر
(تنظیم‌نشده)حالت warn (پیش‌فرض) — فایل نوشته می‌شود و هشدار به نتیجه اضافه می‌گردد
SECURITY_GUIDANCE_BLOCK=1حالت block — نوشتن رد می‌شود و هشدار به‌عنوان دلیل بلاک برگردانده می‌شود
SECURITY_GUIDANCE_DISABLE=1کلید قطع — پلاگین بارگذاری می‌شود ولی کاری نمی‌کند

فعال‌سازی: ‏hermes plugins enable security-guidance ‏(یا تیک زدن در hermes plugins).

غیرفعال‌سازی دوباره: ‏hermes plugins disable security-guidance.

کاری که هنوز انجام نمی‌دهد: پلاگین بالادستی Anthropic دو لایهٔ دیگر دارد — بازبینی diff توسط LLM روی هر نوبتِ ایجنتی که فایل‌ها را لمس کرده، و یک بازبینی agentic در زمان commit که جریان داده را بین فایل‌ها دنبال می‌کند. هیچ‌کدام پرتاب نشده‌اند. ایجنت همین حالا هم می‌تواند این بازبینی‌ها را در صورت نیاز از طریق delegate_task اجرا کند.

observability/langfuse

نوبت‌های هرمس، فراخوانی‌های LLM و فراخوانی ابزارها را در Langfuse ردیابی می‌کند — یک پلتفرم متن‌باز observability برای LLM. یک span برای هر نوبت، یک generation برای هر فراخوانی API و یک مشاهدهٔ tool برای هر فراخوانی ابزار. جمع مصرف، تعداد توکن به تفکیک نوع و تخمین هزینه‌ها از اعداد مرجع agent.usage_pricing هرمس بیرون می‌آیند، پس داشبورد Langfuse همان تفکیک (input / output / cache_read_input_tokens / cache_creation_input_tokens / reasoning_tokens) را می‌بیند که در hermes logs ظاهر می‌شود.

این پلاگین fail-open است: نبود SDK، نبود اعتبارنامه یا خطای گذرای Langfuse — همه به یک no-op بی‌صدای داخل هوک تبدیل می‌شوند. حلقهٔ ایجنت هیچ‌وقت تحت تأثیر قرار نمی‌گیرد.

راه‌اندازی (تعاملی — پیشنهادشده):

hermes tools          # → Langfuse Observability → Cloud or Self-Hosted

ویزارد کلیدهایتان را جمع می‌کند، SDK ی langfuse را با pip install نصب می‌کند و observability/langfuse را برایتان به plugins.enabled اضافه می‌کند. هرمس را ری‌استارت کنید و نوبت بعدی یک trace ارسال می‌کند.

راه‌اندازی (دستی):

pip install langfuse
hermes plugins enable observability/langfuse

سپس اعتبارنامه‌ها را در ~/.hermes/.env بگذارید:

HERMES_LANGFUSE_PUBLIC_KEY=pk-lf-...
HERMES_LANGFUSE_SECRET_KEY=sk-lf-...
HERMES_LANGFUSE_BASE_URL=https://cloud.langfuse.com   # or your self-hosted URL

نحوهٔ کار:

هوکرفتار
pre_api_request / pre_llm_callیک span ریشهٔ «Hermes turn» به‌ازای هر نوبت باز (یا بازاستفاده) می‌کند. برای این فراخوانی API یک مشاهدهٔ فرزند generation با پیام‌های اخیر سریالایز‌شده به‌عنوان ورودی شروع می‌کند.
post_api_request / post_llm_callgeneration را می‌بندد و usage_details، ‏cost_details، ‏finish_reason، خروجی دستیار + فراخوانی ابزارها را الصاق می‌کند. اگر فراخوانی ابزاری نباشد و محتوا غیرخالی باشد، نوبت بسته می‌شود.
pre_tool_callیک مشاهدهٔ فرزند tool با args پاک‌سازی‌شده شروع می‌کند.
post_tool_callمشاهدهٔ tool را با result پاک‌سازی‌شده می‌بندد. payloadهای read_file خلاصه می‌شوند (سر + دم + تعداد خطوط حذف‌شده) تا خواندن یک فایل عظیم زیر سقف HERMES_LANGFUSE_MAX_CHARS بماند.

گروه‌بندی نشست از روی شناسهٔ نشست هرمس (یا شناسهٔ تسک برای زیرایجنت‌ها) از طریق langfuse.propagate_attributes کلید می‌خورد، پس همه‌چیز در یک نشست hermes chat زیر یک نشست Langfuse زندگی می‌کند.

تأیید:

hermes plugins list                 # observability/langfuse should show "enabled"
hermes chat -q "hello"              # check the Langfuse UI for a "Hermes turn" trace

تنظیم دقیق اختیاری (در .env):

متغیرپیش‌فرضهدف
HERMES_LANGFUSE_ENV—برچسب محیط روی traceها (production، ‏staging و…)
HERMES_LANGFUSE_RELEASE—برچسب release / نسخه
HERMES_LANGFUSE_SAMPLE_RATE1.0نرخ نمونه‌برداری پاس‌داده‌شده به SDK (۰٫۰ تا ۱٫۰)
HERMES_LANGFUSE_MAX_CHARS12000برش هر-فیلد برای محتوای پیام / args ابزار / نتایج ابزار
HERMES_LANGFUSE_DEBUGfalseلاگ پرحجم پلاگین در agent.log

هم متغیرهای با-پیشوند Hermes و هم متغیرهای استاندارد SDK (LANGFUSE_PUBLIC_KEY، ‏LANGFUSE_SECRET_KEY، ‏LANGFUSE_BASE_URL) پذیرفته می‌شوند — وقتی هر دو ست شده باشند پیشوند-دارِ هرمس برنده است.

کارایی: کلاینت Langfuse بعد از اولین فراخوانی هوک کش می‌شود. اگر اعتبارنامه یا SDK غایب باشد آن تصمیم هم کش می‌شود — هوک‌های بعدی بدون بررسی دوبارهٔ متغیرهای محیطی یا بارگذاری config سریع برمی‌گردند.

غیرفعال‌سازی: ‏hermes plugins disable observability/langfuse. ماژول پلاگین همچنان کشف می‌شود ولی تا فعال‌سازی مجدد هیچ کدی از ماژول اجرا نمی‌شود.

۴ یکپارچگی بومی NeMo Relay ‏(یادداشت مهاجرت)

‏NeMo Relay دیگر یک پلاگین داخلی هرمس نیست. دستور hermes plugins enable observability/nemo_relay را اجرا نکنید؛ هستهٔ هرمس اکنون مالک چرخه‌حیات Relay session، ‏turn، ‏LLM و tool است.

برای انتخاب middleware یا exporterهای Relay، یک plugins.toml استاندارد Relay بسازید و سپس پیش از شروع هرمس، HERMES_NEMO_RELAY_PLUGINS_TOML را روی آن فایل ست کنید. این سیاست برای کل پروسه و همهٔ پروفایل‌های میزبانی‌شده توسط آن پروسهٔ هرمس اعمال می‌شود. گزینه‌های ATOF، ‏ATIF و OpenTelemetry را در مستندات observability مربوط به NeMo Relay ببینید.

تنظیمات قدیمی HERMES_NEMO_RELAY_ATOF_* و HERMES_NEMO_RELAY_ATIF_* دیگر exporterها را فعال نمی‌کنند. وقتی plugins.toml جایگزینی انتخاب نشده باشد، دستور hermes doctor این تنظیمات کهنه را گزارش می‌کند.

بخش‌بندی span نشست ‏(نشست‌های پیوسته)

‏Relay یک span را هنگام بسته شدن scope آن export می‌کند. یک نشست گیت‌وی پیوسته ممکن است span نشستش را روزها باز نگه دارد، حتی اگر span هر نوبت به‌طور عادی export شود. بخش‌بندی اختیاری فقط scope نشست را در مرز یک نوبت می‌چرخاند:

yaml
gateway:
  telemetry:
    session_segments:
      on_compaction: false  # rotate after context compaction
      max_turns: 0          # 0 = unlimited; N = turns per segment
کلیدپیش‌فرضرفتار
on_compactionfalseپس از تکمیل فشرده‌سازی ‏(compaction)، در مرز نوبت بعدی می‌چرخد.
max_turns0بعد از هر N نوبتِ کامل‌شده می‌چرخد؛ ‏0 سقف را غیرفعال می‌کند.

هر دو پیش‌فرض یک scope نشست واحد را برای کل نشست حفظ می‌کنند. spanهای چرخیده همان session_id را نگه می‌دارند و hermes.session.segment به‌علاوهٔ hermes.session.segment_reason ‏(compaction یا max_turns) را اضافه می‌کنند.

۵ google_meet

به ایجنت اجازه می‌دهد به تماس‌های Google Meet بپیوندد، آنها را رونویسی و در آنها شرکت کند — یادداشت‌برداری از جلسه، خلاصه‌سازی گفت‌وگوها بعد از تماس، پیگیری نقاط مشخص و (به‌صورت اختیاری) گفتن پاسخ‌ها با TTS داخل خود تماس.

چه چیزی اضافه می‌کند:

  • یک شرکت‌کنندهٔ مجازی headless که با اتوماسیون مرورگر به URL ی Meet می‌پیوندد
  • رونویسی زندهٔ صدای جلسه از طریق ارائه‌دهندهٔ STT پیکربندی‌شده
  • مجموعه ابزار meet_join / meet_status / meet_transcript / meet_leave / meet_say که ایجنت برای پیوستن به تماس‌ها، پایش رونوشت زنده و عمل بر اساس شنیده‌ها فراخوانی می‌کند
  • محصولات پس از جلسه (رونوشت، وضعیت) زیر ~/.hermes/workspace/meetings/<meeting_id>/ ذخیره می‌شوند

راه‌اندازی:

hermes plugins enable google_meet
hermes meet setup   # preflight: playwright, chromium, auth file
hermes meet auth    # opens a browser to sign into Google and saves session state —
                    # needs a Google account with Meet access. Host approval may be
                    # required if the meeting enforces "only invited participants can join".

استفاده از داخل چت:

«Join meet.google.com/abc-defg-hij and take notes. After the call, send me a summary with action items.»

ایجنت پیوستن به جلسه را آغاز می‌کند، رونویسی را همزمان با پیشرفت تماس به زمینهٔ خودش استریم می‌کند و وقتی جلسه تمام شد (یا شما بگویید متوقف شود) یک خلاصهٔ ساختاریافته تولید می‌کند.

چه زمانی از آن استفاده کنید: استندآپ‌های تکرارشونده که می‌خواهید ربات برای غایبان، رونویسی + خلاصه بسازد؛ مصاحبه‌های بازجویی‌گونه که یادداشت ساختاریافته می‌خواهند؛ هر موردی که در آن مجبور بودید از Fireflies / Otter / Grain استفاده کنید. وقتی نمی‌خواهید یک AI به گفتگو گوش دهد — فعالش نکنید.

غیرفعال‌سازی: ‏hermes plugins disable google_meet. رونوشت‌های ذخیره‌شده تا وقتی خودتان حذفشان کنید در ~/.hermes/workspace/meetings/ می‌مانند.

۶ hermes-achievements

یک تب دستاوردهای به سبک Steam به داشبورد اضافه می‌کند — بیش از ۶۰ نشان کلکسیونی و طبقه‌بندی‌شده که از تاریخچهٔ واقعی نشست‌های هرمس شما ساخته می‌شوند. رکوردهای زنجیرهٔ ابزار، الگوهای دیباگ، رگبارهای vibe-coding، مصرف مهارت/حافظه، تنوع مدل/ارائه‌دهنده و رفتارهای سبک زندگی (نشست‌های آخر هفته و شبانه). در اصل توسط @PCinkusz به‌عنوان پلاگین خارجی نوشته شده بود و برای هماهنگ ماندن با تغییرات قابلیت‌های هرمس به داخل مخزن آورده شد.

نحوهٔ کار:

  • کل تاریخچهٔ نشست‌های ~/.hermes/state.db را در بک‌اند داشبورد اسکن می‌کند
  • آمار هر نشست با اثر انگشت (started_at, last_active) کش می‌شود، پس در اسکن‌های بعدی فقط نشست‌های جدید یا تغییرکرده دوباره تحلیل می‌شوند
  • اولین اسکن در یک thread پس‌زمینه اجرا می‌شود — داشبورد هیچ‌وقت منتظر آن نمی‌ماند، حتی روی پایگاه‌داده‌هایی با هزاران نشست
  • وضعیت باز شدن نشان‌ها در $HERMES_HOME/plugins/hermes-achievements/state.json ذخیره می‌شود

پیشرفت طبقات: مس ← نقره‌ای ← طلا ← الماس ← المپ‌بر. هر کارت بخش «What counts» دارد که معیار دقیق تحت پیگیری را فهرست می‌کند.

وضعیت‌های دستاورد:

وضعیتمعنا
Unlockedحداقل یک طبقه به دست آمده است
Discoveredدستاورد شناخته شده، پیشرفت قابل مشاهده است، هنوز کسب نشده
Secretپنهان می‌ماند تا هرمس اولین سیگنال مرتبط را در تاریخچهٔ شما آشکار کند

API — مسیرها زیر /api/plugins/hermes-achievements/ سوار می‌شوند:

نقطهٔ پایانیهدف
GET /achievementsکاتالوگ کامل همراه وضعیت باز شدن هر نشان (در حال اجرای اولین اسکن سرد، یک placeholder در انتظار برمی‌گرداند)
GET /scan-statusوضعیت اسکنر پس‌زمینه: idle / running / failed، آخرین مدت، تعداد اجرا
GET /recent-unlocksبیست نشان اخیراً باز‌شده، جدیدترین اول
GET /sessions/{id}/badgesنشان‌هایی که عمدتاً در یک نشست خاص کسب شده‌اند
POST /rescanاسکن مجدد دستی و همگام (بلاک می‌کند؛ برای کلیک کاربر روی دکمهٔ rescan)
POST /reset-stateپاک کردن تاریخچهٔ باز شدن‌ها و snapshot کش‌شده

فایل‌های وضعیت — زیر $HERMES_HOME/plugins/hermes-achievements/:

فایلمحتوا
state.jsonتاریخچهٔ باز شدن‌ها: کدام نشان‌ها و چه زمانی. در برابر به‌روزرسانی‌های هرمس پایدار است.
scan_snapshot.jsonآخرین payload اسکن کامل‌شده (هنگام بارگذاری داشبورد بلافاصله سرو می‌شود)
scan_checkpoint.jsonکش آمار هر-نشست کلیدخورده با اثر انگشت (rescanهای گرم را سریع می‌کند)

نکات کارایی:

  • اسکن سرد روی حدود ۸٬۰۰۰ نشست چند دقیقه طول می‌کشد. در اولین درخواست داشبورد در یک thread پس‌زمینه اجرا می‌شود؛ رابط کاربری placeholder در انتظار می‌بیند و /scan-status را poll می‌کند.
  • نتایج افزایشی حین اسکن سرد — اسکنر هر حدود ۲۵۰ نشست یک snapshot جزئی منتشر می‌کند تا هر بار refresh کردن داشبورد نشان‌های باز‌شدهٔ بیشتری در جریان اسکن ببینید. نه خیره شدن چند دقیقه‌ای به صفرها.
  • اسکن گرمِ مجدد آمار هر-نشست را برای هر نشستی که اثر انگشت started_at + last_active اش با checkpoint بخورد دوباره استفاده می‌کند — حتی روی تاریخچه‌های بزرگ در چند ثانیه تمام می‌شود.
  • TTL ی snapshot درون-حافظه ۱۲۰ ثانیه است؛ درخواست‌های کهنه فوراً snapshot قبلی را می‌گیرند و یک refresh پس‌زمینه راه می‌افتد. هیچ‌وقت فقط به این دلیل که TTL منقضی شده پشت spinner منتظر نمی‌مانید.

فعال‌سازی: چیزی برای فعال کردن نیست — ‏hermes-achievements یک پلاگین فقط-داشبوردی است (بدون هوک‌های چرخه‌حیات، بدون ابزار قابل‌مشاهده برای مدل). در اولین اجرای hermes dashboard خودکار به‌عنوان تب ثبت نام می‌شود. پیکربندی plugins.enabled فقط پلاگین‌های lifecycle/tool را گیت می‌کند؛ پلاگین‌های داشبورد صرفاً از طریق dashboard/manifest.json خود کشف می‌شوند.

انصراف: فایل plugins/hermes-achievements/dashboard/manifest.json را حذف یا rename کنید، یا آن را با یک پلاگین کاربری همنام در ~/.hermes/plugins/hermes-achievements/ که داشبوردی ندارد بازنویسی کنید. فایل‌های وضعیت پلاگین زیر $HERMES_HOME/plugins/hermes-achievements/ باقی می‌مانند — نصب دوباره، تاریخچهٔ باز شدن‌هایتان را حفظ می‌کند.

۷ افزودن یک پلاگین داخلی

پلاگین‌های داخلی دقیقاً مثل هر پلاگین دیگری هرمس نوشته می‌شوند — بخش ساخت یک پلاگین هرمس را ببینید. تنها تفاوت‌ها:

  • دایرکتوری به‌جای ~/.hermes/plugins/<name>/ در <repo>/plugins/<name>/ قرار می‌گیرد
  • منبع manifest در hermes plugins list به‌صورت bundled گزارش می‌شود
  • پلاگین‌های کاربری همنام، نسخهٔ داخلی را بازنویسی می‌کنند

یک پلاگین وقتی نامزد خوبی برای داخلی شدن است که:

  • وابستگی اختیاری نداشته باشد (یا آنها از قبل جزو pip install .[all] باشند)
  • رفتارش برای بیشتر کاربران سودمند باشد و به‌جای opt-in از نوع opt-out باشد
  • منطقش به هوک‌های چرخه‌حیات گره بخورد که ایجنت در غیر این صورت باید خودش یادش می‌ماند فراخوانی کند
  • یک قابلیت هسته را کامل کند بدون اینکه سطح ابزارهای قابل‌مشاهده برای مدل را بزرگ کند

مثال‌های نقض — چیزهایی که باید به‌صورت پلاگین قابل‌نصب توسط کاربر بمانند نه داخلی: یکپارچه‌سازی‌های ثالث دارای کلید API، گردش‌کارهای خاص و کم‌مصرف، درخت‌های وابستگی بزرگ، و هر چیزی که به‌طور محسوس رفتار ایجنت را به‌صورت پیش‌فرض تغییر دهد.
