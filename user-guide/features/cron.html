کارهای زمان‌بندی‌شده ‏(Cron)

کارها را با زبان طبیعی یا عبارات cron برای اجرای خودکار زمان‌بندی کنید. هرمس مدیریت کرون را از طریق یک ابزار واحدِ ‏cronjob با عملیات سبک-اقدامی expose می‌کند به‌جای ابزارهای جدای schedule/list/remove.

۱ کرون الان چه کارهایی می‌تواند بکند

کارهای کرون می‌توانند:

  • کارهای یک‌باره یا تکرارشونده را زمان‌بندی کنند
  • job ها را مکث، ازسرگیری، ویرایش، اجرا و حذف کنند
  • صفر، یک یا چند مهارت را به یک job الصاق کنند
  • نتایج را به چت مبدأ، فایل‌های محلی یا هدف‌های پلتفرمی پیکربندی‌شده تحویل دهند
  • در نشست‌های تازهٔ ایجنت با فهرست ایستای عادی ابزارها اجرا شوند
  • در حالت بدون-ایجنت اجرا شوند — یک اسکریپت طبق زمان‌بندی که خروجی stdout آن تحت‌اللفظی تحویل می‌شود، بدون هیچ دخالت LLM ‏(بخش «حالت بدون-ایجنت» پایین را ببینید)

همهٔ این‌ها برای خود هرمس هم از طریق ابزار ‏cronjob در دسترس است، پس می‌توانید با پرسیدن به زبان ساده job بسازید، مکث، ویرایش و حذف کنید — بدون CLI.

💡 کدام مدل روی یک کار کرون اجرا می‌شود؟

ترتیب حل هنگام شلیک: pin به‌ازای-job ← ‏cron.model در config.yaml ← پیش‌فرض سراسری از ‏hermes model.

  • Pin به‌ازای-job — توسط *خودتان* از داشبورد، ‏hermes cron create/edit --model … --provider … یا ویرایش ‏~/.hermes/cron/jobs.json تنظیم می‌شود. بعد از تنظیم تا تغییر شما می‌ماند. ابزار ‏cronjob ایجنت نمی‌تواند مدل به‌ازای-job را ست یا عوض کند — pin های inference متعلق به کاربرند.
  • ‏cron.model/cron.model_provider — پیش‌فرض ناوگان-کرون: هر job بدون-pin روی این مدل اجرا می‌شود مستقل از مدل چت شما. یک‌بار ست کنید ‏(hermes config set cron.model <name>) و تغییر مدل چت با ‏hermes model یا ‏/model هرگز به ناوگان کرونتان دست نمی‌زند.
  • پیش‌فرض سراسری — فقط وقتی هیچ‌کدام از بالا تنظیم نباشد job دنبال ‏hermes model می‌رود. در این حالت هرمس ارائه‌دهنده و مدل را هنگام ساخت snapshot می‌کند و اگر پیش‌فرض سراسری بعداً عوض شود job fail-closed می‌شود: اجرا را رد، فراخوانی inference نمی‌زند و یک‌بار هشدارتان می‌دهد — job روی تیک‌های بعدی رد‌شده ‏(و بی‌صدا) می‌ماند تا اقدام کنید یا پیکربندی برگردد ‏(#44585). برای job های تکرارشونده صریحاً provider/model را pin کنید ‏(hermes cron edit <job_id> --provider <provider> --model <model>). یک one-shot مصرف‌شدهٔ متناهی قابل به‌روزرسانی نیست؛ به‌جایش یک one-shot آیندهٔ جدید با provider و model صریح بسازید. این مانع می‌شود job بی‌نگهبان بی‌صدا به تعویض به یک ارائه‌دهنده/مدل پرداخت‌دار ارث برساند. گذاشتن ‏cron.model ‏(یا pin به‌ازای-job) راه آگاهانه مسیریابی هزینهٔ کرون است و نگهبان-رانش برای محورِ تحت‌پوشش فعال نمی‌شود. اپراتورهایی که می‌خواهند job های بدون-pin دنبال پیش‌فرض سراسریِ متغیر بروند می‌توانند نگهبان رانش را خاموش کنند.

‏hermes setup --portal کمترین اصطکاک را برای اجراهای بی‌نگهبان دارد چون refresh ‏OAuth خودکار است. بخش Nous Portal را ببینید.

💡 سطح استدلال به‌ازای-job

یک job می‌تواند سطح تفکر خودش را مستقل از pin مدل قفل کند: یکی از ‏none، ‏minimal، ‏low، ‏medium، ‏high، ‏xhigh، ‏max، ‏ultra. با تنظیم شدن، هم ‏agent.reasoning_effort سراسری و هم ‏agent.reasoning_overrides به‌ازای-مدل را برای اجراهای همان job override می‌کند ‏(none تفکر را خاموش می‌کند). با ‏hermes cron create/edit --reasoning-effort high ست کنید؛ هنگام ویرایش رشتهٔ خالی بدهید تا pin پاک و دوباره از config پیروی شود. ‏(عمداً روی ابزار ‏cronjob ایجنت expose نشده — پیکربندی مدل تصمیم کاربر می‌ماند.) سطح‌هایی که مدل پشتیبانی نمی‌کند توسط ارائه‌دهنده هنگام درخواست clamp یا حذف می‌شوند — pin کردن ‏xhigh روی مدلی که سقفش high است با high اجرا می‌شود. این pin روی job های ‏no_agent اثری ندارد ‏(فراخوانی LLM‌ای برای تنظیم نیست). از آن استفاده کنید تا تحلیل‌های سنگین زمان‌بندی‌شده روی ‏high و کارهای تکراری ارزان روی ‏minimal اجرا شوند بدون دست زدن به پیش‌فرض سراسری‌تان.

⚠️ هشدار

نشست‌های اجراشده-با-کرون نمی‌توانند بازگشتی کار کرون بیشتری بسازند. هرمس ابزارهای مدیریت کرون را داخل اجراهای کرونی خاموش می‌کند تا جلوگیری از حلقه‌های زمان‌بندی سرکش.

۲ ساخت کارهای زمان‌بندی‌شده

در چت با ‏/cron

bash
/cron add 30m "Remind me to check the build"
/cron add "every 2h" "Check server status"
/cron add "every 1h" "Summarize new feed items" --skill blogwatcher
/cron add "every 1h" "Use both skills and combine the result" --skill blogwatcher --skill maps

از CLI مستقل

bash
hermes cron create "every 2h" "Check server status"
hermes cron create "every 1h" "Summarize new feed items" --skill blogwatcher
hermes cron create "every 1h" "Use both skills and combine the result" \
  --skill blogwatcher \
  --skill maps \
  --name "Skill combo"

عادی از هرمس بخواهید:

Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram.

هرمس داخلش از ابزار یکپارچهٔ ‏cronjob استفاده خواهد کرد.

۳ اعتبارسنجی پیش-از-dispatch پیکربندی

قبل از ساخت هر ماشین ایجنتی برای یک اجرای زمان‌بندی‌شده، زمان‌بند اعتبارسنجی می‌کند پیکربندی job واقعاً بتواند اجرای موفق تولید کند:

  • کلید API ارائه‌دهنده حل شود ‏(وقتی زنجیرهٔ ‏fallback_providers پیکربندی شده رد می‌شود چون مسیر fallback ممکن است کلید اصلی غایب را نجات دهد)،
  • مهارت‌های الصاقی آماده باشند ‏(بدون متغیر محیطی، فرمان یا فایل اعتبارنامهٔ الزامیِ غایب)،
  • هدف‌های پلتفرم تحویل شناخته و دارای اعتبارنامهٔ گیت‌وی باشند ‏(هدف‌های ‏local/origin هرگز چک نمی‌شوند).

وقتی اعتبارسنجی شکست بخورد، ‏last_status مربوط به job مقدار ‏blocked_config می‌گیرد، یک هشدار تحویل می‌شود ‏(هر تیک تکرار نمی‌شود) و هیچ فراخوانی LLM زده نمی‌شود — یک job بدپیکربندی هرگز توکن خرج نمی‌کند. اولین اجرای سالم وضعیت بلوک را پاک می‌کند تا شکست پیکربندی بعدی دوباره هشدار بدهد.

برای غیرفعال‌کردن اعتبارسنجی و بازگرداندن رفتار قدیمی ‏(اجرا ادامه یابد و حین اجرا بشکند):

yaml
cron:
  preflight: false

یا: ‏hermes config set cron.preflight false

۴ اجازه به job های بدون-pin برای دنبال‌کردن پیش‌فرض‌های سراسری

نگهبان رانش مدل/ارائه‌دهنده پیش‌فرض روشن است. اگر job های بدون-pin کرونتان باید عمداً هر تغییر سراسری مدل یا ارائه‌دهنده را دنبال کنند، در config.yaml خاموشش کنید:

yaml
cron:
  model_drift_guard: false

یا با فرمان پیکربندی:

hermes config set cron.model_drift_guard false

این هم بلوک runtime هم هشدارِ نمایش‌داده‌شده هنگام تغییر تنظیمات سراسری inference را خاموش می‌کند. snapshot های موجود همچنان ذخیره می‌مانند، پس برگرداندن گزینه به ‏true حفاظت را بدون بازسازی job ها دوباره فعال می‌کند.

⚠️ هشدار

با خاموش بودن نگهبان، job های بدون-pinِ بی‌نگهبان فوراً پیش‌فرض‌های سراسریِ عوض‌شده را ارث می‌برند. پس تعویض به ارائه‌دهنده یا مدل پرداخت‌دار می‌تواند روی هر اجرای زمان‌بندی‌شده پول خرج کند.

۵ کارهای کرون پشتیبان-مهارت

یک کار کرون می‌تواند قبل از اجرای پرامپت یک یا چند مهارت بارگذاری کند.

تک مهارت

python
cronjob(
    action="create",
    skill="blogwatcher",
    prompt="Check the configured feeds and summarize anything new.",
    schedule="0 9 * * *",
    name="Morning feeds",
)

چند مهارت

مهارت‌ها به ترتیب لود می‌شوند. پرامپت تبدیل به دستورالعمل کارِ لایه‌گذاری‌شده روی آن مهارت‌ها می‌شود.

python
cronjob(
    action="create",
    skills=["blogwatcher", "maps"],
    prompt="Look for new local events and interesting nearby places, then combine them into one short brief.",
    schedule="every 6h",
    name="Local brief",
)

وقتی مفید است که بخواهید یک ایجنت زمان‌بندی‌شده گردش‌کارهای قابل‌استفاده-مجدد ارث ببرد بدون اینکه متن کامل مهارت را داخل خود پرامپت کرون بچپانید.

۶ اجرای job داخل یک پوشهٔ پروژه

کارهای کرون پیش‌فرض جدا از هر repo ای اجرا می‌شوند — هیچ ‏AGENTS.md، ‏CLAUDE.md یا ‎.cursorrules لود نمی‌شود و ابزارهای ترمینال/فایل/اجرای-کد از هر پوشهٔ کاری که گیت‌وی در آن شروع شده اجرا می‌شوند. ‏--workdir ‏(CLI) یا ‏workdir= ‏(فراخوانی ابزار) را بدهید تا عوض شود:

bash
# Standalone CLI (schedule و prompt موقعیتی‌اند)
hermes cron create "every 1d at 09:00" \
  "Audit open PRs, summarize CI health, and post to #eng" \
  --workdir /home/me/projects/acme
python
# From a chat, via the cronjob tool
cronjob(
    action="create",
    schedule="every 1d at 09:00",
    workdir="/home/me/projects/acme",
    prompt="Audit open PRs, summarize CI health, and post to #eng",
)

وقتی ‏workdir تنظیم باشد:

  • ‏AGENTS.md، ‏CLAUDE.md و ‎.cursorrules آن پوشه داخل پرامپت سیستمی تزریق می‌شوند ‏(همان ترتیب کشف CLI تعاملی)
  • ‏terminal، ‏read_file، ‏write_file، ‏patch، ‏search_files و ‏execute_code همه آن پوشه را پوشهٔ کاری خودشان می‌گیرند
  • مسیر باید پوشهٔ مطلق موجود باشد — مسیرهای نسبی و پوشه‌های غایب هنگام create/update رد می‌شوند
  • هنگام ویرایش ‏--workdir "" ‏(یا ‏workdir="" از طریق ابزار) بدهید تا پاک و رفتار قبلی برگردد
📌 سریال‌سازی

job های دارای ‏workdir روی تیک زمان‌بند به‌طور متوالی اجرا می‌شوند نه در pool موازی. عمدی است: worker کرون workdir مربوط به job را از طریق وضعیت terminal سطح-پروسه اعمال می‌کند، پس دو job دارای-workdir که هم‌زمان اجرا شوند cwd همدیگر را خراب می‌کنند. job های بدون-workdir مثل قبل موازی اجرا می‌شوند.

۷ ویرایش job ها

لازم نیست صرفاً برای تغییر دادن، job را حذف و دوباره بسازید.

💡 ارجاع به job

placeholder ‏<job_id> در پایین ‏(و در «اقدامات چرخهٔ حیات») نام job را هم می‌پذیرد ‏(بی‌حساس-به-حروف) — وقتی ‏morning-digest را یادتان هست ولی شناسهٔ hex را نه کاربردی است. تطبیق دقیق ID بر تطبیق نام مقدم است؛ اگر مرجع ID نباشد و نامی با بیش از یک job بخواند فرمان امتناع و شناسه‌های کاندیدا را چاپ می‌کند تا مشخص کنید.

چت

bash
/cron edit <job_id> --schedule "every 4h"
/cron edit <job_id> --prompt "Use the revised task"
/cron edit <job_id> --skill blogwatcher --skill maps
/cron edit <job_id> --remove-skill blogwatcher
/cron edit <job_id> --clear-skills

CLI مستقل

bash
hermes cron edit <job_id> --schedule "every 4h"
hermes cron edit <job_id> --prompt "Use the revised task"
hermes cron edit <job_id> --skill blogwatcher --skill maps
hermes cron edit <job_id> --add-skill maps
hermes cron edit <job_id> --remove-skill blogwatcher
hermes cron edit <job_id> --clear-skills

یادداشت‌ها:

  • تکرار ‏--skill فهرست مهارت‌های الصاقی job را جایگزین می‌کند
  • ‏--add-skill به فهرست موجود می‌افزاید بدون جایگزینی
  • ‏--remove-skill مهارت‌های مشخص الصاقی را حذف می‌کند
  • ‏--clear-skills همهٔ مهارت‌های الصاقی را حذف می‌کند

۸ اقدامات چرخهٔ حیات

کارهای کرون الان چرخهٔ حیات کامل‌تری از فقط ساختن/حذف دارند.

چت

bash
/cron list
/cron pause <job_id>
/cron resume <job_id>
/cron run <job_id>
/cron remove <job_id>

CLI مستقل

bash
hermes cron list
hermes cron pause <job_id_or_name>
hermes cron resume <job_id_or_name>
hermes cron run <job_id_or_name>
hermes cron remove <job_id_or_name>
hermes cron edit <job_id_or_name> [...flags]
hermes cron status
hermes cron tick

چه می‌کنند:

  • ‏pause — job را نگه می‌دارد ولی زمان‌بندی‌اش را متوقف می‌کند
  • ‏resume — job را دوباره فعال و اجرای آیندهٔ بعدی را حساب می‌کند
  • ‏run — job را در تیک بعدی زمان‌بند تریگر می‌کند
  • ‏remove — کاملاً حذفش می‌کند
  • ‏edit — زمان‌بندی، پرامپت، تحویل و... را تغییر می‌دهد

جست‌وجوی مبتنی بر نام. هر چهار فعل تغییردهنده ‏(pause، ‏resume، ‏run، ‏remove، ‏edit) به‌اضافهٔ ابزار ‏cronjob ایجنت الان نام job ‏(بی‌حساس-به-حروف) را به‌جای ID هگز می‌پذیرند. ایجنت و CLI هر دو اگر تطبیق دقیق ID موجود باشد همان را ترجیح می‌دهند؛ تطبیق‌های مبهم نام ‏(چند job هم‌نام) با فهرست کامل شناسه‌های کاندیدا رد می‌شود تا صریحاً انتخاب کنید. نام‌ها یکتا نیستند، پس این محافظ بار-بر است — مانع تغییر بی‌صدای job اشتباه وقتی دو تا هم‌نام‌اند.

۹ زمان‌بندی اداره‌شده-با-ایجنت ‏(کارهای کرونی که کار کرون مدیریت می‌کنند)

به‌طور پیش‌فرض ایجنت‌هایی که توسط زمان‌بند launch می‌شوند نمی‌توانند از ابزار ‏cronjob استفاده کنند — یک کار زمان‌بندی‌شده نمی‌تواند job های دیگر بسازد، ویرایش یا حذف کند. از طریق config.yaml انتخاب کنید:

yaml
cron:
  allow_agent_scheduling: true   # پیش‌فرض: false

با فعال شدن، یک ایجنت زمان‌بندی‌شده می‌تواند جدول کرون را مثل هر نشست چتی مدیریت کند: از داخل کارِ زمان‌بندی‌شده one-shot های پیگیری زمان‌بندی کند، ضرباهجه خودش را تنظیم کند، یا یک job «کتابدار کرون» اجرا کند که کل جدول را آشتی می‌دهد ‏(اول list، بعد update/remove/create طبق نیاز). دو ویژگی این را منطقی نگه می‌دارد:

  • یک جدول تختِ متعلق-به-کاربر. job های ساخته‌شده از یک اجرای کرونی داخل همان ‏jobs.json بقیه می‌روند بدون مالکیت خاص — دقیقاً انگار خودتان ساخته‌اید می‌توانید list/edit/remove‌شان کنید.
  • بدون تحویل معلق. یک اجرای کرونی گذراست، پس ‏deliver: origin از داخلش هنگام ساخت به هدف عینیِ خودِ job سازنده حل می‌شود ‏(platform:chat_id[:thread_id]، یا ‏local اگر job سازنده جایی تحویل ندهد). job ساخته‌شده توسط ایجنت زمان‌بندی‌شده هرگز نمی‌تواند خروجیش را به نشستی که دیگر وجود ندارد اشاره دهد. هدف‌های صریح ‏(local، ‏all، ‏telegram:<chat_id>) عیناً محترم شمرده می‌شوند.

پرامپت‌هایی را ترجیح دهید که job های موجود را به‌روز می‌کنند ‏(اول list، بعد update با ID) بر پرامپت‌هایی که هر بار job جدید می‌سازند.

۱۰ نحوهٔ کار

اجرای کرون توسط دیمن گیت‌وی هندل می‌شود. گیت‌وی هر ۶۰ ثانیه زمان‌بند را تیک می‌زند و job های سررسید را در نشست‌های ایجنتی ایزوله اجرا می‌کند.

bash
hermes gateway install     # نصب به‌عنوان سرویس کاربر
sudo hermes gateway install --system   # لینوکس: سرویس سیستمی زمان-بوت برای سرورها
hermes gateway             # یا اجرا در پیش‌زمینه

hermes cron list
hermes cron status

در هر تیک هرمس:

  1. job ها را از ‏~/.hermes/cron/jobs.json لود می‌کند
  2. ‏next_run_at را با زمان فعلی مقایسه می‌کند
  3. برای هر job سررسید یک نشست تازهٔ ‏AIAgent شروع می‌کند
  4. به‌صورت اختیاری یک یا چند مهارت الصاقی داخل آن نشست تازه تزریق می‌کند
  5. پرامپت را تا تکمیل اجرا می‌کند
  6. پاسخ نهایی را تحویل می‌دهد
  7. متادیتای اجرا و زمان‌بندی بعدی را به‌روز می‌کند

یک قفل فایل در ‏~/.hermes/cron/.tick.lock مانع می‌شود تیک‌های هم‌پوشان زمان‌بند همان batch از job ها را دوبار اجرا کنند.

تاریخچهٔ اجرا

هرمس هر تلاش کرونیِ گرفته‌شده را قبل از dispatch مجری یا ارائه‌دهنده در ‏~/.hermes/cron/executions.db محلی-پروفایل ثبت می‌کند. تلاش‌ها از ‏claimed، ‏running و یک وضعیت پایانی تغییرناپذیر عبور می‌کنند: ‏completed، ‏failed یا ‏unknown. بعد از ری‌استارت هرمس یک تلاش رهاشده را فقط وقتی ‏unknown علامت می‌زند که PID اصلی و fingerprint شروع-پروسه ثابت کنند مالکش رفته. تلاش‌های unknown رکورد حسابرسی‌اند و هرگز خودکار rerun نمی‌شوند.

تلاش‌های اخیر را با ‏hermes cron runs [job-id] --limit 20 بازرسی کنید ‏(alias: ‏history). تاریخچهٔ پایانی bounded است؛ تلاش‌های فعال هرگز هرس نمی‌شوند. دفتر در بکاپ‌های سریع گنجانده می‌شود.

سرکش بازبینی شکست‌های مکرر

هر job یک ‏failure_streak ردیابی می‌کند — اجراهای متوالی شکست‌خورده ‏(شکست‌های تحویل حساب نمی‌شوند). اجرایی که قبل از رسیدن به ایجنت اصلاً شکست بخورد — ایمپورت بد بعد از به‌روزرسانی نصفه-اعمال‌شده، کلاینت ارائه‌دهنده‌ای که نتوان ساخت — حساب و مثل اجرایی که خود ایجنت شکستش داده هشدار می‌دهد. وقتی streak یک job تکرارشونده به آستانه برسد، پیام شکستِ تحویل‌شده به چت یک سرکش بازبینی می‌گیرد که می‌گوید job پشت‌سرهم N بار شکست خورده و پیشنهاد می‌کند رفع، مکث ‏(hermes cron pause <job>) یا حذفش کنید. هر اجرای موفق streak را ریست می‌کند و ‏hermes cron list کنار آخرین اجرای job در حال شکست، streak را نشان می‌دهد. job های one-shot هرگز سرکش نمی‌زنند.

yaml
cron:
  failure_nudge_threshold: 3   # پیش‌فرض؛ 0 سرکش را خاموش می‌کند

تحویل Bot Chat ‏(bot-chat)

‏bot-chat خروجی را به‌عنوان یک پیام واقعی داخل نشست مرجع «Bot Chat» یک پروفایل تحویل می‌دهد. برخلاف همهٔ هدف‌های دیگر — که گیرنده‌شان انسانی است که یک کانال را می‌خواند — گیرنده اینجا خود بات است: خروجی را به‌عنوان پیام ورودی می‌گیرد، هر چه نیازمند اقدام است انجام و در چتش پاسخ می‌دهد. وقتی استفاده کنید که خروجی زمان‌بندی‌شده باید پردازش شود نه فقط پست.

  • ‏bot-chat ‏(لخت) پروفایل خود job را هدف می‌گیرد.
  • ‏bot-chat:<profile> پروفایل دیگری را روی همان ماشین هدف می‌گیرد. نام‌ها هنگام ساخت job نسبت به ‏hermes profile list اعتبارسنجی می‌شوند؛ پروفایل‌های روی گیت‌وی‌ها یا ماشین‌های دیگر هرگز قابل هدف‌گیری نیستند، پس پروفایل‌های هم‌نام بین ماشین‌ها مبهم نیستند.
  • هر تحویل یک نوبت کامل ایجنت از بات هدف می‌گیرد — به فراوانی زمان‌بندی توجه کنید.
  • با هدف‌های دیگر ترکیب می‌شود ‏(bot-chat,telegram) ولی هرگز داخل ‏all گنجانده نمی‌شود.

نیت مسیریابی ‏(all)

‏all اجازه می‌دهد یک کار کرون را به همهٔ کانال‌های پیام‌رسانی پیکربندی‌شده‌تان بفرستید بدون شمارش دستی‌شان. هنگام شلیک حل می‌شود، پس job ای که قبل از سیم‌کشی تلگرام ساخته شده، در تیک بعدیِ گذاشتن ‏TELEGRAM_HOME_CHANNEL تلگرام را برمی‌دارد.

معناشناسی: ‏all به هر پلتفرمی با کانال خانگی پیکربندی‌شده باز می‌شود. صفر هم اوکی است؛ job صرفاً هیچ هدف تحویلی تولید نمی‌کند و بالادستی به‌عنوان شکست تحویل ثبت می‌شود.

‏all با هدف‌های صریح ترکیب می‌شود. ‏origin,all به چت مبدأ + همهٔ کانال‌های خانگی متصل دیگر تحویل می‌دهد، با حذف تکرار بر اساس ‏(platform, chat_id, thread_id).

تاپیک کرون تلگرام ‏(TELEGRAM_CRON_THREAD_ID)

وقتی حالت تاپیک تلگرام فعال است، DM ریشه به‌عنوان لابی سیستم رزرو می‌شود — ریپلای‌های فرستاده‌شده به آن با یادآوری لابی رد و ‏reply_to_message_id دور انداخته می‌شود، پس نمی‌توانید به پیام کرونی که در چت اصلی نشسته ریپلای بدهید.

کرون را به یک تاپیک فروم اختصاصی اشاره دهید:

  1. در تلگرام DM بات را باز و تاپیکی مثلاً به نام ‏Cron بسازید. سربرگ تاپیک را لمس طولانی ← Copy link؛ عدد انتهایی همان ‏message_thread_id تاپیک است.
  2. ‏TELEGRAM_CRON_THREAD_ID=<that id> را در .env بگذارید.

این فقط روی تحویل‌های کرون اعمال می‌شود. ‏TELEGRAM_HOME_CHANNEL_THREAD_ID ‏(که جای دیگر استفاده می‌شود مثل اعلان‌های ری‌استارت) تغییری نمی‌کند. هدف‌های صریح ‏deliver="telegram:chat_id:thread_id" همچنان بر env مقدم‌اند. ریپلای‌های پیام‌های کرون حالا در نشست تاپیک موجود می‌آیند تا مستقیم رویشان عمل کنید.

پیچیدن پاسخ

به‌طور پیش‌فرض خروجی کرونیِ تحویل‌شده با سربرگ و فوتر پیچیده می‌شود تا گیرنده بداند از یک کار زمان‌بندی‌شده آمده:

text
Cronjob Response: Morning feeds
-------------

<agent output here>

Note: The agent cannot see this message, and therefore cannot respond to it.

برای تحویل خروجی خام ایجنت بدون پیچیدگی، ‏cron.wrap_response را ‏false کنید:

yaml — ~/.hermes/config.yaml
cron:
  wrap_response: false

کارهای قابل-ادامه ‏(ریپلای به یک تحویل کرونی)

به‌طور پیش‌فرض تحویل کرونی fire-and-forget است: پیام فرستاده می‌شود ولی در تاریخچهٔ گفتگوی چت زندگی نمی‌کند، پس اگر ریپلای بدهید ایجنت هیچ رکوردی از گفته‌اش ندارد. یک job را قابل-ادامه کنید و خلاصهٔ تحویل‌شده به گفتگویی تبدیل می‌شود که می‌توانید واردش ریپلای بدهید — ایجنت خلاصه را داخل زمینه دارد به‌جای پرسیدن «Task #2 چیست؟».

انتخابی، پیش‌فرض خاموش. سراسری در config یا به‌ازای job از طریق ‏attach_to_session ابزار ‏cronjob فعال کنید ‏(که برای همان یک job تنظیم سراسری را override می‌کند):

yaml — ~/.hermes/config.yaml
cron:
  mirror_delivery: false   # true کنید تا تحویل‌های کرون قابل-ادامه شوند

رفتار ترد-محور است و به چت مبدأِ job محدود:

  • پلتفرم‌های توانمند-ترد ‏(تاپیک‌های تلگرام، تردهای دیسکورد/اسلک): هر تحویل ترد اختصاصی خودش را باز و خلاصه در نشست همان ترد seed می‌شود، پس ریپلای داخل ترد با زمینهٔ کامل ادامه می‌یابد. یک job تکرارشونده ‏(مثل خلاصهٔ روزانه) به‌ازای هر اجرا ترد تازه‌ای باز می‌کند و بحث پیگیری هر تحویل ایزوله می‌ماند.
  • پلتفرم‌های فقط-DM ‏(واتساپ، سیگنال، SMS): تردی وجود ندارد، پس خلاصه به‌جایش در نشست DM مبدأ mirror می‌شود — خود DM سطح ادامه است.

فقط چت مبدأ دست‌خوش می‌شود: هدف‌های fan-out/broadcast ‏(all، تحویل‌های صریح چت دیگر) هرگز قابل-ادامه نمی‌شوند. mirror به‌عنوان یک نوبت کاربر برچسب‌دار نوشته می‌شود ‏([Cron delivery: <task name>]) که تاریخچهٔ گفتگو را در همهٔ ارائه‌دهندگان مدل alternation-safe نگه می‌دارد.

ادامهٔ تخت درون-کانالی ‏(Slack)

رفتار ترد-محور بالا در هر تحویل یک ترد اختصاصی ضرب می‌کند. اگر ترجیح می‌دهید job قابل-ادامه تخت در خط‌زمان کانال بنشیند — بدون ترد — سطح قابل-ادامهٔ اسلک را روی ‏in_channel بگذارید:

yaml — ~/.hermes/config.yaml
slack:
  cron_continuable_surface: in_channel   # پیش‌فرض: thread
  reply_in_thread: false                 # جفت‌سازی لازم (پایین را ببینید)
  require_mention: false                 # تا یک ریپلای ساده کار را ادامه دهد

در حالت ‏in_channel خلاصه به‌عنوان یک پیام معمولی سطح‌بالای کانال تحویل می‌شود ‏(تردی باز نمی‌شود) و ریپلای شما کار را از طریق نشست مشترک کانال ادامه می‌دهد. سه تنظیم با هم کار می‌کنند:

  • ‏cron_continuable_surface: in_channel — ساخت ترد هنگام تحویل را رد می‌کند.
  • ‏reply_in_thread: false ‏(لازم) — بات را وامی‌کند ریپلایتان را تخت در کانال جواب دهد و به همان نشست تمام-کانالی که خلاصه درش seed شده کلید بخورد. بدون آن ادامه هنوز کار می‌کند ولی داخل ترد می‌رسد ‏(امن به ادامهٔ سبک-ترد fallback می‌شود، هرگز ریپلای دورریخته نیست — گیت‌وی در شروع هشدار لاگ می‌کند تا عدم‌تطبیق را ببینید).
  • ‏require_mention: false ‏(یا افزودن کانال به free_response_channels) — تا با پیام ساده ریپلای بدهید؛ وگرنه بات فقط وقتی بیدار می‌شود که در هر ریپلای @منشنش کنید.

چون ادامه، نشست تمام-کانال است، مشترک است: چت‌وچورت دیگر کانال — و job دومِ قابل-ادامهٔ درون-کانالی — به همان گفتگوی چرخشی می‌پیوندند. این ذات «تخت در یک کانال» است و همان موازنه‌ای که کاربران ‏reply_in_thread: false قبلاً می‌پذیرند؛ وقتی پیگیریِ هر تحویل را ایزوله می‌خواهید سطح پیش‌فرض ‏thread را استفاده کنید.

این امروز قابلیت Slack است. سایر پلتفرم‌ها کلید را می‌پذیرند ولی به سطح ‏thread برمی‌گردند ‏(primitives ادامه‌شان متفاوت است)؛ انتخاب به‌ازای-پلتفرم و زیر پیکربندی هر پلتفرم است. فلگ پیکربندی سمت-گیت‌وی است — ‏/restart آن را برمی‌دارد؛ reinstall اپ اسلک لازم نیست.

📌 ‏DM های ۱:۱

‏cron_continuable_surface یک تنظیم کانال است — ‏DM یک‌به‌یک تقسیم ترد-vs-خط‌زمان ندارد که بین‌شان انتخاب کنید ‏(خود DM از قبل تخته)، پس کلید آنجا اثر ندارد. اینکه آیا تحویل کرونیِ DM قابل-ادامه باشد را کلید جداگانه و از-قبل-موجود ‏slack.dm_top_level_threads_as_sessions تعیین می‌کند:

  • ‏false — همهٔ DM های سطح‌بالا یک نشست DM چرخشی مشترک دارند، پس خلاصهٔ کرونی قابل-ادامه و ریپلایتان در همان نشست می‌نشینند و کار با زمینه ادامه می‌یابد. این چیزی است که برای کرون قابل-ادامه در DM می‌خواهید.
  • ‏true ‏(پیش‌فرض) — هر پیام DM سطح‌بالا نشست خودش است، پس ریپلای به خلاصهٔ تحویل‌شده نشست تازه‌ای شروع می‌کند که هیچ رکوردی از خلاصه ندارد. ادامه در این حالت کار نمی‌کند ‏(برای کرون یا هر تحویل تخت دیگری).

پس برای کار کرون قابل-ادامه‌ای که به DM یک‌به‌یک تحویل می‌شود ‏slack.dm_top_level_threads_as_sessions: false را بگذارید. ‏cron_continuable_surface برای DM ها لازم نیست ‏(و نادیده گرفته می‌شود).

سرکوب بی‌صدا

اگر پاسخ نهایی ایجنت شامل ‏[SILENT] باشد، تحویل کلاً سرکوب می‌شود. خروجی همچنان برای حسابرسی محلی ذخیره می‌شود ‏(در ‏~/.hermes/cron/output/) ولی هیچ پیامی به هدف تحویل نمی‌رود.

برای job های مانیتورینگ که باید فقط وقتی مشکلی هست گزارش بدهند مفید است:

Check if nginx is running. If everything is healthy, respond with only [SILENT].
Otherwise, report the issue.

job های شکست‌خورده فارغ از نشانگر ‏[SILENT] همیشه تحویل می‌دهند — فقط اجراهای موفق می‌توانند ساکت شوند. برای job های مانیتورینگِ بی‌سر‌وصدا به ایجنت بگویید وقتی چیزی برای گزارش نیست فقط [SILENT] جواب بدهد.

۱۲ timeout اسکریپت

اسکریپت‌های پیش-از-اجرا ‏(الصاقی با پارامتر ‏script) پیش‌فرض timeout ‏۳۶۰۰ ثانیه دارند ‏(۱ ساعت). این فقط اسکریپت را محدود می‌کند — job های مبتنی-بر-مهارت / محرک-LLM روی بودجه جدایی از بی‌فعالیتی اجرا می‌شوند و با این مقدار سقف نمی‌خورند. اگر اسکریپت‌هایتان حد متفاوت می‌خواهند عوضش کنید:

yaml — ~/.hermes/config.yaml
cron:
  script_timeout_seconds: 1800   # ۳۰ دقیقه

یا متغیر محیطی ‏HERMES_CRON_SCRIPT_TIMEOUT را بگذارید. ترتیب حل: env ← config.yaml ← پیش‌فرض ۳۶۰۰ ثانیه.

کرون پاکسازی منابع نشست و ایجنتِ پس-از-اجرا را هم محدود می‌کند. این بعد از برگشتن نوبت LLM اتفاق می‌افتد، پس از timeout بی‌فعالیتی جداست. پیش‌فرض ۱۰ ثانیه به‌ازای هر عملیات پاکسازی است. اگر یک finalizer ذخیره‌سازی یا کلاینت از پاسخ‌دادن بایستد، زمان‌بند خطا لاگ، نگهبان در-جراحی job را آزاد و اجازه می‌دهد اجراهای بعدی dispatch شوند به‌جای رد شدن همیشگی آن job.

yaml — ~/.hermes/config.yaml
cron:
  cleanup_timeout_seconds: 10

‏cleanup_timeout_seconds: 0 را فقط برای بازگرداندن رفتار قدیمیِ پاکسازی بی‌کران بگذارید.

timeout ارسال رسانه

وقتی تحویل کرونی شامل پیوست‌های رسانه‌ای باشد ‏(PDF تولیدی، صدای TTS، گزارش export‌شده) که از طریق آداپتور گیت‌وی زنده فرستاده می‌شوند، آپلود هر پیوست با timeout محدود می‌شود — پیش‌فرض ۳۰۰ ثانیه. فایل‌های بزرگ روی uplink های کند ممکن است بیشتر بخواهند:

yaml — ~/.hermes/config.yaml
cron:
  media_send_timeout_seconds: 600   # ۱۰ دقیقه به‌ازای هر پیوست

یا متغیر محیطی ‏HERMES_CRON_MEDIA_SEND_TIMEOUT. ترتیب حل: env ← config.yaml ← پیش‌فرض ۳۰۰ ثانیه. پیوستِ timeout‌شده در وضعیت اجرای job به‌عنوان شکست تحویل جزئی ثبت می‌شود ‏(متن همچنان تحویل می‌گیرد).

timeout تحویل Bot Chat

تحویل ‏bot-chat یک نوبت کامل ایجنت در چت بات هدف اجرا می‌کند، پس حدش دقیقه است نه ثانیه — پیش‌فرض ‏۶۰۰ ثانیه:

yaml — ~/.hermes/config.yaml
cron:
  bot_chat_delivery_timeout_seconds: 900

تحویل timeout‌شده در ‏last_delivery_error ثبت می‌شود؛ نوبت بات ممکن است همچنان خودش تمام شود.

۱۳ حالت بدون-ایجنت ‏(job های فقط-اسکریپت)

برای کارهای تکرارشونده‌ای که به استدلال LLM نیاز ندارند — watchdog های کلاسیک، alert های دیسک/حافظه، ضربان‌ها، پینگ‌های CI — هنگام ساخت ‏no_agent=True بدهید. زمان‌بند اسکریپت شما را طبق برنامه اجرا و stdout‌اش را مستقیم تحویل می‌دهد، ایجنت کلاً رد می‌شود:

bash
hermes cron create "every 5m" \
  --no-agent \
  --script memory-watchdog.sh \
  --deliver telegram \
  --name "memory-watchdog"

معناشناسی:

  • stdout اسکریپت ‏(trim‌شده) → تحت‌اللفظی به‌عنوان پیام تحویل می‌شود.
  • stdout خالی → تیک بی‌صدا، بدون تحویل. الگوی watchdog همین است: «فقط وقتی مشکلی هست حرفی بزن».
  • خروج غیرصفر یا timeout → alert خطا تحویل می‌شود تا watchdog خراب نتواند بی‌صدا شکست بخورد.
  • ‏{"wakeAgent": false} در آخرین خط → تیک بی‌صدا ‏(همان گیتی که job های LLM استفاده می‌کنند).
  • بدون توکن، بدون مدل، بدون fallback ارائه‌دهنده — job هرگز به لایه inference دست نمی‌زند.

فایل‌های ‏.sh/.bash وقتی موجود باشد زیر ‏bash از PATH اجرا می‌شوند وگرنه ‏/bin/bash ‏(روی Windows Git Bash مهم است). بقیه زیر مفسر Python فعلی ‏(sys.executable) اجرا می‌شوند. اسکریپت‌ها باید داخل ‏$HERMES_HOME/scripts/ حل شوند — نام‌های نسبی، مسیرهای مطلق و مسیرهای با پیشوند ~ وقتی هدف حل‌شده در همان پوشه بماند پذیرفته می‌شوند؛ مسیرهایی که ازش خارج شوند رد می‌شوند. env زیرپروسه پاکسازی می‌شود ‏(_sanitize_subprocess_env): اعتبارنامه‌های API ارائه‌دهنده و سایر رمزهای مدیریت‌شده توسط هرمس به اسکریپت‌های کرون ارث نمی‌رسند.

ایجنت این‌ها را برایتان راه می‌اندازد

schema ابزار ‏cronjob مقدار ‏no_agent را مستقیماً به هرمس می‌دهد، پس می‌توانید یک watchdog را در چت توصیف و سیم‌کشی را به ایجنت بسپارید:

Ping me on Telegram if RAM is over 85%, every 5 minutes.

هرمس اسکریپت چک را با ‏write_file در ‏~/.hermes/scripts/ می‌نویسد، سپس صدا می‌زند:

python
cronjob(action="create", schedule="every 5m",
        script="memory-watchdog.sh", no_agent=True,
        deliver="telegram", name="memory-watchdog")

وقتی محتوای پیام کاملاً توسط اسکریپت تعیین می‌شود ‏(watchdog ها، alert های آستانه، ضربان‌ها) خودش ‏no_agent=True را انتخاب می‌کند. همان ابزار اجازه می‌دهد ایجنت job ها را pause، resume، edit و remove کند — پس کل چرخهٔ حیات چت‌محور است بدون دست‌زدن کسی به CLI.

راهنمای کارهای کرون فقط-اسکریپت را برای مثال‌های کاربردی ببینید.

۱۴ زنجیره‌کردن job ها با ‏context_from

کارهای کرون در نشست‌های ایزوله بدون حافظه از اجراهای قبلی اجرا می‌شوند. ولی بعضی وقت‌ها خروجی یک job دقیقاً همان چیزی است که job بعدی لازم دارد. پارامتر ‏context_from این اتصال را خودکار سیم می‌کشد — پرامپتِ Job B آخرین خروجی Job A را هنگام runtime به‌عنوان زمینه پیشوند می‌گیرد.

python
# Job 1: Collect raw data
cronjob(
    action="create",
    prompt="Fetch the top 10 AI/ML stories from Hacker News. Save them to ~/.hermes/data/briefs/raw.md in markdown format with title, URL, and score.",
    schedule="0 7 * * *",
    name="AI News Collector",
)

# Job 2: Triage — receives Job 1's output as context
# Get Job 1's ID from: cronjob(action="list")
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/raw.md. Score each story 1–10 for engagement potential and novelty. Output the top 5 to ~/.hermes/data/briefs/ranked.md.",
    schedule="30 7 * * *",
    context_from="<job1_id>",
    name="AI News Triage",
)

# Job 3: Ship — receives Job 2's output as context
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/ranked.md. Write 3 tweet drafts (hook + body + hashtags). Deliver to telegram:7976161601.",
    schedule="0 8 * * *",
    context_from="<job2_id>",
    name="AI News Brief",
)

نحوهٔ کار:

  • وقتی Job 2 شلیک می‌کند هرمس آخرین خروجی Job 1 را از ‏~/.hermes/cron/output/{job1_id}/*.md می‌خواند
  • آن خروجی خودکار به ابتدای پرامپت Job 2 الصاق می‌شود
  • Job 2 لازم نیست «این فایل را بخوان» را هاردکد کند — محتوا را به‌عنوان زمینه می‌گیرد
  • زنجیره می‌تواند هر طولی باشد: Job 1 ← Job 2 ← Job 3 ← ...

‏context_from چه می‌پذیرد:

قالبمثال
شناسهٔ job واحد ‏(رشته)context_from="a1b2c3d4"
چند شناسهٔ job ‏(فهرست)context_from=["job_a", "job_b"]

خروجی‌ها به ترتیب فهرست الحاق می‌شوند.

تداوم: حمل خروجی اجرای قبلی

‏continuity=true را بگذارید و job آخرین خروجی خودش را در هر اجرا تزریق می‌کند. job های تکرارشونده معمولاً هر اجرا با فراموشی شروع می‌کنند — خبرنگاری که همان اخبار را دوباره گزارش می‌کند، مانیتوری که روی همان شرط دوباره هشدار می‌دهد. با روشن بودن continuity، job بیدار می‌شود و می‌بیند بار قبل چه گزارش کرده و می‌تواند حذف تکرار و ادامه از همان‌جا:

python
cronjob(
    action="create",
    prompt="Scan HN and arXiv for new agent-tooling papers. Report only items NOT already covered in your previous run's output.",
    schedule="every 6h",
    continuity=True,
    name="Agent Tooling Scout",
)

اجرای اول خروجی قبلی ندارد، پس پرامپت عیناً اجرا می‌شود. در اجراهای بعدی خروجی قبلی با قاب continuity («آنچه قبلاً گزارش شده را تکرار نکن») الصاق می‌شود. با job های بالادستی آزادانه ترکیب می‌شود ‏(context_from=["<other_job_id>"] به‌اضافهٔ ‏continuity=true) و ‏continuity=false هنگام update آن را خاموش می‌کند در حالی که ورودی‌های دیگر ‏context_from حفظ می‌شوند. داخلی فلگ به‌عنوان ورودی رزروشدهٔ ‏self در ‏context_from ذخیره می‌شود.

از CLI: ‏hermes cron create "every 6h" "Scan for news" --continuity و برای تغییر روی job موجود ‏hermes cron edit <job_id> --continuity / ‏--no-continuity. همان کلید در ویرایشگر کرون داشبورد و دیالوگ روتین Bot Mode دسکتاپ هم هست.

کِی استفاده کنیم:

  • خط‌لوله‌های چندمرحله‌ای ‏(جمع‌آوری ← فیلتر ← قالب ← تحویل)
  • کارهای وابسته که کار مرحله N به خروجی مرحله N−1 وابسته است
  • الگوهای fan-out/fan-in که یک job نتایج چند job دیگر را تجمیع می‌کند
  • خبرنگاران/مانیتورهای تکرارشونده که باید علیه گزارش قبلی‌شان dedupe کنند ‏(continuity=true)

۱۵ بازیابی ارائه‌دهنده

کارهای کرون ارائه‌دهنده‌های fallback پیکربندی‌شده و چرخش pool اعتبارنامه را ارث می‌برند. اگر کلید API اصلی rate-limit شود یا ارائه‌دهنده خطا برگرداند، ایجنت کرونی می‌تواند:

  • به ارائه‌دهندهٔ جایگزین برگردد اگر ‏fallback_providers ‏(یا ‏fallback_model قدیمی) را در config.yaml دارید
  • به اعتبارنامهٔ بعدی در pool اعتبارنامه‌تان برای همان ارائه‌دهنده بچرخد

یعنی کارهای کرونی با فراوانی بالا یا در ساعت‌های اوج مقاوم‌ترند — یک کلید rate-limit‌شده کل اجرا را شکست نمی‌دهد.

۱۶ شلیک‌های از‌دست‌رفتهٔ زمان‌بندی ‏(last_fire_error)

در استقرارهای میزبانی‌شده ‏(کرون-مدیریتی)، یک شلیک زمان‌بندی‌شده از زمان‌بند پلتفرم از طریق داشبورد به سرور API داخلی گیت‌وی سفر می‌کند. اگر آن تحویل نهایی شکست بخورد — پروسهٔ گیت‌وی خاموش است یا شنونده سرور-API‌اش هرگز شروع نشده — اجرا اصلاً شروع نمی‌شود، پس رکورد اجرایی و last_status‌ای برای بررسی وجود ندارد. شکل گویا: job هر بار که دستی تریگرش می‌کنید کار می‌کند ولی هرگز خودکار شلیک نمی‌شود.

این ردشده‌ها روی رکورد job به‌صورت ‏last_fire_error مهر می‌خورند ‏(timestamp + دلیل) و اینجا سطح پیدا می‌کنند:

  • ابزار ‏cronjob ← ‏action: "list" — فیلد ‏last_fire_error
  • ‏hermes cron list — خط قرمز ‏⚠ Missed scheduled fire: زیر job
  • نمای job در داشبورد

مهر همیشه سلامت فعلیِ شلیک-خودکار را بازتاب می‌دهد: با ردشده‌های جدیدتر بازنویسی و توسط اولین اجرای موفق بعدی خودکار پاک می‌شود. اگر دیدیدش job و زمان‌بندی‌اش سالم‌اند — سمت گیت‌وی مسیر شلیک توجه می‌خواهد ‏(رایج‌ترین: گیت‌وی را از طریق supervisor ری‌استارت کنید تا محیط کامل پروفایل لود شود: ‏hermes gateway restart).

جبران misfire

وقتی ارائه‌دهندهٔ زمان‌بند خارجی فعال است ‏(کرون مدیریتی روی استقرارهای میزبانی‌شده)، گیت‌وی یک sweep جبران هم اجرا می‌کند: job‌ای که زمانش گذشته و شلیکی تحویل نشده — و پنجرهٔ grace‌اش سپری شده — گرفته و محلی اجرا می‌شود، تا قطعی در تحویل شلیک به‌جای کل روز فقط چند دقیقه هزینه داشته باشد. sweep نسبت به retry های دیرهنگامِ زمان‌بند با همان claim مخزنِ شلیک‌های عادی dedupe می‌شود.

yaml
cron:
  misfire_grace_minutes: 10   # این‌قدر منتظر retry های خودِ زمان‌بند می‌ماند
                              # قبل از جبران محلی؛ 0 جبران را خاموش می‌کند

استقرارهای محلی ‏(ticker داخلی) به این نیاز ندارند — ticker خودش job های عقب‌افتاده را در تیک بعدی برمی‌دارد.

۱۷ قالب‌های زمان‌بندی

پاسخ نهایی ایجنت خودکار به هدف ‏deliver: مربوط به job تحویل می‌شود — ایجنت دیگر خودش پیام شلیک نمی‌کند، پس محتوای رو-به-کاربر به‌سادگی در پاسخ نهایی می‌رود. برای تحویل به هدف‌های اضافی یا متفاوت چند هدف ‏deliver: را روی کار کرون فهرست کنید ‏(جداشده با ویرگول، مثل ‏deliver: "telegram,discord") به‌جای اینکه ایجنت بفرستد.

اجراهای دستی ناهمگام‌اند

‏cronjob(action="run") job را فوراً در پس‌زمینه شلیک می‌کند ‏(مثل ‏delegate_task): فراخوانی ابزار بلافاصله با یک handle برمی‌گردد و پیامد job — موفقیت/شکست، هدف تحویل، اجرای زمان‌بندی‌شده بعدی و گزیدهٔ خروجی — وقتی اجرا تمام شد به‌عنوان پیام جدید به گفتگو برمی‌گردد. ایجنت ‏(و شما) می‌توانید در این فاصله به کار ادامه دهید و job‌ای که از قبل میان-اجراست با «already running» رد می‌شود نه شلیک دوباره.

می‌توانید همراه ‏action="run" مقدار ‏prompt هم بدهید تا زمینهٔ گذرا به‌ازای-اجرا تزریق کنید:

python
cronjob(action="run", job_id="...", prompt="CONTEXT: focus on the EU region today")

زمینه برای همان یک شلیک زیر سربرگ ‏## Run Context به پرامپت ذخیره‌شده job الصاق می‌شود — هرگز در تعریف job ماندگار نمی‌شود و از همان اسکن prompt-injection پرامپت‌های ذخیره‌شده عبور می‌کند.

runtime هایی که نمی‌توانند نتیجهٔ جدا‌شده بگیرند ‏(hermes -z یک‌باره، ‏hermes cron run از CLI، نشست‌های فرزند کرون، worker های کانبان) خودکار به اجرای همگام برمی‌گردند.

۱۹ تول‌ست‌های در دسترس job های کرون

کرون هر job را در نشست تازهٔ ایجنتی بدون هیچ پلتفرم چت الصاقی اجرا می‌کند. پیش‌فرض ایجنت کرونی تول‌ست پیکربندی‌شده برای پلتفرم cron در ‏hermes tools را می‌گیرد — نه پیش‌فرض CLI، نه همه‌چیزِ زیر آفتاب.

bash
hermes tools
# → در UI curses پلتفرم "cron" را انتخاب کنید
# → تول‌ست‌ها را مثل Telegram/Discord و... روشن/خاموش کنید

کنترل دقیق‌تر به‌ازای-job از طریق فیلد ‏enabled_toolsets روی ‏cronjob.create ‏(یا روی job موجود با ‏cronjob.update) در دسترس است:

text
cronjob(action="create", name="weekly-news-summary",
        schedule="every sunday 9am",
        enabled_toolsets=["web", "file"],      # فقط web + file، بدون terminal/browser/etc.
        prompt="Summarize this week's AI news: ...")

وقتی ‏enabled_toolsets روی job تنظیم باشد آن برنده است؛ وگرنه پیکربندی پلتفرم-cron مربوط به ‏hermes tools برنده است؛ وگرنه هرمس به پیش‌فرض‌های داخلی برمی‌گردد. برای کنترل هزینه مهم است: حمل ‏browser و ‏delegation داخل هر job کوچک «گرفتن خبر» پرامپت schema-ابزار را در هر فراخوانی LLM متورم می‌کند.

رد شدن کلاً از ایجنت: ‏wakeAgent

اگر کار کرون‌تان اسکریپت پیش-چک الصاق کند ‏(با ‏script=)، اسکریپت می‌تواند در runtime تصمیم بگیرد اصلاً هرمس ایجنت را invoke کند یا نه. خط نهایی stdout به این شکل چاپ کنید:

{"wakeAgent": false}

…و کرون اجرای ایجنت را برای این تیک کلاً رد می‌کند. برای poll های پرتکرار ‏(هر ۱–۵ دقیقه) که فقط وقتی وضعیت واقعاً عوض شده باید LLM بیدار شود مفید است — وگرنه بارها برای نوبت‌های ایجنتیِ بدون-محتوا هزینه می‌دهید.

python
# pre-check script
import json, sys
latest = fetch_latest_issue_count()
prev = read_state("issue_count")
if latest == prev:
    print(json.dumps({"wakeAgent": False}))   # skip this tick
    sys.exit(0)
write_state("issue_count", latest)
print(json.dumps({"wakeAgent": True, "context": {"new_issues": latest - prev}}))

وقتی ‏wakeAgent حذف شود پیش‌فرض ‏true است ‏(بیدارکردن عادی ایجنت).

دستورالعمل‌ها: گیت‌های ارزان پیش-از-اجرا

گیتی ‏wakeAgent راه $0‌ای می‌دهد برای تصمیم اینکه کار زمان‌بندی‌شده اصلاً توکن LLM خرج کند یا نه. سه الگو بیشتر موارد استفاده را پوشش می‌دهد.

گیتی تغییر-فایل — فقط وقتی اجرا شود که فایل تحت‌نظارت از آخرین تیک موفق محتوای جدید داشته باشد. زمان‌بند ‏last_run_at هر job را ثبت می‌کند؛ آن را با mtime فایل مقایسه کنید.

bash — ~/.hermes/scripts/feed-changed.sh
#!/bin/bash
FEED="$HOME/data/feed.json"
STATE="$HOME/.hermes/scripts/.feed-changed.last"
test -f "$FEED" || { echo '{"wakeAgent": false}'; exit 0; }
mtime=$(stat -c %Y "$FEED")
last=$(cat "$STATE" 2>/dev/null || echo 0)
if [ "$mtime" -le "$last" ]; then
  echo '{"wakeAgent": false}'
else
  echo "$mtime" > "$STATE"
  echo '{"wakeAgent": true}'
fi
cronjob(action="create", name="process-feed",
        schedule="every 30m",
        script="feed-changed.sh",
        prompt="A new ~/data/feed.json has landed. Summarize what changed.")

گیتی فلگ-خارجی — فقط وقتی اجرا شود که پروسهٔ دیگری آمادگی را علامت داده باشد ‏(مثل deploy hook که فایلی می‌اندازد یا job ‏CI که مقداری در state store شما ست می‌کند).

bash — ~/.hermes/scripts/flag-ready.sh
#!/bin/bash
if test -f /tmp/new-data-ready; then
  rm -f /tmp/new-data-ready
  echo '{"wakeAgent": true}'
else
  echo '{"wakeAgent": false}'
fi
cronjob(action="create", name="nightly-analysis",
        schedule="0 9 * * *",
        script="flag-ready.sh",
        prompt="Run the nightly analysis over today's batch.")

گیتی شمارش-SQL — فقط وقتی ردیف‌های جدیدی برای پردازش در دیتابیس خودتان هست اجرا شود. اسکریپت می‌تواند تعداد را هم از طریق ‏context به ایجنت بدهد تا بدون re-query بداند با چه حجمی طرف است.

python — ~/.hermes/scripts/new-rows.py
#!/usr/bin/env python
import json, sqlite3
conn = sqlite3.connect("/home/me/data/app.db")
n = conn.execute(
    "SELECT COUNT(*) FROM messages WHERE ts > strftime('%s','now','-2 hours')"
).fetchone()[0]
if n < 1:
    print(json.dumps({"wakeAgent": False}))
else:
    print(json.dumps({"wakeAgent": True, "context": {"new_rows": n}}))
cronjob(action="create", name="summarize-new-msgs",
        schedule="every 2h",
        script="new-rows.py",
        prompt="Summarize the new messages from the last 2 hours.")

همان الگو برای هر منبع داده‌ای که از اسکریپت قابل پرس‌وجوست کار می‌کند — Postgres، یک HTTP API، state store خودتان — بدون bake کردن یک evaluator SQL داخل زیرسیستم کرون.

💡 نکته

‏~/.hermes/state.db خودِ هرمس یک schema داخلی است که بین ریلیزها عوض می‌شود. از داخل گیت پیش-اجرا رویش query نزنید — به‌جایش به دیتابیس یا feed خودتان اشاره دهید.

اعتبار: این مجموعه دستورالعمل با کاوش ‏@iankar8 در ‏#2654 الهام گرفت که افزودن تریگرهای sql/file/command را به‌عنوان مکانیزم موازی پیشنهاد کرده بود. گیتی ‏script + ‏wakeAgent هر سه مورد را با $0 پوشش می‌داد، پس کار به‌جای کد به‌صورت مستندات فرود آمد.

زنجیره‌کردن job ها: ‏context_from

یک کار کرون می‌تواند با ذکر نام‌ها ‏(یا شناسه‌ها) در ‏context_from آخرین خروجی موفق یک یا چند job دیگر را مصرف کند:

text
cronjob(action="create", name="daily-digest",
        schedule="every day 7am",
        context_from=["ai-news-fetch", "github-prs-fetch"],
        prompt="Write the daily digest using the outputs above.")

آخرین خروجی‌های کامل‌شدهٔ job های ارجاع‌شده به‌عنوان زمینه بالای پرامپت این اجرا تزریق می‌شوند. هر ورودی بالادستی باید شناسه یا نام معتبر job باشد ‏(‏cronjob action="list" را ببینید). توجه: زنجیره آخرین خروجی کامل‌شده را می‌خواند — منتظر job های بالادستی که در همان تیک در حال اجرایند نمی‌ماند.

۲۰ ذخیرهٔ job ها

‏job ها در ‏~/.hermes/cron/jobs.json ذخیره می‌شوند. خروجی اجرای job ها در ‏~/.hermes/cron/output/{job_id}/{timestamp}.md ذخیره می‌شود.

تعاریف job JSON ساده روی دیسک‌اند: از ‏hermes update، ری‌استارت‌های گیت‌وی و ری‌بوت ماشین جان سالم می‌برند. job‌ای که حین ری‌استارت وسط اجرا بوده در دفتر اجرا ‏unknown علامت می‌خورد — خودکار retry نمی‌شود ولی تیک زمان‌بندی‌شده بعدی job عادی شلیک می‌کند. جزئیات در «تاریخچهٔ اجرا».

💡 نکته

از ایجنت بخواهید job ها را از طریق ابزار ‏cronjob، ‏hermes cron edit یا ‏/cron مدیریت کند — نه با patch مستقیم ‏jobs.json. ویرایش مستقیم وقتی امنیت نوشتن فایل مسیر را بلاک می‌کند ‏(مثلاً وقتی ‏HERMES_WRITE_SAFE_ROOT تنظیم است) می‌تواند بی‌صدا شکست بخورد و فوتر تأییدگر جهش-فایل سیگنال مرجع این است که چیزی ذخیره نشده.

‏job ها ممکن است ‏model و ‏provider را به‌صورت ‏null ذخیره کنند. وقتی آن فیلدها حذف شده باشند هرمس هنگام اجرا از پیکربندی سراسری حل‌شان می‌کند. فقط وقتی override به‌ازای-job تنظیم شده در رکورد job ظاهر می‌شوند.

ذخیره‌سازی از نوشته‌های atomic استفاده می‌کند تا نوشته‌های قطع‌شده فایل job نیمه‌نوشته جا نگذارند.

۲۱ پرامپت‌های خودبسنده همچنان مهم‌اند

⚠️ مهم

کارهای کرون در نشست ایجنتیِ کاملاً تازه اجرا می‌شوند. پرامپت باید هر چیزی را که ایجنت لازم دارد و توسط مهارت‌های الصاقی فراهم نمی‌شود در بر داشته باشد.

بد: ‏"Check on that server issue"

خوب: ‏"SSH into server 192.168.1.100 as user 'deploy', check if nginx is running with 'systemctl status nginx', and verify https://example.com returns HTTP 200."

۲۲ امنیت

پرامپت‌های کارهای زمان‌بندی‌شده هنگام ساخت و به‌روزرسانی برای الگوهای prompt-injection و خروج برداشتگاه-اعتبارنامه اسکن می‌شوند. پرامپت‌های حاوی ترفندهای یونیکد نامرئی، تلاش‌های درب-پشتی SSH یا payload های واضح خروج-رمز بلوک می‌شوند.
