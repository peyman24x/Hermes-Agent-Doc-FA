حافظهٔ پایدار

هرمس ایجنت حافظه‌ای کراندار و گزینش‌شده دارد که بین نشست‌ها باقی می‌ماند. این به او اجازه می‌دهد ترجیحات شما، پروژه‌هایتان، محیطتان و چیزهایی را که یاد گرفته به خاطر بسپارد.

۱ چگونه کار می‌کند

دو فایل حافظهٔ ایجنت را می‌سازند:

فایلهدفسقف کاراکتر
MEMORY.mdیادداشت‌های شخصی ایجنت — حقایق محیط، قراردادها، چیزهای آموخته‌شده۲٬۲۰۰ کاراکتر (حدود ۸۰۰ توکن)
USER.mdپروفایل کاربر — ترجیحات شما، سبک ارتباطی، انتظارات۱٬۳۷۵ کاراکتر (حدود ۵۰۰ توکن)

هر دو در ~/.hermes/memories/ ذخیره می‌شوند و در شروع نشست به‌صورت اسنپ‌شاتِ منجمد به پرامپت سیستمی تزریق می‌شوند. ایجنت حافظهٔ خودش را با ابزار memory مدیریت می‌کند — می‌تواند مدخل اضافه، جایگزین یا حذف کند.

⛔ یک ایجنت به ازای هر home هرمس

دو پروسهٔ ایجنت را به یک پوشهٔ home هرمس اشاره ندهید. نوشتن حافظه خودکار است و در شروع نشست به پرامپت سیستمی برمی‌گردد، پس دو نویسنده روی یک home، مدخل‌های هم را با هم ترکیب می‌کنند تا وضعیتی بسازند که نه آن‌ها و نه شما نوشته‌اید. حافظه به‌طور طراحی‌شده به‌ازای پروفایل جداست — به ایجنت دوم پروفایل خودش را بدهید، و اگر به حافظهٔ مشترک نیاز دارند به‌جایش از یک ارائه‌دهندهٔ حافظهٔ خارجی استفاده کنید.

ℹ️ توجه

سقف‌های کاراکتری حافظه را متمرکز نگه می‌دارند. حافظه به‌طور خودکار فشرده نمی‌شود: وقتی یک نوشتن از سقف بگذرد، ابزار memory خطا برمی‌گرداند به‌جای اینکه بی‌صدا مدخلی را بیندازد. آن‌گاه ایجنت خودش جا باز می‌کند — در همان نوبت، مدخل‌ها را ادغام یا حذف می‌کند و دوباره امتحان می‌کند (به «وقتی حافظه پُر می‌شود چه اتفاقی می‌افتد» مراجعه کنید). توجه کنید replace هم مشمول سقف است: جایگزینیِ یک مدخل با نسخهٔ بلندتر همچنان می‌تواند سرریز کند، پس محتوای جدید باید کوتاه‌تر شود (یا مدخل دیگری حذف شود) تا جا شود.

۲ حافظه چگونه در پرامپت سیستمی ظاهر می‌شود

در شروع هر نشست، مدخل‌های حافظه از دیسک بارگذاری و به‌صورت یک بلوک منجمد در پرامپت سیستمی رندر می‌شوند:

نمونهٔ بلوک حافظه در پرامپت
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations

قالب شامل این‌هاست:

  • یک سرصفحه که نشان می‌دهد کدام مخزن است (MEMORY یا USER PROFILE)
  • درصد مصرف و شمار کاراکترها تا ایجنت ظرفیت را بداند
  • مدخل‌های جدا با جداکننده‌های § (نشان بخش)
  • مدخل‌ها می‌توانند چندخطی باشند

الگوی اسنپ‌شات منجمد: تزریقِ پرامپت سیستمی یک بار در شروع نشست گرفته می‌شود و وسط نشست هرگز تغییر نمی‌کند. این عمدی است — حفظ کش پیشوندِ LLM برای کارایی. وقتی ایجنت وسط نشست مدخل حافظه اضافه/حذف می‌کند، تغییرها بلافاصله روی دیسک ماندگار می‌شوند اما تا شروع نشست بعدی در پرامپت سیستمی ظاهر نمی‌شوند. پاسخ‌های ابزار همیشه وضعیت زنده را نشان می‌دهند.

۳ اکشن‌های ابزار memory

ایجنت از ابزار memory با این اکشن‌ها استفاده می‌کند:

  • add — افزودن مدخل حافظهٔ جدید
  • replace — جایگزینی یک مدخل موجود با محتوای به‌روزشده (با تطبیق زیررشته از طریق old_text)
  • remove — حذف مدخلی که دیگر مرتبط نیست (با تطبیق زیررشته از طریق old_text)

اکشن read وجود ندارد — محتوای حافظه در شروع نشست به‌طور خودکار به پرامپت سیستمی تزریق می‌شود. ایجنت خاطراتش را به‌عنوان بخشی از زمینهٔ گفتگوی خودش می‌بیند.

تطبیق زیررشته

اکشن‌های replace و remove از تطبیقِ زیررشتهٔ کوتاهِ یکتا استفاده می‌کنند — متن کامل مدخل لازم نیست. پارامتر old_text فقط باید زیررشته‌ای یکتا باشد که دقیقاً یک مدخل را شناسایی کند:

python
# اگر حافظه شامل "User prefers dark mode in all editors" باشد
memory(action="replace", target="memory",
       old_text="dark mode",
       content="User prefers light mode in VS Code, dark mode in terminal")

اگر زیررشته با چند مدخل مطابقت یابد، خطایی برگردانده می‌شود که تطبیق دقیق‌تری می‌خواهد.

۴ توضیح دو مقصد

memory — یادداشت‌های شخصی ایجنت

برای اطلاعاتی که ایجنت باید دربارهٔ محیط، گردش‌کارها و درس‌های آموخته به خاطر بسپارد:

  • حقایق محیط (سیستم‌عامل، ابزارها، ساختار پروژه)
  • قراردادها و پیکربندی پروژه
  • رفتارهای عجیب ابزارها و راه‌حل‌های کشف‌شده
  • مدخل‌های دفترچهٔ کارهای تمام‌شده
  • مهارت‌ها و تکنیک‌هایی که جواب دادند

user — پروفایل کاربر

برای اطلاعاتی دربارهٔ هویت کاربر، ترجیحات و سبک ارتباطی:

  • نام، نقش، منطقهٔ زمانی
  • ترجیحات ارتباطی (مختصر در برابر مفصل، ترجیح قالب)
  • حساسیت‌ها و چیزهایی که باید پرهیز شوند
  • عادت‌های گردش‌کار
  • سطح مهارت فنی

۵ چه چیزی را ذخیره کنیم و چه را نه

این‌ها را ذخیره کن (پیشگیرانه)

ایجنت خودکار ذخیره می‌کند — لازم نیست بخواهید. وقتی این‌ها را می‌آموزد ذخیره می‌کند:

  • ترجیحات کاربر: «TypeScript را به JavaScript ترجیح می‌دهم» ← ذخیره در user
  • حقایق محیط: «این سرور دبیان ۱۲ با PostgreSQL 16 اجرا می‌کند» ← ذخیره در memory
  • اصلاحات: «برای دستورات داکر sudo نزن، کاربر در گروه docker است» ← ذخیره در memory
  • قراردادها: «پروژه tab استفاده می‌کند، عرض خط ۱۲۰، docstring به سبک گوگل» ← ذخیره در memory
  • کارهای تمام‌شده: «دیتابیس در ۲۰۲۶-۰۱-۱۵ از MySQL به PostgreSQL مهاجرت کرد» ← ذخیره در memory
  • درخواست‌های صریح: «به خاطر بسپر که چرخش کلید API من ماهانه است» ← ذخیره در memory

این‌ها را رد کن

  • اطلاعات پیش‌پاافتاده: «کاربر دربارهٔ پایتون پرسید» — بیش از حد مبهم
  • واقعیت‌های راحتِ کشف‌مجدد: «پایتون ۳.۱۲ تودرتویی f-string را پشتیبانی می‌کند» — قابل جستجوی وب
  • سرریز دادهٔ خام: بلوک‌های کد بزرگ، فایل‌های لاگ، جدول‌های داده — برای حافظه بزرگ‌اند
  • موقتیاتِ مخصوص-نشست: مسیرهای فایل موقت، زمینهٔ دیباگ یک‌باره
  • اطلاعاتِ از-قبل-در-فایل‌های-زمینه: محتوای SOUL.md و AGENTS.md

وقتی حافظه پُر می‌شود چه اتفاقی می‌افتد

وقتی سعی کنید مدخلی اضافه کنید که از سقف بگذرد، ابزار خطا برمی‌گرداند:

json
{
  "success": false,
  "error": "Memory at 2,100/2,200 chars. Adding this entry (250 chars) would exceed the limit. Consolidate now: use 'replace' to merge overlapping entries into shorter ones or 'remove' stale or less important entries (see current_entries below), then retry this add — all in this turn.",
  "current_entries": ["..."],
  "usage": "2,100/2,200"
}

سپس ایجنت باید:

  1. مدخل‌های فعلی را بخواند (در پاسخ خطا نمایش داده می‌شوند)
  2. مدخل‌هایی که می‌توانند حذف یا ادغام شوند را شناسایی کند
  3. با replace مدخل‌های مرتبط را در نسخه‌های کوتاه‌تر ادغام کند
  4. سپس مدخل جدید را add کند

بهترین شیوه: وقتی حافظه بالای ۸۰٪ ظرفیت است (در سرصفحهٔ پرامپت سیستمی پیدا می‌شود)، پیش از افزودنِ تازه‌ها مدخل‌ها را یکدست کنید. مثلاً سه مدخل جداگانهٔ «پروژه X را استفاده می‌کند» را در یک مدخل جامعِ توصیف پروژه ادغام کنید.

۷ جلوگیری از تکرار

سیستم حافظه مدخل‌های تکراریِ عیناً یکسان را خودکار رد می‌کند. اگر محتوایی که از قبل موجود است را اضافه کنید، با پیام «no duplicate added» موفقیت برگردانده می‌شود.

۸ اسکن امنیتی

مدخل‌های حافظه پیش از پذیرفته‌شدن از الگوهای تزریق و استخراج اسکن می‌شوند، چون به پرامپت سیستمی تزریق می‌شوند. محتوای منطبق با الگوهای تهدید (تزریق پرامپت، استخراج اعتبارنامه، درِ پشتی SSH) یا دارای کاراکترهای یونیکد نامرئی مسدود می‌شود.

۹ جستجوی نشست

فراتر از MEMORY.md و USER.md، ایجنت می‌تواند گفتگوهای گذشته‌اش را با ابزار session_search جستجو کند:

  • همهٔ نشست‌های CLI و پیام‌رسانی در SQLite (~/.hermes/state.db) با جستجوی تمام‌متن FTS5 ذخیره می‌شوند
  • کوئری‌های جستجو پیام‌های واقعی را از دیتابیس برمی‌گردانند — بدون خلاصه‌سازی LLM، بدون برش
  • ایجنت می‌تواند چیزهایی را که هفته‌ها پیش درباره‌شان صحبت کرده پیدا کند، حتی اگر در حافظهٔ فعالش نباشند
  • ایجنت همچنین می‌تواند داخل هر نشستی که پیدا می‌کند به جلو/عقب اسکرول کند
bash
hermes sessions list    # مرور نشست‌های گذشته

برای سه شکل فراخوانی (کشف / اسکرول / مرور) و قالب پاسخ، به «ابزار جستجوی نشست» مراجعه کنید.

۱۰ سفر یادگیری (/journey)

سفر یادگیری، نمای خط‌زمانیِ همهٔ چیزهایی است که هرمس آموخته — مهارت‌های ذخیره‌شده و مدخل‌های حافظه روی زمان رسم شده‌اند (قدیمی‌ترین بالا، جدیدترین پایین)، با یک اسکرابر «صورت‌فلکی» قابل‌پخش که انباشتگی را بازپخیر می‌کند. همان دادهٔ گراف، سه سطح را می‌راند:

  • CLI کلاسیک / مستقل — hermes journey (نام‌های مستقل: hermes learning، hermes memory-graph) خط‌زمانی را در ترمینال رندر می‌کند. پرچم‌ها: --play انباشتگی را انیمیت می‌کند (--fps برای تنظیم)، --width/--height اندازهٔ رندر را بازنویسی می‌کنند، --no-color رنگ را خاموش می‌کند و --json دادهٔ خام گراف را می‌ریزد.
  • TUI — /journey (نام‌های مستقل: /learning، /memory-graph) خط‌زمانی را به‌صورت اورلی باز می‌کند.
  • اپ دسکتاپ — /journey پنل Star Map / memory-graph را باز می‌کند، یک بصری‌سازی تعاملی از همان گره‌ها.

فراتر از دیدن، سفر همان جایی است که آنچه هرمس آموخته را هرس و اصلاح می‌کنید:

فرمانچه می‌کند
hermes journey listفهرست شناسهٔ گره‌ها — نام مهارت‌ها و شناسه‌های memory:<source>:<index> برای تکه‌های حافظه.
hermes journey delete <node> [-y]حذف یک گره. مهارت‌ها آرشیو می‌شوند (قابل بازیابی)، تکه‌های حافظه حذف می‌شوند. -y تأیید را رد می‌کند.
hermes journey edit <node>باز کردن محتوای گره (SKILL.md یک مهارت یا تکهٔ حافظه) در $EDITOR.

همان زیرفرمان‌های list / delete <id> / edit <id> از فرمان چتِ /journey در CLI هم کار می‌کنند، و پنل دسکتاپ روی گره‌ها مستقیماً ویرایش/حذف دارد.

۱۱ پیکربندی

yaml — در ~/.hermes/config.yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200   # ~800 توکن
  user_char_limit: 1375     # ~500 توکن
  write_approval: false     # false = نوشتن آزاد (پیش‌فرض) | true = نیاز به تأیید

غیرفعال‌کردن هر دو memory_enabled و user_profile_enabled مخزن‌های داخلی را کامل خاموش می‌کند: ابزار memory از طرحواره (schema) انداخته می‌شود و بلوک راهنمایش از پرامپت سیستمی حذف می‌شود، تا مدل هرگز دربارهٔ ابزاری که نمی‌تواند استفاده کند چیزی نشنود. یک ارائه‌دهندهٔ خارجیِ تنظیم‌شده با memory.provider (Hindsight، Mem0، Honcho، …) متأثر نمی‌شود و ابزارهای خودش را نگه می‌دارد — این را وقتی بخواهید که یک بک‌اند حافظهٔ شخص ثالث *به‌جای* فایل‌های داخلی. آوردن memory زیر agent.disabled_toolsets کلید سنگین‌تری است: ابزارهای ارائه‌دهندهٔ خارجی را هم پنهان می‌کند.

با فقط memory_enabled: false (پروفایل کاربر روشن)، ابزار می‌ماند — پشتیبانِ مخزن پروفایل است — اما پرامپت سیستمی راهنمای کامل حافظه را با بلوک باریک‌ترِ فقط-پروفایل عوض می‌کند. طرحوارهٔ ابزار فقط مقصد user را اعلام می‌کند و نوشتن مستقیم یا مرحله‌ای به MEMORY.mdِ غیرفعال رد می‌شود. پیکربندی معکوس فقط memory را اعلام و نوشتن USER.md را رد می‌کند.

۱۲ کنترل نوشتن‌های حافظه (write_approval)

به‌طور پیش‌فرض ایجنت آزادانه حافظه ذخیره می‌کند — از جمله از بازبینیِ خودبهبودی پس‌زمینه‌ای که بعد از یک نوبت اجرا می‌شود. اگر ترجیح می‌دهید اول ذخیره‌ها را تأیید کنید، memory.write_approval: true را تنظیم کنید. یک دروازهٔ سادهٔ روشن/خاموش است که روی هر دو نوبت پیش‌زمینه و بازبینی پس‌زمینه اعمال می‌شود:

write_approvalرفتار
false (پیش‌فرض)نوشتن آزاد — دروازه خاموش است (رفتار پیش از دروازه).
trueپیش از ذخیرهٔ هر چیزی تأیید لازم است. در CLI تعاملی، نوشتن‌های پیش‌زمینه درجا از شما می‌پرسند (مدخل‌ها به‌اندازهٔ کافی کوچک‌اند که کامل خوانده شوند). در هر جای دیگر — پلتفرم‌های پیام‌رسانی، اسکریپت‌ها و بازبینی خودبهبودی پس‌زمینه — نوشتن‌ها برای بازبینی مرحله‌بندی می‌شوند با /memory pending.

برای خاموش‌کردن کامل حافظه (نه صرفاً دروازه‌گذاری)، هم memory_enabled: false و هم user_profile_enabled: false را تنظیم کنید. وقتی هر دو مخزن داخلی غیرفعالند، ابزار memory داخلی به‌طور خودکار پنهان می‌شود.

بازبینی نوشتن‌های مرحله‌شده از CLI یا هر پلتفرم پیام‌رسانی:

فرمان‌ها
/memory pending             # فهرست نوشتن‌های مرحله‌شدهٔ حافظه (خودکارها با برچسب [auto])
/memory approve <id>        # اعمال یکی (یا 'all')
/memory reject <id>         # انداختن یکی (یا 'all')
/memory approval on         # روشن‌کردن دروازه (یا 'off') و ماندگارکردنش

این پاسخِ «ایجنت یک فرض غلط دربارهٔ من ذخیره کرد» است: write_approval: true را تنظیم کنید، و هر ذخیره — به‌ویژه آن‌های خودانگیختهٔ پس‌زمینه — پیش از آنکه وارد پروفایلتان شود، منتظر بله/نهی شما می‌ماند.

۱۳ اعلان‌های بازبینی پس‌زمینه (display.memory_notifications)

بعد از یک نوبت، بازبینیِ خودبهبودیِ پس‌زمینه ممکن است بی‌سروصدا حافظه‌ای ذخیره یا مهارتی را به‌روزرسانی کند. این حلقهٔ یادگیریِ آگاه-از-رضایتِ هرمس است: اصلاحات مکرر و درس‌های پایدار گردش‌کار به مدخل‌های فشردهٔ حافظه یا مهارت‌های رویه‌ای تبدیل می‌شوند، در حالی که write_approval می‌تواند آن نوشتن‌ها را پیش از اثرگذاری بر نشست‌های آینده برای بازبینی مرحله‌بندی کند. به‌طور پیش‌فرض یک خط کوتاه 💾 Memory updated در چت نشان می‌دهد تا باخبر شوید. کنترل پرحرفیِ آن:

yaml
display:
  memory_notifications: on    # off | on (پیش‌فرض) | verbose
مقداررفتار
offبدون اعلان چت. بازبینی همچنان اجرا و ذخیره می‌کند — فقط خطی برایش نمی‌بینید.
on (پیش‌فرض)خط عمومی، مثل 💾 Memory updated یا 💾 Skill 'foo' patched.
verboseپیش‌نمایش فشردهٔ تغییر را هم می‌آورد، مثل 💾 Memory ➕ User prefers terse replies یا تکه‌ای از دیف مهارت به شکل "old" → "new".

این فقط اعلان چتِ گیت‌وی را تنظیم می‌کند. خود بازبینی و نوشتن به مخازن حافظه/مهارت شما از این تنظیم متأثر نمی‌شوند. به‌ازای-پلتفرم با display.platforms.<platform>.memory_notifications تنظیمش کنید.

۱۴ اجرای بازبینی روی مدل ارزان‌تر (auxiliary.background_review)

بازبینی به‌طور پیش‌فرض روی مدل چت اصلی شما اجرا می‌شود و گفتگو را بازپخیر می‌کند — که از قبل در کش پرامپت گرم است، پس خواندن‌های کشِ ارزانی است. روی یک مدل اصلی گران می‌توانید بازبینی را به‌جایش روی مدلی ارزان‌تر اجرا کنید:

yaml
auxiliary:
  background_review:
    provider: openrouter
    model: google/gemini-3-flash-preview   # auto (پیش‌فرض) = مدل چت اصلی

وقتی به مدلی متفاوت از مدل اصلی‌تان اشاره‌اش می‌دهید، بازبینی برای هزینهٔ بسیار کمتر آنجا اجرا می‌شود (در بنچمارک‌ها حدود ۳ تا ۵ برابر). چون یک مدل متفاوت به‌هرحال نمی‌تواند کش پرامپت مدل اصلی شما را دوباره استفاده کند، انشعاب به‌طور خودکار به‌جای رونوشت کامل، یک چکیدهٔ فشرده از گفتگو (نوبت‌های اخیر عیناً + خلاصهٔ قدیمی‌ترها) را بازپخیر می‌کند — و مقدار نوشته‌شده به کش جدید را حداقل می‌سازد. کیفیت ثبت حفظ می‌شود: در تست‌ها، ثبت حافظه یکسان و ثبت مهارت تقریباً یکسان با بازبینی مدل-اصلی بود.

روی auto بگذاریدش (یا مدل اصلی‌تان) — هیچ‌چیز عوض نمی‌شود؛ بازبینی با بازپخیر کاملِ کش-گرم روی مدل اصلی ادامه می‌دهد.

غیرفعال‌کردن بازبینی‌های خودکار (enabled)

انشعاب بازبینی می‌تواند روی میزبان‌های شلوغ سهم معناداری از کل توکن‌ها را بسوزاند. اپراتورها می‌توانند بدون صفرکردن بازه‌های یادآوری‌اش غیرفعالش کنند:

yaml
auxiliary:
  background_review:
    enabled: true              # false = پرش از انشعاب‌های خودکار پس از نوبت

با enabled: false، انشعاب‌های خودکارِ پس از نوبت تولید نمی‌شوند؛ /refine دستی همچنان کار می‌کند.

مصرف انشعاب در session_model_usage با task='background_review' ماندگار می‌شود و یک خط اتمام به agent.log نوشته می‌شود (Background review complete: thread=bg-review calls=… in=… out=… result=…).

۱۵ کنترل نوشتن‌های مهارت (skills.write_approval)

مهارت‌ها از همان دروازهٔ روشن/خاموش استفاده می‌کنند، اما تجربهٔ بازبینی‌شان فرق دارد چون یک SKILL.md برای خواندن در حباب چت زیادی بزرگ است:

yaml
skills:
  write_approval: false     # false = نوشتن آزاد (پیش‌فرض) | true = نیاز به تأیید

وقتی write_approval: true است، نوشتن‌های مهارت (ایجاد / ویرایش / patch / write_file / حذف) بدون توجه به مبدأ همیشه مرحله‌بندی می‌شوند. خلاصهٔ یک‌خطی را درجا بازبینی می‌کنید، اما دیف کامل برون‌خط می‌ماند:

فرمان‌ها
/skills pending             # فهرست نوشتن‌های مرحله‌شدهٔ مهارت + خلاصهٔ یک‌خطی هرکدام
/skills diff <id>           # دیف کامل یکسان‌شده (بهترین جا: CLI یا داشبورد)
/skills approve <id>        # اعمال (یا 'all')
/skills reject <id>         # انداختن (یا 'all')
/skills approval on         # روشن‌کردن دروازه (یا 'off') و ماندگارکردنش

روی پلتفرم پیام‌رسانی، مهارتی را از خلاصه + فراداده‌اش تأیید کنید، یا وقتی می‌خواهید کل تغییر را بخوانید /skills diff را در CLI / داشبورد / فایل مرحله‌شده زیر ~/.hermes/pending/skills/<id>.json باز کنید. جزئیات کامل در «دروازه‌گذاری نوشتن‌های مهارت ایجنت».

۱۶ ارائه‌دهندگان حافظهٔ خارجی

برای حافظه‌ای عمیق‌تر و پایدارتر که از MEMORY.md و USER.md فراتر می‌رود، هرمس با ۸ پلاگین ارائه‌دهندهٔ حافظهٔ خارجی عرضه می‌شود — از جمله Honcho، OpenViking، Mem0، Hindsight، Holographic، RetainDB، ByteRover و Supermemory.

ارائه‌دهندگان خارجی در کنار حافظهٔ داخلی اجرا می‌شوند (هرگز جایگزینش نمی‌شوند) و قابلیت‌هایی مثل گراف دانش، جستجوی معنایی، استخراج خودکار واقعیت و مدل‌سازی کاربر بین-نشستی اضافه می‌کنند.

bash
hermes memory setup      # انتخاب یک ارائه‌دهنده و پیکربندی‌اش
hermes memory status     # بررسی فعال‌بودن چه چیزی

برای جزئیات کامل هر ارائه‌دهنده، راهنمای نصب و مقایسه، به «ارائه‌دهندگان حافظه» مراجعه کنید.
