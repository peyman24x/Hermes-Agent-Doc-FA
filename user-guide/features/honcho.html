حافظهٔ Honcho ‏(Honcho Memory)

Honcho یک بک‌اند حافظهٔ AI-native است که استدلال جدلی و مدل‌سازی عمیق کاربر را روی سیستم حافظهٔ داخلی هرمس اضافه می‌کند. به‌جای storage ی سادهٔ کلید-مقدار، ‏Honcho مدلی در حال اجرا از اینکه کاربر کیست — ترجیحات، سبک ارتباط، اهداف و الگوها — نگه می‌دارد با استدلال دربارهٔ گفتگوها بعد از وقوعشان.

ℹ️ Honcho یک پلاگین ارائه‌دهندهٔ حافظه است

‏Honcho در سیستم ارائه‌دهندگان حافظه یکپارچه شده. همهٔ قابلیت‌های پایین از طریق رابط واحد ارائه‌دهندهٔ حافظه در دسترس‌اند.

۱ چه چیزی Honcho اضافه می‌کند

پروفایل کاربر✔ curate ی دستی توسط ایجنت✔ استدلال جدلی خودکار
خلاصهٔ نشست—✔ تزریق زمینهٔ scope شده-به-نشست

استدلال جدلی: بعد از هر نوبت گفتگو ‏(گیت‌خورده با dialecticCadence)، ‏Honcho مبادله را تحلیل و بینش‌هایی دربارهٔ ترجیحات، عادات و اهداف کاربر مشتق می‌کند. این‌ها انباشته می‌شوند و به ایجنت درکی عمیق‌کننده می‌دهد که فراتر از گفته‌های صریح کاربر است. جدلی عمق چند-پاسی ‏(۱ تا ۳ پاس) با انتخاب خودکار پرامپت cold/warm دارد — کوئری‌های cold-start روی حقایق عمومی کاربر متمرکزند و کوئری‌های warm زمینهٔ scope‌شده-به-نشست را اولویت می‌دهند.

زمینهٔ scope‌شده-به-نشست: زمینهٔ پایه حالا خلاصهٔ نشست را کنار بازنمایی کاربر و کارت peer شامل می‌شود. این به ایجنت آگاهی از آنچه در نشست فعلی بحث شده می‌دهد؛ تکرار را کم و پیوستگی را ممکن می‌کند.

پروفایل‌های چندایجنتی: وقتی چند نمونهٔ هرمس با همان کاربر حرف می‌زنند ‏(مثلاً دستیار کدنویسی و دستیار شخصی)، ‏Honcho پروفایل‌های peer جدا نگه می‌دارد. هر peer فقط مشاهده‌ها و نتیجه‌گیری‌های خودش را می‌بیند تا زمینه‌ها به هم آلوده نشوند.

Setup

hermes memory setup    # select "honcho" from the provider list

یا دستی:

# ~/.hermes/config.yaml
memory:
  provider: honcho
echo 'HONCHO_API_KEY=***' >> ~/.hermes/.env

کلید API را از ‏honcho.dev بگیرید.

۲ معماری

تزریق زمینهٔ دولایه

هر نوبت ‏(در حالت hybrid یا context)، ‏Honcho دو لایهٔ زمینه داخل پرامپت سیستمی می‌سازد:

  1. زمینهٔ پایه — خلاصهٔ نشست، بازنمایی کاربر، کارت peer کاربر، بازنمایی خودِ AI و کارت هویت AI. refresh روی contextCadence. لایهٔ «این کاربر کیست».
  2. مکمل جدلی — استدلال ترکیب‌شده-با-LLM دربارهٔ وضعیت و نیازهای فعلی کاربر. refresh روی dialecticCadence. لایهٔ «الان چه چیزی مهم است».

هر دو لایه الحاق و به بودجهٔ contextTokens بریده می‌شوند ‏(اگر ست باشد).

انتخاب پرامپت Cold/Warm

  • Cold start ‏(هنوز زمینهٔ پایه نیست): کوئری عمومی — «این فرد کیست؟ ترجیحات، اهداف و سبک کاری‌اش چیست؟»
  • Warm session ‏(زمینهٔ پایه هست): کوئری scope‌شده-به-نشست — «با توجه به آنچه تا الان در این نشست بحث شده، مرتبط‌ترین زمینه دربارهٔ این کاربر چیست؟»

خودکار بر اساس پر شدن زمینهٔ پایه انتخاب می‌شود.

سه پیچ مستقل پیکربندی

پیچکنترل می‌کندپیش‌فرض
contextCadenceنوبت‌های بین فراخوانی‌های API ی context() ‏(refresh لایهٔ پایه)۱
dialecticCadenceنوبت‌های بین فراخوانی‌های LLM ی peer.chat() ‏(refresh لایهٔ جدلی)۲ ‏(توصیه ۱–۵)
dialecticDepthتعداد پاس‌های chat() به‌ازای هر invocation ی جدلی ‏(۱–۳)۱

اینها متعامدند: می‌توانید refresh ی مکرر زمینه با جدلی کم‌بسامد، یا جدلی چند-پاسیِ عمیق با بسامد کم داشته باشید. مثال: ‏contextCadence: 1، ‏dialecticCadence: 5، ‏dialecticDepth: 2 یعنی زمینهٔ پایه هر نوبت refresh، جدلی هر ۵ نوبت و هر اجرای جدلی ۲ پاس.

عمق جدلی ‏(چند-پاس)

وقتی dialecticDepth > 1، هر invocation ی جدلی چند پاس chat() اجرا می‌کند:

  • پاس ۰: پرامپت cold یا warm ‏(بالا)
  • پاس ۱: خود-ممیزی — شکاف‌های ارزیابی اولیه را شناسایی و شواهدی از نشست‌های اخیر ترکیب می‌کند
  • پاس ۲: آشتی‌دهی — تناقض‌های بین پاس‌های قبلی را چک و ترکیب نهایی تولید می‌کند

هر پاس سطح استدلال تناسبی مصرف می‌کند ‏(پاس‌های اولیه سبک‌تر، سطح پایه برای پاس اصلی). با dialecticDepthLevels per-pass override کنید — مثلاً ["minimal", "medium", "high"] برای اجرای depth-3. پاس‌ها اگر پاس قبلی سیگنال قوی برگردانده باشد ‏(خروجی بلند ساختاریافته) زود bail می‌کنند، پس depth 3 همیشه یعنی ۳ فراخوانی LLM نیست.

Prewarm ی شروع-نشست

موقع init ی نشست، ‏Honcho یک فراخوانی جدلی در پس‌زمینه با dialecticDepth کامل پیکربندی‌شده شلیک و نتیجه را مستقیم به assembly ی زمینهٔ نوبت ۱ می‌دهد. prewarm ی تک‌پاس روی peer سرد اغلب خروجی کم برمی‌گرداند — اجرای چند-پاسی چرخهٔ audit/reconcile را قبل از اولین حرف کاربر اجرا می‌کند. اگر prewarm تا نوبت ۱ نرسیده باشد، نوبت ۱ به فراخوانی همگام با timeout ی محدود fallback می‌کند.

سطح استدلال تطبیقی-با-کوئری

جدلیِ خود-تزریق‌شونده مقدار dialecticReasoningLevel را با طول کوئری مقیاس می‌دهد: ‎+۱‎ سطح در ≥۱۲۰ نویسه، ‎+۲‎ در ≥۴۰۰، سقف reasoningLevelCap ‏(پیش‌فرض high). با reasoningHeuristic: false خاموش کنید تا هر فراخوانی خودکار روی dialecticReasoningLevel پین شود. سطوح موجود: minimal، low، medium، high، max.

۳ گزینه‌های پیکربندی

‏Honcho در ~/.honcho/config.json ‏(سراسری) یا $HERMES_HOME/honcho.json ‏(مخصوص-پروفایل) پیکربندی می‌شود. ویزارد setup این کار را برایتان می‌کند.

‏Honcho خودمیزبان با احراز هویت

وقتی هرمس را به سرور self-hosted ی Honcho اشاره می‌دهید، ‏hermes honcho setup ‏(و hermes memory setup) بعد از base URL یک توکن محلی JWT / bearer می‌پرسد. JWT ای امضاشده با AUTH_JWT_SECRET ی سرور ‏(متغیر env ی compose ی Honcho) paste کنید تا دسترسی احراز‌شده فعال شود؛ برای سرورهایی با AUTH_USE_AUTH=false خالی بگذارید. توکن محلی زیر بلوک host ذخیره می‌شود ‏(hosts.<host>.apiKey در honcho.json) جدا از apiKey ی ابری، پس بعداً می‌توانید پرامپت Cloud or local? را بدون از دست دادن هیچ‌کدام از credential ها به cloud برگردانید.

استراتژی نشست تعیین می‌کند نشست‌های Honcho چطور به کار شما نگاشت شوند:

  • per-session — هر اجرای herms نشست تازه. شروع تمیز، حافظه از طریق ابزار. برای کاربران جدید توصیه می‌شود.
  • per-directory — یک نشست Honcho per دایرکتوری کاری. زمینه بین اجراها انباشته می‌شود.
  • per-repo — یک نشست per مخزن git.
  • global — یک نشست واحد بین همهٔ دایرکتوری‌ها.

حالت recall کنترل می‌کند حافظه چطور وارد گفتگو شود:

  • hybrid — زمینه خود-تزریق به پرامپت سیستمی و ابزارها در دسترس ‏(مدل تصمیم می‌گیرد کی کوئری بزند).
  • context — فقط خود-تزریق؛ ابزارها پنهان.
  • tools — فقط ابزارها، بدون خود-تزریق. ایجنت باید صریحاً honcho_reasoning، ‏honcho_search و… را صدا بزند.

تنظیمات per-recall-mode: در hybrid همه فعال‌اند؛ در context فقط writeFrequency/contextCadence/contextTokens مهم‌اند و cadence ی جدلی هنوز فراخوانی‌های خودکار را گیت می‌کند ولی ابزارها نیستند؛ در tools مدل کاملاً در کنترل است — هر وقت خواست با reasoning_level دلخواه honcho_reasoning صدا می‌زند و تنظیمات cadence/بودجه فقط به حالت‌های خود-تزریق ‏(hybrid و context) اعمال می‌شود.

۴ نگاشت هویت گیت‌وی و Observation

این تنظیمات فقط وقتی مهم‌اند که گیت‌وی هرمس را اجرا کنید — تنها نقطهٔ ورودی‌ای که کاربران با runtime ID های بومی-پلتفرم وارد می‌شوند ‏(UID تلگرام، snowflake دیسکورد، کاربر اسلک). نشست‌های CLI/TUI/دسکتاپ runtime ID ندارند و همیشه به peerName حل می‌شوند، پس بیرون گیت‌وی این کلیدها بی‌اثرند.

ویزارد setup تشخیص می‌دهد پلتفرم گیت‌وی وصل است یا نه و نبودش این گام را کامل skip می‌کند. موقع اجرا یک سؤال می‌پرسد — چه کسی با این گیت‌وی حرف می‌زند؟ — و کلیدها را مشتق می‌کند:

پاسخنتیجه
فقط خودمpinUserPeer: true — همهٔ کاربران غیر-ایجنتی به peer شما جمع می‌شوند. pin بر همهٔ alias ها مقدم است، پس فقط وقتی برداریدش که هیچ هویت سمت-کاربری peer ی خودش را لازم نداشته باشد. اگر ایجنت‌های جدا به گیت‌وی می‌رسند و هرکدام peer مجزا needs، pin نکنید — pinUserPeer را false بگذارید و با userPeerAliases ‏(ادیتور [e]) نگاشت کنید
من + دیگران ‏(pooled)pinUserPeer: false + userPeerAliases که runtime ID های شما را به peerName نگاشت می‌کند — شما روی تاریخچهٔ مشترک می‌مانید و بقیه peer های خودشان را می‌گیرند
فقط دیگرانpinUserPeer: false، ‏runtimePeerPrefix اختیاری — هر کاربر peer خودش را می‌گیرد

روی پرامپت [e] را بردارید تا سه کلید را مستقیم ست کنید. resolver کلیدها را بالا-به-پایین امتحان می‌کند، اولین تطبیق برنده: pinUserPeer ← userPeerAliases[id] ← runtimePeerPrefix + id ← raw runtime ID ← peerName ← fallback ی session-key.

⚠️ un-pin کردن حافظهٔ pooled را یتیم می‌کند

فلپ کردن pinUserPeer از true به false داده را migrate نمی‌کند — حافظهٔ انباشته زیر peerName همانجا می‌ماند و کاربران پلتفرم به peer های تازه و خالی حل می‌شوند. برای حفظ پیوستگی خودتان مسیر pooled را بردارید تا runtime ID هایتان به peerName نام‌مستعار شوند. ویزارد موقع تشخیص این گذار خودش همین steer را پیشنهاد می‌دهد.

📌 کلید deprecated

pinPeerName نام مستعار legacy ی pinUserPeer است — برای سازگاری خوانده می‌شود ‏(در صورت ست بودن هر دو، pinUserPeer برنده)، هرگز نوشته نمی‌شود. اجرای دوباره setup آن را روی کلید مرجع مهاجرت می‌دهد.

Observation ‏(Directional در برابر Unified)

‏Honcho گفتگو را peers ی تبادل‌کنندهٔ پیام مدل می‌کند. هر peer دو toggle ی مشاهده دارد که ۱:۱ به SessionPeerConfig ی Honcho نگاشت می‌شود:

toggleاثر
observeMeHoncho از پیام‌های خودِ این peer بازنمایی‌اش را می‌سازد
observeOthersاین peer پیام‌های peer دیگر را مشاهده می‌کند ‏(خوراک استدلال cross-peer)

دو peer × دو toggle = چهار فلگ. observationMode پیش‌تنظیمِ خلاصار است:

پیش‌تنظیمفلگ‌های کاربرفلگ‌های AIمعنا
"directional" ‏(پیش‌فرض)me روشن، others روشنme روشن، others روشنمشاهدهٔ متقابل کامل. جدلی cross-peer را فعال می‌کند — «AI بر اساس گفتهٔ کاربر و reply ی خودش چه می‌داند»
"unified"me روشن، others خاموشme خاموش، others روشنمعناشناسی استخر-مشترک — AI فقط پیام‌های کاربر را مشاهده می‌کند و peer ی کاربر فقط خودش را مدل می‌کند. استخر ناظر-واحد

پیش‌تنظیم را با بلوک صریح observation برای کنترل per-peer بازنویسی کنید. الگوهای رایج: مشاهدهٔ کامل برای بیشتر کاربران با directional؛ جلوگیری از re-model کردن کاربر توسط AI با ai.observeMe: true + observeOthers: false؛ شخصیت قوی که AI نباید از مشاهدهٔ خودش به‌روزش کند با ai.observeMe: false + observeOthers: true. toggle های سمت-سرور ست‌شده از طریق داشبورد Honcho بر پیش‌فرض‌های محلی می‌چربند — هرمس موقع init ی نشست sync‌شان برمی‌گرداند.

فرمان‌های CLI

زیرفرمان hermes honcho فقط وقتی ثبت می‌شود که Honcho ارائه‌دهندهٔ فعال حافظه باشد ‏(memory.provider: honcho در config.yaml). روی نصب تازه مستقیماً با hermes memory setup honcho پیکربندی‌اش کنید؛ زیرفرمان hermes honcho در invocation بعدی ظاهر می‌شود.

hermes memory setup honcho    # Configure Honcho directly (works before activation)
hermes honcho status          # Connection status, config, and key settings
hermes honcho strategy        # Show or set session strategy
hermes honcho peer            # Show or update peer names + dialectic reasoning level
hermes honcho mode            # Show or set recall mode (hybrid/context/tools)
hermes honcho tokens          # Show or set token budget for context and dialectic
hermes honcho identity        # Seed or show the AI peer's Honcho identity
hermes honcho sync            # Sync Honcho config to all existing profiles
hermes honcho peers           # Show peer identities across all profiles
hermes honcho sessions        # List known Honcho session mappings
hermes honcho map             # Map current directory to a Honcho session name
hermes honcho enable          # Enable Honcho for the active profile
hermes honcho disable         # Disable Honcho for the active profile
hermes honcho migrate         # Step-by-step migration guide from openclaw-honcho

مهاجرت از hermes honcho قدیمی

  1. config موجودتان ‏(honcho.json یا ~/.honcho/config.json) حفظ می‌شود
  2. داده‌های سمت-سرور ‏(حافظه‌ها، نتیجه‌گیری‌ها، پروفایل‌های کاربر) سالم‌اند
  3. memory.provider: honcho را در config.yaml ست کنید تا دوباره فعال شود

بدون re-login یا re-setup. ‏hermes memory setup را اجرا و honcho را بردارید — ویزارد config موجودتان را تشخیص می‌دهد.
