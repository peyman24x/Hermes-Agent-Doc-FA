‏MCP ‏(Model Context Protocol)

‏MCP اجازه می‌دهد هرمس ایجنت به سرورهای ابزار خارجی وصل شود تا ایجنت بتواند از ابزارهایی استفاده کند که بیرون از خود هرمس زندگی می‌کنند — ‏GitHub، ‏دیتابیس‌ها، فایل‌سیستم‌ها، پشته‌های مرورگر، APIهای داخلی و بیشتر.

اگر همیشه دوست داشته‌اید هرمس از ابزاری که قبلاً جای دیگری وجود دارد استفاده کند، ‏MCP معمولاً تمیزترین راه انجامش است.

💡 از Claude Code می‌آیید؟

بلوک ‏mcpServers در ‏~/.claude.json` شما به `mcp_servers در config.yaml هرمس نگاشت می‌شود — و ‏hermes import-agent claude-code آن را ‏(همراه مهارت‌ها و دستورالعمل‌ها) خودکار مهاجرت می‌دهد. بخش «ورود از سایر ایجنت‌ها» را ببینید.

۱ ‏MCP چه چیزی به شما می‌دهد

  • دسترسی به اکوسیستم‌های ابزار خارجی بدون نوشتن اولیهٔ ابزار native هرمس
  • سرورهای stdio محلی و سرورهای HTTP راه‌دور MCP در یک پیکربندی واحد
  • کشف و ثبت خودکار ابزارها هنگام شروع
  • wrapper های کاربردی برای منابع و پرامپت‌های MCP وقتی سرور پشتیبانی کند
  • فیلترکردن به‌ازای-سرور تا فقط ابزارهای MCP واقعاً موردنظرتان را هرمس ببیند

شروع سریع

  1. پشتیبانی MCP با نصب استاندارد عرضه می‌شود — گام اضافه‌ای لازم نیست.
  2. یک سرور MCP به config.yaml اضافه کنید:
yaml
mcp_servers:
  filesystem:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/projects"]
  1. هرمس را شروع کنید:
hermes chat
  1. از هرمس بخواهید قابلیت پشتیبان-MCP را استفاده کند. مثلاً:
List the files in /home/user/projects and summarize the repo structure.

هرمس ابزارهای سرور MCP را کشف و مثل هر ابزار دیگری استفاده می‌کند.

۲ کاتالوگ: نصب یک‌کلیکی برای MCP های تأییدشده توسط Nous

هرمس یک کاتالوگ منتخب از سرورهای MCP عرضه می‌کند که توسط کارکنان Nous بازبینی و ادغام شده‌اند. پیش‌فرض خاموش‌اند — فقط چیزی که واقعاً می‌خواهید نصب کنید.

bash
hermes mcp                # انتخاب‌گر تعاملی (پیش‌فرض)
hermes mcp catalog        # فهرست متنی ساده، قابل‌اسکریپت
hermes mcp install n8n    # نصب یک ورودی کاتالوگ با نام

انتخاب‌گر هر ورودی با وضعیت فعلی‌اش نشان می‌دهد:

text
n8n          available              Manage and inspect n8n workflows from Hermes
linear       enabled                Linear issue/project management (remote OAuth)
github       installed (disabled)   GitHub repo + PR tools

روی یک ردیف Enter بزنید تا نصب ‏(و طی کردن اعتبارنامه‌های لازم)، فعال‌سازی، غیرفعال‌سازی یا حذف نصب شود. ورودی‌های کاتالوگ زیر ‏optional-mcps/ در مخزن hermes-agent ذخیره می‌شوند — حضور در آن پوشه یعنی تأیید Nous. هیچ سطح ارسال اجتماعی وجود ندارد؛ ورودی‌ها با ادغام یک PR اضافه می‌شوند.

ورودی‌های کاتالوگ می‌توانند نیازمند باشند:

  • کلید API — هرمس هنگام نصب می‌پرسد و مقدار را در ‏~/.hermes/.env می‌نویسد. مقادیر غیر-محرمانه ‏(URLهای پایه) به همان فایل می‌روند.
  • OAuth ‏(MCP راه‌دور) — به‌صورت ‏auth: oauth در پیکربندی نوشته می‌شود؛ کلاینت MCP اولین اتصال مرورگر باز می‌کند.
  • OAuth ‏(ارائه‌دهندهٔ شخص ثالث مثل Google/GitHub) — اگر هنوز احراز نکرده باشید هرمس شما را به ‏hermes auth <provider> اشاره می‌دهد.

انتخاب ابزار هنگام نصب

بعد از پیکربندی اعتبارنامه‌ها، هرمس سرور MCP را probe می‌کند تا همهٔ ابزارهای expose‌شده را فهرست و چک‌لیستی نشان دهد:

text
Select tools for 'linear' (SPACE toggle, ENTER confirm)
  [x] find_issues       Find issues matching a query
  [x] get_issue         Get a single issue
  [x] create_issue      Create a new issue
  [ ] delete_workspace  Delete a Linear workspace
  ...

ردیف‌های پیش‌تیک‌خورده از این‌جا می‌آیند:

  1. انتخاب قبلی شما اگر قبلاً این ورودی را نصب کرده بودید ‏(نصب مجدد همان قبلی‌ها را حفظ می‌کند — پیش‌فرض‌های manifest آن را override نمی‌کنند)
  2. ‏tools.default_enabled مربوط به manifest اگر ورودی یکی اعلام کرده باشد ‏(بعضی ورودی‌های کاتالوگ ابزارهای تغییردهنده یا کم‌کاربرد را از قبل هرس می‌کنند)
  3. همه‌چیز اگر هیچ‌کدام اعمال نشود

چک‌لیست را با ENTER ثبت کنید. فقط ابزارهای تیک‌خورده به ‏mcp_servers.<name>.tools.include می‌روند. اگر همه را انتخاب کنید هیچ فیلتری نوشته نمی‌شود ‏(تمیزترین شکل پیکربندی، رفتار یکسان).

اگر probe شکست بخورد ‏(سرور غیرقابل‌دسترس، OAuth هنوز کامل نشده، سرویس پشتیبان روشن نیست)، نصب همچنان موفق می‌شود: ‏tools.default_enabled مربوط به manifest مستقیم اعمال می‌شود ‏(اگر اعلام شده) یا هیچ فیلتری نوشته نمی‌شود ‏(اگر نه). وقتی سرور در دسترس شد ‏hermes mcp configure <name> را دوباره اجرا کنید تا دقیق شود.

مدل اعتماد

نصب یک ورودی کاتالوگ هرچه manifest مشخص کند را اجرا می‌کند — ‏git clone، فرمان‌های ‏bootstrap ورودی ‏(pip install، ‏npm install و...) و در نهایت کد خودِ سرور MCP. ‏manifest ها با بازبینی PR داخل مخزن hermes-agent گیت می‌خورند، پس Nous هر ورودی را قبل از عرضه بازبینی کرده — ولی همچنان باید قبل از نصب خودتان manifest را بخوانید، مخصوصاً مخزنِ فیلد ‏source:، فرمان‌های ‏install.bootstrap: و هر فراخوانی ‏transport.command:.

‏manifest ها در گیت‌هاب روی مسیر ‏optional-mcps/<name>/manifest.yaml زندگی می‌کنند. انتخاب‌گر هم URL ‏source: مربوط به manifest را هنگام نصب چاپ می‌کند تا سریع مخزن بالادستی را تأیید کنید. صفحهٔ MCP داشبورد وب همین جزئیات را به‌ازای هر ورودی کاتالوگ نشان می‌دهد — ترنسپورت، نوع احراز، URL نقطهٔ پایانی ‏(HTTP) یا فرمان+آرگومان‌ها ‏(stdio)، منبع/ref نصب گیت و فرمان‌های bootstrap و یادداشت‌های setup — با رندر شدن ‏source: به‌صورت لینک کلیک‌پذیر، تا قبل از زدن Install دقیقاً ببینید ورودی به چه چیزی وصل یا چه چیزی اجرا می‌کند.

سازگاری نسخهٔ manifest

‏manifest ها مقدار ‏manifest_version را pin می‌کنند. کاتالوگ رو-به-جلو سازگار است: اگر PR ای ورودی‌ای با ‏manifest_version جدیدتری از هرمس نصب‌شده شما اضافه کند، انتخاب‌گر برای آن ورودی هشدار سطح پیدا می‌کند ‏(⚠ '<name>' requires a newer Hermes) به‌جای مخفی‌کردن بی‌صدایش. وقتی دیدید ‏hermes update را اجرا کنید تا آخرین هرمس نصب شود.

جانشینی runtime ‏${ENV_VAR}

داخل ‏transport.command، ‏transport.args، ‏transport.url و ‏headers مربوط به یک ورودی، placeholder های ‏${VAR} هنگام اتصال سرور از متغیرهای محیطی حل می‌شوند ‏(که شامل همهٔ ‏~/.hermes/.env است). وقتی مفید است که ورودی کاتالوگی بخواهد به مقداری که کاربر جای دیگر پیکربندی کرده اشاره کند — مثل ‏${HOME}/foo یا ‏${MY_PROVIDER_TOKEN}.

متغیرهای زمینه سبک Cursor هم جانشین می‌شوند ‏(حساس-به-حروف): ‏${userHome} ‏(پوشهٔ خانه)، ‏${workspaceFolder} ‏(ریشهٔ ورک‌اسپیس نشست)، ‏${workspaceFolderBasename} و ‏${pathSeparator}/${/} ‏(جداکنندهٔ مسیر OS). جزئیات در مرجع پیکربندی MCP.

توجه کنید این جدا از ‏${INSTALL_DIR} در manifest های کاتالوگ است که هنگام نصب با مسیری که کاتالوگ repo ورودی را clone کرده جانشین می‌شود.

به‌روزرسانی بعدیِ انتخاب ابزار

hermes mcp configure linear

همان چک‌لیست را با انتخاب فعلی شما پیش‌تیک‌خورده دوباره باز می‌کند. وقتی ابزارهای بیشتری می‌خواهید فعال شوند یا سرور ابزارهای جدیدی اضافه کرده که می‌خواهید انتخابشان کنید استفاده کنید.

به‌روزرسانی manifest کاتالوگ

‏MCP ها هرگز خودکار به‌روز نمی‌شوند. بعد از به‌روزرسانی هرمس، اگر نسخهٔ manifest عوض شده ‏hermes mcp install <name> را دوباره اجرا کنید.

برای افزودن MCP به کاتالوگ علیه ‏optional-mcps/ ‏PR باز کنید.

متادیتای پیشنهاد ‏(suggest:)

یک manifest ممکن است بلوک اختیاری ‏suggest: با فهرست‌های ‏keywords: و/یا ‏hosts: اعلام کند. سطوح UI ‏(الان کامپوزر اپ Desktop) از آن برای پیشنهاد قرص یک‌کلیکی «Add <server>» استفاده می‌کنند وقتی پیش‌نویس شما یکی از کلیدواژه‌ها را به‌عنوان واژهٔ کامل ذکر کند یا لینک چسبانده‌شده‌ای داشته باشد که hostname اش به یکی از پسوندهای میزبان ختم شود. صرفاً مشورتی است — نصب‌ها همچنان از همان مسیرهای اعتبارسنجی‌شدهٔ کاتالوگ/config می‌گذرند — و بیشتر ورودی‌های راه‌دورِ میزبانی‌شده ‏(Atlassian، ‏Sentry، ‏Notion، ‏Stripe، ‏Vercel، ‏Supabase و رفقایش) آن را اعلام می‌کنند.

‏GitHub عمداً در کاتالوگ نیست: ‏MCP میزبانی‌شده‌اش از هر کلاینت می‌خواهد اپ OAuth خودش را بیاورد ‏(ثبت داینامیک عمومی کلاینت رد می‌شود) و مهارت‌های همراه‌بستهٔ ‏github/* هرمس که CLI ‏gh را می‌رانند یکپارچه‌سازی توانمندتری هستند. روی Desktop، ذکر GitHub به‌جایش وقتی gh هنوز وارد نشده مهارت ‏github-auth را پیشنهاد می‌دهد.

۳ دو نوع سرور MCP

سرورهای Stdio

سرورهای stdio به‌عنوان زیرپروسه‌های محلی اجرا و از طریق stdin/stdout حرف می‌زنند.

yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"

سرورهای stdio را وقتی استفاده کنید که:

  • سرور محلی نصب شده باشد
  • دسترسی کم‌تأخیر به منابع محلی بخواهید
  • مستندات سرور MCP‌ای را دنبال می‌کنید که ‏command و args و env نشان می‌دهد

سرورهای HTTP

سرورهای HTTP ‏MCP نقاط پایانی راه‌دوری هستند که هرمس مستقیم به آن‌ها وصل می‌شود.

yaml
mcp_servers:
  remote_api:
    url: "https://mcp.example.com/mcp"
    headers:
      Authorization: "Bearer ***"

سرورهای HTTP را وقتی استفاده کنید که:

  • سرور MCP جای دیگری میزبانی شده باشد
  • سازمان‌تان نقاط پایانی MCP داخلی expose کند
  • نخواهید هرمس برای آن یکپارچه‌سازی زیرپروسه محلی spawn کند

سرورهای HTTP با احراز OAuth

بیشتر سرورهای MCP میزبانی‌شده ‏(Linear، ‏Sentry، ‏Atlassian، ‏Asana، ‏Figma، ‏Stripe و...) به‌جای bearer token ثابت OAuth 2.1 می‌خواهند. مقدار ‏auth: oauth را بگذارید و هرمس کشف، شناسایی کلاینت، ‏PKCE، تبادل توکن، refresh و auth مرحله‌ای را از طریق SDK پایتونی MCP هندل می‌کند.

هرمس خودش با یک ‏سند متادیتای Client ID روی سرورهایی که پشتیبانی‌اش می‌کنند معرفی می‌شود و روی بقیه به Dynamic Client Registration برمی‌گردد. هر دو خودکارند؛ چیزی برای پیکربندی نیست.

💡 ‏MCP راه‌دور فیتما

نقطهٔ پایانی میزبانی‌شده فیتما ‏(https://mcp.figma.com/mcp) ثبت داینامیک کلاینت را با تطبیق ‏دقیق ‏client_name لیست‌مجاز می‌کند — ‏"Hermes Agent" لخت مقدار 403 می‌گیرد در حالی که ‏"Claude Code" و ‏"Codex" موفق می‌شوند. هرمس برای ‏mcp.figma.com خودکار ‏oauth.client_name: "Claude Code" را ست می‌کند تا نصب/ورود بدون ترفند خاص کار کند:

yaml
mcp_servers:
  figma:
    url: "https://mcp.figma.com/mcp"
    auth: oauth

یا: ‏hermes mcp install figma سپس ‏hermes mcp login figma.

yaml
mcp_servers:
  linear:
    url: "https://mcp.linear.app/mcp"
    auth: oauth

در اولین اتصال هرمس URL مجوز چاپ، در صورت امکان مرورگرتان را باز و روی یک پورت loopback محلی منتظر callback می‌ماند. توکن‌ها با دسترسی ‏0o600 در ‏~/.hermes/mcp-tokens/<server>.json کش می‌شوند؛ اجراهای بعدی بی‌صدا ازشان بازمصرف می‌کنند تا refresh شکست بخورد.

میزبان‌های راه‌دور / headless. وقتی هرمس روی ماشینی غیر از ماشین مرورگرتان اجراست، callback loopback نمی‌تواند به لپ‌تاپ‌تان برسد. دو راه تکمیل جریان:

  • چسباندن-برگردان ‏(بدون setup): روی ترمینال تعاملی هرمس کنار URL مجوز «Or paste the redirect URL here…» چاپ می‌کند. URL را در مرورگر باز، تأیید و URL کاملِ نهایی‌شده در مرورگر را کپی کنید ‏(redirect خطای اتصال نشان می‌دهد — طبیعی است) و در پرامپت بچسبانید. query string های لخت ‏?code=…&state=… هم کار می‌کنند.
  • Port forward از طریق SSH: در ترمینال جدا ‏ssh -N -L <port>:127.0.0.1:<port> user@host و بعد بگذارید redirect عادی جریان یابد.
  • callback پروکسی‌شده ‏(redirect_uri): وقتی endpoint عمومی HTTPS به میزبان فوروارد می‌کند ‏(مثل Tailscale Funnel یا پروکسی معکوس اشاره‌شده به پورت callback)، مقدار ‏oauth.redirect_uri را بگذارید تا redirect مرورگر خودش به هرمس برسد — بدون تونل یا چسباندن:
yaml
mcp_servers:
  myserver:
    url: "https://mcp.example.com/mcp"
    auth: oauth
    oauth:
      redirect_port: 8765                                # پورت ثابت برای هدف پروکسی
      redirect_uri: "https://oauth.example.ts.net/callback"

برای گیت‌وی‌های کاملاً headless ‏(بات پیام‌رسانی، اصلاً بدون ترمینال تعاملی)، مهارت اختیاری ‏mcp-oauth-remote-gateway ایجنت را قدم‌به‌قدم برای تکمیل دستی جریان و نوشتن توکن‌ها در محل موردانتظار هرمس راهنمایی می‌کند.

دام — ‏WAF مقدار redirect ‏127.0.0.1 را رد می‌کند. چند ارائه‌دهنده سرور مجوزشان را با WAFی جلو می‌گیرند که هر درخواست authorize دارای query string حاوی ‏127.0.0.1 لخت را 403 می‌کند ‏(AWS API Gateway شرکت Reclaim.ai نمونهٔ شناخته‌شده است — هر تلاشی قبل از رسیدن به اپ OAuth مقدار ‏{"message":"Forbidden"} برمی‌گرداند). مقدار ‏oauth.redirect_host: localhost را بگذارید تا به‌جایش ‏http://localhost:<port>/callback استفاده شود؛ شنونده callback در هر صورت همچنان روی ‏127.0.0.1 بایند می‌شود.

OAuth از طریق SSH / میزبان‌های راه‌دور را برای راهنمای کامل ببینید، شامل سرورهای بدون ‏DCR ‏(مثل Slack)، ‏client_id/client_secret پیش-ثبت‌شده، سفارشی‌سازی scope و احراز مجدد با ‏hermes mcp login <server>.

دام — ارائه‌دهنده‌هایی که ثبت خودکار را پشتیبانی نمی‌کنند ‏(Google Drive، ‏Atlassian). بعضی سرورها مرحلهٔ ثبت داینامیک کلاینت ‏(RFC 7591) را که ‏auth: oauth لخت به آن اتکا دارد رد می‌کنند — سرور رسمی Drive گوگل ‏(https://drivemcp.googleapis.com/mcp/v1) مقدار ‏400 Bad Request برمی‌گرداند، پس هیچ کلاینت OAuth ساخته و هیچ توکنی گرفته نمی‌شود. علامتش ظریف است: این سرورها ‏tools/list را هم بدون احراز سرو می‌کنند، پس ‏hermes mcp login می‌تواند ابزارها را فهرست و موفق به نظر برسد ولی هر فراخوانی واقعی ابزار بعداً timeout می‌شود. ‏hermes mcp login الان این را تشخیص می‌دهد ‏(چک می‌کند توکن واقعاً روی دیسک بنشیند) و می‌گوید کلاینت OAuth خودتان را بدهید. یکی در کنسول ارائه‌دهنده بسازید و به پیکربندی اضافه کنید:

yaml
mcp_servers:
  googledrive:
    url: "https://drivemcp.googleapis.com/mcp/v1"
    auth: oauth
    oauth:
      client_id: "<your-oauth-client-id>"
      client_secret: "<your-oauth-client-secret>"

سپس ‏hermes mcp login googledrive را اجرا کنید — با کلاینت پیش-ثبت‌شده هرمس از ثبت می‌گذرد و جریان عادی مجوز مرورگری را اجرا می‌کند.

دام — race بارگذاری مجدد خودکار پیکربندی. وقتی ‏~/.hermes/config.yaml را از داخل یک نشست در-حال-اجرا هرمس ویرایش کنید، ‏CLI اتصالات MCP را با timeout ۳۰ ثانیه‌ای خودکار reload می‌کند. برای جریان OAuth تعاملی کافی نیست. ورودی را اضافه کنید، بعد ‏hermes mcp login <server> را از ترمینال تازه اجرا کنید — تمام ۵ دقیقه برای تکمیل احراز شما صبر می‌کند.

۴ ‏mTLS / گواهی کلاینت

سرورهای HTTP راه‌دور MCP که نیاز به mutual TLS دارند ‏(احراز گواهی-کلاینت) از طریق ‏client_cert/client_key پشتیبانی می‌شوند. هرمس گواهی حل‌شده را برای دست‌دادن TLS به کلاینت HTTP زیرین می‌دهد.

‏client_cert سه شکل می‌پذیرد:

  • یک مسیر PEM ترکیبی واحد — یک فایل هم گواهی هم کلید خصوصی:
yaml
mcp_servers:
  internal_api:
    url: "https://mcp.internal.example.com/mcp"
    client_cert: "~/.certs/mcp-client.pem"
  • یک ۲تایی ‏[cert, key] — گواهی و کلید در فایل‌های جدا ‏(معادل تنظیم ‏client_cert + ‏client_key):
yaml
mcp_servers:
  internal_api:
    url: "https://mcp.internal.example.com/mcp"
    client_cert: ["~/.certs/mcp-client.crt", "~/.certs/mcp-client.key"]
  • یک ۳تایی ‏[cert, key, password] — وقتی کلید خصوصی رمزگذاری شده، عنصر سوم passphrase کلید است:
yaml
mcp_servers:
  internal_api:
    url: "https://mcp.internal.example.com/mcp"
    client_cert: ["~/.certs/mcp-client.crt", "~/.certs/mcp-client.key", "${MCP_KEY_PASSWORD}"]

می‌توانید گواهی و کلید را کاملاً جدا هم نگه دارید: ‏client_cert ‏(PEM ترکیبی) به‌اضافهٔ ‏client_key صریح. مسیرها از ‏~ پشتیبانی می‌کنند؛ فایل غایب به‌جای شکست دست‌دادن TLS مبهم، خطای واضح scoped-به-سرور می‌دهد.

۵ هدر هویت به‌ازای-کاربر

سرورهای HTTP/SSE راه‌دور MCP که رفتارشان بر هویت فراخواننده کلید می‌خورد ‏(سقف نرخ به‌ازای-کاربر، رد حسابرسی، مسیریابی چند-مستأجری) می‌توانند با ‏identity_header در هر درخواست هدر هویت دریافت کنند:

yaml
mcp_servers:
  team_api:
    url: "https://mcp.team.example.com/mcp"
    identity_header:
      name: "X-User-Id"
      value_from: "static"   # "static" (پیش‌فرض) یا "profile"
      value: "alice"         # برای static الزامی
  • ‏value_from: static مقدار تحت‌اللفظی ‏value را از config.yaml می‌فرستد.
  • ‏value_from: profile نام پروفایل فعال هرمس را می‌فرستد که یک‌بار هنگام اتصال حل می‌شود — مفید وقتی چند پروفایل روی یک ماشین با همان سرور حرف می‌زنند و سرور باید تفریقشان کند.

ورودی صریح در mapping ‏headers سرور با همان نام ‏(هر حروف‌چینی) همیشه برنده است؛ هدر هویت هرگز پیکربندی هدر خودتان را override نمی‌کند. بلوک‌های ‏identity_header نامعتبر هشدار داده و نادیده گرفته می‌شوند — هرگز مانع اتصال سرور نمی‌شوند. روی سرورهای stdio این کلید با هشدار نادیده گرفته می‌شود ‏(ترنسپورت‌های stdio هدر ندارند).

۶ مرجع پیکربندی پایه

هرمس پیکربندی MCP را از ‏~/.hermes/config.yaml زیر ‏mcp_servers می‌خواند.

بازیافت سرورهای stdio سنگین-حافظه

سرورهای MCP مبتنی بر مرورگر ‏(مثل ‏@playwright/mcp) بعد از اولین فراخوانی ابزار یک Chromium کامل مقیم نگه می‌دارند — صدها مگابایت که هرگز آزاد نمی‌شود. بازیافت خودکار را انتخاب کنید و سرور بعد از حد idle/lifetime جمع و دفعه بعد که یکی از ابزارش صدا زده شود شفاف ری‌استارت می‌شود ‏(ابزارش در طول این مدت ثبت‌شده می‌مانند):

yaml
mcp_servers:
  playwright:
    command: "npx"
    args: ["-y", "@playwright/mcp@latest", "--headless"]
    idle_timeout_seconds: 900     # بازیافت بعد از ۱۵ دقیقه بدون فراخوانی ابزار
    max_lifetime_seconds: 86400   # و مستقل از آن حداقل روزی یک‌بار

مثال حداقلی HTTP

yaml
mcp_servers:
  company_api:
    url: "https://mcp.internal.example.com"
    headers:
      Authorization: "Bearer ***"

۷ preset های داخلی

برای سرورهای MCP معروف، ‏hermes mcp add فلگ ‏--preset را می‌پذیرد که جزئیات ترنسپورت را پر می‌کند تا لازم نباشد دنبال فرمان و آرگومان‌ها بگردید. preset فقط پیش‌فرض می‌دهد — هر چیز دیگری ‏(env، هدرها، فیلتر) که در همان خط فرمان بدهید همچنان برنده است.

Presetچه چیزی را سیم‌کشی می‌کند
codexسرور MCP مربوط به CLI ‏Codex ‏(codex mcp-server روی stdio). نیازمند حضور CLI ‏codex روی PATH.
 
# افزودن CLI Codex به‌عنوان سرور MCP در یک خط
hermes mcp add codex --preset codex

معادل این را می‌نویسد:

yaml
mcp_servers:
  codex:
    command: "codex"
    args: ["mcp-server"]

می‌توانید هر نام محلی انتخاب کنید ‏(hermes mcp add my-codex --preset codex هم اوکی است)؛ preset فقط پیش‌فرض‌های ‏command/args را می‌دهد.

۸ نحوهٔ ثبت ابزارهای MCP توسط هرمس

هرمس به ابزارهای MCP پیشوند می‌زند تا با نام‌های داخلی تداخل نکنند:

mcp_<server_name>_<tool_name>

مثال‌ها:

سرورابزار MCPنام ثبت‌شده
filesystemread_filemcp_filesystem_read_file
githubcreate-issuemcp_github_create_issue
my-apiquery.datamcp_my_api_query_data

در عمل معمولاً لازم نیست نام پیشونددار را دستی صدا بزنید — هرمس ابزار را می‌بیند و حین استدلال عادی انتخابش می‌کند.

پاکسازی نتیجهٔ ابزار و ‏_meta

دو رفتار روی هر نتیجهٔ ابزار MCP قبل از دید مدل اعمال می‌شود:

  • کاراکترهای TAG یونیکد نامرئی حذف می‌شوند. کاراکترهای بازهٔ U+E0000–U+E007F در ترمینال‌ها و UIهای چت هیچ رندر نمی‌شوند ولی کاملاً برای مدل مرئی‌اند — یک کلاسیک کانال قاچاق prompt-injection برای سرور مخرب یا آلوده. هرمس آنها را از نتایج ابزار، محتوای منابع و توصیفات ابزار حذف می‌کند. دنباله‌های تگ ایموجی مشروع ‏(پرچم‌های منطقه‌ای مثل 🏴󠁧󠁢󠁳󠁣󠁴󠁿) حفظ می‌شوند.
  • ‏_meta فروشنده سطح پیدا می‌کند؛ کلیدهای رزروشدهٔ پروتکل نه. وقتی سروری mapping ‏_metaای به نتیجهٔ ابزار الصاق کند ‏(namespace های فروشنده مثل ‏com.example/handoff)، هرمس آن را همراه محتوای نتیجه به مدل می‌دهد. کلیدهای زیر پیشوندهای رزروشدهٔ پروتکل — برچسب ‏modelcontextprotocol یا ‏mcp به‌دنبال‌شده با برچسب دیگر، مثل ‏modelcontextprotocol.io/... یا ‏tools.mcp.com/... — دور ریخته می‌شوند مطابق قواعد نام‌کلید مشخصات MCP. اگر چیزی رو-به-مدل باقی نماند، فیلد _meta کلاً حذف می‌شود.

۹ ابزارهای کاربردی MCP

وقتی پشتیبانی شود، هرمس حول منابع و پرامپت‌های MCP هم ابزارهای کاربردی ثبت می‌کند:

  • ‏list_resources
  • ‏read_resource
  • ‏list_prompts
  • ‏get_prompt

این‌ها به‌ازای هر سرور با همان الگوی پیشوند ثبت می‌شوند، مثلاً:

  • ‏mcp_github_list_resources
  • ‏mcp_github_get_prompt

مهم

این ابزارهای کاربردی الان قابلیت-آگاه‌اند:

  • هرمس wrapper های منابع را فقط اگر نشست MCP واقعاً از عملیات منابع پشتیبانی کند ثبت می‌کند
  • هرمس wrapper های پرامپت را فقط اگر نشست MCP واقعاً از عملیات پرامپت پشتیبانی کند ثبت می‌کند

پس سروری که ابزارهای قابل‌فراخوانی دارد ولی منبع/پرامپت ندارد آن wrapper های اضافه را نمی‌گیرد.

۱۰ فیلتر به‌ازای-سرور

می‌توانید کنترل کنید هر سرور MCP چه ابزارهایی به هرمس بدهد و مدیریت دقیقی روی namespace ابزارتان داشته باشید.

غیرفعال‌سازی کامل یک سرور

yaml
mcp_servers:
  legacy:
    url: "https://mcp.legacy.internal"
    enabled: false

با ‏enabled: false هرمس سرور را کامل رد و حتی تلاش به اتصال هم نمی‌کند.

لیست‌سفید ابزارهای سرور

yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"
    tools:
      include: [create_issue, list_issues]

فقط همان ابزارهای سرور MCP ثبت می‌شوند.

لیست‌سیاه ابزارهای سرور

yaml
mcp_servers:
  stripe:
    url: "https://mcp.stripe.com"
    tools:
      exclude: [delete_customer]

همهٔ ابزارهای سرور به‌جز موارد حذف‌شده ثبت می‌شوند.

الگوهای Glob

هر دو فهرست در کنار نام‌های دقیق الگوهای glob سبک fnmatch هم می‌پذیرند — برای سطوح تختِ عظیم مثل API ‏MCP کلادفلر ‏(?codemode=false، حدود ۳٬۳۰۰ ابزار) که حذف نواحی محصول یکی‌یکی غیرعملی است ضروری است:

yaml
mcp_servers:
  cloudflare:
    url: "https://mcp.cloudflare.com/mcp?codemode=false"
    auth: oauth
    tools:
      exclude: ["*_radar_*", "*_accounts_dlp_*", "*_zones_web3_*"]

ورودی‌های بدون متاکاراکتر glob ‏(*، ‏?، ‏[) دقیق تطبیق می‌یابند — ‏docs فقط ابزارِ نام‌دار docs را حذف می‌کند هرگز ‏docs_search را نه.

قاعدهٔ تقدم

اگر هر دو موجود باشند:

yaml
tools:
  include: [create_issue]
  exclude: [create_issue, delete_issue]

‏include برنده است.

فیلتر ابزارهای کاربردی هم

می‌توانید wrapper های کاربردیِ افزوده‌شده توسط هرمس را جداگانه هم خاموش کنید:

yaml
mcp_servers:
  docs:
    url: "https://mcp.docs.example.com"
    tools:
      prompts: false
      resources: false

یعنی:

  • ‏tools.resources: false مقدار ‏list_resources و ‏read_resource را خاموش می‌کند
  • ‏tools.prompts: false مقدار ‏list_prompts و ‏get_prompt را خاموش می‌کند

مثال کامل

yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"
    tools:
      include: [create_issue, list_issues, search_code]
      prompts: false

  stripe:
    url: "https://mcp.stripe.com"
    headers:
      Authorization: "Bearer ***"
    tools:
      exclude: [delete_customer]
      resources: false

  legacy:
    url: "https://mcp.legacy.internal"
    enabled: false

۱۱ اگر همه‌چیز فیلتر شود چه می‌شود؟

اگر پیکربندی‌تان همهٔ ابزارهای قابل‌فراخوانی را فیلتر و همهٔ کاربردی‌های پشتیبانی‌شده را غیرفعال یا حذف کند، هرمس برای آن سرور تول‌ست runtime خالی نمی‌سازد.

این فهرست ابزار را تمیز نگه می‌دارد.

۱۲ رفتار runtime

زمان کشف

هرمس سرورهای MCP را هنگام شروع کشف و ابزارشان را در رجیستری عادی ابزار ثبت می‌کند.

کشف داینامیک ابزار

سرورهای MCP می‌توانند با فرستادن اعلان ‏notifications/tools/list_changed به هرمس خبر دهند ابزارهای در دسترسشان در runtime عوض شده. هرمس با دریافت این اعلان خودکار فهرست ابزار سرور را دوباره می‌گیرد و رجیستری را به‌روز می‌کند — بدون ‏/reload-mcp دستی.

برای سرورهای MCP‌ای که قابلیت‌هایشان داینامیک عوض می‌شود مفید است ‏(مثل سروری که با لود اسکیمای جدید دیتابیس ابزار اضافه یا وقتی سرویسی آفلاین می‌شود ابزار حذف می‌کند).

refresh قفل-محافظت‌شده است تا اعلان‌های رگباری از یک سرور باعث refresh های هم‌پوشان نشوند. اعلان‌های تغییر پرامپت و منبع ‏(prompts/list_changed، ‏resources/list_changed) دریافت ولی هنوز عملیاتی نمی‌شوند.

بارگذاری مجدد

اگر پیکربندی MCP را عوض کردید از این استفاده کنید:

/reload-mcp

سرورهای MCP را از پیکربندی reload و فهرست ابزارهای موجود را refresh می‌کند. برای تغییرات ابزار runtime که خود سرور push می‌کند «کشف داینامیک ابزار» بالاتر را ببینید.

تول‌ست‌ها

هر سرور MCP پیکربندی‌شده وقتی دست‌کم یک ابزار ثبت‌شده بیاورد یک تول‌ست runtime هم می‌سازد:

mcp-<server>

این سرورهای MCP را در سطح تول‌ست راحت‌تر قابل-استدلال می‌کند.

۱۳ مدل امنیت

فیلتر env مربوط به stdio

برای سرورهای stdio هرمس کل محیط شل شما را کورکورانه عبور نمی‌دهد.

فقط ‏env صریحاً پیکربندی‌شده به‌اضافهٔ یک baseline امن عبور می‌کند. این نشت تصادفی رمزها را کم می‌کند.

کنترل قرارگرفتن-در-معرض در سطح پیکربندی

پشتیبانی فیلتر جدید یک کنترل امنیتی هم هست:

  • غیرفعال‌کردن ابزارهای خطرناکی که نمی‌خواهید مدل ببیند
  • قرار دادن فقط یک لیست‌سفید حداقلی برای سرور حساس
  • خاموش‌کردن wrapper های منبع/پرامپت وقتی نمی‌خواهید آن سطح در معرض باشد

۱۴ نمونه‌های کاربرد

mcp_servers:

  • کشف شکست خورده

  • سرور با ‏enabled: false غیرفعال شده

اگر عمداً فیلتر می‌کنید، این موردانتظار است.

چرا wrapper های منبع یا پرامپت ظاهر نشدند؟

چون هرمس الان آن wrapper ها را فقط وقتی هر دو درست است ثبت می‌کند:
۱. پیکربندی‌تان اجازه‌شان دهد
۲. نشست سرور واقعاً قابلیت را پشتیبانی کند

این عمدی است و فهرست ابزار را صادق نگه می‌دارد.

۱۶ فراخوانی‌های موازی ابزار

به‌طور پیش‌فرض ابزارهای MCP متوالی اجرا می‌شوند — یکی در لحظه. اگر سرور MCP شما ابزارهایی دارد که اجرای هم‌زمان‌شان امن است ‏(مثل پرس‌وجوهای فقط-خواندنی، فراخوانی‌های API مستقل)، می‌توانید اجرای موازی را انتخاب کنید:

yaml
mcp_servers:
  docs:
    command: "docs-server"
    supports_parallel_tool_calls: true

وقتی ‏supports_parallel_tool_calls برابر ‏true باشد، هرمس می‌تواند چند ابزار از آن سرور را هم‌زمان داخل یک batch فراخوانی-ابزار اجرا کند، درست مثل ابزارهای داخلی فقط-خواندنی ‏(web_search، ‏read_file و...).

⚠️ توجه

فقط برای سرورهای MCP‌ای که ابزارشان اجرای هم‌زمان‌شان امن است فراخوانی موازی را فعال کنید. اگر ابزارها وضعیت، فایل، دیتابیس یا منابع خارجی مشترک را بخوانند و بنویسند، قبل از فعال‌کردن این تنظیم شرایط مسابقهٔ خواندن/نوشتن را بررسی کنید.

۱۷ پشتیبانی Sampling مربوط به MCP

سرورهای MCP می‌توانند inference ‏LLM را از طریق پروتکل ‏sampling/createMessage از هرمس درخواست کنند. این اجازه می‌دهد سرور MCP از هرمس بخواهد به‌نیابت از او متن تولید کند — برای سرورهایی که قابلیت LLM می‌خواهند ولی دسترسی مدل خودشان ندارند مفید است.

‏Sampling برای همهٔ سرورهای MCP پیش‌فرض فعال است ‏(وقتی SDK مربوط به MCP پشتیبانی کند). به‌ازای هر سرور زیر کلید sampling پیکربندی می‌شود:

yaml
mcp_servers:
  my_server:
    command: "my-mcp-server"
    sampling:
      enabled: true            # فعال‌سازی sampling (پیش‌فرض: true)
      model: "openai/gpt-4o"  # override مدل برای درخواست‌های sampling (اختیاری)
      max_tokens_cap: 4096     # حداکثر توکن به‌ازای هر پاسخ sampling (پیش‌فرض: 4096)
      timeout: 30              # timeout به ثانیه به‌ازای هر درخواست (پیش‌فرض: 30)
      max_rpm: 10              # سقف نرخ: حداکثر درخواست در دقیقه (پیش‌فرض: 10)
      max_tool_rounds: 5       # حداکثر دورهای استفاده-از-ابزار در حلقه‌های sampling (پیش‌فرض: 5)
      allowed_models: []       # لیست مجاز نام‌های مدلی که سرور حق درخواست دارد (خالی = هر)
      log_level: "info"        # سطح لاگ حسابرسی: debug، info یا warning (پیش‌فرض: info)

هندلر sampling شامل محدودکنندهٔ نرخ پنجره-لغزان، timeout های به‌ازای-درخواست و سقف عمق حلقه-ابزار برای پیشگیری از مصرف سرکش است. متریک‌ها ‏(تعداد درخواست، خطاها، توکن مصرفی) به‌ازای هر نمونه سرور ردیابی می‌شوند.

برای خاموش‌کردن sampling برای یک سرور مشخص:

yaml
mcp_servers:
  untrusted_server:
    url: "https://mcp.example.com"
    sampling:
      enabled: false

۱۸ پشتیبانی Elicitation مربوط به MCP

سرورهای MCP می‌توانند وسط فراخوانی ابزار از طریق پروتکل ‏elicitation/create ‏(SDK پایتونی mcp ≥ 1.11.0) از کاربر ورودی ساختاریافته بخواهند. هرمس elicitation های حالت-فرم را از سطح تأیید موجودش مسیریابی می‌کند — پرامپت تعاملی در CLI/TUI یا دکمه‌های تأیید روی پلتفرم‌های گیت‌وی مثل تلگرام و اسلک — تا درخواست هرجا که نشست است به شما برسد. elicitation های حالت-URL ‏(جایی که سرور شما را به URL خارجی اشاره می‌دهد) به‌عنوان پشتیبانی‌نشده رد می‌شوند.

‏Elicitation به‌ازای هر سرور پیش‌فرض فعال است. زیر کلید elicitation پیکربندی می‌شود:

yaml
mcp_servers:
  my_server:
    command: "my-mcp-server"
    elicitation:
      enabled: true    # پیش‌فرض: true
      timeout: 300     # ثانیه انتظار برای جواب شما (پیش‌فرض: 300)

timeout پیش‌فرض ۵ دقیقه‌ای آینهٔ پیش‌فرض تأیید گیت‌وی است تا کاربران سطوح ناهمگام قبل از تسلیم سرور وقت پاسخ داشته باشند. متریک‌های به‌ازای-سرور ‏(درخواست‌ها، پذیرفته‌شده، رد‌شده، خطاها) روی هندلر ردیابی می‌شوند.

۱۹ اجرای هرمس به‌عنوان سرور MCP

علاوه بر اتصال به سرورهای MCP، هرمس می‌تواند خودش هم باشد سرور MCP. این اجازه می‌دهد سایر ایجنت‌های توانمند-MCP ‏(Claude Code، ‏Cursor، ‏Codex یا هر کلاینت MCP) از قابلیت‌های پیام‌رسانی هرمس استفاده کنند — فهرست گفتگوها، خواندن تاریخچه پیام و ارسال پیام بین همهٔ پلتفرم‌های متصل شما.

کِی از این استفاده کنیم

  • می‌خواهید Claude Code، ‏Cursor یا ایجنت کدنویس دیگری از طریق هرمس پیام‌های تلگرام/دیسکورد/اسلک را بفرستد و بخواند
  • یک سرور MCP واحد می‌خواهید که یک‌جا به همهٔ پلتفرم‌های پیام‌رسانی متصل هرمس پل بزند
  • قبلاً یک گیت‌وی هرمس در حال اجرا با پلتفرم‌های متصل دارید

شروع سریع

hermes mcp serve

این یک سرور MCP از نوع stdio شروع می‌کند. مدیریت چرخهٔ حیات پروسه با کلاینت MCP است نه شما.

پیکربندی کلاینت MCP

هرمس را به پیکربندی کلاینت MCP اضافه کنید. مثلاً در ‏~/.claude/claude_desktop_config.json مربوط به Claude Code:

json
{
  "mcpServers": {
    "hermes": {
      "command": "hermes",
      "args": ["mcp", "serve"]
    }
  }
}

یا اگر هرمس را در مکان خاصی نصب کرده‌اید:

json
{
  "mcpServers": {
    "hermes": {
      "command": "/home/user/.hermes/hermes-agent/venv/bin/hermes",
      "args": ["mcp", "serve"]
    }
  }
}

ابزارهای موجود

سرور MCP ‏۱۰ ابزار expose می‌کند، مطابق سطح پل-کانال OpenClaw به‌اضافهٔ مرورگر کانال مخصوص هرمس:

ابزارتوضیح
conversations_listفهرست گفتگوهای فعال پیام‌رسانی. فیلتر بر اساس پلتفرم یا جست‌وجو با نام.
conversation_getاطلاعات تفصیلی یک گفتگو با session key.
messages_readخواندن تاریخچهٔ اخیر پیام‌های یک گفتگو.
attachments_fetchاستخراج پیوست‌های غیر-متنی ‏(تصاویر، رسانه) از یک پیام مشخص.
events_pollPoll برای رویدادهای گفتگوی جدید از یک موقعیت cursor.
events_waitLong-poll / انتظار تا رسیدن رویداد بعدی ‏(نزدیک-به-بلادرنگ).
messages_sendارسال پیام از طریق یک پلتفرم ‏(مثل ‏telegram:123456، ‏discord:#general).
channels_listفهرست اهداف پیام‌رسانی موجود بین همهٔ پلتفرم‌ها.
permissions_list_openفهرست درخواست‌های تأیید در انتظار مشاهده‌شده در این نشست پل.
permissions_respondاجازه یا رد یک درخواست تأیید در انتظار.

سیستم رویداد

سرور MCP شامل پل رویداد زنده‌ای است که دیتابیس نشست هرمس را برای پیام‌های جدید poll می‌کند. این به کلاینت‌های MCP آگاهی تقریباً-بلادرنگ از گفتگوهای ورودی می‌دهد:

text
# Poll for new events (non-blocking)
events_poll(after_cursor=0)

# Wait for next event (blocks up to timeout)
events_wait(after_cursor=42, timeout_ms=30000)

انواع رویداد: ‏message، ‏approval_requested، ‏approval_resolved

صف رویداد درون-حافظه است و با اتصال پل شروع می‌شود. پیام‌های قدیمی‌تر از طریق ‏messages_read در دسترس‌اند.

گزینه‌ها

bash
hermes mcp serve              # حالت عادی
hermes mcp serve --verbose    # لاگ دیباگ روی stderr

نحوهٔ کار

سرور MCP دادهٔ گفتگو را مستقیم از مخزن نشست هرمس می‌خواند — ‏~/.hermes/state.db منبع اصلی است و ‏sessions.json فقط fallback قدیمی. یک thread پس‌زمینه دیتابیس را برای پیام‌های جدید poll و یک صف رویداد درون-حافظه نگه می‌دارد. برای ارسال پیام از همان موتور ارسال داخلی ‏(tools/send_message_tool.py) استفاده می‌کند که تحویل کرون و CLI ‏hermes send را قدرت می‌دهد.

گیت‌وی برای عملیات خواندن ‏(فهرست گفتگوها، خواندن تاریخچه، poll رویدادها) لازم نیست اجرا باشد. برای عملیات ارسال لازم است چون آداپتورهای پلتفرم به اتصالات فعال نیاز دارند.

محدودیت‌های فعلی

  • ‏hermes mcp serve داخلی امروز سرور MCP فقط-stdio expose می‌کند. اگر سرور MCP ‏HTTP لازم دارید یک آداپتور جدا اجرا کنید — یا خیلی رایج‌تر، سمت کلاینت MCP هرمس را استفاده کنید که هم استdio هم HTTP صحبت می‌کند ‏(url + ‏headers در ‏mcp_servers.yaml/config.yaml؛ سرورهای HTTP بالا را ببینید).
  • ‏Poll رویداد با فواصل ~۲۰۰ میلی‌ثانیه از طریق polling دیتابیس بهینه‌شده با mtime ‏(وقتی فایل‌ها تغییری نکرده‌اند کار را رد می‌کند)
  • هنوز پروتکل اعلان push ‏claude/channel وجود ندارد
  • ارسال فقط-متنی ‏(بدون ارسال رسانه/پیوست از طریق messages_send)
