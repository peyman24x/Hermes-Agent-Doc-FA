‏سرور زبان ‏(LSP) — تشخیص معنایی

هرمس سرورهای زبانِ کامل — ‏pyright، ‏gopls، ‏rust-analyzer، ‏typescript-language-server، ‏clangd و حدود ۲۰ مورد دیگر — را به‌صورت زیرپروسه‌های پس‌زمینه اجرا می‌کند و تشخیص‌های معنایی آنها را به بررسی lint پس از نوشتن، که توسط write_file و patch استفاده می‌شود، تزریق می‌کند. وقتی ایجنت فایلی را ویرایش می‌کند دقیقاً همان خطاهایی را می‌بیند که همان ویرایش ایجاد کرده است — نه فقط خطاهای نحوی، بلکه خطاهای نوع، نام‌های تعریف‌نشده، importهای جاافتاده و مسائل معنایی در مقیاس کل پروژه که سرور زبان آشکار می‌کند.

این همان معماری‌ای است که بهترین ایجنت‌های کدنویسی رده‌بالا استفاده می‌کنند. هرمس آن را خودکفا ارائه می‌دهد: نیازی به میزبان ویرایشگر نیست، پلاگینی برای نصب نیست و دیمون جداگانه‌ای برای مدیریت وجود ندارد.

۱ LSP چه زمانی اجرا می‌شود

اجرای LSP منوط به تشخیص فضای‌کاری git است. وقتی دایرکتوری کاری ایجنت (یا فایلِ در حال ویرایش) داخل یک مخزن git باشد، LSP روی همان فضای‌کاری اجرا می‌شود. وقتی هیچ‌کدام داخل مخزن git نباشند، LSP خوابیده می‌ماند — این برای گیت‌وی‌های پیام‌رسانی مفید است که دایرکتوری کاری‌شان خانهٔ کاربر است و پروژه‌ای برای تشخیص وجود ندارد.

بررسی لایه‌بندی‌شده است: نخست بررسی نحوی درون-پروسه (در حد میکروثانیه)، سپس در صورت تمیز بودن نحو، تشخیص‌های LSP در مرحلهٔ دوم. یک سرور زبانِ بی‌ثبات یا غایب هرگز نمی‌تواند عملیات نوشتن را از کار بیندازد — هر مسیر شکست LSP بی‌صدا به نتیجهٔ فقط-نحوی برمی‌گردد.

به‌طور مشخص، در هر write_file یا patch موفق:

  1. هرمس یک وضعیت پایه ‏(baseline) از تشخیص‌های فعلی فایل ثبت می‌کند.
  2. عملیات نوشتن را انجام می‌دهد.
  3. دوباره از سرور زبان پرس‌وجو می‌کند، تشخیص‌هایی را که از قبل در وضعیت پایه حضور داشتند فیلتر می‌کند و فقط موارد جدید را نمایش می‌دهد.

خروجی‌ای که ایجنت می‌بیند چیزی شبیه این است:

json
{
  "bytes_written": 42,
  "dirs_created": false,
  "lint": {"status": "ok", "output": ""},
  "lsp_diagnostics": "LSP diagnostics introduced by this edit:\n<diagnostics file=\"/path/to/foo.py\">\nERROR [42:5] Cannot find name 'foo' [reportUndefinedVariable] (Pyright)\nERROR [50:1] Argument of type \"str\" is not assignable to \"int\" [reportArgumentType] (Pyright)\n</diagnostics>"
}

فیلد lint نتیجهٔ بررسی نحوی را حمل می‌کند (تجزیهٔ درون-پروسهٔ میکروثانیه‌ای از طریق ast.parse، ‏json.loads و…؛ فیلد lsp_diagnostics تشخیص‌های معنایی سرور زبان واقعی را حمل می‌کند. دو کانال با سیگنال‌های مستقل — ایجنت فایلی با نحو تمیز ولی مشکلات معنایی را به‌صورت lint: ok به‌همراه یک lsp_diagnostics پُر می‌بیند.

برای ردیف‌های «دستی»، سرور را از طریق هر ابزار مدیریت زنجیره‌ابزارِ مناسبِ آن زبان ‏(rustup، ‏ghcup، ‏opam، ‏brew و…) نصب کنید. هرمس باینری را به‌طور خودکار روی PATH یا در مسیر <HERMES_HOME>/lsp/bin/ آشکار می‌کند.

PowerShell

‏PowerShellEditorServices یک باینری واحد نیست — این یک بستهٔ ماژول PowerShell است که توسط میزبان pwsh ‏(PowerShell 7 به بالا) یا powershell راه‌اندازی می‌شود. مراحل نصب:

  1. PowerShell را نصب کنید تا pwsh ‏(یا powershell در ویندوز) روی PATH باشد.
  2. آخرین فایل zip انتشار را از انتشارهای PowerShellEditorServices دانلود و استخراج کنید.
  3. هرمس را به بستهٔ استخراج‌شده اشاره دهید — دایرکتوری‌ای که شامل PowerShellEditorServices/Start-EditorServices.ps1 است. یکی از این راه‌ها:
    • تنظیم lsp.servers.powershell.command: ["/path/to/bundle"] در config.yaml، یا
    • استخراج آن در مسیر <HERMES_HOME>/lsp/PowerShellEditorServices، یا
    • تنظیم متغیر محیطی PSES_BUNDLE_PATH=/path/to/bundle.

دستور hermes lsp status به‌محض پیدا شدن pwsh وضعیت installed را گزارش می‌کند؛ اگر بسته غایب باشد یک هشدار یک‌باره همراه با لینک دانلود در لاگ‌ها می‌بینید.

چند سرور در کنار یک وابستگی هم‌بسته نصب می‌شوند که npm آن را خودکار نمی‌کشد. مورد فعلی typescript-language-server است که به SDK ی typescript قابل-import از همان درخت node_modules نیاز دارد — هرمس هنگام اجرای hermes lsp install typescript یا فعال شدن نصب خودکار در اولین استفاده، هر دو پکیج را با هم نصب می‌کند.

۳ رابط خط فرمان

bash
hermes lsp status          # service state + per-server install status
hermes lsp list            # registry, optionally --installed-only
hermes lsp install <id>    # eagerly install one server
hermes lsp install-all     # try every server with a known recipe
hermes lsp restart         # tear down running clients
hermes lsp which <id>      # print resolved binary path

hermes lsp status بهترین نقطهٔ شروع است — نشان می‌دهد امروز کدام زبان‌ها تشخیص معنایی می‌گیرند و کدام‌ها برای نصب باینری نیاز به اقدام دارند.

۴ پیکربندی

پیش‌فرض‌ها برای راه‌اندازی‌های معمول کار می‌کنند؛ اگر باینری‌ها روی PATH باشند چیزی برای تنظیم کردن وجود ندارد.

yaml
# config.yaml
lsp:
  # Master toggle. Disabling skips the entire subsystem — no servers
  # spawn, no background event loop runs.
  enabled: true

  # How long to wait for diagnostics after each write.
  wait_mode: document      # "document" or "full"
  # Max seconds to wait for the server to re-check the file after an
  # edit. Only *fresh* diagnostics (produced for the post-edit
  # content) are ever reported; if the server doesn't finish within
  # this budget, the edit reports "no LSP data" rather than stale
  # errors from before the edit. Raise this for slow servers on big
  # projects (tsserver, rust-analyzer mid-indexing).
  wait_timeout: 5.0

  # How to handle missing server binaries.
  #   auto    — install via npm/pip/go install into <HERMES_HOME>/lsp/bin
  #   manual  — only use binaries already on PATH
  install_strategy: auto

  # How long an unused language-server client stays alive (seconds).
  # Idle servers are shut down automatically and respawned on the next
  # relevant file operation. Set to 0 to disable idle reaping and keep
  # servers alive for the life of the process. Values below 30s are
  # clamped to 30 so a sweep can never reap a client mid-operation.
  idle_timeout: 600

  # Per-server overrides (all optional).
  servers:
    pyright:
      disabled: false
      command: ["/abs/path/to/pyright-langserver", "--stdio"]
      env: { PYRIGHT_LOG_LEVEL: "info" }
      initialization_options:
        python:
          analysis:
            typeCheckingMode: "strict"
    typescript:
      disabled: true       # skip TS even when its extensions match

کلیدهای هر-سرور

  • disabled: true — این سرور کاملاً رد می‌شود حتی وقتی پسوندهایش با یک فایل تطبیق می‌خورد.
  • command: [bin, ...args] — مسیر یک باینری سفارشی را پین می‌کند و از نصب خودکار عبور می‌کند.
  • env: {KEY: value} — متغیرهای محیطی اضافه‌ای که به پروسهٔ spawn‌شده پاس داده می‌شود.
  • initialization_options: {...} — در payload ی initializationOptions مربوط به LSP که در هندشیک initialize فرستاده می‌شود ادغام می‌گردد. مخصوص هر سرور است؛ مستندات خود سرور زبان را ببینید.

۵ مکان‌های نصب

وقتی install_strategy: auto باشد، هرمس باینری‌ها را در <HERMES_HOME>/lsp/bin/ نصب می‌کند. پکیج‌های NPM در <HERMES_HOME>/lsp/node_modules/ جای می‌گیرند و symlinkهای bin یک سطح بالاتر قرار می‌گیرند. باینری‌های Go از طریق go install با GOBIN اشاره‌کننده به دایرکتوری staging می‌آیند.

هیچ‌چیز هرگز در /usr/local/، ‏~/.local/ یا هر مکان مشترک دیگری نصب نمی‌شود — دایرکتوری staging کاملاً در اختیار هرمس است و هنگام ریست پروفایل حذف می‌شود.

۶ ویژگی‌های کارایی

سرورهای LSP با تأخیر و در اولین استفاده spawn می‌شوند. ویرایش یک فایل پایتون در پروژه‌ای که تا حالا ترافیکی از نوع .py نداشته، pyright را spawn می‌کند؛ این spawn برای بیشتر سرورها ۱ تا ۳ ثانیه طول می‌کشد ‏(rust-analyzer روی پروژهٔ سرد ممکن است بیش از ۱۰ ثانیه طول بدهد). ویرایش‌های بعدی در همان فضای‌کاری از سرورِ در حال اجرا دوباره استفاده می‌کنند.

لایهٔ LSP وقتی هیچ تشخیصی صادر نشود فقط چند میلی‌ثانیه به نوشتن‌های تمیز اضافه می‌کند. وقتی تشخیصی صادر شود، بودجهٔ انتظار برابر wait_timeout ثانیه است — به‌طور معمول سرور برای pyright/tsserver در حد ده‌ها میلی‌ثانیه و برای rust-analyzer در میانهٔ ایندکس‌گذاری چند ثانیه پاسخ می‌دهد.

تشخیص‌ها دارای گیت تازگی هستند: یک نتیجه فقط وقتی حساب می‌شود که سرور آن را برای محتوای ویرایش فعلی تولید کرده باشد ‏(یک push از نوع publishDiagnostics در لحظهٔ تغییر یا بعد از آن، یا پاسخ یک pull request که بعد از تغییر آمده باشد). سرورهای کندی که هنوز بازرسی نکرده‌اند برای آن ویرایش «بدون داده» به بار می‌آورند — هرگز خطاهای دیروز به‌عنوان خطاهای فعلی دوباره گزارش نمی‌شوند.

سرورها تا وقتی در حال استفاده هستند زنده نگه داشته می‌شوند و بعد از lsp.idle_timeout ثانیه ‏(پیش‌فرض ۶۰۰) بدون فعالیت فایلی خاموش می‌شوند — یک گیت‌وی بلندمدت که با many worktreeها کار دیگر تا همیشه برای هر فضای‌کاری یک پروسهٔ سرور زبان انباشته نمی‌کند. سروری که جمع‌آوری ‏(reap) شده در اولین عملیات فایل مرتبط به‌طور خودکار دوباره spawn می‌شود. برای غیرفعال کردن جمع‌آوری و گرم نگه داشتن اندیس همهٔ سرورها تا پایان عمر پروسه، idle_timeout: 0 را ست کنید.

۷ غیرفعال‌سازی

برای غیرفعال کردن کل زیرسیستم lsp.enabled: false را در config.yaml ست کنید. بررسی پس از نوشتن به بررسی نحوی درون-پروسه (ast.parse برای پایتون، ‏json.loads برای JSON و…) برمی‌گردد که بدون تغییر از نسخه‌های قبل‌تر ارائه می‌شود.

برای غیرفعال کردن فقط یک زبان بدون از کار انداختن کل لایه:

yaml
lsp:
  servers:
    rust-analyzer:
      disabled: true

۸ عیب‌یابی

‏hermes lsp status یک سرور را «missing» نشان می‌دهد

باینری نه روی PATH هست و نه در <HERMES_HOME>/lsp/bin/. برای تلاش برای نصب خودکار hermes lsp install <server_id> را اجرا کنید یا باینری را از طریق زنجیره‌ابزار عادی آن زبان به‌صورت دستی نصب کنید.

بخش «Backend warnings» در hermes lsp status

بعضی سرورها پوشش‌های نازک دور یک CLI خارجی برای تشخیص واقعی هستند — تمیز spawn می‌شوند و درخواست‌ها را می‌پذیرند ولی وقتی باینری sidecar غایب است هرگز خطایی صادر نمی‌کنند. رایج‌ترین مورد bash-language-server است که تشخیص‌ها را به shellcheck واگذار می‌کند. وقتی hermes lsp status بخش «Backend warnings» نشان داد، ابزار نام‌برده را از طریق مدیر پکیج سیستم‌عامل نصب کنید:

bash
apt install shellcheck      # Debian / Ubuntu
brew install shellcheck     # macOS
scoop install shellcheck    # Windows

همین هشدار یک‌باره در زمان spawn سرور در ~/.hermes/logs/agent.log لاگ می‌شود.

سرور شروع می‌شود ولی هرگز تشخیصی برنمی‌گرداند

فایل ~/.hermes/logs/agent.log را برای ورودی‌های [agent.lsp.client] بررسی کنید — هم stderr سرور زبان و هم خطاهای پروتکل آنجا فرود می‌آیند. بعضی سرورها (به‌خصوص rust-analyzer) باید پیش از صدور تشخیص‌های هر-فایل، ایندکس کل پروژه را تمام کنند؛ اولین ویرایش بعد از شروع سرور ممکن است بدون تشخیص تمام شود و ویرایش‌های بعدی آنها را دریافت کنند.

سرور کرش کرده است

سرورِ کرش‌شده به مجموعهٔ خراب‌ها اضافه می‌شود و تا پایان نشست دوباره تلاش نمی‌شود. برای پاک کردن مجموعه hermes lsp restart را اجرا کنید؛ ویرایش بعدی دوباره spawn می‌کند.

ویرایش فایلی بیرون از هر مخزن git

بنا به طراحی، LSP فقط داخل مخزن git اجرا می‌شود. اگر پروژه هنوز مقداردهی اولیه نشده، برای فعال‌سازی تشخیص‌های LSP دستور git init را اجرا کنید. در غیر این صورت fallback فقط-نحوی درون-پروسه اعمال می‌شود.
