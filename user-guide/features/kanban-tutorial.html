آموزش کانبان

مروری گام‌به‌گام بر چهار مورد-کاربردی که سیستم کانبان هرمس برای آنها طراحی شده، با داشبورد باز در مرورگر. اگر هنوز نگاه کلی کانبان را نخوانده‌اید، از آنجا شروع کنید — این آموزش فرض می‌کند می‌دانید تسک، run، assignee و dispatcher چه هستند.

۱ راه‌اندازی

bash
hermes kanban init           # optional; first `hermes kanban <anything>` auto-inits
hermes dashboard             # opens http://127.0.0.1:9119 in your browser
# click Kanban in the left nav

داشبورد راحت‌ترین جا برای شماست تا سیستم را تماشا کنید. کارگرانِ ایجنتی که dispatcher به وجود می‌آورد هرگز داشبورد یا CLI را نمی‌بینند — آنها برد را از طریق تول‌ست اختصاصی kanban_* هدایت می‌کنند ‏(kanban_show، ‏kanban_list، ‏kanban_complete، ‏kanban_block، ‏kanban_heartbeat، ‏kanban_comment، ‏kanban_attach، ‏kanban_attach_url، ‏kanban_attachments، ‏kanban_create، ‏kanban_link، ‏kanban_unblock). هر سه سطح — داشبورد، CLI، ابزارهای کارگر — از طریق همان پایگاه‌دادهٔ SQLite مخصوص هر برد مسیریابی می‌شوند ‏(~/.hermes/kanban.db برای برد پیش‌فرض و ~/.hermes/kanban/boards/<slug>/kanban.db برای هر بردی که بعداً بسازید)، پس هر برد فارغ از اینکه تغییر از کدام سمت آمده باشد سازگار می‌ماند.

این آموزش سراسر از برد default استفاده می‌کند. اگر صف‌های ایزولهٔ متعدد می‌خواهید ‏( یکی به‌ازای هر پروژه / مخزن / حوزه)، بخش بردها ‏(چند-پروژه‌ای) را در نگاه کلی ببینید — همان جریان‌های CLI / داشبورد / کارگر برای هر برد اعمال می‌شود و کارگران فیزیکالاً نمی‌توانند تسک‌های بردهای دیگر را ببینند.

📌 قرارداد این آموزش

در سراسر آموزش، بلوک‌های کدی با برچسب bash دستوراتی هستند که «شما» اجرا می‌کنید. بلوک‌های کدی با برچسب # worker tool calls چیزی‌اند که مدلِ کارگرِ spawn‌شده به‌صورت فراخوانی ابزار صادر می‌کند — اینها را نشان می‌دهیم تا حلقه را سر-تا-سر ببینید، نه اینکه خودتان قرار باشد اجرایشان کنید.

۲ برد در یک نگاه

شش ستون، از چپ به راست:

  • Triage — ایده‌های خام. به‌طور پیش‌فرض dispatcher روی تسک‌های اینجا تجزیه‌گر ‏(decomposer) را خودکار اجرا می‌کند: تجزیه‌گر داخلی از auxiliary.kanban_decomposer استفاده می‌کند، فهرست پروفایل‌ها + توضیحات شما را می‌خواند و گرافی از تسک‌های فرزند تولید می‌کند که به بهترین متخصص‌های مناسب مسیریابی می‌شوند. تسک اصلی به‌عنوان والد زنده نگه داشته می‌شود تا assignee اش ‏(kanban.orchestrator_profile یا پروفایل پیش‌فرض فعال وقتی تنظیم نشده) وقتی همه‌چیز تمام شد دوباره بیدار شود و تکمیل را قضاوت کند. برای تعویض حالت، حبهٔ Orchestration: Auto/Manual را بالای صفحهٔ کانبان بزنید. در حالت Manual روی کارت ⚗ Decompose را کلیک کنید یا hermes kanban decompose <id> / ‏/kanban decompose <id> را اجرا کنید. برای تسک‌های تکی که fan-out نمی‌خواهند، ✨ Specify یک بازنویسی spec یک‌باره انجام می‌دهد ‏(هدف، رویکرد، معیارهای پذیرش) و تسک را به todo ارتقا می‌دهد. مدل‌ها را زیر auxiliary.kanban_decomposer و auxiliary.triage_specifier در config.yaml پیکربندی کنید. بخش ارجاع خودکار در برابر دستی را در راهنمای اصلی کانبان ببینید.
  • Todo — ساخته‌شده ولی منتظر وابستگی‌ها، یا هنوز محول‌نشده.
  • Ready — محول‌شده و منتظر ادعا توسط dispatcher.
  • In progress — کارگری فعالانه در حال اجرای تسک است. با روشنبودن «Lanes by profile» ‏(پیش‌فرض) این ستون بر اساس assignee زیرگروه‌بندی می‌شود تا یک‌نگاهی ببینید هر کارگر چه می‌کند.
  • Blocked — کارگری ورودی انسانی خواسته، یا مدارشکن عمل کرده است.
  • Done — تکمیل‌شده.

نوار بالا فیلترهایی برای جستجو، tenant و assignee دارد، به‌همراه کلید Lanes by profile و دکمهٔ Nudge dispatcher که همین حالا یک tick دیسپچ اجرا می‌کند به‌جای انتظار برای بازهٔ بعدی دیمن. کلیک روی هر کارت، کشوی آن را در سمت راست باز می‌کند.

نمای تخت

اگر لِین‌های پروفایل شلوغ‌اند، «Lanes by profile» را خاموش کنید تا ستون In Progress به یک فهرست تختِ مرتب‌شده بر اساس زمان claim جمع شود:

۳ داستان ۱ — توسعه‌دهندهٔ تنها در حال انتشار یک قابلیت

دارید یک قابلیت می‌سازید. جریان کلاسیک: طراحی اسکیما، پیاده‌سازی API، نوشتن تست‌ها. سه تسک با وابستگی والد→فرزند:

bash
SCHEMA=$(hermes kanban create "Design auth schema" \
    --assignee backend-dev --tenant auth-project --priority 2 \
    --body "Design the user/session/token schema for the auth module." \
    --json | jq -r .id)

API=$(hermes kanban create "Implement auth API endpoints" \
    --assignee backend-dev --tenant auth-project --priority 2 \
    --parent $SCHEMA \
    --body "POST /register, POST /login, POST /refresh, POST /logout." \
    --json | jq -r .id)

hermes kanban create "Write auth integration tests" \
    --assignee qa-dev --tenant auth-project --priority 2 \
    --parent $API \
    --body "Cover happy path, wrong password, expired token, concurrent refresh."

چون API والدش SCHEMA است و tests والدش API، فقط SCHEMA در وضعیت ready شروع می‌شود. دو مورد دیگر در todo می‌مانند تا والدهایشان کامل شوند. این موتور ارتقای وابستگی است که کارش را می‌کند — هیچ کارگر دیگری تا وقتی API ای برای تست نباشد سراغ نوشتن تست نمی‌رود.

در tick بعدی dispatcher ‏(پیش‌فرض ۶۰ ثانیه، یا بلافاصله اگر Nudge dispatcher را بزنید) پروفایل backend-dev به‌عنوان کارگر با HERMES_KANBAN_TASK=$SCHEMA در env اش spawn می‌شود. حلقهٔ فراخوانی-ابزار کارگر از داخل ایجنت این‌طور دیده می‌شود:

# worker tool calls
# worker tool calls — NOT commands you run
kanban_show()
# → returns title, body, worker_context, parents, prior attempts, comments

# (worker reads worker_context, uses terminal/file tools to design the schema,
#  write migrations, run its own checks, commit — the real work happens here)

kanban_heartbeat(note="schema drafted, writing migrations now")

kanban_complete(
    summary="users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); "
            "refresh tokens stored as sessions with type='refresh'",
    metadata={
        "changed_files": ["migrations/001_users.sql", "migrations/002_sessions.sql"],
        "decisions": ["bcrypt for hashing", "JWT for session tokens",
                      "7-day refresh, 15-min access"],
    },
)

‏kanban_show مقدار task_id را به‌طور پیش‌فرض روی $HERMES_KANBAN_TASK می‌گذارد، پس کارگر لازم نیست شناسهٔ خودش را بداند. ‏kanban_complete خلاصه + metadata را روی سطر فعلی task_runs می‌نویسد، آن run را می‌بندد و تسک را به done منتقل می‌کند — همه در یک جهش اتمی از طریق kanban_db.

وقتی SCHEMA به done می‌رسد، موتور وابستگی API را خودکار به ready ارتقا می‌دهد. کارگرِ API وقتی آن را برمی‌دارد kanban_show() را صدا می‌زند و خلاصه و metadata ی SCHEMA را پیوستِ تحویلِ والد می‌بیند — پس تصمیمات اسکیما را بدون بازخوانی یک سند طراحی طولانی می‌داند.

روی برد روی تسک اسکیمای تکمیل‌شده کلیک کنید؛ کشو همه‌چیز را نشان می‌دهد:

بخش Run History پایین کشو افزودهٔ کلیدی است. یک تلاش: نتیجهٔ completed، کارگر @backend-dev، مدت، زمان و خلاصهٔ تحویل به‌طور کامل. حباب metadata ‏(changed_files، ‏decisions) هم روی run ذخیره می‌شود و به هر کارگر پایین‌دستی که این والد را بخواند نمایش داده می‌شود.

می‌توانید هر لحظه از ترمینال همان داده را بررسی کنید — این دستورات «شما» هستید که به برد سرک می‌کشید، نه کارگر:

bash
hermes kanban show $SCHEMA
hermes kanban runs $SCHEMA
# #  OUTCOME       PROFILE       ELAPSED  STARTED
# 1  completed     backend-dev        0s  2026-04-27 19:34
#     → users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); refresh tokens ...

۴ داستان ۲ — مزرعهٔ کارگران ‏(Fleet Farming)

سه کارگر دارید ‏(یک مترجم، یک رونویس‌کننده، یک کپی‌رایتر) و انبوهی تسک مستقل. می‌خواهید هر سه به‌موازات کار کنند و پیشرفت قابل‌مشاهده‌ای داشته باشند. ساده‌ترین مورد-کاربردی کانبان است و همان که طراحی اولیه برایش بهینه شده بود.

کارها را بسازید:

bash
for lang in Spanish French German; do
    hermes kanban create "Translate homepage to $lang" \
        --assignee translator --tenant content-ops
done
for i in 1 2 3 4 5; do
    hermes kanban create "Transcribe Q3 customer call #$i" \
        --assignee transcriber --tenant content-ops
done
for sku in 1001 1002 1003 1004; do
    hermes kanban create "Generate product description: SKU-$sku" \
        --assignee copywriter --tenant content-ops
done

گیت‌وی را روشن کنید و بروید سراغ کارتان — همان dispatcher تعبیه‌شده را میزبانی می‌کند که تسک‌های هر سه پروفایل متخصص را روی همان kanban.db برمی‌دارد:

hermes gateway start

حالا برد را روی content-ops فیلتر کنید ‏(یا فقط «Transcribe» را جستجو کنید) تا این را ببینید:

دو رونویسی تمام‌شده، یکی در حال اجرا، دو مورد ready در انتظار tick بعدی dispatcher. ستون In Progress بر اساس پروفایل گروه‌بندی شده ‏(پیش‌فرض «Lanes by profile») پس تسک فعال هر کارگر را بدون گشتن در فهرستی مخلوط می‌بینید. dispatcher به‌محض تکمیل تسک فعلی، تسک ready بعدی را به running ارتقا می‌دهد. با سه دیمن که روی سه مخزن assignee موازی کار می‌کنند، کل صف محتوا بدون هیچ ورودی انسانی بیشتری تخلیه می‌شود.

هرچه داستان ۱ دربارهٔ تحویل ساختاریافته گفت اینجا هم برقرار است. کارگرِ مترجم هنگام اتمام یک تماس، ‏kanban_complete(summary="translated 4 pages, style matched existing marketing voice", metadata={"duration_seconds": 720, "tokens_used": 2100}) صادر می‌کند — برای تحلیل‌ها و برای هر تسک پایین‌دستی که به آن وابسته است مفید.

۵ داستان ۳ — خط‌لولهٔ نقش‌ها با تلاش مجدد

اینجاست که کانبان در مقابل یک فهرست TODO تخت ارزش واقعی‌اش را نشان می‌دهد. یک PM یک spec می‌نویسد. یک مهندس پیاده‌سازی می‌کند. یک بازبین تلاش اول را رد می‌کند. مهندس با تغییرات دوباره تلاش می‌کند. بازبین تأیید می‌کند.

نمای داشبورد، فیلترشده روی auth-project:

اسکرین‌شات از مدل کارت پایین‌دستیِ از-پیش-ساخته استفاده می‌کند: کارت پیاده‌سازی یک فرزندِ بازبینِ اختصاصی دارد. در آن مدل مهندس باید وقتی پیاده‌سازی آماده است kanban_complete را صدا بزند تا فرزندِ بازبین بتواند todo را ترک کند. هرگز والدِ پیاده‌سازی را صرفاً برای درخواست بازبینی بلاک نکنید.

برای گردش‌کارهایی که همان کارت مالکیت پیاده‌سازی و بازبینی را دارد، از چرخه‌حیات بازبینی درجه‌یک استفاده کنید. رقص کامل implement → review → changes → re-review چنین است:

# worker tool calls
# --- Engineer: first implementation attempt ---
kanban_show()
# (write code, run tests, prepare the candidate)
kanban_request_review(
    summary="implemented reset flow; candidate is ready for review",
    metadata={"changed_files": ["auth/reset.py"], "tests_run": 8},
    reviewer="reviewer",
)
# → the same card enters review; the implementation run closes as
#   outcome='review_requested'

# --- Reviewer: request concrete changes ---
kanban_show()
# (inspect the handoff and candidate)
kanban_request_changes(
    reason="Add password-strength validation and make reset tokens single-use."
)
# → the review run closes as outcome='changes_requested'; the card returns
#   to backend-dev in ready/todo without touching block-loop accounting

# --- Engineer: second implementation attempt ---
kanban_show()  # prior review evidence is in worker_context
# (apply feedback and re-run tests)
kanban_request_review(
    summary="added zxcvbn validation and single-use reset tokens",
    metadata={
        "changed_files": [
            "auth/reset.py",
            "auth/tests/test_reset.py",
            "migrations/003_single_use_reset_tokens.sql",
        ],
        "tests_run": 11,
        "review_iteration": 2,
    },
    reviewer="reviewer",
)

# --- Reviewer: approve ---
kanban_complete(summary="review passed; acceptance criteria verified")
# → done

تاریخچهٔ run تسک اکنون review_requested → changes_requested → review_requested → completed را ثبت می‌کند. هر تلاش بازیگر، خلاصه، metadata و نتیجهٔ خودش را دارد، پس مهندس دوم دقیقاً می‌بیند بازبین چه چیزی را رد کرده و تأیید نهایی قابل ممیزی می‌ماند. ‏kanban_block برای تشدید واقعیِ خارجی رزرو شده ‏(نبود دسترسی، یک تصمیم محصول، زیرساخت در دسترس نیست)، نه بازخورد عادی بازبینی.

اگر عمداً از مدل کارت-پایین‌دستیِ نشان‌داده‌شده در اسکرین‌شات استفاده می‌کنید، بازبین پس از تکمیل والدِ پیاده‌سازی، کارت «Review password reset PR» را باز می‌کند:

‏worker_context کارت بازبین شامل تحویلِ پیاده‌سازیِ تکمیل‌شده است. این یک گردش‌کار کارتِ جداست؛ آن را با kanban_request_review روی همان‌کارت ترکیب نکنید وگرنه لِین بازبینی دوباره‌سازی می‌شود.

۶ داستان ۴ — مدارشکن و بازیابی از کرش

کارگرهای واقعی شکست می‌خورند. اعتبارنامهٔ جامانده، OOM kill، خطاهای گذرای شبکه. dispatcher دو خط دفاعی دارد: یک مدارشکن که بعد از N شکست متوالی خودکار بلاک می‌کند تا برد تا ابد تق‌تق نکند، و آشکارسازی کرش که تسکی را که PID کارگرش قبل از پایان TTL از بین رفته پس می‌گیرد.

مدارشکن — شکستی که همیشگی به نظر می‌رسد

تسک دیپلویی که نمی‌تواند کارگرش را spawn کند چون AWS_ACCESS_KEY_ID در env پروفایل تنظیم نشده:

bash
hermes kanban create "Deploy to staging (missing creds)" \
    --assignee deploy-bot --tenant ops \
    --max-retries 3

dispatcher تلاش می‌کند کارگر را spawn کند. Spawn شکست می‌خورد ‏(RuntimeError: AWS_ACCESS_KEY_ID not set). dispatcher ادعا را آزاد، شمارندهٔ شکست را زیاد و در tick بعد دوباره تلاش می‌کند. چون این مثال --max-retries 3 ست کرده، مدار بعد از سه شکست متوالی قطع می‌شود: تسک با نتیجهٔ gave_up به blocked می‌رود. اگر فلگ را حذف کنید هرمس از kanban.failure_limit استفاده می‌کند ‏(پیش‌فرض: ۲). تا یک انسان رفع‌بلاکش کند دیگر تلاشی نمی‌شود.

روی تسک بلاک‌شده کلیک کنید:

سه run، همه با همان خطا در فیلد error. دوی اول spawn_failed ‏(قابل‌تلاش مجدد) و سومی gave_up ‏(پایانه) است. لاگ رویداد بالا کل توالی را نشان می‌دهد: ‏created → claimed → spawn_failed → claimed → spawn_failed → claimed → gave_up.

روی ترمینال:

bash
hermes kanban runs t_ef5d
# #   OUTCOME        PROFILE        ELAPSED  STARTED
# 1   spawn_failed   deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
# 2   spawn_failed   deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
# 3   gave_up        deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env

اگر تلگرام / دیسکورد / اسلک وصل باشد، روی رویداد gave_up یک نوتیفیکیشن گیت‌وی شلیک می‌شود تا وقفه را بدون سرک کشیدن به بشنوید.

بازیابی از کرش — کارگر وسط کار می‌میرد

گاهی spawn موفق است ولی پروسهٔ کارگر بعداً می‌میرد — segfault، ‏OOM، ‏systemctl stop. dispatcher ‏kill(pid, 0) را poll می‌کند و pid مرده را آشکار می‌سازد؛ ادعا آزاد، تسک به ready برمی‌گردد و tick بعدی آن را به یک کارگر تازه می‌دهد.

مثال دادهٔ seed، مهاجرتی بود که حافظه‌اش تمام می‌شد:

# Worker claims, starts scanning 2.4M rows, OOM kills it at ~2.3M
# Dispatcher detects dead pid, releases claim, increments attempt counter
# Retry with a chunked strategy succeeds

کشو تاریخچهٔ کامل دومرحله‌ای را نشان می‌دهد:

Run 1 — ‏crashed با خطای OOM kill at row 2.3M (process 99999 gone). ‏Run 2 — ‏completed با "strategy": "chunked with LIMIT + WHERE id > last_id" در metadata اش. کارگرِ درحال‌تلاش‌مجدد کرش run 1 را در زمینهٔ خود دیده و استراتژی امن‌تری برگزیده بود؛ metadata برای ناظر آینده ‏(یا نویسندهٔ postmortem) شفاف می‌کند چه چیزی عوض شد.

۷ تحویل ساختاریافته — چرا summary و metadata مهم‌اند

در هر داستان بالا، کارگرها آخر کار kanban_complete(summary=..., metadata=...) را صدا زدند. این تزئین نیست — کانال اصلی تحویل میان مرحله‌های یک گردش‌کار است.

وقتی کارگری روی تسک B spawn می‌شود و kanban_show() را صدا می‌زند، worker_context ای که برمی‌گردد شامل:

  • تلاش‌های قبلیِ B ‏(runهای قبلی: نتیجه، خلاصه، خطا، metadata) تا کارگرِ درحال‌تلاش‌مجدد مسیر شکست‌خورده را تکرار نکند.
  • نتایج تسک‌های والد — برای هر والد، خلاصه و metadata ی آخرین run تکمیل‌شده — تا کارگرهای پایین‌دست ببینند کار بالادستی چرا و چطور انجام شده.

این جایگزین رقصِ «گشتن زیر کامنت‌ها و خروجی کار» است که سیستم‌های کانبان تخت گرفتارش می‌کند. PM معیارهای پذیرش را در metadata ی spec می‌نویسد و کارگر مهندس آنها را ساختاریافته در تحویلِ والد می‌بیند. مهندس ثبت می‌کند کدام تست‌ها را اجرا و چند مورد پاس شد، و کارگر بازبین قبل از باز کردن یک diff آن فهرست را در دست دارد.

نگهبان close گروهی وجود دارد چون این داده per-run است. ‏hermes kanban complete a b c --summary X ‏(شما، از CLI) رد می‌شود — کپی-پیست کردن یک خلاصه برای سه تسک تقریباً همیشه غلط است. بستن گروهی بدون فلگ‌های تحویل برای حالت رایجِ «تمام کردم انبوهی کار اداری را» همچنان کار می‌کند. سطح ابزار اصلاً نوع گروهی را expose نمی‌کند؛ ‏kanban_complete همیشه تک-تسک-در-آن- واحد است به همان دلیل.

۸ پیگیری کارت done — رفع مشکل CI از طریق لینک والد

کارت پیاده‌سازی داستان ۱ حالا done است. دو ساعت بعد CI روی شاخهٔ merge‌شده شکست می‌خورد. کارت done را reopen نکنید — کارت‌های تکمیل‌شده تاریخ‌اند و تحویلشان رو-به-جلو جریان دارد. یک کارت اصلاحی بسازید با کارت done به‌عنوان والد:

bash
hermes kanban create "Fix CI: test_backoff_jitter flakes on 3.11" \
    --assignee backend-dev \
    --parent t_impl \
    --workspace worktree --branch wt/ci-fix-backoff \
    --body "CI run #4812 failed after t_impl completed.
FAILED tests/test_retry.py::test_backoff_jitter - TimeoutError
Acceptance: tests/test_retry.py green on 3.11 and 3.12."

سه چیز اینجا کار می‌کند:

  • دیسپچ فوری. چون والد از قبل done است، فرزند مستقیماً در ready ساخته می‌شود — dispatcher می‌تواند در tick بعدی ادعایش کند. ‏(فرزندِ والدی هنوز-باز در todo انتظار می‌کشید.)
  • زمینهٔ به‌ارث‌رسیده. زمینهٔ کارگرِ اصلاحی بخشی از نوع Parent task results دارد که خلاصهٔ تکمیل و metadata ی t_impl را حمل می‌کند — فایل‌های تغییریافته و تصمیماتی که کارگر اصلی ثبت کرده — پس قبل از خواندن حتی یک خط کد می‌فهمد چرا کد این‌طور شکل گرفته.
  • شواهد تازه در بدنه. لاگ CI موقع تکمیل t_impl وجود نداشت، پس نمی‌تواند در تحویلِ والد باشد — در بدنهٔ کارت جدید می‌رود، کنار معیارهای پذیرش صریح.

برای کارت اصلاحی worktree/شاخهٔ تازه ترجیح دهید. checkout کردن شاخهٔ اصلی به کارگر وضعیت مخزن را می‌دهد اما هیچ‌کدام از دلایل را — تحویلِ والد آن‌ها را حمل می‌کند. معمولاً همان پروفایل assignee درست است: پروفیالی که کد را نوشته مهارت درست‌کردنش را دارد.

۹ بازرسی تسکی که همین حالا در حال اجراست

برای کامل بودن — این هم کشوی تسکی هنوز در جریان ‏(پیاده‌سازی API از داستان ۱، ادعا‌شده توسط backend-dev ولی هنوز ناتمام):

وضعیت Running است. run فعال در بخش Run History با نتیجهٔ active و بدون ended_at ظاهر می‌شود. اگر این کارگر بمیرد یا timeout شود، dispatcher این run را با نتیجهٔ مناسب می‌بندد و روی ادعای بعدی یکی جدید باز می‌کند — سطر تلاش هرگز ناپدید نمی‌شود.

۱۰ گام‌های بعدی

  • نگاه کلی کانبان — مدل دادهٔ کامل، واژگان رویداد و مرجع CLI.
  • ‏hermes kanban --help — هر زیرفرمان، هر فلگ.
  • ‏hermes kanban watch --kinds completed,gave_up,timed_out — استریم زندهٔ رویدادهای پایانه در سراسر برد.
  • ‏hermes kanban notify-subscribe <task> --platform telegram --chat-id <id> — با پایان یک تسک مشخص، پینگ گیت‌وی بگیرید.
