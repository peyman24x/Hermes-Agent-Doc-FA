نگهدارندهٔ مهارت‌ها (Curator)

نگهدارنده (کرتور) یک گذرِ نگهداریِ پس‌زمینه برای **مهارت‌های ساخته‌شده توسط ایجنت** است. دفعات دیده‌شدن، استفاده و patch شدنِ هر مهارت را پیگیری می‌کند، مهارت‌های مدت‌ها-استفاده‌نشده را از حالت‌های active → stale → archived عبور می‌دهد، و دوره‌ای یک بازبینی کوتاهِ مدل-کمکی تولید می‌کند که ادغام‌ها یا patchهای انحراف را پیشنهاد می‌دهد.

وجودش برای این است که مهارت‌هایی که از طریق حلقهٔ خودبهبودی ساخته می‌شوند برای همیشه انبار نشوند. هر بار ایجنت مسئلهٔ تازه‌ای را حل و مهارتی ذخیره می‌کند، آن مهارت در ~/.hermes/skills/ فرود می‌آید. بدون نگهداری، با ده‌ها نزدیک-تکرارِ باریک مواجه می‌شوید که کاتالوگ را آلوده و توکن را هدر می‌دهند.

به‌طور پیش‌فرض‏ (prune_builtins: true) کرتور می‌تواند **مهارت‌های داخلیِ همراهِ استفاده‌نشده** را (که با مخزن عرضه شده‌اند) پس از archive_after_days روز عدم استفاده آرشیو کند، در کنار مهارت‌های ایجنت‌ساخته‌ای که عمدتاً مدیریت می‌کند. مهارت‌های نصب‌شده از هاب‏ (از agentskills.io) همیشه مصون‌اند. curator.prune_builtins: false را برای برگرداندن رفتار قدیمیِ فقط-ایجنت‌ساخته بگذارید، جایی که مهارت‌های همراه هرگز لمس نمی‌شوند. کرتور همچنین هرگز خودکار حذف نمی‌کند — بدترین نتیجه، آرشیو در ~/.hermes/skills/.archive/ است که قابل‌بازیابی است.

۱ چگونه اجرا می‌شود

کرتور با بررسی بیکاری تریگر می‌شود، نه با دیمن کرون. در شروع نشست CLI، و در تیکِ ادواری داخل نخِ کرون‌تیکرِ گیت‌وی، هرمس بررسی می‌کند آیا:

  1. زمان کافی از آخرین اجرای کرتور گذشته‏ (interval_hours، پیش‌فرض ۷ روز)، و
  2. ایجنت به‌اندازهٔ کافی بیکار مانده‏ (min_idle_hours، پیش‌فرض ۲ ساعت).

اگر هر دو درست باشند، یک انشعاب پس‌زمینه از AIAgent تولید می‌کند — همان الگویی که یادآورهای خودبهبودیِ حافظه/مهارت استفاده می‌کنند. انشعاب در کش پرامپت خودش اجرا و هرگز گفتگوی فعال را لمس نمی‌کند.

ℹ️ رفتار اولین اجرا

در نصب کاملاً-تازه (یا اولین تیکِ نصبِ پیش-کرتوری بعد از hermes update)، کرتور بلافاصله اجرا نمی‌شود. اولین مشاهده last_run_at را روی «الان» می‌کارد و اولین گذرِ واقعی را یک interval_hours کامل عقب می‌اندازد. این به شما یک بازهٔ کامل می‌دهد تا کتابخانهٔ مهارت‌تان را بازبینی، چیز مهمی را پین یا کلاً خارج شوید، پیش از آنکه کرتور به آن دست بزند.

اگر می‌خواهید ببینید کرتور چه می‌کرد پیش از اجرای واقعی، hermes curator run --dry-run را بزنید — همان گزارش بازبینی را بدون جهش در کتابخانه تولید می‌کند.

یک اجرا دو فاز دارد:

  1. گذرهای خودکار (قطعی، بدون LLM). مهارت‌های استفاده‌نشده برای stale_after_days ‏(۳۰) stale می‌شوند؛ مهارت‌های استفاده‌نشده برای archive_after_days ‏(۹۰) به ~/.hermes/skills/.archive/ منتقل می‌شوند. این رفتار همیشه-روشنِ هرس است — هر وقت کرتور فعال باشد اجرا می‌شود، بدون هزینهٔ مدل-کمکی.
    • مهارت‌های پین‌شده و مهارت‌های ارجاع‌شده توسط هر کار کرونی (شامل کارهای متوقف/غیرفعال) کلاً رد می‌شوند — برای گذرهای خودکار مثل پین رفتار می‌کنند تا زمان‌بندیِ کند یا متوقف نتواند مهارتی را زیر پای یک کار آرشیو کند. ادغام هم ارجاعات کرونیِ مهارت را هنگام ادغام چترها بازنویسی می‌کند.
    • مهارت‌های هرگز-استفاده‌نشده‏ (use_count == 0) یک کف مهلت می‌گیرند: تا حداقل stale_after_days روزه نشوند آرشیو نمی‌شوند. صفر استفاده یعنی نبودِ شاهد، نه اثباتِ دورانداختنی‌بودن.
  2. ادغام LLM (یک گذر تکی مدل-کمکی با سقف تکرار بالا — یک جاروی کامل کیوریشن معمولاً ۵۰-۱۰۰ فراخوانی API) — پیش‌فرض خاموش. وقتی curator.consolidate: true باشد، ایجنتِ انشعاب‌یافته مهارت‌های ایجنت‌ساخته را بررسی، هر کدام را با skill_view می‌خواند و به‌ازای-هر-مهارت تصمیم می‌گیرد نگه دارد، ‏patch کند‏ (با skill_manage)، مهارت‌های هم‌پوشان را در چترهای سطح-کلاس ادغام کند، یا با ابزار ترمینال آرشیو کند. ادغام مهارت را بستهٔ کامل تلقی می‌کند: اگر مهارتی references/، ‏templates/، ‏scripts/، ‏assets/ یا لینک‌های نسبی به آن مسیرها دارد، کرتور باید یا آن را مستقل نگه دارد، فایل‌های پشتیبان لازم را خانه‌دادن و مسیرها را بازنویسی کند، یا کل بسته را بدون تغییر آرشیو کند — نه اینکه فقط SKILL.md را در فایل references/ مهارتی دیگر تخت کند.
ℹ️ ادغام اختیاری است

به‌طور پیش‌فرض کرتور فقط هرس می‌کند — گذرِ قطعیِ بیکاری مهارت‌ها را stale علامت و بلندمدت-استفاده‌نشده‌ها را آرشیو می‌کند. گذرِ نظرمحور ادغامِ LLM ‏(ساخت چتر، ادغام هم‌پوشان‌ها) پیش‌فرض خاموش است چون هر اجرا توکن مدل-کمکی خرج و تغییرات ساختاری گسترده‌ای به کتابخانه‌تان می‌دهد. با curator.consolidate: true روشنش کنید، یا یک‌باره با hermes curator run --consolidate به‌درخواست اجرایش کنید.

مهارت‌های پین‌شده هم برای گذرهای خودکار کرتور و هم برای خودِ ابزار skill_manage ایجنت مصون‌اند. به «پین‌کردن یک مهارت» پایین مراجعه کنید.

۲ پیکربندی

همهٔ تنظیمات در config.yaml زیر curator: زندگی می‌کنند (نه .env — این یک راز نیست). پیش‌فرض‌ها:

yaml
curator:
  enabled: true
  interval_hours: 168          # ۷ روز
  min_idle_hours: 2
  stale_after_days: 30
  archive_after_days: 90
  consolidate: false           # گذر ساخت-چترِ LLM — اختیاری (پیش‌فرض فقط-هرس)
  prune_builtins: true         # آرشیو داخلی‌های همراهِ استفاده‌نشده هم (هاب‌ها همیشه مصون)

برای کلاً غیرفعال‌کردن، curator.enabled: false. برای نگه‌داشتن هرسِ همیشه-روشن و اختیارگرفتنِ ادغام LLM، ‏curator.consolidate: true.

اجرای بازبینی روی مدل کمکیِ ارزان‌تر

گذر بازبینی LLM مربوط به کرتور یک جایگاه کار کمکیِ عادی است — auxiliary.curator — کنار بینایی، فشرده‌سازی، جستجوی نشست و غیره. «auto» یعنی «مدل چت اصلی‌ام را استفاده کن»؛ جایگاه را بازنویسی کنید تا ارائه‌دهنده + مدل مشخصی برای گذر بازبینی پین شود.

آسان‌ترین — ‏hermes model:

bash
hermes model                   # ← "Auxiliary models — side-task routing"
                               # ← "Curator" را بردارید ← ارائه‌دهنده ← مدل

همان انتخاب‌گر در داشبورد وب زیر تب **Models** هم موجود است.

config.yaml مستقیم (هم‌ارز):

yaml
auxiliary:
  curator:
    provider: openrouter
    model: google/gemini-3-flash-preview
    timeout: 600               # سخاوتمندانه — بازبینی‌ها می‌توانند چند دقیقه طول بکشند

رهاکردن provider: auto (پیش‌فرض) گذر بازبینی را از همان مدلی که چت اصلی‌تان است عبور می‌دهد، منطبق با رفتار هر کار کمکی دیگر.

ℹ️ پیکربندی قدیمی

ریلیزهای قبلی از بلوک یک‌بارهٔ curator.auxiliary.{provider,model} استفاده می‌کردند. آن مسیر هنوز کار می‌کند ولی یک خط لاگ منسوخ‌شدن صادر می‌کند — لطفاً به auxiliary.curator بالا مهاجرت کنید تا کرتور همان لوله‌کشی‏ (hermes model، ‏تب Models داشبورد، ‏base_url، ‏api_key، ‏timeout، ‏extra_body) را با هر کار کمکی دیگر شریک شود.

۳ CLI

bash
hermes curator status         # آخرین اجرا، شمارش‌ها، فهرست پین‌شده‌ها، ۵ تای LRU
hermes curator run            # تریگر اجرا همین حالا (تا اتمام بلاک). فقط-هرس مگر consolidate: true
hermes curator run --consolidate # روشن‌کردن اجباریِ گذر ادغام LLM برای همین اجرا
hermes curator run --background  # شلیک-و-رها: شروع اجرا در نخ پس‌زمینه
hermes curator run --dry-run  # فقط پیش‌نمایش — گزارش بدون هیچ جهشی
hermes curator backup         # اسنپ‌شات دستی از ~/.hermes/skills/
hermes curator rollback       # بازیابی از جدیدترین اسنپ‌شات
hermes curator rollback --list     # فهرست اسنپ‌شات‌های موجود
hermes curator rollback --id <ts>  # بازیابی اسنپ‌شات مشخص
hermes curator rollback -y         # ردکردن اعلان تأیید
hermes curator pause          # توقف اجراها تا resume
hermes curator resume
hermes curator pin <skill>    # هرگز گذر خودکار برای این مهارت
hermes curator unpin <skill>
hermes curator adopt <skill>    # سپردن مهارتِ مدیریت‌نشده به کرتور
hermes curator adopt --all-unmanaged   # سپردن همهٔ مدیریت‌نشده‌ها
hermes curator list-unmanaged   # فهرست مشروط مهارت‌های بدون نشان منشأ
hermes curator restore <skill>  # برگرداندن مهارت آرشیوشده به active
hermes curator list-archived    # فهرست مهارت‌های فعلاً در ~/.hermes/skills/.archive/
hermes curator archive <skill>  # آرشیو دستی یک مهارت تکی همین حالا
hermes curator prune [--days N] # آرشیو گروهی مهارت‌های ایجنت‌ساختهٔ بیکارِ ≥ N روز (پیش‌فرض ۹۰)
hermes curator ledger           # فهرست دفتر ممیزیِ به‌ازایی-جهش (همهٔ بازیگران)
hermes curator ledger --skill <name> --limit 50  # فیلتر/صفحه‌بندی مدخل‌های دفتر
hermes curator rollback <entry-id>  # خنثی‌کردن یک جهش تکی از دفتر
hermes curator purge [--days N] [--dry-run]  # حذف آرشیوهای قدیمی‌تر از TTL (فقط صریح)

۴ پشتیبان‌ها و بازگشت

پیش از هر گذرِ واقعی کرتور، هرمس اسنپ‌شات tar.gz از ~/.hermes/skills/ در ~/.hermes/skills/.curator_backups/<utc-iso>/skills.tar.gz می‌گیرد. اگر گذری چیزی را آرشیو یا ادغام کرد که نمی‌خواستید لمس شود، کل اجرا را با یک فرمان خنثی کنید:

bash
hermes curator rollback        # بازیابی جدیدترین اسنپ‌شات (با تأیید)
hermes curator rollback -y     # ردکردن پرامپت
hermes curator rollback --list # دیدن همهٔ اسنپ‌شات‌ها با دلیل + حجم

خود بازگشت هم برگشت‌پذیر است: پیش از جایگزینی درخت مهارت‌ها، هرمس اسنپ‌شات دیگری با برچسب pre-rollback to <target-id> می‌گیرد، پس یک بازگشت اشتباه با بازگشتِ رو-به-جلو به همان یکی با --id خنثی‌شدنی است.

هر زمان اسنپ‌شات دستی هم می‌توانید بگیرید: hermes curator backup --reason "before-refactor". رشتهٔ --reason در manifest.json اسنپ‌شات می‌نشیند و در --list نشان داده می‌شود.

اسنپ‌شات‌ها برای کرانداشتن مصرف دیسک به curator.backup.keep (پیش‌فرض ۵) هرس می‌شوند:

yaml
curator:
  backup:
    enabled: true
    keep: 5

curator.backup.enabled: false اسنپ‌شات‌گیری خودکار را خاموش می‌کند. فرمان دستی hermes curator backup وقتی پشتیبان‌ها خاموش‌اند فقط کار می‌کند که اول enabled: true گذاشته باشید — پرچم هر دو مسیر را متقارن گیت می‌کند تا راهی برای پرشِ تصادفی از اسنپ‌شاتِ پیش-اجرا روی اجراهای جهش‌دهنده نباشد.

hermes curator status همچنین پنج مهارتِ کمترین-استفادهٔ-اخیر را فهرست می‌کند — راه سریعی برای دیدن چیزی که احتمالاً بعدی stale می‌شود. همان زیرفرمان‌ها به‌صورت فرمان اسلش /curator داخل نشستِ در حال اجرا‏ (‏CLI یا پلتفرم‌های گیت‌وی) هم موجودند.

۵ دفتر ممیزی و بازگشتِ تکی‌ویرایش

اسنپ‌شات‌های کل-اجرا به «همهٔ کاری که آخرین گذر کرتور کرد را خنثی کن» پاسخ می‌دهند — ولی گاهی می‌خواهید بدانید چه کسی چه چیزی را تغییر داد و دقیقاً یک جهش را خنثی کنید. هر جهش مهارت — گذرهای خودکار کرتور، فراخوانی‌های skill_manage ایجنت، و archive/restore/purge خودتان از CLI — یک مدخل به دفتر JSONL فقط-الحاقیِ ~/.hermes/skills/.curator_ledger.jsonl می‌افزاید:

  • بازیگر — ‏curator ‏(انشعاب بازبینی پس‌زمینه / گذرهای خودکار)، ‏agent ‏(فراخوانی‌های ابزار ایجنتِ پیش‌زمینه)، یا user ‏(فرمان‌های CLI)
  • اقدام — ‏create، ‏edit، ‏patch، ‏delete، ‏write_file، ‏remove_file، ‏archive، ‏restore، ‏purge، ‏rollback
  • شاهد — نیت حذف‏ (absorbed_into برای ادغام‌ها، خالی برای هرس‌ها، و اینکه مسیر آرشیوِ-قابل-بازیابی هندلش کرده)، شناسهٔ نشستِ تریگرکننده وقتی موجود است
  • قبل/بعد — مانیفستهای به‌ازای-فایلِ {path, sha256}. محتویات فایل به‌صورت محتوا-نشانی‏ (بی‌تکرار با هش) زیر ~/.hermes/.curator_backups/blobs/ ذخیره می‌شوند، پس صد مدخلِ لمس‌کنندهٔ همان فایلِ تغییرنکرده یک blob هزینه می‌دهد.
bash
hermes curator ledger                  # ۲۰ مدخل جدیدترین
hermes curator ledger --skill my-skill --limit 50
hermes curator rollback <entry-id>     # بازیابی وضعیت-قبلِ همان یک جهش

بازگشت تکی‌مدخلی دقیقاً فایل‌هایی را که آن جهش لمس کرد بازیابی‏ (و فایل‌هایی که ساخته را حذف می‌کند) از مخزن blob — هیچ‌چیز دیگری در درخت مهارت‌ها حرکت نمی‌کند. مثل بازگشت کل-درخت، اول یک مدخلِ ایمنیِ وضعیت فعلی به دفتر می‌گیرد و ایمن می‌شکند: اگر ثبتِ ایمنی نوشتنی نباشد، هیچ‌چیز تغییر نمی‌کند. چون حذف‌های پیش‌زمینه هم در دفتر ثبت می‌شوند، hermes curator rollback <entry-id> می‌تواند مهارتِ سخت‌حذف‌شده را زنده کند.

دفتر تلمتری است، هرگز دروازه نه — اگر نوشتن مدخلی شکست بخورد، جهش همچنان انجام می‌شود. غیرفعالش کنید با:

yaml
skills:
  ledger: false

۶ پاک‌سازی TTL آرشیو

مهارت‌های آرشیوشده به‌طور پیش‌فرض برای همیشه نگه داشته می‌شوند. اگر می‌خواهید ~/.hermes/skills/.archive/ کراندار باشد، یک TTL بگذارید و صریح purge کنید — purging هرگز خودکار اجرا نمی‌شود، و هر مهارتِ purge‌شده اول در دفتر‏ (با blobها) ثبت می‌شود، پس حتی یک purge هم ردِ ممتحن-شونده و قابل‌بازیابی می‌گذارد:

yaml + bash
curator:
  archive_ttl_days: 180   # ۰ (پیش‌فرض) = هرگز purge نکن

hermes curator purge --dry-run   # پیش‌نمایش آنچه حذف می‌شد
hermes curator purge             # حذف آرشیوهای قدیمی‌تر از TTL (با تأیید)
hermes curator purge --days 90   # بازنویسی یک‌بارهٔ TTL

۷ معنای «ایجنت‌ساخته»

کرتور فقط مهارت‌هایی را مدیریت می‌کند که صریحاً در ~/.hermes/skills/.usage.json به‌عنوان ایجنت‌ساخته علامت خورده‌اند. مهارتی واجدشرط است وقتی همهٔ موارد زیر درست باشند:

  1. نامش در ~/.hermes/skills/.bundled_manifest نیست (مهارت‌های همراهِ عرضه‌شده با مخزن).
  2. نامش در ~/.hermes/skills/.hub/lock.json نیست (مهارت‌های نصب‌شده از هاب).
  3. مدخل .usage.json‌اش "created_by": "agent" یا "agent_created": true دارد.

فعلاً فقط انشعاب بازبینیِ خودبهبودیِ پس‌زمینه این نشان را می‌گذارد — وقتی در گذر بازبینی دوره‌ای‌اش‏ (‏~هر ۱۰ نوبت ایجنت) مهارت چتری تازه می‌سازد. انشعاب پس‌زمینه با خاستگاهِ نوشتنِ "background_review" اجرا می‌شود‏ (از tools/skill_provenance.py)، که تنها مسیرِ تریگرکردنِ فراخوانی mark_agent_created() در skill_manage است.

مهارت‌هایی که ایجنتِ پیش‌زمینه در طول گفتگو با skill_manage(action="create") می‌سازد ایجنت‌ساخته علامت نمی‌خورند — کاربر-هدایت‌شده تلقی و کرتور آگاهانه رهایشان می‌کند.

⚠️ مهارت‌های دست‌نوشتهٔ شما کیور نمی‌شوند

اگر دستی SKILL.md ساخته‌اید یا هرمس را به پوشهٔ مهارت بیرونی اشاره داده‌اید، آن مهارت مدخل .usage.json با created_by: null دارد (یا فیلد غایب). کرتور به آن دست نمی‌زند. همین برای مهارت‌هایی که ایجنت پیش‌زمینه به درخواست شما ساخته صادق است.

برای دیدن اینکه کرتور واقعاً چه مهارت‌هایی را مدیریت می‌کند، hermes curator status را اجرا کنید. اگر شمار ایجنت‌ساخته‌ها ۰ بود، هیچ مهارتی فعلاً در صلاحیت کرتور نیست — گذر بازبینی LLM رد می‌شود و گزارش Model: (not resolved) via (not resolved) با Duration: 0s نشان می‌دهد.

به‌فرزندخواندن مهارت‌های مدیریت‌نشده

hermes curator status شمار مدیریت‌نشده را کنار شمار مدیریت‌شده گزارش می‌کند:

خروجی
curator-managed skills: 43 total  (agent-created=43  bundled=0)
  active     41
  stale       2
  archived    0

unmanaged (no provenance marker): 112 total
  pre-dates marker    34
  foreground-created  78
  never auto-staled or archived — `hermes curator adopt <name>` hands one over

آن ۱۱۲ تا کیور-واجدشرط ولی برای چرخهٔ حیات برای همیشه نامرئی‌اند، به یکی از این دو دلیل:

  • قدیمی‌تر از نشان — رکورد قبل از وجود created_by نوشته شده، پس اصلاً سیگنال منشأیی حمل نمی‌کند. مؤلفّیت از روی رکورد واقعاً دانستنی نیست.
  • پیش‌زمینه‌ساخته — یک skill_manage(create) پیش‌زمینه‌ای نشان را عمداً تنظیم‌نشده گذاشته، چون مهارت‌هایی که شما می‌خواهید مال شما هستند.

پس کتابخانهٔ بزرگی می‌تواند کاملاً کیورشده به‌نظر برسد در حالی که بیشترش دست‌نخوردنی است. adopt این شکاف را با اعلام می‌بندد:

bash
hermes curator list-unmanaged                    # فهرست مشروط با دلایل
hermes curator adopt <name> [<name> ...]         # سپردن مهارت‌های مشخص
hermes curator adopt --all-unmanaged --dry-run   # پیش‌نمایش فهرست کامل
hermes curator adopt --all-unmanaged             # سپردن همه (با پرامپت)
hermes curator adopt --all-unmanaged --yes       # ردکردن پرامپت

به‌فرزندخواندن همان نشان created_by: agentی را می‌نویسد که انشعاب بازبینی پس‌زمینه می‌نویسد. ساعت بیکاری را ریست نمی‌کند — مهارت فرزندخوانده last_activity_at موجودش را نگه می‌دارد، پس سپردن کتابخانه‌ای که از قبل دست‌کشیده‌اید پنجرهٔ تازهٔ ۹۰ روزه‌ای به آن نمی‌خرد. انتظار داشته باشید مهارت‌های فرزندخواندهٔ بلندبیکار در گذر بعدی stale ‏(یا archived) شوند؛ نکته همین است.

به‌فرزندخواندن همان چیزی است که بهبودِ خودمختار را باز می‌کند. انشعاب بازبینی پس‌زمینه از patch‌کردن مهارتی که مدیریت-کرتوری نیست سر باز می‌زند، پس اگر متوجه شود یکی از مهارت‌هایتان قدیمی شده، می‌گوید و به‌فرزندخواندن را توصیه می‌کند به‌جای ویرایشش. ویرایش‌های پیش‌زمینه‏ (کاربر-هدایت) هرگز متأثر نمی‌شوند — شما و ایجنت همیشه می‌توانید مهارت‌های خودتان را به درخواست ویرایش کنید.

ℹ️ created_by یک پرچم سیاست است، نه ادعای منشأ

فیلد ذخیره‌شده created_by نام دارد، ولی به‌عنوانِ «آیا کیوریشنِ خودمختار می‌تواند به این دست بزند؟» مصرف می‌شود — نه «چه کسی این فایل را نوشت». این‌ها سؤال‌های متفاوتی‌اند و برای رکوردهای قدیمی‌تر از نشان، پاسخ مؤلفّیت صرفاً بازیابی‌ناپذیر است. نام نگه داشته شده چون از قبل در هر .usage.json روی دیسک است؛ آن را به‌عنوان سیاست بخوانید. hermes curator adopt سیاست را عوض می‌کند و چیزی دربارهٔ مؤلف فایل نمی‌گوید.

ℹ️ منشأ اعلام می‌شود، هرگز استنتاج نمی‌شود

به‌فرزندخواندن عمداً دستی است. تلمتری نمی‌تواند مؤلفّیت را اثبات کند: مهارتی با هزاران patch ثابت می‌کند ایجنت آن را نگهداری می‌کند، نه اینکه ایجنت آن را نوشته — هرمس دائماً از طرف شما مهارت‌های کاربر-نوشته را ویرایش می‌کند. یک ابتکار خودکارِ «ایجنت‌ساخته-به‌نظر-می‌رسد، به‌فرزندش بگیر» بالاخره چیزی را که خودتان نوشته بودید آرشیو می‌کرد. adopt از مهارت‌های همراه، هاب‌نصب، بیرونی و داخلیِ محافظت‌شده — که مالکی جز شما دارند — سر باز می‌زند.

مهارت‌هایی که ایجنت‌ساخته‌اند چرخهٔ کامل را طی می‌کنند:

  • active ← ‏(۳۰ روز بیکار) stale ← ‏(۹۰ روز بیکار) archived
  • مهارت‌های پین‌شده از همهٔ گذرهای خودکار عبور می‌کنند
  • آرشیوها با hermes curator restore <name> قابل‌بازیابی‌اند

اگر می‌خواهید مهارت مشخصی را برای همیشه مصون کنید — مثلاً مهارت دست‌نوشته‌ای که به آن تکیه دارید — از hermes curator pin <name> استفاده کنید. بخش بعدی را ببینید.

۸ پین‌کردن یک مهارت

پین‌کردن مهارت را از حذف محافظت می‌کند — هم گذرهای آرشیوِ خودکارِ کرتور و هم فراخوانی ابزار skill_manage(action="delete") ایجنت. وقتی مهارتی پین شد:

  • کرتور آن را در گذرهای خودکار‏ (active → stale → archived) رد می‌کند، و به گذر بازبینی LLMش دستور داده شده کاری با آن نکند.
  • ابزار skill_manage ایجنت delete روی آن را رد کرده و کاربر را به hermes curator unpin <name> اشاره می‌کند. ‏Patchها و ویرایش‌ها همچنان عبور می‌کنند، پس ایجنت می‌تواند محتوای مهارت پین‌شده را وقتی دام‌ها پیدا شدند بهبود دهد، بدون رقصِ پین/آنپین/بازپین.
bash
hermes curator pin <skill>
hermes curator unpin <skill>

پرچم به‌صورت "pinned": true روی مدخل مهارت در ~/.hermes/skills/.usage.json ذخیره می‌شود، پس بین نشست‌ها می‌ماند.

مهارت‌های نام‌برده در فهرست skills: هر کار کرونی برای گذرهای خودکار به همین شکل محافظت می‌شوند‏ (کرتور تا وقتی ارجاع هست هرگز آن‌ها را stale/آرشیو نمی‌کند)، حتی وقتی کار متوقف یا غیرفعال است. وقتی می‌خواهید skill_manage delete هم بلاک شود پین صریح را ترجیح دهید.

فقط مهارت‌های ایجنت‌ساخته پین‌پذیرند — hermes curator pin روی مهارت‌های همراه و هاب‌نصب با پیام توضیحی رد می‌شود. مهارت‌های هاب‌نصب هرگز تابع جهش کرتور نیستند. داخلی‌های همراه فقط وقتی curator.prune_builtins: true (پیش‌فرض) لمس می‌شوند، و حتی آن‌وقت فقط پس از archive_after_days روز عدم استفاده آرشیو — هرگز patch، ادغام یا حذف نمی‌شوند. برای مصون‌کردن کامل داخلی‌ها curator.prune_builtins: false بگذارید.

مجموعهٔ کوچکی از داخلی‌های محافظت‌شده به‌صورت هاردکد هرگز-آرشیو-پذیر و هرگز-ادغام-پذیرند، صرف‌نظر از curator.prune_builtins، وضعیت پین یا قضاوت LLM. این‌ها UX حمل‌بار را پشتیبانی می‌کنند — مثلاً plan جریان فرمان اسلش /plan را قدرت می‌دهد — پس آرشیو خاموشِ یکی فرمان اسلشش را به خطای «Unknown command» تبدیل می‌کرد بدون سیگنالی به شما. داخلی‌های محافظت‌شده کلاً از فهرست کاندیدهای کرتور فیلتر می‌شوند، پس گذر ادغام هرگز نمی‌بیندشان.

اگر تضمینی قوی‌تر از «بدون حذف» می‌خواهید — مثلاً فریز کامل محتوای مهارت در حالی که ایجنت همچنان می‌خواندش — ~/.hermes/skills/<name>/SKILL.md را مستقیم با ادیتور خودتان ویرایش کنید. پین، حذفِ ابزار-محور را گیت می‌کند، نه دسترسیِ خودتان به فایل‌سیستم را.

۹ تلمتری استفاده

کرتور یک سایدکار در ~/.hermes/skills/.usage.json با یک مدخل به‌ازای-هر-مهارت نگه می‌دارد:

json
{
  "my-skill": {
    "use_count": 12,
    "view_count": 34,
    "last_used_at": "2026-04-24T18:12:03Z",
    "last_viewed_at": "2026-04-23T09:44:17Z",
    "patch_count": 3,
    "last_patched_at": "2026-04-20T22:01:55Z",
    "created_at": "2026-03-01T14:20:00Z",
    "state": "active",
    "pinned": false,
    "archived_at": null
  }
}

شمارنده‌ها وقتی بالا می‌روند:

  • view_count: ایجنت skill_view را روی مهارت صدا می‌زند.
  • use_count: مهارت در پرامپت گفتگویی بارگذاری می‌شود.
  • patch_count: skill_manage patch/edit/write_file/remove_file روی مهارت اجرا می‌شود.

مهارت‌های همراه و هاب‌نصب صریحاً از نوشتنِ تلمتری مستثنا‌اند.

۱۰ گزارش‌های به‌ازایی-اجرا

هر اجرای کرتور یک پوشهٔ مُهردار-با-زمان زیر ~/.hermes/logs/curator/ می‌نویسد:

text
~/.hermes/logs/curator/
└── 20260429-111512/
    ├── run.json      # ماشین‌خوان: وفاداری کامل، آمار، خروجی LLM
    └── REPORT.md     # خلاصهٔ انسانی‌خوان

REPORT.md راه سریعی است برای دیدن اجرای معین چه کرد — کدام مهارت‌ها گذر کردند، بازبین LLM چه گفت، کدام‌ها را patch کرد. برای ممیزی بدون grep ‏agent.log خوب است.

ℹ️ بدون کاندید؟ گزارش (not resolved) نشان می‌دهد

وقتی کرتور مهارت ایجنت‌ساخته‌ای برای بازبینی ندارد، گذر بازبینی LLM کلاً رد می‌شود. سرصفحهٔ گزارش Model: (not resolved) via (not resolved) با Duration: 0s نشان می‌دهد — این خطای پیکربندی یا شکست حل مدل نیست. صرفاً یعنی کاندیدی نبود، پس مدلی هرگز فراخوانی نشد. فاز گذر خودکار همچنان اجرا و شمارش‌هایش را عادی گزارش می‌کند.

نقشهٔ تغییرنام در خلاصه

اگر اجرایی چند مهارت را زیر چتری ادغام کرد‏ (یا نزدیک-تکرارها را مرج)، خلاصهٔ رو-به-کاربری که در پایان اجرا چاپ می‌شود نقشهٔ تغییرنام صریحی شامل هر جفتِ old-name → new-nameی که کرتور اعمال کرد را می‌گیرد. این به‌علاوهٔ خطوط گذرِ به‌ازای-مهارت است، پس وقتی موجی از تغییرنام‌ها می‌آید بدون diff ‏گزارش JSON در یک نگاه می‌بینیدشان. راهنما زیر hermes curator pin هم ظاهر می‌شود تا اگر می‌خواهید برچسب جدید را قفل کنید، بلافاصله نام چتر را پین کنید.

۱۱ بازیابی مهارت آرشیوشده

اگر کرتور چیزی را آرشیو کرد که هنوز می‌خواهید:

bash
hermes curator restore <skill-name>

این مهارت را از ~/.hermes/skills/.archive/ به درخت فعال برمی‌گرداند و وضعیتش را به active ریست می‌کند. اگر مهارت همراه یا هاب‌نصبی از آن زمان با همان نام نصب شده باشد بازیابی رد می‌شود (بالاترین را سایه می‌انداشت).

۱۲ غیرفعال‌سازی به‌ازای-محیط

کرتور پیش‌فرض روشن است. برای خاموش‌کردن:

  • فقط یک پروفایل: ~/.hermes/config.yaml (یا config پروفایل فعال) را ویرایش و curator.enabled: false کنید.
  • فقط یک مدت: hermes curator pause — توقف بین نشست‌ها می‌ماند؛ با resume دوباره فعال کنید.

کرتور اگر min_idle_hours نگذشته هم اجرا نمی‌شود، پس روی ماشین dev فعال به‌طور طبیعی فقط در سکوت‌ها اجرا می‌شود.
