کانبان — همکاری چند-پروفایلیِ چند-ایجنتی

راهنمای گام‌به‌گام می‌خواهید؟ آموزش کانبان را بخوانید — چهار داستان کاربری ‏(توسعه‌دهندهٔ تنها، مزرعهٔ ناوگان، خط‌لولهٔ نقش‌محور با retry، مدارشکن) با اسکرین‌شات داشبورد هرکدام. این صفحه مرجع است؛ آموزش روایت است.

هرمس کانبان یک تختهٔ کار ماندگار، مشترک بین همهٔ پروفایل‌های هرمس شماست که اجازه می‌دهد چند ایجنت نام‌دار روی کار همکاری کنند بدون ازدحام‌های شکنندهٔ زیرایجنت درون-پروسه. هر task یک ردیف در ‏~/.hermes/kanban.db است؛ هر handoff ردیفی است که هر کسی می‌تواند بخواند و بنویسد؛ هر worker یک پروسهٔ کامل OS با هویت خودش است.

۱ دو سطح: مدل از طریق ابزار حرف می‌زند، شما از طریق CLI

تخته دو در ورودی دارد که هر دو پشت همان ‏~/.hermes/kanban.db هستند:

  • ایجنت‌ها تخته را از طریق تول‌ست اختصاصی ‏kanban_* می‌رانند — ‏kanban_show، ‏kanban_list، ‏kanban_complete، ‏kanban_request_review، ‏kanban_request_changes، ‏kanban_block، ‏kanban_heartbeat، ‏kanban_comment، ‏kanban_attach، ‏kanban_attach_url، ‏kanban_attachments، ‏kanban_create، ‏kanban_link، ‏kanban_unblock. ‏dispatcher هر worker را با این ابزارها از قبل در schema‌اش spawn می‌کند؛ پروفایل‌های ارکستراتور هم می‌توانند تول‌ست ‏kanban را صریحاً فعال کنند. مدل task ها را با فراخوانی مستقیم ابزار می‌خواند و مسیریابی می‌کند، *نه* با شل‌کردن به ‏hermes kanban.
  • شما ‏(و اسکریپت‌ها و کرون) تخته را با ‏hermes kanban … روی CLI، ‏/kanban … به‌عنوان فرمان اسلش یا داشبورد می‌رانند. این‌ها برای انسان‌ها و اتوماسیون‌اند — جاهایی بدون مدل فراخوانی‌کنندهٔ ابزار پشتشان.

هر دو سطح از همان لایهٔ ‏kanban_db عبور می‌کنند، پس خواندها نمای سازگار می‌بینند و نوشته‌ها واگرایی پیدا نمی‌کنند. بقیهٔ این صفحه مثال‌های CLI را نشان می‌دهد چون کپی-پیست‌شان راحت است ولی هر فعل CLI معادل فراخوانی-ابزاری دارد که مدل استفاده می‌کند.

این شکلی است که workload های ‏delegate_task را که نمی‌تواند پوشش دهد:

  • triage تحقیقاتی — محقق‌های موازی + تحلیلگر + نویسنده، انسان-در-حلقه.
  • عملیات زمان‌بندی‌شده — خلاصه‌های روزانهٔ تکرارشونده که طی هفته‌ها ژورنال می‌سازند.
  • دوقلوهای دیجیتال — دستیارهای نام‌دارِ ماندگار ‏(inbox-triage، ‏ops-review) که با گذر زمان حافظه جمع می‌کنند.
  • خط‌لوله‌های مهندسی — تجزیه ← پیاده‌سازی موازی در worktree ها ← بازبینی ← تکرار ← PR.
  • کار ناوگانی — یک متخصص که N سوژه را مدیریت می‌کند ‏(۵۰ اکانت شبکه اجتماعی، ۱۲ سرویس تحت‌مانیتور).

برای rationale طراحی کامل، تحلیل تطبیقی با Cline Kanban/Paperclip/NanoClaw/Google Gemini Enterprise و هشت الگوی همکاری مرجع، فایل ‏docs/hermes-kanban-v1-spec.pdf در مخزن را ببینید.

تمایز یک‌جمله‌ای: ‏delegate_task یک فراخوانی تابع است؛ Kanban صف کاری است که هر handoff آن ردیفی است که هر پروفایل ‏(یا انسان) می‌تواند ببیند و ویرایش کند.

‏delegate_task را وقتی استفاده کنید که ایجنت والد قبل از ادامه به یک جواب استدلالی کوتاه نیاز دارد، انسانی در میان نیست و نتیجه به زمینهٔ والد برمی‌گردد.

Kanban را وقتی استفاده کنید که کار از مرز ایجنت‌ها عبور می‌کند، باید از ری‌استارت‌ها جان ببرد، ممکن است ورودی انسانی بخواهد، ممکن است نقش دیگری برداردش، یا باید بعداً قابل‌یافتن باشد.

آن‌ها همزیستی دارند: یک worker کانبانی ممکن است حین اجرایش داخلا ‏delegate_task صدا بزند.

۳ مفاهیم اصلی

  • Board — یک صف مستقل از task ها با دیتابیس SQLite، پوشهٔ workspaces و حلقهٔ dispatcher خودش. یک نصب واحد می‌تواند board های زیادی داشته باشد ‏(مثلاً یکی به‌ازای هر پروژه/repo/دامنه)؛ «Board ها (چند-پروژه‌ای)» پایین را ببینید. کاربران تک-پروژه روی board ‏default می‌مانند و بیرون از همین بخش مستندات هرگز کلمهٔ «board» را نمی‌بینند.
  • Task — ردیفی با عنوان، بدنهٔ اختیاری، یک assignee ‏(نام پروفایل)، وضعیت ‏(triage | todo | ready | running | blocked | review | done | archived)، namespace اختیاری tenant و کلید idempotency اختیاری ‏(dedup برای اتوماسیون‌های تکراری).
  • Link — ردیف ‏task_links ثبت‌کنندهٔ وابستگی والد ← فرزند. ‏dispatcher وقتی همهٔ والدین ‏done شوند ‏todo → ready را ارتقا می‌دهد.
  • Comment — پروتکل بین-ایجنتی. ایجنت‌ها و انسان‌ها کامنت اضافه می‌کنند؛ وقتی worker ‏(مجدداً) spawn می‌شود کل رشتهٔ کامنت را جزء زمینه‌اش می‌خواند.
  • Workspace — پوشه‌ای که worker در آن عمل می‌کند. سه نوع:
    • ‏scratch ‏(پیش‌فرض) — پوشهٔ tmp تازه زیر ‏~/.hermes/kanban/workspaces/<id>/ ‏(یا ‏~/.hermes/kanban/boards/<slug>/workspaces/<id>/ روی board های غیر-default). وقتی task تمام شود حذف می‌شود — scratch عمداً گذراست. فایل‌هایی که صریحاً از طریق ‏kanban_complete(artifacts=[...]) اعلام شده باشند قبل از پاکسازی داخل ذخیرهٔ ماندگار پیوست به‌ازای-task کپی می‌شوند؛ مسیرهای deliverable موجود در خلاصه‌های اتمام قدیمی همان رفتار را می‌گیرند. سایر فایل‌های scratch حذف می‌شوند. آرتیفکت scratch اعلام‌شدهٔ غایب task را در-جراحی نگه می‌دارد تا worker مسیر را اصلاح و retry کند. وقتی کل workspace باید در دسترس بماند از ‏worktree: یا ‏dir:<path> استفاده کنید. اولین بار که workspace اسکرچی روی یک نصب ساخته شود dispatcher هشدار لاگ و رویداد ‏tip_scratch_workspace روی task صادر می‌کند ‏(قابل‌مشاهده از ‏hermes kanban show <id>).
    • ‏dir:<path> — یک پوشهٔ مشترک موجود ‏(vault اوبسیدین، پوشهٔ عملیات ایمیل، پوشهٔ به‌ازای-اکانت). باید مسیر مطلق باشد. مسیرهای نسبی مثل ‏dir:../tenants/foo/ هنگام dispatch رد می‌شوند چون نسبت به هر CWD ای که dispatcher اتفاقی در آن است حل می‌شدند که مبهم و بردار فرار confused-deputy است. در غیر این صورت مسیر مطمئن تلقی می‌شود — ماشین شما، فایل‌سیستم شما، worker با uid شما اجرا می‌شود. این مدل تهدید کاربر-محلی-مطمئن است؛ کانبان عمداً تک-میزبان است. هنگام اتمام حفظ می‌شود.
    • ‏worktree — یک git worktree زیر ‏.worktrees/<id>/ برای کارهای کدنویسی. برای pin کردن دقیق مسیر هدف از ‏worktree:<path> استفاده کنید. سمت-worker ‏git worktree add می‌سازدش و وقتی داده شده از ‏--branch استفاده می‌کند. هنگام اتمام حفظ می‌شود.
  • Dispatcher — حلقهٔ طولانی‌عمری که هر N ثانیه ‏(پیش‌فرض ۶۰): claim های کهنه را پس می‌گیرد، worker های کرش‌کرده را پس می‌گیرد ‏(PID رفته ولی TTL هنوز منقضی نشده)، task های ready را ارتقا می‌دهد، اتمیک claim و پروفایل‌های تعیین‌شده را spawn می‌کند. پیش‌فرض داخل گیت‌وی اجرا می‌شود ‏(kanban.dispatch_in_gateway: true). یک dispatcher همهٔ board ها را در هر تیک sweep می‌کند؛ worker ها با ‏HERMES_KANBAN_BOARD قفل‌شده spawn می‌شوند تا board های دیگر را نبینند. بعد از ‏kanban.failure_limit شکست متوالی spawn روی همان task ‏(پیش‌فرض: ۲) dispatcher خودکار آن را با آخرین خطا به‌عنوان دلیل بلاک می‌کند — مانع thrash شدن روی task هایی که پروفایلشان وجود ندارد یا workspace قابل mount نیست و... .
  • Tenant — namespace رشته‌ای اختیاری *داخل* یک board. یک ناوگان متخصص می‌تواند به چند کسب‌وکار خدمت کند ‏(--tenant business-a) با جداسازی داده از طریق مسیر workspace و پیشوند کلید حافظه. ‏tenant ها فیلتر نرم‌اند؛ board ها مرز ایزولاسیون سخت‌اند.

۴ Board ها ‏(چند-پروژه‌ای)

‏Board ها اجازه می‌دهند جریان‌های کاری نامرتبط — یکی به‌ازای هر پروژه، repo یا دامنه — به صف‌های ایزوله تفکیک شوند. نصب جدید دقیقاً یک board به نام ‏default دارد ‏(DB روی ‏~/.hermes/kanban.db برای سازگاری رو-به-عقب). کاربرانی که فقط یک جریان کار می‌خواهند هیچ‌وقت لازم نیست از board ها خبر داشته باشند؛ قابلیت انتخابی است.

ایزولاسیون به‌ازای-board مطلق است:

  • دیتابیس SQLite جداگانه به‌ازای هر board ‏(~/.hermes/kanban/boards/<slug>/kanban.db).
  • پوشه‌های جداگانهٔ ‏workspaces/ و ‏logs/.
  • worker های spawn‌شده برای یک task فقط task های board خودشان را می‌بینند — dispatcher مقدار ‏HERMES_KANBAN_BOARD را در env فرزند ست و هر ابزار ‏kanban_* که worker به آن دسترسی دارد آن را می‌خواند.
  • لینک‌کردن task ها بین board ها مجاز نیست ‏(schema ساده می‌ماند؛ اگر واقعاً ارجاع بین-پروژه‌ای لازم دارید از منشن‌های متنی آزاد استفاده و با شناسه دستی پیدایشان کنید).

مدیریت board ها از CLI

bash
# See what's on disk. Fresh installs show only "default".
hermes kanban boards list

# Create a new board.
hermes kanban boards create atm10-server \
    --name "ATM10 Server" \
    --description "Minecraft modded server ops" \
    --icon 🎮 \
    --switch                   # optional: make it the active board

# Operate on a specific board without switching.
hermes kanban --board atm10-server list
hermes kanban --board atm10-server create "Restart ATM server" --assignee ops

# Change which board is "current" for subsequent calls.
hermes kanban boards switch atm10-server
hermes kanban boards show             # who's active right now?

# Rename the display name (the slug is immutable — it's the directory name).
hermes kanban boards rename atm10-server "ATM10 (Prod)"

# Archive (default) — moves the board's dir to boards/_archived/<slug>-<ts>/.
# Recoverable by moving the dir back.
hermes kanban boards rm atm10-server

# Hard delete — `rm -rf` the board dir. No recovery.
hermes kanban boards rm atm10-server --delete

ترتیب حل board ‏(بالاترین تقدم اول):

  1. ‏--board <slug> صریح روی فراخوانی CLI.
  2. متغیر env ‏HERMES_KANBAN_BOARD ‏(توسط dispatcher هنگام spawn worker ست می‌شود تا worker ها board های دیگر را نبینند).
  3. ‏~/.hermes/kanban/current — اسلاگی که ‏hermes kanban boards switch ماندگار کرده.
  4. ‏default.

‏slug ها اعتبارسنجی می‌شوند: حروف کوچک الفبایی + خط‌تیره + زیرخط، ‏۱–۶۴ کاراکتر، باید با حرف شروع شوند. ورودی بزرگ خودکار کوچک می‌شود. هر چیز دیگر ‏(اسلش، فاصله، نقطه، ‎..‎‎) در لایهٔ CLI رد می‌شود تا ترفندهای path-traversal نتوانند نام یک board باشند.

مدیریت board ها از داشبورد

‏hermes dashboard ← تب Kanban به‌محض وجود بیش از یک board ‏(یا هر board دارای task) سوییچر board بالای صفحه نشان می‌دهد. کاربران تک-board فقط دکمهٔ کوچک ‏+ New board می‌بینند؛ سوییچر تا وقتی مهم نشود مخفی است.

  • کشویی Board — board فعال را انتخاب کنید. انتخابتان در ‏localStorage مرورگر ذخیره می‌شود تا بین reload ها بماند بدون اینکه pointer ‏current مربوط به CLI را از زیر ترمینال بازِ شما جابه‌جا کند.
  • + New board — modalی می‌دهد برای slug، نام نمایشی، توضیح و آیکون. گزینهٔ سوئیچ خودکار به board جدید.
  • Settings — modalی برای ویرایش نام نمایشی، توضیح و پوشهٔ پروژه ‏(default_workdir) board فعلی. پوشهٔ پروژه پیش‌فرض workspace در سطح-board است که هر task جدید ارث می‌برد ‏(repo گیت ← worktree حفظ‌شده، پوشهٔ ساده ← پوشهٔ حفظ‌شده)؛ هر task همچنان می‌تواند هنگام ساخت override‌اش کند. پاک‌کردن فیلد task های جدید را به workspace های scratch دورریزنی برمی‌گرداند.
  • Archive — فقط روی board های غیر-default نشان داده می‌شود. تأیید می‌گیرد و بعد پوشهٔ board را به ‏boards/_archived/ منتقل می‌کند.

همهٔ endpoint های API داشبورد ‏?board=<slug> را برای scoping می‌پذیرند. WebSocket رویدادها هنگام اتصال به یک board قفل می‌شود؛ سوئیچ در UI یک WS تازه علیه board جدید باز می‌کند.

۵ پیوست‌های فایل

task ها می‌توانند پیوست فایل حمل کنند — PDF، تصویر، سند مبدأ — تا worker مواد مبدأ لازم را داشته باشد بدون اینکه شما مسیرها را داخل بدنه بچپانید و امیدوار باشید پیدایشان کند.

  • Upload — task را در drawer داشبورد باز کنید و از بخش Attachments دکمهٔ *Upload file* را بزنید ‏(چند فایل هم‌زمان اوکی است). هر آپلود سقف ۲۵ مگابایت دارد.
  • Storage — فایل‌ها برای board پیش‌فرض زیر ‏<hermes-home>/kanban/attachments/<task_id>/ و برای board نام‌دار زیر ‏<hermes-home>/kanban/boards/<slug>/attachments/<task_id>/ می‌نشینند. برای قفل‌کردن محل سفارشی ‏HERMES_KANBAN_ATTACHMENTS_ROOT را ست کنید.
  • worker چه می‌بیند — وقتی dispatcher task را به worker می‌دهد، زمینهٔ worker بخشی به نام Attachments دارد که نام هر فایل و مسیر مطلقش را فهرست می‌کند. worker دسترسی کامل ابزار فایل/ترمینال دارد، پس پیوست‌ها را مستقیم می‌خواند ‏(read_file یا ابزارهای شلی مثل ‏pdftotext).
  • Download / remove — drawer هر پیوست را با لینک دانلود و کنترل حذف ‏(×) فهرست می‌کند. حذف پیوست هم ردیف متادیتا هم فایل روی دیسک را پاک می‌کند.
📌 بک‌اندهای ترمینال راه‌دور

مسیرهای پیوست روی بک‌اند ترمینال محلی مستقیم حل می‌شوند که پیش‌فرض worker های Kanban است. اگر worker ها را روی بک‌اند راه‌دور اجرا می‌کنید ‏(Docker، ‏Modal)، پوشهٔ ‏attachments مربوط به board را داخل sandbox مانت کنید تا مسیرهای مطلق داخل زمینهٔ worker قابل‌رسید باشند.

۶ شروع سریع

فرمان‌های پایین شما ‏(انسان) هستید که board را راه می‌اندازید و task می‌سازید. بعد از assign شدن یک task، dispatcher پروفایل تعیین‌شده را به‌عنوان worker spawn می‌کند و از آن به بعد مدل task را از طریق فراخوانی‌های ابزار ‏kanban_* می‌رانند نه فرمان‌های CLI.

bash
# 1. Create the board (you)
hermes kanban init

# 2. Start the gateway (hosts the embedded dispatcher)
hermes gateway start

# 3. Create a task (you — or an orchestrator agent via kanban_create)
hermes kanban create "research AI funding landscape" --assignee researcher

# 4. Watch activity live (you)
hermes kanban watch

# 5. See the board (you)
hermes kanban list
hermes kanban stats

وقتی dispatcher ‏t_abcd را برمی‌دارد و پروفایل ‏researcher را spawn می‌کند، اولین کاری که مدل آن worker می‌کند صدازدن ‏kanban_show() برای خواندن task‌اش است. ‏hermes kanban show t_abcd را اجرا نمی‌کند.

dispatcher جاسازی‌شده در گیت‌وی ‏(پیش‌فرض)

‏dispatcher داخل پروسهٔ گیت‌وی اجرا می‌شود. چیزی برای نصب نیست، سرویس جداگانه‌ای برای مدیریت نیست — اگر گیت‌وی بالا باشد task های ready در تیک بعدی برداشته می‌شوند ‏(پیش‌فرض ۶۰ ثانیه).

yaml
# config.yaml
kanban:
  dispatch_in_gateway: true        # default
  dispatch_interval_seconds: 60    # default
  review_dispatch: true            # default: spawn the assigned profile with
                                   # the bundled sdlc-review skill. Set false
                                   # for human-only review boards.

فلگ پیکربندی را در runtime با ‏HERMES_KANBAN_DISPATCH_IN_GATEWAY=0 برای دیباگ override کنید. نظارت استاندارد گیت‌وی اعمال می‌شود: ‏hermes gateway start را مستقیم اجرا یا گیت‌وی را به‌عنوان unit کاربر systemd سیم کنید ‏(مستندات گیت‌وی را ببینید). بدون گیت‌وی در حال اجرا، task های ‏ready سر جایشان می‌مانند تا یکی بالا بیاید — ‏hermes kanban create هنگام ساخت درباره‌اش هشدار می‌دهد.

اجرای ‏hermes kanban daemon به‌عنوان پروسهٔ جداگانه deprecated است؛ از گیت‌وی استفاده کنید. اگر واقعاً نمی‌توانید گیت‌وی را اجرا کنید ‏(سیاست میزبان headless سرویس‌های بلند-عمر را ممنوع می‌کند و...) دریچهٔ ‏--force دیمون مستقل قدیمی را یک چرخهٔ ریلیز زنده نگه می‌دارد ولی اجرای هم‌زمان dispatcher جاسازی‌شده-در-گیت‌وی و دیمون مستقل روی همان ‏kanban.db باعث race های claim می‌شود و پشتیبانی نمی‌شود.

create ایدمپوتنت ‏(برای اتوماسیون / وب‌هوک‌ها)

bash
# First call creates the task. Any subsequent call with the same key
# returns the existing task id instead of duplicating.
hermes kanban create "nightly ops review" \
    --assignee ops \
    --idempotency-key "nightly-ops-$(date -u +%Y-%m-%d)" \
    --json

افعال انبوه CLI

همهٔ افعال چرخهٔ حیات چند شناسه می‌پذیرند تا batch را در یک فرمان پاکسازی کنید:

bash
hermes kanban complete t_abc t_def t_hij --result "batch wrap"
hermes kanban archive  t_abc t_def t_hij
hermes kanban unblock  t_abc t_def
hermes kanban block    t_abc "need input" --ids t_def t_hij
📌 task رفع‌بلاک‌شده کجا می‌نشیند

‏unblock فاز مبدأ امن را بازیابی می‌کند: review برای کارهای برخاسته-از-بازبین که والدینشان کامل‌اند، ready برای کارهای پیاده‌سازی که والدینشان کامل‌اند، یا todo وقتی هنوز والدی باز است. یک task ‏todo اثبات فاز-مبدأ خودش را نگه می‌دارد و وقتی گیتی وابستگی پاک شد خودکار به ‏review یا ready برمی‌گردد. ‏unblock هرگز مستقیم به ‏triage مسیریابی نمی‌کند.

اگر taskی را unblock کردید و بعداً در triage ظاهر شد، unblock نیست که آنجا برده. یک بلاک-مجدد به همان دلیل بعدی چنین کرده: بعد از اینکه task ‏blocked ← unblocked ← re-blocked برای همان علت به تعداد ‏BLOCK_RECURRENCE_LIMIT بار ‏(پیش‌فرض ‏۲) شود، مدارشکن حلقهٔ unblock دیگر آن را به ‏blocked نفرستاده — جایی که یک cron مدام unblock‌اش می‌کرد — و برای تصمیم انسانی به ‏triage مسیریابی می‌کند. این یک محافظ DB قطعی است نه قضاوت LLM و متن بدنهٔ task نمی‌تواند از آن معاف شود: شمارندهٔ تکرار عمداً از هر unblock جان می‌برد ‏(فقط با complete موفق ریست می‌شود). برای نگه‌داشتن task رفع‌بلاک‌شده در pool کار، قبل از unblock «چرا مدام دوباره بلاک می‌شود» را حل کنید ‏(والد ناتمام، ورودی غایب، قابلیت برآورده‌نشده) یا اگر حلقه انتظار می‌رود ‏BLOCK_RECURRENCE_LIMIT را بالا ببرید.

۷ نحوهٔ تعامل worker ها با تخته

‏Worker ها به ‏hermes kanban شل نمی‌زنند. وقتی dispatcher worker را spawn می‌کند مقدار ‏HERMES_KANBAN_TASK=t_abcd را در env فرزند ست می‌کند و آن متغیر یک تول‌ست اختصاصی kanban را در schema مدل روشن می‌کند. همان تول‌ست برای پروفایل‌های ارکستراتوری که ‏kanban را در پیکربندی تول‌ست‌هایشان فعال کرده‌اند هم موجود است. این ابزارها مثل CLI مستقیماً از طریق لایهٔ پایتونی ‏kanban_db تخته را می‌خوانند و تغییر می‌دهند. یک worker در حال اجرا این‌ها را مثل هر ابزار دیگری صدا می‌زند؛ هرگز CLI ‏hermes kanban را نه می‌بیند نه لازم دارد.

ابزارهای «‹ارکستراتورها›» — ‏kanban_list، ‏kanban_create، ‏kanban_link، ‏kanban_unblock و ‏kanban_comment روی task های خارجی — از طریق همان تول‌ست در دسترس‌اند؛ قاعدهٔ غیررسمی ‏(رمزگذاری‌شده در راهنمای کانبانِ خودکار-تزریق‌شده) این است که پروفایل‌های worker fan-out نمی‌کنند یا کار نامرتبط را مسیریابی نمی‌کنند و پروفایل‌های ارکستراتور کارِ پیاده‌سازی اجرا نمی‌کنند. worker های spawn‌شده توسط dispatcher برای عملیات چرخه-حیات مخرب همچنان task-scoped هستند و نمی‌توانند task های نامرتبط را تغییر دهند.

چرا ابزار به‌جای شل‌زدن به ‏hermes kanban

سه دلیل:

  1. قابلیت حمل بک‌اند. worker هایی که ابزار ترمینالشان به بک‌اند راه‌دور اشاره می‌کند ‏(Docker/Modal/Singularity/SSH) ‏hermes kanban complete را داخل کانتینر اجرا می‌کردند، جایی که hermes نصب نیست و ‏~/.hermes/kanban.db مانت نشده. ابزارهای کانبان در پروسهٔ Python خود ایجنت اجرا می‌شوند و فارغ از بک‌اند ترمینال همیشه به ‏~/.hermes/kanban.db می‌رسند.
  2. بدون شکنندگی quoting شل. پاس‌دادن ‏--metadata '{"files": [...]}' از میان shlex + argparse تلهٔ پنهانی است. آرگومان‌های ساختاریافته ابزار کلاً از آن می‌گذرند.
  3. خطاهای بهتر. نتایج ابزار JSON ساختاریافته‌ای است که مدل می‌تواند درباره‌اش استدلال کند نه رشته stderr که باید parse کند.

صفر ردپای schema روی نشست‌های عادی. یک نشست عادی ‏hermes chat مگر پروفایل فعال صریحاً تول‌ست ‏kanban را برای کار ارکستراسیون فعال کند هیچ ابزار ‏kanban_* در schema ندارد. worker های task‌ایِ spawn‌شده-توسط-dispatcher چون ‏HERMES_KANBAN_TASK ست است ابزارهای task-scoped می‌گیرند؛ پروفایل‌های ارکستراتور سطح مسیریابی پهن‌تر را از طریق config می‌گیرند. بدون تورم ابزار برای کاربرانی که هرگز به کانبان دست نمی‌زنند.

راهنمای کانبانِ خودکار-تزریق‌شده به مدل یاد می‌دهد کدام ابزار را کِی و به چه ترتیبی صدا بزند.

شواهد handoff توصیه‌شده

‏kanban_complete(summary=..., metadata={...}) عمداً منعطف است: summary بستنِ خوانا-برای-انسان است و metadata handoff ماشین‌خوانی که ایجنت‌های پایین‌دستی، بازبین‌ها یا داشبوردها می‌توانند بدون خراشیدن نثر بازمصرفش کنند.

برای task های مهندسی و بازبینی، این شکل اختیاری metadata را ترجیح دهید:

json
{
  "changed_files": ["path/to/file.py"],
  "verification": ["pytest tests/hermes_cli/test_kanban_db.py -q"],
  "dependencies": ["parent task id or external issue, if any"],
  "blocked_reason": null,
  "retry_notes": "what failed before, if this was a retry",
  "residual_risk": ["what was not tested or still needs human review"]
}

این کلیدها قاعده‌اند نه الزام schema. خاصیت مفید این است که هر worker به‌اندازه‌ای شواهد بگذارد که خواننده بعدی چهار سؤال را سریع جواب دهد:

  1. چه چیزی تغییر کرد؟
  2. چطور اعتبارسنجی شد؟
  3. اگر شکست بخورد چه چیزی می‌تواند unblock یا retry‌اش کند؟
  4. چه ریسکی هنوز عمداً باز مانده؟

‏رمزها، لاگ خام، توکن‌ها، مواد OAuth و رونویسی‌های نامرتبط را داخل metadata نگذارید. به‌جایش pointer و خلاصه ذخیره کنید. اگر taskی فایل یا تستی ندارد، صریحاً در summary بگویید و metadata را برای شواهدی که هست به کار ببرید مثل URL های مبدأ، شناسه‌های issue یا گام‌های بازبینی دستی.

چرخهٔ حیات worker

هر پروفایلی که کارِ کانبانی می‌کند خودکار چرخهٔ حیات worker را می‌گیرد — هنگام spawn داخل پرامپت سیستمی worker تزریق می‌شود ‏(بلوک ‏KANBAN_GUIDANCE)، پس هیچ چیزی برای نصب یا پیکربندی نیست. چرخهٔ حیات کامل را به worker در فراخوانی‌های ابزار یاد می‌دهد نه فرمان‌های CLI:

  1. هنگام spawn ‏kanban_show() را صدا بزن تا عنوان + بدنه + handoff های والد + تلاش‌های قبلی + کل رشتهٔ کامنت را بخوانی.
  2. ‏cd $HERMES_KANBAN_WORKSPACE ‏(از طریق ابزار terminal) و کار را آنجا انجام بده.
  3. در عملیات‌های طولانی هر چند دقیقه ‏kanban_heartbeat(note="...") را صدا بزن. اگر کارت ممکن است بیش از ۱ ساعت طول بکشد دست‌کم ساعتی یک‌بار ‏kanban_heartbeat بزن — dispatcher task هایی که از ‏kanban.dispatch_stale_timeout_seconds ‏(پیش‌فرض ۴ ساعت) گذشته و در ساعت اخیر ضربانی نداشته‌اند را پس می‌گیرد با این فرض که worker بدون پاکسازی کرش کرده. reclaim بی‌آزار است ‏(task بدون تیک شمارندهٔ شکست به ready برای dispatch مجدد برمی‌گردد) ولی پیشرفت اجرای فعلی‌ات را از دست می‌دهی.
  4. با ‏kanban_complete(summary="...", metadata={...}) تمام کن، یا اگر گیر کردی ‏kanban_block(reason="...").

همان فراخوانی نهایی ‏kanban_complete/kanban_block جزء پروتکل worker است. اگر پروسهٔ worker با وضعیت ۰ خارج شود در حالی که task هنوز ‏running است، dispatcher آن را نقض پروتکل تلقی و رویداد ‏protocol_violation صادر می‌کند.

پیشگیری سمت-ایجنت: قبل از خروج worker، هرمس وقتی تشخیص دهد مدل در آستانهٔ توقف بدون فراخوانی ابزار پایانیِ board است تا دو سرکش مصنوعی تزریق می‌کند. این حالت رایج را می‌گیرد که مدل گام بعد را روایت می‌کند ‏(«Let me write the report») و با ‏finish_reason=stop می‌ایستد. سرکش مدل را یادآوری می‌کند فوراً ‏kanban_complete یا ‏kanban_block را صدا بزند. این محافظ فقط برای worker های spawn‌شده-توسط-dispatcher فعال است ‏(HERMES_KANBAN_TASK ست است) و با ‏HERMES_KANBAN_STOP_NUDGE=0 خاموش می‌شود.

بازیابی سمت-dispatcher: اگر سرکش‌ها تمام شده یا worker قبل از رسیدن به سرکش کرش کرده باشد، dispatcher به نقض پروتکل retry محدود می‌دهد ‏(تا ‏_PROTOCOL_VIOLATION_FAILURE_LIMIT نقض متوالی، پیش‌فرض ۳) قبل از اینکه به‌جای respawn کردنش به همان حلقه، task را خودکار بلاک کند. بودجه فقط نقض‌های خروج-تمیزِ متوالی را می‌شمارد — requeue های rate-limit‌شدهٔ درمیانی خنثی‌اند و هر نوع شکست دیگر streak را ریست می‌کند — و ‏max_retries به‌ازای-task روی حد غلبه می‌کند. این معمولاً یعنی مدل یک جواب plain-text نوشته و بدون استفاده از سطح ابزار کانبان خارج شده است.

چرخهٔ حیات به‌اضافهٔ جزئیات مرجع بار-بر ‏(انواع workspace، آرتیفکت‌های deliverable، گرفتن کارت‌های ساخته‌شده) در همان بلوک پرامپت-سیستمی عرضه می‌شود، پس هر worker فارغ از پروفایلی که زیرش اجرا می‌شود آنها را دارد — بدون setup مهارت به‌ازای-پروفایل.

Pin کردن مهارت‌های اضافی به یک task مشخص

گاهی یک task تنها به زمینهٔ متخصصی نیاز دارد که پروفایل assignee به‌طور پیش‌فرض حمل نمی‌کند — کار ترجمه‌ای که مهارت ‏translation می‌خواهد، task بازبینی که ‏github-code-review می‌خواهد، audit امنیتی که ‏security-pr-audit می‌خواهد. به‌جای هر بار ویرایش پروفایل assignee، مهارت‌ها را مستقیم به task الصاق کنید.

از یک ایجنت ارکستراتور ‏(حالت رایج — یک ایجنت کار را به دیگری مسیریابی می‌کند) آرایهٔ ‏skills ابزار ‏kanban_create را استفاده کنید:

text
kanban_create(
    title="translate README to Japanese",
    assignee="linguist",
    skills=["translation"],
)

kanban_create(
    title="audit auth flow",
    assignee="reviewer",
    skills=["security-pr-audit", "github-code-review"],
)

از یک انسان ‏(CLI / فرمان اسلش) برای هرکدام ‏--skill را تکرار کنید:

bash
hermes kanban create "translate README to Japanese" \
    --assignee linguist \
    --skill translation

hermes kanban create "audit auth flow" \
    --assignee reviewer \
    --skill security-pr-audit \
    --skill github-code-review

از داشبورد مهارت‌ها را با کاما داخل فیلد skills دیالوگ ساخت task تایپ کنید.

‏dispatcher به‌ازای هر مهارت فهرست‌شده یک فلگ ‏--skills <name> صادر می‌کند، پس worker با همهٔ آنها لود‌شده روی راهنمای کانبانِ خودکار-تزریق‌شده spawn می‌شود. نام مهارت‌ها باید با مهارت‌هایی که واقعاً روی پروفایل assignee نصب‌اند بخواند ‏(‏hermes skills list را بزنید تا ببینید چه هست)؛ نصب runtime وجود ندارد.

override مدل به‌ازای-task

worker یک task را به مدل مشخصی ‏(و اختیاراً ارائه‌دهنده) قفل کنید، مستقل از پیش‌فرض پروفایل assignee:

bash
# At creation
hermes kanban create "hard refactor" --assignee coder \
    --model claude-opus-4.6 --provider anthropic

# Or later — takes effect on the next dispatch
hermes kanban set-model t_abcd claude-opus-4.6 --provider anthropic
hermes kanban set-model t_abcd none    # clear the override

‏dispatcher worker را با مدل pinned spawn می‌کند ‏(‏--provider <name> وقتی ست شده پاس می‌شود؛ ‏--provider مدل می‌خواهد). کشویی مدل به‌ازای-task در داشبورد همان فیلد ‏model_override را می‌رانند. بدون override، worker از مدل پیکربندی‌شدهٔ پروفایلش استفاده می‌کند.

استراتژی هزینه: ارکستراتور frontier، worker های ارزان

پیکربندی‌های به‌ازای-پروفایل کانبان تفکیک هزینهٔ planner/worker را طبیعی می‌کند. تجزیهٔ یک پروژه به کارت‌های خوش-دامنه قضاوت سطح-frontier می‌خواهد؛ اجرای کارتی که از قبل هدف، زمینه و شواهد handoff روشنی حمل می‌کند معمولاً نه — و worker ها جایی‌اند که اکثریت قاطع توکن خرج می‌شود، پس مدل worker جایی است که هزینه زندگی می‌کند. پروفایل ارکستراتور/dispatcher خود را روی مدل frontier اجرا و پروفایل‌های worker را به مدل‌های ارزان اشاره دهید. هر پروفایل config.yaml خودش را زیر ‏~/.hermes/profiles/<name>/ دارد و dispatcher هنگام spawn ‏hermes -p <assignee> مقدار ‏HERMES_HOME scoped-به-پروفایل را تزریق می‌کند، پس هر worker تنظیمات مدل پروفایل خودش را می‌خواند:

yaml
# ~/.hermes/config.yaml (orchestrator / dispatcher profile)
model:
  default: "your-frontier-model"

# ~/.hermes/profiles/coder/config.yaml (worker profile)
model:
  default: "your-inexpensive-model"

# ~/.hermes/profiles/researcher/config.yaml (another worker profile)
model:
  default: "your-inexpensive-model"

برای کارت‌های گاه‌به‌گاهِ حساس-به-کیفیت فقط همان task را با override مدل به‌ازای-task به مدلی قوی‌تر pin کنید ‏(--model/--provider هنگام ساخت، ‏hermes kanban set-model بعداً، یا کشویی مدل داشبورد) — بدون ویرایش پروفایل.

هوک‌های افزونهٔ چرخهٔ حیات

جابه‌جایی‌های board هوک‌های افزونه شلیک می‌کنند: ‏kanban_task_claimed، ‏kanban_task_completed و ‏kanban_task_blocked، هرکدام حامل ‏task_id و ‏profile_name. هوک‌ها بعد از commit شدن تغییر DB مربوط به board شلیک می‌شوند، پس callback ها همیشه وضعیت ماندگار را می‌بینند. تقسیم پروسه را توجه کنید: ‏kanban_task_claimed در پروسهٔ dispatcher شلیک می‌شود در حالی که ‏completed/blocked در پروسهٔ worker شلیک می‌شوند — برای مشاهدهٔ مرکزی هر جابه‌جایی، هوک را در پروفایل dispatcher ثبت کنید.

python
def register(ctx):
    def on_blocked(task_id=None, profile_name=None, **kw):
        ctx.dispatch_tool("terminal", {"command": f"notify-send 'kanban blocked: {task_id}'"})
    ctx.register_hook("kanban_task_blocked", on_blocked)

کارت‌های حالت-هدف ‏(--goal)

پیش‌فرض هر worker یک شانس برای کارتش دارد — کار را انجام بده، ‏kanban_complete/kanban_block را صدا بزن، خارج شو. ‏--goal ‏(CLI) یا ‏goal_mode=True ‏(ابزار ‏kanban_create / داشبورد) را بدهید تا به‌جایش آن worker در یک حلقهٔ هدف اجرا شود، همان موتور سبک-Ralph پشت فرمان اسلش ‏/goal: بعد از هر نوبت یک قاضی کمکی خروجی worker را با عنوان + بدنهٔ کارت ‏(به‌عنوان معیارهای پذیرش) مقایسه می‌کند و اگر کار تمام نشده — و بودجهٔ نوبت باقی است — worker در همان نشست ادامه می‌دهد تا قاضی موافقت کند، خود worker task را پایان دهد، یا بودجه تمام شود ‏(که کارت را به‌جای خروج بی‌صدا برای بازبینی انسانی بلاک می‌کند).

bash
hermes kanban create "Translate the docs site to French" \
    --body "Acceptance: every page translated, no English left, links intact." \
    --assignee linguist \
    --goal \
    --goal-max-turns 15      # optional; default 20

برای کارت‌های باز، چندمرحله‌ای یا «ادامه بده تا X درست شود» استفاده‌اش کنید. برای کارهای one-shot ارزان ردش کنید — overhead قاضی به‌ازای-نوبت نمی‌ارزد و retry/مدارشکن موجود dispatcher شکست‌های گذرای worker را همین الان هندل می‌کند. قاضی فقط به خوبی متن هدف شماست، پس بدنه را به‌صورت معیارهای پذیرش صریح بنویسید.

📌 کارت‌های حالت-هدف موتور ‎/goal را قرض می‌گیرند — به آن وصله نمی‌شوند

‏--goal حلقهٔ ادامه را داخل نشست worker همان یک کارت اجرا می‌کند. موتور را با فرمان اسلش ‏[/goal] ‏(goals) شریک می‌کند نه وضعیت را: ست کردن یک ‏/goal در نشست چت هرگز کارت کانبانی نمی‌سازد، نمی‌گیرد یا جابه‌جا نمی‌کند و حلقهٔ کارت حالت-هدف برای ‏/goal status هیچ نشست چتی نامرئی است. اگر می‌خواهید این گفتگو به تکرار ادامه دهد از [/goal] استفاده کنید؛ اگر کار روی تخته می‌خواهید کارت بسازید.

رفتار ارکستراتور

ارکستراتور خوش‌رفتار خودش کار را انجام نمی‌دهد. هدف کاربر را به task ها تجزیه، لینک، هرکدام را به یکی از پروفایل‌هایی که راه انداخته‌اید assign و عقب می‌نشیند. راهنمای ارکستراتور — قواعد ضدوسوسه، پرامپت Step-0 کشف-پروفایل ‏(dispatcher روی نام‌های assignee ناشناخته بی‌صدا شکست می‌خورد، پس ارکستراتور باید هر کارت را در پروفایل‌هایی که واقعاً روی ماشینتان وجود دارند زمین‌گیری کند) و کتاب بازی تجزیه کلید‌خورده روی ‏kanban_create/kanban_link/kanban_comment — خودکار داخل پرامپت سیستمی worker تزریق می‌شود؛ چیزی برای نصب نیست.

یک نوبت مرجع ارکستراتور ‏(دو محقق موازی که به نویسنده handoff می‌دهند):

text
# Goal from user: "draft a launch post on the ICP funding landscape"
kanban_create(title="research ICP funding, NA angle",  assignee="researcher-a", body="…")  # → t_r1
kanban_create(title="research ICP funding, EU angle",  assignee="researcher-b", body="…")  # → t_r2
kanban_create(
    title="synthesize ICP funding research into launch post draft",
    assignee="writer",
    parents=["t_r1", "t_r2"],        # promoted to 'ready' when both researchers complete
    body="one-pager, neutral tone, cite sources inline",
)                                     # → t_w1
# Optional: add cross-cutting deps discovered later without re-creating tasks
kanban_link(parent_id="t_r1", child_id="t_followup")
kanban_complete(
    summary="decomposed into 2 parallel research tasks → 1 synthesis task; writer starts when both researchers finish",
)

راهنمای ارکستراتور خودکار در پرامپت سیستمی worker عرضه می‌شود — هیچ چیزی برای نصب یا sync به‌ازای-پروفایل نیست.

قبل از fan-out تصمیم بگیرید. تصمیم‌های طراحی مال ارکستراتورند نه worker ها. اگر دو کارت موازی هرکدام باید همان یک چیز را انتخاب کنند — طرح نام‌گذاری، schema، فرمت فایل، شکل API — ارکستراتور یک‌بار تصمیم می‌گیرد و آن را داخل بدنهٔ هر دو کارت مهر می‌زند. worker ها کارت‌های خواهر را نمی‌بینند، پس بدنهٔ هر کارت فرزند باید هر تصمیمی که به آن وابسته است را حمل کند. مثال: برای کارت‌های موازی «build the exporter» و «build the importer» نگذارید هر worker فرمت فایل خودش را اختراع کند — از بالا یکی انتخاب کنید ‏(مثلاً JSON جداشده-با-خط‌جدید با فیلد version) و در هر دو بدنه بنویسید، وگرنه دو نیمه هرگز round-trip نخواهند شد.

برای بهترین نتیجه آن را با پروفایلی جفت کنید که تول‌ست‌هایش به عملیات board محدود شده ‏(kanban، ‏gateway، ‏memory) تا ارکستراتور حتی اگر تلاش کند واقعاً نتواند task پیاده‌سازی اجرا کند.

۸ داشبورد ‏(GUI)

‏CLI و فرمان اسلش ‏/kanban برای اجرای headless تخته کافی‌اند ولی تختهٔ بصری غالباً رابط درست برای انسان‌های-در-حلقه است: triage، سرپرستی بین-پروفایلی، خواندن رشته‌های کامنت و کشیدن کارت‌ها بین ستون‌ها. هرمس این را به‌عنوان یک افزونهٔ همراه‌بستهٔ داشبورد در ‏plugins/kanban/ عرضه می‌کند — نه قابلیت هسته، نه سرویس جداگانه — مطابق مدلی که در توسعه داشبورد ترسیم شده.

باز کردنش:

bash
hermes kanban init      # one-time: create kanban.db if not already present
hermes dashboard        # "Kanban" tab appears in the nav, after "Skills"

افزونه چه چیزی به شما می‌دهد

  • تب Kanban با یک ستون به‌ازای هر وضعیت: ‏triage، ‏todo، ‏ready، ‏running، ‏blocked، ‏done ‏(+ ‏archived وقتی toggle روشن است).
    • ‏triage ستون پارک ایده‌های خام است. پیش‌فرض ‏(kanban.auto_decompose: true)، dispatcher خودکار تجزیه‌گر را روی task هایی که اینجا می‌نشینند اجرا می‌کند. تجزیه‌گر داخلی مسیر مدل ‏auxiliary.kanban_decomposer را استفاده، فهرست پروفایل‌های شما ‏(با توضیحات) را می‌خواند و task را به یک گراف کوچک از کارت‌های فرزندِ مسیریابی‌شده-به-بهترین-متخصص fan-out می‌کند. task اصلی به‌عنوان والد هر فرزند زنده می‌ماند تا assignee‌اش ‏(kanban.orchestrator_profile یا پروفایل پیش‌فرض فعال وقتی unset است) وقتی همه تمام شد بیدار شود و تکمیل را قضاوت کند. قرص Orchestration: Auto/Manual بالای صفحه ‏(زمردی = Auto، خاکستری بی‌رنگ = Manual) را برگردانید یا مستقیم config.yaml را ویرایش کنید. هر دو حالت با ‏hermes kanban specify همزیستی دارند — آن همچنان به‌عنوان بازنویسی spec تک-task وقتی fan-out نمی‌خواهید موجود است.
  • کارت‌ها شناسهٔ task، عنوان، badge اولویت، تگ tenant، پروفایل assign شده، شمارش کامنت/لینک، قرص پیشرفت ‏(N/M فرزند انجام‌شده وقتی task وابسته دارد) و «ساخته‌شده N قبل» را نشان می‌دهند. چک‌باکس به‌ازای هر کارت چندانتخابی را ممکن می‌کند.
  • لاین‌های به‌ازای-پروفایل داخل Running — چک‌باکس نوار ابزار زیرگروه‌بندی ستون Running بر اساس assignee را toggle می‌کند.
  • به‌روزرسانی زنده از طریق WebSocket — افزونه جدول الحاقیِ task_events را روی interval پول کوتاه دنبال می‌کند؛ تخته لحظهٔ اقدام هر پروفایل ‏(CLI، گیت‌وی یا تب دیگرِ داشبورد) تغییرات را بازتاب می‌دهد. reload ها debounce می‌شوند تا رگبار رویداد فقط یک refetch تریگر کند.
  • Drag-drop کارت‌ها بین ستون‌ها برای تغییر وضعیت. drop مقدار ‏PATCH /api/plugins/kanban/tasks/:id را می‌فرستد که از همان کد ‏kanban_db مربوط به CLI عبور می‌کند — سه سطح هرگز واگرا نمی‌یابند. جابه‌جایی به وضعیت‌های مخرب ‏(done، ‏archived، ‏blocked) تأیید می‌گیرد. دستگاه‌های لمسی fallback مبتنی-بر-pointer دارند تا تخته از تبلت هم قابل استفاده باشد.
  • دیالوگ ساخت task — روی + هر سربرگ ستون کلیک کنید تا modal با فیلدهای برچسب‌دار باز شود: عنوان، assignee، اولویت، مهارت‌ها، نوع/مسیر workspace ‏(seed‌شده از پوشهٔ پروژه board؛ override به‌ازای-task)، حالت هدف و ‏(اختیاری) task والد از کشویی روی همهٔ task های موجود. Enter برای ساخت، Shift+Enter برای خط جدید در فیلد عنوان، Escape برای لغو. ساخت از ستون Triage خودکار task جدید را در triage پارک می‌کند.
  • چندانتخاب با اکشن‌های انبوه — shift/ctrl-click روی کارت یا تیک چک‌باکسش آن را به انتخاب اضافه می‌کند. نوار اکشن انبوه بالای صفحه ظاهر می‌شود با جابه‌جایی وضعیت گروهی، آرشیو و reassign ‏(از کشویی پروفایل یا «(unassign)»). batch های مخرب اول تأیید می‌گیرند. شکست‌های جزئی per-id بدون قطع بقیه گزارش می‌شوند.
  • کلیک روی کارت ‏(بدون shift/ctrl) drawer کناری باز می‌کند ‏(Escape یا کلیک-بیرون می‌بندد) با:
    • عنوان قابل‌ویرایش — روی heading کلیک کنید تا rename شود.
    • assignee / اولویت قابل‌ویرایش — روی ردیف متا کلیک کنید تا بازنویسی شود.
    • توضیح قابل‌ویرایش — پیش‌فرض markdown-رندر ‏(تیتر، ضخیم، ایتالیک، کد درون‌خطی، بلوک کد محصور، لینک‌های http(s)/mailto، فهرست گلوله‌ای) با دکمهٔ «edit» که textarea عوض می‌کند. رندر مارک‌داون یک renderer کوچک XSS-safe است — هر جانشینی روی ورودی HTML-escape اجرا می‌شود، فقط لینک‌های http(s)/mailto عبور می‌کنند و همیشه ‏target="_blank" + ‏rel="noopener noreferrer" ست می‌شود.
    • ویرایشگر وابستگی — فهرست چیپ والدین و فرزندان هرکدام با × برای unlink، به‌اضافهٔ کشویی روی همهٔ task های دیگر برای افزودن والد یا فرزند جدید. تلاش‌های چرخه سمت سرور با پیام واضح رد می‌شوند.
    • ردیف اکشن وضعیت ‏(→ triage / → ready / → running / block / unblock / complete / archive) با پرامپت تأیید برای جابه‌جایی‌های مخرب. برای کارت‌های ستون Triage دو اکشن LLM-محور هم دارد: ⚗ Decompose که task را به گرافی از task های فرزند مسیریابی‌شده-به-پروفایل‌های متخصص بر اساس توضیح fan-out می‌کند و ✨ Specify که یک بازنویسی spec تک-task انجام می‌دهد. Decompose وقتی LLM تشخیص دهد task از fan-out سود نمی‌برد به ارتقای سبک-spec برمی‌گردد، پس ابرمجموعهٔ سخت‌گیرانه است. هر دو از CLI ‏(hermes kanban decompose <id>/specify <id>/--all)، از هر پلتفرم گیت‌وی ‏(/kanban decompose <id>) و programmatik از طریق ‏POST /api/plugins/kanban/tasks/:id/decompose و ‏…/specify در دسترس‌اند. مدل‌ها را زیر ‏auxiliary.kanban_decomposer و ‏auxiliary.triage_specifier در config.yaml پیکربندی کنید.
    • بخش نتیجه ‏(هم markdown-رندر)، رشتهٔ کامنت با Enter-to-submit و ۲۰ رویداد آخر.
  • فیلترهای نوار ابزار — جست‌وجوی متن آزاد، کشویی tenant ‏(پیش‌فرض از ‏dashboard.kanban.default_tenant)، کشویی assignee، toggle «show archived»، toggle «lanes by profile» و دکمهٔ Nudge dispatcher تا لازم نباشد منتظر تیک ۶۰ ثانیه بعدی بمانید.

از نظر بصری هدف، چیدمان آشنای Linear/Fusion است: تم تیره، سربرگ ستون با شمارنده‌ها، نقاط وضعیت رنگی، قرص‌های chip برای اولویت و tenant. افزونه فقط CSS var های تم را می‌خواند ‏(--color-*، --radius، --font-mono و...)، پس با هر تم فعال داشبورد خودکار reskin می‌شود.

Auto در برابر Manual ارکستراسیون

تخته کانبان دو راه برای هندل کردن taskی که داخل ستون Triage می‌اندازید دارد:

Auto ‏(پیش‌فرض) — ‏kanban.auto_decompose: true. dispatcher جاسازی‌شده-در-گیت‌وی در هر تیک تجزیه‌گر را اجرا می‌کند، محدود به ‏kanban.auto_decompose_per_tick ‏(پیش‌فرض ۳ task در هر تیک) تا بار انبوه task های triage باعث خرج انفجاری LLM کمکی نشود. تجزیه‌گر پرامپت تجزیه داخلی + مسیر مدل ‏auxiliary.kanban_decomposer را استفاده، پروفایل‌های نصب‌شده + توضیحاتشان را می‌خواند و از LLM می‌خواهد گراف JSON task تولید کند: کدام task ها spawn شوند، به چه کسی بروند و کدام به کدام وابسته‌اند. task اصلی triage والد هر برگ گراف می‌شود، پس تا کامل شدن کل گراف زنده می‌ماند — و سپس به ‏ready برمی‌گردد تا assignee‌اش ‏(kanban.orchestrator_profile یا پروفایل پیش‌فرض فعال) تکمیل را قضاوت و اگر کار تمام نیست task بیشتری اضافه کند. این جریانِ «یک خط بینداز و برو» است.

Manual — ‏kanban.auto_decompose: false. task های triage تا اقدام شما در triage می‌مانند. دکمهٔ ⚗ Decompose روی کارت را کلیک، ‏hermes kanban decompose <id> ‏(یا ‏--all) را اجرا یا از چت ‏/kanban decompose <id> را بزنید. این رفتار قبل-از-تجزیه‌گر تخته را مطابقت می‌دهد؛ وقتی کنترل کامل دارید که چه چیزی کِی اجرا شود مفید است.

مرز مهم: حالت Manual فقط تجزیه‌گر داخلی Triage را غیرفعال می‌کند. مانع ‏kanban_create توسط پروفایل نمی‌شود و بیدارشدن‌های نشست-سازنده را هم خاموش نمی‌کند. با ‏kanban.auto_subscribe_on_create: true، رویداد پایانی task ایجنت مبدأ را با یک نوبت وضعیت مصنوعی ازسر می‌گیرد تا handoff را بازرسی و تصمیم بگیرد آیا کار پیگیریِ واقعاً جدیدی لازم است. وقتی تکمیل باید منفعل بماند ‏auto_subscribe_on_create: false کنید. برای provenance، فرزندان تجزیه‌گر داخلی ‏created_by=auto-decomposer دارند؛ task های ساخته‌شده توسط پروفایل ازسرگرفته‌شده نام همان پروفایل را حمل می‌کنند.

جابه‌جایی بین دو حالت از قرص Orchestration: Auto/Manual بالای صفحه کانبان ‏(زمردی = Auto، خاکستری بی‌رنگ = Manual)، یا ویرایش مستقیم config.yaml. هر دو حالت با ‏hermes kanban specify همزیستی دارند — همچنان به‌عنوان بازنویسی spec تک-task موجود است.

تصمیم‌های مسیریابی تجزیه‌گر به توضیحات پروفایل وابسته است که primitive برچسب‌گذاری به‌ازای-پروفایلی است با ‏hermes profile create --description "..."، ‏hermes profile describe <name> --text "..."، ‏hermes profile describe <name> --auto ‏(LLM از مهارت‌ها + مدل نصب‌شدهٔ پروفایل تولید می‌کند) یا ویرایشگر به‌ازای-پروفایل داشبورد داخل پنل گستردهٔ Orchestration settings. پروفایل‌های بدون توضیح همچنان در فهرست می‌آیند — با نام قابل مسیریابی‌اند فقط دقیق‌تر نیستند. تجزیه‌گر هرگز فرزندی با ‏assignee=None زمین نمی‌زند: وقتی LLM پروفایل ناشناخته‌ای انتخاب کند فرزند به ‏kanban.default_assignee ‏(یا پروفایل پیش‌فرض فعال اگر unset باشد) مسیریابی می‌شود.

‏kanban.orchestrator_profile پرامپت، مهارت‌ها یا منطق سفارشی آن پروفایل را داخل فراخوانی تجزیه لود نمی‌کند. تعیین می‌کند بعد از fan-out چه کسی مالک task ریشه/ارکستراسیون است. برای تغییر مدل/ارائه‌دهندهٔ تجزیه‌گر ‏auxiliary.kanban_decomposer را پیکربندی کنید. برای استفاده از منطق تقسیم-کارِ سفارشی یک پروفایل به‌جای تجزیه‌گر داخلی، به Manual سوئیچ کنید و بگذارید آن پروفایل صریحاً task بسازد یا تجزیه کند.

مدل امنیت

middleware احراز HTTP داشبورد صریحاً از ‏/api/plugins/ می‌گذرد — مسیرهای افزونه عمداً بدون احراز هستند چون داشبورد پیش‌فرض به localhost بایند می‌شود. یعنی سطح REST کانبان از هر پروسه‌ای روی میزبان قابل‌رسید است.

WebSocket یک گام اضافی برمی‌دارد: توکن نشست گذرا داشبورد را به‌عنوان پارامتر query ‏?token=… می‌خواهد ‏(مرورگرها روی درخواست upgrade نمی‌توانند Authorization ست کنند)، مطابق الگوی پل PTY درون-مرورگری.

اگر ‏hermes dashboard --host 0.0.0.0 اجرا کنید هر مسیر افزونه — کانبان هم شامل — از شبکه قابل‌رسید می‌شود. روی میزبان مشترک این کار را نکنید. تخته بدنهٔ task ها، کامنت‌ها و مسیرهای workspace را دارد؛ مهاجمی که به این مسیرها برسد دسترسی خواندن به کل سطح همکاری شما می‌گیرد و می‌تواند task بسازد / reassign / archive کند.

‏task ها در ‏~/.hermes/kanban.db عمداً پروفایل-بی‌تفاوت‌اند ‏(همان primitive هماهنگی است). اگر داشبورد را با ‏hermes -p <profile> dashboard باز کنید تخته همچنان task های ساخته‌شده توسط هر پروفایل دیگر روی میزبان را نشان می‌دهد. یک کاربر همهٔ پروفایل‌ها را مالک است ولی اگر چند persona همزیستی دارند دانستنش ارزش دارد.

به‌روزرسانی‌های زنده

‏task_events جدول SQLite الحاقی با ‏id یکنواست. endpoint ‏WebSocket آخرین شناسهٔ رویداد دیده‌شده هر کلاینت را نگه و ردیف‌های جدید را به‌محض فرود push می‌کند. وقتی رگبار رویداد برسد فرانت endpoint ارزانِ تخته را reload می‌کند — ساده‌تر و درست‌تر از تلاش برای وصله‌کردن وضعیت محلی از هر نوع رویداد. حالت WAL یعنی حلقهٔ خواندن هرگز تراکنش‌های claim ‏BEGIN IMMEDIATE مربوط به dispatcher را بلاک نمی‌کند.

توسعه‌دادنش

افزونه قرارداد استاندارد افزونهٔ داشبورد هرمس را استفاده می‌کند — مرجع کامل manifest، slot های shell، slot های page-scoped و Plugin SDK را در «توسعه داشبورد» ببینید. ستون‌های اضافه، chrome سفارشی کارت، layout های فیلتر-tenant یا جایگزین‌های کامل ‏tab.override همه بدون fork کردن این افزونه بیان‌پذیرند.

غیرفعال‌کردن بدون حذف: ‏dashboard.plugins.kanban.enabled: false را به config.yaml بیفزایید ‏(یا ‏plugins/kanban/dashboard/manifest.json را حذف کنید).

مرز دامنه

‏GUI عمداً لاغر است. هرچه افزونه انجام می‌دهد از CLI قابل‌رسید است؛ افزونه فقط آن را برای انسان‌ها راحت می‌کند. auto-assignment، بودجه‌ها، گیتی‌های حاکمیتی و نماهای چارت-سازمانی در فضای-کاربر می‌مانند — یک پروفایل router، افزونهٔ دیگری، یا بازاستفاده از ‏tools/approval.py — دقیقاً طبق بخش خارج-از-دامنهٔ spec طراحی.

‏--max-retries مدارشکن به‌ازای-task برای dispatcher است. ‏--max-retries 1 task را روی اولین تلاش ناموفق بلاک می‌کند و ‏--max-retries 3 دو retry اجازه و روی شکست سوم بلاک می‌کند. حذفش کنید تا ‏kanban.failure_limit از config.yaml و بعد پیش‌فرض داخلی استفاده شود.

bash

نگهبان respawn

‏dispatcher از respawn مجدد یک task ready وقتی اجرای قبلی خطای quota/auth/429 خورده بود ‏(blocker_auth)، یا یک اجرا داخل پنجرهٔ نگهبان موفق کامل شده بود ‏(recent_success)، یا کامنت اخیر task به PR گیت‌هابی لینک می‌دهد ‏(active_pr) امتناع می‌کند. مانع طوفان‌های مکرر worker روی همان باگ یا task می‌شود تا انسان عقب برسد. ردیف ‏respawn_guarded در مرجع رویداد را ببینید.

کشیدن-به-حذف و حذف انبوه ‏(داشبورد)

داشبورد یک منطقهٔ drop سطل‌زباله روی صفحه کانبان expose می‌کند — هر کارتی را داخلش بکشید تا task حذف شود ‏(آبشاری از طریق task_events، لینک‌های فرزند و اشتراک‌ها). پرامپت تأییدی مانع تصادف است. حذف انبوه هم از طریق ‏DELETE /api/plugins/kanban/tasks با بدنهٔ JSON ‏{"ids": ["t_abc", "t_def", ...]} در دسترس است.

helper توپولوژی Kanban Swarm

‏hermes kanban swarm گراف ماندگار Kanban Swarm v1 را یک‌جا می‌سازد: یک کارت ریشه/blackboard کامل‌شده، N کارت worker موازی، یک کارت verifier گیت‌خورده-روی-همهٔ-worker ها و یک کارت synthesizer گیت‌خورده-روی-verifier. زمینهٔ مشترک swarm ‏(«blackboard») به‌صورت کامنت‌های JSON ساختاریافته روی کارت ریشه ذخیره می‌شود تا هر worker بخواندش.

bash
hermes kanban swarm "Design a multi-region failover plan" \
  --workers researcher,architect,sre \
  --verifier reviewer --synthesizer writer

گراف حاصل اتمیک commit می‌شود: dispatcher ها و خواننده‌های داشبورد یا هیچ swarm جدیدی یا توپولوژی کامل می‌بینند، هرگز گراف ریشه/worker/verifier جزئی‌لینک‌شده نه. سپس عادی dispatch می‌شود — worker ها موازی اجرا می‌شوند، verifier بعد از اتمام همه بیدار می‌شود و synthesizer بعد از اینکه verifier کار را تمیز علامت زد بیدار می‌شود.

۱۰ فرمان اسلش ‏/kanban

هر فعل ‏hermes kanban <action> به‌صورت ‏/kanban <action> هم قابل‌رسید است — از داخل نشست تعاملی ‏hermes chat و از هر پلتفرم گیت‌وی ‏(تلگرام، دیسکورد، اسلک، واتساپ، سیگنال، ماتریکس، Mattermost، ایمیل، SMS). هر دو سطح دقیقاً همان نقطهٔ ورودی ‏hermes_cli.kanban.run_slash() را صدا می‌زنند که درخت argparse مربوط به ‏hermes kanban را بازمصرف می‌کند، پس سطح آرگومان، فلگ‌ها و قالب خروجی بین CLI، ‏/kanban و ‏hermes kanban یکسان‌اند. لازم نیست برای راندن تخته چت را ترک کنید.

text
/kanban list
/kanban show t_abcd
/kanban create "write launch post" --assignee writer --parent t_research
/kanban comment t_abcd "looks good, ship it"
/kanban unblock t_abcd
/kanban dispatch --max 3
/kanban specify t_abcd                  # flesh out a triage one-liner into a real spec
/kanban specify --all --tenant engineering  # sweep every triage task in one tenant

آرگومان‌های چندواژه‌ای همانطور که روی شل quote کنید — ‏run_slash بقیهٔ خط را با ‏shlex.split parse می‌کند، پس ‏"..." و ‏'...' هر دو کار می‌کنند.

استفاده میان-اجرا: ‏/kanban از گیتی agent-در-حال-اجرا می‌گذرد

گیت‌وی معمولاً فرمان‌های اسلش و پیام‌های کاربر را وقتی ایجنت هنوز در حال فکر کردن است صف می‌کند — همان چیزی که مانع شروع اتفاقی نوبت دوم وقتی اولی در جراحی است می‌شود. ‏/kanban صریحاً از این گیت معاف است. تخته در ‏~/.hermes/kanban.db زندگی می‌کند نه در وضعیت ایجنت در حال اجرا، پس خوانده‌ها ‏(list، ‏show، ‏context، ‏tail، ‏watch، ‏stats، ‏runs) و نوشته‌ها ‏(comment، ‏unblock، ‏block، ‏assign، ‏archive، ‏create، ‏link و...) همه فوراً عبور می‌کنند حتی میان-نوبت.

این کل هدف جداسازی است:

  • workerی بلاک شد منتظر همتا ← شما از گوشی ‏/kanban unblock t_abcd می‌فرستید و dispatcher همتا را در تیک بعدی برمی‌دارد. worker بلاک‌شده قطع نمی‌شود — فقط دیگر بلاک نیست.
  • کارتی می‌بینید که زمینهٔ انسانی لازم دارد ← ‏/kanban comment t_xyz "use the 2026 schema, not 2025" روی رشتهٔ task می‌نشیند و اجراهای بعدی آن task آن را در ‏kanban_show() می‌خوانند.
  • می‌خواهید بدانید ناوگانتان چه می‌کند بدون توقف ارکستراتور ← ‏/kanban list --mine یا ‏/kanban stats تخته را بدون دست‌زدن به گفتگوی اصلی‌تان بازرسی می‌کند.

اشتراک خودکار روی ‏/kanban create ‏(فقط گیت‌وی)

وقتی از گیت‌وی با ‏/kanban create "…" task بسازید، چت مبدأ ‏(پلتفرم + شناسهٔ چت + شناسهٔ ترد) خودکار به رویدادهای پایانی آن task ‏(completed، ‏blocked، ‏gave_up، ‏crashed، ‏timed_out) مشترک می‌شود. به‌ازای هر رویداد پایانی یک پیام می‌گیرید — شامل خط اول خلاصهٔ نتیجهٔ worker روی completed — بدون polling یا یادسپاری شناسهٔ task.

text
you> /kanban create "transcribe today's podcast" --assignee transcriber
bot> Created t_9fc1a3  (ready, assignee=transcriber)
     (subscribed — you'll be notified when t_9fc1a3 completes or blocks)

… ~8 minutes later …

bot> ✓ t_9fc1a3 completed by transcriber
     transcribed 42 minutes, saved to podcast/2026-05-04.md

اشتراک‌ها از رسیدن task به ‏done جان می‌برند — تکمیل برگشت‌پذیر است ‏(بازبین یا کنترل‌گر می‌تواند task انجام‌شده را reopen کند)، پس نشست مبدأ از طریق چرخه‌های reopen به گرفتن اعلان ادامه می‌دهد. روی ‏archived ‏(وضعیت پایانی برگشت‌ناپذیر) خودحذف می‌شوند. روی board هایی که هرگز آرشیو نمی‌کنند sweep ‏GC اشتراک‌های task هایی را که ‏kanban.done_sub_retention_days روز ‏(پیش‌فرض ۳۰؛ ۰ برای خاموشی) بدون فعالیت جدید در done نشسته‌اند purge می‌کند تا ردیف‌های کهنه برای همیشه جمع نشوند. اگر create را با ‏--json اسکریپت کنید ‏(خروجی ماشینی) auto-subscribe رد می‌شود — فرض این است که فراخواننده‌های اسکریپتی می‌خواهند اشتراک‌ها را صریحاً با ‏/kanban notify-subscribe مدیریت کنند.

auto-subscribe برخاسته-از-چت در حالت ‏notify+wake ساخته می‌شود: روی رویداد پایانی ایجنت مقصد هم پیام منفعل می‌گیرد و نوبت واقعی می‌زند، پس می‌تواند زمینهٔ board را بخواند و به صدای خودش جواب دهد. «حالت‌های تحویل» پایین را ببینید.

برش خروجی در پیام‌رسانی

پلتفرم‌های گیت‌وی سقف عملی طول پیام دارند. اگر ‏/kanban list، ‏/kanban show یا ‏/kanban tail بیش از ~۳۸۰۰ کاراکتر خروجی تولید کنند پاسخ با فوتر ‏… (truncated; use \`hermes kanban …\` in your terminal for full output) بریده می‌شود. سطح CLI چنین سقفی ندارد.

Autocomplete

در CLI تعاملی تایپ ‏/kanban و زدن Tab بین فهرست زیرفرمان‌های داخلی می‌چرخد ‏(list، ‏ls، ‏show، ‏create، ‏assign، ‏link، ‏unlink، ‏claim، ‏comment، ‏complete، ‏block، ‏unblock، ‏archive، ‏tail، ‏dispatch، ‏context، ‏init، ‏gc). افعال باقی‌ماندهٔ فهرست‌شده در مرجع CLI بالا ‏(watch، ‏stats، ‏runs، ‏log، ‏assignees، ‏heartbeat، ‏notify-subscribe، ‏notify-list، ‏notify-unsubscribe، ‏daemon) هم کار می‌کنند — فقط هنوز در فهرست سرنخ autocomplete نیستند.

۱۲ تحویل زمینه به کارت‌های پیگیری (لینک والد)

لینک والد فقط گیتی زمان‌بندی نیست — کانال تحویل زمینه از کارت کامل‌شده به کارت جدید است. وقتی کارتی با ‏--parent <done-card-id> می‌سازید دو اتفاق می‌افتد:

  1. بلافاصله واجد شرایط است. ‏create_task وضعیت را بر اساس وضعیت والدی ست می‌کند: فرزندی که والدینش همه ‏done هستند مستقیماً در ‏ready ساخته می‌شود — بدون انتظار، بدون ارتقای دستی. ‏(فرزندان والدین باز در todo می‌نشینند تا ‏recompute_ready وقتی آخرین والد تمام شد ارتقایشان دهد.)
  2. handoff والد سوار می‌شود. زمینهٔ worker ساخته‌شده برای فرزند ‏(build_worker_context، همان چیزی که ‏kanban_show() برمی‌گرداند) بخشی به نام ‏## Parent task results دارد با ‏summary و ‏metadata تکمیل هر والد، عیناً:
text
## Parent task results
### t_77c26979 (completed just now)
Added exponential backoff with jitter to the retry helper.
_metadata_: `{"changed_files": ["hermes_cli/retry.py", "tests/test_retry.py"], "decisions": ["capped backoff at 60s", "jitter = full"]}`

به همین دلیل الگوی کارِ پیگیری روی کارت تمام‌شده یک کارت فرزند جدید است نه reopen کردن کارت done. کارت‌های کامل‌شده تاریخچهٔ تغییرناپذیرند — زمینه‌شان از طریق لینک والد به جلو جریان می‌یابد. بازکاری همان-کارت ‏(حلقه‌های retry روی کارت در حال شکست) مکانیزم متفاوتی است: تلاش‌های قبلی روی همان کارت به‌عنوان «prior attempts» در زمینهٔ خودِ همان کارت surface می‌شوند.

worktree یا branch به‌تنهایی جایگزین نیست: وضعیت repo به worker پیگیری می‌گوید کد چه شکلی است ولی نه چرا — تصمیم‌ها، تست‌های اجراشده و فایل‌های دست‌خورده در handoff ساختاریافته والد زندگی می‌کنند نه در گیت. شاهدی که موقع تکمیل والد وجود نداشت ‏(مثلاً لاگ CI که بعداً شکست خورد) جای‌اش بدنهٔ کارت جدید است.

bash
# Implementation card t_impl is done. CI fails two hours later.
hermes kanban create "Fix CI failure from t_impl: test_retry flakes on 3.11" \
    --assignee coder \
    --parent t_impl \
    --body "$(cat <<'EOF'
CI run #4812 failed after t_impl merged.
Log excerpt: FAILED tests/test_retry.py::test_backoff_jitter - TimeoutError
Acceptance: tests/test_retry.py green on 3.11 and 3.12 in CI.
Use a fresh worktree/branch; do not force-push the original branch.
EOF
)"

worker اصلاح با summary و metadata کارت اصلی ‏(فایل‌های تغییر یافته، تصمیم‌ها) از قبل در زمینه spawn می‌شود به‌اضافهٔ شواهد تازه‌ای که در بدنه گذاشته‌اید.

آشتی‌دادن شاخه‌های متضاد worker ها

در خط‌لوله‌های مهندسی ‏(P1/P2 با worktree ها) شاخه‌های دو worker هنگام merge می‌توانند تداخل کنند. نگذارید هیچ‌یک از دو worker خودش داوری کند — ایجنتِ متضاد زمینهٔ همتایش را ندارد و به‌طور قابل‌اتکا سمت دیگر را overwrite یا کار خودش را رها می‌کند. به‌جایش یک کارت آشتی به یک پروفایل سومِ بی‌طرف assign کنید با هر دو کارت متضاد به‌عنوان والد لینک‌شده: لینک‌های والد خلاصه‌های تکمیل هر دو طرف را وارد زمینهٔ آشتی‌گر می‌کنند، پس هم هر دو diff و هم هر دو نیت را می‌گیرد. مهارت همراه‌بستهٔ merge-reconciler به آن worker رویهٔ کامل را می‌دهد: طبقه‌بندی هر hunk متضاد، حل منصفانه، تأیید و برگرداندن summary‌ای که هر تصمیم را نام می‌برد.

نقاط داغ برخورد در کارزارهای موازی

در کارزارهای پهن بعضی فایل‌ها آهنربای برخورد می‌شوند: خیلی worker ها هرکدام کمی به همان فایل اضافه می‌کنند، هیچ‌کس مالک کوچک‌نگه‌داشتنش نیست و تبدیل به محل دائمی conflict های merge می‌شود. mitigation یک قاعدهٔ کامنت است نه primitive جدید. worker‌ای که متوجه شود diff‌اش مدام با خواهرانش در یک فایل تداخل دارد — یا فایلی که لمس می‌کند مدام در کامنت‌های اخیر کارت‌های دیگر ظاهر می‌شود — نباید بی‌صدا روی هم بریزد. به‌جایش روی کارت خودش کامنتی با پیشوند قابل‌تشخیص می‌گذارد:

hotspot: hermes_cli/kanban_db.py — third conflicting edit to the dispatch loop this wave

و فلگ را در metadata تکمیلش تکرار می‌کند. ارکستراتورها ‏(یا انسان‌هایی که تخته را بازبینی می‌کنند) که دو یا بیشتر کامنت hotspot: نام‌برندهٔ همان مسیر ببینند باید قبل از صف‌کردن کار بیشتری که بهش دست می‌زند یک کارت اختصاصی refactor/تجزیه برای آن فایل بسازند — شکافتن فایل آهنربا ارزان‌تر از آشتی‌دادن هر برخورد آینده‌ای است که ایجاد می‌کند. برای conflict هایی که قبلاً رخ داده از الگوی کارت-آشتی بالا با مهارت merge-reconciler استفاده کنید؛ فلگ‌گذاری hotspot اصلاح بالادستی است که مانع می‌شود آشتی‌گر تبدیل به لاین دائمی شود.

۱۳ استفاده چند-مستأجری

وقتی یک ناوگان متخصص به چند کسب‌وکار خدمت می‌کند هر task را با tenant تگ کنید:

bash
hermes kanban create "monthly report" \
    --assignee researcher \
    --tenant business-a \
    --workspace dir:~/tenants/business-a/data/

‏worker ها ‏$HERMES_TENANT دریافت و نوشته‌های حافظه‌شان را با پیشوند namespace می‌کنند. تخته، dispatcher و تعاریف پروفایل همگی مشترک‌اند؛ فقط داده scoped است.

۱۴ اعلان‌های دسکتاپ

افزونهٔ Kanban اپ Desktop همان رویدادهای پایانی را native سطح می‌کند — بدون نیاز به پلتفرم گیت‌وی. وقتی سوکت رویداد زندهٔ تخته متصل است هر رویداد ‏completed، ‏blocked، ‏gave_up، ‏crashed، ‏timed_out یا مسیریابی-به-triage ‏(block_loop_detected) یک toast درون-اپ با handoff مربوط به worker ‏(خلاصه، دلیل بلاک یا خطا) و اکشن «Open Kanban» بالا می‌آورد. وقتی از پنجرهٔ هرمس دورید همان رویداد اعلان OS native هم شلیک می‌کند ‏(گیت‌خورده با ‏Settings ▸ Notifications ▸ Plugin notifications)، پس task‌ای که در اپ دیگری هستید به مانع می‌خورد همچنان به شما می‌رسد.

پنجرهٔ پوشش: اعلان‌های دسکتاپ روی استریم رویداد زنده سوارند، پس فقط وقتی اپ در حال اجرا با افزونهٔ Kanban فعال است شلیک می‌شوند. رویدادهایی که وقتی اپ بسته است می‌رسند در launch بعدی به‌عنوان اعلان بازپخش نمی‌شوند — برای تحویلی که باید از بسته‌بودن اپ جان ببرد از اشتراک گیت‌وی ‏(پایین) استفاده کنید.

۱۵ اعلان‌های گیت‌وی

وقتی ‏/kanban create … را از گیت‌وی ‏(تلگرام، دیسکورد، اسلک و...) اجرا کنید چت مبدأ خودکار به task جدید مشترک می‌شود. notifier پس‌زمینهٔ گیت‌وی هر چند ثانیه ‏task_events را poll و به‌ازای هر رویداد پایانی ‏(completed، ‏blocked، ‏gave_up، ‏crashed، ‏timed_out) یک پیام به آن چت تحویل می‌دهد. task های کامل‌شده خط اول ‏--result مربوط به worker را هم می‌فرستند تا بدون ‏/kanban show نتیجه را ببینید.

اشتراک‌ها را از CLI هم صریحاً می‌شود مدیریت کرد — وقتی اسکریپت/job کرونی بخواهد چتی را که خودش ازش برنیامده مطلع کند مفید است:

bash
hermes kanban notify-subscribe t_abcd \
    --platform telegram --chat-id 12345678 --thread-id 7 \
    --chat-type group --delivery-mode notify+wake
hermes kanban notify-list
hermes kanban notify-unsubscribe t_abcd \
    --platform telegram --chat-id 12345678 --thread-id 7

اشتراک به‌محض رسیدن task به ‏done یا ‏archived خودش را حذف می‌کند؛ cleanup لازم نیست.

حالت‌های تحویل

‏--delivery-mode کنترل می‌کند notifier چگونه به رویداد پایانی واکنش دهد. هر اشتراک در یکی از سه حالت است ‏(notify پیش‌فرض و رفتار اصلی است):

حالتپیام منفعلایجنت را بیدار می‌کندکِی استفاده کنید
notifyبلهخیرفقط پیام خبری در چت می‌خواهید ‏(پیش‌فرض).
notify+wakeبلهبلهمی‌خواهید ایجنت مقصد هم نوبت واقعی بزند — زمینهٔ board را بخواند و به صدای خودش جواب دهد. auto-subscribe های برخاسته-از-چت همین‌اند.
wakeخیربلهفقط می‌خواهید ایجنت روی رویداد عمل کند بدون ping جداگانه.

«wake» یک پیام ورودی مصنوعی به ایجنت گیت‌وی مقصد جعل می‌کند تا نوبت عادی بزند ‏(کامنت + نتیجه را می‌خواند، استدلال، ریپلای می‌دهد) به‌جای اعلان منفعل یک‌خطی. فقط وقتی شلیک می‌شود که notifier داخل یک پروسهٔ گیت‌وی زنده اجرا شود؛ وگرنه اشتراک ‏notify+wake همچنان پیام منفعلش را تحویل می‌دهد در حالی که اشتراک فقط-wake در آن پروسه هیچ نمی‌کند.

‏--chat-type ‏(dm | group | channel | thread) نوع چت مبدأ را ثبت می‌کند تا نوبت بیدارشده نشست واقعیِ اپراتور را حل کند: ‏build_session_key گروه‌ها، کانال‌ها و تردها را متفاوت از DM ها کلید می‌زند، پس chat_type نادرست wake را به نشست جدا و بی‌زمینه مسیریابی می‌کرد. مسیرهای auto-subscribe و فرمان-اسلش ‏/kanban این را خودکار می‌گیرند — فقط وقتی از اسکریپت یا cron چتی را مشترک می‌کنید دستی ست می‌شود. حذفش کنید تا اشتراک موجود تغییری نکند ‏(اشتراک‌های جدید پیش‌فرض dm).

setup های چند-پروفایلی: تحویل متعلق-به-پروفایل است

در استقرار یک-گیت‌وی-به‌ازای-پروفایل ‏(یک dispatcher، پروسه‌های گیت‌وی جدا برای writer، admin و... — راهنمای multi-gateway در مخزن را ببینید) dispatch و تحویل مالک‌های جدا دارند:

  • Dispatch تک-مالک می‌ماند. دقیقاً یک گیت‌وی ‏kanban.dispatch_in_gateway: true نگه و dispatcher را اجرا می‌کند؛ هر گیت‌وی دیگر آن را false می‌کند.
  • تحویل اعلان متعلق-به-پروفایل است. هر گیت‌وی — شامل غیر-dispatch — notifier را اجرا و فقط اشتراک‌هایی را poll می‌کند که با پروفایلی مهر خورده‌اند whose آداپتورهای پلتفرمش را میزبانی می‌کند. task‌ای که از تلگرام پروفایل writer ساخته شده پیام completed/blocked‌اش توسط گیت‌وی writer تحویل می‌گیرد حتی اگر گیت‌وی default کار dispatch را کرده باشد.
  • اشتراک‌های قدیمی ساخته‌شده قبل از مهر-پروفایل ‏(بدون notifier_profile روی ردیف) فقط توسط گیت‌وی‌ای تحویل می‌گیرند که قفل singleton واقعی dispatcher را دارد، تا دو گیت‌وی هرگز برایشان race نکنند.

تحویل تکراری بین گیت‌وی‌ها با claim اتمیک به‌ازای-رویداد در DB تخته پیشگیری می‌شود. هیچ relay، اشتراک اعتبارنامه یا dispatcher اضافه لازم نیست — هر گیت‌وی پروفایل به‌سادگی از آداپتورهای خودش تحویل می‌دهد.

۱۶ اجراها ‏(Runs) — یک ردیف به‌ازای هر تلاش

task واحد منطقی کار است؛ run یک تلاش برای اجرای آن است. وقتی dispatcher یک task ready را claim می‌کند ردیفی در ‏task_runs می‌سازد و ‏tasks.current_run_id را به آن اشاره می‌دهد. وقتی آن تلاش تمام شود — completed، blocked، crashed، timed_out، spawn-failed، reclaimed — ردیف run با یک ‏outcome بسته و pointer مربوط به task پاک می‌شود. task‌ای که سه بار تلاش شده سه ردیف ‏task_runs دارد.

چرا دو جدول به‌جای صرفاً جهش‌دادن task: برای postmortem های دنیای واقعی به تاریخچهٔ کامل تلاش نیاز دارید ‏(«تلاش دومِ بازبین به approve رسید، سومی merge کرد») و مکان تمیزی برای آویزان‌کردن متادیتای به‌ازای-تلاش لازم دارید — کدام فایل‌ها عوض شدند، کدام تست‌ها اجرا شدند، کدام یافته‌ها را بازبین یادداشت کرد. آن‌ها حقایق run هستند نه حقایق task.

‏Runs جایی است که handoff ساختاریافته هم زندگی می‌کند. وقتی worker taskی را کامل می‌کند ‏(با ‏kanban_complete(...)) می‌تواند بدهد:

  • ‏summary ‏(پارامتر ابزار)/‏--summary ‏(CLI) — handoff انسانی؛ روی run می‌نشیند؛ فرزندان پایین‌دستی در build_worker_context خودش می‌بینند.
  • ‏metadata ‏(پارامتر ابزار)/‏--metadata ‏(CLI) — dict ‏JSON آزاد روی run؛ فرزندان سری‌شده را کنار summary می‌بینند.
  • ‏result ‏(پارامتر ابزار)/‏--result ‏(CLI) — خط لاگ کوتاه که روی ردیف task می‌نشیند ‏(فیلد قدیمی، برای سازگاری حفظ شده).

فرزندان پایین‌دستی summary + metadata آخرین run کامل‌شدهٔ هر والد را می‌خوانند. worker های retry‌کننده تلاش‌های قبلی روی task خودشان را ‏(outcome، summary، error) می‌خوانند تا مسیری که قبلاً شکست خورده را تکرار نکنند.

text
# What a worker actually does — a tool call, from inside the agent loop:
kanban_complete(
    summary="implemented token bucket, keys on user_id with IP fallback, all tests pass",
    metadata={"changed_files": ["limiter.py", "tests/test_limiter.py"], "tests_run": 14},
    result="rate limiter shipped",
)

همان handoff از CLI هم وقتی شما ‏(انسان) باید taskی را که worker نمی‌تواند ببندید در دسترس است — مثلاً taskی رهاشده، یا یکی که از داشبورد دستی done علامت زده‌اید:

bash
hermes kanban complete t_abcd \
    --result "rate limiter shipped" \
    --summary "implemented token bucket, keys on user_id with IP fallback, all tests pass" \
    --metadata '{"changed_files": ["limiter.py", "tests/test_limiter.py"], "tests_run": 14}'

# Review the attempt history on a retried task:
hermes kanban runs t_abcd
#   #  OUTCOME       PROFILE           ELAPSED  STARTED
#   1  blocked       worker               12s  2026-04-27 14:02
#        → BLOCKED: need decision on rate-limit key
#   2  completed     worker                8m   2026-04-27 15:18
#        → implemented token bucket, keys on user_id with IP fallback

‏Runs روی داشبورد هم expose می‌شوند ‏(بخش Run History در drawer، یک ردیف رنگی به‌ازای هر تلاش) و روی REST API ‏(GET /api/plugins/kanban/tasks/:id آرایهٔ ‏runs[] برمی‌گرداند). ‏PATCH /api/plugins/kanban/tasks/:id با ‏{status: "done"، summary، metadata} هر دو را به کرنل فوروارد می‌کند، پس دکمهٔ «mark done» داشبورد هم‌ارز CLI است. ردیف‌های ‏task_events ‏run_id متعلقشان را حمل می‌کنند تا UI بتواند بر اساس تلاش گروه‌بندی‌شان کند و رویداد completed خلاصهٔ خط-اول را در payload‌اش تعبیه می‌کند ‏(سقف ۴۰۰ کاراکتر) تا notifier های گیت‌وی بتوانند handoff ساختاریافته را بدون round-trip دوم SQL رندر کنند.

نکتهٔ بستن انبوه. ‏hermes kanban complete a b c --summary X رد می‌شود — handoff ساختاریافته به‌ازای-run است، پس کپی-پیست همان summary برای N task تقریباً همیشه غلط است. بستن انبوه بدون ‏--summary/--metadata برای حالت رایج «یک تلنبار کار اداری را تمام کردم» همچنان کار می‌کند.

‏Run های reclaim‌شده از تغییرات وضعیت. اگر task در حال اجرایی را در داشبورد از running بکشید بیرون ‏(به ready، یا مستقیم به todo) یا taskی را که هنوز در حال اجراست آرشیو کنید، run در-جراحی با ‏outcome='reclaimed' بسته می‌شود به‌جای یتیم ماندن. ردیف ‏task_runs همیشه در وضعیت پایانی است وقتی ‏tasks.current_run_id برابر NULL باشد و برعکس — این ناوردا بین CLI، داشبورد، dispatcher و notifier برقرار است.

‏Run های مصنوعی برای تکمیل‌های هرگز-claim-نشده. کامل یا بلاک کردن taskی که هرگز claim نشده ‏(مثلاً انسانی task ‏ready را از داشبورد با summary می‌بندد، یا کاربر CLI ‏hermes kanban complete <ready-task> --summary X می‌زند) وگرنه handoff را دور می‌ریزد. به‌جایش کرنل ردیف run با مدت-صفر ‏(started_at == ended_at) حامل summary/metadata/reason درج می‌کند تا تاریخچهٔ تلاش کامل بماند. ‏run_id رویداد completed/blocked به آن ردیف اشاره می‌کند.

refresh زندهٔ drawer. وقتی استریم رویداد WebSocket داشبورد رویدادهای جدید برای taskی که کاربر الان می‌بیند گزارش کند drawer خودش را reload می‌کند ‏(با شمارندهٔ رویداد به‌ازای-task رشته‌شده در لیست وابستگی useEffect). دیگر نیازی به بستن و باز کردن برای دیدن ردیف جدید یا outcome به‌روز یک run نیست.

سازگاری رو-به-جلو

دو ستون nullable روی ‏tasks برای مسیریابی workflow نسخهٔ v2 رزرو شده‌اند: ‏workflow_template_id ‏(این task متعلق به کدام template است) و ‏current_step_key ‏(کدام گام آن template فعلی است). کرنل v1 آنها را برای مسیریابی نادیده ولی نوشتن توسط کلاینت‌ها را اجازه می‌دهد، تا ریلیز v2 بتواند ماشین‌کاری مسیریابی را بدون migration اسکیمای دیگر بیفزاید.

۱۷ مرجع رویدادها

هر جابه‌جایی ردیفی به ‏task_events الصاق می‌کند. هر ردیف ‏run_id اختیاری حمل می‌کند تا UI ها بتوانند رویدادها را بر اساس تلاش گروه کنند. انواع در سه خوشه گروه می‌شوند تا فیلتر راحت باشد ‏(hermes kanban watch --kinds completed,gave_up,timed_out):

چرخهٔ حیات ‏(چه دربارهٔ task به‌عنوان واحد منطقی تغییر کرد):

نوعPayloadکِی
created{assignee, status, parents, tenant}Task درج شد. ‏run_id برابر NULL.
promoted—‏todo ← ready چون همهٔ والدین به done رسیدند. ‏run_id برابر NULL.
claimed{lock, expires, run_id}Dispatcher اتمیک یک task ‏ready را برای spawn گرفت.
completed{result_len, summary?}Worker مقدار --result/--summary نوشت و task به done رسید. ‏summary همان handoff خط-اول است ‏(سقف ۴۰۰ کاراکتر)؛ نسخهٔ کامل روی ردیف run زندگی می‌کند. اگر ‏complete_task روی task هرگز-claim-نشده با فیلدهای handoff صدا زده شود یک run با مدت-صفر مصنوع می‌شود تا run_id همچنان به چیزی اشاره کند.
blocked{reason, kind, recurrences}Worker یا انسان task را به blocked برگرداند. ‏kind دلیل بلاک typed است ‏(needs_input، ‏capability، ‏transient یا null برای بلاک عمومی)؛ ‏recurrences شمارندهٔ حلقه-unblock است. وقتی روی task هرگز-claim-نشده با --reason صدا زده شود run با مدت-صفر مصنوع می‌کند.
dependency_wait{reason, kind}Worker با ‏kind=dependency بلاک شد — task فقط منتظر task دیگری است، پس به todo مسیریابی می‌شود ‏(گیتی-والد، خودارتقا) به‌جای blocked. انسان لازم نیست.
block_loop_detected{reason, kind, recurrences, limit}Taskی unblock و برای همان دلیل BLOCK_RECURRENCE_LIMIT بار ‏(پیش‌فرض ۲) دوباره بلاک شد. به‌جای نشستن مجدد در blocked — جایی که cron مدام unblock‌اش می‌کرد — به triage برای تصمیم انسانی می‌رود و حلقهٔ unblock↔re-block را می‌شکند.
unblocked—‏blocked ← ready ‏(یا todo اگر والدین بازند)، دستی یا از طریق ‎/unblock. ‏consecutive_failures مربوط به dispatcher را ریست ولی عمداً block_recurrences را حفظ می‌کند تا مدارشکن حلقه حافظه‌اش بماند. ‏run_id برابر NULL.
archived—از تخته پیش‌فرض مخفی می‌شود. اگر task هنوز در حال اجرا بود ‏run_id اجرایی که به‌عنوان side effect پس گرفته شد را حمل می‌کند.

نوعPayloadکِی

status{status}Drag-drop داشبورد مستقیم وضعیت نوشت ‏(مثل todo ← ready). ‏run_id اجرایی که هنگام کشیدن بیرون از running پس گرفته شد را حمل می‌کند؛ وگرنه NULL.

heartbeat{note?}Worker برای علامت دادن زنده‌بودن حین عملیات طولانی ‏hermes kanban heartbeat $TASK را صدا زد.
reclaimed{stale_lock}TTL claim بدون تکمیل منقضی شد؛ task به ready برمی‌گردد.
crashed{pid, claimer}PID worker دیگر زنده نیست ولی TTL هنوز منقضی نشده بود.
timed_out{pid, elapsed_seconds, limit_seconds, sigkill}‏max_runtime_seconds گذشت؛ dispatcher ‏SIGTERM داد ‏(سپس بعد از ۵ ثانیه grace ‏SIGKILL) و دوباره صف کرد.
stale{elapsed_seconds, last_heartbeat_at, heartbeat_age_seconds, timeout_seconds, pid, terminated}Task بیشتر از ‏kanban.dispatch_stale_timeout_seconds ‏(پیش‌فرض ۴ ساعت) اجرا شد و در ساعت اخیر هیچ ‏kanban_heartbeat‌ای نرسید. Dispatcher worker میزبان-محلی را ‏(اگر بود) SIGTERM، task را برای dispatch مجدد به ready ریست می‌کند. شمارندهٔ شکست را تیک نمی‌زند ‏(stale تشخیص غیبت سمت-dispatcher است نه خطای worker). Worker هایی که عملیات طولانی اجرا می‌کنند باید دست‌کم ساعتی یک‌بار kanban_heartbeat بزنند تا از این در امان باشند.
reconciled{reason, claim_lock, claim_expires, worker_pid}آشتی کارت-یتیم: کارت running بود با حساب‌داری claim خراب ‏(claim_lock یا claim_expires برابر NULL — کرش وسط claim، SQL دستی، بازیابی DB) و هیچ worker زنده‌ای نداشت، پس هیچ مسیر TTL/crash/stale‌ای هرگز بازیابی‌اش نمی‌کرد. Dispatcher آن را با کامنت توضیحی به ready صف کرد. گیتی با ‏kanban.reconcile_orphans در config.yaml ‏(پیش‌فرض true).
respawn_guarded{reason}Dispatcher از respawn مجدد این task ready در این تیک امتناع کرد. دلایل: ‏blocker_auth ‏(آخرین شکست خطای quota/auth/429 بود — صبر برای ریست پنجرهٔ نرخ)، ‏recent_success ‏(اجرای کامل‌شده در ساعت اخیر بوده — قبل از اجرای مجدد منتظر بازبینی باشید)، ‏active_pr ‏(URL PR گیت‌هابی در کامنت اخیر است — worker قبلی PR باز کرده). Task در ready می‌ماند؛ تیک بعدی شانس spawn دیگری می‌گیرد. اگر شرط زمینه‌ای پابرجا باشد مدارشکن عادی consecutive_failures بعد از failure_limit شکست از طریق gave_up خودکار بلاک می‌کند.
spawn_failed{error, failures}یک تلاش spawn شکست خورد ‏(PATH غایب، workspace غیرقابل-mount و...). شمارنده افزایش؛ task برای retry به ready برمی‌گردد.
protocol_violation{pid, claimer, exit_code, protocol_violation}Worker با موفقیت خارج شد در حالی که task هنوز running بود، معمولاً چون بدون صدازدن ‏kanban_complete یا ‏kanban_block جواب داد. روی هر نقض صادر می‌شود ‏(نشانگر protocol_violation: true داخل payload به متادیتای run کپی و به بودجهٔ retry فقط-نقض تغذیه می‌شود). زیر بودجه — تا ‏_PROTOCOL_VIOLATION_FAILURE_LIMIT ‏(پیش‌فرض ۳) نقض متوالی، با override ‏max_retries به‌ازای-task — task به‌سادگی برای تلاش دیگر به ready برمی‌گردد؛ وقتی streak به حد برسد dispatcher ‏gave_up هم صادر و خودکار بلاک می‌کند.
gave_up{failures, effective_limit, limit_source, error}مدارشکن بعد از N تلاش متوالی ناموفق شلیک شد. Task با آخرین خطا خودکار بلاک می‌شود. حد مؤثر به‌ترتیب حل می‌شود: ‏max_retries مربوط به task، بعد ‏failure_limit مربوط به dispatcher / ‏kanban.failure_limit، بعد پیش‌فرض داخلی.

‏hermes kanban tail <id> این‌ها را برای یک task نشان می‌دهد. ‏hermes kanban watch سراسر تخته استریم‌شان می‌کند.

۱۸ خارج از دامنه

کانبان عمداً تک-میزبان است. ‏~/.hermes/kanban.db فایل SQLite محلی است و dispatcher worker ها را روی همان ماشین spawn می‌کند. اجرای تختهٔ مشترک بین دو میزبان پشتیبانی نمی‌شود — primitive هماهنگی برای «worker X روی میزبان A، worker Y روی میزبان B» وجود ندارد و مسیر تشخیص-کرش فرض می‌کند PID ها میزبان-محلی‌اند. اگر چند-میزبانی لازم دارید یک board مستقل به‌ازای هر میزبان اجرا و با ‏delegate_task/صف پیام پل بزنید.
