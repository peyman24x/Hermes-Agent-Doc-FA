ارائه‌دهندگان حافظهٔ خارجی ‏(Memory Providers)

هرمس ایجنت با ۸ پلاگین ارائه‌دهندهٔ حافظهٔ خارجی ارسال می‌شود که به ایجنت دانشِ پایدار و بین-نشستی فراتر از MEMORY.md و USER.md داخلی می‌دهد. در هر لحظه فقط یک ارائه‌دهندهٔ خارجی می‌تواند فعال باشد — حافظهٔ داخلی همیشه کنارش فعال است.

۱ شروع سریع

hermes memory setup      # interactive picker + configuration
hermes memory status     # check what's active
hermes memory off        # disable external provider

می‌توانید ارائه‌دهندهٔ فعال حافظه را از مسیر ‏hermes plugins ← Provider Plugins ← Memory Provider هم انتخاب کنید.

یا دستی در ~/.hermes/config.yaml:

yaml
memory:
  provider: openviking   # or honcho, mem0, hindsight, holographic, retaindb, byterover, supermemory

۲ نحوهٔ کار

وقتی یک ارائه‌دهندهٔ حافظه فعال باشد، هرمس خودکار:

  1. زمینهٔ ارائه‌دهنده را تزریق می‌کند به پرامپت سیستمی ‏(آنچه ارائه‌دهنده می‌داند)
  2. حافظه‌های مرتبط را پیش‌واکشی می‌کند قبل از هر نوبت ‏(پس‌زمینه، غیربلاک‌کننده)
  3. نوبت‌های گفتگو را sync می‌کند به ارائه‌دهنده بعد از هر پاسخ
  4. در پایان نشست حافظه استخراج می‌کند ‏(برای ارائه‌دهنده‌هایی که پشتیبانی می‌کنند)
  5. نوشتن‌های حافظهٔ داخلی را آینه می‌کند به ارائه‌دهندهٔ خارجی
  6. ابزارهای مخصوص ارائه‌دهنده اضافه می‌کند تا ایجنت بتواند حافظه‌ها را جستجو، ذخیره و مدیریت کند

حافظهٔ داخلی ‏(MEMORY.md / USER.md) دقیقاً مثل قبل ادامه می‌دهد. ارائه‌دهندهٔ خارجی افزودنی است.

۳ Honcho

مدل‌سازی کاربر بین-نشستیِ AI-native با استدلال جدلی ‏(dialectic)، تزریق زمینهٔ مخصوص-نشست، جستجوی معنایی و نتیجه‌گیری‌های پایدار. زمینهٔ پایه حالا خلاصهٔ نشست را کنار بازنمایی کاربر و کارت‌های peer شامل می‌شود تا ایجنت بداند چه چیزهایی قبلاً بحث شده.
بهترین برایسیستم‌های چندایجنت با زمینهٔ بین-نشستی، همسویی کاربر-ایجنت
نیازمندی‌ها‏pip install honcho-ai + ‏کلید API یا نمونهٔ خودمیزبان
ذخیره‌سازی دادهHoncho Cloud یا خودمیزبان
هزینهقیمت‌گذاری Honcho ‏(کلود) / رایگان ‏(خودمیزبان)

ابزارها ‏(۵): ‏honcho_profile ‏(خواندن/به‌روزرسانی کارت peer)، ‏honcho_search ‏(جستجوی معنایی)، ‏honcho_context ‏(زمینهٔ نشست — خلاصه، بازنمایی، کارت، پیام‌ها)، ‏honcho_reasoning ‏(ترکیب LLM)، ‏honcho_conclude ‏(ساخت/حذف نتیجه‌گیری‌ها)

معماری: تزریق زمینهٔ دولایه — یک لایهٔ پایه ‏(خلاصهٔ نشست + بازنمایی + کارت peer؛ refresh روی ‏contextCadence) به‌علاوهٔ مکمل جدلی ‏(استدلال LLM؛ refresh روی dialecticCadence). جدلی خودکار بر اساس وجود زمینهٔ پایه بین پرامپت‌های cold-start ‏(حقایق عمومی کاربر) و پرامپت‌های warm ‏(زمینهٔ مخصوص-نشست) انتخاب می‌کند.

سه پیچ مستقل پیکربندی هزینه و عمق را جداگانه کنترل می‌کنند:

  • ‏contextCadence — چند وقت یک بار لایهٔ پایه refresh شود ‏(فرکانس فراخوانی API)
  • ‏dialecticCadence — چند وقت یک بار LLM ی جدلی شلیک شود ‏(فرکانس فراخوانی LLM)
  • ‏dialecticDepth — چند پاس ‏.chat() به‌ازای هر فراخوانی جدلی ‏(۱–۳، عمق استدلال)

جدلیِ خود-تزریق‌شونده سطح استدلالش را هم با طول کوئری مقیاس می‌دهد ‏(کوئری طولانی‌تر ← استدلال عمیق‌تر، سقف ‏reasoningLevelCap)؛ بخش Query-Adaptive Reasoning Level را ببینید.

ویزارد راه‌اندازی:

hermes memory setup        # select "honcho" — runs the Honcho-specific post-setup

فرمان قدیمی ‏hermes honcho setup همچنان کار می‌کند ‏(الان به ‏hermes memory setup ریدایرکت می‌شود) ولی فقط بعد از انتخاب Honcho به‌عنوان ارائه‌دهندهٔ فعال ثبت می‌شود.

ماشین‌های headless / راه‌دور: برای auth ی کلود روی سیستمی بدون مرورگر ‏(SSH، ‏VM راه‌دور)، در پرامپت روش-auth ویزارد گزینهٔ device را بردارید. CLI یک کد کوتاه و لینک تأیید چاپ می‌کند؛ لینک را در مرورگر روی هر ماشین دیگری باز، تأیید کنید و setup تمام می‌شود — بدون کپی-پیست کلید API. ویزارد وقتی مرورگر محلی قابل‌استفاده تشخیص ندهد خودکار همین گزینه را پیشنهاد می‌دهد.

Config: ‏$HERMES_HOME/honcho.json ‏(مخصوص-پروفایل) یا ‏~/.honcho/config.json ‏(سراسری). ترتیب حل: ‏$HERMES_HOME/honcho.json > ‏~/.hermes/honcho.json > ‏~/.honcho/config.json. بخش مرجع config و ‏راهنمای یکپارچه‌سازی Honcho را ببینید.

💡 مهاجرت از ‏hermes honcho

اگر قبلاً از ‏hermes honcho setup استفاده کرده‌اید، config و تمام داده‌های سمت-سرور شما سالم‌اند. کافی است دوباره از طریق ویزارد راه‌اندازی فعالش کنید یا دستی memory.provider: honcho را ست کنید تا از طریق سیستم جدید reactivate شود.

راه‌اندازی چند-peer:

‏Honcho گفتگوها را به‌صورت peers مبادله‌کنندهٔ پیام مدل می‌کند — یک peer ی کاربر به‌علاوهٔ یک peer ی AI به‌ازای هر پروفایل هرمس، همگی در یک فضای‌کاری مشترک. فضای‌کاری محیط مشترک است: peer ی کاربر سراسری بین پروفایل‌هاست و هر peer ی AI هویت مستقل خودش را دارد. هر peer ی AI بازنمایی/کارت مستقل از مشاهده‌های خودش می‌سازد، پس یک پروفایل coder کد-محور می‌ماند و یک پروفایل writer تحریریه‌محور، در برابر همان کاربر.

نگاشت:

مفهومچه چیزی است
Workspaceمحیط مشترک. همهٔ پروفایل‌های هرمس زیر یک workspace همان هویت کاربر را می‌بینند.
User peer ‏(peerName)انسان. بین پروفایل‌های فضای‌کاری مشترک.
AI peer ‏(aiPeer)یکی به‌ازای هر پروفایل هرمس. کلید host ی ‏hermes ← پیش‌فرض؛ برای بقیه ‏hermes.<profile>.
Observationtoggle های per-peer که کنترل می‌کنند Honcho از پیام‌های چه کسی چه چیزی مدل کند. ‏directional ‏(پیش‌فرض، هر چهار مورد روشن) یا ‏unified ‏(استخر ناظر-واحد).

پروفایل جدید، peer ی Honcho تازه

hermes profile create coder --clone

‏--clone یک بلوک host ی ‏hermes.coder در ‏honcho.json می‌سازد با ‏aiPeer: "coder"، ‏workspace مشترک، ‏peerName به‌ارث‌رسیده، ‏recallMode، ‏writeFrequency، ‏observation و… . peer ی AI پیشاپیش در Honcho ساخته می‌شود تا قبل از اولین پیام موجود باشد.

پروفایل‌های موجود، backfill ی peers ی Honcho

hermes honcho sync

هر پروفایل هرمس را اسکن، برای هر پروفایل بدون بلوک host یکی می‌سازد، تنظیمات را از بلوک پیش‌فرض ‏hermes به ارث می‌برد و peer های AI جدید را پیشاپیش می‌سازد. idempotent است — پروفایل‌هایی که بلوک host دارند رد می‌شوند.

Observation ی per-profil

هر بلوک host می‌تواند config ی observation را مستقل override کند. مثال: پروفایل کد-محوری که peer ی AI اش کاربر را مشاهده می‌کند ولی خودش را مدل نمی‌کند:

"hermes.coder": {
  "aiPeer": "coder",
  "observation": {
    "user": { "observeMe": true, "observeOthers": true },
    "ai":   { "observeMe": false, "observeOthers": true }
  }
}

toggle های Observation ‏(یک مجموعه به‌ازای هر peer):

toggleاثر
observeMeHoncho از پیام‌های خودِ این peer بازنمایی‌اش را می‌سازد
observeOthersاین peer پیام‌های peer دیگر را مشاهده می‌کند ‏(خوراک استدلال بین-peer)

پیش‌تنظیم‌ها با ‏observationMode:

  • ‏"directional" ‏(پیش‌فرض) — هر چهار فلگ روشن. مشاهدهٔ دوطرفهٔ کامل؛ جدلی بین-peer را ممکن می‌کند.
  • ‏"unified" — کاربر ‏observeMe: true، ‏AI ‏observeOthers: true، بقیه خاموش. استخر ناظر-واحد؛ AI کاربر را مدل می‌کند نه خودش را، و peer ی کاربر فقط خودش را مدل می‌کند.

toggle های سمت-سرور که از طریق داشبورد Honcho ست شده‌اند بر پیش‌فرض‌های محلی مقدم‌اند — در init ی نشست برگشت sync می‌شوند.

مرجع کامل observation را در صفحهٔ Honcho ببینید.

نگاشت هویت گیت‌وی

مدل peer بالا نشست‌های CLI، ‏TUI و دسکتاپ را پوشش می‌دهد که در آنها هر گفتگو به ‏peerName حل می‌شود. گیت‌وی محور دومی اضافه می‌کند: کاربرها با شناسه‌های runtime ی بومی-پلتفرم می‌آیند ‏(UID تلگرام، snowflake دیسکورد، کاربر اسلک) و سه کلید تعیین می‌کنند هر شناسه به کدام peer حل شود.

کلیداثر
pinUserPeer: trueهمهٔ کاربران غیر-ایجنت گیت‌وی به peerName جمع می‌شوند. pin اول بررسی می‌شود پس بر همهٔ alias ها مقدم است — فقط وقتی برداریدش که هیچ هویت سمت-کاربری peer ی خودش را لازم ندارد
userPeerAliasesشناسه‌های runtime مشخص را به peers نگاشت می‌کند ‏({"7654321": "alice"}). خانهٔ مسیریابی هویت‌های متمایز — شامل ایجنت‌هایی که هرکدام peer ی خودشان را حمل می‌کنند
runtimePeerPrefixهر شناسهٔ runtime نگاشت‌نشده را namespace می‌کند ‏(telegram_7654321) تا پلتفرم‌هایی با ID های هم‌شکل تصادم نکنند

بیرون گیت‌وی این کلیدها کاری نمی‌کنند. ‏hermes memory setup فقط وقتی برایشان پرامپت می‌دهد که پلتفرم گیت‌وی متصلی آشکار کند. نردبان resolver و جریان setup را در صفحهٔ Honcho ببینید.

نمونهٔ کامل honcho.json ‏(چند-پروفایل) 
{
  "apiKey": "your-key",
  "workspace": "hermes",
  "peerName": "eri",
  "hosts": {
    "hermes": {
      "enabled": true,
      "aiPeer": "hermes",
      "workspace": "hermes",
      "peerName": "eri",
      "recallMode": "tools",
      "observation": {
        "user": { "observeMe": true, "observeOthers": false },
        "ai": { "observeMe": true, "observeOthers": true }
      }
    },
    "hermes.writer": {
      "enabled": true,
      "aiPeer": "writer",
      "workspace": "hermes",
      "peerName": "eri"
    }
  },
  "sessions": {
    "/home/user/myproject": "myproject-main"
  }
}

۴ OpenViking

پایگاه‌دادهٔ زمینهٔ شرکت Volcengine ‏(ByteDance) با سلسله‌مراتب دانش به سبک فایل‌سیستم، بازیابی طبقه‌بندی‌شده و استخراج خودکار حافظه در ۶ دسته.
بهترین برایمدیریت دانش خودمیزبان با مرور ساختاریافته
نیازمندی‌هاOpenViking مقداردهی اولیه، اعتبارسنجی‌شده و درحال‌اجرا
ذخیره‌سازی دادهخودمیزبان ‏(محلی یا کلود)
هزینهرایگان ‏(متن‌باز، ‏AGPL-3.0)

ابزارها ‏(۶): ‏viking_search ‏(جستجوی معنایی)، ‏viking_read ‏(طبقه‌بندی: abstract/overview/full)، ‏viking_browse ‏(ناوبری فایل‌سیستمی)، ‏viking_remember ‏(ذخیرهٔ حقایق)، ‏viking_forget ‏(حذف فایل حافظه با URI دقیق ‏viking://)، ‏viking_add_resource ‏(ورودی‌گیری URL/اسناد)

راه‌اندازی:

# Prepare OpenViking first
openviking-server init
openviking-server doctor
openviking-server

# Then configure Hermes
hermes memory setup    # select "openviking"
# Or manually:
hermes config set memory.provider openviking

‏hermes memory setup می‌تواند مقادیر اتصال را از ‏~/.openviking/ovcli.conf دوباره استفاده یا کپی کند. راه‌اندازی دستی از فایل .env پروفایل فعال استفاده می‌کند؛ برای پروفایل پیش‌فرض همان ‏~/.hermes/.env است و برای پروفایل‌های نام‌دار ‏~/.hermes/profiles/<profile>/.env.

OPENVIKING_ENDPOINT=http://127.0.0.1:1933
# OPENVIKING_API_KEY=...
# OPENVIKING_ACCOUNT=default
# OPENVIKING_USER=default
# OPENVIKING_AGENT=hermes

تنظیمات سرور OpenViking در ‏ov.conf زندگی می‌کنند ‏(--config، ‏OPENVIKING_CONFIG_FILE یا ‏~/.openviking/ov.conf). مقادیر اتصال کلاینت در ‏ovcli.conf است ‏(OPENVIKING_CLI_CONFIG_FILE یا ‏~/.openviking/ovcli.conf).

قابلیت‌های کلیدی:

  • بارگذاری زمینهٔ طبقه‌بندی‌شده: ‏L0 ‏(~۱۰۰ توکن) ← L1 ‏(~۲ هزار) ← L2 ‏(کامل)
  • استخراج خودکار حافظه هنگام commit ی نشست ‏(پروفایل، ترجیحات، موجودیت‌ها، رویدادها، موارد، الگوها)
  • طرح URI ی ‏viking:// برای مرور سلسله‌مراتبی دانش

‏OPENVIKING_ACCOUNT و ‏OPENVIKING_USER برای حالت محلی/مورد-اعتماد به کار می‌روند. ‏OPENVIKING_AGENT شناسهٔ peer ی هرمس در OpenViking برای حافظه‌های مخصوص-peer است.

۵ Mem0

استخراج واقعیت با LLM سمت-سرور همراه جستجوی معنایی، reranking و حذف تکرار خودکار. سه حالت اتصال: Platform ‏(Mem0 Cloud)، داشبورد خودمیزبان ‏(سرور Mem0 که با Docker اجرا می‌کنید) و OSS ‏(Mem0 درون-پروسه‌ای با LLM و vector store خودتان).
بهترین برایمدیریت حافظه بدون-دست‌کاری — Mem0 استخراج را خودکار انجام می‌دهد
نیازمندی‌ها‏pip install mem0ai + کلید API ‏(platform)، یک سرور Mem0 درحال‌اجرا ‏(خودمیزبان) یا LLM + vector store ‏(OSS)
ذخیره‌سازی دادهMem0 Cloud ‏(platform)، سرور Mem0 خودتان ‏(خودمیزبان) یا درون-پروسه‌ای ‏(OSS)
هزینهقیمت‌گذاری Mem0 ‏(platform) / رایگان ‏(خودمیزبان یا OSS)

ابزارها ‏(۴): ‏mem0_search ‏(جستجوی معنایی؛ reranking اختیاری فقط در حالت platform، پیش‌فرض خاموش)، ‏mem0_add ‏(ذخیرهٔ واقعیت‌ها verbatim)، ‏mem0_update ‏(به‌روزرسانی با ID)، ‏mem0_delete ‏(حذف با ID)

  • ingest گفتگو در پایان نشست ‏(به ‏/v4/conversations) برای پروفایل غنی‌تر + ساخت گراف در Supermemory
  • مسیریابی سر-تا-سر خودمیزبان — درخواست‌های SDK، ‏probe و ingest گفتگو از همان نقطهٔ پایانی پیکربندی‌شده استفاده می‌کنند
  • حقایق پروفایل روی نوبت اول و فواصل قابل‌پیکربندی تزریق می‌شود
  • کانتینرهای مخصوص-پروفایل — از ‏{identity} در ‏container_tag استفاده کنید ‏(مثلاً hermes-{identity} ← ‏hermes-coder) تا حافظه‌ها per-profil هرمس ایزوله شوند
  • حالت چند-کانتینری — با فهرست ‏custom_containers مقدار ‏enable_custom_container_tags را روشن کنید تا ایجنت بتواند بین کانتینرهای نام‌دار بخواند/بنویسد. عملیات خودکار روی کانتینر اصلی می‌مانند.

  • ارائه‌دهنده‌های ابری ‏(RetainDB) نام پروژهٔ مخصوص-پروفایل را خودکار مشتق می‌کنند
  • ارائه‌دهنده‌های متغیر-محیطی ‏(OpenViking) از فایل ‏.env هر پروفایل پیکربندی می‌شوند

برای ساختن ارائه‌دهندهٔ اختصاصی خودتان بخش راهنمای توسعه‌دهنده: پلاگین‌های ارائه‌دهندهٔ حافظه را ببینید.
