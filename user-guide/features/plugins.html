افزونه‌ها ‏(Plugins)

هرمس سیستم افزونه‌ای برای افزودن ابزار، هوک و یکپارچه‌سازی سفارشی بدون دست‌زدن به کد هسته دارد.

اگر می‌خواهید یک ابزار سفارشی برای خودتان، تیم‌تان یا یک پروژه بسازید، معمولاً همین مسیر درست است. صفحهٔ افزودن ابزارها راهنمای توسعه‌دهندگان مخصوص ابزارهای هستهٔ داخلی هرمس است که در ‏tools/ و ‏toolsets.py زندگی می‌کنند.

← ساخت افزونهٔ هرمس — راهنمای گام‌به‌گام با مثال کاملِ کارا.

۱ نمای سریع

یک پوشه داخل ‏~/.hermes/plugins/ بیندازید با یک ‏plugin.yaml و کد پایتون:

text
~/.hermes/plugins/my-plugin/
├── plugin.yaml      # manifest
├── __init__.py      # register() — اتصال schema ها به هندلرها
├── schemas.py       # schema های ابزار (آنچه LLM می‌بیند)
└── tools.py         # هندلرهای ابزار (آنچه هنگام فراخوانی اجرا می‌شود)

هرمس را شروع کنید — ابزارهایتان کنار ابزارهای داخلی ظاهر می‌شوند. مدل بلافاصله می‌تواند صدایشان بزند.

مثال کمینهٔ کارا

این یک افزونهٔ کامل است که ابزار ‏hello_world اضافه و هر فراخوانی ابزار را از طریق هوک لاگ می‌کند.

‏~/.hermes/plugins/hello-world/plugin.yaml

yaml
name: hello-world
version: "1.0"
description: A minimal example plugin

‏~/.hermes/plugins/hello-world/__init__.py

python
"""Minimal Hermes plugin — registers a tool and a hook."""

import json


def register(ctx):
    # --- Tool: hello_world ---
    schema = {
        "name": "hello_world",
        "description": "Returns a friendly greeting for the given name.",
        "parameters": {
            "type": "object",
            "properties": {
                "name": {
                    "type": "string",
                    "description": "Name to greet",
                }
            },
            "required": ["name"],
        },
    }

    def handle_hello(params, **kwargs):
        del kwargs
        name = params.get("name", "World")
        return json.dumps({"success": True, "greeting": f"Hello, {name}!"})

    ctx.register_tool(
        name="hello_world",
        toolset="hello_world",
        schema=schema,
        handler=handle_hello,
    )

    # --- Hook: log every tool call ---
    def on_tool_call(tool_name, params, result):
        print(f"[hello-world] tool called: {tool_name}")

    ctx.register_hook("post_tool_call", on_tool_call)

هر دو فایل را داخل ‏~/.hermes/plugins/hello-world/ بیندازید، هرمس را ری‌استارت کنید و مدل بلافاصله می‌تواند ‏hello_world را صدا بزند. هوک بعد از هر فراخوانی ابزار یک خط لاگ چاپ می‌کند.

توصیف رو-به-مدلِ ابزار باید در ‏schema["description"] باشد. مقدار اختیاری ‏ctx.register_tool(description=...) متادیتای جداگانهٔ رجیستری ‏ToolEntry است: اگر حذف شود به توصیف schema پیش‌فرض می‌شود ولی هرمس آن را داخل schema فاقد ‏description کپی برنمی‌گرداند. متن را ترجیحاً یک‌بار در schema تعریف کنید. اگر هر دو را دادید همگام نگهشان دارید؛ مدل مقدار schema را می‌بیند.

افزونه‌های محلی-پروژه زیر ‏./.hermes/plugins/ به‌طور پیش‌فرض خاموش‌اند. فقط برای مخازن مطمئن با گذاشتن ‏HERMES_ENABLE_PROJECT_PLUGINS=true قبل از شروع هرمس فعالشان کنید.

۲ افزونه‌ها چه کارهایی می‌توانند بکنند

هر API ‏ctx.* پایین داخل تابع ‏register(ctx) افزونه در دسترس است.

قابلیتچطور
افزودن ابزار‏ctx.register_tool(name=..., toolset=..., schema=..., handler=...)
افزودن هوک‏ctx.register_hook("post_tool_call", callback)
افزودن فرمان اسلش‏ctx.register_command(name, handler, description) — ‏/name را به CLI و نشست‌های گیت‌وی اضافه می‌کند
dispatch ابزار از فرمان‌ها‏ctx.dispatch_tool(name, args) — ابزار ثبت‌شده را با زمینهٔ والد-ایجنت خودکار-سیم‌شده invoke می‌کند
افزودن فرمان CLI‏ctx.register_cli_command(name, help, setup_fn, handler_fn) — ‏hermes <plugin> <subcommand> اضافه می‌کند
تزریق پیام‏ctx.inject_message(content, role="user", session_key=...) — «تزریق پیام» را ببینید
حمل فایل‌های داده‏Path(__file__).parent / "data" / "file.yaml"
همراه‌کردن مهارت‌ها‏ctx.register_skill(name, path) — namespace شده به ‏plugin:skill، لود با ‏skill_view("plugin:skill")
گیت روی env‏requires_env: [API_KEY] در plugin.yaml — حین ‏hermes plugins install پرسیده می‌شود
توزیع با pip‏[project.entry-points."hermes_agent.plugins"]
ثبت پلتفرم گیت‌وی ‏(دیسکورد، تلگرام، IRC و...)‏ctx.register_platform(name, label, adapter_factory, check_fn, ...) — راهنمای افزودن آداپتورهای پلتفرم
ثبت بک‌اند تولید تصویر‏ctx.register_image_gen_provider(provider) — راهنمای افزونه‌های ارائه‌دهندهٔ تولید تصویر
ثبت بک‌اند تولید ویدیو‏ctx.register_video_gen_provider(provider) — راهنمای افزونه‌های ارائه‌دهندهٔ تولید ویدیو
ثبت موتور فشرده‌سازی زمینه‏ctx.register_context_engine(engine) — راهنمای افزونه‌های موتور زمینه
مسیریابی پرامپت‌های تأیید انسانی‏ctx.register_approval_transport(name, present_fn) — «ترنسپورت‌های تأیید» را ببینید
ثبت بک‌اند حافظهزیرکلاس ‏MemoryProvider در ‏plugins/memory/<name>/__init__.py — راهنمای افزونه‌های ارائه‌دهندهٔ حافظه ‏(سیستم کشف جدایی استفاده می‌کند)
اجرای فراخوانی LLM متعلق-به-میزبان‏ctx.llm.complete(...) / ‏ctx.llm.complete_structured(...) — قرض‌دادن مدل فعال و احراز کاربر برای یک تکمیل یک‌باره با اعتبارسنجی اختیاری JSON schema
صدازدن ابزار MCP ‏(با گیت قابلیت)‏ctx.call_mcp(server, tool, arguments, timeout=30) — «صدازدن سرورهای MCP از افزونه‌ها» را ببینید
ثبت بک‌اند inference ‏(ارائه‌دهندهٔ LLM)‏register_provider(ProviderProfile(...)) در ‏plugins/model-providers/<name>/__init__.py — راهنمای افزونه‌های ارائه‌دهندهٔ مدل ‏(سیستم کشف جدایی)

زیر-دسته‌های افزونه

داخل هر منبع، هرمس زیر-پوشه‌های زیر-دسته‌ای را هم می‌شناسد که افزونه‌ها را به سیستم‌های کشف تخصصی مسیریابی می‌کنند:

زیر-پوشهچه چیزی داردسیستم کشف
plugins/ ‏(ریشه)افزونه‌های عمومی — ابزار، هوک، فرمان اسلش، فرمان CLI، مهارت‌های همراه‌بسته‏PluginManager ‏(kind: ‏standalone یا ‏backend)
plugins/platforms/<name>/آداپتورهای کانال گیت‌وی ‏(ctx.register_platform())‏PluginManager ‏(kind: ‏platform، یک سطح پایین‌تر)
plugins/image_gen/<name>/بک‌اندهای تولید تصویر ‏(ctx.register_image_gen_provider())‏PluginManager ‏(kind: ‏backend، یک سطح پایین‌تر)
plugins/memory/<name>/ارائه‌دهنده‌های حافظه ‏(زیرکلاس MemoryProvider)لودر مستقل در ‏plugins/memory/__init__.py ‏(kind: ‏exclusive — در هر لحظه یکی فعال)
plugins/context_engine/<name>/موتورهای فشرده‌سازی زمینه ‏(ctx.register_context_engine())لودر مستقل در ‏plugins/context_engine/__init__.py ‏(در هر لحظه یکی فعال)
plugins/model-providers/<name>/پروفایل‌های ارائه‌دهندهٔ LLM ‏(register_provider(ProviderProfile(...)))لودر مستقل در ‏providers/__init__.py ‏(lazy؛ در اولین فراخوانی ‏get_provider_profile اسکن می‌شود)

افزونه‌های کاربر در ‏~/.hermes/plugins/model-providers/<name>/ و ‏~/.hermes/plugins/memory/<name>/ بر افزونه‌های همراه‌بستهٔ هم‌نام مقدم‌اند — آخرین-نویسنده-برنده در ‏register_provider()/register_memory_provider(). پوشه را بیندازید و بدون هیچ ویرایش مخزنی داخلی را جایگزین می‌کند.

۴ افزونه‌ها انتخابی‌اند ‏(با چند استثنا)

افزونه‌های عمومی و بک‌اندهای نصب‌شده توسط کاربر به‌طور پیش‌فرض خاموش‌اند — کشف پیدایشان می‌کند ‏(پس در ‏hermes plugins و ‏/plugins دیده می‌شوند) ولی هیچ چیزی با هوک یا ابزار لود نمی‌شود تا نام افزونه را به ‏plugins.enabled در config.yaml بیفزایید. این مانع اجرای کد شخص ثالث بدون رضایت صریح شماست.

yaml
plugins:
  enabled:
    - my-tool-plugin
    - disk-cleanup
  disabled:       # لیست-رد اختیاری — اگر نامی در هر دو بود همیشه این برنده است
    - noisy-plugin

سه راه تغییر وضعیت:

bash
hermes plugins                    # کلید تعاملی (SPACE برای تیک/برداشتن تیک)
hermes plugins enable <name>      # افزودن به لیست مجاز
hermes plugins disable <name>     # حذف از لیست مجاز + افزودن به disabled

بعد از ‏hermes plugins install owner/repo سؤال می‌شود ‏Enable 'name' now? [y/N] — پیش‌فرض خیر. برای نصب‌های اسکریپتی پرامپت را با ‏--enable یا ‏--no-enable رد کنید.

برای نصب بازتولیدپذیر، یک commit کامل تغییرناپذیر pin کنید ‏(تگ‌ها، شاخه‌ها و SHA های مخفف پذیرفته نمی‌شوند):

hermes plugins install owner/repo --ref 0123456789abcdef0123456789abcdef01234567

هرمس commit را detached checkout، تأیید می‌کند ‏HEAD دقیقاً با SHA درخواستی بخواند و منبع مرجع، revision نصب‌شده و وضعیت pin را در پروفایل فعلی ثبت می‌کند. ‏hermes plugins update از جابه‌جا کردن افزونهٔ pinned امتناع می‌کند؛ با ‏hermes plugins install <source> --force --ref <new-commit> صریحاً commit دقیق جدید انتخاب کنید. متادیتای نصبِ محلی-پروفایل هیچ مقدار پیکربندی، محیط، رمز یا grant قابلیتی ندارد.

چه چیزی لیست مجاز گیت نمی‌زند

چند دسته از افزونه‌ها از ‏plugins.enabled می‌گذرند — بخشی از سطح داخلی هرمس‌اند و اگر به‌طور پیش‌فرض گیت شوند عملکردهای پایه می‌شکند:

نوع افزونهبه‌جایش چگونه فعال می‌شود
افزونه‌های پلتفرمی همراه‌بسته ‏(IRC، ‏Teams و... زیر ‏plugins/platforms/)خودکار لود می‌شوند تا همهٔ کانال‌های گیت‌وی عرضه‌شده در دسترس باشند. روشن‌شدن واقعی کانال با ‏gateway.platforms.<name>.enabled در config.yaml است.
بک‌اندهای همراه‌بسته ‏(ارائه‌دهنده‌های image-gen زیر ‏plugins/image_gen/ و...)خودکار لود می‌شوند تا بک‌اند پیش‌فرض «از جعبه کار کند». انتخاب با ‏<category>.provider در config.yaml است ‏(مثل ‏image_gen.provider: openai).
ارائه‌دهنده‌های حافظه ‏(plugins/memory/)همه کشف می‌شوند؛ دقیقاً یکی فعال است که با ‏memory.provider در config.yaml انتخاب می‌شود.
موتورهای زمینه ‏(plugins/context_engine/)همه کشف می‌شوند؛ یکی فعال است که با ‏context.engine در config.yaml انتخاب می‌شود.
ارائه‌دهنده‌های مدل ‏(plugins/model-providers/)همهٔ ارائه‌دهنده‌های همراه‌بسته در اولین فراخوانی ‏get_provider_profile کشف و ثبت می‌شوند. کاربر در هر لحظه یکی را با ‏--provider یا config.yaml انتخاب می‌کند.
افزونه‌های ‏backend نصب‌شده با pipانتخابی با ‏plugins.enabled ‏(مثل افزونه‌های عمومی).
پلتفرم‌های نصب‌شده توسط کاربر ‏(زیر ‏~/.hermes/plugins/platforms/)انتخابی با ‏plugins.enabled — آداپتورهای گیت‌وی شخص ثالث رضایت صریح می‌خواهند.

خلاصه: زیربنای همراه‌بستهٔ «همیشه-کارا» خودکار لود می‌شود؛ افزونه‌های عمومی شخص ثالث انتخابی‌اند. لیست مجاز ‏plugins.enabled دقیقاً گیتِ کد دلخواهی است که کاربر داخل ‏~/.hermes/plugins/ می‌اندازد.

ترنسپورت‌های تأیید

یک ترنسپورت تأیید تغییر می‌دهد یک انسان کجا می‌بیند و جواب می‌دهد به یک درخواست تأیید ابزارِ موجود هرمس. تصمیم نمی‌گیرد آیا فرمانی نیاز به تأیید دارد و API سیاست-مجوز هم نیست.

python
def present(request):
    # Deliver request.command and request.description to your UI, wait for
    # its authenticated human response, then return a request-bound decision.
    choice = send_to_my_ui_and_wait(request)  # once/session/always/deny
    return request.respond(choice)


def register(ctx):
    ctx.register_approval_transport("my-ui", present)

‏present می‌تواند sync یا async باشد. هرمس روی worker محدود اجرایش می‌کند و ‏approvals.timeout مرجع را حتی اگر افزونه نگذارد اجرا می‌کند. درخواست تغییرناپذیر است و متن نمایشیِ سانسورشده، کلاس ارائهٔ میزبانش ‏(cli یا ‏gateway)، timeout میزبان، گزینه‌های مجاز و شناسه/digest مبهم درخواست را دارد.
نتیجهٔ ‏request.respond(choice) را برگردانید؛ دیکشنری‌های unbound و شناسه/digest های قدیمی یا عوض‌شده رد می‌شوند. افزونه نمی‌تواند scope‌ای برگرداند که میزبان پیشنهاد نکرده ‏(مثلاً ‏always روی درخواست فقط-یک‌بار).

ثبت به‌تنهایی هیچ نمی‌کند. فعال‌کردن افزونه و انتخاب صریح ترنسپورتش دو مرحلهٔ رضایت جدا هستند:

yaml
plugins:
  enabled: [my-approval-plugin]

security:
  approval:
    transport: my-ui
    transport_fallback: deny     # پیش‌فرض

استثناهای ترنسپورت، timeout ها، ثبت‌های ناموجود، گزینه‌های نامعتبر و پاسخ‌های کهنه به‌طور پیش‌فرض رد می‌شوند. برای اینکه عمداً پرامپت روی سطح عادی CLI/TUI/گیت‌وی/ACP وقتی ترنسپورت انتخابی شکست خورد نشان داده شود، ‏transport_fallback: builtin بگذارید. بدون همین انتخاب صریح، هرمس هرگز پرامپت را روی سطح دیگری materialize نمی‌کند.

هرمس همچنان مالک بلوک‌های سخت‌گیرانه، حفاظت sudo-stdin، قواعد رد کاربر، اتصال درخواست، scope های مجاز، ماندگاری، هوک‌ها و مجوز نهایی است. فرمان‌های hardline قبل از هر callback ترنسپورت بلاک می‌شوند. عمداً هیچ سیاست تأیید افزونه‌ای، callback اجازه-خودکار یا سیاست الزامی ‏pre_tool_call در این interface نیست. قابلیت سیاست-تأیید آینده ممکن است از مدل رضایت-قابلیت افزونه استفاده کند ولی انتخاب ترنسپورت آن را نمی‌دهد.

مهاجرت کاربران موجود

وقتی به نسخه‌ای از هرمس ارتقا دهید که افزونه‌های انتخابی دارد ‏(اسکیمای پیکربندی v21+)، هر افزونهٔ کاربری نصب‌شده زیر ‏~/.hermes/plugins/ که در ‏plugins.disabled نباشد خودکار grandfathered به ‏plugins.enabled می‌شود. setup فعلی‌تان به کار ادامه می‌دهد. افزونه‌های standalone همراه‌بسته NOT ‏grandfathered می‌شوند — حتی کاربران فعلی باید صریحاً انتخاب کنند. ‏(افزونه‌های پلتفرمی/بک‌اند همراه‌بسته هرگز نیازی به grandfathering نداشتند چون هیچ‌وقت گیت نشده بودند.)

۵ هوک‌های موجود

افزونه‌ها می‌توانند ۲۶ رویداد چرخه-حیات را ثبت کنند که الان ‏hermes_cli.plugins.VALID_HOOKS می‌پذیرد. کاتالوگ هوک‌های رویداد مرجع زمان‌بندی دقیق، هندل برگشتی، فیلدهای payload و یادداشت‌های حریم خصوصی است.

دستهٔ توصیفیهوک‌های عرضه‌شده
هدایتی/کنترلی‏pre_tool_call، ‏pre_llm_call، ‏pre_verify، ‏pre_gateway_dispatch
تبدیل‏transform_tool_result، ‏transform_terminal_output، ‏transform_llm_output، ‏pre_transcription
ناظر‏post_tool_call، ‏post_llm_call، ‏pre_api_request، ‏post_api_request، ‏api_request_error، ‏on_stream_start، ‏on_stream_delta، ‏on_stream_end، ‏on_interim_message، ‏on_session_start، ‏on_session_end، ‏on_session_finalize، ‏on_session_reset، ‏on_skill_lifecycle، ‏subagent_start، ‏subagent_stop، ‏pre_approval_request، ‏post_approval_response، ‏pre_command، ‏kanban_task_claimed، ‏kanban_task_completed، ‏kanban_task_blocked

این دسته‌ها رفتار فعلی را توصیف می‌کنند نه قواعد نام‌گذاری آینده را. middleware افزونه رجیستری/سطح جداگانه‌ای باقی است.

همه‌چیز افزونهٔ پایتونی نیست. بعضی سطوح توسعه عمداً از فرمان‌های شل محرک-config استفاده می‌کنند ‏(TTS، ‏STT، هوک‌های شل) تا هر CLI موجودتان بدون نوشتن پایتون تبدیل به افزونه شود. بعضی دیگر سرورهای خارجی‌اند ‏(MCP) که ایجنت به آن‌ها وصل و ابزارشان را خودکار ثبت می‌کند. و بعضی پوشه‌های drop-in‌اند ‏(هوک‌های گیت‌وی) با فرمت manifest خودشان. سطح مناسب با سبک یکپارچه‌سازی موردنیازتان را انتخاب کنید؛ راهنماهای نگارش بالای جدول هرکدام placeholder ها، کشف و مثال‌ها را پوشش می‌دهند.

۸ افزونه‌های اعلامی NixOS

در NixOS افزونه‌ها می‌توانند به‌صورت اعلامی از طریق گزینه‌های ماژول نصب شوند — بدون ‏hermes plugins install. جزئیات کامل در راهنمای Nix Setup.

nix
services.hermes-agent = {
  # Directory plugin (source tree with plugin.yaml)
  extraPlugins = [ (pkgs.fetchFromGitHub { ... }) ];
  # Entry-point plugin (pip package)
  extraPythonPackages = [ (pkgs.python312Packages.buildPythonPackage { ... }) ];
  # Enable in config
  settings.plugins.enabled = [ "my-plugin" ];
};

افزونه‌های اعلامی با پیشوند ‏nix-managed- symlink می‌شوند — با افزونه‌های نصب‌شدهٔ دستی هم‌زیستی دارند و با حذف از پیکربندی Nix خودکار پاک می‌شوند.

۹ مدیریت افزونه‌ها

bash
hermes plugins                               # UI تعاملی واحد
hermes plugins list                          # جدول: enabled / disabled / not enabled
hermes plugins search <term>                 # جست‌وجوی ایندکس افزونهٔ جامعه
hermes plugins install <name>                # نصب با نام ایندکس (حل‌شده به repo @ ref پین‌شده)
hermes plugins install user/repo             # نصب از Git، سپس پرسش Enable? [y/N]
hermes plugins install user/repo --enable    # نصب و فعال‌سازی (بدون پرسش)
hermes plugins install user/repo --no-enable # نصب ولی خاموش بماند (بدون پرسش)
hermes plugins update my-plugin              # کشیدن آخرین (ویرایش‌های محلی autostash و اعمال مجدد می‌شوند)
hermes plugins remove my-plugin              # حذف نصب
hermes plugins enable my-plugin              # افزودن به لیست مجاز
hermes plugins disable my-plugin             # حذف از لیست مجاز + افزودن به disabled
hermes plugins capabilities [my-plugin]      # قابلیت‌های اعلام‌شده در برابر اعطاشده

لینک‌های نصب یک‌کلیکی ‏(Desktop)

‏Hermes Desktop طرح URL ‏hermes:// را ثبت می‌کند، پس وب‌سایت، README یا پیام چت می‌تواند مستقیم به نصب افزونه لینک دهد:

text
hermes://plugin/install?repo=owner/repo            # لینک اصلی نصب
hermes://plugin/install?repo=owner/repo&enable=1   # فعال‌سازی افزونه ایجنت بعد از نصب
hermes://plugin/install?repo=owner/repo&force=1    # جایگزینی نصب موجود

کلیک، هرمس را باز و یک دیالوگ تأیید نشان می‌دهد — شناسهٔ repo، یادداشت «قبل از نصب» و لینک‌های browse و clone گیت‌هاب — سپس repo را shallow-clone می‌کند تا تشخیص دهد چه حمل می‌کند ‏(افزونهٔ agent — پایتون بک‌اند، افزونهٔ desktop — UI اپ، یا هر دو). مؤلفه‌ها را با چک‌باکس انتخاب و تأیید می‌کنید. تا تأیید شما چیزی نصب نمی‌شود؛ لینک‌های deep هرگز خودکار نصب نمی‌کنند و نصب افزونه‌های agent همان اسکن امنیتی زمان‌نصب ‏hermes plugins install را طی می‌کنند.

مخازن هیبریدی ‏(نیمه-agent + نیمه-desktop در یک repo) یک لینک و یک دیالوگ دارند. همین modal بدون لینک هم از مسیر ‏Settings ← Plugins ← Install from Git در دسترس است. URL های قدیمی ‏hermes://plugin-agent/… و ‏hermes://plugin-desktop/… به همان دیالوگ می‌روند. در build های dev ‏(npm run dev) طرح می‌شود ‏hermes-dev://.

وب‌سایت‌ها SDK لازم ندارند — anchor معمولی کافی است:

html
<a href="hermes://plugin/install?repo=owner/repo&enable=1">Install in Hermes</a>

سرورهای MCP فرم لینک معادل دارند — لینک «Add to Hermes» را در مرجع پیکربندی MCP ببینید.

۱۰ قابلیت‌های افزونه و رضایت

افزونه‌ها می‌توانند سطوح ممتاز میزبانی که می‌خواهند را در plugin.yaml‌شان اعلام کنند:

yaml
name: my-plugin
capabilities:
  - tools.override        # جایگزینی ابزارهای داخلی
  - llm.model_override    # انتخاب مدل برای فراخوانی‌های LLM متعلق-به-میزبان

وقتی افزونه‌ای قابلیت اعلام کند، ‏hermes plugins install ‏(و ‏hermes plugins enable) فهرست را با توضیح یک‌خطی ریسک نشان و یک‌بار می‌پرسد. رضایت، grant را زیر ‏plugins.entries.<id>.granted_capabilities همراه hash رضایت و timestamp ثبت می‌کند. رد کردن، افزونه را با آن قابلیت‌های خاموش فعال نگه می‌دارد — افزونهٔ خوش‌رفتار با ‏ctx.has_capability() probe می‌کند و با ملایمت تنزل می‌یابد.

رضایت مجدد به‌روزرسانی: اگر به‌روزرسانی افزونه‌ای قابلیتی اعلام کند که اعطا نکرده‌اید، ‏hermes plugins update افزوده‌ها را نشان و دوباره می‌پرسد. قابلیت‌های جدید خاموش می‌مانند تا رضایت بدهید — به‌روزرسانی افزونه هرگز نمی‌تواند دسترسی‌اش را بی‌صدا پهن کند.

نشست‌های غیرتعاملی fail-closed می‌شوند: نصب/به‌روزرسانی بدون TTY نصب را تمام می‌کند ولی قابلیت‌های اعلام‌شده اعطا نمی‌شوند. برای اعطای بعدی ‏hermes plugins enable <id> را تعاملی اجرا کنید.

هر وقت وضعیت را بازرسی کنید:

bash
hermes plugins capabilities             # همهٔ افزونه‌ها با قابلیت‌های declared/granted
hermes plugins capabilities my-plugin   # یک افزونه، declared vs granted

شناسه‌های قابلیت یک‌به‌یک به گیت‌های پیکربندی قدیمیِ هر-قابلیت نگاشت می‌شوند که همچنان کار می‌کنند ولی به نفع جریان رضایت deprecated شده‌اند:

قابلیتکلید قدیمی ‏(plugins.entries.<id>.…)
tools.overrideallow_tool_override
llm.provider_overridellm.allow_provider_override
llm.model_overridellm.allow_model_override
llm.agent_id_overridellm.allow_agent_id_override
llm.profile_overridellm.allow_profile_override
llm.task_overridellm.allow_task_override
gateway.platform_actionsallow_platform_actions

گیت وقتی باز است که یا قابلیت اعطا شده یا کلید قدیمی تنظیم شده باشد — پیکربندی‌های موجود بدون تغییر کار می‌کنند.

⚠️ سندباکس نیست

قابلیت‌ها یک لایهٔ رضایت و حسابرسی‌اند نه ایزوله‌سازی. افزونه‌ها مثل پایتون عادی درون-پروسه اجرا می‌شوند: افزونهٔ مخرب می‌تواند از هر گیت اینجا عبور کند. اعطای قابلیت بیان اعتماد به نویسندهٔ افزونه است — audit کد نیست و هرمس کد افزونه را بازبینی نکرده. فقط افزونه‌ها را از منابع مورداطمینان نصب کنید.

۱۱ اکشن‌های پلتفرمی

‏ctx.platform_actions به افزونه مجموعه‌فعل حداقلیِ گیت‌خورده-با-قابلیت برای عمل روی پلتفرم‌های چت متصل از طریق رجیستری زندهٔ آداپتور گیت‌وی می‌دهد — جایگزین تأییدشده برای monkeypatching آداپتور. پیش‌فرض خاموش است: هر فراخوانی قابلیت ‏gateway.platform_actions را دوباره چک می‌کند ‏(کلید قدیمی ‏plugins.entries.<id>.allow_platform_actions) و فراخوانی بدون اعطا به‌جای عمل، خطای ساختاریافته برمی‌گرداند.

افعال v1 ‏(هر دو async، هر دو dict ساده برمی‌گردانند و هیچ‌کدام هرگز به dispatch هوک exception نمی‌پراکنند):

python
result = await ctx.platform_actions.add_reaction(
    platform="telegram", chat_id="-100123", message_id="456", emoji="👍",
)
result = await ctx.platform_actions.set_thread_title(
    platform="discord", chat_id="123", thread_id="456", title="New title",
)
if not result["ok"]:
    print(result["error"], result.get("detail"))

موفقیت ‏{"ok": True, "action": <verb>} است. شکست‌ها ‏{"ok": False, "error": <code>, "detail": <str>} با کدهای خطای پایدارند: ‏capability_not_granted، ‏invalid_argument، ‏gateway_unavailable، ‏unknown_platform، ‏adapter_not_registered، ‏adapter_disconnected، ‏unsupported_platform_action، ‏action_failed. اکشن‌ها قبل از عمل تأیید می‌کنند آداپتور هدف موجود و متصل است؛ آداپتور قطع یا غایب به خطای ساختاریافته تنزل می‌یابد هرگز exception نمی‌شود.

پلتفرم‌های پشتیبان v1: تلگرام و دیسکورد. ‏add_reaction تلگرام واکنش بات را تنظیم می‌کند ‏(Bot API واکنش قبلی بات را جایگزین می‌کند نه انباشته). هر اکشن — مجاز یا رد — با شناسهٔ افزونه، فعل، پلتفرم و نتیجه لاگ می‌شود.

⚠️ یادداشت امنیتی

اکشن‌های پلتفرمی یک قدرت پیام‌رسانی-به‌عنوان-بات‌اند: افزونهٔ دارای grant می‌تواند در هر چتی که بات گیت‌وی به آن می‌رسد — نه فقط چت محرک هوک — react کند و تردها را rename کند. ‏gateway.platform_actions را فقط به افزونه‌های مورداطمینان بدهید و افزونه‌هایی را ترجیح دهید که دقیقاً مستند کرده‌اند چه اکشن‌هایی می‌زنند. دسترسی خام payload/handle SDK پلتفرم عمداً جزء این سطح نیست — طبق اصلاح طراحی دور-۲ شمارهٔ ۶۴۱۷۶ قابلیت خودش را ‏(gateway.raw_events) با برچسب «بدون تضمین پایداری» و طراحی جدا می‌خواهد و هنوز منتشر نشده.

۱۲ کشف افزونه‌های جامعه

‏hermes plugins search <term> در ایندکس افزونهٔ جامعه جست‌وجو می‌کند — کاتالوگ JSON استاتیک و ماشین‌خوانِ افزونه‌های جامعه. تطبیق فازی روی نام، توضیح و تگ‌هاست:

bash
hermes plugins search telegram               # جست‌وجوی فازی
hermes plugins search                        # مرور کل ایندکس
hermes plugins search --capability platform  # فیلتر بر اساس قابلیت اعلام‌شده
hermes plugins search media --json           # خروجی ماشین‌خوان
hermes plugins search --refresh              # رد شدن از کش محلی ۲۴ساعته

بعد از یافتن افزونه، با نام لخت نصبش کنید — نام از طریق ایندکس به ‏owner/repo به‌اضافهٔ commit پین‌شدهٔ ایندکس حل می‌شود:

hermes plugins install hermes-media-studio

اگر نامی با بیش از یک ورودی بخواند، کاندیداها فهرست و چیزی نصب نمی‌شود. شناسه‌های صریح ‏owner/repo یا URL گیت هرگز به ایندکس دست نمی‌زنند و دقیقاً مثل قبل کار می‌کنند. ‏--ref <sha> صریح همیشه بر پین ایندکس مقدم است.

نحوهٔ گرفتن ایندکس. ایندکس در URL مرجعی زندگی می‌کند ‏(https://raw.githubusercontent.com/NousResearch/hermes-plugin-index/main/index.json، قابل override با ‏hermes config set plugins.index_url <url>). دریافت‌ها ۲۴ ساعت زیر ‏~/.hermes/cache/plugin_index.json کش می‌شوند؛ وقتی مقصد راه‌دور غیرقابل‌دسترس است از کش کهنه و وقتی اصلاً کشی نیست از کپی seed همراه‌بسته استفاده می‌شود — پس search کاملاً آفلاین کار می‌کند.

  "added_at": "2026-08-12"
}

‏repo شناسهٔ گیت‌هابی ‏owner/name است، ‏ref یک commit SHA تغییرناپذیر را pin می‌کند و ‏subdir اختیاری monorepo ها را پشتیبانی می‌کند. فایل seed همراه‌بسته ‏(hermes_cli/data/plugin_index.json در مخزن) مرجع قالب است.

ارسال افزونه. ایندکس به‌عنوان فایل JSON ساده نگه داشته می‌شود — pull request به مخزن hermes-plugin-index بفرستید و ورودی‌تان را اضافه کنید ‏(نام، توضیح، نویسنده، تگ‌ها، ‏owner/repo و SHA commit پین‌شده). بازبینی فقط متادیتای ورودی را پوشش می‌دهد.

⚠️ ایندکس‌شده ≠ بازرسی‌شده

حضور در ایندکس جامعه یعنی متادیتای ورودی بازبینی شده — audit کد نیست. نصب همچنان از جریان عادی رضایت/بازبینی می‌گذرد ‏(نصب افزونه‌ها پیش‌فرض خاموش، فعال‌سازی گام صریح، و حق override ابزار grant جدا می‌خواهد). قبل از فعال‌کردن افزونه سورسش را بازبینی کنید.

۱۳ بسته‌های افزونه ‏(Plugin Packs)

بستهٔ افزونه فایل YAML اعلامی و اشتراک‌پذیری است ‏(hermes-pack.yaml) که مجموعه‌ای از افزونه‌ها را pin می‌کند — مثل به‌اشتراک‌گذاشتن یک modpack. نصب بسته به نصب‌های pinned معمولی fan-out می‌کند؛ در runtime هیچ چیز جدیدی وجود ندارد.

yaml
name: voice-assistant-pack
description: STT + streaming TTS + approval relay
author: hyper
version: 1.0.0
plugins:
  - name: hermes-media-studio            # نام لخت ایندکس جامعه…
    ref: e8d59971d2b7901405b39dac7b03bdd616272d0d
  - repo: owner/approval-relay           # …یا owner/repo صریح (یا URL گیت)
    ref: 8f3c2d1a9b4e5f6071829304a5b6c7d8e9f00112
    subdir: plugins/relay                # مسیر monorepo اختیاری
config:                                  # اختیاری، فقط seed های غیر-محرمانه
  hermes-media-studio:
    default_model: flux-3
skills: []                               # فقط فهرست اعلامی (هنوز خودکار نصب نمی‌شود)
bash
hermes plugins pack show ./hermes-pack.yaml     # بازبینی dry-run
hermes plugins pack install ./hermes-pack.yaml  # بازبینی → تأیید → نصب
hermes plugins pack export > hermes-pack.yaml   # snapshot نصب فعلی
hermes plugins pack export --enabled-only       # فقط plugins.enabled

وضعیت زنجیرهٔ تأمین. ‏ref هر ورودی باید دقیقاً SHA ‏commit چهل‌کاراکتری باشد — تگ‌ها و نام شاخه‌ها با خطایی که ورودی را نام می‌برد رد می‌شوند، همان قاعدهٔ ایندکس جامعه. نصب بسته دقیقاً از همان مسیر نصب پین‌شدهٔ ‏hermes plugins install --ref <sha> می‌رود و همان provenance را در ‏plugins/.install-metadata.json ثبت می‌کند، پس دو نصب از یک بسته یکسان حل می‌شوند. بسته‌ها روی فیلدهای manifest v2 ‏(manifest_version، ‏api_version، ‏requires_plugins) ساخته می‌شوند — manifest خود هر افزونه همچنان از مسیر نصب عادی اعتبارسنجی می‌شود.

رضایت هیچ‌وقت bulk اعطا نمی‌شود. ‏pack install صفحهٔ بازبینی اجباری نشان می‌دهد ‏(هر افزونه، منبع، ref پین‌شده و قابلیت‌های اعلامی‌اش)، بعد یک تأیید برای محتوای بسته می‌گیرد. بعد از آن قابلیت‌های اعلامی هر افزونه از پرامپت رضایت-قابلیت استاندارد به‌ازای-افزونه می‌گذرد — عیناً مثل یک ‏hermes plugins install تکی. ‏--yes وجود ندارد و نشست‌های غیرتعاملی نمی‌توانند بسته نصب کنند.

رمزها هرگز داخل بسته سفر نمی‌کنند. ‏seed های ‏config: به کلیدهای غیر-محرمانهٔ ‏plugins.entries.<id> محدودند — نام‌های کلید شبیه-رمز ‏(*token*، ‏*key*، ‏*password* و...)، grant های قابلیت و گیت‌های اعتماد قدیمی ‏allow_* هنگام نصب رد و هنگام export حذف می‌شوند. افزونه‌هایی که رمز می‌خواهند در ‏requires_env خودشان اعلام می‌کنند که مثل همیشه حین نصب پرسیده می‌شود. مقادیر موجود کاربر در ‏plugins.entries.<id> همیشه بر seed های بسته مقدم‌اند.

شکست جزئی. هر افزونه مستقل نصب می‌شود؛ شکست‌ها به‌ازای افزونه گزارش، بقیه ادامه می‌یابند و فرمان اگر افزونه‌ای شکست بخورد با کد غیرصفر خارج می‌شود.

نکات export. ‏pack export فقط افزونه‌هایی با provenance گیت شناخته ‏(نصب‌شده با ‏hermes plugins install) را شامل می‌شود. افزونه‌های فقط-محلی در YAML خروجی به‌صورت کامنت هشدار می‌آیند نه ورودی قابل‌نصب.

فهرست ‏skills: parse و هنگام نصب نمایش داده می‌شود ولی هنوز خودکار نصب نمی‌شود — فعلاً دستی نصبشان کنید ‏(hermes skills). سیم‌کشی شناسه‌های skill-hub به نصب بسته، درز پیگیری‌شدهٔ مستند است.

۱۴ اسکن امنیتی زمان‌نصب

هر ‏hermes plugins install و ‏hermes plugins update قبل از فعال‌شدن یک اسکن امنیتی استاتیک روی درخت افزونه اجرا می‌کند ‏(الهام از اسکن امنیتی skill و افزونهٔ Claude Cowork). اسکنر همان موتور الگو-تهدید Skills Hub Guard را بازمصرف می‌کند — خروج برداشتگاه‌های اعتبارنامه، reverse shell، فرمان‌های مخرب، مکانیزم‌های persistence، اجرای مبهم و prompt injection در فایل‌های مستندات — با معافیت‌های آگاه-از-افزونه: افزونهٔ provider که کلید API خودش را از محیط می‌خواند ‏(الگوی مستند ‏requires_env) فلگ نمی‌شود.

سه حکم، مطابق pass/warn/fail کاورک:

حکمرفتار
safeعادی نصب می‌شود، بدون خروجی اضافه
cautionیافته‌ها نشان داده می‌شوند؛ تأیید می‌کنید ‏Install anyway? [y/N] ‏(یا ‏--force)
dangerousبلوک می‌شود. ‏--force آن را override نمی‌کند

روی ‏hermes plugins update، حکم dangerous روی درخت به‌روزرسانی‌شده افزونه را تا بازبینی یافته‌ها و فعال‌سازی مجدد شما غیرفعال می‌کند.

اسکن پیش‌فرض روشن است؛ در config.yaml خاموشش کنید:

yaml
plugins:
  scan_on_install: false

۱۵ UI تعاملی

اجرای ‏hermes plugins بدون آرگومان یک صفحه تعاملی ترکیبی باز می‌کند:

text

  ↑↓ navigate  SPACE toggle  ENTER configure/confirm  ESC done

  General Plugins
 → [✓] my-tool-plugin — Custom search tool
   [ ] webhook-notifier — Event hooks
   [ ] disk-cleanup — Auto-cleanup of ephemeral files [bundled]

  • بخش General Plugins — چک‌باکس‌ها، تغییر با SPACE. تیک‌دار = داخل ‏plugins.enabled، بی‌تیک = داخل ‏plugins.disabled ‏(خاموش صریح).
  • بخش Provider Plugins — انتخاب فعلی را نشان می‌دهد. ENTER را بزنید تا وارد picker رادیویی شوید و یک ارائه‌دهندهٔ فعال انتخاب کنید.
  • افزونه‌های همراه‌بسته با تگ ‏[bundled] در همان فهرست ظاهر می‌شوند.

انتخاب‌های افزونهٔ provider در config.yaml ذخیره می‌شود:

yaml
memory:
  provider: "honcho"      # رشتهٔ خالی = فقط داخلی

context:
  engine: "compressor"    # فشرده‌ساز داخلی پیش‌فرض

فعال در برابر غیرفعال در برابر هیچ‌کدام

افزونه‌ها یکی از سه وضعیت را دارند:

وضعیتمعنیداخل plugins.enabled؟داخل plugins.disabled؟

پیش‌فرض افزونهٔ تازه‌نصب یا همراه‌بسته ‏not enabled است. ‏hermes plugins list هر سه حالت متمایز را نشان می‌دهد تا بدانید چه چیزی صریحاً خاموش شده و چه چیزی فقط منتظر فعال‌سازی است.

در نشست در حال اجرا، ‏/plugins نشان می‌دهد کدام افزونه‌ها الان لودند.

۱۶ تزریق پیام‌ها

افزونه‌ها می‌توانند با ‏ctx.inject_message() پیامی به گفتگوی CLI یا نشست گیت‌وی شناخته تزریق کنند:

python
# گفتگوی فعال CLI
ctx.inject_message("New data arrived from the webhook", role="user")

# گفتگوی موجود گیت‌وی
ctx.inject_message(
    "New data arrived from the webhook",
    role="user",
    session_key="agent:main:telegram:dm:123456789",
)

امضا: ‏ctx.inject_message(content: str, role: str = "user", *, session_key: str | None = None) -> bool

در حالت CLI:

  • اگر ایجنت idle باشد ‏(منتظر ورودی کاربر)، پیام به‌عنوان ورودی بعدی صف و نوبت جدید شروع می‌شود.
  • اگر ایجنت میان-نوبت باشد ‏(فعلاً در حال اجرا)، پیام عملیات فعلی را قطع می‌کند — مثل اینکه کاربر پیام جدید تایپ و Enter بزند.
  • برای نقش‌های غیر-"user" محتوا با ‏[role] پیشوند می‌گیرد ‏(مثل ‏[system] ...).
  • اگر پیام موفقانه صف شد ‏True برمی‌گرداند.

در حالت گیت‌وی:

  • ‏session_key الزامی است و باید نشست موجود گیت‌وی را مشخص کند. کلید مسیریابی پایدار است نه شناسهٔ نشست CLI.
  • هرمس پلتفرم، چت، ترد، پروفایل و تاریخچهٔ گفتگوی ذخیره‌شدهٔ همان نشست را بازمصرف می‌کند. افزونه‌ها نمی‌توانند از طریق این API مسیر چت جدیدی بدهند.
  • هرمس قبل از dispatch مسیر ذخیره‌شده را دوباره علیه قواعد مجوز فعلی گیت‌وی چک می‌کند.
  • مسیرهایی که فقط به تصمیم احرازِ لحظه-آداپتور یا بالادستی تکیه داشتند رد می‌شوند مگر هرمس بتواند آنها را از لیست‌های مجاز فعلی هسته، pairing یا پیکربندی صریح allow-all دوباره اعتبارسنجی کند.
  • متن تزریق‌شده همیشه ورودی گفتگویی است. نمی‌تواند فرمان اسلش invoke، ابزار تأیید یا پرامپت‌های در انتظار تأیید/شفاف‌سازی را حل کند.
  • تا وقتی dispatch در انتظار است، مسیر و گفتگو قفل می‌شوند. اگر بازیابی topic مسیر را عوض کند یا نشست قبل از شروع هندل بچرخد هرمس درخواست را دور می‌ریزد.
  • درخواست وارد مسیر عادی پیام آداپتور پلتفرم می‌شود. نشست‌های فعال از صف busy-session موجود استفاده می‌کنند نه شروع نوبت رقیب.
  • وقتی گیت‌وی زنده درخواست را برای dispatch ناهمگام می‌پذیرد ‏True برمی‌گرداند. این تأیید نمی‌کند نوبت ایجنت یا تحویل پلتفرمی تمام شده.
  • وقتی ‏session_key حذف شده، مجوز اعطا نشده یا گیت‌وی زنده‌ای درخواست را نمی‌پذیرد ‏False برمی‌گرداند. کلیدهای نشست ناشناخته یا غیرقابل-مسیریابی که بعد از پذیرش ناهمگام پیدا شوند در لاگ گیت‌وی نوشته می‌شوند.

این افزونه‌هایی مثل viewer های کنترل-از-راه‌دور، پل‌های پیام‌رسانی یا گیرنده‌های وب‌هوک را ممکن می‌کند پیام‌ها را از منابع خارجی به گفتگو بدهند.

تزریق گیت‌وی می‌تواند پاسخ ایجنت را به یک پلتفرم پیام‌رسانی خارجی بفرستد. به‌طور پیش‌فرض برای هر افزونه خاموش است. به‌ازای هر افزونه در config.yaml اعطا کنید:

yaml
plugins:
  entries:
    my-plugin:
      allow_gateway_injection: true
⚠️ هشدار

تزریق گیت‌وی را فقط به افزونه‌های مورداطمینان اعطا کنید. هرمس این مجوز API میزبان را چک و به مسیرهای نشست موجود محدود می‌کند ولی افزونه‌های پایتونی درون-پروسه اجرا می‌شوند و این تنظیم سندباکس نیست.

📌 یادداشت

این API افزونه endpoint HTTP عمومی یا فرمان CLI برای پروسه‌های خارجی expose نمی‌کند. افزونه باید از قبل ‏session_key هدف گیت‌وی را بشناسد، مثلاً از پیکربندی مطمئن خودش یا وضعیت نشستِ قبلاً نگهداری‌شده.

۱۷ صدازدن سرورهای MCP از افزونه‌ها

‏ctx.call_mcp() اجازه می‌دهد افزونه ابزاری روی یکی از سرورهای MCP پیکربندی‌شدهٔ کاربر را — همگام، از داخل هر هوک یا هندل ابزار — صدا بزند و از طریق کلاینت native MCP موجود هرمس مسیریابی شود ‏(همان اتصالات، گیت‌های trust-tier، مدارشکن و منطق reconnect ابزارهای MCP فراخوانی‌شده-با-مدل؛ هرگز کلاینت موازی).

python
result = ctx.call_mcp(
    "knowledge_rag",            # نام سرور از mcp.servers
    "query_knowledge",          # ابزار روی همان سرور
    {"query": "deploy runbook"},
    timeout=30,                 # ثانیه؛ محدود به ۱–۶۰۰
)
if result["ok"]:
    print(result["result"])
else:
    print("MCP error:", result["error"])

امضا: ‏ctx.call_mcp(server: str, tool: str, arguments: dict | None = None, timeout: float = 30) -> dict

پاکت پایدار برمی‌گرداند: ‏{"ok": True, "result": ...} ‏(+ ‏structuredContent وقتی سرور بدهد) یا ‏{"ok": False, "error": "..."}. نتایج بالای ~۶۴ کیلوبایت بریده و با ‏"truncated": True فلگ می‌شوند.

امنیت: پیش‌فرض خاموش، لیست مجاز به‌ازای-سرور

افزونه به‌طور پیش‌فرض هیچ دسترسی MCP ندارد. اپراتور باید هر سرور را صریحاً در config.yaml اعطا کند:

yaml
plugins:
  entries:
    my-plugin:
      mcp_allowlist: ["knowledge_rag", "github"]
  • صدازدن سروری خارج از فهرست ‏PermissionError می‌دهد و کلید پیکربندی دقیقی که باید ست شود را نام می‌برد.
  • اعطا به‌ازای-سرور و به‌ازای-افزونه است — هرگز اقتدار محیطی روی همهٔ سرورهای پیکربندی‌شده، و wildcard ‏«"*"» پذیرفته نمی‌شود.
  • هر فراخوانی timeout اجراشده دارد ‏(پیش‌فرض ۳۰ ثانیه) تا سرور MCP معلق نتواند خط‌لوله هوک یا ابزارِ فراخواننده را stall کند.
  • سرورهای MCP محتوای غیرقابل‌اعتماد برمی‌گردانند. ‏result را داده تلقی کنید نه دستورالعمل — بدون اعتبارسنجی وارد تصمیمات ممتازش نکنید ‏(تأییدها، اجرای فرمان).
⚠️ هشدار

اعطای ‏mcp_allowlist به افزونه همان دسترسی مدل به آن سرور MCP را می‌دهد — شامل هر ابزار دارای-قابلیت-نوشتنی که سرور expose کند ‏(مشروط به گیت‌های tier ‏trust سرور). فقط سرورهایی را اعطا کنید که افزونه واقعاً لازم دارد.

راهنمای کامل را برای قراردادهای هندلر، قالب schema، رفتار هوک، هندل خطا و اشتباهات رایج ببینید.
