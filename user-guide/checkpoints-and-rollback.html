خانه/کار با Hermes/چک‌پوینت و بازگشت

چک‌پوینت‌ها و /rollback

هرمس ایجنت می‌تواند پیش از عملیات مخرب به‌طور خودکار از پروژهٔ شما اسنپ‌شات بگیرد و با یک فرمان آن را بازیابی کند. چک‌پوینت‌ها از نسخهٔ v2 اختیاری شده‌اند — اغلب کاربران هرگز از /rollback استفاده نمی‌کنند و ذخیره‌گاه سایه‌ای در طول زمان سبک نیست، پس پیش‌فرض خاموش است.

با --checkpoints به‌ازای-نشست فعالش کنید:

bash
hermes chat --checkpoints

یا به‌صورت سراسری در ~/.hermes/config.yaml:

yaml
checkpoints:
  enabled: true

این تور ایمنی توسط یک **مدیر چک‌پوینت** داخلی قدرت می‌گیرد که یک مخزن گیتِ سایه‌ایِ مشترکِ واحد را زیر ~/.hermes/checkpoints/store/ نگه می‌دارد — به .git واقعی پروژهٔ شما هرگز دست نمی‌خورد. هر پروژه‌ای که ایجنت در آن کار می‌کند همان ذخیره‌گاه را به اشتراک می‌گذارد، پس دیتابیس اشیای محتوامنشأِ گیت بین پروژه‌ها و بین نوبت‌ها هم‌پوشانی‌ها را حذف می‌کند.

۱ چه چیزی چک‌پوینت را تریگر می‌کند

چک‌پوینت‌ها به‌طور خودکار پیش از این‌ها گرفته می‌شوند:

  • ابزارهای فایل — ‏write_file و patch
  • فرمان‌های ترمینالی مخرب — ‏rm، ‏rmdir، ‏cp، ‏install، ‏mv، ‏sed -i، ‏truncate، ‏dd، ‏shred، ریدایرکت‌های خروجی‏ (>) و git reset/clean/checkout

ایجنت حداکثر یک چک‌پوینت به‌ازای هر پوشه در هر نوبت می‌سازد، پس نشست‌های طولانی اسنپ‌شات اسپم نمی‌کنند.

۲ مرجع سریع

فرمان‌های اسلش درون‌نشستی:

فرمانتوضیح
/rollbackفهرست همهٔ چک‌پوینت‌ها با آمار تغییر
/rollback <N>بازیابی به چک‌پوینت N با حفظ ویرایش‌های دستی شما (آخرین نوبت چت را هم خنثی می‌کند)
/rollback <N> --allبازیابی کامل — ویرایش‌های دستی شما را هم بازنویسی می‌کند
/rollback diff <N>پیش‌نمایش دیف بین چک‌پوینت N و وضعیت فعلی
/rollback <N> <file>بازیابی یک فایل تکی از چک‌پوینت N

‏CLI برای بازبینی و مدیریت ذخیره‌گاه بیرون از نشست:

فرمانتوضیح
hermes checkpointsنمایش حجم کل، شمار پروژه، تفکیک به‌ازای-پروژه
hermes checkpoints statusهمان checkpoints خالی
hermes checkpoints listنام‌مستقل status
hermes checkpoints pruneاجبار جاروب: حذف یتیم‌ها/کهنه‌ها، ‏GC، اجرای سقف حجم
hermes checkpoints clearنابودی کل پایهٔ چک‌پوینت (اول می‌پرسد)
hermes checkpoints clear-legacyحذف فقط آرشیوهای legacy-* از مهاجرت v1

۳ چک‌پوینت‌ها چگونه کار می‌کنند

در سطح بالا:

  • هرمس تشخیص می‌دهد کِی ابزارها در شرف تغییر فایل‌ها در درخت کاری شما هستند.
  • یک بار در هر نوبت گفتگو (به‌ازای پوشه):
    • ریشهٔ پروژهٔ معقولی برای فایل حل می‌کند.
    • ذخیره‌گاه سایه‌ای مشترک واحد را در ~/.hermes/checkpoints/store/ مقداردهی یا بازاستفاده می‌کند.
    • در اندکسی به‌ازای-پروژه stage می‌کند، یک tree می‌سازد و به ref مخصوص پروژه‏ (refs/hermes/<project-hash>) کامیت می‌زند.
  • این refهای به‌ازای-پروژه تاریخچه‌ای از چک‌پوینت‌ها می‌سازند که می‌توانید با /rollback بازبینی و بازیابی‌شان کنید.
text — جریان
user ──▶ agent ──▶ tools ──▶ cpMgr ──▶ store (shadow git)
                        ◀──────┘
        tools قبل از هر جهش: ensure_checkpoint()
        cpMgr با git add/commit-tree/update-ref کامیت می‌زند

۴ پیکربندی

در ~/.hermes/config.yaml پیکربندی کنید:

yaml
checkpoints:
  enabled: false              # کلید اصلی (پیش‌فرض: false — اختیاری)
  max_snapshots: 20           # حداکثر چک‌پوینت به‌ازای پروژه (با بازنویسی ref + gc اجرا می‌شود)
  max_total_size_mb: 500      # سقف سفت حجم کل ذخیره‌گاه؛ قدیمی‌ترین کامیت‌ها انداخته می‌شوند
  max_file_size_mb: 10        # رد هر فایل تکیِ بزرگ‌تر از این

  # نگهداری خودکار (پیش‌فرض روشن): جاروب ~/.hermes/checkpoints/ هنگام شروع
  # و حذف مدخل‌های پروژه‌ای که last_touch‌شان از retention_days گذشته.
  # حداکثر یک بار در min_interval_hours اجرا می‌شود، با نشانگر .last_prune
  # پیگیری. این جاروب هرگز مدخل‌های «یتیم» (پوشهٔ کاری پیدا نشدنی) را حذف
  # نمی‌کند — نبودِ workdir هنگام شروع مبهم است (پروژهٔ حذف‌شده در برابر
  # والوم خارجیِ مانت‌نشده / اشتراک شبکه‌ای / VPN هنوز-بالا-نیامده)، پس
  # پاک‌سازی یتیم‌ها فقط از طریق فرمان صریح `hermes checkpoints prune`
  # پایین، با اعلان تأیید انجام می‌شود.
  auto_prune: true
  retention_days: 7
  min_interval_hours: 24

برای خاموش‌کردن همه‌چیز:

yaml
checkpoints:
  enabled: false
  auto_prune: false

وقتی enabled: false است، مدیر چک‌پوینت no-op است و هرگز عملیات گیت را تلاش نمی‌کند. وقتی auto_prune: false است، ذخیره‌گاه رشد می‌کند تا وقتی hermes checkpoints prune را دستی اجرا کنید.

۵ فهرست‌کردن چک‌پوینت‌ها

از یک نشست CLI:

فرمان در چت
/rollback

هرمس با فهرستی قالب‌بندی‌شده نشان‌دهندهٔ آمار تغییر پاسخ می‌دهد:

خروجی
📸 Checkpoints for /path/to/project:

  1. 4270a8c  2026-03-16 04:36  before patch  (1 file, +1/-0)
  2. eaf4c1f  2026-03-16 04:35  before write_file
  3. b3f9d2e  2026-03-16 04:34  before terminal: sed -i s/old/new/ config.py  (1 file, +1/-1)

  /rollback <N>             restore to checkpoint N (keeps your hand-edits)
  /rollback <N> --all       full restore, overwriting your hand-edits too
  /rollback diff <N>        preview changes since checkpoint N
  /rollback <N> <file>      restore a single file from checkpoint N

بازبینی ذخیره‌گاه از شل

bash
hermes checkpoints

اجبار جاروب کامل (نشانگر همانی ۲۴ ساعته را نادیده می‌گیرد):

bash
hermes checkpoints prune --retention-days 3 --max-size-mb 200

۶ پیش‌نمایش تغییرات با /rollback diff

پیش از پایبندشدن به بازیابی، ببینید از یک چک‌پوینت به بعد چه تغییری کرده:

فرمان در چت
/rollback diff 1

این یک خلاصهٔ diff stat گیت و سپس دیف واقعی را نشان می‌دهد.

۷ بازیابی با /rollback

فرمان در چت
/rollback 1

در پس‌زمینه، هرمس:

  1. وجود کامیت هدف را در ذخیره‌گاه سایه‌ای تأیید می‌کند.
  2. یک اسنپ‌شات پیش-بازگشت از وضعیت فعلی می‌گیرد تا بعداً بتوانید «خنثی‌کردنِ خنثی‌کردن» کنید.
  3. فایل‌های ردیابی‌شده را در پوشهٔ کاری شما بازیابی می‌کند — با حفظ ویرایش‌های دستی‌تان (پایین را ببینید).
  4. آخرین نوبت گفتگو را خنثی می‌کند تا زمینهٔ ایجنت با وضعیت فایل‌سیستمِ بازیابی‌شده مطابق شود.

ویرایش‌های دستی کاربر به‌طور پیش‌فرض حفظ می‌شوند

/rollback <N> فقط فایل‌هایی را بازیابی می‌کند که خود هرمس تغییر داده. هر write_file / ‏patch موفق، هش محتوای فایل را در یک دفتر نوشتارهای ایجنت ثبت می‌کند؛ هنگام بازیابی، هر فایلی که محتوای فعلی‌اش دیگر با آخرین چیزی که هرمس نوشته مطابق نباشد (بعدش ویرایشش کرده‌اید، یا هرمس هرگز لمسش نکرده) به‌جای بازنویسی رد می‌شود و در خروجی فهرست می‌گردد:

خروجی
✅ Restored to checkpoint a1b2c3d4: before write_file
↷ Kept your hand-edits: src/config.py, notes.md
Use /rollback <N> --all to restore those too.

برای اجبار بازیابی کاملِ کلاسیک که همه‌چیز — شامل ویرایش‌های خودتان — را برمی‌گرداند، ‏--all اضافه کنید:

فرمان در چت
/rollback 1 --all

اگر دفتر خالی باشد (ذخیره‌گاهی از پیش از این قابلیت، یا هرمس هنوز در پروژه فایلی ننوشته)، ‏/rollback خودکار به بازیابی کامل برمی‌گردد.

بازیابی تک‌فایل

فقط یک فایل را از یک چک‌پوینت بازیابی کنید بدون اثر بر بقیهٔ پوشه:

فرمان در چت
/rollback 1 src/broken_file.py

۸ گاردهای ایمنی و کارایی

  • موجودیت گیت — اگر git روی PATH پیدا نشود، چک‌پوینت‌ها شفاف غیرفعال می‌شوند.
  • دامنهٔ پوشه — هرمس پوشه‌های بیش‌ازحد گسترده را رد می‌کند (ریشهٔ /، ‏خانگی $HOME).
  • حجم مخزن — پوشه‌های بیش از ۵۰٬۰۰۰ فایل رد می‌شوند.
  • سقف حجم به‌ازای-فایل — فایل‌های بزرگ‌تر از max_file_size_mb (پیش‌فرض ۱۰ مگابایت) از اسنپ‌شات مستثنی‌اند. جلوی بلعیدن تصادفی دیتاست‌ها، وزن‌های مدل یا رسانه‌های تولیدی را می‌گیرد.
  • سقف حجم کل ذخیره‌گاه — وقتی ذخیره‌گاه از max_total_size_mb (پیش‌فرض ۵۰۰ مگابایت) بگذرد، قدیمی‌ترین کامیتِ هر پروژه به‌صورت گردشی انداخته می‌شود تا زیر سقف بیاید.
  • هرس واقعی — ‏max_snapshots با بازنویسی ref به‌ازای-پروژه و اجرای git gc --prune=now بعدش اجرا می‌شود، تا اشیای آزاد انباشته نشوند.
  • اسنپ‌شات‌های بدون-تغییر — اگر از آخرین اسنپ‌شات تغییری نباشد، چک‌پوینت رد می‌شود.
  • خطاهای غیرکشنده — همهٔ خطاهای داخل مدیر چک‌پوینت در سطح دیباگ لاگ می‌شوند؛ ابزارهای شما به کار ادامه می‌دهند.

۹ چک‌پوینت‌ها کجا زندگی می‌کنند

text
~/.hermes/checkpoints/
  ├── store/                 # مخزن گیت bare مشترک واحد
  │   ├── HEAD, objects/     # داخل‌های گیت (بین پروژه‌ها مشترک)
  │   ├── refs/hermes/<hash> # نوک شاخه به‌ازای-پروژه
  │   ├── indexes/<hash>     # اندکس گیت به‌ازای-پروژه
  │   ├── projects/<hash>.json  # workdir + created_at + last_touch
  │   └── info/exclude
  ├── .last_prune            # نشانگر همانیِ هرس خودکار
  └── legacy-<ts>/           # مخازن سایه‌ای به‌ازای-پروژه از پیش-v2 آرشیو‌شده

هر <hash> از مسیر مطلق پوشهٔ کاری مشتق می‌شود. معمولاً هرگز لازم نیست دستی به این‌ها دست بزنید — به‌جایش از hermes checkpoints status / ‏prune / ‏clear استفاده کنید.

مهاجرت از v1

پیش از بازنویسی v2، هر پوشهٔ کاری مخزن سایه‌ای گیتِ کاملِ خودش را مستقیم زیر ~/.hermes/checkpoints/<hash>/ می‌گرفت. آن چیدمان نمی‌توانست اشیا را بین پروژه‌ها هم‌پوشانی‌زدایی کند و یک هرس‌کنندهٔ no-op مستند داشت — ذخیره‌گاه بی‌کران رشد می‌کرد.

در اولین اجرای v2، هر مخزن سایه‌ای پیش-v2 به ~/.hermes/checkpoints/legacy-<timestamp>/ منتقل می‌شود تا چیدمان تک‌ذخیره‌ایِ جدید تمیز شروع شود. تاریخچهٔ قدیمی /rollback همچنان با بازبینی دستی آرشیو legacy با git در دسترس است؛ وقتی مطمئن شدید لازمش ندارید، اجرا کنید:

bash
hermes checkpoints clear-legacy

تا فضا پس گرفته شود. آرشیوهای legacy همچنین توسط auto_prune پس از retention_days جاروب می‌شوند.

۱۰ بهترین شیوه‌ها

  • چک‌پوینت‌ها را فقط وقتی لازم‌اند فعال کنید — ‏hermes chat --checkpoints یا enabled: true به‌ازای-پروفایل.
  • قبل از بازیابی از /rollback diff استفاده کنید — پیش‌نمایش آنچه تغییر خواهد کرد تا چک‌پوینت درست را بردارید.
  • وقتی فقط می‌خواهید تغییرات ایجنت‌محور را خنثی کنید، به‌جای git reset از /rollback استفاده کنید.
  • اگر چک‌پوینت‌ها را مرتب استفاده می‌کنید، گاهی hermes checkpoints status را چک کنید — نشان می‌دهد کدام پروژه‌ها فعال‌اند و ذخیره‌گاه چه هزینه‌ای برایتان دارد.
  • برای حداکثر ایمنی با گیت‌ورک‌تری ترکیب کنید — هر نشست هرمس را در ورک‌تری/شاخهٔ خودش نگه دارید، با چک‌پوینت‌ها به‌عنوان لایهٔ اضافی.

برای اجرای چند ایجنت موازی روی همان مخزن، به راهنمای «گیت‌ورک‌تری» مراجعه کنید.
