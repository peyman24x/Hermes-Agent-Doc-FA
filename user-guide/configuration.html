پیکربندی

همهٔ تنظیمات برای دسترسی آسان در پوشهٔ ~/.hermes/ ذخیره می‌شوند.

💡 آسان‌ترین مسیر تا config.yaml کاری

hermes setup --portal را اجرا کنید — یک OAuth هم ارائه‌دهندهٔ مدل و هم هر چهار ابزار گیت‌وی ابزار را می‌گیرد بدون ویرایش دستی YAML. مشترکان پورتال همچنین ۱۰٪ تخفیف روی ارائه‌دهندگان صورت‌حساب-توکنی می‌گیرند. به «Nous Portal» مراجعه کنید.

۱ ساختار پوشه

text
~/.hermes/
├── config.yaml     # تنظیمات (مدل، ترمینال، TTS، فشرده‌سازی و غیره)
├── .env            # کلیدهای API و رازها
├── auth.json       # اعتبار ارائه‌دهندگان OAuth (‏Nous Portal و غیره)
├── SOUL.md         # هویت اصلی ایجنت (جایگاه ۱ در پرامپت سیستمی)
├── memories/       # حافظهٔ پایدار (‏MEMORY.md، ‏USER.md)
├── skills/         # مهارت‌های ایجنت‌ساخته (مدیریت با ابزار skill_manage)
├── cron/           # کارهای زمان‌بندی‌شده
├── sessions/       # نشست‌های گیت‌وی
└── logs/           # لاگ‌ها (errors.log، gateway.log — رازها خودکار پاک می‌شوند)

۲ مدیریت پیکربندی

bash
hermes config              # مشاهدهٔ پیکربندی فعلی
hermes config edit         # باز کردن config.yaml در ادیتور شما
hermes config get KEY      # چاپ مقدار حل‌شده
hermes config set KEY VAL  # تنظیم مقدار مشخص
hermes config unset KEY    # حذف مقدار تنظیم‌شده توسط کاربر
hermes config check        # بررسی گزینه‌های مفقود (بعد از به‌روزرسانی)
hermes config migrate      # افزودن تعاملی گزینه‌های مفقود

# مثال‌ها:
hermes config get model
hermes config set model anthropic/claude-opus-4
hermes config set terminal.backend docker
hermes config unset terminal.backend
hermes config set OPENROUTER_API_KEY sk-or-...  # در .env ذخیره می‌شود
💡 نکته

فرمان hermes config set خودکار مقادیر را به فایل درست می‌فرستد — کلیدهای API در .env و همه‌چیز دیگر در config.yaml ذخیره می‌شود.

۳ اولویت پیکربندی

تنظیمات به این ترتیب حل می‌شوند (اول بیشترین اولویت):

  1. آرگومان‌های CLI — مثل hermes chat --model anthropic/claude-sonnet-4 (بازنویسی به‌ازای-فراخوانی)
  2. ~/.hermes/config.yaml — فایل پیکربندی اصلی همهٔ تنظیمات غیررمزی
  3. ~/.hermes/.env — جایگزین متغیرهای محیطی؛ برای رازها الزامی است (کلیدهای API، توکن‌ها، رمزها)
  4. پیش‌فرض‌های داخلی — پیش‌فرض‌های امنِ هاردکد وقتی هیچ‌چیز دیگر تنظیم نشده
ℹ️ قاعدهٔ سرانگشتی

رازها (کلیدهای API، توکن‌های بات، رمزها) در .env می‌روند. بقیه (مدل، بک‌اند ترمینال، تنظیمات فشرده‌سازی، سقف‌های حافظه، تول‌ست‌ها) در config.yaml. وقتی هر دو تنظیم شده‌اند، برای تنظیمات غیررمزی config.yaml می‌برد.

💡 استقرارهای سازمانی

مدیر می‌تواند پیکربندی و مقادیر رمزی خاصی را که کاربر عادی نمی‌تواند بازنویسی کند، از طریق یک پوشهٔ مدیریت‌شدهٔ سطح-سیستم پین کند. به «دامنهٔ مدیریت‌شده» مراجعه کنید.

۴ محدودیت‌های زمان اجرا

سطوح سرور بلندمدت هرمس (شامل گیت‌وی و hermes serve --isolated) هنگام شروع، سقف نرمِ پیکربندی‌شدهٔ RLIMIT_NOFILE را وقتی سیستم‌عامل پشتیبانی کند اعمال می‌کنند:

yaml
runtime:
  nofile_soft_limit: 4096

پیش‌فرض 4096 است. هرمس هدف را به سقف سخت سیستم‌عامل محدود و هرگز پروسه‌ای که از قبل سقف نرم بالاتری دارد را پایین نمی‌آورد. مقدار را 0، ‏false یا null بگذارید تا تنظیم غیرفعال شود. در ویندوز و سندباکس‌هایی که سقف قابل تغییر نیست، شروع بدون تغییر سقف ادامه می‌یابد.

۵ جایگزینی متغیرهای محیطی

می‌توانید در config.yaml با نگارش ${VAR_NAME} به متغیرهای محیطی اشاره کنید:

yaml
auxiliary:
  vision:
    api_key: ${GOOGLE_API_KEY}
    base_url: ${CUSTOM_VISION_URL}

delegation:
  api_key: ${DELEGATION_KEY}

چند ارجاع در یک مقدار کار می‌کند: url: "${HOST}:${PORT}". اگر متغیر ارجاع‌شده تنظیم نباشد، جانگهدار تحت‌اللفظی می‌ماند (${UNDEFINED_VAR} همان‌طور که هست می‌ماند) و هشداری لاگ می‌شود. $VAR خالی گسترش نمی‌یابد.

نگارش SecretRef به سبک Cursor هم پذیرفته می‌شود: ${env:VAR_NAME} دقیقاً مثل ${VAR_NAME} حل می‌شود (پیشوند env: کنده می‌شود)، پس قطعات MCP یا ارائه‌دهندهٔ کپی‌شده از تنظیمات Cursor / ‏Claude هم در config.yaml و هم بلوک mcp_servers بدون تغییر کار می‌کنند. سایر منابع SecretRef‏ (${file:...}، ‏${vault:...}، ‏${bitwarden:...}) درجا حل نمی‌شوند — بک‌اندهای راز خارجی مقادیرشان را هنگام شروع از طریق بلوک secrets: به محیط تزریق می‌کنند، پس به‌صورت ${env:NAME} به آن‌ها اشاره کنید؛ پیشوندهای ناشناخته یک بار هشدار می‌گیرند و تحت‌اللفظی می‌مانند.

برای راه‌اندازی ارائه‌دهندگان هوش مصنوعی (‏OpenRouter، ‏آنتروپیک، ‏Copilot، اندپوینت‌های سفارشی، ‏LLMهای خودمیزبان، مدل‌های fallback و غیره) به صفحهٔ «ارائه‌دهندگان هوش مصنوعی» مراجعه کنید.

تایم‌اوت‌های ارائه‌دهنده

می‌توانید providers.<id>.request_timeout_seconds را برای تایم‌اوت درخواست در سطح ارائه‌دهنده بگذارید، به‌علاوهٔ providers.<id>.models.<model>.timeout_seconds برای بازنویسی مخصوص-مدل. روی کلاینت نوبتِ اصلی در همهٔ ترنسپورت‌ها (‏OpenAI-wire، ‏آنتروپیک بومی، آنتروپیک-سازگار)، زنجیرهٔ fallback، بازسازی‌ها پس از چرخش اعتبارنامه و (برای OpenAI-wire) آرگومان کلیدواژهٔ تایم‌اوت به‌ازای-درخواست اعمال می‌شود — پس مقدار پیکربندی‌شده بر متغیر محیطی قدیمی HERMES_API_TIMEOUT مقدم است.

همچنین providers.<id>.stale_timeout_seconds برای آشکارساز فراخوانیِ بی‌پاسخِ غیراستریمی، به‌علاوهٔ بازنویسی مخصوص-مدلش. این بر متغیر قدیمی HERMES_API_CALL_STALE_TIMEOUT مقدم است.

تنظیم‌نگذاشتن این‌ها پیش‌فرض‌های قدیمی را نگه می‌دارد‏ (HERMES_API_TIMEOUT=1800 ثانیه، ‏HERMES_API_CALL_STALE_TIMEOUT=90 ثانیه، آنتروپیک بومی ۹۰۰ ثانیه). آشکارساز بی‌پاسخِ غیراستریمی برای اندپوینت‌های محلی وقتی ضمنی رها شده خودکار غیرفعال و برای زمینه‌های خیلی بزرگ رو به بالا مقیاس می‌شود. فعلاً برای AWS Bedrock سیم‌ نشده‏ (هر دو مسیر bedrock_converse و SDK مربوط به AnthropicBedrock از boto3 با پیکربندی تایم‌اوت خودش استفاده می‌کنند). مثال کامنت‌گذاری‌شده در cli-config.yaml.example مخزن را ببینید.

۶ رفتار به‌روزرسانی

تنظیمات hermes update زیر updates در config.yaml زندگی می‌کنند:

yaml
updates:
  pre_update_backup: quick       # quick (اسنپ‌شات وضعیت، پیش‌فرض) | full (اسنپ‌شات + زیپ HERMES_HOME) | off
  backup_keep: 5                 # حفظ این تعداد زیپِ پشتیبان کامل پیش-به‌روزرسانی
  non_interactive_local_changes: stash  # stash | discard
  auto_switch_parked_branch: true       # بازگردانی خودکار شاخهٔ پارک‌شدهٔ تمیزِ کاملاً-merge‌شده به main

pre_update_backup تنهای پیچ ایمنیِ پیش-به‌روزرسانی است: quick (پیش‌فرض) از فایل‌های وضعیت حیاتی (دادهٔ جفت‌سازی، کارهای کرون، پیکربندی، احراز؛ فایل‌های بالای ۱ گیگابایت رد می‌شوند) در state-snapshots/ اسنپ‌شات می‌گیرد؛ ‏full به‌علاوه کل HERMES_HOME را در backups/ زیپ می‌کند و روی خانه‌های بزرگ می‌تواند چند دقیقه اضافه کند؛ ‏off هر دو را خاموش می‌کند. بولی‌های قدیمی محترم شمرده می‌شوند‏ (true ← full، ‏false ← off).

برای نصب‌های گیت، هرمس پیش از checkout شاخهٔ به‌روزرسانی یا pull، فایل‌های ردیابی‌شدهٔ کثیف و untrackedها را خودکار stash می‌کند. به‌روزرسانی‌های ترمینالیِ تعاملی پیش از بازگردانی آن stash می‌پرسند. به‌روزرسانی‌های غیرتعاملی (دسکتاپ/اپ چت، گیت‌وی یا --yes) از updates.non_interactive_local_changes استفاده می‌کنند: stash ویرایش‌های محلی سورس را پس از pull موفق بازمی‌گرداند، discard stashِ ساخته‌شده-به‌روزرسانی را پس از pull موفق می‌اندازد. discard را فقط روی نصب‌های مدیریت‌شده‌ای بگذارید که ویرایش محلی سورس هرگز قرار نیست بماند.

پیش از آن گام stash، هرمس دیف‌های ردیابی‌شدهٔ package-lock.jsonی که چرخهٔ npm install/build جا گذاشته هم بازمی‌گرداند. ویرایش‌های عمدی lockfile را قبل از به‌روزرسانی کامیت یا دستی stash کنید.

۷ پیکربندی بک‌اند ترمینال

هرمس هفت بک‌اند ترمینال دارد. هر کدام تعیین می‌کند فرمان‌های شلی ایجنت واقعاً کجا اجرا می‌شوند — ماشین محلی شما، یک کانتینر داکر، سرور راهن از طریق SSH، سندباکس ابری Modal، ورک‌اسپیس Daytona، ‏Vercel Sandbox یا کانتینر Singularity/Apptainer.

yaml
terminal:
  backend: local    # local | docker | ssh | modal | daytona | vercel_sandbox | singularity
  cwd: "."          # پوشهٔ کاری گیت‌وی/کرون (‏CLI همیشه پوشهٔ اجرا را می‌گیرد)
  font_family: ""   # فونت ترمینال دسکتاپ؛ مثل "MesloLGS NF"
  timeout: 180      # تایم‌اوت به‌ازای-فرمان به ثانیه
  home_mode: auto   # auto | real | profile — سیاست HOME زیرپروسه‌ها
  env_passthrough: []  # نام متغیرهای محیطی برای فوروارد به اجرای سندباکسی (terminal + execute_code)
  singularity_image: "docker://nikolaik/python-nodejs:python3.11-nodejs20"  # ایمیج کانتینر Singularity
  modal_image: "nikolaik/python-nodejs:python3.11-nodejs20"                 # ایمیج کانتینر Modal
  daytona_image: "nikolaik/python-nodejs:python3.11-nodejs20"               # ایمیج کانتینر Daytona

terminal.font_family ترمینال جاسازی‌شده در هرمس دسکتاپ را کنترل می‌کند. یک نام خانوادهٔ محلی‌نصب (مثلاً MesloLGS NF) یا یک پشتهٔ فونت CSS می‌پذیرد. هرمس پشتهٔ JetBrains Mono همراهش را به‌عنوان جایگزین می‌افزاید و مقدار خالی پیش‌فرض را نگه می‌دارد. همان تنظیمِ در-دامنهٔ پروفایل را در Settings ← Appearance ← Terminal Font هم می‌توانید ویرایش کنید؛ بدون دانلود Google Fonts یا مجوز فونت-سیستم.

برای سندباکس‌های ابری مثل Modal، ‏Daytona و Vercel Sandbox، ‏container_persistent: true یعنی هرمس تلاش می‌کند وضعیت فایل‌سیستم را در بازسازی سندباکس حفظ کند. وعده نمی‌دهد همان سندباکس زنده، فضای PID یا پروسه‌های پس‌زمینه بعداً هنوز در حال اجرا باشند.

بک‌اند local

پیش‌فرض. فرمان‌ها مستقیم روی ماشین شما بدون ایزوله‌سازی اجرا می‌شوند. بدون راه‌اندازی خاص.

yaml
terminal:
  backend: local

به‌طور پیش‌فرض، زیرپروسه‌های ابزار محلی HOME واقعیِ کاربر OS شما را نگه می‌دارند. این به CLIهای خارجی مثل git، ‏ssh، ‏gh، ‏az، ‏npm، ‏Claude Code و Codex اجازه می‌دهد اعتبارنامه‌ها و پیکربندی‌ای را که از قبل در شل عادی‌تان استفاده می‌کنند پیدا کنند. وضعیت هرمس همچنان از طریق HERMES_HOME در-دامنهٔ پروفایل است؛ HOME آن چیزی نیست که پروفایل‌ها پیکربندی، حافظه، نشست یا مهارت انتخاب می‌کنند.

هرمس HOME سراسری-سیستم شما، فایل‌های راه‌اندازی شل یا خانهٔ حساب سیستم‌عامل را تغییر نمی‌دهد. این تنظیم فقط محیط پاس‌داده‌شده به زیرپروسه‌هایی را کنترل می‌کند که هرمس از طریق ابزارهایی مثل terminal، پروسه‌های ترمینال پس‌زمینه، ‏execute_code و پروسه‌های کمکی ACP راه می‌اندازد.

terminal.home_mode

حالتنصب‌های میزبانکانتینرهامبادله
autoHOME واقعی کاربر OS نگه داشته می‌شود{HERMES_HOME}/home استفاده می‌شودپیش‌فرض توصیه‌شده. ‏CLIهای میزبان کار می‌کنند؛ وضعیت کانتینر می‌ماند.
realاجبار HOME واقعی کاربر OSاجبار HOME واقعی اگر مرئی باشدمفید اگر پروسهٔ والدی تصادفاً با HOME اشاره‌شده به خانهٔ پروفایل شروع شده باشد.
profile{HERMES_HOME}/home وقتی موجود است{HERMES_HOME}/home وقتی موجود استایزوله‌سازی سخت‌گیرانهٔ پیکربندی CLI به‌ازای-پروفایل، ولی ~/.ssh، ‏~/.gitconfig، ‏~/.azure، ‏~/.config/gh، احراز Claude/Codex، وضعیت npm و غیره مرئی نخواهند بود مگر داخل خانهٔ پروفایل مقداردهی یا لینکشان کنید.

نقطه‌ضعف پیش‌فرض این است که پروفایل‌های میزبان همان اعتبارنامه/پیکربندی سطح-کاربر عادیِ زیر ~ را به اشتراک می‌گذارند. اگر پروفایلی با هویت گیت جداگانه، کلیدهای SSH، ورود GitHub CLI، پیکربندی npm یا ورود CLI ابری می‌خواهید، از home_mode: profile استفاده و آن ابزارها را آگاهانه داخل خانهٔ همان پروفایل مقداردهی کنید.

yaml
terminal:
  home_mode: profile

در آن حالت زیرپروسه‌های ابزار از {HERMES_HOME}/home به‌عنوان HOME استفاده می‌کنند. هرمس همچنین HERMES_REAL_HOME را می‌گذارد تا اسکریپت‌ها بتوانند خانهٔ واقعی کاربر را وقتی لازم دارند پیدا کنند. بک‌اندهای کانتینری در حالت auto همچنان از {HERMES_HOME}/home استفاده می‌کنند چون آن پوشه روی والوم دادهٔ پایدار هرمس زندگی می‌کند.

اسکریپت‌هایی که باید وضعیت پروفایل را از خانهٔ واقعی کاربر تفکیک کنند، برای دادهٔ هرMES از HERMES_HOME و برای خانهٔ حساب از HERMES_REAL_HOME استفاده کنند:

python
from pathlib import Path
import os

hermes_home = Path(os.environ["HERMES_HOME"])
real_home = Path(os.environ.get("HERMES_REAL_HOME", os.environ["HOME"]))

ایجنت همان دسترسی فایل‌سیستم را دارد که حساب کاربری شما. با hermes tools ابزارهای ناخواسته را غیرفعال کنید، یا برای سندباکس‌شدن به داکر بروید.

بک‌اند docker

فرمان‌ها داخل کانتینر داکری با سخت‌سازی امنیتی اجرا می‌شوند (حذف همهٔ قابلیت‌ها، بدون ارتقای امتیاز، محدودیت PID).

یک کانتینر ماندگار، مشترک بین پروسه‌های هرمس. هرمس در اولین استفاده یک کانتینر طولانی‌عمرِ واحد شروع و هر فراخوانی ترمینال، فایل و execute_code را از طریق docker exec به همان کانتینر هدایت می‌کند — بین نشست‌ها، ‏/new، ‏/reset و ساب‌ایجنت‌های delegate_task. تغییرهای پوشهٔ کاری، پکیج‌های نصب‌شده، فایل‌های /workspace و پروسه‌های پس‌زمینه همه از فراخوانی ابزاری به بعدی و از پروسهٔ هرمسی به بعدی باقی می‌مانند. وقتی نشست TUI را می‌بندید، ‏/quit می‌زنید یا هرمس جدیدی شروع می‌کنید، کانتینر به کار ادامه می‌دهد و پروسهٔ بعدی هرمس از طریق lookup برچسب‌دار دوباره استفاده‌اش می‌کند. قواعد دقیق teardown را در «چرخهٔ حیات کانتینر» پایین ببینید.

حالت ایزوله‌سازی به‌ازای-نشست‏ (container_persistent: false). با این تنظیم روی بک‌اند داکر، به یک کانتینر به‌ازای هر نشست سوییچ می‌شود: هر چت (نشست اپ دسکتاپ، گفتگوی گیت‌وی، نشست TUI) سندباکس تازهٔ خودش را می‌گیرد که در اولین فراخوانی ترمینال/فایل ساخته و با بسته‌شدن نشست یا بیکاری بیش از lifetime_seconds حذف می‌شود. هیچ‌چیز بین نشست‌ها منتقل نمی‌شود — نه وضعیت فایل‌سیستم، نه مانت‌ها، نه پروسه‌های پس‌زمینه. با docker_mount_cwd_to_workspace: true فقط ورک‌اسپیسِ متصل به همان نشست در /workspace مانت می‌شود؛ نشست تازهٔ بدون پوشهٔ متصل، ورک‌اسپیس خالی می‌گیرد به‌جای ارث‌بردن مانت نشست قبلی. ساب‌ایجنت‌های delegate_task همچنان کانتینر نشستِ والدشان را به اشتراک می‌گذارند. این حالت را وقتی استفاده کنید که سندباکس مرز امنیتی بین گفتگوهاست؛ پیش‌فرض true را نگه دارید وقتی کانتینرِ بلندعمرِ مشترکِ بالا را می‌خواهید.

yaml
terminal:
  backend: docker
  docker_image: "nikolaik/python-nodejs:python3.11-nodejs20"
  docker_mount_cwd_to_workspace: false  # مانت پوشهٔ اجرا در /workspace
  docker_run_as_host_user: false   # «اجرا به‌عنوان کاربر میزبان» را پایین ببینید
  docker_forward_env:              # متغیرهای محیطی میزبان برای فوروارد داخل کانتینر
    - "GITHUB_TOKEN"
  docker_env:                      # متغیرهای تحت‌اللفظی برای تزریق (KEY=value)
    DEBUG: "1"
    PYTHONUNBUFFERED: "1"
  docker_volumes:                  # مانت‌های پوشهٔ میزبان
    - "/home/user/projects:/workspace/projects"
    - "/home/user/data:/data:ro"   # :ro یعنی فقط‌خواندنی
  docker_extra_args:               # پرچم‌های اضافی تحت‌اللفظی به `docker run`
    - "--gpus=all"
    - "--network=host"
  docker_network: true             # false = قطع شبکهٔ کانتینر (--network=none)

  # محدودیت‌های منابع
  container_cpu: 1                 # هسته‌های CPU (‏۰ = نامحدود)
  container_memory: 5120           # مگابایت (‏۰ = نامحدود)
  container_disk: 51200            # مگابایت (نیازمند overlay2 روی XFS+pquota)
  container_persistent: true       # true = ماندگاری /workspace + /root، کانتینر مشترک؛ false = کانتینر تازه به‌ازای-نشست

  # استفادهٔ مجدد کانتینر بین پروسه‌ها (پیش‌فرض‌ها با قرارداد «یک کانتینر بلندعمرِ
  # مشترک بین نشست‌ها» هم‌راستا هستند — چرخهٔ حیات را ببینید).
  docker_persist_across_processes: true   # استفادهٔ مجدد کانتینر بین ری‌استارت‌های هرمس
  docker_orphan_reaper: true              # جاروب کانتینرهای Exited رهاشده هنگام شروع

  # تنظیمات چرخهٔ حیات بین-بک‌اندی (روی داکر هم اعمال می‌شوند)
  timeout: 180                     # تایم‌اوت به‌ازای-فرمان به ثانیه
  lifetime_seconds: 300            # پنجرهٔ هرسِ بیکاری؛ آستانهٔ هرس یتیم هم ۲ برابر همین است

docker_env در برابر docker_forward_env: اولی جفت‌های تحت‌اللفظی KEY=valueای که در پیکربندی مشخص می‌کنید تزریق می‌کند (مقادیر در config.yaml شما زندگی می‌کنند یا به‌صورت دیکشنری JSON با TERMINAL_DOCKER_ENV='{"DEBUG":"1"}' پاس می‌شوند). دومی مقادیر را از شل یا ~/.hermes/.env فوروارد می‌کند، پس راز واقعی هرگز در فایل پیکربندی ظاهر نمی‌شود. برای توکن‌ها از docker_forward_env و برای پیچ‌های ایستایی که کانتینر لازم دارد از docker_env استفاده کنید.

terminal.docker_extra_args (قابل بازنویسی با TERMINAL_DOCKER_EXTRA_ARGS='["--gpus=all"]') اجازه می‌دهد پرچم‌های دلخواه docker runی را که هرمس به‌صورت درجه‌یک عرضه نکرده پاس دهید — ‏--gpus، ‏--network، ‏--add-host، بازنویسی‌های جایگزین --security-opt و غیره. هر مدخل باید رشته باشد؛ فهرست در انتهای فراخوانی docker run الصاق می‌شود تا بتواند در صورت نیاز پیش‌فرض‌های هرمس را بازنویسی کند. کم استفاده کنید — پرچم‌هایی که با سخت‌سازی سندباکس تعارض دارند (حذف قابلیت‌ها، ‏--user، مانت ورک‌اسپیس) ایزوله‌سازی را خاموش تضعیف می‌کنند.

terminal.docker_network (پیش‌فرض true؛ ‏env: ‏TERMINAL_DOCKER_NETWORK) — روی false بگذارید تا کانتینر سندباکس با --network=none اجرا شود و همهٔ خروجی شبکه از فرمان‌های ایجنت قطع شود. روی کانتینر اجراییِ استفاده‌شده توسط terminal، ‏execute_code و ابزارهای فایل اعمال می‌شود. چون کانتینرها بین پروسه‌های هرمس می‌مانند، ‏false کردن وقتی کانتینر شبکه‌دار قدیمی‌ای هست، آن کانتینر را حذف و یک قطع‌شده-از-شبکهٔ تازه می‌سازد (هشداری لاگ می‌شود)؛ پروسه‌های پس‌زمینهٔ داخلش از دست می‌روند. این کلید را به‌جای پاس‌دادن --network=none از docker_extra_args ترجیح دهید.

نیازمندی‌ها: Docker Desktop یا Docker Engine نصب و در حال اجرا. هرمس $PATH به‌علاوهٔ مسیرهای نصب رایج مک‏ (/usr/local/bin/docker، ‏/opt/homebrew/bin/docker، باندل اپ Docker Desktop) را می‌کاود. پودمن هم از جعبه پشتیبانی می‌شود: HERMES_DOCKER_BINARY=podman (یا مسیر کامل) را بگذارید تا وقتی هر دو نصب‌اند اجبار شود.

چرخهٔ حیات کانتینر

هر کانتینرِ مدیریت‌شده-با-هرمس با سه برچسب تگ می‌خورد تا پروسه‌های بعدی (و هرس‌کنندهٔ یتیم) بتوانند شناسایی‌اش کنند:

  • hermes-agent=1 — نشان‌دادنِ مدیریت‌شده-با-هرمس
  • hermes-task-id=<sanitized task_id> — کلید کردنِ کاوِ استفادهٔ مجدد به‌ازای-کار
  • hermes-profile=<sanitized profile name> — دامنه‌دادن استفادهٔ مجدد و هرس به پروفایل فعال هرمس

هنگام شروع، هرمس docker ps --filter label=hermes-task-id=<id> --filter label=hermes-profile=<profile> را اجرا و وقتی یکی پیدا کند به کانتینر موجود می‌چسبد. اگر کانتینر exited باشد (مثلاً پس از ری‌استارت دیمن داکر)، docker start و استفادهٔ مجدد می‌شود — وضعیت فایل‌سیستم و پکیج‌های نصب‌شده جان سالم می‌برند، ولی پروسه‌های پس‌زمینهٔ درون‌کانتینری نه.

وقتی پروسهٔ هرمس خارج می‌شود — /quit، بستن نشست TUI، خاموشی گیت‌وی، حتی SIGKILL — مسیر پاک‌سازی در حالت پیش‌فرض برای کانتینر no-op است. کانتینر به کار ادامه می‌دهد. پروسهٔ بعدی هرمس در میلی‌ثانیه‌ها از طریق کاوِ برچسب به آن می‌چسبد. این رفتاری است که قرارداد «یک کانتینر بلندعمرِ مشترک بین نشست‌ها» لازم دارد: تنها راه بقاى پروسه‌های پس‌زمینه (watcherهای npm، سرورهای dev، ‏pytest طولانی) بین نشست‌ها همین است.

کانتینر فقط در این موارد تخریب می‌شود (متوقف و docker rm -f):

تریگرکی فعال می‌شود
docker_persist_across_processes: falseایزوله‌سازی صریح به‌ازای-پروسه. هر cleanup() ‏stop + ‏rm -f می‌کند. مطابق رفتار پیش از issue شمارهٔ ۲۰۵۶۱.
هرس بیکاری‏ (lifetime_seconds، پیش‌فرض ۳۰۰ ثانیه)فقط وقتی محیط persist_across_processes=false است. محیط‌های ماندگار no-op می‌شوند؛ کانتینر از جاروب بیکاری جان سالم می‌برد.
هرس یتیم در شروع بعدیکانتینرهای برچسب‌دار هرمسِ ‏Exited بالای ۲ × lifetime_seconds (پیش‌فرض ۶۰۰ ثانیه = ۱۰ دقیقه) را در دامنهٔ پروفایل فعلی جاروب می‌کند. کانتینرهای Running هرگز لمس نمی‌شوند — ایمنی پروسه‌های خواهر. docker_orphan_reaper: false برای غیرفعال‌کردن.
اقدام مستقیم کاربرdocker rm -f، ‏docker system prune، ری‌استارت Docker Desktop. ما --restart=always نمی‌گذاریم، پس ری‌بوت میزبان کانتینر را Exited می‌گذارد (لایهٔ CoW جان سالم می‌برد و در شروع بعدی بازاستفاده می‌شود، ولی پروسه‌های پس‌زمینه رفته‌اند).

حالت‌های مرزی شایان دانستن:

  • کشتن OOM‏ِ PID 1 داخل کانتینر وضعیت را به Exited می‌برد. استفادهٔ مجدد بعدی docker start می‌کند؛ وضعیت فایل‌سیستم می‌ماند، پروسه‌های پس‌زمینه نه.
  • تعویض پروفایل کانتینرها را از هم ایزوله می‌کند — کانتینری با برچسب hermes-profile=work برای پروسهٔ هرمسی که زیر hermes-profile=research اجرا می‌شود نامرئی است. هرس یتیم هم در دامنهٔ پروفایل است، پس کانتینرهای بین‌پروفایلی تصادفاً هرس نمی‌شوند، ولی تا وقتی دوباره زیر پروفایل اصلی‌شان هرمس اجرا نکنید خودکار پاک هم نمی‌شوند.

ساب‌ایجنت‌های موازیِ تولیدشده با delegate_task(tasks=[...]) از همین یک کانتینر استفاده می‌کنند — cdهای هم‌زمان، جهش‌های محیط و نوشتن به همان مسیر با هم تصادم می‌کنند. اگر ساب‌ایجنتی سندباکس ایزوله لازم دارد، باید بازنویسی ایمیج به‌ازای-کار را با register_task_env_overrides() ثبت کند، که محیط‌های RL و بنچمارک‏ (TerminalBench2، ‏HermesSweEnv و غیره) برای ایمیج‌های داکری به‌ازای-کارِ خودشان خودکار انجام می‌دهند.

سخت‌سازی امنیتی:

  • --cap-drop ALL با فقط DAC_OVERRIDE، ‏CHOWN، ‏FOWNER برگردانده‌شده
  • --security-opt no-new-privileges
  • --pids-limit 256
  • tmpfs با سقف حجم برای /tmp (‏۵۱۲MB)، ‏/var/tmp (‏۲۵۶MB) و /run (‏۶۴MB)

فوروارد اعتبارنامه: متغیرهای فهرست‌شده در docker_forward_env اول از محیط شل شما حل می‌شوند، بعد ~/.hermes/.env. مهارت‌ها هم می‌توانند required_environment_variables اعلام کنند که خودکار مرج می‌شوند.

بک‌اند ssh

فرمان‌ها روی سرور راهن از طریق SSH اجرا می‌شوند. از ControlMaster برای استفادهٔ مجدد اتصال استفاده می‌کند (نگه‌داشتن ۵ دقیقه‌ای بیکاری). شل پایدار به‌طور پیش‌فرض فعال است — وضعیت (cwd، متغیرهای محیط) بین فرمان‌ها می‌ماند.

yaml + bash
terminal:
  backend: ssh
  persistent_shell: true           # نگه‌داشتن نشست bash بلندعمر (پیش‌فرض: true)

# متغیرهای محیطی لازم (در ~/.hermes/.env):
TERMINAL_SSH_HOST=my-server.example.com
TERMINAL_SSH_USER=ubuntu

اختیاری‌ها:

متغیرپیش‌فرضتوضیح
TERMINAL_SSH_PORT22پورت SSH
TERMINAL_SSH_KEY(پیش‌فرض سیستم)مسیر کلید خصوصی SSH
TERMINAL_SSH_PERSISTENTtrueفعال‌کردن شل پایدار

نحوهٔ کار: هنگام مقداردهی با BatchMode=yes و StrictHostKeyChecking=accept-new وصل می‌شود. شل پایدار یک پروسهٔ bash -l را روی میزبان راهن زنده نگه می‌دارد و از طریق فایل‌های موقت ارتباط می‌گیرد. فرمان‌هایی که stdin_data یا sudo می‌خواهند خودکار به حالت یک‌باره برمی‌گردند.

بک‌اند modal

فرمان‌ها در سندباکس ابری Modal اجرا می‌شوند. هر کار یک VM ایزوله با CPU، حافظه و دیسک قابل‌پیکربندی می‌گیرد. فایل‌سیستم می‌تواند بین نشست‌ها اسنپ‌شات/بازیابی شود.

yaml
terminal:
  backend: modal
  container_cpu: 1                 # هسته‌های CPU
  container_memory: 5120           # مگابایت (۵GB)
  container_disk: 51200            # مگابایت (۵۰GB)
  container_persistent: true       # اسنپ‌شات/بازیابی فایل‌سیستم

لازم: یا متغیرهای MODAL_TOKEN_ID + ‏MODAL_TOKEN_SECRET، یا فایل پیکربندی ~/.modal.toml.

ماندگاری: وقتی فعال باشد، فایل‌سیستم سندباکس هنگام پاک‌سازی اسنپ‌شات و در نشست بعدی بازیابی می‌شود. اسنپ‌شات‌ها در ~/.hermes/modal_snapshots.json پیگیری می‌شوند. این وضعیت فایل‌سیستم را حفظ می‌کند، نه پروسه‌های زنده، فضای PID یا کارهای پس‌زمینه.

فایل‌های اعتبارنامه: به‌طور خودکار از ~/.hermes/ مانت (توکن‌های OAuth و غیره) و پیش از هر فرمان همگام می‌شوند.

بک‌اند daytona

فرمان‌ها در ورک‌اسپیس مدیریت‌شدهٔ Daytona اجرا می‌شوند. توقف/ازسرگیری برای ماندگاری را پشتیبانی می‌کند.

yaml
terminal:
  backend: daytona
  container_cpu: 1                 # هسته‌های CPU
  container_memory: 5120           # مگابایت → به GiB تبدیل می‌شود
  container_disk: 10240            # مگابایت → به GiB تبدیل می‌شود (حداکثر ۱۰ GiB)
  container_persistent: true       # توقف/ازسرگیری به‌جای حذف

لازم: متغیر محیطی DAYTONA_API_KEY.

ماندگاری: وقتی فعال باشد، سندباکس‌ها هنگام پاک‌سازی متوقف (نه حذف) و در نشست بعدی ازسر گرفته می‌شوند. نام سندباکس‌ها از الگوی hermes-{task_id} پیروی می‌کند.

سقف دیسک: دیتونا حداکثر ۱۰ GiB را اجباری می‌کند. درخواست‌های بالاتر با هشدار سقف می‌خورند.

بک‌اند vercel_sandbox

فرمان‌ها در میکروVM ابری Vercel Sandbox اجرا می‌شوند. هرمس از سطوح عادی ابزار ترمینال و فایل استفاده می‌کند؛ ابزار رو-به-مدلِ مخصوص ورسل وجود ندارد.

yaml + bash
terminal:
  backend: vercel_sandbox
  vercel_runtime: node24          # node24 | node22 | python3.13
  cwd: /vercel/sandbox            # ریشهٔ ورک‌اسپیس پیش‌فرض
  container_persistent: true      # اسنپ‌شات/بازیابی فایل‌سیستم
  container_disk: 51200           # فقط پیش‌فرض مشترک؛ دیسک سفارشی پشتیبانی نمی‌شود

# نصب لازم: بستهٔ اختیاری SDK
pip install 'hermes-agent[vercel]'

# احراز لازم: هر سه‌ی VERCEL_TOKEN، VERCEL_PROJECT_ID و VERCEL_TEAM_ID
# برای توسعهٔ محلیِ موردی، توکن کوتاه‌عمر OIDC ورسل هم پذیرفته می‌شود:
VERCEL_OIDC_TOKEN="$(vc project token <project-name>)" hermes chat

این راه‌اندازیِ پشتیبانی‌شده برای استقرارها و پروسه‌های بلندمدت عادی هرمس روی Render، ‏Railway، داکر و میزبان‌های مشابه است. توکن‌های OIDC کوتاه‌عمرند و نباید مسیر استقرارِ مستند باشند.

ماندگاری: با container_persistent: true، هرمس فایل‌سیستم سندباکس را هنگام پاک‌سازی اسنپ‌شات و سندباکسِ بعدیِ همان کار را از آن اسنپ‌شات بازیابی می‌کند. محتوای اسنپ‌شات می‌تواند اعتبارنامه‌ها، مهارت‌ها و فایل‌های کشِ همگام‌شده-با-هرمسِ کپی‌شده داخل سندباکس را شامل شود. فقط وضعیت فایل‌سیستم حفظ می‌شود؛ هویت زندهٔ سندباکس، فضای PID، وضعیت شل یا پروسه‌های پس‌زمینهٔ در حال اجرا نه.

فرمان‌های پس‌زمینه: terminal(background=true) از جریان عمومیِ پروسهٔ پس‌زمینهٔ غیر-محلی هرمس استفاده می‌کند. تا وقتی سندباکس زنده است می‌توانید از طریق ابزار process معمولی پروسه تولید، poll، منتظر ماند، لاگ دید و کشتن. هرمس بازیابیِ بومیِ پروسهٔ جداشدهٔ ورسل پس از پاک‌سازی یا ری‌استارت ارائه نمی‌دهد.

اندازهٔ دیسک: Vercel Sandbox فعلاً پیچِ منبع container_disk هرمس را پشتیبانی نمی‌کند. container_disk را تنظیم‌نشده یا روی پیش‌فرض مشترک 51200 بگذارید؛ مقادیر غیرپیش‌فرض به‌جای نادیده‌گرفتن خاموش، تشخیص‌ها و ساخت بک‌اند را شکست می‌دهند.

بک‌اند singularity/apptainer

فرمان‌ها در کانتینر Singularity/Apptainer اجرا می‌شوند. برای خوشه‌های HPC و ماشین‌های مشترکی که داکر در دسترس نیست طراحی شده.

yaml
terminal:
  backend: singularity
  singularity_image: "docker://nikolaik/python-nodejs:python3.11-nodejs20"
  container_cpu: 1                 # هسته‌های CPU
  container_memory: 5120           # مگابایت
  container_persistent: true       # اورلی قابل‌نوشتن بین نشست‌ها می‌ماند

نیازمندی‌ها: باینری apptainer یا singularity در $PATH.

هندل ایمیج: ‏URLهای داکری‏ (docker://...) خودکار به فایل SIF تبدیل و کش می‌شوند. فایل‌های .sif موجود مستقیم استفاده می‌شوند.

پوشهٔ scratch: به ترتیب حل می‌شود: TERMINAL_SCRATCH_DIR ← ‏TERMINAL_SANDBOX_DIR/singularity ← ‏/scratch/$USER/hermes-agent (قرارداد HPC) ← ‏~/.hermes/sandboxes/singularity.

ایزوله‌سازی: از --containall --no-home برای ایزوله‌سازی کامل namespace بدون مانت پوشهٔ خانگی میزبان.

مشکلات رایج بک‌اندهای ترمینال

اگر فرمان‌های ترمینال بلافاصله شکست می‌خورند یا ابزار ترمینال غیرفعال گزارش می‌شود:

  • محلی — بدون نیازمندی خاص. امن‌ترین پیش‌فرض هنگام شروع.
  • داکر — ‏docker version را اجرا کنید تا درستی کار داکر تأیید شود. اگر شکست خورد، داکر را درست کنید یا hermes config set terminal.backend local.
  • SSH — هر دوی TERMINAL_SSH_HOST و TERMINAL_SSH_USER باید تنظیم باشند. هرمس در نبود هرکدام خطای روشنی لاگ می‌کند.
  • Modal — متغیر MODAL_TOKEN_ID یا ~/.modal.toml لازم. hermes doctor را اجرا کنید.
  • Daytona — DAYTONA_API_KEY لازم. ‏SDK دیتونا پیکربندی URL سرور را هندل می‌کند.
  • Singularity — apptainer یا singularity در $PATH لازم. روی خوشه‌های HPC رایج است.

وقتی شک دارید، terminal.backend را به local برگردانید و اول درستی اجرا شدن فرمان‌ها را همان‌جا تأیید کنید.

همگام‌سازی وضعیت راهن-به-میزبان هنگام تخریب

برای بک‌اندهای SSH، ‏Modal و Daytona، هرمس وضعیت ~/.hermes/ شما (فایل‌های اعتبارنامه، مهارت‌ها، کش) را حین نشست به سندباکس راهن می‌فرستد، و هنگام تخریب فایل‌های وضعیتِ تغییرکرده را به مکان‌های اصلی میزبان برمی‌گرداند. فایل‌هایی که با آنچه در اصل فرستاده شده تفاوت دارند (مقایسه با هش محتوا) درجا اعمال می‌شوند؛ فایل‌های راهنِ جدید زیر یک پوشهٔ همگام‌شده (مثلاً مهارتی که ایجنت راهن ساخته) به مسیر میزبانِ متناظر نگاشت می‌شوند. فایل‌های اعتبارنامهٔ فقط-بارگذاری هرگز روی میزبان بازنویسی نمی‌شوند.

  • همگام‌سازیِ برگشت تا ۳ بار با backoff امتحان می‌شود و از استخراج آرشیوهای راهن بزرگ‌تر از ۲ گیگابایت سر باز می‌زند.
  • داکر و Singularity از bind-mount استفاده می‌کنند (نمای زندهٔ فایل‌سیستم میزبان) و به این نیاز ندارند.
  • این وضعیت هرMES را پوشش می‌دهد‏ (~/.hermes/)، نه فایل‌های دلخواه درخت کاری داخل سندباکس — از ایجنت بخواهید مصنوعات مهم را پیش از نابودی سندباکس صریح بیرون کپی کند (مثلاً scp، ‏modal volume put).

مانت والوم‌های داکر

با بک‌اند داکر، docker_volumes اجازه می‌دهد پوشه‌های میزبان را با کانتینر به اشتراک بگذارید. هر مدخل از نگارش استاندارد -v داکر استفاده می‌کند: host_path:container_path[:options].

yaml
terminal:
  backend: docker
  docker_volumes:
    - "/home/user/projects:/workspace/projects"   # خواندنی-نوشتنی (پیش‌فرض)
    - "/home/user/datasets:/data:ro"              # فقط‌خواندنی
    - "/home/user/.hermes/cache/documents:/output" # صادرات مرئی-برای-گیت‌وی

مفید برای:

  • رساندن فایل به ایجنت (دیتاست‌ها، پیکربندی، کد مرجع)
  • دریافت فایل از ایجنت (کد تولیدشده، گزارش‌ها، صادرات)
  • ورک‌اسپیس‌های مشترک که هم شما و هم ایجنت به همان فایل‌ها دسترسی دارید

اگر از گیت‌وی پیام‌رسانی استفاده می‌کنید و می‌خواهید ایجنت فایل‌های تولیدشده را با MEDIA:/... بفرستد، یک مانت صادراتِ مرئی-برای-میزبانِ اختصاصی مثل /home/user/.hermes/cache/documents:/output را ترجیح دهید:

  • داخل داکر فایل‌ها را به /output/... بنویسید
  • مسیر میزبان را در MEDIA: بدهید، مثلاً: MEDIA:/home/user/.hermes/cache/documents/report.txt
  • /workspace/... یا /output/... را ندهید مگر همان مسیر دقیق برای پروسهٔ گیت‌وی روی میزبان هم موجود باشد
⚠️ هشدار

کلیدهای تکراری YAML خاموش بر هم‌دست‌های قبلی را بازنویسی می‌کنند. اگر از قبل بلوک docker_volumes: دارید، مانت‌های جدید را در همان فهرست ادغام کنید به‌جای افزودن کلید docker_volumes: دیگری در پایین فایل.

از متغیر محیطی هم می‌شود تنظیمش کرد: TERMINAL_DOCKER_VOLUMES='["/host:/container"]' (آرایهٔ JSON).

فوروارد اعتبارنامهٔ داکر

به‌طور پیش‌فرض، نشست‌های ترمینال داکری اعتبارنامه‌های دلخواه میزبان را به ارث نمی‌برند. اگر توکن مشخصی داخل کانتینر لازم دارید، به terminal.docker_forward_env اضافه‌اش کنید:

yaml
terminal:
  backend: docker
  docker_forward_env:
    - "GITHUB_TOKEN"
    - "NPM_TOKEN"

هرمس هر متغیر فهرست‌شده را اول از شل فعلی شما حل می‌کند، بعد اگر با hermes config set ذخیره شده به ~/.hermes/.env برمی‌گردد.

⚠️ هشدار

هر چیزی در docker_forward_env فهرست شود برای فرمان‌های داخل کانتینر مرئی می‌شود. فقط اعتبارهایی را فوروارد کنید که پذیرفته‌اید در معرض نشست ترمینال باشند.

اجرای کانتینر به‌عنوان کاربر میزبان شما

به‌طور پیش‌فرض کانتینرهای داکر به‌عنوان root (‏UID 0) اجرا می‌شوند. فایل‌های ساخته‌شده داخل /workspace یا سایر bind-mountها روی میزبان در مالکیت root درمی‌آیند، پس بعد از نشست باید پیش از ویرایش از ادیتور میزبان sudo chownشان کنید. پرچم terminal.docker_run_as_host_user این را درست می‌کند:

yaml
terminal:
  backend: docker
  docker_run_as_host_user: true   # پیش‌فرض: false

وقتی فعال باشد، هرمس --user $(id -u):$(id -g) به فرمان docker run می‌افزاید تا فایل‌های نوشته‌شده در پوشه‌های bind-mount‏ (/workspace، ‏/root، هر چیزی در docker_volumes) در مالکیت کاربر میزبان شما باشند نه root. مبادله: کانتینر دیگر نمی‌تواند apt install کند یا به مسیرهای root-مالک مثل /root/.npm بنویسد — اگر هر دو را می‌خواهید از ایمیج پایه‌ای استفاده کنید که HOMEش در مالکیت کاربر غیر-root است (یا ابزار لازم را هنگام بیلد ایمیج اضافه کنید).

برای رفتار سازگار-به-عقب false (پیش‌فرض) بگذارید. وقتی روشن کنید که گردش‌کارتان عمدتاً «ویرایش فایل‌های مانت‌شدهٔ میزبان» است و از sudo chown -R خسته شده‌اید.

اختیاری: مانت پوشهٔ اجرا در /workspace

سندباکس‌های داکر به‌طور پیش‌فرض ایزوله می‌مانند. هرمس پوشهٔ کاری فعلی میزبان‌تان را داخل کانتینر پاس نمی‌دهد مگر صریح فعالش کنید:

yaml
terminal:
  backend: docker
  docker_mount_cwd_to_workspace: true

وقتی فعال است:

  • اگر هرمس را از ~/projects/my-app اجرا کنید، همان پوشهٔ میزبان به /workspace بایند-مانت می‌شود
  • بک‌اند داکر در /workspace شروع می‌شود
  • ابزارهای فایل و فرمان‌های ترمینال هر دو همان پروژهٔ مانت‌شده را می‌بینند

وقتی غیرفعال است، /workspace در مالکیت سندباکس می‌ماند مگر با docker_volumes چیزی صریح مانت کنید.

مبادلۀ امنیتی: false مرز سندباکس را حفظ می‌کند؛ ‏true به سندباکس دسترسی مستقیم به پوشه‌ای می‌دهد که هرمس را از آن اجرا کرده‌اید. این اختیار را فقط وقتی بدهید که آگاهانه می‌خواهید کانتینر روی فایل‌های زندهٔ میزبان کار کند.

شل پایدار

به‌طور پیش‌فرض هر فرمان ترمینال در زیرپروسهٔ خودش اجرا می‌شود — پوشهٔ کاری، متغیرهای محیط و متغیرهای شل بین فرمان‌ها ریست می‌شوند. وقتی شل پایدار فعال باشد، یک پروسهٔ bash بلندعمرِ واحد بین فراخوانی‌های execute() زنده نگه داشته می‌شود تا وضعیت بین فرمان‌ها باقی بماند.

این برای بک‌اند SSH مفیدترین است، جایی که سربار اتصال به‌ازای-فرمان را هم حذف می‌کند. شل پایدار برای SSH به‌طور پیش‌فرض فعال و برای بک‌اند محلی غیرفعال است.

yaml
terminal:
  persistent_shell: true   # پیش‌فرض — شل پایدار برای SSH فعال

برای غیرفعال‌کردن: hermes config set terminal.persistent_shell false

چه چیزی بین فرمان‌ها می‌ماند: پوشهٔ کاری‏ (cd /tmp برای فرمان بعدی می‌چسبد)، متغیرهای محیطِ export‌شده‏ (export FOO=bar)، متغیرهای شل‏ (MY_VAR=hello).

اولویت:

سطحمتغیرپیش‌فرض
پیکربندیterminal.persistent_shelltrue
بازنویسی SSHTERMINAL_SSH_PERSISTENTتابع پیکربندی
بازنویسی محلیTERMINAL_LOCAL_PERSISTENTfalse

متغیرهای محیطی به‌ازای-بک‌اند بالاترین اولویت را دارند. اگر شل پایدار را روی بک‌اند محلی هم می‌خواهید: export TERMINAL_LOCAL_PERSISTENT=true

ℹ️ توجه

فرمان‌هایی که stdin_data یا sudo لازم دارند خودکار به حالت یک‌باره برمی‌گردند، چون stdin شل پایدار از قبل توسط پروتکل IPC اشغال شده.

برای جزئیات هر بک‌اند به «اجرای کد» و بخش ترمینالِ صفحهٔ ابزارها مراجعه کنید.

۸ تنظیمات مهارت

مهارت‌ها می‌توانند تنظیمات پیکربندی خودشان را از طریق frontmatter مربوط به SKILL.md اعلام کنند. این‌ها مقادیر غیررمزی (مسیرها، ترجیحات، تنظیمات دامنه) زیر فضای‌نام skills.config در config.yaml ذخیره می‌شوند.

yaml
skills:
  config:
    myplugin:
      path: ~/myplugin-data   # مثال — هر مهارت کلیدهای خودش را تعریف می‌کند

نحوهٔ کار تنظیمات مهارت:

  • hermes config migrate همهٔ مهارت‌های فعال را اسکن، تنظیماتِ پیکربندی‌نشده را پیدا و پیشنهاد پرسش می‌دهد
  • hermes config show همهٔ تنظیمات مهارت را زیر «Skill Settings» همراه مهارتِ صاحبشان نمایش می‌دهد
  • وقتی مهارتی بارگذاری می‌شود، مقادیر پیکربندیِ حل‌شده‌اش خودکار به زمینهٔ مهارت تزریق می‌شوند

تنظیم دستی مقادیر: hermes config set skills.config.myplugin.path ~/myplugin-data

برای جزئیات اعلام تنظیمات در مهارت‌های خودتان به «ساخت مهارت‌ها ← تنظیمات پیکربندی» مراجعه کنید.

گارد روی نوشتن‌های مهارتِ ایجنت‌ساخته

وقتی ایجنت با skill_manage مهارتی می‌سازد، ویرایش، patch یا حذف می‌کند، هرمس می‌تواند اختیاراً محتوای جدید/به‌روزشده را از الگوهای کلیدواژهٔ خطرناک اسکن کند (برداشت اعتبارنامه، تزریق پرامپت بدیهی، دستورالعمل‌های قاچاق). اسکنر به‌طور پیش‌فرض خاموش است — گردش‌های کاری واقعیِ ایجنت که قانوناً به ~/.ssh/ دست می‌زنند یا $OPENAI_API_KEY را ذکر می‌کنند، بیش از حد این ابتکار را تریگر می‌کردند. دوباره روشنش کنید اگر می‌خواهید اسکنر پیش از فرودِ نوشتن‌های مهارت ایجنت از شما بپرسد:

yaml
skills:
  guard_agent_created: true   # پیش‌فرض: false

وقتی روشن است، هر نوشتنِ skill_manageِ علامت‌خورده به‌صورت اعلان تأیید با منطق اسکنر ظاهر می‌شود. نوشتن‌های پذیرفته‌شده فرود می‌آیند؛ ردشدها خطای توضیحی به ایجنت برمی‌گردانند.

تأیید نوشتن برای نوشتن‌های مهارت

مستقل از اسکنر محتوا، skills.write_approval هر نوشتن مهارتِ ایجنت (ایجاد / ویرایش / patch / حذف / فایل‌های پشتیبان) را پشت تأیید صریح شما می‌گذارد — همان سازوکار تأیید/رد فرمان‌های خطرناک:

yaml
skills:
  write_approval: false   # false = نوشتن آزاد (پیش‌فرض) | true = مرحله‌بندی هر نوشتن برای بازبینی

وقتی روشن است، نوشتن‌های مهارت زیر ~/.hermes/pending/skills/ مرحله‌بندی و با /skills pending، ‏/skills diff <id>، ‏/skills approve <id>، ‏/skills reject <id> — از CLI یا هر پلتفرم پیام‌رسانی — بازبینی می‌شوند. در زمان اجرا با /skills approval on|off سوییچ کنید. حافظه همان دروازه را دارد‏ (memory.write_approval، پایین). راهنمای کامل: «دروازه‌گذاری نوشتن‌های مهارت ایجنت» در صفحهٔ مهارت‌ها.

۹ پیکربندی حافظه

yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200   # ~۸۰۰ توکن
  user_char_limit: 1375     # ~۵۰۰ توکن
  write_approval: false     # true = نیاز به تأیید پیش از هر نوشتن حافظه

با memory.write_approval: true، نوشتن‌های حافظه پیش از فرود به تأیید شما نیاز دارند: نوبت‌های CLI تعاملی درجا می‌پرسند؛ نشست‌های پیام‌رسانی و بازبینیِ خودبهبودیِ پس‌زمینه نوشتن را برای بازبینی /memory pending ← /memory approve <id> / /memory reject <id> مرحله‌بندی می‌کنند. در زمان اجرا با /memory approval on|off سوییچ کنید. به «کنترل نوشتن‌های حافظه» در صفحهٔ حافظه مراجعه کنید.

۱۰ برش فایل‌های زمینه

کنترل می‌کند هرمس پیش از اعمال برش سر/دُم چقدر محتوا از هر فایل زمینهٔ خودکار بارگذاری کند. به فایل‌هایی که به پرامپت سیستمی تزریق می‌شوند مثل SOUL.md، ‏.hermes.md، ‏AGENTS.md، ‏CLAUDE.md و .cursorrules اعمال می‌شود. ابزار read_file را تأثیر نمی‌دهد.

yaml
context_file_max_chars: null  # پیش‌فرض — سقف پویا مقیاس‌شده به پنجرهٔ زمینهٔ مدل (کف ۲۰K، سقف ۵۰۰K کاراکتر)

یک عدد صحیح مثبت بگذارید تا به‌جای رفتار پویا، سقف ثابتی پین شود: context_file_max_chars: 25000

۱۱ ایمنی خواندن فایل

کنترل می‌کند یک فراخوانی read_file تکی چقدر محتوا می‌تواند برگرداند. خوانده‌های عبورکرده از سقف با خطایی رد می‌شوند که به ایجنت می‌گوید از offset و limit برای بازهٔ کوچک‌تر استفاده کند. این جلوی سیل‌گرفتن پنجرهٔ زمینه توسط یک خواندنِ تکِ باندل JS مینیفای‌شده یا فایل دادهٔ بزرگ را می‌گیرد.

yaml
file_read_max_chars: 100000  # پیش‌فرض — ~۲۵-۳۵K توکن

# مدل زمینه-بزرگ (‏200K+):
file_read_max_chars: 200000

# مدل محلی کوچک (زمینهٔ ۱۶K):
file_read_max_chars: 30000

ایجنت خواندن‌های فایل را هم خودکار بی‌تکرار می‌کند — اگر همان ناحیهٔ فایل دوبار خوانده شود و فایل تغییر نکرده باشد، به‌جای ارسال مجدد محتوا یک stub سبک برگردانده می‌شود. این با فشرده‌سازی زمینه ریست می‌شود تا ایجنت بتواند پس از خلاصه‌شدن محتوایش فایل‌ها را دوباره بخواند.

۱۲ سقف‌های برش خروجی ابزار

سه سقف مرتبط کنترل می‌کنند یک ابزار پیش از برش‌خوردنِ هرمس چقدر خروجی خام می‌تواند برگرداند:

yaml
tool_output:
  max_bytes: 50000        # سقف خروجی ترمینال (کاراکتر)
  max_lines: 2000         # سقف صفحه‌بندی read_file
  max_line_length: 2000   # سقف به‌ازای-خط در نمای شماره‌خط‌دار read_file
  • max_bytes — وقتی فرمان terminal بیش از این تعداد کاراکتر stdout/stderr ترکیبی تولید کند، هرمس ۴۰٪ اول و ۶۰٪ آخر را نگه و اعلان [OUTPUT TRUNCATED] بین‌شان می‌گذارد. پیش‌فرض 50000 (≈۱۲-۱۵K توکن روی توکنایزرهای معمول).
  • max_lines — سقف بالای پارامتر limit یک فراخوانی read_file تکی. درخواست‌های بالاتر سقف می‌خورند تا یک خواندن نتواند پنجرهٔ زمینه را غرق کند. پیش‌فرض 2000.
  • max_line_length — سقف به‌ازای-خط وقتی read_file نمای شماره‌خط‌دار صادر می‌کند. خطوط بلندتر به این تعداد کاراکتر + ‏... [truncated] بریده می‌شوند. پیش‌فرض 2000.

روی مدل‌های زمینه‌بزرگ که خروجی خام بیشتری به‌ازای فراخوانی می‌خرند سقف‌ها را بالا ببرید؛ برای مدل‌های زمینه-کوچک پایین بیاورید تا نتایج ابزار فشرده بمانند:

yaml
# مدل زمینه-بزرگ (‏200K+)
tool_output:
  max_bytes: 150000
  max_lines: 5000

# مدل محلی کوچک (زمینهٔ ۱۶K)
tool_output:
  max_bytes: 20000
  max_lines: 500

بودجهٔ سرریز نتایج ابزار

جدا از برش، نتایج ابزارِ بیش‌ازحد بزرگ به دیسک سرریز می‌شوند نه اینکه بریده: خروجی کامل زیر $HERMES_HOME/cache/spillover/ ذخیره و محتوای درون-زمینه با پیش‌نمایشی به‌علاوهٔ مسیر فایل ذخیره‌شده جایگزین می‌شود (با read_file و offset/limit خوانا، یا با execute_code پردازش‌پذیر). آستانهٔ سرریز عمومی به‌ازای-نتیجه ۱۰۰٬۰۰۰ کاراکتر است که برای مدل‌های زمینه-کوچک خودکار پایین می‌آید.

نتایج ابزار MCP ‏(ابزارهای نام‌دار mcp_*) با پیش‌فرض سفت‌ترِ ۵۰٬۰۰۰ کاراکتر سرریز می‌شوند: سرورهای MCP روتین‌آور بارهای بزرگِ غیرصفحه‌بندی‌شده برمی‌گردانند (کاتالوگ‌های کشف ابزار، اجراهای دسته‌ای) که وگرنه زیر آستانهٔ عمومی می‌ماندند و در هر نوبت بعدی زمینه را متورم می‌کردند. هیچ‌چیز از دست نمی‌رود — نتیجهٔ کامل روی دیسک حفظ می‌شود. آستانه را بازنویس کنید با:

yaml
tool_budget:
  mcp_result_size_chars: 50000   # آستانهٔ سرریز به‌ازای-نتیجه برای ابزارهای mcp_*

آستانهٔ MCP همیشه به آستانهٔ عمومی به‌ازای-نتیجه (که ممکن است زمینه-مقیاس شده باشد) سقف می‌خورد، پس بالا بردنش نمی‌تواند از آنچه پنجرهٔ مدل فعال اجازه می‌دهد بگذرد.

هرمس حذف سمت-ارائه‌دهنده را هم علامت می‌زند: وقتی نتیجهٔ ابزار MCP یا وب نشانگرهای برشِ خودش را جاسازی می‌کند‏ (...N more items، ‏"has_more": true، یادداشت‌های «saved to sandbox»)، یک خط اعلان به نتیجه افزوده می‌شود که هشدار می‌دهد دادهٔ مرئی ناقص است و پیش از کامل‌تلقی‌کردن هر شمارش باید صفحه‌بندی/دریافت شود.

۱۳ غیرفعال‌سازی سراسری تول‌ست

برای سرکوب تول‌ست‌های مشخص در سراسر CLI و همهٔ پلتفرم‌های گیت‌وی در یک جا، نام‌شان را زیر agent.disabled_toolsets فهرست کنید:

yaml
agent:
  disabled_toolsets:
    - memory       # مخفی‌کردن ابزارهای حافظه + تزریق MEMORY_GUIDANCE
    - web          # بدون web_search / web_extract در هیچ‌جا

این بعد از پیکربندی ابزار به‌ازای-پلتفرم اعمال می‌شود‏ (platform_toolsetsی که hermes tools می‌نویسد)، پس تول‌ستی که اینجا فهرست شود همیشه حذف می‌شود — حتی اگر پیکربندی ذخیره‌شدهٔ پلتفرمی هنوز آن را فهرست کند. وقتی استفاده کنید که یک کلید واحدِ «X را همه‌جا خاموش کن» می‌خواهید به‌جای ویرایش ۱۵+ سطر پلتفرم در UI مربوط به hermes tools.

خالی گذاشتن فهرست یا حذف کلید، no-op است.

۱۴ ایزوله‌سازی گیت‌ورک‌تری

برای اجرای چند ایجنت موازی روی همان مخزن، ورک‌تری‌های گیتِ ایزوله را فعال کنید:

yaml
worktree: true    # همیشه ساخت ورک‌تری (مثل hermes -w)
# worktree: false # پیش‌فرض — فقط وقتی پرچم -w داده شود

worktree_sync: true    # پیش‌فرض — انشعاب از نوکِ راهنِ fetch‌شده
# worktree_sync: false # انشعاب از HEAD محلی (آفلاین / پایهٔ پین‌شده)

وقتی فعال است، هر نشست CLI ورک‌تری تازه‌ای زیر .worktrees/ با شاخهٔ خودش می‌سازد. ایجنت‌ها می‌توانند بدون مزاحمت هم فایل ویرایش، کامیت، push و PR بسازند. ورک‌تری‌های تمیز هنگام خروج حذف؛ کثیف‌ها برای بازیابی دستی نگه داشته می‌شوند.

به‌طور پیش‌فرض شاخهٔ ورک‌تری جدید از نوکِ راهنِ تازه-fetch‌شده منشعب می‌شود (بالادستیِ شاخهٔ فعلی، وگرنه شاخهٔ پیش‌فرض راهن) تا با روزِ پروژه شروع شود نه از HEAD احتمالاً-کهنهٔ کلون محلی. این دیفِ PR را به تغییر واقعی محدود می‌کند به‌جای ارث‌بردن عقب‌ماندگیِ کلون محلی. worktree_sync: false برای انشعاب از HEAD محلی — آفلاین مفید است، یا وقتی آگاهانه وضعیت دقیق فعلی کلون را پایه می‌خواهید. اگر راهن در دسترس نباشد، خودکار به HEAD محلی برمی‌گردد.

فایل‌های gitignored برای کپی‌شدن به ورک‌تری‌ها را از طریق .worktreeinclude در ریشهٔ مخزن فهرست کنید:

text — .worktreeinclude
# .worktreeinclude
.env
.venv/
node_modules/

۱۵ فشرده‌سازی زمینه

هرمس گفتگوهای طولانی را خودکار فشرده می‌کند تا در پنجرهٔ زمینه مدل‌تان بماند. خلاصه‌سازِ فشرده‌سازی یک فراخوانی LLM جداگانه است — می‌توانید به هر ارائه‌دهنده یا اندپوینتی اشاره‌اش کنید. همهٔ تنظیمات فشرده‌سازی در config.yaml زندگی می‌کنند (بدون متغیر محیطی).

مرجع کامل

yaml
compression:
  enabled: true                                     # سوییچ روشن/خاموش فشرده‌سازی
  progress_notices: false                           # اختیاری: تحویل اعلان‌های روتینِ پیشرفت فشرده‌سازی به پلتفرم‌های چت
  threshold: 0.50                                   # فشرده‌سازی در این ٪ از سقف زمینه
  threshold_tokens: null                            # سقف توکن مطلق (اختیاری) — کمینهٔ نسبت در برابر مطلق گرفته می‌شود
  target_ratio: 0.20                                # کسری از آستانه که به‌عنوان دُمِ اخیر حفظ می‌شود
  tail_mode: legacy                                 # حفظ دُم: "legacy" یا "lean" (~۳ برابر توکنِ نگه‌داشتهٔ کمتر پس از فشرده‌سازی)
  protect_last_n: 20                                # حداقل پیام‌های اخیرِ حفظ‌شده بدون فشرده‌سازی
  protect_first_n: 3                                # پیام‌های سرِ غیرسیستمیِ پین‌شده در همهٔ فشرده‌سازی‌ها (۰ = پین‌نکردن هیچ)
  in_place: true                                    # فشرده‌سازی روی همان شناسهٔ نشست (بدون چرخش)
  idle_compact_after_seconds: 0                     # فشرده‌سازی بیکاریِ اختیاری (۰ = خاموش)
  hygiene_hard_message_limit: 5000                  # شیر ایمنی گیت‌وی
  hygiene_timeout_seconds: 30                       # حداکثر ثانیه‌های بی‌خروجیِ مدل-خلاصه پیش از قطع فشرده‌سازی بهداشتی
  hygiene_total_ceiling_seconds: 600                # سقف مطلق انتظار بهداشتی حتی حین جریان توکن‌ها
  hygiene_failure_cooldown_seconds: 300             # پلهٔ اول backoff شکستِ بهداشتی به‌ازای-نشست (‏x1/x3/x9، سقف ۱ ساعت)
  context_timeout_seconds: 120                      # بودجهٔ بی‌حرکتیِ compress_context درون-ایجنت
  context_total_ceiling_seconds: 600                # سقف مطلق انتظار پیش-کامیت درون-ایجنت حتی حین جریان توکن‌ها
  proactive_prune_tokens: 0                         # تریگر توکنیِ اختیاری برای هرسِ بدون-LLM نتایج ابزار (۰ = خاموش)
  proactive_prune_min_result_chars: 8000            # گذرِ خلاصه‌سازیِ هرس فقط نتایج ابزار بزرگ‌تر از این را لمس می‌کند (سقف‌شده ≥ ۲۰۰)
  proactive_prune_min_reclaim_tokens: 4096          # هرس فقط وقتی commit می‌شود که حداقل این تعداد توکن پس بگیرد (۰ = commit هرچیزی)

# مدل/ارائه‌دهندهٔ خلاصه‌سازی زیر auxiliary پیکربندی می‌شود:
auxiliary:
  compression:
    model: ""                                       # خالی = مدل چت اصلی. مثل "google/gemini-3-flash-preview" برای فشرده‌سازی ارزان‌تر/سریع‌تر.
    provider: "auto"                                # ارائه‌دهنده: "auto"، "openrouter"، "nous"، "codex"، "main" و غیره
    base_url: null                                  # اندپوینت سفارشی سازگار با OpenAI (ارائه‌دهنده را بازنویسی می‌کند)
ℹ️ مهاجرت پیکربندی قدیمی

پیکربندی‌های قدیمی‌تر با compression.summary_model، ‏compression.summary_provider و compression.summary_base_url در اولین بارگذاری خودکار به auxiliary.compression.* مهاجرت می‌کنند (نسخهٔ پیکربندی ۱۷). بدون اقدام دستی.

progress_notices (پیش‌فرض false) کنترل می‌کند آیا وضعیت‌های روتینِ پیشرفت فشرده‌سازی به پلتفرم‌های چت برسند. به‌طرز طراحی‌شده، فشرده‌سازی خودکار روی سطوح چت ساکت است — در پس‌زمینه با لاگ سمت-سرور اجرا می‌شود. progress_notices: true بگذارید تا چرخهٔ روتین را روی چت ببینید: اعلان شروع «Compacting context…»، ‏تریگرهای پیش‌پرواز/پیش-API، فشرده‌سازی بیکاری، پیشرفت retry و اعلان «Context compaction complete». این دروازه فقط به وضعیت‌های فشرده‌سازی دامنه دارد — نویز عملیاتی نامرتبط در هر دو حالت سرکوب می‌ماند. اعلان‌های شکست فشرده‌سازی و بازخورد /compress دستی صرف‌نظر از این تنظیم همیشه مرئی‌اند. ویرایش این مقدار روی گیت‌ویِ در حال اجرا در پیام بعدی اثر می‌کند.

hygiene_hard_message_limit یک شیر ایمنی پیش-فشرده‌سازیِ فقط-گیت‌وی است. برای شکستن یک مارپیچ مرگ وجود دارد: وقتی فراخوانی‌های API روی نشستِ بیش‌ازحد بزرگ مدام قطع می‌شوند، گیت‌وی هرگز دادهٔ مصرف توکن دریافت نمی‌کند، پس آستانهٔ توکنی نمی‌تواند شلیک کند، پس رونوشت به رشد ادامه می‌دهد و قطعی‌ها بدتر می‌شوند. این کفِ مبتنی-بر-شمارش تنها بر شمار پیام شلیک می‌کند (همیشه شناخته، صرف‌نظر از شکست‌های API) تا فشرده‌سازی را اجبار و نشست را بازیابی کند. پیش‌فرض 5000 — بسیار بالای هر نشست عادی، شامل مدل‌های زمینه‌بزرگ (۱M+) که هزاران نوبت کوتاه می‌دهند و مدتها پیش از این، روی آستانهٔ توکنی فشرده می‌شوند. برای پلتفرم‌های غیرعادی بالاتر، برای فشرده‌سازی تهاجمی‌تر پایین‌تر. ویرایش روی گیت‌وی در حال اجرا در پیام بعدی اثر می‌کند.

hygiene_timeout_seconds بودجهٔ بی‌حرکتیِ گیت‌وی برای این گذرِ فشرده‌سازیِ پیش-ایجنت است — نه سقف کل دیوار-ساعتی. فراخوانی خلاصه از مدل استریم می‌شود و هر توکنِ رسیده پیشرفت رو به جلو حساب می‌شود: مدل استدلالیِ کند که هنوز تولید می‌کند، ضرب‌الاجلِ خودش را مدام تمدید می‌کند، پس مدل‌های خلاصهٔ کند-اما-سالم هرگز وسط تولید قطع نمی‌شوند. فقط وقتی مدل خلاصه به این تعداد ثانیه هیچ خروجی ندهد (بک‌اند پایین، اتصان گیرکرده، ارائه‌دهندهٔ ساکت) گیت‌وی به کاربر هشدار می‌دهد، پیام ورودی را بدون فشرده‌سازی ادامه می‌دهد، و به‌جای معلق‌نمایی، یک cooldown موقتِ شکستِ به‌ازای-نشست ثبت می‌کند.

hygiene_total_ceiling_seconds (پیش‌فرض 600) انتظار کل را حتی حین حرکت توکن‌ها مقید می‌کند تا جریان چکه‌ایِ منحط نتواند نوبتی را بی‌نهایت گروگان بگیرد. به حداقل hygiene_timeout_seconds سقف می‌خورد.

hygiene_failure_cooldown_seconds آن cooldown به‌ازای-نشست را پس از تایم‌اوت یا سقط فشرده‌سازی بهداشتی کنترل می‌کند. حین cooldown، گیت‌وی تلاش‌های بهداشتیِ مکرر برای همان نشستِ بیش‌ازحد بزرگ را رد می‌کند تا هر پیام ورودی روی همان بک‌اند کمکیِ خراب بلاک نماند. ‏/compress، ‏/reset یا نوبت سالمِ بعدی همچنان می‌توانند نشست را بازیابی کنند.

این مقدار پلهٔ اولِ نردبانی صعودی است، نه بازه‌ای ثابت: شکست‌های متوالی همان نشست 1x، سپس 3x، سپس 9x این مقدار را صبر می‌کنند، با سقف یک ساعت. نشستی که مدل خلاصه‌اش دائماً خراب است بنابراین back-off می‌گیرد به‌جای retry بی‌نهایت روی بازهٔ ثابت، و اجرایی که واقعاً رونوشت را کوچک می‌کند به پلهٔ اول برمی‌گردد. صعود به‌ازای-نشست و محلیِ پروسه است — ری‌استارت گیت‌وی به پلهٔ اول برمی‌گرداند در حالی که ضرب‌الاجلِ cooldown خودش می‌ماند.

context_timeout_seconds (پیش‌فرض 120) همان بودجهٔ بی‌حرکتی برای compress_context درون-ایجنت — حلقهٔ گفتگو، فشرده‌سازی پیش‌پرواز و /compress دستی — است تا مدل خلاصهٔ گیرکرده نتواند نشستی را بی‌نهایت معلق کند. توکن‌های خلاصهٔ استریم‌شده انتظار را تمدید می‌کنند؛ فقط کارگرِ ساکت قطع می‌شود. در تایم‌اوت هرمس فشرده‌سازی را رد می‌کند، پیام‌های موجود را نگه می‌دارد و به کاربر هشدار می‌دهد. 0 برای غیرفعال‌کردن. بهداشت نشستِ گیت‌وی مسیر hygiene_timeout_seconds خودش را دارد و دوبار پوشیده نمی‌شود.

context_total_ceiling_seconds (پیش‌فرض 600) انتظار پیش-کامیت درون-ایجنت (فاز خلاصه / استریم) را حتی حین حرکت توکن‌ها مقید می‌کند. به حداقل context_timeout_seconds سقف می‌خورد. تضمین دقیق: فاز خلاصه با این سقف مقید است؛ فاز کامیت اگر از آن بگذرد لاگ و ظاهر می‌شود. وقتی کارگر وارد حصارِ کامیتِ فشرده‌سازی و جهش SessionDB در پرواز شده، کامیت هرگز وسط پرواز رها نمی‌شود — که خطر واگرایی رونوشت دارد — ولی انتظار دیگر خاموش نیست: اگر کامیت از سقف بگذرد، هرمس تجاوز را لاگ می‌کند‏ (WARNING، با تکرار به ERROR)، یک هشدار یک‌باره از کانال هشدارِ رو-به-کاربر می‌فرستد، و در گام‌های کراندار تا تکمیل کامیت صبر می‌کند.

protect_first_n کنترل می‌کند چند پیام غیرسیستمیِ سر در سراسر هر فشرده‌سازی پین شوند. پیش‌فرض 3 — تبادل آغازین کاربر/دستیار از هر گذر خلاصه‌ساز جان سالم می‌برد تا هدف اصلی مرئی بماند. روی نشست‌های طولانیِ فشرده‌سازی-غلتان که نوبت آغازین دیگر مرتبط نیست، protect_first_n: 0 بگذارید تا جز پرامپت سیستمی + خلاصه + دُم چیزی پین نشود. خود پرامپت سیستمی صرف‌نظر از این تنظیم همیشه حفظ می‌شود.

in_place (پیش‌فرض true) کنترل می‌کند هنگام شلیک فشرده‌سازی با هویت نشست چه شود. وقتی true است، فشرده‌سازی فهرست پیام را بازنویسی و پرامپت سیستمی را بدون چرخش شناسهٔ نشست دوباره می‌سازد — گفتگو کل عمرش یک شناسهٔ پایدار دارد (بدون زنجیرهٔ parent_session_id، بدون شماره‌گذاری مجدد name #2 / ‏#3 در فهرست نشست‌ها). فشرده‌سازی غیرمخرب است: زمینهٔ زنده فشرده می‌شود، ولی نوبت‌های پیش-فشرده‌سازی زیر همان شناسه نرم‌آرشیو می‌شوند (نشانه‌گذاری غیرفعال/فشرده) — همچنان با session_search قابل‌جستجو و قابل‌بازیابی، نه حذف. هوک‌ها حالت را از فیلد in_place روی رویداد session:compress می‌بینند. in_place: false رفتار قدیمی را برمی‌گرداند که هر فشرده‌سازی به شناسهٔ نشستِ جدیدِ پیوندخورده به قدیمی می‌چرخد.

threshold_tokens یک سقف توکن مطلقِ اختیاری برای تریگر فشرده‌سازی می‌گذارد. وقتی تنظیم شود، فشرده‌سازی در کمینهٔ threshold نسبت‌محور و این شمار مطلق شلیک می‌کند — پس فشرده‌سازی هرگز دیرتر از شمارهٔ توکنِ ترجیحیِ کاربر شلیک نمی‌کند صرف‌نظر از اینکه کدام مدل فعال است. این مشکل جابه‌جاییِ نقطهٔ تریگر مطلق هنگام سوییچ بین مدل‌های با پنجره‌های زمینهٔ متفاوت (مثلاً ۱M ← ‏۴۰۰K) را حل می‌کند. سقف به طول زمینهٔ مدل محدود می‌شود، پس بالاتر گذاشتنش از پشتیبانی مدل امن است — آستانهٔ نسبت‌محور به‌جایش استفاده می‌شود. پیش‌فرض null (غیرفعال — فقط آستانهٔ نسبت‌محور). سقف از سوییچ مدل و فعال‌شدن fallback جان سالم به در می‌برد.

idle_compact_after_seconds یک تریگر زمان‌محورِ اختیاری است که مکملِ threshold حجم‌محور است. پیش‌فرض 0 (خاموش). وقتی بالای ۰ گذاشته شود، نشستی که پس از حداقل این تعداد ثانیه بیکاری ازسر گرفته شود، تاریخچهٔ انباشته‌اش را پیش از اولین پاسخ، از پیش فشرده می‌کند — تا رشتهٔ طولانی‌عمر (مثلاً گفتگوی تلگرامی که ساعت‌ها بعد به آن برمی‌گردید) زمینهٔ کهنهٔ کاملش را در هر نوبت بعدی دوباره نخواند. هرگز وقتی زمینه از قبل در یا زیر هدفِ پس-فشرده‌سازی است‏ (threshold × target_ratio) شلیک نمی‌کند، و همان گاردهای cooldown-شکست، ضد-تشنج و قفل به‌ازای-نشستِ هر فشرده‌سازی خودکار را رعایت می‌کند. مثال: idle_compact_after_seconds: 1800 پس از ۳۰ دقیقه بیکاری فشرده می‌کند.

proactive_prune_tokens یک هرس قطعیِ بدون-LLM از بارهای نتیجهٔ ابزار قدیمی را فعال می‌کند که مستقل از threshold اجرا می‌شود. روی مدل‌های پنجره-بزرگ، فشرده‌سازیِ threshold (≈۵۰٪ پنجره) به‌ندرت شلیک می‌شود، پس خروجی‌های حجیم ابزار (dump ترمینال، خواندن فایل، استخراج وب) سوار تاریخچه می‌مانند و در هر نوبت بعدی دوباره ارسال می‌شوند. وقتی تاریخچهٔ ارسال‌مجدد از proactive_prune_tokens بگذرد (پیش‌فرض 0 = خاموش؛ برای فعال‌سازی 48000 را امتحان کنید)، هرس نتایج یکسان را بی‌تکرار، نتایجِ قدیمیِ بیش‌ازحد را خلاصه و آرگومان‌های فراخوانی ابزار بزرگ را بریده — با حفاظت از protect_last_n پیامِ اخیر و بدون فراخوانی مدل. خروجی‌های کامل از مخزن نشست بازیابی‌پذیر می‌مانند. proactive_prune_min_result_chars (پیش‌فرض 8000، سقف‌شده به ≥ ۲۰۰) اندازه‌ای را تعیین میکند که زیرش نتیجهٔ ابزار دست‌نخورده می‌ماند. proactive_prune_min_reclaim_tokens (پیش‌فرض 4096) مانع commit شدن هرسی می‌شود مگر آن‌قدر توکن پس بگیرد — یک هرسِ commit‌شده تاریخچهٔ ارسال‌شده را بازنویسی و پیشوندِ کش پرامپتِ ارائه‌دهنده را بی‌اعتبار می‌کند، پس این دروازه شکست‌های کش را دوره‌ای و مستهلک‌شده نگه می‌دارد (یک شکست معنادار، مثل مرز فشرده‌سازی) به‌جای شلیک در هر تکرار ابزار. این فقط زیر موتور داخلی compressor اجرا می‌شود؛ سایر موتورهای زمینه no-op به ارث می‌برند.

💡 هات-ری‌لود گیت‌وی برای فشرده‌سازی و طول زمینه

از ریلیزهای اخیر، ویرایش model.context_length یا هر کلید compression.* در config.yaml روی گیت‌ویِ در حال اجرا در پیام بعدی اثر می‌کند — بدون ری‌استارت گیت‌وی، بدون /reset، بدون چرخش نشست. امضای ایجنتِ کش‌شده این کلیدها را شامل می‌شود، پس گیت‌وی با دیدن تغییر، ایجنت را شفاف بازسازی می‌کند. کلیدهای API و پیکربندی ابزار/مهارت همچنان مسیرهای reload معمول را می‌خواهند.

راه‌اندازی‌های رایج

پیش‌فرض (تشخیص-خودکار) — بدون پیکربندی لازم:

yaml
compression:
  enabled: true
  threshold: 0.50

از ارائه‌دهنده و مدل اصلی شما استفاده می‌کند. به‌ازای-کار بازنویسی کنید (مثلاً auxiliary.compression.provider: openrouter + ‏model: google/gemini-2.5-flash) اگر فشرده‌سازی را روی مدل ارزان‌تری از مدل چت اصلی‌تان می‌خواهید.

اجبار ارائه‌دهندهٔ مشخص (‏OAuth یا مبتنی-بر-کلید-API):

yaml
auxiliary:
  compression:
    provider: nous
    model: gemini-3-flash

با هر ارائه‌دهنده‌ای کار می‌کند: nous، ‏openrouter، ‏codex، ‏anthropic، ‏main و غیره.

اندپوینت سفارشی (خودمیزبان، ‏Ollama، ‏zai، ‏DeepSeek و غیره):

yaml
auxiliary:
  compression:
    model: glm-4.7
    base_url: https://api.z.ai/api/coding/paas/v4

به اندپوینت سفارشی سازگار با OpenAI اشاره می‌کند. از OPENAI_API_KEY برای احراز استفاده می‌کند.

مدل خلاصه باید پنجرهٔ زمینه‌ای حداقل به بزرگی مدلِ اصلی ایجنت شما داشته باشد. فشرده‌ساز بخش میانیِ کامل گفتگو را به مدل خلاصه می‌فرستد — اگر پنجرهٔ آن مدل کوچک‌تر از مدل اصلی باشد، فراخوانی خلاصه‌سازی با خطای طول زمینه شکست می‌خورد. وقتی این اتفاق بیفتد، نوبت‌های میانی بدون خلاصه انداخته می‌شوند و زمینهٔ گفتگو خاموش گم می‌شود. اگر مدل را بازنویسی کردید، تطبیق طول زمینه‌اش با مدل اصلی را تأیید کنید.

۱۶ تایم‌اوت لیز نوبت گیت‌وی

گیت‌وی نوبت‌ها را با شناسهٔ نشستِ حل‌شده سریال می‌کند تا دو کلید مسیریابی نتوانند هم‌زمان همان رونوشت را بارگذاری و بنویسند. حداکثر انتظار لیز را مستقل از تایم‌اوت بی‌حرکتی معمولِ ایجنت پیکربندی کنید:

yaml
agent:
  gateway_turn_lease_timeout: 1800

اگر نوبت دیگری هنوز لیز نشست را نگه داشته باشد وقتی این بودجه تمام شود، هرمس ایمن شکست می‌خورد: رونوشت را برای پیام منتظر بارگذاری یا مدل را اجرا نمی‌کند. کاربر اعلان رد دریافت و باید دوباره بفرستد. هرمس پیام را خودکار requeue نمی‌کند چون انجامش بدون ترتیب پایدار و idempotency ممکن بود دو بار پردازش شود. مقادیر غیرمثبت پیش‌فرض ۱۸۰۰ ثانیه را می‌گیرند.

۱۷ نگهبان گیرِ نشست

گیت‌وی یک نگهبانِ فقط-اعلانِ گیر اجرا می‌کند‏ (agent.session_stall_timeout، پیش‌فرض 300 ثانیه، ‏0 = خاموش). وقتی نشستِ مشغول پیگیریِ ورودیِ در-انتظار داشته باشد و ساعت فعالیت مشترک ایجنت حداقل این‌قدر بی‌حرکت مانده باشد، گیت‌وی یک WARNING لاگ و یک اعلان یک‌باره به کاربر می‌فرستد:

خروجی
⚠️ Agent session appears stalled (last activity N min ago). Try /new to reset.

معناشناسی:

  • فقط-اعلان. نگهبان هرگز نوبت را نمی‌کشد — در تقابل با agent.gateway_timeout که اجرایی را پس از بی‌حرکتی طولانی لغو می‌کند. اعلان گیر فقط می‌گوید ایجنت گیرکرده به‌نظر می‌رسد تا شما تصمیم بگیرید‏ (/new، ‏/stop یا ادامهٔ انتظار).
  • یک اعلان به‌ازای هر دورهٔ گیر. قفل با تخلیهٔ ورودیِ در-انتظار یا ازسرگیری فعالیت پاک می‌شود، پس نشستی که بازیابی و دوباره گیر می‌کند دوباره اعلان می‌گیرد.
  • پیشرفت فقط از تصویر لحظه‌ای فعالیت مشترک می‌آید (فراخوانی ابزار، پیشرفت استریم API، ضربان فشرده‌سازی). ورودیِ در-انتظار یک دروازهٔ اعلان است، نه ساعت پیشرفت.
yaml
agent:
  session_stall_timeout: 300   # ثانیه؛ ۰ نگهبان را خاموش می‌کند

۱۸ تشدید توجهِ اتصال‌مجدد

وقتی آداپتور پلتفرمی در اتصال شکست می‌خورد (قطعی شبکه، توکن بات لغوشده، sidecar خراب)، گیت‌وی با backoff نماییِ کراندار نامحدود retry می‌کند — retryها هرگز نمی‌ایستند، پس قطعی گذرا همیشه بدون اقدام اپراتور خوددرمانی می‌شود. نقطه‌ضعفش این است که شکست دائمی (توکن تلگرام لغوشده، privileged intents غایب دیسکورد) دقیقاً مثل یک لرزش لحظه‌ای به‌نظر می‌رسد: «retrying»، برای همیشه.

دو سازوکار شکست‌های دائمی را مرئی می‌کنند:

  • طبقه‌بندی پایانی. شکست‌هایی که نوعِ استثنایشان ثابت می‌کند هرگز خوددرمان نمی‌شوند — توکن‌های رد/لغوشده‏ (telegram_auth_error، ‏discord_auth_error، ‏email_auth_error)، ‏privileged intents غایب‏ (discord_intents_required)، ‏sidecar فوتونی که وابستگی‌هایش نمی‌توانند نصب شوند‏ (SIDECAR_DEPS_MISSING) یا باینری nodeش غایب است‏ (SIDECAR_NODE_MISSING) — به‌جای ورود به صف retry، مرگبار علامت می‌خورند. طبقه‌بندی اکیداً مبتنی-بر-نوع است؛ خطاهای مبهم همیشه retry می‌شوند.
  • تشدید نیاز-به-توجه. پلتفرمی که پیوسته در صف retry pastِ agent.reconnect_attention_after بماند (پیش‌فرض 7200 ثانیه = ۲ ساعت، ‏0 خاموش) در وضعیت اجرایی گیت‌وی‏ (hermes status) ‏needs_attention: true و مهر زمانی retrying_since به‌علاوهٔ WARNING لاگ می‌گیرد. Retryها بی‌تغییر ادامه می‌یابند — این یک سیگنال است، نه قطع‌کنندهٔ مدار. پرچم با اتصال‌مجدد موفق پاک می‌شود.
yaml
agent:
  reconnect_attention_after: 7200   # ثانیه؛ ۰ پرچم تشدید را خاموش می‌کند

۱۹ کش ایجنت گیت‌وی

گیت‌وی یک ایجنت به‌ازای-نشست نگه می‌دارد تا گفتگو پیشوندِ پرامپتِ کش‌شده‌اش را بازاستفاده کند به‌جای بازسازی پرامپت سیستمی در هر نوبت. آن ایجنتِ کش‌شده رونوشت کامل نشست — شامل خروجی ابزار که روی نشستی با صد فراخوانی ابزار ده‌ها مگابایت است — را هم نگه می‌دارد. روی گیت‌وی چندپلتفرمیِ شلوغ، کش بزرگ‌ترین مصرف‌کنندهٔ حافظهٔ تکیِ پروسه است.

yaml
agent:
  agent_cache:
    max_size: 128            # سقف مدخل LRU
    idle_ttl_secs: 3600      # بیرون‌انداختن ایجنتی این‌قدر بیکار
    memory_high_mb: auto     # بودجهٔ anon-RSS؛ عدد، "auto" یا 0/خاموش
    max_evictions_per_pass: 16
    protect_recent: 8

max_size و idle_ttl_secs کش را بر اساس شمار و زمان مقید می‌کنند. هیچ‌کدام نمی‌دانند چند بایت نگه داشته‌اند، پس memory_high_mb سومین قید را می‌افزاید: به‌محض عبور حافظهٔ ساکنِ ناشناسِ خودِ گیت‌وی از بودجه، رونوشت‌های کمترین-استفادهٔ-اخیر را می‌ریزد که در نوبت بعدی از نشستِ ذخیره‌شده دوباره بارگذاری می‌شوند. اگر گیت‌وی با سرویس‌های دیگر بر سر حافظه رقابت می‌کند پایینش بیاورید؛ اگر ترجیح می‌دهید همهٔ پیشوندها گرم بمانند بالایش یا 0 بگذارید (خاموش‌کردن گذر).

auto بودجه را از سقف حافظه‌ای که گیت‌وی واقعاً زیرش اجرا می‌شود مشتق می‌کند — سقف cgroup برای کانتینر یا یونیت systemd، وگرنه کل RAM — تا یک MemoryMax/MemoryHigh روی یونیت بدون شمارهٔ دومی که همگام نگه دارید محترم شمرده شود.

نشست‌های میان-نوبت، ‏protect_recent تای اخیراً-استفاده‌شده، و هر نشستی که رونوشتش هنوز تمام‌نوشته‌نشده است هرگز ریخته نمی‌شوند. بیرون‌انداختن با WARNING همراه RSS اندازه‌گیری‌شده و نشست‌های ریخته‌شده لاگ می‌شود:

لاگ

۲۰ موتور زمینه

موتور زمینه کنترل می‌کند گفتگوها هنگام نزدیک‌شدن به سقف توکن مدل چگونه مدیریت شوند. موتور داخلی compressor از خلاصه‌سازی زیان‌آور استفاده می‌کند (به «فشرده‌سازی و کش زمینه» در راهنمای توسعه‌دهنده). موتورهای پلاگینی می‌توانند جایگزینش شوند با راهبردهای بدیل.

yaml
context:
  engine: "compressor"    # پیش‌فرض — خلاصه‌سازی زیان‌آور داخلی

# استفاده از موتور پلاگینی (مثلاً LCM برای مدیریت زمینهٔ بدون‌زیان):
context:
  engine: "lcm"          # باید با نام پلاگین مطابق باشد

موتورهای پلاگینی هرگز خودکار فعال نمی‌شوند — باید صریح context.engine را روی نام پلاگین بگذارید. موتورهای موجود را می‌توان از hermes plugins ← Provider Plugins ← Context Engine مرور و انتخاب کرد.

برای سیستمِ مشابهِ تک‌انتخابیِ پلاگین‌های حافظه به «ارائه‌دهندگان حافظه» مراجعه کنید.

۲۱ بودجه تکرار

وقتی ایجنت روی کار پیچیده‌ای با فراخوانی‌های ابزار زیاد کار می‌کند، می‌تواند بودجه تکرارش (پیش‌فرض: ۵۰۰ نوبت) را بسوزاند. هرمس هشدار فشارِ میان-کار تزریق نمی‌کند — بیلدهای قدیمی‌تر مدل را در ۷۰٪/۹۰٪ بودجه هشدار می‌دادند که باعث رهاکردن زودهنگام کارهای پیچیده توسط مدل‌ها می‌شد و در آوریل ۲۰۲۶ حذف شد.

به‌جایش، وقتی بودجه واقعاً تمام شود (‏۵۰۰/۵۰۰)، هرمس یک پیام درخواست جمع‌بندی تزریق و یک فراخوانی بخشش تکی اجازه می‌دهد تا پاسخ نهایی بدهد. اگر آن فراخوانی هم متن تولید نکند، از ایجنت خواسته می‌شود آنچه انجام داد را خلاصه کند.

yaml
agent:
  max_turns: none              # تکرارها به‌ازای-نوبت-گفتگو (پیش‌فرض: none = نامحدود)
                               # عدد صحیح مثبت برای سقف؛ "none"/"null"/"unlimited"/"inf"/
                               # "infinity"/"infinite"/0/-1 = بدون سقف
  api_max_retries: 3           # Retry به‌ازای-ارائه‌دهنده پیش از فعال‌شدن fallback (پیش‌فرض: 3)

agent.max_turns به‌طور پیش‌فرض نامحدود است — سقف نوبت مشکلات بیشتری از حل‌هاش ایجاد می‌کرد (برش خاموش میان-کار)، پس هرمس از جعبه نوبت گفتگو را تا تکمیل اجرا می‌کند. برای سقف، عدد صحیح مثبت بگذارید. برای صراحتِ «بدون سقف»، هر یک از این املاها (بدون حساسیت به بزرگی/کوچکی) کار می‌کند: "none"، ‏"null"، ‏"unlimited"، ‏"infinite"، ‏"infinity"، ‏"inf"، ‏0، ‏-1 (به نشانگر sys.maxsize حل می‌شوند تا حلقه هرگز روی شمار نوبت خارج نشود).

agent.api_max_retries کنترل می‌کند چند بار هرمس فراخوانی API ارائه‌دهنده را روی خطاهای گذرا (محدودیت نرخ، قطع اتصان، ‏۵xx) پیش از فعال‌شدن سوییچِ ارائه‌دهنده-پشتیبان retry می‌کند. پیش‌فرض 3 — مجموعاً چهار تلاش. اگر ارائه‌دهندگان پشتیبان پیکربندی کرده‌اید و شکست‌دادن سریع‌تر می‌خواهید، به 0 بیاورید تا اولین خطای گذرا روی ارائه‌دهندهٔ اصلی بلافاصله به fallback واگذار شود به‌جای چرخیدن retry مقابل اندپوینتِ ناپایدار.

۲۲ بودجه اجرای دیوار-ساعتی

جدا از بودجه تکرار، می‌توانید به هر اجرای گفتگو یک بودجهٔ دیوار-ساعتی اختیاری بدهید. برای فراخوانی‌های یک‌باره و هارنس‌ارزی که زیر سقف خارجی سخت اجرا می‌شوند (مثلاً سقف ۹۰۰ ثانیه‌ای به‌ازای-کار) طراحی شده: بدونش، اجرا می‌تواند با کارِ عملاً تمام‌شده تایم‌اوت بخورد — یک تولید مانده به صدور پاسخ نهایی، یا گیرکرده در یک فراخوانی ارائه‌دهندهٔ قفل‌شده.

yaml + bash
agent:
  run_budget_seconds: null     # اختیاری؛ تنظیم‌نشده/null = قابلیت کاملاً خاموش (پیش‌فرض)

# یا به‌ازای-فراخوانی از CLI:
hermes chat --run-budget 850 -q "..."

وقتی بودجه تنظیم شود دو چیز اتفاق می‌افتد:

  1. اعلان جمع‌بندی در ۸۰٪. وقتی ۸۰٪ بودجه بگذرد، هرمس یک اعلان یک‌باره تزریق می‌کند (با ایمنی کش، الصاق‌شده به جدیدترین نتیجهٔ ابزار مثل پیام‌های /steer) که به مدل می‌گوید کار کشف/راستی‌آزمایی جدید را متوقف و خروجی نهایی را از وضعیتی که دارد تولید کند. حداکثر یک بار به‌ازای اجرا شلیک می‌شود و آینهٔ سازوکار جمع‌بندیِ بودجه-تکرار موجود است — هشدار فشارِ مکرر وجود ندارد.
  2. تایم‌اوت‌های بی‌پاسخِ مقیاس‌شده-بر-ضرب‌الاجل. تایم‌اوت‌های ضمنیِ بی‌پاسخِ غیراستریمی (پیش‌فرض ۹۰ ثانیه و کف‌های مدل‌های استدلالی، مثلاً ۶۰۰ ثانیه برای مدل‌های استدلالی DeepSeek) به max(60, remaining_budget × 0.5) سقف می‌خورند تا یک فراخوانی ارائه‌دهندهٔ قفل‌شدهٔ ساکت هرگز نتواند باقی اجرا را مصرف کند. سقف فقط تایم‌اوت را تنگ‌تر می‌کند — هرگز بالا نمی‌برد — و stale_timeout_seconds صریحاً پیکربندی‌شده (پیکربندی ارائه‌دهنده/مدل یا HERMES_API_CALL_STALE_TIMEOUT) همیشه دست‌نخورده می‌برد.

بودجه به‌ازای نوبت run_conversation است (با هر پیام کاربر ریست می‌شود) و قابلیت وقتی تنظیم نشده کاملاً خفته است — بدون خواندن ساعت، بدون تزریق، بدون تغییر تایم‌اوت.

۲۳ راستی‌آزمایی هنگام توقف (کد)

وقتی فعال باشد، هرمس پذیرش پاسخ نهایی در نوبتی را که ایجنت در ورک‌اسپیسی کد ویرایش کرده ولی شواهد راستی‌آزمایی تازه‌ای (اجرای تستِ گذرنده، بیلد، lint و غیره) تولید نکرده رد می‌کند — یک پیگیری ساختگی تزریق می‌کند که از ایجنت می‌خواهد راستی‌آزمایی کند یا توضیح دهد چرا نمی‌تواند. ویرایش‌های فقط-داک/مارک‌داون/مهارت هرگز تریگرش نمی‌کنند، و حلقه کراندار است تا هرگز ایجنت را نگیرد.

yaml
agent:
  verify_on_stop: false        # true | false | "auto" (آگاه-سطح: روشن برای CLI/TUI/دسکتاپ، خاموش برای پیام‌رسانی)
  verify_guidance: true        # الصاق راهنمای UI-خلاقانه / دیف-تمیز به هدیهٔ شواهد-مفقود
  max_verify_nudges: 3         # سقف هدیه‌های ادامهٔ متوالی به‌ازای-نوبت (داخلی + هوک‌های pre_verify)
  coding_instructions: ""      # قواعد کدنویسی ایستادهٔ سراسر-پروژه الصاق‌شده به بریف کدنویسی

verify_on_stop مقدار true (همه‌جا روشن)، ‏false (خاموش — پیش‌فرض) یا "auto" (رفتار قدیمی آگاه-سطح: روشن برای سطوح کدنویسی تعاملی — CLI، ‏TUI، ‏دسکتاپ — و فراخوان‌های برنامه‌پذیر؛ خاموش برای سطوح پیام‌رسانی مثل تلگرام/دیسکورد که روایت راستی‌آزمایی مثل نویز چت خوانده می‌شود) می‌پذیرد. خاموش همه‌جا پیش‌فرض است: نصب‌های تازه با false عرضه و مهاجرت پیکربندی روی نصب‌های موجود خاموشش کرده، پس فعال‌سازی یک اختیار صریح است. متغیر محیطی HERMES_VERIFY_ON_STOP وقتی تنظیم باشد مقدار پیکربندی را بازنویسی می‌کند.

برای یک دروازهٔ سیاستِ کاربر/پلاگین در همان نقطه — ادامهٔ ایجنت با بررسی‌های خودتان — به هوک pre_verify در صفحهٔ هوک‌ها مراجعه کنید.

۲۴ اهداف ایستاده (/goal)

وقتی هدف ایستاده‌ای فعال است، هرمس قضاوت می‌کند آیا هر پاسخ دستیار آن را برآورده می‌کند. اگر نه، یک پرامپت ادامه را به همان نشست بازخورانده و تا رسیدن هدف، اتمام بودجهٔ نوبت یا توقف/پاک‌کردن توسط کاربر به کار ادامه می‌دهد. بودجهٔ نوبت پشتیبان واقعی است — شکست قاضی باز می‌شود (ادامه) تا قاضیِ لرزان هرگز پیشرفت را گیر نیندازد.

yaml
goals:
  max_turns: 20   # حداکثر نوبت‌های ادامه پیش از توقف-خودکار هدف توسط هرمس (پیش‌فرض: 20)

max_turns سقف می‌زند یک هدف چند نوبت ادامه می‌تواند راند پیش از اینکه هرمس خودکار مکثش کند و از کاربر /goal resume بخواهد. در برابر منفی‌های کاذبِ قاضی (هدف واقعاً تمام ولی قاضی می‌گوید ادامه) و خرج بی‌کرانِ مدل روی اهداف مبهم یا دست‌نیافتنی محافظت می‌کند. برای قابلیت کامل به صفحهٔ «اهداف» مراجعه کنید.

۲۵ تایم‌اوت‌های API

هرمس لایه‌های تایم‌اوت جداگانه برای استریم، به‌علاوهٔ آشکارساز بی‌پاسخ برای فراخوانی‌های غیراستریمی دارد. آشکارسازهای بی‌پاسخ فقط وقتی روی پیش‌فرض‌های ضمنی‌شان رها شده باشید برای ارائه‌دهندگان محلی خودتنظیم می‌شوند.

تایم‌اوتپیش‌فرضارائه‌دهندگان محلیپیکربندی / env
تایم‌اوت خواندن سوکت۱۲۰sخودکار به ۱۸۰۰s بالاHERMES_STREAM_READ_TIMEOUT
تشخیص استریم بی‌پاسخ۱۸۰sبه سقف ۹۰۰s بالا (agent.local_stream_stale_timeout)HERMES_STREAM_STALE_TIMEOUT
تشخیص غیراستریم بی‌پاسخ۹۰sوقتی ضمنی رها شده خودکار خاموشproviders.<id>.stale_timeout_seconds یا HERMES_API_CALL_STALE_TIMEOUT
فراخوانی API (غیراستریمی)۱۸۰۰sبدون تغییرproviders.<id>.request_timeout_seconds / ‏timeout_seconds یا HERMES_API_TIMEOUT

تایم‌اوت خواندن سوکت کنترل می‌کند httpx چقدر برای تکهٔ بعدی داده از ارائه‌دهنده صبر می‌کند. ‏LLMهای محلی می‌توانند روی زمینه‌های بزرگ دقیقه‌ها برای prefill پیش از تولید اولین توکن وقت بگیرند، پس هرمس وقتی اندپوینت محلی تشخیص می‌دهد این را به ۳۰ دقیقه می‌برد. اگر HERMES_STREAM_READ_TIMEOUT را صریح بگذارید، آن مقدار صرف‌نظر از تشخیص اندپوینت همیشه استفاده می‌شود.

تشخیص استریم بی‌پاسخ اتصال‌هایی را می‌کشد که پینگ‌های keep-alive ‏SSE می‌گیرند ولی محتوای واقعی نه. برای ارائه‌دهندگان محلی (که حین prefill پینگ keep-alive نمی‌فرستند) پیش‌فرض به سقف متناهی ۹۰۰ ثانیه‌ای به‌جای پایهٔ ۱۸۰ ثانیه بالا می‌رود — با agent.local_stream_stale_timeout یا متغیر محیطی HERMES_LOCAL_STREAM_STALE_TIMEOUT قابل پیکربندی.

تشخیص غیراستریم بی‌پاسخ فراخوانی‌های غیراستریمیِ خیلی طولانی بدون پاسخ را می‌کشد. به‌طور پیش‌فرض هرمس این را روی اندپوینت‌های محلی خاموش می‌کند تا از مثبت‌های کاذب حین prefillهای طولانی جلوگیری شود. اگر providers.<id>.stale_timeout_seconds، ‏providers.<id>.models.<model>.stale_timeout_seconds یا HERMES_API_CALL_STALE_TIMEOUT را صریح بگذارید، همان مقدار صریح حتی روی اندپوینت‌های محلی محترم شمرده می‌شود.

این بودجه همهٔ فراخوانی‌های غیراستریمی — شامل اجراهای درون‌خطی کارهای کرونی و ساب‌ایجنت‌های واگذارشده — را مقید می‌کند. ارائه‌دهنده‌ای که درخواست را می‌پذیرد و بعد ساکت می‌شود — اتصال باز، بدون بایت، بدون خطا — در تایم‌اوت بی‌پاسخ ساقط و retry می‌شود، به‌جای آویزان‌ماندن تا تایم‌اوت خیلی طولانی‌ترِ خواندن سوکت (یا برای اجرای کرونیِ بدون-سرپرست، تا وقتی چیز بیرونی پروسه را بکشد).

۲۶ هشدارهای فشار زمینه

جدا از فشار بودجه تکرار، فشار زمینه می‌پیماید گفتگو چقدر به آستانهٔ فشرده‌سازی — نقطه‌ای که فشرده‌سازی زمینه شلیک می‌شود تا پیام‌های قدیمی‌تر خلاصه شوند — نزدیک است. این به شما و ایجنت کمک می‌کند بفهمید کِی گفتگو طولانی می‌شود.

پیشرفتسطحچه اتفاقی می‌افتد
≥ ۶۰٪ تا آستانهاطلاع‏CLI نوار پیشرفت فیروزه‌ای نشان می‌دهد؛ گیت‌وی اعلان اطلاعاتی می‌فرستد
≥ ۸۵٪ تا آستانههشدار‏CLI نوار زرد پررنگ؛ گیت‌وی هشدار می‌دهد فشرده‌سازی قریب‌الوقوع است

در CLI فشار زمینه به‌صورت نوار پیشرفت در فید خروجی ابزار ظاهر می‌شود:

روی پلتفرم‌های پیام‌رسانی، اعلان متنی-ساده فرستاده می‌شود:

اگر فشرده‌سازی خودکار خاموش باشد، هشدار می‌گوید زمینه ممکن است به‌جایش بریده شود. فشار زمینه خودکار است — بدون پیکربندی. صرفاً به‌عنوان اعلان رو-به-کاربر شلیک می‌شود و جریان پیام را تغییر یا چیزی به زمینه مدل تزریق نمی‌کند.

۲۷ راهبردهای استخر اعتبارنامه

وقتی چند کلید API یا توکن OAuth برای همان ارائه‌دهنده دارید، راهبرد چرخش را پیکربندی کنید:

yaml
credential_pool_strategies:
  openrouter: round_robin    # چرخش یکنواخت بین کلیدها
  anthropic: least_used      # همیشه کمترین-استفاده‌شده

گزینه‌ها: fill_first (پیش‌فرض)، ‏round_robin، ‏least_used، ‏random. برای مستندات کامل به «استخرهای اعتبارنامه» مراجعه کنید.

۲۸ کش پرامپت

هرمس وقتی ارائه‌دهندهٔ فعال پشتیبانی کند، کش پرامپت بین-نشستی را خودکار روشن می‌کند — بدون پیکربندی کاربر.

برای Claude روی آنتروپیک بومی، ‏OpenRouter و Nous Portal، هرمس نقاط شکست cache_control را با TTL یک‌ساعته‏ (ttl: "1h") روی پرامپت سیستمی و بلوک‌های مهارت الصاق می‌کند. اولین ارسال در ساعتِ تازه نرخ ورودی کامل می‌پرداز؛ ارسال‌های بعدی در همان ساعت از هر نشستی از کش با نرخ ارزان‌ترِ خواندن-کش‌شده می‌کشند. یعنی پرامپت سیستمی، محتوای مهارتِ بارگذاری‌شده و بخش ابتداییِ هر گنجایش زمینه-بلند در ساعت اول بین نشست‌های hermes و ساب‌ایجنت‌های انشعابی بازاستفاده می‌شوند.

بالادستیِ Qwen Cloud ‏(‏Alibaba DashScope) ‏TTL کش را ۵ دقیقه سقف می‌کند، پس هرمس آنجا از TTL نقطهٔ شکست ۵ دقیقه‌ای استفاده می‌کند. سایر مسیرهای Claude-از-طرف-شخص‌ثالث‏ (‏AWS Bedrock، ‏Azure Foundry) به پیش‌فرض‌های کش خود ارائه‌دهنده برمی‌گردند. ‏xAI Grok سازوکار جداگانهٔ شناسه-گفتگویِ پین‌شده-به-نشست دارد — به «کش پرامپت xAI» در صفحهٔ ارائه‌دهندگان مراجعه کنید.

پیچی برای خاموش‌کردنش وجود ندارد — کش همیشه-روشن است و حتی روی گفتگوهای تک‌نوبتی پول پس می‌دهد چون خودِ پرامپت سیستمی به‌تنهایی کسر معناداری از شمار توکن ورودی است.

تنها پیچ صریح، ردهٔ TTL کشی است که هرمس روی نقاط شکست سبک-آنتروپیک می‌خواهد:

yaml
prompt_caching:
  cache_ttl: "5m"   # "5m" یا "1h" (رده‌های پشتیبانی‌شدهٔ آنتروپیک)؛ مقادیر دیگر نادیده گرفته می‌شوند

cache_ttl ‏TTL نقطهٔ شکستی را که هرمس برای Claude از طریق API بومی آنتروپیک، ‏OpenRouter و Nous Portal الصاق می‌کند انتخاب می‌کند. فقط دو ردهٔ پشتیبانی‌شدهٔ آنتروپیک‏ ("5m"، ‏"1h") محترم‌اند — هر مقدار دیگر نادیده گرفته می‌شود. ارائه‌دهندگان با سقف خودشان (مثلاً Qwen Cloud که حداکثر ۵ دقیقه است) همچنان به آنچه بالادستی اجازه می‌دهد محدود می‌شوند.

۲۹ مدل‌های کمکی

هرمس از مدل‌های «کمکی» برای کارهای جانبی مثل تحلیل تصویر، خلاصه‌سازی صفحهٔ وب، تحلیل اسکرین‌شات مرورگر، تولید عنوان نشست و فشرده‌سازی زمینه استفاده می‌کند. به‌طور پیش‌فرض‏ (auxiliary.*.provider: "auto")، هرمس هر کار کمکی را به مدل چت اصلی شما مسیریابی می‌کند — همان ارائه‌دهنده/مدیلی که در hermes model برداشته‌اید. برای شروع چیزی پیکربندی نکنید، ولی آگاه باشید روی مدل‌های استدلالی گران (‏Opus، ‏MiniMax M2.7 و غیره) کارهای کمکی هزینهٔ معناداری اضافه می‌کنند. اگر کارهای جانبیِ ارزان-و-سریع صرف‌نظر از مدل اصلی‌تان می‌خواهید، auxiliary.<task>.provider و auxiliary.<task>.model را صریح تنظیم کنید (مثلاً Gemini Flash روی OpenRouter برای بینایی و استخراج وب).

ℹ️ چرا «auto» مدل اصلی شما را می‌گیرد

بیلدهای قدیمی‌تر کاربران تجمیع‌گر‏ (‏OpenRouter، ‏Nous Portal) را روی پیش‌فرض ارزانِ سمت-ارائه‌دهنده می‌گذاشتند. آن غافلگیرکننده بود — کاربرانی که برای اشتراک تجمیع‌گر پول داده بودند مدل متفاوتی را روی ترافیک کمکی‌شان می‌دیدند. auto حالا برای همه از مدل اصلی استفاده می‌کند، و بازنویسی‌های به‌ازای-کار در config.yaml همچنان می‌برند (به «مرجع کامل پیکربندی کمکی» پایین).

پیکربندی تعاملی مدل‌های کمکی

به‌جای ویرایش دستی YAML، hermes model را اجرا و «Configure auxiliary models» را از منو بردارید. یک انتخاب‌گر تعاملی به‌ازای-کار می‌گیرید:

خروجی
$ hermes model
→ Configure auxiliary models

[ ] vision               currently: auto / main model
[ ] web_extract          currently: auto / main model
[ ] title_generation     currently: openrouter / google/gemini-3-flash-preview
[ ] tts_audio_tags       currently: auto / main model
[ ] compression          currently: auto / main model
[ ] approval             currently: auto / main model
[ ] triage_specifier     currently: auto / main model
[ ] kanban_decomposer    currently: auto / main model
[ ] profile_describer    currently: auto / main model
[ ] delegation           currently: auto / inherit main agent

کاری را انتخاب، ارائه‌دهنده‌ای بردارید (جریان‌های OAuth مرورگر باز می‌کنند؛ ارائه‌دهندگان کلید-API می‌پرسند)، مدلی بردارید. تغییر در auxiliary.<task>.* در config.yaml ماندگار می‌شود. همان ماشینِ انتخاب‌گر مدل-اصلی — بدون نگارش اضافه‌ای برای یادگیری.

مدخل Delegation خاص است: مدلی را که ساب‌ایجنت‌های delegate_task استفاده می‌کنند مسیریابی و به‌جای auxiliary.* در بخش سطح‌بالا delegation.*‏ (delegation.provider / ‏delegation.model) ماندگار می‌کند، چون ساب‌ایجنت‌ها ایجنت‌های فرزند کامل‌اند نه فراخوانی‌های LLM جانبی. ‏autoی او یعنی «ارث‌بردن ارائه‌دهنده، مدل و اعتبارنامهٔ ایجنت والد».

اگر نمی‌خواهید هرمس پس از اولین تبادل خودکار عنوان بسازد، auxiliary.title_generation.enabled: false بگذارید. عنوان‌های دستی همچنان با /title و hermes sessions rename کار می‌کنند.

اندپوینت‌های فقط-استریم

برخی اندپوینت‌های سازگار با OpenAI درخواست‌های چت غیراستریمی را کلاً رد می‌کنند (مثلاً Tencent Copilot ‏HTTP 400 ‏«Non-stream chat request is currently not supported» برمی‌گرداند). چت تعاملی از قبل استریم می‌شود، ولی کارهای کمکی (تولید عنوان، فشرده‌سازی، استخراج وب) فراخوانی غیراستریمی می‌کنند و در هر تلاش شکست می‌خوردند. هرمس همیشه copilot.tencent.com را فقط-استریم تلقی می‌کند؛ برای هر اندپوینت دیگری از این دست، یک زیررشتهٔ URL زیر auxiliary.stream_only_base_urls فهرست کنید:

yaml
auxiliary:
  stream_only_base_urls:
    - "my-stream-only-proxy.example.com"

فراخوانی‌های کمکیِ مطابق با stream=True فرستاده و تکه‌ها (شامل دلتای فراخوانی ابزار) سمت-کلاینت تجمیع می‌شوند — بدون تغییر رفتار برای هیچ اندپوینت دیگری.

الگوی جهانی پیکربندی

هر جایگاه مدل در هرمس — کارهای کمکی، فشرده‌سازی، ‏fallback — از همان سه پیچ استفاده می‌کند:

کلیدچه می‌کندپیش‌فرض
providerکدام ارائه‌دهنده برای احراز و مسیریابی"auto"
modelکدام مدل درخواست شودپیش‌فرض ارائه‌دهنده
base_urlاندپوینت سفارشی سازگار با OpenAI (ارائه‌دهنده را بازنویسی می‌کند)تنظیم‌نشده

بلوک‌های کار کمکی به‌علاوهً پیچ reasoning_effort می‌پذیرند:

کلیدچه می‌کندپیش‌فرض
reasoning_effortسطح تفکر برای فراخوانی‌های LLM آن کار: none، ‏minimal، ‏low، ‏medium، ‏high، ‏xhigh، ‏max، ‏ultraتنظیم‌نشده (پیش‌فرض ارائه‌دهنده)

این همتای به‌ازای-کارِ agent.reasoning_effort سراسری است: فشرده‌سازی را روی low یا بینایی را روی none بگذارید تا وقتی مدل اصلی‌تان مدل استدلالی گران است، تأخیر و هزینهٔ کارهای جانبی را ببُرید — بدون دست‌زدن به رفتار چت اصلی. روی هر بلوک کار کمکی‏ (vision، ‏web_extract، ‏compression، ‏title_generation، ‏curator، ‏background_review، …) و در هر سه قالب سیمی کمکی (چت‌کامپلشنز، ‏Responses کدکس، ‏Messages آنتروپیک) کار می‌کند. extra_body.reasoning صریح روی همان کار بر این خلاصه‌نویسی مقدم است.

MoA تنها استثناست: عمق استدلال برای ترکیب-ایجنت‌ها به‌ازای-جایگاه در پیش‌تنظیم MoA پیکربندی می‌شود‏ (moa.presets.<name>.reference_models[].reasoning_effort / ‏aggregator.reasoning_effort)، نه روی بلوک‌های کمکی moa_reference/moa_aggregator — به «ترکیب ایجنت‌ها» مراجعه کنید.

yaml
auxiliary:
  compression:
    reasoning_effort: "low"    # خلاصه‌ها تفکر عمیق نمی‌خواهند
  vision:
    reasoning_effort: "none"   # غیرفعال‌کردن تفکر برای توصیف تصویر

وقتی base_url تنظیم شده باشد، هرمس ارائه‌دهنده را نادیده و آن اندپوینت را مستقیم صدا می‌زند (با api_key یا OPENAI_API_KEY برای احراز). وقتی فقط provider تنظیم شده باشد، هرمس از احراز و base URL داخلی همان ارائه‌دهنده استفاده می‌کند.

ارائه‌دهندگان موجود برای کارهای کمکی: auto، ‏main، به‌علاوهٔ هر ارائه‌دهنده در رجیستری — ‏openrouter، ‏nous، ‏openai-codex، ‏copilot، ‏copilot-acp، ‏anthropic، ‏gemini، ‏qwen-oauth، ‏zai، ‏kimi-coding، ‏kimi-coding-cn، ‏minimax، ‏minimax-cn، ‏minimax-oauth، ‏deepseek، ‏nvidia، ‏xai، ‏xai-oauth، ‏ollama-cloud، ‏alibaba، ‏bedrock، ‏huggingface، ‏arcee، ‏xiaomi، ‏kilocode، ‏opencode-zen، ‏opencode-go، ‏opencode-free، ‏commandcode، ‏commandcode-anthropic، ‏ai-gateway، ‏azure-foundry — یا هر ارائه‌دهندهٔ سفارشیِ نام‌دار از دیکشنری providers: شما (مثلاً provider: "beans").

💡 MiniMax OAuth

minimax-oauth با OAuth مرورگر وارد می‌شود (بدون کلید API). hermes model را اجرا و «MiniMax (OAuth)» را برای احراز انتخاب کنید. کارهای کمکی خودکار از MiniMax-M2.7-highspeed استفاده می‌کنند. به راهنمای MiniMax OAuth مراجعه کنید.

💡 xAI Grok OAuth

xai-oauth با OAuth مرورگر برای مشترکان SuperGrok و X Premium+ وارد می‌شود (بدون کلید API). hermes model را اجرا و «xAI Grok OAuth (SuperGrok / Premium+)» را انتخاب کنید. همان توکن OAuth برای هر سطح مستقیم-به-xAI‏ (چت، کارهای کمکی، ‏TTS، تولید تصویر، تولید ویدیو، رونویسی) بازاستفاده می‌شود. اگر هرمس روی میزبان راهن است به راهنمای «OAuth روی SSH» مراجعه کنید.

⚠️ «main» فقط برای کارهای کمکی است

گزینهٔ ارائه‌دهندهٔ "main" یعنی «هر ارائه‌دهنده‌ای که ایجنت اصلی‌ام استفاده می‌کند» — فقط داخل auxiliary:، ‏compression: و مدخل‌های fallback اصلی‏ (fallback_providers: یا fallback_model: قدیمی) معتبر است. برای تنظیم سطح‌بالا model.provider مقدار معتبری نیست. اگر اندپوینت سفارشی سازگار با OpenAI استفاده می‌کنید، در بخش model: ‏provider: custom بگذارید. برای همهٔ گزینه‌های ارائه‌دهندهٔ مدل اصلی به «ارائه‌دهندگان هوش مصنوعی» مراجعه کنید.

مرجع کامل پیکربندی کمکی

yaml
auxiliary:
  # تحلیل تصویر (ابزار vision_analyze + اسکرین‌شات‌های مرورگر)
  vision:
    provider: "auto"           # "auto", "openrouter", "nous", "codex", "main" و غیره
    model: ""                  # مثل "openai/gpt-4o", "google/gemini-2.5-flash"
    base_url: ""               # اندپوینت سفارشی سازگار با OpenAI (ارائه‌دهنده را بازنویسی می‌کند)
    api_key: ""                # کلید API برای base_url (به OPENAI_API_KEY برمی‌گردد)
    timeout: 120               # ثانیه — تایم‌اوت فراخوانی LLM؛ بارهای بینایی تایم‌اوت سخاوتمیزانه می‌خواهند
    download_timeout: 30       # ثانیه — دانلود HTTP تصویر؛ برای اتصال‌های کند بالا ببرید
    max_concurrency: 8         # حداکثر انفجارهای هم‌زمان کدگذاری/تغییراندازهٔ تصویر در کل پروسه
                               # (پیش‌فرض: شمار هستهٔ CPU میزبان، بدون سقف) — فقط گام کدگذاریِ
                               # CPU-محور را مقید می‌کند تا پخش فریم-ویدیو نتواند همهٔ هسته‌ها را
                               # اشغال و حلقهٔ رویداد را گرسنه کند؛ فراخوانی‌های LLM کاملاً
                               # هم‌زمان می‌مانند. حداقل ۱؛ مقادیر < ۱ نادیده گرفته می‌شوند.

  # خلاصه‌سازی صفحهٔ وب + استخراج متن صفحهٔ مرورگر
  web_extract:
    provider: "auto"
    model: ""                  # مثل "google/gemini-2.5-flash"

    api_key: ""
    timeout: 360               # ثانیه (۶ دقیقه) — خلاصه‌سازی LLM به‌ازای-تلاش

  # عناوین خودکار نشست. زبان خالی از گفتگو پیروی می‌کند؛
  # مثل "English" یا "Japanese" بگذارید تا عناوین به یک زبان پین شوند.

💡 نکته

هر کار کمکی timeout قابل‌پیکربندی‌ای دارد (به ثانیه). پیش‌فرض‌ها: بینایی ۱۲۰s، ‏web_extract ‏۳۶۰s، ‏تأیید ۳۰s، ‏فشرده‌سازی ۱۲۰s. اگر از مدل‌های محلی کند برای کارهای کمکی استفاده می‌کنید این‌ها را بالا ببرید. بینایی به‌علاوه download_timeout جداگانه‌ای (پیش‌فرض ۳۰s) برای دانلود HTTP تصویر دارد — برای اتصال‌های کند یا سرورهای تصویر خودمیزبان بالایش بیاورید.

ℹ️ توجه

فشرده‌سازی زمینه بلوک compression: خودش را برای آستانه‌ها و بلوک auxiliary.compression: را برای تنظیمات مدل/ارائه‌دهنده دارد — به «فشرده‌سازی زمینه» بالاتر مراجعه کنید. زنجیرهٔ fallback اصلی از فهرست سطح‌بالا fallback_providers: استفاده می‌کند — به «ارائه‌دهندگان پشتیبان». هر سه از الگوی یکسان ارائه‌دهنده/مدل/base_url پیروی می‌کنند.

زنجیرهٔ fallback به‌ازایی-کار برای کارهای کمکی

هر کار کمکی می‌تواند اختیاراً fallback_chainای تعریف کند — فهرستی از مدخل‌های ارائه‌دهنده/مدل که هرمس وقتی ارائه‌دهندهٔ کمکیِ اصلی به‌خاطر محدودیت نرخ، مشکل اتصال یا محدودیت پرداخت شکست می‌خورد امتحان می‌کند:

yaml
auxiliary:
  compression:
    provider: openrouter
    model: openai/gpt-4o-mini
    fallback_chain:
      - provider: nous
        model: deepseek/deepseek-chat
      - provider: openrouter
        model: google/gemini-2.5-flash

وقتی ارائه‌دهندهٔ کمکی اصلی‏ (openrouter / ‏openai/gpt-4o-mini) خطای محدودیت-نرخ، تایم‌اوت اتصال یا پرداخت-لازم برگرداند، هرمس fallback_chain را به ترتیب می‌پیماید. مدخل‌هایی که ارائه‌دهنده‌شان با ارائه‌دهندهٔ از-قبل-شکست‌خورده مطابق است را رد می‌کند، و هر مدخل باقی‌مانده را تا موفقیت یکی یا اتمام زنجیره امتحان می‌کند. اگر همهٔ fallbackها شکست بخورند، هرمس به‌عنوان تور ایمنی نهایی به مدل ایجنت اصلی برمی‌گردد.

هر مدخل همان سه پیچِ هر پیکربندی کار کمکی را پشتیبانی می‌کند: provider، ‏model و ‏base_url اختیاری. fallback_chain روی هر کار کمکی موجود است — ‏compression، ‏vision، ‏web_extract، ‏approval، ‏skills_hub، ‏mcp و غیره.

محدودسازی هم‌زمانی کمکی

max_concurrency فراخوانی‌های LLM در-پروازِ کارهای کمکی مثل compression و title_generation را در کل پروسه سقف می‌زند. auxiliary.vision.max_concurrency مستثناست: از قبل فقط کارگرهای کدگذاری/تغییراندازهٔ تصویرِ CPU-محور بینایی را کنترل می‌کند، نه درخواست‌های LLM را. این بیش از همه مفید است وقتی:

  • نشست‌های زیاد می‌توانند هم‌زمان کار پس‌زمینه تولید کنند‏ (کانال‌های دیسکورد/تلگرام، چند ترمینال)
  • ارائه‌دهنده‌تان محدودیت-نرخ دارد یا حادثه‌ای را می‌گذراند و retryها انفجار را تقویت می‌کنند

پیش‌فرض نامحدود است. یک سقف ایمنی معمول 2 است:

yaml
auxiliary:
  title_generation:
    max_concurrency: 2
  compression:
    max_concurrency: 2

سمافور کل فراخوانی شامل retryها و fallbackها را می‌پیچد، پس یک فراخوانی کُند تکی فقط یک بار به سمت حد حساب می‌شود.

مسیریابی OpenRouter و Pareto Code برای کارهای کمکی

وقتی کاری کمکی به OpenRouter حل می‌شود (صریح یا با provider: "main" وقتی ایجنت اصلی‌تان روی OpenRouter است)، تنظیمات provider_routing و openrouter.min_coding_score ایجنت اصلی منتقل نمی‌شوند — به‌طرز طراحی‌شده، هر کار کمکی مستقل است. برای تنظیم ترجیحات ارائه‌دهندهٔ OpenRouter یا استفاده از «روتر Pareto Code» برای کار کمکی مشخص، به‌ازای-کار از طریق extra_body تنظیمشان کنید:

yaml
auxiliary:
  compression:
    provider: openrouter
    model: openrouter/pareto-code         # استفاده از روتر Pareto Code برای این کار
    extra_body:
      provider:                            # ترجیحات مسیریابی ارائه‌دهندهٔ OpenRouter
        order: [anthropic, google]         # امتحان این ارائه‌دهندگان به ترتیب
        sort: throughput                   # یا "price" | "latency"
        # only: [anthropic]                # محدودکردن به ارائه‌دهندهٔ مشخص
        # ignore: [deepinfra]              # حذف ارائه‌دهندگان مشخص
      plugins:                             # پیچ روتر Pareto Code مربوط به OpenRouter
        - id: pareto-router
          min_coding_score: 0.5            # ۰٫۰–۱٫۰؛ بالاتر = کدنویس‌های قوی‌تر

شکل آینهٔ چیزی است که OpenRouter در بدنهٔ درخواست چت‌کامپلشنز می‌پذیرد. هرمس کل extra_body را تحت‌اللفظی فوروارد می‌کند، پس هر فیلد دیگری از بدنهٔ درخواست OpenRouter که در openrouter.ai/docs مستند شده به همان شکل کار می‌کند.

گزینه‌های ارائه‌دهنده

این گزینه‌ها روی پیکربندی‌های کار کمکی‏ (auxiliary:، ‏compression:) و مدخل‌های fallback اصلی‏ (fallback_providers: یا fallback_model: قدیمی) اعمال می‌شوند، نه روی تنظیم model.provider اصلی شما.

ارائه‌دهندهتوضیحنیازمندی‌ها
"auto"بهترین موجود (پیش‌فرض). بینایی OpenRouter ← Nous ← Codex را امتحان می‌کند.—
"openrouter"اجبار OpenRouter — مسیریابی به هر مدل (‏Gemini، ‏GPT-4o، ‏Claude و غیره)OPENROUTER_API_KEY
"nous"اجبار Nous Portalhermes auth
"codex"اجبار Codex OAuth (حساب ChatGPT). بینایی پشتیبانی می‌شود (gpt-5.3-codex).hermes model ← ChatGPT یا Codex Subscription
"minimax-oauth"اجبار MiniMax OAuth (ورود مرورگر، بدون کلید API). از MiniMax-M2.7-highspeed برای کارهای کمکی استفاده می‌کند.hermes model ← MiniMax (OAuth)
"xai-oauth"اجبار xAI Grok OAuth (ورود مرورگر برای مشترکان SuperGrok یا X Premium+، بدون کلید API). همان توکن OAuth چت، ‏TTS، تصویر، ویدیو و رونویسی را پوشش می‌دهد.hermes model ← xAI Grok OAuth
"main"استفاده از اندپوینت سفارشی/اصلی فعال شما. می‌تواند از OPENAI_BASE_URL + ‏OPENAI_API_KEY یا اندپوینت سفارشیِ ذخیره‌شده با hermes model / config.yaml بیاید. با OpenAI، مدل‌های محلی یا هر API سازگار با OpenAI کار می‌کند. فقط کارهای کمکی — برای model.provider معتبر نیست.اعتبار + base URL اندپوینت سفارشی

ارائه‌دهندگان کلید-API مستقیم از کاتالوگ اصلی اینجا هم وقتی می‌خواهید کارهای جانبی از روتر پیش‌فرضتان عبور کنند کار می‌کنند. مثلاً gmi وقتی GMI_API_KEY پیکربندی شد معتبر است، و fireworks وقتی FIREWORKS_API_KEY پیکربندی شد:

yaml
auxiliary:
  compression:
    provider: "gmi"
    model: "anthropic/claude-opus-4.6"

برای مسیریابی کمکی GMI، شناسهٔ دقیق مدلِ برگردانده‌شده توسط اندپوینت /v1/models مربوط به GMI را استفاده کنید. شناسه‌های Fireworks از فرم اسلش بومی ارائه‌دهنده استفاده می‌کنند، مثلاً accounts/fireworks/models/glm-5p2.

راه‌اندازی‌های رایج

استفاده از اندپوینت سفارشی مستقیم (روشن‌تر از provider: "main" برای APIهای محلی/خودمیزبان):

yaml
auxiliary:
  vision:
    base_url: "http://localhost:1234/v1"
    api_key: "local-key"
    model: "qwen2.5-vl"

base_url بر provider مقدم است، پس این صریح‌ترین راه مسیریابی کار کمکی به اندپوینت مشخص است. برای بازنویسی اندپوینت مستقیم، هرمس از api_key پیکربندی‌شده استفاده یا به OPENAI_API_KEY برمی‌گردد؛ ‏OPENROUTER_API_KEY را برای آن اندپوینت سفارشی بازاستفاده نمی‌کند.

استفاده از کلید OpenAI برای بینایی:

yaml
# در ~/.hermes/.env:
# OPENAI_BASE_URL=https://api.openai.com/v1
# OPENAI_API_KEY=sk-...

auxiliary:
  vision:
    provider: "main"
    model: "gpt-4o"       # یا "gpt-4o-mini" برای ارزان‌تر

استفاده از OpenRouter برای بینایی (مسیریابی به هر مدل):

yaml
auxiliary:
  vision:
    provider: "openrouter"
    model: "openai/gpt-4o"      # یا "google/gemini-2.5-flash" و غیره

yaml

    # مدل پیش‌فرض gpt-5.3-codex است (بینایی پشتیبانی می‌شود)

استفاده از MiniMax OAuth (ورود مرورگر، بدون کلید API):

yaml
model:
  default: MiniMax-M2.7
  provider: minimax-oauth
  base_url: https://api.minimax.io/anthropic

hermes model را اجرا و «MiniMax (OAuth)» را برای ورود و تنظیم خودکار انتخاب کنید. برای منطقهٔ چین، ‏base URL ‏https://api.minimaxi.com/anthropic خواهد بود. برای راهنمای کامل به راهنمای MiniMax OAuth مراجعه کنید.

استفاده از مدل محلی/خودمیزبان:

yaml
auxiliary:
  vision:
    provider: "main"      # از اندپوینت سفارشی فعال شما استفاده می‌کند
    model: "my-local-model"

provider: "main" از هر ارائه‌دهنده‌ای که هرمس برای چت عادی استفاده می‌کند — چه ارائه‌دهندهٔ سفارشیِ نام‌دار (مثلاً beans)، چه ارائه‌دهندهٔ داخلی مثل openrouter، چه اندپوینت قدیمی OPENAI_BASE_URL — استفاده می‌کند.

💡 نکته

اگر Codex OAuth را به‌عنوان ارائه‌دهندهٔ مدل اصلی استفاده می‌کنید، بینایی خودکار کار می‌کند — بدون پیکربندی اضافه. کدکس در زنجیرهٔ تشخیص خودکار بینایی هست.

⚠️ هشدار

بینایی مدل چندهمدیایی می‌خواهد. اگر provider: "main" گذاشته‌اید، مطمئن شوید اندپوینت‌تان چندمدیایی/بینایی را پشتیبانی می‌کند — وگرنه تحلیل تصویر شکست می‌خورد.

متغیرهای محیطی (قدیمی)

مدل‌های کمکی از طریق متغیرهای محیطی هم قابل پیکربندی‌اند. با این حال config.yaml روش ترجیحی است — مدیریتش آسان‌تر است و همهٔ گزینه‌ها از جمله base_url و api_key را پشتیبانی می‌کند.

تنظیمات فشرده‌سازی و مدل fallback فقط از config.yaml هستند. hermes config را اجرا کنید تا تنظیمات کمکی فعلی‌تان را ببینید. بازنویسی‌ها فقط وقتی با پیش‌فرض‌ها فرق دارند ظاهر می‌شوند.

۳۰ سطح تلاش استدلال

کنترل می‌کند مدل پیش از پاسخ چقدر «فکر» می‌کند:

yaml
agent:
  reasoning_effort: ""   # خالی = medium. گزینه‌ها: none, minimal, low, medium, high, xhigh, max, ultra

وقتی تنظیم نشده (پیش‌فرض)، سطح استدلال «medium» است — سطحی متعادل که برای اغلب کارها خوب کار می‌کند. گذاشتن مقدار آن را بازنویسی می‌کند — استدلال بالاتر نتیجهٔ بهتر روی کارهای پیچیده به بهای توکن و تأخیر بیشتر می‌دهد.

ℹ️ مدل‌های استدلال-تطبیقی (‏Claude 4.6+، کلاس Fable/Mythos) روی OpenRouter

این مدل‌ها از استدلال تطبیقی استفاده و فیلد معمول reasoning.effort را نمی‌پذیرند — OpenRouter برایشان نادیده می‌گیرد. هرمس شفاف reasoning_effort شما را به پارامتر verbosity مربوط به OpenRouter می‌رساند (که به output_config.effort آنتروپیک نگاشت می‌شود)، پس همان پیچ با سطوح پشتیبانی‌شده توسط مدل انتخابی کار می‌کند. none (یا تنظیم‌نشده) مدل را روی پیش‌فرض تطبیقی خودش می‌گذارد. ارائه‌دهندهٔ آنتروپیکِ بومی از قبل مستقیماً تلاش را کنترل می‌کند و متأثر نمی‌شود.

ℹ️ مدل‌های OpenRouter و سطوح تلاش پشتیبانی‌شده

برای سایر مدل‌های مسیریابی‌شده از طریق OpenRouter، هرمس فرادادهٔ استدلال کاتالوگ زندهٔ مدل‏ (supported_parameters + ‏reasoning.supported_efforts به‌ازای-مدل) را می‌خواند تا تصمیم بگیرد اصلاً کنترل استدلال بفرستد یا نه، و تلاشِ درخواستی‌تان را به نزدیک‌ترین سطحی که مسیر واقعاً پشتیبانی می‌کند سقف بزند (همیشه رو به پایین — مثلاً ultra روی مسیری که تا high می‌ایستد می‌شود high، هرگز تشدید خاموش نه). فروشندگانِ جدیدِ استدلال‌پذیر بدون انتظار برای به‌روزرسانی هرمس خودکار کار می‌کنند؛ وقتی کاتالوگ در دسترس نیست یا مدلی فهرست نیست، هرمس به فهرست خانواده-مدلِ داخلی‌اش برمی‌گردد و تلاش شما را بی‌تغییر پاس می‌دهد.

در زمان اجرا هم با فرمان /reasoning عوضش کنید:

فرمان‌ها
/reasoning                # نمایش سطح فعلی و وضعیت نمایش
/reasoning high           # تلاش high (فقط همین نشست)
/reasoning high --global  # تنظیم تلاش و ماندگاری در config.yaml
/reasoning none           # غیرفعال‌کردن استدلال (فقط همین نشست)
/reasoning show           # نمایش تفکر مدل بالای هر پاسخ
/reasoning hide           # مخفی‌کردن تفکر مدل

تغییرها به‌طور پیش‌فرض در-دامنهٔ-نشست‌اند؛ ‏--global اضافه کنید تا سطح جدید به‌عنوان پیش‌فرض agent.reasoning_effort ذخیره شود.

بازنویسی استدلال به‌ازای-مدل

می‌توانید برای مدل‌های متفاوت سطوح متفاوت بگذارید — مفید وقتی استدلال بالا برای مدل‌های پیچیده ولی medium برای سریع‌ها می‌خواهید:

yaml
agent:
  reasoning_effort: "medium"       # پیش‌فرض سراسری
  reasoning_overrides:
    "openrouter/anthropic/claude-opus-4.5": "xhigh"
    "openai/gpt-5": "low"
    "claude-sonnet-4.6": "high"    # نام خالی مدل هم کار می‌کند

تطبیق کلید روا-به-املاست — هر املاً معقولی مطابق می‌شود: ‏claude-opus-4.5، ‏claude-opus-4-5، ‏claude-opus.4.5 (نقطه و خط تیره قابل‌معاوضه‌اند)؛ ‏anthropic/claude-opus-4.5، ‏openrouter/anthropic/claude-opus-4.5 (پیشوند ارائه‌دهنده اختیاری)؛ تطبیق دقیق بر واریانت مقدم است.

ℹ️ توجه

پشتیبانی hermes config set برای کلیدهای reasoning_overrides وجود ندارد — فایل YAML را مستقیم ویرایش کنید. چون نام مدل‌ها اغلب نقطه دارند (مثلاً claude-opus-4.5) که با نگارش کلید-نقطه‌چین CLI تعارض می‌کند.

اولویت حل:

  1. بازنویسی /reasoning --session در-دامنهٔ-نشست (فقط گیت‌وی)
  2. بازنویسی به‌ازای-مدل از agent.reasoning_overrides (روا-به-امل)
  3. agent.reasoning_effort سراسری
  4. پیش‌فرض ارائه‌دهنده

بازنویسی همه‌جا خودکار اعمال می‌شود: شروع CLI، گیت‌وی پیام‌رسانی، دسکتاپ/TUI، کارهای کرونی، سوییچ‌های /model میان-نشستی و فعال‌شدن مدل fallback.

۳۱ اجبار استفاده از ابزار

برخی مدل‌ها گاهی اقداماتِ قصدشده را به‌صورت متن توصیف می‌کنند به‌جای فراخوانی ابزار («تست‌ها را اجرا می‌کردم…» به‌جای فراخوانی واقعی ترمینال). اجبار استفاده از ابزار، راهنمای پرامپت سیستمی تزریق می‌کند که مدل را به فراخوانی واقعی ابزارها برمی‌گرداند.

yaml
agent:
  tool_use_enforcement: "auto"   # "auto" | true | false | ["model-substring", ...]
مقداررفتار
"auto" (پیش‌فرض)برای مدل‌های منطبق روشن: gpt، ‏codex، ‏gemini، ‏gemma، ‏grok، ‏glm، ‏qwen، ‏deepseek. برای بقیه (مثلاً Claude) خاموش.
trueهمیشه روشن، صرف‌نظر از مدل. مفید اگر می‌بینید مدل فعلی‌تان به‌جای انجام، توصیف می‌کند.
falseهمیشه خاموش، صرف‌نظر از مدل.
["gpt", "codex", "qwen", "llama"]فقط وقتی روشن که نام مدل یکی از زیررشته‌های فهرست‌شده را داشته باشد (بدون حساسیت به بزرگی/کوچکی).

چه چیزی تزریق می‌شود

وقتی فعال است، دو لایه راهنما ممکن است به پرامپت سیستمی اضافه شوند:

  1. اجبار عمومی استفاده از ابزار (همهٔ مدل‌های مطبق) — به مدل دستور می‌دهد فراخوانی ابزار را فوری انجام دهد به‌جای توصیف نیت، تا وقتی کار تمام نشده به کار ادامه دهد و هرگز نوبتی را با وعدهٔ اقدام آینده تمام نکند.
  2. راهنمای عملیاتی گوگل (فقط مدل‌های Gemini و Gemma) — اختصار، مسیرهای مطلق، فراخوانی موازی ابزار و الگوهای راستی‌آزمایی-پیش-از-ویرایش.

این‌ها برای کاربر شفاف‌اند و فقط پرامپت سیستمی را تأثیر می‌دهند. مدل‌هایی که از قبل قابل‌اعتماد ابزار استفاده می‌کنند (مثل Claude) این راهنما را لازم ندارند — برای همین "auto" آن‌ها را مستثنا می‌کند.

کِی روشنش کنید

اگر مدلی خارج از فهرست خودکار دارید و می‌بینید مکرراً آنچه می‌کرد را توصیف می‌کند به‌جای انجامش، tool_use_enforcement: true بگذارید یا زیررشتهٔ مدل را به فهرست اضافه کنید:

yaml
agent:
  tool_use_enforcement: ["gpt", "codex", "gemini", "grok", "my-custom-model"]

۳۲ راهنمای انضباط اجرا

جدا از اجبار استفاده از ابزار، هرمس بلوکِ انضباط-اجرایی را برای خانواده‌های مدل تزریق می‌کند که مجموعه‌ای از حالات شکست ایجنتیِ مشترک در رده‌های ارزیابی را تقسیم می‌کنند: حساب ذهنی به‌جای کد، نادیده‌گرفتن راستی‌آزماییِ خواندن-مجدد پس از نوشتن‌های بیرونی، «تعمیر» شناسه‌های بدشکل، ادعای کامل‌بودن با وجود ناهم‌خوانی شمارش، و اعلام «تمام» بدون راستی‌آزمایی همهٔ معیارهای پذیرش.

yaml
agent:
  execution_guidance: "auto"   # "auto" | true | false | ["model-substring", ...]
مقداررفتار
"auto" (پیش‌فرض)برای مدل‌های منطبق روشن: gpt، ‏codex، ‏grok، ‏deepseek، ‏kimi، ‏qwen، ‏glm، ‏minimax، ‏mimo، ‏mistral.
trueهمیشه روشن، صرف‌نظر از مدل.
falseهمیشه خاموش، صرف‌نظر از مدل.
["deepseek", "my-custom-model"]فقط وقتی روشن که نام مدل یکی از زیررشته‌ها را داشته باشد.

بلوک تزریق‌شده پوشش می‌دهد:

  • پایداری ابزار — به فراخوانی ابزار ادامه دهید تا کار کامل و راستی‌آزمایی‌شده باشد؛ نتایج خالی/جزئی/مشکوک‌به-باریک را با کوئری گسترده‌تر یا متفاوت retry کنید پیش از نتیجه‌گیری.
  • استفادهٔ الزامی از ابزار — حساب، هش، تاریخ، وضعیت سیستم و حقایق فایل همیشه از ابزار می‌آیند، هرگز از محاسبهٔ ذهنی.
  • خواندن-مجدد نوشتن بیرونی — پس از هر نوشتنِ تغییردهنده-وضعیت به سیستم بیرونی، هدفِ دقیق را پیش از ادعای موفقیت دوباره بخوانید (ویرایش‌های فایل داخلیِ از-پیش-تأیید‌شده-با-ابزار دوباره راستی‌آزمایی نمی‌شوند).
  • تطبیق شمارش — مجموع‌های اعلام‌شده‏ (total، ‏reply_count، ‏has_more) ادعاهای سخت‌اند؛ هنگام ناهم‌خوانی، دوباره fetch یا برنامه‌ای تجزیه کنید.
  • حفظ تحت‌اللفظی — شناسه‌هایی که با قالبِ تصریح‌شده شکست می‌خورند هرگز نرمال یا «تعمیر» نشوند؛ یک lookup موفق، توکنِ منبعِ بدشکل را تأیید نمی‌کند.
  • تکمیلِ گیت‌شده-با-راستی‌آزمایی — «تمام» یعنی هر معیار پذیرشِ نام‌برده راستی‌آزمایی شده، هرگز زیرمجموعهٔ موجهی نیست.

دروازه مستقل از tool_use_enforcement است — هر کدام می‌توانند بدون دیگری روشن باشند. راهنما یک بار در شروع نشست با کلیدِ نام مدل انتخاب می‌شود، پس پرامپت سیستمی برای عمر گفتگو بایت-پایدار (و کش-پرامپت-دوست) می‌ماند. ‏Gemini/Gemma از فهرست auto مستثنا‌اند چون راهنمای عملیاتی خاص‌تر گوگل را می‌گیرند؛ ‏Claude مستثناست چون این حالات شکست را نشان نمی‌دهد — هر مدلی را با true یا فهرست زیررشته به آن بیاورید.

۳۳ گاردریل‌های حلقهٔ ابزار

هرمس تشخیص می‌دهد کِی ایجنت در حلقهٔ فراخوانی ابزارِ غیرمولد گیر کرده — همان فراخوانی ابزار مکرراً شکست می‌خورد، همان ابزار دوباره و دوباره می‌سوزد، یا فراخوانی idempotent همان نتیجه را بدون پیشرفت برمی‌گرداند. به‌طور پیش‌فرض یک هشدار به نتیجهٔ ابزار تزریق می‌کند تا مدل خوداصلاح شود؛ هارد-استاپ نمی‌زند، چون انسانی که CLI/TUI را می‌بیند می‌تواند مداخله کند.

برای استقرارهای گیت‌وی/سرورِ بدون سرپرست، هارد-استاپ‌ها را فعال کنید تا ایجنتِ گیرکرده قطع‌شودنهٔ مدار شود به‌جای سوزاندن بودجه تکرار:

yaml
tool_loop_guardrails:
  warnings_enabled: true       # تزریق هشدارها به نتایج ابزار (پیش‌فرض: true)
  hard_stop_enabled: false     # همچنین BLOCK فراخوانی پس از آستانهٔ هارد-استاپ (پیش‌فرض: false)
  warn_after:
    exact_failure: 2           # فراخوانیِ شکست‌خوردهٔ یکسان تکرار N بار
    same_tool_failure: 3       # همان ابزار N بار می‌سوزد (آرگومان‌های متفاوت)
    idempotent_no_progress: 2  # همان نتیجه، بدون پیشرفت، N بار
  hard_stop_after:
    exact_failure: 5
    same_tool_failure: 8
    idempotent_no_progress: 5
  loop_caps:
    max_web_searches: 50       # حداکثر فراخوانی web_search به‌ازای-نوبت (۰ = نامحدود)
    max_subagents: 50          # حداکثر ساب‌ایجنتِ تولیدشده به‌ازای-نوبت (۰ = نامحدود)

hard_stop_enabled پیش‌فرض false چون نشست‌های تعاملی انسانی در حلقه دارند. در استقرارهای بدون-سرپرست (گیت‌وی، کرون، کارگرهای کانبان) true بگذارید تا شکست‌های مکرر بلاک شوند به‌جای فقط-هشدارشدن. به «داکر / استقرارهای بدون سرپرست» هم مراجعه کنید.

سقف‌های حلقهٔ فراری به‌ازای-نوبت

جدا از آستانه‌های مبتنی-بر-شکست بالا، loop_caps سقف‌های سفت چقدر فراخوانی web_search و تولید ساب‌ایجنت یک حلقهٔ (نوبتِ) تکی ایجنت می‌تواند بگذارد. شمارنده‌ها در شروع هر نوبت ریست می‌شوند، پس نشست مشروعِ چندنوبتی هرگز گرسنه نمی‌ماند — ولی نوبتی که به حلقهٔ جستجو یا واگذاریِ بی‌کران مارپیچ شود متوقف می‌شود. این‌ها همیشه روشن‌اند و صرف‌نظر از hard_stop_enabled شلیک می‌شوند. نوبتی که ده‌ها جستجوی وب صادر یا ده‌ها ساب‌ایجنت تولید می‌کند از قبل پاتولوژیک است، پس پیش‌فرض‌ها پایین‌اند. وقتی سقفی رسید، فراخوانی خاطی با پیام توضیحی بلاک و نوبت تمیز متوقف می‌شود به‌جای سوزاندن باقی بودجه. هر مقدار را 0 بگذارید تا آن سقف کلاً خاموش شود.

یک بچِ تکیِ delegate_task هر کار را به سمت max_subagents حساب می‌کند (بچِ ۳، ‏۳ خرج می‌کند)، پس سقف ساب‌ایجنت‌های واقعیِ تولیدشده را دنبال می‌کند نه فراخوانی‌های delegate_task را. این آینهٔ سقف‌های WebSearch و ساب‌ایجنت به‌ازای-نشستِ Claude Code ‏(‏v2.1.212) است که پیش‌فرض ۲۰۰ دارند و با /clear ریست می‌شوند.

گاردهای ضد-تعلیق زمان اجرا

مکمل گاردریل‌های مبتنی-بر-شکست بالا، agent.stall_guards (پیش‌فرض true) دو گارد محافظه‌کار زمان-اجرا در برابر نوبت‌های هدررفته فعال می‌کند. اول، یک شکنندهٔ حلقهٔ فراخوانی-یکسان: وقتی همان ابزار ۳+ بار متوالی با آرگومان‌های یکسان صدا زده شود و نتیجهٔ یکسان برگرداند، یک یادداشت یک‌خطی کوتاه به آن نتیجهٔ ابزار الصاق می‌شود که به مدل بگوید فراخوانی را تکرار نکند — هرگز فراخوانی را بلاک نمی‌کند، و pollerهای قانوناً-تکرارپذیر‏ (process، ‏*_get_result، ‏*_poll) معاف‌اند. دوم، بازیابی نیتِ ادامه: وقتی مدل نوبتی را بدون فراخوانی ابزار ولی با پاسخ کوتاهِ معلق‌کنندهٔ اعلام اقدام («حالا فایل را به‌روزرسانی می‌کنم…») تمام می‌کند، هرمس با همان سازوکار ادامهٔ کراندارِ استفاده‌شده برای بازیابی نیت-تصریح، دوباره پرامپتش می‌کند (حداکثر ۲ re-prامپت به‌ازای-نوبت). هر دو کش-امن‌اند (اعلان‌ها هنگام ساخت نتیجه افزوده می‌شوند، هرگز بازگشتی نه) و با هم قابل‌غیرفعال‌کردن‌اند:

yaml
agent:
  stall_guards: false

همان دروازه stub‌سازی ارجاع-نتیجه را هم فعال می‌کند: وقتی فراخوانی ابزارِ یکسانِ بازصادرشده نتیجهٔ تازهٔ بایت-به-بایت یکسان برگرداند، بار تکراری به‌صورت stub ارجاعیِ کوتاهی وارد زمینه می‌شود که به نتیجهٔ قبلی اشاره دارد (نام ابزار، ‏tool_call_id، خلاصهٔ آرگومان‌ها و — اگر نتیجهٔ اول روی دیسک ماندگار شده — مسیر سرریزش) به‌جای تکرار خروجی کامل. ابزار هر بار همچنان اجرا می‌شود، پس معناشناسی polling حفظ می‌شود: نتیجهٔ تغییرکرده همیشه کامل جریان می‌یابد. نتایج زیر ۵۱۲ کاراکتر، نتایج خطا و نتایج چندمدیایی هرگز stub نمی‌شوند، و pollerها stub می‌شوند (poll بدون تغییر دقیقاً حالتی است که بار تکراری هیچ اطلاعاتی حمل نمی‌کند).

شمارش از فید پیشرفت ابزاری که CLI از قبل می‌گیرد مشاهده می‌شود، پس هزینهٔ اضافه‌ای ندارد. جزئیات:

  • زمان دیواری، مدت واقعی نوبت است‏ (2m05s پس از گذر از دقیقهٔ یک).
  • فراخوانی‌های ابزار بر اساس فعل گروه‌بندی می‌شوند‏ (edited، ‏read، ‏ran، ‏searched، …) با جمع‌بندی درست؛ ابزارهای پلاگین/MCP بدون فعل گزینش‌شده به called N tools فرو می‌ریزند.
  • دلتاهای خط +X -Y فقط وقتی ظاهر می‌شوند که نتیجهٔ ابزار از قبل دیف گزارش کند (فعلاً patch). هرمس هرگز برای محاسبه‌شان به git نمی‌زند، پس ویرایش write_file بدون دلتا شمرده می‌شود.
  • فراخوانی‌های ابزارِ شکست‌خورده شمرده نمی‌شوند — نوشتنِ ردشده هرگز به‌عنوان ویرایش موفق رندر نمی‌شود (پانوشت راستی‌آزمای جهش-فایل را برای هشدار مکمل ببینید).
  • نوبت‌های طولانی روی چهار قطعه فعل + دنبالهٔ +N more سقف می‌خورند تا خط هرگز نپیچد.
  • نوبت سریع بدون فراخوانی ابزار اصلاً چیزی چاپ نمی‌کند.

شمارش به‌ازای-نوبت است (مجموع‌های نشست در شروع نوبت پایه‌گذاری می‌شوند) و با گزارش مصرفِ هر فراخوانی API در نوبت به‌روز می‌شود. پیش از رسیدن اولین گزارش مصرف چیزی رندر نمی‌شود، پس هرگز ↓ 0 tok گمراه‌کننده نمی‌بینید.

هر دو کلید فقط-نمایش و فقط-CLI‌اند: در حالت ساکت، وقتی display.tool_progress برابر off است، در اجراهای تک-کوئری/بچ -Q و در سطوح گیت‌وی/پیام‌رسانی سرکوب می‌شوند (آنها به‌جایش display.runtime_footer را دارند). هر کدام را false بگذارید تا خاموش شود.

راستی‌آزمای جهش-فایل

وقتی display.file_mutation_verifier برابر true (پیش‌فرض) است، هرمس هرگاه فراخوانی write_file یا patchی در نوبت شکست بخورد و هرگز با نوشتن موفق به همان مسیر جبران نشود، یک پانوشت مشورتی یک‌خطی به پاسخ نهایی دستیار می‌چسباند. این کلاسِ ادعای مازادِ «بچِ patchهای موازی، نیمی خاموش شکست می‌خورند، مدل موفقیت خلاصه می‌کند» را بدون اجرای دستی git status بعد از هر ویرایش می‌گیرد.

برای سرکوب پانوشت file_mutation_verifier: false (یا HERMES_FILE_MUTATION_VERIFIER=0). راستی‌آزمو فقط وقتی شلیک می‌شود که شکست واقعی در پایان نوبت برجسته باشد — مدلی که patch شکست‌خورده را retry و در همان نوبت موفق شود، برای آن فایل تریگرش نمی‌کند.

به راستی‌آزمو بیش از خلاصهٔ مدل اعتماد کنید. پانوشت یعنی فایل‌های فهرست‌شده روی دیسک تغییر نکرده‌اند، حتی اگر پیام پایانی دستیار بگوید کار تمام است. علل رایج:

  • نوشتن رد شد — مسیر روی فهرست رد اعتبارنامه یا بیرون HERMES_WRITE_SAFE_ROOT است (به «ایمنی نوشتن فایل» در صفحهٔ امنیت)
  • عدم تطبیق patch — ‏old_string با فایل روی دیسک مطابق نبود
  • دروازهٔ نحوی — محتوای کاندید پیش از نوشتن در اعتبارسنجی JSON/YAML/TOML شکست خورد

اگر نوشتن‌های وضعیت هرمس‏ (کارهای کرون، مهارت‌ها، اسکریپت‌های زیر ~/.hermes/) شکست می‌خورند، چک کنید HERMES_WRITE_SAFE_ROOT در محیط‌تان تنظیم شده یا نه. برای تغییرهای کرون، از ابزار cronjob یا hermes cron edit به‌جای patch مستقیم jobs.json استفاده کنید.

زبان UI برای پیام‌های ایستا

تنظیم display.language مجموعهٔ کوچکی از پیام‌های ایستای رو-به-کاربر را ترجمه می‌کند — اعلان تأیید CLI، مشتی از پاسخ‌های فرمان‌های اسلشِ گیت‌وی (اعلان‌های drain-ری‌استارت، «approval expired»، «goal cleared»). پاسخ‌های ایجنت، خطوط لاگ، خروجی ابزار، تریس‌بک‌های خطا یا توضیحات فرمان‌های اسلش را ترجمه نمی‌کند — آن‌ها انگلیسی می‌مانند. اگر می‌خواهید خود ایجنت به زبان دیگری پاسخ دهد، کافیست در پرامپت یا پیام سیستمی‌تان بگویید.

مقادیر پشتیبانی‌شده: en (پیش‌فرض)، ‏zh، ‏zh-hant، ‏ja، ‏de، ‏es، ‏fr، ‏tr، ‏uk، ‏af، ‏ko، ‏it، ‏ga، ‏pt، ‏ru، ‏hu. مقادیر ناشناخته به انگلیسی برمی‌گردند. به‌ازای-نشست با متغیر محیطی HERMES_LANGUAGE هم می‌شود که مقدار پیکربندی را بازنویسی می‌کند.

حالت‌های پیشرفت ابزار

در CLI با /verbose بین این حالت‌ها بچرخید. برای استفاده از /verbose در پلتفرم‌های پیام‌رسانی، tool_progress_command: true را در بخش display بگذارید. فرمان آن‌گاه حالت را می‌چرخاند و در پیکربندی ذخیره می‌کند. پیشرفت ابزار به آداپتور گیت‌وی‌ای نیاز دارد که بتواند به‌روزرسانی‌های پیشرفت را امن نمایش دهد. پلتفرم‌های بدون پشتیبانی ویرایش پیام، شامل سیگنال، حباب‌های پیشرفت ابزار را سرکوب می‌کنند حتی اگر /verbose حالت غیر-off ذخیره کند.

نمای تمرکز (/focus، ‏CLI + TUI)

display.focus_view: true نمای تمرکز را فعال می‌کند — حالت نمایشِ خروجی-کاهش‌یافته برای وقتی که پاسخ را می‌خواهید نه گزارش لحظه‌به‌لحظه را. لایهٔ نازکی روی همان ماشینِ tool_progress است نه مسیر سرکوب دومی:

  • روشن‌کردنش tool_progress را روی off پین و حالت قبلی‌تان را در display.focus_saved_tool_progress کنار می‌گذارد؛
  • /focus off همان حالت را دقیقاً بازمی‌گرداند، پس چیدمان /verbose verbose از یک رفت‌وبرگشت جان سالم می‌برد؛
  • هر نوبتِ تکمیل‌شده با خط بازیابی کم‌رنگ تمام می‌شود — ⋯ 7 tool lines hidden · /focus off to show — شمرده بر اساس حالتِ پیش-از-تمرکز شما، پس هرگز ادعا نمی‌کند خطوطی را پنهان کرده که از قبل خاموش کرده بودید؛
  • نشان پایدار ◉ focus در نوار وضعیت می‌نشیند تا حالت کاهش‌یافته هرگز نامرئی نباشد؛
  • چرخاندن /verbose حین تمرکز، حالت را به /verbose پس می‌دهد و نشان را پاک می‌کند.

نمای تمرکز فقط-نمایش است. هرگز تاریخچهٔ گفتگو، پرامپت سیستمی، طرحوارهٔ ابزار یا هیچ بار درخواستی را ویرایش نمی‌کند — جزئیات پنهان روی صفحه سرکوب می‌شود، هرگز دور انداخته نه، و کش پرامپت کاملاً بی‌تأثیر می‌ماند.

پانوشت فراداده-اجرا (فقط گیت‌وی)

وقتی display.runtime_footer.enabled: true است، هرمس پانوشت کوچک زمینه-اجرایی به آخرین پیام هر نوبت گیت‌وی می‌چسباند. پانوشت فعلی می‌تواند مدل، درصد پنجرهٔ زمینه و پوشهٔ کاری فعلی را نشان دهد. پیش‌فرض خاموش؛ اگر تیم‌تان می‌خواهد هر پاسخ این منشأ را داشته باشد به‌ازای-گیت‌وی فعالش کنید.

yaml
display:
  runtime_footer:
    enabled: true
    fields: ["model", "context_pct", "cwd"]   # ترتیب نمایش؛ هرکدام را حذف کنید تا مخفی شود
فیلدرندرمثال

context_pctاشغال زمینهٔ آخرین-فراخوانی به درصد5%
latencyمدت دیوار-ساعتی نوبت22s، ‏1m05s
cwdپوشهٔ کاری نسبی-به-خانه~

مجموعهٔ فیلد پیش‌فرض ["model", "context_pct", "cwd"] است. latency اختیاری است — به fields اضافه‌اش کنید. فیلدهایی که داده‌شان ناموجود است بی‌صدا رد می‌شوند به‌جای رندر جای خالی. فرمان اسلش /footer این را در زمان اجرا در هر نشستی سوییچ می‌کند. نمونهٔ پانوشت الصاق‌شده به پاسخ تلگرام/دیسکورد/اسلک:

بازنویسی‌های پیشرفت به‌ازای-پلتفرم

پلتفرم‌های متفاوت نیازهای پرگویی متفاوتی دارند. از display.platforms برای حالت‌های به‌ازای-پلتفرم استفاده کنید:

yaml
display:
  tool_progress: all          # پیش‌فرض سراسری
  platforms:
    signal:
      tool_progress: 'off'    # سیگنال فعلاً نمی‌تواند حباب‌های پیشرفت ابزار نمایش دهد
    telegram:
      tool_progress: verbose  # پیشرفت مفصل روی تلگرام
    slack:
      tool_progress: 'off'    # ساکت در ورک‌اسپیس مشترک اسلک

پلتفرم‌های بدون بازنویسی به مقدار سراسری tool_progress برمی‌گردند. کلیدهای پلتفرم معتبر: telegram، ‏discord، ‏slack، ‏signal، ‏whatsapp، ‏matrix، ‏mattermost، ‏email، ‏sms، ‏homeassistant، ‏dingtalk، ‏feishu، ‏wecom، ‏weixin، ‏bluebubbles، ‏qqbot. کلید قدیمی display.tool_progress_overrides هنوز برای سازگاری بارگذاری می‌شود ولی منسوخ است و در اولین بارگذاری به display.platforms مهاجرت می‌کند.

سیگنال به‌عنوان کلید معتبر فهرست شده چون تنظیم به‌ازای-پلتفرم ذخیره می‌شود، ولی آداپتور فعلی سیگنال نمی‌تواند پیام‌های ارسال‌شده را ویرایش کند و حباب پیشرفت رندر نمی‌کند. ‏tool_progress سیگنال را روی off نگه دارید؛ اگر نیاز دارید هر فراخوانی ابزار را زنده ببینید از CLI یا پلتفرم پیام‌رسانیِ دارای-ویرایش استفاده کنید.

interim_assistant_messages فقط-گیت‌وی است. وقتی فعال باشد، هرمس به‌روزرسانی‌های تکمیل‌شدهٔ میان-نوبتِ دستیار را به‌صورت پیام چت جداگانه می‌فرستد. این مستقل از tool_progress است و استریم گیت‌وی نمی‌خواهد.

show_commentary (پیش‌فرض true) کانال commentary مدل‌های Codex Responses را کنترل می‌کند — روایتِ پرداختشدهٔ پیشرفتی که این مدل‌ها در کنار استدلال خصوصی‌شان تولید می‌کنند. وقتی فعال است، هر پیام commentaryِ تکمیل‌شده به‌صورت به‌روزرسانی میان-نوبت مرئی تحویل می‌شود (روی گیت‌وی این به interim_assistant_messages هم نیاز دارد). اگر روایت اضافه آزارتان می‌کند false بگذارید: commentary آن‌گاه به کانال استدلال برمی‌گردد و فقط وقتی show_reasoning فعال است نمایش می‌یابد.

privacy:

وقتی redact_pii برابر true است، گیت‌وی اطلاعات شناسایی‌پذیر شخصی را پیش از ارسال پرامپت سیستمی به LLM روی پلتفرم‌های پشتیبان‌شده پاک می‌کند:

فیلدرفتار

پشتیبانی پلتفرمی: پاک‌سازی روی واتساپ، سیگنال و تلگرام اعمال می‌شود. دیسکورد و اسلک مستثنا‌اند چون سیستم‌های منشنشان‏ (<@user_id>) به شناسهٔ واقعی در زمینهٔ LLM نیاز دارند.

هش‌ها قطعی‌اند — همان کاربر همیشه به همان هش نگاشت می‌شود، پس مدل همچنان می‌تواند در گفتگوهای گروهی بین کاربران تمایز بگذارد. مسیریابی و تحویل از مقادیر اصلی به‌صورت داخلی استفاده می‌کنند.

۳۷ گفتار-به-متن (STT)

yaml
stt:
  enabled: true                # رونویسی خودکار پیام‌های صوتی ورودی (پیش‌فرض: true)
  echo_transcripts: true       # پس‌فرستادن رونوشت خام به چت به‌صورت 🎙️ "..." (پیش‌فرض: true)
  provider: "local"            # "local" | "groq" | "openai" | "mistral" | "xai" | "elevenlabs" | "deepinfra" | ...
  language: "en"               # اشارهٔ زبان سراسری برای همهٔ ارائه‌دهندگان (به‌ازای-ارائه‌دهنده مقدم)؛ "" برای تشخیص خودکار
  cloud_trim_silence: true     # برش مکث‌های طولانی با ffmpeg پیش از آپلود به ارائه‌دهندهٔ ابری (پیش‌فرض: true)
  cloud_trim_threshold_db: -40 # صدای آرام‌تر از این سکوت حساب می‌شود
  cloud_trim_keep_ms: 300      # چقدر از هر مکث پس از برش می‌ماند (ریتم طبیعی حفظ می‌شود)
  # prompt: "Hermes, Teknium, Nous Research, kanban"   # اشارهٔ واژگانی ایستا (پایین را ببینید)
  local:
    model: "base"              # tiny, base, small, medium, large-v3
    language: ""               # بازنویسی به‌ازای-ارائه‌دهندهٔ stt.language
    initial_prompt: ""         # پرامپت اختیاری whisper برای بایاس واژگان/خط
    vad: true                  # فیلتر Silero VAD (پیش‌فرض روشن) — سکوت هرگز به whisper نمی‌رسد؛ false = رفتار خام (موزیک/محیط)
    vad_min_silence_ms: 500    # حداقل سکوت (ms) که تکه‌های گفتار را جدا می‌کند وقتی vad روشن است
    no_speech_prob_threshold: 0.6  # انداختن یک قطعه فقط وقتی no_speech_prob > این...
    logprob_threshold: -1.0        # ...و هم‌زمان avg_logprob < این (هر دو باید بخورند — گفتار واقعی آرام زنده می‌ماند)
    unload_after_idle_seconds: 0   # ۰=هرگز تخلیه نکن (پیش‌فرض)؛ مثل ۳۰۰ = آزادکردن مدل پس از ۵ دقیقه بیکاری
  groq:
    language: ""               # بازنویسی به‌ازای-ارائه‌دهندهٔ stt.language
  openai:
    model: "whisper-1"         # whisper-1 | gpt-4o-mini-transcribe | gpt-4o-transcribe | gpt-transcribe
    language: ""               # بازنویسی به‌ازای-ارائه‌دهندهٔ stt.language
  # model: "whisper-1"         # کلید جایگزین قدیمی هنوز محترم است

حل زبان برای هر ارائه‌دهندهٔ STT یکسان است: stt.<provider>.language ← ‏stt.language ← متغیر محیطی HERMES_LOCAL_STT_LANGUAGE ← تشخیص خودکار ارائه‌دهنده. پیش‌فرض stt.language: "en" است — تشخیص خودکار Whisper اغلب کلیپ‌های کوتاه یا لهجه‌دار را اشتباه تشخیص می‌دهد که به‌صورت یادداشت صوتیِ به زبان اشتباه رونویسی‌شده ظاهر می‌شود. غیرانگلیسی‌زبان‌ها باید stt.language را یک بار روی کد زبانشان بگذارند (مثل "fa")؛ برای استفادهٔ چندزبانه روی "" بگذارید تا تشخیص خودکار برگردد.

وقتی گیت‌وی باید یادداشت‌های صوتی را برای ایجنت رونویسی ولی رونوشت خام را به چت پس نفرستد (مثلاً بات‌های واتساپ رو-به-مشتری)، stt.echo_transcripts: false بگذارید.

رفتار ارائه‌دهندگان:

  • local از faster-whisper روی ماشین شما استفاده می‌کند. جدا نصبش کنید: pip install faster-whisper. سخت‌سازی توهم-سکوت پیش‌فرض روشن است: فیلتر Silero VAD نمی‌گذارد سکوت/نویز هرگز به Whisper برسد، شرطی‌سازی بین‌پنجره‌ای غیرفعال و قطعاتی که خود مدل احتمالاً-غیرگفتار و کم‌اطمینان علامت می‌زند انداخته می‌شوند. stt.local.vad: false برای رونویسی صدای غیرگفتاری (موزیک، محیط) با رفتار خام. مدل بین پیام‌های صوتی در حافظه برای رونویسی کم‌تأخیر می‌ماند؛ stt.local.unload_after_idle_seconds (مثلاً ۳۰۰ برای ۵ دقیقه) را بگذارید تا هنگام بیکاری خودکار آزاد شود. این حافظهٔ GPU را روی میزبان‌های CUDA آزاد می‌کند (بزرگ‌ترین برد وقتی LLM محلی GPU را به اشتراک می‌گذارد). پیام صوتی بعدی مدل را شفاف بارگذاری مجدد می‌کند.
  • groq از اندپوینت سازگار-با-Whisper مربوط به Groq استفاده و GROQ_API_KEY را می‌خواند. stt.groq.language را بدهید تا تشخیص خودکار رد و تأخیر کم شود.
  • openai از API گفتار OpenAI استفاده و VOICE_TOOLS_OPENAI_KEY را می‌خواند.

ارائه‌دهندگان ابری‏ (groq، ‏openai، ‏mistral، ‏xai، ‏elevenlabs، ‏deepinfra) وقتی ffmpeg نصب باشد به‌طور پیش‌فرض برش سکوت پیش-آپلود می‌گیرند: مکث‌های طولانی یادداشت صوتی سمت-کلاینت فشرده می‌شوند پیش از آپلود فایل، با نگه‌داشتن cloud_trim_keep_ms از هر مکث تا ریتم طبیعی زنده بماند. صدای کوتاه‌تر یعنی آپلود سریع‌تر، صورت‌حسابِ کمتر به‌ازای-دقیقه-صوتی و توهم سکوتِ کمتر از مدل راهن. کلیپ‌های کوتاه‌تر از ۱۲ ثانیه کلاً از برش رد می‌شوند. برش در-حد-توان است — اگر ffmpeg غایب باشد، برش شکست بخورد، کلیپ عمدتاً سکوت باشد یا برش کمتر از ~۱۰٪ صرفه کند، فایل اصلی دست‌نخورده آپلود می‌شود. stt.cloud_trim_silence: false برای همیشه اصلی آپلود کردن. ارائه‌دهندگان فرمانی و پلاگینی هرگز صدای برش‌خورده نمی‌گیرند.

یک stt.provider صریحاً-انتخاب‌شده اکیداً محترم است — اگر در دسترس نباشد، رونویسی با راهنماییِ اجرای hermes tools خطا می‌دهد نه سوییچ ارائه‌دهنده. فقط وقتی هیچ ارائه‌دهنده‌ای هرگز انتخاب نشده هرمس به این ترتیب تشخیص خودکار می‌کند: local ← ‏groq ← ‏openai. بازنویسی مدل Groq و OpenAI محیط‌محور است: STT_GROQ_MODEL، ‏STT_OPENAI_MODEL، ‏GROQ_BASE_URL، ‏STT_OPENAI_BASE_URL.

پرامپت رونویسی (اشاره‌های واژگانی)

stt.prompt اشارهٔ ایستای اختیاری‌ای است که به بک‌اندهای STTِ دارای-پرامپت داده می‌شود. برای اسم‌های خاص، نام محصولات و اصطلاحاتی که مدل‌های خانوادهٔ Whisper وگرنه بد می‌شنوند:

yaml
stt:
  provider: "local"
  prompt: "Hermes, Teknium, Nous Research, kanban, Ollama"

ترکیب. مقدار پیکربندی پایه است. پلاگین‌هایی که هوک pre_transcription ثبت می‌کنند رویش جهش می‌دهند، آخرین-نویسنده-برنده به‌ازای-فیلد. اشاره‌های چند پلاگین قطعی ترکیب می‌شوند (کشف به ترتیب مرتب شناسهٔ پلاگین؛ callbackها به ترتیب ثبت خودشان). هوکی که برای prompt رشتهٔ خالی برگرداند پرامپت پیکربندی را برای آن درخواست پاک می‌کند. هوک‌ها می‌توانند language و model را هم بازنویسی کنند؛ ‏file_path فقط‌خواندنی است. بدون هوک ثبت‌شده و بدون stt.prompt، درخواست خروجی با ریلیزهای قبلی یکسان است.

پشتیبانی ارائه‌دهنده: محلی‏ (initial_prompt)، ‏openai، ‏groq، ‏mistral و deepinfra پرامپت را بدون تغییر فوروارد می‌کنند؛ ‏xai، ‏elevenlabs و ارائه‌دهندگان فرمانی پشتیبانی نمی‌کنند (لاگ DEBUG و ادامه بدون پرامپت)؛ ارائه‌دهندگان پلاگینی prompt را فقط وقتی تنظیم شده در kwargs مربوط به transcribe(**extra) می‌گیرند.

طول. مدل‌های خانوادهٔ Whisper فقط روی ~۲۲۴ توکنِ آخر پرامپت شرط می‌شوند. برای بک‌اندهای خانواده-whisper‏ (local، ‏openai، ‏groq، ‏deepinfra) هرمس این سقف را سمت-کلاینت اجرا می‌کند: پرامپت نهاییِ بیش‌ازحد بلند با هشدارِ لاگ‌شده به دُمش بریده می‌شود — درخواست هرگز به‌خاطر طول پرامپت خطا نمی‌گیرد. بک‌اندهای دیگر پرامپت را بی‌تغییر می‌گیرند و اعتبارسنجی خودشان را دارند. به‌هرحال اشاره‌ها را کوتاه و مشخص نگه دارید.

⚠️ پرامپت‌ها همراه صدایتان آپلود می‌شوند

پرامپت نهایی همراه فایل صوتی به ارائه‌دهندهٔ STT تنظیم‌شده فرستاده می‌شود. رازها و زمینهٔ مشتق-از-نشست را از stt.prompt و هر چیزی که هوک pre_transcription برمی‌گرداند دور نگه دارید، به‌ویژه وقتی ارائه‌دهنده API میزبانی‌شده است نه faster-whisper محلی.

۳۸ حالت صوتی (CLI)

yaml
voice:
  record_key: "ctrl+b"         # کلید push-to-talk داخل CLI
  max_recording_seconds: 120    # توقف سخت ضبط‌های طولانی
  auto_tts: false               # فعال‌سازی خودکار پاسخ گفتاری هنگام /voice on
  beep_enabled: true            # پخش بیپ شروع/توقف ضبط در حالت صوتی CLI
  beep_volume: 0.3              # دامنهٔ بیپ (0.0-1.0)؛ روی سیستم‌های بی‌صدا / هدفون بالا ببرید
  silence_threshold: 200        # آستانهٔ RMS برای تشخیص گفتار
  silence_duration: 3.0         # ثانیه‌های سکوت پیش از توقف خودکار

برای فعال‌سازی حالت میکروفن در CLI از /voice on استفاده کنید، ‏record_key برای شروع/توقف ضبط و /voice tts برای سوییچ پاسخ‌های گفتاری. برای راه‌اندازی سرتاسری به صفحهٔ «حالت صوتی» مراجعه کنید.

۳۹ استریم

توکن‌ها هم‌زمان با رسیدن به ترمینال یا پلتفرم‌های پیام‌رسانی استریم شوند، به‌جای انتظار برای پاسخ کامل.

استریم CLI

yaml
display:
  streaming: true         # استریم توکن‌ها به ترمینال در زمان واقعی
  show_reasoning: true    # استریم توکن‌های استدلال/تفکر هم (اختیاری)

وقتی فعال است، پاسخ‌ها توکن‌به‌توکن داخل جعبهٔ استریم ظاهر می‌شوند. فراخوانی‌های ابزار همچنان خاموش گرفته می‌شوند. اگر ارائه‌دهنده استریم را پشتیبانی نکند، خودکار به نمایش عادی برمی‌گردد.

استریم گیت‌وی (تلگرام، دیسکورد، اسلک)

yaml
streaming:
  enabled: true           # فعال‌سازی ویرایش پیشروندهٔ پیام (پیش‌فرض: false)
  transport: auto         # "auto" (پیش‌فرض) | "edit" (ویرایش پیشروندهٔ پیام) | "off"
  edit_interval: 0.8      # ثانیه بین ویرایش‌های پیام (پیش‌فرض: 0.8)
  buffer_threshold: 24    # کاراکترها پیش از اجبار flush ویرایش (پیش‌فرض: 24)
  cursor: " ▉"            # مکان‌نمای نمایش‌داده‌شده حین استریم
  fresh_final_after_seconds: 0    # اختیار گرفتن final تازه (تلگرام) وقتی پیش‌نمایش این‌قدر قدیمی است

وقتی فعال است، بات در اولین توکن پیام می‌فرستد و سپس آن را با رسیدن توکن‌های بیشتر پیشرونده ویرایش می‌کند. پلتفرم‌های بدون پشتیبانی ویرایش پیام (سیگنال، ایمیل، هوم‌اسیسنت) در اولین تلاش خودکار تشخیص داده می‌شوند — استریم برای آن نشست بی‌درنگ غیرفعال می‌شود بدون سیل پیام.

برای به‌روزرسانی‌های طبیعی میان-نوبتِ جداگانه بدون ویرایش پیشروندهٔ توکن، display.interim_assistant_messages: true بگذارید.

هندل سرریز: اگر متن استریم‌شده از سقف طول پیام پلتفرم بگذرد (~۴۰۹۶ کاراکتر)، پیام فعلی نهایی و یکی جدید خودکار شروع می‌شود.

‏Final تازه (تلگرام): ‏editMessageText تلگرام مهر زمانی پیام اصلی را حفظ می‌کند. fresh_final_after_seconds > 0 بگذارید تا پیش‌نمایش‌های قدیمی به‌صورت پیام نهاییِ کاملاً-تازه با حذفِ در-حد-توانِ پیش‌نمایش تحویل شوند. پیش‌فرض 0 است که همیشه درجا نهایی می‌کند و از توالی کوتاهِ پیام-تکراری/حذف روی کلاینت‌هایی که هر دو عملیات را نشان می‌دهند اجتناب می‌کند.

ℹ️ پیش‌فرض‌های استریم به‌ازای-پلتفرم

کلید اصلی streaming.enabled به‌طور پیش‌فرض false است — هیچ‌چیز تا برنگردانیدش استریم نمی‌شود. پس از فعال‌سازی، استریم به‌ازای-پلتفرم تصمیده می‌شود: تلگرام با display.platforms.telegram.streaming: true (استریم می‌کند) و دیسکورد با display.platforms.discord.streaming: false (نمی‌کند) عرضه می‌شود. پس از فعال‌سازی، تلگرام از جعبه استریم می‌کند و دیسکورد روی پاسخ پیام-کامل می‌ماند تا سوییچش را عوض کنید. این سوییچ‌ها را از toggleهای «Channels» داشبورد یا مستقیم در config.yaml تنظیم کنید.

۴۰ ایزوله‌سازی نشست و سقف هم‌زمانی

محدود کنید چند نشست چت می‌توانند در CLI، ‏TUI/داشبورد و گیت‌وی پیام‌رسانی هم‌زمان باز باشند:

yaml
max_concurrent_sessions: null  # null/0 = نامحدود؛ عدد صحیح مثبت = سقف نشست فعال

یک شیفت وقتی گرفته می‌شود که نشست اولین نوبتش را اجرا کند، نه وقتی پنجرهٔ چت باز می‌شود. باز کردن، ازسرگیری یا اتصال‌مجدد به چت تا وقتی پیام نفرستید چیزی هزینه ندارد، پس تب‌های دسکتاپِ بیکار نمی‌توانند گیت‌وی پیام‌رسانیِ سهم این سقف را گرسنه کنند.

وقتی سقف پر شود، هرمس پیام محدودیت مستقیمی برمی‌گرداند که نام می‌برد کدام سطوح شیفتها را نگه داشته‌اند. نشست‌های فعالِ موجود رفتار عادی‌شان را نگه می‌دارند. hermes status مصرف فعلی شیفت‌ها و هر نگهدارنده را نشان می‌دهد. کلید متعارف سطح‌بالا max_concurrent_sessions است؛ ‏gateway.max_concurrent_sessions هم جایگزین است ولی سطح‌بالا وقتی هر دو تنظیم باشند می‌برد. سقف با فایل لیزِ اجرایی محلی اجرا و در-حد-توان است: هرمس اگر رجیستری خواندنی/قفل‌شدنی نباشد باز می‌شکند تا کاربران سرگردان نمانند. برای زمان-اجرای تک-میزبان/تک-پروفایل است، نه HERMES_HOME مشترک بین چند ماشین.

کنترل کنید چت‌های مشترک یک گفتگو به‌ازای-اتاق نگه دارند یا به‌ازای-شرکت‌کننده:

yaml
group_sessions_per_user: true  # true = ایزوله‌سازی به‌ازای-کاربر در گروه‌ها/کانال‌ها، false = یک نشست مشترک به‌ازای-چت
  • true پیش‌فرض و تنظیم توصیه‌شده است. در کانال‌های دیسکورد، گروه‌های تلگرام و کانال‌های اسلک، هر فرستنده وقتی پلتفرم شناسهٔ کاربر می‌دهد نشست خودش را می‌گیرد.
  • false به رفتار اتاق-مشترک قدیمی برمی‌گردد — مفید اگر آگاهانه می‌خواهید هرمس کانالی را مثل یک گفتگوی همکارانه تلقی کند، ولی یعنی کاربران زمینه، هزینهٔ توکن و وضعیت وقفه را به اشتراک می‌گذارند.
  • پیام‌های مستقیم بی‌تأثیرند. رشته‌ها به‌هرحال از کانال والدشان ایزوله می‌مانند؛ با true، هر شرکت‌کننده داخل رشته هم نشست خودش را می‌گیرد.

۴۱ رفتار DM غیرمجاز

yaml
unauthorized_dm_behavior: pair

whatsapp:
  unauthorized_dm_behavior: ignore
  • pair پیش‌فرض پلتفرم‌های DMِ سبک-چت است. هرمس دسترسی را رد، ولی در DM با یک کد جفت‌سازی یک‌باره پاسخ می‌دهد.
  • ignore ‏DMهای غیرمجاز را خاموش رد می‌کند.
  • ایمیل پیش‌فرض ignore است مگر platforms.email.unauthorized_dm_behavior: pair تنظیم شود، چون صندوق‌های ورودی می‌توانند نامهٔ ناخواندهٔ بی‌ربط داشته باشند.
  • بخش‌های پلتفرمی پیش‌فرض سراسری را بازنویسی می‌کنند، پس می‌توانید جفت‌سازی را گسترده فعال نگه دارید و یک پلتفرم را ساکت‌تر کنید.

۴۲ فرمان‌های سریع

فرمان‌های سفارشی تعریف کنید که یا بدون فراخوانی LLM فرمان شلی اجرا کنند، یا یک فرمان اسلش را به دیگری نام‌مستقل کنند. فرمان‌های سریعِ exec صفر-توکن‌اند و از پلتفرم‌های پیام‌رسانی برای بررسی سریع سرور یا اسکریپت‌های کمکی کاربردی‌اند.

yaml
quick_commands:
  status:
    type: exec
    command: systemctl status hermes-agent
  disk:
    type: exec
    command: df -h /
  update:
    type: exec
    command: cd ~/.hermes/hermes-agent && git pull && uv pip install -e .
  gpu:
    type: exec
    command: nvidia-smi --query-gpu=name,utilization.gpu,memory.used,memory.total --format=csv,noheader
  restart:
    type: alias
    target: /gateway restart

استفاده: در CLI یا هر پلتفرم پیام‌رسانی /status، ‏/disk، ‏/update، ‏/gpu یا /restart را تایپ کنید. فرمان‌های exec محلی روی میزبان اجرا و خروجی را مستقیم برمی‌گردانند — بدون فراخوانی LLM، بدون مصرف توکن. فرمان‌های alias به مقصد فرمان اسلشِ پیکربندی‌شده بازنویسی می‌شوند.

  • تایم‌اوت ۳۰ ثانیه‌ای — فرمان‌های طولانی با پیام خطا کشته می‌شوند
  • اولویت — فرمان‌های سریع پیش از فرمان‌های مهارت بررسی می‌شوند، پس می‌توانید نام مهارت‌ها را بازنویسی کنید
  • تکمیل‌خودکار — فرمان‌های سریع هنگام اعزام حل می‌شوند و در جدول‌های تکمیل‌خودکار داخلی نشان داده نمی‌شوند
  • نوع — انواع پشتیبانی‌شده exec و alias‌اند؛ انواع دیگر خطا نشان می‌دهند
  • همه‌جا کار می‌کند — ‏CLI، تلگرام، دیسکورد، اسلک، واتساپ، سیگنال، ایمیل، هوم‌اسیسنت

میان‌برهای فقط-رشته‌ایِ پرامپت فرمان سریع معتبر نیستند. برای گردش‌کارهای پرامپتِ قابل‌استفادهٔ مجدد، مهارت بسازید یا به فرمان اسلش موجود نام‌مستقل بدهید.

۴۳ تأخیر انسانی

شبیه‌سازی ریتم پاسخ انسانی‌گونه در پلتفرم‌های پیام‌رسانی:

yaml
human_delay:
  mode: "off"                  # off | natural | custom
  min_ms: 800                  # حداقل تأخیر (حالت custom)
  max_ms: 2500                 # حداکثر تأخیر (حالت custom)

۴۴ اجرای کد

ابزار execute_code را پیکربندی کنید:

yaml
code_execution:
  mode: project                # project (پیش‌فرض) | strict
  timeout: 300                 # حداکثر زمان اجرا به ثانیه
  max_tool_calls: 50           # حداکثر فراخوانی ابزار داخل اجرای کد

mode پوشهٔ کاری و مفسر پایتون اسکریپت‌ها را کنترل می‌کند:

  • project (پیش‌فرض) — اسکریپت‌ها در پوشهٔ کاری نشست با پایتون محیط virtualenv/conda فعال اجرا می‌شوند. وابستگی‌های پروژه و مسیرهای نسبی‏ (.env، ‏./data.csv) طبیعی حل می‌شوند، منطبق با آنچه terminal() می‌بیند.
  • strict — اسکریپت‌ها در پوشهٔ stage موقت با sys.executable (پایتون خود هرمس) اجرا می‌شوند. حداکثر تکرارپذیری، ولی وابستگی‌های پروژه و مسیرهای نسبی حل نمی‌شوند.

پاک‌سازی محیط (کنده‌شدن *_API_KEY، ‏*_TOKEN، ‏*_SECRET، ‏*_PASSWORD، ‏*_CREDENTIAL، ‏*_PASSWD، ‏*_AUTH) و فهرست سفید ابزار در هر دو حالت یکسان اعمال می‌شوند — تعویض حالت وضعیت امنیتی را تغییر نمی‌دهد.

۴۵ بک‌اندهای جستجوی وب

ابزارهای web_search و web_extract پنج ارائه‌دهندهٔ بک‌اند پشتیبانی می‌کنند. بک‌اند را در config.yaml یا با hermes tools پیکربندی کنید:

yaml
web:
  backend: firecrawl    # firecrawl | searxng | parallel | tavily | exa

  # یا کلیدهای به‌ازای-قابلیت برای ترکیب ارائه‌دهندگان (مثلاً جستجوی رایگان + استخراج پولی):
  search_backend: "searxng"
  extract_backend: "firecrawl"

  # جایگزین سطح-رایگانِ بدون‌کلید (پیش‌فرض: true). بدون بک‌اند پیکربندی‌شده
  # و بدون کلید API، ابزارهای وب روی سطوح رایگان Exa/Parallel/Tavily/Firecrawl/Keenable می‌چرخند.
  keyless_fallback: true

  # نجات یک‌بارهٔ بدون‌کلید (پیش‌فرض: true). وقتی بک‌اندِ انتخاب‌شده/کلیددار
  # یک فراخوانی را شکست دهد، همان یک فراخوانی روی حلقهٔ بدون‌کلید retry می‌شود.
  keyless_rescue: true

  # پین‌کردن Exa/Parallel به یک رده: free = همیشه اندپوینت ناشناس؛
  # paid = همیشه مسیر SDK کلیددار؛ تنظیم‌نشده = خودکار.
  provider_tier:
    parallel: free
    exa: paid

انتخاب بک‌اند: زمان اجرا همیشه از انتخاب ذخیره‌شدهٔ web.backend استفاده می‌کند (با hermes tools تنظیم می‌شود؛ nous از طریق گیت‌وی ابزارِ مدیریت‌شده مسیریابی می‌شود). فقط اگر هیچ بک‌اند وبی هرگز انتخاب نشده باشد از کلیدهای API موجود تشخیص خودکار می‌شود. با هیچ انتخاب و هیچ اعتباری، درخواست‌ها round-robin روی حلقهٔ سطح-رایگانِ بدون‌کلید با failover خودکارِ بعدی-در-صف هنگام محدودیت نرخ می‌چرخند. وقتی انتخابی وجود دارد، افزودن کلید به .env مسیر را عوض نمی‌کند. انتخاب Tavily، ‏Firecrawl یا Keenable در hermes tools هم بدون کلید کار می‌کند.

SearXNG موتور فراجستجویِ رایگان، خودمیزبان و حریم‌خصوصی‌محور است که ۷۰+ موتور جستجو را می‌پرسد. بدون کلید API — فقط SEARXNG_URL را به نمونهٔ خودتان بگذارید (مثل http://localhost:8080). فقط-جستجوست؛ ‏web_extract ارائه‌دهندهٔ استخراج جداگانه‌ای می‌خواهد‏ (web.extract_backend).

‏Firecrawl خودمیزبان: ‏FIRECRAWL_API_URL را به نمونهٔ خودتان بگذارید. وقتی URL سفارشی تنظیم شده، کلید API اختیاری می‌شود. حالت‌های جستجوی Parallel: ‏PARALLEL_SEARCH_MODE — ‏fast، ‏one-shot یا agentic (پیش‌فرض: agentic). ‏Exa: فیلتر category‏ (company، ‏news، ‏people، ‏pdf و غیره) و فیلترهای دامنه/تاریخ را پشتیبانی می‌کند.

browser:

  command_timeout: 30             # تایم‌اوت ثانیه‌ای فرمان‌های مرورگر (اسکرین‌شات، ناوبری و غیره)
  record_sessions: false         # ضبط خودکار نشست‌های مرورگر به‌صورت ویدیو WebM در ~/.hermes/browser_recordings/
  # بازنویسی اختیاری CDP — وقتی تنظیم شود، هرمس مستقیم به مرورگر خانوادهٔ کرومیوم خودتان
  # می‌چسبد (از طریق /browser connect) به‌جای راه‌اندازی مرورگر headless.
  cdp_url: ""
  # ناظر دیالوگ — نحوهٔ هندل دیالوگ‌های JS بومی (alert / confirm / prompt) وقتی بک‌اند
  # CDP متصل است. روی Camofox و حالت پیش‌فرض agent-browser محلی نادیده گرفته می‌شود.
  dialog_policy: must_respond    # must_respond | auto_dismiss | auto_accept
  dialog_timeout_s: 300          # auto-dismiss ایمنی زیر must_respond (ثانیه)
  camofox:
    managed_persistence: false   # وقتی true، نشست‌های Camofox کوکی/ورودها را بین ری‌استارت‌ها حفظ می‌کنند
    user_id: ""                  # userId اختیاریِ خارجاً-مدیریت‌شدهٔ Camofox
    session_key: ""              # کلید نشست اختیاری هنگام ساخت تب توسط هرمس
    adopt_existing_tab: false    # بازاستفاده از تب موجود برای این هویت پیش از ساخت یکی

سیاست‌های دیالوگ:

  • must_respond (پیش‌فرض) — دیالوگ گرفته، در browser_snapshot.pending_dialogs ظاهر و منتظر فراخوانی browser_dialog(action=...) توسط ایجنت می‌ماند. پس از dialog_timeout_s ثانیه بدون پاسخ، دیالوگ خودکار رد می‌شود تا نخ JS صفحه برای همیشه قفل نماند.
  • auto_dismiss — بگیر، فوراً رد کن. ایجنت رکورد دیالوگ را بعد از ماجرا در browser_snapshot.recent_dialogs با closed_by="auto_policy" می‌بیند.
  • auto_accept — بگیر، فوراً بپذیر. برای صفحات با پرامپت‌های beforeunload تهاجمی مفید.

برای گردش‌کار کامل دیالوگ و جزئیات Browserbase، ‏Browser Use و راه‌اندازی CDP محلیِ خانوادهٔ کرومیوم به صفحهٔ مرورگر مراجعه کنید.

۴۷ منطقهٔ زمانی

منطقهٔ زمانی محلی-سرور را با رشتهٔ منطقهٔ زمانی IANA بازنویسی کنید. بر مهرهای زمانی در لاگ‌ها، زمان‌بندی کرون و تزریق زمانِ پرامپت سیستمی اثر دارد.

yaml
timezone: "America/New_York"   # منطقهٔ زمانی IANA (پیش‌فرض: "" = زمان محلی-سرور)

مقادیر پشتیبانی‌شده: هر شناسهٔ منطقهٔ زمانی IANA‏ (مثل America/New_York، ‏Europe/London، ‏Asia/Tehran، ‏UTC). برای زمان محلی-سرور خالی بگذارید یا حذفش کنید.

۴۸ دیسکورد

yaml
discord:
  require_mention: true          # نیاز به @mention برای پاسخ در کانال‌های سرور
  free_response_channels: ""     # شناسه‌های کانال جدا با ویرگول که بات بدون @mention پاسخ می‌دهد

  • auto_thread — وقتی true (پیش‌فرض)، منشن‌ها در کانال‌ها خودکار رشته‌ای برای گفتگو می‌سازند تا کانال‌ها تمیز بمانند (مشابه رشته‌سازی اسلک).

۴۹ امنیت

اسکن امنیتی پیش-از-اجرا و پاک‌سازی راز:

yaml
security:
  redact_secrets: true           # پاک‌سازی الگوهای کلید API در خروجی ابزار و لاگ‌ها (پیش‌فرض روشن)
  tirith_enabled: true           # فعال‌سازی اسکن امنیتی Tirith برای فرمان‌های ترمینالی
  tirith_path: "tirith"          # مسیر باینری tirith (پیش‌فرض: "tirith" در $PATH)
  tirith_timeout: 5              # ثانیه‌های انتظار برای اسکن tirith پیش از تایم‌اوت
  tirith_fail_open: true         # اجازهٔ اجرای فرمان وقتی tirith در دسترس نیست
  website_blocklist:             # بخش «فهرست رد وب‌سایت» پایین را ببینید
    enabled: false
    domains: []
    shared_files: []
  • redact_secrets — وقتی true، الگوهای شبیه کلید API، توکن و رمز را در خروجی ابزار پیش از ورودش به زمینهٔ گفتگو و لاگ‌ها خودکار تشخیص و پاک می‌کند. پیش‌فرض روشن. فقط وقتی به رشته‌های شبیه-اعتبارِ خام برای دیباگ نیاز دارید صریحاً false کنید.
  • tirith_enabled — وقتی true، فرمان‌های ترمینالی پیش از اجرا توسط Tirith اسکن می‌شوند تا عملیاتِ بالقوه خطرناک تشخیص شود.
  • tirith_path — مسیر باینری tirith. اگر در مکان غیراستاندارد نصب است این را بگذارید.
  • tirith_timeout — حداکثر ثانیه‌های انتظار برای اسکن tirith. فرمان‌ها اگر اسکن تایم‌اوت بخورد ادامه می‌یابند.
  • tirith_fail_open — وقتی true (پیش‌فرض)، فرمان‌ها اگر tirith ناموجود یا شکست‌خورده باشد مجاز به اجرا هستند. false بگذارید تا وقتی tirith نمی‌تواند تأییدشان کند فرمان‌ها بلاک شوند.

۵۰ فهرست رد وب‌سایت

مسدودکردن دامنه‌های مشخص از دسترسی ابزارهای وب و مرورگر ایجنت:

yaml
security:
  website_blocklist:
    enabled: false               # فعال‌سازی مسدودسازی URL (پیش‌فرض: false)
    domains:                     # فهرست الگوهای دامنهٔ مسدود
      - "*.internal.company.com"
      - "admin.example.com"
      - "*.local"
    shared_files:                # بارگذاری قواعد اضافی از فایل‌های بیرونی
      - "/etc/hermes/blocked-sites.txt"

وقتی فعال است، هر URL منطبق با الگوی دامنهٔ مسدود پیش از اجرای ابزار وب یا مرورگر رد می‌شود. این به web_search، ‏web_extract، ‏browser_navigate و هر ابزار URL-خوان اعمال می‌شود.

قواعد دامنه پشتیبانی می‌کنند: دامنهٔ دقیق؛ زیردامنهٔ وایلدکارد‏ (*.internal.company.com که همهٔ زیردامنه‌ها را می‌بندد)؛ وایلدکارد TLD‏ (*.local). فایل‌های مشترک یک قاعدهٔ دامنه به‌ازای-خط دارند (خطوط خالی و کامنت‌های # نادیده). فایل‌های مفقود یا ناخوانا هشداری لاگ می‌کنند ولی سایر ابزارهای وب را غیرفعال نمی‌کنند. سیاست ۳۰ ثانیه کش می‌شود، پس تغییرهای پیکربندی بدون ری‌استارت سریع اثر می‌کنند.

۵۱ تأییدهای هوشمند

yaml
approvals:
  mode: smart   # smart | manual | off
حالترفتار
smart (پیش‌فرض)از یک LLM کمکی برای ارزیابی اینکه آیا فرمانِ علامت‌خورده واقعاً خطرناک است استفاده می‌کند. فرمان‌های کم‌ریسک فقط برای همان فرمان خودکار تأیید می‌شوند. فرمان‌های واقعاً پرخطر رد؛ تصمیم‌های نامطمئن به کاربر ارجاع.
manualپیش از اجرای هر فرمان علامت‌خورده از کاربر پرسیدن. در CLI دیالوگ تأیید تعاملی؛ در پیام‌رسانی درخواست تأییدِ در-انتظار صف می‌شود.
offرد از همهٔ بررسی‌های تأیید. معادل HERMES_YOLO_MODE=true. با احتیاط استفاده شود.

حالت هوشمند به‌ویژه برای کاهش خستگی تأیید مفید است — به ایجنت اجازه می‌دهد روی عملیات‌های امن خودمختارتر کار کند در حالی که فرمان‌های واقعاً مخرب را همچنان می‌گیرد.

⚠️ هشدار

approvals.mode: off همهٔ بررسی‌های امنیتی فرمان‌های ترمینالی را خاموش می‌کند. فقط در محیط‌های مطمئن و سندباکس‌شده استفاده کنید.

قطع‌کنندهٔ مدارِ رد

approvals.denial_breaker_threshold (پیش‌فرض 3) در برابر retryِ واریانت‌های فرمانی که بازبین تأیید-هوشمند مدام رد می‌کند محافظ می‌کند — هر retry یک فراخوانی LLM نگهبان دیگر می‌سوزاند. پس از آن تعداد رد متوالی در یک نشست، پیام رد به دستورِ هارد-استاپ تشدید می‌شود که به ایجنت می‌گوید بایستد، عملیات بلاک‌شده را گزارش دهد و از شما بخواهد دستی یا با /approve اجرایش کند. هر تأیید شمارش را ریست می‌کند؛ ‏0 برای غیرفعال‌کردن:

yaml
approvals:
  denial_breaker_threshold: 3   # ۰ قطع‌کننده را خاموش می‌کند

قواعد رد

approvals.deny فهرستی از الگوهای glob است که فرمان‌های ترمینالیِ مطابق را بی‌قیدوشرط مسدود می‌کند — حتی زیر --yolo، ‏/yolo یا mode: off. همتای قابل-ویرایشِ فهرست رد سفت‌وسخت داخلی است:

yaml
approvals:
  deny:
    - "git push --force*"
    - "*curl*|*sh*"

الگوها fnmatch بدون حساسیت به بزرگی/کوچکی‌اند و در YAML باید گیومه بخورند (* ابتداییِ خالی خطای parse است). برای جزئیات به «امنیت ← قواعد رد تعریف‌شده توسط کاربر» مراجعه کنید.

سیاست تأیید-هوشمند سفارشی

approvals.smart_policy اجازه می‌دهد قواعد خودتان را به دستورالعمل‌های بازبین تأیید-هوشمند بچسبانید. وقتی تنظیم شود، متن به پرامپت سیستمی LLM نگهبان اضافه می‌شود (کانال مورد-اعتماد — هرگز در کنار متنِ نامطمئنِ فرمان)، تا بتوانید قضاوتش را برای محیطتان بدون ویرایش کد سخت‌گیرانه‌تر یا بخشنده‌تر کنید:

yaml
approvals:
  smart_policy: |
    Always ESCALATE commands that modify anything under /etc.
    APPROVE docker compose restarts in ~/deploys — they are routine here.

۵۳ واگذاری (Delegation)

رفتار ساب‌ایجنت را برای ابزار delegate پیکربندی کنید:

yaml
delegation:
  # model: "google/gemini-3-flash-preview"  # بازنویسی مدل (خالی = ارث از والد)
  # provider: "openrouter"                  # بازنویسی ارائه‌دهنده (خالی = ارث از والد)
  # base_url: "http://localhost:1234/v1"    # اندپوینت مستقیم سازگار با OpenAI (بر ارائه‌دهنده مقدم)
  # api_key: "local-key"                    # کلید API برای base_url (به OPENAI_API_KEY برمی‌گردد)
  # api_mode: ""                            # پروتکل سیمی: "chat_completions"، "codex_responses" یا "anthropic_messages".
                                           # خالی = تشخیص خودکار از URL (مثل پسوند /anthropic).
  max_concurrent_children: 3                # فرزندان موازی به‌ازای-بچ (کف ۱، بدون سقف). env: DELEGATION_MAX_CONCURRENT_CHILDREN.
  worktree_isolation: false                 # دادن ورک‌تری گیتِ خودش به هر فرزند منشعب از HEAD (فقط بک‌اند محلی + مخازن گیت).
  max_spawn_depth: 1                        # سقف عمق درخت واگذاری (۱-۳). ۱ = تخت (پیش‌فرض). ۲ = فرزندان ارکستراتور
                                           # می‌توانند نوه‌های برگ بسازند. ۳ = سه سطح.
  orchestrator_enabled: true                # کلید قطع سراسری. وقتی false، role="orchestrator" نادیده و هر فرزندی
                                           # صرف‌نظر از max_spawn_depth به برگ اجبار می‌شود.

بازنویسی provider:model ساب‌ایجنت: به‌طور پیش‌فرض ساب‌ایجنت‌ها ارائه‌دهنده و مدل ایجنت والد را به ارث می‌برند. delegation.provider و delegation.model را تنظیم کنید تا ساب‌ایجنت‌ها به جفت provider:model دیگری مسیریابی شوند — مثلاً مدل ارزان/سریع برای زیرکارهای محدوددامنه در حالی که ایجنت اصلی‌تان روی مدل استدلالی گران اجرا می‌شود.

بازنویسی اندپوینت مستقیم: اگر مسیر اندپوینت-سفارشیِ بدیهی را می‌خواهید، delegation.base_url، ‏delegation.api_key و delegation.model را بگذارید. ساب‌ایجنت‌ها را مستقیم به آن اندپوینت سازگار با OpenAI می‌فرستد و بر delegation.provider مقدم است. اگر delegation.api_key حذف شود، هرمس فقط به OPENAI_API_KEY برمی‌گردد.

پروتکل سیمی (api_mode): هرمس پروتکل سیمی را از delegation.base_url تشخیص می‌دهد (مثلاً مسیرهای منتهی به /anthropic ← anthropic_messages). برای اندپوینت‌هایی که ابتکار نمی‌تواند طبقه‌بندی کند — مثلاً Azure AI Foundry، ‏MiniMax، ‏Zhipu GLM یا پروکسی‌های LiteLLM جلوی بک‌اند آنتروپیک‌شکل — ‏delegation.api_mode را صریحاً روی یکی از سه مقدار بگذارید. خالی (پیش‌فرض) تشخیص خودکار را نگه می‌دارد.

ارائه‌دهندهٔ واگذاری از همان حل اعتبارِ شروع CLI/گیت‌وی استفاده می‌کند. همهٔ ارائه‌دهندگان پیکربندی‌شده پشتیبانی می‌شوند: openrouter، ‏nous، ‏copilot، ‏zai، ‏kimi-coding، ‏minimax، ‏minimax-cn. وقتی ارائه‌دهنده‌ای تنظیم شود، سیستم خودکار base URL، کلید API و حالت API درست را حل می‌کند — بدون سیم‌کشی دستی اعتبار.

اولویت: ‏delegation.base_url در پیکربندی ← ‏delegation.provider در پیکربندی ← ارائه‌دهندهٔ والد (ارثی). ‏delegation.model در پیکربندی ← مدل والد (ارثی). تنظیمِ فقط model بدون provider فقط نام مدل را عوض می‌کند و اعتبار والد را نگه می‌دارد (مفید برای تعویض مدل در همان ارائه‌دهنده مثل OpenRouter).

عرض و عمق: ‏max_concurrent_children سقف می‌زند چند ساب‌ایجنت به‌ازای-بچ موازی اجرا شوند (پیش‌فرض 3، کف ۱، بدون سقف). وقتی مدل آرایهٔ tasksای بلندتر از سقپ می‌فرستد، delegate_task به‌جای برش خاموش، خطای ابزاری برمی‌گرداند که سقف را توضیح می‌دهد. max_spawn_depth عمق درخت واگذاری را کنترل می‌کند (سقف‌شده به ۱-۳). در پیش‌فرض 1، واگذاری تخت است: فرزندان نمی‌توانند نوه بسازند و role="orchestrator" خاموش به leaf تنزل می‌کند. برای اینکه فرزندان ارکستراتور بتوانند نوهٔ برگ بسازند به 2؛ برای درخت‌های سه‌سطحی 3. ایجنت با role="orchestrator" به‌ازای-فراخوانی اختیار می‌کند؛ ‏orchestrator_enabled: false هر فرزندی را صرف‌نظر از همه به برگ برمی‌گرداند. هزینه ضربی مقیاس می‌شود — با max_spawn_depth: 3 و max_concurrent_children: 3، درخت می‌تواند به ۳×۳×۳ = ۲۷ ایجنت برگِ هم‌زمان برسد. برای الگوهای استفاده به «واگذاری ساب‌ایجنت ← سقف عمق و ارکستراسیون تودرتو» مراجعه کنید.

۵۴ شفاف‌سازی (Clarify)

پیکربندی چقدر گیت‌وی برای پاسخ به سؤال شفاف‌ساز منتظر می‌ماند. کلید متعارف agent.clarify_timeout است (پیش‌فرض 3600 ثانیه)؛ clarify.timeout سطح‌بالای قدیمی هم اگر صریحاً تنظیم شده باشد محترم است:

yaml
agent:
  clarify_timeout: 3600        # ثانیه‌های انتظار برای پاسخ شفاف‌سازی کاربر (۰ یا کمتر = نامحدود)

۵۷ شبکه

راه‌حل‌های اتصال برای HTTP خروجی:

yaml
network:
  force_ipv4: false   # اجبار IPv4 برای اتصال‌های خروجی (پیش‌فرض: false)

force_ipv4 — روی سرورهایی با IPv6 خراب یا در دسترس‌ناپذیر، پایتون اول رکوردهای AAAA را حل و می‌تواند برای کل تایم‌اوت TCP قبل از بازگشت به IPv4 آویزان بماند. true بگذارید تا کلاً از IPv6 رد شده و مستقیم روی IPv4 وصل شود.

۵۸ آنبوردینگ

نکته‌های لمس-اول و پیشنهاد ساخت-ساختارمندِ پروفایل:

yaml
onboarding:
  profile_build: "ask"   # "ask" (پیش‌فرض) | "off"
  seen: {}               # قفل داخلی — خالی بگذارید
  • profile_build — مسیر ساخت-پروفایلِ پیشنهادشده روی اولین پیام گیت‌وی را کنترل می‌کند. "ask" (پیش‌فرض) پیشنهاد ساخت پروفایل کاربر را می‌دهد؛ پیشنهاد اختیاری و گیت‌شده-با-رضایت است — ایجنت پیش از هر جستجو می‌پرسد و هرگز حساب‌های متصل را خاموش نمی‌خواند. "off" فقط یک معرفی ساده نشان می‌دهد. پیشنهاد حداکثر یک بار شلیک می‌شود.
  • seen — وضعیت داخلی. هر نکتهٔ نمایش‌داده‌شده اینجا قفل می‌شود تا هرگز دوباره شلیک نشود. دستی ویرایشش نکنید — اگر می‌خواهید همهٔ نکته‌ها را دوباره ببینید کل بخش onboarding را پاک کنید.

۵۹ داشبورد

پیکربندی «داشبورد وب» — تم بصری، ‏URL عمومی و ارائه‌دهندگان احراز هویت. ارائه‌دهندگان احراز با جزئیات در صفحهٔ داشبورد وب مستند شده‌اند؛ این شکل config.yaml است:

yaml
dashboard:
  theme: "default"            # "default" | "midnight" | "ember" | "mono" | "cyberpunk" | "rose"
  show_token_analytics: false # بازفعال‌سازی سطوح تحلیل توکن/هزینه (فقط تخمین-محلی)
  public_url: ""              # اختیار کامل عمومی برای redirect_uri مربوط به OAuth (env: HERMES_DASHBOARD_PUBLIC_URL)
  oauth:                      # دروازهٔ OAuth پورتال (با --host و نه --insecure درگیر می‌شود)
    client_id: ""             # agent:{instance_id} — پورتال این را تأمین می‌کند
    portal_url: ""            # خالی ← پیش‌فرض پلاگین (پورتال پروداکشن)
  basic_auth:                 # دروازهٔ نام‌کاربری/رمز خودمیزبان (پلاگین dashboard_auth/basic)
    username: ""              # خالی ← پلاگین no-op
    password_hash: ""         # scrypt$... (ترجیح‌دارد — بدون متن-ساده در سکونت)
    password: ""              # جایگزین متن-ساده (هنگام بارگذاری در حافظه هش می‌شود)
    secret: ""                # کلید امضای توکن؛ خالی ← تصادفی به‌ازای-پروسه
    session_ttl_seconds: 0    # ۰ ← پیش‌فرض پلاگین (۱۲ ساعت)
  drain_auth:                 # دروازهٔ اعتبار-سرویسِ کنترل-drain (پلاگین dashboard_auth/drain)
    scope: "drain"            # برچسب قابلیت روی اصلِ راستی‌آزمایی‌شده
    min_secret_chars: 43      # میزان آنتروپی (کاراکترهای url-safe-b64؛ ‏۴۳ ≈ ۲۵۶ بیت)
  • theme — تم بصری داشبورد.
  • show_token_analytics — پیش‌فرض خاموش. صفحهٔ Analytics و ارقام توکن/هزینه یک تخمین کران-پایین محلی هستند (فراخوانی‌های کمکی، retryها، ‏fallbackها و نوشتن‌های کش را مستثنا می‌کنند)، پس می‌توانند خیلی پایین‌تر از صورت‌حساب ارائه‌دهنده خوانده شوند. فقط اگر می‌فهمید که صورت‌حساب نیستند true کنید.
  • public_url — وقتی تنظیم شود، اختیار کامل‏ (طرح + میزبان + پیشوند مسیر اختیاری)یی است که redirect_uri مربوط به OAuth از آن ساخته می‌شود. برای استقرارهای پشت پروکسی معکوسی که هدرهای X-Forwarded-* را مطمئن فوروارد نمی‌کنند بگذاریدش.
  • oauth / ‏basic_auth / ‏drain_auth — پیکربندی ارائه‌دهندهٔ احراز که پلاگین‌های dashboard-authِ همراه می‌خوانند. خود راز drain اینجا تنظیم نمی‌شود؛ از طریق متغیر محیطی HERMES_DASHBOARD_DRAIN_SECRET تأمین می‌گردد. برای راه‌اندازی کامل احراز به «داشبورد وب» مراجعه کنید.
