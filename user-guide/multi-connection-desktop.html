خانه/کار با Hermes/اتصال دسکتاپ به چند نمونه

اتصال Desktop به نمونه‌های متعدد هرمس

هر بک‌اند هرمس که دارید — runtime ی محلی، گیت‌وی‌های راه‌دور روی LAN یا VPS، ‏میزبان‌های SSH و نمونه‌های Hermes Cloud — را در یک اپ دسکتاپ ثبت کنید و با ایجنت‌های همهٔ آنها کنار هم کار کنید. اتصالات پایدارند: هر گیت‌وی ثبت‌شده در صورت نیاز بک‌اندها و WebSocket های خودش را dial می‌کند و ایجنت‌های پس‌زمینه حین نگاه شما به گیت‌وی دیگری به استریم ادامه می‌دهند.

این مکمل سمت-دسکتاپِ صفحهٔ «اجرای چند گیت‌وی هم‌زمان» است: آن صفحه دربارهٔ میزبانی چند گیت‌وی روی یک ماشین است؛ این یکی دربارهٔ یک اپ دسکتاپ است که با چند ماشین حرف می‌زند.

۱ کجا پیدا می‌شود

همه‌چیز در صفحهٔ واحد Settings ← Gateways است ‏(بیلدهای قدیمی‌تر صفحات جداگانهٔ Gateway و Connections داشتند؛ deep link های قدیمی Connections به آنجا redirect می‌شوند). سه در به آنجا می‌رسد:

  • Settings ← Gateways — خود صفحه ‏(Cmd/Ctrl+، بعد Gateways در nav ی تنظیمات). registry ی اتصالات بخشی از آن صفحه است زیر کنترل‌های connection-mode ی سطح-ماشین.
  • ریل پروفایل sidebar — دکمهٔ plug در انتهای راست ریل ‏(tooltip: «Connect another Hermes gateway…») مستقیم به صفحهٔ Gateways می‌رود. همیشه مرئی است حتی قبل از ساخت دومین پروفایل یا دومین اتصال.
  • پالت فرمان — ‏Cmd/Ctrl+K و تایپ Gateways ‏(connections، add gateway، remote، ssh، instances را هم می‌یابد).

۲ registry ی گیت‌وی

بخش Registered gateways ی Settings ← Gateways فهرستی نام‌دار از گیت‌وی‌های هرمس را مدیریت می‌کند. متن معرفی‌اش صریح است: «این دستگاه و هر گیت‌وی هرمس ی که می‌تواند برسد را از طریق اتصالات remote، ‏SSH یا Cloud مدیریت کنید.» هر ورودی یک اتصال است:

نوعچه چیزی استAuth
Local«runtime ی هرمس که توسط این اپ مدیریت می‌شود.»خودکار
Remote gateway«گیت‌وی هرمس ی که از طریق HTTP(S) قابل‌رسید است — LAN، ‏Tailscale یا اینترنت.»session token یا OAuth
SSH«نصب هرمس ی که از طریق SSH رسیده می‌شود.» اپ tunnel را باز و داشبورد را برایتان شروع می‌کندکلید SSH + توکن adopt شده
Hermes Cloud«نمونهٔ میزبانی‌شده کشف‌شده از طریق حسابتان در Hermes Cloud.»ورود portal

قواعدی که دانستنش می‌ارزد:

  • هر اتصال به نام دستگاه یکتا نیاز دارد ‏(«Homelab»، «Work laptop»). نام هر جا که نمونه ظاهر شود دیده می‌شود — badge های roster، ‏handle ها، نتایج به‌روزرسانی. یکتایی case-insensitive است پس Homelab و homelab نمی‌توانند همزیست باشند.
  • ورودی local توسط اپ مدیریت می‌شود ‏(حبهٔ App-managed دارد) و قابل‌حذف نیست. حذف هر اتصال دیگر بک‌اندها و tunnel های زنده اش را جمع می‌کند؛ خود نمونه دست نمی‌خورد.
  • یک اتصال همیشه Primary است ‏(حبه روی ردیفش): fallback ی registry برای فراخوانی‌های چند-گیت‌وی‌ای که گیت‌وی نام نمی‌برند. Make primary فضای کاری فعلی Sessions را عوض نمی‌کند؛ حذف primary به ورودی local برمی‌گردد.
  • ‏At startup, return to Sessions on the last-used gateway تعیین می‌کند بعد از ری‌استارت کامل اپ، Sessions روی کدام گیت‌وی باز شود. پیش‌فرض خاموش است پس Sessions روی Primary باز می‌شود. روشنش کنید تا آخرین گیت‌وی موفق بازیابی شود. سوئیچ ناموفق هرگز به یاد سپرده نمی‌شود و گیت‌وی ذخیره‌شدهٔ حذف‌شده یا غیرقابل‌رسید به Primary برمی‌گردد.
  • Test هر دو پای HTTP و WebSocket ی اتصال را probe می‌کند، پس قبولی ‏(toast ی Reachable) یعنی چت واقعاً کار خواهد کرد — نه فقط اینکه host ping شد.
  • تکراری‌ها موقع ذخیره رد می‌شوند: فقط همیشه یک ورودی local هست؛ ورودی‌های remote و cloud روی URL ی نرمال‌شده dedup می‌شوند ‏(trim، حذف اسلش انتهایی، حروف کوچک — و بین هر دو نوع، تا ورود cloud و remote به یک URL اشاره نکنند)؛ ورودی‌های SSH روی user@host:port ی نرمال‌شده به‌علاوه پروفایل راه‌دور dedup می‌شوند.
  • ورودی‌های Cloud معمولاً از جریان ورود/کشف Hermes Cloud در بالای صفحهٔ Gateways می‌آیند — مقدار Hermes Cloud در ادیتور افزودن-اتصال شما را به همانجا می‌فرستد.

گیت‌وی‌ها را از sidebar ی Sessions عوض کنید. پروفایل‌ها، گفتگوها، پیام‌رسانی و cron به همان گیت‌وی scope می‌مانند؛ backend ی window ی مدیریت‌شده-توسط-اپ همچنان توسط کنترل‌های connection-mode ی بالا انتخاب می‌شود. Primary فقط fallback ی registry است و فضای کاری فعلی را عوض نمی‌کند.

۳ افزودن اتصال، قدم‌به‌قدم

  1. ‏Settings ← Gateways را باز و به registry ی اتصالات اسکرول کنید ‏(یا plug را در ریل پروفایل کلیک کنید).
  2. روی Add connection کلیک کنید.
  3. نوع را بردارید: Local، ‏Hermes Cloud، ‏Remote gateway یا SSH. ‏(Local وقتی ورودی محلیِ مدیریت‌شده-توسط-اپ موجود باشد غیرفعال است — تقریباً همیشه؛ Hermes Cloud شما را به جریان ورود/کشف ابری می‌فرستد.)
  4. فیلدها را پر کنید:
    • Name — الزامی، یکتا؛ «نام دستگاه» که هر جا این نمونه ظاهر شود نمایش داده می‌شود ‏(placeholder: Homelab). حداکثر ۶۴ نویسه.
    • فقط Remote gateway:
      • Gateway URL — URL پایه یک backend ی در حال اجرای hermes serve مثلاً http://homelab.lan:9119. پیشوندهای مسیر reverse-proxy هم کار می‌کنند.
      • Authentication — Session token یا OAuth:
        • Session token — توکن نشست داشبورد گیت‌وی راه‌دور را paste کنید. هنگام ویرایش «برای نگه داشتن توکن ذخیره‌شده خالی بگذارید.»
        • OAuth — از طریق جریان مرورگری Nous Portal وارد شوید؛ توکنی برای paste نیست.
    • فقط SSH:
      • SSH host — یک فیلد ترکیبی به شکل user@host:22 ‏(کاربر و پورت اختیاری). کلید SSH شما استفاده می‌شود؛ اپ روی tunnel توکن داشبورد را adopt می‌کند.
  5. Save connection ‏(یا Cancel) را کلیک کنید.
  6. روی ردیف جدید Test را بزنید و منتظر Reachable بمانید.

بعداً هر ورودی غیر-local را با دکمهٔ مداد ویرایش یا با دکمهٔ سطل حذف کنید — حذف تأیید می‌خواهد و یادآوری می‌کند «خود نمونه دست نمی‌خورد — هر وقت خواستید دوباره اضافه‌اش کنید.»

ℹ️ بک‌اند راه‌دور یک پروسهٔ در حال اجرای hermes serve است

هیچ‌کدام اینها کار نمی‌کند مگر اینکه backend واقعاً روی ماشین دیگر بالا و قابل‌رسید باشد. اپ دسکتاپ به آن attach می‌شود؛ آن را برایتان شروع نمی‌کند ‏(به‌جز اتصالات SSH که اپ داشبورد را on-demand روی tunnel شروع می‌کند). راه‌اندازی سمت-backend — ارائه‌دهنده‌های auth، ‏bind به آدرس غیر-loopback و راهنمای Tailscale — را در بخش اتصال-به-بک‌اند-راه‌دور راهنمای دسکتاپ ببینید.

مهاجرت از تنظیمات تک-اتصاله

اولین اجرای یک build ی دارای-registry تنظیمات فعلی‌تان را خودکار import می‌کند: حالت اتصال سراسری و override های legacy ی per-profile از Settings ← Gateway به ورودی‌های نام‌دار registry تبدیل می‌شوند ‏(dedup روی URL/host). فایل تنظیمات قدیمی دست‌نخورده می‌ماند پس بیلدهای قدیمی‌تر روی همان ماشین همچنان کار می‌کنند. اگر نام مهاجرت‌شده تداخل داشت پسوند گرفت ‏(Homelab 2).

۴ ایجنت‌ها بین گیت‌وی‌ها

هر پروفایل روی هر اتصال ثبت‌شده یک ایجنت است. roster ی اجتماع چیزی است که سطح‌های چند-گیت‌وی ‏(و roster ی Bot Mode داخلی) رندر می‌کنند:

  • وقتی نام پروفایل یکسان روی چند گیت‌وی وجود داشته باشد handle ها به‌صورت @name-device تفکیک می‌شوند — research روی Homelab شما @research-homelab رندر می‌شود در حالی که پروفایلی که سراسر گیت‌وی‌ها یکتاست نام لخت خودش را نگه می‌دارد.
  • شماره‌گذاری eager ولی socket ها lazy اند: اپ ایجنت‌ها را از طریق REST فهرست بدون dial کردن WebSocket هر گیت‌وی. گیت‌وی غیرقابل‌رسید per-row خطا گزارش می‌کند نه شکستن roster؛ اتصالات SSH تا اولین بار که رویشان ایجنتی باز کنید connect-on-demand می‌مانند ‏(بدون tunnel های غافلگیرکننده).
  • باز کردن ایجنت به گیت‌وی خودش dial می‌کند — چت‌ها، نشست‌ها و حافظه روی ماشینی زندگی می‌کنند که مالک پروفایل است، دقیقاً انگار مستقیم با آن نمونه کار می‌کردید.

هر جفت (connection, profile) بک‌اند و socket خودش را دارد، pooled با همان idle-reaping ی بک‌اندهای per-profil ی محلی — ایجنت‌های پس‌زمینه حین نگاه شما به گیت‌وی دیگر به استریم ادامه می‌دهند.

سوئیچ و scope

پای sidebar یک سلسله‌مراتب را دنبال می‌کند: gateway ← profile ← sessions. گیت‌وی‌ها ماشین‌ها یا backend های میزبانی‌شده‌اند؛ پروفایل‌ها ایجنت‌های هرمس ایزوله‌ای هستند که روی یک گیت‌وی زندگی می‌کنند.

  • با یک گیت‌وی ثبت‌شده هیچ کنترل gateway اضافه نمی‌شود. Desktop فقط-محلی همان ریل پروفایل و جریان کیبورد قبلی را نگه می‌دارد.
  • با چند گیت‌وی، sidebar یک انتخابگر گیت‌وی نام‌دار نشان می‌دهد. آیکن device/cloud/network/terminal نوع اتصال را شناسایی می‌کند؛ آواتارهای پروفایل بعد از divider کنترل جدایی می‌مانند. همین انتخابگر از دو گیت‌وی تا fleet بزرگتر مقیاس می‌یابد بدون اینکه backend ها به glyph شبیه-پروفایل تبدیل یا اقدامات پروفایل از ریل بیرون رانده شوند.
  • انتخاب گیت‌وی آخرین پروفایل استفاده‌شده در آن را بازیابی می‌کند. ریل پروفایل سپس فقط پروفایل‌های همان گیت‌وی را نشان می‌دهد؛ حبهٔ home به پروفایل پیش‌فرض برمی‌گردد و حبهٔ layers مقدار «همهٔ پروفایل‌های این گیت‌وی» را نشان می‌دهد. Cmd/Ctrl+1–9 همچنان پروفایل‌ها را داخل گیت‌وی فعال عوض می‌کنند.
  • گیت‌وی انتخاب‌شده فقط وقتی از quit و relaunch جان می‌ماند که Settings ← Gateways ← At startup, return to Sessions on the last-used gateway روشن باشد. ترجیح و id ی گیت‌وی در registry ی user-data ی اپ زندگی می‌کنند، پس جایگزینی یا به‌روزرسانی bundle ی اپ آنها را reset نمی‌کند.
  • با بیش از سیزده پروفایل روی گیت‌وی فعال، نوار آواتارشان به یک انتخابگر پروفایل نام‌دار فشرده می‌شود. مجموعه‌های بزرگ گیت‌وی و پروفایل پس می‌توانند بدون تغییر مدل gateway ← profile ← sessions همزیست باشند.
  • This device حتی وقتی اتصال راه‌دوری Primary است یک گیت‌وی درجه‌یک می‌ماند. می‌تواند حین قطعی راه‌دور نشست‌های محلی را در دسترس نگه دارد ولی اپ آن را «offline mode» نمی‌نامد: مدل یا ابزارهای انتخابی ممکن است همچنان اینترنت بخواهند.
  • فهرست نشست‌ها، کانال‌های پیام‌رسانی، cron job ها، تنظیمات، فایل‌ها و حافظه همه به جفت فعال (gateway, profile) scope شده‌اند. سوئیچ از گیت‌وی تلگرامی به گیت‌وی سیگنالی نمی‌تواند گروه‌های کانال یا نشست‌های گیت‌وی قبلی را در sidebar باقی بگذارد.
  • صرف نمایش انتخابگر registry ی اتصال محلی Electron را می‌خواند. گیت‌وی‌های راه‌دور فقط موقع انتخاب باز می‌شوند؛ polling دوره‌ای fleet وجود ندارد.
  • hover روی ایجنت backend اش را pre-warm می‌کند تا سوئیچ هزینهٔ cold boot نپردازد.
  • صفحهٔ Capabilities ‏(Skills / Tools / MCP) scope ی متناظر دارد: انتخابگر Configuring اش هر ایجنت (profile, device) را از roster ی اجتماع فهرست و انتخاب یکی مهارت‌ها، تول‌ست‌ها و سرورهای MCP ی آن ماشین را می‌خواند و می‌نویسد بدون تعویض فضای کاری Sessions. نصب hub، ‏کلیدهای env و setup ی MCP همگی روی backend ی ایجنت انتخابی فرود می‌آیند. دکمهٔ hot-reload-into-a-live-session تب MCP فقط برای ایجنت‌های گیت‌وی‌ای که window به آن وصل است ظاهر می‌شود؛ ویرایش‌ها روی ماشین‌های دیگر در نشست بعدی‌شان اعمال می‌شوند.

افزودن، تست، rename یا حذف گیت‌وی‌ها در Settings ← Gateways انجام می‌شود. دکمهٔ plug کنار اقدامات پروفایل میان‌بری به آن خانهٔ مدیریتی واحد است نه یک جریان add دوم.

Sessions و Bot Mode

‏Sessions عمداً هر بار یک گیت‌وی فعال نشان می‌دهد: تا فایل‌ها، ابزارها، کانال‌ها، cron و تاریخچهٔ نشست در یک زمینهٔ اجرایی قابل‌فهم بمانند. Bot Mode کار متفاوتی دارد و ممکن است roster ی اجتماع را گروه‌بندی-بر-اساس-گیت‌وی ارائه دهد تا کاربر از یک سطح، ایجنتی روی NAS و دیگری روی VPS باز کند. باز کردن یک bot همچنان route دقیق (gateway, profile) آن را فعال می‌کند.

منشن مستقیم بات‌ها و delegation به‌طور پیش‌فرض gateway-local می‌مانند. عبور از مرز backend یعنی تغییر فایل‌سیستم، credential ها، ابزارها و زمینهٔ اعتماد، پس اجرای cross-gateway باید یک پُل صریح باشد نه عارضهٔ جانبی تصادفی شریک شدن یک پنجرهٔ Desktop.

۵ به‌روزرسانی همهٔ نمونه‌ها یکجا

‏Settings ← Gateways ← Update all instances ‏(با ثبت بیش از یک اتصال نمایش داده می‌شود) مقدار hermes update را به‌موازات به هر اتصال واجد شرایط dispatch می‌کند:

  • Local از طریق خط‌لوله به‌روزرسانی خود اپ به‌روز می‌شود ‏(همان جریان Settings ← Updates).
  • اتصالات Remote و SSH told می‌شوند خودشان از طریق backend خودشان به‌روز شوند — به‌روزرسانی روی آن ماشین اجرا می‌شود.
  • نمونه‌های Hermes Cloud با یادداشت Managed by Hermes Cloud skip می‌شوند: پلتفرم نسخه‌هایشان را مدیریت می‌کند.

هر نمونه مستقل گزارش می‌دهد، پس یک جعبه غیرقابل‌رسید هرگز batch را گیر نمی‌اندازد. backend هایی که به‌روزرسانی را بیرونی مدیریت می‌کنند ‏(Docker، ‏Nix) مؤدبانه با پیام خودشان در هر ردیف امتناع می‌کنند.

البته به‌ندرت به دکمهٔ Settings نیاز دارید: به‌محض وجود بیش از یک هدف به‌روزرسانی، affordance های عادی به‌روزرسانی اپ ‏(Update now روی پنل About، ‏⌘K Update Hermes، ‏toast ی update-ready) همان fan-out را خودکار اجرا می‌کنند — اول backend فعال، بعد هر گیت‌وی واجد شرایط دیگر، و آخر از همه خود اپ دسکتاپ.

۶ نکات امنیتی

  • توکن‌ها کجا زندگی می‌کنند. توکن‌های نشست گیت‌وی راه‌دور با safeStorage ی Electron در حالت rest رمز می‌شوند ‏(keychain سیستم‌عامل — Keychain روی macOS، ‏DPAPI روی ویندوز، ‏backend ی session keyring روی لینوکس) و در پروسهٔ main ی Electron می‌مانند؛ renderer و پلاگین‌ها هرگز بایت‌های توکن را نمی‌بینند. توکن‌های OAuth ی ورود native هم به همین شکل کلیدخورده-با-URL پایهٔ گیت‌وی ذخیره و قبل از انقضا خودکار refresh می‌شوند.
  • لینوکس بدون keyring. روی نشست لینوکسی بدون keychain قابل‌استفاده اپ نمی‌تواند توکن را رمز کند؛ ذخیرهٔ یکی قبل از نگهداری توکن به‌صورت plaintext دیالوگ opt-in ی صریح می‌طلبد.
  • فایل registry ‏(connections.json زیر دایرکتوری user-data ی اپ) برچسب‌ها، URL ها و host ها را حمل می‌کند — secrets فقط داخل envelope های رمزشده ظاهر می‌شوند.
  • متد host.connections() ی SDK ی پلاگین عمداً فقط برچسب‌ها، انواع و id ی primary را برمی‌گرداند — هرگز مواد توکن نه.

برای نویسندگان پلاگین

‏SDK ی پلاگین Desktop سطح چند-گیت‌وی را مستقیم expose می‌کند ‏(Desktop Plugin SDK):

  • ‏host.connections() — فهرست اتصالات ثبت‌شده ‏(برچسب‌ها، انواع، primary؛ هرگز بایت‌های توکن).
  • ‏host.agents() — roster ی اجتماع: یک ردیف per جفت (gateway, profile) با handle ی از-قبل-محاسبه‌شده @name-device.
  • ‏host.ensureAgent(connectionId, profile) — فعال‌سازی گیت‌وی ایجنت تا فراخوانی‌های بعدی host.request به backend او بخورد.
  • ‏host.warmAgent(connectionId, profile) — pre-warm ی fire-and-forget ی socket ‏(hover-intent).

هر چهار مورد feature-detected هستند: روی build ی قدیمی‌تر Desktop غایب‌اند و پلاگین باید به جریان تک-گیت‌وی profiles.list برگردد. roster ی چند-گیت‌وی Bot Mode مصرف‌کنندهٔ مرجع است.

۷ عیب‌یابی

  • «Connection test failed» — backend از این ماشین در آن URL قابل‌رسید نیست. بررسی کنید hermes serve روی host ی راه‌دور اجرا باشد، پورت باز باشد و ‏(برای auth ی توکن) توکن current باشد. بعد از اصلاح دوباره Test را اجرا کنید.
  • ایجنتی نشان داده می‌شود ولی باز نمی‌شود — روی اتصالش Test را اجرا کنید. شکست پای WebSocket همراه قبولی HTTP معمولاً یعنی proxy، ‏فایروال یا گارد auth/origin ی گیت‌وی /api/ws را بلاک می‌کند.
  • گیت‌وی راه‌دوری در roster نیست — backend اش پایین یا غیرقابل‌رسید است؛ roster آن را همراه خطا زیر گیت‌وی‌ها فهرست می‌کند. اتصالات SSH تا اولین استفاده connect-on-demand نشان داده می‌شوند — این طراحی است نه شکست.
  • «Update Hermes Desktop to chat with agents on other connections» — اپ قدیمی‌تر از stack ی چند-اتصاله است؛ خود اپ دسکتاپ را به‌روز کنید.
  • نام‌های تکراری دستگاه — ممکن نیست؛ نام‌ها موقع ذخیره یکتا اجبار می‌شوند. اگر نام مهاجرت‌شده تداخل داشت پسوند گرفته بود ‏(Homelab 2).
  • «Could not save the connection» — رایج‌ترین‌ها: Name جامانده، نامی که قبلاً استفاده شده یا Gateway URL / SSH host ی بدفرم؛ پیام خطا نقض دقیق را نام می‌برد.
