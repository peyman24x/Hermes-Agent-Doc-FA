1Password

کلیدهای API ی ارائه‌دهنده‌ها را هنگام شروع پروسه از ‏1Password حل کنید به‌جای ذخیرهٔ plaintext شان داخل ‏~/.hermes/.env. کلیدها را به‌عنوان آیتم‌های 1Password نگه می‌دارید و با ‏op://vault/item/field ارجاع می‌دهید؛ چرخاندن یک credential تک‌تغییری در 1Password می‌شود.

۱ نحوهٔ کار

  1. ‏CLI ی رسمی 1Password ‏(op) را نصب و احراز هویت می‌کنید — یا با یک توکن service-account ‏(سرورهای headless) یا یک نشست تعاملی/دسکتاپ ‏(لپ‌تاپ).
  2. نام‌های متغیر محیطی را در ~/.hermes/config.yaml به ارجاع‌های op:// نگاشت می‌کنید.
  3. هر بار که hermes ‏(یا گیت‌وی یا cron job) شروع شود، بعد از لود شدن ~/.hermes/.env، هرمس برای هر ارجاع op read اجرا و مقادیر حل‌شده را در os.environ ست می‌کند.
  4. به‌طور پیش‌فرض هرمس مقادیر از-قبل-موجود محیط را بازنویسی می‌کند، پس 1Password منبع حقیقت است — credential را یک بار بچرخانید و هر پروسهٔ هرمس در شروع بعدی می‌گیردش. اگر می‌خواهید .env برنده باشد override_existing: false را فلپ کنید.

هرمس هرگز از طرف شما احراز هویت نمی‌شود و op را دانلود نمی‌کند: به CLI ی نصب‌ و مورد-اعتماد-از-قبل شما shelling out می‌کند. اگر op غایب باشد، نشستتان قفل باشد یا ارجاعی غلط باشد، هشداری یک‌خطی چاپ و با credential هایی که .env از قبل داشته ادامه می‌دهد — startup را هرگز بلاک نمی‌کند.

احراز هویت

‏op دو حالت مناسب-غیرتعاملی دارد؛ هرمس با هر دو کار می‌کند:

  • Service accounts ‏(توصیه‌شده برای سرورها/CI): در 1Password یک service account بسازید، دسترسی خواندن به vault مربوطه بدهید و توکنش را به‌عنوان OP_SERVICE_ACCOUNT_TOKEN در ~/.hermes/.env export کنید. توکن خودِ credential است — مثل هر bearer token دیگری رفتارش کنید.
  • نشست‌های دسکتاپ / تعاملی ‏(لپ‌تاپ‌ها): ‏op signin را اجرا کنید ‏(یا CLI integration را در اپ 1Password فعال کنید). هرمس متغیرهای OP_SESSION_* تان را به فرزند op عبور می‌دهد. کلید کش ی 1Password آن متغیرهای نشست را هم شامل می‌شود، پس ورود به حساب دیگر هیچ‌وقت مقداری که زیر هویت قبلی کش شده را سرو نمی‌کند.

۲ توکن bootstrap

وقتی با توکن service-account احراز هویت می‌کنید، آن توکن خودش credential ی bootstrap است که هرمس پیش از حل هر ارجاع op:// لازم دارد. باید در os.environ هر پروسه‌ای که secrets را حل می‌کند حاضر باشد — شامل cron job ها ‏(kanban.dispatch_in_gateway: false)، فراخوانی‌های زیرپروسه، اجرای CLI، ‏launchd agents ی macOS و کانتینرهای Docker — نه فقط گیت‌وی تعاملی. سه راه فراهم کردن آن به ترتیب اولویت:

  1. داخل ~/.hermes/.env ‏(توصیه‌شده). ‏hermes secrets onepassword setup --token <token> توکن را در ~/.hermes/.env می‌نویسد، دقیقاً مثل BWS_ACCESS_TOKEN ی Bitwarden. چون load_hermes_dotenv() همیشه .env را لود می‌کند توکن همه‌جا بدون هیچ setup اضافه‌ای حاضر است. ساده‌ترین گزینهٔ قابل‌اعتماد.
  2. داخل ~/.hermes/.op.env ‏(gitignored). اگر ترجیح می‌دهید توکن service-account بیرون .env بماند — مثلاً تا .env وارد مخزن dotfiles ی خصوصی شود ولی توکن خارج version control بماند — آن را در ~/.hermes/.op.env بگذارید: 
    echo 'OP_SERVICE_ACCOUNT_TOKEN=ops_...' > ~/.hermes/.op.env
chmod 600 ~/.hermes/.op.env
    هرمس .op.env را موقع startup خودکار — بعد از .env — لود و هرگز توکن از-قبل-موجود در محیط را بازنویسی نمی‌کند. .op.env ی gitignored است پس توکن هرگز وارد فایل commit‌شده نمی‌شود.
  3. با EnvironmentFile ی systemd ‏(گیت‌وی لینوکس). اگر گیت‌وی را زیر systemd اجرا می‌کنید می‌توانید توکن را مستقیم داخل env ی سرویس تزریق کنید: 
    [Service]
EnvironmentFile=-/home/youruser/.hermes/.op.env
    توکنی که این‌طور تزریق شود اولویت دارد — هرمس می‌بیند OP_SERVICE_ACCOUNT_TOKEN از قبل ست است و کلاً از لود .op.env عبور می‌کند.

اگر توکن فقط از طریق شل تعاملی قابل‌رسید باشد ‏(op signin، ‏export های OP_SESSION_* در .bashrc و…)، cron job ها یا زیرپروسه‌های تازه-spawn آن را به ارث نمی‌برند؛ آن زمینه‌ها هشدار لاg و به credential هایی که .env از قبل داشته fallback می‌کنند. برای هر workload غیرتعاملی یکی از سه گزینه بالا را به کار ببرید.

۳ راه‌اندازی

۱. نصب و ورود به op

راهنمای شروع CLI ی 1Password را دنبال کنید. تأیید کنید کار می‌کند:

op whoami

۲. فعال کردن یکپارچه‌سازی

hermes secrets onepassword setup

این verify می‌کند op روی PATH باشد ‏(یا --binary-path)، تنظیمات حساب/توکن را ثبت، نشست فعال را بررسی و ‏secrets.onepassword.enabled: true را فلپ می‌کند. فلگ‌های غیرتعاملی:

hermes secrets onepassword setup \
  --account my.1password.com \
  --token-env OP_SERVICE_ACCOUNT_TOKEN \
  --token "$OP_SERVICE_ACCOUNT_TOKEN"

۳. نگاشت credential ها

قالب ارجاع ‏op://<vault>/<item>/<field> است:

hermes secrets onepassword set OPENAI_API_KEY    "op://Private/OpenAI/api key"
hermes secrets onepassword set ANTHROPIC_API_KEY "op://Private/Anthropic/credential"

۴. پیش‌نمایش و تأیید

hermes secrets onepassword sync     # dry-run: resolve now, show what would apply
hermes secrets onepassword status   # config + binary + references + auth

از این به بعد هر invocation ی hermes ارجاع‌ها را موقع startup حل می‌کند. اولین باری که secrets در یک پروسه اعمال شوند خلاصه‌ای یک‌خطی در stderr می‌بینید.

۵ پیکربندی

پیش‌فرض‌ها در ‏~/.hermes/config.yaml:

yaml
secrets:
  onepassword:
    enabled: false
    env:
      OPENAI_API_KEY: "op://Private/OpenAI/api key"
      ANTHROPIC_API_KEY: "op://Private/Anthropic/credential"
    account: ""
    service_account_token_env: OP_SERVICE_ACCOUNT_TOKEN
    binary_path: ""
    cache_ttl_seconds: 300
    override_existing: true
کلیدپیش‌فرضکارش
enabledfalseکلید اصلی. خاموش باشد op هرگز invoke نمی‌شود.
env{}نگاشت نام-متغیر ← ارجاع op://vault/item/field. ورودی‌هایی که نامشان نام متغیر env معتبر نیست یا مقدارشان ارجاع op:// نیست با هشدار skip می‌شوند.
account""نام مختصر / آدرس ورود که به‌عنوان op read --account پاس می‌شود. خالی = حساب پیش‌فرض op.
service_account_token_envOP_SERVICE_ACCOUNT_TOKENمتغیر env ی که هرمس توکن service-account را از آن می‌خواند. مقدارش به فرزند op به‌صورت OP_SERVICE_ACCOUNT_TOKEN ‏(نامی که op انتظار دارد) export می‌شود. متغیر را unset بگذارید تا از نشست دسکتاپ/تعاملی استفاده شود.
binary_path""مسیر مطلق op. ست شود همان verbatim استفاده و PATH مشورت نمی‌شود — پین کنید تا به هر op ی که اول PATH ظاهر شد اعتماد نکنید.
cache_ttl_seconds300مقادیر حل‌شده چه مدت دوباره استفاده شوند ‏(درون-پروسه و روی دیسک). صفر = غیرفعال کردن هر دو لایه کش — هیچ مقداری اصلاً روی دیسک نوشته نمی‌شود.
override_existingtruetrue یعنی مقادیر حل‌شده بر هرچه در env هست می‌نویسند ‏(تا rotation اثر کند). false کنید تا .env / export های شل برنده شوند؛ آن ارجاع‌ها قبل از invoke شدن op skip می‌شوند.

۶ حالت‌های شکست

‏1Password هرگز startup ی هرمس را بلاک نمی‌کند. هر چه خراب شود هشدار یک‌خطی در stderr می‌بینید و هرمس ادامه می‌دهد:

علامتعلتاصلاح
‏the op CLI was not found on PATHop نصب نیست / روی PATH نیستCLI را نصب یا secrets.onepassword.binary_path را ست کنید
‏op read failed for 'op://…': …نشست قفل، توکن منقضی یا نبود دسترسی vault‏op signin، ‏hermes secrets onepassword token برای چرخاندن توکن service-account، یا اعطای دسترسی به service account
‏op read returned an empty value for 'op://…'فیلد ارجاع‌شده هست ولی خالی استitem/field را در 1Password درست کنید ‏(مقدار خالی هرگز اعمال نمی‌شود — متغیر env ی فعلی‌تان دست‌نخورده می‌ماند)
‏… is not an op:// secret referenceمقدار نگاشتی ارجاع op:// نیستبا قالب درست op://vault/item/field دوباره ست کنید
‏op read timed outشبکه بلاک یا 1Password کنداتصال / یکپارچگی اپ دسکتاپ را چک کنید

هشدارهای startup حالا خط اصلاح ← دارند که دقیقاً می‌گوید کدام فرمان شکست را درست می‌کند.

Caching

pull های موفق و کامل درون-پروسه و روی دیسک زیر ‏<hermes_home>/cache/op_cache.json کش می‌شوند ‏(نوشتن اتمی، مود ۰۶۰۰)، تا invocation های کوتاه پشت‌سرهم hermes برای هر ارجاع دوباره op صدا نزنند. کش:

  • فقط مقادیر resolved ی secret را ذخیره می‌کند — هرگز توکن service-account یا مواد auth خام ‏(auth به‌صورت fingerprint در کلید کش می‌آید)؛
  • وقتی توکن، ‏حساب، ‏متغیرهای OP_SESSION_* یا مجموعه ارجاع‌ها عوض شود باطل می‌شود؛
  • وقتی pull حتی یک خطای per-reference داشته نوشته نمی‌شود تا یک شکست auth گذرا برای TTL منجمد نشود؛
  • با ‏cache_ttl_seconds: 0 کاملاً غیرفعال می‌شود — هم خواندن هم نوشتن.

۷ نکات امنیتی و چه وقت استفاده نکنیم

  • توکن service-account ی 1Password می‌تواند هر secret ی که حساب دسترسی دارد بخواند. در ~/.hermes/.env ذخیره‌اش کنید ‏(نه config.yaml) و اگر لو رفت از 1Password revoke + regenerate کنید.
  • هرمس اجازه نمی‌دهد مقدار حل‌شده خود متغیر env ی توکن را بازنویسی کند حتی با override_existing: true.
  • فرزند op یک محیط allowlist ی مینیمال می‌گیرد ‏(متغیرهای auth/نشست + PATH/HOME)، نه کپی کامل os.environ، پس credential های ارائه‌دهندهٔ post-dotenv همه به فرزند به ارث نمی‌رسند.
  • ارجاع‌ها validate می‌شوند که با op:// شروع شوند و ارجاع بعد از terminator ی گزینه -- پاس می‌شود تا مقدار دستکاری‌شده نتواند به‌عنوان فلگ op parse شود.

چه وقت استفاده نکنیم

  • راه‌اندازی‌های شخصی تک‌ماشینه که ~/.hermes/.env کافی است.
  • محیط‌های air-gapped که به 1Password نمی‌رسند.
  • CI/CD که سازوکار تزریق-secrets موجود از قبل سیم‌کشی شده — یکی را بردارید نه دو تا را.

مورد خوب برای این: fleet های چند-ماشینه، جعبه‌های dev مشترک، ‏VPS های گیت‌وی یا هرجایی که چرخش و revoke ی متمرکز بین چند نصب هرمس می‌خواهید.
