Bitwarden Secrets Manager

کلیدهای API را هنگام شروع پروسه از ‏Bitwarden Secrets Manager بکشید به‌جای ذخیرهٔ plaintext شان داخل ‏~/.hermes/.env. یک secret ی bootstrap ‏(توکن دسترسی حساب-ماشین) جای N کلید per-provider را می‌گیرد و rotate کردن یک credential تک‌تغییری در اپ وب Bitwarden می‌شود.

۱ نحوهٔ کار

  1. در Bitwarden Secrets Manager یک حساب-ماشین می‌سازید، دسترسی خواندن به یک پروژه می‌دهید و یک توکن دسترسی تولید می‌کنید.
  2. هرمس آن تک توکن را در ‏~/.hermes/.env به‌عنوان BWS_ACCESS_TOKEN ذخیره می‌کند.
  3. هر بار که hermes ‏(یا گیت‌وی یا cron job) شروع شود، بعد از لود ~/.hermes/.env، هرمس ‏bws secret list <project_id> را صدا و کلیدهای برگشتی را در os.environ ست می‌کند.
  4. به‌طور پیش‌فرض هرمس مقادیر از-قبل-موجود در محیط را بازنویسی می‌کند، پس Bitwarden منبع حقیقت است — یک کلید را یک بار در اپ وب بچرخانید و هر پروسهٔ هرمس در شروع بعدی می‌گیردش. اگر می‌خواهید .env برنده باشد override_existing: false را در config بزنید.

باینری bws در اولین استفاده خوددانلود به ~/.hermes/bin/ می‌رود — بدون apt، بدون brew، بدون sudo.

چرا حساب-ماشین ‏(و چرا بدون پرامپت 2FA)

‏Bitwarden Secrets Manager برای workload های غیرتعاملی طراحی شده: حساب‌های ماشین نمی‌توانند 2FA-gate شوند چون انسانی در حلقه نیست. توکن دسترسی خودِ credential است. هرکس آن را داشته باشد هر secret ی که حساب-ماشین به آن دسترسی دارد را می‌خواند، پس مثل یک bearer token ی باارزش رفتارش کنید — در .env ذخیره‌اش کنید ‏(نه config.yaml) و اگر لو رفت از اپ وب Bitwarden revoke + regenerate کنید.

حساب-ماشین را در اپ وب می‌سازید جایی که 2FA ی عادی‌تان اعمال می‌شود. بعدش توکن مستقل است.

۲ راه‌اندازی

۱. ساخت حساب-ماشین و توکن دسترسی

در اپ وب Bitwarden ‏(یا ‏vault.bitwarden.eu برای حساب‌های EU):

  1. از سوییچر محصول به Secrets Manager سوئیچ کنید.
  2. یک Project بسازید یا بردارید ‏(مثلاً «Hermes keys»).
  3. کلیدهای ارائه‌دهنده‌تان را به‌عنوان secret اضافه کنید. مقدار Name ی secret نام متغیر محیطی می‌شود — OPENROUTER_API_KEY، ‏ANTHROPIC_API_KEY و… به کار ببرید.
  4. ‏Machine accounts ← New machine account ← My Hermes machine ← تب Projects ← دسترسی Read به پروژه‌تان بدهید.
  5. تب Access tokens ← Create access token ← انقضا Never ‏(یا تاریخ انتخابی) ← توکن را کپی کنید ‏(با 0. شروع می‌شود). Bitwarden دیگر نمی‌تواند پس بدهد — کپی را نگه دارید.

‏Secrets Manager روی تیر رایگان Bitwarden با محدودیت شامل است؛ برای امتحان کردن پلن پولی لازم نیست.

۲. اجرای ویزارد

hermes secrets bitwarden setup

این کارها را می‌کند:

  1. bws v2.0.0 را دانلود و verify و داخل ~/.hermes/bin/bws می‌گذارد.
  2. توکن دسترسی را می‌پرسد ‏(ورودی مخفی). در ~/.hermes/.env به‌عنوان BWS_ACCESS_TOKEN ذخیره می‌شود.
  3. ناحیهٔ Bitwarden حساب-ماشین را می‌پرسد — ‏US Cloud، ‏EU Cloud یا self-hosted / URL سفارشی. در config.yaml به‌عنوان secrets.bitwarden.server_url ذخیره و به bws به‌عنوان BWS_SERVER_URL پاس می‌شود.
  4. پروژه‌های قابل‌مشاهده توسط حساب-ماشین را فهرست؛ یکی را بردارید. در config.yaml به‌عنوان secrets.bitwarden.project_id ذخیره می‌شود.
  5. secrets های پروژه را تست-واکشی و نشان می‌دهد کدام متغیرهای env حل خواهند شد.
  6. ‏secrets.bitwarden.enabled: true را فلپ می‌کند.

setup غیرتعاملی هم با فلگ‌ها پشتیبانی می‌شود:

hermes secrets bitwarden setup \
  --access-token "$BWS_ACCESS_TOKEN" \
  --server-url https://vault.bitwarden.eu \
  --project-id <project-uuid>

۳. تأیید

hermes secrets bitwarden status

از این به بعد هر invocation ی herms ‏(hermes) secrets تازه را موقع startup می‌کشد. اولین باری که secrets در یک پروسه اعمال شوند خلاصه‌ای یک‌خطی در stderr می‌بینید.

چرخاندن توکن منقضی یا revoke شده

وقتی توکن حساب-ماشین منقضی شود، revoke شود یا حساب حذف شود startup نشان می‌دهد:

Bitwarden Secrets Manager: Bitwarden rejected the machine-account access token (BWS_ACCESS_TOKEN) — it was likely revoked, expired, or belongs to another region.  (...)
Bitwarden Secrets Manager: → Run `hermes secrets bitwarden token` to paste a fresh access token ...

بدون اجرای دوباره کل ویزارد درستش کنید:

hermes secrets bitwarden token                     # masked prompt
hermes secrets bitwarden token --access-token 0.…  # non-interactive

فرمان قبل از نوشتن هر چیزی Bitwarden را با توکن جدید probe می‌کند — توکن رد‌شده .env ی فعلی شما را دست‌نخورده می‌گذارد. روی موفقیت توکن را ذخیره، کش‌های واکشی را پاک و اگر پروژهٔ پیکربندی‌شده برای حساب-ماشین جدید مرئی نباشد هشدار می‌دهد.

۴ پیکربندی

پیش‌فرض‌ها در ‏~/.hermes/config.yaml:

yaml
secrets:
  bitwarden:
    enabled: false
    access_token_env: BWS_ACCESS_TOKEN
    project_id: ""
    server_url: ""
    cache_ttl_seconds: 300
    encrypted_cache:
      enabled: false
      max_stale_seconds: 0
    override_existing: true
    auto_install: true
کلیدپیش‌فرضکارش
enabledfalseکلید اصلی. خاموش باشد هرگز با Bitwarden تماس نمی‌گیرد.
access_token_envBWS_ACCESS_TOKENنام متغیر env ی حامل توکن bootstrap. اگر BWS_ACCESS_TOKEN را جای دیگری مصرف می‌کنید عوضش کنید.
project_id""UUID پروژه‌ای که از آن sync می‌شود.
server_url""ناحیهٔ Bitwarden یا نقطهٔ پایانی self-hosted. خالی = پیش‌فرض bws ‏(US Cloud). برای EU Cloud مقدار https://vault.bitwarden.eu یا URL خودتان. به زیرپروسهٔ bws به‌عنوان BWS_SERVER_URL لوله می‌شود.
cache_ttl_seconds300نتیجهٔ واکشی درون-پروسه یا دیسکی چه مدت دوباره استفاده شود. صفر = غیرفعال.
encrypted_cache.enabledfalseآخرین واکشی موفق در کش رمزشده AES-GCM در ~/.hermes/cache/bws_cache.enc.json ذخیره شود.
encrypted_cache.max_stale_seconds0با فعال بودن کش رمز، بعد از شکست شبکه/timeout تا این سن مجاز به استفاده است. شکست‌های احراز هویت هرگز stale نمی‌خوانند. نوشتن رمز موفق، cache/bws_cache.json ی قدیمی plaintext را حذف می‌کند.
override_existingtruetrue یعنی مقادیر Bitwarden بر هرچه در env هست می‌نویسند ‏(تا rotation در اپ وب واقعاً اثر کند). false کنید اگر می‌خواهید .env / export های شل محلی برنده شوند.
auto_installtruetrue یعنی bws در اولین استفاده خوددانلود به ~/.hermes/bin/ می‌رود.

۵ حالت‌های شکست

‏Bitwarden هرگز startup ی هرمس را بلاک نمی‌کند. هر چه خراب شود هشدار یک‌خطی در stderr می‌بینید و هرمس با credential هایی که .env از قبل داشته ادامه می‌دهد:

علامتعلتاصلاح
‏BWS_ACCESS_TOKEN is not setدر config فعال ولی توکن از .env پاک شدهدوباره hermes secrets bitwarden setup را اجرا کنید
‏Bitwarden rejected the machine-account access token … invalid_clientتوکن revoke/منقضی، حساب-ماشین حذف شده — یا توکن مال ناحیهٔ دیگری است ‏(مثلاً توکن EU به نقطهٔ identity ی US)‏hermes secrets bitwarden token را با توکن تازه اجرا کنید؛ برای عدم تطبیق ناحیه setup را دوباره اجرا و EU/self-hosted را بردارید ‏(یا secrets.bitwarden.server_url را ست کنید)
‏bws exited 1: invalid access tokenتوکن revoke شده یا غلط‏hermes secrets bitwarden token را با توکن جدید اجرا کنید
‏bws timed outشبکه بلاک یا API ی Bitwarden کنداتصال به api.bitwarden.com ‏(یا server_url تان) را چک کنید
‏bws binary not available‏auto_install: false و bws روی PATH نیستدستی از releases ی github.com/bitwarden/sdk-sm نصب کنید یا auto_install را روشن کنید
‏Checksum mismatchدانلود خراب یا دستکاری‌شدهدوباره اجرا کنید، retry می‌شود؛ اگر ادامه یافت issue ثبت کنید

هشدارهای startup حالا خط اصلاح ← دارند که دقیقاً می‌گوید کدام فرمان شکست را درست می‌کند.

۶ نکات امنیتی و چه وقت استفاده نکنیم

امنیت

  • توکن bootstrap ‏(BWS_ACCESS_TOKEN) خودش حساس است — هرکس آن را دارد هر secret ی که حساب-ماشین می‌بیند را می‌خواند. مثل هر کلید API ی دیگر رفتارش کنید.
  • هرمس اجازه نمی‌دهد Bitwarden خود توکن bootstrap را بازنویسی کند حتی با override_existing: true. اگر BWS_ACCESS_TOKEN را داخل پروژه به‌عنوان secret ذخیره کنید موقع apply بی‌سروصدا skip می‌شود.
  • دانلود باینری bws علیه checksum ی SHA-256 منتشرشده در همان GitHub release verify می‌شود. عدم تطبیق نصب را abort می‌کند.
  • نسخهٔ پین‌شده ‏(bws v2.0.0 هنگام نگارش) از طریق PR ها به این مخزن به‌روز می‌شود — هرمس bws را خودکار به «latest» ارتقا نمی‌دهد چون شکل release های بالادستی ممکن است عوض شود.

چه وقت استفاده نکنیم

  • راه‌اندازی‌های شخصی تک‌ماشینه که ~/.hermes/.env کافی است. یک credential را با دیگری معامله و یک وابستگی شبکه به startup اضافه می‌کنید.
  • محیط‌های air-gapped که به api.bitwarden.com نمی‌رسند.
  • CI/CD که سازوکار تزریق-secrets موجود ‏(GitHub Actions secrets، ‏Vault و…) از قبل راه افتاده — یکی را بردارید نه دو تا را.

مورد خوب برای این: fleet های چند-ماشینه، جعبه‌های dev مشترک، ‏VPS های گیت‌وی یا هر setup ای که چرخش و revoke ی متمرکز بین چند نصب هرمس می‌خواهید.
