اجرای چند گیت‌وی هم‌زمان ‏(Running Many Gateways at Once)

چند پروفایل را — هرکدام با توکن‌های بات، نشست‌ها و حافظهٔ خودش — به‌عنوان سرویس‌های مدیریت‌شده روی یک ماشین اداره کنید. این صفحه نگرانی‌های عملیاتی را پوشش می‌دهد: روشن کردن همه با هم، دیدن لاگ‌ها بین پروفایل‌ها، جلوگیری از خواب رفتن host و ریکاوری از عیب‌های رایج launchd/systemd.

فقط یک ایجنت هرمس اجرا می‌کنید؟ این صفحه لازم نیست — اصول در بخش پروفایل‌ها. نمونه‌هایتان روی ماشین‌های متفاوتاند که یک اپ دسکتاپ باید هم‌زمان به آنها برسد؟ بخش اتصال دسکتاپ به چند نمونه را ببینید.

۱ چه وقت استفاده کنیم

این setup را وقتی می‌خواهید که دو ایجنت هرمس یا بیشتر دارید که همه باید هم‌زمان آنلاین باشند. دلایل رایج:

  • دستیار شخصی روی یک بات تلگرامی و یک ایجنت کدنویس روی بات دیگر
  • یک ایجنت per عضو خانواده یا یکی per فضای کاری اسلک
  • نمونه‌های sandbox + production از یک پیکربندی واحد
  • ایجنت پژوهش + ایجنت نگارش + بات cron-رانده — هرکدام با حافظه و مهارت‌های ایزوله

هر پروفایل از قبل LaunchAgent ی per-platform خودش ‏(ai.hermes.gateway-<name>.plist) یا سرویس کاربری systemd ی ‏(hermes-gateway-<name>.service) را دارد. این guide الگوهای مدیریت جمعی‌شان را اضافه می‌کند.

شروع سریع

# Create profiles (once)
hermes profile create coder
hermes profile create personal-bot
hermes profile create research

# Configure each
coder setup
personal-bot setup
research setup

# Install each gateway as a managed service
coder gateway install
personal-bot gateway install
research gateway install

# Start them all
coder gateway start
personal-bot gateway start
research gateway start

همین — سه ایجنت مستقل، هرکدام روی پروسهٔ خودش، ری‌استارت خودکار روی کرش و ورود کاربر.

۲ جایگزین: یک گیت‌وی برای همهٔ پروفایل‌ها ‏(multiplexing)

الگوی بالا یک پروسه per-profil اجرا می‌کند. آن پیش‌فرض است و انتخاب درست برای بیشتر setup ها. ولی روی host ای با پروفایل‌های زیاد — یا استقراری کانتینری که یک پروسه per-profil از نظر عملیاتی سنگین است — می‌توانید به‌جایش یک گیت‌وی multiplexing ی واحد اجرا کنید: گیت‌وی پروفایل پیش‌فرض تنها پروسهٔ inbound می‌شود و پیام‌های هر پروفایل روی جعبه را سرو می‌کند.

این opt-in و به‌طور پیش‌فرض خاموش است. خاموش باشد هیچ چیز این صفحه تغییر نمی‌کند — همهٔ رفتارهای پایین بی‌اثرند.

کی multiplexing ترجیح دارد

  • استقرار کانتینر/VPS ای که N تا unit ی supervisor، ‏N پورت و N فایل PID بار سنگینی است.
  • پروفایل‌های کم-ترافیک زیاد که هرکدام توجیه یک پروسه کامل ندارند.
  • می‌خواهید فقط یک چیز را شروع، مانیتور و ری‌استارت کنید.

وقتی ایزوله‌سازی سخت سطح-پروسه بین پروفایل‌ها می‌خواهید ‏(حافظه جدا، دامنه‌های کرش مستقل، توان ری‌استارت یک پروفایل بدون دست زدن به بقیه) روی one-process-per-profile بمانید.

نحوهٔ opt-in

فلگ را روی پروفایل پیش‌فرض ست کنید ‏(مالک multiplexer است) و گیت‌وی‌اش را ری‌استارت کنید:

hermes config set gateway.multiplex_profiles true
hermes gateway restart

معادلاً در config.yaml ی پروفایل پیش‌فرض:

gateway:
  multiplex_profiles: true

(فلگ به‌صورت top-level ی multiplex_profiles: true هم برای راحتی پذیرفته می‌شود.) در شروع بعدی گیت‌وی پیش‌فرض هر پروفایل را فهرست، پلتفرم‌های فعال هر پروفایل را زیر credential های همان پروفایل بالا می‌آورد و هر پیام ورودی را به پروفایل متعلقش مسیریابی می‌کند. هر نوبت config، مهارت‌ها، حافظه، SOUL و کلیدهای ارائه‌دهندهٔ پروفایلِ مسیریابی‌شده را حل می‌کند — credential ها هرگز بین پروفایل‌ها شریک نمی‌شوند.

برای پروفایل‌های ثانویه hermes gateway start اجرا نمی‌کنید — گیت‌وی پیش‌فرض آنها را سرو می‌کند. تغییرات قرارداد را پایین ببینید.

با روشن بودن multiplexing چه چیزهایی عوض می‌شود

۱. پروفایل‌های ثانویه نباید گیت‌وی خودشان را شروع کنند

با multiplexer ی در حال اجرا، ‏hermes gateway start / run ی پروفایل نام‌دار یک خطای سخت است که شما را به multiplexer ارجاع می‌دهد:

The default gateway is running as a profile multiplexer and already serves
profile 'coder'. ...

multiplexer تنها پروسهٔ inbound است؛ گیت‌وی دومِ یک پروفایل پلتفرم‌های آن پروفایل را double-bind می‌کرد. --force را فقط اگر عمداً برای آن پروفایل پروسهٔ جدایی می‌خواهید پاس دهید ‏(حین اجرای multiplexer توصیه نمی‌شود). پس wrapper ی چرخه‌حیات cross-profil ابتدای این صفحه در حالت multiplex استفاده نمی‌شود — فقط گیت‌وی پیش‌فرض را مدیریت می‌کنید.

۲. پلتفرم‌های HTTP-inbound با پیشوند URL ی ‎/p/<profile>/‎ رسیده می‌شوند

ترافیک وب‌هوک ‏(و سایر HTTP-inbound) ی پروفایل ثانویه روی شنوندهٔ پیش‌فرض زیر یک پیشوند پروفایل می‌آید نه پورت دوم:

# default profile
POST http://host:8644/webhooks/<route>
# the "coder" profile, same listener
POST http://host:8644/p/coder/webhooks/<route>

پروفایل نامعلوم یا پیکربندی‌نشده در پیشوند ۴۰۴ می‌دهد. چون شنوندهٔ مشترکِ واحد همین‌طوری هر پروفایل را سرو می‌کند، پروفایل ثانویه نباید خودش پلتفرم port-binding را فعال کند — انجامش خطای config است که کل پروفایل ثانویه را skip می‌کند در حالی که پیش‌فرض و سایر پروفایل‌های سالم ادامه می‌یابند. هشدار نام پروفایل skip شده و همهٔ پلتفرم‌های متعارض را نام می‌برد:

Skipping secondary profile 'coder' due to port-binding config error: Profile
'coder' enables port-binding platform(s) webhook, but gateway.multiplex_profiles
is on. ... Remove these platform entries from profile 'coder's config.yaml or
configure them only on the default profile.

پلتفرم‌های port-binding مشمول این قاعده: ‏webhook، ‏api_server، ‏msgraph_webhook، ‏feishu، ‏wecom_callback، ‏bluebubbles، ‏sms، ‏whatsapp_cloud، ‏line. اینها را فقط روی پروفایل پیش‌فرض پیکربندی کنید؛ هر پروفایل از طریق پیشوند /p/<profile>/ اش reachable است.

احراز هویت از پروفایلی که در URL نام برده شده پیروی می‌کند. نقاط پایانی بدون پیشوند همچنان از credential های موجود شنوندهٔ پیش‌فرض استفاده می‌کنند:

  • درخواست‌های API-server ی ‎/p/coder/... باید از API_SERVER_KEY ی ~/.hermes/profiles/coder/.env استفاده کنند؛ کلید شنوندهٔ پیش‌فرض رد می‌شود.
  • مسیر وب‌هوکی که هدفش coder است باید کنار secret ی مخصوص-مسیر موجودش مقدار profile: coder را در config.yaml ی پروفایل پیش‌فرض اعلام کند. آن secret سپس فقط در /p/coder/webhooks/<route> پذیرفته و روی هر پیشوند پروفایل دیگری رد می‌شود.
  • مسیرهای وب‌هوک بدون profile مسیرهای پروفایل-پیش‌فرض می‌مانند و از طریق پیشوند پروفایل نام‌دار reachable نیستند.

پلتفرم‌های port-binding را در config های پروفایل ثانویه غیرفعال نگه دارید. شنوندهٔ مشترک و تعاریف route هایش روی پروفایل پیش‌فرض می‌مانند؛ binding ی پروفایل تعیین می‌کند هر route ی وب‌هوک احراز‌شده مجاز به اجرای کدام پروفایل باشد. درخواست‌های API ی نام‌دار وقتی پروفایل هدف API_SERVER_KEY ندارد fail closed می‌شوند.

فقط همین تداخل شنونده-مشترک به skip شدن پروفایل تنزل می‌یابد. خطاهای پیکربندی امنیتی fatal می‌مانند: مثلاً پلتفرم own-policy ی open بدون GATEWAY_ALLOW_ALL_USERS یا opt-in ی allow-all ی مخصوص همان پلتفرم همچنان startup ی گیت‌وی را abort می‌کند نه اینکه بی‌سروصدا پروفایل ناامن را بیندازد.

۳. پلتفرم‌های دارای-credential هنوز توکن خودشان را per-profil می‌خواهند

پلتفرم‌های polling/اتصالی ‏(تلگرام، دیسکورد، اسلک، ماتریکس، سیگنال و…) multiplexed خوب کار می‌کنند ولی هر پروفیلی که یکی را فعال کند باید توکن بات خودش را بدهد — همان توکن نمی‌تواند همزمان توسط دو پروفایل poll شود. اگر دو پروفایل همان جفت (platform, token) را پیکربندی کنند startup سریع شکست می‌خورد و هر دو پروفایل را نام می‌برد ‏(بخش ایمنی تعارض توکن — قاعده تغییر نکرده فقط الان داخل همان یک پروسه اجبار می‌شود).

۴. کلیدهای نشست per-profil namespace می‌شوند

نشست‌های هر پروفایل زیر namespace ی agent:<profile>:… زندگی می‌کنند تا دو پروفایل روی همان پلتفرم/چت هرگز در store ی نشست مشترک تصادم نکنند. پروفایل پیش‌فرض namespace ی تاریخی agent:main:… را بایت‌به-بایت نگه می‌دارد، پس نشست‌های فعلی پروفایل پیش‌فرض بی‌تأثیرند — نه مهاجرت، نه تاریخچهٔ یتیم.

۵. یک PID/lock و یک سطح status

یک PID و lock ی سطح-پروسه وجود دارد ‏(multiplexer، زیر خانهٔ پیش‌فرض). hermes وضعیت multiplexer و پروفایل‌هایی که سرو می‌کند را گزارش؛ ‏hermes status -p <name> به یک پروفایل می‌بُرد. هر پروفایل همچنان runtime_status.json خودش را زیر خانهٔ خودش می‌نویسد پس reader های per-profil ی موجود سر کار می‌مانند.

چه چیزی تغییر نمی‌کند

ایزوله‌سازی credential ی .env ی per-profil حفظ و حتی سخت‌گیرانه‌تر است: کلیدهای پروفایل از scope ی خودش حل می‌شوند و هرگز داخل محیط مشترک union نمی‌شوند ‏(یعنی زیرپروسه‌هایی مثل سرورهای MCP و worker های کانبان فقط secrets ی پروفایل خودشان را می‌بینند). کانبان، مهارت‌ها/حافظه/SOUL ی scope‌شده-به-پروفایل و مسیریابی مدل همگی دقیقاً مثل گیت‌وی‌های جدا per-profil رفتار می‌کنند.

سرو کردن پروفایل‌های منتخب

پیش‌فرض این است که ‏gateway.multiplex_profiles: true هر پروفایل نام‌دار معتبر روی host را سرو کند. برای نگه داشتن پروفایل‌های بی‌ربط بدون راه افتادن adapter ها یا cron job هایشان مقدار gateway.multiplex_profile_allowlist را ست کنید:

gateway:
  multiplex_profiles: true
  multiplex_profile_allowlist:
    - worker
    - guest

پروفایل پیش‌فرض همیشه سرو می‌شود و نیازی به فهرست شدن ندارد. allowlist ی unset رفتار تاریخی serve-all را نگه می‌دارد؛ فهرست خالی فقط پروفایل پیش‌فرض را سرو می‌کند. نام‌ها نرمال و dedup می‌شوند. ورودی‌های نامعتبر یا نام‌های نصب‌نشده با هشدار skip می‌شوند. مقدار غیر-فهرستیِ بدفرم امنانه به فقط-پیش‌فرض fail می‌کند.

مجموعهٔ سروشده همچنین پیشوندهای API/وب‌هوک ی /p/<profile>/، ‏وضعیت runtime، ‏واجد بودن profile-route و اینکه scheduler ی cron ی درون-پروسه کدام پروفایل‌ها را tick کند را کنترل می‌کند. پروفایل نام‌دار بیرون allowlist همچنان می‌تواند گیت‌وی مستقل خودش را اجرا کند.

مسیریابی گفتگوهای بات-مشترک به پروفایل‌ها ‏(profile_routes)

‏Multiplexing پروفایل را per-credential ‏(توکن بات خود هر پروفایل) یا per-پیشوند-URL انتخاب می‌کند. وقتی چند جامعه یک توکن بات را شریک‌اند — مثلاً یک بات دیسکوردی سرویس‌دهندهٔ چند guild — می‌توانید guild/channel/thread های مشخص را با gateway.profile_routes به پروفایل‌های متفاوت مسیریابی کنید:

yaml
gateway:
  multiplex_profiles: true
  profile_routes:
    # An entire Discord server → one profile
    - name: acme-server
      platform: discord
      guild_id: "1234567890"
      profile: acme

    # One channel in that server → a different profile
    - name: acme-support
      platform: discord
      guild_id: "1234567890"
      chat_id: "9876543210"
      profile: acme-support

    # A Telegram group (no guild concept — chat_id only)
    - name: tg-group
      platform: telegram
      chat_id: "-1001234567890"
      profile: tg-profile

مسیرها specific-ترین-اول تطبیق می‌یابند ‏(thread_id > chat_id > guild_id)، همهٔ فیلدهای اعلام‌شده باید برقرار باشند ‏(AND) و مسیری کلیدخورده-با-کانال thread ها/forum post هایی که والدشان همان کانال است را هم تطبیق می‌دهد. پیام‌هایی که هیچ مسیری نمی‌خورند روی پروفایل پیش‌فرض/فعال می‌مانند. پروفایل مسیریابی‌شده ایزوله‌سازی کامل per-profil ی توضیح داده‌شده بالا را می‌گیرد ‏(config، مهارت‌ها، حافظه، credential ها، namespace ی نشست). مسیریابی روی همهٔ adapter های پلتفرم کار می‌کند نه فقط دیسکورد.

‏profile_routes به gateway.multiplex_profiles: true نیاز دارد؛ با خاموش بودن multiplexing مسیرها نادیده گرفته می‌شوند. اگر مسیر صریحی تطبیق کند ولی پروفایل هدفش نصب نباشد یا خارج multiplex_profile_allowlist باشد، گیت‌وی آن ingress را رد و مسیر و هدف را لاg می‌کند. پروفایل پیش‌فرض را اجرا نمی‌کند. ترافیکی که هیچ مسیری نمی‌خورد رفتار تاریخی پروفایل-پیش‌فرض را نگه می‌دارد.

۳ شروع، توقف یا ری‌استارت همهٔ گیت‌وی‌ها یکجا

CLI فرمان‌های چرخه‌حیات تک-پروفایلی دارد. برای اقدام بین همهٔ پروفایل‌ها آنها را در یک حلقهٔ شل بپیچید. قطعهٔ زیر را در ‏~/.local/bin/hermes-gateways بگذارید و chmod +x کنید:

#!/bin/sh
set -eu

# Add or remove profile names here as you create / delete profiles.
profiles="default coder personal-bot research"

usage() {
  echo "Usage: hermes-gateways {start|stop|restart|status|list}"
}

run_for_profile() {
  profile="$1"
  action="$2"
  if [ "$profile" = "default" ]; then
    hermes gateway "$action"
  else
    hermes -p "$profile" gateway "$action"
  fi
}

action="${1:-}"
case "$action" in
  start|stop|restart|status)
    for profile in $profiles; do
      echo "==> $action $profile"
      run_for_profile "$profile" "$action"
    done
    ;;
  list)
    hermes gateway list
    ;;
  *)
    usage
    exit 2
    ;;
esac

سپس:

hermes-gateways start      # start every configured profile
hermes-gateways stop       # stop every configured profile
hermes-gateways restart    # restart all
hermes-gateways status     # status across all
hermes-gateways list       # delegates to `hermes gateway list`
💡

پروفایل default با ‏hermes gateway <action> ‏(بدون -p) هدف می‌گیرد نه با hermes -p default gateway <action>. wrapper بالا هر دو فرم را هندل می‌کند.

مدیریت یک پروفایل

فرمان‌های میانبری که هر پروفایل نصب می‌کند:

coder gateway run        # foreground (Ctrl-C to stop)
coder gateway start      # start the managed service
coder gateway stop       # stop the managed service
coder gateway restart    # restart
coder gateway status     # status
coder gateway install    # create the LaunchAgent / systemd unit
coder gateway uninstall  # remove the service file

معادل ‏hermes -p coder gateway <action> هستند — مفید وقتی alias ی پروفایل روی PATH نیست یا از داخل اسکریپت به‌صورت داینامیک پروفایل هدف می‌گیرید.

فایل‌های سرویس

هر پروفایل سرویس خودش را با نام یکتا نصب می‌کند پس نصب‌ها هرگز تصادم نمی‌کنند:

پلتفرممسیر
macOS‏~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist
لینوکس‏~/.config/systemd/user/hermes-gateway-<profile>.service

پروفایل پیش‌فرض نام‌های تاریخی را نگه می‌دارد: ai.hermes.gateway.plist / hermes-gateway.service.

دیدن لاگ‌ها

# Default profile
tail -f ~/.hermes/logs/gateway.log
tail -f ~/.hermes/logs/gateway.error.log

# Named profile
tail -f ~/.hermes/profiles/<name>/logs/gateway.log
tail -f ~/.hermes/profiles/<name>/logs/gateway.error.log

استریم همزمان لاگ همهٔ پروفایل‌ها:

tail -f ~/.hermes/logs/gateway.log ~/.hermes/profiles/*/logs/gateway.log

CLI نمایشگر لاg ساختاریافته هم دارد:

hermes logs -f                  # follow default profile
hermes -p coder logs -f         # follow one profile
hermes logs --help              # filters, levels, JSON output

شناسایی چیزی که واقعاً در حال اجراست

hermes profile list             # profiles + model + gateway state
hermes-gateways status          # full status across every profile
launchctl list | grep hermes    # macOS — PIDs and labels
systemctl --user list-units 'hermes-gateway-*'   # Linux — units

ویرایش پیکربندی

هر پروفایل config اش را داخل دایرکتوری خودش نگه می‌دارد:

~/.hermes/profiles/<name>/
├── .env              # API keys, bot tokens (chmod 600)
├── config.yaml       # model, provider, toolsets, gateway settings
└── SOUL.md           # personality / system prompt

پروفایل پیش‌فرض ~/.hermes/ را مستقیم با همین سه فایل استفاده می‌کند.

با هر ویرایشگری یا از طریق CLI:

hermes config set model.model anthropic/claude-sonnet-4    # default profile
coder config set model.model openai/gpt-5                  # named profile

بعد از ویرایش .env یا config.yaml گیت‌وی مربوطه را ری‌استارت کنید:

coder gateway restart
# or, for everything:
hermes-gateways restart

۴ بیدار نگه داشتن host

پروسهٔ گیت‌وی تمام روز می‌تواند اجرا شود ولی سیستم‌عامل هنوز موقع idle تلاش به خواب رفتن می‌کند. دو الگو:

macOS — caffeinate

‏caffeinate داخل macOS ساخته شده و تا وقتی اجراست جلوی خواب را می‌گیرد. بدون نصب.

caffeinate -dis                    # block display, idle, and system sleep
caffeinate -dis -t 28800           # same, auto-exit after 8 hours
caffeinate -i -w $(cat ~/.hermes/gateway.pid) &   # awake while default gateway runs

# Persistent: run in background and forget
nohup caffeinate -dis >/dev/null 2>&1 &
disown

# Inspect / stop
pmset -g assertions | grep -iE 'caffeinate|prevent|user is active'
pkill caffeinate
فلگاثر
-dبلاک خواب display
-iبلاک خواب سیستم روی idle ‏(پیش‌فرض)
-mبلاک خواب دیسک
-sبلاک خواب سیستم ‏(فقط Mac های AC-powered)
-uشبیه‌سازی فعالیت کاربر ‏(جلوی قفل صفحه)
-t Nخروج خودکار بعد از N ثانیه
-w Pخروج وقتی PID ی P خارج شد
⚠️ بستن لید هنوز مک را می‌خواباند

‏caffeinate نمی‌تواند خوابِ سخت‌افزاریِ بستن لید را روی MacBook ها override کند. برای عملکرد با لید بسته تنظیمات Energy Saver / Battery را عوض کنید یا ابزار ثالث به کار ببرید.

لینوکس — systemd-inhibit یا loginctl

# Inhibit suspend while a command runs
systemd-inhibit --what=idle:sleep --who=hermes --why="gateways running" \
  sleep infinity &

# Allow user services to keep running after logout (recommended)
sudo loginctl enable-linger "$USER"

بعد از فعال کردن lingering یونیت‌های کاربری systemd تان ‏(شامل hermes-gateway-<profile>.service) قطع شدن SSH و ری‌بوت‌ها را عبور می‌کنند.

ایمنی تعارض توکن

هر پروفایل باید توکن‌های بات یکتا برای هر پلتفرم مصرف کند. اگر دو پروفایل یک توکن تلگرام، دیسکورد، اسلک، واتساپ یا سیگنال را شریک شوند گیت‌وی دوم با خطایی نام‌برندهٔ پروفایل متعارض امتناع از شروع می‌کند.

بررسی:

grep -H 'TELEGRAM_BOT_TOKEN\|DISCORD_BOT_TOKEN' \
     ~/.hermes/.env ~/.hermes/profiles/*/.env

به‌روزرسانی کد

‏hermes update آخرین کد را یک بار pull و مهارت‌های bundled جدید را به هر پروفایل sync می‌کند:

hermes update
hermes-gateways restart

مهارت‌های ویرایش‌شده-توسط-کاربر هرگز بازنویسی نمی‌شوند.

۵ عیب‌یابی

«Could not find service in domain for user gui: 501»

‏hermes gateway start را بعد از hermes gateway stop قبلی اجرا کرده‌اید. stop ی CLI یک launchctl unload کامل انجام می‌دهد که سرویس را از registry ی launchd حذف می‌کند. CLI همین خطای خاص را روی start می‌گیرد و plist را خودکار دوباره load می‌کند ‏(↻ launchd job was unloaded; reloading service definition). سرویس عادی شروع می‌شود. چیزی برای درست کردن نیست.

PID ی کهنه بعد از کرش

اگر گیت‌وی پروفایلی not running نشان دهد ولی پروسه‌ای زنده باشد:

ps -ef | grep "hermes_cli.*-p <profile>"
cat ~/.hermes/profiles/<profile>/gateway.pid
kill -TERM <pid>          # graceful
kill -KILL <pid>          # if that fails after a few seconds
<profile> gateway start

ریست سخت یک سرویس

# macOS
launchctl unload ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist
launchctl load   ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist

# Linux
systemctl --user restart hermes-gateway-<profile>.service

بررسی سلامت

hermes doctor                  # default profile
hermes -p <profile> doctor     # one profile
