خانه/کار با Hermes/دامنهٔ مدیریت‌شده

دامنهٔ مدیریت‌شده ‏(Managed Scope)

دامنهٔ مدیریت‌شده به یک مدیر اجازه می‌دهد خط پایه‌ای از پیکربندی و secrets را push کند که کاربر عادی ‏(غیر-root) نمی‌تواند override کند. برای استقرارهای fleet/سازمانی طراحی شده که IT لازم دارد مثلاً ارائه‌دهندهٔ مدل، URL پایهٔ API مشترک یا ‏security.redact_secrets: true را روی همهٔ کاربران یک ماشین پین کند.

وقتی دامنهٔ مدیریت‌شده حاضر باشد، مقادیری که مشخص می‌کند دقیقاً برای همان کلیدهایی که پین کرده بر ‏~/.hermes/config.yaml و ~/.hermes/.env و حتی محیط شل کاربر می‌چربند. بقیهٔ چیزها کاملاً تحت کنترل کاربر می‌مانند.

📌 فرقش با نصب قفل‌شده توسط مدیر-پکیج

نصبِ مدیریت‌شده-توسط-مدیر-پکیج ‏(توزیع تعریفی / formula) همهٔ جهش‌های config را بلاک و به مدیر پکیج ارجاع می‌دهد. دامنهٔ مدیریت‌شده سازوکار جداگانه‌ای است: به‌جای قفل کردن کل config، مقادیر تغییرناپذیر مشخص را به تفکیک کلید تزریق می‌کند. این دو مستقل‌اند و می‌توانند همزیست باشند.

۱ کجا زندگی می‌کند

دامنهٔ مدیریت‌شده از یک دایرکتوری سطح-سیستم خوانده می‌شود، پیش‌فرض ‏/etc/hermes:

/etc/hermes/
├── config.yaml     # managed config layer (wins over ~/.hermes/config.yaml)
└── .env            # managed env layer (wins over ~/.hermes/.env + shell)

دایرکتوری و فایل‌ها متعلق به root هستند ‏(حالت دایرکتوری ۰۷۵۵، فایل‌ها ۰۶۴۴): برای همه قابل‌خواندن، فقط برای مدیر قابل‌نوشتن. همان مجوز فایل‌سیستم سازوکار اعمال است — کاربر عادی فایل‌های مدیریت‌شده را می‌تواند بخواند ولی نمی‌تواند ویرایششان کند.

هرکدام از دو فایل اختیاری است. نبود دایرکتوری یا فایل مدیریت‌شده صرفاً یعنی «بدون دامنهٔ مدیریت‌شده» و پیکربندی دقیقاً مثل بدون این قابلیت حل می‌شود.

جابه‌جا کردن دایرکتوری

مکان با متغیر محیطی ‏HERMES_MANAGED_DIR قابل‌جابه‌جایی است ‏(برای کانتینرها یا استقرارهای غیر-/etc). این یک پیچ مسیر استقرار/bootstrap است — مثل HERMES_HOME — که توسط همان مدیری که مالک فایل‌های مدیریت‌شده است ست می‌شود. هرمس هرگز آن را در هیچ .env ای ماندگار نمی‌کند.

# Point managed scope at a custom directory (set by IT / the deployment, not the user)
export HERMES_MANAGED_DIR=/opt/org/hermes-policy
⚠️

کاربری که بتواند HERMES_MANAGED_DIR را ست کند می‌تواند دامنهٔ مدیریت‌شده را به دایرکتوری تحت کنترل خودش repoint و از آن عبور کند. در استقرار واقعی این متغیر باید توسط مدیر ثابت شود ‏(مثلاً داخل unit ی سرویس یا image ی کانتینر پخته شود) نه اینکه قابل-ست-توسط-کاربر بماند. hermes doctor دایرکتوری مدیریت‌شدهٔ حل‌شده را گزارش می‌کند تا redirect مرئی باشد.

۲ اولویت

برای کلیدهایی که لایهٔ مدیریت‌شده مشخص می‌کند ترتیب این است ‏(بالاترین برنده):

طبقهconfig.yaml.env
۱‏/etc/hermes/config.yaml ‏(مدیریت‌شده)‏/etc/hermes/.env ‏(مدیریت‌شده)
۲‏~/.hermes/config.yaml ‏(کاربر)‏~/.hermes/.env ‏(کاربر)
۳پیش‌فرض‌های داخلیمحیط شل از-قبل-موجود

ادغام سطح-برگ است: پین کردن model.default بقیهٔ model.* را منجمد نمی‌کند. یک config.yaml ی مدیریت‌شدهٔ:

model:
  default: org/standard-model

مقدار model.default را برای همهٔ کاربران اجباری می‌کند در حالی که model.fallback ‏(و هر کلید دیگر) زیر کنترل کاربر می‌ماند.

📌 یادداشت اولویت

برای کلیدهایی که پین می‌کند دامنهٔ مدیریت‌شده عمداً بر محیط شل هم می‌چربد — وگرنه «مدیریت‌شده» نبود. این تنها جایی است که قاعدهٔ معمول «متغیر محیطی بر config.yaml می‌چربد» معکوس می‌شود و فقط به کلیدهای مشخصی که لایهٔ مدیریت‌شده اعلام می‌کند اعمال می‌شود.

۳ دیدن چه چیزهایی مدیریت‌شده است

hermes config        # shows a header naming the managed source + the pinned keys
hermes doctor        # reports the resolved managed dir + pinned key counts

اگر بخواهید مقدار مدیریت‌شده‌ای را عوض کنید هرمس رد می‌کند و منبع را نام می‌برد:

$ hermes config set model.default my/model
Cannot set 'model.default': it is managed by your administrator
(/etc/hermes/config.yaml) and cannot be changed.

همین برای secrets های مدیریت‌شده هم صادق است — hermes config set / setup مقدار کاربری برای کلید env ی پین‌شده توسط .env ی مدیریت‌شده نمی‌نویسد.

۴ راه‌اندازی دامنهٔ مدیریت‌شده ‏(مدیرها)

sudo mkdir -p /etc/hermes

# Pin some config values for every user on this machine
sudo tee /etc/hermes/config.yaml >/dev/null <<'YAML'
model:
  provider: nous
security:
  redact_secrets: true
YAML

# Optionally pin a shared, non-sensitive env value
sudo tee /etc/hermes/.env >/dev/null <<'ENV'
OPENAI_API_BASE=https://inference.example.com/v1
ENV

sudo chmod 0755 /etc/hermes
sudo chmod 0644 /etc/hermes/config.yaml /etc/hermes/.env

تغییرات از شروع بعدی هرمس مؤثر می‌شوند ‏(فایل مدیریت‌شدهٔ بدفرم بلند لاg و نادیده گرفته می‌شود — هرگز startup را بلاک نمی‌کند ولی مدیر باید hermes doctor را چک کند تا مطمئن شود سیاست اعمال می‌شود).

۵ مدل امنیتی و محدودیت‌ها ‏(v1)

  • اعمال فقط با مجوزهای فایل‌سیستم است. اگر کاربر دسترسی نوشتن به دایرکتوری مدیریت‌شده داشته باشد ‏(یا هرمس را به‌عنوان root اجرا کند) دامنهٔ مدیریت‌شده صرفاً توصیه‌ای است.
  • .env ی مدیریت‌شده world-readable است ‏(۰۶۴۴)، پس هر کاربر محلی می‌تواند secrets ی push‌شده از طریق آن را بخواند. برای مقادیر مشترک غیر-حساس ‏(URL پایهٔ API سازمانی، پیش‌فرض‌های قابلیت‌ها) استفاده کنید نه secrets های بسیار حساس.
  • ابزارهای خود ایجنت از مقدار env ی مدیریت‌شده hard-block نیستند. متغیر محیطی مدیریت‌شده هنگام startup اعمال می‌شود ولی هیچ‌چیز جلوی ایجنت را نمی‌گیرد که داخل شل زیرپروسهٔ خودش مقدار دیگری ست کند. v1 مرز راحتی-مدیریت در برابر یک کاربر عادی است نه sandbox ی غیرقابل‌فرار.

موارد زیر عمداً خارج از دامنهٔ v1 اند و ممکن است بعداً بیایند:

  • مرز سختی که خود ایجنت نتواند از آن عبور کند.
  • محل‌های مدیریت‌شدهٔ native روی macOS و ویندوز ‏(v1 اول-لینوکس/POSIX است).
  • دایرکتوری‌های قطعه drop-in ‏(managed.d/) برای سیاست لایه‌لایه.
  • فایل‌های مدیریت‌شدهٔ امضاشده / دارای بررسی یکپارچگی.
  • تحویل راه‌دور / مدیریت-دستگاه ‏(MDM).
  • مجوزهای محدودتر ‏(scope شده به گروه) برای secrets های مدیریت‌شده.
