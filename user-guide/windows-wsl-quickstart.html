خانه/کار با Hermes/راهنمای ویندوز ‏(WSL2)

راهنمای ویندوز ‏(WSL2)

‏هرمس Agent حالا هم ویندوز native هم WSL2 را پشتیبانی می‌کند. این صفحه مسیر WSL2 را پوشش می‌دهد؛ برای نصب PowerShell ی native بخش اختصاصی راهنمای ویندوز ‏(Native) را ببینید.

کی WSL2 به‌جای native:

  • ترمینال تعبیه‌شدهٔ داشبورد ‏(تب /chat) را می‌خواهید — آن pane به PTY ی POSIX نیاز دارد و فقط-WSL2 است.
  • کار توسعهٔ سنگین-POSIX می‌کنید و می‌خواهید نشست‌های هرمس همان فایل‌سیستم / مسیرهای ابزارهای dev تان را شریک شوند.
  • از قبل محیط WSL2 دارید و نمی‌خواهید نصب دومی نگه دارید.

کی native کافی ‏(یا بهتر) است:

  • چت تعاملی، گیت‌وی ‏(تلگرام/دیسکورد/…)، زمان‌بند cron، ابزار مرورگر، سرورهای MCP و بیشتر قابلیت‌های هرمس natively روی ویندوز اجرا می‌شوند.
  • نمی‌خواهید هربار ارجاع به فایل یا باز کردن URL فکر کنید که کدام سمت مرز WSL↔ویندوز هستید.

در WSL2 عملاً دو کامپیوتر در بازی است: host ی ویندوز شما و یک VM لینوکسی مدیریت‌شده توسط WSL. بیشتر سردرگمی‌ها از این است که مطمئن نیستید در هر لحظه روی کدام هستید. این guide بخش‌هایی از همین دوگانگی را پوشش می‌دهد که مخصوصاً هرمس را درگیر می‌کند: نصب WSL2، رفت‌وآمد فایل‌ها بین ویندوز و لینوکس، شبکه در هر دو جهت و دام‌هایی که مردم واقعاً می‌خورند.

۱ چرا WSL2 ‏(در برابر ویندوز native)

نصب native ی ویندوز مستقیم در ویندوز اجرا می‌شود: ترمینال ویندوزی‌تان ‏(PowerShell، ‏Windows Terminal و…)، مسیرهای فایل‌سیستم ویندوزی ‏(C:\Users\…) و پروسه‌های ویندوزی. هرمس فرمان‌های شل را با Git Bash اجرا می‌کند — روشی که Claude Code و سایر ایجنت‌ها امروز برای ویندوز دارند — شکاف POSIX-vs-Windows را بدون بازنویسی کامل دور می‌زند.

‏WSL2 یک کرنل لینوکس واقعی داخل VM سبک اجرا می‌کند، پس هرمس داخلش عملاً با اجرا روی Ubuntu یکی است. وقتی محیط POSIX واقعی می‌خواهید ارزشمند است: fork، ‏/tmp، ‏UNIX socket ها، معناشناسی سیگنال‌ها، ترمینال‌های PTY-dar، شل‌هایی مثل bash/zsh و ابزارهایی مثل rg/git/ffmpeg که مثل لینوکس رفتار می‌کنند.

پیامدهای عملی WSL2:

  • CLI ی هرمس، گیت‌وی، نشست‌ها، حافظه، مهارت‌ها و runtime های ابزار همگی داخل VM لینوکسی زندگی می‌کنند.
  • برنامه‌های ویندوزی ‏(مرورگرها، اپ‌های native، Chrome با پروفایل وارد‌شده‌تان) بیرون آن هستند.
  • هر بار بخواهید این دو با هم حرف بزنند — شریک کردن فایل، باز کردن URL، کنترل Chrome، زدن به سرور مدل محلی، expose کردن گیت‌وی هرمس به گوشی — از مرزی عبور می‌کنید. همین مرزها موضوع این guide اند.

۲ نصب WSL2 و هرمس

از یک PowerShell ی Admin یا Windows Terminal:

wsl --install

روی ویندوز ۱۰ نسخهٔ ۲۲H2+ تازه یا ویندوز ۱۱ این، کرنل WSL2، قابلیت Virtual Machine Platform و یک توزیع پیش‌فرض Ubuntu را نصب می‌کند. موقع درخواست ری‌بوت کنید. بعد از ری‌بوت Ubuntu باز می‌شود و نام کاربری + رمز لینوکسی می‌پرسد — این یک کاربر لینوکسی جدید است و ربطی به حسابتان ویندوزی ندارد.

تأیید کنید واقعاً روی WSL2 هستید نه WSL1 ی قدیمی:

wsl --list --verbose
# VERSION 2 باید ببینید؛ اگر 1 بود:
wsl --set-version Ubuntu 2
wsl --set-default-version 2

هرمس روی WSL1 قابل‌اعتماد نیست — WSL1 syscall های لینوکس را on-the-fly ترجمه می‌کند و بعضی رفتارها ‏(procfs، سیگنال‌ها، شبکه) از لینوکس واقعی فاصله دارند.

انتخاب توزیع

Ubuntu ‏(LTS) همان است که علیه‌اش تست می‌کنیم. Debian کار می‌کند. Arch و NixOS برای کسانی که می‌خواهندشان کار می‌کنند ولی نصب‌کنندهٔ یک‌خطی سیستم apt ی مشتق-از-Debian فرض می‌کند — آن مسیر را در راهنمای setup ی Nix ببینید.

فعال کردن systemd ‏(توصیه‌شده)

گیت‌وی هرمس ‏(و هر چیز دیگری که می‌خواهید بالا بماند) با systemd راحت‌تر مدیریت می‌شود. روی WSL مدرن یک بار داخل توزیع‌تان فعالش کنید:

sudo tee /etc/wsl.conf >/dev/null <<'EOF'
[boot]
systemd=true

[interop]
enabled=true
appendWindowsPath=true

[automount]
options = "metadata,umask=22,fmask=11"
EOF

سپس از PowerShell:

wsl --shutdown

ترمینال WSL را دوباره باز کنید. ‏ps -p 1 -o comm= باید systemd چاپ کند. گزینهٔ mount ی metadata بالا مهم است — بدون آن فایل‌های /mnt/c/... نمی‌توانند بیت‌های مجوز لینوکسی واقعی ذخیره کنند که چیزهایی مثل chmod +x روی اسکریپت‌های زیر مسیرهای ویندوزی را می‌شکند.

نصب هرمس داخل WSL

وقتی شل WSL2 داشتید:

curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
source ~/.bashrc
hermes

نصب‌کننده WSL2 را لینوکس ساده تلقی می‌کند — هیچ چیز WSL-خاصی لازم نیست. چیدمان کامل را در بخش نصب ببینید.

۳ فایل‌سیستم: عبور از مرز ویندوز ↔ WSL2

این همان بخشی است که بیشترین‌ها را می‌اندازد. دو فایل‌سیستم وجود دارد و اینکه فایل‌ها را کجا می‌گذارید مهم است — برای کارایی، صحت و دید ابزارها.

جهتمسیر داخلمسیری که استفاده می‌کنید
دیسک ویندوز از دید WSLC:\Users\you\Documents/mnt/c/Users/you/Documents
دیسک WSL از دید ویندوز/home/you/code\\wsl$\Ubuntu\home\you\code ‏(یا \\wsl.localhost\Ubuntu\... روی بیلدهای جدید)

هر دو واقعی و کارا هستند ولی یک فایل‌سیستم نیستند — زیر کاپوت با پروتکل شبکهٔ ۹P پل شده‌اند و پیامدهای کارایی و معنایی واقعی دارد.

هرمس و پروژه‌ها را کجا بگذاریم

قاعدهٔ سرانگشتی: همه‌چیزِ لینوکی‌وار داخل فایل‌سیستم لینوکس بماند.

  • نصب هرمس ‏(~/.hermes/) — سمت لینوکس. نصب‌کننده همین کار را می‌کند.
  • مخازن git ای که از WSL رویشان کار می‌کنید — سمت لینوکس ‏(~/code/...، ~/projects/...).
  • مدل‌ها، dataset ها، venv ها — سمت لینوکس.

با رعایت این قاعده می‌گیرید:

  • I/O سریع. عملیات روی /mnt/c/... از ۹P می‌گذرند و ۱۰ تا ۱۰۰ برابر کندتر از ext4 ی native‌اند. ‏git status روی مخزن ۱۰هزارفایلی که زیر ~/code لحظه‌ای حس می‌شود زیر /mnt/c ممکن است +۱۵ ثانیه طول بکشد.
  • مجوزهای درست. بیت‌های مجوز لینوکس روی /mnt/c شبیه‌سازیِ حداقلی‌اند. ssh ی امتناع‌کننده از کلید با «bad permissions» یا chmod +x ی بی‌سروصدا بی‌اثر رایج است.
  • file watcher های قابل‌اعتماد. inotify روی ۹P ناپایدار است — watcher ها ‏(dev server ها، test runner ها) مرتباً تغییرات /mnt/c را از دست می‌دهند.
  • بدون غافلگیری case-sensitivity. مسیرهای ویندوز پیش‌فرض case-insensitive اند؛ لینوکس حساس. پروژه‌هایی که هم Readme.md دارند هم README.md بسته به سمت متفاوت رفتار می‌کنند.

فقط وقتی چیزی را روی /mnt/c بگذارید که واقعاً لازم است سمت ویندوز زندگی کند — مثلاً می‌خواهید از یک اپ GUI ی ویندوزی بازش کنید یا DevTools ی Chrome ی ویندوز cwd ی قابل‌رسید-از-ویندوز می‌خواهد.

رفت‌وآمد فایل‌ها

  • ویندوز ← WSL: راحت‌ترین: Explorer را باز و \\wsl.localhost\Ubuntu را در نوار آدرس بنویسید؛ بعد drag-drop به \home\<you>\... . یا از PowerShell:
    wsl cp /mnt/c/Users/you/Downloads/file.pdf ~/incoming/
  • WSL ← ویندوز: به /mnt/c/Users/<you>/... کپی کنید و فوراً در Explorer ظاهر می‌شود:
    cp ~/reports/output.pdf /mnt/c/Users/you/Desktop/
  • باز کردن فایل WSL در اپ ویندوزی: از explorer.exe یا wslview:
    sudo apt install wslu ‏(یک بار) سپس ‏wslview ~/reports/output.pdf یا ‏explorer.exe .
  • تبدیل مسیر بین دو جهان:
    wslpath -w ~/code/project ← ‏\\wsl.localhost\Ubuntu\home\you\code\project
    wslpath -u 'C:\Users\you' ← ‏/mnt/c/Users/you

Line endings، BOM ها و git

اگر فایل‌ها را سمت ویندوز با ویرایشگر ویندوزی ویرایش کنید ممکن است line ending ی CRLF بگیرند. وقتی bash یا پایتون سمت لینوکس بخواندشان اسکریپت‌ها با bad interpreter: /bin/bash^M می‌شکنند و پایتون ممکن است روی فایل‌های .env ی BOM-dar fail شود. اصلاح، config ی منطقی git داخل WSL است ‏(نه روی ویندوز):

git config --global core.autocrlf input
git config --global core.eol lf

برای فایل‌هایی که قبلاً CRLF دارند:

sudo apt install dos2unix
dos2unix path/to/script.sh

«clone داخل WSL یا روی /mnt/c؟»

داخل WSL. همیشه، مگر دلیل مشخصی داشته باشید. گردش‌کار معمول هرمس ‏(hermes chat، ‏فراخوانی‌های rg روی مخزن، ‏file watcher ها، گیت‌وی پس‌زمینه) روی ~/code/myrepo به‌طور چشمگیر سریع‌تر و قابل‌اعتمادتر از /mnt/c/Users/you/myrepo است.

یک استثنا: پل‌های MCP که باینری‌های ویندوزی launch می‌کنند. اگر chrome-devtools-mcp را از طریق cmd.exe مصرف می‌کنید، ویندوز ممکن است اگر cwd ی هرمس ~ باشد هشدار UNC بدهد. در آن صورت هرمس را از جایی زیر /mnt/c/ شروع کنید تا پروسهٔ ویندوزی cwd ی درایو-دار بگیرد.

۴ شبکه: WSL ↔ ویندوز

‏WSL2 داخل VM سبکی با stack ی شبکه خودش اجرا می‌شود. یعنی localhost داخل WSL همان localhost روی ویندوز نیست — از دید شبکه دو host جدایند. برای هر سرویس باید تصمیم بگیرید ترافیک چه جهتی دارد و پل درست را بردارید. دو مورد مدام تکرار می‌شود:

حالت ۱ — هرمس در WSL با سرویسی روی ویندوز حرف می‌زند

رایج‌ترین: ‏Ollama، ‏LM Studio یا llama-server را روی ویندوز اجرا دارید و هرمس ‏(داخل WSL) باید به آن بخورد. راهنمای مرجع در راهنمای ارائه‌دهنده‌ها: WSL2 Networking for Local Models ←. خلاصه:

  • ویندوز ۱۱ ۲۲H2+: حالت mirrored networking را روشن کنید ‏(networkingMode=mirrored در %USERPROFILE%\.wslconfig سپس wsl --shutdown). localhost بعداً در هر دو جهت کار می‌کند.
  • ویندوز ۱۰ یا بیلدهای قدیمی‌تر: IP ی host ی ویندوز ‏(default gateway ی شبکهٔ مجازی WSL) را به کار ببرید و مطمئن شوید سرور روی ویندوز به 0.0.0.0 bind شده نه فقط 127.0.0.1. ‏Windows Firewall هم معمولاً قانونی برای پورت می‌خواهد.

حالت ۲ — چیزی روی ویندوز ‏(یا LAN) با هرمس در WSL حرف می‌زند

جهت معکوس، کمتر مستند، اما برای اینها لازم است:

  • استفاده از داشبورد وب هرمس از مرورگر ویندوزی.
  • استفاده از سرور API سازگار-با-OpenAI ‏(expose‌شده توسط hermes gateway وقتی API_SERVER_ENABLED=true) از ابزاری سمت-ویندوز. صفحهٔ سرور API را ببینید.
  • تست گیت‌وی پیام‌رسانی که پلتفرم به URL ی وب‌هوک محلی ping بزند — معمولاً cloudflared/ngrok بهتر از port forwarding خام است.

ذیل ۲a — از خود host ی ویندوز: روی ویندوز ۱۱ ۲۲H2+ با mirrored mode هیچ کاری لازم نیست؛ پروسه‌ای در WSL که به 0.0.0.0:8080 ‏(یا حتی 127.0.0.1:8080) bind شده از مرورگر ویندوزی در http://localhost:8080 reachable است. روی NAT mode، localhost forwarding پیش‌فرض WSL2 معمولاً bind های 127.0.0.1 سمت-لینوکس را به localhost ی ویندوز forward می‌کند. اگر نشد: صریحاً داخل WSL به 0.0.0.0 bind کنید یا با ip -4 addr show eth0 | grep inet مقدار IP ی VM را پیدا و از ویندوز به همان بزنید.

ذیل ۲b — از دستگاه دیگری روی LAN ‏(گوشی، تبلت، PC دیگر): درد اصلی اینجاست. ترافیک جریان دارد LAN ← host ی ویندوز ← VM ی WSL و هر دو hop را باید ست کنید:

  1. داخل WSL روی همهٔ interface ها bind کنید. شنوندهٔ 127.0.0.1 هرگز از بیرون VM قابل‌رسید نیست. 0.0.0.0 را به کار ببرید.
  2. Port-forward از ویندوز به VM: در mirrored خودکار است؛ در NAT دستی per-port در PowerShell ی Admin: 
    # Grab the WSL VM's current IP (it changes on every WSL restart under NAT)
$wslIp = (wsl hostname -I).Trim().Split(' ')[0]

# Forward Windows port 8080 → WSL:8080
netsh interface portproxy add v4tov4 `
  listenaddress=0.0.0.0 listenport=8080 `
  connectaddress=$wslIp connectport=8080

# Allow it through Windows Firewall
New-NetFirewallRule -DisplayName "Hermes WSL 8080" `
  -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow
    حذف بعدی با netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8080.
  3. دستگاه LAN را به http://<windows-lan-ip>:8080 اشاره دهید.

چون IP ی VM ی WSL در NAT mode با هر ری‌استارت جابه‌جا می‌شود قانون یک‌باره فقط تا wsl --shutdown بعدی دوام دارد. برای چیز پایدار یا mirrored mode را به کار ببرید یا مرحلهٔ port-proxy را در اسکریپتی که موقع ورود ویندوز اجرا می‌شود بگذارید. برای وب‌هوک‌های ارائه‌دهندگان پیام‌رسانی ابری ‏(setWebhook تلگرام و…) با port-forwarding نجنگید — tunnel های cloudflared را به کار ببرید؛ بخش وب‌هوک‌ها را ببینید.

۵ اجرای بلندمدت سرویس‌های هرمس روی ویندوز

Shortcut ی دسکتاپ برای باز کردن سریع هرمس

  1. روی دسکتاپ ویندوز راست‌کلیک ← New ← Shortcut.
  2. برای Target ‏(نام توزیع را در صورت نیاز عوض کنید):
    wt.exe -w 0 -p "Ubuntu" wsl.exe -d Ubuntu --cd ~ -- bash -ic "hermes"
  3. نامی واضح مثل Hermes بگذارید.

این Windows Terminal را باز، توزیع WSL را شروع، شما را به خانهٔ لینوکسی‌تان می‌برد و هرمس را launch می‌کند. اگر hermes هنوز روی PATH نیست یک بار دستی WSL را باز و source ~/.bashrc را بزنید یا فرمان را به uv run hermes داخل checkout ی پروژه تغییر دهید. جلا دادن اختیاری: آیکن سفارشی از Properties ← Change Icon، و pin کردن به Start یا Taskbar.

داخل WSL با systemd ‏(توصیه‌شده)

اگر systemd را طبق بخش راه‌اندازی بالا فعال کرده باشید hermes gateway و سرور API مثل هر ماشین لینوکسی کار می‌کنند. ویزارد:

hermes gateway setup

پیشنهاد نصب unit ی کاربری systemd را می‌دهد تا گیت‌وی موقع شروع WSL خودکار بالا بیاید.

شروع شدن خود WSL موقع ورود به ویندوز

VM ی WSL فقط تا وقتی کسی استفاده‌اش کند زنده می‌ماند. برای اینکه گیت‌وی بدون ترمینال باز قابل‌رسید بماند، موقع ورود ویندوز یک پروسهٔ WSL را با Task Scheduler boot کنید:

  • Trigger: At log on ‏(کاربر شما).
  • Action: Start a program — Program: ‏C:\Windows\System32\wsl.exe · Arguments: ‏-d Ubuntu --exec /bin/sh -c "sleep infinity"

این VM را زنده نگه می‌دارد تا گیت‌وی مدیریت‌شده-توسط-systemd در حال اجرا بماند. روی ویندوز ۱۱ جریان‌های جدیدتر wsl --install --no-launch + auto-start هم کار می‌کنند؛ ترفند sleep infinity نسخهٔ قابل‌حمل است.

Passthrough ی GPU ‏(مدل‌های محلی)

‏WSL2 از کرنل ۵٫۱۰٫۴۳+ به بالا GPU های NVIDIA را natively پشتیبانی می‌کند — درایور استاندارد NVIDIA را روی ویندوز نصب کنید ‏(نه درایور NVIDIA ی لینوکسی داخل WSL) و nvidia-smi داخل WSL GPU را می‌بیند. از آنجا CUDA toolkit ها، ‏torch، ‏vllm، ‏sglang و llama-server مثل همیشه علیه GPU ی واقعی build می‌شوند. پشتیبانی AMD ROCm و Intel Arc داخل WSL2 هنوز در حال تحول و خارج ماتریس تست هرمس است.

اگر سرور مدل محلی ویندوز-native اجرا می‌کنید ‏(Ollama for Windows، ‏LM Studio) که از قبل از طریق درایورهای ویندوز GPU تان را مصرف می‌کند اصلاً به passthrough نیازی ندارید — حالت ۱ بالا را دنبال و از WSL از طریق شبکه به آن بزنید.

۶ دام‌های رایج

  • «Connection refused» به Ollama / LM Studio ی میزبانی-ویندوز. بخش شبکهٔ WSL2 را ببینید. نود درصد مواقع سرور روی 127.0.0.1 bind است و 0.0.0.0 می‌خواهد ‏(Ollama: ‏OLLAMA_HOST=0.0.0.0) یا قانون فایروال جامانده.
  • کندی شدید git status / hermes chat روی یک مخزن. احتمالاً زیر /mnt/c/... کار می‌کنید. مخزن را به ~/code/... ‏(سمت لینوکس) منتقل کنید. مرتبه بزرگی سریع‌تر.
  • bad interpreter: /bin/bash^M روی اسکریپت‌ها. ‏line ending ی CRLF از ویرایشگر ویندوزی. dos2unix script.sh و core.autocrlf input در git config ی WSL.
  • هشدار «UNC paths are not supported» از باینری‌های ویندوزی launch‌شده توسط MCP. cwd ی هرمس داخل فایل‌سیستم لینوکس است و cmd.exe ی ویندوز نمی‌داند با آن چه کند. برای آن نشست هرمس را از /mnt/c/... شروع کنید یا wrapper ای به کار ببرید که قبل از invoke کردن executable ی ویندوزی cd به مسیر قابل‌رسید-از-ویندوز کند.
  • انحراف ساعت بعد از sleep/hibernate. ساعت WSL2 بعد از resume میزبان می‌تواند چند دقیقه عقب بماند و هر چیز گواهی-محوری ‏(OAuth، ‏API های HTTPS) را بشکند. اصلاح on-demand:
    sudo hwclock -s
    یا ntpdate نصب و در ورود اجرایش کنید.
  • DNS بعد از فعال کردن mirrored mode یا اتصال VPN از کار می‌افتد. mirrored تنظیمات شبکهٔ host را به WSL proxy می‌کند — اگر DNS ی ویندوز عجیب باشد ‏(VPN split-tunnel، ‏resolver سازمانی) WSL همان را به ارث می‌برد. دور زدن: resolv.conf را دستی override کنید ‏(generateResolvConf=false در /etc/wsl.conf سپس /etc/resolv.conf ی خودتان با 1.1.1.1 یا DNS ی VPN).
  • hermes بعد از نصب‌کننده پیدا نمی‌شود. نصب‌کننده ~/.local/bin را از طریق ~/.bashrc به PATH شل اضافه کرده. برای نشست فعلی source ~/.bashrc لازم است ‏(یا ترمینال جدید).
  • Windows Defender روی فایل‌های WSL کند است. Defender فایل‌ها را از طریق پل ۹P اسکن می‌کند وقتی از ویندوز access شوند که کندی دسترسی‌های cross-boundary از نوع /mnt/c را بزرگنمایی می‌کند. اگر فقط از داخل WSL فایل‌های WSL را لمس می‌کنید بی‌اهمیت است. اگر ابزارهای ویندوزی مدام به \\wsl$\... می‌زنند مسیر توزیع WSL را از اسکن real-time مستثنا کنید.
  • کم آوردن دیسک. ‏WSL2 دیسک VM اش را به‌صورت VHDX ی sparse زیر %LOCALAPPDATA%\Packages\... نگه می‌دارد؛ با delete کردن فایل‌ها auto-shrink نمی‌شود. بازپس‌گیری: ‏wsl --shutdown سپس از PowerShell ی Admin ‏Optimize-VHD -Path <path-to-ext4.vhdx> -Mode Full ‏(نیازمند ابزارهای Hyper-V) — یا مسیر ساده‌تر diskpart ی مستند در docs ی WSL.

قدم بعدی

  • نصب — مراحل واقعی نصب ‏(Linux/WSL2/Termux همه از یک نصب‌کننده).
  • یکپارچه‌سازی‌ها ← ارائه‌دهنده‌ها ← شبکهٔ WSL2 — عمق‌کاوی مرجعِ شبکه برای سرورهای مدل محلی.
  • راهنمای MCP ← WSL ← Chrome ی ویندوز — کنترل Chrome ی وارد‌شدهٔ ویندوزی‌تان از هرمس در WSL.
  • Tool Gateway و ‏داشبورد وب — سرویس‌های بلندمدتی که بیشترین تمایل را دارید از WSL به بقیهٔ شبکه expose کنید.
