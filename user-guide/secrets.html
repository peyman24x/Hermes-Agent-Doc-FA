رمزها ‏(Secrets)

هرمس می‌تواند کلیدهای API را موقع شروع پروسه از مدیران رمز بیرونی بکشد به‌جای ذخیره‌شان در ‏~/.hermes/.env. توکن bootstrap ی مدیر رمز در .env زندگی می‌کند؛ هر کلید ارائه‌دهندهٔ دیگر ‏(OpenAI، ‏Anthropic، ‏OpenRouter و…) می‌تواند داخل مدیر بماند و به‌صورت متمرکز rotate شود.

۱ منبع‌های پشتیبانی‌شده

  • Bitwarden Secrets Manager — CLI ی ‏bws، lazy-install، تیر رایگان کافی است.
  • 1Password — ارجاع‌های ‏op:// از طریق CLI ی رسمی op؛ احراز هویت service-account یا نشست دسکتاپ.
  • Command helper — هر گاوصندوق CLI ‏(keepassxc-cli، ‏secret-tool، ‏pass، اسکریپت‌های سفارشی) از طریق یک helper ی پیکربندی-توسط-کاربر که خطوط KEY=VALUE چاپ می‌کند.

۲ چند منبع هم‌زمان

می‌توانید بیش از یک منبع رمز را همزمان فعال کنید — مثلاً پروژهٔ Bitwarden تیمی کنار پلاگین گاوصندوق شخصی. منبع‌ها per-env-var با یک نردبان اولویت قطعی ترکیب می‌شوند:

  1. .env / شل شما پیش‌فرض برنده است. منبع فقط وقتی مقدار از-قبل-موجود را جایگزین می‌کند که ‏override_existing: true خودش ست باشد ‏(Bitwarden پیش‌فرض true دارد تا چرخش متمرکز کار کند).
  2. منبع‌های نگاشتی بر منبع‌های انبوه می‌چربند. منبعی که صریحاً متغیرهای env را به ارجاع‌ها bind کرده ‏(یک نقشهٔ env:) از منبعی که یک پروژهٔ کامل از secrets را ضمنی تزریق می‌کند رتبه بالاتر دارد فارغ از ترتیب.
  3. اولین منبع برنده است. درون همان شکل، ترتیب فهرست اختیاری ‏secrets.sources ‏(یا ترتیب ثبت) تصمیم می‌گیرد. ادعاهای بعدی روی متغیری که قبلاً ادعا شده skip می‌شوند — با هشدار startup، هرگز بی‌سروصدا.

‏override_existing هرگز اجازه نمی‌دهد یک منبع متغیری را که منبع دیگری قبلاً تصاحب کرده بازنویسی کند و هیچ منبعی نمی‌تواند توکن bootstrap ی منبع دیگری ‏(مثل BWS_ACCESS_TOKEN) را بازنویسی کند.

yaml
secrets:
  sources: [bitwarden]     # optional explicit ordering
  bitwarden:
    enabled: true
    project_id: "..."

هر credential ی تزریق‌شده توسط یک منبع با منشأ اش برچسب می‌خورد — جریان‌های setup و ‏hermes model کنار کلیدهای آشکار‌شده عبارت ‏(from Bitwarden) نشان می‌دهند تا همیشه بدانید هر مقدار از کجا آمده.

۳ پروفایل‌ها و گاوصندوق‌های مشترک

دو پیچ سطح-orchestrator یک گاوصندوق مشترک را برای پروفایل‌ها امن می‌کنند:

  • ‏secrets.preserve_existing — فهرستی از نام متغیرهای env که مقدار موجود .env/شل‌شان همیشه برنده است حتی در برابر منبعی با ‏override_existing: true. برای secrets پلتفرمی per-profil ‏(مثل FEISHU_APP_SECRET) استفاده‌اش کنید که عمداً بین پروفایل‌ها فرق دارند در حالی که بقیه متمرکز rotate می‌شوند:
    yaml
    secrets:
  preserve_existing: [FEISHU_APP_SECRET, TELEGRAM_BOT_TOKEN]
  • نام‌مستعار پروفایل ‏(پیش‌فرض روشن؛ ‏secrets.profile_alias: false برای خاموشی) — وقتی هرمس زیر پروفایلی نام‌دار اجرا شود، secret گاوصندوقی به نام FOO_<PROFILE> ‏(تنها پسوندهای credential-گونه: *_API_KEY، ‏*_TOKEN، ‏*_SECRET، ‏*_KEY، ‏*_PASSWORD) مقدار FOO ی مرجع را هم hydrate می‌کند. ‏TELEGRAM_BOT_TOKEN_MILLA را در پروژهٔ مشترک ذخیره کنید و adapter های پروفایل milla — که نام ثابت TELEGRAM_BOT_TOKEN را می‌خوانند — خودکار مقدار درست را می‌گیرند. متغیری که گاوصندوق مستقیماً تحت نام مرجعش تأمین کند همیشه بر نام‌مستعار می‌چربد.

هر دو روی همهٔ منبع‌ها اعمال می‌شوند — داخلی و پلاگینی — چون در orchestrator زندگی می‌کنند نه بک‌اندها.

۴ افزودن بک‌اند اختصاصی

مدیران رمز ثالث به‌صورت پلاگین مستقل ارسال می‌شوند نه PR به هسته. یک بک‌اند از ‏agent.secret_sources.base.SecretSource ارث می‌برد ‏(یک متد الزامی: ‏fetch(cfg, home_path) -> FetchResult) و در register(ctx) ی پلاگین با ‏ctx.register_secret_source(MySource()) ثبت می‌شود. orchestrator مالک اولویت، هندل تعارض، ‏timeout ها و provenance است — منبع شما فقط fetch می‌کند. راهنمای کامل همراه قواعد قرارداد، helper ی امنیت-زیرپروسه و کیت تطابق: بخش ساخت پلاگین منبع رمز.

مجموعهٔ داخلی عمداً بسته است ‏(همان سیاست ارائه‌دهندگان حافظه): Bitwarden و 1Password داخل مخزن ارسال می‌شوند. بقیه — ‏Infisical، ‏Proton Pass، ‏HashiCorp Vault، ‏AWS Secrets Manager، keystores سیستم‌عامل — جای‌شان مخازن پلاگین است؛ آنها را در دیسکورد Nous Research ‏(#plugins-skills-and-skins) به اشتراک بگذارید.
