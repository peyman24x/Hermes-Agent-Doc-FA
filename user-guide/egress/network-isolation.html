خانه/کار با Hermes/جداسازی شبکه

جداسازی ترافیک خروجی شبکه برای استقرارهای Docker

هنگام اجرای Hermes در Docker، تنظیم پیش‌فرض network_mode: host به فرایند ایجنت دسترسی نامحدود به ترافیک خروجی شبکه می‌دهد. این راهنما نشان می‌دهد چگونه ترافیک را تفکیک کنید تا هستهٔ ایجنت فقط به سرویس‌های موردنیازش دسترسی داشته باشد و اتصال‌های خروجی دلخواه مسدود شوند.

هدف اصلی این کار، دفاع در برابر حملات تزریق پرامپت است که می‌کوشند از طریق فرمان‌های شل تولیدشده توسط ابزارها، داده‌ها را با curl، wget یا درخواست‌های مستقیم HTTP به بیرون نشت دهند.

۱ مدل تهدید

بخش ۲ از فایل SECURITY.md در پروژهٔ Hermes، مدل اعتماد را تعریف می‌کند. بک‌اند ترمینال، مرز اصلی اجرای کد است. بااین‌حال، هنگام اجرا با network_mode: host، هر فرمانی که ایجنت اجرا کند می‌تواند به هر نقطهٔ پایانی در شبکه، از جمله مقصدهای بیرونی، دسترسی داشته باشد.

جداسازی ترافیک خروجی شبکه لایهٔ دومی اضافه می‌کند: حتی اگر فرمانی مخرب داخل کانتینر اجرا شود، نمی‌تواند به نقاط پایانی خارج از مجموعه‌ای که صریحاً در فهرست مجاز آمده است دسترسی پیدا کند.

└──────────────────────────────────────────────┘

دو شبکهٔ Docker داریم:

  • internal — بدون مسیر پیش‌فرض و بدون دسترسی به اینترنت. ایجنت، داشبورد و دروازه در این شبکه اجرا می‌شوند.
  • egress — دارای دسترسی به اینترنت. فقط سرویس‌هایی که باید به APIهای بیرونی دسترسی داشته باشند به این شبکه متصل می‌شوند.

سرویس دروازه به هر دو شبکه متصل است (dual-homed) تا بتواند پیام‌های ورودی را از تلگرام، اسلک و سایر پلتفرم‌ها دریافت کند و به ایجنت در شبکهٔ داخلی بفرستد.

۳ پیکربندی Compose

تنظیمات پیش‌فرض docker-compose.yml را با یک فایل docker-compose.override.yml بازنویسی کنید:

# docker-compose.override.yml
# Network egress isolation for production deployments.
#
# Usage:
#   HERMES_UID=$(id -u) HERMES_GID=$(id -g) docker compose up -d
#
# This overrides network_mode: host with isolated Docker networks.

networks:
  internal:
    driver: bridge
    internal: true          # no default route, no internet
  egress:
    driver: bridge

services:
  gateway:
    network_mode: ""        # clear the host-mode default
    networks:
      - internal
      - egress              # needs outbound for Telegram, LLM APIs
    ports:
      - "127.0.0.1:9119:9119"   # dashboard proxy, localhost only

  dashboard:
    network_mode: ""
    networks:
      - internal            # internal only, no egress needed

همراه با پروکسی خروجی (پیشنهادی)

برای کنترل دقیق‌تر، تمام ترافیک خروجی را از یک پروکسی HTTP با فهرست مجاز صریح عبور دهید:

# docker-compose.override.yml (with egress proxy)

networks:
  internal:
    driver: bridge
    internal: true
  egress:
    driver: bridge

services:
  gateway:
    network_mode: ""
    networks:
      - internal
      - egress
    environment:
      - HTTP_PROXY=http://egress-proxy:3128
      - HTTPS_PROXY=http://egress-proxy:3128
      - NO_PROXY=hermes,hermes-dashboard,localhost

  dashboard:
    network_mode: ""
    networks:
      - internal

  egress-proxy:
    image: ubuntu/squid:6.10-24.04_edge
    networks:
      - egress
    volumes:
      - ./config/squid-allowlist.conf:/etc/squid/conf.d/allowlist.conf:ro
    restart: unless-stopped

نمونهٔ فایل config/squid-allowlist.conf:

# Only allow HTTPS CONNECT to these hosts
acl allowed_hosts dstdomain api.openai.com
acl allowed_hosts dstdomain api.anthropic.com
acl allowed_hosts dstdomain openrouter.ai
acl allowed_hosts dstdomain generativelanguage.googleapis.com
acl allowed_hosts dstdomain api.telegram.org
acl allowed_hosts dstdomain api.github.com
acl allowed_hosts dstdomain discord.com

http_access allow CONNECT allowed_hosts
http_access deny all

فهرست مجاز را متناسب با ارائه‌دهندهٔ مدل زبانی بزرگ و پلتفرم پیام‌رسان خود تنظیم کنید.

۴ اعتبارسنجی پیکربندی

پس از راه‌اندازی مجموعهٔ سرویس‌ها، جداسازی را بررسی کنید:

# From the agent container: this should FAIL (no egress)
docker compose exec gateway \
  curl -sf --max-time 5 https://example.com && echo "FAIL: egress not blocked" || echo "OK: egress blocked"

# From the agent container: this should SUCCEED (internal network)
docker compose exec gateway \
  curl -sf --max-time 5 http://hermes-dashboard:9119/health && echo "OK: internal reachable" || echo "FAIL"

# If using egress proxy: this should SUCCEED (allowlisted)
docker compose exec gateway \
  curl -sf --max-time 5 --proxy http://egress-proxy:3128 https://api.openai.com/v1/models && echo "OK" || echo "FAIL"

۵ محدودیت‌ها

یادداشت مترجم — محدودیت نمونه‌های منبع: در پیکربندی‌های بالا، سرویس gateway مستقیماً به شبکهٔ دارای دسترسی اینترنت متصل است. تنظیم HTTP_PROXY و HTTPS_PROXY به‌تنهایی استفاده از پروکسی را برای همهٔ برنامه‌ها اجباری نمی‌کند؛ بنابراین این نمونه‌ها تضمین مسدودبودن تمام اتصال‌های خارج از فهرست مجاز نیستند. همچنین بازبودن پرس‌وجوهای DNS را نباید تضمینی برای جلوگیری از نشت داده دانست. نمونه‌های کد و توضیح منبع در ادامه بدون تغییر محتوایی حفظ شده‌اند.

  • تفکیک نام با DNS: شبکهٔ internal همچنان می‌تواند نام‌های DNS بیرونی را تفکیک کند، مگر اینکه یک سرویس محلی تفکیک نام DNS نیز اجرا کنید که پرس‌وجوهای بیرونی را مسدود کند. طبق متن اصلی، این وضعیت برای بیشتر مدل‌های تهدید پذیرفتنی است، زیرا تفکیک نام DNS به‌تنهایی دادهٔ معناداری را به بیرون نشت نمی‌دهد.
  • جایگزین بک‌اندهای سندباکس نیست: این راهنما شبکهٔ کانتینر ایجنت را جدا می‌کند. اگر از بک‌اند پیش‌فرض ترمینال محلی استفاده کنید، فرمان‌های ابزارها داخل همان کانتینر اجرا می‌شوند. برای جداسازی قوی‌تر، تفکیک شبکه را با یک بک‌اند ترمینال سندباکس‌شده (Docker، Modal یا Daytona) ترکیب کنید.
  • آداپتورهای پلتفرم به دسترسی خروجی نیاز دارند: سرویس دروازه برای دسترسی به APIهای پلتفرم‌های پیام‌رسان به اتصال خروجی نیاز دارد. اگر آداپتور پلتفرم جدیدی اضافه می‌کنید، نقاط پایانی API آن را به فهرست مجاز پروکسی بیفزایید.
