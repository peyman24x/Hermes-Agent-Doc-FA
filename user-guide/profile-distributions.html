توزیع پروفایل: به اشتراک گذاشتن یک ایجنت کامل

یک توزیع پروفایل یک ایجنت کامل هرمس — شخصیت، مهارت‌ها، cron job ها، اتصالات MCP، پیکربندی — را به‌عنوان یک مخزن git بسته‌بندی می‌کند. هرکس دسترسی به مخزن دارد کل ایجنت را با یک فرمان نصب، درجا به‌روزرسانی و حافظه‌ها، نشست‌ها و کلیدهای API خودش را دست‌نخورده نگه می‌دارد.

اگر پروفایل یک ایجنت محلی است، توزیع همان ایجنتِ قابل-اشتراک‌شده است.

۱ دو راه اشتراک یک پروفایل

هرمس دو مسیر اشتراک دارد که به دو سؤال متفاوت جواب می‌دهند. توزیع ماندگار است؛ فایل export سریع.

توزیع ‏(مخزن git)فایل export ‏(.tar.gz)
ارسال با‏hermes profile install <repo>فرستادن فایل — چت، ‏AirDrop، ‏USB، ایمیل
گیرنده لازم داردgit و دسترسی به مخزنفایل
به‌روزرسانی‏hermes profile update نسخهٔ جدید pull می‌کنددوباره فایل را بفرستید
نسخه‌بندیtag ها، branch ها، SHA ی commitهیچ — اسنپ‌شاتی در زمان
هزینهٔ راه‌اندازی برای نویسنده‏distribution.yaml + .gitignore + مخزنهیچ — یک فرمان
حمل می‌کندSOUL، config، مهارت‌ها، cron، ‏MCP، پلاگین‌هاهمان‌ها به‌علاوه تم و چیدمان دسکتاپ
ساخته‌شده با‏hermes profile install / ‏update‏/export و /import یا hermes profile export / import

وقتی ایجنت محصولی است که مدام بهترش می‌کنید و دیگران باید دنبال کنند توزیع را بردارید: ایجنت داخلی بازبینی‌شدهٔ تیم، انتشار عمومی جامعه، همان ایجنت مستقر روی پنج ماشین.

وقتی فقط همین الان می‌خواهید کسی setup تان را داشته باشد یا دارید لپ‌تاپ عوض می‌کنید فایل export. نه مخزن نه manifest — در چت /export بزنید، فایل را بدهید، او /import بزند. بخش export/import پایین را ببینید.

این دو انحصاری نیستند. خیلی از نویسنده‌ها پروفایلی را dogfood کرده، برای نظر دوم /export به همکار می‌دهند و وقتی ارزش نسخه‌بندی پیدا کرد به‌صورت توزیع منتشرش می‌کنند.

این یعنی چه

قبل از توزیع‌ها، اشتراک یک ایجنت هرمس یعنی فرستادن:

  1. ‏SOUL.md شما
  2. فهرست مهارت‌هایی که باید نصب شود
  3. config.yaml تان منهای secrets
  4. توضیح اینکه کدام سرورهای MCP را سیم‌کشی کرده بودید
  5. cron job های زمان‌بندی‌شده
  6. دستورالعمل اینکه کدام متغیرهای env ست شوند

…و امید که گیرنده درست سرهم کند. هر ارتقای نسخه یا رفع باگ یعنی تکرار همین تحویل.

با توزیع‌ها همهٔ آن داخل یک مخزن git زندگی می‌کند:

my-research-agent/
├── distribution.yaml    # manifest: name, version, env-var requirements
├── SOUL.md              # the agent's personality / system prompt
├── config.yaml          # model, temperature, reasoning, tool defaults
├── skills/              # bundled skills that come with the agent
├── cron/                # scheduled tasks the agent runs
└── mcp.json             # MCP servers the agent connects to

گیرنده‌ها اجرا می‌کنند:

hermes profile install github.com/you/my-research-agent --alias

…و حالا کل ایجنت را دارند. کلیدهای API خودشان را پر می‌کنند ‏(.env.EXAMPLE ← .env) و می‌توانند my-research-agent chat را اجرا یا از طریق تلگرام/دیسکورد/اسلک/هر پلتفرم گیت‌وی صدا بزنند. شما نسخه جدید push کنید، آنها hermes profile update my-research-agent را اجرا و تغییرات را pull کنند — حافظه‌ها و نشست‌هایشان سر جایشان می‌ماند.

چرا git؟

  • صفر مرحله build برای نویسنده. Push به GitHub؛ مصرف‌کننده نصب می‌کند. هیچ حلقهٔ «این را pack کن، آن را آپلود کن، ایندکس را به‌روز کن» وجود ندارد.
  • tag ها، branch ها و commit ها از قبل سیستم نسخه‌بندی‌اند. push ی tag برای ما کاری می‌کند که «pack + upload ی release» برای ابزارهای دیگر می‌کند.
  • به‌روزرسانی یک fetch است نه دانلود دوبارهٔ کل آرشیو.
  • شفاف. کاربر مخزن را مرور، diff بین نسخه‌ها را می‌خواند، issue باز و fork می‌کند تا سفارشی‌اش کند.
  • مخازن خصوصی مجانی کار می‌کنند. کلیدهای SSH، ‏helper های git credential، ‏credential های ذخیره‌شدهٔ GitHub CLI — هر auth ی که ترمینالتان از قبل بلد است شفاف اعمال می‌شود.
  • بازتولیدپذیری یک SHA ی commit است — همان چیزی که pip و npm ثبت می‌کنند.

معامله: گیرنده‌ها git لازم دارند. روی هر ماشینی که در ۲۰۲۶ هرمس اجرا می‌کند از قبل برقرار است.

چه وقت توزیع مناسب است

  • ایجنت تخصصی‌تان را به اشتراک می‌گذارید — مانیتور انطباق، بازبین کد، دستیار پژوهش، بات پشتیبانی مشتری — با تیم یا جامعه.
  • همان ایجنت را روی چند ماشین مستقر می‌کنید و نمی‌خواهید هر بار دستی فایل کپی کنید.
  • روی ایجنتی iterate می‌کنید و می‌خواهید گیرنده‌ها با یک فرمان نسخه جدید بگیرند.
  • ایجنت را به‌عنوان محصول می‌سازید — پیش‌فرض‌های موضع‌دار، مهارت‌های منتخب، پرامپت‌های تنظیم‌شده — که دیگران نقطهٔ شروعشان کنند.

مناسب نیست:

  • می‌خواهید همین الان یک بار setup را تحویل دهید. توزیع مخزن، manifest و .gitignore می‌خواهد؛ /export هیچ‌کدام را نه — بخش فایل export را ببینید. پشتیبان‌گیری یا انتقال پروفایل به ماشین جدید هم همین‌طور.
  • می‌خواهید تم و چیدمان دسکتاپ‌تان را share کنید. توزیع خود ایجنت را حمل می‌کند؛ export ی که از اپ دسکتاپ گرفته شود ظاهر را هم حمل می‌کند: skin، ‏حالت روشن/تیره، تم‌های سفارشی، رنگ rail و چیدمان window.
  • می‌خواهید کلیدهای API را همراه ایجنت share کنید. ‏auth.json و .env عمداً از توزیع‌ها مستثنی‌اند؛ هر نصب‌کننده credential های خودش را می‌آورد. ‏(فایل‌های export هم حذفشان می‌کنند.)
  • می‌خواهید حافظه‌ها / نشست‌ها / تاریخچهٔ گفتگو را share کنید. آن‌ها دادهٔ کاربرند نه محتوای توزیع. هرگز shipped نمی‌شوند ‏(فایل‌های export اینجا فرق دارند — قبل از فرستادن بخش محتوای فایل export را بخوانید).
⚠️ هرمس کنترلی روی git ندارد

استثناهای فایلی این صفحه توسط نصب‌کننده موقع اجرای hermes profile install یا update اعمال می‌شوند، نه هنگام git add یا git commit شما.

۲ برای نویسنده‌ها: انتشار توزیع

گام ۱ — از یک پروفایل کارا شروع کنید

hermes profile create research-bot
research-bot setup                    # configure model, API keys
# Edit ~/.hermes/profiles/research-bot/SOUL.md
# Install skills, wire up MCP servers, schedule cron jobs, etc.
research-bot chat                     # dogfood until it feels right

گام ۲ — distribution.yaml اضافه کنید

در ~/.hermes/profiles/research-bot/distribution.yaml بسازید:

name: research-bot
version: 1.0.0
description: "Autonomous research assistant with arXiv and web tools"
hermes_requires: ">=0.12.0"
author: "Your Name"
license: "MIT"

# Tell installers which env vars the agent needs. These are checked against
# the installer's shell and existing .env file so they don't get nagged
# about keys they already have configured.
env_requires:
  - name: OPENAI_API_KEY
    description: "OpenAI API key (for model access)"
    required: true
  - name: SERPAPI_KEY
    description: "SerpAPI key for web search"
    required: false
    default: ""

کل manifest همین است. هر فیلدی جز name پیش‌فرض منطقی دارد.

گام ۳ — قبل از اولین commit مقدار .gitignore بسازید

⚠️

این را قبل از git init یا git add انجام دهید. اگر قبلاً با پروفایل گفتگو کرده، setup اجرا کرده یا استفاده‌اش کرده باشید دایرکتوری الان فایل‌هایی دارد که نباید ship شوند: .env، ‏auth.json، ‏memories/، ‏sessions/، ‏state.db*، ‏logs/ و بیشتر.

.gitignore با حداقل این‌ها بسازید:

# Runtime databases & state

# Caches & generated artifacts

آینهٔ مسیرهای hard-excluded است که نصب‌کننده سمت خودش حذف می‌کند. هر چیز دیگری که نمی‌خواهید وارد مخزن شود ‏(فایل‌های scratch، ‏asset های بزرگ، مهارت‌های فقط-محلی) هم باید اینجا بیاید.

گام ۴ — push به مخزن git

cd ~/.hermes/profiles/research-bot
git init
git add .
git commit -m "v1.0.0"
git remote add origin git@github.com:you/research-bot.git
git tag v1.0.0
git push -u origin main --tags

مخزن حالا یک توزیع است. هرکس دسترسی دارد نصبش می‌کند.

📌

نصب‌کننده به‌علاوه مسیرهای hard-excluded را حتی اگر نویسنده به طریقی ship کرده باشد حذف می‌کند — ولی آن فقط نصب‌کننده‌ها را حفظ می‌کند نه نویسنده را.

گام ۵ — tag کردن release های نسخه‌دار

هر بار ایجنت به نقطهٔ پایدار رسید نسخه را bump و tag کنید:

# Edit distribution.yaml: version: 1.1.0
git add distribution.yaml SOUL.md skills/
git commit -m "v1.1.0: tighter research SOUL, add arxiv skill"
git tag v1.1.0
git push --tags

گیرنده‌هایی که hermes profile update research-bot را اجرا کنند آخرین را pull می‌کنند.

مالکیت توزیع در برابر کاربر

موقع update بعضی چیزها جایگزین ‏(دامنهٔ نویسنده) و بعضی سر جایشان می‌مانند ‏(دامنهٔ نصب‌کننده). پیش‌فرض‌ها:

دستهمسیرهاروی update
متعلق-به-توزیع‏SOUL.md، config.yaml، mcp.json، skills/، cron/، distribution.yamlاز clone ی جدید جایگزین می‌شود
Override ی configconfig.yamlدر واقع پیش‌فرض حفظ می‌شود — نصب‌کننده ممکن است مدل یا ارائه‌دهنده را تنظیم کرده باشد. برای reset روی update مقدار --force-config را پاس دهید.
متعلق-به-کاربرmemories/، sessions/، state.db*، auth.json، .env، logs/، workspace/، plans/، home/، *_cache/، local/هرگز لمس نمی‌شود

فهرست متعلق-به-توزیع را در manifest بازنویسی کنید:

distribution_owned:
  - SOUL.md
  - skills/research/            # only my research skills; other installed skills stay
  - cron/digest.json

بدون آن، پیش‌فرض‌های بالا اعمال می‌شوند — همان چیزی که بیشتر توزیع‌ها می‌خواهند.

۳ برای نصب‌کننده‌ها: استفاده از توزیع

نصب

hermes profile install github.com/you/research-bot --alias

چه اتفاقی می‌افتد:

  1. مخزن را داخل دایرکتوری temp کلون می‌کند.
  2. distribution.yaml را می‌خواند و manifest را نشان می‌دهد ‏(name، version، description، author، env var های لازم).
  3. هر env var الزامی را علیه شل شما و .env ی موجود پروفایل هدف بررسی. هرکدام را ✓ set یا needs setting علامت می‌زند تا دقیقاً بدانید چه چیزی را پیکربندی کنید.
  4. تأیید می‌خواهد. با ‎-y‎ / --yes رد شوید.
  5. فایل‌های متعلق-به-توزیع را به ~/.hermes/profiles/research-bot/ ‏(یا جایی که name ی manifest حل شود) کپی می‌کند. مسیرهای hard-excluded حین همین کپی حتی اگر نویسنده تصادفی در مخزن گذاشته باشد حذف می‌شوند.
  6. .env.EXAMPLE را با کلیدهای لازم کامنت‌شده می‌نویسد — به .env کپی و پر کنید.
  7. با --alias wrapper ای می‌سازد تا مستقیم research-bot chat اجرا کنید.

انواع منبع

# GitHub shorthand
hermes profile install github.com/you/research-bot

# Full HTTPS
hermes profile install https://github.com/you/research-bot.git

# SSH
hermes profile install git@github.com:you/research-bot.git

# Self-hosted, GitLab, Gitea, Forgejo — any Git host
hermes profile install https://git.example.com/team/research-bot.git

# Private repo using your configured git auth
hermes profile install git@github.com:your-org/internal-bot.git

# Local directory during development (no git push needed)
hermes profile install ~/my-profile-in-progress/

بازنویسی نام پروفایل

# Alice
hermes profile install github.com/acme/support-bot --name support-us --alias
# Bob (same distribution, different local name)
hermes profile install github.com/acme/support-bot --name support-eu --alias

پر کردن env var ها

بعد از نصب پروفایل یک .env.EXAMPLE دارد؛ به .env کپی و مقادیر واقعی را بگذارید. کلیدهای الزامی که از قبل در شل‌تان بودند موقع نصب ✓ set علامت خورده‌اند و نیازی به تکرار در .env نیست.

بررسی چیزی که نصب کردید

hermes profile info research-bot

توزیع، نسخه، توضیح، نویسنده، نیازمندی هرمس، منبع، زمان نصب و فهرست متغیرهای env با وضعیت الزامی/اختیاری را نشان می‌دهد. ‏hermes profile list هم ستون Distribution دارد تا یک‌نگاهی ببینید کدام پروفایل‌هایتان از مخزن آمده‌اند و کدام دستی ساخته شده‌اند.

به‌روزرسانی

hermes profile update research-bot
  1. مخزن را از URL ی منبع ثبت‌شده دوباره کلون می‌کند.
  2. فایل‌های متعلق-به-توزیع ‏(SOUL، مهارت‌ها، cron، mcp.json) را جایگزین می‌کند.
  3. config.yaml تان را حفظ می‌کند — شاید مدل یا دما یا تنظیمات دیگر را تنظیم کرده باشید. برای بازنویسی --force-config.
  4. دادهٔ کاربر — حافظه‌ها، نشست‌ها، auth، ‏.env، لاگ‌ها، وضعیت — را هرگز لمس نمی‌کند.

بدون دانلود دوبارهٔ کل آرشیو، بدون له کردن تغییرات محلی config، بدون حذف تاریخچهٔ گفتگو.

حذف

hermes profile delete research-bot

پرامپت حذف قبل از تأیید اطلاعات توزیع را نشان می‌دهد: مسیر، مدل، تعداد مهارت‌ها، توزیع و منبع نصب؛ سپس فهرست آنچه برای همیشه حذف خواهد شد ‏(config، کلیدها، حافظه‌ها، نشست‌ها، مهارت‌ها، cron ها، alias ی فرمان) و از شما می‌خواهد برای تأیید نام پروفایل را تایپ کنید. پس هرگز بدون دانستن منشأ و توان نصب دوباره، ایجنتی را تصادفی حذف نمی‌کنید.

۴ موارد استفاده و الگوها

شخصی: sync یک ایجنت بین ماشین‌ها

# Laptop — create .gitignore first, then:
cd ~/.hermes/profiles/research-bot
git init && git add . && git status   # confirm no secrets staged
git commit -m "initial"
git remote add origin git@github.com:you/research-bot.git
git push -u origin main

# Workstation
hermes profile install github.com/you/research-bot --alias
# Fill in .env. Done.

هر iterate روی لپ‌تاپ با ‏commit && push روی workstation با hermes profile update research-bot می‌آید. حافظه‌ها per-machine می‌مانند — لپ‌تاپ گفتگوهای خودش را یادش می‌ماند workstation هم مال خودش را؛ تصادم نمی‌کنند.

تیم: انتشار ایجنت داخلی بازبینی‌شده

تیم مهندسی بات بازبینی PR مشترکی با SOUL مشخص، مهارت‌های مشخص و cron ی که هر PR را از آن عبور می‌دهد wants. سرپرست می‌سازد، tag و به Git host داخلی شرکت push می‌کند؛ هر مهندس ‏hermes profile install git@github.com:your-org/pr-reviewer.git --alias را اجرا، .env را با کلید خودش ‏(صورتحساب برای خودش) پر و pr-reviewer chat را اجرا می‌کند. سرپرست v1.1 بفرستد همه ظرف چند دقیقه با hermes profile update pr-reviewer روی نسخه جدید هستند.

جامعه: انتشار ایجنت عمومی

چیز نوآورانه‌ای ساختید — معامله‌گر Polymarket، خلاصه‌ساز مقالات دانشگاهی، دستیار ops ی سرور Minecraft — و می‌خواهید share کنید. README ی محکم در ریشهٔ مخزن بنویسید ‏(گوگل آن را صفحهٔ مخزن نشان می‌دهد)، tag و به مخزن عمومی push کنید؛ هرکس با hermes profile install github.com/you/hermes-polymarket-trader --alias نصب می‌کند. فرمان نصب را توییت کنید؛ امتحان‌کننده‌ها issue و PR می‌فرستند. کسی خواست سفارشی کند fork می‌کند — همان گردش‌کار git آشنای همه.

محصول: انتشار ایجنت موضع‌دار

هرمس-روی-هرمس ساختید — بستر مانیتورینگ انطباق، پشتهٔ پشتیبانی مشتری، پلتفرم پژوهشی دامنه‌خاص — و می‌خواهید به‌عنوان محصول توزیعش کنید. manifest با license تجاری، ‏env_requires ی مستند و پیش‌فرض‌ها می‌نویسید؛ مشتریان با یک فرمان نصب می‌کنند، پیش‌نمایش نصب دقیقاً می‌گوید کدام کلیدها آماده باشند، به‌روزرسانی‌ها لحظهٔ tag شدن rollout می‌شوند و دادهٔ انطباق مشتریان ‏(memories/، sessions/) هرگز ماشینشان را ترک نمی‌کند.

Zودگذر: اسکریپت‌های یک‌باره روی زیرساخت مشترک

سرپرست ops هستید و ایجنت موقتی برای تشخیص یک incident ی production می‌خواهید — SOUL ی کنسرو با ابزارها و اتصالات MCP درست — که یک هفته روی لپ‌تاپ سه مهندس on-call اجرا شود. پروفایل را بسازید به مخزن خصوصی push؛ هر on-call ‏profile install با --alias اجرا می‌کند؛ incident حل شد؟ ‏hermes profile delete incident-2026-q2. چرخهٔ نصب-حذف آنقدر ارزان است که disposable می‌شود.

۵ دستورالعمل‌ها

پین کردن به نسخهٔ مشخص

📌

پین کردن git ref ‏(#v1.2.0) برنامه‌ریزی شده ولی در انتشار اولیه نیست — نصب فعلی default branch را دنبال می‌کند. نسخهٔ نصب‌شده را با hermes profile info <name> ردیابی و تا آماده نشدید update نکنید.

مقایسه نسخهٔ نصب‌شده با آخرین

# Your installed version
hermes profile info research-bot | grep Version

# Latest upstream (without installing)
git ls-remote --tags https://github.com/you/research-bot | tail -5

حفظ سفارشی‌سازی‌های محلی config در طول update

رفتار پیش‌فرض update همین را انجام می‌دهد: config.yaml حفظ می‌شود. برای اطمینان تیون‌های محلی را در فایلی بنویسید که توزیع مالکش نیست:

# ~/.hermes/profiles/research-bot/local/my-overrides.yaml
# (distribution never touches local/)

…و در صورت نیاز از داخل config.yaml یا SOUL تان به آن ارجاع دهید.

نصب مجدد تمیز اجباری

# Nuke and re-install from scratch (loses memories/sessions too)
hermes profile delete research-bot --yes
hermes profile install github.com/you/research-bot --alias

# Update to current main but reset config.yaml to the distribution's default
hermes profile update research-bot --force-config --yes

Fork و سفارشی‌سازی

گردش‌کار استاندارد git — توزیع‌ها فقط مخزن‌اند: روی گیت‌هاب fork، فورک خودتان را نصب، محلیاً iterate کنید ‏(ویرایش SOUL.md، ‏commit، ‏push به فورک) و تغییرات بالادستی را به روش همیشگی به فورکتان pull کنید.

تست توزیع قبل از push

از ماشین نویسنده، از یک دایرکتوری محلی بدون git push نصب کنید ‏(hermes profile install ~/.hermes/profiles/research-bot --name research-bot-test --alias)، تیرکمانی tweak/delete/install تا درست شود.

۶ export و import ی فایل پروفایل

وقتی نسخه‌بندی نمی‌خواهید مخزن را skip کنید. ‏/export پروفایل را در یک tar.gz. ی واحد pack و /import آن را سر راه دیگر به‌عنوان پروفایل جدید باز می‌کند. credential ها حین خروج حذف می‌شوند.

Export

در CLI، TUI یا چت دسکتاپ:

/export                          # the active profile → <name>.tar.gz
/export research-bot             # a named profile
/export research-bot -o ~/Desktop/research-bot.tar.gz

یا از شل با همان ساز‌وکار:

hermes profile export research-bot
hermes profile export research-bot -o ./research-bot.tar.gz

در اپ دسکتاپ سه در هست که همه به دیالوگ ذخیره native می‌رسند: ⌘K ← Export profile…؛ راست‌کلیک روی مربع پروفایل در ریل sidebar ← Export profile…؛ و دکمهٔ import کنار + ی ریل برای جهت معکوس.

export ی دسکتاپ یک فایل اضافه‌تر از CLI دارد: desktop.json حامل skin، حالت روشن/تیره، تعریف تم‌های سفارشی لازم برای skin، رنگ rail پروفایل و چیدمان window شما. به همین دلیل پروفیلی که از دسکتاپ share می‌شود علاوه بر رفتار، ظاهرِ شما هم می‌آید.

Import

/import ~/Downloads/research-bot.tar.gz
/import ~/Downloads/research-bot.tar.gz --name research-bot-2
hermes profile import ./research-bot.tar.gz
hermes profile import ./research-bot.tar.gz --name research-bot-2

نام پروفایل از آرشیو استنباط می‌شود مگر --name پاس دهید. import روی پروفایل موجود رد می‌شود — اول قدیمی را rename یا delete کنید. wrapper ی شل ‏(research-bot ← hermes -p research-bot) وقتی نام با فرمان موجود تصادم نکند ساخته می‌شود.

Import در اپ دسکتاپ overlay ی desktop.json را هم اعمال و شما را در پروفایل جدید روی چت تازه می‌اندازد. Import آرشیو دسکتاپی از CLI مشکلی ندارد — فایل overlay روی دیسک می‌آید و دفعه بعد که آن پروفایل را در دسکتاپ باز کنید اعمال می‌شود.

📌

نمی‌توانید به‌عنوان default وارد کنید — آن نام پروفایل ریشهٔ داخلی است ‏(~/.hermes). مقدار --name something-else را پاس دهید.

فایل export چه دارد

همیشه مستثنی برای هر دو نوع پروفایل: auth.json و .env. کلیدهای API تان هرگز ماشین را ترک نمی‌کنند.

پروفایل پیش‌فرض ‏(~/.hermes) از طریق allow-list export می‌شود — فقط artifact های شناخته‌شدهٔ هرمس، تا فایل بی‌ربطی در خانه‌تان قورت داده نشود: config.yaml، ‏SOUL.md، ‏MEMORY.md، ‏USER.md، ‏todo.json، ‏system_prompt.md، ‏AGENTS.md، ‏CLAUDE.md، ‏.cursorrules، ‏skills/، ‏plugins/، ‏cron/، ‏scripts/، ‏sessions/، ‏memories/، ‏knowledge/، ‏preferences/ و desktop.json اگر دسکتاپ staged کرده باشد.

پروفایل نام‌دار ‏(~/.hermes/profiles/<name>) کل دایرکتوری منهای auth.json/.env را کپی می‌کند. این پهن‌تر است — اگر پروفایل state.db، لاg یا کش داشته باشد داخل آرشیو می‌روند و فایل بزرگ می‌شود.

⚠️ قبل از فرستادن آرشیو را بخوانید

export اسنپ‌شاتی از پروفایل شماست نه release ای منتخب. برخلاف توزیع می‌تواند memories/ و sessions/ و USER.md را شامل شود — و هیچ چیز مهارت‌ها، حافظه‌ها یا شخصیت شما را برای محتوای شخصی نوشته‌شده در آنها اسکن نمی‌کند. credential ها بر اساس نام فایل فیلتر می‌شوند؛ محتوا نه.
قبل از share با دیگری فهرستش کنید:
tar -tzf research-bot.tar.gz | less
اگر تاریخچهٔ گفتگویی دارد که نمی‌خواهید تحویل دهید به‌جایش یک توزیع منتشر کنید — توزیع‌ها هرگز حافظه یا نشست ship نمی‌کنند.

۷ چه چیزهایی هرگز داخل توزیع نیست

نصب‌کننده این مسیرها را حتی اگر نویسنده تصادفی ship کرده باشد hard-exclude می‌کند. هیچ گزینهٔ config ای اجازه override این را نمی‌دهد — گارد امنیتی ناورداییِ تست‌شده-با-رگرسیون است:

  • ‏auth.json — توکن‌های OAuth، credential های پلتفرم
  • ‏.env — کلیدهای API، ‏secrets
  • ‏memories/ — حافظهٔ گفتگو
  • ‏sessions/ — تاریخچهٔ گفتگو
  • ‏state.db، ‏state.db-shm، ‏state.db-wal — متادیتای نشست
  • ‏logs/ — لاگ‌های ایجنت و خطا
  • ‏workspace/ — فایل‌های کاری تولیدشده
  • ‏plans/ — طرح‌های scratch
  • ‏home/ — mount خانهٔ کاربر در backend های Docker
  • ‏*_cache/ — کش‌های تصویر/صدا/سند
  • ‏local/ — namespace ی سفارشی‌سازی رزرو-شده-برای-کاربر

وقتی به‌عنوان نصب‌کننده توزیعی را clone می‌کنید اینها اصلاً داخل دایرکتوری پروفایل‌تان کپی نمی‌شوند. موقع update کپی‌های شما سر جایشان می‌مانند. اگر همان توزیع را روی پنج ماشین نصب کرده باشید پنج مجموعه ایزوله از این داده دارید — یکی per-machine.

⚠️

این استثنا در زمان نصب/update روی ماشین نصب‌کننده اجرا می‌شود. جلوی commit کردن فایل‌های حساس/غیرضروری توسط نویسنده را نمی‌گیرد. نویسنده‌ها باید با .gitignore secrets را خارج از مخزن نگه دارند.

امنیت و اعتماد

توزیع‌های پروفایل پیش‌فرض unsigned اند. شما به این‌ها اعتماد می‌کنید:

  • git host ‏(GitHub/GitLab/…) که بایت‌های pushed توسط نویسنده را سرو کند.
  • نویسنده که SOUL، مهارت‌ها یا cron job های مخرب نفرستد.

cron job های توزیع خودکار زمان‌بندی نمی‌شوند — نصب‌کننده ‏hermes -p <name> cron list را چاپ و شما صریحاً فعالشان می‌کنید. ‏SOUL.md و مهارت‌ها همین که با پروفایل شروع به چت کنید فعال‌اند، پس اگر از کسی نمی‌شناسیدش نصب می‌کنید قبل از اولین اجرا بخوانیدشان.

تشبیه تقریبی: نصب توزیع مثل نصب افزونهٔ مرورگر یا افزونهٔ VS Code است. اصطکاک کم، قدرت بالا، به منبع اعتماد کن. برای توزیع‌های داخلی شرکت از مخزن خصوصی و auth ی عادی git تان استفاده کنید — هیچ چیز جدیدی برای پیکربندی نیست.

نسخه‌های آینده ممکن است امضا، lockfile ‏(.distribution-lock.yaml) با SHA ی commit ی حل‌شده و فلگ --dry-run ی چاپ diff قبل از اعمال update اضافه کنند. فعلاً هیچ‌کدام shipping نیست.

زیر کاپوت

  • ‏install/update/info داخل hermes profile زندگی می‌کنند — نه یک درخت فرمان موازی.
  • قالب manifest ی YAML با schema ی کوچک الزامی ‏(فقط name) است.
  • نصب‌کننده برای کلون از باینری محلی git شما استفاده می‌کند پس هر auth ای که شل‌تان هندل می‌کند شفاف کار می‌کند.
  • بعد از clone مقدار .git/ حذف می‌شود — پروفایل نصب‌شده خودش checkout ی git نیست تا تله‌های «وای، اتفاقی .env ام را وارد تاریخچهٔ git ی توزیع کردم» رخ ندهد.
  • نام‌های پروفایل رزروشده ‏(hermes، test، tmp، root، sudo) موقع نصب رد می‌شوند تا با باینری‌های رایج تصادم نکنند.

جزئیات پیاده‌سازی، رفتار دقیق CLI و همهٔ فلگ‌ها را در مرجع Profile Commands ببینید. مفاهیم پایه در بخش پروفایل‌ها.
