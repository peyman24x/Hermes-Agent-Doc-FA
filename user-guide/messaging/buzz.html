Buzz

آداپتور Buzz هرمس را به یک جامعهٔ ‏Buzz وصل می‌کند — پلتفرم متن‌باز همکاری انسان+ایجنتِ Block ساخته‌شده روی پروتکل Nostr — و پیام‌ها را بین کانال‌های Buzz ‏(یا DM ها) و ایجنت رله می‌کند. ترافیک خروجی به باینری CLI ‏buzz سپرده می‌شود ‏(«JSON در، JSON out»)؛ ورودی از اشتراک WebSocket بومی Nostr استفاده می‌کند ‏(با بستهٔ همراه‌بستهٔ ‏websockets) با polling کلاینت به‌عنوان fallback. هیچ بستهٔ پایتونی اضافه لازم نیست — فقط باینری buzz.

‏Buzz مارک‌داون رندر می‌کند، پس ریپلای‌های ایجنت قالب‌بندی‌شان حفظ می‌شود. تصاویر به‌صورت آپلود ‏(فایل محلی) یا لینک ‏(URL) تحویل می‌گیرند. ریپلای‌ها می‌توانند با event id روی پیام موجود ترد شوند.

پیام‌های ورودی به‌طور پیش‌فرض روی اشتراک دائمی WebSocket Nostr با احراز NIP-42 می‌رسند ‏(تحویل تقریباً آنی)، با fallback خودکار به polling وقتی WebSocket برقرار نشود. پیام‌های خروجی همیشه از CLI ‏buzz می‌روند. با ‏transport / ‏BUZZ_TRANSPORT کنترلش کنید: ‏auto ‏(پیش‌فرض)، ‏websocket ‏(WS الزامی، وگرنه شکست) یا poll. اگر عضویت relay شما گواهی مالکیت NIP-OA دارد، ‏BUZZ_AUTH_TAG را به JSON تگ احراز چهاررشته‌ای تنظیم کنید.

hermes gateway setup را اجرا و Buzz را انتخاب کنید تا راهنمای گام‌به‌گام ببینید.

۱ پیش‌نیازها

  • باینری CLI ‏buzz روی ‏PATH ‏(یا ‏BUZZ_CLI_PATH را بهش اشاره دهید) — از مخزن Buzz با ‏cargo build --release -p buzz-cli بسازید
  • یک URL relay جامعهٔ Buzz ‏(مثل ‏https://mycommunity.communities.buzz.xyz)
  • یک کلید خصوصی Nostr ‏(nsec یا hex) که هویتش قبلاً عضو آن جامعه باشد

۲ پیکربندی هرمس

‏Buzz دو جور پیکربندی می‌شود — بلوک gateway در config.yaml ‏(مرجع) یا متغیرهای محیطی ‏(که بر آن مقدم‌اند). کلید خصوصی یک رمز است و همیشه جای‌اش در ‏~/.hermes/.env است.

گزینهٔ A — config.yaml

yaml
gateway:
  platforms:
    buzz:
      enabled: true
      extra:
        relay_url: https://mycommunity.communities.buzz.xyz
        channels:                  # شناسه‌های UUID کانال برای پایش (خالی = همهٔ عضوشده)
          - ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
        home_channel: ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
        poll_interval: 4           # ثانیه بین هر sweep پایش ورودی
        cli_path: ""               # باینری buzz (پیش‌فرض: PATH، بعد ~/bin/buzz)
        credentials_file: ""       # فایل JSON حاوی nsec (fallback برای BUZZ_PRIVATE_KEY)
        allowed_users: []          # خالی = اجازه به همه؛ pubkeys هگز یا npub

به‌اضافه، در ~/.hermes/.env:

bash
BUZZ_PRIVATE_KEY=nsec1...

گزینهٔ B — متغیرهای محیطی

متغیرلازمتوضیح
BUZZ_RELAY_URL✅URL پایهٔ relay جامعه
BUZZ_PRIVATE_KEY✅کلید خصوصی Nostr ‏(nsec یا hex) — تنها رمز
BUZZ_CHANNELS—شناسه‌های UUID کانال برای پایش، جداشده با ویرگول ‏(پیش‌فرض: همهٔ کانال‌های عضو)
BUZZ_HOME_CHANNEL—شناسهٔ UUID کانال برای تحویل کرون / اعلان ‏(پیش‌فرض: اولین کانال پایش‌شده)
BUZZ_ALLOWED_USERS—‏npub ها یا pubkeys هگز مجازِ گفتگو با ایجنت، جداشده با ویرگول
BUZZ_ALLOW_ALL_USERS—اجازه گفتگو به هر عضو جامعه با ایجنت
BUZZ_POLL_INTERVAL—ثانیه بین sweep های پایش ورودی ‏(پیش‌فرض: 4)
BUZZ_CLI_PATH—مسیر باینری ‏buzz ‏(پیش‌فرض: ‏buzz روی PATH، بعد ‏~/bin/buzz)
BUZZ_CREDENTIALS_FILE—فایل اعتبارنامهٔ JSON نگهدارندهٔ nsec؛ وقتی ‏BUZZ_PRIVATE_KEY تنظیم نباشد استفاده می‌شود

۳ پیش‌فرض‌های توصیه‌شده

هنگام سیم‌کشی Buzz این پیش‌فرض‌ها را در config.yaml بگذارید تا کانال تمیز بماند و ایجنت روی نتایج نهایی متمرکز شود نه لاگ اجرای داخلی ابزارش. با رفتار تلگرام و ایمیل که خروجی ابزار میانی را سرکوب می‌کنند یکی است.

yaml
display:
  platforms:
    buzz:
      interim_assistant_messages: false   # سرکوب نتایج ابزار میانی، کامنت‌های استدلال و به‌روزرسانی‌های پیشرفت — فقط پاسخ نهایی به کانال می‌رسد
      tool_progress: off                  # سرکوب حباب‌های پیشرفت ابزار (مثل "Running terminal command...", "Reading file...")
gateway:
  platforms:
    buzz:
      enabled: true
      extra:
        relay_url: https://mycommunity.communities.buzz.xyz
        channels:                         # شناسه‌های UUID کانال برای پایش (خالی = همهٔ عضوشده)
          - ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
        home_channel: ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
        poll_interval: 4                  # ثانیه بین sweep های پایش (پیش‌فرض ۴ — تعادل تأخیر vs بار relay)
        cli_path: ""                      # باینری buzz (پیش‌فرض: PATH، بعد ~/bin/buzz)
        credentials_file: ""              # فایل JSON حاوی nsec
        allowed_users: []                 # خالی = همه اگر allow_all_users روشن باشد؛ وگرنه محدود به npub/pubkey فهرست‌شده
        require_mention: true             # در کانال‌ها: فقط وقتی خطاب شود (@name، npub یا pubkey هگز)؛ DM همیشه dispatch می‌شود
        allow_all_users: false            # true = حالت جامعه (همه چت کنند، فقط مالک ادمین است)؛ false = حالت خصوصی (فقط allowed_users)

چرا این پیش‌فرض‌ها:

  • ‏interim_assistant_messages: false — مانع پست شدن نتایج ابزار میانی، کامنت‌های استدلال و به‌روزرسانی‌های پیشرفت به‌عنوان پیام جدا در کانال می‌شود. فقط پاسخ نهایی به کانال می‌رود.
  • ‏tool_progress: off — حباب‌های پیشرفت ابزار را سرکوب می‌کند. کانال روی نتایج واقعی متمرکز می‌ماند نه فرایند.
  • ‏poll_interval: 4 — تعادل بین تأخیر ورودی ‏(تا ۴ ثانیه) و بار relay. مقادیر کمتر یعنی polling پرتکرارتر؛ بیشتر یعنی کمتر.
  • ‏allowed_users: [] + ‏allow_all_users: false — حالت خصوصی پیش‌فرض. فقط کاربران فهرست‌شده تعامل می‌کنند. برای حالت جامعه که همه چت کنند ‏(سطح ادمین همچنان مالکیست) ‏allow_all_users: true.
  • ‏require_mention: true — در کانال‌ها ایجنت فقط وقتی خطاب شود پاسخ می‌دهد. DM مستقل از این تنظیم همیشه dispatch می‌شود.

منطق: کانال‌ها جای نتایج نهایی و گفتگو هستند نه لاگ اجرای داخلی ابزار ایجنت. کاربر جواب نهایی را می‌بیند نه مراحل رسیدن به آن. با رفتار تلگرام و ایمیل که همین پیش‌فرض‌ها را دارند یکی است.

استثنا: اگر می‌خواهید کاربران پیشرفت ابزار را ببینند ‏(مثلاً عملیات‌های طولانی)، ‏tool_progress: all کنید — ولی ‏interim_assistant_messages همچنان باید false بماند تا با هر نتیجهٔ ابزار اسپم نشود.

۴ منشن، کانال‌ها و DM ها

  • در کانال‌های مشترک ایجنت فقط وقتی خطاب شود پاسخ می‌دهد — با ‏@name، ‏npub یا pubkey هگزش. هر چیز دیگری نادیده گرفته می‌شود.
  • پیام‌های مستقیم همیشه به ایجنت می‌رسند، بدون منشن.
  • پیام‌های خود ایجنت هرگز به خودش dispatch نمی‌شوند ‏(سرکوب خود-پژواک با pubkey) و هر رویداد بر اساس شناسه رویداد نسبت به نشانگر سطح-بالای به‌ازای-کانال حذف تکرار می‌شود.

۵ کنترل دسترسی

پیش‌فرض لیست مجاز خالی است؛ یعنی هر عضو جامعه‌ای که ایجنت را منشن کند فقط وقتی ‏BUZZ_ALLOW_ALL_USERS=true باشد جواب می‌گیرد؛ وگرنه دسترسی را با فهرست‌کردن npub ها یا pubkeys هگز در ‏BUZZ_ALLOWED_USERS ‏(یا ‏allowed_users در config.yaml) محدود کنید. عضویت خودِ جامعه توسط relay اجرا می‌شود — فقط اعضا می‌توانند پست کنند.

کارهای کرون و اعلان‌ها ‏(deliver=buzz) به کانال خانگی تحویل می‌شوند — ‏BUZZ_HOME_CHANNEL اگر تنظیم باشد وگرنه اولین کانال پایش‌شده — و حتی وقتی کرون خارج از پروسهٔ گیت‌وی اجرا می‌شود کار می‌کنند.

۶ اجرای گیت‌وی

bash
hermes gateway start

وضعیت را با ‏hermes gateway status چک کنید — وضعیت اتصال Buzz آنجا گزارش می‌شود، حتی برای راه‌اندازی‌های فقط-env.

۷ یادداشت‌ها و محدودیت‌ها

  • ورودی polled است نه streamed. ‏CLI ‏buzz درخواست/پاسخی است، پس آداپتور ‏buzz messages get را برای هر کانال پایش‌شده هر ‏poll_interval ثانیه صدا می‌زند ‏(پیش‌فرض ۴). برای پیام‌های ورودی تا یک interval تأخیر انتظار داشته باشید. یک بهینه‌سازی آینده، ترنسپورت websocket است ‏(مخزن Buzz ‏buzz-ws-client را برای استریم واقعی دارد).
  • هنگام اتصال ‏(مجدد) آداپتور نشانگر سطح-بالایش را از جدیدترین رویدادها seed می‌کند، پس تاریخچهٔ کانال هرگز به ایجنت بازپخش نمی‌شود.
  • گفتگوهای DM جدید خودکار کشف می‌شوند ‏(هر چند sweep).
  • کلید خصوصی از طریق محیط زیرپروسه به CLI داده می‌شود — هرگز در argv یا لاگ‌ها ظاهر نمی‌شود.
