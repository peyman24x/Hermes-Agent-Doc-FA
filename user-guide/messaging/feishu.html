راه‌اندازی Feishu / Lark

هرمس ایجنت با Feishu و Lark به‌عنوان یک بات کاملاً امکان‌دار یکپارچه می‌شود. بعد از اتصال می‌توانید در پیام خصوصی یا چت گروهی با ایجنت حرف بزنید، نتایج کارهای کرون را در یک چت خانگی بگیرید و متن، تصویر، صوت و پیوست فایل را از مسیر عادی گیت‌وی بفرستید.

یکپارچه‌سازی هر دو حالت اتصال را پشتیبانی می‌کند:

  • ‏websocket — توصیه‌شده؛ هرمس اتصال خروجی را باز می‌کند و endpoint وب‌هوک عمومی لازم ندارید
  • ‏webhook — وقتی می‌خواهید Feishu/Lark رویدادها را روی HTTP به گیت‌وی‌تان push کند مفید است

۱ رفتار هرمس

زمینهرفتار
پیام خصوصیهرمس به همهٔ پیام‌ها پاسخ می‌دهد.
چت گروهیهرمس فقط وقتی بات در چت @منشن شود پاسخ می‌دهد.
چت گروهی مشترکبه‌طور پیش‌فرض تاریخچهٔ نشست داخل یک چت مشترک به‌ازای هر کاربر ایزوله است.

این رفتار چت-مشترک با config.yaml کنترل می‌شود:

group_sessions_per_user: true

فقط اگر صریحاً یک گفتگوی مشترک به‌ازای هر چت می‌خواهید ‏false کنید.

۲ گام ۱: ساخت اپ Feishu / Lark

توصیه‌شده: ساخت با اسکن QR ‏(یک فرمان)

hermes gateway setup

Feishu / Lark را انتخاب و کد QR را با اپ موبایل Feishu یا Lark اسکن کنید. هرمس خودکار اپلیکیشن بات با دسترسی‌های درست می‌سازد و اعتبارنامه‌ها را ذخیره می‌کند.

روش جایگزین: راه‌اندازی دستی

اگر ساخت با اسکن در دسترس نباشد ویزارد به ورودی دستی برمی‌گردد:

  1. کنسول توسعه‌دهندهٔ Feishu یا Lark را باز کنید:
    • ‏Feishu: ‏https://open.feishu.cn/
    • ‏Lark: ‏https://open.larksuite.com/
  2. اپ جدیدی بسازید.
  3. در ‏Credentials & Basic Info مقدارهای ‏App ID و ‏App Secret را کپی کنید.
  4. قابلیت Bot را برای اپ فعال کنید.
  5. ‏hermes gateway setup را اجرا، ‏Feishu / Lark را انتخاب و هنگام پرسش اعتبارنامه‌ها را وارد کنید.
⚠️ هشدار

رمز اپ را خصوصی نگه دارید. هر کسی با آن می‌تواند خودش را جای اپ شما جا بزند.

پیکربندی دسترسی‌ها

در کنسول توسعه‌دهندهٔ Feishu به ‏Permission Management بروید و scope های زیر را اضافه کنید. در صفحهٔ دسترسی‌ها می‌توانید bulk-import کنید.

دسترسی‌های الزامی:

im:messageدریافت و خواندن پیام‌ها
im:message:send_as_botارسال پیام به‌عنوان بات
im:resourceدسترسی به تصاویر، فایل‌ها و صدای فرستاده‌شدهٔ کاربران
im:chatدسترسی به متادیتای چت/گروه
im:chat:readonlyخواندن فهرست چت‌ها و عضویت

دسترسی‌های توصیه‌شده ‏(برای عملکرد کامل):

Scopeهدف
im:message.reactions:readonlyدریافت رویدادهای واکنش ایموجی

contact:user.id:readonlyحل شناسه‌های کاربر برای تطبیق لیست مجاز

پیکربندی رویدادها

در ‏Events and Callbacks:

  1. حالت اتصال را روی ‏Long Connection (WebSocket) ‏(توصیه‌شده) بگذارید یا URL وب‌هوک را پیکربندی کنید
  2. در بخش ‏Event Configuration مشترک شوید:
    • ‏im.message.receive_v1 — برای دریافت پیام‌ها الزامی

انتشار اپ

بعد از پیکربندی دسترسی‌ها و رویدادها به ‏Version Management بروید و نسخهٔ جدیدی از اپ منتشر کنید. دسترسی‌ها تا انتشار و تأیید یک نسخه اثر نمی‌کنند ‏(برای اپ‌های سازمانی ممکن است تأیید ادمین لازم باشد).

۳ گام ۲: انتخاب حالت اتصال

توصیه‌شده: حالت WebSocket

حالت WebSocket را وقتی هرمس روی لپ‌تاپ، ایستگاه کار یا سرور خصوصی شما اجراست استفاده کنید. بدون نیاز به URL عمومی. SDK رسمی Lark یک اتصال WebSocket خروجی دائمی با اتصال‌مجدد خودکار باز و نگه می‌دارد.

FEISHU_CONNECTION_MODE=websocket

الزامات: بستهٔ پایتونی ‏websockets باید نصب باشد. SDK چرخهٔ حیات اتصال، ضربان‌ها و اتصال‌مجدد خودکار را داخلی هندل می‌کند.

نحوهٔ کار: آداپتور کلاینت WebSocket مربوط به SDK لارک را در یک thread اجرای پس‌زمینه اجرا می‌کند. رویدادهای ورودی ‏(پیام‌ها، واکنش‌ها، اکشن‌های کارت) به حلقهٔ اصلی asyncio dispatch می‌شوند. در قطع، SDK خودش تلاش به اتصال‌مجدد می‌کند.

اختیاری: حالت Webhook

حالت webhook را فقط وقتی استفاده کنید که هرمس را از قبل پشت یک endpoint HTTP قابل‌دسترس اجرا می‌کنید.

FEISHU_CONNECTION_MODE=webhook

در حالت webhook هرمس یک سرور HTTP ‏(با ‏aiohttp) راه می‌اندازد و نقطهٔ پایانی فیشو را سرو می‌کند:

/feishu/webhook

الزامات: بستهٔ پایتونی ‏aiohttp باید نصب باشد.

آدرس bind و مسیر سرور وب‌هوک قابل سفارشی‌سازی است:

bash
FEISHU_WEBHOOK_HOST=127.0.0.1   # پیش‌فرض: 127.0.0.1
FEISHU_WEBHOOK_PORT=8765         # پیش‌فرض: 8765
FEISHU_WEBHOOK_PATH=/feishu/webhook  # پیش‌فرض: /feishu/webhook

وقتی فیشو چالش تأیید URL می‌فرستد ‏(type: url_verification)، وب‌هوک خودکار پاسخ می‌دهد تا setup اشتراک در کنسول توسعه‌دهنده کامل شود. پاسخ چالش وقتی ‏FEISHU_VERIFICATION_TOKEN تنظیم باشد به آن گیت می‌خورد — درخواست‌های چالش با توکن غایب یا نامطابق رد می‌شوند تا یک مقصد راه‌دورِ احرازنشده نتواند کنترل endpoint را با بازتاب دادن دادهٔ چالشِ تحت-کنترل-مهاجم اثبات کند.

۴ گام ۳: پیکربندی هرمس

گزینهٔ A: راه‌اندازی تعاملی

hermes gateway setup

Feishu / Lark را انتخاب و پرسش‌ها را پر کنید.

گزینهٔ B: پیکربندی دستی

این‌ها را به ‏~/.hermes/.env اضافه کنید:

bash
FEISHU_APP_ID=cli_xxx
FEISHU_APP_SECRET=secret_xxx
FEISHU_DOMAIN=feishu
FEISHU_CONNECTION_MODE=websocket

# اختیاری ولی قویاً توصیه‌شده
FEISHU_ALLOWED_USERS=ou_xxx,ou_yyy
FEISHU_HOME_CHANNEL=oc_xxx

‏FEISHU_DOMAIN این‌ها را می‌پذیرد:

  • ‏feishu برای فیشوی چین
  • ‏lark برای لارک بین‌المللی

۵ گام ۴: شروع گیت‌وی

hermes gateway

سپس از داخل Feishu/Lark به بات پیام دهید تا زنده بودن اتصال تأیید شود.

چت خانگی

‏/set-home را در یک چت Feishu/Lark بزنید تا همانجا به‌عنوان کانال خانگیِ نتایج کارهای کرون و اعلان‌های بین-پلتفرمی علامت بخورد.

می‌توانید از قبل هم پیکربندی کنید:

FEISHU_HOME_CHANNEL=oc_xxx

۶ امنیت

لیست مجاز کاربران

برای تولید، لیستی از Open ID های فیشو تنظیم کنید:

FEISHU_ALLOWED_USERS=ou_xxx,ou_yyy

اگر لیست مجاز را خالی بگذارید هر کسی که به بات برسد شاید بتواند استفاده‌اش کند. در چت گروهی لیست مجاز قبل از پردازش پیام علیه ‏open_id فرستنده چک می‌شود.

کلید رمزنگاری وب‌هوک

در حالت webhook برای فعال‌کردن اعتبارسنجی امضای payload های وب‌هوک ورودی کلید رمزنگاری بگذارید:

FEISHU_ENCRYPT_KEY=your-encrypt-key

این کلید در بخش ‏Event Subscriptions پیکربندی اپ فیشو‌تان پیدا می‌شود. با تنظیم شدن آداپتور هر درخواست وب‌هوک را با الگوریتم امضا تأیید می‌کند:

SHA256(timestamp + nonce + encrypt_key + body)

هش محاسبه‌شده با هدر ‏x-lark-signature با مقایسهٔ timing-safe تطبیق می‌یابد. درخواست‌های دارای امضای نامعتبر یا غایب با HTTP 401 رد می‌شوند.

💡 نکته

در حالت WebSocket اعتبارسنجی امضا توسط خود SDK هندل می‌شود، پس ‏FEISHU_ENCRYPT_KEY اختیاری است. در حالت webhook برای تولید قویاً توصیه می‌شود.

توکن تأیید

لایهٔ احراز اضافی که فیلد token داخل payload های وب‌هوک را چک می‌کند:

FEISHU_VERIFICATION_TOKEN=your-verification-token

این توکن هم در بخش Event Subscriptions اپ فیشو‌تان است. با تنظیم شدن هر payload وب‌هوک ورودی باید ‏token منطبقی داخل آبجکت header اش داشته باشد. توکن‌های نامطابق با HTTP 401 رد می‌شوند.

هر دو ‏FEISHU_ENCRYPT_KEY و ‏FEISHU_VERIFICATION_TOKEN را می‌توان با هم برای دفاع چندلایه به کار برد.

۷ سیاست پیام گروهی

متغیر محیطی ‏FEISHU_GROUP_POLICY کنترل می‌کند هرمس در چت‌های گروهی پاسخ بدهد یا نه و چگونه:

FEISHU_GROUP_POLICY=allowlist   # پیش‌فرض
مقداررفتار
openهرمس به منشن‌های هر کاربری در هر گروهی جواب می‌دهد.
allowlistهرمس فقط به منشن‌های کاربران فهرست‌شده در ‏FEISHU_ALLOWED_USERS جواب می‌دهد.
disabledهرمس همهٔ پیام‌های گروهی را کلاً نادیده می‌گیرد.

در همهٔ حالت‌ها بات باید صریحاً در گروه @منشن ‏(یا ‎@all) شود تا پیام پردازش شود. پیام خصوصی همیشه از این گیت می‌گذرد.

‏FEISHU_REQUIRE_MENTION=false را بگذارید تا هرمس کل ترافیک گروه را بدون الزام منشن بخواند:

FEISHU_REQUIRE_MENTION=false

برای کنترل به‌ازای-چت، مقدار ‏require_mention را روی یک ورودی ‏group_rules بگذارید — «کنترل دسترسی به‌ازای-گروه» پایین را ببینید.

هویت بات

هرمس ‏open_id و نام نمایشی بات را هنگام شروع خودکار تشخیص می‌دهد. فقط وقتی تشخیص خودکار به API فیشو نرسد یا اپ‌تان از شناسه‌های کاربر tenant-scoped استفاده کند باید دستی تنظیمشان کنید:

bash
FEISHU_BOT_OPEN_ID=ou_xxx     # فقط وقتی تشخیص خودکار شکست خورد
FEISHU_BOT_USER_ID=xxx        # اگر اپ شما sender_id_type=user_id دارد الزامی است
FEISHU_BOT_NAME=MyBot         # فقط وقتی تشخیص خودکار شکست خورد

۸ پیام‌رسانی بات-به-بات

به‌طور پیش‌فرض هرمس پیام‌های سایر بات‌ها را نادیده می‌گیرد. وقتی می‌خواهید هرمس در هماهنگی A2A شرکت کند یا از بات‌های دیگر همان گروه اعلان بگیرد پیام‌رسانی بات-به-بات را فعال کنید.

FEISHU_ALLOW_BOTS=mentions   # پیش‌فرض: none
مقداررفتار
noneنادیده گرفتن همهٔ پیام‌های سایر بات‌ها ‏(پیش‌فرض).
mentionsفقط وقتی بات همتا هرمس را @منشن کند قبول می‌شود.
allپذیرش همهٔ پیام‌های بات همتا.

به‌صورت ‏feishu.allow_bots در config.yaml هم قابل تنظیم است ‏(با تنظیم هر دو، env برنده است).

بات‌های همتا لازم نیست به ‏FEISHU_ALLOWED_USERS اضافه شوند — آن لیست فقط روی فرستندگان انسان اعمال می‌شود.

برای نمایش نام بات‌های همتا scope ‏application:bot.basic_info:read را بدهید؛ بدون آن بات‌های همتا همچنان درست مسیریابی می‌شوند ولی به‌صورت ‏open_idشان دیده می‌شوند.

۹ اکشن‌های کارت تعاملی

وقتی کاربران روی دکمه‌ها کلیک کنند یا با کارت‌های تعاملی ارسالی بات تعامل کنند، آداپتور این‌ها را به‌عنوان رویداد فرمان مصنوعی ‏/card مسیریابی می‌کند:

  • کلیک دکمه تبدیل می‌شود به: ‏/card button {"key": "value", ...}
  • payload ‏value اکشن از تعریف کارت به‌صورت JSON گنجانده می‌شود.
  • اکشن‌های کارت با پنجرهٔ ۱۵ دقیقه‌ای dedupe می‌شوند تا دوباره پردازش نشوند.

پرامپت‌های به‌روزرسانی محرک-گیت‌وی به‌جای fallback به ریپلای متنی خام از کارت بومی ‏Yes/No فیشو استفاده می‌کنند. وقتی ‏hermes update --gateway تأیید لازم دارد، آداپتور پاسخ انتخابی را در فایل ‏.update_response هرمس ثبت و کارت را درجا با وضعیت حل‌شده جایگزین می‌کند.

رویدادهای اکشن کارت با ‏MessageType.COMMAND dispatch می‌شوند، پس از خط‌لوله عادی پردازش فرمان عبور می‌کنند.

به همین ترتیب تأیید فرمان کار می‌کند — وقتی ایجنت لازم است فرمان خطرناکی اجرا کند، کارت تعاملی با دکمه‌های Allow Once / Session / Always / Deny می‌فرستد. کاربر دکمه‌ای را کلیک می‌کند و callback اکشن کارت تصمیم تأیید را به ایجنت برمی‌گرداند.

پیکربندی الزامی اپ فیشو

کارت‌های تعاملی سه مرحلهٔ پیکربندی در کنسول توسعه‌دهندهٔ فیشو می‌خواهند. جا افتادن هرکدام باعث خطای ۲۰۰۳۴۰ هنگام کلیک کاربر روی دکمه‌های کارت می‌شود.

  1. مشترک‌شدن در رویداد اکشن کارت:
    در ‏Event Subscriptions مقدار ‏card.action.trigger را به رویدادهای مشترک‌شده بیفزایید.
  2. فعال‌سازی قابلیت Interactive Card:
    در ‏App Features > Bot مطمئن شوید کلید ‏Interactive Card روشن است. این به فیشو می‌گوید اپ شما می‌تواند callback های اکشن کارت دریافت کند.
  3. پیکربندی Card Request URL ‏(فقط حالت webhook):
    در ‏App Features > Bot > Message Card Request URL مقدار URL را روی همان endpoint وب‌هوک رویدادتان بگذارید ‏(مثل ‏https://your-server:8765/feishu/webhook). در حالت WebSocket این خودکار توسط SDK هندل می‌شود.
⚠️ هشدار

بدون هر سه مرحله، فیشو کارت‌های تعاملی را موفقانه می‌فرستد ‏(ارسال فقط دسترسی ‏im:message:send می‌خواهد) ولی کلیک روی هر دکمه خطای ۲۰۰۳۴۰ برمی‌گرداند. کارت ظاهراً کار می‌کند — خطا فقط وقتی کاربر با آن تعامل کند سطح پیدا می‌کند.

۱۰ ریپلای هوشمند کامنت اسناد

فراتر از چت، آداپتور می‌تواند به @منشن‌های گذاشته‌شده روی اسناد Feishu/Lark هم جواب دهد. وقتی کاربری روی یک سند کامنت می‌گذارد ‏(انتخاب متن محلی یا کامنت کل-سند) و بات را @منشن می‌کند، هرمس سند به‌اضافهٔ رشتهٔ کامنت اطراف را می‌خواند و ریپلای LLM را درجا روی همان رشته پست می‌کند.

محرک با رویداد ‏drive.notice.comment_add_v1، هندلر:

  • محتوای سند و تایم‌لاین کامنت را موازی می‌گیرد ‏(۲۰ پیام برای رشته‌های کل-سند، ۱۲ برای رشته‌های انتخاب-محلی).
  • ایجنت را با تول‌ست‌های ‏feishu_doc + ‏feishu_drive محدود به همان نشست تک‌کامنت اجرا می‌کند.
  • ریپلای‌ها را در ۴۰۰۰ کاراکتر تکه و به‌عنوان ریپلای‌های تردی پست برمی‌گرداند.
  • نشست‌های به‌ازای-سند را ۱ ساعت با سقف ۵۰ پیام کش می‌کند تا کامنت‌های بعدی روی همان سند زمینه داشته باشند.

کنترل دسترسی سه‌طبقه

ریپلای کامنت-اسند فقط-اعطای-صریح است — هیچ حالت ضمنی allow-all وجود ندارد. دسترسی‌ها به این ترتیب حل می‌شوند ‏(اولین تطبیق برنده است، به‌ازای هر فیلد):

  1. سند دقیق — قیدشده به توکن یک سند مشخص.
  2. Wildcard — قیدی که الگویی از اسناد را تطبیق می‌دهد.
  3. سطح‌بالا — قاعدهٔ پیش‌فرض برای ورک‌اسپیس.

دو سیاست به‌ازای هر قاعده موجود است:

  • ‏allowlist — فهرست ایستای کاربران / tenant ها.
  • ‏pairing — فهرست ایستا ∪ مخزن تأییدشدهٔ runtime. مفید برای rollout هایی که مدیران می‌توانند دسترسی را زنده اعطا کنند.

قواعد در ‏~/.hermes/feishu_comment_rules.json زندگی می‌کنند ‏(اعطاهای pairing در ‏~/.hermes/feishu_comment_pairing.json) با hot-reload کش‌شده با mtime — ویرایش‌ها روی رویداد کامنت بعدی اثر می‌کنند بدون ری‌استارت گیت‌وی.

CLI:

bash
# بازرسی قواعد فعلی و وضعیت pairing
python -m gateway.platforms.feishu_comment_rules status

# شبیه‌سازی چک دسترسی برای سند + کاربر مشخص
python -m gateway.platforms.feishu_comment_rules check <fileType:fileToken> <user_open_id>

# مدیریت اعطاهای pairing در runtime
python -m gateway.platforms.feishu_comment_rules pairing list
python -m gateway.platforms.feishu_comment_rules pairing add <user_open_id>
python -m gateway.platforms.feishu_comment_rules pairing remove <user_open_id>

پیکربندی الزامی اپ فیشو

روی دسترسی‌های چت/کارتی که قبلاً داده شده، رویداد کامنت drive را اضافه کنید:

  • مشترک ‏drive.notice.comment_add_v1 در ‏Event Subscriptions شوید.
  • scope های ‏docs:doc:readonly و ‏drive:drive:readonly را بدهید تا هندلر بتواند محتوای سند را بخواند.

۱۱ رویدادهای دعوت جلسه

می‌توانید بات هرمس Feishu/Lark را مثل دعوت یک شرکت‌کننده انسانی به یک جلسه تصویری دعوت کنید. وقتی بات رویداد دعوت جلسه را بگیرد، هرمس می‌تواند خودکار یک نوبت ایجنت شروع کند که تلاش به پیوستن به جلسه می‌کند.

محرک با رویداد ‏vc.bot.meeting_invited_v1، جریان این است:

  • کاربری بات را به یک جلسه تصویری Feishu/Lark دعوت می‌کند.
  • ‏Feishu/Lark رویداد دعوت جلسه را به هرمس می‌فرستد.
  • هرمس دعوت‌کننده، موضوع جلسه و شماره جلسه را استخراج می‌کند.
  • اگر دعوت‌کننده توسط لیست مجاز عادی گیت‌وی یا سیاست pairing مجاز باشد، ایجنت شماره جلسه را می‌گیرد و تلاش به پیوستن خودکار می‌کند.
  • اگر دعوت بدفرم باشد یا ایجنت نتواند بپیوندد، هرمس رویداد را دور می‌ریزد یا با توضیح موجزی به دعوت‌کننده جواب می‌دهد.

دعوت‌های بدفرمِ بدون هم دعوت‌کننده هم ‏meeting_no نادیده گرفته می‌شوند.

پیکربندی الزامی اپ فیشو

روی دسترسی‌های چت/کارتی قبلاً داده‌شده، رویداد دعوت جلسه تصویری را اضافه کنید:

  • مشترک ‏vc.bot.meeting_invited_v1 در ‏Event Subscriptions شوید.
  • scope دسترسی Video Conferencing را که کنسول توسعه‌دهندهٔ Feishu/Lark برای آن رویداد پیشنهاد می‌دهد فعال کنید.
  • ‏im:message و ‏im:message:send_as_bot را روشن نگه دارید تا هرمس بتواند به دعوت‌کننده جواب دهد.
  • مطمئن شوید لیست مجاز کاربر گیت‌وی یا سیاست pairing دعوت‌کننده را مجاز می‌کند. دعوت‌های جلسه چک‌های دسترسی عادی گیت‌وی را دور نمی‌زنند.

۱۳ رندر مارک‌داون و fallback به Post

وقتی متن خروجی قالب‌بندی مارک‌داون داشته باشد ‏(تیتر، ضخیم، فهرست، بلوک کد، لینک و...)، آداپتور خودکار آن را به‌عنوان پیام post فیشو با تگ ‏md تعبیه‌شده می‌فرستد نه متن خام. این رندر غنی در کلاینت فیشو را ممکن می‌کند.

اگر API فیشو payload پست را رد کند ‏(مثلاً به‌خاطر ساختارهای مارک‌داون پشتیبان‌نشده)، آداپتور خودکار به ارسال متن خام با حذف مارک‌داون برمی‌گردد. این fallback دومرحله‌ای تضمین می‌کند پیام‌ها همیشه تحویل شوند.

پیام‌های متنی خام ‏(مارک‌داون تشخیص‌داده‌نشده) به‌عنوان نوع سادهٔ ‏text فرستاده می‌شوند.

۱۴ واکنش‌های وضعیت پردازش

حین کار ایجنت، بات روی پیام شما واکنش ‏Typing نشان می‌دهد. با رسیدن ریپلای پاک می‌شود یا اگر پردازش شکست بخورد با ‏CrossMark جایگزین می‌شود.

برای خاموشی ‏FEISHU_REACTIONS=false.

۱۶ سقف نرخ ‏(حالت Webhook)

در حالت webhook آداپتور سقف نرخ به‌ازای-IP برای مقابله با سوءاستفاده اجرا می‌کند:

  • پنجره: پنجرهٔ لغزان ۶۰ ثانیه‌ای
  • سقف: ۱۲۰ درخواست به‌ازای پنجره به‌ازای سه‌تایی ‏(app_id، مسیر، IP)
  • سقف ردیابی: تا ۴۰۹۶ کلید یکتا ردیابی می‌شود ‏(جلوگیری از رشد نامحدود حافظه)

درخواست‌های فراتر از سقف HTTP 429 ‏(Too Many Requests) می‌گیرند.

ردیابی ناهنجاری وب‌هوک

آداپتور پاسخ‌های خطای متوالی به‌ازای هر IP را ردیابی می‌کند. بعد از ۲۵ خطای متوالی از یک IP در پنجرهٔ ۶ ساعته، هشدار لاگ می‌شود. کمک می‌کند کلاینت‌های بدپیکربندی یا تلاش‌های probe شناسایی شوند.

محافظت‌های اضافی وب‌هوک:

  • سقف حجم بدنه: حداکثر ۱ مگابایت
  • timeout خواندن بدنه: ۳۰ ثانیه
  • اجبار Content-Type: فقط ‏application/json پذیرفته می‌شود

۱۸ کنترل دسترسی به‌ازای-گروه

فراتر از ‏FEISHU_GROUP_POLICY سراسری، می‌توانید با ‏group_rules در config.yaml قواعد دقیق به‌ازای هر چت گروهی بگذارید:

yaml
platforms:
  feishu:
    extra:
      default_group_policy: "open"     # پیش‌فرض گروه‌های خارج از group_rules
      admins:                          # کاربرانی که می‌توانند تنظیمات بات را مدیریت کنند
        - "ou_admin_open_id"
      group_rules:
        "oc_group_chat_id_1":
          policy: "allowlist"          # open | allowlist | blacklist | admin_only | disabled
          allowlist:
            - "ou_user_open_id_1"
            - "ou_user_open_id_2"
        "oc_group_chat_id_2":
          policy: "admin_only"
        "oc_group_chat_id_3":
          policy: "blacklist"
          blacklist:
            - "ou_blocked_user"
        "oc_free_chat":
          policy: "open"
          require_mention: false       # override FEISHU_REQUIRE_MENTION برای همین چت
سیاستتوضیح
openهر کسی در گروه می‌تواند از بات استفاده کند
allowlistفقط کاربران ‏allowlist گروه حق استفاده دارند
blacklistهمه به‌جز کاربران ‏blacklist گروه حق استفاده دارند
admin_onlyفقط کاربران فهرست سراسری ‏admins در این گروه حق استفاده دارند
disabledبات همهٔ پیام‌های این گروه را نادیده می‌گیرد

‏require_mention: false را روی یک ورودی ‏group_rules بگذارید تا شرط @منشن برای آن چت خاص رد شود. در صورت حذف، چت مقدار سراسری ‏FEISHU_REQUIRE_MENTION را ارث می‌برد.

گروه‌های خارج از ‏group_rules به ‏default_group_policy برمی‌گردند ‏(پیش‌فرض همان مقدار ‏FEISHU_GROUP_POLICY).
