خانه/پیام‌رسان‌ها/واتساپ بیزینس ‏(Cloud API)

راه‌اندازی WhatsApp Business Cloud API

هرمس می‌تواند از طریق رسمی‌ترین مسیر یعنی Cloud API ی WhatsApp Business متا به واتساپ وصل شود. این مسیر درجه-production است: بدون زیرپروسهٔ پُل Node.js، بدون QR کد، بدون ریسک بن شدن حساب.

در عوض:

  • به یک حساب Meta Business نیاز دارید ‏(نه واتساپ شخصی).
  • بات روی یک شماره تلفن بیزینسی اختصاصی کار می‌کند نه شمارهٔ شخصی شما.
  • گیت‌وی هرمس به یک URL ی HTTPS عمومی نیاز دارد تا متا بتواند پیام‌های ورودی را با وب‌هوک تحویل دهد.
  • پاسخ‌های بیش از ۲۴ ساعت بعد از آخرین پیام کاربر به یک قالب پیش-تأییدشده نیاز دارند ‏(این قاعدهٔ «پنجرهٔ خدمات مشتری» متاست نه محدودیت هرمس).

اگر این محدودیت‌ها برای مورد استفاده‌تان جواب نمی‌دهد، یکپارچه‌سازی پل Baileys جایگزین است — حساب شخصی، بدون URL عمومی، ولی غیررسمی و مستعد-بن.

💡 کدام را استفاده کنم؟
  • Cloud API ‏(این راهنما) — یک ربات بیزینسی واقعی اجرا می‌کنید، پایداری می‌خواهید، با کاغذبازی تأیید متا + قالب مشکلی ندارید
  • پل Baileys — پروژه‌های شخصی، دموهای سریع، setup های تک‌کاربره، حاضرید ریسک حسابِ شمارهٔ ربات را بکنید

۱ شروع سریع

hermes whatsapp-cloud

ویزارد شما را از میان هر اعتبارنامه می‌برد، هرکدام را همزمان با paste کردن اعتبارسنجی می‌کند ‏(دام شماره-۱ ی راه‌اندازی را می‌گیرد — چسباندن شماره تلفن در فیلد Phone Number ID) و دستورالعمل دقیق ادامه را برای بخش‌هایی که باید بیرون ویزارد انجام شوند چاپ می‌کند ‏(اجرای cloudflared، پیکربندی داشبورد وب‌هوک متا).

بقیهٔ این صفحه مرجع دستی است.

۲ پیش‌نیازها

  1. حساب Meta Business. در ‏business.facebook.com بسازید.
  2. یک اپ متا با واتساپ فعال. بخش «ساخت اپ متا» پایین را ببینید.
  3. راهی برای expose کردن یک پورت محلی به اینترنت عمومی با HTTPS. ‏Cloudflare Tunnel ‏(cloudflared) توصیه می‌شود — رایگان، بدون port forwarding، بدون نیاز به دامنه. ‏ngrok، دامنهٔ خودتان با reverse proxy + TLS یا VPS ای که گیت‌وی مستقیم روی IP عمومی bind شده همه کار می‌کنند.
  4. اختیاری ولی توصیه‌شده: ffmpeg روی PATH تا پیام‌های صوتی خروجی به‌صورت حباب native ویس‌نوت واتساپ ‏(موج سبز) رندر شوند نه پیوست MP3. هرمس در نبودش با لطف تنزل می‌کند.

۳ ساخت اپ متا

  1. به ‏developers.facebook.com/apps بروید ← Create App.
  2. مورد استفاده را انتخاب کنید: ‏«Connect with customers through WhatsApp» ← Next.
  3. یک business portfolio بردارید یا بسازید. نیازمندی‌های انتشار را مرور کنید. تأیید ← Create app.
  4. بعد از ساخت به ‏Customize use case ← Connect on WhatsApp ← Quickstart می‌رسید. روی ‏Start using the API کلیک کنید ← الان در صفحهٔ ‏API Setup هستید.
  5. مطمئن شوید یک WhatsApp Business Account ‏(WABA) لینک شده. اگر در گام ۳ portfolio جدید ساختید یکی خودکار ساخته شده. در صفحهٔ API Setup تأیید کنید.

این مقادیر را از داشبورد لازم دارید — ویزارد به همین ترتیب می‌پرسد:

۴ توکن دائمی ‏(production)

توکن‌های دسترسی موقت بعد از ۲۴ ساعت منقضی می‌شوند، یعنی توکنی که امروز ساخته شده فردا از کار می‌افتد. برای استقرار production از توکن دائمی System User استفاده کنید:

  1. به ‏business.facebook.com/latest/settings بروید ← System users ‏(sidebar چپ).
  2. Add ← نام ‏(مثلاً hermes-bot) ← نقش: ‏Admin.
  3. کاربر جدید را انتخاب ← Assign Assets:
    • اپ‌تان را انتخاب ← toggle ی Manage app زیر Full control.
    • حساب واتساپ‌تان را انتخاب ← toggle ی Manage WhatsApp Business Accounts زیر Full control.
    • Assign assets را کلیک کنید.
  4. Generate token با این مجوزها:
    • ‏business_management
    • ‏whatsapp_business_messaging
    • ‏whatsapp_business_management
  5. token expiration: Never را ست کنید.
  6. توکن را کپی ← ‏WHATSAPP_CLOUD_ACCESS_TOKEN را در ‏~/.hermes/.env به‌روز کنید ← گیت‌وی را ری‌استارت کنید.

توکن‌های System User مگر اینکه صریحاً revoke شوند منقضی نمی‌شوند.

۵ expose کردن هرمس به اینترنت

Cloud API پیام‌های ورودی را با POST ی HTTPS به URL ی وب‌هوکتان تحویل می‌دهد — یعنی گیت‌وی هرمس باید از سرورهای متا قابل‌رسید باشد. سه راه رایج:

Cloudflare Tunnel ‏(توصیه‌شده)

رایگان، بدون port forwarding، روی Windows / macOS / Linux کار می‌کند. به‌عنوان پروسهٔ جدا کنار گیت‌وی اجرا می‌شود.

نصب:

# Windows
winget install Cloudflare.cloudflared

# macOS
brew install cloudflared

# Linux
# Download the binary from https://github.com/cloudflare/cloudflared/releases

اجرای quick tunnel ‏(بدون نیاز به حساب Cloudflare — یک URL ی ‏https://<random>.trycloudflare.com می‌دهد):

cloudflared tunnel --url http://localhost:8090

URL چاپ‌شده را یادداشت کنید — همان چیزی است که به متا می‌دهید.

⚠️ quick tunnel ها می‌چرخند

URL ی quick-tunnel رایگان هر بار ری‌استارت cloudflared عوض می‌شود. برای URL پایدار با ‏cloudflared tunnel login وارد شوید و tunnel ی نام‌دار بسازید. حساب‌های رایگان Cloudflare tunnel نام‌دار نامحدود می‌گیرند — گردش‌کار named-tunnel را در مستندات Cloudflare ببینید.

ngrok

ngrok http 8090

تیر رایگان در هر ری‌استارت URL متفاوتی نشان می‌دهد. تیر پولی subdomain پایدار می‌دهد.

دامنهٔ خودتان + reverse proxy

اگر از قبل سروری با گواهی TLS دارید ‏(Caddy، ‏nginx و…) یک route را به ‏localhost:8090 اشاره دهید. پایدارترین گزینه برای production است ولی زیرساخت موجود می‌خواهد.

۶ پیکربندی وب‌هوک سمت متا

وقتی tunnel تان اجراست:

  1. URL عمومی چاپ‌شده توسط tunnel را یادداشت کنید — مثلاً ‏https://abc123.trycloudflare.com.
  2. یک Verify Token بسازید — ویزارد این کار را با ‏secrets.token_urlsafe(32) برایتان می‌کند؛ اگر دستی پیکربندی می‌کنید اجرا کنید: 
    python -c "import secrets; print(secrets.token_urlsafe(32))"
    آن را به‌عنوان WHATSAPP_CLOUD_VERIFY_TOKEN در ~/.hermes/.env ذخیره کنید.
  3. گیت‌وی هرمس را شروع کنید: ‏hermes gateway.
  4. در Meta App Dashboard ← WhatsApp ← Configuration ‏(یا Use cases ← Customize ← Configuration بسته به نسخهٔ UI) ← روی Edit بخش Webhook کلیک کنید.
  5. پر کنید:
    • Callback URL: ‏https://abc123.trycloudflare.com/whatsapp/webhook
    • Verify Token: رشتهٔ گام ۲ ‏(باید دقیقاً بخورد)
  6. Verify and save را کلیک کنید. متا با GET به URL تان می‌زند، گیت‌وی challenge را echo می‌کند و متا وب‌هوک را verified علامت می‌زند.
  7. زیر Webhook fields روی Manage کلیک ← به فیلد messages مشترک شوید. همین به متا می‌گوید پیام‌های ورودی را واقعاً به وب‌هوکتان تحویل دهد.

تأیید دستی حلقه ‏(از ترمینال سوم):

TUNNEL="https://abc123.trycloudflare.com"
VERIFY="<your verify token>"

# Should print HTTP 200 with body "hello"
curl -i "$TUNNEL/whatsapp/webhook?hub.mode=subscribe&hub.verify_token=$VERIFY&hub.challenge=hello"

# Health endpoint — should show verify_token_configured: true and app_secret_configured: true
curl "$TUNNEL/health"

۷ whitelist گیرنده ‏(سمت متا) و allowlist ‏(سمت هرمس)

whitelist گیرنده سمت متا

در حالت توسعه ‏(قبل از عبور اپ از App Review)، متا محدود می‌کند ربات به کدام شماره‌ها پیام بدهد:

  1. App Dashboard ← WhatsApp ← API Setup ← dropdown ی To.
  2. روی Manage phone number list کلیک کنید.
  3. شماره‌هایی را که می‌خواهید پیام بدهند اضافه کنید ‏(شما، تیم‌تان، تسترهای دوست). متا به هرکدام یک کد تأیید ۶رقمی با SMS یا واتساپ می‌فرستد.

در حالت dev تا ۵ شماره. رفتن به App Review این محدودیت را برمی‌دارد.

allowlist سمت هرمس

علاوه بر whitelist گیرندهٔ متا، هرمس allowlist ی per-platform ی خودش دارد که کنترل می‌کند کدام پیام‌های ورودی توسط ایجنت پردازش شوند. به ‏~/.hermes/.env اضافه کنید:

# Comma-separated phone numbers, country code, no '+' / spaces / dashes
WHATSAPP_CLOUD_ALLOWED_USERS=15551234567,15557654321

# Or allow everyone (only safe in combination with Meta's recipient whitelist)
# WHATSAPP_CLOUD_ALLOW_ALL_USERS=true

ویزارد این را در گام ۶ ست می‌کند. بدون allowlist هر پیام ورودی رد می‌شود — عمدی است تا ربات اگر روزی whitelist گیرنده شل شود توسط شماره‌های تصادفی invoke نشود.

۸ پراکندن پروفایل واتساپی ربات

‏WhatsApp یک نام و تصویر پروفایل برای رباتتان در header گفتگو و فهرست مخاطبین نمایش می‌دهد. اینها از طریق Cloud API قابل‌تنظیم نیستند — در Business Manager ی متا زندگی می‌کنند.

وقتی رباتتان کار کرد به ‏business.facebook.com/wa/manage/phone-numbers بروید، روی شماره‌تان کلیک کنید و اینها را پیدا می‌کنید:

۱۰ قابلیت‌ها

ورودی

  • پیام‌های متنی — مستقیم به ایجنت پاس داده می‌شوند.
  • تصاویر — خوددانلود و الصاقی به ورودی ایجنت. مدل‌های دارای بینایی native ‏(Claude، ‏GPT-4o، ‏Gemini و…) تصویر را مستقیم می‌خوانند؛ مدل‌های غیر-بینایی توضیح متنی خودتولید دریافت می‌کنند.
  • ویس‌نوت‌ها — به‌صورت .ogg خوددانلود، با ارائه‌دهندهٔ STT پیکربندی‌شده‌تان ‏(faster-whisper محلی، ‏OpenAI/Nous، ‏Groq و…) رونویسی و سپس به‌عنوان متن به ایجنت داده می‌شوند.
  • اسناد — خوددانلود. فایل‌های کوچک قابل-خواندن-متنی ‏(.txt، .md، .json، .py، .csv و…) تا ‎۱۰۰KB‎ داخل ورودی ایجنت inline می‌شوند تا بدون فراخوانی ابزار بخواندشان. فایل‌های بزرگتر محلی کش می‌شوند برای دسترسی سایر ابزارهای ایجنت.
  • tap ی دکمه‌ها — وقتی کاربر روی دکمه‌ای که ربات قبلاً فرستاده tap کند ‏(انتخاب clarify، ‏تأیید فرمان، تأیید دستور اسلش)، tap مستقیم به هندلر درست مسیریابی می‌شود. tap های قدیمی به‌عنوان ورودی متن عادی fallback می‌شوند.
  • زمینهٔ reply — وقتی کاربر به پیام قبلی ربات reply کند، ایجنت پیام اصلی را به‌عنوان زمینه می‌بیند.

خروجی

  • متن — markdown خودکار به نحو flavored ی واتساپ تبدیل می‌شود ‏(**bold** ← ‏*bold*، ‏~~strike~~ ← ‏~strike~، ‏headers ← bold، ‏[link](url) ← link (url)). پیام‌های بلند در chunk های ۴۰۹۶ نویسه‌ای شکسته می‌شوند.
  • تصاویر — تصاویر تولید-ایجنت و فایل‌های تصویری محلی هر دو پشتیبانی و به‌عنوان پیوست عکس native تحویل می‌شوند.
  • پیام‌های صوتی — خروجی TTS با ffmpeg به حباب native ویس‌نوت واتساپ ‏(موج سبز) تبدیل می‌شود. بدون ffmpeg به پیوست MP3 برمی‌گردد. بخش «پیام‌های صوتی» پایین را ببینید.
  • ویدیو / اسناد — هر دو پشتیبانی و به‌عنوان پیوست native ارسال می‌شوند.

UX تعاملی

وقتی ایجنت هرکدام از این جریان‌ها را invoke کند هرماس از پیام‌های تعاملی native ی واتساپ استفاده می‌کند — دکمه‌های tap-کن-جواب به‌جای پرامپت‌های «با شماره جواب بده»:

  • ابزار clarify — سؤالات چندگزینه‌ای به‌صورت دکمه‌های quick-reply ‏(۱–۳ گزینه) یا برگهٔ لیست tap-کن-باز ‏(۴+ گزینه) رندر می‌شوند. انتخاب «✏️ Other» اجازه می‌دهد کاربر پاسخ آزاد تایپ کند که ایجنت به‌عنوان نتیجه دریافت می‌کند.
  • تأیید فرمان‌های خطرناک — وقتی اجرای terminal/code ی ایجنت به فرمان gated بخورد، کاربر دکمه‌های ‏✅ Approve / ❌ Deny را می‌بیند به‌جای تایپ /approve یا /deny.
  • تأییدهای دستور اسلش — فرمان‌های ممتاز مثل /reload-mcp دکمه‌های ✅ Approve Once / 🔒 Always / ❌ Cancel نشان می‌دهند.

همهٔ پرامپت‌های تعاملی اگر دکمه‌ها رندر نشوند ‏(مثلاً روی کلاینت‌های قدیمی واتساپ) با لطف به متن ساده تنزل می‌یابند.

رسید خواندن و نشانگر تایپ

هرمس پیام‌های ورودی را فوراً acknowledge می‌کند:

  • پیامتان به‌محض دریافت توسط گیت‌وی دوتیک آبی نشان می‌دهد.
  • نام ربات در چت واتساپ‌تان حین آماده‌سازی پاسخ «typing…» نشان می‌دهد.
  • نشانگر typing وقتی اولین پیام پاسخ ربات برسد خودکار dismiss می‌شود.

این باعث می‌شود دیدنِ پیامتان توسط ربات در مقابل هنوز-درحال-کاربودنش واضح باشد.

پیام‌های صوتی

‏واتساپ بین «ویس‌نوت» ‏(حباب موج سبز) و پیوست فایل صوتی عمومی تفکیک قائل است. تفاوت صرفاً codec است: ویس‌نوت‌ها audio/ogg با کدگذاری opus می‌خواهند.

‏TTS ی هرمس MP3 تولید می‌کند. دو مسیر:

  • با ffmpeg روی PATH ‏(توصیه‌شده) — TTS ی خروجی تبدیل و به‌عنوان ویس‌نوت واقعی می‌رسد. نصب: ‏Windows: ‏winget install Gyan.FFmpeg · ‏macOS: ‏brew install ffmpeg · ‏Linux: مدیر پکیج
  • بدون ffmpeg — TTS ی خروجی به‌عنوان پیوست MP3 می‌رسد. خوب پخش می‌شود فقط شبیه ویس‌نوت نیست. یک هشدار یک‌باره در لاگ گیت‌وی شلیک می‌شود تا بدانید.

پیدا شدن ffmpeg توسط گیت‌وی را از طریق نقطهٔ پایانی health چک کنید:

curl http://localhost:8090/health
# look for "ffmpeg_present": true

۱۱ محدودیت‌های شناخته‌شده

پنجرهٔ گفتگوی ۲۴ ساعته

متا فقط پیام‌های آزاد را داخل پنجرهٔ ۲۴ ساعته بعد از آخرین پیام ورودی کاربر اجازه می‌دهد. بیرون آن پنجره تنها چیزی که API ی متا می‌پذیرد یک قالب پیام پیش-تأییدشده است.

در عمل یعنی:

  • چت واکنشی ‏(DM کاربر ← پاسخ ربات زیر ۲۴h ← reply کاربر ← ...) برای همیشه کار می‌کند. بیش از ۹۵٪ مصرف عادی ربات را پوشش می‌دهد.
  • cron job هایی که به واتساپ تحویل می‌دهند بعد از فاصلهٔ بالای ۲۴h با خطای Graph ی ‏131047 شکست می‌خورند ‏(«Re-engagement message»).
  • نتایج async ی delegate_task های بلندمدت که بیشتر از ۲۴h طول بکشند همین‌طور شکست می‌خورند.
  • مشترکان وب‌هوک که رویدادهای بیرونی را به واتساپ مسیریابی می‌کنند وقتی کاربر اخیراً DM نداده شکست می‌خورند.

هرمس در پرامپت سیستمی ایجنت دربارهٔ این پنجره هشدار می‌دهد تا مدل موقع زمان‌بندی پیام‌های تأخیری بداند به آن اشاره کند.

پشتیبانی قالب-پیام ‏(راه‌حل ارسال خارج-از-پنجره) فعلاً در هرمس پیاده نشده. اگر لازمش دارید لطفاً issue باز کنید — برنامه‌ریزی شده ولی منتظر سیگنال تقاضای روشن است.

گفتگوهای گروهی

Cloud API پشتیبانی گروهی محدودی دارد ‏(gate شده با سطح-قابلیت متا). adapter ی whatsapp_cloud ی هرمس فعلاً در v1 فقط پیام‌های مستقیم را هندل می‌کند. اگر گروه‌چت لازم دارید از پل Baileys استفاده کنید.

rate limit خروجی

توان پیش‌فرض متا ۸۰ پیام/ثانیه per شماره تلفن بیزینسی است با امکان ارتقا. هرمس فعلاً سمت-کلاینت این را اعمال نمی‌کند — ارسال‌های حجم-بسیار-بالا ممکن است به سقف متا بخورند.

۱۲ عیب‌یابی

تأیید setup شکست می‌خورد ‏(«URL couldn't be validated») در داشبورد متا

تقریباً همیشه یکی از اینها:

  • URL ی tunnel غلط یا کهنه است — quick tunnel های cloudflared می‌چرخند. URL تازه بگیرید و هم .env هم داشبورد متا را به‌روز کنید.
  • عدم تطبیق Verify token — توکن در WHATSAPP_CLOUD_VERIFY_TOKEN ی ~/.hermes/.env باید دقیقاً با آنچه در داشبورد متا تایپ کردید بخورد. اول probe ی curl بالا را اجرا کنید تا handshake ی verify ی گیت‌وی محلیاً کار کند.
  • گیت‌وی اجرا نیست — بررسی کنید hermes gateway بالا باشد.
  • App Secret ست نیست — بدون آن هرمس POST های ورودی را با ۵۰۳ رد می‌کند. متا آن را «قابل‌اعتبارسنجی نیست» تفسیر می‌کند.

‏graph error 100: Object with ID '...' does not exist

شماره تلفن‌تان ‏(۱۰–۱۱ رقم) را به‌جای Phone Number ID ‏(ID داخلی ۱۵–۱۷ رقمی متا) داخل WHATSAPP_CLOUD_PHONE_NUMBER_ID چسبانده‌اید. صفحهٔ API Setup را دوباره چک کنید — Phone Number ID زیر dropdown ی From نشان داده می‌شود.

ویزارد حالا با validator این را می‌گیرد ولی اگر دستی پیکربندی می‌کنید دانستنش بد نیست.

‏graph error 190: Authentication Error

توکن دسترسی‌تان نامعتبر است. زیرکدها:

  • ‏subcode 463 — توکن منقضی شده. توکن‌های موقت ۲۴ ساعت دوام دارند. دوباره بسازید یا به توکن دائمی System User سوئیچ کنید.
  • ‏subcode 467 — توکن بی‌اعتبار شده ‏(revoke یا تغییر رمز).
  • سایر ۱۹۰ — توکن هنگام ساخت مجوزهای لازم را نداشته. مطمئن شوید هر سه انتخاب شده بودند.

‏graph error 131047: Re-engagement message

پنجرهٔ گفتگوی ۲۴ ساعته منقضی شده ‏(محدودیت‌های شناخته‌شده را ببینید). یا:

  • از کاربر بخواهید اول به ربات DM بدهد تا پنجره دوباره باز شود.
  • منتظر رسیدن پشتیبانی قالب به هرمس بمانید.

پیام ورودی: ‏media metadata fetch failed (status=401)

همان ریشه‌های ۴۰۱ ی خروجی ‏(graph error 190) — توکن دسترسی نامعتبر یا منقضی است. توکن را درست کنید.

پاسخ‌های ربات به‌صورت JSON خام / نشت tool-call ظاهر می‌شوند

علت رایج: تول‌ست پیکربندی‌شده برای whatsapp_cloud ابزارهایی را که ایجنت می‌خواهد صدا بزند ندارد. ‏hermes tools list را چک و تأیید کنید پلتفرم از hermes-whatsapp استفاده می‌کند ‏(تول‌ست پیش‌فرض adapter ی Cloud، مثل Baileys).

اگر مدل به‌جای فراخوانی ساختاریافته متنِ شبیه-tool-call منتشر کند معمولاً یعنی تول‌ست عملاً خالی بوده. نگاشت platform ← default-toolset را در hermes_cli/platforms.py ببینید.

‏STT ‏(رونویسی ویس‌نوت) خالی برمی‌گرداند / «could not transcribe»

پیش‌فرض ‏stt.provider: local به ‏pip install faster-whisper نیاز دارد. اگر مشترک Nous هستید می‌توانید STT را از طریق گیت‌وی مدیریت‌شده مسیریابی کنید — در hermes tools برای speech-to-text مقدار Nous Subscription را بردارید یا مستقیم ست کنید:

hermes config set stt.provider nous
hermes gateway restart

این به‌جای کلید جداگانهٔ OpenAI از توکن دسترسی Nous Portal شما استفاده می‌کند. ‏(مستندات قدیمی ‏stt.use_gateway true را پیشنهاد می‌دادند — آن فلگ legacy است؛ الان فقط انتخاب provider مسیریابی را کنترل می‌کند.)

۱۳ نکات امنیتی

  • App Secret را مثل رمز عبور تلقی کنید — هرکس آن را داشته باشد می‌تواند payload های وب‌هوکی جعل کند که هرمس اصیل می‌پذیرد.
  • Verify token یک secret مشترک است — نشتش کم‌خطرتر است ‏(بدترین حالت کسی می‌تواند وب‌هوک متا را به URL دیگری از خودش re-subscribe کند) ولی باز هم commit اش نکنید.
  • توکن دسترسی هویت ربات شماست — توکن‌های System User معادل کلیدهای API ی بلندمدت‌اند. در صورت به‌خطر افتادن استقرار فوراً rotate کنید.
  • نقطهٔ پایانی webhook فقط وقتی WHATSAPP_CLOUD_APP_SECRET ست باشد درخواست‌های امضاشده می‌پذیرد — حتی در توسعه ست نگهش دارید. بدون آن گیت‌وی تحویل ورودی را با HTTP 503 رد می‌کند.
  • نقطهٔ پایانی /health احراز-هویت‌نشده است — امن است چون فقط بولین‌های حضور-config را گزارش می‌کند نه مقادیرشان. ولی اگر نمی‌خواهیدش surface کنید دسترسی را در لایهٔ reverse proxy / tunnel محدود کنید.
