وب‌هوک‌ها

رویدادهای سرویس‌های خارجی ‏(GitHub، ‏GitLab، ‏JIRA، ‏Stripe و...) را دریافت کنید و اجرای ایجنت هرمس را خودکار تریگر کنید. آداپتور webhook یک سرور HTTP اجرا می‌کند که درخواست‌های POST را می‌پذیرد، امضاهای HMAC را اعتبارسنجی، payload ها را به پرامپت‌های ایجنت تبدیل و پاسخ‌ها را به منبع یا پلتفرم پیکربندی‌شدهٔ دیگر مسیریابی می‌کند.

ایجنت رویداد را پردازش و می‌تواند با پست کامنت روی PR ها، ارسال پیام به تلگرام/دیسکورد یا لاگ نتیجه پاسخ دهد.

🎬 آموزش تصویری

ویدیوی آموزشی رسمی: Hermes Agent — Webhooks Tutorial ‏(یوتیوب)

۱ شروع سریع

  1. با hermes gateway setup یا متغیرهای محیطی فعال کنید
  2. مسیرها ‏(routes) را در config.yaml تعریف کنید یا با hermes webhook subscribe به‌صورت داینامیک بسازید
  3. سرویس‌تان را به http://your-server:8644/webhooks/<route-name> اشاره دهید

۲ راه‌اندازی

آداپتور webhook دو جور فعال می‌شود.

با ویزارد راه‌اندازی

bash
hermes gateway setup

طبق پرسش‌ها webhooks را فعال، پورت را تعیین و رمز HMAC سراسری بگذارید.

با متغیرهای محیطی

به ~/.hermes/.env اضافه کنید:

bash
WEBHOOK_ENABLED=true
WEBHOOK_PORT=8644        # پیش‌فرض
WEBHOOK_SECRET=your-global-secret

تأیید سرور

وقتی گیت‌وی اجراست:

bash
curl http://localhost:8644/health

پاسخ موردانتظار:

json
{"status": "ok", "platform": "webhook"}

۳ پیکربندی مسیرها ‏(Routes)

مسیرها تعیین می‌کنند منابع مختلف webhook چطور هندل شوند. هر مسیر یک ورودی نام‌دار زیر platforms.webhook.extra.routes در config.yaml شماست.

ویژگی‌های مسیر

ویژگیلازمتوضیح
eventsخیرفهرست انواع رویداد قابل قبول ‏(مثل ["pull_request"]). اگر خالی باشد همهٔ رویدادها پذیرفته می‌شوند. نوع رویداد از X-GitHub-Event، ‏X-GitLab-Event یا event_type داخل payload خوانده می‌شود.
secretبلهرمز HMAC برای اعتبارسنجی امضا. اگر روی مسیر تنظیم نشده باشد به رمز سراسری secret برمی‌گردد. فقط برای تست ‏(رد اعتبارسنجی) روی "INSECURE_NO_AUTH".
profileخیرپروفایل مجازِ اجرای این مسیر وقتی gateway.multiplex_profiles فعال است. برای مسیر فقط-پروفایل-پیش‌فرض حذفش کنید؛ نام پروفایل ‏(مثل coder) بگذارید تا مسیر و رمزش به ‏/p/coder/webhooks/<route> قفل شوند.
promptخیررشتهٔ قالب با دسترسی dot-notation به payload ‏(مثل {pull_request.title}). اگر حذف شود کل JSON payload داخل پرامپت dump می‌شود. فیلدهای payload غیرقابل‌اعتمادند — «احراز‌شده به معنی مطمئن نیست» را ببینید.
filtersخیرفیلترهای اعلانیِ payload که بعد از فیلتر auth/body/event و قبل از کار ایجنت یا تحویل مستقیم ارزیابی می‌شوند. عدم‌تطبیق با HTTP 200 برمی‌گردد: ‏{"status":"ignored","reason":"filter"}.
scriptخیراسکریپت فیلتر/تبدیل زیر ~/.hermes/scripts/. payload وب‌هوک به‌صورت JSON روی stdin داده می‌شود. خروجی stdout آبجکت JSON جایگزین payload پیش از قالب‌سازی می‌شود؛ متن stdout به‌صورت script_output expose می‌شود؛ stdout خالی، ‏[SILENT] یا کد خروج ناصفر webhook را نادیده می‌گیرد.
skillsخیرفهرست نام مهارت‌ها برای بارگذاری در اجرای ایجنت.
toolsetsخیرفهرست کلیدهای تول‌ست ‏(مثل ["terminal", "file", "web"]) که تول‌ست سطح-پلتفرم webhook را فقط برای اجراهای این مسیر جایگزین می‌کند. فقط با ویرایش دستی config — از طریق hermes webhook subscribe قابل تنظیم نیست تا اشتراک‌های ساختهٔ ایجنت نتوانند ابزار ممتاز خودشان را grant کنند. نام‌ها مثل ورودی‌های platform_toolsets اعتبارسنجی می‌شوند ‏(نام‌های ناشناخته یا محدود-به-پلتفرم رد می‌شوند).
deliverخیرمقصد پاسخ: ‏github_comment، ‏telegram، ‏discord، ‏slack، ‏signal، ‏sms، ‏whatsapp، ‏matrix، ‏mattermost، ‏homeassistant، ‏email، ‏dingtalk، ‏feishu، ‏wecom، ‏weixin، ‏bluebubbles، ‏qqbot یا log ‏(پیش‌فرض).
deliver_extraخیرپیکربندی تحویل اضافی — کلیدها بسته به نوع deliver ‏(مثل repo، ‏pr_number، ‏chat_id). مقادیر همان قالب‌های {dot.notation} را مثل prompt پشتیبانی می‌کنند.
deliver_onlyخیراگر true، ایجنت کلاً رد می‌شود — قالب prompt رندرشده همان پیام تحت‌اللفظی است که تحویل می‌گیرد. بدون هزینهٔ LLM، تحویل زیرثانیه‌ای. Requires ‏deliver هدف واقعی باشد ‏(نه log).

مثال کامل

yaml
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      secret: "global-fallback-secret"
      routes:
        github-pr:
          events: ["pull_request"]
          secret: "github-webhook-secret"
          prompt: |
            Review this pull request:
            Repository: {repository.full_name}
            PR #{number}: {pull_request.title}
            Author: {pull_request.user.login}
            URL: {pull_request.html_url}
            Diff URL: {pull_request.diff_url}
            Action: {action}
          skills: ["github-code-review"]
          deliver: "github_comment"
          deliver_extra:
            repo: "{repository.full_name}"
            pr_number: "{number}"
        deploy-notify:
          events: ["push"]
          secret: "deploy-secret"
          prompt: "New push to {repository.full_name} branch {ref}: {head_commit.message}"
          filters:
            - field: "ref"
              equals: "refs/heads/main"
          deliver: "telegram"

فیلترهای Payload

وقتی یک ارائه‌دهنده جریان رویداد پهنی می‌فرستد ولی فقط بعضی payload ها باید ایجنت را بیدار یا تحویل deliver_only تریگر کنند از filters استفاده کنید. فیلترها بعد از اعتبارسنجی امضا، parse بدنه و events اجرا می‌شوند ولی قبل از رندر پرامپت، idempotency، dispatch ایجنت یا تحویل مستقیم.

yaml
platforms:
  webhook:
    extra:
      routes:
        todoist:
          events: ["item:updated"]
          secret: "todoist-secret"
          filters:
            - field: "payload.labels"
              contains: "hermes"
            - any:
                - field: "payload.priority"
                  equals: 4
                - field: "payload.project_id"
                  in_file: "~/.hermes/data/todoist/watchlist.json"
          prompt: "Todoist task changed: {payload.content}"

عملگرهای پشتیبانی‌شده:

  • ‏exists: true|false
  • ‏missing: true
  • ‏equals / ‏not_equals
  • ‏contains برای رشته‌ها، فهرست‌ها و کلیدهای dict
  • ‏in برای فهرست‌های درجا
  • ‏in_file برای آرایه‌های JSON، آبجکت‌های JSON ‏(کلیدها استفاده می‌شوند) یا فایل‌های متنی جداشده با خط جدید
  • ‏regex
  • گروه‌های all، ‏any و not

مسیر فیلدها dot-notation است. ‏payload.foo وقتی آبجکت سطح‌بالای payload وجود دارد از آن می‌خواند وگرنه از بدنهٔ ریشهٔ webhook برای payload های تخت. ‏event / ‏event_type نوع رویداد حل‌شده را تطبیق می‌دهد و headers.<Name> هدرهای درخواست را می‌خواند.

فیلترها و تبدیل‌های اسکریپتی

وقتی فیلترهای اعلانی کافی نیستند از script استفاده کنید. اسکریپت‌ها باید زیر ~/.hermes/scripts/ پروفایل فعال باشند؛ مسیرهای نسبی آنجا حل می‌شوند و path traversal بیرون آن دایرکتوری مسدود است. اسکریپت‌های .sh و .bash با bash اجرا می‌شوند و بقیهٔ پسوندها با مفسر Python فعلی.

payload مسیر به‌صورت JSON به stdin فرستاده می‌شود:

python — ~/.hermes/scripts/todoist-hermes-label.py
import json
import sys

payload = json.load(sys.stdin)
labels = payload.get("payload", {}).get("labels", [])
if "hermes" not in labels:
    print("[SILENT]")
    raise SystemExit(0)

payload["body"] = payload["payload"]["content"]
print(json.dumps(payload))

پیامدهای اسکریپت:

  • stdout آبجکت JSON جایگزین payload استفاده‌شده توسط prompt و deliver_extra می‌شود.
  • stdout متنیِ غیر-JSON به payload به‌صورت script_output اضافه می‌شود.
  • stdout خالی، عیناً ‏[SILENT]، ‏{"__hermes_ignore__": true}، timeout، نبودن اسکریپت یا کد خروج ناصفر HTTP 200 با ‏{"status":"ignored","reason":"script"} برمی‌گرداند.

قالب‌های پرامپت

پرامپت‌ها برای دسترسی به فیلدهای تودرتوی payload از dot-notation استفاده می‌کنند:

  • ‏{pull_request.title} به ‏payload["pull_request"]["title"] حل می‌شود
  • ‏{repository.full_name} به ‏payload["repository"]["full_name"] حل می‌شود
  • ‏{__raw__} — توکن ویژه که کل payload را به‌صورت JSON تورفتگی‌دار dump می‌کند ‏(بریده در ۴۰۰۰ کاراکتر). برای هشدارهای مانیتورینگ یا webhook های عمومی که ایجنت زمینهٔ کامل لازم دارد مفید است.
  • کلیدهای گمشده به‌عنوان رشتهٔ تحت‌اللفظی {key} می‌مانند ‏(بدون خطا)
  • dict و list های تودرتو JSON-serialize و در ۲۰۰۰ کاراکتر بریده می‌شوند

می‌توانید {__raw__} را با متغیرهای قالب معمولی مخلوط کنید:

yaml
prompt: "PR #{pull_request.number} by {pull_request.user.login}: {__raw__}"

اگر برای مسیری قالب prompt پیکربندی نشده باشد، کل payload به‌صورت JSON تورفتگی‌دار dump می‌شود ‏(بریده در ۴۰۰۰ کاراکتر).

همان قالب‌های dot-notation در مقادیر deliver_extra هم کار می‌کنند.

تحویل تاپیک فروم

برای تحویل پاسخ‌های webhook به تلگرام می‌توانید با گنجاندن message_thread_id ‏(یا thread_id) در deliver_extra یک تاپیک فروم مشخص را هدف بگیرید:

yaml
webhooks:
  routes:
    alerts:
      events: ["alert"]
      prompt: "Alert: {__raw__}"
      deliver: "telegram"
      deliver_extra:
        chat_id: "-1001234567890"
        message_thread_id: "42"

اگر chat_id در deliver_extra نباشد، تحویل به کانال خانگیِ پیکربندی‌شدهٔ پلتفرم هدف برمی‌گردد.

۴ بازبینی PR گیت‌هاب ‏(گام‌به‌گام)

این راهنما بازبینی خودکار کد را برای هر pull request راه می‌اندازد.

۱. ساخت وب‌هوک در گیت‌هاب

  1. به مخزن ← Settings ← Webhooks ← Add webhook بروید
  2. ‏Payload URL را روی ‏http://your-server:8644/webhooks/github-pr بگذارید
  3. ‏Content type را روی ‏application/json بگذارید
  4. ‏Secret را مطابق پیکربندی مسیر بگذارید ‏(مثل github-webhook-secret)
  5. تحت Which events? گزینهٔ Let me select individual events را انتخاب و Pull requests را تیک بزنید
  6. Add webhook را کلیک کنید

۲. افزودن پیکربندی مسیر

مسیر github-pr را طبق مثال بالا به ~/.hermes/config.yaml اضافه کنید.

۳. احراز CLI ‏gh

نوع تحویل github_comment برای پست کامنت از GitHub CLI استفاده می‌کند:

bash
gh auth login

۴. تست

یک pull request روی مخزن باز کنید. وب‌هوک شلیک می‌شود، هرمس رویداد را پردازش و کامنت بازبینی روی PR می‌گذارد.

۵ راه‌اندازی وب‌هوک گیت‌لب

وب‌هوک‌های گیت‌لب مشابه کار می‌کنند ولی مکانیزم احراز متفاوت دارند. گیت‌لب رمز را به‌عنوان هدر سادهٔ X-Gitlab-Token می‌فرستد ‏(تطبیق دقیق رشته، نه HMAC).

۱. ساخت وب‌هوک در گیت‌لب

  1. به پروژه ← Settings ← Webhooks بروید
  2. ‏URL را روی ‏http://your-server:8644/webhooks/gitlab-mr بگذارید
  3. Secret token را وارد کنید
  4. Merge request events را انتخاب کنید ‏(+ هر رویداد دیگری که می‌خواهید)
  5. Add webhook را کلیک کنید

۲. افزودن پیکربندی مسیر

yaml
platforms:
  webhook:
    enabled: true
    extra:
      routes:
        gitlab-mr:
          events: ["merge_request"]
          secret: "your-gitlab-secret-token"
          prompt: |
            Review this merge request:
            Project: {project.path_with_namespace}
            MR !{object_attributes.iid}: {object_attributes.title}
            Author: {object_attributes.last_commit.author.name}
            URL: {object_attributes.url}
            Action: {object_attributes.action}
          deliver: "log"

۷ حالت تحویل مستقیم

به‌طور پیش‌فرض هر POST وب‌هوک یک اجرای ایجنت تریگر می‌کند — payload تبدیل به پرامپت می‌شود، ایجنت پردازش می‌کند و پاسخش تحویل می‌گیرد. این روی هر رویداد توکن LLM هزینه دارد.

برای مواردی که فقط می‌خواهید یک اعلان ساده push کنید — نه استدلال، نه حلقهٔ ایجنت، فقط تحویل پیام — ‏deliver_only: true را روی مسیر بگذارید. قالب prompt رندرشده همان بدنهٔ تحت‌اللفظی پیام می‌شود و آداپتور مستقیم به هدف تحویل پیکربندی‌شده dispatch‌اش می‌کند.

کِی از تحویل مستقیم استفاده کنیم

  • push سرویس خارجی — وب‌هوک Supabase/Firebase روی تغییر دیتابیس شلیک می‌شود ← اعلان فوری به کاربر در تلگرام
  • هشدارهای مانیتورینگ — وب‌هوک alert دیتاداگ/گرافانا ← push به کانال دیسکورد
  • پینگ بین-ایجنتی — ایجنت A به کاربر ایجنت B خبر می‌دهد کار طولانی تمام شد
  • اتمام job پس‌زمینه — کار کرون تمام شد ← پست نتیجه در اسلک

مزایا:

  • صفر توکن LLM — ایجنت هیچ‌وقت فراخوانی نمی‌شود
  • تحویل زیرثانیه‌ای — یک فراخوانی آداپتور، بدون حلقهٔ استدلال
  • همان امنیت حالت ایجنت — احراز HMAC، سقف نرخ، idempotency و سقف حجم بدنه همه همچنان اعمال می‌شوند
  • پاسخ همگام — POST بعد از موفقیت تحویل ‏200 OK برمی‌گرداند یا در صورت رد شدن توسط هدف ‏502، تا سرویس بالادستی بتواند هوشمندانه retry کند

مثال: push تلگرام از Supabase

yaml
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      secret: "global-secret"
      routes:
        antenna-matches:
          secret: "antenna-webhook-secret"
          deliver: "telegram"
          deliver_only: true
          prompt: "🎉 New match: {match.user_name} matched with you!"
          deliver_extra:
            chat_id: "{match.telegram_chat_id}"

‏edge function ساپابیزتان payload را با HMAC-SHA256 امضا و به ‏https://your-server:8644/webhooks/antenna-matches پست می‌کند. آداپتور امضا را تأیید، قالب را از payload رندر، به تلگرام تحویل و ‏200 OK برمی‌گرداند.

مثال: اشتراک داینامیک با CLI

bash
hermes webhook subscribe antenna-matches \
  --deliver telegram \
  --deliver-chat-id "123456789" \
  --deliver-only \
  --prompt "🎉 New match: {match.user_name} matched with you!" \
  --description "Antenna match notifications"

نکته‌های پیکربندی

  • ‏deliver_only: true نیازمند هدف واقعی در deliver است. ‏deliver: log ‏(یا حذف deliver) هنگام شروع رد می‌شود — آداپتور اگر مسیر بدپیکربندی ببیند از شروع امتناع می‌کند.
  • فیلد skills در حالت تحویل مستقیم نادیده گرفته می‌شود ‏(اجرای ایجنت نیست، پس مهارتی برای تزریق وجود ندارد).
  • رندر قالب همان syntax ‏{dot.notation} حالت ایجنت را دارد شامل توکن {__raw__}.
  • Idempotency از همان هدر ‏X-GitHub-Delivery / ‏X-Request-ID استفاده می‌کند — retry با شناسهٔ یکسان ‏status=duplicate برمی‌گرداند و دوباره تحویل نمی‌دهد.

۸ اشتراک‌های داینامیک ‏(CLI)

علاوه بر مسیرهای ثابت config.yaml، می‌توانید اشتراک‌های webhook را با فرمان CLI ‏hermes webhook داینامیک بسازید. مخصوصاً وقتی خود ایجنت نیاز دارد تریگرهای رویدادمحور راه بیندازد مفید است.

ساخت اشتراک

bash
hermes webhook subscribe github-issues \
  --events "issues" \
  --prompt "New issue #{issue.number}: {issue.title}\nBy: {issue.user.login}\n\n{issue.body}" \
  --deliver telegram \
  --deliver-chat-id "-100123456789" \
  --description "Triage new GitHub issues"

این فرمان URL وب‌هوک و یک رمز HMAC خودکار تولیدشده برمی‌گرداند. سرویس‌تان را طوری پیکربندی کنید که به آن URL پست کند.

فهرست اشتراک‌ها

bash
hermes webhook list

حذف اشتراک

bash
hermes webhook remove github-issues

تست اشتراک

bash
hermes webhook test github-issues
hermes webhook test github-issues --payload '{"issue": {"number": 42, "title": "Test"}}'

نحوهٔ کار اشتراک‌های داینامیک

  • اشتراک‌ها در ~/.hermes/webhook_subscriptions.json ذخیره می‌شوند
  • آداپتور webhook این فایل را روی هر درخواست ورودی hot-reload می‌کند ‏(گیت‌خورده با mtime، overhead ناچیز)
  • مسیرهای ثابت config.yaml همیشه بر داینامیک‌های هم‌نام مقدم‌اند
  • اشتراک‌های داینامیک همان فرمت و قابلیت‌های مسیر ثابت را دارند ‏(events، قالب‌های پرامپت، مهارت‌ها، تحویل)
  • ری‌استارت گیت‌وی لازم نیست — subscribe کنید و بلافاصله لایو است

اشتراک‌های ایجنت‌محور

ایجنت می‌تواند با ابزار ترمینال و هدایت مهارت webhook-subscriptions اشتراک بسازد. از ایجنت بخواهید «برای issue های گیت‌هاب یک وب‌هوک راه بینداز» و خودش فرمان مناسب ‏hermes webhook subscribe را اجرا می‌کند.

۹ تول‌ست به‌ازای-مسیر

اجراهای ایجنتِ webhook به‌طور پیش‌فرض تول‌ست عمداً محدودی دارند ‏(web_search، ‏web_extract، ‏vision_analyze، ‏clarify) چون payload های وب‌هوک ممکن است محتوای شخص ثالثِ غیرقابل‌اعتماد حمل کنند — تیتر PR عمومی یا کامنت issue هرگز نباید بتواند با prompt-injection راهش را به ترمینال شما باز کند.

برای مسیرهای مطمئن — دیمن مانیتورینگ localhost که هشدار سیستم push می‌کند، سیستم CI داخلی — می‌توانید فقط به همان مسیر تول‌ست پهن‌تری بدهید بدون پهن‌کردن بقیهٔ مسیرها:

yaml
platforms:
  webhook:
    enabled: true
    extra:
      routes:
        oom-emergency:
          secret: "monitor-secret"
          prompt: "Memory emergency: {detail}. Diagnose with ps/free/py-spy and report."
          toolsets: ["terminal", "file", "code_execution", "web"]
          deliver: "telegram"

برای اشتراک‌های داینامیک، کلید toolsets را با ویرایش مستقیم ~/.hermes/webhook_subscriptions.json اضافه کنید:

json
{
  "oom-emergency": {
    "secret": "...",
    "prompt": "...",
    "toolsets": ["terminal", "file", "web"],
    "deliver": "telegram"
  }
}

رفتار و ویژگی‌های امنیتی:

  • فهرست مسیر، حل تول‌ست سطح-پلتفرم webhook را برای اجراهای آن مسیر جایگزین می‌کند ‏(merge نمی‌شود).
  • نام‌ها از همان مسیر پیکربندی platform_toolsets اعتبارسنجی می‌شوند — نام‌های ناشناخته و تول‌ست‌های محدود-به-پلتفرم رد می‌شوند.
  • ‏hermes webhook subscribe عمداً فلگ toolsets نمی‌پذیرد. دادن ابزار ممتاز فقط ویرایش دستی فایل پیکربندی است، تا ایجنتی که در runtime اشتراکش را می‌سازد نتواند خودش terminal را grant کند.
  • فقط به مسیرهایی تول‌ست ممتاز بدهید که فرستنده‌شان را کاملاً کنترل می‌کنید و رمز HMAC واقعی دارند. هر کسی بتواند payload دارای امضای معتبر به آن مسیر پست کند عملاً ایجنتی با آن ابزارها اجرا می‌کند.

۱۰ امنیت

آداپتور webhook چند لایهٔ امنیتی دارد:

اعتبارسنجی امضای HMAC

آداپتور امضاهای ورودی را با روش مناسب هر منبع اعتبارسنجی می‌کند:

  • ‏GitHub: هدر ‏X-Hub-Signature-256 — digest hex ‏HMAC-SHA256 با پیشوند sha256=
  • ‏GitLab: هدر ‏X-Gitlab-Token — تطبیق رشتهٔ سادهٔ رمز
  • عمومی ‏(V2، توصیه‌شده): هدرهای ‏X-Webhook-Signature-V2 + ‏X-Webhook-Timestamp — digest hex ‏HMAC-SHA256 از ‏<timestamp>.<body>. timestamp ‏(ثانیه یونیکس) باید در بازهٔ ±۳۰۰ ثانیه ساعت سرور باشد تا درخواست‌های ضبط‌شده نتوانند بعداً replay شوند.
  • عمومی ‏(V1، legacy): هدر ‏X-Webhook-Signature — digest hex خام ‏HMAC-SHA256 فقط بدنه. برای سازگاری هنوز پذیرفته می‌شود ولی محافظت replay ندارد ‏(درخواست ضبط‌شده بی‌نهایت بار تکرارپذیر است)؛ گیت‌وی یک هشدار deprecation به‌ازای هر مسیر لاگ می‌کند. فرستنده‌ها را به V2 منتقل کنید.

اگر رمزی پیکربندی شده باشد ولی هیچ هدر امضای شناخته‌شده‌ای نباشد، درخواست رد می‌شود.

رمز الزامی است

هر مسیر باید رمز داشته باشد — چه مستقیم روی مسیر چه ارثی از secret سراسری. مسیر بدون رمز باعث می‌شود آداپتور هنگام شروع با خطا fail شود. فقط برای توسعه/تست می‌توانید رمز را "INSECURE_NO_AUTH" بگذارید تا اعتبارسنجی کلاً رد شود.

وقتی مسیریابی چند-پروفایلی فعال است، فیلد profile مسیر آن رمز را به یک هدف اجرا قفل می‌کند. مسیرِ بدون profile فقط پروفایل‌پیش‌فرض است. درخواستی که امضای مسیرِ معتبر داشته باشد همچنان رد می‌شود اگر پیشوند ‏/p/<profile>/اش با قید مسیر نخواند.

‏INSECURE_NO_AUTH فقط وقتی پذیرفته می‌شود که گیت‌وی به میزبان loopback ‏(127.0.0.1، ‏localhost، ‏::1) بایند شده باشد. ترکیبش با bind غیر-loopback مثل 0.0.0.0 یا IP شبکهٔ محلی باعث می‌شود آداپتور از شروع امتناع کند — تا endpoint بدون احراز تصادفی روی interface عمومی در معرض قرار نگیرد.

سقف نرخ

هر مسیر به‌طور پیش‌فرض به ‍۳۰ درخواست در دقیقه سقف دارد ‏(fixed-window). سراسری تنظیمش کنید:

yaml
platforms:
  webhook:
    extra:
      rate_limit: 60  # درخواست در دقیقه

درخواست‌های فراتر از سقف پاسخ ‏429 Too Many Requests می‌گیرند.

Idempotency

شناسه‌های تحویل ‏(از ‏X-GitHub-Delivery، ‏X-Request-ID یا fallback timestamp) به مدت ۱ ساعت کش می‌شوند. تحویل‌های تکراری ‏(مثل retry های webhook) بی‌صدا با پاسخ 200 رد می‌شوند تا اجرای ایجنت تکراری نشود.

سقف حجم بدنه

‏Payload های بالای ۱ مگابایت قبل از خواندن بدنه رد می‌شوند. تنظیم:

yaml
platforms:
  webhook:
    extra:
      max_body_bytes: 2097152  # ۲ مگابایت

احراز‌شده به معنی مطمئن نیست

⚠️ مدل اعتماد

اعتبارسنجی HMAC فرستنده را احراز می‌کند نه محتوا را. امضای معتبر فقط ثابت می‌کند درخواست از طرفی آمده که رمز مسیر را دارد ‏(مثل گیت‌هاب). هیچ‌چیز دربارهٔ نویسندهٔ فیلدهای کسب‌وکاری داخل payload نمی‌گوید — تیترهای PR، پیام‌های کامیت، توضیحات issue و هر متن بالادستی دیگر را افراد دلخواه ثالث نوشته‌اند و باید غیرقابل‌اعتماد تلقی شوند.

همان مدل اعتمادی که روی هر چیزی که ایجنت می‌خواند اعمال می‌شود: صفحات وب، فایل‌ها و خروجی ابزار همه ورودی غیرقابل‌اعتمادند. هرمس متن غیرقابل‌اعتماد را با blocklist پاکسازی نمی‌کند ‏— و نمی‌تواند مطمئن کند؛ صیغه‌بازی، انکودینگ و ترجمه دورزدنش را بدیهی می‌کنند. مرز اعتماد، سطح قابلیت ایجنت است نه کانال ورودی. همان‌جا مقاوم‌سازی کنید:

  • ‏runtime را سندباکس کنید. وقتی به اینترنت در معرض است، گیت‌وی را با بک‌اند ترمینال Docker یا SSH ‏(یا داخل VM) اجرا کنید تا نوبت ربوده‌شده نتواند به میزبان دست بزند.
  • تول‌ست را scope کنید. ‏terminal، file و ابزارهای اکشن-خروجی را روی نشست‌های تریگرشدهٔ webhook خاموش کنید اگر مسیر فقط باید بخواند و خلاصه کند. قابلیت کمتر یعنی شعاع انفجار کوچکتر وقتی فیلدی از payload دستورالعمل تزریق‌شده حمل کند.
  • تأییدها روشن بمانند برای هر عمل مخرب یا خروجی، تا دستورالعمل تزریق‌شده نتواند بدون نظارت عمل کند.
  • قالب را باریک بگیرید. ‏prompt مشخص با فیلدهای نام‌دار ‏({pull_request.title}) را بر ‏{__raw__} یا قالب خالیِ dumpکنندهٔ کل payload ترجیح دهید تا فقط فیلدهای موردنظرتان به پرامپت برسند.

۱۱ عیب‌یابی

وب‌هوک نمی‌رسد

  • تأیید کنید پورت expose و از منبع وب‌هوک قابل‌دسترس است
  • قواعد فایروال را چک کنید — پورت 8644 ‏(یا پورت پیکربندی‌شده) باید باز باشد
  • تأیید کنید مسیر URL مطابق است: ‏http://your-server:8644/webhooks/<route-name>
  • با endpoint ‏/health تأیید کنید سرور اجراست

اعتبارسنجی امضا شکست می‌خورد

  • مطمئن شوید رمز در پیکربندی مسیر دقیقاً با رمز پیکربندی‌شده در منبع وب‌هوک یکی است
  • برای گیت‌هاب رمز مبتنی بر HMAC است — ‏X-Hub-Signature-256 را چک کنید
  • برای گیت‌لب رمز تطبیق توکن ساده است — ‏X-Gitlab-Token را چک کنید
  • هشدارهای Invalid signature را در لاگ‌های گیت‌وی چک کنید

رویداد نادیده گرفته می‌شود

  • چک کنید نوع رویداد در فهرست events مسیرتان باشد
  • رویدادهای گیت‌هاب مقادیری مثل pull_request، ‏push، ‏issues دارند ‏(مقدار هدر X-GitHub-Event)
  • رویدادهای گیت‌لب مقادیری مثل merge_request، ‏push ‏(مقدار هدر X-GitLab-Event)
  • اگر events خالی یا تنظیم‌نشده باشد همهٔ رویدادها پذیرفته می‌شوند

ایجنت پاسخ نمی‌دهد

  • گیت‌وی را در پیش‌زمینه اجرا کنید تا لاگ‌ها را ببینید: ‏hermes gateway run
  • چک کنید قالب پرامپت درست رندر می‌شود
  • تأیید کنید هدف تحویل پیکربندی و متصل است

پاسخ‌های تکراری

  • کش idempotency باید جلویش را بگیرد — چک کنید منبع وب‌هوک هدر شناسهٔ تحویل می‌فرستد ‏(X-GitHub-Delivery یا X-Request-ID)
  • شناسه‌های تحویل ۱ ساعت کش می‌شوند

خطاهای CLI ‏gh ‏(تحویل کامنت گیت‌هاب)

  • ‏gh auth login را روی میزبان گیت‌وی اجرا کنید
  • مطمئن شوید کاربر گیت‌هابِ احرازشده دسترسی write به مخزن دارد
  • چک کنید gh نصب و روی PATH باشد
