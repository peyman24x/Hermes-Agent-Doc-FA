گیت‌وی پیام‌رسانی

با هرمس از تلگرام، دیسکورد، اسلک، واتساپ، سیگنال، پیامک، ایمیل، هوم‌اسیسنت، مترمست، ماتریکس، دینگ‌تاک، فیشو/لارک، ‏WeCom، ‏ویکسین، ‏BlueBubbles ‏(‏iMessage)، ‏QQ، ‏یوان‌بائو، مایکروسافت تیمز، لاین، ‏ntfy یا مرورگر خود حرف بزنید. گیت‌وی یک پروسهٔ پس‌زمینهٔ واحد است که به همهٔ پلتفرم‌های پیکربندی‌شده‌تان وصل می‌شود، نشست‌ها را هندل می‌کند، کارهای کرونی را اجرا و پیام‌های صوتی را تحویل می‌دهد.

برای مجموعهٔ کامل قابلیت‌های صوتی به «حالت صوتی» و «استفاده از حالت صوتی با هرمس» مراجعه کنید.

💡 نکته

بات‌ها هم به ارائه‌دهندهٔ مدل و هم به ارائه‌دهندگان ابزار‏ (‏TTS، ‏وب) نیاز دارند. یک اشتراک «Nous Portal» همه را باندل می‌کند.

ℹ️ Hermes Relay

«Hermes Relay» (آزمایشی) خودش یک پلتفرم چت نیست — یک سیستم کانکتور است که پلتفرم‌هایی مثل دیسکورد، تلگرام، اسلک و واتساپ را از طریق کانکتور خارجیِ مالکِ اعتبارنامه‌های پلتفرم جلو می‌گیرد. قابلیت‌ها‏ (رسانه، اعلان‌های تأیید/شفاف‌سازی بومی، واکنش‌ها، رشته‌ها، تایپینگ، استریم) به‌ازای-کانکتور هنگام دست‌دادن مذاکره می‌شوند نه در جدول بالا ثابت باشند.

هر آداپتور پلتفرمی پیام‌ها را دریافت، از طریق مخزن نشستِ به‌ازای-چت مسیریابی و برای پردازش به AIAgent اعزام می‌کند. گیت‌وی همچنین زمان‌بند کرون را اجرا می‌کند که هر ۶۰ ثانیه تیک می‌زند تا کارهای سررسید را اجرا کند.

۳ توکن‌های سکوت عمدی

برای گفتگوهای گروهی، هوک‌ها و جریان‌های اتوماسیون، هرمس توکن‌های سکوت صریح را پشتیبانی می‌کند. اگر پاسخ نهایی ایجنت دقیقاً یکی از توکن‌های پشتیبانی‌شده باشد، گیت‌وی تحویل خروجی را سرکوب و هیچ‌چیز به چت نمی‌فرستد.

توکن‌های پشتیبانی‌شده: ‏[SILENT]، ‏SILENT، ‏NO_REPLY، ‏NO REPLY

فضای سفید و بزرگی/کوچکی نرمال می‌شوند، ولی کل پاسخ نهایی باید همان توکن باشد. جمله‌ای مثل «Use [SILENT] when nothing changed» عادی تحویل می‌شود.

سکوت فقط یک تصمیم تحویل است. هرمس نوبتِ سکوتِ دستیار را در رونوشت نشست نگه می‌دارد، پس گفتگو همچنان عادی یکی‌درمیان می‌شود:

text
user: side-channel chatter
assistant: [SILENT]   # ذخیره می‌شود، تحویل نمی‌شود
user: next message

نوبت‌های شکست‌خورده همچنان به‌صورت خطا ظاهر می‌شوند؛ هرمس شکست‌ها را فقط چون متن شبیه توکن سکوت است پنهان نمی‌کند.

۴ راه‌اندازی سریع و فرمان‌های گیت‌وی

آسان‌ترین راه پیکربندی پلتفرم‌های پیام‌رسانی، ویزارد تعاملی است:

bash
hermes gateway setup        # راه‌اندازی تعاملی همهٔ پلتفرم‌های پیام‌رسانی

این شما را با انتخاب کلیدهای جهت از پیکربندی هر پلتفرم عبور می‌دهد، نشان می‌دهد کدام‌ها از قبل پیکربندی شده‌اند و پیشنهاد شروع/ری‌استارت گیت‌وی را می‌دهد.

bash
hermes gateway              # اجرا در پیش‌زمینه
hermes gateway setup        # پیکربندی تعاملی پلتفرم‌های پیام‌رسانی
hermes gateway install      # نصب به‌عنوان سرویس کاربر (لینوکس) / سرویس launchd (مک)
sudo hermes gateway install --system   # فقط لینوکس: نصب سرویس سیستمیِ زمان-بوت
hermes gateway start        # شروع سرویس پیش‌فرض
hermes gateway stop         # توقف سرویس پیش‌فرض
hermes gateway status       # بررسی وضعیت سرویس پیش‌فرض
hermes gateway status --system         # فقط لینوکس: بازرسی صریح سرویس سیستمی

نگهبان حلقهٔ رویداد لینوکس (اختیاری)

یک گیت‌وی مدیریت‌شده-با-systemd می‌تواند بازیابی پروسه را وقتی حلقهٔ رویداد asyncio پایتون دیگر زمان‌بندی نمی‌گیرد اختیار کند. این توقف‌های کل-پروسه را پوشش می‌دهد که اجرای وظایف زنده‌ماندنِ مخصوص-پلتفرم را هم متوقف می‌کنند:

yaml — ~/.hermes/config.yaml
gateway:
  systemd_watchdog_seconds: 120

پس از تغییر این تنظیم، یونیت سرویس را دوباره تولید کنید: hermes gateway install --force

مقدار مثبت makes یونیت تولیدشده از Type=notify، ‏NotifyAccess=main و WatchdogSec مطابق استفاده می‌کند. هرمس فقط تا وقتی حلقهٔ رویدادش پیشرفت به‌موقع دارد ضربان می‌فرستد؛ ‏systemd وقتی متوقف شدند پروسه را ری‌استارت می‌کند. پیش‌فرض 0 رفتار موجودِ Type=simple را نگه می‌دارد. این تنظیم فقط لینوکس/systemd است و قطع شبکهٔ عادیِ پلتفرم را شکست حلقهٔ رویداد تلقی نمی‌کند.

۶ مدیریت نشست

ماندگاری: نشست‌ها بین پیام‌ها تا ریست‌شدن می‌مانند. ایجنت زمینهٔ گفتگوی شما را به خاطر می‌سپارد.

یافتن نشست‌های گذشته (/sessions): نشست‌های قبلی چت فعلی را فهرست و با /sessions <name> یکی را ازسر می‌گیرد. وقتی فهرست بلند شد، ‏/sessions search <query> بر اساس عنوان/شناسه فیلتر می‌کند. فهرست‌کردن بین‌مبدأ با /sessions all فقط-مدیر است — کاربران عادی فقط نشست‌های مبدأ چت خودشان را می‌بینند.

بازنویسی‌های پایدار /model: یک سوییچ /model در چت گیت‌وی به همان نشست اعمال و اکنون از ری‌استارت‌های گیت‌وی جان سالم به در می‌برد: انتخاب مدل/ارائه‌دهنده در مخزن نشست ماندگار و پس از ری‌استارت در اولین استفاده بازآباری می‌شود‏ (اعتبارنامه‌ها هنگام بارگذاری دوباره حل و هرگز روی دیسک نوشته نمی‌شوند). ‏/new بازنویسی را پاک، و /model <name> --global آن را به config.yaml می‌نویسد. ‏--once فقط برای یک نوبت اعمال می‌شود.

قابلیت اطمینان تحویل

پاسخ‌های نهایی ایجنت در یک دفتر تحویل پایدار‏ (state.db) دور هر ارسال پلتفرمی ثبت می‌شوند. اگر گیت‌وی بین تولید پاسخ و تأیید رسیدِ پلتفرم کرش یا ری‌استارت کند، بوت بعدی پاسخ ذخیره‌شده را دوباره تحویل می‌دهد به‌جای گم‌کردنش — یا اجرای کل نوبت.

معناشناسی صادقانهٔ حداقل-یک‌بار است:

  • پاسخی که ارسالش هرگز شروع نشد عیناً دوباره تحویل می‌شود.
  • پاسخی که وسط-ارسال وقتی گیت‌وی مرد (پلتفرم شاید گرفته شاید نه) با پیشوند مرئی «♻️ Recovered reply — … may be a duplicate» دوباره تحویل می‌شود. ابهام برچسب می‌خورد، هرگز خاموش بازفرست نمی‌شود.
  • بازتحویل کراندار است: ۳ تلاش، تازگی ۲۴ ساعته، بعد از آن مدخل رها می‌شود. مدخل‌های تحویل‌شده پس از ۷ روز هرس می‌شوند.

با gateway.delivery_ledger: false در config.yaml غیرفعالش کنید‏ (رفتار قدیمی: پاسخ‌های در-پرواز هنگام کرش گم می‌شوند).

سیاست‌های ریست

به‌طور پیش‌فرض نشست‌ها هرگز خودکار ریست نمی‌شوند — زمینه تا /reset دستی یا فعال‌شدن فشرده‌سازی زمینه می‌ماند. برای ریست خودکار، با بخش session_reset اختیارش کنید:

yaml + json
session_reset:
  mode: idle        # "idle"، "daily"، "both" یا "none" (پیش‌فرض)
  idle_minutes: 1440  # برای idle/both: دقیقه‌های بیکاری پیش از ریست
  at_hour: 4          # برای daily/both: ساعت روز (۰-۲۳، زمان محلی)

# بازنویسی به‌ازای-پلتفرم در ~/.hermes/gateway.json:
{
  "reset_by_platform": {
    "telegram": { "mode": "idle", "idle_minutes": 240 },
    "discord": { "mode": "idle", "idle_minutes": 60 }
  }
}

یک پروسهٔ پس‌زمینهٔ زنده‏ (شروع‌شده با terminal(background=true)) معمولاً نشستش را از ریست محافظت می‌کند تا خروجی گم نشود. تا پروسهٔ فراموش‌شده‌ای — مثلاً سرور پیش‌نمایش — نشستی را برای همیشه باز نگه ندارد، پروسهٔ پس‌زمینهٔ قدیمی‌تر از bg_process_max_age_hours (پیش‌فرض ۲۴) دیگر ریست را بلاک نمی‌کند. پروسه کشته نمی‌شود، فقط توسط گارد ریست نادیده گرفته می‌شود. 0 برای غیرفعال‌کردن برش‏ (هر پروسهٔ زنده ریست را بلاک می‌کند، رفتار قدیمی)، یا برای کارهای مشروعِ چندروزه که زنده‌بودنشان باید گفتگو را باز نگه دارد بالا ببرید.

۷ بازنویسی مدل و پرامپت سیستمی به‌ازای-کانال

کانال‌های متفاوت می‌توانند از یک گیت‌وی واحد مدل‌ها و پرسوناهای متفاوت اجرا کنند — مثلاً مدل ارزان سریع در #daily و مدل مرزی با پرامپت متخصص در #dev. ‏channel_overrides را زیر پلتفرم در ~/.hermes/gateway-config.yaml پیکربندی کنید:

yaml
platforms:
  discord:
    enabled: true
    channel_overrides:
      "123456789012345678":        # شناسهٔ کانال/رشته
        model: anthropic/claude-sonnet-4.6
        provider: anthropic
        system_prompt: "You are the #dev channel code-review specialist."
      "987654321098765432":
        model: openai/gpt-5-mini

جزئیات:

  • هر سه کلید اختیاری‌اند — فقط model، فقط system_prompt یا هر ترکیبی. فیلدهای تنظیم‌نشده به پیش‌فرض‌های سراسری برمی‌گردند.
  • ترتیب جستجو اول شناسهٔ دقیق کانال/رشته، بعد شناسهٔ کانال/فرومِ والد — پس رشته‌های دیسکورد بازنویسی کانال والدشان را خودکار به ارث می‌برند.
  • اولویت حل مدل: بازنویسی /model نشست ← ‏channel_overrides ← ‏پیکربندی سراسری. کاربری که /model بزند همچنان بر پیش‌فرض کانال می‌برد.
  • بازنویسی system_prompt پرامپت سراسری گیت‌وی را برای آن کانال جایگزین می‌کند‏ (زودگذر است — به‌ازای-نوبت تزریق، در تاریخچه ذخیره نمی‌شود).

جفت‌سازی DM (جایگزین فهرست‌های مجاز)

به‌جای پیکربندی دستی شناسه‌های کاربر، کاربران ناشناس هنگام DM به بات یک کد جفت‌سازی یک‌باره می‌گیرند. ایمیل استثناست: فرستندگان ناشناس ایمیل نادیده گرفته می‌شوند مگر جفت‌سازی ایمیل صریحاً فعال باشد.

bash
# کاربر می‌بیند: "Pairing code: XKGH5N7P"
# شما تأییدش می‌کنید با:
hermes pairing approve telegram XKGH5N7P

# سایر فرمان‌های جفت‌سازی:
hermes pairing list          # دیدن کاربران در-انتظار + تأییدشده
hermes pairing revoke telegram 123456789  # حذف دسترسی

کدهای جفت‌سازی پس از ۱ ساعت منقضی، محدود-نرخ و با تصادفی‌بودن رمزنگارانه‌اند.

مدیران در برابر کاربران عادی

فهرست‌های مجاز به «آیا این اصلاً می‌تواند به بات برسد؟» پاسخ می‌دهند. تفکیک مدیر / کاربر به «حالا که وارد شده، چه کاری مجاز است؟» پاسخ می‌دهد.

هر کاربر مجاز به‌ازای-دامنه‏ (‏DM در برابر گروه/کانال) در یکی از دو رده می‌افتد:

  • مدیر — دسترسی کامل. می‌تواند هر فرمان اسلشِ ثبت‌شده‏ (داخلی + پلاگین) و هر قابلیت گیت‌شده را اجرا کند.
  • کاربر عادی — دسترسی محدود. می‌تواند عادی با ایجنت چت کند، ولی فقط فرمان‌های اسلشی را اجرا کند که صریحاً فعال کرده‌اید. کفِ همیشه-مجاز /help و /whoami است.

رده‌ها به‌ازای-پلتفرم و به‌ازای-دامنه پیکربندی می‌شوند. مدیرِ DM لزوماً مدیر گروه/کانال نیست — هر دامنه فهرست مدیر خودش را دارد.

امروز چه چیزی را گیت می‌کنند: فرمان‌های اسلش. تفکیک از رجیستری زندهٔ فرمان‌ها می‌گذرد، پس داخلی‌ها و فرمان‌های ثبت‌شده-پلاگین را بدون سیم‌کشی به‌ازای-قابلیت پوشش می‌دهد. چت ساده متأثر نیست — غیرمدیرها همچنان می‌توانند با ایجنت حرف بزنند.

در آینده چه ممکن است گیت شود: سطوح قابلیت بیشتر (دسترسی ابزار، تعویض مدل، عملیات گران) از همین تفکیک مدیر/کارگر آویزان خواهند شد. پیکربندی تفکیک الان یعنی آن محدودیت‌های آینده تمیز فرود می‌آیند بدون بازمدل‌سازیِ اینکه مدیر کیست.

yaml
gateway:
  platforms:
    discord:
      extra:
        allow_from: ["111", "222", "333"]
        allow_admin_from: ["111"]                    # مدیرها ← همهٔ فرمان‌های اسلش
        user_allowed_commands: [status, model]       # غیرمدیرها چه می‌توانند
        # اختیاری: دامنهٔ جداگانهٔ گروه/کانال
        group_allow_admin_from: ["111"]
        group_user_allowed_commands: [status]

سازگاری-به-عقب: اگر allow_admin_from برای دامنه‌ای تنظیم نشده باشد، تفکیک رده برای آن دامنه خاموش و هر کاربر مجاز دسترسی کامل دارد. نصب‌های موجود بدون تغییر کار می‌کنند — وقتی تمایز را خواستید اختیارش کنید. برای بازبینی دسترسی‌تان از هر پلتفرمی /whoami بزنید.

۹ بازهدایت ایجنت

حین کار ایجنت پیام بفرستید تا نوبت فعال اصلاح شود:

  • تولید مدل با زمینه دوباره شروع می‌شود — استدکارِ نمایش‌داده‌شده و متن جزئیِ مرئی به‌عنوان یک checkpoint عادی دستیار حفظ می‌شوند
  • کارِ تکمیل‌شده در دسترس می‌ماند — فراخوانی‌ها و نتایج ابزار قبلی در نوبت می‌مانند
  • ابزارهای در حال اجرا امن تمام می‌شوند — اصلاح در مرزِ نتیجهٔ ابزارِ بعدی اعمال می‌شود نه کشتن ابزار
  • /stop همچنان توقف سخت است — برای لغو نوبت فعال و کار پیش‌زمینه

صف در برابر وقفه در برابر هدایت (حالت ورودی-مشغول)

به‌طور پیش‌فرض، پیام‌دادن به ایجنتِ مشغول نوبتش را بازهدایت می‌کند. دو حالت دیگر هم هست:

  • queue — پیام‌های پیگیری صبر و پس از اتمام کار فعلی به‌عنوان نوبت بعدی اجرا می‌شوند.
  • steer — پیام‌های پیگیری از طریق /steer به اجرای فعلی تزریق و پس از فراخوانی ابزار بعدی به ایجنت می‌رسند. بدون وقفه، بدون نوبت جدید. اگر ایجنت هنوز شروع نشده به رفتار queue برمی‌گردد.
yaml
display:
  busy_input_mode: steer   # یا queue، یا interrupt (پیش‌فرض)
  busy_ack_enabled: true   # false برای سرکوب کامل پاسخ ⚡/⏳/⏩ در چت

اولین باری که روی هر پلتفرمی به ایجنتِ مشغول پیام می‌دهید، هرمس یک یادآور یک‌خطی به تأییدِ مشغولیتی اضافه می‌کند که پیچ را توضیح می‌دهد. یادآور یک بار به‌ازای-نصب صادر می‌شود — پرچمی زیر onboarding.seen.busy_input_prompt قفلش می‌کند. آن کلید را حذف کنید تا نکته دوباره بیاید. اگر تأییدِ مشغولیتی پر نویز است، display.busy_ack_enabled: false بگذارید. هندل ورودی بدون تغییر؛ فقط پیام تأیید مخفی می‌شود.

۱۰ سؤالات شفاف‌سازی (چندانتخابی)

وقتی ایجنت با ابزار clarify از شما سؤال می‌پرسد، گیت‌وی گزینه‌ها را به‌صورت پرامپت شماره‌دار‏ (یا دکمه‌های بومی روی پلتفرم‌های پشتیبان‌کننده) رندر می‌کند. شفاف‌سازی سؤالات چندانتخابی را هم پشتیبانی می‌کند — ایجنت می‌تواند بگذارد چند گزینه را یک‌جا بردارید:

  • پلتفرم‌های پیام‌رسانی — پرامپت می‌گوید «Multiple selections allowed»؛ با شماره‌های جداشده با ویرگول یا فاصله‏ (مثل 1, 3)، متن گزینه یا پاسخ آزاد خودتان جواب دهید.
  • ‏CLI کلاسیک / ‏TUI — چندانتخابی به‌صورت چک‌باکس رندر می‌شود: Space یک گزینه را سوییچ، ‏Enter انتخاب را ثبت می‌کند.

پرامپت‌های تک‌انتخابی مثل قبل: یک گزینه با شماره، دکمه یا متن بردارید، یا از مسیر «Other» پاسخ خودتان را بنویسید.

۱۱ اعلان‌های پیشرفت ابزار

yaml
display:
  tool_progress: all    # off | new | all | verbose | log
  tool_progress_command: false  # true برای فعال‌سازی /verbose در پیام‌رسانی
  # گروهبندی پیشرفت روی پلتفرم‌های دارای ویرایش پیام:
  #   accumulate (پیش‌فرض) — یک حباب را درجا حین اجرای ابزارها ویرایش کن
  #   separate             — یک پیام به‌ازای-ابزار (سبک پیش-v0.9؛ پرنویزتر)
  tool_progress_grouping: accumulate   # accumulate | separate

حالت log — فایل ممیزی به‌جای پیام چت

display.tool_progress: log هیچ حباب پیشرفتی به چت نمی‌فرستد. به‌جایش هر فراخوانی ابزار به‌صورت خطی به ~/.hermes/logs/tool_calls.log الصاق می‌شود — فایل ممیزی چرخشی‏ (۵MB × ۳ پشتیبان) که از همان پاک‌ساز رازِ لاگ‌های عادی عبور می‌کند، پس اعتبارنامه‌ها هرگز روی دیسک نمی‌نشینند. وقتی بخواهید ردِ کامل فراخوانی ابزار بدون نویز چت داشته باشید استفاده‌اش کنید.

عبارت‌های وضعیت قابل‌پیکربندی

خطوط وضعیتِ بلندمدت گیت‌وی‏ (ضربان‌های سبک «هنوز کار می‌کند…») از کاتالوگ عبارت می‌آیند. پیش‌فرض‌های داخلی در gateway/assets/status_phrases.yaml عرضه می‌شوند؛ می‌توانید با فایل‌های قابل‌حمل-با-پروفایل زیر HERMES_HOME خودتان را بیفزایید: ‏~/.hermes/status_phrases.yaml یا هر *.yaml در ~/.hermes/status_phrases/‏ (مسیرهای قراردادی، بارگذاری خودکار)، یا پیکربندی را به مسیر نسبی اشاره کنید:

yaml
display:
  status_phrases:
    path: status_phrases/whatsapp.yaml  # نسبی به HERMES_HOME
    mode: append                        # append (پیش‌فرض) یا replace

فایل‌های عبارت یک سطح‏ (status، ‏generic) را به فهرستی از رشته‌ها نگاشت می‌کنند‏ (حداکثر ۸۰ عبارت به‌ازای-سطح، ۱۶۰ کاراکتر هرکدام). مسیرهای مطلق و فرارهای .. نادیده گرفته می‌شوند تا پیکربندی قابل‌حمل بماند. فقط رشته‌های عبارتِ پیکربندی‌شدهٔ شما استفاده می‌شوند — آرگومان‌های خام ابزار، فرمان‌ها و متن استدلال هرگز در عبارت وضعیت درج نمی‌شوند.

مهرهای زمانی پیام در زمینهٔ مدل

پیش‌فرض خاموش. وقتی فعال باشد، هرمس یک مهر زمانی انسانی‌خوان‏ (مثل [Tue 2026-04-28 13:40:53 CEST]) روی هر پیام کاربر در زمینهٔ مدل پیشوند می‌کند تا ایجنت بداند پیام‌ها کِی فرستاده شده‌اند — برای استدلال زمانی مفید است. به پیام‌های دستیار یا پرامپت سیستمی اضافه نمی‌شود. رونوشت‌های ماندگار همیشه تمیز می‌مانند — مهر به‌صورت فرادادهٔ پیام صرف‌نظر از این سوییچ ذخیره می‌شود، پس فعال‌کردن بعدی مهرهای پیام‌های گذشته را هم ظاهر می‌کند و بازپخش هرگز پیشوندهای تکراری انبار نمی‌کند.

yaml
gateway:
  message_timestamps:
    enabled: false   # true برای نمایش زمان-ارسال به مدل

وقتی پیشرفت فعال است، بات حین کار پیام‌های وضعیت می‌فرستد:

نمونه
💻 `ls -la`...
🔍 web_search...
📄 web_extract...
🐍 execute_code...

۱۲ نشست‌های پس‌زمینه

پرامپتی را در نشست پس‌زمینهٔ جداگانه اجرا کنید تا ایجنت مستقل رویش کار کند در حالی که چت اصلی‌تان پاسخگو می‌ماند:

فرمان در چت
/background Check all servers in the cluster and report any that are down

هرمس بلافاصله تأیید می‌کند:

خروجی
🔄 Background task started: "Check all servers in the cluster..."
   Task ID: bg_143022_a1b2c3

هر پرامپت /background یک نمونهٔ ایجنت جداگانه تولید می‌کند که غیرهم‌زمان اجرا می‌شود: نشست ایزوله با تاریخچهٔ خودش‏ (هیچ دانشی از زمینهٔ چت فعلی ندارد)؛ همان پیکربندی‏ (مدل، ارائه‌دهنده، تول‌ست‌ها و مسیریابی ارث‌بری از گیت‌وی فعلی)؛ غیرمسدودکننده؛ و نتیجه وقتی کار تمام شد به همان چت/کانالی که فرمان را دادید با پیشوند «✅ Background task complete» فرستاده می‌شود‏ (یا «❌ Background task failed» با خطا).

اعلان‌های پروسهٔ پس‌زمینه

وقتی ایجنتِ نشستِ پس‌زمینه از terminal(background=true) برای شروع پروسه‌های بلندمدت‏ (سرورها، بیلدها و غیره) استفاده کند، گیت‌وی می‌تواند به‌روزرسانی وضعیت به چت‌تان پوش کند. با display.background_process_notifications کنترلش کنید:

yaml
display:
  background_process_notifications: concise    # concise | all | result | error | off
حالتچه می‌گیرید
conciseپیام وضعیت یک‌خطی هنگام تکمیل؛ شکست‌ها یک دنبالهٔ کوتاه خروجی می‌افزایند (پیش‌فرض)
allبه‌روزرسانی خروجی-در-اجرا و پیام نهایی خروجی-خام
resultفقط پیام نهایی خروجی-خام‏ (صرف‌نظر از کد خروج)
errorفقط پیام نهایی وقتی کد خروج غیرصفر است
offهیچ پیام ناظر-پروسه‌ای

با متغیر محیطی هم می‌شود: ‏HERMES_BACKGROUND_NOTIFICATIONS=result. موارد استفاده: پایش سرور، بیلدهای طولانی، کارهای پژوهشی و عملیات فایل — همه شلیک-و-رها؛ نتایج خودکار در همان چت می‌رسند.

۱۳ مدیریت سرویس

لینوکس (systemd)

bash
hermes gateway install               # نصب به‌عنوان سرویس کاربر
hermes gateway start                 # شروع سرویس
hermes gateway stop                  # توقف سرویس
hermes gateway status                # بررسی وضعیت
journalctl --user -u hermes-gateway -f  # دیدن لاگ‌ها

# فعال‌سازی linger (ادامهٔ اجرا پس از خروج)
sudo loginctl enable-linger $USER

# یا نصب سرویس سیستمیِ زمان-بوت که همچنان به‌عنوان کاربر شما اجرا می‌شود
sudo hermes gateway install --system
sudo hermes gateway start --system
sudo hermes gateway status --system
journalctl -u hermes-gateway -f

روی لپ‌تاپ و ماشین‌های dev سرویس کاربر را استفاده کنید. روی VPS یا هاست‌های headless که باید هنگام بوت برگردند بدون اتکا به linger، سرویس سیستمی.

⛔ دراپ-اینِ کشتنِ ExecStopPost سفارشی اضافه نکنید

یونیتی که هرمس نصب می‌کند از قبل با KillMode=mixed + ‏KillSignal=SIGTERM تمیز خاموش می‌شود و از Restart=always با RestartForceExitStatus استفاده می‌کند تا به‌روزرسانی‌ها و /restart درست respawn شوند. یک دراپ-این systemd مثل ExecStopPost=/bin/kill -9 $MAINPID اضافه نکنید — ‏ExecStopPost روی هر توقف شامل ری‌استارت‌های تمیز شلیک می‌شود، پس نمونهٔ تازه-تولیدشده را پیش از پایداری SIGKILL می‌کند و Restart=always بلافاصله دوباره تولیدش می‌کند. نتیجه حلقهٔ بی‌نهایت ری‌استارت است (و روی تلگرام، سیل پیام‌های ری‌استارت). اگر چنین دراپ‌اینی گذاشته‌اید حذفش کنید: systemctl --user edit hermes-gateway و خط ExecStopPost را پاک، سپس systemctl --user daemon-reload.

💡 VMهای headless: سرویس کاربر + linger از پرامپت‌های root اجتناب می‌کند

سرویس سیستمی برای هر ری‌استارت root می‌خواهد — از جمله ری‌استارت خودکار گیت‌وی در پایان hermes update. وقتی hermes update به‌عنوان کاربر غیر-root اجرا می‌شود، ‏sudo بدون-رمز systemctl را امتحان می‌کند؛ اگر نبود، ری‌استارت را رد و فرمان دستی را چاپ می‌کند‏ (هرگز روی پرامپت رمز تعاملی بلاک نمی‌شود). برای VMای که هرگز لاگین نمی‌کنید، سرویس کاربر با linger همان رفتار شروع-هنگام-بوت را بدون دخالت root می‌دهد. پس از آن hermes update می‌تواند بدون هیچ امتیازی گیت‌وی را ری‌استارت کند. اگر سرویس سیستمی را ترجیح می‌دهید، یا به‌روزرسانی‌ها را با sudo hermes update اجرا کنید یا sudo بدون-رمز برای systemctl بدهید.

از نصب هم‌زمان یونیت‌های کاربر و سیستم خودداری کنید مگر واقعاً منظورتان باشد — هرمس هشدار می‌دهد چون رفتار start/stop/status مبهم می‌شود. برای نصب‌های چندگانه، هر HERMES_HOME نام سرویس خودش را می‌گیرد‏ (hermes-gateway برای پیش‌فرض؛ hermes-gateway-<hash> برای بقیه) و فرمان‌های hermes gateway خودکار سرویس درست را هدف می‌گیرند.

مک (launchd)

bash
hermes gateway install               # نصب به‌عنوان launchd agent
hermes gateway start                 # شروع سرویس
hermes gateway stop                  # توقف سرویس
hermes gateway status                # بررسی وضعیت
tail -f ~/.hermes/logs/gateway.log   # دیدن لاگ‌ها

plist تولیدشده در ~/Library/LaunchAgents/ai.hermes.gateway.plist می‌نشیند و شامل سه متغیر محیطی است: PATH‏ (کل شل‌PATH شما هنگام نصب، با bin/ مربوط به venv و node_modules/.bin پیشوندشده تا ابزارهای کاربرنصب برای زیرپروسه‌های گیت‌وی مثل پل واتساپ موجود باشند)؛ VIRTUAL_ENV؛ و HERMES_HOME. ‏plistهای launchd ایستا‌اند — اگر بعد از راه‌اندازی گیت‌وی ابزار جدیدی نصب کردید‏ (نسخهٔ جدید Node با nvm یا ffmpeg با Homebrew) دوباره hermes gateway install اجرا کنید تا PATH به‌روز گرفته شود؛ گیت‌وی plist کهنه را تشخیص و خودکار بارگذاری مجدد می‌کند.

۱۵ بهره‌برداری از گیت‌وی چندپلتفرمی

فرمان /platform

وقتی گیت‌وی اجراست، از هر نشست CLI یا چتِ متصل با فرمان /platform آداپتورهای تکی را بدون ری‌استارت کل گیت‌وی بازبینی و هدایت کنید:

فرمان‌ها
/platform list                  # نمایش همهٔ آداپتورها و وضعیتشان
/platform pause <name>          # توقف اعزام پیام‌های جدید به یک آداپتور
/platform resume <name>         # بازفعال‌سازی آداپتور متوقف‌شده

/platform list نشان می‌دهد هر آداپتور running، ‏paused (دستی) یا paused-by-breaker است. توقف، آداپتور را بارگذاری و حلقه‌های پس‌زمینه‌اش را زنده نگه می‌دارد — پیام‌های ورودی روی زمین انداخته می‌شوند، ولی خود اتصال باز می‌ماند تا resume آنی باشد.

قطع‌کنندهٔ مدار خودکار

هر آداپتور در یک قطع‌کنندهٔ مدار پیچیده شده. شکست‌های مکررِ قابل-retry‏ (لرزش شبکه، پاسخ‌های محدودیت-نرخ، ‏۵xx بالادستی، قطع websocket) قطع‌کننده را وامی‌اندازند — آداپتور خودکار متوقف، اعلان اپراتوری به کانال خانگی پلتفرم زندهٔ دیگری وقتی پیکربندی شده فرستاده و یک خط لاگ ساخت‌یافته صادر می‌شود.

قطع‌کننده خودکار resume نمی‌شود — تا وقتی دستی /platform resume <name> نکنید باز می‌ماند. عمدی است: اگر پلتفرمی در قطعیِ پایدار است، نمی‌خواهید گیت‌وی اتصال‌مجدد بزند. وقتی آداپتوری متوقف است بررسی کنید: ‏(۱) لاگ گیت‌وی‏ (~/.hermes/logs/gateway.log یا لاگ یونیت) با جستجوی نام پلتفرم و circuit breaker؛ ‏(۲) خروجی /platform list؛ ‏(۳) صفحهٔ وضعیت ارائه‌دهنده. وقتی بالادستی سالم شد، resume قطع‌کننده را پاک و آداپتور را مسلح می‌کند.

اعلان‌های ری‌استارت

وقتی گیت‌وی ری‌استارت می‌شود‏ (یا با نشست‌های در-پرواز خاموش)، می‌تواند پیام یک‌بارهٔ «ایجنت برگشت» / «ایجنت قطع شد» به کانال خانگی هر پلتفرم بفرستد. با پرچم gateway_restart_notification در gateway-config.yaml به‌ازای-پلتفرم کنترل می‌شود‏ (پیش‌فرض true). روی پلتفرم‌های پونویز/کم‌اولویت غیرفعال و روی چت اصلی روشنش نگه دارید. اعلون یک‌باره به‌ازای-ری‌استارت است، صرف‌نظر از شمار نشست‌های در-پرواز.

نشانگرهای تایپینگ

حین پردازش پیام، گیت‌وی وضعیت تایپ زنده روی پلتفرم‌های پشتیبان‌کننده نشان می‌دهد — حباب «typing…» روی تلگرام/دیسکورد/سیگنال یا وضعیت دستیار «is thinking…» روی اسلک. با پرچم typing_indicator به‌ازای-پلتفرم کنترل می‌شود‏ (پیش‌فرض true). برخی اسلک‌ها وضعیت «is thinking…» را پونویز می‌دانند‏ (جعبهٔ نگارش را هم لحظه‌ای غیرفعال می‌کند چون از Assistant API اسلک استفاده می‌کند). غیرفعال‌کردن فقط نشانگر را سرکوب می‌کند — تحویل پیام و بقیه بدون تغییر. پرچم عمومی است و برای همهٔ پلتفرم‌ها کار می‌کند.

ازسرگیری نشست در سراسر ری‌استارت‌ها

وقتی گیت‌وی با فراخوانی ابزار یا تولیدِ در-پرواز خاموش می‌شود، نشست‌های متأثر restart_interrupted علامت می‌خورند. در استارتاپ بعدی، گیت‌وی برای هرکدام یک ازسرگیری خودکار زمان‌بندی می‌کند — کاربر یک خبر کوتاه در چت می‌گیرد‏ («بعد از ری‌استارت هر پیامی بفرست تا از همان‌جا که بودید ادامه بدهم») و نشست با پاسخ او از آخرین نوبتِ ثبت‌شده ادامه می‌یابد. این رفتار پیش‌فرض روشن است و نیازی به پیکربندی ندارد.

پیش‌فرض‌های پیشرفت موبایل‌دوست

تلگرام معمولاً اینباکس موبایل است، پس پیش‌فرض‌ها برای آن سطح تنظیم شده‌اند: tool_progress پیش‌فرض خاموش (بدون جریان ردپای به‌ازای-ابزار که چت را پر کند)؛ ‏busy_ack_detail پیش‌فرض خاموش (تأییدها و ضربان‌ها مختصر می‌مانند)؛ ‏interim_assistant_messages روشن می‌ماند (توضیح واقعی میان-نوبت سیگنال است نه نویز)؛ و long_running_notifications روشن می‌ماند (یک حباب «⏳ Working — N min» با ویرایش درجا هر چند دقیقه به‌روز می‌شود تا ضربان داشته باشید). برای بازگشت به پیشرفت پرگویانه به‌ازای-پلتفرم:

yaml
display:
  platforms:
    telegram:
      tool_progress: new               # بازفعال‌سازی جریان پیشرفت ابزار
      busy_ack_detail: true           # نمایش "iteration N/M, running: tool"
      interim_assistant_messages: false   # یا کاملاً ساکت
      long_running_notifications: false

پاکسازی حباب‌های پیشرفت (اختیاری)

پیام‌های پیشرفت ابزار، ضربانِ «هنوز کار می‌کند…» و حباب‌های callback وضعیت می‌توانند پس از فرود پاسخ نهایی خودکار حذف شوند. به‌ازای-پلتفرم با display.platforms.<platform>.cleanup_progress فعال کنید‏ (پیش‌فرض false؛ فقط پلتفرم‌هایی که delete_message پیاده کرده‌اند‏ — فعلاً تلگرام و دیسکورد — آن را رعایت می‌کنند). اجراهای شکست‌خورده پاکسازی را رد می‌کنند تا حباب‌ها به‌عنوان ردپا بمانند.
