راه‌اندازی Matrix

هرمس ایجنت با Matrix، پروتکل پیام‌رسانی باز و فدرال، یکپارچه می‌شود. Matrix اجازه می‌دهد هوم‌سرور خودتان را اجرا کنید یا از عمومی مثل matrix.org استفاده کنید — به هر حال کنترل ارتباطات با شماست. بات از طریق SDK پایتونی ‏mautrix وصل می‌شود، پیام‌ها را از خط‌لولهٔ هرمس ایجنت ‏(شامل استفاده از ابزار، حافظه و استدلال) عبور می‌دهد و در لحظه پاسخ می‌دهد. متن، پیوست فایل، تصویر، صوت، ویدیو و رمزنگاری سرتاسری اختیاری ‏(E2EE) را پشتیبانی می‌کند.

هرمس با هر هوم‌سرور Matrixی کار می‌کند — Synapse، ‏Conduit، ‏Dendrite یا matrix.org.

پیش از راه‌اندازی، بخشی که بیشتر افراد می‌خواهند بدانند: رفتار هرمس پس از اتصال چگونه است.

۱ رفتار هرمس

زمینهرفتار
پیام‌های خصوصی ‏(DM)هرمس به همهٔ پیام‌ها پاسخ می‌دهد؛ نیازی به منشن نیست. هر DM نشست مستقل دارد. برای شروع ترد وقتی در DM منشن شود ‏MATRIX_DM_MENTION_THREADS=true را بگذارید.
اتاق‌هابه‌طور پیش‌فرض هرمس برای پاسخ منشن لازم دارد. برای اتاق‌های پاسخ-آزاد ‏MATRIX_REQUIRE_MENTION=false کنید یا شناسهٔ اتاق‌ها را به ‏MATRIX_FREE_RESPONSE_ROOMS بیفزایید. دعوت‌های اتاق خودکار پذیرفته می‌شوند.
تردهاهرمس تردهای Matrix ‏(MSC3440) را پشتیبانی می‌کند. اگر داخل تردی ریپلای بدهید، هرمس زمینهٔ ترد را از خط‌زمان اصلی اتاق ایزوله نگه می‌دارد. تردهایی که بات قبلاً در آن‌ها بوده منشن نمی‌خواهند.
ساخت خودکار تردبه‌طور پیش‌فرض هرمس برای هر پیامی که در یک اتاق به آن پاسخ می‌دهد ترد می‌سازد تا گفتگوها ایزوله بمانند. با ‏MATRIX_AUTO_THREAD=false خاموشش کنید. برای ساخت خودکار ترد برای DM ها هم ‏MATRIX_DM_AUTO_THREAD=true ‏(پیش‌فرض false)؛ این جدا از ‏MATRIX_DM_MENTION_THREADS است که فقط وقتی در DM منشن شود ترد می‌سازد.
فرمان‌هاهرمس ‏/commands عادی را وقتی کلاینت Matrix شما ارسالشان کند می‌پذیرد. اگر کلاینت‌تان / را برای فرمان‌های محلی رزرو کرده، به‌جایش از ‏!commands استفاده کنید؛ هرمس نام‌های جایگزین شناخته‌شدهٔ ‏!command را به ‏/command نرمال می‌کند.
کنترل‌های تعاملیتأیید فرمان خطرناک و انتخاب /model می‌توانند از واکنش‌های Matrix استفاده کنند. واکنش‌های تأیید را می‌توان فقط به کاربرِ درخواست‌کننده محدود کرد.
تفکر و فعالیت ابزار‏Matrix وقتی پیشرفت گیت‌وی فعال باشد از پنل‌های تفکر/فعالیت-ابزار تردی و قابل‌ویرایش استفاده می‌کند تا به‌روزرسانی‌ها خط‌زمان اصلی اتاق را سیل‌بار نکنند.
اتاق‌های مشترک چندکاربرهبه‌طور پیش‌فرض هرمس تاریخچهٔ نشست را داخل اتاق به‌ازای هر کاربر جدا می‌کند. دو نفر که در یک اتاق حرف می‌زنند مگر صریحاً غیرفعالش کنید رونویسی مشترک ندارند.
💡 نکته

بات هنگام دعوت خودکار به اتاق‌ها می‌پیوندد. کافی است کاربر Matrix بات را به هر اتاقی دعوت کنید؛ می‌پیوندد و شروع به پاسخ می‌کند.

مدل نشست در Matrix

به‌طور پیش‌فرض:

  • هر DM نشست مستقل خودش را دارد
  • هر ترد فضای‌نام نشست خودش را دارد
  • هر کاربر در یک اتاق مشترک، داخل همان اتاق نشست خودش را دارد

این با config.yaml کنترل می‌شود:

yaml
group_sessions_per_user: true

فقط اگر صریحاً یک گفتگوی مشترک برای کل اتاق می‌خواهید false کنید:

yaml
group_sessions_per_user: false

نشست مشترک برای اتاق مشارکتی مفید است ولی یعنی:

  • کاربران در رشد زمینه و هزینهٔ توکن شریک‌اند
  • یک کار سنگین-ابزارِ طولانیِ یک نفر می‌تواند زمینهٔ بقیه را متورم کند
  • اجرای در-جریانِ یک نفر می‌تواند پیام بعدیِ فرد دیگری در همان اتاق را قطع کند

پیکربندی منشن و تردینگ

رفتار منشن و ترد خودکار را با env یا config.yaml تنظیم کنید:

yaml
matrix:
  require_mention: true           # منشن در اتاق‌ها لازم باشد (پیش‌فرض: true)
  allowed_users:                  # کاربران Matrix مجازِ فعال‌کردن نوبت ایجنت
    - "@alice:matrix.org"
  allowed_rooms:                  # اتاق‌های مجازِ فعال‌کردن نوبت ایجنت
    - "!abc123:matrix.org"
  free_response_rooms:            # اتاق‌های معاف از شرط منشن
    - "!abc123:matrix.org"
  ignore_user_patterns:           # کاربران شبح پل/appservice برای نادیده‌گرفتن
    - "^@telegram_"
    - "^@whatsapp_"
  process_notices: false          # نادیده گرفتن m.notice به‌طور پیش‌فرض
  session_scope: room             # auto|room|thread؛ room برای اتاق‌های پروژه توصیه می‌شود
  auto_thread: true               # ساخت خودکار ترد برای پاسخ‌ها (پیش‌فرض: true)
  dm_mention_threads: false       # ترد هنگام منشن در DM (پیش‌فرض: false)
  max_message_length: 16000       # حجم chunk خروجی به کاراکتر (پیش‌فرض: 16000، بیشینه: 65535)

یا با متغیرهای محیطی:

bash
MATRIX_REQUIRE_MENTION=true
MATRIX_ALLOWED_USERS=@alice:matrix.org
MATRIX_ALLOWED_ROOMS=!abc123:matrix.org
MATRIX_FREE_RESPONSE_ROOMS=!abc123:matrix.org,!def456:matrix.org
MATRIX_IGNORE_USER_PATTERNS='^@telegram_,^@whatsapp_'
MATRIX_PROCESS_NOTICES=false
MATRIX_SESSION_SCOPE=room       # توصیه‌شده برای زمینهٔ پایدار اتاق پروژه
MATRIX_AUTO_THREAD=true
MATRIX_DM_MENTION_THREADS=false
MATRIX_REACTIONS=true          # پیش‌فرض: true — واکنش ایموجی حین پردازش
MATRIX_ALLOW_ROOM_MENTIONS=false
💡 خاموش‌کردن واکنش‌ها

‏MATRIX_REACTIONS=false واکنش‌های چرخه-حیات-پردازش ‏(👀/✅/❌) که بات روی پیام‌های ورودی می‌گذارد را خاموش می‌کند. برای اتاق‌هایی که رویدادهای واکنش پرسر و صدایند یا همهٔ کلاینت‌ها پشتیبانی نمی‌کنند مفید است.

💡 منشن سراسر اتاق

هرمس برای شناسه‌های Matrix صریح مثل ‏@alice:example.org منشن ساختاریافتهٔ کاربر می‌فرستد. اعلان‌های سراسر-اتاقِ ‏@room پیش‌فرض غیرفعال‌اند؛ ‏MATRIX_ALLOW_ROOM_MENTIONS=true را فقط در اتاق‌هایی بگذارید که بات حق بیدارکردن همه را دارد.

📌 یادداشت مهاجرت

اگر از نسخه‌ای بدون MATRIX_REQUIRE_MENTION ارتقا می‌دهید، بات قبلاً به همهٔ پیام‌های اتاق‌ها جواب می‌داد. برای حفظ آن رفتار ‏MATRIX_REQUIRE_MENTION=false بگذارید.

ایزوله‌سازی اتاق پروژه

اگر همان بات Matrix را در چند اتاق پروژه استفاده می‌کنید، نشست‌های پایدارِ اتاق-محور را پیکربندی کنید:

bash
MATRIX_SESSION_SCOPE=room
MATRIX_AUTO_THREAD=false

‏MATRIX_SESSION_SCOPE این‌ها را می‌پذیرد:

دامنهرفتار
autoپیش‌فرض سازگار رو به عقب. رفتار موجود ‏MATRIX_AUTO_THREAD تردهای مصنوعی را کنترل می‌کند.
roomپیام‌های بی‌ترد اتاق در یک نشست پایدار اتاق می‌مانند. تردهای واقعی Matrix همچنان از ریشهٔ ترد خودشان استفاده می‌کنند.
threadپیام‌های بی‌ترد اتاق از شناسهٔ رویداد تریگر یک ترد/نشست مصنوعی می‌سازند.

هرمس الان نام فعلی اتاق Matrix، شناسهٔ اتاق، موضوع، شناسهٔ پیام و یک یادداشت مرز-اتاق Matrix را داخل پرامپت ایجنت می‌گذارد. ‏/status هم دامنهٔ فعلی اتاق/نشست Matrix را نشان می‌دهد و ‏/resume مگر صریحاً ‏/resume --cross-room <session name> بزنید، نشست نام‌دار اتاق دیگری را بی‌صدا ازسر نمی‌گیرد.

‏MATRIX_SESSION_SCOPE=room لاین اتاق/ترد را کنترل می‌کند. تنظیم موجود group_sessions_per_user همچنان تعیین می‌کند کاربران داخل آن اتاق لاین را شریک شوند یا نه. با ‏true ‏(پیش‌فرض) آلیس و باب نشست‌های جدا Project B می‌گیرند. با ‏false اتاق یک رونویسی مشترک Project B دارد.

این راهنما کل فرایند راه‌اندازی را قدم‌به‌قدم توضیح می‌دهد — از ساخت حساب بات تا ارسال اولین پیام.

۲ گام ۱: ساخت حساب بات

برای بات به یک حساب کاربری Matrix نیاز دارید. چند راه دارید:

گزینهٔ A: ثبت‌نام روی هوم‌سرور خودتان ‏(توصیه‌شده)

اگر هوم‌سرور خودتان را اجرا می‌کنید ‏(Synapse، ‏Conduit، ‏Dendrite):

bash
# مثال Synapse
register_new_matrix_user -c /etc/synapse/homeserver.yaml http://localhost:8008

یوزرنیمی مثل hermes انتخاب کنید — شناسهٔ کامل کاربر می‌شود ‏@hermes:your-server.org.

گزینهٔ B: استفاده از matrix.org یا هوم‌سرور عمومی دیگر

  1. به Element Web بروید و حساب جدید بسازید.
  2. یوزرنیمی برای بات‌تان انتخاب کنید ‏(مثل hermes-bot).

گزینهٔ C: استفاده از حسابتان

می‌توانید هرمس را به‌عنوان کاربر خودتان اجرا کنید. یعنی بات به‌عنوان شما پست می‌کند — برای دستیارهای شخصی مفید است.

۳ گام ۲: دریافت توکن دسترسی

هرمس برای احراز نزد هوم‌سرور به access token نیاز دارد. دو گزینه دارید:

گزینهٔ A: توکن دسترسی ‏(توصیه‌شده)

قابل‌اعتمادترین راه گرفتن توکن:

از طریق Element:

  1. با حساب بات وارد Element شوید.
  2. به Settings ← Help & About بروید.
  3. به پایین اسکرول و بخش Advanced را باز کنید — توکن دسترسی آنجاست.
  4. فوراً کپیش کنید.

از طریق API:

bash
curl -X POST https://your-server/_matrix/client/v3/login \
  -H "Content-Type: application/json" \
  -d '{
    "type": "m.login.password",
    "user": "@hermes:your-server.org",
    "password": "your-password"
  }'

پاسخ فیلد access_token را دارد — کپیش کنید.

⚠️ توکن دسترسی را امن نگه دارید

توکن دسترسی دسترسی کامل به حساب Matrix بات می‌دهد. هرگز عمومی به اشتراکش نگذارید یا به گیت کامیتش نکنید. اگر لو رفت، با خروج‌دادن همهٔ نشست‌های آن کاربر ابطالش کنید.

گزینهٔ B: ورود با رمز عبور

به‌جای توکن دسترسی می‌توانید شناسهٔ کاربر و رمز بات را بدهید. هرمس هنگام شروع خودکار لاگین می‌کند. ساده‌تر است ولی یعنی رمز در فایل .env ذخیره می‌شود.

bash
MATRIX_USER_ID=@hermes:your-server.org
MATRIX_PASSWORD=your-password

۴ گام ۳: یافتن شناسهٔ کاربری Matrix

هرمس ایجنت از شناسهٔ کاربری Matrix شما برای کنترل اینکه چه کسی با بات تعامل کند استفاده می‌کند. شناسه‌های کاربر Matrix قالب @username:server دارند.

برای یافتن شناسه‌تان:

  1. Element ‏(یا کلاینت دلخواه Matrix‌تان) را باز کنید.
  2. روی آواتار کلیک ← Settings.
  3. شناسهٔ کاربری بالای پروفایل نمایش داده می‌شود ‏(مثل @alice:matrix.org).
💡 نکته

شناسه‌های کاربر Matrix همیشه با @ شروع و : به‌اضافهٔ نام سرور دارند. مثلاً: ‏@alice:matrix.org، ‏@bob:your-server.com.

۵ گام ۴: پیکربندی هرمس ایجنت

گزینهٔ A: راه‌اندازی تعاملی ‏(توصیه‌شده)

bash
hermes gateway setup

هنگام پرسش Matrix را انتخاب کنید و URL هوم‌سرور، توکن دسترسی ‏(یا شناسهٔ کاربر + رمز) و شناسه‌های کاربر مجاز را بدهید.

گزینهٔ B: پیکربندی دستی

این‌ها را به ~/.hermes/.env اضافه کنید:

با توکن دسترسی:

bash
# الزامی
MATRIX_HOMESERVER=https://matrix.example.org
MATRIX_ACCESS_TOKEN=***

# اختیاری: شناسهٔ کاربر (اگر حذف شود از توکن کشف می‌شود)
# MATRIX_USER_ID=@hermes:matrix.example.org

# امنیت: محدودکردن تعامل با بات
MATRIX_ALLOWED_USERS=@alice:matrix.example.org

# اختیاری: محدودکردن اتاق‌های تریگرکنندهٔ بات
MATRIX_ALLOWED_ROOMS=!abc123:matrix.example.org

# چند کاربر مجاز (با ویرگول)
# MATRIX_ALLOWED_USERS=@alice:matrix.example.org,@bob:matrix.example.org

با ورود رمزی:

bash
# الزامی
MATRIX_HOMESERVER=https://matrix.example.org
MATRIX_USER_ID=@hermes:matrix.example.org
MATRIX_PASSWORD=***

# امنیت
MATRIX_ALLOWED_USERS=@alice:matrix.example.org

مقاوم‌سازی استقرار خصوصی

برای استقرارهای خصوصی Matrix هم لیست مجاز کاربر هم اتاق را بگذارید. اگر ‏MATRIX_ALLOWED_USERS تنظیم نباشد هر فرستنده‌ای که در اتاق عضوشده به بات برسد می‌تواند نوبت ایجنت تریگر کند. اگر ‏MATRIX_ALLOWED_ROOMS تنظیم نباشد هر اتاقی که بات به آن می‌پیوندد می‌تواند تریگر کند. یک استقرار قفل‌شده هر دو را می‌گذارد:

bash
MATRIX_ALLOWED_USERS=@alice:matrix.example.org,@bob:matrix.example.org
MATRIX_ALLOWED_ROOMS=!ops:matrix.example.org,!dmroom:matrix.example.org

استقرارهای پل و appservice به محافظت اضافی حلقه نیاز دارند. هرمس همیشه رویدادهای خودش، کاربران appservice-گونه‌ای که localpart شان با _ شروع می‌شود، شناسه‌های رویداد تکراری، رویدادهای قدیمیِ شروع، رویدادهای جایگزینی ویرایش و رویدادهای m.notice را به‌طور پیش‌فرض نادیده می‌گیرد. وقتی پل شما قرارداد نام‌گذاری متفاوتی دارد الگوهای شبح مخصوص همان استقرار را اضافه کنید:

bash
MATRIX_IGNORE_USER_PATTERNS='^@telegram_,^@slack_,^@whatsapp_'

‏notice ها را فقط وقتی یک گردش‌کار انسانیِ مطمئن واقعاً m.notice می‌فرستد فعال کنید:

bash
MATRIX_PROCESS_NOTICES=true

اعلان‌های سراسر-اتاق خروجی پیش‌فرض خاموش‌اند. ‏MATRIX_ALLOW_ROOM_MENTIONS=false را نگه دارید مگر اینکه بات صریحاً حق بیدارکردن کل اتاق با @room را داشته باشد.

payload های تشخیص و دیباگ توکن‌های دسترسی Matrix، کلیدهای بازیابی، شناسه‌های دستگاه و بدنهٔ پیام‌ها را سانسور می‌کنند. دانلود رسانه به URIهای محتوای ‏mxc:// محدود و در عبور از ‏MATRIX_MAX_MEDIA_BYTES رد می‌شود. اتاق‌های فدرال و هوم‌سرورهای غیرقابل‌اعتماد را ورودی غیرقابل‌اعتماد تلقی کنید: لیست‌مجاز اتاق‌ها را تنگ نگه دارید، برای کار سنگین-ابزار DM یا اتاق خصوصی را ترجیح دهید و از مجوز دادن به شبح‌های پل یا عروسک‌های appservice به‌عنوان کاربر مجاز بپرهیزید.

تنظیم رفتاری اختیاری در config.yaml:

yaml
group_sessions_per_user: true
  • ‏group_sessions_per_user: true زمینهٔ هر شرکت‌کننده را داخل اتاق‌های مشترک ایزوله نگه می‌دارد

شروع گیت‌وی

بعد از پیکربندی، گیت‌وی Matrix را شروع کنید:

bash
hermes gateway

بات باید ظرف چند ثانیه به هوم‌سرور وصل و sync را شروع کند. برای تست بهش پیام بدهید — DM یا در اتاقی که پیوسته.

💡 نکته

می‌توانید hermes gateway را در پس‌زمینه یا به‌صورت سرویس systemd برای عملکرد مداوم اجرا کنید. جزئیات در مستندات استقرار.

۶ رمزنگاری سرتاسری ‏(E2EE)

هرمس از رمزنگاری سرتاسری Matrix پشتیبانی می‌کند، پس می‌توانید در اتاق‌های رمزنگاری‌شده با بات چت کنید.

پیش‌نیازها

E2EE کتابخانهٔ ‏mautrix با extras رمزنگاری و کتابخانهٔ C ‏libolm می‌خواهد:

bash
# نصب mautrix با پشتیبانی E2EE
pip install 'mautrix[encryption]'

# یا نصب با extras هرمس
cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

همچنین libolm باید روی سیستم نصب باشد:

bash
# Debian/Ubuntu
sudo apt install libolm-dev

# macOS
brew install libolm

# Fedora
sudo dnf install libolm-devel

فعال‌سازی E2EE

به ~/.hermes/.env اضافه کنید:

bash
MATRIX_E2EE_MODE=required
حالترفتار
offE2EE مقداردهی اولیه نمی‌شود.
optionalوقتی وابستگی‌ها موجودند E2EE را امتحان می‌کند ولی اگر رمزنگاری مقداردهی نشود اتاق‌های بدون رمز همچنان کار می‌کنند.
requiredاگر وابستگی‌ها یا setup رمزنگاری موجود نباشد fail-closed می‌شود.

حالت optional ممکن است وقتی setup رمزنگاری در دسترس نیست به عملکرد غیر-E2EE برگردد. حالت required به‌جای تنزل بی‌صدا fail-closed می‌شود. برای سازگاری رو به عقب، ‏MATRIX_ENCRYPTION=true همچنان رفتار E2EE الزامی را فعال می‌کند.

وقتی E2EE فعال است هرمس:

  • کلیدهای رمزنگاری را در ~/.hermes/platforms/matrix/store/ ذخیره می‌کند ‏(نصب‌های قدیمی: ~/.hermes/matrix/store/)
  • کلیدهای دستگاه را در اولین اتصال آپلود می‌کند
  • پیام‌های ورودی را خودکار decrypt و خروجی‌ها را encrypt می‌کند
  • هنگام دعوت به اتاق‌های رمزنگاری‌شده خودکار می‌پیوندد

ابزارها و کنترل‌های Matrix

در گفتگوهای Matrix هرمس ابزارهای مخصوص Matrix را به ایجنت می‌دهد:

  • ‏matrix_send_reaction
  • ‏matrix_redact_message
  • ‏matrix_create_room
  • ‏matrix_invite_user
  • ‏matrix_fetch_history
  • ‏matrix_set_presence

این ابزارها به زمینه‌های Matrix محدودند و در تول‌ست‌های غیر-Matrix در دسترس نیستند. ابزارهای ادمین‌گونه پیش‌فرض خاموش‌اند: ‏redaction نیازمند ‏MATRIX_TOOLS_ALLOW_REDACTION=true، دعوت نیازمند ‏MATRIX_TOOLS_ALLOW_INVITES=true و ساخت اتاق نیازمند ‏MATRIX_TOOLS_ALLOW_ROOM_CREATE=true. ساخت اتاق عمومی همچنین ‏MATRIX_ALLOW_PUBLIC_ROOMS=true می‌خواهد. اگر ‏MATRIX_ALLOWED_ROOMS تنظیم باشد ابزارهای Matrix فقط می‌توانند آن اتاق‌ها را هدف بگیرند.

کنترل‌های واکنش:

  • ✅ تأیید یک‌بار
  • ♾️ تأیید همیشه
  • ❌ رد
  • واکنش‌های عددی برای گزینه‌های /model

اگر عمداً می‌خواهید هر کاربر مجاز Matrix در اتاق بتواند پرامپت تأیید/انتخاب‌گر مدل را عملیاتی کند ‏MATRIX_APPROVAL_REQUIRE_SENDER=false بگذارید. پیش‌فرض، وقتی هرمس بداند چه کسی اکشن را خواسته، مقید-به-همان-درخواست‌کننده است.

سقف‌های رسانه

هرمس تصاویر، فایل‌ها، صدا و ویدیوی Matrix را از طریق APIهای رسانه Matrix آپلود/دانلود می‌کند. چند تصویر تولیدی به‌عنوان یک batch منطقی مرتب فرستاده می‌شوند و کپشن و زمینهٔ ترد در طول batch حفظ می‌شود.

به‌طور پیش‌فرض رسانهٔ Matrix بالای ۱۰۰ مگابایت قبل از آپلود/دانلود رد می‌شود. override:

bash
MATRIX_MAX_MEDIA_BYTES=104857600

رسانهٔ ورودی باید URI محتوای ‏mxc:// Matrix باشد. هرمس URLهای رسانه‌ای HTTP(S) دلخواه را در رویدادهای Matrix رد می‌کند تا یک اتاق فدرال به دانلودکنندهٔ بدون محدودیت تبدیل نشود.

تأیید امضای متقاطع ‏(توصیه‌شده)

اگر حسابتان امضای متقاطع ‏(cross-signing) دارد ‏(پیش‌فرض Element)، کلید بازیابی را بدهید تا بات هنگام شروع دستگاهش را self-sign کند. بدون این، سایر کلاینت‌های Matrix ممکن است بعد از چرخش کلید دستگاه از اشتراک نشست‌های رمزنگاری با بات خودداری کنند.

bash
MATRIX_RECOVERY_KEY=EsT... your recovery key here

کجا پیدا می‌شود: در Element به ‏Settings ← Security & Privacy ← Encryption بروید ← کلید بازیابی‌تان ‏(با نام «Security Key» هم معروف). همان کلیدی است که موقع راه‌اندازی اولیه cross-signing ازتان خواسته شد ذخیره کنید.

در هر شروع، اگر ‏MATRIX_RECOVERY_KEY تنظیم باشد هرمس کلیدهای cross-signing را از مخزن امن اسرار هوم‌سرور import و دستگاه فعلی را امضا می‌کند. idempotent است و امن است دائمی روشن بماند.

اگر هرمس کلید بازیابی جدید بسازد هرگز کلید خام را لاگ نمی‌کند. قبل از شروع ‏MATRIX_RECOVERY_KEY_OUTPUT_FILE=/secure/path/matrix-recovery-key.txt را بگذارید تا کلید تولیدشده یک‌بار با دسترسی فایل 0600 نوشته شود؛ فایل موجود بازنویسی نمی‌شود.

⚠️ حذف مخزن رمزنگاری

اگر ‏~/.hermes/platforms/matrix/store/crypto.db را حذف کنید بات هویت رمزنگاری‌اش را از دست می‌دهد. ری‌استارت ساده با همان device ID کامل بازیابی نمی‌شود — هوم‌سرور هنوز one-time key هایی دارد که با کلید هویت قدیمی امضا شده‌اند و طرف مقابل نمی‌تواند نشست Olm جدید بسازد.

هرمس این وضعیت را هنگام شروع تشخیص و از فعال‌کردن E2EE امتناع می‌کند و لاگ می‌کند: ‏device XXXX has stale one-time keys on the server signed with a previous identity key.

آسان‌ترین بازیابی: توکن دسترسی جدید بسازید ‏(که device ID تازه‌ای بدون تاریخچهٔ کلید کهنه می‌گیرد). بخش «ارتقا از نسخهٔ قبلی با E2EE» پایین را ببینید. مطمئن‌ترین مسیر است و دست‌زدن به دیتابیس هوم‌سرور ندارد.

بازیابی دستی ‏(پیشرفته — همان device ID حفظ می‌شود):

  1. Synapse را متوقف و دستگاه قدیمی را از دیتابیسش حذف کنید:
    bash
    sudo systemctl stop matrix-synapse
sudo sqlite3 /var/lib/matrix-synapse/homeserver.db "
  DELETE FROM e2e_device_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
  DELETE FROM e2e_one_time_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
  DELETE FROM e2e_fallback_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
  DELETE FROM devices WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
"
sudo systemctl start matrix-synapse
    یا از طریق admin API سیناپس ‏(توجه: شناسهٔ کاربر URL-encoded):
    bash
    curl -X DELETE -H "Authorization: Bearer ADMIN_TOKEN" \
  'https://your-server/_synapse/admin/v2/users/%40hermes%3Ayour-server/devices/DEVICE_ID'
    توجه: حذف دستگاه از طریق admin API ممکن است توکن دسترسی مرتبط را هم باطل کند. بعدش شاید لازم باشد توکن جدید بسازید.
  2. مخزن رمزنگاری محلی را حذف و هرمس را ری‌استارت کنید:
    bash
    rm -f ~/.hermes/platforms/matrix/store/crypto.db*
# restart hermes

سایر کلاینت‌های Matrix ‏(Element، ‏matrix-commander) ممکن است کلیدهای دستگاه قدیمی را کش کرده باشند. بعد از بازیابی در Element ‏/discardsession بزنید تا نشست رمزنگاری جدیدی با بات ساخته شود.

📌 نکته

اگر ‏mautrix[encryption] نصب نباشد یا libolm غایب باشد، بات خودکار به کلاینت ساده ‏(بدون رمز) سقوط می‌کند. هشدارش را در لاگ‌ها خواهید دید.

۷ اتاق خانگی

می‌توانید یک «اتاق خانگی» تعیین کنید که بات پیام‌های پیش‌فعال را به آن بفرستد ‏(مثل خروجی job های کرون، یادآوری‌ها و اعلان‌ها). دو راه دارد:

با فرمان اسلش

‏/sethome را در هر اتاق Matrixی که بات حضور دارد تایپ کنید. همان اتاق اتاق خانگی می‌شود. اگر کلاینت Matrix‌تان فرمان‌های اسلش را intercept می‌کند به‌جایش ‏!sethome بنویسید.

پیکربندی دستی

این را به ~/.hermes/.env اضافه کنید:

bash
MATRIX_HOME_ROOM=!abc123def456:matrix.example.org

۸ لیست‌مجاز اتاق (allowed_rooms)

بات را به مجموعهٔ ثابتی از اتاق‌های Matrix محدود کنید. با تنظیم، بات فقط در اتاق‌هایی که شناسه‌شان در فهرست است پاسخ می‌دهد — پیام‌های هر اتاق دیگری بی‌صدا نادیده گرفته می‌شوند حتی با منشن.

‏DM ها ‏(اتاق‌های گفتگوی مستقیم) از این فیلتر معاف‌اند، پس کاربران مجاز همیشه یک‌به‌یک به بات می‌رسند.

yaml
matrix:
  allowed_rooms:
    - "!abc123def456:matrix.example.org"
    - "!opsroom789:matrix.example.org"

یا با متغیر محیطی ‏(جداشده با ویرگول):

bash
MATRIX_ALLOWED_ROOMS="!abc123def456:matrix.example.org,!opsroom789:matrix.example.org"

رفتار:

  • خالی / تنظیم‌نشده ← بدون محدودیت ‏(پیش‌فرض).
  • غیرخالی ← شناسهٔ اتاق باید روی فهرست باشد. چک قبل از هر gating دیگری ‏(شرط منشن، لیست مجاز فرستنده و...) اجرا می‌شود.
  • شناسهٔ داخلی اتاق را استفاده کنید ‏(!abc...:server) نه alias‌اش ‏(#room:server). شناسهٔ داخلی اتاق در Element از مسیر Room ← Settings ← Advanced پیدا می‌شود.

همچنین ببینید: تفکیک فرمان ادمین/کاربر.

💡 نکته

برای یافتن Room ID: در Element وارد اتاق شوید ← Settings ← Advanced ← ‏Internal room ID آنجاست ‏(با ! شروع می‌شود).

۹ فرمان‌ها در Matrix

هرمس همان فرمان‌های گیت‌وی دیگر پلتفرم‌ها را در Matrix پشتیبانی می‌کند شامل ‏/commands، ‏/model، ‏/stop، ‏/queue، ‏/steer، ‏/goal، ‏/subgoal، ‏/background، ‏/bg، ‏/btw، ‏/tasks و /yolo.

بعضی کلاینت‌های Matrix / ابتدایی را برای فرمان‌های محلی کلاینت رزرو می‌کنند و ممکن است فرمان‌های اسلش ناشناخته را به اتاق نفرستند. در این صورت ! را به‌عنوان alias سازگار-با-Matrix استفاده کنید:

text
!commands
!model
!model gpt-5.5 --provider openrouter
!queue continue with the next task
!stop

هرمس ‏!command را فقط وقتی نرمال می‌کند که فرمان برای گیت‌وی شناخته شده باشد، فرمان افزونهٔ ثبت‌شده یا مهارت نصب‌شده باشد. تعجب‌های معمولی مثل ‏!important پیام چت عادی می‌مانند.

۱۰ عیب‌یابی

بات به پیام‌ها پاسخ نمی‌دهد

علت: بات به اتاق نپیوسته، ‏MATRIX_ALLOWED_USERS شناسهٔ شما را ندارد، ‏MATRIX_ALLOWED_ROOMS اتاق را ندارد، یا پیام اتاق بات را منشن نکرده.

راه‌حل: بات را به اتاق دعوت کنید — با دعوت خودکار می‌پیوندد. تأیید کنید شناسه‌تان ‏(قالب کامل @user:server) در ‏MATRIX_ALLOWED_USERS و شناسهٔ اتاق در ‏MATRIX_ALLOWED_ROOMS است اگر آن لیست پیکربندی شده. در اتاق‌ها بات را منشن کنید یا اتاق را به ‏MATRIX_FREE_RESPONSE_ROOMS اضافه کنید. گیت‌وی را ری‌استارت کنید.

بات به اتاق‌ها می‌پیوندد ولی همهٔ پیام‌ها را بی‌صدا دور می‌ریزد ‏(اختلاف ساعت)

علت: ساعت سیستمِ میزبان جلوتر از زمان واقعی است. آداپتور Matrix فیلتر grace شروع ۵ثانیه‌ای دارد ‏(event_ts < startup_ts - 5) تا رویدادهای بازپخش‌شده از sync اولیه نادیده گرفته شوند. وقتی ساعت دیواری جلو باشد هر رویداد ورودی «قدیمی‌تر از شروع» به نظر می‌رسد و قبل از رسیدن به هندلر پیام دور ریخته می‌شود — بات متصل به نظر می‌رسد ولی هرگز جواب نمی‌دهد. issue شمارهٔ ۱۲۶۱۴ را ببینید.

علامت: لاگ گیت‌وی نشان می‌دهد ‏Matrix: dropped N live events as 'too old' more than 30s after startup.

راه‌حل: ساعت میزبان را با NTP سینک و بات را ری‌استارت کنید:

bash
# Debian/Ubuntu
sudo timedatectl set-ntp true
timedatectl status   # تأیید "System clock synchronized: yes"

# macOS
sudo sntp -sS time.apple.com

«Failed to authenticate» / «whoami failed» هنگام شروع

علت: توکن دسترسی یا URL هوم‌سرور اشتباه است.

راه‌حل: تأیید کنید ‏MATRIX_HOMESERVER به هوم‌سرورتان اشاره دارد ‏(با https://، بدون اسلش انتهایی). اعتبار ‏MATRIX_ACCESS_TOKEN را چک کنید — با curl امتحانش کنید:

bash
curl -H "Authorization: Bearer YOUR_TOKEN" \
  https://your-server/_matrix/client/v3/account/whoami

اگر اطلاعات کاربر برگرداند توکن معتبر است. اگر خطا برگرداند توکن جدید بسازید.

خطای «mautrix not installed»

علت: بستهٔ پایتونی mautrix نصب نیست.

راه‌حل: نصبش کنید:

bash
pip install 'mautrix[encryption]'

یا با extras هرمس:

bash
cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

خطاهای رمزنگاری / «could not decrypt event»

علت: کلیدهای رمزنگاری غایب، ‏libolm نصب نیست، یا دستگاه بات مطمئن‌سازی نشده.

راه‌حل:

  1. تأیید کنید libolm روی سیستم نصب است ‏(بخش E2EE بالا).
  2. مطمئن شوید MATRIX_ENCRYPTION=true در .env است.
  3. در کلاینت Matrix‌تان ‏(Element) به پروفایل بات ← Sessions بروید و دستگاه بات را verify/trust کنید.
  4. اگر بات تازه به اتاق رمزنگاری‌شده‌ای پیوسته فقط پیام‌های بعد از پیوستنش را می‌تواند decrypt کند. پیام‌های قدیمی‌تر در دسترس نیستند.

ارتقا از نسخهٔ قبلی با E2EE

💡 نکته

اگر خودتان هم crypto.db را دستی حذف کرده‌اید، هشدار «حذف مخزن رمزنگاری» در بخش E2EE بالا را ببینید — گام‌های اضافی برای پاک‌کردن one-time key های کهنه از هوم‌سرور لازم است.

اگر قبلاً هرمس را با ‏MATRIX_ENCRYPTION=true استفاده می‌کردید و به نسخه‌ای با مخزن رمزنگاری SQLite جدید ارتقا می‌دهید، هویت رمزنگاری بات عوض شده است. کلاینت Matrix‌تان ‏(Element) ممکن است کلیدهای دستگاه قدیمی را کش کرده باشد و از اشتراک نشست رمزنگاری با بات خودداری کند.

علامت‌ها: بات وصل می‌شود و در لاگ‌ها «E2EE enabled» نشان می‌دهد ولی همهٔ پیام‌ها «could not decrypt event» هستند و بات هرگز جواب نمی‌دهد.

چه می‌شود: وضعیت رمزنگاری قدیمی ‏(از بک‌اند قبلی matrix-nio یا سریال‌سازی mautrix) با مخزن رمزنگاری SQLite جدید ناسازگار است. بات هویت رمزنگاری تازه می‌سازد ولی کلاینت شما هنوز کلیدهای قدیمی را کش کرده و با دستگاهی که کلیدهایش عوض شده نشست رمزنگاری اتاق را share نمی‌کند. این یک ویژگی امنیتی Matrix است — کلاینت‌ها تغییر کلیدهای هویت برای همان دستگاه را مشکوک تلقی می‌کنند.

راه‌حل ‏(مهاجرت یک‌باره):

  1. توکن دسترسی جدید بسازید تا device ID تازه بگیرید. ساده‌ترین راه:
    bash
    curl -X POST https://your-server/_matrix/client/v3/login \
  -H "Content-Type: application/json" \
  -d '{
    "type": "m.login.password",
    "identifier": {"type": "m.id.user", "user": "@hermes:your-server.org"},
    "password": "***",
    "initial_device_display_name": "Hermes Agent"
  }'
    ‏access_token جدید را کپی و ‏MATRIX_ACCESS_TOKEN در ‏~/.hermes/.env را به‌روز کنید.
  2. وضعیت رمزنگاری قدیمی را حذف کنید:
    bash
    rm -f ~/.hermes/platforms/matrix/store/crypto.db
rm -f ~/.hermes/platforms/matrix/store/crypto_store.*
  3. کلید بازیابی‌تان را بگذارید ‏(اگر cross-signing دارید — بیشتر کاربران Element دارند). به ‏~/.hermes/.env اضافه کنید:
    bash
    MATRIX_RECOVERY_KEY=EsT... your recovery key here
    این باعث می‌شود بات هنگام شروع با کلیدهای cross-signing self-sign کند تا Element فوراً به دستگاه جدید اعتماد کند. بدون این، Element دستگاه جدید را unverified می‌بیند و از اشتراک نشست رمزنگاری خودداری می‌کند. کلید بازیابی در Element زیر ‏Settings ← Security & Privacy ← Encryption است.
  4. کلاینت Matrix‌تان را مجبور به چرخش نشست رمزنگاری کنید. در Element اتاق DM با بات را باز و ‏/discardsession تایپ کنید. این Element را مجبور می‌کند نشست رمزنگاری جدیدی بسازد و با دستگاه جدید بات share کند.
  5. گیت‌وی را ری‌استارت کنید:
    bash
    hermes gateway run
    اگر ‏MATRIX_RECOVERY_KEY تنظیم باشد باید ‏Matrix: cross-signing verified via recovery key را در لاگ‌ها ببینید.
  6. پیام جدید بفرستید. بات باید decrypt و عادی پاسخ دهد.
📌 یادداشت

بعد از مهاجرت، پیام‌های فرستاده‌شده قبل از ارتقا قابل decrypt نیستند — کلیدهای رمزنگاری قدیمی رفته‌اند. این فقط انتقال را تحت تأثیر قرار می‌دهد؛ پیام‌های جدید عادی کار می‌کنند.

💡 نکته

نصب‌های جدید تحت تأثیر نیستند. این مهاجرت فقط وقتی لازم است که setup E2EE کارکرده با نسخهٔ قبلی هرمس داشته‌اید و ارتقا می‌دهید.

چرا توکن دسترسی جدید؟ هر توکن دسترسی Matrix به یک device ID مشخص قفل است. استفادهٔ مجدد از همان device ID با کلیدهای رمزنگاری جدید باعث می‌شود سایر کلاینت‌ها به دستگاه بی‌اعتماد شوند ‏(تغییر کلیدهای هویت را نفوذ امنیتی بالقوه می‌بینند). توکن جدید device ID تازه‌ای بدون تاریخچهٔ کلید کهنه می‌گیرد، پس کلاینت‌های دیگر فوراً اعتماد می‌کنند.

بات وصل و ارسال می‌کند ولی پیام‌های ورودی را نادیده می‌گیرد

علت: هندلرهای رویداد Matrix فقط وقتی شلیک می‌کنند که payload های sync از ماشین ‏handle_sync() ماتریکس dispatch شوند. یک poll خام ‏client.sync() که هرگز handle_sync() را صدا نمی‌زند می‌تواند آداپتور را متصل نگه دارد ‏(ارسال کار می‌کند) در حالی که پیام‌های ورودی هرگز به _on_room_message نمی‌رسند.

راه‌حل: هرمس از حلقهٔ sync صریحی استفاده می‌کند که هم روی sync اولیه هم روی هر پاسخ sync افزایشی ‏client.handle_sync() را صدا می‌زند. این با تشخیص issue شمارهٔ ۷۹۱۴ بالادستی و PR بسته‌شدهٔ ۳۷۸۰۷ می‌خواند ولی وظایف نگهداشت پس‌زمینهٔ خود هرمس ‏(ردیابی اتاق‌های عضو، هندل دعوت، share کلید E2EE) را حفظ می‌کند به‌جای سپردن کل چرخهٔ حیات به ‏client.start(). اگر بعد از ری‌استارت گیت‌وی پیام‌های ورودی هنوز نمی‌آیند، تأیید کنید هندلرها قبل از اولین sync ثبت شده باشند و لاگ‌ها را برای ‏sync event dispatch error چک کنید.

مشکلات sync / بات عقب می‌افتد

علت: اجراهای طولانی ابزار می‌توانند حلقهٔ sync را عقب بیندازند، یا هوم‌سرور کند است.

راه‌حل: حلقهٔ sync در خطا هر ۵ ثانیه خودکار retry می‌کند. هشدارهای مرتبط با sync را در لاگ‌های هرمس چک کنید. اگر بات مدام عقب می‌افتد مطمئن شوید هوم‌سرورتان منابع کافی دارد.

بات آفلاین است

علت: گیت‌وی هرمس اجرا نیست یا اتصال شکست خورده.

راه‌حل: چک کنید hermes gateway در حال اجراست. خروجی ترمینال را برای پیام خطا ببینید. مسائل رایج: URL هوم‌سرور اشتباه، توکن دسترسی منقضی، هوم‌سرور در دسترس نیست.

«User not allowed» / بات شما را نادیده می‌گیرد

علت: شناسهٔ کاربری شما در MATRIX_ALLOWED_USERS نیست.

راه‌حل: شناسه‌تان را به MATRIX_ALLOWED_USERS در ~/.hermes/.env اضافه و گیت‌وی را ری‌استارت کنید. قالب کامل ‏@user:server را استفاده کنید.

بات کل یک اتاق را نادیده می‌گیرد

علت: ‏MATRIX_ALLOWED_ROOMS تنظیم است و شناسهٔ اتاق فعلی فهرست نیست، یا اتاق منشن می‌خواهد و پیام بات را منشن نکرده.

راه‌حل: شناسهٔ اتاق را به ‏MATRIX_ALLOWED_ROOMS اضافه کنید، یا اگر استقرار شخصی است لیست‌مجاز اتاق را حذف کنید. برای یافتن Room ID در Element تنظیمات اتاق را باز و بخش Advanced را چک کنید.

پیام‌های پل حلقه می‌زنند یا echo می‌شوند

علت: یک عروسک پل/appservice خروجی بات را به‌عنوان پیام کاربر جدید رله می‌کند، یا پل از شناسه‌های شبح غیریعادی استفاده می‌کند.

راه‌حل: شبح‌های پل را خارج از ‏MATRIX_ALLOWED_USERS نگه دارید، یک ورودی منطبق به ‏MATRIX_IGNORE_USER_PATTERNS اضافه کنید و مگر notice ها بخش گردش‌کار مطمئنی باشند ‏MATRIX_PROCESS_NOTICES=false بماند.

۱۱ حالت پروکسی ‏(E2EE روی macOS)

‏E2EE ماتریکس به libolm نیاز دارد که روی macOS ARM64 ‏(Apple Silicon) کامپایل نمی‌شود. extra ‏hermes-agent[matrix] فقط برای لینوکس gate شده است. اگر روی macOS هستید، حالت پروکسی اجازه می‌دهد E2EE را در یک کانتینر Docker روی VM لینوکسی اجرا کنید در حالی که خود ایجنت به‌صورت native روی macOS با دسترسی کامل به فایل‌های محلی، حافظه و مهارت‌ها اجرا می‌شود.

نحوهٔ کار

text
macOS (Host):
  └─ hermes gateway
       ├─ api_server adapter ← listens on 0.0.0.0:8642
       ├─ AIAgent ← single source of truth
       ├─ Sessions, memory, skills
       └─ Local file access (Obsidian, projects, etc.)

Linux VM (Docker):
  └─ hermes gateway (proxy mode)
       ├─ Matrix adapter ← E2EE decryption/encryption
       └─ HTTP forward → macOS:8642/v1/chat/completions
           (no LLM API keys, no agent, no inference)

کانتینر Docker فقط پروتکل Matrix + E2EE را هندل می‌کند. وقتی پیامی می‌رسد decrypt و متنش با یک درخواست HTTP استاندارد به میزبان فوروارد می‌شود. میزبان ایجنت را اجرا، ابزار را صدا، پاسخ را تولید و استریم برمی‌گرداند. کانتینر encrypt و به Matrix می‌فرستد. همهٔ نشست‌ها واحدند — CLI، ‏Matrix، ‏تلگرام و هر پلتفرم دیگری همان حافظه و تاریخچهٔ گفتگو را شریک‌اند.

گام ۱: پیکربندی میزبان ‏(macOS)

‏API server را فعال کنید تا میزبان درخواست‌های ورودی کانتینر را بپذیرد. به ‏~/.hermes/.env اضافه کنید:

bash
API_SERVER_ENABLED=true
API_SERVER_KEY=your-secret-key-here
API_SERVER_HOST=0.0.0.0
  • ‏API_SERVER_HOST=0.0.0.0 به همهٔ interface ها بایند می‌شود تا کانتینر Docker بهش برسد.
  • ‏API_SERVER_KEY برای bind غیر-loopback الزامی است. رشتهٔ تصادفی قوی انتخاب کنید.
  • ‏API server پیش‌فرض روی پورت ۸۶۴۲ اجرا می‌شود ‏(در صورت نیاز با API_SERVER_PORT عوض کنید).

گیت‌وی را شروع کنید:

bash
hermes gateway

‏API server را کنار پلتفرم‌های پیکربندی‌شده‌تان می‌بینید که شروع می‌شود. از VM قابل‌دسترسی بودنش را تأیید کنید:

bash
# از داخل Linux VM
curl http://<mac-ip>:8642/health

گام ۲: پیکربندی کانتینر Docker ‏(Linux VM)

کانتینر اعتبارنامه‌های Matrix و URL پروکسی را می‌خواهد. کلیدهای API لالم لازم ندارد.

docker-compose.yml:

yaml
services:
  hermes-matrix:
    build: .
    environment:
      # اعتبارنامه‌های Matrix
      MATRIX_HOMESERVER: "https://matrix.example.org"
      MATRIX_ACCESS_TOKEN: "syt_..."
      MATRIX_ALLOWED_USERS: "@you:matrix.example.org"
      MATRIX_ENCRYPTION: "true"
      MATRIX_DEVICE_ID: "HERMES_BOT"

      # حالت پروکسی — فوروارد به ایجنت میزبان
      GATEWAY_PROXY_URL: "http://192.168.1.100:8642"
      GATEWAY_PROXY_KEY: "your-secret-key-here"
    volumes:
      - ./matrix-store:/root/.hermes/platforms/matrix/store

Dockerfile:

dockerfile
FROM python:3.11-slim

RUN apt-get update && apt-get install -y libolm-dev && rm -rf /var/lib/apt/lists/*
RUN cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

CMD ["hermes", "gateway"]

تمام کانتینر همین است. هیچ کلید API برای OpenRouter، ‏Anthropic یا هیچ ارائه‌دهندهٔ inference‌ای.

گام ۳: اجرای هر دو

  1. اول گیت‌وی میزبان را شروع کنید:
    bash
    hermes gateway
  2. کانتینر Docker را شروع کنید:
    bash
    docker compose up -d
  3. در یک اتاق رمزنگاری‌شدهٔ Matrix پیام بدهید. کانتینر decrypt، به میزبان فوروارد و پاسخ را استریم برمی‌گرداند.

مرجع پیکربندی

حالت پروکسی روی سمت کانتینر ‏(گیت‌وی لاغر) پیکربندی می‌شود:

تنظیمتوضیح
GATEWAY_PROXY_URLURL سرور API هرمسِ راه‌دور ‏(مثل http://192.168.1.100:8642)
GATEWAY_PROXY_KEYتوکن Bearer برای احراز ‏(باید با ‏API_SERVER_KEY میزبان یکی باشد)
gateway.proxy_urlهمان ‏GATEWAY_PROXY_URL ولی در config.yaml

سمت میزبان این‌ها را می‌خواهد:

تنظیمتوضیح
API_SERVER_ENABLEDروی true
API_SERVER_KEYتوکن Bearer ‏(مشترک با کانتینر)
API_SERVER_HOST‏0.0.0.0 برای دسترسی شبکه‌ای
API_SERVER_PORTشمارهٔ پورت ‏(پیش‌فرض: 8642)

برای هر پلتفرمی کار می‌کند

حالت پروکسی محدود به Matrix نیست. هر آداپتور پلتفرمی می‌تواند استفاده کند — روی هر نمونهٔ گیت‌وی ‏GATEWAY_PROXY_URL را بگذارید تا به‌جای اجرای ایجنت محلی به ایجنت راه‌دور فوروارد کند. برای هر استقراری که آداپتور پلتفرم باید در محیط متفاوتی از ایجنت اجرا شود مفید است ‏(ایزوله‌سازی شبکه، الزامات E2EE، محدودیت منابع).

💡 نکته

تداوم نشست با هدر ‏X-Hermes-Session-Id حفظ می‌شود. ‏API server میزبان نشست‌ها را با این ID ردیابی می‌کند، پس گفتگوها بین پیام‌ها مثل ایجنت محلی ادامه می‌یابند.

📌 محدودیت‌ها ‏(v1)

پیام‌های پیشرفت ابزار از ایجنت راه‌دور رله برنمی‌گردند — کاربر فقط پاسخ نهایی استریم‌شده را می‌بیند نه فراخوانی‌های تک‌تک ابزار. پرامپت‌های تأیید فرمان خطرناک سمت میزبان هندل می‌شوند نه رله به کاربر Matrix. این‌ها در به‌روزرسانی‌های آینده قابل رسیدگی‌اند.

۱۲ امنیت

⚠️ هشدار

همیشه ‏MATRIX_ALLOWED_USERS و برای استقرارهای مشترک/خصوصی ‏MATRIX_ALLOWED_ROOMS را تنظیم کنید. بدون آن‌ها هر کسی که بتواند در اتاقی عضوشده به بات پیام دهد می‌تواند ایجنت را تریگر کند. فقط افراد و اتاق‌های مورداطمینان را مجاز کنید — کاربران مجاز دسترسی کامل به قابلیت‌های ایجنت دارند شامل استفاده از ابزار و دسترسی سیستم.

برای اطلاعات بیشتر دربارهٔ امن‌سازی استقرار هرمس ایجنت، راهنمای امنیت را ببینید.

۱۳ یادداشت‌ها

  • هر هوم‌سروری: با Synapse، ‏Conduit، ‏Dendrite، ‏matrix.org یا هر هوم‌سرور سازگار-با-مشخصات کار می‌کند. نرم‌افزار خاصی لازم نیست.
  • فدراسیون: اگر روی هوم‌سرور فدرال هستید بات می‌تواند با کاربران سرورهای دیگر حرف بزند — فقط شناسهٔ کامل ‏@user:server آن‌ها را به ‏MATRIX_ALLOWED_USERS اضافه کنید.
  • پیوستن خودکار: بات دعوت‌های اتاق را خودکار می‌پذیرد و می‌پیوندد. بلافاصله بعد از پیوستن پاسخ می‌دهد.
  • پشتیبانی رسانه: هرمس می‌تواند تصویر، صوت، ویدیو و پیوست فایل بفرستد و بگیرد. رسانه با API مخزن محتوای Matrix روی هوم‌سرور شما آپلود می‌شود.
  • پیام‌های صوتی بومی ‏(MSC3245): آداپتور Matrix پیام‌های صوتی خروجی را خودکار با فلگ ‏org.matrix.msc3245.voice تگ می‌کند. یعنی پاسخ‌های TTS و صدای صوتی به‌عنوان حباب صوتی بومی در Element و سایر کلاینت‌های پشتیبان MSC3245 رندر می‌شوند نه به‌عنوان پیوت فایل صوتی عمومی. پیام‌های صوتی ورودی دارای فلگ MSC3245 هم درست شناسایی و به رونویسی گفتار-به-متن مسیریابی می‌شوند. پیکربندی لازم نیست — خودکار کار می‌کند.
