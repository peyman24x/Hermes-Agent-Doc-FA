راه‌اندازی اسلک

هرمس ایجنت را با حالت Socket ‏(Socket Mode) به اسلک به‌عنوان بات وصل کنید. Socket Mode به‌جای نقاط پایانی عمومی HTTP از WebSocket استفاده می‌کند، پس نمونهٔ هرمس شما نیازی به قابل‌دسترس‌بودن عمومی ندارد — پشت فایروال، روی لپ‌تاپ یا سرور خصوصی کار می‌کند.

⚠️ اپ‌های کلاسیک اسلک منسوخ شده‌اند

اپ‌های کلاسیک اسلک ‏(با RTM API) در مارس ۲۰۲۵ کاملاً منسوخ شدند. هرمس از SDK مدرن Bolt با Socket Mode استفاده می‌کند. اگر اپ کلاسیک قدیمی دارید باید طبق گام‌های زیر یک اپ جدید بسازید.

۱ نمای کلی

مؤلفهمقدار
کتابخانه‏slack-bolt / ‏slack_sdk برای پایتون ‏(Socket Mode)
اتصالWebSocket — بدون نیاز به URL عمومی
توکن‌های احراز لازمتوکن بات ‏(xoxb-) + توکن سطح‌اپ ‏(xapp-)
شناسایی کاربرشناسه‌های عضو اسلک ‏(مثل U01ABC2DEF3)

۲ گام ۱: ساخت اپ اسلک

سریع‌ترین مسیر این است که مانیفستی که هرمس برایتان تولید می‌کند را بچسبانید. این مانیفست همهٔ فرمان‌های اسلش داخلی ‏(/btw، ‏/stop، ‏/model و...)، همهٔ scope های OAuth لازم، همهٔ اشتراک‌های رویداد را اعلام و Socket Mode را فعال می‌کند — همه‌با هم.

گزینهٔ A: از مانیفست تولیدشده توسط هرمس ‏(توصیه‌شده)

  1. مانیفست را تولید کنید. اپ‌های جدید اسلک باید از Agent view استفاده کنند:
bash
hermes slack manifest --agent-view --write

این فرمان ~/.hermes/slack-manifest.json را می‌نویسد و دستورالعمل چسباندن را چاپ می‌کند. اپ‌های موجودی که هنوز از Assistant view قدیمی اسلک استفاده می‌کنند تا آمادهٔ مهاجرت نشوند می‌توانند --agent-view را حذف کنند.

برای پرکردن توضیح بلند اپ اسلک از یک فایل متنی UTF-8 یا Markdown موجود، ‏--long-description-file را اضافه کنید:

bash
hermes slack manifest --agent-view \
  --long-description-file AGENTS.md --write

محتوای فایل دقیقاً در بازهٔ ۱۷۵ تا ۴٬۰۰۰ کاراکتری اسلک حفظ می‌شود. برای متن درجا به‌جایش --long-description "..."؛ گزینهٔ درجا و فایل با هم جمع‌ناپذیرند و با --slashes-only هم قابل ترکیب نیستند.

  1. به https://api.slack.com/apps بروید ← Create New App ← From an app manifest
  2. ورک‌اسپیس‌تان را انتخاب، محتوای JSON را بچسبانید، بازبینی کنید و Next ← Create را بزنید
  3. مستقیم به گام ۶: نصب اپ در ورک‌اسپیس بروید. مانیفست scope ها، رویدادها و فرمان‌های اسلش را برایتان انجام داده است.

گزینهٔ B: از صفر ‏(دستی)

  1. به https://api.slack.com/apps بروید
  2. روی Create New App کلیک کنید
  3. From scratch را انتخاب کنید
  4. نام اپ ‏(مثلاً «Hermes Agent») را وارد و ورک‌اسپیس‌تان را انتخاب کنید
  5. روی Create App کلیک کنید

به صفحهٔ Basic Information اپ می‌روید. با گام‌های ۲ تا ۶ پایین ادامه دهید.

۳ گام ۲: پیکربندی scope های توکن بات

به Features ← OAuth & Permissions در نوار کناری بروید. به Scopes ← Bot Token Scopes اسکرول کنید و این‌ها را اضافه کنید:

chat:writeارسال پیام به‌عنوان بات
app_mentions:readتشخیص @منشن شدن در کانال‌ها
channels:historyخواندن پیام‌ها در کانال‌های عمومیِ عضو بات
channels:readفهرست و اطلاعات کانال‌های عمومی
groups:historyخواندن پیام‌ها در کانال‌های خصوصیِ دعوت‌شدهٔ بات

⚠️ scope ناموجود = قابلیت ناموجود

بدون channels:history و groups:history بات پیام‌های کانال را دریافت نمی‌کند — فقط در DM کار می‌کند. بدون files:read هرمس می‌تواند چت کند ولی نمی‌تواند پیوست‌های آپلودی کاربران را مطمئن بخواند. این‌ها رایج‌ترین scope های جاافتاده‌اند.

scope های اختیاری:

Scopeهدف
groups:readفهرست و اطلاعات کانال‌های خصوصی
assistant:writeرندر خط وضعیت حالت-کار ‏(«در حال فکر کردن است…») کنار نام بات حین پردازش پیام. بدون این scope فراخوانی assistant.threads.setStatus بی‌صدا شکست می‌خورد و اسلک به‌جایش placeholder های عمومی چرخان خودش را نشان می‌دهد ‏(«Finding answers…»، «Reviewing findings…» و...) — هرمس هیچ‌وقت متن را کنترل نمی‌کند. برای اثر مرئیِ typing_status_text الزامی است.

۴ گام ۳: فعال‌سازی Socket Mode

Socket Mode اجازه می‌دهد بات از طریق WebSocket وصل شود نه اینکه URL عمومی لازم داشته باشد.

  1. در نوار کناری به Settings ← Socket Mode بروید
  2. ‏Enable Socket Mode را روشن کنید
  3. برای ساخت App-Level Token از شما پرسیده می‌شود:
    • نامی مثل hermes-socket بگذارید ‏(نام مهم نیست)
    • scope ‏connections:write را اضافه کنید
    • روی Generate کلیک کنید
  4. توکن را کپی کنید — با xapp- شروع می‌شود. این همان SLACK_APP_TOKEN شماست
💡 نکته

توکن‌های سطح‌اپ را همیشه می‌توانید زیر Settings ← Basic Information ← App-Level Tokens پیدا یا بازتولید کنید.

۵ گام ۴: اشتراک رویدادها

این گام بحرانی است — کنترل می‌کند بات چه پیام‌هایی را ببیند.

  1. در نوار کناری به Features ← Event Subscriptions بروید
  2. ‏Enable Events را روشن کنید
  3. بخش Subscribe to bot events را باز و این‌ها را اضافه کنید:
رویدادلازم؟هدف
message.imبلهبات پیام‌های خصوصی را دریافت می‌کند
message.mpimبلهبات پیام‌های DM های گروهی ‏(چندنفره) که به آن‌ها افزوده شده را دریافت می‌کند
message.channelsبلهبات پیام‌های کانال‌های عمومی عضوشده را دریافت می‌کند
message.groupsتوصیه‌شدهبات پیام‌های کانال‌های خصوصی دعوت‌شده را دریافت می‌کند
app_mentionبلهخطاهای Bolt SDK هنگام @منشن شدن بات را پیشگیری می‌کند
  1. در پایین صفحه Save Changes را کلیک کنید
🚨 جاافتادن اشتراک رویدادها = مشکل شمارهٔ ۱ راه‌اندازی

اگر بات در DM کار می‌کند ولی در کانال‌ها نه، تقریباً قطعاً فراموش کرده‌اید message.channels ‏(برای کانال‌های عمومی) و/یا message.groups ‏(برای خصوصی) را اضافه کنید. بدون این رویدادها اسلک اصلاً پیام‌های کانال را به بات تحویل نمی‌دهد.

۶ گام ۵: فعال‌سازی تب Messages

این گام پیام خصوصی به بات را ممکن می‌کند. بدون آن کاربران هنگام DM به بات پیام «Sending messages to this app has been turned off» می‌بینند.

  1. در نوار کناری به Features ← App Home بروید
  2. به Show Tabs اسکرول کنید
  3. ‏Messages Tab را روشن کنید
  4. گزینهٔ «Allow users to send Slash commands and messages from the messages tab» را تیک بزنید
🚨 بدون این گام، DM کلاً مسدود است

حتی با همهٔ scope ها و اشتراک‌های رویداد درست، اسلک اجازه نمی‌دهد کاربران به بات پیام خصوصی بدهند مگر تب Messages فعال باشد. این الزام پلتفرم اسلک است نه مسئلهٔ پیکربندی هرمس.

۷ گام ۶: نصب اپ در ورک‌اسپیس

  1. در نوار کناری به Settings ← Install App بروید
  2. روی Install to Workspace کلیک کنید
  3. دسترسی‌ها را بازبینی و Allow را بزنید
  4. پس از تأیید، یک Bot User OAuth Token با شروع xoxb- می‌بینید
  5. این توکن را کپی کنید — این همان SLACK_BOT_TOKEN شماست
💡 نکته

اگر بعداً scope ها یا اشتراک‌های رویداد را تغییر دادید، برای اعمال تغییرات باید اپ را دوباره نصب کنید. صفحهٔ Install App بنری برای همین نشان می‌دهد.

۸ گام ۷: یافتن شناسه‌های کاربری برای فهرست مجاز

هرمس برای فهرست مجاز از Member ID های اسلک استفاده می‌کند ‏(نه یوزرنیم یا نام نمایشی).

برای یافتن Member ID:

  1. در اسلک روی نام یا آواتار کاربر کلیک کنید
  2. روی View full profile کلیک کنید
  3. دکمهٔ ⋮ ‏(بیشتر) را بزنید
  4. Copy member ID را انتخاب کنید

‏Member ID ها شبیه U01ABC2DEF3 هستند. دست‌کم Member ID خودتان را لازم دارید.

۹ گام ۸: پیکربندی هرمس

این‌ها را به فایل ~/.hermes/.env اضافه کنید:

bash
# الزامی
SLACK_BOT_TOKEN=xoxb-your-bot-token-here
SLACK_APP_TOKEN=xapp-your-app-token-here
SLACK_ALLOWED_USERS=U01ABC2DEF3              # شناسه‌های عضو جدا با ویرگول

# اختیاری
SLACK_HOME_CHANNEL=C01234567890              # کانال پیش‌فرض پیام‌های کرون/زمان‌بندی‌شده
SLACK_HOME_CHANNEL_NAME=general              # نام خوانا برای کانال خانگی (اختیاری)

یا راه‌اندازی تعاملی:

bash
hermes gateway setup    # هنگام پرسش Slack را انتخاب کنید

سپس گیت‌وی را شروع کنید:

bash
hermes gateway              # پیش‌زمینه
hermes gateway install      # نصب به‌عنوان سرویس کاربر
sudo hermes gateway install --system   # فقط لینوکس: سرویس سیستمی زمان‌بوت
💡 ایمنی reasoning-effort برای Codex

برای کانال‌های همتای اسلکِ پشتیبان Codex، ‏agent.reasoning_effort: high یا کمتر را ترجیح دهید. ‏xhigh می‌تواند کل نوبت را در استدلال پنهان بگذراند و هرگز متن مرئی دستیار تولید نکند؛ هرمس الان آن هشدارهای نوبت-ناقص را از ترد حذف و تشخیص‌ها را در لاگ‌های گیت‌وی نگه می‌دارد.

۱۰ گام ۹: دعوت بات به کانال‌ها

پس از شروع گیت‌وی باید بات را به هر کانالی که می‌خواهید پاسخ دهد دعوت کنید:

text
/invite @Hermes Agent

بات به‌طور خودکار به کانال‌ها نمی‌پیوندد. باید تک‌تک کانال‌ها را دعوتش کنید.

۱۱ فرمان‌های اسلش

هر فرمان هرمس ‏(/btw، ‏/stop، ‏/new، ‏/model، ‏/help و...) یک فرمان اسلش بومی اسلک است — دقیقاً مثل رفتارشان در تلگرام و دیسکورد. در اسلک / تایپ کنید و انتخاب‌گر تکمیل‌خودکار همهٔ فرمان‌های هرمس را با توضیحشان فهرست می‌کند.

در پس‌زمینه: هرمس با یک مانیفست اپ اسلکِ تولیدشده عرضه می‌شود ‏(گام ۱، گزینهٔ A) که هر فرمان COMMAND_REGISTRY را به‌عنوان فرمان اسلش اعلام می‌کند. در Socket Mode اسلک رویداد فرمان را مستقل از فیلد url مانیفست از طریق WebSocket مسیریابی می‌کند.

تجربهٔ پیام‌رسانی ایجنت

اپ‌های جدید اسلک از تجربهٔ پیام‌رسانی Agent اسلک استفاده می‌کنند. اپ‌های Assistant موجود هرمس می‌توانند با بازتولید مانیفست با --agent-view مهاجرت کنند:

bash
hermes slack manifest --agent-view --write

مانیفست را در Features ← App Manifest به‌روز کنید و اگر اسلک خواست اپ را دوباره نصب کنید. Agent view به Assistant view برگشت‌پذیر نیست و کاربران ممکن است بعد از تغییر نیاز به hard-refresh اسلک داشته باشند. مانیفست Agent تولیدشده به message.im، ‏app_home_opened و app_context_changed اشتراک دارد تا هرمس بتواند DM تب Messages را شناسایی و زمینهٔ فعال اسلک کاربر را همراه نوبت دریافت کند. هرمس آن زمینه را فقط به‌عنوان برچسب می‌دهد؛ تاریخچهٔ کانال مشاهده‌شده را نمی‌خواند.

بازخوانی فرمان‌های اسلش پس از به‌روزرسانی

وقتی هرمس فرمان جدیدی اضافه می‌کند ‏(مثلاً بعد از hermes update)، مانیفست را بازتولید و اپ اسلک‌تان را به‌روز کنید:

bash
hermes slack manifest --write

سپس در اسلک:

  1. https://api.slack.com/apps را باز کنید ← اپ هرمس‌تان
  2. Features ← App Manifest ← Edit
  3. محتوای جدید ~/.hermes/slack-manifest.json را بچسبانید
  4. Save را بزنید. اگر scope یا فرمان‌های اسلش عوض شده باشند اسلک reinstall را پیشنهاد می‌دهد.

‏/hermes <زیرفرمان> قدیمی همچنان کار می‌کند

برای سازگاری رو به عقب با مانیفست‌های قدیمی‌تر هنوز می‌توانید /hermes btw run the tests تایپ کنید — هرمس همان‌طور مثل /btw run the tests مسیریابی‌اش می‌کند. پرسش‌های آزاد هم کار می‌کنند: ‏/hermes what's the weather? به‌عنوان پیام معمولی پردازش می‌شود.

استفاده از فرمان‌ها داخل تردها (پیشوند !cmd)

خود اسلک فرمان‌های اسلش بومی را داخل ریپلای‌های ترد مسدود می‌کند — ‏/queue را در ترد امتحان کنید و اسلک پاسخ می‌دهد: *«‎/queue is not supported in threads. Sorry!»* هیچ تنظیم سمت-اپی وجود ندارد که آنها را دوباره فعال کند؛ اسلک هرگزشان را به هرمس تحویل نمی‌دهد.

به‌عنوان راه‌حل جایگزین، هرمس یک ! ابتدایی را به‌عنوان پیشوند فرمان جایگزین می‌شناسد که در تردها ‏(و هر جای دیگر) کار می‌کند. ‏!queue، ‏!stop، ‏!model gpt-5.4 و غیره را به‌عنوان ریپلای عادی ترد بنویسید — هرمس عیناً مثل فرم اسلش رفتار و در همان ترد پاسخ می‌دهد.

فقط توکن اول با فهرست فرمان‌های شناخته‌شده چک می‌شود، پس پیام‌های معمولی مثل !nice work بدون تغییر به ایجنت می‌رسند. فرم تعجبی پشت منشن هم ‏(@Hermes !stop) و با فضای سفید ابتدایی هم کار می‌کند — هر دو در تردها به‌عنوان فرمان dispatch می‌شوند.

پرامپت‌های تأیید ‏(تأیید فرمان خطرناک / ‏execute_code) معمولاً به‌صورت دکمه‌های تعاملی رندر می‌شوند. وقتی دکمه‌ها قابل‌تحویل نباشند و هرمس به پرامپت متنی سقوط کند، پرامپت به شما می‌گوید با !approve / ‏!deny پاسخ دهید — فرمی که داخل تردها کار می‌کند.

پاسخ‌های اسلش زودگذر (ephemeral) هستند

پاسخ به فرمان اسلش بومی ‏(مثل /status، ‏/help) به‌صورت زودگذر تحویل می‌شود — «Only visible to you» — پس خروجی فرمان هرگز کانال را اسپم نمی‌کند. placeholder «Running /cmd…» با پاسخ واقعی جایگزین می‌شود؛ پاسخ‌های بلند به پیام‌های زودگذر پیاپی تقسیم می‌شوند. اسلک جریان پاسخ را به ۵ پست سقف می‌زند، پس خروجی خیلی بلند با یک اعلان برشِ صریح بسته می‌شود نه حذف بی‌صدا. اگر مسیر اصلی زودگذر شکست بخورد، هرمس از یک مسیر API زودگذر دوم تلاش مجدد می‌کند — پاسخ اسلش هرگز به‌عنوان fallback عمومی در کانال پست نمی‌شود. ‏(فرمان‌هایی که به‌صورت پیام عادی تایپ شده‌اند — ‏!cmd در تردها، ‏@Hermes /cmd — به‌جایش مثل پیام‌های مرئی عادی پاسخ می‌گیرند.)

پرامپت‌های شفاف‌سازی (دکمه‌های یک‌ضربه‌ای)

وقتی ایجنت لازم باشد یک پرسش چندگزینه‌ای بپرسد ‏(ابزار clarify)، اسلک آن را به‌صورت دکمه‌های Block Kit رندر می‌کند — یک ضربه به‌ازای هر گزینه، به‌اضافهٔ دکمهٔ «✏️ Other…» که به حالت متن آزاد می‌رود ‏(پیام تایپی بعدی‌تان تبدیل به پاسخ می‌شود). پس از ضربه، پیام درجا به‌روز می‌شود تا نشان دهد چه کسی پاسخ داد و چه چیزی انتخاب شد؛ کلیک‌های بعدی روی همان پرامپت نادیده گرفته می‌شوند. کلیک دکمه‌ها همان مجوزدهی کاربر پیام‌ها را رعایت می‌کنند و پرامپت‌های منقضی ‏(ری‌استارت گیت‌وی، timeout) به‌جای بلع بی‌صدای کلیک، می‌گویند دوباره بپرسید. پرسش‌های بازِ clarify به‌صورت پرسش ساده رندر و ریپلای تایپی بعدی‌تان را می‌پذیرند. هیچ پیکربندی‌ای لازم نیست — مستقل از تنظیم rich_blocks کار می‌کند.

پیشرفته: فقط آرایهٔ فرمان‌های اسلش

اگر مانیفست اسلک‌تان را دستی نگه می‌دارید و فقط فهرست فرمان‌های اسلش را می‌خواهید:

bash
hermes slack manifest --slashes-only > /tmp/slashes.json

آن آرایه را در کلید features.slash_commands مانیفست موجودتان بچسبانید.

۱۳ گزینه‌های پیکربندی

فراتر از متغیرهای محیطی الزامی گام ۸، می‌توانید رفتار بات اسلک را از طریق ~/.hermes/config.yaml سفارشی کنید.

رفتار ترد و ریپلای

yaml
platforms:
  slack:
    # نحوهٔ تردشدن پاسخ‌های چندبخشی
    # "off"   — هرگز ریپلای به پیام اصلی ترد نشود
    # "first" — اولین بخش به پیام کاربر ترد شود (پیش‌فرض)
    # "all"   — همهٔ بخش‌ها به پیام کاربر ترد شوند
    reply_to_mode: "first"

    extra:
      # پاسخ در ترد باشد یا نه (پیش‌فرض: true).
      # با false، پیام‌های کانال به‌جای ترد مستقیم در کانال پاسخ می‌گیرند.
      # پیام‌های داخل تردهای موجود همچنان داخل ترد ریپلای می‌شوند.
      reply_in_thread: true

      # ارسال ریپلای‌های ترد به کانال اصلی هم
      # (قابلیت "Also send to channel" اسلک).
      # فقط اولین بخش اولین ریپلای broadcast می‌شود.
      reply_broadcast: false

      # رندر پیام‌های ایجنت به‌صورت بلوک‌های Block Kit اسلک (پیش‌فرض: false).
      # با true، پیام نهایی ایجنت با بلوک‌های ساختاریافته فرستاده می‌شود —
      # تیترهای بخش، جداکننده، فهرست‌های تودرتوی واقعی (با rich_text)،
      # و جدول‌های بومی Block Kit — به‌جای متن mrkdwn تخت. یک fallback
      # متنی ساده همیشه همراهش فرستاده می‌شود برای اعلان/دسترس‌پذیری.
      # جدول‌های فراتر از سقف‌های اسلک (100 ردیف / 20 ستون / 10k کاراکتر)
      # با ملایمت به مونواسپیس هم‌تراز برمی‌گردند.
      rich_blocks: false

      # افزودن کنترل‌های بازخورد بومی اسلک به ریپلای‌های نهایی Block Kit.
      # نیازمند rich_blocks: true. پیش‌فرض: false.
      feedback_buttons: false

      # رندر فراخوانی‌های زندهٔ ابزار به‌صورت کارت‌های plan/task بومی اسلک.
      # این انتخاب صریح، پیشرفت بومی را حتی با خاموشی text tool_progress فعال می‌کند.
      # اگر اسلک استریم بومی را رد کند، هرمس برای بقیه نوبت یک fallback
      # متنی قابل‌ویرایش را به‌روز نگه می‌دارد.
      native_task_cards: false

      # پرامپت‌های پیشنهادی پین‌شده بالای تب Messages نمای Agent.
      # یا فهرستی از ردیف‌های {title, message}، یا آبجکت عنوان‌دار:
      # {title: "Start here", prompts: [{title: "Plan", message: "..."}]}
      suggested_prompts: []

      # عنوان‌گذاری تردهای DM ایجنت/دستیار از اولین پیام کاربر.
      # پیش‌فرض: true. با false عناوین پیش‌فرض اسلک می‌مانند.
      assistant_thread_titles: true

      # پذیرش پیام‌های بات‌های دیگر اسلک (پیش‌فرض: "none").
      # "none" بات‌ها را نادیده می‌گیرد، "mentions" فقط وقتی پیام بات
      # خودش هرمس را @منشن کرده قبول می‌کند، "all" همهٔ بات‌های دیگر را.
      # هرمس همیشه کاربر باتِ خودش را برای پیشگیری از خود-پژواک نادیده می‌گیرد.
      allow_bots: "none"

      # سطح تحویل کرون قابل-ادامه (پیش‌فرض: "thread").
      # "in_channel" کار کرونِ قابل‌ادامه را FLAT داخل کانال تحویل می‌دهد
      # (بدون ترد اختصاصی)؛ با reply_in_thread: false (و require_mention: false)
      # جفتش کنید تا یک ریپلای ساده کار را ادامه دهد.
      # راهنمای کرون ← "Flat, in-channel continuation".
      cron_continuable_surface: thread
کلیدپیش‌فرضتوضیح
platforms.slack.reply_to_mode"first"حالت تردشدن پیام‌های چندبخشی: ‏"off"، ‏"first" یا "all"
platforms.slack.extra.reply_in_threadtrueبا false پیام‌های کانال به‌جای ترد مستقیم پاسخ می‌گیرند. پیام‌های داخل تردهای موجود همچنان داخل ترد ریپلای می‌شوند.
platforms.slack.extra.reply_broadcastfalseبا true ریپلای‌های ترد به کانال اصلی هم پست می‌شوند. فقط اولین بخش broadcast می‌شود.
platforms.slack.extra.rich_blocksfalseبا true پیام‌های ایجنت به‌صورت بلوک‌های Block Kit رندر می‌شوند ‏(تیتر، جداکننده، فهرست تودرتوی واقعی و جدول بومی). fallback متنی ساده همیشه فرستاده می‌شود. جدول‌های فراتر از سقف اسلک به مونواسپیس هم‌تراز برمی‌گردند. reinstall لازم ندارد — فقط تغییر سمت ارسال است.

platforms.slack.extra.suggested_prompts[]تا چهار پرامپت {title, message} برای نقطهٔ ورود DM ایجنت/دستیار؛ هم فهرست می‌پذیرد هم {title, prompts}.
platforms.slack.extra.assistant_thread_titlestrueبا true تردهای DM ایجنت/دستیار از اولین پیام کاربر نام‌گذاری می‌شوند.
platforms.slack.extra.allow_bots"none"کنترل پیام‌های بات‌های دیگر اسلک: ‏"none" نادیده می‌گیرد، ‏"mentions" فقط وقتی خودِ پیام هرمس را @منشن کرده می‌پذیرد، ‏"all" همه را می‌پذیرد. امن‌ترین حالت همکاری بات-به-بات "mentions" است.
platforms.slack.extra.cron_continuable_surface"thread"سطح تحویل کارهای کرون قابل‌ادامه. ‏"thread" به‌ازای هر تحویل ترد اختصاصی باز می‌کند ‏(پیش‌فرض)؛ ‏"in_channel" flat در خط‌زمان کانال تحویل می‌دهد. ‏in_channel را با reply_in_thread: false ‏(و require_mention: false) جفت کنید تا ریپلای سادهٔ کانال کار را ادامه دهد.

متغیر محیطی معادل SLACK_ALLOW_BOTS=none|mentions|all است. وقتی هر دو تنظیم باشند platforms.slack.extra.allow_bots مقدم است. وقتی بات‌های همتا می‌توانند بدون منشن صریح به هم جواب دهند از all بپرهیزید، چون سیاست‌های ریپلای خودشان هنوز می‌توانند حلقه بسازند.

خط وضعیت حالت-کار

حین پردازش پیام توسط ایجنت، اسلک خط وضعیتی کنار نام بات در ترد نشان می‌دهد. پیش‌فرض هرمس is thinking... است؛ با typing_status_text سفارشی‌اش کنید — مثلاً دستیار بچه‌گربه‌ای به نام Ada:

yaml
platforms:
  slack:
    # خط وضعیت حالت-کار سفارشی (پیش‌فرض: "is thinking...").
    typing_status_text: "is pouncing… 🐾"
کلیدپیش‌فرضتوضیح
platforms.slack.typing_status_text"is thinking..."متن خط وضعیت حالت-کار حین پردازش پیام. scope ‏assistant:write لازم دارد — بدون آن فراخوانی وضعیت بی‌صدا شکست می‌خورد و اسلک placeholder عمومی خودش را نشان می‌دهد فارغ از مقدار این کلید. برای غیرفعال‌سازی کامل خط وضعیت typing_indicator: false را بگذارید.
📌 وضعیت کجا رندر می‌شود

وضعیت سفارشی در فوترِ زیر جعبهٔ نوشتن پاسخ ظاهر می‌شود ‏(«*BotName* is thinking…»)، نه درجا در فهرست پیام‌ها. خطوط «Generating response…» / «Finding answers…» درون‌خطی که اسلک در ناحیهٔ پیام حین کار یک اپ AI نشان می‌دهد نشانگرهای چرخانِ خودِ اسلک‌اند — ‏assistant.threads.setStatus آن‌ها را کنترل نمی‌کند و هر دو می‌توانند هم‌زمان دیده شوند.

همین کلید پیام نشانگر حالت-کارِ مرئی Google Chat را هم سفارشی می‌کند ‏(platform.google_chat.typing_status_text، پیش‌فرض "Hermes is thinking…") — توجه: در Google Chat این یک پیام واقعی پست‌شده است که به ریپلای وصله می‌شود، نه وضعیت زودگذر.

وضعیت زنده (به‌ازای هر ابزار)

به‌طور پیش‌فرض خط وضعیت همراه کار ایجنت زنده به‌روز می‌شود: به‌جای is thinking... ثابت نشان می‌دهد ایجنت همین الان چه می‌کند — ‏is running pytest tests/…، ‏is reading docs/api.md…، ‏is searching the web for slack api limits…. بین فراخوانی‌های ابزار به متن ثابت برمی‌گردد. این روی همان ضرباهجهٔ refresh وضعیت موجود سوار است، پس فراخوانی API اضافه‌ای به اسلک نمی‌زند و حتی با tool_progress: off ‏(پیش‌فرض اسلک) کار می‌کند — برخلاف حباب‌های پیشرفت، خط وضعیت زودگذر است و چیزی در کانال جا نمی‌گذارد.

با display.live_status ‏(سراسری یا به‌ازای پلتفرم) کنترلش کنید:

yaml
display:
  platforms:
    slack:
      # full = فعل + آرگومان ("is running pytest…")   [پیش‌فرض]
      # verb = فقط فعل ("is running…") — دستورها/مسیرها را مخفی می‌کند،
      #        مناسب کانال‌های مشترک یا رو‌به‌مشتری
      # off  = متن ثابت (typing_status_text یا "is thinking...")
      live_status: full
کلیدپیش‌فرضتوضیح
display.live_status"full"خط وضعیت زندهٔ به‌ازای-ابزار. ‏full فعل + پیش‌نمایش آرگومان؛ ‏verb فقط فعل ‏(مسیر فایل و فرمان وارد کانال‌های مشترک نمی‌شود)؛ ‏off متن ثابت. مثل خط وضعیت ثابت، scope ‏assistant:write می‌خواهد.

استریم بومی (پاسخ‌های تایپ-زنده)

قابلیت Agents & AI Apps اسلک یک سطح استریم بومی دارد ‏(chat.startStream / ‏chat.appendStream / ‏chat.stopStream) که پاسخ را به‌صورت پیام تایپ-زنده رندر می‌کند — بسیار روان‌تر از به‌روزرسانی‌های تدریجی مبتنی بر ویرایش. وقتی streaming.enabled روشن باشد ‏(ترنسپورت auto یا draft)، هرمس هر جا در دسترس باشد خودکار از استریم بومی استفاده می‌کند:

  • استریم با اولین فریم شروع و فقط دلتاها الصاق می‌شوند ‏(API فقط-الصاقی است). پیام استریم‌شده همان پیام نهایی است — هرمس با chat.stopStream مهرش می‌زند به‌جای پست یک ریپلای نهایی تکراری.
  • اگر اپ اسلک‌تان قابلیت AI نداشته باشد ‏(یا scope ‏assistant:write را ندارد)، اولین شکست کش می‌شود و هرمس با یک هشدار لاگِ واحد که راه‌حل را نام می‌برد به استریم مبتنی بر ویرایش سقوط می‌کند.
  • ‏Block Kit انتخابی ‏(rich_blocks: true) روی پیام مهروشده اعمال می‌شود، مثل مسیر finalize مبتنی بر ویرایش.

فراتر از فعال‌کردن streaming پیکربندی اضافه لازم نیست:

yaml
streaming:
  enabled: true       # ترنسپورت auto/draft استریم بومی اسلک را روشن می‌کند

کارت‌های Task بومی (پیشرفت زندهٔ ابزار)

با platforms.slack.extra.native_task_cards: true فراخوانی‌های زندهٔ ابزار به‌صورت کارت‌های plan/task بومی اسلک رندر می‌شوند ‏(همان UI قابلیت‌های AI خود اسلک) به‌جای حباب‌های متنی پیشرفت: یک کارت به‌ازای هر نوبت، یک ردیف به‌ازای هر فراخوانی ابزار، با وضعیت‌های running/complete/error به‌ازای هر task که درجا به‌روز می‌شوند.

yaml
platforms:
  slack:
    extra:
      native_task_cards: true
  • این یک انتخاب صریح پیشرفت است — حتی با پیش‌فرض tool_progress: off اسلک کار می‌کند ‏(حباب‌های متنی کانال را اسپم می‌کنند؛ کارت‌های بومی نمی‌کنند).
  • فراخوانی‌های هم‌زمان یک ابزار با شناسهٔ واقعی فراخوانی correlate می‌شوند، پس فراخوانی‌های موازی web_search هرکدام ردیف خودشان را با وضعیت درست دارند.
  • اگر استریم بومی شروع یا به‌روز نشود، هرمس به یک پیام متنی واحدِ پیوسته-ویرایش‌شونده سقوط می‌کند تا پیشرفت برای همان نوبت زنده بماند.
  • استریم کارت دقیقاً یک‌بار هنگام نهایی‌شدن نوبت متوقف می‌شود، شامل وقفه/قطعی، پس هیچ نشانگر زندهٔ معلق جا نمی‌ماند.

ایزوله‌سازی نشست

yaml
# تنظیم سراسری — روی اسلک و همهٔ پلتفرم‌های دیگر اعمال می‌شود
group_sessions_per_user: true

وقتی true ‏(پیش‌فرض)، هر کاربر در کانال مشترک نشست گفتگوی ایزولهٔ خودش را دارد. دو نفری که در #general با هرمس حرف می‌زنند تاریخچه و زمینهٔ جدا دارند.

اگر حالت مشارکتی می‌خواهید که کل کانال یک نشست مشترک داشته باشد false کنید. بدانید این یعنی کاربران در رشد زمینه و هزینهٔ توکن شریک‌اند و /reset یک نفر نشست همه را پاک می‌کند.

۱۴ رفتار منشن و تریگر

yaml
slack:
  # منشن اجباری در کانال‌ها (این رفتار پیش‌فرض است؛
  # آداپتور اسلک در کانال‌ها به هر حال گیت منشن را اعمال می‌کند،
  # ولی برای یکدستی با پلتفرم‌های دیگر می‌توانید صریحش کنید)
  require_mention: true

  # جلوگیری از درگیری خودکار ترد: فقط به پیام‌های کانالی که
  # @منشن صریح دارند پاسخ بده. با خاموشی این گزینه (پیش‌فرض)،
  # اسلک می‌تواند «خودکار درگیر شود» — منشن‌های گذشتهٔ ترد را
  # به یاد دارد، ریپلای به پیام‌های بات را دنبال می‌کند و نشست‌های
  # فعال را بدون منشن تازه ادامه می‌دهد. با strict_mention روشن،
  # هر پیام جدید کانال باید قبل از پاسخ هرمس بات را @منشن کند.
  strict_mention: false

  # نادیده گرفتن پیام‌های خطاب‌شده به کاربر دیگر: وقتی پیام کانال/ترد
  # با @منشن شخصی غیر از بات «شروع» می‌شود (مثلاً "@rasha می‌گیری این را؟")،
  # ساکت بمان مگر بات هم منشن شده باشد. فقط منشن «ابتدایی» حساب
  # «خطاب‌شده» می‌شود — پیامی که وسط جمله کسی را ذکر کند
  # ("loop in @rasha") همچنان به بات می‌رسد. بر free_response_channels
  # و درگیری خودکار ترد مقدم است. انتخابی؛ پیش‌فرض خاموش. Env: SLACK_IGNORE_OTHER_USER_MENTIONS.
  ignore_other_user_mentions: false

  # منشن صریح برای ریپلای‌های ترد لازم باشد، در حالی که پیام‌های
  # سطح‌بالای کانال تابع require_mention / free_response_channels می‌مانند.
  # محدودتر از strict_mention: وقتی بات پاسخ-آزاد نباید وارد هر
  # پیام بعدیِ تردهای شلوغ شود. انتخابی؛ پیش‌فرض خاموش. Env: SLACK_THREAD_REQUIRE_MENTION.
  thread_require_mention: false

  # بازنویسی اجبار-منشن به‌ازای کانال — در جهت مقابل free_response_channels.
  # کانال‌های این فهرست ALWAYS منشن صریح می‌خواهند، حتی وقتی
  # require_mention سراسری false است. گفتگوهای در جریان همچنان
  # خودکار دنبال می‌شوند (تردهای منشن‌شده، نشست‌های فعال، تردهای ساختهٔ بات).
  # شناسه‌ها با ویرگول یا فهرست. Env: SLACK_REQUIRE_MENTION_CHANNELS.
  require_mention_channels: ""

  # الگوهای منشن سفارشی که بات را فعال می‌کنند
  # (علاوه بر تشخیص پیش‌فرض @منشن)
  mention_patterns:
    - "hey hermes"
    - "hermes,"

  # متنی که به ابتدای هر پیام خروجی الصاق می‌شود
  reply_prefix: ""
💡 کِی strict_mention؟

در ورک‌اسپیس‌های شلوغی که رفتار پیش‌فرض «بات این ترد را به یاد دارد» اسلک کاربران را غافلگیر می‌کند true کنید — مثلاً ترد طولانی پشتیبانی فنی که بات اولش کمک کرد و ترجیح می‌دهید مگر دوباره صریحاً پینگ شود ساکت بماند. DM‌ها و نشست‌های تعاملی فعال بی‌تأثیرند.

💡 کِی ignore_other_user_mentions؟

وقتی بات تردهای شلوغ را دنبال می‌کند ‏(با درگیری خودکار ترد یا free_response_channels) و وسط پیام‌هایی که انسان‌ها به همدیگر داده‌اند پا می‌گذارد true کنید. ابزار محدودتری از strict_mention: پیام‌های ادامه‌دهندهٔ عادی تردِ درگیر همچنان جواب می‌گیرند؛ فقط پیام‌هایی که با منشن شخص دیگری باز می‌شوند رد می‌شوند. ‏DM های ۱:۱ بی‌تأثیرند؛ ‏DM گروهی ‏(MPIM) و کانال هر دو شامل‌اند، مطابق سیاست سطح-مشترک پایین. توکن‌های broadcast ‏(@here، ‏@channel) و ارجاعات کانال خطاب به اتاق‌اند نه شخص، پس هرگز رد نمی‌شوند.

📌 نکته

اسلک هر دو الگو را پشتیبانی می‌کند: پیش‌فرض @منشن برای شروع گفتگو لازم است، ولی می‌توانید کانال‌های خاص را با SLACK_FREE_RESPONSE_CHANNELS ‏(شناسه‌های کانال جدا با ویرگول) یا slack.free_response_channels در config.yaml مستثنا کنید. وقتی بات نشست فعالی در ترد داشته باشد ریپلای‌های بعدی ترد منشن نمی‌خواهند. در DM های ۱:۱ بات همیشه بدون منشن پاسخ می‌دهد.

⚠️ DM های گروهی ‏(MPIM) سطح مشترک‌اند نه DM یک‌به‌یک

‏پیام خصوصی ۱:۱ گفتگوی خصوصی با یک نفر است، پس از منشن معاف است. ‏DM گروهی ‏(MPIM / چندنفره) یک سطح مشترک است — چند نفر می‌توانند ببینند و بات را فعال کنند — پس همان کنترل‌های اپراتوریِ کانال را دارد: ‏require_mention، ‏strict_mention، ‏free_response_channels و allowed_channels همه اعمال می‌شوند و بات فقط وقتی واقعاً @منشن شود واکنش ‏:eyes:/:white_check_mark: می‌گذارد. برای پاسخ آزاد بات در یک MPIM مشخص، شناسهٔ کانالش ‏(شروع با G) را به free_response_channels اضافه کنید.

DM های ۱:۱ همیشه پاسخ می‌دهند و از همهٔ این‌ها بی‌تأثیرند.

پذیرش پیام از بات‌های دیگر (allow_bots)

به‌طور پیش‌فرض هرمس هر پیامِ نوشته‌شده توسط بات یا اپ دیگر اسلک را نادیده می‌گیرد ‏(شامل پست‌های Workflow Builder). برای ورک‌اسپیس‌های چندایجنتی — چند نمونهٔ هرمس یا بات‌های همتا که در یک کانال همکاری می‌کنند — با allow_bots انتخاب کنید:

yaml
platforms:
  slack:
    extra:
      # "none" (پیش‌فرض) — نادیده گرفتن همهٔ پیام‌های بات/اپ
      # "mentions"       — پذیرش پیام بات فقط وقتی همان پیام
      #                    این بات را @منشن کرده باشد
      # "all"            — پذیرش همهٔ پیام‌های بات (غیر از خودِ بات)
      allow_bots: mentions

معادل env: ‏SLACK_ALLOW_BOTS=none|mentions|all ‏(با تنظیم هر دو، کلید config برنده است). مقادیر ناشناخته none فرض می‌شوند.

نحوهٔ gating حالت mentions:

  • پیام بات همتا فقط وقتی پذیرفته می‌شود که خود پیام یک @منشن جاری از این بات داشته باشد — در متنش یا بلوک‌های Block Kitش. تاریخچهٔ ترد حساب نمی‌شود: منشن‌شدن قبلی بات در ترد، ریپلای به پیام‌های خود بات، و نشست‌های فعال ترد، پیام‌های بعدیِ بی-منشنِ بات همتا را نمی‌پذیرند. این عمدی است — همان چیزی که حلقه‌های ack/status ایجنت-به-ایجنت را می‌شکند.
  • پیام‌های انسان بی‌تأثیرند؛ gating منشن عادی رویشان اعمال می‌شود.
  • هرمس در همهٔ حالت‌ها پیام‌های خودش را نادیده می‌گیرد تا حلقهٔ خود-پژواک نسازد.

‏mentions حالت توصیه‌شده برای همکاری بات-به-بات است: هر ایجنت باید به‌ازای هر نوبت صریحاً دیگری را احضار کند. جز وقتی سیاست ریپلای همهٔ بات‌های همتا loop-safe باشد از all بپرهیزید — دو باتی که به همه‌چیز جواب می‌دهند تا ابد به همدیگر جواب خواهند داد. تشخیص، پیام‌های برچسب‌دار بات ‏(bot_id، ‏subtype: bot_message)، رویدادهای برخاسته از اپ و کاربران باتِ بی‌برچسب ‏(با probe ‏users.info) را پوشش می‌دهد، پس ایجنت‌های هرمس همتا در همهٔ ورک‌اسپیس‌ها یکدست فیلتر می‌شوند.

برای استقرارهای سخت‌گیرانهٔ چند-بات با require_mention: true و strict_mention: true جفتش کنید — پروفایل smoke-check پایین را ببینید.

تریگرهای واکنش (reaction_triggers)

به‌طور پیش‌فرض واکنش‌های ایموجی فقط تأیید و رها می‌شوند — 👍 روی پیام بات کاری نمی‌کند. ‏slack.reaction_triggers را بگذارید تا واکنش‌ها وارد حلقهٔ ایجنت شوند ‏(scope ‏reactions:read به‌اضافهٔ اشتراک رویدادهای بات ‏reaction_added/reaction_removed در مانیفست اپ اسلک لازم است — با hermes slack manifest بازتولید کنید):

yaml
slack:
  # انتخابی. false/غایب (پیش‌فرض) = واکنش‌ها تأیید و رها می‌شوند.
  # true = هر واکنشی روی پیام‌های خودِ بات به ایجنت مسیریابی می‌شود.
  reaction_triggers: true
  # یا لیست‌مجاز صریح ایموجی — فقط این نام‌ها مسیریابی می‌شوند و
  # می‌توانند هر پیامی را هدف بگیرند (گردش‌کار emoji-handoff، مثل :task: برای ثبت):
  # reaction_triggers: [white_check_mark, thumbsup, task]
  # هدف handoff اختیاری: در این کانال (سطح‌بالا) یا ترد (C123:<thread_ts>)
  # پاسخ بده به‌جای ترد پیامِ واکنش‌خورده.
  # reaction_trigger_target: C0123456789

معادل‌های محیطی: ‏SLACK_REACTION_TRIGGERS ‏(true/all یا فهرست جداشده با ویرگول) و SLACK_REACTION_TRIGGER_TARGET.

رفتار:

  • واکنش به‌عنوان یک نوبت عادی ایجنت با متن ‏reaction:added:👍 / ‏reaction:removed:👍 می‌رسد ‏(نام‌های رایج اسلک به یونیکد ترجمه می‌شوند؛ نام‌های ناشناخته عیناً عبور می‌کنند مثل reaction:added:custom-emoji)، زیر پیامِ واکنش‌خورده ترد می‌شود تا ایجنت ببیند به چه چیزی واکنش داده شده و نوبت در همان نشستِ یک ریپلای می‌نشیند.
  • واکنش‌دهنده کاربرِ پیام می‌شود، پس مجوزدهی کاربر و گیت allowed_channels دقیقاً مثل پیام‌های تایپی اعمال می‌شود — واکنش کاربر غریبه نمی‌تواند ایجنت را جایی تریگر کند که پیامش نمی‌توانست.
  • با reaction_triggers: true فقط واکنش‌های روی پیام‌های خودی بات مسیریابی می‌شوند ‏(گردش‌کارهای تأیید). با لیست‌مجاز صریح ایموجی، ایموجی‌های فهرست‌شده از هر پیامی مسیریابی می‌شوند.
  • واکنش‌های چرخه‌حیاتِ خود بات ‏(:eyes: و مانند آن) هرگز برنمی‌گردند.
  • مستقل از این انتخاب، هر واکنش انسان هوک‌های گیت‌وی ‏reaction:added/reaction:removed را برای ناظرانی که نوبت ایجنت لازم ندارند شلیک می‌کند.

Smoke-check ایجنت همتا

برای استقرارهای چند-بات اسلکی که به منشن سخت‌گیرانهٔ به‌ازای-نوبت تکیه دارند این پروفایل را حفظ کنید:

yaml
slack:
  require_mention: true
  strict_mention: true
  allow_bots: mentions
  allowed_channels: ""

بعد از تغییرات config گیت‌وی، deploy یا ری‌استارت، این هدف smoke مصنوعی را اجرا کنید:

bash
uv run --frozen pytest -q tests/gateway/test_slack_peer_agent_smoke.py -o addopts=''

این هدف فقط از رویدادهای مصنوعی درون-پروسه‌ای استفاده می‌کند. پیام زندهٔ اسلک نمی‌فرستد و به‌طور پیش‌فرض توکن بات واقعی نمی‌خواهد.

سبدهای شکست:

  • config: ‏test_peer_agent_smoke_preflight_contract عدم‌تطبیق پروفایل را گرفت ‏(require_mention، ‏strict_mention، ‏allow_bots یا allowed_channels).
  • platform_connectivity: آداپتور/کلاینت مقداردهی نشده بود، پس smoke مسیریابی هنوز سیگنال قابل‌اعتمادی نیست.
  • bot_identity: آداپتور هرگز شناسهٔ کاربر باتش را حل نکرد، پس چک منشنِ پیام-جاری نمی‌تواند کار کند.
  • routing_logic: آداپتور اسلک روی یکی از ناورداها‌های ایجنت-همتا پسروی کرد ‏(مسیریابی منشن انسان، نادیده‌گرفتن بات همتا، پذیرش منشن صریح همتا، یا سرکوب منفعل ack/status/error).

اگر این هدف پاس شد ولی ورک‌اسپیس زنده هنوز پیام‌ها را بد مسیریابی می‌کند، اتصال توکن/ورک‌اسپیس اسلک و وضعیت استقرار runtime را خارج از منطق مسیریابی بررسی کنید.

لیست‌مجاز کانال (allowed_channels)

بات را به مجموعهٔ ثابتی از کانال‌های اسلک محدود کنید — وقتی بات به کانال‌های زیادی دعوت شده ولی باید فقط در چندتا پاسخ دهد مفید است. با تنظیم، پیام‌های کانال‌های خارج از این فهرست بی‌صدا نادیده گرفته می‌شوند حتی با @منشن.

‏DM های ۱:۱ از این فیلتر معاف‌اند، پس کاربران مجاز همیشه در پیام خصوصی به بات می‌رسند. ‏DM های گروهی ‏(MPIM) معاف نیستند — مثل کانال‌ها، MPIM باید روی لیست‌مجاز باشد ‏(شناسه‌اش با G شروع می‌شود) وگرنه پیام‌هایش رد می‌شوند.

yaml
slack:
  allowed_channels:
    - "C0123456789"   # ‎#ops
    - "C0987654321"   # ‎#incident-response

یا با متغیر محیطی ‏(جداشده با ویرگول):

bash
SLACK_ALLOWED_CHANNELS="C0123456789,C0987654321"

رفتار:

  • خالی / تنظیم‌نشده ← بدون محدودیت ‏(کاملاً سازگار رو به عقب).
  • غیرخالی ← شناسهٔ کانال باید روی فهرست باشد وگرنه پیام قبل از هر gating دیگری ‏(شرط منشن، ‏free_response_channels و...) رد می‌شود.
  • شناسه‌های کانال اسلک با C ‏(عمومی)، ‏G ‏(خصوصی) یا D ‏(DM) شروع می‌شوند. از UI اسلک «Open channel details» ← پنل «About» یا از API پیدا کنید.

همچنین ببینید: تفکیک فرمان ادمین/کاربر.

مدیریت کاربر غیرمجاز

yaml
slack:
  # وقتی کاربر غیرمجاز (خارج از SLACK_ALLOWED_USERS) به بات DM بدهد چه شود
  # "pair"   — کد جفت‌سازی از او بپرس (پیش‌فرض)
  # "ignore" — پیام را بی‌صدا دور بینداز
  unauthorized_dm_behavior: "pair"

سراسری هم برای همهٔ پلتفرم‌ها می‌شود گذاشت:

yaml
unauthorized_dm_behavior: "pair"

تنظیم مخصوص پلتفرم زیر slack: بر تنظیم سراسری مقدم است.

رونویسی صوت

yaml
# تنظیم سراسری — فعال/غیرفعال‌کردن رونویسی خودکار پیام‌های صوتی ورودی
stt_enabled: true

وقتی true ‏(پیش‌فرض)، پیام‌های صوتی ورودی قبل از پردازش توسط ایجنت خودکار با ارائه‌دهندهٔ STT پیکربندی‌شده رونویسی می‌شوند.

مثال کامل

yaml
# تنظیمات سراسری گیت‌وی
group_sessions_per_user: true
unauthorized_dm_behavior: "pair"
stt_enabled: true

# تنظیمات مخصوص اسلک
slack:
  require_mention: true
  unauthorized_dm_behavior: "pair"

# پیکربندی پلتفرم
platforms:
  slack:
    reply_to_mode: "first"
    extra:
      reply_in_thread: true
      reply_broadcast: false

۱۵ کانال خانگی

‏SLACK_HOME_CHANNEL را روی شناسهٔ کانالی بگذارید که هرمس پیام‌های زمان‌بندی‌شده، نتایج job های کرون و سایر اعلان‌های پیش‌فعال را به آن تحویل دهد. برای یافتن شناسهٔ کانال:

  1. روی نام کانال در اسلک راست‌کلیک کنید
  2. View channel details را بزنید
  3. به پایین اسکرول کنید — Channel ID آنجاست
bash
SLACK_HOME_CHANNEL=C01234567890

حتماً بات به کانال دعوت شده باشد ‏(/invite @Hermes Agent).

هدف‌گذاری تحویل کرون

کارهای کرون ‏(راهنمای کرون را ببینید) سه راه به اسلک هدف می‌گیرند:

مقدار deliver:کجا می‌نشیند
slackکانال خانگی ‏(SLACK_HOME_CHANNEL)
slack:C0123456789یک کانال مشخص با شناسه
slack:U0123456789DM آن کاربر — شناسهٔ لخت کاربر خودکار به گفتگوی DM حل می‌شود ‏(scope ‏im:write لازم دارد)

تحویل حتی وقتی پروسهٔ کرون هم‌مکان با گیت‌وی نیست کار می‌کند — هرمس به یک فرستندهٔ مستقل Web API با SLACK_BOT_TOKEN سقوط می‌کند. پیوست‌های MEDIA: در خروجی کرون به‌عنوان file share بومی اسلک به همان هدف آپلود می‌شوند.

ارسال پیام و رسانه (send_message)

ابزار send_message ایجنت همان شکل‌های هدف را می‌پذیرد: شناسهٔ کانال ‏(C…/G…)، گفتگوی DM ‏(D…) یا شناسهٔ لخت کاربر ‏(U…/W…) که در همهٔ مسیرهای ارسال — متن، رسانه و پرامپت‌های تعاملی — به DM کاربر حل می‌شود. پیوست‌های MEDIA:<path> ‏(تصویر، PDF، سند) به‌صورت file share بومی آپلود می‌شوند؛ وقتی پیام کوتاهی همراه یک پیوست واحد باشد به‌جای پیام جداگانه به‌عنوان کپشن فایل سوار می‌شود. فایل‌های گمشده به‌ازای هر فایل به‌عنوان هشدار گزارش می‌شوند نه شکست کل ارسال.

۱۶ پشتیبانی چند-ورک‌اسپیس

هرمس می‌تواند با یک نمونهٔ گیت‌وی به‌طور هم‌زمان به چند ورک‌اسپیس اسلک وصل شود. هر ورک‌اسپیس مستقلاً با شناسهٔ کاربر بات خودش احراز می‌شود.

پیکربندی

چند توکن بات را به‌صورت فهرست جداشده با ویرگول در SLACK_BOT_TOKEN بدهید:

bash
# چند توکن بات — یکی به‌ازای هر ورک‌اسپیس
SLACK_BOT_TOKEN=xoxb-workspace1-token,xoxb-workspace2-token,xoxb-workspace3-token

# یک توکن سطح‌اپ واحد همچنان برای Socket Mode استفاده می‌شود
SLACK_APP_TOKEN=xapp-your-app-token

یا در ~/.hermes/config.yaml:

yaml
platforms:
  slack:
    token: "xoxb-workspace1-token,xoxb-workspace2-token"

فایل توکن OAuth

علاوه بر توکن‌های محیط/config، هرمس توکن‌ها را از یک فایل توکن OAuth هم بار می‌کند:

text
~/.hermes/slack_tokens.json

این فایل آبجکت JSON نگاشت team ID به رکورد توکن است:

json
{
  "T01ABC2DEF3": {
    "token": "xoxb-workspace-token-here",
    "team_name": "My Workspace"
  }
}

توکن‌های این فایل با توکن‌های SLACK_BOT_TOKEN ادغام می‌شوند. توکن‌های تکراری خودکار dedupe می‌شوند.

نحوهٔ کار

  • اولین توکن فهرست، توکن اصلی است و برای اتصال Socket Mode ‏(AsyncApp) استفاده می‌شود.
  • هر توکن هنگام شروع با auth.test احراز می‌شود. گیت‌وی هر team_id را به WebClient و bot_user_id خودش نگاشت می‌کند.
  • وقتی پیامی می‌رسد هرمس از کلاینت مخصوص همان ورک‌اسپیس برای پاسخ استفاده می‌کند.
  • ‏bot_user_id اصلی ‏(از اولین توکن) برای سازگاری رو به عقب با قابلیت‌هایی که هویت بات واحد انتظار دارند استفاده می‌شود.

۱۷ پیام‌های صوتی

هرمس صدا را روی اسلک پشتیبانی می‌کند:

  • ورودی: پیام‌های صوتی خودکار با ارائه‌دهندهٔ STT پیکربندی‌شده رونویسی می‌شوند: ‏faster-whisper محلی، ‏Groq Whisper ‏(GROQ_API_KEY) یا OpenAI Whisper ‏(VOICE_TOOLS_OPENAI_KEY)
  • خروجی: پاسخ‌های TTS به‌صورت پیوست فایل صوتی فرستاده می‌شوند

۱۸ پرامپت به‌ازای-کانال

پرامپت‌های سیستمی زودگذر را به کانال‌های مشخص اسلک اختصاص دهید. پرامپت در زمان اجرا در هر نوبت تزریق می‌شود — هرگز در تاریخچهٔ رونویسی ذخیره نمی‌شود — پس تغییرات فوراً اثر می‌کنند.

yaml
slack:
  channel_prompts:
    "C01RESEARCH": |
      You are a research assistant. Focus on academic sources,
      citations, and concise synthesis.
    "C02ENGINEERING": |
      Code review mode. Be precise about edge cases and
      performance implications.

کلیدها شناسه‌های کانال اسلک‌اند ‏(از channel details ← «About» ← اسکرول تا پایین). همهٔ پیام‌های کانال منطبق پرامپت را به‌عنوان دستور سیستمی زودگذر دریافت می‌کنند.

۱۹ اتصال مهارت به‌ازای-کانال

هر وقت نشست جدیدی در کانال یا DM مشخصی شروع شود یک مهارت خودکار بارگذاری کنید. برخلاف پرامپت‌های به‌ازای-کانال ‏(که در هر نوبت تزریق می‌شوند)، اتصال مهارت محتوای مهارت را در شروع نشست به‌عنوان پیام کاربر تزریق می‌کند — بخشی از تاریخچهٔ گفتگو می‌شود و نیازی به بارگذاری مجدد در نوبت‌های بعدی نیست.

برای DM ها یا کانال‌های با هدف مشخص ‏(فلش‌کارت، بات پرسش‌وپاسخ حوزه‌محور، کانال triage پشتیبانی و...) ایده‌آل است که نمی‌خواهید انتخابگر مهارتِ مدل تصمیم بگیرد در هر ریپلای کوتاه بار بگیرد یا نه.

yaml
slack:
  channel_skill_bindings:
    # کانال DM — همیشه در حالت "german-flashcards" اجرا می‌شود
    - id: "D0ATH9TQ0G6"
      skills:
        - german-flashcards
    # کانال تحقیقاتی — پیش‌بارگذاری چند مهارت به ترتیب
    - id: "C01RESEARCH"
      skills:
        - arxiv
        - writing-plans
    # فرم کوتاه: یک مهارت به‌صورت رشته
    - id: "C02SUPPORT"
      skill: hubspot-on-demand

یادداشت‌ها:

  • اتصال با شناسهٔ کانال تطبیق می‌کند. برای پیام‌های تردی در کانال متصل، ترد از اتصال کانال والد ارث می‌برد.
  • مهارت فقط در شروع نشست ‏(نشست جدید یا بعد از auto-reset) بارگذاری می‌شود. اگر اتصال را عوض کردید /new بزنید یا منتظر auto-reset نشست بمانید تا اثر کند.
  • با channel_prompts ترکیبش کنید تا لحن/محدودیت به‌ازای-کانال روی دستورالعمل‌های مهارت بیاید.

۲۰ عیب‌یابی

مشکلراه‌حل
بات به DM پاسخ نمی‌دهدتأیید کنید message.im در اشتراک‌های رویداد است و اپ دوباره نصب شده
بات در DM کار می‌کند ولی در کانال‌ها نهرایج‌ترین مشکل. ‏message.channels و message.groups را به اشتراک‌های رویداد اضافه، اپ را دوباره نصب و بات را با /invite @Hermes Agent به کانال دعوت کنید
بات به @منشن در کانال‌ها پاسخ نمی‌دهد۱) رویداد message.channels مشترک شده؟ ۲) بات باید به کانال دعوت شده باشد. ۳) scope ‏channels:history اضافه شده؟ ۴) بعد از تغییر scope/رویداد اپ را دوباره نصب کنید
بات پیام‌های کانال‌های خصوصی را نادیده می‌گیردهم اشتراک رویداد message.groups هم scope ‏groups:history را اضافه، بعد اپ را reinstall و بات را /invite کنید
بات در DM های گروهی پاسخ نمی‌دهداشتراک رویداد message.mpim و scope ‏mpim:history ‏(+ ‏mpim:read) را اضافه و اپ را reinstall کنید. بدون message.mpim اسلک هرگز پیام‌های DM گروهی را به بات نمی‌دهد — حتی اگر DM یک‌به‌یک کار کند.
پیام «Sending messages to this app has been turned off» در DMتب Messages Tab را در تنظیمات App Home فعال کنید ‏(گام ۵)
خطاهای not_authed یا invalid_authتوکن بات و توکن اپ را بازتولید و .env را به‌روز کنید
بات پاسخ می‌دهد ولی نمی‌تواند در کانال پست کندبات را با /invite @Hermes Agent به کانال دعوت کنید
بات چت می‌کند ولی تصاویر/فایل‌های آپلودی را نمی‌خواند‏files:read را اضافه و اپ را reinstall کنید. هرمس الان تشخیص‌های دسترسی پیوست را هنگام شکست scope/auth/permission اسلک درون‌چت نشان می‌دهد.
خطای missing_scopescope لازم را در OAuth & Permissions اضافه و اپ را reinstall کنید
اتصال Socket مدام قطع می‌شودشبکه‌تان را چک کنید؛ Bolt خودش reconnect می‌شود ولی اتصال ناپایدار تأخیر می‌سازد
scope/رویداد را عوض کردم ولی چیزی عوض نشدبعد از هر تغییر scope یا اشتراک رویداد باید اپ را دوباره در ورک‌اسپیس نصب کنید

چک‌لیست سریع

اگر بات در کانال‌ها کار نمی‌کند همهٔ موارد زیر را تأیید کنید:

  1. ✅ رویداد message.channels مشترک شده ‏(کانال‌های عمومی)
  2. ✅ رویداد message.groups مشترک شده ‏(کانال‌های خصوصی)
  3. ✅ رویداد app_mention مشترک شده
  4. ✅ scope ‏channels:history اضافه شده ‏(کانال‌های عمومی)
  5. ✅ scope ‏groups:history اضافه شده ‏(کانال‌های خصوصی)
  6. ✅ اپ بعد از افزودن scope/رویداد دوباره نصب شده
  7. ✅ بات به کانال دعوت شده ‏(/invite @Hermes Agent)
  8. ✅ در پیام‌تان بات را @منشن می‌کنید

۲۱ امنیت

⚠️ هشدار

همیشه SLACK_ALLOWED_USERS را با Member ID های کاربران مجاز تنظیم کنید. بدون این تنظیم، گیت‌وی به‌عنوان اقدام ایمنی به‌طور پیش‌فرض همهٔ پیام‌ها را رد می‌کند. هرگز توکن‌های بات را به اشتراک نگذارید — مثل رمز عبور با آن‌ها رفتار کنید.

  • توکن‌ها باید در ~/.hermes/.env ذخیره شوند ‏(دسترسی فایل 600)
  • توکن‌ها را به‌طور دوره‌ای از تنظیمات اپ اسلک بچرخانید
  • بازبینی کنید چه کسانی به دایرکتوری پیکربندی هرمس دسترسی دارند
  • Socket Mode یعنی هیچ نقطهٔ پایانی عمومی‌ای در معرض نیست — یک سطح حمله کمتر
