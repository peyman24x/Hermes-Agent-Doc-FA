راه‌اندازی Google Chat

‏Hermes Agent را به‌عنوان یک بات به Google Chat وصل کنید. این یکپارچه‌سازی برای رویدادهای ورودی از اشتراک pull ی Cloud Pub/Sub و برای پیام‌های خروجی از Chat REST API استفاده می‌کند. ارگونومی معادل Slack Socket Mode یا long-polling ی تلگرام: پروسهٔ هرمس شما به URL عمومی، ‏tunnel یا گواهی TLS نیاز ندارد. وصل می‌شود، احراز هویت و روی یک subscription گوش می‌دهد — همان‌طور که یک بات تلگرامی روی توکن گوش می‌دهد.

برای مرور راهنمایی دستوری، ‏hermes gateway setup را اجرا و Google Chat را انتخاب کنید.

📌 نسخهٔ Workspace

‏Google Chat بخشی از Google Workspace است. با یک Workspace شخصی ‏(@yourdomain.com ثبت‌شده نزد گوگل) یا Workspace کاری که حق Admin برای انتشار اپ دارید می‌توانید از این یکپارچه‌سازی استفاده کنید. حساب‌های فقط-Gmail نمی‌توانند اپ چت میزبانی کنند.

۱ نمای کلی

جزءمقدار
کتابخانه‌ها‏google-cloud-pubsub، ‏google-api-python-client، ‏google-auth
transport ی ورودیاشتراک pull ی Cloud Pub/Sub ‏(بدون نقطهٔ پایانی عمومی)
transport ی خروجیChat REST API ‏(chat.googleapis.com)
احراز هویتJSON ی Service Account با ‏roles/pubsub.subscriber روی subscription
شناسایی کاربرresource name های چت ‏(users/{id}) + ایمیل

گام ۱: ساخت یا انتخاب پروژهٔ GCP

برای میزبانی topic ی Pub/Sub به پروژهٔ Google Cloud نیاز دارید. ندارید؟ در ‏console.cloud.google.com بسازید — حساب‌های شخصی تیر رایگان می‌گیرند که ترافیک بات را راحت پوشش می‌دهد.

ID پروژه را یادداشت کنید ‏(مثلاً my-chat-bot-123). در همهٔ گام‌های بعدی از آن استفاده می‌کنید.

گام ۲: فعال کردن دو API

در کنسول به ‏APIs & Services ← Library بروید و فعال کنید:

  • Google Chat API
  • Cloud Pub/Sub API

هر دو برای حجمی که یک بات شخصی تولید می‌کند رایگان‌اند.

گام ۳: ساخت Service Account

‏IAM & Admin ← Service Accounts ← Create Service Account.

  • نام: ‏hermes-chat-bot
  • گام «Grant this service account access to project» را skip کنید. IAM روی subscription مشخص همهٔ چیزی است که لازم دارید — نقش‌های Pub/Sub سطح-پروژه ندهید.

بعد از ساخت SA را باز، به Keys ← Add Key ← Create new key ← JSON بروید و فایل را دانلود کنید. جایی ذخیره‌اش کنید که فقط هرمس بخواند ‏(مثلاً ‏~/.hermes/google-chat-sa.json با chmod 600).

⚠️ هیچ نقش «Chat Bot Caller» وجود ندارد

اشتباه رایج: جستجو برای نقش IAM مخصوص-چت و اعطای آن در سطح پروژه. چنین نقشی وجود ندارد. اختیار بات چت از نصب شدن در یک space می‌آید نه از IAM. تنها چیزی که SA تان لازم دارد Pub/Sub Subscriber روی subscription ای است که در گام بعد می‌سازید.

گام ۴: ساخت topic و subscription ی Pub/Sub

‏Pub/Sub ← Topics ← Create topic.

  • Topic ID: ‏hermes-chat-events
  • برای بقیه پیش‌فرض‌ها را رها کنید.

بعد از ساخت، صفحهٔ جزئیات topic تب Subscriptions دارد. یکی بسازید:

  • Subscription ID: ‏hermes-chat-events-sub
  • Delivery type: ‏Pull
  • Message retention: ‏۷ روز ‏(تا backlog از ری‌استارت هرمس جان سالم به در برد)
  • بقیه را پیش‌فرض رها کنید.

گام ۵: binding ی IAM روی topic ‏(حیاتی)

روی topic ‏(نه subscription) یک principal ی IAM اضافه کنید:

  • Principal: ‏chat-api-push@system.gserviceaccount.com
  • Role: ‏Pub/Sub Publisher

بدون این، Google Chat نمی‌تواند رویدادها را به topic تان منتشر کند و رباتتان هرگز هیچ چیزی دریافت نخواهد کرد.

گام ۶: binding ی IAM روی subscription

روی subscription مقدار Service Account خودتان را به‌عنوان principal اضافه کنید:

  • Principal: ‏hermes-chat-bot@<your-project>.iam.gserviceaccount.com
  • Role: ‏Pub/Sub Subscriber

همچنین ‏Pub/Sub Viewer را روی همان subscription اعطا کنید — هرمس موقع شروع برای بررسی قابلیت‌رسیدی ‏subscription.get() را صدا می‌زند.

گام ۷: پیکربندی اپ چت

به APIs & Services ← Google Chat API ← Configuration بروید.

  • App name: هر چه می‌خواهید کاربران ببینند ‏(«Hermes» منطقی است).
  • Avatar URL: هر PNG عمومی ‏(گوگل چند پیش‌فرض دارد).
  • Description: جملهٔ کوتاهی که در دایرکتوری اپ نمایش داده می‌شود.
  • Functionality: ‏Receive 1:1 messages و Join spaces and group conversations را فعال کنید.
  • Connection settings: مقدار Cloud Pub/Sub را بردارید و نام topic را وارد کنید: ‏projects/<your-project>/topics/hermes-chat-events.
  • Visibility: محدود به workspace خودتان ‏(یا کاربران مشخص) — حین تست به همه منتشر نکنید.

ذخیره کنید.

۲ نصب بات در فضای تست و پیکربندی هرمس

گام ۸: نصب بات در یک space ی آزمایشی

Google Chat را در مرورگر باز کنید. با جستجوی نام اپ در منوی + New Chat یک DM با آن شروع کنید. اولین باری که پیام بدهید گوگل رویداد ADDED_TO_SPACE می‌فرستد که هرمس برای کش کردن users/{id} ی خودِ بات جهت فیلتر self-message استفاده می‌کند.

گام ۹: پیکربندی هرمس

بخش Google Chat را به ‏~/.hermes/.env اضافه کنید:

# Required
GOOGLE_CHAT_PROJECT_ID=my-chat-bot-123
GOOGLE_CHAT_SUBSCRIPTION_NAME=projects/my-chat-bot-123/subscriptions/hermes-chat-events-sub
GOOGLE_CHAT_SERVICE_ACCOUNT_JSON=/home/you/.hermes/google-chat-sa.json

# Authorization — paste the emails of people allowed to talk to the bot
GOOGLE_CHAT_ALLOWED_USERS=you@yourdomain.com,coworker@yourdomain.com

# Optional
GOOGLE_CHAT_HOME_CHANNEL=spaces/AAAA...         # default delivery destination for cron jobs
GOOGLE_CHAT_MAX_MESSAGES=1                      # Pub/Sub FlowControl; 1 serializes commands per session
GOOGLE_CHAT_MAX_BYTES=16777216                  # 16 MiB — cap on in-flight message bytes

ID پروژه به GOOGLE_CLOUD_PROJECT و مسیر SA به GOOGLE_APPLICATION_CREDENTIALS هم fallback می‌کنند — هر قراردادی که ترجیح می‌دهید.

وابستگی‌های adapter ی Google Chat را از طریق نصب‌کنندهٔ نگهداری‌شده‌اش نصب کنید. همان کف‌های امنیتی pin‌شده‌ای را اعمال می‌کند که بررسی‌های runtime استفاده می‌کنند:

python -m plugins.platforms.google_chat.oauth --install-deps

گیت‌وی را شروع کنید:

hermes gateway

لاگی شبیه این باید ببینید:

[GoogleChat] Connected; project=my-chat-bot-123, subscription=<redacted>,
             bot_user_id=users/XXXX, flow_control(msgs=1, bytes=16777216)

در DM ی آزمایشی «hola» بفرستید. ربات نشانگر «Hermes is thinking…» پست می‌کند و بعد همان پیام را درجا با پاسخ واقعی edit می‌کند — بدون سنگ‌قبرهای «message deleted».

سفارشی کردن نشانگر وضعیت-کار

متن نشانگر از طریق typing_status_text در ~/.hermes/config.yaml قابل‌پیکربندی است — مثلاً دستیار بچه‌گربه‌ای به نام Ada:

yaml
platforms:
  google_chat:
    # Custom working-state marker text (default: "Hermes is thinking…").
    typing_status_text: "is pouncing… 🐾"

برخلاف خط status زودگذر اسلک، این یک پیام واقعی پست‌شده است که درجا با پاسخ edit می‌شود — پس هرچه اینجا ست کنید موقتاً به‌عنوان پیام عادی در چت ظاهر می‌شود. برای غیرفعال کردن کامل نشانگر ‏typing_indicator: false را ست کنید.

۳ فرمت و قابلیت‌ها

‏Google Chat زیرمجموعهٔ محدودی از markdown را رندر می‌کند:

پشتیبانی‌شدهپشتیبانی‌نشده
‏*bold*، ‏_italic_، ‏~strike~، ‏`code`سرصفحه‌ها، فهرست‌ها
تصاویر inline از طریق URLدکمه‌های Interactive Card v2 ‏(v1 این گیت‌وی)
پیوست‌های native ی فایل ‏(بعد از /setup-files — گام ۴ را ببینید)ویس‌نوت native / ویدیوی دایره‌ای

پرامپت سیستمی ایجنت سرنخ مخصوص-Google-Chat دارد تا این محدودیت‌ها را بداند و از فرمت‌هایی که رندر نمی‌شوند اجتناب کند.

سقف اندازهٔ پیام: ۴۰۰۰ نویسه per-message. پاسخ‌های بلندتر ایجنت خودکار بین چند پیام شکسته می‌شوند.

پشتیبانی thread: وقتی کاربر داخل thread reply کند هرمس thread.name را آشکار و پاسخش را در همان thread پست می‌کند، پس هر thread نشست جداگانهٔ هرمس می‌گیرد.

سؤالات clarify به‌صورت کارت‌های تعاملی

وقتی ایجنت سؤال چندگزینه‌ای clarify بپرسد، adapter آن را به‌صورت Card v2 ی native با یک دکمه per-gزینه به‌علاوهٔ دکمهٔ «Other / type answer» رندر می‌کند به‌جای فهرست متنی شماره‌دار. کلیک روی دکمه مستقیماً به سؤال جواب می‌دهد ‏(رویدادهای CARD_CLICKED گزینه را به نشست منتظر برمی‌گردانند). اگر ارسال کارت شکست بخورد یا سؤال گزینه‌های ثابت نداشته باشد adapter به clarify متنی استاندارد برمی‌گردد. بدون هیچ پیکربندی.

۴ تحویل پیوست native ‏(اختیاری)

همان اول ربات می‌تواند متن بفرستد، تصویر inline از طریق URL و دانلود-کارت برای صدا/ویدیو/اسناد. برای تحویل پیوست‌های native چت — همون widget ی فایل که وقتی انسان drag-and-drop می‌کند می‌بینید — هر کاربر یک بار از طریق جریان OAuth ی per-user به ربات مجوز می‌دهد.

چرا جریان جداگانه

نقطهٔ پایانی media.upload ی Google Chat احراز هویت service-account را hard-reject می‌کند:

This method doesn't support app authentication with a service account. Authenticate with a user account.

هیچ نقش یا scope ی IAM این را درست نمی‌کند. نقطهٔ پایانی فقط credential های کاربر می‌پذیرد. پس ربات هر وقت فایل آپلود کند باید به‌عنوان کاربر عمل کند — دقیقاً به‌عنوان کاربری که فایل را خواسته.

راه‌اندازی یک‌باره ‏(per profile)

  1. در همان پروژهٔ GCP به APIs & Services ← Credentials بروید.
  2. Create credentials ← OAuth client ID ← Desktop app.
  3. JSON را دانلود و روی ماشینی که هرمس اجراست منتقل کنید.
  4. کلاینت را با هرمس ثبت کنید ‏(زیر پروفایلی که می‌خواهید scope شود اجرا کنید):
# Default profile:
python -m plugins.platforms.google_chat.oauth \
    --client-secret /path/to/client_secret.json

# A named profile gets its own separate registration:
hermes -p <profile> python -m plugins.platforms.google_chat.oauth \
    --client-secret /path/to/client_secret.json

این client secret را در خانهٔ هرمس پروفایل فعال می‌نویسد ‏(مثلاً ‏~/.hermes/google_chat_user_client_secret.json برای پروفایل پیش‌فرض). client secret مخصوص-پروفایل است نه مشترک بین پروفایل‌ها — هر پروفایل خودش را ثبت می‌کند. عمدی است: پروفایل‌ها مرزهای auth ایزوله‌اند، پس دو پروفایل می‌توانند به اپ‌ها/حساب‌های OAuth ی گوگل متفاوت اشاره کنند. یک بار per-profil ی نیازمند تحویل پیوست ثبتش کنید.

مجوزدهی per-user ‏(داخل چت)

هر کاربر جریان را یک بار در DM خودش با ربات اجرا می‌کند:

  1. /setup-files را به ربات می‌فرستد. ربات وضعیت و گام بعد را جواب می‌دهد.
  2. ‏/setup-files start می‌فرستد. ربات URL ی OAuth جواب می‌دهد.
  3. URL را باز می‌کند، Allow را می‌زند و می‌بیند مرورگر در بارگیری ‏http://localhost:1/?...&code=... شکست می‌خورد. این شکست مورد انتظار است — کد auth در نوار URL است.
  4. URL ی شکست‌خورده ‏(یا فقط مقدار code=...) را کپی و به‌صورت ‏/setup-files <PASTED_URL> به چت paste می‌کند. ربات آن را با refresh token مبادله می‌کند.

توکن در ‏~/.hermes/google_chat_user_tokens/<sanitized_email>.json فرود می‌آید. درخواست‌های فایل بعدی در DM ی آن کاربر از توکن خودش استفاده می‌کنند، پس ربات به‌عنوان او آپلود و پیام در space اش فرود می‌آید.

برای revoke ی بعدی: ‏/setup-files revoke فقط توکن همان کاربر را حذف می‌کند. توکن سایرین دست‌نخورده می‌ماند.

Scope

جریان دقیقاً یک scope می‌خواهد: ‏chat.messages.create. هم media.upload و هم messages.create ی ارجاع‌کننده به attachmentDataRef ی آپلود‌شده را پوشش می‌دهد. نه Drive، نه scope های گسترده‌تر چت — کمترین-امتیاز، عمداً.

رفتار چند-کاربره

وقتی درخواست‌کننده هنوز توکن per-user نداشته باشد ربات به توکن legacy تک‌کاربره در ‏~/.hermes/google_chat_user_token.json برمی‌گردد ‏(اگر از نصب pre-multi-user مانده). وقتی هیچ‌کدام موجود نباشد ربات اعلان متنی واضحی پست می‌کند که از درخواست‌کننده می‌خواهد /setup-files را اجرا کند.

revoke کردن توسط کاربر فقط slot خودش را پاک می‌کند. خطای 401/403 از توکن یک کاربر فقط cache ی همان کاربر را اخراج می‌کند. کاربران همدیگر را به هم نمی‌ریزند.

۵ عیب‌یابی

ربات بعد از فرستادن «hola» ساکت می‌ماند.

  1. در کنسول بررسی کنید subscription ی Pub/Sub پیام‌های تحویل‌نشده دارد. اگر دارد یعنی هرمس احراز هویت نشده — GOOGLE_CHAT_SERVICE_ACCOUNT_JSON را تأیید و اینکه SA به‌عنوان Pub/Sub Subscriber روی subscription فهرست شده.
  2. اگر subscription صفر پیام دارد یعنی Google Chat منتشر نمی‌کند. binding ی IAM روی topic را دوباره چک کنید: chat-api-push@system.gserviceaccount.com باید Pub/Sub Publisher داشته باشد.
  3. لاگ‌های hermes gateway را برای [GoogleChat] Connected چک کنید. اگر [GoogleChat] Config validation failed دیدید پیام خطا می‌گوید کدام env var را درست کنید.

ربات reply می‌کند ولی به‌جای پاسخ ایجنت پیام خطا می‌آید.

لاگ‌ها را برای [GoogleChat] Pub/Sub stream died ببینید — اگر تکرار شد شاید credential های SA تان rotate شده یا subscription حذف شده باشد. بعد از ۱۰ تلاش adapter خودش را fatal علامت می‌زند.

«403 Forbidden» روی هر پیام خروجی.

ربات از space حذف شده یا در کنسول Chat API revoke شده. دوباره در space نصبش کنید ‏(رویداد ADDED_TO_SPACE بعدی پیام‌رسانی را خودکار دوباره فعال می‌کند).

هشدارهای «Rate limit hit» زیادی.

سهمیه‌های پیش‌فرض Chat API اجازهٔ ۶۰ پیام per-space-per-minute می‌دهند. اگر ایجنت‌تان پاسخ‌های استریم بلندی تولید می‌کند که از آن عبور می‌کند adapter با backoff نمایی retry می‌کند — ولی همچنان latency ی قابل‌دید برای کاربر می‌بینید. پاسخ‌های مختصر یا بالا بردن سهمیه در کنسول GCP را در نظر بگیرید.

ربات مدام اعلان «/setup-files» را پست می‌کند به‌جای فایل‌ها.

درخواست‌کننده توکن OAuth ی per-user ندارد و fallback ی legacy هم نیست. در DM اش /setup-files را اجرا و گام ۴ را دنبال کنید. بعد از تکمیل مبادله، درخواست فایل بعدی بدون ری‌استارت گیت‌وی natively آپلود می‌شود.

‏/setup-files start می‌گوید «No client credentials stored.»

راه‌اندازی یک‌باره برای این پروفایل انجام نشده (client secret مخصوص-پروفایل است، پس ثبت زیر یک پروفایل توسط پروفایل دیگر دیده نمی‌شود). از ترمینال زیر پروفیلی که گیت‌وی استفاده می‌کند اجرایش کنید:

# Default profile:
python -m plugins.platforms.google_chat.oauth \
    --client-secret /path/to/client_secret.json

# Named profile:
hermes -p <profile> python -m plugins.platforms.google_chat.oauth \
    --client-secret /path/to/client_secret.json

سپس دوباره /setup-files start را بفرستید.

‏/setup-files <PASTED_URL> می‌گوید «Token exchange failed.»

کد auth تک‌مصرفی و کوتاه‌عمر است ‏(معمولاً چند دقیقه). /setup-files start را بفرستید تا URL تازه بگیرید و دوباره تلاش کنید.

۶ نکات امنیتی

  • Scope ی Service Account: adapter مقادیر chat.bot و pubsub را می‌خواهد. اعمال واقعی باید IAM باشد — به SA حداقل را بدهید ‏(roles/pubsub.subscriber + roles/pubsub.viewer روی subscription) نه نقش‌های Pub/Sub ی سطح-پروژه یا سطح-سازمان.
  • محافظت دانلود پیوست: هرمس فقط به URL هایی توکن bearer ی SA را الصاق می‌کند که host شان با allowlist ی کوتاهی از دامنه‌های متعلق-به-گوگل بخورد ‏(googleapis.com، ‏drive.google.com، ‏lh[3-6].googleusercontent.com و چند مورد دیگر). هر host دیگری قبل از درخواست HTTP reject می‌شود تا سناریوهای SSRF ای که رویداد دستکاری‌شده می‌تواند توکن bearer را به سرویس metadata ی GCE redirect کند مهار شوند.
  • Redaction: ایمیل‌های Service Account، مسیرهای subscription و topic توسط agent/redact.py از خروجی لاg حذف می‌شوند. dump ی envelope ی دیباگ ‏(GOOGLE_CHAT_DEBUG_RAW=1) از همان فیلتر redaction عبور و در DEBUG لاگ می‌شود.
  • سازگاری: اگر قصد دارید این ربات را به workspace ی مقررات‌مند ‏(هر چیزی با سیاست data-residency یا AI-governance) وصل کنید قبل از اولین نصب آن تأیید را بگیرید.
  • Scope ی OAuth ی کاربر: جریان پیوست per-user فقط chat.messages.create را می‌خواهد — حداقلی که media.upload و messages.create ی پیگیری را پوشش می‌دهد. توکن‌ها به‌صورت JSON خام در ~/.hermes/google_chat_user_tokens/<sanitized_email>.json ماندگار می‌شوند ‏(محافظ، مجوزهای فایل‌سیستم است — همان مدل فایل کلید SA). هر توکن دقیقاً متعلق به یک کاربر است؛ revoke به همان کاربر scope می‌شود.
