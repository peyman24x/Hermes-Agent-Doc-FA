خانه/کار با Hermes/گیت‌ورک‌تری

گیت‌ورک‌تری (Git Worktrees)

هرمس ایجنت اغلب روی مخازن بزرگ و طولانی‌عمر استفاده می‌شود. وقتی می‌خواهید:

  • چند ایجنت را موازی روی همان پروژه اجرا کنید، یا
  • بازآرایی‌های آزمایشی را از شاخهٔ اصلی‌تان ایزوله نگه دارید،

ورک‌تری‌های گیت امن‌ترین راه دادنِ چک‌اوتِ خودش به هر ایجنت بدون تکثیر کل مخزن هستند.

این صفحه نشان می‌دهد چطور ورک‌تری را با هرمس ترکیب کنید تا هر نشست پوشهٔ کاری تمیز و ایزوله داشته باشد.

۱ چرا ورک‌تری با هرمس؟

هرمس پوشهٔ کاری جاری را ریشهٔ پروژه تلقی می‌کند:

  • ‏CLI: پوشه‌ای که hermes یا hermes chat را در آن اجرا می‌کنید
  • گیت‌وی‌های پیام‌رسانی: پوشهٔ تنظیم‌شده با terminal.cwd در ~/.hermes/config.yaml

اگر چند ایجنت را در همان چک‌اوت اجرا کنید، تغییرهایشان می‌تواند در هم تداخل کند:

  • ایجنتی ممکن است فایل‌هایی را که دیگری استفاده می‌کند حذف یا بازنویسی کند.
  • فهمیدن اینکه کدام تغییرها متعلق به کدام آزمایش‌اند سخت‌تر می‌شود.

با ورک‌تری، هر ایجنت می‌گیرد:

  • شاخه و پوشهٔ کاری خودش
  • تاریخچهٔ چک‌پوینت‌منیجر خودش برای /rollback

همچنین ببینید: «چک‌پوینت‌ها و /rollback».

۲ شروع سریع: ساخت ورک‌تری

از داخل نشست: /worktree new

سریع‌ترین مسیر (الهام‌گرفته از /worktree new مربوط به Copilot CLI): از یک نشست CLI تعاملی، اجرا کنید

فرمان در چت
/worktree new my-experiment

هرمس .worktrees/my-experiment/ را داخل مخزن می‌سازد (شاخهٔ hermes/my-experiment، بر پایهٔ نوکِ راهنِ تازه-fetch‌شده مگر worktree_sync: false)، و ابزارهای ترمینال و فایل نشست را به آن بازهدایت می‌کند — بدون نیاز به ری‌استارت. نام را حذف کنید تا یک درخت تصادفی hermes-<id> بگیرید. /worktree به‌تنهایی درخت فعال را نشان می‌دهد؛ ‏/worktree list همه را فهرست می‌کند. هنگام خروج، درخت فقط اگر کامیت ناپوش‌شده داشته باشد نگه داشته می‌شود، دقیقاً مثل hermes -w.

دستی با گیت

از مخزن اصلی‌تان (دارای .git/)، یک ورک‌تری جدید برای شاخهٔ ویژگی بسازید:

bash
# از ریشهٔ مخزن اصلی
cd /path/to/your/repo

# ساخت شاخه و ورک‌تری جدید در ../repo-feature
git worktree add ../repo-feature feature/hermes-experiment

این می‌سازد:

  • یک پوشهٔ جدید: ../repo-feature
  • یک شاخهٔ جدید: feature/hermes-experiment چک‌اوت‌شده در آن پوشه

حالا می‌توانید به ورک‌تری جدید cd کنید و هرمس را آنجا اجرا کنید:

bash
cd ../repo-feature

# شروع هرمس در ورک‌تری
hermes

هرمس خواهد:

  • ../repo-feature را ریشهٔ پروژه ببیند.
  • آن پوشه را برای فایل‌های زمینه، ویرایش کد و ابزارها استفاده کند.
  • یک تاریخچهٔ چک‌پوینت جدا برای /rollback در دامنهٔ همین ورک‌تری استفاده کند.

۳ اجرای چند ایجنت به‌صورت موازی

می‌توانید چند ورک‌تری، هرکدام با شاخهٔ خودش، بسازید:

bash
cd /path/to/your/repo

git worktree add ../repo-experiment-a feature/hermes-a
git worktree add ../repo-experiment-b feature/hermes-b

در ترمینال‌های جدا:

bash
# ترمینال ۱
cd ../repo-experiment-a
hermes

# ترمینال ۲
cd ../repo-experiment-b
hermes

هر پروسهٔ هرمس:

  • روی شاخهٔ خودش کار می‌کند‏ (feature/hermes-a در برابر feature/hermes-b).
  • چک‌پوینت‌ها را زیر هش مخزن سایهٔ متفاوتی می‌نویسد (مشتق از مسیر ورک‌تری).
  • می‌تواند مستقل /rollback استفاده کند بدون اثر بر دیگری.

این به‌ویژه مفید است وقتی:

  • بازآرایی‌های گروهی اجرا می‌کنید.
  • رویکردهای متفاوتی به همان کار را امتحان می‌کنید.
  • نشست‌های CLI + گیت‌وی را روی همان مخزن بالادستی جفت می‌کنید.

۴ پاک‌سازی امن ورک‌تری‌ها

وقتی با آزمایشی تمام کردید:

  1. تصمیم بگیرید کار را نگه دارید یا دور بریزید.
  2. اگر نگه‌داشتن را می‌خواهید:
    • شاخه را مثل همیشه در شاخهٔ اصلی merge کنید.
  3. ورک‌تری را حذف کنید:
bash
cd /path/to/your/repo

# حذف پوشهٔ ورک‌تری و ارجاعش
git worktree remove ../repo-feature

نکته‌ها:

  • git worktree remove از حذف ورک‌تریِ دارای تغییرات کامیت‌نشده بدون force سر باز می‌زند.
  • حذف ورک‌تری شاخه را خودکار حذف نمی‌کند؛ می‌توانید با فرمان‌های عادی git branch شاخه را حذف یا نگه دارید.
  • دادهٔ چک‌پوینت هرمس زیر ~/.hermes/checkpoints/ با حذف ورک‌تری خودکار هرس نمی‌شود، ولی معمولاً بسیار کوچک است.

۵ بهترین شیوه‌ها

  • یک ورک‌تری به‌ازای هر آزمایش هرمس
    • برای هر تغییر اساسی، شاخه/ورک‌تری اختصاصی بسازید. این دیف‌ها را متمرکز و PRها را کوچک و بازبینی‌پذیر نگه می‌دارد.
  • شاخه‌ها را به نام آزمایش بگذارید
    • مثلاً feature/hermes-checkpoints-docs، ‏feature/hermes-refactor-tests.
  • مکرر کامیت کنید
    • از کامیت‌های گیت برای نقاط عطف سطح‌بالا استفاده کنید. از «چک‌پوینت‌ها و /rollback» به‌عنوان تور ایمنی برای ویرایش‌های ابزارمحور بین کامیت‌ها.
  • هنگام استفاده از ورک‌تری، هرمس را از ریشهٔ مخزن bare اجرا نکنید
    • به‌جایش پوشه‌های ورک‌تری را ترجیح دهید تا هر ایجنت دامنهٔ روشنی داشته باشد.

۶ استفاده از hermes -w (حالت ورک‌تری خودکار)

هرمس پرچم داخلی -w دارد که خودکار یک ورک‌تری گیتِ یک‌بارمصرف با شاخهٔ خودش می‌سازد. لازم نیست ورک‌تری را دستی راه بیندازید — فقط داخل مخزنتان cd کنید و اجرا کنید:

bash
cd /path/to/your/repo
hermes -w

هرمس خواهد:

  • یک ورک‌تری موقت زیر .worktrees/ داخل مخزنتان بسازد.
  • یک شاخهٔ ایزوله چک‌اوت کند (مثلاً hermes/hermes-<hash>).
  • کل نشست CLI را داخل همان ورک‌تری اجرا کند.

این آسان‌ترین راه گرفتن ایزوله‌سازی ورک‌تری است. می‌توانید با کوئری تکی هم ترکیبش کنید:

bash
hermes -w -z "Fix issue #123"

برای ایجنت‌های موازی، چند ترمینال باز کنید و در هرکدام hermes -w اجرا کنید — هر فراخوانی به‌طور خودکار ورک‌تری و شاخهٔ خودش را می‌گیرد.

۷ جمع‌بندی

  • از ورک‌تری‌های گیت استفاده کنید تا هر نشست هرمس چک‌اوت تمیز خودش را داشته باشد.
  • از شاخه‌ها برای ثبت تاریخچهٔ سطح‌بالای آزمایش‌هایتان.
  • از چک‌پوینت + ‏/rollback برای بازیابی از اشتباهات داخل هر ورک‌تری.

این ترکیب به شما می‌دهد:

  • تضمین قوی که ایجنت‌ها و آزمایش‌های متفاوت روی هم نمی‌روند.
  • چرخه‌های تکرار سریع با بازیابی آسان از ویرایش‌های بد.
  • پول‌ریکوئست‌های تمیز و بازبینی‌پذیر.

۸ توسعهٔ سطوح UI روی ورک‌تری‌ها

سطوح TypeScript‏ (ui-tui/، ‏apps/desktop/) هرکدام به یک node_modules نیاز دارند که یک npm ci تازه به‌ازای هر ورک‌تری، روی هر شاخه تکثیرش می‌کند. اگر روی TUI یا اپ دسکتاپ از چند ورک‌تری کار می‌کنید، «TUI و دسکتاپ از Worktreeها» را برای راهنماهای htui / hgui که با سیم‌لینک یک نصب را به اشتراک می‌گذارند ببینید.
