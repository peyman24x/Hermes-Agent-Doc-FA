۱ مقدمه: داکر و Hermes Agent

دو روش کاملاً متمایز برای پیوند داکر با Hermes Agent وجود دارد:

  • اجرای Hermes درون داکر — خودِ ایجنت داخل یک کانتینر اجرا می‌شود (تمرکز اصلی همین صفحه).
  • داکر به‌عنوان بک‌اند ترمینال — ایجنت روی سیستم میزبان شما اجرا می‌شود، اما هر دستور را داخل یک کانتینر سندباکس داکرِ واحد و ماندگار اجرا می‌کند که در تمام طول عمر پروسهٔ Hermes، بین فراخوانی‌های ابزار، دستور /new و ساب‌ایجنت‌ها زنده می‌ماند (شرح کامل در بخش «داکر به‌عنوان بک‌اند ترمینال» و مستندات Configuration ← Docker Backend).

این صفحه گزینهٔ اول را پوشش می‌دهد. کانتینر تمام داده‌های کاربر (پیکربندی، کلیدهای API، نشست‌ها، مهارت‌ها و حافظه‌ها) را در یک پوشهٔ واحد ذخیره می‌کند که از سیستم میزبان در مسیر /opt/data به کانتینر متصل (mount) شده است. خودِ ایمیج بی‌حالت (stateless) است و می‌توان آن را با دریافت (pull) نسخهٔ جدید ارتقا داد، بدون اینکه چیزی از پیکربندی از دست برود.

۲ شروع سریع

اگر این اولین بار است که Hermes Agent را اجرا می‌کنید، روی میزبان یک پوشهٔ داده بسازید و کانتینر را به‌صورت تعاملی اجرا کنید تا ویزارد راه‌اندازی (Setup Wizard) فعال شود:

bash
mkdir -p ~/.hermes
docker run -it --rm \
  -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent setup
⚠️ از کنسول‌های مبتنی بر مرورگر VPS برای دستورات نصب استفاده نکنید

برخی ارائه‌دهندگان VPS (مثل Hetzner Cloud و چند مورد دیگر) کنسولی مبتنی بر مرورگر برای مدیریت سرورها ارائه می‌دهند. این کنسول‌ها کاراکترهای خاص را به‌درستی منتقل نمی‌کنند — مثلاً : ممکن است به‌صورت ; برسد، @ ممکن است نادرست نمایش داده شود و چیدمان‌های صفحه‌کلید غیرانگلیسی وضعیت بدتری دارند — که به‌طور خاموش آرگومان‌های docker run مانند -v ~/.hermes:/opt/data و -e KEY=value و کلیدها/توکن‌های API که پیست می‌کنید را خراب می‌کند.

به‌جای آن از طریق SSH وصل شوید (ssh root@<host>) تا با خیال راحت بتوانید دستورات را کپی/پیست کنید. اگر مجبورید از کنسول مرورگر استفاده کنید، دستورات را به‌جای پیست کردن، دستی تایپ کنید و قبل از زدن Enter، همهٔ :، @، = و /ها را در نتیجه دوباره بررسی کنید.

این کار شما را وارد ویزارد راه‌اندازی می‌کند که کلیدهای API را از شما می‌پرسد و آن‌ها را در ~/.hermes/.env می‌نویسد. این کار فقط یک بار لازم است. به‌شدت توصیه می‌شود در همین مرحله یک سیستم چت را برای کار کردن گیت‌وی تنظیم کنید.

💡 نکته

داخل کانتینر، یک بار hermes setup --portal را اجرا کنید — توکنِ بازنشانی (refresh token) در والوم متصل‌شدهٔ ~/.hermes باقی می‌ماند. برای اطلاعات بیشتر به بخش «Nous Portal» مراجعه کنید.

۳ اجرا در حالت گیت‌وی (Gateway)

پس از پیکربندی، کانتینر را در پس‌زمینه به‌عنوان یک گیت‌وی دائمی اجرا کنید (تلگرام، دیسکورد، اسلک، واتساپ و غیره):

bash
docker run -d \
  --name hermes \
  --restart unless-stopped \
  -v ~/.hermes:/opt/data \
  -p 8642:8642 \
  nousresearch/hermes-agent gateway run

پورت 8642 سرور API سازگار با OpenAI گیت‌وی و نقطهٔ پایانی سلامت (health endpoint) را در دسترس قرار می‌دهد. اگر فقط از پلتفرم‌های چت استفاده می‌کنید (تلگرام، دیسکورد و غیره) این پورت اختیاری است، اما اگر می‌خواهید داشبورد یا ابزارهای بیرونی به گیت‌وی دسترسی داشته باشند، ضروری است.

🛡 گیت‌وی تحت نظارت (Supervised) اجرا می‌شود

داخل ایمیج رسمی داکر، دستور gateway run به‌طور خودکار توسط s6-overlay نظارت می‌شود: اگر پروسهٔ گیت‌وی از کار بیفتد، ظرف چند ثانیه و بدون از دست رفتن کانتینر دوباره راه‌اندازی می‌شود، و داشبورد (وقتی HERMES_DASHBOARD=1 تنظیم شده باشد) هم در کنار آن نظارت می‌شود. خودِ پروسهٔ CMD مربوط به gateway run یک ضربانِ sleep infinity است که کانتینر را زنده نگه می‌دارد در حالی که s6 پروسهٔ واقعی گیت‌وی را مدیریت می‌کند — بنابراین docker stop همچنان همه‌چیز را تمیز خاموش می‌کند، اما docker logs خروجی گیت‌ویِ تحت نظارت را نشان می‌دهد.

در docker logs یک پیام یک‌خطی مبنی بر تأیید این ارتقا خواهید دید. برای خارج شدن از این حالت — و دریافت رفتار قدیمیِ «گیت‌وی پروسهٔ اصلی کانتینر است و خروج کانتینر یعنی خروج گیت‌وی» — از پرچم --no-supervise استفاده کنید یا HERMES_GATEWAY_NO_SUPERVISE=1 را تنظیم کنید. این خروج از حالت برای تست‌های دودی CI که می‌خواهند کانتینر هم‌راستا با کد وضعیت گیت‌وی خارج شود مفید است؛ برای استقرارهای عملیاتی (پروداکشن)، حالت پیش‌فرضِ تحت نظارت به‌طور مطلق بهتر است.

این رفتار فقط به ایمیج مبتنی بر s6 اعمال می‌شود. ایمیج‌های قدیمی‌تر (مبتنی بر tini) همچنان gateway run را به‌عنوان پروسهٔ اصلی foreground اجرا می‌کنند.

لاگ‌های گیت‌وی کجا می‌روند؟ برای نقشهٔ کامل مسیریابی لاگ‌ها (گیت‌وی هر پروفایل، داشبورد، آشتی‌ساز بوت و docker logs کل کانتینر) به بخش «لاگ‌ها کجا می‌روند؟» مراجعه کنید.

توقف‌های سختِ حلقهٔ ابزار برای گیت‌وی‌های بدون نظارت

تنظیم tool_loop_guardrails.hard_stop_enabled به‌طور پیش‌فرض false است که برای نشست‌های تعاملی CLI و TUI — جایی که یک انسان می‌تواند هشدارهای مکررِ فراخوانی ابزار را ببیند — منطقی است. اما در استقرارهای گیت‌وی یا سروریِ بدون نظارت، هشدارها به‌تنهایی ممکن است نتوانند ایجنتی را که در حلقهٔ تکراریِ فراخوانی ابزار گیر کرده متوقف کنند. اپراتورهایی که رفتار قطع‌کنندهٔ مدار (circuit-breaker) می‌خواهند، باید توقف‌های سخت را به‌طور صریح در فایل config.yaml پروفایل فعال کنند:

yaml — config.yaml
tool_loop_guardrails:
  hard_stop_enabled: true
  hard_stop_after:
    exact_failure: 5
    idempotent_no_progress: 5

فعال‌سازی سرور API روی شبکه

نکته: سرور API مشروط به API_SERVER_ENABLED=true است. برای در دسترس قرار دادن آن فراتر از 127.0.0.1 داخل کانتینر، باید API_SERVER_HOST=0.0.0.0 و یک API_SERVER_KEY هم تنظیم کنید (حداقل ۸ کاراکتر — یکی با دستور openssl rand -hex 32 بسازید). مثال:

bash
docker run -d \
  --name hermes \
  --restart unless-stopped \
  -v ~/.hermes:/opt/data \
  -p 8642:8642 \
  -e API_SERVER_ENABLED=true \
  -e API_SERVER_HOST=0.0.0.0 \
  -e API_SERVER_KEY="$(openssl rand -hex 32)" \
  -e API_SERVER_CORS_ORIGINS='*' \
  nousresearch/hermes-agent gateway run
⛔ هشدار امنیتی

باز کردن هر پورتی روی ماشینِ متصل به اینترنت یک ریسک امنیتی است. نباید این کار را بکنید، مگر اینکه ریسک‌های آن را به‌طور کامل درک کرده باشید.

۴ اجرای داشبورد

داشبورد وب داخلی، به‌عنوان یک سرویس تحت نظارت s6-rc در کنار گیت‌وی و در همان کانتینر اجرا می‌شود. برای فعال شدن آن، HERMES_DASHBOARD=1 را تنظیم کنید:

bash
docker run -d \
  --name hermes \
  --restart unless-stopped \
  -v ~/.hermes:/opt/data \
  -p 8642:8642 \
  -p 9119:9119 \
  -e HERMES_DASHBOARD=1 \
  nousresearch/hermes-agent gateway run

داشبورد توسط s6 نظارت می‌شود — اگر از کار بیفتد، s6-supervise پس از یک تأخیر کوتاه (backoff) به‌طور خودکار آن را دوباره راه‌اندازی می‌کند. خروجی stdout/stderr داشبورد به docker logs <container> هدایت می‌شود (بدون پیشوند؛ خروجی خودِ گیت‌وی اکنون در فایل s6-log مربوط به هر پروفایل جداگانه ذخیره می‌شود — به بخش «لاگ‌ها کجا می‌روند؟» مراجعه کنید — تا این دو جریان با هم تداخل نکنند).

متغیرهای محیطی داشبورد

متغیر محیطیتوضیحاتپیش‌فرض

داشبورد داخل کانتینر به‌طور پیش‌فرض به 0.0.0.0 متصل می‌شود — بدون این کار، پورتِ منتشرشدهٔ -p 9119:9119 از میزبان در دسترس نبود. برای محدود کردن اتصال به loopback کانتینر (برای راه‌اندازی‌های sidecar یا پروکسی معکوس)، HERMES_DASHBOARD_HOST=127.0.0.1 را تنظیم کنید.

دروازهٔ احراز هویت داشبورد

دروازهٔ احراز هویت داشبورد به‌طور خودکار وقتی هر دو شرایط زیر برقرار باشند فعال می‌شود:

  • آدرس اتصال، غیرحلقه‌محلی باشد (مثلاً پیش‌فرضِ 0.0.0.0 داخل کانتینر)، و
  • یک پلاگین DashboardAuthProvider ثبت شده باشد.

سه روش داخلی برای برآورده کردن شرط دوم وجود دارد:

  • نام‌کاربری/رمزعبور — ساده‌ترین حالت برای کانتینرهای خودمیزبان (self-hosted) / داخلی / homelab روی یک شبکهٔ مطمئن یا پشت VPN: مقادیر HERMES_DASHBOARD_BASIC_AUTH_USERNAME + HERMES_DASHBOARD_BASIC_AUTH_PASSWORD را تنظیم کنید (و HERMES_DASHBOARD_BASIC_AUTH_SECRET را برای نشست‌های پایدار در برابر ری‌استارت). برای مواجههٔ مستقیم با اینترنت عمومی مناسب نیست.
  • OAuth (Nous Portal) — برای استقرارهای میزبانی‌شده/عمومی: ارائه‌دهندهٔ dashboard_auth/nous هر زمان که HERMES_DASHBOARD_OAUTH_CLIENT_ID تنظیم شود فعال می‌گردد.
  • OIDC خودمیزبان — برای احراز هویت در برابر ارائه‌دهندهٔ هویتِ خودتان از طریق OpenID Connect استاندارد: ارائه‌دهندهٔ dashboard_auth/self_hosted وقتی HERMES_DASHBOARD_OIDC_ISSUER + HERMES_DASHBOARD_OIDC_CLIENT_ID تنظیم شوند فعال می‌شود.

هر کدام را که انتخاب کنید، دروازه پیش از آنکه فراخوان‌کننده بتواند به هر مسیر محافظت‌شده برسد، او را به صفحهٔ ورود هدایت می‌کند. برای جزئیات هر سه ارائه‌دهنده به بخش «داشبورد وب ← احراز هویت» مستندات مراجعه کنید.

اگر هیچ ارائه‌دهنده‌ای ثبت نشده باشد و اتصال هم غیرحلقه‌محلی باشد، داشبورد هنگام راه‌اندازی با خطایی مشخص — که به متغیر محیطیِ مفقود اشاره می‌کند — به‌طور ایمن متوقف می‌شود (fail closed). دیگر هیچ «راه فراری» وجود ندارد که داشبورد را بدون احراز هویت روی یک اتصال عمومی سرو کند: HERMES_DASHBOARD_INSECURE=1 اکنون یک تنظیم منسوخ و بی‌اثر است (فقط یک هشدار ثبت می‌کند و نادیده گرفته می‌شود). یا یک ارائه‌دهنده پیکربندی کنید، یا HERMES_DASHBOARD_HOST=127.0.0.1 را تنظیم کنید و از طریق تونل SSH یا Tailscale به داشبورد دسترسی پیدا کنید.

🔐 چرا --insecure حذف شد؟

داشبوردِ عمومیِ بدون احراز هویت، نقطهٔ ورودِ کمپینِ ماندگاری پیکربندی MCP در ژوئن ۲۰۲۶ بود: اسکنرهای اینترنتی به داشبوردهای در معرض دید (و سرورهای OpenAI API) رسیدند و ایجنت را وادار به کاشتنِ یک درِ پشتی کلید SSH کردند. دروازهٔ احراز هویت اکنون روی هر اتصالِ غیرحلقه‌محلی اجباری است. برای یک ماشین در شبکهٔ محلی مطمئن / homelab، ارائه‌دهندهٔ داخلیِ نام‌کاربری/رمزعبور (HERMES_DASHBOARD_BASIC_AUTH_USERNAME + _PASSWORD) ساده‌ترین راهِ برآورده کردن این الزام بدون نیاز به زیرساخت اضافه است.

اجرای داشبورد در کانتینری جداگانه

اجرای داشبورد به‌عنوان کانتینری جداگانه پشتیبانی می‌شود، به شرط آن‌که آن کانتینر فضای نام PID و شبکهٔ میزبان را با هم به اشتراک بگذارد (مثلاً network_mode: host — همان‌طور که فایل docker-compose.yml خود مخزن این کار را می‌کند؛ به سرویس dashboard آن مراجعه کنید). تشخیصِ زنده‌بودنِ گیت‌وی به فضای نام PID مشترک با پروسهٔ گیت‌وی نیاز دارد، بنابراین این محدودیت فقط به داشبوردهایی اعمال می‌شود که در کانتینرهای شبکهٔ bridge ایزوله و بدون فضای نام PID مشترک اجرا می‌شوند.

۷ درخت نصب تغییرناپذیر

در ایمیج‌های میزبانی‌شده و منتشرشده، مسیر /opt/hermes درختِ نصب برنامه است. مالک آن root است و برای کاربرِ زمانِ اجرا یعنی hermes فقط‌خواندنی است؛ بنابراین نوبت‌های ایجنت، نشست‌های گیت‌وی، عملیات داشبورد و دستورات معمولِ docker exec hermes hermes ... نمی‌توانند سورسِ هسته، .venv داخلی، node_modules یا بستهٔ TUI را در محل ویرایش کنند.

تمام وضعیتِ قابل‌تغییرِ Hermes باید زیر /opt/data باشد: پیکربندی، .env، پروفایل‌ها، مهارت‌ها، حافظه‌ها، نشست‌ها، لاگ‌ها، فایل‌های بارگذاری‌شده در داشبورد، پلاگین‌ها و سایر فایل‌های مدیریت‌شده توسط کاربر. ایمیج همچنین نوشتن فایل‌های .pyc در زمان اجرا و نصب‌های تنبلِ (lazy) وابستگی‌های Hermes در /opt/hermes را غیرفعال می‌کند؛ وابستگی‌های پلتفرمیِ اختیاریِ مورد نیازِ ایمیج منتشرشده باید از قبل داخل ایمیج پخته (baked) شوند یا از طریق ساختِ ایمیج جدید نصب گردند.

در ایمیج‌های میزبانی‌شده/منتشرشده، خودبهبودیِ ایجنت (self-improvement) محدود به مهارت‌ها، حافظه، پلاگین‌ها و پیکربندی زیر /opt/data است. سورس هستهٔ نصب‌شده زیر /opt/hermes تغییرناپذیر است؛ تغییرات هسته از طریق PR به مخزن اعمال می‌شود و با به‌روزرسانی ایمیج عرضه می‌گردد، نه با ویرایش زندهٔ نصبِ در حال اجرا.

اگر یک اپراتور نیاز به تعمیر یا بررسی فایل‌های خارج از /opt/data دارد، باید آگاهانه از شل root استفاده کند. شیمِ (shim) مربوط به hermes معمولاً دستور docker exec hermes hermes ... را به کاربر زمان اجرا بازمی‌گرداند؛ متغیر HERMES_DOCKER_EXEC_AS_ROOT=1 را برای یک فراخوانی یک‌باره با دسترسی root تنظیم کنید، وقتی که صریحاً به معنای‌شناسیِ root نیاز دارید.

CLIهای مهارت‌ها که اعتبارنامه‌ها را زیر ~ ذخیره می‌کنند باید در برابر HOMEِ زیرپروسه راه‌اندازی اولیه شوند، نه فقط ریشهٔ والوم داده. مثلاً مهارت xurl وضعیت OAuth را در ~/.xurl نگه می‌دارد؛ در چیدمان رسمی داکر، فراخوانی‌های ابزار Hermes آن را به‌صورت /opt/data/home/.xurl می‌خوانند، بنابراین احراز هویت دستی xurl را با HOME=/opt/data/home اجرا کنید و درستی آن را با HOME=/opt/data/home xurl auth status بررسی کنید.

⚠️ هشدار مهم

هرگز دو کانتینر گیت‌وی Hermes را همزمان روی همان پوشهٔ داده اجرا نکنید — فایل‌های نشست و مخازن حافظه برای دسترسی همزمانِ نوشتن طراحی نشده‌اند.

۸ پشتیبانی چندپروفایلی

Hermes از چندین پروفایل پشتیبانی می‌کند — زیرپوشه‌های جداگانه در ~/.hermes/ که به شما امکان می‌دهند از یک نصب واحد، ایجنت‌های مستقل اجرا کنید (با SOUL، مهارت‌ها، حافظه، نشست‌ها و اعتبارنامه‌های متفاوت). داخل ایمیج رسمی داکر، درخت نظارت s6 هر پروفایل را به‌عنوان یک سرویس تحت نظارتِ درجه‌یک می‌بیند؛ بنابراین استقرار توصیه‌شده، یک کانتینر است که همهٔ پروفایل‌ها را میزبانی می‌کند.

هر پروفایلی که با hermes profile create <name> ساخته می‌شود، این‌ها را دریافت می‌کند:

  • یک جایگاه سرویس s6 اختصاصی در /run/service/gateway-<name>/ که به‌صورت پویا توسط زمان اجرا ثبت می‌شود — بدون نیاز به بازسازی کانتینر.
  • راه‌اندازی مجدد خودکار پس از خرابی، با تأخیرِ مدیریت‌شده توسط s6-supervise.
  • لاگ‌های چرخشیِ هر پروفایل در ${HERMES_HOME}/logs/gateways/<name>/current (۱۰ آرشیو × ۱ مگابایت).
  • ماندگاری وضعیت در سراسر ری‌استارت‌های کانتینر: آشتی‌سازِ زمانِ بوت، فایل gateway_state.json را از هر پوشهٔ پروفایل می‌خواند و جایگاه سرویس را فقط برای پروفایل‌هایی که آخرین وضعیت ثبت‌شده‌شان «در حال اجرا» بوده بالا می‌آورد. تنها گیت‌ویی که خودتان صریحاً متوقف کرده‌اید (hermes gateway stop) در سراسر ری‌استارت خاموش می‌ماند — ری‌استارت کانتینر، ارتقای ایمیج یا خروج غیرمنتظره، وضعیت ثبت‌شده را «در حال اجرا» باقی می‌گذارد و بنابراین گیت‌وی در بوت بعدی به‌طور خودکار راه‌اندازی می‌شود.

فرمان‌های چرخهٔ حیات

فرمان‌های چرخهٔ حیات را که روی میزبان اجرا می‌کردید، به همان شکل می‌توانید از داخل کانتینر هم اجرا کنید:

bash
# ساخت یک پروفایل — جایگاه s6 مربوط به gateway-<name> را ثبت می‌کند.
docker exec hermes hermes profile create coder

# شروع / توقف / ری‌استارت — به s6-svc فرمان می‌دهد؛ چرخهٔ حیات گیت‌وی از docker restart جان سالم به در می‌برد.
docker exec hermes hermes -p coder gateway start
docker exec hermes hermes -p coder gateway stop
docker exec hermes hermes -p coder gateway restart

# مشاهدهٔ وضعیت — داخل کانتینر عبارت `Manager: s6 (container supervisor)` را گزارش می‌کند.
docker exec hermes hermes -p coder gateway status

# حذف یک پروفایل — جایگاه s6 را هم برمی‌چیند.
docker exec hermes hermes profile delete coder

در پس‌زمینه، دستور hermes gateway start/stop/restart داخل کانتینر رهگیری و به s6-svc روی پوشهٔ سرویسِ درست هدایت می‌شود؛ نیازی نیست دستورات s6 را مستقیماً یاد بگیرید. برای مشاهدهٔ وضعیت خام ناظر، از /command/s6-svstat /run/service/gateway-<name> استفاده کنید (توجه: مسیر /command/ فقط برای پروسه‌هایی که توسط درخت نظارت تولید شده‌اند در PATH قرار دارد — هنگام فراخوانی از docker exec، مسیر مطلق را بدهید).

دسترسی به بیش از یک پروفایل از خارج کانتینر

دو سطحِ متفاوت برای رسیدن به گیت‌وی یک پروفایل از بیرون وجود دارد که رفتار متفاوتی هم دارند — آن‌ها را با هم اشتباه نگیرید:

  • Hermes Desktop (و داشبورد وب). اتصالِ Remote Gateway در اپلیکیشن Desktop با یک بک‌اندِ hermes dashboard صحبت می‌کند (پورت پیش‌فرض 9119 که با HERMES_DASHBOARD=1 فعال می‌شود) — نه با سرور OpenAI API. یک بک‌اند داشبورد به همهٔ پروفایل‌های هم‌مکان سرویس می‌دهد: سوییچر پروفایلِ اپلیکیشن، پروفایل هدف را همراه هر درخواست می‌فرستد و بک‌اند، HERMES_HOME همان پروفایل را روی دیسک باز می‌کند. بنابراین برای Desktop به پورت دوم — یا اتصال دوم — برای هر پروفایل نیاز ندارید؛ یک اتصال به :9119 از طریق سوییچر، همهٔ پروفایل‌ها را پوشش می‌دهد.
  • کلاینت‌های API سازگار با OpenAI (مانند Open WebUI، LobeChat، /v1/...). این‌ها با سرور API هر پروفایل صحبت می‌کنند که برای همهٔ پروفایل‌ها پورت 8642 را می‌گیرد (که از API_SERVER_PORT یا platforms.api_server.extra.port خوانده می‌شود — تخصیص خودکار و کلیدِ config.yaml/gateway.port وجود ندارد). اگر می‌خواهید یک کلاینت به پروفایل دومِ مشخصی برسد، به آن پروفایل یک API_SERVER_PORT متمایز در .env خودش بدهید؛ در غیر این صورت گیت‌وی آن پروفایل هم سعی می‌کند پورت 8642 را بگیرد و با پروفایل پیش‌فرض تداخل می‌کند:
bash
# ساخت پروفایل (جایگاه s6 یعنی gateway-<name> را ثبت می‌کند)
docker exec hermes hermes profile create work

# هدایت سرور API آن به یک پورت آزاد (نوشتن در .env خودِ پروفایل)
cat >> /opt/data/profiles/work/.env <<'EOF'
API_SERVER_ENABLED=true
API_SERVER_PORT=8643
EOF

docker exec hermes hermes -p work gateway restart

مقدار API_SERVER_PORT را همیشه در .env خودِ هر پروفایل نگه دارید، هرگز در بلوک environment: سراسریِ کانتینر — یک مقدار سراسری، همهٔ پروفایل‌ها را مجبور به استفاده از یک پورت می‌کند و با هم تداخل پیدا می‌کنند. با شبکهٔ bridge، پورت اضافه را در docker-compose.yml منتشر کنید (- "8643:8643")؛ با network_mode: host از قبل روی میزبان در دسترس است. اتصالِ پروفایل پیش‌فرض روی پورت 8642 دست‌نخورده می‌ماند.

چرا «یک کانتینر با چند پروفایل»، نه «چند کانتینر»؟

قبل از مهاجرت به s6، الگوی توصیه‌شده «یک کانتینر به ازای هر پروفایل» بود، چون ناظری داخل کانتینر برای مدیریت چند گیت‌وی وجود نداشت. با s6 به‌عنوان PID 1 دیگر چنین ضرورتی نیست و چیدمان تک‌کانتینری تقریباً در همهٔ ابعاد ساده‌تر است:

معیاریک کانتینر، چند پروفایلیک کانتینر به ازای هر پروفایل
سربار دیسکیک ایمیج، یک venv داخلی، یک کش PlaywrightN ایمیج / N کش
سربار حافظهکش مفسر Python و node_modules مشترکدر هر کانتینر تکرار می‌شود
ساخت پروفایلdocker exec ... hermes profile create <name> (چند ثانیه)فراخوانی جدید docker run + تخصیص پورت + پیکربندی bind-mount
بازیابی از خرابی هر پروفایلراه‌اندازی مجدد خودکار با s6-supervise--restart unless-stopped داکر (کندتر، کارهای خواهرِ در حال اجرا را از کار می‌اندازد)
لاگ‌هافایل چرخشیِ هر پروفایل با s6-log + لاگ ممیزیِ بوتِ کانتینرdocker logs <name> به ازای هر کانتینر — بدون چرخش داخلی
پشتیبان‌گیرییک پوشهٔ ~/.hermesN پوشه که باید هماهنگ شوند

پروفایل پیش‌فرض (default) همیشه در اولین بوت ثبت می‌شود؛ بنابراین یک کانتینر تازه، درست از همان ابتدا با یک گیت‌وی تحت نظارت شروع به کار می‌کند. پروفایل‌های اضافی صرفاً افزودنی‌های زمانِ اجرا هستند.

چه زمانی کانتینر جداگانه می‌خواهید؟

پروفایل-داخل-کانتینر، حالت پیش‌فرض است. فقط وقتی برای هر پروفایل کانتینر جداگانه اجرا کنید که دلیل مشخصی داشته باشید:

  • ایزوله‌سازی منابع به ازای هر بار کاری — مثلاً یک نشستِ ابزار مرورگرِ رام‌نشده در پروفایل A نباید بتواند پروفایل B را با اتمام حافظه (OOM) از کار بیندازد. کانتینرها به شما --memory / --cpus جداگانه برای هر پروفایل می‌دهند.
  • پین‌کردن مستقل ایمیج — تگ‌های ایمیج بالادستیِ متفاوت برای هر بار کاری.
  • تفکیک شبکه — شبکه‌های داکر مجزا برای هر پروفایل (مثلاً یکی رو به مشتری، یکی داخلی).
  • انطباق / شعاع تأثیر آسیب (blast radius) — اعتبارنامه‌های مجزا هرگز یک درخت پروسه در سطح سیستم‌عامل را به اشتراک نمی‌گذارند.

در این موارد، به ازای هر پروفایل یک سرویس با container_name، volumes و ports متمایز تعریف کنید:

yaml — docker-compose.yml
services:
  hermes-work:
    image: nousresearch/hermes-agent:latest
    container_name: hermes-work
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"
    volumes:
      - ~/.hermes-work:/opt/data

  hermes-personal:
    image: nousresearch/hermes-agent:latest
    container_name: hermes-personal
    restart: unless-stopped
    command: gateway run
    ports:
      - "8643:8642"
    volumes:
      - ~/.hermes-personal:/opt/data

هشدارِ بخش «حجم‌های پایدار» همچنان اعتبار دارد: هرگز دو کانتینر را همزمان به همان پوشهٔ ~/.hermes اشاره ندهید. ناظر s6 داخل هر کانتینر مجموعه پروفایل‌های خودش را مدیریت می‌کند؛ اشتراک‌گذاری یک والوم داده بین کانتینرها، فایل‌های نشست و مخازن حافظه را خراب می‌کند.

۹ لاگ‌ها کجا می‌روند؟

کانتینر s6 چهار سطحِ لاگ متمایز دارد و این که «چرا گیت‌وی من چیزی در docker logs نشان نمی‌دهد؟» یک موضوع رایج و غافلگیرکننده است. خلاصهٔ راهنما:

منبعکجا ذخیره می‌شودنحوهٔ خواندن
گیت‌وی هر پروفایل (hermes gateway run و گیت‌وی‌های هر پروفایل زیر s6) همزمان در دو جا: docker logs <container> (بلادرنگ، بدون پیشوند اضافه) و ${HERMES_HOME}/logs/gateways/<profile>/current (چرخشی، با مُهر زمانی ISO-8601، ۱۰ آرشیو × ۱ مگابایت) docker logs -f hermes یا روی میزبان: tail -F ~/.hermes/logs/gateways/default/current
داشبورد (وقتی HERMES_DASHBOARD=1 باشد) docker logs <container> (بدون پیشوند) docker logs -f hermes — درهم‌آمیخته با خطوط گیت‌وی
آشتی‌ساز بوت (ثبت می‌کند کدام گیت‌وی‌های پروفایل در هر شروعِ کانتینر بازیابی شده‌اند) ${HERMES_HOME}/logs/container-boot.log (لاگ ممیزیِ فقط-الحاقی) tail -F ~/.hermes/logs/container-boot.log
لاگ‌های عمومی Hermes (agent.log، errors.log) ${HERMES_HOME}/logs/ (آگاه از پروفایل) docker exec hermes hermes logs --follow [--level WARNING] [--session <id>]

دو نکتهٔ عملی که ارزش دانستن دارند:

  • نسخهٔ فایلی در logs/gateways/<profile>/current همان چیزی است که از ری‌استارت کانتینر جان سالم به در می‌برد. docker logs فقط خروجیِ طول عمر کانتینرِ فعلی را نگه می‌دارد (و با docker rm پاک می‌شود)؛ اما فایل‌های چرخشی روی والومِ متصل‌شده به میزبان باقی می‌مانند.
  • شکلِ خط ممیزیِ آشتی‌سازِ بوت چنین است: <iso-timestamp> profile=<name> prior_state=<state> action=<registered|started>؛ بنابراین یک grep profile=coder ~/.hermes/logs/container-boot.log سریع نشان می‌دهد یک پروفایلِ مشخص آخرین بار کِی بازیابی شده و اینکه s6 آن را خودکار راه‌اندازی کرده یا نه.

۱۰ ارسال متغیرهای محیطی

کلیدهای API از فایل /opt/data/.env داخل کانتینر خوانده می‌شوند. همچنین می‌توانید متغیرهای محیطی را مستقیم پاس بدهید:

bash
docker run -it --rm \
  -v ~/.hermes:/opt/data \
  -e ANTHROPIC_API_KEY="sk-ant-..." \
  -e OPENAI_API_KEY="sk-..." \
  nousresearch/hermes-agent

پرچم‌های مستقیمِ -e بر مقادیر فایل .env اولویت دارند. این روش برای CI/CD یا یکپارچه‌سازی با مدیرِ رمزها (secrets manager) مفید است، جایی که نمی‌خواهید کلیدها روی دیسک ذخیره شوند.

۱۱ دنبال «داکر به‌عنوان بک‌اند ترمینال» هستید؟

این صفحه اجرای خودِ Hermes داخل داکر را پوشش می‌دهد. اگر می‌خواهید Hermes فراخوانی‌های terminal / execute_code ایجنت را داخل یک کانتینر سندباکس داکر اجرا کند (یک کانتینرِ طولانی‌عمرِ مشترک بین پروسه‌های Hermes — برای جزئیات به issue شمارهٔ #20561 مراجعه کنید)، آن یک بلوک پیکربندی جداگانه است: terminal.backend: docker به‌همراه terminal.docker_image، terminal.docker_volumes، terminal.docker_forward_env، terminal.docker_env، terminal.docker_run_as_host_user، terminal.docker_extra_args، terminal.docker_persist_across_processes و terminal.docker_orphan_reaper. برای مجموعهٔ کامل تنظیمات، از جمله قواعد چرخهٔ حیات کانتینر، به بخش «پیکربندی ← بک‌اند داکر» مستندات مراجعه کنید.

۱۲ نمونهٔ Docker Compose

برای استقرار پایدار همراه با هم گیت‌وی و داشبورد، استفاده از یک docker-compose.yaml مناسب است:

yaml — docker-compose.yaml
services:
  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"   # API گیت‌وی
      - "9119:9119"   # داشبورد (فقط وقتی HERMES_DASHBOARD=1 باشد در دسترس است)
    volumes:
      - ~/.hermes:/opt/data
    environment:
      - HERMES_DASHBOARD=1
      # برای پاس‌دادن متغیرهای محیطی خاص به‌جای فایل .env، خطوط زیر را از کامنت خارج کنید:
      # - ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY}
      # - OPENAI_API_KEY=${OPENAI_API_KEY}
      # - TELEGRAM_BOT_TOKEN=${TELEGRAM_BOT_TOKEN}
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "2.0"

با docker compose up -d شروع کنید و لاگ‌ها را با docker compose logs -f ببینید. خروجی stdout گیت‌ویِ تحت نظارت هم‌زمان در ${HERMES_HOME}/logs/gateways/<profile>/current روی والوم هم نوشته می‌شود — برای نقشهٔ کامل مسیریابی به بخش «لاگ‌ها کجا می‌روند؟» مراجعه کنید.

۱۳ اختیاری: پل صوت دسکتاپ لینوکس

کار کردن حالت صوتی (Voice Mode) در داکر به دو چیز جداگانه نیاز دارد: باید به Hermes اجازه داده شود دستگاه‌های صوتی را داخل کانتینر جستجو (probe) کند، و کانتینر هم باید بتواند به سرور صوتی میزبان شما دسترسی پیدا کند. راه‌اندازیِ زیر، لوله‌کشی صوتیِ میزبان را برای دسکتاپ‌های لینوکسی پوشش می‌دهد که یک سوکت سازگار با PulseAudio ارائه می‌دهند — از جمله بسیاری از پیکربندی‌های PipeWire.

⚠️ احتیاط

این یک راه‌حل مخصوص دسکتاپ لینوکس است، نه یک قابلیت عمومیِ Docker Desktop. زمانی مفید است که صوتِ میزبان از قبل درست کار می‌کند و شما حالت صوتی CLI را داخل کانتینر Hermes می‌خواهید. اگر Hermes همچنان پیام Running inside Docker container -- no audio devices را نمایش داد، از یک بیلد استفاده کنید که شامل پشتیبانیِ جستجوی صوتِ داکر برای PULSE_SERVER / PIPEWIRE_REMOTE باشد.

ابتدا، یک فایل پیکربندی ALSA در کنار فایل Compose خود بسازید:

asound.conf
pcm.!default {
    type pulse
    hint {
        show on
        description "Default ALSA Output (PulseAudio)"
    }
}

pcm.pulse {
    type pulse
}

ctl.!default {
    type pulse
}

سپس یک ایمیج مشتقِ کوچک با پلاگین ALSA PulseAudio بسازید:

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends libasound2-plugins \
    && rm -rf /var/lib/apt/lists/*

از آن ایمیج در Compose استفاده کنید و سوکت PulseAudio و کوکیِ کاربر میزبان را به کانتینر پاس دهید:

      context: .
      dockerfile: Dockerfile.audio

آن را با UID/GID کاربر میزبان راه‌اندازی کنید تا پروسهٔ کانتینر بتواند به سوکت صوتیِ مخصوصِ آن کاربر دسترسی داشته باشد:

۱۵ Dockerfile چه کاری انجام می‌دهد؟

ایمیج رسمی بر پایهٔ debian:13.4 ساخته شده و شامل موارد زیر است:

  • Python 3.13 با وابستگی‌های همگام‌شده از lockfile از طریق uv sync --frozen --no-install-project برای بسته‌های اختیاریِ از-پیش-نصب‌شده (all، messaging، هویت Anthropic/Bedrock/Azure، Hindsight، Matrix) و سپس یک نصبِ editable بدون وابستگی از خودِ Hermes.
  • Node.js 26 + npm (برای اتوماسیون مرورگر، پل واتساپ، بسته‌های TUI/Desktop و ابزارهای ساخت workspace).
  • Playwright همراه با Chromium (npx playwright install --with-deps chromium --only-shell).
  • ripgrep، ffmpeg، git و xz-utils به‌عنوان ابزارهای سیستمی.
  • docker-cli — تا ایجنت‌های در حال اجرا داخل کانتینر بتوانند دیمن داکرِ میزبان را هدایت کنند (برای فعال‌سازی، /var/run/docker.sock را bind-mount کنید) برای docker build، docker run، بازرسی کانتینر و غیره.
  • openssh-client — بک‌اند ترمینال SSH را از داخل کانتینر ممکن می‌کند. بک‌اند SSH از باینری ssh سیستمی استفاده می‌کند؛ بدون این پکیج، در نصب‌های کانتینری به‌طور خاموش و بی‌صدا شکست می‌خورد.
  • پل واتساپ (scripts/whatsapp-bridge/).
  • s6-overlay نسخهٔ ۳ به‌عنوان PID 1 (جایگزین tini قدیمی) — داشبورد و گیت‌وی‌های هر پروفایل را با راه‌اندازی مجدد خودکار پس از خرابی نظارت می‌کند، پروسه‌های زامبی را جمع می‌کند و سیگنال‌ها را به‌درستی عبور می‌دهد.

ایمیج، مسیر /opt/hermes را در زمان اجرا به‌عنوان یک درخت نصبِ تغییرناپذیر در نظر می‌گیرد. بسته‌های اختیاری Python، ورک‌اسپیس‌های Node و فایل‌های TUI که باید داخل داکر در دسترس باشند، باید حین ساخت ایمیج داخل آن پخته شوند؛ نصب‌های تنبلِ زمانِ اجرا غیرفعال‌اند تا گیت‌وی‌های تحت نظارت و دستورات docker exec hermes … سعی نکنند فایل‌های وابستگی را در درخت سورسِ فقط‌خواندنی بنویسند.

ENTRYPOINT کانتینر یک دیسپچر کوچک است (docker/entrypoint-dispatch.sh). وقتی کانتینر PID 1 را در اختیار دارد (داکر/Podman معمولی)، /init مربوط به s6-overlay را اجرا (exec) می‌کند و درخت نظارتِ کاملِ توضیح‌داده‌شده در ادامه را در اختیارتان می‌گذارد. وقتی یک پلتفرم، entrypoint ایمیج را زیر PID-1 خودش می‌پیچد (Fly.io Machines، docker run --init، برخی راه‌اندازی‌های Nomad/Kubernetes)، دستور /init با خطای s6-overlay-suexec: fatal: can only run as pid 1 سقوط می‌کرد — بنابراین دیسپچر به‌جای آن، بوت‌استرپِ مرحلهٔ ۲ را مستقیماً اجرا می‌کند و wrapper اصلی را بدون s6 اجرا می‌کند. در آن مسیر جایگزین، دستورِ درخواست‌شده همچنان اجرا می‌شود، اما سرویس‌های تحت نظارت (داشبورد و گیت‌وی‌های هر پروفایل) در دسترس نیستند.

در مسیر PID-1، /init این کارها را انجام می‌دهد:

  • /etc/cont-init.d/01-hermes-setup (همان docker/stage2-hook.sh) را به‌عنوان root اجرا می‌کند: نگاشت مجددِ اختیاری UID/GID، اصلاح مالکیت والوم، ایجاد فایل‌های .env / config.yaml / SOUL.md در اولین بوت، اجرای مهاجرت‌های غیرتعاملیِ طرحِ پیکربندی (مگر با HERMES_SKIP_CONFIG_MIGRATION=1)، و همگام‌سازی مهارت‌های داخلی.
  • /etc/cont-init.d/02-reconcile-profiles (همان hermes_cli.container_boot) را اجرا می‌کند: پوشهٔ $HERMES_HOME/profiles/<name>/ را می‌پیماید، جایگاه سرویس s6 گیت‌ویِ هر پروفایل را زیر /run/service/gateway-<profile>/ بازسازی می‌کند، و فقط پروفایل‌هایی را خودکار راه‌اندازی می‌کند که آخرین وضعیت ثبت‌شده‌شان «در حال اجرا» بوده است (به بخش «نظارت بر گیت‌وی هر پروفایل» مراجعه کنید).
  • سرویس‌های ایستای s6-rc یعنی main-hermes و dashboard را راه‌اندازی می‌کند.
  • CMD کانتینر را به‌عنوان برنامهٔ اصلی اجرا می‌کند (/opt/hermes/docker/main-wrapper.sh) که آرگومان‌هایی را که کاربر به docker run داده، این‌گونه مسیریابی می‌کند:
    • بدون آرگومان ← hermes (حالت پیش‌فرض)
    • اگر آرگومان اول یک فایل اجرایی روی PATH باشد (مثلاً sleep یا bash) ← مستقیماً همان اجرا می‌شود
    • هر چیز دیگر ← hermes <args> (عبورِ زیرفرمان)
    کانتینر با خروجِ همین برنامهٔ اصلی، و همراه با همان کد خروج، خارج می‌شود.
💥 تغییر مهم (Breaking Change) نسبت به ایمیج‌های پیش از s6

ENTRYPOINT کانتینر اکنون دیسپچرِ entrypoint-dispatch.sh است (که تحت PID 1 به /init مربوط به s6-overlay واگذار می‌شود)، نه /usr/bin/tini. هر پنج الگوی مستندِ فراخوانی docker run (بدون آرگومان، chat -q "…"، sleep infinity، bash، --tui) دقیقاً مانند ایمیج مبتنی بر tini رفتار می‌کنند. اگر یک اسکریپت wrapper پایین‌دستی دارید که به رفتار سیگنالیِ مخصوص tini یا فراخوانی هاردکد‌شدهٔ /usr/bin/tini -- وابسته بوده، به تگ ایمیج قبلی پین کنید.

۱۶ مدل دسترسی (Privilege Model)

entrypoint ایمیج را بازنویسی نکنید، مگر اینکه /init (یا به‌طور معادل، شیم قدیمی docker/entrypoint.sh که به هوک مرحلهٔ ۲ فوروارد می‌کند) را در زنجیرهٔ فرمان نگه دارید. /init مربوط به s6-overlay به‌عنوان root اجرا می‌شود تا بتواند در اولین بوت مالکیت والوم را تغییر دهد؛ سپس برای هر سرویس تحت نظارت و هم برای برنامهٔ اصلی، از طریق s6-setuidgid به کاربر hermes تنزل دسترسی می‌یابد. اجرای hermes gateway run به‌عنوان root داخل ایمیج رسمی به‌طور پیش‌فرض رد می‌شود، چون می‌تواند فایل‌های متعلق به root در /opt/data به جا بگذارد و راه‌اندازی‌های بعدیِ داشبورد یا گیت‌وی را بشکند. متغیر HERMES_ALLOW_ROOT_GATEWAY=1 را فقط وقتی تنظیم کنید که آگاهانه این ریسک را می‌پذیرید.

docker exec به‌طور خودکار به کاربر hermes تنزل می‌یابد

دستور docker exec hermes <cmd> به‌طور پیش‌فرض به‌عنوان root داخل کانتینر اجرا می‌شود، اما ایمیج یک شیمِ نازک در /opt/hermes/bin/hermes (اولین مسیر روی PATH) دارد که فراخوان‌های root را تشخیص می‌دهد و به‌طور شفاف از طریق s6-setuidgid hermes دوباره اجرا می‌کند. بنابراین docker exec hermes login، docker exec hermes profile create …، docker exec hermes setup و غیره، همگی فایل‌هایی می‌نویسند که مالکشان UID 10000 است — یعنی برای گیت‌ویِ تحت نظارت قابلِ خواندن‌اند — بدون نیاز به پرچم اضافیِ --user. فراخوان‌های غیر root (خودِ پروسه‌های تحت نظارت، docker exec --user hermes، ساب‌ایجنت‌های kanban داخل کانتینر) به یک مسیر میان‌بر می‌خورند که باینری venv را مستقیماً اجرا می‌کند؛ پس روی مسیرهای پرتردد هیچ سربار اضافه‌ای وجود ندارد.

اگر به‌طور خاص به یک docker exec با دسترسی‌های root نیاز دارید (نشست‌های عیب‌یابی، بررسی وضعیت‌های فقط-root، فایل‌های خارج از /opt/data که مالکش root است)، می‌توانید در همان یک فراخوانی از این تنزل خارج شوید:

bash
docker exec -e HERMES_DOCKER_EXEC_AS_ROOT=1 hermes <cmd>

شیم مقادیر 1 / true / yes را (بدون حساسیت به بزرگی و کوچکی حروف) می‌پذیرد. هر مقدار دیگری — از جمله غلط‌های تایپی مثل =0 — به همان تنزلِ دسترسی منجر می‌شود؛ پس خروجِ خاموش و ناخواسته از این سازوکار ممکن نیست. اگر s6-setuidgid در دسترس نباشد (بیلدهای سفارشی که s6-overlay را حذف کرده‌اند)، شیم از اجرا به‌عنوان root خودداری کرده و با کد خروج 126 متوقف می‌شود تا خرابیِ مدل دسترسی به‌وضوح اعلام شود، و نه این‌که به دامِ تاریخی‌ای بازگردد که در آن docker exec hermes login فایل auth.json را با مالکیت root:root می‌نوشت و احراز هویت گیت‌ویِ تحت نظارت را با هر پیامِ پلتفرم چت می‌شکست.

۱۷ نظارت بر گیت‌وی هر پروفایل

هر پروفایلی که با hermes profile create <name> ساخته می‌شود، به‌طور خودکار یک سرویس گیت‌ویِ تحت نظارتِ s6 که در /run/service/gateway-<name>/ ثبت شده و راه‌اندازی مجددِ خودکارِ حفظ‌کنندهٔ وضعیت در سراسر ری‌استارت‌های کانتینر را دارد، دریافت می‌کند. برای گردش‌کارِ کاربرپسند و فرمان‌های چرخهٔ حیات به بخش «پشتیبانی چندپروفایلی» مراجعه کنید.

مزایای نظارت نسبت به ایمیج پیش از s6:

  • خرابی‌های گیت‌وی پس از یک تأخیر حدوداً ۱ ثانیه‌ای توسط s6-supervise به‌طور خودکار راه‌اندازی مجدد می‌شوند.
  • داشبورد، وقتی با HERMES_DASHBOARD=1 فعال باشد، روی همان درخت نظارت تحت نظر است و همان رفتارِ راه‌اندازی مجدد خودکار را دریافت می‌کند.
  • docker restart، ارتقاهای ایمیج (docker compose up -d --force-recreate) و خروج‌های غیرمنتظره، گیت‌وی‌های در حال اجرا را حفظ می‌کنند: آشتی‌سازِ cont-init فایل $HERMES_HOME/profiles/<name>/gateway_state.json را می‌خواند و اگر آخرین وضعیت ثبت‌شده «در حال اجرا» باشد، جایگاه سرویس را دوباره بالا می‌آورد. فقط یک hermes gateway stop صریح است که وضعیتِ «متوقف» ثبت می‌کند و گیت‌وی را در سراسر ری‌استارت خاموش نگه می‌دارد؛ سیگنال SIGTERM کانتینر/s6 که هنگام ری‌استارت یا ارتقا فرستاده می‌شود، به‌معنای «هنوز در حال اجرا» تلقی شده و گیت‌وی خودکار راه‌اندازی می‌شود.
  • لاگ‌های گیت‌ویِ هر پروفایل زیر $HERMES_HOME/logs/gateways/<profile>/current باقی می‌مانند (چرخشی توسط s6-log)، و اقدامات آشتی‌ساز به ازای هر بوت به $HERMES_HOME/logs/container-boot.log الحاق می‌شوند. برای نقشهٔ کامل مسیریابی به بخش «لاگ‌ها کجا می‌روند؟» مراجعه کنید.
  • hermes status داخل کانتینر عبارت Manager: s6 (container supervisor) را گزارش می‌دهد. برای نمای خامِ ناظر از /command/s6-svstat /run/service/gateway-<name> استفاده کنید (توجه: /command/ فقط برای پروسه‌های درخت نظارت روی PATH است؛ هنگام فراخوانی از docker exec مسیر مطلق را بدهید).

۱۸ ارتقا

آخرین ایمیج را دریافت (pull) کنید و کانتینر را بازسازی کنید. پوشهٔ دادهٔ شما حفظ می‌شود، و کانتینر پیش از راه‌اندازی گیت‌وی، مهاجرت‌های غیرتعاملیِ طرحِ پیکربندی را روی config.yaml متصل‌شده در $HERMES_HOME اجرا می‌کند. وقتی مهاجرت لازم باشد، Hermes ابتدا نسخه‌های پشتیبانِ مُهردار‌شده با زمان را کنارِ config.yaml و .env می‌نویسد.

bash
docker pull nousresearch/hermes-agent:latest
docker rm -f hermes
docker run -d \
  --name hermes \
  --restart unless-stopped \
  -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent gateway run

یا با Docker Compose:

bash
docker compose pull
docker compose up -d

متغیر HERMES_SKIP_CONFIG_MIGRATION=1 را فقط در صورتی تنظیم کنید که بخواهید پیکربندی ماندگار را قبل از بازنویسی توسط ایمیج جدید، دستی بررسی یا مهاجرت دهید.

۱۹ مهارت‌ها و فایل‌های اعتبارنامه

وقتی از داکر به‌عنوان محیط اجرا استفاده می‌کنید (نه روش‌های بالا، بلکه وقتی ایجنت دستورات را داخل یک سندباکس داکر اجرا می‌کند — به بخش «بک‌اند ترمینال» مراجعه کنید)، Hermes برای همهٔ فراخوانی‌های ابزار از یک کانتینرِ طولانی‌عمرِ واحد استفاده می‌کند و پوشهٔ مهارت‌ها (~/.hermes/skills/) و هر فایل اعتبارنامه‌ای که مهارت‌ها اعلام کرده‌اند را به‌طور خودکار به‌صورت والوم‌های فقط‌خواندنی به آن کانتینر متصل (bind-mount) می‌کند. اسکریپت‌ها، قالب‌ها و فایل‌های مرجعِ مهارت‌ها بدون هیچ پیکربندی دستی داخل سندباکس در دسترس‌اند؛ و چون کانتینر در تمام طول عمر پروسهٔ Hermes باقی می‌ماند، هر وابستگی‌ای که نصب کنید یا فایلی که بنویسید، برای فراخوانی ابزار بعدی هم باقی می‌ماند.

همین فرایند همگام‌سازی برای بک‌اندهای SSH و Modal هم انجام می‌شود — مهارت‌ها و فایل‌های اعتبارنامه پیش از هر دستور از طریق rsync یا API مونتِ Modal بارگذاری می‌شوند.

۲۰ نصب ابزارهای بیشتر در کانتینر

ایمیج رسمی با مجموعه‌ای گزینش‌شده از ابزارها عرضه می‌شود (به بخش «Dockerfile چه کاری انجام می‌دهد؟» مراجعه کنید)، اما نه هر ابزاری که یک ایجنت ممکن است بخواهد از قبل نصب شده است. پنج رویکرد توصیه‌شده وجود دارد، به ترتیبِ صعودی از نظر میزان تلاش و ماندگاری.

۱) ابزارهای npm یا Python — از npx یا uvx استفاده کنید

برای هر ابزاری که در npm یا PyPI منتشر شده، به Hermes دستور دهید که آن را از طریق npx (برای npm) یا uvx (برای Python) اجرا کند و آن فرمان را در حافظهٔ پایدارش به خاطر بسپارد. اگر ابزار به فایل پیکربندی یا اعتبارنامه نیاز دارد، به آن دستور دهید این‌ها را زیر /opt/data قرار دهد (مثلاً /opt/data/<tool>/config.yaml).

وابستگی‌ها به‌هنگام نیاز دریافت و برای طول عمر کانتینر کش می‌شوند. پیکربندیِ نوشته‌شده زیر /opt/data از ری‌استارت‌های کانتینر جان سالم به در می‌برد، چون روی پوشهٔ میزبانِ متصل‌شده زندگی می‌کند. خودِ کشِ پکیج‌ها پس از docker rm از بین می‌رود، اما npx و uvx بارِ بعدی که ابزار اجرا شود، آن را به‌طور شفاف دوباره دریافت می‌کنند.

۲) ابزارهای دیگر (پکیج‌های apt، باینری‌ها) — نصب کنید و به خاطر بسپارید

برای هر چیزی خارج از npm یا PyPI — پکیج‌های apt، باینری‌های از-پیش-ساخته، یا runtimeهای زبانی که از قبل در ایمیج نیستند — به Hermes نحوهٔ نصب را آموزش دهید (مثلاً apt-get update && apt-get install -y <package>) و به آن بگویید فرمان نصب را به خاطر بسپارد. ابزار برای باقی عمر کانتینر باقی می‌ماند، و Hermes پس از ری‌استارت کانتینر، وقتی دفعهٔ بعد به آن ابزار نیاز داشت، فرمان نصب را دوباره اجرا می‌کند.

این روش برای ابزارهایی که نصبشان سریع است و گاه‌به‌گاه استفاده می‌شوند مناسب است. برای ابزارهایی که دائماً استفاده می‌شوند، رویکرد بعدی را ترجیح دهید.

۳) نصب‌های ماندگار — یک ایمیج مشتق بسازید

وقتی یک ابزار باید در هر شروعِ کانتینر بی‌درنگ و بدون تأخیرِ نصبِ مجدد در دسترس باشد، ایمیجی جدید بسازید که از nousresearch/hermes-agent ارث می‌برد و ابزار را در یکی از لایه‌های خود نصب می‌کند:

Dockerfile
FROM nousresearch/hermes-agent:latest

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends <your-package> \
    && rm -rf /var/lib/apt/lists/*
USER hermes

آن را بسازید و به‌جای ایمیج رسمی استفاده کنید:

bash
docker build -t my-hermes:latest .
docker run -d \
  --name hermes \
  --restart unless-stopped \
  -v ~/.hermes:/opt/data \
  -p 8642:8642 \
  my-hermes:latest gateway run

اسکریپت entrypoint و معنای‌شناسیِ /opt/data بدون تغییر به ارث می‌رسند، پس بقیهٔ این صفحه همچنان برایتان اعتبار دارد. یادتان باشد وقتی نسخهٔ بالادستیِ جدیدتری از nousresearch/hermes-agent منتشر شد، ایمیج خود را دوباره بسازید.

۴) ابزارهای پیچیده یا استک‌های چندسرویسی — یک کانتینر Sidecar اجرا کنید

برای ابزارهایی که سرویسِ خودشان را با خود می‌آورند (یک پایگاه داده، وب‌سرور، صف پیام، یا مزرعهٔ مرورگر headless) یا برای زندگی داخل کانتینر Hermes بیش از حد سنگین‌اند، آن‌ها را به‌عنوان کانتینری جداگانه روی یک شبکهٔ داکرِ مشترک اجرا کنید. Hermes از طریق نامِ کانتینر به sidecar دسترسی پیدا می‌کند — همان‌طور که به یک سرور استنتاج محلی می‌رسد (به بخش «اتصال به سرورهای استنتاج محلی» مراجعه کنید).

yaml — docker-compose.yml
services:
  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"
    volumes:
      - ~/.hermes:/opt/data
    networks:
      - hermes-net

  my-tool:
    image: example/my-tool:latest
    container_name: my-tool
    restart: unless-stopped
    networks:
      - hermes-net

networks:
  hermes-net:
    driver: bridge

از داخل کانتینر Hermes، سایدکار در آدرس http://my-tool:<port> (یا هر پروتکولی که سرویس می‌کند) در دسترس است. این الگو چرخهٔ حیات، محدودیت‌های منابع و آهنگ ارتقای هر سرویس را مستقل نگه می‌دارد و مانع از متورم‌شدن ایمیج Hermes با وابستگی‌هایی می‌شود که فقط یک ابزار به آن‌ها نیاز دارد.

۵) ابزارهای مفید برای عموم — یک issue یا pull request باز کنید

اگر احتمال می‌دهید ابزاری برای بیشترِ کاربران Hermes Agent مفید باشد، به‌جای حملِ آن در یک ایمیج مشتقِ خصوصی، کمک به پروژهٔ اصلی را در نظر بگیرید. یک issue یا pull request روی مخزن hermes-agent باز کنید و ابزار و مورد استفاده‌اش را توصیف کنید. ابزارهایی که در ایمیج رسمی گنجانده می‌شوند به همهٔ کاربران سود می‌رسانند و از سربارِ نگهداریِ یک انشعاب (fork) پایین‌دستی جلوگیری می‌کنند.

۲۱ اتصال به سرورهای استنتاج محلی (vLLM، Ollama و غیره)

وقتی Hermes در داکر اجرا می‌شود و سرور استنتاج شما (vLLM، Ollama، text-generation-inference و غیره) هم روی میزبان یا در کانتینر دیگری در حال اجراست، بخش شبکه‌سازی به توجه بیشتری نیاز دارد.

Docker Compose (توصیه‌شده)

هر دو سرویس را روی یک شبکهٔ داکر مشترک قرار دهید. این مطمئن‌ترین رویکرد است:

yaml — docker-compose.yml
services:
  vllm:
    image: vllm/vllm-openai:latest
    container_name: vllm
    command: >
      --model Qwen/Qwen2.5-7B-Instruct
      --served-model-name my-model
      --host 0.0.0.0
      --port 8000
    ports:
      - "8000:8000"
    networks:
      - hermes-net
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]

  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    restart: unless-stopped
    command: gateway run
    ports:
      - "8642:8642"
    volumes:
      - ~/.hermes:/opt/data
    networks:
      - hermes-net

networks:
  hermes-net:
    driver: bridge

سپس در فایل ~/.hermes/config.yaml خود، از نام کانتینر به‌عنوان نام میزبان (hostname) استفاده کنید:

yaml — config.yaml
model:
  provider: custom
  model: my-model
  base_url: http://vllm:8000/v1
  api_key: "none"

نکات کلیدی:

  • از نام کانتینر (vllm) به‌عنوان نام میزبان استفاده کنید — نه localhost یا 127.0.0.1، چون این آدرس‌ها به خودِ کانتینر Hermes اشاره می‌کنند.
  • مقدار model باید با --served-model-nameای که به vLLM داده‌اید مطابقت داشته باشد.
  • api_key را روی هر رشتهٔ غیرخالی بگذارید (vLLM وجود این هدر را لازم دارد اما به‌طور پیش‌فرض محتوایش را اعتبارسنجی نمی‌کند).
  • در انتهای base_url اسلش (trailing slash) نگذارید.

اجرای مستقل docker run (بدون Compose)

اگر سرور استنتاج شما مستقیماً روی میزبان اجرا می‌شود (نه در داکر)، از host.docker.internal در مک/ویندوز استفاده کنید، یا در لینوکس از --network host:

macOS / Windows:

bash
docker run -d \
  --name hermes \
  -v ~/.hermes:/opt/data \
  -p 8642:8642 \
  nousresearch/hermes-agent gateway run

# config.yaml
model:
  provider: custom
  model: my-model
  base_url: http://host.docker.internal:8000/v1
  api_key: "none"

لینوکس (شبکهٔ میزبان):

bash
docker run -d \
  --name hermes \
  --network host \
  -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent gateway run

# config.yaml
model:
  provider: custom
  model: my-model
  base_url: http://127.0.0.1:8000/v1
  api_key: "none"

با --network host، پرچم -p نادیده گرفته می‌شود — همهٔ پورت‌های کانتینر مستقیماً روی میزبان در معرض دسترس‌اند.

تأیید اتصال

از داخل کانتینر Hermes بررسی کنید که سرور استنتاج در دسترس است:

bash
docker exec hermes curl -s http://vllm:8000/v1/models

باید یک پاسخ JSON که مدلِ سرو‌شدهٔ شما را فهرست می‌کند ببینید. اگر این کار شکست خورد، موارد زیر را بررسی کنید:

  • هر دو کانتینر روی همان شبکهٔ داکر هستند (docker network inspect hermes-net)
  • سرور استنتاج روی 0.0.0.0 گوش می‌دهد، نه 127.0.0.1
  • شمارهٔ پورت با هم مطابقت دارد

Ollama

Ollama هم به همان شکل کار می‌کند. اگر Ollama روی میزبان اجرا می‌شود، از host.docker.internal:11434 (مک/ویندوز) یا 127.0.0.1:11434 (لینوکس با --network host) استفاده کنید. اگر Ollama در کانتینر خودش و روی همان شبکهٔ داکر اجرا می‌شود:

yaml — config.yaml
model:
  provider: custom
  model: llama3
  base_url: http://ollama:11434/v1
  api_key: "none"

۲۲ عیب‌یابی

کانتینر بی‌درنگ خارج می‌شود

لاگ‌ها را بررسی کنید: docker logs hermes. علل رایج:

  • فایل .env مفقود یا نامعتبر است — اول به‌صورت تعاملی اجرا کنید تا راه‌اندازی کامل شود
  • تداخل پورت‌ها، در صورت اجرا با پورت‌های در معرض دسترس

خطاهای «Permission denied»

هوک مرحلهٔ ۲ کانتینر، دسترسی‌ها را داخل هر سرویس تحت نظارت از طریق s6-setuidgid به کاربر غیر root یعنی hermes (با UID 10000) تنزل می‌دهد. اگر پوشهٔ ~/.hermes/ روی میزبان شما مالکِ UID متفاوتی است، متغیرهای HERMES_UID/HERMES_GID — یا نام‌های مستعارِ PUID/PGID برای هم‌ترازی با ایمیج‌های LinuxServer.io و NAS — را منطبق با کاربر میزبان تنظیم کنید، یا مطمئن شوید پوشهٔ داده قابل نوشتن است:

bash
chmod -R 755 ~/.hermes

روی NAS (UGOS، Synology، unRAID) پوشهٔ داده معمولاً یک bind mount متعلق به UID میزبان است که کانتینر نمی‌تواند مالکش را تغییر دهد. در این حالت PUID/PGID (یا HERMES_UID/HERMES_GID) را روی آن کاربر میزبان تنظیم کنید تا زمانِ اجرا به‌عنوان مالکِ mount اجرا شود، نه به‌عنوان UID 10000:

bash
docker run -d \
  --name hermes \
  -e PUID=1000 -e PGID=10 \
  -v /volume1/docker/hermes:/opt/data \
  nousresearch/hermes-agent gateway run

دستور docker exec hermes <cmd> هم به‌طور خودکار به UID 10000 تنزل می‌یابد — برای جزئیات و راهِ خروجِ به‌ازای-هر-فراخوانی، به بخش «سقوط خودکار docker exec» مراجعه کنید.

ابزارهای مرورگر کار نمی‌کنند

Playwright به حافظهٔ مشترک (shared memory) نیاز دارد. پرچم --shm-size=1g را به فرمان Docker run اضافه کنید:

bash
docker run -d \
  --name hermes \
  --shm-size=1g \
  -v ~/.hermes:/opt/data \
  nousresearch/hermes-agent gateway run

گیت‌وی پس از مشکلات شبکه دوباره وصل نمی‌شود

پرچم --restart unless-stopped بیشتر خرابی‌های گذرا را مدیریت می‌کند. اگر گیت‌وی گیر کرده است، کانتینر را ری‌استارت کنید:

bash
docker restart hermes

bash

docker run -it --rm nousresearch/hermes-agent:latest version   # بررسی نسخه
