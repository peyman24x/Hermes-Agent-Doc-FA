نشست‌ها

هرمس ایجنت هر گفتگو را به‌طور خودکار به‌صورت یک نشست ذخیره می‌کند. نشست‌ها امکان ازسرگیری گفتگو، جستجوی بین-نشستی و مدیریت کامل تاریخچهٔ گفتگوها را فراهم می‌کنند.

۱ نشست‌ها چگونه کار می‌کنند

هر گفتگو — چه از CLI، تلگرام، دیسکورد، اسلک، واتساپ، سیگنال، ماتریکس، تیمز یا هر پلتفرم پیام‌رسانی دیگر — به‌صورت نشستی با تاریخچهٔ کامل پیام‌ها ذخیره می‌شود. نشست‌ها در این‌ها پیگیری می‌شوند:

  1. دیتابیس SQLite (~/.hermes/state.db) — فرادادهٔ ساخت‌یافتهٔ نشست با جستجوی تمام‌متن FTS5، به‌علاوهٔ تاریخچهٔ کامل پیام‌ها

دیتابیس SQLite این‌ها را ذخیره می‌کند:

  • شناسهٔ نشست، پلتفرم مبدأ، شناسهٔ کاربر
  • عنوان نشست (نام یکتا و انسانی‌خوان)
  • نام مدل و پیکربندی
  • اسنپ‌شات پرامپت سیستمی
  • تاریخچهٔ کامل پیام‌ها (نقش، محتوا، فراخوانی ابزار، نتایج ابزار)
  • شمارش توکن‌ها (ورودی/خروجی)
  • مهرهای زمانی (started_at، ended_at)
  • شناسهٔ نشست والد (برای انشعاب نشستِ ناشی از فشرده‌سازی)

چه چیزی به زمینه اضافه می‌شود

هرمس تاریخچهٔ نشست را ذخیره می‌کند تا بتواند گفتگوها را ازسر بگیرد، اما هر بایتی که تا حالا داشته را دوباره و دوباره نمی‌فرستد. در هر نوبت، مدل پرامپت سیستمیِ انتخاب‌شده، پنجرهٔ گفتگوی فعلی و هر محتوایی را که هرمس صریحاً برای آن نوبت تزریق می‌کند می‌بیند.

پیوست‌های رسانه‌ای به‌صورت ورودیِ مخصوص-نوبت مدیریت می‌شوند:

  • تصاویر ممکن است به‌صورت بومی به فراخوانی بعدی مدل وصل شوند، یا وقتی مدل فعال از بینایی بومی پشتیبانی نمی‌کند از پیش به توصیف متنی تحلیل شوند.
  • صوت وقتی گفتار-به-متن پیکربندی شده به متن رونویسی می‌شود.
  • اسناد متنی می‌توانند متن استخراج‌شده‌شان لحاظ شود؛ سایر انواع سند معمولاً با مسیر محلیِ ذخیره‌شده و یک یادداشت کوتاه نمایندگی می‌شوند.
  • مسیر پیوست‌ها و متن استخراجی/مشتق‌شده ممکن است در رونوشت ظاهر شود، اما بایت‌های خام تصویر، صوت یا فایل باینری به‌تکرار در پرامپت‌های آینده کپی نمی‌شوند.

مثلاً اگر کاربری تصویری بفرستد و از هرمس بخواهد از آن میم بسازد، هرمس ممکن است آن تصویر را یک بار با بینایی بررسی کند و یک اسکریپت پردازش تصویر اجرا کند. نوبت‌های آینده به‌طور خودکار JPEG اصلی را در زمینه حمل نمی‌کنند. فقط آنچه در گفتگو نوشته شده را حمل می‌کنند: درخواست کاربر، توصیف کوتاه تصویر، مسیر کش محلی یا پاسخ نهایی دستیار.

شایع‌ترین عامل رشد زمینه خودِ فایل رسانه‌ای نیست؛ متن مفصل است: رونوشت‌های پیست‌شده، لاگ‌های کامل، خروجی‌های بزرگ ابزار، دیف‌های بلند، گزارش‌های وضعیت مکرر و سرریزهای اثباتِ باجزئیات. به‌جای کپی‌کردن مصنوعات بزرگ در چت، خلاصه‌ها، مسیرهای فایل، گزیده‌های متمرکز و جستجوهای پشتیبان‌شده با ابزار را ترجیح دهید.

💡 نکته

وقتی نشست طولانی شد از /compress، برای رشتهٔ تازه از /new و فقط وقتی می‌خواهید نشست‌های پایان‌یافتهٔ قدیمی را از ذخیره‌گاه پاک کنید از hermes sessions prune استفاده کنید. اگر state.db صرفاً بزرگ شده، اول از گزینهٔ غیرمخرب شروع کنید: hermes sessions optimize قطعات اندیس FTS5 را ادغام و دیتابیس را VACUUM می‌کند بدون دست‌زدن به هیچ دادهٔ نشستی. فشرده‌سازی زمینهٔ فعال را کوچک می‌کند؛ یک حذفِ حریم خصوصی نیست. به /new نام بدهید (مثلاً /new payments-refactor) تا عنوان اولیهٔ نشست جدید از همان اول تنظیم شود — برای یافتنش بعداً با /resume <name> یا در انتخابگر /sessions مفید است.

۲ ازسرگیری نشست در CLI

گفتگوهای قبلی را از CLI با --continue یا --resume ازسر بگیرید:

ادامهٔ آخرین نشست

bash
# ازسرگیری جدیدترین نشست CLI
hermes --continue
hermes -c

# یا با زیرفرمان chat
hermes chat --continue
hermes chat -c

این جدیدترین نشستِ cli را از دیتابیس SQLite پیدا و تاریخچهٔ کامل گفتگویش را بارگذاری می‌کند.

ادامهٔ مخصوص-هر-ترمینال

یک -c ساده آگاه از ترمینال است: هر نشست CLI یک فایل ردپای کوچک زیر ~/.hermes/terminal-sessions/ می‌گذارد که به ترمینالی که در آن اجرا شده کلید خورده (دستگاه tty، پنل tmux، پنجرهٔ kitty، پنل wezterm، پنل Zellij، نشست ویندوز ترمینال و…). وقتی دوباره در همان ترمینال hermes -c بزنید، هرمس نشستِ خودِ آن ترمینال را ازسر می‌گیرد — پس دو پنل کنار هم هر کدام گفتگوی خودشان را ادامه می‌دهند به‌جای اینکه هر دو سرِ جدیدترینِ سراسری بروند. اگر ردپایی برای آن ترمینال نباشد (اولین استفاده، نشست حذف‌شده یا ردپای کهنه‌تر از ۳۰ روز)، -c به رفتار جدیدترین-نشست برمی‌گردد. -c "name" و --resume متأثر نمی‌شوند. با session.terminal_continue: false در config.yaml غیرفعالش کنید.

ازسرگیری با نام

اگر به نشست عنوان داده‌اید (به «نام‌گذاری نشست» پایین مراجعه کنید)، می‌توانید با نام ازسرش بگیرید:

bash
# ازسرگیری نشستی با نام
hermes -c "my project"

# اگر واریانت‌های تبار وجود دارد (my project، my project #2، my project #3)،
# به‌طور خودکار جدیدترین را ازسر می‌گیرد
hermes -c "my project"   # → "my project #3" را ازسر می‌گیرد

ازسرگیری نشست مشخص

bash
# ازسرگیری نشستی مشخص با شناسه
hermes --resume 20250305_091523_a1b2c3d4
hermes -r 20250305_091523_a1b2c3d4

# ازسرگیری با عنوان
hermes --resume "refactoring auth"

# ازسرگیری جدیدترین نشست — همان جستجوی -c
hermes --resume latest

# یا با زیرفرمان chat
hermes chat --resume 20250305_091523_a1b2c3d4

شناسهٔ نشست‌ها هنگام خروج از نشست CLI نمایش داده می‌شوند و با hermes sessions list پیدا می‌شوند.

ℹ️ توجه

latest یک کلیدواژهٔ رزروشده برای --resume است. نشستی که واقعاً عنوانش «latest» باشد همچنان با شناسه‌اش یا از طریق -c latest (تطبیق عنوان) در دسترس است.

ازسرگیری در پوشهٔ مشخص

--in <dir> را بدهید تا پیش از شروع یا ازسرگیری وارد یک پوشه شوید. همراه با --resume latest (یا -c)، جدیدترین نشستِ متعلق به ورک‌اسپیس آن پوشه انتخاب می‌شود — نه لازم است اول cd بزنید نه شناسه‌ها را به خاطر بسپارید:

bash
# ازسرگیری جدیدترین نشستی که به ./my-project تعلق دارد
hermes --resume latest --in ./my-project

# با TUI هم کار می‌کند
hermes --tui --resume latest --in ./my-project

--in همچنین نشست را به آن پوشه پین می‌کند: پوشهٔ کاریِ ثبت‌شدهٔ نشستِ ازسرگرفته بازگردانده نمی‌شود (مثل اینکه --no-restore-cwd داده باشید).

ازسرگیری پوشهٔ کاری را بازمی‌گرداند

ازسرگیری یک نشست CLI همچنین به پوشهٔ کاریِ ثبت‌شدهٔ نشست (ریشهٔ مخزن git یا پوشهٔ پروژه‌اش) cd می‌کند، تا گفتگو در همان ورک‌اسپیسی که متعلق بود ادامه یابد. اگر ترجیح می‌دهید همان‌جا که هستید بمانید، --no-restore-cwd بدهید:

bash
hermes --resume 20250305_091523_a1b2c3 --no-restore-cwd

یک خط ↪ restored workspace dir: … تغییر را تأیید می‌کند. شکست بازگردانی هرگز خودِ ازسرگیری را نمی‌شکند.

فیلتر نشست‌ها بر اساس ورک‌اسپیس

hermes sessions list گزینهٔ --workspace <needle> را می‌پذیرد تا فقط نشست‌هایی را نشان دهد که کلید ورک‌اسپیس‌شان (ریشهٔ مخزن git، وگرنه cwd) مطابقت دارد — با زیررشتهٔ مسیر یا نام پایهٔ دقیق پوشه:

bash
hermes sessions list --workspace my-project
hermes sessions list --workspace ~/code/hermes-agent

خلاصهٔ گفتگو هنگام ازسرگیری

وقتی نشستی را ازسر می‌گیرید، هرمس پیش از پرامپت ورودی، خلاصهٔ فشرده‌ای از گفتگوی قبلی را در پنلی استایل‌دار نمایش می‌دهد:

این خلاصه:

  • پیام‌های کاربر (با ● طلایی) و پاسخ‌های دستیار (با ◆ سبز) را نشان می‌دهد
  • پیام‌های بلند را می‌بُرَد (۳۰۰ کاراکتر برای کاربر، ۲۰۰ کاراکتر / ۳ خط برای دستیار)
  • فراخوانی‌های ابزار را جمع می‌کند به یک شمارش همراه نام ابزارها (مثلاً [3 tool calls: terminal, web_search])
  • پیام‌های سیستمی، نتایج ابزار و استدلال داخلی را مخفی می‌کند
  • روی ۱۰ تبادل آخر سقف می‌زند با نشانگر «... N earlier messages ...»
  • از استایل کم‌رنگ استفاده می‌کند تا از گفتگوی فعال متمایز باشد

برای غیرفعال‌کردن خلاصه و نگه‌داشتن رفتار یک‌خطیِ مینیمال، در ~/.hermes/config.yaml تنظیم کنید:

yaml
display:
  resume_display: minimal   # پیش‌فرض: full
💡 نکته

شناسهٔ نشست‌ها از قالب YYYYMMDD_HHMMSS_<hex> پیروی می‌کند — نشست‌های CLI/TUI پسوند هگز ۶ کاراکتری دارند (مثلاً 20250305_091523_a1b2c3) و نشست‌های گیت‌وی پسوند ۸ کاراکتری (مثلاً 20250305_091523_a1b2c3d4). می‌توانید با شناسه (کامل یا پیشوند یکتا) یا با عنوان ازسر بگیرید — هر دو با -c و -r کار می‌کنند.

۳ تحویل بین‌پلتفرمی (Handoff)

از یک نشست CLI با /handoff <platform> استفاده کنید تا گفتگوی زنده را به کانال خانگیِ یک پلتفرم پیام‌رسانی منتقل کنید. ایجنت دقیقاً از همان‌جایی که CLI رها کرد ادامه می‌دهد — همان شناسهٔ نشست، رونوشت کاملِ آگاه-از-نقش، با همهٔ فراخوانی‌های ابزار.

داخل یک نشست CLI
/handoff telegram

چه اتفاقی می‌افتد:

  1. CLI اعتبارسنجی می‌کند که <platform> فعال است و کانال خانگی دارد (یک بار /sethome را از چت مقصد اجرا کنید تا پیکربندی شود).
  2. CLI نشست را در انتظار علامت می‌زند و گیت‌وی را به‌صورت بلاک poll می‌کند. اگر ایجنت وسط نوبت باشد امتناع می‌کند — اول صبر کنید پاسخ فعلی تمام شود.
  3. پایان‌بخشِ گیت‌وی تحویل را برمی‌دارد و از آداپتور مقصد یک رشتهٔ تازه می‌خواهد:
    • تلگرام — یک تاپیک فروم جدید باز می‌کند (تاپیک‌های DM اگر حالت Topics از Bot API نسخهٔ 9.4+ در چت فعال باشد، یا تاپیک سوپرگروه فروم).
    • دیسکورد — یک رشته با آرشیو-خودکارِ ۱۴۴۰ دقیقه‌ای زیر کانال متنی خانگی می‌سازد.
    • اسلک — یک پیام بذر می‌فرستد و از ts آن به‌عنوان لنگر رشته استفاده می‌کند.
    • واتساپ / سیگنال / ماتریکس / پیامک — رشتهٔ بومی ندارند، مستقیم به کانال خانگی برمی‌گردند.
  4. گیت‌وی کلید مقصد را به شناسهٔ نشست CLI موجود شما دوباره متصل می‌کند، سپس یک نوبتِ کاربرِ ساختگی می‌سازد که از ایجنت تأیید و خلاصه می‌خواهد. پاسخ در رشتهٔ جدید فرود می‌آید.
  5. وقتی گیت‌وی موفقیت را تأیید کرد، CLI یک راهنمای /resume چاپ کرده و تمیز خارج می‌شود:
    خروجی
    ↻ Handoff complete. The session is now active on telegram.
  Resume it on this CLI later with: /resume my-session-title
  6. از آن نقطه، گفتگو روی پلتفرم زندگی می‌کند. در رشتهٔ جدید پاسخ بدهید — هر کسی که در آن کانال مجاز باشد همان نشست را به اشتراک می‌گذارد، و هر پیام واقعیِ بعدیِ کاربر در رشته، یکپارچه ملحق می‌شود چون نشست‌های رشته بدون user_id کلید می‌خورند.

بازگشت به CLI: وقتی خواستید به دسکتاپ برگردید، فقط /resume <title> را اجرا کنید (یا hermes -r "<title>" از شل) و از همان‌جایی که پلتفرم رها کرد ادامه دهید.

حالت‌های شکست:

  • کانال خانگی پیکربندی نشده ← CLI با راهنمای /sethome امتناع می‌کند.
  • پلتفرم فعال نیست / گیت‌وی در حال اجرا نیست ← CLI در ۶۰ ثانیه تایم‌اوت می‌شود با پیامی روشن و نشست CLI شما دست‌نخورده می‌ماند.
  • ساخت رشته شکست می‌خورد (مجوزها، حالت تاپیک خاموش) ← مستقیم به کانال خانگی برمی‌گردد و همچنان کامل می‌شود؛ ایزوله‌سازی رشته نیست ولی خود تحویل کار می‌کند.
  • adapter.send شکست می‌خورد (محدودیت نرخ، خطای گذرا API) ← تحویل ناموفق با ذکر علت علامت می‌خورد؛ سطر پاک می‌شود تا دوباره امتحان کنید.

محدودیتی که ارزش دانستن دارد: برای پلتفرم‌های بدون-رشته با کانال‌های خانگیِ گروهیِ چندکاربره، نوبت ساختگی به‌صورت نشست سبک-DM کلید می‌خورد. این برای کانال‌های خانگیِ خود-DM (راه‌اندازی معمول) کار می‌کند ولی برای گفتگوهای گروهیِ واقعاً مشترک ایده‌آل نیست. رشته‌سازی تلگرام/دیسکورد/اسلک را پوشش می‌دهد — که اتفاقاً حالت رایج است — پس اغلب راه‌اندازی‌ها هرگز به این نمی‌خورند.

۴ نام‌گذاری نشست

به نشست‌ها عنوان‌های انسانی‌خوان بدهید تا راحت پیدایشان کنید و ازسر بگیرید.

عنوان‌های خودکار

هرمس پس از اولین تبادل، به‌طور خودکار برای هر نشست یک عنوان توصیفیِ کوتاه (۳ تا ۷ واژه) تولید می‌کند. این در یک نخِ پس‌زمینه با یک مدل کمکیِ سریع اجرا می‌شود، پس هیچ تأخیری اضافه نمی‌کند. عنوان‌های خودکار را هنگام مرور نشست‌ها با hermes sessions list یا hermes sessions browse می‌بینید.

عنوان‌گذاری خودکار فقط یک بار برای هر نشست اجرا می‌شود و اگر خودتان از قبل عنوان گذاشته باشید رد می‌شود.

تنظیم دستی عنوان

درون هر نشست چت (CLI یا گیت‌وی) از فرمان اسلش /title استفاده کنید:

فرمان در چت
/title my research project

عنوان بلافاصله اعمال می‌شود. اگر نشست هنوز در دیتابیس ساخته نشده باشد (مثلاً /title را پیش از اولین پیام اجرا کنید)، در صف می‌رود و با شروع نشست اعمال می‌شود.

همچنین می‌توانید نشست‌های موجود را از خط فرمان تغییر نام دهید:

bash
hermes sessions rename 20250305_091523_a1b2c3d4 "refactoring auth module"

قواعد عنوان

  • یکتا — هیچ دو نشستی نمی‌توانند عنوان یکسان داشته باشند
  • حداکثر ۱۰۰ کاراکتر — خروجی فهرست تمیز می‌ماند
  • پاک‌سازی‌شده — کاراکترهای کنترلی، کاراکترهای عرض-صفر و overrideهای RTL خودکار حذف می‌شوند
  • یونیکد عادی مشکلی ندارد — ایموجی، CJK و کاراکترهای لهجه‌دار همه کار می‌کنند

تبارِ خودکار هنگام فشرده‌سازی

وقتی زمینهٔ نشستی فشرده می‌شود (دستی با /compress یا خودکار)، هرمس یک نشست ادامهٔ جدید می‌سازد. اگر نشست اصلی عنوان داشت، نشست جدید به‌طور خودکار عنوانِ شماره‌دار می‌گیرد:

نمونه
"my project" → "my project #2" → "my project #3"

وقتی با نام ازسر می‌گیرید (hermes -c "my project")، به‌طور خودکار جدیدترین نشستِ تبار را انتخاب می‌کند.

/title در پلتفرم‌های پیام‌رسانی

فرمان /title در همهٔ پلتفرم‌های گیت‌وی کار می‌کند (تلگرام، دیسکورد، اسلک، واتساپ):

  • /title My Research — تنظیم عنوان نشست
  • /title — نمایش عنوان فعلی

۵ فرمان‌های مدیریت نشست

هرمس مجموعهٔ کامل فرمان‌های مدیریت نشست را از طریق hermes sessions ارائه می‌کند:

فهرست نشست‌ها

bash
# فهرست نشست‌های اخیر (پیش‌فرض: ۲۰ تای آخر)
hermes sessions list

# فیلتر بر اساس پلتفرم
hermes sessions list --source telegram

# نمایش نشست‌های بیشتر
hermes sessions list --limit 50

صادرات نشست‌ها

hermes sessions export یک سطح واحد برای هر قالب صادراتی است که با --format انتخاب می‌شود:

قالبخروجیبرای چه استفاده کنید
jsonl (پیش‌فرض)یک شیء JSON به‌ازای هر نشستپشتیبان‌ها، رفت‌وبرگشت ماشینی
md / qmdیک فایل Markdown/Quarto به‌ازای هر نشست + مانیفستآرشیو خوانا، یادداشت
htmlیک صفحهٔ خودبسنده (سایدبار برای چند-نشستی)اشتراک، مرور
traceJSONL کلاد-کدHF Agent Trace Viewer و --upload

به‌علاوه --only user-prompts برای نمای فقط-پرامپت (در jsonl یا md).

همهٔ قالب‌ها همان پیچ‌های انتخابی را به اشتراک می‌گذارند: --session-id برای یک نشست، یا مجموعهٔ کامل فیلترهای prune/archive برای گروهی — ‏--older-than / --newer-than / --before / --after (مدت‌هایی مثل 5h/2d/1w، روزِ خالی، یا مهر زمانی ISO)، ‏--source، --title، --model، --provider، --cwd، --min/--max-messages، --min/--max-tokens، --min/--max-cost، --min/--max-tool-calls، --user، --chat-id، --chat-type، --branch، --end-reason. ‏--dry-run مجموعهٔ تطبیق را بدون نوشتن پیش‌نمایش می‌کند. --redact رازها (کلیدهای API، توکن‌ها، اعتبارنامه‌ها) را از محتوای صادرشده در هر قالبی پاک می‌کند — برای هر چیزی که قصد اشتراکش را دارید توصیه می‌شود. نکته: فیلترهای گروهی با نشست‌های پایان‌یافته تطبیق می‌خورند؛ export بدون فیلتر همه‌چیز را می‌ریزد، از جمله فعال‌ها.

JSONL (پیش‌فرض)

bash
# صادرات همهٔ نشست‌ها به یک فایل JSONL
hermes sessions export backup.jsonl

# صادرات نشست‌های یک پلتفرم مشخص
hermes sessions export telegram-history.jsonl --source telegram

# صادرات یک نشست
hermes sessions export session.jsonl --session-id 20250305_091523_a1b2c3d4

# پاک‌سازی کلیدها/توکن‌ها/اعتبارنامه‌ها از محتوای صادرشده
hermes sessions export backup.jsonl --redact

فایل‌های صادرشده در هر خط یک شیء JSON با فرادادهٔ کامل نشست و همهٔ پیام‌ها دارند.

HTML

--format html یک فایل HTML خودبسندهٔ واحد می‌نویسد — بدون وابستگی راهن — با حباب‌های پیام استایل‌دار، خروجی ابزارِ تاشو و (برای صادرات چند-نشستی) سایدباری برای جابه‌جایی بین نشست‌ها:

bash
# یک نشست به‌صورت صفحهٔ HTML مستقل
hermes sessions export --format html --session-id 20250305_091523_a1b2c3d4 transcript.html

# همهٔ نشست‌های تلگرام هفتهٔ اخیر در یک فایل، با پاک‌سازی رازها
hermes sessions export --format html --newer-than 1w --source telegram --redact archive.html

فقط پرامپت‌ها

--only user-prompts فقط پرامپت‌هایی را که نوشته‌اید صادر می‌کند — بدون پاسخ دستیار، خروجی ابزار یا زمینهٔ سیستمی. برای ساخت کتابخانهٔ پرامپت یا بازبینی چیزهایی که پرسیدید مفید است:

bash
# یک رکورد JSONL به‌ازای هر پرامپت (شناسهٔ نشست، اندیس، مهر زمانی، متن)
hermes sessions export prompts.jsonl --session-id 20250305_091523_a1b2c3d4 --only user-prompts

# مارک‌داون، مستقیم در stdout
hermes sessions export - --session-id 20250305_091523_a1b2c3d4 --only user-prompts --format md

با --format jsonl (پیش‌فرض) یا md کار می‌کند، همان فیلترها را برای صادرات گروهی می‌پذیرد و با --redact ترکیب می‌شود.

تریس‌ها (HF Agent Trace Viewer)

--format trace همان JSONL کلاد-کد را تولید می‌کند — شکلی که هاب هاغینگ‌فیس برای Agent Trace Viewer خودکار تشخیص می‌دهد. محلی بنویسیدش، یا --upload را اضافه کنید تا به دیتاست خصوصیِ خودتان hermes-traces پوش شود (HF_TOKEN را می‌خواند):

bash
# تریس جدیدترین نشست، در stdout
hermes sessions export --format trace

# یک نشست به فایل تریس محلی
hermes sessions export --format trace --session-id 20250305_091523_a1b2c3d4 trace.jsonl

# آپلود مستقیم به دیتاست تریس‌های خصوصی HF
hermes sessions export --format trace --session-id 20250305_091523_a1b2c3d4 --upload

صادرات تریس به‌طور پیش‌فرض پاک‌سازیِ راز دارند (برای ترک ماشین ساخته شده‌اند)؛ --no-redact پس از بازبینی دستی از آن خارج می‌شود. --upload بدون --public خصوصی است. صادرات گروهی تریس با فیلترها به‌ازای هر نشست یک <id>.trace.jsonl می‌نویسد.

Markdown / QMD

--format md یا --format qmd را وقتی بدهید که پیش از مخفی یا حذف‌کردن نشست‌های قدیمی یک آرشیو فایل‌مبنا و خوانا می‌خواهید. صادرات Markdown/QMD برای هر نشست یک فایل در یک پوشه می‌نویسد (پیش‌فرض: ~/.hermes/session-exports).

bash
# صادرات یک نشست به Markdown
hermes sessions export --format md --session-id 20250305_091523_a1b2c3d4

# صادرات یک تبار فشرده‌سازی به‌صورت یک سند منطقی واحد
hermes sessions export --format md --session-id 20250305_091523_a1b2c3d4 --lineage logical

# پیش‌نمایش نشست‌های پایان‌یافتهٔ بالای ۹۰ روز بدون نوشتن فایل
hermes sessions export --format md --older-than 90 --dry-run

# صادرات نشست‌های پایان‌یافتهٔ تلگرام بالای ۲ هفته به فایل‌های QMD
hermes sessions export --format qmd --older-than 2w --source telegram

# صادرات نشست‌های بلند Claude، با پاک‌سازی رازها
hermes sessions export --format md --model sonnet --min-messages 50 --redact

# فقط پس از راستی‌آزمایی، صادرات و حذف یک نشستِ صریحاً نام‌برده
hermes sessions export --format md --session-id 20250305_091523_a1b2c3d4 --delete-after-verified --yes

صادرات Markdown/QMD برای هر نشستِ صادرشده یک فایل .md یا .qmd به‌علاوهٔ یک manifest.jsonl با مسیر فایل، تعداد پیام، شناسه‌های تبار و SHA-256 می‌نویسد. صادرات گروهی حداقل یک فیلتر لازم دارد؛ صادرات گروهیِ خالی رد می‌شود. --delete-after-verified عمداً به --session-id محدود است و --yes می‌خواهد. چون حذف نشست والد، نشست‌های delegate/ساب‌ایجنتش را هم حذف می‌کند، این حالت قبل از حذف هر چیز، هر delegate را در فایلی جداگانه صادر و راستی‌آزمایی می‌کند. اگر مجموعهٔ delegate حین صادرات تغییر کند، حذف رد می‌شود. --redact پیش از نوشتن، رازها را از محتوای پیام و خروجی ابزار پاک می‌کند — برای هر صادراتی که قصد اشتراکش را دارید توصیه می‌شود.

حذف یک نشست

bash
# حذف نشست مشخص (با تأیید)
hermes sessions delete 20250305_091523_a1b2c3d4

# حذف بدون تأیید
hermes sessions delete 20250305_091523_a1b2c3d4 --yes

تغییر نام یک نشست

bash
# تنظیم یا تغییر عنوان نشست
hermes sessions rename 20250305_091523_a1b2c3d4 "debugging auth flow"

# عنوان‌های چندواژه‌ای در CLI گیومه نمی‌خواهند
hermes sessions rename 20250305_091523_a1b2c3d4 debugging auth flow

اگر عنوان از قبل به نشست دیگری تعلق داشته باشد، خطا نشان داده می‌شود.

پین‌کردن یک نشست

پین‌کردن یک پرچم پایدار «نگه‌دار» تنظیم می‌کند: نشست‌های پین‌شده از جاروب کهنگیِ sessions.auto_archive معاف‌اند و همیشه در فهرست‌ها ظاهر می‌شوند. همان پرچمی است که بخش Pinned سایدبار دسکتاپ استفاده می‌کند — از هر یک از دو سطح پین کنید و هر دو می‌بینندش.

bash
# پین یک یا چند نشست (پیشوندهای شناسهٔ یکتا هم کار می‌کنند)
hermes sessions pin 20250305_091523_a1b2c3d4
hermes sessions pin 20250305 20250306

# برداشتن پین
hermes sessions unpin 20250305_091523_a1b2c3d4

# فهرست نشست‌های پین‌شده
hermes sessions pinned

# خروجی ماشین‌خوان، مثلاً برای پشتیبان شبانهٔ مجموعهٔ پین‌هایتان
hermes sessions pinned --json > pinned-sessions.json

هرس نشست‌های قدیمی

bash
# حذف نشست‌های پایان‌یافتهٔ غیرفعال برای ۹۰ روز (پیش‌فرض)
hermes sessions prune

# آستانهٔ سن سفارشی — اعداد خالی یعنی روز
hermes sessions prune --older-than 30

# مدت‌ها هم کار می‌کنند: 5h، 30m، 2d، 1w
hermes sessions prune --older-than 12h

# حذف فقط یک بازهٔ زمانی مشخص (مثلاً دسته‌ای از نشست‌های تستی
# ساخته‌شده در ۵ ساعت اخیر)
hermes sessions prune --newer-than 5h

# بازهٔ صریح با مهرهای زمانی مطلق
hermes sessions prune --after "2026-07-05 09:00" --before "2026-07-05 14:30"

# هرس فقط نشست‌های یک پلتفرم مشخص (همهٔ سن‌ها — هر فیلتری
# پیش‌فرض ضمنیِ ۹۰ روز را غیرفعال می‌کند)
hermes sessions prune --source telegram
hermes sessions prune --source cron --older-than 60   # برای محدودترشدن یک پرچم زمانی اضافه کنید

# فیلترهای بیشتر — همگی با هم AND می‌شوند
hermes sessions prune --newer-than 5h --title "smoke test"   # زیررشتهٔ عنوان
hermes sessions prune --older-than 30 --max-messages 3        # نشست‌های ریز
hermes sessions prune --cwd ~/scratch --end-reason done       # بر اساس cwd / علت پایان
hermes sessions prune --model gpt-5 --older-than 1w           # بر اساس مدل (زیررشته)
hermes sessions prune --provider openrouter --older-than 60   # بر اساس ارائه‌دهندهٔ صورت‌حساب
hermes sessions prune --branch feature/old-experiment         # بر اساس شاخهٔ git
hermes sessions prune --user 12345678 --chat-type group       # بر اساس مبدأ پیام‌رسانی
hermes sessions prune --max-tokens 500 --older-than 7         # بر اساس مصرف توکن
hermes sessions prune --max-cost 0.01 --max-tool-calls 0      # اجراهای ارزانِ بدون-ابزار

# پیش‌نمایش آنچه حذف می‌شد، بدون حذف هیچ‌چیز
hermes sessions prune --newer-than 5h --dry-run

# رد کردن تأیید
hermes sessions prune --older-than 30 --yes

مقادیر زمانی (--older-than، --newer-than، --before، --after) یک مدت (5h، 30m، 2d، 1w)، عددِ خالیِ روز، یا مهر زمانی ISO‏ (2026-07-05، 2026-07-05 14:30) می‌پذیرند. --older-than/--before سقف و --newer-than/--after کف را تنظیم می‌کنند. جفتِ --older-than/--newer-than از آخرین فعالیتِ پیام استفاده می‌کند (برای نشست‌های خالی به شروع نشست برمی‌گردد)؛ --before/--after صریحاً زمان شروع نشست را می‌گیرد. هر جفت را برای یک بازه ترکیب کنید.

فیلترهای ویژگی: --source (پلتفرم، دقیق)، --title / --model / --branch (زیررشتهٔ بدون حساسیت به بزرگی/کوچکی)، --provider (ارائه‌دهندهٔ صورت‌حساب، دقیق)، --end-reason، --user، --chat-id، --chat-type (دقیق)، --cwd (پیشوند مسیر)، به‌علاوهٔ کران‌های عددی --min/--max-messages، --min/--max-tokens (ورودی+خروجی)، --min/--max-cost (دلار، واقعی با بازگشت به تخمینی) و --min/--max-tool-calls. استفاده از هر فیلتری پیش‌فرض ضمنیِ ۹۰ روز را غیرفعال می‌کند، پس hermes sessions prune --source cron یا --model gpt-4o با همهٔ سن‌ها تطبیق می‌خورد — برای محدودکردنش پرچم زمانی اضافه کنید. فقط hermes sessions prune کاملاً خالی، برش ۹۰ روزه را نگه می‌دارد. هر اجرای بدون --yes پیش از درخواست تأیید، شمار تطبیق‌ها به‌علاوهٔ قدیمی‌ترین و جدیدترین نشستِ مطابق را نشان می‌دهد.

نشست‌های آرشیوشده به‌طور پیش‌فرض رد می‌شوند؛ برای حذف آن‌ها هم --include-archived بدهید.

ℹ️ توجه

هرس فقط نشست‌های پایان‌یافته را حذف می‌کند (نشست‌هایی که صریحاً پایان یافته یا خودکار ریست شده‌اند). نشست‌های فعال هرگز هرس نمی‌شوند.

آرشیو گروهی نشست‌ها

اگر می‌خواهید نشست‌ها از فهرست‌هایتان بیرون بروند بدون حذف هیچ‌چیز، hermes sessions archive همان فیلترهای prune را می‌گیرد اما به‌جای حذف، نشست‌های مطابق را نرم‌مخفی می‌کند (همان پرچم آرشیوی که آرشیوِ تک‌نشستی از UI دسکتاپ/داشبورد می‌گذارد — پیام‌ها و جستجو سالم می‌مانند):

bash
# آرشیو همه‌چیز از ۵ ساعت اخیر (مثلاً ۷۵ نشست اسموک-تست CI)
hermes sessions archive --newer-than 5h

# آرشیو بر اساس زیررشتهٔ عنوان، اول پیش‌نمایش
hermes sessions archive --title "dry run" --dry-run
hermes sessions archive --title "dry run" --yes

حداقل یک فیلتر لازم است — hermes sessions archive خالی از آرشیوکردن کل تاریخچه‌تان سر باز می‌زند. نشست‌های آرشیوشده از hermes sessions list و /resume پنهان می‌شوند اما در دیتابیس می‌مانند و از فهرست نشست‌های دسکتاپ/داشبورد قابل خروج از آرشیوند.

تعمیر نشست‌های سرگردان گیت‌وی

اگر گفتگوی گیت‌وی بعد از ری‌استارت «به عقب در زمان می‌پرد» — تاپیکی چندروزه را طوری ازسر بگیرد که انگار پیام‌های اخیر هرگز اتفاق نیفتاده‌اند — ممکن است گفتگوی زنده در سطری نشسته باشد که هویت مسیریابی‌اش را گم کرده (کلاس آسیبی که در کار تداوم نشستِ نسخهٔ v0.21 تعمیر شد؛ نسخه‌های فعلی ذاتاً جلویش را می‌گیرند و در زمان اجرا خودترمیم می‌شوند).

hermes sessions repair-routing سطرهای نشستِ دارای-پیامِ بدون هویت مسیریابی را پیدا می‌کند و هر یک را دوباره به گفتگویی که ادامه‌اش است می‌چسباند — اما فقط وقتی شواهد بی‌ابهام باشد:

bash
# فقط گزارش — هر سرگردان، فرزندخواندگی پیشنهادی و شواهد را نشان می‌دهد
hermes sessions repair-routing

# انجام فرزندخواندگی‌ها (اول گیت‌وی را متوقف کنید — گیت‌وی در حال اجرا
# مسیریابی قدیمی را در حافظه دارد و روی تعمیر بازمی‌نویسدش)
hermes sessions repair-routing --apply

# باز/بستن پنجرهٔ پیوستگی (پیش‌فرض ۹۰۰ ثانیه)
hermes sessions repair-routing --max-gap-seconds 300

قواعد شواهد:

  • تبار — parent_session_id سرگردان به سطری کلیددار از همان پلتفرم اشاره می‌کند (یک واقعیتِ ثبت‌شده؛ هیچ پنجرهٔ زمانی اعمال نمی‌شود)
  • پیوستگی — دقیقاً یک سطر کلیددار از همان پلتفرم در پنجرهٔ شروعِ سرگردان ساکت شده

هر چیز مبهمی (دو پیشین‌نمای کاندید، دو سرگردان مدعیِ همان پیشین‌نما) با ذکر دلیل گزارش و دست‌نخورده می‌ماند — یک فرزندخواندگیِ اشتباه، یک گفتگو را به چت دیگری می‌پیوندد. سطر منسوخ‌شده زیر superseded_by_repair بازنشسته می‌شود تا بازیابیِ ری‌استارت هرگز زنده‌اش نکند.

تعمیر عمداً خودکار نیست: اگر چت از آن موقع تاریخچهٔ دومی ساخته، انتخاب اینکه ادامهٔ کدام رشته است با شماست. گفتگوی سرگردان به‌هرحال از طریق /resume و جستجوی نشست خوانا می‌ماند — مسیریابی تنها چیزی است که تعمیر عوض می‌کند. اول پشتیبان بگیرید (cp ~/.hermes/state.db ~/.hermes/state.db.bak).

۶ درون‌ریزی نشست‌ها از Claude Code و Codex CLI

گفتگویی را در CLI ایجنت دیگری شروع کرده‌اید؟ می‌توانید به هرمس بیاوریدش و همین‌جا ادامه دهید. هرمس لاگ‌های نشست Claude Code‏ (~/.claude/projects/) و رول‌اوت‌های Codex CLI‏ (~/.codex/sessions/) را می‌خواند — فایل‌های خارجی فقط خوانده می‌شوند، هرگز تغییر نمی‌کنند.

bash
# انتخابگر تعاملی روی هر دو ابزار، جدیدترین اول
hermes sessions import

# محدود به یک ابزار، یا اشاره به فایل مشخص
hermes sessions import --from claude
hermes sessions import --from codex ~/.codex/sessions/2026/08/15/rollout-....jsonl

# درون‌ریزی و ازسرگیری در یک گام
hermes --resume @claude
hermes --resume @codex

hermes sessions import نشست هرمسی تازه‌ای با عنوان Imported from Claude Code: <اولین پیام کاربر> (یا Codex CLI) می‌سازد و شناسه به‌همراه فرمانِ آماده‌پیست hermes --resume <id> را چاپ می‌کند. --resume @claude / --resume @codex همان انتخابگر را نشان می‌دهند و شما را مستقیم داخل گفتگوی درون‌ریزی‌شده می‌گذارند.

چه چیزی منتقل می‌شود: گفتگوی مرتبِ کاربر/دستیار، با فعالیت ابزار فشرده‌شده به یادداشت‌های کوتاه [ran tool: …] داخل نوبت‌های دستیار. پرامپت‌های سیستمی، زمینهٔ تزریق‌شده، رده‌های استدلال و خروجی خام ابزار جا می‌مانند — درون‌ریزی یک رونوشت تمیز است، نه بازپخشِ بایت‌به‌بایت.

۷ ابزار جستجوی نشست

ایجنت یک ابزار داخلی session_search دارد که با موتور FTS5 مربوط به SQLite جستجوی تمام‌متن روی همهٔ گفتگوهای گذشته انجام می‌دهد — و به ایجنت اجازه می‌دهد در هر نشستی که پیدا می‌کند اسکرول کند. هیچ فراخوانی LLM نمی‌کند و به‌جای تولید خلاصه، نماهایی از پیام‌های واقعیِ دیتابیس را برمی‌گرداند.

چهار شکل فراخوانی

ابزار از اینکه کدام آرگومان‌ها را تنظیم کرده‌اید می‌فهمد چه می‌خواهید. پارامتر mode وجود ندارد.

۱. کشف — query بدهید:

python
session_search(query="auth refactor", limit=3)

FTS5 را اجرا می‌کند، نتایج را بر اساس تبار نشست بی‌تکرار می‌کند و N نشست برتر را برمی‌گرداند. کشف به‌طور پیش‌فرض از جزئیات تطبیقی استفاده می‌کند: نتیجهٔ با بالاترین رتبه پنجرهٔ زمینهٔ کامل و bookendهایش را می‌آورد، در حالی که نتایج پایین‌تر فشرده می‌مانند. برای سیراب‌کردن کامل هر نتیجه detail="full" بدهید.

هر نتیجه این‌ها را دارد:

  • session_id، title، when، source
  • snippet — گزیدهٔ تطبیق با هایلایت FTS5
  • detail — full یا compact
  • bookend_start / bookend_end — اول/آخر ۳ پیام کاربر+دستیار برای نتایج کامل؛ فهرست‌های خالی برای نتایج فشرده
  • messages — ‏±۵ پیام حول تطبیق FTS5 برای نتایج کامل؛ فقط پیامِ لنگرِ علامت‌خورده برای نتایج فشرده
  • match_message_id، messages_before، messages_after

نتیجهٔ برتر بلافاصله «هدف ← تطبیق ← حل» را بازسازی می‌کند. اگر نتیجهٔ فشردهٔ دیگری امیدوارکننده‌تر بود، از شناسه‌های نشست و پیامش با شکل اسکرول استفاده کنید. زمان معمول روی یک دیتابیس نشست واقعی: ده‌ها میلی‌ثانیه.

۲. اسکرول — session_id + around_message_id بدهید:

python
session_search(session_id="20260510_174648_805cc2", around_message_id=590803, window=10)

پنجره‌ای از پیام‌های ±window حول لنگر برمی‌گرداند. بدون FTS5، بدون bookend — فقط همان تکه. بعد از فراخوانی کشف استفاده کنید وقتی زمینهٔ بیشتری از پنجرهٔ پیش‌فرض ±۵ می‌خواهید.

  • اسکرول به جلو: messages[-1].id را به‌عنوان around_message_id پس بدهید
  • اسکرول به عقب: messages[0].id را به‌عنوان around_message_id پس بدهید
  • پیام مرزی در هر دو پنجره به‌عنوان نشانگر جهت‌یابی ظاهر می‌شود
  • وقتی messages_before یا messages_after کمتر از window است، در شروع یا پایان نشست هستید

زمان معمول: ۱ تا ۲ میلی‌ثانیه به‌ازای هر فراخوانی اسکرول.

۳. خواندن — session_id بدون لنگر بدهید:

python
session_search(session_id="20260510_174648_805cc2")

کل نشست را برمی‌گرداند، یا برای نشست‌های بزرگ نمای کراندارِ سر/دُم. این شکل برای حل لینک @session:<profile>/<id> هم استفاده می‌شود.

۴. مرور — بدون آرگومان:

python
session_search()

نشست‌های اخیر را زمان‌گذر برمی‌گرداند (عنوان‌ها، پیش‌نمایش‌ها، مهرهای زمانی). وقتی کاربر بدون نام‌بردن موضوعی می‌پرسد «روی چه کار می‌کردم» مفید است.

نگارش کوئری FTS5

حالت کلیدواژه از نگارش استاندارد کوئری FTS5 پشتیبانی می‌کند:

  • کلیدواژه‌های ساده: docker deployment (پیش‌فرض FTS5 همان AND است)
  • عبارت: "exact phrase"
  • بولی: docker OR kubernetes، python NOT java
  • پیشوند: deploy*

پارامترهای اختیاری

  • sort — newest یا oldest، روی رتبه‌بندی FTS5. برای ترتیبِ فقط-ارتباطی (پیش‌فرض؛ مناسب یادآوری اکتشافی) حذفش کنید. برای سؤال‌های «X را کجا رها کردیم» از newest و برای «X چطور شروع شد» از oldest استفاده کنید.
  • detail — adaptive (پیش‌فرض) فقط نتیجهٔ کشفِ برتر را کامل سیراب می‌کند؛ full هر نتیجهٔ کشف را.
  • role_filter — نقش‌های جداشده با ویرگول برای شمول. کشف به‌طور پیش‌فرض user,assistant است (خروجی ابزار معمولاً نویز است). برای شمول خروجی ابزار user,assistant,tool بدهید (دیباگ رفتار ابزار) یا برای جستجوی فقط خروجی ابزار tool.

کِی استفاده می‌شود

به ایجنت گفته شده که جستجوی نشست را خودکار به‌کار بگیرد:

«وقتی کاربر به چیزی از گفتگوی گذشته اشاره می‌کند یا مشکوکید زمینهٔ قبلی مرتبطی وجود دارد، پیش از اینکه از او بخواهید تکرار کند، با session_search یادش بیاورید.»

تریگرهای معمول: «این را قبلاً انجام دادیم»، «یادت هست وقتی»، «بار قبل»، «همان‌طور که گفتم»، یا هر ارجاعی به پروژه/شخص/مفهومی که در پنجرهٔ فعلی نیست.

۸ پیگیری نشست به‌ازای-پلتفرم

نشست‌های گیت‌وی

روی پلتفرم‌های پیام‌رسانی، نشست‌ها با کلید قطعیِ ساخته‌شده از مبدأ پیام کلید می‌خورند:

نوع چتقالب کلید پیش‌فرضرفتار
DM تلگرامagent:main:telegram:dm:<chat_id>یک نشست به‌ازای هر چت DM
DM دیسکوردagent:main:discord:dm:<chat_id>یک نشست به‌ازای هر چت DM

وقتی هرمس نتواند شناسهٔ شرکت‌کننده‌ای برای چت مشترک بگیرد، به یک نشست مشترکِ واحد برای آن اتاق برمی‌گردد.

نشست‌های گروهی مشترک در برابر ایزوله

به‌طور پیش‌فرض هرمس از group_sessions_per_user: true در config.yaml استفاده می‌کند. یعنی:

  • آلیس و باب می‌توانند هر دو در همان کانال دیسکورد با هرمس حرف بزنند بدون اشتراک تاریخچهٔ رونوشت
  • کارِ طولانیِ پرابزارِ یک کاربر، پنجرهٔ زمینهٔ کاربر دیگر را آلوده نمی‌کند
  • مدیریت وقفه هم به‌ازای-کاربر می‌ماند چون کلید ایجنت-در-حال-اجرا با کلید نشست ایزوله تطبیق می‌کند

اگر به‌جایش یک «مغز اتاقِ» مشترک می‌خواهید، تنظیم کنید:

yaml
group_sessions_per_user: false

این گروه‌ها/کانال‌ها را به یک نشست مشترکِ واحد به‌ازای اتاق برمی‌گرداند که زمینهٔ گفتگوی مشترک را حفظ می‌کند ولی هزینهٔ توکن، وضعیت وقفه و رشد زمینه را هم مشترک می‌کند.

سیاست‌های ریست نشست

به‌طور پیش‌فرض نشست‌های گیت‌وی هرگز خودکار ریست نمی‌شوند‏ (mode: none). می‌توانید با بخش session_reset در config.yaml به ریست خودکار بپیوندید:

  • none — هرگز ریست خودکار نشود (پیش‌فرض؛ زمینه با /reset و فشرده‌سازی مدیریت می‌شود)
  • idle — ریست پس از N دقیقه بی‌فعالیتی
  • daily — ریست در ساعت مشخصی هر روز
  • both — ریست با هرکدام زودتر بیفتد (idle یا daily)

پیش از ریست خودکارِ نشست، به ایجنت یک نوبت داده می‌شود تا خاطرات یا مهارت‌های مهم گفتگو را ذخیره کند.

نشست‌های دارای پروسه‌های پس‌زمینهٔ فعال صرف‌نظر از سیاست، هرگز خودکار ریست نمی‌شوند.

تداوم پس از کرش و ری‌استارت

یک چت گیت‌وی طراحی شده که یک نشست پیوسته باشد — که با رشدش مکرراً فشرده می‌شود — تا وقتی صریحاً /new (یا /reset) بزنید. این در سراسر کرش‌ها، ری‌استارت‌ها و به‌روزرسانی‌های گیت‌وی برقرار است:

  • هویت نشست (کلید مسیریابی، چت، مبدأ) هنگام ساخته‌شدن سطر نشست اتمی نوشته می‌شود، روی همهٔ مسیرهای ساخت (/new، اولین پیام، فرزندان /branch). اگر آن نوشتن شکست بخورد، نوسازیِ مسیریابیِ همان نوبتِ بعدی سطر را خودکار تعمیر می‌کند.
  • پس از ری‌استارت، گیت‌وی هر چت را به نشستی با جدیدترین فعالیتِ واقعی دوباره حل می‌کند — یک سطر قدیمی و کهنه هرگز نمی‌تواند بر گفتگویی که واقعاً داشتید غلبه کند.
  • بازیابی به مرزهای /new احترام می‌گذارد: اگر جدیدترین رویداد یک چت، ریست عمدی باشد، بازیابی از نو شروع می‌کند به‌جای اینکه از پشت ریست گذشته و نشست قدیمی‌تری را زنده کند. نشست‌های بازیابی‌شده زمان بیکاریِ واقعی‌شان را هم نگه می‌دارند، تا سیاست اختیاری idle/daily به‌درستی رویشان اعمال شود به‌جای اینکه هر نشست بازیابی‌شده نو به‌نو تلقی شود.

⚠️ sessions.json فهرست نشست‌ها نیست

اندیس مسیریابی گیت‌وی در جدول gateway_routing داخل state.db زندگی می‌کند؛ ‏~/.hermes/sessions/sessions.json یک آینهٔ قدیمی از آن است که برای سازگاری به عقب نگه داشته شده (با gateway.write_sessions_json: false غیرفعالش کنید). کلیدهای نشست پیام‌رسانی‏ (agent:main:<platform>:...) را به شناسه‌های نشست فعال نگاشت می‌کند. فقط مدخل‌های گیت‌وی/پیام‌رسانی دارد، پس اگر پلتفرم پیام‌رسانی اجرا کنید فقط همان‌ها را می‌بینید (مثلاً agent:main:whatsapp:dm:...).

این انتظارشده است و به‌هیچ‌وجه به معنی گم‌شدن نشست‌های CLI شما نیست. hermes sessions list، ‏/sessions و داشبورد همگی state.db را می‌خوانند که هر نشستی را دارد (CLI، TUI و گیت‌وی). اسنپ‌شات‌های /save زیر ~/.hermes/sessions/saved/*.json صادرات‌های راحتی‌اند، نه اندیس.

اگر نشست‌های CLI واقعاً در hermes sessions list ظاهر نمی‌شوند، علتش این است که state.db آن‌ها را دریافت نکرده — hermes sessions repair را اجرا کنید و هشدار ⚠ Session store unavailable را هنگام راه‌اندازی CLI زیر نظر بگیرید که یعنی ماندگاری SQLite برای آن اجرا شکست خورده.

ℹ️ رونوشت‌های JSONL قدیمی

نشست‌هایی که پیش از رسمی‌شدن state.db ساخته شده‌اند ممکن است فایل‌های *.jsonl باقی‌مانده در ~/.hermes/sessions/ داشته باشند. دیگر توسط هرمس نوشته یا خوانده نمی‌شوند. پس از تأیید وجود نشست متناظر در state.db، حذفشان امن است.

طرح‌وارهٔ دیتابیس

جداول کلیدی در state.db:

  • sessions — فرادادهٔ نشست (شناسه، مبدأ، user_id، مدل، عنوان، مهرهای زمانی، شمارش توکن). عنوان‌ها اندیس یکتا دارند (عنوان NULL مجاز است، فقط غیرNULLها باید یکتا باشند).
  • messages — تاریخچهٔ کامل پیام‌ها (نقش، محتوا، tool_calls، نام ابزار، شمارش توکن)
  • messages_fts — جدول مجازی FTS5 برای جستجوی تمام‌متن روی محتوای پیام

۱۰ انقضا و پاک‌سازی نشست‌ها

پاک‌سازی خودکار

  • نشست‌های گیت‌وی بر اساس سیاست ریستِ پیکربندی‌شده، خودکار ریست می‌شوند
  • پیش از ریست، ایجنت خاطرات و مهارت‌های نشستِ در حال انقضا را ذخیره می‌کند
  • هرس خودکارِ اختیاری: وقتی sessions.auto_prune برابر true باشد، نشست‌های پایان‌یافتهٔ غیرفعال برای sessions.retention_days (پیش‌فرض ۹۰) هنگام راه‌اندازی CLI/گیت‌وی هرس می‌شوند
  • پس از هرسی که واقعاً سطر حذف کرد، وقتی حداقل sessions.min_vacuum_interval_days (پیش‌فرض ۳۰) از آخرین VACUUM موفق گذشته باشد، state.db برای بازیابی فضا VACUUM می‌شود (‏SQLite با DELETE ساده فایل را کوچک نمی‌کند)
  • هرس حداکثر یک بار در هر sessions.min_interval_hours (پیش‌فرض ۲۴) اجرا می‌شود؛ مهر زمانی آخرین اجرا داخل خود state.db پیگیری می‌شود تا بین همهٔ پروسه‌های هرمس در همان HERMES_HOME مشترک باشد

پیش‌فرض خاموش است — تاریخچهٔ نشست برای یادآوریِ session_search ارزشمند است و حذف خاموشش می‌تواند کاربران را غافلگیر کند. در ~/.hermes/config.yaml فعالش کنید:

yaml
sessions:
  auto_prune: true          # فعال‌سازی — پیش‌فرض false
  retention_days: 90        # نشست‌های پایان‌یافته در این بازه فعال نگه داشته می‌شوند
  vacuum_after_prune: true  # بازیابی فضا پس از جاروب هرس
  min_vacuum_interval_days: 30 # دیتابیس را پرتکرارتر از این بازنویسی نکن
  min_interval_hours: 24    # جاروب را پرتکرارتر از این دوباره اجرا نکن

نشست‌های فعال صرف‌نظر از سن، هرگز خودکار هرس نمی‌شوند. سنِ نشست‌های پایان‌یافته از آخرین پیامشان حساب می‌شود، پس گفتگوی طولانی‌عمرِ اخیراً استفاده‌شده، صرفاً چون قبل از بازهٔ نگهداشت شروع شده حذف نمی‌شود.

پاک‌سازی دستی

bash
# هرس نشست‌های بالای ۹۰ روز
hermes sessions prune

# حذف نشست مشخص
hermes sessions delete <session_id>

# صادرات پیش از هرس (پشتیبان)
hermes sessions export backup.jsonl
hermes sessions prune --older-than 30 --yes
💡 نکته

دیتابیس آهسته رشد می‌کند (معمول: ۱۰-۱۵ مگابایت برای صدها نشست) و تاریخچهٔ نشست، یادآوریِ session_search را در گفتگوهای گذشته توانمند می‌کند، پس هرس خودکار خاموش عرضه می‌شود. اگر بار کاری سنگین گیت‌وی/کرون دارید که state.db معنادار بر کارایی اثر می‌گذارد فعالش کنید (حالت شکستِ مشاهده‌شده: state.db سی‌وهشت‌وده‌مگابایتی با ~۱۰۰۰ نشست که درج‌های FTS5 و فهرست‌بندی /resume را کُند می‌کرد). برای پاک‌سازی یک‌باره بدون روشن‌کردن جاروب خودکار از hermes sessions prune استفاده کنید.
