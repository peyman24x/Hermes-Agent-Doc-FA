ارائه‌دهندگان هوش مصنوعی ‏(AI Providers)

این صفحه راه‌اندازی ارائه‌دهندگان استنتاج ‏(inference) برای Hermes Agent را پوشش می‌دهد — از API‌های ابری مثل OpenRouter و Anthropic گرفته تا نقاط پایانی خودمیزبان مثل Ollama و vLLM و تا پیکربندی‌های پیشرفتهٔ مسیریابی و جایگزینی. برای استفاده از هرمس حداقل به یک ارائه‌دهندهٔ پیکربندی‌شده نیاز دارید.

۲ Nous Portal و مدیریت مدل

Nous Portal

Nous Portal گیت‌وی اشتراکِ یکپارچهٔ Nous Research و روش توصیه‌شدهٔ اجرای Hermes Agent است. یک ورود OAuth بیش از ۳۰۰ مدل agentic ی frontier را پوشش می‌دهد ‏(Claude، ‏GPT، ‏Gemini، ‏DeepSeek، ‏Qwen، ‏Kimi، ‏GLM، ‏MiniMax، ‏Grok و...) به‌علاوهٔ Tool Gateway ‏(جستجوی وب، تولید تصویر، TTS، اتوماسیون مرورگر) — همه صورتحساب‌شده روی اشتراک Nous شما به‌جای حساب‌های جداگانه per-ارائه‌دهنده.

hermes setup --portal     # fresh install — OAuth + provider + gateway in one command
hermes model              # existing install — pick "Nous Portal" from the list
hermes portal info        # inspect login + routing at any time

هنوز اشتراک ندارید؟ از portal.nousresearch.com/manage-subscription یکی بگیرید.

جزئیات کامل: صفحهٔ یکپارچه‌سازی Nous Portal ‏(محتوای اشتراک، کاتالوگ مدل، عیب‌یابی) و راهنمای قدم‌به‌قدم اجرای Hermes Agent با Nous Portal را ببینید.

شناسایی سرویس‌گیرنده. هر درخواست Portal از Hermes Agent برچسب client=hermes-client-v<نسخه> ‏(مثل client=hermes-client-v0.13.0) دارد که خودکار با نسخهٔ نصب‌شدهٔ شما هم‌تراز می‌شود. این برچسب روی همهٔ مسیرهای Portal فرستاده می‌شود — حلقهٔ اصلی چت، فراخوانی‌های کمکی، خلاصه‌ساز فشرده‌سازی، استخراج وب — و به تلمتری سمت Portal اجازه می‌دهد ترافیک Hermes را از سایر سرویس‌گیرنده‌ها تشخیص دهد. هیچ پیکربندی لازم نیست؛ برچسب هنگام hermes update خودکار به‌روز می‌شود.

احراز هویت JWT ‏(خودکار). هرمس برای درخواست‌های Portal ترجیحاً از توکن‌های JWT ی scoped با دامنهٔ inference:invoke استفاده می‌کند و مسیر قدیمی کلید نشستِ مات به‌عنوان جایگزین باقی است. هیچ پیکربندی لازم نیست — credential ها توسط جریان OAuth مدیریت و شفاف چرخش می‌شوند. refresh token های باطل‌شده برای جلوگیری از حلقه‌های تکرار قرنطینه می‌شوند.

یادداشت Codex
ارائه‌دهندهٔ OpenAI Codex از طریق کد دستگاه احراز هویت می‌شود ‏(باز کردن یک URL و وارد کردن کد). هرمس credential های حاصل را در مخزن احراز هویت خودش زیر ~/.hermes/auth.json ذخیره می‌کند و در صورت وجود، credential های موجود Codex CLI را از ~/.codex/auth.json وارد می‌کند. نصب Codex CLI الزامی نیست.

اگر refresh توکن با خطای پایانی شکست بخورد ‏(HTTP 4xx، ‏invalid_grant، لغو اعتبار grant و...)، هرمس آن refresh token را مرده علامت می‌زند و تکرارش را متوقف می‌کند تا سیل یکسان خطاهای احراز هویت نبینید. درخواست بعدی به‌جایش پیام re-authentication نوع‌دار نشان می‌دهد. برای شروع ورود تازهٔ کد دستگاه hermes auth add openai-codex را اجرا کنید ‏(یا hermes model ← «اشتراک ChatGPT یا Codex»)؛ قرنطینه در اولین تبادل موفق پاک می‌شود.

⚠️

حتی وقتی از Nous Portal یا Codex یا یک نقطهٔ پایانی سفارشی استفاده می‌کنید، بعضی ابزارها ‏(بینایی، خلاصه‌سازی وب، MoA) از یک مدل «کمکی» جدا استفاده می‌کنند. به‌طور پیش‌فرض ‏(auxiliary.*.provider: "auto") هرمس این کارها را به مدل اصلی چت شما مسیریابی می‌کند — همان مدلی که در hermes model برداشته‌اید. می‌توانید هر کار را جداگانه بازنویسی کنید تا به مدلی ارزان‌تر/سریع‌تر برود ‏(مثلاً Gemini Flash روی OpenRouter) — بخش مدل‌های کمکی را ببینید.

💡

‏Nous Tool Gateway
مشترکان پرداخت‌کنندهٔ Nous Portal به Tool Gateway هم دسترسی دارند — جستجوی وب، تولید تصویر، TTS و اتوماسیون مرورگر که از طریق اشتراک‌تان عبور می‌کنند. بدون کلیدهای API اضافه. در نصب تازه، hermes setup --portal یک‌جا ورودتان می‌کند، Nous را ارائه‌دهندهٔ شما می‌کند و گیت‌وی را روشن می‌کند. کاربران فعلی می‌توانند از hermes model یا per-tool از hermes tools فعالش کنند. وضعیت مسیریابی را هر وقت خواستید با hermes portal info ببینید.

دو فرمان برای مدیریت مدل

اگر می‌خواهید به ارائه‌دهنده‌ای سوئیچ کنید که هنوز راه‌اندازی‌اش نکرده‌اید ‏(مثلاً فقط OpenRouter دارید و Anthropic می‌خواهید)، به hermes model نیاز دارید نه ‎/model‎. اول از نشست خارج شوید ‏(Ctrl+C یا ‎/quit)، بعد hermes model را اجرا کنید، راه‌اندازی ارائه‌دهنده را کامل کنید و بعد نشست جدیدی باز کنید.

۳ طرح‌های اشتراک: اشتراک‌تان واقعاً چه چیزی را می‌پردازد؟

چند ارائه‌دهنده اجازه می‌دهند به‌جای کلید API با یک اشتراک مصرف‌کننده ‏(Claude Max، ‏ChatGPT، ‏SuperGrok / X Premium+ و...) وارد Hermes شوید. اینکه آن اشتراک واقعاً چه چیزی را می‌پردازد — و چه چیزی را نمی‌پردازد — برای هر ارائه‌دهنده فرق دارد و شایع‌ترین منبع سورپرایزهای صورتحساب همین است. جدول زیر نسخهٔ خلاصه است؛ جزئیات هر ارائه‌دهنده در بخش خودش آمده.

⚠️

سلول‌هایی که عبارت «فعلاً مستند نشده» دارند دقیقاً همان را می‌گویند: مستندات هرمس هنوز رفتار را مشخص نکرده. فرض نکنید — داشبورد صورتحساب ارائه‌دهندهٔ خودتان را چک کنید و این‌ها را سؤال‌باز در نظر بگیرید.

‏Anthropic. مسیر OAuth مثل Claude Code روی حسابتان Anthropic عمل می‌کند و فقط روی طرح Claude Max با اعتبارهای خریداری‌شدهٔ مصرف اضافه کار می‌کند — سهمیهٔ پایهٔ Max هرگز توسط هرمس مصرف نمی‌شود، فقط اعتبارهای اضافه/مازاد روی آن. مشترکان Claude Pro نمی‌توانند از این مسیر استفاده کنند؛ جایگزین پشتیبانی‌شده ANTHROPIC_API_KEY است که per-token روی سازمان آن کلید با قیمت استاندارد API صورتحساب می‌شود. بخش ‏Anthropic ‏(بومی) پایین را ببینید.

‏OpenAI Codex. هرمس از طریق OAuth ی کد-دستگاه ChatGPT احراز هویت می‌شود، credential ها را در ~/.hermes/auth.json ذخیره می‌کند و می‌تواند credential های موجود Codex CLI را از ~/.codex/auth.json وارد کند. اینکه کدام رتبه‌های طرح ChatGPT واجد شرایط‌اند و مصرف هرمس چطور روی محدودیت‌های Codex طرح‌تان حساب می‌شود فعلاً مستند نشده — یادداشت Codex در بخش Nous Portal فقط رفتار احراز هویت و refresh توکن را پوشش می‌دهد.

‏xAI ‏(SuperGrok / X Premium+). OAuth مرورگری هم با اشتراک فعال SuperGrok کار می‌کند هم با اشتراک X Premium+ روی حساب X ی متصل، و همین bearer token توسط ابزارهای مستقیم-به-xAI هم دوباره استفاده می‌شود ‏(TTS، تولید تصویر، تولید ویدیو، پیاده‌سازی صدا، جستجوی X). اگر استنتاج بعد از ورود موفق HTTP 403 برگرداند، این محدودیت رتبه/صلاحیت از سمت xAI است نه توکن کهنه — راه‌حل، سوئیچ به XAI_API_KEY است. بخش xAI ‏(Grok) پایین و راهنمای xAI Grok OAuth را ببینید.

‏Google Gemini. فعلاً هیچ راهی برای ورود به هرمس با اشتراک مصرف‌کنندهٔ Gemini وجود ندارد — ارائه‌دهندهٔ gemini کلید API می‌گیرد و Google Vertex AI هم به پروژهٔ GCP تان صورتحساب می‌خورد. برای استفادهٔ ایجنت‌محور یک پروژهٔ Google Cloud با صورتحساب فعال توصیه می‌شود؛ سهمیه‌های tier رایگان برای نشست‌های طولانی ایجنتی خیلی کوچک‌اند. راهنمای Google Gemini را ببینید.

💡

یک اشتراک به‌جای پنج‌تا: اگر دوست ندارید دنبال معناشازی طرح per-ارائه‌دهنده باشید، Nous Portal بیش از ۳۰۰ مدل را زیر یک اشتراک واحد با یک ورود OAuth پوشش می‌دهد.

۴ ‏Anthropic ‏(بومی)

مدل‌های Claude را مستقیم از طریق API ی Anthropic استفاده کنید — بدون پروکسی OpenRouter. سه روش احراز هویت پشتیبانی می‌شود:

⚠️

اعتبارهای «مصرف اضافه» ی Claude Max لازم است
وقتی از طریق hermes model ← Anthropic OAuth احراز هویت می‌کنید ‏(یا با hermes auth add anthropic --type oauth)، هرمس مثل Claude Code روی حسابتان Anthropic عمل می‌کند. فقط وقتی کار می‌کند که روی طرح Claude Max باشید و اعتبارهای مصرف اضافه خریده باشید. سهمیهٔ پایهٔ طرح Max ‏(مصرف پیش‌فرض شامل‌شده در Claude Code) توسط هرمس مصرف نمی‌شود — فقط اعتبارهای اضافه/مازادی که روی آن افزوده‌اید. مشترکان Claude Pro نمی‌توانند از این مسیر استفاده کنند.

اگر Max + اعتبار اضافه ندارید، به‌جایش از ANTHROPIC_API_KEY استفاده کنید — درخواست‌ها per-token روی سازمان آن کلید صورتحساب می‌شوند ‏(قیمت استاندارد API، مستقل از هر اشتراک Claude).

# With an API key (pay-per-token)
export ANTHROPIC_API_KEY=***
hermes chat --provider anthropic --model claude-sonnet-4-6

# Preferred: authenticate through `hermes model`
# Hermes will use Claude Code's credential store directly when available
hermes model

# Manual override with a setup-token (fallback / legacy)
export ANTHROPIC_TOKEN=***  # setup-token or manual OAuth token
hermes chat --provider anthropic

# Auto-detect Claude Code credentials (if you already use Claude Code)
hermes chat --provider anthropic  # reads Claude Code credential files automatically

وقتی از طریق hermes model گزینهٔ Anthropic OAuth را برمی‌گزینید، هرمس مخزن credential خود Claude Code را به کپی کردن توکن در ~/.hermes/.env ترجیح می‌دهد. این‌طوری credential های قابل-refresh ی Claude قابل-refresh می‌مانند.

یا دائمی تنظیم کنید:

model:
  provider: "anthropic"
  default: "claude-sonnet-4-6"
💡

نام‌های مستعار: ‎--provider claude‎ و ‎--provider claude-code‎ هم به‌عنوان شکل کوتاه ‎--provider anthropic‎ کار می‌کنند.

GitHub Copilot

هرمس GitHub Copilot را به‌عنوان ارائه‌دهندهٔ درجه‌اول با دو حالت پشتیبانی می‌کند:

copilot — API ی مستقیم Copilot ‏(توصیه‌شده). از اشتراک GitHub Copilot تان برای دسترسی به GPT-5.x، ‏Claude، ‏Gemini و مدل‌های دیگر از طریق API ی Copilot استفاده می‌کند.

hermes chat --provider copilot --model gpt-5.4

گزینه‌های احراز هویت ‏(به این ترتیب چک می‌شوند):

  1. متغیر محیطی COPILOT_GITHUB_TOKEN
  2. متغیر محیطی GH_TOKEN
  3. متغیر محیطی GITHUB_TOKEN
  4. جایگزین CLI ی gh auth token

اگر هیچ توکنی پیدا نشود، hermes model یک ورود کد-دستگاه OAuth پیشنهاد می‌کند — همان جریانی که Copilot CLI و opencode استفاده می‌کنند.

⚠️

انواع توکن
API ی Copilot از توکن‌های کلاسیک PAT ‏(Personal Access Token) با پیشوند ghp_* پشتیبانی نمی‌کند. انواع توکن پشتیبانی‌شده:

نوعپیشوندروش دریافت
توکن OAuthgho_‏hermes model ← GitHub Copilot ← Login with GitHub
PAT ریزدانهgithub_pat_تنظیمات GitHub ← Developer settings ← Fine-grained tokens ‏(نیازمند مجوز Copilot Requests)
توکن GitHub Appghu_از طریق نصب GitHub App

اگر gh auth token تان توکن ghp_* برگرداند، برای احراز هویت از طریق OAuth از hermes model استفاده کنید.

📌

رفتار احراز هویت Copilot در هرمس
هرمس یک توکن پشتیبانی‌شدهٔ GitHub ‏(gho_*، ‏github_pat_* یا ghu_*) را مستقیم به api.githubcopilot.com می‌فرستد و هدرهای مخصوص Copilot را ضمیمه می‌کند ‏(Editor-Version، ‏Copilot-Integration-Id، ‏Openai-Intent، ‏x-initiator).

روی خطای HTTP 401، هرمس قبل از fallback یک بازیابی credential یک‌باره انجام می‌دهد:

  1. بازمحاسبهٔ توکن از طریق زنجیرهٔ اولویت معمول ‏(COPILOT_GITHUB_TOKEN ← GH_TOKEN ← GITHUB_TOKEN ← gh auth token)
  2. بازسازی سرویس‌گیرندهٔ مشترک OpenAI با هدرهای تازه‌شده
  3. تکرار یک‌بارهٔ درخواست

بعضی پروکسی‌های اجتماعی قدیمی‌تر از جریان تبادل api.github.com/copilot_internal/v2/token استفاده می‌کنند. آن نقطهٔ پایانی برای بعضی انواع حساب در دسترس نیست ‏(404 برمی‌گرداند). بنابراین هرمس احراز هویت مستقیم-با-توکن را مسیر اصلی نگه می‌دارد و برای مقاومت به refresh پویای credential و retry متکی است.

مسیریابی API: مدل‌های GPT-5+ ‏(به‌جز gpt-5-mini) خودکار از Responses API استفاده می‌کنند. همهٔ مدل‌های دیگر ‏(GPT-4o، ‏Claude، ‏Gemini و...) از Chat Completions. مدل‌ها از کاتالوگ زندهٔ Copilot خودکار تشخیص داده می‌شوند.

copilot-acp — بک‌اند عامل ACP ی Copilot.Copilot CLI محلی را به‌صورت زیرفرایند اجرا می‌کند:

hermes chat --provider copilot-acp --model copilot-acp
# Requires the GitHub Copilot CLI in PATH and an existing `copilot login` session

پیکربندی دائمی:

model:
  provider: "copilot"
  default: "gpt-5.4"

۶ ‏xAI ‏(Grok) — Responses API + کش پرامپت

‏xAI از طریق Responses API ‏(ترنسپورت codex_responses) سیم‌کشی شده تا پشتیبانی خودکار reasoning روی مدل‌های Grok 4 داشته باشد — بدون نیاز به پارامتر reasoning_effort، سرور به‌طور پیش‌فرض reasoning می‌کند. مقدار XAI_API_KEY را در ~/.hermes/.env ست کنید، در hermes model گزینهٔ xAI را بردارید، یا میان‌بر grok را در ‎/model grok-4-fast-reasoning‎ بیندازید.

مشترکان SuperGrok و X Premium+ می‌توانند به‌جای کلید API با OAuth مرورگری وارد شوند — در hermes model گزینهٔ xAI Grok OAuth (SuperGrok / Premium+) را بردارید یا hermes auth add xai-oauth را اجرا کنید. همین bearer token ی OAuth خودکار توسط ابزارهای مستقیم-به-xAI هم دوباره استفاده می‌شود ‏(TTS، تولید تصویر، تولید ویدیو، پیاده‌سازی صدا). راهنمای xAI Grok OAuth را برای جریان کامل ببینید — و اگر هرمس روی host راه‌دور اجرا می‌شود، OAuth از طریق SSH / Host های راه‌دور را هم برای تونل لازم ssh -L ببینید.

وقتی xAI به‌عنوان ارائه‌دهنده استفاده می‌شود ‏(هر URL پایه‌ای که x.ai داشته باشد)، هرمس کش پرامپت ‏(prompt caching) را خودکار فعال می‌کند و هدر x-grok-conv-id را با هر درخواست API می‌فرستد. این کار درخواست‌ها را در طول نشست گفتگو به همان سرور مسیریابی می‌کند تا زیرساخت xAI بتواند system prompt های کش‌شده و تاریخچهٔ گفتگو را دوباره استفاده کند.

هیچ پیکربندی لازم نیست — کش وقتی نقطهٔ پایانی xAI تشخیص داده شود و شناسهٔ نشست موجود باشد خودکار فعال می‌شود. این کار تأخیر و هزینهٔ گفتگوهای چندنوبتی را کم می‌کند.

‏xAI یک نقطهٔ پایانی اختصاصی TTS هم دارد ‏(/v1/tts). در hermes tools ← Voice & TTS گزینهٔ xAI TTS را بردارید یا صفحهٔ صدا و TTS را برای پیکربندی ببینید.

مهاجرت مدل‌های بازنشستهٔ xAI ‏(۱۵ مه ۲۰۲۶): ‏xAI در تاریخ 2026-05-15 مدل‌های grok-4*، ‏grok-3، ‏grok-code-fast-1 و grok-imagine-image-pro را بازنشسته می‌کند. هم hermes doctor هم شروع hermes chat هر پیکربندی‌ای که هنوز به یک ارجاع بازنشسته اشاره کند را تشخیص و جایگزین پیشنهادی را چاپ می‌کنند. برای بازنویسی یک‌بارهٔ config از hermes migrate xai استفاده کنید — پیش‌فرض dry-run است؛ برای نوشتن تغییرات ‎--apply‎ اضافه کنید ‏(به‌طور خودکار یک پشتیبان زمان‌دار config.yaml.bak-pre-migrate-xai-* ساخته می‌شود).

hermes migrate xai          # preview replacements
hermes migrate xai --apply  # rewrite ~/.hermes/config.yaml in place

بک‌اند جستجوی وب xAI. وقتی مجموعه‌ابزار جستجوی وب فعال باشد، مقدار web.backend: xai جستجو را با همین credential های XAI_API_KEY / OAuth از طریق نقطهٔ پایانی جستجوی میزبانی‌شدهٔ xAI عبور می‌دهد. اگر xAI قبلاً به‌عنوان ارائه‌دهنده پیکربندی شده، راه‌اندازی اضافه لازم نیست.

۷ سایر ارائه‌دهندگان ابری

NovitaAI

NovitaAI ابرِ AI-بومی برای سازنده‌ها و عامل‌هاست. سه خط محصولش عبارت‌اند از Model API برای بیش از ۲۰۰ مدل، Agent Sandbox برای ساخت و اجرای عامل‌های AI، و GPU Cloud برای محاسبات مقیاس‌پذیر — همه از یک پلتفرم.

# Use any available model
hermes chat --provider novita --model moonshotai/kimi-k2.5
# Requires: NOVITA_API_KEY in ~/.hermes/.env

# Short alias
hermes chat --provider novita-ai --model deepseek/deepseek-v3-0324

یا دائمی در config.yaml:

model:
  provider: "novita"
  default: "moonshotai/kimi-k2.5"
  base_url: "https://api.novita.ai/openai/v1"

کلید API تان را در novita.ai/settings/key-management بگیرید. URL پایه با NOVITA_BASE_URL قابل بازنویسی است.

Ollama Cloud — مدل‌های مدیریت‌شدهٔ Ollama با OAuth + کلید API

Ollama Cloud همان کاتالوگ مدل‌های open-weight ی Ollama محلی را میزبانی می‌کند ولی بدون نیاز به GPU. در hermes model گزینهٔ Ollama Cloud را بردارید، کلید API تان را از ollama.com/settings/keys بچسبانید و هرمس مدل‌های موجود را خودکار کشف می‌کند.

hermes model
# → pick "Ollama Cloud"
# → paste your OLLAMA_API_KEY
# → select from discovered models (gpt-oss:120b, glm-4.6:cloud, qwen3-coder:480b-cloud, etc.)

یا مستقیم config.yaml:

model:
  provider: "ollama-cloud"
  default: "gpt-oss:120b"

کاتالوگ مدل به‌صورت پویا از ollama.com/v1/models گرفته و یک ساعت کش می‌شود. نمادگذاری model:tag ‏(مثل qwen3-coder:480b-cloud) در نرمال‌سازی حفظ می‌شود — از خط تیره استفاده نکنید.

💡

Ollama Cloud در مقابل Ollama محلی: هردو همان API ی سازگار-OpenAI را حرف می‌زنند. نسخهٔ ابری ارائه‌دهندهٔ درجه‌اول است ‏(‎--provider ollama-cloud‎ با OLLAMA_API_KEY)؛ Ollama محلی از طریق مسیر Custom Endpoint در دسترس است ‏(URL پایه http://localhost:11434/v1 بدون کلید). برای مدل‌های بزرگ که محلی نمی‌توانید اجرا کنید از ابری؛ برای حریم خصوصی یا کار آفلاین از محلی.

AWS Bedrock

مدل‌های Anthropic Claude، ‏Amazon Nova، ‏DeepSeek v3.2، ‏Meta Llama 4 و دیگر مدل‌ها از طریق AWS Bedrock. از زنجیرهٔ credential ی AWS SDK ‏(boto3) استفاده می‌کند — بدون کلید API، فقط احراز هویت استاندارد AWS.

# Simplest — named profile in ~/.aws/credentials
hermes chat --provider bedrock --model us.anthropic.claude-sonnet-4-6

# Or with explicit env vars
AWS_PROFILE=myprofile AWS_REGION=us-east-1 hermes chat --provider bedrock --model us.anthropic.claude-sonnet-4-6

یا دائمی در config.yaml:

model:
  provider: "bedrock"
  default: "us.anthropic.claude-sonnet-4-6"
bedrock:
  region: "us-east-1"          # or set AWS_REGION
  # profile: "myprofile"       # or set AWS_PROFILE
  # discovery: true            # auto-discover region from IAM
  # guardrail:                 # optional Bedrock Guardrails
  #   guardrail_identifier: "your-guardrail-id"
  #   guardrail_version: "DRAFT"

احراز هویت از زنجیرهٔ استاندارد boto3 استفاده می‌کند: مقدار صریح AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY، یا AWS_PROFILE از ~/.aws/credentials، یا نقش IAM روی EC2/ECS/Lambda، یا IMDS، یا SSO. اگر قبلاً با AWS CLI وارد شده باشید هیچ متغیر محیطی لازم نیست.

راهنمای AWS Bedrock را برای مرور راه‌اندازی IAM، انتخاب منطقه و استنتاج بین-منطقه‌ای ببینید.

Actual Computer

سخت‌افزار خودتان به‌عنوان خوشهٔ استنتاج خصوصی از طریق Actual Computer. دو حالت سرویس‌دهی، هردو سازگار-OpenAI ‏(هرمس از ترنسپورت Responses API استفاده می‌کند):

  • رلهٔ میزبانی‌شده — ‏https://api.actual.inc، رمزنگاری سرتاسری، مسیریابی به خوشهٔ خودتان. احراز هویت با یک کلید استنتاج ac_ از actual.inc/user/keys.
  • دیمن محلی — روی دستگاه در http://127.0.0.1:8080، کاملاً آفلاین. کلید API لازم نیست: هرمس URL پایهٔ loopback را تشخیص و خودکار با یک placeholder داخلی احراز هویت می‌کند.
# Hosted relay (ACTUAL_API_KEY in ~/.hermes/.env)
hermes chat --provider actual --model <model-id-from-your-cluster>

# Local daemon (ACTUAL_BASE_URL=http://127.0.0.1:8080 in ~/.hermes/.env, no key)
hermes chat --provider actual --model <installed-model-name>

یا دائمی در config.yaml:

model:
  provider: "actual"
  default: "<model-id>"

نکته‌ها:

  • شناسه‌های مدل از GET /v1/models خوشهٔ شما می‌آیند — با hermes model یا ‎curl -s https://api.actual.inc/v1/models -H "Authorization: Bearer $ACTUAL_API_KEY"‎ کشفشان کنید.
  • Host های لخت نرمال می‌شوند: ACTUAL_BASE_URL=http://127.0.0.1:8080 خودکار به http://127.0.0.1:8080/v1 تبدیل می‌شود.
  • میزان تلاش reasoning به بازهٔ پشتیبانی‌شدهٔ Actual محدود می‌شود ‏(none/low/medium/high/max) — تنظیم global ی xhigh/ultra باعث خطای 400 در درخواست‌ها نمی‌شود.
  • مدل‌های محلی کوچک: مجموعه‌ابزار کامل پیش‌فرض هرمس به‌اضلاف system prompt می‌تواند از پنجرهٔ زمینهٔ 32k بزرگ‌تر شود و خطای empty-stream از سرورهای خانوادهٔ llama.cpp بدهد. مجموعه‌ابزار را محدود کنید ‏(‎-t file,web‎) یا مدل را با زمینهٔ بزرگ‌تر بار کنید. مهارت اختیاری actual-setup ‏(hermes skills install official/devops/actual-setup) راه‌اندازی و عیب‌یابی را با جزئیات پوشش می‌دهد.
  • نام‌های مستعار: actual-computer، ‏actualcomputer، ‏aci.

۸ ارائه‌دهندگان LLM سفارشی و خودمیزبان

‏Hermes Agent با هر نقطهٔ پایانی سازگار-OpenAI کار می‌کند. اگر سروری ‎/v1/chat/completions‎ را پیاده‌سازی کرده باشد، می‌توانید هرمس را به آن اشاره دهید. یعنی می‌توانید از مدل‌های محلی، سرورهای استنتاج GPU، مسیریاب‌های چند-ارائه‌دهنده یا هر API ی شخص ثالث استفاده کنید.

راه‌اندازی عمومی

سه راه برای پیکربندی یک نقطهٔ پایانی سفارشی:

راه‌اندازی تعاملی ‏(توصیه‌شده):

hermes model
# Select "Custom endpoint (self-hosted / VLLM / etc.)"
# Enter: API base URL, API key, Model name

پیکربندی دستی ‏(config.yaml):

# In ~/.hermes/config.yaml
model:
  default: your-model-name
  provider: custom
  base_url: http://localhost:8000/v1
  api_key: your-key-or-leave-empty-for-local
⚠️

متغیرهای محیطی قدیمی: مقدار LLM_MODEL در .env حذف شده — config.yaml تنها منبع حقیقت برای پیکربندی مدل و نقطهٔ پایانی است. مقدار OPENAI_BASE_URL هنوز پذیرفته می‌شود ولی فقط برای ارائه‌دهندهٔ openai-api ‏(نقطهٔ پایانی OpenAI را برای دسترسی مستقیم با کلید API بازنویسی می‌کند). برای بقیهٔ ارائه‌دهنده‌ها و نقاط پایانی سفارشی از hermes model یا ست کردن مستقیم model.base_url در config.yaml استفاده کنید. اگر مدخل‌های کهنه در .env تان دارید، در hermes setup یا مهاجرت config بعدی خودکار پاک می‌شوند.

هردو روش در config.yaml ذخیره می‌شوند که منبع حقیقتِ مدل، ارائه‌دهنده و URL پایه است.

سوییچ مدل با ‎/model‎

⚠️

hermes model در مقابل ‎/model‎
hermes model ‏(از ترمینال، بیرون نشست چت) ویزارد کامل راه‌اندازی ارائه‌دهنده است. برای افزودن ارائه‌دهندهٔ جدید، اجرای جریان‌های OAuth، وارد کردن کلیدهای API و پیکربندی نقاط پایانی سفارشی از آن استفاده کنید.

/model ‏(داخل نشست فعال چت Hermes تایپ می‌شود) فقط می‌تواند بین ارائه‌دهنده‌ها و مدل‌هایی که قبلاً راه‌اندازی کرده‌اید سوئیچ کند. نمی‌تواند ارائه‌دهندهٔ جدید اضافه کند، OAuth اجرا کند یا کلید API بپرسد. اگر فقط یک ارائه‌دهنده پیکربندی کرده‌اید ‏(مثلاً OpenRouter)، ‏‎/model‎ فقط مدل‌های همان را نشان می‌دهد.

برای افزودن ارائه‌دهندهٔ جدید: از نشست خارج شوید ‏(Ctrl+C یا ‎/quit)، ‏hermes model را اجرا کنید، ارائه‌دهندهٔ جدید را راه بیندازید و بعد نشست جدیدی شروع کنید.

وقتی حداقل یک نقطهٔ پایانی سفارشی پیکربندی کرده باشید، می‌توانید وسط نشست سوئیچ کنید:

/model custom:qwen-2.5          # Switch to a model on your custom endpoint
/model custom                    # Auto-detect the model from the endpoint
/model openrouter:claude-sonnet-4 # Switch back to a cloud provider

اگر ارائه‌دهندگان سفارشی نام‌دار دارید ‏(پایین را ببینید)، از نماد سه‌تایی استفاده کنید:

/model custom:local:qwen-2.5    # Use the "local" custom provider with model qwen-2.5
/model custom:work:llama3       # Use the "work" custom provider with llama3

هنگام سوییچ ارائه‌دهنده، هرمس URL پایه و ارائه‌دهنده را در config ذخیره می‌کند تا تغییر بعد از restart هم بماند. هنگام سوییچ از یک نقطهٔ پایانی سفارشی به ارائه‌دهندهٔ داخلی، URL پایهٔ کهنه خودکار پاک می‌شود.

💡

‏‎/model custom‎ ‏(لخت، بدون نام مدل) API ی ‎/models‎ نقطهٔ پایانی شما را کوئری می‌کند و اگر دقیقاً یک مدل بار شده باشد آن را خودکار انتخاب می‌کند. برای سرورهای محلی که تک‌مدل اجرا می‌کنند کاربردی است.

همه‌چیز در ادامه همین الگو را دنبال می‌کند — فقط URL، کلید و نام مدل را عوض کنید.

Ollama مدل‌های open-weight را با یک فرمان محلی اجرا می‌کند. بهترین گزینه برای: آزمایش سریع محلی، کارهای حساس به حریم خصوصی، استفادهٔ آفلاین. فراخوانی ابزار را از طریق API ی سازگار-OpenAI پشتیبانی می‌کند.

بعد هرمس را پیکربندی کنید:

hermes model
# Select "Custom endpoint (self-hosted / VLLM / etc.)"
# Enter URL: http://localhost:11434/v1

# Enter model name (e.g. qwen2.5-coder:32b)

  default: qwen2.5-coder:32b

  context_length: 64000   # See warning below
⚠️

Ollama به‌طور پیش‌فرض طول زمینهٔ خیلی کمی دارد
Ollama به‌طور پیش‌فرض از تمام پنجرهٔ زمینهٔ مدل شما استفاده نمی‌کند. بسته به VRAM تان، پیش‌فرض این است:

VRAM موجودزمینهٔ پیش‌فرض
کمتر از ۲۴ گیگابایت۴٬۰۹۶ توکن
۲۴ تا ۴۸ گیگابایت۳۲٬۷۶۸ توکن
بیش از ۴۸ گیگابایت۲۵۶٬۰۰۰ توکن

‏Hermes Agent برای استفادهٔ ایجنتی با ابزارها حداقل به ۶۴٬۰۰۰ توکن زمینه نیاز دارد. پنجره‌های کوچک‌تر در زمان شروع رد می‌شوند چون system prompt، اسکیماهای ابزار و وضعیت گفتگوی جاری برای گردش‌کارهای چندمرحله‌ای قابل‌اعتماد جای کافی لازم دارند.

چطور افزایشش دهید ‏(یکی را انتخاب کنید):

# Option 1: Set server-wide via environment variable (recommended)
OLLAMA_CONTEXT_LENGTH=64000 ollama serve

# Option 2: For systemd-managed Ollama
sudo systemctl edit ollama.service
# Add: Environment="OLLAMA_CONTEXT_LENGTH=64000"
# Then: sudo systemctl daemon-reload && sudo systemctl restart ollama

ollama ps

vLLM استاندارد سرویس‌دهی LLM در تولید است. بهترین گزینه برای: بیشترین توان عملیاتی روی سخت‌افزار GPU، سرویس‌دادن مدل‌های بزرگ، batching پیوسته.

بعد هرمس را پیکربندی کنید:

hermes model

# Enter URL: http://localhost:8000/v1
# Skip API key (or enter one if you configured vLLM with --api-key)
# Enter model name: meta-llama/Llama-3.1-70B-Instruct

طول زمینه: ‏vLLM به‌طور پیش‌فرض max_position_embeddings مدل را می‌خواند. اگر این مقدار از حافظهٔ GPU تان بیشتر باشد خطا می‌دهد و می‌خواهد --max-model-len را پایین‌تر ست کنید. همچنین می‌توانید از --max-model-len auto استفاده کنید تا خودکار بیشینهٔ جا‌شده پیدا شود. مقدار --gpu-memory-utilization 0.95 ‏(پیش‌فرض ۰٫۹) را ست کنید تا زمینهٔ بیشتری در VRAM جا شود.

پارسرهای reasoning ی Qwen: هرمس متادیتای ساختاریافتهٔ reasoning مثل reasoning، ‏reasoning_content و دلتاهای reasoning ی استریم‌شده را وقتی سرورهای سازگار-OpenAI برگردانند حفظ می‌کند. این متادیتا به‌عنوان دادهٔ ردیابی reasoning/تفکر برخورد می‌شود، نه جایگزین پاسخ مرئی دستیار. برای مدل‌های reasoning ی Qwen که vLLM سرویس می‌دهد مطمئن شوید پاسخ نهایی مرئی کاربر همچنان در content ظاهر می‌شود. اگر ‎--reasoning-parser qwen3‎ در استقرار شما content را خالی گذاشت، یا آن پارسر را غیرفعال کنید یا یک گزینهٔ درخواست پشتیبانی‌شدهٔ سرور مثل chat_template_kwargs.enable_thinking: false را از طریق extra_body بفرستید.

💡

‏vLLM اندازه‌های خوانا پشتیبانی می‌کند: ‎--max-model-len 64k‎ ‏(k کوچک = ۱۰۰۰، ‏K بزرگ = ۱۰۲۴).

SGLang جایگزینی برای vLLM است با RadixAttention برای استفادهٔ مجدد از KV cache. بهترین گزینه برای: گفتگوهای چندنوبتی ‏(کش پیشوند)، decoding مقیدشده، خروجی ساختاریافته.

  --port 30000 \
  --context-length 65536 \

بعد هرمس را پیکربندی کنید:

hermes model
# Select "Custom endpoint (self-hosted / VLLM / etc.)"
# Enter URL: http://localhost:30000/v1
# Enter model name: meta-llama/Llama-3.1-70B-Instruct

طول زمینه: ‏SGLang به‌طور پیش‌فرض از config مدل می‌خواند. برای بازنویسی از ‎--context-length‎ استفاده کنید. اگر لازم است از بیشینهٔ اعلام‌شدهٔ مدل فراتر بروید، SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 را ست کنید.

فراخوانی ابزار: از ‎--tool-call-parser‎ با پارسر مناسب خانوادهٔ مدل تان استفاده کنید: qwen ‏(Qwen 2.5)، ‏llama3، ‏llama4، ‏deepseekv3، ‏mistral، ‏glm. بدون این فلگ فراخوانی‌های ابزار به‌صورت متن ساده برمی‌گردند.

llama.cpp / llama-server — استنتاج CPU و Metal

llama.cpp مدل‌های کوانتیزه‌شده را روی CPU، ‏Apple Silicon ‏(Metal) و GPU های مصرفی اجرا می‌کند. بهترین گزینه برای: اجرای مدل بدون GPU ی مرکز داده، کاربران Mac، استقرار edge.

# Build and start llama-server
cmake -B build && cmake --build build --config Release
./build/bin/llama-server \
  --jinja -fa \
  -c 64000 \
  -ngl 99 \
  -m models/qwen2.5-coder-32b-instruct-Q4_K_M.gguf \
  --port 8080 --host 0.0.0.0

طول زمینه ‎(-c)‎: نسخه‌های اخیر به‌طور پیش‌فرض 0 دارند که زمینهٔ آموزشی مدل را از متادیتای GGUF می‌خواند. برای مدل‌هایی با زمینهٔ آموزشی ۱۲۸k+ ممکن است تلاش برای تخصیص کامل KV cache باعث OOM شود. ‎-c‎ را صریحاً حداقل روی ۶۴٬۰۰۰ توکن برای Hermes ست کنید. اگر از اسلات‌های موازی ‏(‎-np‎) استفاده می‌کنید، کل زمینه بین اسلات‌ها تقسیم می‌شود — با ‎-c 64000 -np 4‎ هر اسلات فقط 16k می‌گیرد که زیر حداقل هرمس برای هر نشست فعال است.

بعد هرمس را به آن اشاره دهید:

hermes model
# Select "Custom endpoint (self-hosted / VLLM / etc.)"
# Enter URL: http://localhost:8080/v1
# Skip API key (local servers don't need one)
# Enter model name — or leave blank to auto-detect if only one model is loaded

این کار نقطهٔ پایانی را در config.yaml ذخیره می‌کند پس بین نشست‌ها می‌ماند.

⚠️

‎--jinja‎ برای فراخوانی ابزار الزامی است
بدون ‎--jinja‎، ‏llama-server پارامتر tools را کاملاً نادیده می‌گیرد. مدل سعی می‌کند ابزارها را با نوشتن JSON در متن پاسخ صدا بزند ولی هرمس آن را به‌عنوان فراخوانی ابزار تشخیص نمی‌دهد — JSON خامی مثل {"name": "web_search", ...} را به‌جای یک جستجوی واقعی چاپ‌شده می‌بینید.

پشتیبانی بومی فراخوانی ابزار ‏(بهترین کارایی): Llama 3.x، ‏Qwen 2.5 ‏(شامل Coder)، ‏Hermes 2/3، ‏Mistral، ‏DeepSeek، ‏Functionary. بقیهٔ مدل‌ها از یک handler عمومی استفاده می‌کنند که کار می‌کند ولی ممکن است کم‌بازده‌تر باشد. فهرست کامل را در مستندات function calling ی llama.cpp ببینید.

می‌توانید فعال بودن پشتیبانی ابزار را با چک کردن http://localhost:8080/props تأیید کنید — فیلد chat_template باید موجود باشد.

💡

مدل‌های GGUF را از Hugging Face دانلود کنید. کوانتیزه‌سازی Q4_K_M بهترین توازن کیفیت نسبت به مصرف حافظه را می‌دهد.

LM Studio — برنامهٔ دسکتاپ با مدل‌های محلی

LM Studio برنامهٔ دسکتاپی برای اجرای مدل‌های محلی با GUI است. بهترین گزینه برای: کاربرانی که رابط تصویری می‌پسندند، تست سریع مدل، توسعه‌دهندگان روی macOS/Windows/Linux.

سرور را از برنامهٔ LM Studio اجرا کنید ‏(تب Developer ← Start Server) یا از CLI استفاده کنید:

lms server start                        # Starts on port 1234
lms load qwen2.5-coder --context-length 64000

بعد هرمس را پیکربندی کنید:

hermes model
# Select "LM Studio"
# Press Enter to use http://localhost:1234/v1
# Pick one of the discovered models
# If LM Studio server auth is enabled, enter LM_API_KEY when prompted

هرمس زمینهٔ نمونهٔ از قبل بار‌شدهٔ LM Studio را حفظ می‌کند. برای مدلی که در حالت explicit پیش‌فرض بار نشده، هرمس context_length را حذف می‌کند مگر اینکه خودتان در Hermes ست کرده باشید تا LM Studio تنظیم مدل خودش را اعمال کند. بعد هرمس فقط از طول زمینه‌ای استفاده می‌کند که LM Studio بعد از بارگذاری گزارش می‌کند.

برای تغییر طول زمینه در LM Studio:

  1. روی آیکون چرخ‌دنده کنار انتخاب‌گر مدل کلیک کنید
  2. «Context Length» را حداقل روی ۶۴۰۰۰ بگذارید تا تجربه روان باشد
  3. مدل را دوباره بار کنید تا تغییر اعمال شود
  4. اگر ماشینتان ۶۴۰۰۰ را جا نمی‌دهد، مدل کوچک‌تری با طول زمینهٔ بزرگ‌تر را در نظر بگیرید.

یا از CLI: lms load model-name --context-length 64000

با CLI می‌توانید تخمین بزنید مدل جا می‌شود یا نه: lms load model-name --context-length 64000 --estimate-only

برای پیش‌فرض‌های دائمی per-model: تب My Models ← آیکون چرخ‌دنده روی مدل ← ست کردن اندازهٔ زمینه.

اگر از قابلیت Just-In-Time loading / Auto-Evict ی LM Studio استفاده می‌کنید و می‌خواهید LM Studio بارگذاری و تخلیهٔ مدل را از روی درخواست‌های معمول چت مدیریت کند، مرحلهٔ preload صریح Hermes را رد کنید:

hermes config set model.lmstudio_load_mode jit

برگشت به رفتار پیش‌فرض preload صریح:

hermes config set model.lmstudio_load_mode explicit

فراخوانی ابزار: از LM Studio 0.3.6 پشتیبانی می‌شود. مدل‌هایی با آموزش بومی فراخوانی ابزار ‏(Qwen 2.5، ‏Llama 3.x، ‏Mistral، ‏Hermes) خودکار تشخیص و با نشان ابزار نمایش داده می‌شوند. بقیهٔ مدل‌ها از fallback عمومی استفاده می‌کنند که ممکن است کمتر قابل‌اعتماد باشد.

شبکهٔ WSL2 ‏(کاربران ویندوز)

چون Hermes Agent به محیط یونیکس نیاز دارد، کاربران ویندوز آن را داخل WSL2 اجرا می‌کنند. اگر سرور مدل تان ‏(Ollama، ‏LM Studio و...) روی host ویندوز اجرا می‌شود، باید شکاف شبکه را پل بزنید — WSL2 از یک آداپتور شبکهٔ مجازی با ساب‌نت خودش استفاده می‌کند، پس localhost داخل WSL2 به ماشین مجازی لینوکس اشاره می‌کند نه host ویندوز.

💡

هردو داخل WSL2؟ مشکلی نیست.
اگر سرور مدل تان هم داخل WSL2 اجرا می‌شود ‏(برای vLLM، ‏SGLang و llama-server رایج است)، localhost همان‌طور که انتظار دارید کار می‌کند — فضای نام شبکه‌شان مشترک است. این بخش را رد کنید.

گزینهٔ ۱: حالت شبکهٔ Mirrored ‏(توصیه‌شده)

روی Windows 11 22H2+ در دسترس است؛ حالت mirrored کاری می‌کند localhost دوطرفه بین ویندوز و WSL2 کار کند — ساده‌ترین راه‌حل.

  1. فایل %USERPROFILE%\.wslconfig را بسازید یا ویرایش کنید ‏(مثلاً C:\Users\YourName\.wslconfig): 
    [wsl2]
networkingMode=mirrored
  2. WSL را از PowerShell ری‌استارت کنید: 
    wsl --shutdown
  3. ترمینال WSL2 تان را دوباره باز کنید. حالا localhost به سرویس‌های ویندوز می‌رسد: 
    curl http://localhost:11434/v1/models   # Ollama on Windows — works
📌

دیوارآتش Hyper-V: روی بعضی نسخه‌های Windows 11 دیوارآتش Hyper-V به‌طور پیش‌فرض اتصالات mirrored را مسدود می‌کند. اگر بعد از فعال کردن حالت mirrored همچنان localhost کار نمی‌کند، این را در یک PowerShell ادمین اجرا کنید:

Set-NetFirewallHyperVVMSetting -Name '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -DefaultInboundAction Allow

گزینهٔ ۲: استفاده از IP ی host ویندوز ‏(Windows 10 / نسخه‌های قدیمی‌تر)

اگر نمی‌توانید از حالت mirrored استفاده کنید، از داخل WSL2 آی‌پی host ویندوز را پیدا کنید و به‌جای localhost از آن استفاده کنید:

# Get the Windows host IP (the default gateway of WSL2's virtual network)
ip route show | grep -i default | awk '{ print $3 }'
# Example output: 172.29.192.1

آن IP را در پیکربندی Hermes استفاده کنید:

model:
  default: qwen2.5-coder:32b
  provider: custom
  base_url: http://172.29.192.1:11434/v1   # Windows host IP, not localhost
💡

کمکی پویا: IP ی host با هر ری‌استارت WSL2 ممکن است عوض شود. می‌توانید در شل به‌صورت پویا بگیریدش:

export WSL_HOST=$(ip route show | grep -i default | awk '{ print $3 }')
echo "Windows host at: $WSL_HOST"
curl http://$WSL_HOST:11434/v1/models   # Test Ollama

یا از نام mDNS ماشینی‌تان استفاده کنید ‏(نیازمند libnss-mdns در WSL2):

sudo apt install libnss-mdns
curl http://$(hostname).local:11434/v1/models

آدرس Bind سرور ‏(برای حالت NAT الزامی)

اگر از گزینهٔ ۲ استفاده می‌کنید ‏(حالت NAT با IP ی host)، سرور مدل روی ویندوز باید اتصالات خارج از 127.0.0.1 را قبول کند. به‌طور پیش‌فرض بیشتر سرورها فقط روی localhost گوش می‌دهند — اتصالات WSL2 در حالت NAT از یک ساب‌نت مجازی متفاوت می‌آیند و رد می‌شوند. در حالت mirrored، localhost مستقیم نگاشت می‌شود پس bind پیش‌فرض 127.0.0.1 خوب کار می‌کند.

سرورbind پیش‌فرضراه حل
Ollama127.0.0.1متغیر محیطی OLLAMA_HOST=0.0.0.0 را قبل از اجرای Ollama ست کنید ‏(در ویندوز: System Settings ← Environment Variables، یا ویرایش سرویس Ollama)
LM Studio127.0.0.1گزینهٔ Serve on Network را در تب Developer ← تنظیمات Server فعال کنید
llama-server127.0.0.1‎--host 0.0.0.0‎ را به فرمان اجرا اضافه کنید
vLLM0.0.0.0به‌طور پیش‌فرض به همهٔ اینترفیس‌ها bind می‌شود

Ollama روی ویندوز ‏(با جزئیات):Ollama به‌عنوان یک سرویس ویندوز اجرا می‌شود. برای ست کردن OLLAMA_HOST:

  1. ‏System Properties ← Environment Variables را باز کنید
  2. یک متغیر System جدید اضافه کنید: OLLAMA_HOST = 0.0.0.0
  3. سرویس Ollama را ری‌استارت کنید ‏(یا سیستم را ریبوت کنید)

دیوارآتش ویندوز

دیوارآتش ویندوز با WSL2 مثل یک شبکهٔ جدا رفتار می‌کند ‏(هم در NAT هم در mirrored). اگر بعد از مراحل بالا اتصال‌ها هنوز شکست می‌خورند، یک قانون دیوارآتش برای پورت سرور مدلتان اضافه کنید:

# Run in Admin PowerShell — replace PORT with your server's port
New-NetFirewallRule -DisplayName "Allow WSL2 to Model Server" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 11434

پورت‌های رایج: Ollama ‏۱۱۴۳۴، ‏vLLM ‏۸۰۰۰، ‏SGLang ‏۳۰۰۰۰، ‏llama-server ‏۸۰۸۰، ‏LM Studio ‏۱۲۳۴.

تأیید سریع

از داخل WSL2 تست کنید که به سرور مدل تان می‌رسید:

# Replace URL with your server's address and port
curl http://localhost:11434/v1/models          # Mirrored mode
curl http://172.29.192.1:11434/v1/models       # NAT mode (use your actual host IP)

اگر پاسخی JSON حاوی فهرست مدل‌ها گرفتید، همه‌چیز آماده است. همان URL را به‌عنوان base_url در پیکربندی Hermes استفاده کنید.

عیب‌یابی مدل‌های محلی

این مشکل‌ها روی همهٔ سرورهای استنتاج محلی وقتی با Hermes استفاده می‌شوند اثر می‌گذارند.

«Connection refused» از WSL2 به سرور مدل روی host ویندوز

اگر هرمس داخل WSL2 اجرا می‌شود و سرور مدل تان روی host ویندوز است، ‎http://localhost:<port>‎ در حالت شبکهٔ NAT ی پیش‌فرض WSL2 کار نمی‌کند. راه‌حل را در بخش شبکهٔ WSL2 بالا ببینید.

فراخوانی‌های ابزار به‌جای اجرا شدن، متن می‌شوند

مدل چیزی مثل {"name": "web_search", "arguments": {...}} را به‌عنوان پیام خروجی می‌دهد به‌جای اینکه واقعاً ابزار را صدا بزند.

علت: سرور شما فراخوانی ابزار را فعال نکرده یا مدل از طریق پیاده‌سازی فراخوانی ابزارِ سرور از آن پشتیبانی نمی‌کند.

پیام «Context limit: 2048 tokens» هنگام شروع

هرمس طول زمینه را از نقطهٔ پایانی ‎/v1/models‎ سرور شما تشخیص می‌دهد. اگر سرور مقدار کمی گزارش کند ‏(یا اصلاً گزارش نکند)، هرمس حد اعلام‌شدهٔ مدل را استفاده می‌کند که ممکن است غلط باشد.

راه حل: صریحاً در config.yaml ستش کنید:

model:
  default: your-model
  provider: custom
  base_url: http://localhost:11434/v1
  context_length: 64000

پاسخ‌ها وسط جمله قطع می‌شوند

علت‌های احتمالی:

  1. سقف خروجی کم ‏(max_tokens) روی سرور — SGLang به‌طور پیش‌فرض ۱۲۸ توکن per پاسخ دارد. ‎--default-max-tokens‎ را روی سرور ست کنید یا در config.yaml مقدار model.max_tokens را پیکربندی کنید. توجه: max_tokens فقط طول پاسخ را کنترل می‌کند — ربطی به اینکه تاریخچهٔ گفتگویتان چقدر بلند باشد ندارد ‏(آن مربوط به context_length است).
  2. تمام شدن زمینه — مدل پنجرهٔ زمینه‌اش را پر کرده. model.context_length را افزایش دهید یا فشرده‌سازی زمینه را در هرمس فعال کنید.

تشخیص طول زمینه

📌

دو تنظیم که راحت قاطی می‌شوند
context_length کل پنجرهٔ زمینه است — بودجهٔ ترکیبی توکن‌های ورودی و خروجی ‏(مثلاً ۲۰۰٬۰۰۰ برای Claude Opus 4.6). هرمس با این تصمیم می‌گیرد کی تاریخچه را فشرده کند و درخواست‌های API را اعتبارسنجی می‌کند.

model.max_tokens سقف خروجی است — بیشینهٔ توکن‌هایی که مدل در یک پاسخ می‌تواند تولید کند. هیچ ربطی به بلندای تاریخچهٔ گفتگویتان ندارد. نام استاندارد صنعتی max_tokens منبع رایج سردرگمی است؛ API ی بومی Anthropic بعداً برای شفافیت اسمش را به max_output_tokens تغییر داده.

context_length را وقتی ست کنید که تشخیص خودکار اندازهٔ پنجره را اشتباه گرفته.
model.max_tokens را فقط وقتی ست کنید که بخواهید بلندای پاسخ‌های تکی را محدود کنید.

هرمس برای تشخیص پنجرهٔ زمینهٔ صحیح مدل و ارائه‌دهندهٔ شما از زنجیرهٔ چندمنبعی استفاده می‌کند:

  1. بازنویسی پیکربندی — ‏model.context_length در config.yaml ‏(بالاترین اولویت)
  2. per-model ی ارائه‌دهندهٔ سفارشی — ‏providers.<name>.models.<id>.context_length
  3. کش دائمی — مقادیر کشف‌شدهٔ قبلی ‏(بین restart ها می‌ماند)
  4. نقطهٔ پایانی ‎/models‎ — کوئری API ی سرور شما ‏(نقاط پایانی محلی/سفارشی)
  5. Anthropic ‎/v1/models‎ — کوئری max_input_tokens از API ی Anthropic ‏(فقط کاربران کلید-API)
  6. API ی OpenRouter — متادیتای زندهٔ مدل از OpenRouter
  7. Nous Portal — تطبیق پسوندی شناسه‌های مدل Nous با متادیتای OpenRouter
  8. models.dev — رجیستری جامعه‌محور با طول زمینهٔ اختصاصی-ارائه‌دهنده برای بیش از ۳۸۰۰ مدل در بیش از ۱۰۰ ارائه‌دهنده
  9. پیش‌فرض‌های fallback — الگوهای گستردهٔ خانوادهٔ مدل ‏(پیش‌فرض 128K)

برای بیشتر راه‌اندازی‌ها این بدون دستکاری کار می‌کند. سیستم ارائه‌دهنده-آگاه است — همین مدل می‌تواند بسته به سرویس‌دهنده حدود زمینهٔ متفاوتی داشته باشد ‏(مثلاً claude-opus-4.6 روی Anthropic مستقیم 1M است ولی روی GitHub Copilot برابر 128K).

برای ست کردن صریح طول زمینه، context_length را به پیکربندی مدل اضافه کنید:

model:
  default: "qwen3.5:9b"
  base_url: "http://localhost:8080/v1"
  context_length: 131072  # tokens

برای نقاط پایانی سفارشی می‌توانید طول زمینه را per-model هم ست کنید:

providers:
  my-local-llm:
    api: "http://localhost:11434/v1"
    models:
      qwen3.5:27b:
        context_length: 64000
      deepseek-r1:70b:
        context_length: 65536

‏hermes model هنگام پیکربندی نقطهٔ پایانی سفارشی طول زمینه را می‌پرسد. برای تشخیص خودکار خالی بگذارید.

چه وقت دستی ست کنیم:

  • از Ollama با num_ctx ی سفارشی کمتر از بیشینهٔ مدل استفاده می‌کنید
  • می‌خواهید زمینه را زیر بیشینهٔ مدل محدود کنید ‏(مثلاً 8k روی مدلی با 128k برای صرفه‌جویی VRAM)
  • پشت پروکسی‌ای هستید که ‎/v1/models‎ را expose نمی‌کند

ارائه‌دهندگان سفارشی نام‌دار

اگر با چند نقطهٔ پایانی سفارشی کار می‌کنید ‏(مثلاً یک سرور dev محلی و یک سرور GPU راه‌دور)، می‌توانید آن‌ها را به‌عنوان ارائه‌دهندگان سفارشی نام‌دار زیر دیکشنری providers: در config.yaml تعریف کنید، با کلیدِ نام ارائه‌دهنده:

providers:
  local:
    api: http://localhost:8080/v1
    # api_key omitted — Hermes uses "no-key-required" for keyless local servers
  work:
    api: https://gpu-server.internal.corp/v1
    key_env: CORP_API_KEY
    transport: chat_completions   # set explicitly by `hermes model` → Custom Endpoint wizard; auto-detection still happens as a fallback
  anthropic-proxy:
    api: https://proxy.example.com/anthropic
    key_env: ANTHROPIC_PROXY_KEY
    transport: anthropic_messages  # for Anthropic-compatible proxies

هر مدخل این‌ها را قبول می‌کند: api ‏(URL پایهٔ نقطهٔ پایانی — ‏base_url/url به‌عنوان نام مستعار پذیرفته می‌شوند)، ‏name ‏(نام نمایشی اختیاری؛ پیش‌فرض کلید دیکشنری)، ‏key_env یا inline ی api_key یا key_cmd ‏(پایین را ببینید)، ‏transport ‏(chat_completions / anthropic_messages / codex_responses)، ‏default_model، ‏models، ‏context_length، ‏discover_models، ‏extra_body، ‏extra_headers، ‏ssl_ca_cert / ssl_verify و enabled: false برای مخفی کردن مدخل بدون حذفش.

credential های ضرب‌شده با فرمان ‏(key_cmd)

گیت‌وی‌های سازمانی اغلب به‌جای کلیدهای API ایستا، توکن‌های bearer کوتاه‌عمر صادر می‌کنند ‏(بروکرهای SSO/OIDC، ‏IAM ابری، پروکسی‌های احراز هویت داخلی)؛ پس توکنی که در .env کپی شده وسط نشست کهنه می‌شود و درخواست‌ها شروع به برگرداندن 401 می‌کنند. مقدار key_cmd نام فرمانی است که توکن را چاپ می‌کند؛ هرمس اجرایش می‌کند و نتیجه را تا کمی قبل از انقضا کش می‌کند، پس نشست‌های طولانی بدون ری‌استارت سرِ جایشان می‌مانند:

providers:
  my-gateway:
    base_url: "https://gateway.internal.example.com/v1"
    api_mode: chat_completions
    key_cmd: "my-auth-cli print-token --profile prod"

با هر کمکی که توکن چاپ کند کار می‌کند — ‏databricks auth token، ‏gcloud auth print-access-token، ‏az account get-access-token، ‏vault read یا اسکریپت‌های apiKeyHelper سبک Claude Code.

فرمان باید فقط توکن را روی stdout چاپ کند: یا لخت، یا به‌صورت JSON با فیلد access_token ‏(expires_in هم پذیرفته می‌شود؛ مهر زمانی ISO ی مطلق expiry/expiresOn هم). خروجی چندخطی به‌جای حدس زدن رد می‌شود. اگر انقصایی اعلام نشده باشد، توکن در یک بازهٔ محدود دوباره ضرب می‌شود.

اولویت: فلگ صریح ‎--api-key‎ همچنان برنده است؛ وگرنه key_cmd از api_key/key_env ایستا روی همان مدخل جلوتر است. credential ضرب‌شده هم برای نوبت اصلی عامل اعمال می‌شود هم برای کارهای کمکی ‏(تولید عنوان، فشرده‌سازی، بینایی، embedding).

با secrets.command اشتباه نشود، که یک کمکی را فقط یک بار هنگام شروع اجرا می‌کند تا متغیرهای محیطی فرایند را پر کند. از آن برای کمکی vault/keychain استفاده کنید که خیلی secret ها را برمی‌گرداند؛ از key_cmd وقتی credential یک ارائه‌دهنده باید وسط نشست دوباره ضرب شود.

📌

قالب قدیمی: پیکربندی‌های قدیمی‌تر از فهرست top-level ی custom_providers: استفاده می‌کردند. هنوز کار می‌کند — هرمس هر دو را می‌خواند — و hermes update خودکار آن را به دیکشنری providers: مهاجرت می‌دهد ‏(config نسخهٔ ۱۲). نام فیلدها در قالب دیکشنری کمی فرق دارد: مدلِ قدیمی model می‌شود default_model و api_mode ی قدیمی می‌شود transport.

بعضی نقاط پایانی سازگار-OpenAI به فیلدهای بدنهٔ درخواست اختصاصی-ارائه‌دهنده نیاز دارند. یک نگاشت extra_body به ارائه‌دهندهٔ سفارشی مربوطه اضافه کنید و هرمس آن را در هر درخواست chat-completions به آن نقطهٔ پایانی ادغام خواهد کرد:

providers:
  gemma-local:
    api: http://localhost:8080/v1
    default_model: google/gemma-4-31b-it
    extra_body:
      enable_thinking: true
      reasoning_effort: high

شکلی را استفاده کنید که سرورتان مستند کرده. مثلاً استقرارهای vLLM Gemma و بعضی نقاط پایانی NVIDIA NIM انتظار دارند enable_thinking زیر chat_template_kwargs بیاید نه به‌عنوان فیلد سطح-بالای extra_body:

extra_body:
  chat_template_kwargs:
    enable_thinking: true

برای مدل‌های reasoning ی Qwen که vLLM سرویس می‌دهد، همین شکل می‌تواند برای غیرفعال کردن تفکر استفاده شود وقتی پارسری همهٔ متن تولیدی را به فیلدهای reasoning منتقل و content ی دستیار را خالی گذاشته:

extra_body:
  chat_template_kwargs:
    enable_thinking: false

ویزارد hermes model ← Custom Endpoint حالا حالت API را صریحاً می‌پرسد و پاسخ شما را در config.yaml ذخیره می‌کند ‏(به‌صورت transport روی مدخل ارائه‌دهنده). تشخیص خودکار مبتنی بر URL ‏(مثلاً مسیرهای ‎/anthropic‎ ← anthropic_messages) وقتی فیلد خالی بماند همچنان به‌عنوان جایگزین اتفاق می‌افتد.

بینایی بومی برای مدل‌های ارائه‌دهندهٔ سفارشی. اگر نقطهٔ پایانی سفارشی تان مدلی با قابلیت بینایی سرویس می‌دهد که در models.dev نیست، model.supports_vision: true را ست کنید تا هرمس تصاویر پیوستی را به‌طور بومی مسیریابی کند ‏(به‌صورت بخش‌های image_url) به‌جای پیش‌پردازش از طریق vision_analyze. فقط همین یک کلید — نیازی به ست کردن agent.image_input_mode: native نیست.

model:
  provider: custom
  base_url: http://localhost:8080/v1
  default: qwen3.6-35b-a3b
  supports_vision: true   # send images natively; otherwise vision_analyze pre-describes them

همین کلید روی مدل‌های per-named-provider هم پذیرفته می‌شود ‏(providers.<name>.models.<id>.supports_vision) و مقادیر بولی استاندارد YAML را قبول می‌کند ‏(true/false/yes/no/on/off/1/0).

وسط نشست با نماد سه‌تایی بین‌شان سوئیچ کنید:

/model custom:local:qwen-2.5       # Use the "local" endpoint with qwen-2.5
/model custom:work:llama3-70b      # Use the "work" endpoint with llama3-70b
/model custom:anthropic-proxy:claude-sonnet-4  # Use the proxy

می‌توانید ارائه‌دهندگان سفارشی نام‌دار را از منوی تعاملی hermes model هم انتخاب کنید.

ارائه‌دهندگان ابری فهرست‌شده در سایر ارائه‌دهندگان سازگار همه گویش REST ی OpenAI را حرف می‌زنند، پس به همان شکل زیر دیکشنری providers: سیم‌کشی می‌شوند. سه دستور عملی در ادامه آمده. هر کدام داخل ~/.hermes/config.yaml می‌رود و کلید API ی مربوطه در ~/.hermes/.env.

Together AI

مدل‌های open-weight ‏(Llama، ‏MiniMax، ‏Gemma، ‏DeepSeek، ‏Qwen) را با قیمت‌هایی به‌طور چشمگیری زیر API‌های اول-طرف میزبانی می‌کند. پیش‌فرض خوب برای ناوگان‌های چند-مدلی.

# ~/.hermes/config.yaml
providers:
  together:
    api: https://api.together.xyz/v1
    key_env: TOGETHER_API_KEY
    # transport: chat_completions  # default — no need to set

model:
  default: MiniMaxAI/MiniMax-M2.7   # or any model from together.ai/models
  provider: custom:together
# ~/.hermes/.env
TOGETHER_API_KEY=your-together-key

سوییچ مدل وسط نشست:

/model custom:together:meta-llama/Llama-3.3-70B-Instruct-Turbo
/model custom:together:google/gemma-4-31b-it
/model custom:together:deepseek-ai/DeepSeek-V3

نقطهٔ پایانی ‎/v1/models‎ ی Together کار می‌کند، پس hermes model می‌تواند مدل‌های موجود را خودکار کشف کند.

Groq

استنتاج فوق‌سریع ‏(حدود ۵۰۰ توکن/ثانیه روی Llama-3.3-70B). کاتالوگ کوچک ولی برای استفادهٔ تعاملی حساس به تأخیر عالی است.

# ~/.hermes/config.yaml
providers:
  groq:
    api: https://api.groq.com/openai/v1
    key_env: GROQ_API_KEY

model:
  default: llama-3.3-70b-versatile
  provider: custom:groq
# ~/.hermes/.env
GROQ_API_KEY=your-groq-key

Perplexity

وقتی مدلی می‌خواهید که خودکار جستجوی وب زنده و ارجاع‌دهی انجام دهد کاربردی است. دربارهٔ اینکه کدام مدل‌ها موجودند سخت‌گیر است — فهرست فعلی را در perplexity.ai/settings/api چک کنید.

# ~/.hermes/config.yaml
providers:
  perplexity:
    api: https://api.perplexity.ai
    key_env: PERPLEXITY_API_KEY

model:
  default: sonar
  provider: custom:perplexity
# ~/.hermes/.env
PERPLEXITY_API_KEY=your-perplexity-key

چند ارائه‌دهنده در یک پیکربندی

سه دستور بالا ترکیب‌شدنی‌اند — همه را با هم استفاده کنید و per نوبت با ‎/model custom:<name>:<model> سوئیچ کنید:

providers:
  together:
    api: https://api.together.xyz/v1
    key_env: TOGETHER_API_KEY
  groq:
    api: https://api.groq.com/openai/v1
    key_env: GROQ_API_KEY
  perplexity:
    api: https://api.perplexity.ai
    key_env: PERPLEXITY_API_KEY

model:
  default: MiniMaxAI/MiniMax-M2.7
  provider: custom:together      # boot to Together; switch freely after
💡

  • ‏hermes doctor بعد از اصلاحات اعتبارسنج CLI در #15083 نباید برای هیچ‌کدام از این نام‌ها هشدار Unknown provider چاپ کند.
  • اگر نقطهٔ پایانی ‎/v1/models‎ ی ارائه‌دهنده‌ای در دسترس نباشد ‏(Perplexity رایج‌ترین است)، hermes model مدل را با یک هشدار ذخیره می‌کند نه رد قطعی — ببینید #15136.
  • برای رد شدن کامل از ارائه‌دهندگان نام‌دار و استفاده از provider: custom لخت با متغیر محیطی CUSTOM_BASE_URL ببینید #15103.

خودمیزبان کردن Firecrawl

به‌طور پیش‌فرض هرمس برای جستجو و استخراج وب از API ابری Firecrawl استفاده می‌کند. اگر ترجیح می‌دهید Firecrawl را محلی اجرا کنید، می‌توانید هرمس را به یک نمونهٔ خودمیزبان اشاره دهید. دستورالعمل کامل راه‌اندازی را در SELF_HOST.md ی Firecrawl ببینید.

چه چیزی به دست می‌آورید: بدون نیاز به کلید API، بدون محدودیت نرخ، بدون هزینهٔ per-page، حاکمیت کامل داده.

چه چیزی از دست می‌دهید: نسخهٔ ابری از موتور اختصاصی Fire-engine ی Firecrawl برای دور زدن پیشرفتهٔ ضدربات ‏(Cloudflare، ‏CAPTCHA، ‏چرخش IP) استفاده می‌کند. نسخهٔ خودمیزبان fetch ساده + Playwright دارد، پس بعضی سایت‌های محافظت‌شده ممکن است شکست بخورند. جستجو هم به‌جای Google از DuckDuckGo استفاده می‌کند.

راه‌اندازی:

  1. استک Docker ی Firecrawl را کلون و اجرا کنید ‏(۵ کانتینر: ‏API، ‏Playwright، ‏Redis، ‏RabbitMQ، ‏PostgreSQL — حدود ۴ تا ۸ گیگ رم لازم دارد): 
    git clone https://github.com/firecrawl/firecrawl
cd firecrawl
# In .env, set: USE_DB_AUTHENTICATION=false, HOST=0.0.0.0, PORT=3002
docker compose up -d
  2. هرمس را به نمونهٔ خودتان اشاره دهید ‏(بدون نیاز به کلید API): 
    hermes config set FIRECRAWL_API_URL http://localhost:3002

اگر نمونهٔ خودمیزبان تان احراز هویت فعال داشته باشد، می‌توانید هم FIRECRAWL_API_KEY هم FIRECRAWL_API_URL را ست کنید.

۱۱ مسیریابی ارائه‌دهنده در OpenRouter و ارائه‌دهندگان جایگزین

مسیریابی ارائه‌دهندهٔ OpenRouter

هنگام استفاده از OpenRouter می‌توانید کنترل کنید درخواست‌ها چطور بین ارائه‌دهندگان مسیریابی شوند. یک بخش provider_routing به ~/.hermes/config.yaml اضافه کنید:

provider_routing:
  sort: "throughput"          # "price" (default), "throughput", or "latency"
  # only: ["anthropic"]      # Only use these providers
  # ignore: ["deepinfra"]    # Skip these providers
  # order: ["anthropic", "google"]  # Try providers in this order
  # require_parameters: true  # Only use providers that support all request params
  # data_collection: "deny"   # Exclude providers that may store/train on data

میان‌برها: پسوند ‎:nitro‎ را به هر نام مدل بچسبانید برای مرتب‌سازی بر اساس throughput ‏(مثل anthropic/claude-sonnet-4:nitro) یا ‎:floor‎ برای مرتب‌سازی قیمتی.

OpenRouter Pareto Code Router

‏OpenRouter یک مسیریاب آزمایشی مدل‌های کدنویسی به نام openrouter/pareto-code دارد که درخواست‌ها را خودکار به ارزان‌ترین مدلی مسیریابی می‌کند که حد کیفیت کدنویسی را پاس کند ‏(رتبه‌بندی توسط Artificial Analysis). این مدل را بردارید و پیچ تنظیم min_coding_score را در ~/.hermes/config.yaml tune کنید:

model:
  provider: openrouter
  model: openrouter/pareto-code

openrouter:
  min_coding_score: 0.65   # 0.0–1.0; higher = stronger (more expensive) coders. Default 0.65.

نکته‌ها:

  • ‏min_coding_score فقط وقتی فرستاده می‌شود که model.model برابر openrouter/pareto-code باشد. روی هر مدل دیگر این مقدار no-op است.
  • آن را رشتهٔ خالی ست کنید ‏(یا خط را حذف کنید) تا OpenRouter قوی‌ترین کدر موجود را انتخاب کند — رفتار مستندشده وقتی بلوک plugins حذف شود همین است.
  • انتخاب در یک روز مشخص بر اساس امتیاز قطعی است، ولی مدل واقعی انتخاب‌شده می‌تواند با حرکت جبههٔ Pareto عوض شود ‏(مدل‌های جدید، به‌روزرسانی بنچمارک‌ها).
  • رفتار کامل مسیریاب را در مستندات Pareto Router ی OpenRouter ببینید.
  • برای استفاده از Pareto Code router برای یک کار کمکی مشخص ‏(فشرده‌سازی، بینایی و...) به‌جای عامل اصلی، مقدار extra_body.plugins را زیر همان کار ست کنید — بخش مسیریابی OpenRouter و Pareto Code برای کارهای کمکی را ببینید.

ارائه‌دهندگان جایگزین ‏(Fallback)

یک زنجیره از ارائه‌دهندگان پشتیبان پیکربندی کنید که هرمس به ترتیب امتحانشان می‌کند وقتی مدل اصلی شکست می‌خورد ‏(محدودیت نرخ، خطاهای سرور، شکست‌های احراز هویت). قالب متعارف فهرست top-level ی fallback_providers: است:

fallback_providers:
  - provider: openrouter
    model: anthropic/claude-sonnet-4
  - provider: anthropic
    model: claude-sonnet-4
    # base_url: http://localhost:8000/v1    # optional, for custom endpoints
    # api_mode: chat_completions           # optional override

قالب قدیمی تک‌جفتی fallback_model: هم برای سازگاری به‌عقب پذیرفته می‌شود:

fallback_model:
  provider: openrouter
  model: anthropic/claude-sonnet-4

وقتی فعال شود، fallback مدل و ارائه‌دهنده را وسط نشست عوض می‌کند بدون از دست رفتن گفتگوی شما. زنجیره مدخل‌به‌مدخل امتحان می‌شود؛ فعال‌سازی per نشست یک‌باره است.

💡

fallback منحصراً از طریق config.yaml پیکربندی می‌شود — یا به‌صورت تعاملی با hermes fallback. جزئیات کامل دربارهٔ اینکه کی فعال می‌شود، زنجیره چطور جلو می‌رود و چطور با کارهای کمکی و واگذاری تعامل دارد را در صفحهٔ ارائه‌دهندگان جایگزین ببینید.
